# 第2章：模块系统——CommonJS vs ESM 的前世今生

## 引言：从混沌到秩序

2009年之前的 JavaScript 世界，模块化是什么？不存在的。所有代码都在全局作用域里裸奔，变量名冲突就像交通事故一样频繁。想象一下，所有人都挤在一个没有隔断的大办公室里，你取了个变量名叫 `data`，隔壁工位的老王也叫 `data`——恭喜，程序爆炸了。

```html
<!-- 远古时代的"模块化" -->
<script src="jquery.js"></script>
<script src="utils.js"></script>       <!-- 依赖 jquery -->
<script src="component.js"></script>   <!-- 依赖 utils -->
<script src="app.js"></script>         <!-- 依赖 component -->
<!-- 顺序错了？全部崩溃！变量污染？自认倒霉！ -->
```

于是 JavaScript 社区开始了艰难的模块化探索之旅：

```
全局变量 → IIFE → AMD(RequireJS) → CommonJS(Node.js) → UMD → ES Module
   2005      2007      2009            2009          2011     2015
```

今天的 Node.js 世界有两大模块系统并存：**CommonJS（老大哥）** 和 **ES Module（新王者）**。理解它们的区别和共存方式，是每个 Node.js 开发者的必修课。

## 2.1 CommonJS：Node.js 的亲儿子

CommonJS 是 Node.js 诞生时就自带的模块系统。它的设计哲学很简单：**同步加载，因为服务器上文件都在本地磁盘，同步读取很快。**

### 基本语法

```javascript
// math.cjs（或 math.js，当 type 为 "commonjs" 时）

// 导出方式1：逐个挂载到 module.exports
module.exports.add = function(a, b) {
  return a + b;
};

module.exports.subtract = function(a, b) {
  return a - b;
};

// 导出方式2：直接替换 module.exports
module.exports = {
  add(a, b) { return a + b; },
  subtract(a, b) { return a - b; },
  PI: 3.14159
};

// 导出方式3：使用 exports 快捷方式
// exports 其实就是 module.exports 的引用
exports.multiply = function(a, b) {
  return a * b;
};
// ⚠️ 但是！不能直接赋值 exports = {...}
// 因为这会断开 exports 和 module.exports 的引用关系
```

```javascript
// app.cjs

// 导入整个模块
const math = require('./math.cjs');
console.log(math.add(1, 2)); // 3

// 解构导入
const { add, subtract } = require('./math.cjs');
console.log(add(1, 2)); // 3

// 导入 Node.js 内置模块
const fs = require('fs');
const path = require('path');

// 导入第三方包
const express = require('express');
```

### CommonJS 加载机制深度解析

当你写 `require('./module')` 时，Node.js 在背后做了什么？

```
require(X) 的解析算法：
│
├── X 是内置模块（fs, path, http...）?
│   └── 直接返回内置模块
│
├── X 以 '/', './', '../' 开头?（相对/绝对路径）
│   └── 按路径查找：
│       ├── 精确文件名匹配
│       ├── X.js
│       ├── X.json
│       ├── X.node（C++ addon）
│       └── X/index.js, X/index.json, X/index.node
│
└── X 不以路径开头?（包名）
    └── 从当前目录向上查找 node_modules：
        ├── ./node_modules/X
        ├── ../node_modules/X
        ├── ../../node_modules/X
        └── ... 直到文件系统根目录
```

### require 的缓存机制

```javascript
// counter.cjs
let count = 0;
module.exports = {
  increment() { return ++count; },
  getCount() { return count; }
};
```

```javascript
// app.cjs
const counter1 = require('./counter.cjs');
const counter2 = require('./counter.cjs');

counter1.increment();
counter1.increment();

console.log(counter2.getCount()); // 2！不是 0！
// 因为 require 有缓存，counter1 和 counter2 是同一个对象

// 查看缓存
console.log(require.cache);
// 清除缓存（一般不建议这么做）
delete require.cache[require.resolve('./counter.cjs')];
```

**重要发现**：`require` 是有缓存的！同一个模块只会被执行一次，后续的 `require` 直接返回缓存的 `module.exports` 对象。这就是为什么 Node.js 中的模块天然是"单例"的。

### exports vs module.exports 的经典陷阱

```javascript
// ❌ 错误写法
exports = {
  hello() { return 'world'; }
};
// 这不会生效！因为你只是让 exports 变量指向了新对象
// 但 require 返回的始终是 module.exports

// ✅ 正确写法
module.exports = {
  hello() { return 'world'; }
};

// 本质原因：
// Node.js 在加载模块前，实际上执行的是：
// var exports = module.exports = {};
// 你的代码...
// return module.exports;  ← require 返回这个
```

## 2.2 ES Module：JavaScript 的亲生标准

ES Module（ESM）是 ECMAScript 2015 (ES6) 引入的官方模块系统。与 CommonJS 是社区方案不同，ESM 是 JavaScript 语言规范的一部分。

### 基本语法

```javascript
// math.mjs

// 命名导出（Named Export）
export function add(a: number, b: number): number {
  return a + b;
}

export function subtract(a: number, b: number): number {
  return a - b;
}

export const PI = 3.14159;

// 默认导出（Default Export）
export default class Calculator {
  #history: string[] = [];

  calculate(expression: string): number {
    // ... 实现
    this.#history.push(expression);
    return eval(expression); // 仅示例，别在生产环境用 eval！
  }

  getHistory(): string[] {
    return [...this.#history];
  }
}
```

```javascript
// app.mjs

// 导入命名导出
import { add, subtract, PI } from './math.mjs';

// 导入默认导出
import Calculator from './math.mjs';

// 混合导入
import Calculator, { add, subtract } from './math.mjs';

// 重命名导入
import { add as sum, subtract as minus } from './math.mjs';

// 导入所有命名导出为命名空间对象
import * as math from './math.mjs';
console.log(math.add(1, 2));
console.log(math.PI);

// 动态导入（返回 Promise）
const { readFile } = await import('node:fs/promises');

// 导入 Node.js 内置模块（推荐加 node: 前缀）
import { readFileSync } from 'node:fs';
import { join, resolve } from 'node:path';
import { createServer } from 'node:http';
```

### 导出的各种姿势

```javascript
// styles.mjs

// 1. 声明时导出
export const PRIMARY_COLOR = '#007bff';
export function formatColor(hex) { /* ... */ }

// 2. 统一导出（列表导出）
const SECONDARY_COLOR = '#6c757d';
const DANGER_COLOR = '#dc3545';
function parseColor(str) { /* ... */ }

export { SECONDARY_COLOR, DANGER_COLOR, parseColor };

// 3. 重命名导出
export { parseColor as parse, DANGER_COLOR as RED };

// 4. 重新导出（桶文件/Barrel Export）
export { add, subtract } from './math.mjs';
export { default as Calculator } from './math.mjs';
export * from './utils.mjs';  // 导出 utils 的所有命名导出
export * as utils from './helpers.mjs';  // 作为命名空间重导出

// 5. 默认导出（每个模块只能有一个）
export default class Theme { /* ... */ }
```

### ESM 的静态结构

ESM 最重要的特性是**静态结构**——import/export 语句必须在模块顶层，不能放在 if/for/函数 里：

```javascript
// ❌ 错误：ESM 的 import 不能是动态的
if (condition) {
  import { something } from './module.mjs'; // SyntaxError!
}

// ✅ 正确：使用动态 import()
if (condition) {
  const { something } = await import('./module.mjs'); // OK!
}
```

为什么要这样设计？因为静态结构让工具（bundler）可以在编译时就分析出模块依赖关系，从而实现：

- **Tree Shaking**：删除未使用的导出（dead code elimination）
- **静态分析**：IDE 可以提供精确的自动补全
- **循环依赖检测**：编译时就能发现问题

## 2.3 CJS vs ESM 详细对比

| 特性 | CommonJS (CJS) | ES Module (ESM) |
| ------ | --------------- | ----------------- |
| 语法 | `require()` / `module.exports` | `import` / `export` |
| 加载时机 | 运行时（动态） | 编译时（静态）+ 动态 import() |
| 加载方式 | 同步 | 异步 |
| 顶层 this | `module.exports`（即 `{}`) | `undefined` |
| `__filename` | ✅ 可用 | ❌ 用 `import.meta.url` 替代 |
| `__dirname` | ✅ 可用 | ❌ 用 `import.meta.dirname` (Node 21+) |
| JSON 导入 | `require('./data.json')` 直接用 | 需要 import assertion |
| 条件导入 | `require` 可以放在 if 里 | 顶层 import 不行，动态 import() 可以 |
| 循环引用 | 返回已执行部分的快照 | 返回"活绑定"（live binding） |
| 文件扩展名 | 可省略 `.js` | 必须写完整扩展名 |
| 缓存 | `require.cache` 对象 | 内部缓存，无公开 API |
| 值的性质 | 导出值的**拷贝** | 导出值的**引用**（活绑定） |

### 活绑定 vs 值拷贝——最关键的区别

```javascript
// ===== CommonJS: 值拷贝 =====
// counter.cjs
let count = 0;
module.exports = {
  count,              // 导出的是此刻 count 的值（0）
  increment() { count++; }
};
```

```javascript
// app.cjs
const mod = require('./counter.cjs');
console.log(mod.count); // 0
mod.increment();
mod.increment();
console.log(mod.count); // 还是 0！因为导出的是值拷贝
```

```javascript
// ===== ES Module: 活绑定 =====
// counter.mjs
export let count = 0;
export function increment() { count++; }
```

```javascript
// app.mjs
import { count, increment } from './counter.mjs';
console.log(count); // 0
increment();
increment();
console.log(count); // 2！因为 import 得到的是活绑定/引用
```

这个区别非常重要！ESM 的"活绑定"意味着导入方总是能看到导出方的最新值。

### 循环引用的处理差异

```javascript
// ===== CommonJS 循环引用 =====
// a.cjs
console.log('a.cjs 开始加载');
const b = require('./b.cjs');
console.log('在 a.cjs 中，b.done =', b.done);
exports.done = true;
console.log('a.cjs 加载完毕');
```

```javascript
// b.cjs
console.log('b.cjs 开始加载');
const a = require('./a.cjs');
console.log('在 b.cjs 中，a.done =', a.done);
// ⚠️ 此时 a.cjs 还没执行完，a.done 是 undefined！
exports.done = true;
console.log('b.cjs 加载完毕');
```

```javascript
// main.cjs
require('./a.cjs');
// 输出：
// a.cjs 开始加载
// b.cjs 开始加载
// 在 b.cjs 中，a.done = undefined  ← 拿到不完整的导出！
// b.cjs 加载完毕
// 在 a.cjs 中，b.done = true
// a.cjs 加载完毕
```

```javascript
// ===== ESM 循环引用 =====
// a.mjs
console.log('a.mjs 开始');
import { bValue } from './b.mjs';
console.log('在 a.mjs 中，bValue =', bValue);
export const aValue = 'A';
```

```javascript
// b.mjs
console.log('b.mjs 开始');
import { aValue } from './a.mjs';
console.log('在 b.mjs 中，aValue =', aValue);
export const bValue = 'B';
```

ESM 处理循环引用时，会先完成模块图的构建（所有 import 声明都被"提升"），然后再执行。由于"活绑定"的特性，等模块执行完毕后，所有引用都能正确指向最终的值。但如果在模块执行时就访问尚未初始化的绑定，会得到 `ReferenceError`（而不是 `undefined`）。

## 2.4 package.json 的 "type" 字段

```json
{
  "type": "module"
}
```

这个小小的字段决定了整个项目中 `.js` 文件的解析方式：

| "type" 值 | .js 文件解析为 | 要用另一种格式时 |
| ----------- | -------------- | ---------------- |
| `"module"` | ESM | 使用 `.cjs` 后缀 |
| `"commonjs"` (默认) | CJS | 使用 `.mjs` 后缀 |
| 未设置 | CJS（默认） | 使用 `.mjs` 后缀 |

### 文件后缀策略

```
.js    → 根据最近的 package.json 的 "type" 字段决定
.mjs   → 永远是 ESM（无视 package.json）
.cjs   → 永远是 CJS（无视 package.json）
```

**最佳实践建议**：

- 新项目：设置 `"type": "module"`，使用 `.js` 写 ESM，偶尔需要 CJS 用 `.cjs`
- 老项目迁移：保持默认 CJS，新模块用 `.mjs`
- 发布 npm 包：同时提供 CJS 和 ESM（双模式包）

## 2.5 条件导出（Exports Map）与双模式包

### exports 字段：现代包的标配

```json
{
  "name": "my-awesome-lib",
  "version": "2.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.mjs"
    },
    "./utils": {
      "types": "./dist/utils.d.ts",
      "import": "./dist/utils.mjs",
      "require": "./dist/utils.cjs"
    },
    "./package.json": "./package.json"
  }
}
```

**条件解析顺序很重要**：Node.js 从上到下匹配第一个适用的条件。

常用条件：

- `"types"` → TypeScript 类型（永远放第一个）
- `"import"` → ESM 环境（import 语句或动态 import()）
- `"require"` → CJS 环境（require 调用）
- `"node"` → Node.js 环境
- `"browser"` → 浏览器环境（bundler 可能识别）
- `"default"` → 兜底

### 使用方式

```javascript
// 消费者使用：
import { something } from 'my-awesome-lib';        // 命中 "." → "import"
import { helper } from 'my-awesome-lib/utils';     // 命中 "./utils" → "import"

// 这个会失败（没在 exports 中声明）：
import { internal } from 'my-awesome-lib/src/internal.mjs'; // Error!
```

`exports` 字段不仅定义了入口，还**封装**了内部结构——消费者只能访问你声明的路径，内部文件被完全隐藏。这是信息隐藏的最佳实践。

### 构建一个双模式包的实际结构

```
my-lib/
├── src/
│   └── index.ts           # TypeScript 源码
├── dist/
│   ├── index.mjs          # ESM 构建产物
│   ├── index.cjs          # CJS 构建产物
│   └── index.d.ts         # 类型声明
├── package.json
└── tsconfig.json
```

## 2.6 模块解析算法深度解析

### ESM 的模块解析

ESM 的解析分为三个阶段：

```
1. 构造（Construction）
   - 下载/读取所有模块文件
   - 解析出 import/export 语句
   - 构建模块依赖图（Module Graph）
   - 此时代码尚未执行

2. 实例化（Instantiation）
   - 为每个模块创建环境记录
   - 为所有 export 分配内存空间（但还没有值）
   - 将 import 连接到对应的 export 内存位置（建立活绑定）

3. 求值（Evaluation）
   - 执行模块顶层代码
   - 填充 export 的实际值
   - 按依赖顺序执行（深度优先，后序遍历）
```

这就是为什么 ESM 的 import 会被"提升"——实际上不是提升，而是在构造阶段就建立了所有连接。

### ESM 中的 import.meta

```javascript
// ESM 特有的元信息对象
console.log(import.meta.url);      // 当前文件的 file:// URL
console.log(import.meta.dirname);  // 当前文件所在目录 (Node.js 21+)
console.log(import.meta.filename); // 当前文件路径 (Node.js 21+)
console.log(import.meta.resolve);  // 模块解析函数

// 替代 __filename 和 __dirname（Node.js 20 及之前）
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
```

### 在 ESM 中使用 require

从 Node.js 22 开始，ESM 中可以通过 `module.createRequire` 来使用 require：

```javascript
// 在 ESM 中需要用 require 加载 CJS 模块或 JSON
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);

// 现在可以用 require 了
const data = require('./config.json');
const legacyCjsModule = require('./old-module.cjs');
```

### JSON 导入

```javascript
// CJS：直接 require
const config = require('./config.json');

// ESM 方式 1：Import Attributes (Node.js 20.10+, 稳定)
import config from './config.json' with { type: 'json' };

// ESM 方式 2：fs 读取
import { readFileSync } from 'node:fs';
const config = JSON.parse(readFileSync('./config.json', 'utf-8'));

// ESM 方式 3：createRequire
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const config = require('./config.json');
```

## 2.7 实战：从 CJS 迁移到 ESM

假设你有一个 CJS 项目要迁移到 ESM，步骤如下：

```javascript
// ===== 迁移前 (CJS) =====

// config.js
const path = require('path');
const fs = require('fs');

const configPath = path.join(__dirname, 'config.json');
const config = JSON.parse(fs.readFileSync(configPath, 'utf-8'));

module.exports = config;
```

```javascript
// ===== 迁移后 (ESM) =====

// config.mjs (或 .js + "type": "module")
import { readFileSync } from 'node:fs';
import { join, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';

// __dirname 替代方案
const __dirname = dirname(fileURLToPath(import.meta.url));
// 或 Node.js 21+：直接用 import.meta.dirname

const configPath = join(__dirname, 'config.json');
const config = JSON.parse(readFileSync(configPath, 'utf-8'));

export default config;
```

### 迁移清单

```markdown
✅ 1. package.json 添加 "type": "module"
✅ 2. require() → import
✅ 3. module.exports → export / export default
✅ 4. __filename → import.meta.filename (或 fileURLToPath)
✅ 5. __dirname → import.meta.dirname (或 dirname(fileURLToPath(...)))
✅ 6. require.resolve() → import.meta.resolve()
✅ 7. JSON 导入方式修改
✅ 8. 动态 require → 动态 import()
✅ 9. 文件引用添加完整扩展名
✅ 10. 检查第三方依赖是否支持 ESM
```

## 2.8 常见坑点

### 坑1：ESM 中忘记写文件扩展名

```javascript
// ❌ CJS 思维习惯
import { helper } from './utils';  // Error!

// ✅ ESM 要求写完整
import { helper } from './utils.mjs';
import { helper } from './utils.js';
```

### 坑2：在 ESM 中使用 __dirname

```javascript
// ❌ ESM 中没有 __dirname
console.log(__dirname); // ReferenceError: __dirname is not defined

// ✅ Node.js 21+
console.log(import.meta.dirname);

// ✅ Node.js 20 及之前
import { dirname } from 'node:path';
import { fileURLToPath } from 'node:url';
const __dirname = dirname(fileURLToPath(import.meta.url));
```

### 坑3：CJS 模块不能 import ESM 模块（同步情况下）

```javascript
// ❌ 在 CJS 中不能 require 一个 ESM 模块
const esmModule = require('./esm-module.mjs'); // Error!

// ✅ 但可以用动态 import()（返回 Promise）
async function loadEsm() {
  const mod = await import('./esm-module.mjs');
  return mod;
}
// 注意：这在 CJS 中也是异步的

// ✅ ESM 可以 import CJS（反向可以）
import cjsModule from './cjs-module.cjs'; // OK
```

### 坑4：默认导出的解构陷阱

```javascript
// cjs-module.cjs
module.exports = {
  foo: 'bar',
  baz: 42
};
```

```javascript
// 在 ESM 中导入 CJS 模块
import cjsModule from './cjs-module.cjs';
// cjsModule = { foo: 'bar', baz: 42 }  ← 整个 module.exports 作为默认导出

// ❌ 可能不生效（取决于 Node.js 版本和具体情况）
import { foo, baz } from './cjs-module.cjs';

// ✅ 稳妥做法
import cjsModule from './cjs-module.cjs';
const { foo, baz } = cjsModule;
```

### 坑5：Top-level await 只在 ESM 中可用

```javascript
// ✅ ESM 中可以直接 await
const response = await fetch('https://api.example.com/data');
const data = await response.json();
export { data };

// ❌ CJS 中不行
const data = await fetch('...'); // SyntaxError!
```

## 2.9 本章小结

| 知识点 | 核心要点 |
| -------- | --------- |
| CommonJS | `require`/`module.exports`，同步加载，值拷贝 |
| ES Module | `import`/`export`，异步加载，活绑定，静态分析 |
| "type" 字段 | 决定 .js 文件的解析方式 |
| 文件后缀 | .mjs 永远是 ESM，.cjs 永远是 CJS |
| exports map | 现代包的条件导出标准 |
| 迁移建议 | 新项目用 ESM，老项目渐进迁移 |

**一句话总结**：ESM 是未来，CJS 是现实。新项目果断 ESM，老项目量力迁移，两者共存是当下的常态。
