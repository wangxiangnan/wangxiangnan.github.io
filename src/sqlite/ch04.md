# 第 4 章 SQL 基础（中）—— DML 增删改查

## 4.1 幽默开场：数据库的日常四件套

上一章你画好了户型图（表结构）。现在到了每天的日常：**买菜（INSERT）、翻冰箱（SELECT）、扔过期的东西（DELETE）、把牛奶从上层移到下层（UPDATE）**。

这四件事，程序员美其名曰 **CRUD**（Create / Read / Update / Delete），中文叫**增删改查**，江湖人称"码农四大件"。

任何面试问你"你会 SQL 吗"，本质上就是问"你熟不熟 CRUD"。所以这一章的东西你必须闭着眼都能写。

## 4.2 `INSERT` 完整用法

### 4.2.1 三种基本形式

**形式一：显式指定列名（推荐）**

```sql
INSERT INTO users (username, email, age)
VALUES ('alice', 'alice@example.com', 25);
```

**形式二：省略列名，按顺序传所有值（不推荐）**

```sql
INSERT INTO users VALUES (NULL, 'alice', 'alice@example.com', 25, ...);
```

坑：一旦你 ALTER TABLE 加了列，这条 SQL 就全废了。**新项目坚持写列名。**

**形式三：`DEFAULT VALUES`**

```sql
INSERT INTO users DEFAULT VALUES;
```

所有列都用默认值。你的表必须**所有列都有 DEFAULT** 或允许 NULL，否则报错。

### 4.2.2 批量插入的三种姿势

写"批量插入"这件事，SQLite 里有三种写法，性能天差地别。

**姿势 1：一条一条 INSERT（最慢）**

```sql
INSERT INTO users (username, email) VALUES ('a', 'a@x.com');
INSERT INTO users (username, email) VALUES ('b', 'b@x.com');
INSERT INTO users (username, email) VALUES ('c', 'c@x.com');
-- ...插入 1 万条 → 每条都是一次事务，一次 fsync → 慢到怀疑人生
```

在默认 journal 模式下，SQLite **每一条 INSERT 都会隐式起一个事务并 fsync 到磁盘**。你插入 1 万条 = 1 万次 fsync = 大概几十秒（机械盘更惨）。

**姿势 2：多行 VALUES（快很多）**

```sql
INSERT INTO users (username, email) VALUES
    ('a', 'a@x.com'),
    ('b', 'b@x.com'),
    ('c', 'c@x.com');
```

一条 SQL 插多行，性能爆炸提升。**限制**：SQLite 单条 SQL 最多 500 个组合（`SQLITE_MAX_COMPOUND_SELECT`，一般 500）；单条 SQL 最多约 1MB 长（可调 `SQLITE_MAX_SQL_LENGTH`）。

**姿势 3：手动包一个事务（最快）**

```sql
BEGIN;
INSERT INTO users (username, email) VALUES ('a', 'a@x.com');
INSERT INTO users (username, email) VALUES ('b', 'b@x.com');
-- ... 一万条 ...
COMMIT;
```

一个事务只 fsync 一次，1 万条插入从几十秒降到几十毫秒。**性能提升 100 倍不是段子，是实测。**

**大批量场景的组合拳（最优）**：**事务 + 多行 VALUES + 预编译语句**。

```sql
BEGIN;
INSERT INTO users (username, email) VALUES (?,?), (?,?), (?,?), ...;  -- 每批 100 行
INSERT INTO users (username, email) VALUES (?,?), (?,?), (?,?), ...;
...
COMMIT;
```

写 Flutter 代码就是这样：

```dart
Future<void> insertUsersBatch(List<Map<String, Object?>> rows) async {
  final db = await AppDb.instance;
  await db.transaction((txn) async {
    final batch = txn.batch();
    for (final row in rows) {
      batch.insert('users', row);
    }
    // noResult: true 避免收集每条 rowId，减少 IPC 开销
    await batch.commit(noResult: true);
  });
}
```

### 4.2.3 从 SELECT 插入

**"复制表数据"的经典写法**：

```sql
INSERT INTO users_archive (id, username, email)
SELECT id, username, email FROM users WHERE created_at < 1000000000;
```

或者建表并复制：

```sql
CREATE TABLE users_backup AS
SELECT * FROM users WHERE created_at < 1000000000;
-- 注意：这种方式不会复制约束、索引、外键、DEFAULT！
-- 只复制数据 + 列名 + 类型亲和性。
```

### 4.2.4 拿到刚插入的 id

```sql
INSERT INTO users (username, email) VALUES ('alice', 'a@x.com');
SELECT last_insert_rowid();
-- 返回刚插入的 rowid（如果主键是 INTEGER PRIMARY KEY，就是它）
```

Flutter 里更方便，`db.insert` 直接返回 rowid：

```dart
final id = await db.insert('users', {
  'username': 'alice',
  'email': 'a@x.com',
});
print('inserted id = $id');
```

### 4.2.5 `RETURNING` 子句（3.35+）

有了 `RETURNING`（借鉴 PostgreSQL），插入同时拿数据：

```sql
INSERT INTO users (username, email)
VALUES ('alice', 'a@x.com')
RETURNING id, username, created_at;
```

**同样支持 UPDATE / DELETE**：

```sql
DELETE FROM sessions WHERE expires < unixepoch()
RETURNING id, user_id;
```

sqflite 用 `rawQuery` 执行：

```dart
final rows = await db.rawQuery('''
  INSERT INTO users (username, email)
  VALUES (?, ?)
  RETURNING id, username, created_at;
''', ['alice', 'a@x.com']);

print(rows.first);   // {id: 1, username: alice, created_at: 1700000000}
```

## 4.3 UPSERT：`ON CONFLICT DO UPDATE`

**"存在就更新，不存在就插入"** —— 老程序员的痛。SQLite 3.24+ 加了 UPSERT 语法，源自 PostgreSQL。

### 4.3.1 语法

```sql
INSERT INTO users (id, username, email, updated_at)
VALUES (1, 'alice', 'alice@example.com', unixepoch())
ON CONFLICT (id) DO UPDATE SET
    username   = excluded.username,
    email      = excluded.email,
    updated_at = excluded.updated_at;
```

关键点：

- `ON CONFLICT (col)` 里的列必须是 UNIQUE / PRIMARY KEY 列。
- `excluded.xxx` 引用**本次想插入但因冲突被排除的值**。
- 你也可以在 UPDATE 里加 `WHERE`（条件式更新）。

### 4.3.2 `DO NOTHING`：静默跳过

```sql
INSERT INTO users (id, username, email)
VALUES (1, 'alice', 'a@x.com')
ON CONFLICT (id) DO NOTHING;
-- 如果 id 已存在，什么都不做，不报错
```

### 4.3.3 老写法：`INSERT OR REPLACE`

SQLite 更早还有一个"简化版 UPSERT"：

```sql
INSERT OR REPLACE INTO users (id, username, email)
VALUES (1, 'alice', 'a@x.com');
```

**行为**：如果发生冲突（PK / UNIQUE），**先 DELETE 旧行，再 INSERT 新行**。

**这有个大坑**：DELETE 会触发 `ON DELETE CASCADE`！比如你 REPLACE 一个用户，其所有 posts 都被级联删除，然后你插入了新的 user 但 posts 没了 —— 数据大爆炸。

**建议**：**用 `ON CONFLICT DO UPDATE`，别用 `INSERT OR REPLACE`**，除非你非常清楚级联影响。

### 4.3.4 `INSERT OR IGNORE`

```sql
INSERT OR IGNORE INTO users (id, username, email) VALUES (1, 'alice', 'a@x.com');
-- 冲突时静默跳过，不报错
```

等价于 `ON CONFLICT DO NOTHING`，写法更短。

## 4.4 `UPDATE` 与 `WHERE` 子句的重要性

### 4.4.1 基础用法

```sql
UPDATE users
SET email = 'new@example.com',
    updated_at = unixepoch()
WHERE id = 1;
```

### 4.4.2 危险案例："不写 WHERE 的 UPDATE"

```sql
UPDATE users SET email = 'oops@example.com';
```

**祝贺你，你已经把全公司用户的邮箱都改成 <oops@example.com>。**

这是 SQL 界的经典事故，江湖上人称"**删库到跑路**"的近亲："**改库到失业**"。

**防范手段**：

1. **写 UPDATE 之前先写 SELECT 验证 WHERE**：

   ```sql
   SELECT id, email FROM users WHERE id = 1;   -- 先看
   UPDATE users SET email = ... WHERE id = 1;   -- 再改
   ```

2. **CLI 里开启 `.headers on` 和 `.timer on`**，能看到"1 row updated"就放心，"1000000 rows updated"就赶紧回滚。
3. **生产环境永远开事务**：

   ```sql
   BEGIN;
   UPDATE ...;
   SELECT ...;  -- 检查
   COMMIT;      -- 或 ROLLBACK;
   ```

### 4.4.3 用 FROM 子句多表更新（3.33+）

```sql
UPDATE posts
SET view_count = view_count + 1
FROM daily_stats
WHERE posts.id = daily_stats.post_id
  AND daily_stats.date = '2024-01-15';
```

这是 3.33 引入的语法，之前要用相关子查询绕。

### 4.4.4 `RETURNING` 也能用

```sql
UPDATE users SET email = 'x@y.com' WHERE id = 1
RETURNING id, email, updated_at;
```

## 4.5 `DELETE` 与 SQLite 没有 TRUNCATE

### 4.5.1 基础

```sql
DELETE FROM users WHERE id = 1;
DELETE FROM users WHERE created_at < 1000000000;
DELETE FROM users;   -- ⚠ 删除全部数据（但保留表结构）！
```

**没写 WHERE 就是全删！** 请务必确认。

### 4.5.2 SQLite 有 TRUNCATE 吗？没有

MySQL / PostgreSQL 有 `TRUNCATE TABLE`：一次性快速清空整张表（不逐行删除、重置自增 id）。

SQLite **没有 TRUNCATE**。但它有个"隐藏优化"：

> **当你执行 `DELETE FROM t;`（无 WHERE、无触发器）时，SQLite 会启用 "TRUNCATE OPTIMIZATION"，直接清空 B-Tree 页，不逐行删除。**

也就是说，你写 `DELETE FROM users;` 其实内部就是 TRUNCATE 级别的性能。**除非**：

- 有 `WHERE` 子句。
- 表上有 `DELETE` 触发器。
- 表有外键引用其他表（需要级联删除）。

**重置自增 id**（AUTOINCREMENT 场景）：

```sql
DELETE FROM users;
DELETE FROM sqlite_sequence WHERE name = 'users';
-- 下次插入 id 从 1 开始
```

### 4.5.3 软删除 vs 硬删除

现代 App 一般不物理删除，而是加个 `deleted_at`：

```sql
UPDATE users SET deleted_at = unixepoch() WHERE id = 1;

-- 查询时过滤
SELECT * FROM users WHERE deleted_at IS NULL;
```

好处：可撤销、可审计。坏处：查询要多写条件，数据量长期增大。**看业务需求。**

## 4.6 `SELECT` 基础：投影 / 过滤 / 排序 / 分页

SQL 最核心的语句：

```sql
SELECT [DISTINCT] column1, column2, ...   -- 投影
FROM table_name
WHERE condition                           -- 过滤
ORDER BY column ASC|DESC                  -- 排序
LIMIT n OFFSET m;                         -- 分页
```

### 4.6.1 投影

**全部列**：

```sql
SELECT * FROM users;
```

**只查需要的列**（生产环境永远这样）：

```sql
SELECT id, username, email FROM users;
```

**为什么不 `SELECT *`？**

- 网络 / IPC 传输开销（sqflite 会把结果打包传给 Dart 端）。
- 表结构变化会影响你的代码假设。
- 无法使用覆盖索引（后续章节详解）。

**列别名**：

```sql
SELECT
    id AS user_id,
    username AS name,
    unixepoch() - created_at AS age_seconds
FROM users;
```

**`DISTINCT` 去重**：

```sql
SELECT DISTINCT country FROM users;
```

**注意 DISTINCT 会引起排序/哈希，大数据集慢**，能不用就不用。

### 4.6.2 过滤（WHERE）

**运算符**：

```sql
=  !=  <>  <  <=  >  >=
```

**逻辑组合**：

```sql
SELECT * FROM users
WHERE age >= 18 AND (country = 'CN' OR country = 'US');
```

**NULL 处理**：

```sql
-- ⚠ 这两种都是错的！
SELECT * FROM users WHERE deleted_at = NULL;      -- 永远返回空
SELECT * FROM users WHERE deleted_at != NULL;     -- 永远返回空

-- ✅ 正确写法
SELECT * FROM users WHERE deleted_at IS NULL;
SELECT * FROM users WHERE deleted_at IS NOT NULL;
```

**为什么？** 因为 SQL 里 `NULL = NULL` 返回的不是真也不是假，而是 **NULL（未知）**，永远不会通过 WHERE。这是 SQL 的三值逻辑（True / False / Null），初学者最大的坑之一。

**`BETWEEN` / `IN`**：

```sql
SELECT * FROM users WHERE age BETWEEN 18 AND 30;
SELECT * FROM users WHERE country IN ('CN', 'US', 'JP');
```

`BETWEEN` 是**闭区间**：包含 18 和 30。

### 4.6.3 排序（ORDER BY）

```sql
SELECT * FROM users ORDER BY age DESC, username ASC;
```

- 默认 `ASC`（升序）。
- 多字段：先按第一个，再按第二个 ……
- **NULL 排在哪？** SQLite 默认 NULL 在 ASC 时最前、DESC 时最后。用 `NULLS FIRST / NULLS LAST` 显式指定（3.30+）。

**性能提示**：ORDER BY 的字段若有索引，可以直接走索引顺序（Index Scan）；否则要 sort（排序缓冲，慢）。

### 4.6.4 分页（LIMIT / OFFSET）

```sql
-- 第一页（10 条）
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10;

-- 第二页
SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 10;

-- 第 N 页（每页 20 条）
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET (N-1)*20;

-- 语法糖：LIMIT 10, 20 相当于 LIMIT 20 OFFSET 10（注意 MySQL 语义相反！）
```

## 4.7 LIMIT / OFFSET 的性能陷阱：大偏移量问题

**看着人畜无害的 OFFSET，其实是分页界的大杀器。**

```sql
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

你以为它跳过了 10 万条直接取 20 条？**不。SQLite 会一条一条数过 10 万行才丢弃它们，然后取 20 条。** OFFSET 越大越慢。

**这不是 SQLite 的锅，是 SQL OFFSET 语义的通病**（MySQL / PostgreSQL 都一样）。

### 4.7.1 解决方案：Keyset Pagination（游标分页）

不用 OFFSET，用**上一页最后一条的排序字段**做游标：

```sql
-- 第一页
SELECT * FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 记住最后一条的 (created_at, id)，作为下一页参数
-- 第 N+1 页：
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- **无论第几页，都只扫描 20 行**，性能恒定。
- 前提是排序字段（组合）能保证唯一，通常带上主键 id。
- 缺点：**不能跳页**（只能"下一页 / 上一页"），适合无限滚动 UI（比如朋友圈 / 微博）。

## 4.8 LIKE 与 GLOB 模式匹配

### 4.8.1 LIKE

```sql
-- 以 'a' 开头
SELECT * FROM users WHERE username LIKE 'a%';

-- 包含 'lice'
SELECT * FROM users WHERE username LIKE '%lice%';

-- 第二个字符是 l
SELECT * FROM users WHERE username LIKE '_l%';
```

- `%` 匹配任意长度（包括 0）。
- `_` 匹配单个字符。
- **默认大小写不敏感**（ASCII 范围，且要求 SQLite 编译时开了默认）。
- 想大小写敏感：`PRAGMA case_sensitive_like = ON;`

### 4.8.2 GLOB（Unix 风格）

```sql
SELECT * FROM files WHERE name GLOB '*.jpg';
SELECT * FROM files WHERE name GLOB '[abc]*';   -- 以 a、b、c 之一开头
SELECT * FROM files WHERE name GLOB '[!0-9]*';  -- 不以数字开头
```

- `*` 匹配任意长度。
- `?` 匹配单个字符。
- `[]` 字符集。
- **大小写敏感**（跟 LIKE 相反）。

**性能提示**：`LIKE 'abc%'`（前缀匹配）可以用索引；`LIKE '%abc'`（后缀）或 `LIKE '%abc%'`（包含）**用不了索引**，全表扫描。想全文搜索请用 **FTS5**（Part 3 详解）。

### 4.8.3 REGEXP（默认不带）

SQL 有 `REGEXP` 运算符，但**SQLite 默认不实现**！你需要加载扩展或自定义函数才能用。sqflite 默认没带正则扩展。

## 4.9 参数化查询与 SQL 注入防范

**"我永远不会中 SQL 注入"** —— 每个中 SQL 注入之前的程序员都这么说过。

### 4.9.1 危险写法（永远别这么写）

```dart
// ❌ 危险！字符串拼接
final username = 'alice';
final rows = await db.rawQuery(
  "SELECT * FROM users WHERE username = '$username'"
);
```

如果 `username = "alice' OR '1'='1"`，你的 SQL 就变成：

```sql
SELECT * FROM users WHERE username = 'alice' OR '1'='1';
-- 返回所有用户
```

更严重的：

```
username = "alice'; DROP TABLE users; --"
```

**祝你好运。**

### 4.9.2 正确写法：参数占位符

**位置占位符 `?`**：

```dart
final rows = await db.rawQuery(
  'SELECT * FROM users WHERE username = ? AND age >= ?',
  ['alice', 18],
);
```

**命名占位符 `:name`**（sqflite 有些场景支持，通用可用位置符）：

```sql
SELECT * FROM users WHERE username = :name AND age >= :min_age
```

sqflite 里最常用的还是 `?`，各语言绑定都支持。

### 4.9.3 底层原理

**参数化查询 = 预编译语句（Prepared Statement）**：

1. SQL 模板发给 SQLite → 编译成字节码（VDBE program）。
2. 参数**单独**通过 `sqlite3_bind_*()` API 传入。
3. 参数**不会**被拼进 SQL，永远被当作**数据**处理。

哪怕参数里包含 `'; DROP TABLE users; --`，它也只是一个字符串值，不会被解析为 SQL。

**额外好处**：多次执行相同结构 SQL 时，可以复用预编译结果，性能更好。

### 4.9.4 sqflite 的高层 API 也是参数化

```dart
await db.insert('users', {'name': userInput});   // 内部走参数化，安全
await db.update('users', {...}, where: 'id = ?', whereArgs: [id]);
await db.delete('users', where: 'id = ?', whereArgs: [id]);
await db.query('users', where: 'name LIKE ?', whereArgs: ['%$q%']);
```

**注意最后一条**：LIKE 里的 `%` 是模式的一部分，可以在 Dart 端拼接（因为它不参与 SQL 结构），但**用户输入的 `q` 里如果有 `%` 或 `_`，会被当通配符**。想要精确搜索需要用 `ESCAPE`：

```dart
final safe = q.replaceAll('!', '!!').replaceAll('%', '!%').replaceAll('_', '!_');
await db.query('users',
    where: "name LIKE ? ESCAPE '!'",
    whereArgs: ['%$safe%']);
```

## 4.10 Flutter 实战：完整的 CRUD 封装

我们把用户和文章的 CRUD 都写一遍。

### 4.10.1 User 数据模型

```dart
// lib/models/user.dart
class User {
  final int? id;
  final String username;
  final String email;
  final String? avatarUrl;
  final String? bio;
  final int createdAt;
  final int updatedAt;

  User({
    this.id,
    required this.username,
    required this.email,
    this.avatarUrl,
    this.bio,
    required this.createdAt,
    required this.updatedAt,
  });

  Map<String, Object?> toMap() => {
        if (id != null) 'id': id,
        'username': username,
        'email': email,
        'avatar_url': avatarUrl,
        'bio': bio,
        'created_at': createdAt,
        'updated_at': updatedAt,
      };

  factory User.fromMap(Map<String, Object?> m) => User(
        id: m['id'] as int?,
        username: m['username'] as String,
        email: m['email'] as String,
        avatarUrl: m['avatar_url'] as String?,
        bio: m['bio'] as String?,
        createdAt: m['created_at'] as int,
        updatedAt: m['updated_at'] as int,
      );
}
```

### 4.10.2 UserRepository

```dart
// lib/repos/user_repo.dart
import 'package:sqflite/sqflite.dart';
import '../db.dart';
import '../models/user.dart';

class UserRepo {
  Future<Database> get _db async => AppDb.instance;

  int _now() => DateTime.now().millisecondsSinceEpoch ~/ 1000;

  // ===== CREATE =====
  Future<int> insert(User u) async {
    final db = await _db;
    final now = _now();
    return db.insert(
      'users',
      {
        'username': u.username,
        'email': u.email,
        'avatar_url': u.avatarUrl,
        'bio': u.bio,
        'created_at': now,
        'updated_at': now,
      },
      conflictAlgorithm: ConflictAlgorithm.abort,
    );
  }

  // ===== UPSERT =====
  Future<void> upsertByUsername(User u) async {
    final db = await _db;
    await db.rawInsert('''
      INSERT INTO users (username, email, avatar_url, bio, created_at, updated_at)
      VALUES (?, ?, ?, ?, ?, ?)
      ON CONFLICT(username) DO UPDATE SET
        email      = excluded.email,
        avatar_url = excluded.avatar_url,
        bio        = excluded.bio,
        updated_at = excluded.updated_at
    ''', [
      u.username, u.email, u.avatarUrl, u.bio,
      _now(), _now(),
    ]);
  }

  // ===== READ =====
  Future<User?> findById(int id) async {
    final db = await _db;
    final rows = await db.query(
      'users',
      where: 'id = ?',
      whereArgs: [id],
      limit: 1,
    );
    if (rows.isEmpty) return null;
    return User.fromMap(rows.first);
  }

  Future<User?> findByUsername(String username) async {
    final db = await _db;
    final rows = await db.query(
      'users',
      where: 'username = ? COLLATE NOCASE',
      whereArgs: [username],
      limit: 1,
    );
    if (rows.isEmpty) return null;
    return User.fromMap(rows.first);
  }

  Future<List<User>> search(String keyword, {int limit = 20}) async {
    final db = await _db;
    final safe = keyword
        .replaceAll('!', '!!')
        .replaceAll('%', '!%')
        .replaceAll('_', '!_');
    final rows = await db.query(
      'users',
      where: "username LIKE ? ESCAPE '!'",
      whereArgs: ['%$safe%'],
      orderBy: 'username COLLATE NOCASE',
      limit: limit,
    );
    return rows.map(User.fromMap).toList();
  }

  Future<List<User>> page({int page = 1, int size = 20}) async {
    final db = await _db;
    final rows = await db.query(
      'users',
      orderBy: 'created_at DESC, id DESC',
      limit: size,
      offset: (page - 1) * size,
    );
    return rows.map(User.fromMap).toList();
  }

  // ===== UPDATE =====
  Future<int> updateBio(int id, String? bio) async {
    final db = await _db;
    return db.update(
      'users',
      {'bio': bio, 'updated_at': _now()},
      where: 'id = ?',
      whereArgs: [id],
    );
  }

  // ===== DELETE =====
  Future<int> deleteById(int id) async {
    final db = await _db;
    return db.delete(
      'users',
      where: 'id = ?',
      whereArgs: [id],
    );
  }
}
```

**看几个细节**：

- 所有 WHERE 都用 `?` + `whereArgs`，参数化，安全。
- `insert / update / delete` 返回受影响行数或 rowid。
- `conflictAlgorithm` 可选 `abort` / `ignore` / `replace` / `fail` / `rollback`，对应 SQL 的 `INSERT OR ...` 语法。**推荐 abort（默认），显式冲突时才用 replace/ignore**。
- 中文/大小写不敏感搜索用 `COLLATE NOCASE`（限 ASCII）。

## 4.11 原理深挖：INSERT 一条数据发生了什么

以 WAL 模式为例（Part 2 详解），一次 `INSERT` 大致流程：

1. **SQL 解析** → 生成 AST。
2. **代码生成** → 生成 VDBE 字节码。
3. **执行**：
   - 开事务（若尚未开启）。
   - 校验约束（NOT NULL / UNIQUE / CHECK / FK）。
   - 在 B-Tree 中定位插入位置（按 rowid 或 PK）。
   - 写入内存中的 page cache。
   - 追加日志到 WAL 文件。
4. **COMMIT**：
   - `fsync(WAL 文件)` 保证日志落盘。
   - 更新 `wal-index` 指针。
5. **异步 checkpoint**：把 WAL 内容合并回主 DB 文件。

**关键点**：**fsync 是慢操作**（机械盘 ~10ms，SSD ~0.1ms）。所以"一条 INSERT 一次事务"意味着每条都 fsync 一次，累积起来非常慢。**大批量插入务必用事务合并 fsync。**

## 4.12 常见坑点

1. **`WHERE col = NULL` 不工作**：用 `IS NULL`。
2. **忘写 WHERE 的 UPDATE / DELETE**：可能导致全表被改/删。
3. **`SELECT *` 遇上表结构变化**：代码可能错位。
4. **大 OFFSET 分页性能爆炸**：改 Keyset。
5. **`INSERT OR REPLACE` 触发级联删除**：慎用。
6. **LIKE 通配符注入**：用户输入的 `%_` 会被当模式，需要 escape。
7. **字符串拼接 SQL**：SQL 注入门口大开，永远参数化。
8. **批量插入不开事务**：性能恶劣。
9. **`sqlite_sequence` 不重置**：清空表后 AUTOINCREMENT 会从最大值继续。
10. **`typeof(NULL) = 'null'`**：NULL 是一等公民，判断类型用 `typeof()`。

## 4.13 本章小结

- INSERT 三种形式：显式列 / 全列 / DEFAULT VALUES；**推荐显式列**。
- 批量插入：**事务 + 多行 VALUES**，性能提升 100x。
- UPSERT：`ON CONFLICT (col) DO UPDATE SET ...`，避免 `INSERT OR REPLACE` 的级联坑。
- UPDATE / DELETE **永远先写 WHERE 再执行**。
- SQLite 没有 TRUNCATE，但 `DELETE FROM t;` 有 TRUNCATE 优化。
- 分页大 OFFSET 慢，用 **Keyset Pagination**。
- LIKE 前缀能走索引，任意匹配全表扫；正则 SQLite 默认不支持。
- **永远参数化查询**，never 拼字符串。
- Flutter 用 sqflite 的 `db.insert/update/delete/query` 高层 API 或 `rawXxx`。
