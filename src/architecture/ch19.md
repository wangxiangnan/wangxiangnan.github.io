# 第19章：从单体到微服务的演进

> [!TIP] Part 4: 架构演进与治理（进阶实战篇）
> 架构不是画完图就结束了——它要随业务一起生长、被度量、被治理。本章是进阶实战的开篇，回答一个几乎每个团队都会遇到的问题：单体到底该不该拆、按什么顺序拆、拆错了怎么退回来。

前 18 章我们讲了概念、风格和横切专题，这一章把它们串成一条实战路线。先把一个观念掰正：微服务不是"升级"，而是一次代价高昂的组织手术——它把一个编译期就能发现的问题，变成三个运行时才暴露的问题。所以正确的问题从来不是"要不要上微服务"，而是"什么信号出现了才拆、按什么顺序拆、每一步如何回退"。

我们继续用贯穿全书的例子——云书店（卖书的电商平台，起步期日订单 1 千、成长期 5 万、成熟期 50 万），把它从单体一路演进到云原生，每一步都给出触发信号、动作、收益与代价。

## 19.1 该不该拆：四个判断信号

"我们什么时候该上微服务？"——这是架构师被问得最多的问题。答案不看公司融了几轮资，而是看下面四个信号是否亮灯：

| 信号 | 绿灯（继续单体） | 黄灯（警惕） | 红灯（该拆了） |
| ---- | ---- | ---- | ---- |
| 部署时间 | 全量构建+部署 < 15 分钟 | 30-60 分钟，开始有人绕过测试 | 2 小时以上，发布像开盲盒 |
| 变更半径 | 改一个功能只碰 1-2 个模块 | 改 A 功能要回归测试 B 和 C | 改促销逻辑弄崩了物流 |
| 团队人数 | < 10 人，一张桌子坐得下 | 20-50 人，代码评审开始排队 | > 50 人，多个团队挤同一个仓库 |
| 模块耦合度 | 模块间只通过接口调用 | 出现跨模块直接读对方数据表 | 循环依赖，谁都不敢先动 |

这四个信号其实说的是同一件事：**协作成本超过了生产效率**。部署慢、变更半径大、人多踩脚、耦合深——本质都是所有团队共用一个部署单元和一个代码库，任何变更都要全队协调。

四个信号里，"变更半径"最值得量化，因为它最容易被数据戳穿：随机抽最近 30 次合并记录，数一数每次需求平均触碰的模块数；再问每个被触碰模块的负责人"这次变更需要你评审吗"。如果"要"的答案超过三个，说明团队实际在为一个虚拟大单体付出协调成本。

给团队做季度自检时，可以直接用这份十项清单打勾：

1. 全量构建加部署，能否在 15 分钟内完成？
2. 最近一个月，有没有"改 A 崩 B"的事故？
3. 代码评审的平均等待时间是否超过一天？
4. 有没有两个以上团队在改同一个模块？
5. 是否存在跨模块直读对方数据库表的情况？
6. 新人能在一周内独立完成一个端到端的小需求吗？
7. 有没有没人敢动、只能绕着走的"坟墓模块"？
8. 测试环境联调，是否要排队等别人先部署？
9. 线上问题定位，平均要跨几个团队的群？
10. 如果明天要把某个功能下线，需要协调多少人？

> [!NOTE] 反过来想
> 如果四个信号全是绿灯，拆微服务只会让你变慢。云书店起步期日订单 1 千、团队 8 个人，单体半小时就能发布一次——这个阶段拆服务纯属给自己找事。把这张清单做成模板，每季度对着打勾一次，比任何"技术先进性"讨论都更能帮你判断拆分时机。

## 19.2 绞杀者模式与防腐层

决定要拆之后，下一个问题是怎么拆。直接推倒重写（Big Bang Rewrite）是业界公认的高危操作：旧系统一边继续接需求，新系统一边追功能，追两年追不上，最后上线一个功能更少的系统。

正确姿势是**绞杀者模式（Strangler Fig Pattern）**，名字来自热带的绞杀榕：种子落在老树上，慢慢长出气根，若干年后新树独立成林，老树枯萎退场。落到工程上分四步：

1. 在旧单体前面加一层路由（网关或反向代理）；
2. 新功能直接写成新服务，路由把对应的 URL 指过去；
3. 旧功能按模块逐个搬出，搬完一个，路由切一个；
4. 单体上的功能搬空后，择机下线。

```text
        前端/APP 的所有请求
              │
              ▼
      ┌─────────────────┐
      │    路由/网关层    │   ← 新增的"绞杀者门面"，只做转发
      └──┬───────────┬──┘
   /books/*       /checkout/*
         │            │
         ▼            ▼
  ┌────────────┐  ┌──────────────────┐
  │ 新书籍服务   │  │   旧单体（遗留）    │
  │ 独立代码库   │  │ 还没搬走的功能照旧  │
  └────────────┘  └──────────────────┘
         ▲                │
         └── 每周搬走一个模块，路由随之切换
```

绞杀过程从头到尾系统都是可用的：任何时刻都有两个能工作的部署单元，搬错了随时把路由切回去。这与"停机三个月重写"是两种命运。

拆分路上的第二个必备工具是**防腐层（Anti-Corruption Layer, ACL）**。旧单体对外吐出的数据结构，往往带着多年的历史包袱——魔法数字、冗余字段、拼音缩写。如果让新服务直接消费这些结构，旧系统的"腐败"会顺着接口传染进来。防腐层的职责只有一个：**在边界上做一次翻译，让旧的脏结构出不了新服务的门**。

```typescript
// 旧单体返回的"用户快照"：历史悠久，字段没人敢动
interface LegacyUserResponse {
  uid: number;          // 用户 ID
  uname: string;        // 昵称
  lv: number;           // 会员等级（新服务根本用不到）
  status_flag: number;  // 0/1/2 的魔法数字，含义靠口口相传
  ext_json: string;     // 一段 JSON 字符串，天知道里面是什么
}

// 新订单服务内部的干净模型
interface UserProfile {
  userId: string;
  nickname: string;
  active: boolean;
}

// 防腐层：翻译只发生在这里，旧结构不许越过这一行
export function fromLegacy(raw: LegacyUserResponse): UserProfile {
  return {
    userId: String(raw.uid),
    nickname: raw.uname,
    active: raw.status_flag === 1, // 1=正常，其余一律按注销处理
  };
}
```

执行规则很简单：新服务代码里出现 `LegacyUserResponse` 的地方只允许有这一个文件。防腐层多花的一天，能替你省掉之后每个月的"兼容性大扫除"。

## 19.3 拆分的推荐顺序：先边缘后核心，先无状态后数据

模块搬家跟搬家一样讲究顺序：先搬不怕摔的，最后搬易碎品。推荐顺序由易到难分四档：

| 顺序 | 拆什么 | 为什么先拆它 | 云书店的例子 |
| ---- | ---- | ---- | ---- |
| 1 | 边缘功能 | 独立性强、接口少、失败影响小 | 评价、消息通知、文件服务 |
| 2 | 无状态服务 | 不带数据，拆完只需路由切换 | 商品搜索、推荐、图片处理 |
| 3 | 核心业务流 | 收益最大，但要配消息队列与一致性方案 | 订单、支付、库存 |
| 4 | 数据层拆分 | 风险最高，放在功能拆稳之后 | 共库拆私库、分库分表 |

两个"先"背后的原理：

- **先边缘后核心**：边缘功能（评价、通知）就算拆挂了，主交易链路照样转。拿它们练手，团队顺便把服务化流水线（CI/CD、监控、日志）趟熟，再去动核心。
- **先无状态后数据**：无状态服务拆错了一版，改配置回滚就行；数据库一旦拆错，回滚成本是以"天"为单位计算的。

顺带说一个经典反例：**按技术层拆**。有的团队把所有接口定义拆成"接口服务"、所有数据访问拆成"数据服务"、所有定时任务拆成"任务服务"——每个服务看起来都很"整"，但任何一条业务变更都要横穿三个服务。技术分层是单体内部的组织方式，一旦变成服务边界，就等于把分层的缺点从性能层面放大到了组织层面：每一次需求都是一次跨团队协作。

## 19.4 数据拆分：从共库到私库的过渡

功能拆出去了，数据库还连着同一个 MySQL——这是演进中最常见的"半拆状态"，也是最危险的状态：服务是独立的，数据是耦合的，一个慢查询能把三个服务一起拖死。推荐分四步过渡：

```text
第 1 步  共库 + 逻辑隔离
         所有模块还在同一个 MySQL，但各自用独立 Schema 和数据库账号
         order_svc 账号只有 shop_order.* 的权限，想跨库 JOIN？授权都不给
              │
第 2 步  共库 + 接口化访问
         禁止跨 Schema 直连，库存数据只能调 inventory-service 的 API
         这个阶段把所有 JOIN 改造成接口调用，顺便摸清全部数据依赖点
              │
第 3 步  私库 + 双写同步
         核心表迁到独立数据库实例，新旧库双写，读流量切到新库验证
              │
第 4 步  私库 + 各自自治
         停掉旧库写入，跨服务一致性靠"本地消息表 + 事件"保证
```

```sql
-- 第 1 步落地：用数据库权限做硬隔离，比"代码规范"靠谱一百倍
CREATE USER 'order_svc' IDENTIFIED BY '***';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop_order.* TO 'order_svc';
REVOKE ALL ON shop_inventory.* FROM 'order_svc';  -- 订单服务摸不到库存表
```

双写期间的一致性校验别省：每天用离线任务比对新旧两库的差异行数，差异清零才允许切读流量。同步工具直接用 Canal（订阅 MySQL binlog）或 DataX 就够了，不必自己造轮子——省下的开发时间，够团队多搬走一个边缘模块。

> [!WARNING] 最难的一步在第 4 步
> 私库自治意味着放弃跨库事务："下单扣库存"从一条 SQL 变成两笔跨服务操作，必须用本地消息表、TCC 或 Saga 补偿来保证最终一致（第 13 章详细讨论过）。动手前先数一数代码里有多少条跨模块事务——超过 20 条，就要做好打一年持久战的准备。

## 19.5 云书店完整演进案例

把前面的方法串起来，看云书店的完整演进。它与第 0 章的演进图一一对应：

```mermaid
graph LR
    S0["阶段0\n单体+单库\n日订单1千"] -->|"用户10万\n代码50万行"| S1["阶段1\n模块化单体\n读写分离+缓存"]
    S1 -->|"大促打不进来\n团队50人"| S2["阶段2\n拆核心服务\n订单支付库存+MQ"]
    S2 -->|"服务15个\n治理一片混乱"| S3["阶段3\n网关+服务治理\n云原生"]
```

### 阶段 0：单体 + 单库（起步期，日订单 1 千）

**触发信号**：无——这是一切的起点。业务还没验证，怎么快怎么来。

**动作**：一个 Spring Boot 单体 + 一个 MySQL，模块按包结构隔离（用户、商品、购物车、订单、支付、库存、评价、物流），部署在一台 2 核 4G 的云主机上。

**收益**：发布 10 分钟一次，全栈联调零成本，一个人就能看懂整个系统。**代价**：技术债先欠着——反正业务随时可能转型，这些债是用"快"换来的，值得。

### 阶段 1：模块化单体 + 读写分离 + 缓存（成长期，日订单 5 万）

**触发信号**：用户涨到 10 万，代码 50 万行，"改一处崩三处"成了团队口头禅；一次全量发布从 10 分钟涨到 50 分钟。

**动作**：Maven 多模块 + ArchUnit 规则强制模块边界（工具守护在第 21 章讲）；MySQL 主从读写分离，报表查询走从库；给商品详情加 Redis 缓存，热点书目命中率 95%；接入 CI 流水线，发布自动化。

**收益**：发布回到 15 分钟以内；商品详情接口 P99 从 800ms 降到 60ms；数据库 CPU 从 85% 降到 40%。

**代价**：团队要立"模块间禁止直连对方表"的规矩，并且必须配工具守护——纪律靠自觉维持不超过三个月；缓存引入一致性新问题，商品改价后有 3 秒的新旧价格并存窗口。

### 阶段 2：拆核心服务 + 消息队列（成长期后段）

**触发信号**：大促流量打不进来——单体只能整体扩容，为了订单模块扛量，得把整个应用复制 20 份；团队涨到 50 人，六个小组在同一个仓库互相踩脚，每周固定有两天在等别人的代码合入。

**动作**：按 19.3 的顺序，先用绞杀者模式搬走评价、通知、搜索三个边缘服务练手；再拆订单、支付、库存三个核心服务并各自配私库；下单链路改成事件驱动——订单服务落库后发布"订单已创建"事件，库存、积分服务订阅消费，用本地消息表保证事件不丢；引入 RocketMQ。

**收益**：订单服务独立扩容，大促期间从 20 副本加到 60 副本，而评价服务 2 个就够，机器总成本反而降了 30%；六个小组各自发布，互不阻塞。

**代价**：运维复杂度陡增——三个服务三种日志格式，排查问题靠人肉 grep；"下单成功但扣库存失败"这类跨服务一致性问题开始出现，需要补偿机制；联调从本地变成长测试环境排队。

### 阶段 3：网关 + 服务治理 + 云原生（成熟期，日订单 50 万）

**触发信号**：服务涨到 15 个之后，配置、监控、调用链一片混乱——配置散落在各服务的 yaml 里，改一个超时参数要发 15 个版本；新服务接入要手工配注册中心、监控、告警，每次两天。

**动作**：API 网关统一入口（认证、限流、灰度）；配置中心（Nacos）+ 链路追踪（OpenTelemetry）补齐可观测性；整体搬上 Kubernetes 统一编排，服务上下线从"发工单"变成"调副本数"；完善熔断降级与容量预案。

**收益**：新服务接入从 2 天降到半天；全链路追踪让"晚上 8 点下单慢"这类问题的定位时间从 2 小时缩到 15 分钟；基础设施弹性伸缩，大促前不再需要提前一个月扩容。

**代价**：需要 3-5 人的平台团队专门维护这套基础设施；每个开发都得补容器与 K8s 的课；一次 K8s 版本升级事故能让大家记一年。

三个时期的关键数字对照，这也是全书举例时使用的基准：

| 指标 | 起步期（阶段 0） | 成长期（阶段 1-2） | 成熟期（阶段 3） |
| ---- | ---- | ---- | ---- |
| 日订单量 | 1 千 | 5 万 | 50 万 |
| 团队规模 | 8 人 | 50 人 | 150 人 |
| 部署单元 | 1 个单体 | 1 个单体 + 6 个服务 | 15 个以上服务 |
| 发布频率 | 每周 1-2 次 | 每天 1-2 次 | 每天数十次 |
| 核心矛盾 | 业务能不能活 | 边界与协作 | 治理与效率 |

四个阶段的完整对照表：

| 阶段 | 架构形态 | 触发信号 | 核心动作 | 最大代价 |
| ---- | ---- | ---- | ---- | ---- |
| 0 | 单体 + 单库 | 无（起点） | 快速验证业务 | 技术债随业务膨胀 |
| 1 | 模块化单体 + 读写分离 + 缓存 | 用户 10 万、代码 50 万行 | 模块边界、缓存、主从 | 纪律要靠工具守护 |
| 2 | 核心服务 + 消息队列 | 大促扛不住、50 人踩脚 | 绞杀者拆分、事件驱动 | 分布式一致性与运维 |
| 3 | 微服务 + 网关 + 云原生 | 服务 15 个治理混乱 | 平台化、可观测性 | 平台团队人力成本 |

## 19.6 每一步的回滚策略

演进式架构和普通重构最大的区别，是每一步都必须带"后悔药"。下面是云书店每阶段关键动作与对应的回滚策略：

| 动作 | 回滚策略 | 回滚耗时 |
| ---- | ---- | ---- |
| 网关切流到新服务 | 路由开关切回旧单体，新服务停写 | 分钟级 |
| 商品详情上缓存 | 缓存开关降级为直查数据库 | 秒级 |
| 读写分离 | 写不受影响，读流量切回主库 | 分钟级 |
| 私库迁移双写期 | 暂停切换，数据仍在新旧两库，回滚只改数据源配置 | 分钟级 |
| 私库切换完成 | 保留旧库 30 天只读快照，用双向同步脚本回灌 | 小时级 |
| 下单链路改事件驱动 | 消息队列保留，消费者降级为同步调用旧逻辑 | 小时级 |
| 上 Kubernetes | 虚拟机部署方案保留一个版本，DNS 层切换 | 小时级 |

三条回滚纪律：

1. **先写回滚方案，再做变更**。写不出回滚方案的变更，说明自己还没想清楚，那就先别做。
2. **旧系统退役设缓冲期**。旧单体在新服务稳定运行 30 天后才允许下线，期间只读保留。
3. **回滚要演练**。大促前把关键开关真的拉一次——演练过的回滚叫预案，没演练过的叫祈祷。

大促前的演练清单可以更具体：

- 关掉一半数据库从库，验证主从切换时长与告警是否触发；
- 手动杀掉订单服务一半实例，验证流量摘除与自动拉起；
- 把库存服务熔断开关拉下 5 分钟，验证下单降级文案与恢复动作；
- 将网关路由从新服务切回旧单体，计时验证"分钟级回滚"是否属实。

把全章收拢成一句话：微服务是"信号驱动"的组织手术——四个信号亮红灯才动手，按"先边缘、先无状态"的顺序拆，数据最后动，每一步配好回滚。拆的时机错了，后面全错；时机对了，拆得再慢都不算慢。

## 本章小结

- 判断是否拆分看四个信号：部署时间、变更半径、团队人数、模块耦合度，绿灯时别折腾
- 绞杀者模式让新旧系统并行工作，逐模块搬迁、逐路由切换，随时可退
- 防腐层在边界做一次翻译，防止旧系统的脏数据结构污染新服务
- 拆分顺序：先边缘后核心，先无状态后数据；数据拆分放最后，分四步过渡
- 共库到私库的路径：逻辑隔离、接口化访问、双写同步、各自自治
- 跨服务一致性靠本地消息表与事件补偿，动手前先数清跨模块事务的数量
- 云书店四阶段演进（单体、模块化单体、核心服务、云原生）每步都由真实痛点触发，而不是技术潮流
- 每一步变更先写回滚方案再动手，回滚开关要定期演练
