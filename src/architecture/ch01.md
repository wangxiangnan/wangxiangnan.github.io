# 第1章：软件架构是什么

> [!TIP] Part 1: 从零认识软件架构（基础概念篇）
> 在画第一张架构图之前，先把"内功"练好。这六章帮你建立软件架构的完整概念框架：它是什么、目标是什么、怎么描述、按什么原则做决策、有哪些流派、用什么工具。所有例子都围绕同一个虚构项目"云书店"展开。

你可能写过不少代码，也可能正在带一个小团队，被"架构"这个词包围：面试要聊架构，开会要画架构图，出了线上事故会被追问"当初怎么设计的"。但真让你说清楚"架构到底指什么"，答案往往只剩下"微服务""高并发"这类零碎的名词。

这一章，我们把这个概念本身掰开揉碎：先讲一个云书店从 0 到 1 的故事，再给出一个可操作的定义，最后厘清三组最容易混淆的概念。读完这一章，你再被问到"架构是什么"，应该能脱口而出一个公式，而不是一串术语。

## 1.1 先讲个故事：云书店从 0 到 1

云书店是本教程的贯穿示例：一个卖书的电商平台，包含用户、商品、购物车、订单、支付、库存、评价、物流八个业务模块。它不是一开始就有"架构"的，它的架构是被业务增长一步一步逼出来的。

**阶段 0：怎么快怎么来（第 1 至 6 个月）**

三个人的创始团队：你负责架构和后端，阿珍负责后端，小飞负责前端。技术选型毫无悬念：一个 Spring Boot 单体（Monolith）应用加一个 MySQL 数据库，Nginx 做反向代理，所有业务跑在一个进程里，打一个 jar 包部署完事。

上线第 6 个月，日订单稳定在 1 千单。这个阶段单体是真香：改完代码 10 分钟就能重新部署，出了问题日志一翻一个准，阿珍休年假一周，你一个人也能扛下全部需求。

**阶段 0 尾声：第一道裂缝（第 18 个月）**

用户涨到 10 万，团队涨到 20 人，代码膨胀到 50 万行。新人小王接到需求"满 199 减 50 的大促活动"。他打开 OrderService——一个 3,400 行的类，促销、运费、库存、短信全在里面。他小心翼翼只改了促销逻辑，结果把运费计算改坏了：满减商品"满 99 包邮"的判断失效，一夜之间 1,000 多个订单多收了 6 元运费，客服电话被打爆。

事故之后团队统计出一个吓人的数字：任何一个需求上线，全量回归测试都要 4 小时以上——因为没人敢保证"我只改了这个模块"。这就是经典的**改一处崩三处**。

**阶段 1：把边界画清楚（第 30 个月）**

团队做了模块化单体（Modular Monolith）改造：应用还是一个进程，但内部按业务域切出八个模块，模块之间只准通过接口调用，数据库表按模块划清归属。改造后日订单涨到 5 万，架构稳稳撑住，回归测试从 4 小时降到 40 分钟。

**阶段 2：流量与人数的双重爆炸（第 3 年）**

团队涨到 50 人。一次大促的 0 点抢购，下单峰值冲到日常的 10 倍，数据库连接池耗尽，核心交易瘫痪 47 分钟——按大促日 1,500 万 GMV 折算，直接损失约 50 万，还没算舆情。与此同时，50 个人往一个代码库里提交代码，发布要排队，合并冲突天天上演。

这次之后，团队把最痛的三个域——订单、支付、库存——拆成了独立服务，中间加一层消息队列（Message Queue）做削峰。这条演进路径的第 19 章会完整重演一遍。

**阶段 3：平台化（第 5 年）**

日订单 50 万，团队 150 人，微服务、网关、服务治理、云原生一整套铺开。这个阶段的"架构"已经不只是技术问题，更是组织问题——对应第 4 章要讲的康威定律。

回看这条时间线：

| 时间 | 注册用户 | 日订单 | 团队规模 | 代码量 | 架构阶段 |
| ---- | -------- | ------ | -------- | ------ | -------- |
| 第 6 个月 | 5 万 | 1 千 | 3 人 | 8 万行 | 阶段 0：单体 + 单库 |
| 第 18 个月 | 10 万 | 5 千 | 20 人 | 50 万行 | 阶段 0 尾声：改一处崩三处 |
| 第 30 个月 | 150 万 | 5 万 | 50 人 | 80 万行 | 阶段 1：模块化单体 |
| 第 5 年 | 3000 万 | 50 万 | 150 人 | 200 万行 | 阶段 3：微服务 + 云原生 |

用一张图把云书店的演进串起来，后面每一章的例子都会挂在这条时间线的某个阶段上：

```mermaid

    P2["阶段2 拆核心服务\n订单支付库存加消息队列"]
```

> [!NOTE] 一个重要观察
> 云书店每一次架构调整，都不是被技术潮流推动的，而是被真实的痛推动的：先是变更成本失控，然后是流量，然后是团队规模。看到别人上微服务就跟着上，是这个行业最贵的从众行为。

这套数字设定会在全书反复出现，先做几个锚点记忆：起步期日订单 1 千时，单体是甜蜜的；成长期日订单 5 万、用户 10 万量级时，模块边界比部署形态更值钱；成熟期日订单 50 万时，组织问题反过来主导技术问题。后面每章举例，都会告诉你"此时云书店处于哪个阶段、日订单多少"，你可以随时回到这张表校准自己的位置。

## 1.2 架构的定义：结构 + 决策

故事讲完了，现在给出定义。业界对"架构"的定义不下二十种，但剥开外壳，内核都是同一句话：

**架构 = 组件划分（怎么切）+ 组件关系（怎么连）+ 关键决策（为什么这么切、这么连）**

拆开来看这三个部分：

- **组件划分**回答"系统由几块组成"：订单是一块，库存是一块，支付是一块。切的依据不是技术炫技，而是业务变化的方向。
- **关系定义**回答"块与块怎么打交道"：同步调用、消息事件，还是共享数据库？谁拥有数据、谁依赖谁？
- **关键决策**回答"为什么"：为什么拆服务而不是拆模块？为什么用消息而不是 RPC？没有"为什么"的架构图，只是一张好看的画。

注意顺序：很多人以为"先有结构、后有决策"，其实**决策在前**——组件怎么切、关系怎么连，本身就是决策的产物；决策还解释了结构为什么长这样、明天会往哪长。所以读一个陌生系统，最值钱的信息永远是它的决策记录。

设计模式四巨头之一的 Ralph Johnson 说过一句流传很广的话："架构是那些你希望一开始就做对、但很难在后期更改的决策（Architecture is the decisions you wish you could get right early in a project）。"这句话点出了架构决策的核心特征：**改起来代价极高**。

如果把架构决策画成一座冰山，大概是这个样子：

```text
            水面上：人人都在讨论的部分
   ┌─────────────────────────────────────────────┐
   │  技术选型：用 MySQL 还是 PostgreSQL？          │
   │  用 Spring Cloud 还是 Go + K8s？              │
   └─────────────────────────────────────────────┘
   ───────────────────── 水面线 ────────────────────
            水面下：真正决定项目生死的部分
   ┌─────────────────────────────────────────────┐
   │  组件划分：系统切成哪几块？边界画在哪？          │
   │  关系定义：同步调用还是事件？数据谁拥有？        │
   │  约束声明：依赖方向是什么？什么永远不许做？      │
   │  权衡记录：为什么这么选？为此放弃了什么？        │
   └─────────────────────────────────────────────┘
```

水面上的选型最容易吵，却最不致命——数据库不行可以换，框架不喜欢可以迁。水面下的切与连，一旦代码写上几万行，再动就是伤筋动骨。所以判断一个决策是不是"架构级"，可以用三个问题：

1. **改起来贵不贵？** 贵到要动几十个文件的，是架构决策。
2. **影响面广不广？** 波及多个团队、多个模块的，是架构决策。
3. **能不能晚点再定？** 能推迟且推迟了不亏的，别现在定——这直接引出第 4 章的 YAGNI 原则。

顺手排掉三个流传最广的误解：

- **"架构就是画图"**——图是决策的输出，不是决策本身。没有"为什么"的图只是装饰品。
- **"架构就是技术选型"**——选型是冰山水面上的部分，切与连才是水下的主体。
- **"小项目不需要架构"**——小项目不需要专职架构师，但每一次"这个功能放哪个模块"的决定都是架构决策。云书店第 1 年的架构决策，是三个人在白板前顺手做的，做的次数一点没少。
- **"架构是架构师一个人的事"**——架构决策需要业务输入和团队共识，闭门造车的架构图最后都进了回收站。

还有一个反直觉的事实：**架构不会因为没人管就"保持原样"，它只会熵增**。每次赶工塞进去的一个 if 分支、一次图省事的跨模块调用，都是往系统里扔熵。架构工作的本质，就是持续地对抗这种熵增。

## 1.3 架构师到底做什么

先破除一个误解：**架构师不是画图匠**。图只是决策的表达形式，就像菜谱不等于厨艺。一个只会画漂亮的框图、却说不清"为什么这么切"的人，不是架构师，是 PPT 工程师。

真正的架构师每天做三类事：

**做决策**：组件怎么切、块之间怎么连、用什么技术实现、在质量属性之间怎么取舍（第 2 章展开）。决策的标志是"可执行的结论"，而不是"我觉得都可以"。

**定约束**：把决策翻译成团队能遵守的规则——依赖方向、模块边界、编码规范、评审清单。约束的价值在于让 20 个人的代码库看起来像一个人写的。

**陪演进**：上线不是终点。看监控、定容量、还技术债、规划重构节奏，让架构跟业务一起长（第 19 章的演进专题）。

这三类事可以浓缩成一句话：**架构师用决策和约束，为团队换取长期的变更自由**。

云书店起步期只有 3 个人，没人挂着"架构师"的头衔，但架构工作一直存在——只是当时你凭直觉做了决策。一个典型架构师的时间分配大概是这样：

| 事项 | 时间占比 | 说明 |
| ---- | -------- | ---- |
| 沟通与对齐（产品、业务、团队） | 35% | 架构决策大半发生在对话里，见第 6 章 |
| 设计与评审（写方案、看方案） | 25% | 输出 C4 视图、ADR、评审意见 |
| 写代码与验证 | 15% | 关键路径亲自写，走线骨架带头干（第 6 章） |
| 技术调研与学习 | 10% | 维护技术雷达的输入 |
| 线上问题与容量治理 | 10% | 事故复盘、容量规划、技术债治理 |
| 培养人与布道 | 5% | 把"为什么"讲清楚，让决策被团队传承 |

注意第一行：架构师花在**沟通**上的时间超过了画图和写代码的总和。因为架构决策的难点从来不是"想出一个方案"，而是"让所有相关的人理解并认同这个方案，且知道它的代价"。

按产出物清点，架构师的交付物清单其实很固定：

- **决策**：以 ADR 的形式沉淀（第 6 章详述），每条都带着"为什么"和"放弃了什么"
- **约束**：依赖规则、模块边界、编码规范、评审清单——让 20 个人的代码库像一个人写的
- **视图**：以 C4 的 L1、L2 图为主，关键链路补时序图（第 3 章详述）
- **示范代码**：关键路径亲自写或亲自 review，尤其是走线骨架阶段
- **度量**：质量属性目标表（第 2 章）与后续的监控指标对齐

## 1.4 架构、设计、框架：别再混着说

"我们用了 Spring Cloud，所以是微服务架构。"这句话混淆了三个维度，必须拆开：

| 维度 | 回答的问题 | 变更成本 | 云书店的例子 |
| ---- | ---------- | -------- | ------------ |
| 架构 | 系统怎么**切**、怎么**连** | 极高，后期几乎改不动 | 单体还是微服务、同步调用还是事件驱动 |
| 设计 | 模块内部怎么**组织** | 中等，可以渐进重构 | 订单模块用策略模式还是 if-else |
| 框架/技术 | 用什么**工具**实现 | 较低，可以替换 | MySQL 还是 PostgreSQL、RocketMQ 还是 Kafka |

三层的关系是层层"服务"于上一层：框架是为了实现设计，设计是为了落实架构。反过来的逻辑不成立——先买了 Spring Cloud 全家桶，然后宣布自己是微服务架构，等于先买锅再决定开什么餐厅。

> [!TIP] 记忆锚点
> **架构决定生死，设计决定好坏，框架决定效率。**

用变更成本来体会一下：云书店把 Redis 换成 Memcached，一周搞定（框架层）；把订单模块的 if-else 促销改成策略模式，一个月搞定（设计层）；把模块化单体改成微服务，三个团队停掉新需求干了半年（架构层）。层级越高，翻船越难救，所以本教程反复强调：**先定切与连，再谈用什么**。

一道自测题，检验你是否真分清了三层：云书店"把下单接口从同步扣库存改成发消息异步扣库存"，这是哪一层的变化？答案是架构层——它改变了组件之间的关系定义（同步变异步），动了数据一致性模型，改动横跨订单与库存两个模块。而"把促销 if-else 重构成策略模式"是设计层，"把 MySQL 从 5.7 升到 8.0"是框架层。用这个标准去审你日常的每一个"技术改动"，层级感很快就有了。

## 1.5 大泥球：系统的默认结局

讲完正面的定义，看一个反面教材：大泥球（Big Ball of Mud）。这个概念由 Brian Foote 和 Joseph Yoder 在上世纪 90 年代末提出，指的是"功能凑合能跑，但内部毫无结构可言"的系统。它的典型症状：

- 模块之间没有边界，任何类都可以调用任何类
- 一个叫"Common"或"Utils"的包里塞了几百个类，谁都能引用
- 没人能说清一个请求从进来到返回经过了多少层
- 删代码比加代码危险——你不知道谁在用它
- 测试必须连真实数据库，跑一遍要半小时
- 新人要三个月才敢独立上线功能

对照一下，你的项目命中了几条？命中三条以上，就是大泥球预备役。

云书店第 18 个月的 OrderService 就是一个微缩大泥球。看一眼它的样子：

```typescript
// 反例：起步期第 18 个月的 OrderService（节选），一个类 3,412 行
class OrderService {
  createOrder(cart: Cart) { /* 组装订单、算价、落库，全在这里 */ }
  applyPromotion(order: Order) { /* 1,200 行 if-else 的促销规则 */ }
  calcFreight(order: Order) { /* 运费模板，里面还混着满减包邮的判断 */ }
  deductStock(order: Order) { /* 直接 UPDATE 库存表，绕过库存模块 */ }
  sendSms(order: Order) { /* 下单成功短信，模板硬编码在业务里 */ }
  exportDailyReport() { /* 运营要的经营日报，不知道该放哪就放这了 */ }
}
```

这个类的问题不是"大"，而是**它有五个独立的变更理由**：促销规则会变、运费模板会变、库存流程会变、短信文案会变、报表口径会变。每周都有理由改它，每次改动都可能踩到别的职责——小王的"满 99 包邮"事故就是这么发生的。

| 变更理由 | 触发频率 | 模块化改造后归属 |
| -------- | -------- | ---------------- |
| 促销规则 | 每周 | 营销模块 |
| 运费模板 | 每月 | 物流模块 |
| 库存流程 | 每季度 | 库存模块 |
| 短信文案 | 随时 | 通知模块 |
| 报表口径 | 每月 | 数据模块 |

对照这张表可以看出：变更理由的触发频率，就是模块切分优先级的信号——越是频繁变化的理由，越该拥有独立的边界。

要害在于：大泥球不是菜鸟写出来的，它是**任何缺乏边界约束的团队高速迭代的必然产物**。deadline 压力下，"先加个 if 判断"永远比"先定义清楚边界"快，一次两次看不出差别，两年后就是 50 万行改一处崩三处。架构的存在，就是让"正确地改"和"快速地改"成为同一条路，而不是二选一。

反过来，一个结构健康的系统有三个对照信号：改一个需求只动一个模块；新人两周内敢提交上线；出了问题日志五分钟内定位到模块。云书店阶段 1 改造验收时用的就是这三条——它们比任何漂亮的架构图都诚实。

## 1.6 为什么需要架构——把教训翻译成动作

回到云书店的三次教训，每一次都能翻译成一个具体的架构动作：

| 云书店的教训 | 症状 | 对应的架构动作 | 本教程章节 |
| ------------ | ---- | -------------- | ---------- |
| 变更成本失控 | 改促销崩了运费，回归测试 4 小时 | 画清模块边界，强制单向依赖 | 第 4、8 章 |
| 流量增长压垮系统 | 大促 0 点连接池耗尽，瘫痪 47 分钟 | 缓存、异步化、水平扩展 | 第 15、17 章 |
| 团队规模互相踩脚 | 50 人合并冲突，发布排队 | 服务化拆分，组织与架构对齐 | 第 4、11、19 章 |

三行表就是一部架构史：变更成本、流量、组织，三大动力依次登场，缺一个故事都不完整。

归纳起来，架构给团队带来三样东西：

**控制熵增**：用边界和约束让系统在长期变更中保持结构清晰，而不是一路烂下去。

**管理不可逆决策**：把"贵"的决策尽早想清楚、写下来，把"便宜"的决策尽量推迟——这叫架构的杠杆。

**对齐认知**：一张 C4 图、一份 ADR，让产品、老板、开发对"系统是什么、为什么长这样"达成一致，减少每天无数次的重复解释。

最后澄清一个常见误解：架构不是项目启动时画一张蓝图然后供起来。云书店的架构图每半年都和一年前不一样，但它始终回答同样三个问题：切成了几块？怎么连的？为什么？**架构是持续演进的决策记录，不是一次性的仪式。**

用一句更狠的话收束本章：**架构的对手从来不是"没有架构"，而是"错误的架构时机"**——在错误的阶段追求完美的结构是浪费，在正确的阶段拒绝投入是灾难。云书店踩过的每个坑，坑底都写着同一个教训：架构动作要么早于痛点半步，要么晚于痛点十步，前者是远见，后者是考古。

## 本章小结

- 架构 = 组件划分（怎么切）+ 组件关系（怎么连）+ 关键决策（为什么），前两者是结构，最后一个是灵魂
- 云书店的演进：单体（日订单 1 千）到模块化单体（5 万）到拆核心服务再到微服务（50 万），每次调整都被真实的痛推动，而不是被潮流推动
- 判断架构级决策的三个问题：改起来贵不贵？影响面广不广？能不能晚点再定？
- 架构师的核心产出是决策与约束，不是图；沟通与对齐占了近一半时间
- 架构、设计、框架三个维度：架构决定生死，设计决定好坏，框架决定效率
- 大泥球是缺乏边界约束的系统高速迭代的默认结局，架构的本质之一是给熵增设减速带
- 架构是持续演进的决策记录：任何时刻都能回答"切成了几块、怎么连的、为什么"
- 架构师近一半时间花在沟通对齐上——决策的难点在于让所有人理解并认同代价

**下一章预告**：知道了架构是什么，下一章回答"架构为了什么"——六大质量属性逐一登场，你会看到性能、可用性、可扩展性、可维护性、安全性、可演进性之间没有硝烟的权衡战争。
