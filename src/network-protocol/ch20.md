## 20.1 TCP 的局限：三个根深蒂固的问题

TCP 服役四十多年，了不起，但对现代 Web 有三个越来越致命的问题：

**1. TCP 层的队头阻塞**——19.7 的诊断在此确认。TCP 保证字节流有序交付（8.1），一个包丢了，9.1 的累积确认会卡住整个连接：Stream 3 丢一包，已经完整到达的 Stream 5、7 也交付不了。

**2. 握手延迟**——TCP 三次握手（8.3）1 RTT + TLS 1.3 握手（15.2）1 RTT = 2 RTT 才能发数据。跨洋 RTT 200ms，用户等 400ms 才见第一个字节。

**3. 连接迁移困难**——TCP 连接由四元组标识（12.4）。手机从 WiFi 切 5G，IP 变了，连接断了，一切从头再来。

这三个问题都不是「调参数」能解决的——病根在协议设计本身。

## 20.2 设计选择：为什么是 UDP

Google 的工程师做了个大胆决定：不用 TCP，基于 UDP 重新造轮子。

为什么不在 TCP 上改？因为 TCP 是内核实现的——改 TCP 意味着更新全球数十亿设备的操作系统内核，等所有设备升级完可能要十年。而 UDP（7.1 说过）是「最薄的传输层」，几乎什么都不做：没有连接、没有确认、没有拥塞控制。

「先猜再读」第一问的答案：7 章的 UDP 白板论在此兑现——UDP 的「什么都不管」不是缺陷而是留白。QUIC 在这块白板上、于**用户空间**写齐了 TCP 的全部本领：

- 可靠传输（按流选择性重传，而非全连接按序阻塞）
- 拥塞控制（第10章的算法，实现在应用层，随浏览器更新迭代）
- 流多路复用（每条流独立丢包恢复）
- 内置 TLS 1.3 加密

用户空间实现意味着 QUIC 的进化速度和浏览器一样快——不用等内核版本，这正是绕开僵化的第一步。

## 20.3 内置加密：不只是安全，更是防僵化

QUIC 几乎所有内容都是加密的——连大部分包头都是。TLS 1.3 的握手细节本章不重复（15.2 是主场），这里只讲 QUIC 把加密「内置」的两个深意：

**隐私与完整性**：传统 TCP+TLS 中 TCP 包头明文可见，中间设备能观察序列号、确认号。QUIC 只露出 UDP 包头和连接 ID，其余全部加密。

**防协议僵化（Ossification）**：这是更重要的动机。中间设备会按「看懂的字段」做优化或拦截——TFO（11.7）推广缓慢的部分原因就是中间盒不认识它，把它当异常丢掉。QUIC 把字段全部加密后，中间设备**看不懂就无法乱动**：既不能基于字段值「优化」，也不能因为字段值「古怪」而拦截。加密在此成了协议的「保鲜膜」——端到端特性得以保全。第22章讲威胁模型时，「中间人」还会有更系统的登场。

## 20.4 0-RTT 与 1-RTT：连接建立的速度赛

三种建连方式对比：

```
TCP + TLS 1.3:
  Client → Server: SYN
  Server → Client: SYN-ACK
  Client → Server: ACK + ClientHello
  Server → Client: ServerHello + ...
  Client → Server: Finished
  → 可以发送应用数据（总计约 2 RTT）

QUIC（首次连接）:
  Client → Server: Initial（ClientHello + 密钥参数 + 第一个请求）
  Server → Client: Handshake + 响应
  → 应用数据开始往返（总计约 1 RTT）

QUIC（0-RTT 重连）:
  Client → Server: 0-RTT 数据（用缓存的会话密钥直接加密的请求）
  → 0 RTT 即可发数据！
```

1-RTT 快在合并：传输层握手与加密握手不再分家，ClientHello 跟着第一个数据包一起走。0-RTT 更进一步——客户端缓存上次连接的传输参数与密钥材料，重连时直接加密发送。

「先猜再读」第二问的答案：0-RTT 数据由**客户端自己声称**「这是上次会话的我」，服务器没有当前往返做实时验证——攻击者截获这段加密数据后可以原样重放给服务器（比如重复下单）。所以规范要求应用层把 0-RTT 数据限制为幂等操作——13.3 讲的幂等性在这里成了安全底线。服务器也会对 0-RTT 有额外限流，防的就是重放放大。

## 20.5 连接迁移：Connection ID 取代四元组

「先猜再读」第三问的答案：TCP 会断，QUIC 不会。TCP 用四元组标识连接——IP 一变，内核认为连接不复存在。QUIC 引入 **Connection ID**：双方协商的标识符，与 IP 地址无关。

```
WiFi 场景:
  Client (192.168.1.100:54321) → Server (93.184.216.34:443)
  Connection ID: 0x3a7f2c91

切换到 5G:
  Client (10.45.67.89:12345) → Server (93.184.216.34:443)
  Connection ID: 0x3a7f2c91  ← 同一个 ID，连接继续
```

网络切换时 IP 变了，但 Connection ID 没变——服务器认 ID 不认地址，连接无缝继续。对移动设备这是体验级的改进：视频通话不断流、下载不重来。同时 QUIC 有路径验证机制（PATH_CHALLENGE/RESPONSE），确认新路径真的通向同一个对端，防止连接 ID 被冒用——细节仍是 ch15 的加密体系在撑腰。

## 20.6 把 TCP 的经典机制重做一遍

QUIC 不是 TCP 的简化版，而是它三十年经验教训的重构。对照着看（每行都能在前面的章节找到出处）：

| TCP 机制（出处） | QUIC 的对应做法 |
| ---------------- | ---------------- |
| 序号 + 累积确认（8.4、9.1） | 包号单调递增不重复 + ACK 范围块（无歧义，重传包不用假序号） |
| 快速重传：3 个重复 ACK（9.4） | 同理保留，且因包号唯一判断更直接 |
| SACK 选项（9.6） | ACK 帧原生支持多个区间 |
| rwnd 窗口（11.2） | MAX_DATA / MAX_STREAM_DATA 帧，连接级 + 流级两层 |
| 拥塞控制（第10章） | 用户空间实现，CUBIC/BBR 随浏览器升级 |
| Keep-Alive 探测（11.5） | 内置 PING/PADDING 保活与路径验证 |
| TIME_WAIT 悬置（8.6） | 无状态重置（ Stateless Reset）快速清理 |
| MSS 协商（11.6） | Initial 包强制 ≥1200 字节探测路径，动态调包大小 |

「先猜再读」第一问的完整答案就在这张表里：可靠传输在 QUIC 里被重新实现——按流独立确认与重传，19.7 的阿喀琉斯之踵在这里拔了根。两种传输层丢一包时的命运对比：

> [!TIP] 浏览器怎么发现 HTTP/3
> 首次 HTTP/2 响应头里的 `Alt-Svc: h3=":443"` 是一张「另类服务」名片：「我还有个 HTTP/3 入口，下次先试 UDP 443」。失败自动回退 TCP，所以 H3 的灰度是无感的。DNS 的 HTTPS 记录（16.4 记录家族的新成员）也在做同样的事——发现机制建立在 DNS 与 HTTP 头部之上。

## 20.7 HTTP/3、QPACK 与三代演进

HTTP/3 本质是 HTTP/2 语义在 QUIC 上的映射：

| HTTP/2 概念 | HTTP/3 对应 |
| ----------- | ----------- |
| TCP 连接 | QUIC 连接 |
| Stream | QUIC Stream（每方向独立编号） |
| HEADERS 帧 | HEADERS 帧（QPACK 压缩） |
| HPACK | QPACK（避免压缩自身的队头阻塞） |

QPACK 解决一个微妙的二阶问题：HPACK（19.4）的动态字典依赖头部**按序**到达，可 QUIC 的流是乱序交付的——如果字典更新堵在某条流上，后续所有头部都得等它，压缩自己又造出队头阻塞。QPACK 允许头部区块在独立的控制流上传输并容忍乱序，用少量压缩率换彻底解耦。

三代 HTTP 的演进逻辑一图流：

```
HTTP/1.1: 文本协议，按序请求 → 多开连接弥补（六连接并行）
HTTP/2:   二进制帧，多路复用 → TCP 层队头阻塞仍在
HTTP/3:   QUIC on UDP → 队头阻塞根治 + 0-RTT + 连接迁移
```

每一代都在解决上一代遗留的最痛问题，同时保持 HTTP 语义（方法、状态码、头部）不变——13 章学的本体一路通用。这也是为什么我们还叫它 HTTP：变的只是脚下的传输层。

## 20.8 编程实践：实测 HTTP/1.1、HTTP/2、HTTP/3

```bash
# 需要编译时启用 HTTP/3 的 curl（较新系统发行版自带）
curl --http3 -v https://cloudflare-quic.com/

# 对比三代协议的各阶段延迟
for v in 1.1 2 3; do
  echo "=== HTTP/$v ==="
  curl -o /dev/null -s -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" \
    --http$v https://www.google.com
done
```

预期观察：HTTP/3 的 `time_connect` 与 `time_appconnect` 明显更短——QUIC 把传输与加密握手合并了（20.4）；`time_connect` 一栏对 HTTP/3 甚至意义不大，因为 UDP 没有「连接」阶段。多跑几次取均值，并注意 DNS 解析时间会掺在 `time_namelookup` 里（16 章的缓存层次决定了它波动很大）。

## 20.9 抓包实践：对比 QUIC 与 TLS 1.3 握手

QUIC 跑在 UDP 443。抓包过滤 `quic` 或 `udp.port == 443`：

**QUIC 握手观察要点：**

1. 客户端 `Initial` 包（含 ClientHello），大小通常 ≥1200 字节——协议强制填充，防止反射放大攻击（7.3 说过 UDP 可以不握手就发数据，这个填充就是防它被滥用）。
2. 服务器回 `Handshake` 包（ServerHello、证书等）。
3. 客户端 `Finished`，此后是 1-RTT 加密数据；重连场景能看到 0-RTT 包直接携带请求。
4. 观察包头的 `DCID`（目的连接 ID）与 `SCID`（源连接 ID）——20.5 的主角。

对比 TLS 1.3 over TCP：

```bash
# 分别抓取 HTTP/2 (TCP+TLS) 和 HTTP/3 (QUIC) 的握手
tshark -i eth0 -f "tcp port 443" -w tcp_tls.pcap -c 100
tshark -i eth0 -f "udp port 443" -w quic.pcap -c 100
```

数一数包数：TCP+TLS 至少 5-6 个包往返（SYN、SYN-ACK、ACK、ClientHello、ServerHello、Finished），QUIC 只需 2-3 个。15.9 学过的 TLS 字段在 QUIC 里全部健在，只是换了载体——这正是「内置加密引用 ch15」的注脚。

## 本章小结

- TCP 的三大局限：字节流队头阻塞、传输+加密握手 2 RTT、四元组锁死连接——都不是参数能调好的。
- UDP 是白板：QUIC 在用户空间补齐可靠传输、拥塞控制、多路复用与加密，进化速度与浏览器同步。
- 全量加密一举两得：保护隐私，更防协议僵化——中间设备看不懂就乱动不了，端到端特性保鲜。
- 1-RTT 靠传输与加密握手合并，0-RTT 靠缓存密钥直接发数据——代价是重放风险，幂等性成为安全底线。
- Connection ID 让连接脱离四元组：WiFi 切 5G 不断流，配合路径验证防冒用。
- QUIC 重做而非简化 TCP：包号唯一、ACK 区间、双层窗口、用户空间拥塞控制——每项都能在前面的 TCP 章节找到原型。
- QPACK 解掉 HPACK 字典的按序依赖，压缩不再自己造队头阻塞。
- 三代演进一条主线：1.1 多开连接、2 复用连接、3 重造传输——HTTP 语义始终不变。
