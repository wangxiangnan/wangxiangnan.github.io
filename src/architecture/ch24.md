# 第24章：架构师成长之路与速查表

> [!TIP] Part 4: 架构演进与治理（进阶实战篇）
> 全书压轴。前 23 章讲的是"架构"，这一章讲的是"架构师"：类型与能力模型、成长路径、常见误区，最后把整本教程浓缩成三张可以随身携带的表——决策速查、评审 checklist、术语表。

很多工程师把"成为架构师"理解成"学会一堆技术名词"。但如果你跟着本教程走到了这里，你应该已经发现：架构的核心竞争力不是知道得多，而是**在约束下做对权衡，并让别人愿意跟你一起承担代价**。这一章我们先聊成长，再交付工具箱。

## 24.1 架构师的三种类型与能力雷达

"架构师"其实是个伞形词，伞下至少有三种不同的职业形态：

| 类型 | 关注层面 | 典型产出 | 在云书店里的对应角色 |
| ---- | ---- | ---- | ---- |
| 应用架构师 | 单个应用/服务内部 | 服务拆分方案、领域模型、技术选型 | 决定把订单和库存拆开的那个人 |
| 解决方案架构师 | 跨系统的业务方案 | 端到端集成方案、供应商选型 | 设计"书店 + 第三方物流 + 支付渠道"对接的人 |
| 企业架构师 | 全公司层面的系统版图 | 技术标准、架构治理、投资优先级 | 决定全公司统一用哪个消息队列的人 |

三者在职业路径上可以递进：多数人从应用架构师起步，横向参与更多系统后走向解决方案架构师，最终少数人进入企业架构的视野。反过来的路很难走——没在代码里泡过的人，很难让一线团队服气。

三种类型没有高低之分，只有能力配比不同。用一张雷达图看差异（满星五星）：

```text
能力维度         应用架构师    解决方案架构师   企业架构师
业务理解           ★★★★         ★★★★★          ★★★★★
技术深度           ★★★★★        ★★★            ★★
技术广度           ★★★          ★★★★           ★★★★★
沟通协作           ★★★          ★★★★★          ★★★★★
系统设计           ★★★★★        ★★★★           ★★★
行业与组织视野      ★★           ★★★            ★★★★★
```

不确定自己是哪种，拿三个问题自测：过去一年你影响过的最大系统边界是什么——一个服务、一条业务线，还是全公司？你的产出更多是代码与设计文档，还是跨团队的对齐方案？出问题时第一个被找的人是谁——找你是因为你懂，还是因为你认识所有该懂的人？

## 24.2 技术深度与广度：T 型策略

架构师的能力形状应该是一横一竖的"T"：

```text
              一横：广度——知道"什么时候该用什么"
 ┌──────────────────────────────────────────────────────────┐
 │  消息队列    缓存     K8s     搜索引擎    数据仓库    安全   │
 │  ── 知道原理、选型依据和边界，不要求能手写 ──                 │
 └───────────────────────────────┬──────────────────────────┘
                                 │
                                 │ 一竖：深度——一行行代码里泡出来
                                 │ 的判断力："这个方案上线后会怎么挂"
                         ┌───────┴────────┐
                         │   你的立身之本   │
                         │ （如：交易系统）  │
                         └────────────────┘
```

- **只有横没有竖**：什么都聊得头头是道，一到关键决策就飘——因为他没经历过"凌晨三点排查内存泄漏"的毒打，给出的方案没有落点。
- **只有竖没有横**：是优秀的专家，但容易拿着锤子看什么都是钉子——精通数据库的人倾向于把所有问题都塞进存储过程里解决。

怎么选那个"竖"？两个标准：一是你所在业务的核心域（参考第 20 章——核心域要放最强的人），二是你愿意投入十年不觉得枯燥的领域，两者的交集就是你的深度阵地。

深度的维护还有个日常动作值得养成：**每周跑一次热点分析**，看看自己和团队的精力真实地花在哪里：

```bash
# 用 git 粗测"热点"与"变更半径"：统计最近 90 天各顶层目录的修改频率
git log --since="3 months ago" --name-only --pretty=format: \
  | grep -v '^$' \
  | awk -F/ '{print $1}' \
  | sort | uniq -c | sort -rn | head -10
```

广度的补法可以参照这份清单，逐项做到"知道边界"：

- 消息队列：至少用过一种，知道削峰、解耦、顺序性三类语义；
- 缓存：知道多级结构，分得清穿透、击穿、雪崩及各自对策；
- 容器与编排：能读懂 Deployment 的 yaml，知道 HPA 靠什么伸缩；
- 搜索引擎：知道倒排索引与相关性排序解决什么问题；
- 数据仓库：知道 OLTP 与 OLAP 为什么分家；
- 安全：分得清认证与授权，理解最小权限原则。

修改最频繁的前十个目录，就是系统的热点——它们要么值得投入重构，要么藏着最多的业务价值。这份名单比任何口头汇报都诚实地反映系统现状。

## 24.3 软技能：向上沟通、跨团队推动、把决策变成共识

架构师的产出里，一半以上靠说和写。三项最关键的软技能：

**向上沟通：翻译，而不是汇报**。老板不关心 RocketMQ 的 ISR 机制，只关心钱、时间和风险。同一个方案，两种说法天差地别：

```text
错误说法："我们要把订单模块拆成独立服务，引入 RocketMQ，做最终一致性。"
老板内心OS：所以呢？要花多少钱？不拆会怎样？

正确说法："现在大促要提前一个月备机器，一年多花约 40 万，还不一定够用；
拆分后按需扩容，预计省 30% 机器成本。代价是两个开发投入一个季度，
且期间有 8 处一致性风险需要补偿机制。我建议拆，这是回滚预案。"
```

注意正确说法的结构：**业务影响先行、方案一句带过、代价主动交代、预案给出落点**。主动说代价不会削弱你，反而让人觉得这个方案被认真掂量过。

**跨团队推动：先一对一，再上会**。评审会上当场说服六个反对者几乎不可能。云书店拆订单服务前，架构师的做法是先分别找六个小组的负责人一对一过方案，把"你们组最担心什么"收集回来改进方案——等正式评审时，会上已经没有意外，只有确认。带着情绪上会争取"赢"，不如会前把"赢"拆解成各方的"不亏"。

操作上固定三步：①会前一对一，收集每方最担心的一条；②修改方案，让每条担心都有交代（哪怕是"记录在案、二期处理"）；③正式会上只确认、不辩论，把时间留给没被预处理的分歧。

**把决策变成共识：ADR + 评审 + 原型**。第 22 章的 ADR 是共识的载体：写下来，反对者才有明确的靶子；补充备选方案，反对者会觉得被尊重。有重大分歧时，别在会议室里吵——花两天做个原型，让数据替你说话。

三项技能有个共同的底层动作：**把模糊变成具体**。向上沟通是把技术模糊翻译成钱与风险的具体；跨团队推动是把对立立场具体成可交换的利益；共识机制是把口头赞成具体成写下来的承诺。练架构师的软技能，就从"每次发言都带数字、带方案、带代价"开始。

## 24.4 常见误区：三个坑与两个暗坑

| 误区 | 典型表现 | 解法 |
| ---- | ---- | ---- |
| 过度设计 | 日订单 1 千就上微服务 + 分库分表 + 服务网格 | 用第 19 章的信号清单自查，绿灯时不折腾 |
| 追新 | 新东西发布三个月就引入生产 | 新技术在测试环境养半年，先看别人踩坑 |
| 纸上架构师 | 图画得漂亮，说不出接口超时该设几秒 | 每个方案自己至少走查一遍关键代码路径 |
| 用地位代替论据（暗坑） | "就这么定了，我是架构师" | 回到 ADR：备选方案和理由写不出来就重新想 |
| 只做加法（暗坑） | 架构只拆不合并，服务越拆越多 | 每季度评估一次：有没有该合回去的服务 |

这五个误区有一条共同的根：**把手段当成了目的**。微服务是手段，DDD 是手段，新技术也是手段；忘了目的（业务的成功），手段就会自己膨胀。每次决策时把"这个选择服务了哪个质量属性"写进 ADR，就是最简单的自检。

> [!WARNING] 最危险的信号
> 当你发现自己很久没有打开过 IDE，所有判断都来自"以前的经验"——你已经站到代码的对面去了。架构判断力的半衰期大约两年，保持深度的唯一办法是定期下场：读核心模块的代码、参与一次事故复盘、亲手写一个小服务的原型。

## 24.5 五年成长路径建议

从工程师到架构师没有考试，只有一些被广泛验证的成长节点。以下路径假定你已经在写业务代码：

```mermaid
graph LR
    Y1["第1年\n把手头代码写好"] --> Y2["第2年\n理解模块设计\n追问为什么"]
    Y2 --> Y3["第3年\n跨模块设计\n主导评审"]
    Y3 --> Y4["第4年\n系统级决策\n带出新人"]
    Y4 --> Y5["第5年\n业务与架构\n双视野"]
```

| 阶段 | 主战场 | 关键动作 | 达成标志 |
| ---- | ---- | ---- | ---- |
| 第 1 年 | 自己的模块 | 把代码写清楚：命名、测试、重构 | 你的模块别人接手零痛苦 |
| 第 2 年 | 模块之间 | 每个设计追问"为什么这么定"，读优秀开源项目的分层 | 能独立设计一个模块的接口与模型 |
| 第 3 年 | 整个系统 | 主导技术方案评审，学着写 ADR | 方案被采纳且一年后没人想推翻 |
| 第 4 年 | 团队与系统 | 主导一次中型重构或服务拆分，带出一两个新人 | 拆分全程有回滚，新人能独当一面 |
| 第 5 年 | 业务与架构 | 参与业务规划，用架构语言翻译业务战略 | 老板主动找你要架构意见 |

顺带回答两个高频问题：架构师认证和在职学位有没有用？作为知识体系的敲门砖有点用，作为能力的证明几乎没用——面试架构师时没人问证书，问的全是"你主导过什么、后来怎么样了"。把时间投在作品集上：你主导的拆分、你写的 ADR、你复盘的事故，就是你最好的简历。

两个贯穿始终的习惯：**每次故障后写复盘**（故障是最好的架构课），**每个项目结束写下"如果重来会怎么设计"**（这本质上是给自己的 ADR）。如果还能加上第三个：每年用 24.1 的六个维度给自己做一次能力打分，看看今年长的是横还是竖。成长最怕的不是慢，而是三年下来发现一直在舒适区里横向打转。

## 24.6 架构决策速查大表

全书 23 章的内容，浓缩成一张"场景到方案"的速查表。它不替你思考——场景总有例外——但它保证你在讨论开始时不会从零起步：

| 场景 | 推荐方案 | 一句话理由 |
| ---- | ---- | ---- |
| 高并发读（读多写少） | 多级缓存：本地 + Redis | 命中率 95% 以上，数据库压力直接降一个量级 |
| 复杂且多变的业务规则 | DDD + 六边形架构 | 规则内聚进领域层，改规则不动外围 |
| 跨团队协作解耦 | 事件驱动 + 消息队列 | 团队间只依赖事件契约，不依赖彼此的实现 |
| 大促瞬时写流量 | 消息队列削峰 + 限流降级 | 把秒级尖峰摊平到分钟级消费 |
| 跨服务数据一致 | 本地消息表 + Saga 补偿 | 避开重量级分布式事务，可回滚可追踪 |
| 读写负载差异大 | 读写分离 / CQRS | 读写各自扩展，报表查询不再打扰交易 |
| 新业务快速验证 | 模块化单体 | 部署简单、试错成本低，业务死了不心疼 |
| 多团队并行开发 | 微服务 + 独立流水线 | 服务边界即团队边界，消除合并冲突 |
| 遗留系统替换 | 绞杀者模式 + 防腐层 | 不停机渐进替换，任何一步都可切回 |
| 服务能力对外暴露 | API 网关 | 认证、限流、灰度收口一处，服务保持纯粹 |
| 排障定位慢 | 统一日志 + 链路追踪 | MTTR 从小时级降到分钟级 |
| 配置散落、环境漂移 | 配置中心 + GitOps | Git 是唯一事实源，变更可审计可回滚 |
| 秒杀、抢购类洪峰 | Redis 预扣 + MQ 异步落库 | 内存判定扛住 10 万 QPS，落库异步慢慢来 |
| 单表数据量过亿 | 分库分表 / 冷热分离 | 先按时间冷热分层，多数查询根本不碰冷数据 |
| 流量昼夜波动大 | 容器化 + K8s HPA | 副本数随指标伸缩，只为实际用量付费 |
| 第三方接口不稳定 | 防腐层 + 熔断重试 + 兜底数据 | 故障隔离在自己这边，用户体验有底线 |
| 需要全文检索 | 独立搜索引擎（如 ES） | LIKE 走不了索引，搜索的事交给搜索引擎 |

使用这张表的正确姿势：先确认"场景"那一列真的匹配你的问题——**诊断错了场景，方案再对也是错的**。这正好是第 0 章心智模型的回响：先问切成了几块、怎么连的、为什么这么切，再谈具体技术。

落地前再过一遍决策四问：

1. 这个场景的质量属性优先级是什么？（性能优先还是一致性优先）
2. 表里的方案在什么条件下会失效？我的约束触发这些条件了吗？
3. 有没有更便宜的方案也能过及格线？
4. 这个决策要不要写成 ADR？（影响超过一个团队就要写）

## 24.7 架构评审 Checklist

每次架构评审前过一遍这十项。建议直接印在评审模板里，逐项打勾。评审者构成也有讲究：至少一位不写这块代码的架构师（防近亲繁殖）、一位 QA（质量属性视角）、一位 SRE（运维视角），业务方代表可选。

| # | 检查项 | 要问的问题 |
| ---- | ---- | ---- |
| 1 | 质量属性优先级 | 最重要的是哪个属性？量化目标是什么（P99、可用率）？ |
| 2 | 关键决策有 ADR | 备选方案是什么？为什么否决？负面后果接受了吗？ |
| 3 | 视图缩放级别 | 这张图是 C4 的哪一级？有没有把不同级别的概念画在一起？ |
| 4 | 边界与团队匹配 | 模块边界和团队结构一致吗（康威定律绕不过去）？ |
| 5 | 一致性方案明确 | 哪些操作强一致、哪些最终一致？补偿怎么做？ |
| 6 | 失败模式分析 | 最依赖的组件挂了会怎样？降级开关在哪里？ |
| 7 | 容量与扩展预案 | 预估 QPS 和存储量？撑不住时的预案是什么？ |
| 8 | 安全基线 | 认证授权、敏感数据加密、审计日志有方案吗？ |
| 9 | 可观测性 | 日志、指标、链路追踪三件套齐全吗？关键告警发给谁？ |
| 10 | 回滚与灰度 | 写出回滚步骤了吗？灰度从 1% 流量到全量的路径是什么？ |

十项全绿，这个方案的成熟度已经超过大多数线上系统；有红项不可怕，可怕的是没讨论过。

使用方式建议：评审前 24 小时把 checklist 发给评审者逐项预审，会上只讨论红项；每项允许三种结论——通过、有条件通过（写明条件与期限）、不通过。禁止"先过了吧，回头补"：没有期限的条件通过，约等于不通过。

## 24.8 全书术语表

最后一张表：30 个高频术语，一句话解释。读完这本书，这张表里的每个词你都应该能展开讲五分钟：

建议的用法：团队例会上不定期玩"术语接龙"——随机抽三个词，每人一句话解释，解释偏了就回对应章节重读。术语对齐的成本极低，收益却贯穿每一次架构沟通。

| 术语 | 一句话解释 |
| ---- | ---- |
| 架构 | 组件划分 + 组件关系 + 关键决策的总和 |
| 质量属性 | 系统做得好不好的非功能维度：性能、可用性、扩展性等 |
| 权衡 | 同时改善两个互相牵制的质量属性时必须做出的取舍 |
| C4 模型 | 用上下文、容器、组件、代码四级缩放描述架构的方法 |
| ADR | 架构决策记录：一个决策一个文件，写清背景、备选与后果 |
| 分层架构 | 按职责纵向切层、单向依赖的最经典组织方式 |
| 模块化单体 | 单进程部署 + 强制模块边界，被低估的起步形态 |
| 六边形架构 | 业务核心在内、外部依赖通过端口适配器接入的架构 |
| 事件驱动架构 | 组件通过发布/订阅消息异步协作的架构风格 |
| 微服务 | 按业务域拆分、可独立部署和伸缩的服务化架构 |
| CQRS | 命令与查询职责分离，读写模型分开设计 |
| 事件溯源 | 不存状态只存事件，当前状态由事件回放推导 |
| 限界上下文 | 一个领域模型适用的边界，DDD 划服务边界的单位 |
| 通用语言 | 业务与开发共用的同一套词汇，直接落进代码 |
| 聚合 / 聚合根 | 强一致绑定的对象组；聚合根是它对外的唯一入口 |
| 领域事件 | 已发生业务事实的记录，过去式命名，跨上下文协作的载体 |
| 绞杀者模式 | 新服务逐步包围旧系统、按模块替换直至旧系统退役 |
| 防腐层 | 在系统边界做翻译，挡住外部脏模型进入内部 |
| 技术债务 | 为赶进度欠下的设计妥协，之后每次改动都在还利息 |
| 适应度函数 | 写进 CI 的架构规则测试，违反即构建失败 |
| ATAM | 用效用树和权衡点系统评估架构的工业级方法 |
| 变更半径 | 一次典型需求需要触碰的模块或服务数量 |
| 康威定律 | 系统结构必然长得像组织的沟通结构 |
| 熔断 | 依赖持续失败时主动断开调用，防止雪崩蔓延 |
| 降级 | 压力过大时主动砍掉次要功能，保住核心链路 |
| 幂等 | 同一操作执行多次与执行一次效果相同，异步重试的前提 |
| Saga | 用一串本地事务加补偿操作替代分布式事务的模式 |
| 本地消息表 | 业务与消息同一事务落库，再异步投递，保证事件不丢 |
| 多级缓存 | 本地缓存加分布式缓存逐层挡流量，降低回源压力 |
| 缓存穿透 | 查询不存在的数据绕过缓存直击数据库，用空值或布隆器挡 |
| GitOps | Git 仓库作为唯一事实源，工具自动把集群状态向它对齐 |

## 本章小结

- 架构师分三类：应用架构师管单系统、解决方案架构师管跨系统集成、企业架构师管全公司版图
- 能力模型是 T 型：广度知道边界，深度提供判断力，深度靠定期下场写代码维持
- 向上沟通翻译成钱、时间和风险；跨团队推动先一对一收集顾虑再上会
- 共识三件套：ADR 写下来、评审会确认、原型让数据说话
- 五大误区：过度设计、追新、纸上架构师、用地位代替论据、只做加法
- 成长路径：写好模块、设计模块、主导评审、主导拆分、业务双视野，约五年一个循环
- 速查表和 checklist 不替代思考，它们保证讨论不从零起步
- 术语表是全书的索引：每个词都应能展开讲五分钟

走到这里，整本教程就讲完了。回头看书里反复出现的那句话——**架构 = 组件划分 + 组件关系 + 关键决策**——它不是定义，而是习惯：从今天起，面对任何系统，无论是别人的开源项目还是自己手上的老系统，先问三个问题：切成了几块？怎么连的？为什么这么切？回答得出，你已经具备架构师的眼睛；回答不出，你也已经知道该去哪里找了。架构不是一次性的设计，而是一场与业务一起生长的长期实践：演进时想好回滚，评估时盯着数字，决策时写下代价。愿你拆过的每个服务都拆得其所，欠下的每笔债都还得及时——我们江湖再见。
