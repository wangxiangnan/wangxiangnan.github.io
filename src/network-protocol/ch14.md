# 第14章：HTTP 深入——缓存、内容协商与 Cookie

## HTTP 缓存：让网络变快的魔法

HTTP 缓存是 Web 性能优化中最有效的手段之一。道理很简单：如果浏览器本地有一份资源的副本，而且这份副本还没过期，那就没必要再走一遍网络去服务器要——省下的不仅是带宽，还有延迟。

HTTP 缓存分为两种策略：

**强缓存（Freshness）**：浏览器自己判断缓存是否"新鲜"，根本不发请求。

- `Expires`：HTTP/1.0 的产物，指定一个绝对过期时间。比如 `Expires: Thu, 18 Jan 2024 12:00:00 GMT`。问题很明显——它依赖客户端和服务器时钟同步，如果客户端时间被改了，缓存判断就出错。
- `Cache-Control`：HTTP/1.1 引入的更强大的缓存指令。常用值包括：
  - `max-age=3600`：从响应生成起，3600 秒内有效（相对时间，不怕时钟不同步）
  - `no-cache`：每次使用前必须向服务器验证（不是"不缓存"，是"不信任本地缓存"）
  - `no-store`：完全不缓存，什么都不存（敏感数据用这个）
  - `public`：任何节点（CDN、代理、浏览器）都可以缓存
  - `private`：只有用户的浏览器可以缓存，中间节点不行
  - `immutable`：资源永远不会变（打包后的带 hash 的静态文件）

**协商缓存（Validation）**：浏览器不确定缓存是否新鲜，发一个请求去问服务器："我这边的版本还是最新的吗？"

- `Last-Modified` / `If-Modified-Since`：基于最后修改时间。服务器响应带上 `Last-Modified: Fri, 12 Jan 2024 10:00:00 GMT`，浏览器下次请求带上 `If-Modified-Since: Fri, 12 Jan 2024 10:00:00 GMT`。如果资源没变，服务器返回 `304 Not Modified`，不带消息体。
- `ETag` / `If-None-Match`：基于资源的"指纹"。ETag 通常是资源内容的哈希值，比如 `ETag: "a3f2b8c"`。比 `Last-Modified` 更精确——文件可能在一秒内被修改了多次，但内容不变时 ETag 不变。

一个完整的缓存协商流程：

```
第一次请求：
GET /style.css HTTP/1.1
Host: www.example.com

响应：
HTTP/1.1 200 OK
Content-Type: text/css
Content-Length: 8234
Last-Modified: Fri, 12 Jan 2024 10:00:00 GMT
ETag: "a3f2b8c"
Cache-Control: max-age=0

第二次请求（协商缓存）：
GET /style.css HTTP/1.1
Host: www.example.com
If-Modified-Since: Fri, 12 Jan 2024 10:00:00 GMT
If-None-Match: "a3f2b8c"

响应：
HTTP/1.1 304 Not Modified
ETag: "a3f2b8c"
```

304 响应没有消息体，浏览器直接使用本地缓存。这就是一次成功的协商缓存——用极小的网络开销验证了资源未变化。

## 缓存策略的工程权衡

为什么不能把所有东西都缓存到天荒地老？因为**一致性**问题。如果服务器更新了页面，但用户看到的还是旧版本，那缓存就从优化变成了 Bug。

工程中的典型策略：

- **HTML 页面**：`Cache-Control: no-cache`——每次都要验证，确保用户看到最新内容
- **带哈希的静态资源**（如 `app.a3f2b8c.js`）：`Cache-Control: max-age=31536000, immutable`——文件名里有哈希，内容变了文件名就变，所以可以放心缓存一年
- **API 响应**：`Cache-Control: no-store` 或 `private, no-cache`——通常不应该缓存动态数据
- **图片和视频**：适度缓存，比如 `max-age=86400`（一天）

**"新鲜度"（Freshness）**是 HTTP 缓存的核心概念——一个响应在 `max-age` 指定的时间内是"新鲜的"，浏览器可以直接使用。过了这个时间就变成"陈旧的"（Stale），需要重新验证。

## 内容协商（Content Negotiation）

同一个 URL，不同客户端可能想要不同的内容。手机想要移动版页面，法国用户想要法语内容，现代浏览器想要 WebP 图片而旧浏览器只能要 JPEG。HTTP 通过**内容协商**机制解决这个问题。

客户端通过请求头部告诉服务器自己的偏好：

```http
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Accept-Encoding: gzip, deflate, br
```

`q` 值是**权重（Quality Value）**，范围 0 到 1，默认 1。上面的 `Accept` 头部表示：最想要 `text/html` 或 `application/xhtml+xml`，如果不行，`application/xml` 也行但偏好度只有 0.9，最后 `*/*`（任意类型）的偏好度是 0.8。

服务器根据这些偏好选择最合适的内容返回，并在响应中说明自己选了什么：

```http
Content-Type: text/html; charset=UTF-8
Content-Language: zh-CN
Content-Encoding: gzip
Vary: Accept, Accept-Language, Accept-Encoding
```

`Vary` 头部告诉缓存系统：同一个 URL 的不同请求，如果这些头部不同，可能会得到不同的响应，所以缓存时要区分对待。

## 压缩传输

HTTP 内容压缩可以显著减少传输体积。主流压缩算法：

- **gzip**：最古老也最广泛，几乎所有浏览器和服务器都支持。压缩率中等。
- **deflate**：使用 zlib 或 deflate 算法，比 gzip 稍小但兼容性差一些。
- **br（Brotli）**：Google 开发的现代压缩算法，专为 Web 内容优化。对文本类资源（HTML/CSS/JS）压缩率比 gzip 高 15-25%。需要 HTTPS 才能使用（浏览器只在安全连接下启用 Brotli）。

压缩通常用于文本类资源（HTML、CSS、JS、JSON），对图片和视频这类已经是压缩格式的资源不会再次压缩（压缩了也不会更小，反而浪费 CPU）。

## Cookie 与 Session：HTTP 无状态下的状态管理

前面简单提到了 Cookie，现在深入理解它的完整机制。

**Cookie 的工作流程**：

1. 服务器在响应中设置 Cookie：

```http
Set-Cookie: session_id=abc123; Path=/; Domain=.example.com; HttpOnly; Secure; SameSite=Lax
```

1. 浏览器存储这个 Cookie，后续向匹配 `Domain` 和 `Path` 的请求自动附带：

```http
Cookie: session_id=abc123
```

**Set-Cookie 的关键属性**：

- **Domain**：指定 Cookie 对哪些域名有效。`.example.com` 表示所有 `example.com` 的子域名都能读到。如果不设置，默认为当前请求的域名（不含子域名）。
- **Path**：指定 Cookie 对哪些路径有效。`Path=/` 表示所有路径都能读到。`Path=/api` 则只有以 `/api` 开头的路径才能读到。
- **HttpOnly**：禁止 JavaScript 通过 `document.cookie` 读取这个 Cookie。这是防止 XSS（跨站脚本）攻击窃取 Cookie 的重要手段。Session ID 必须设置 HttpOnly。
- **Secure**：Cookie 只能通过 HTTPS 传输。在 HTTP 连接上不会被发送。
- **SameSite**：控制跨站请求是否携带 Cookie，防止 CSRF（跨站请求伪造）攻击：
  - `Strict`：任何跨站请求都不携带
  - `Lax`（现代浏览器默认）：顶级导航（点击链接跳转）携带，AJAX 跨站请求不携带
  - `None`：所有请求都携带，但必须同时设置 `Secure`

**Session 的实现**：Cookie 只存一个 `session_id`，真正的用户数据存在服务器端（内存、数据库、Redis 等）。这是一个经典的设计——客户端轻量，服务端掌控数据。

另一种方案是把状态全部放在客户端——**JWT（JSON Web Token）**。JWT 是一个经过签名的 JSON 对象，包含了用户信息和过期时间，服务器不需要存储任何东西。它的好处是无状态扩展（多台服务器不需要共享 Session），但缺点是签发后无法主动撤销。

## 编程实践：用 Python requests 库演示缓存行为

```python
import requests
import time

def demo_cache():
    """演示 HTTP 缓存行为"""
    session = requests.Session()
    
    # 目标 URL - 使用 httpbin 的缓存接口
    url = "https://httpbin.org/cache/60"  # 服务器设置 max-age=60
    
    print("=== 第一次请求 ===")
    resp1 = session.get(url)
    print(f"Status: {resp1.status_code}")
    print(f"Cache-Control: {resp1.headers.get('Cache-Control')}")
    print(f"Date: {resp1.headers.get('Date')}")
    print(f"Body length: {len(resp1.content)} bytes")
    print()
    
    print("=== 第二次请求（应该命中缓存，requests 默认不做客户端缓存） ===")
    resp2 = session.get(url)
    print(f"Status: {resp2.status_code}")
    print(f"From-Cache: {'from_cache' in str(resp2.raw)}")
    print()
    
    # 手动实现条件请求
    print("=== 手动发送条件请求（If-None-Match） ===")
    etag = resp1.headers.get('ETag')
    if etag:
        print(f"Using ETag: {etag}")
        resp3 = session.get(url, headers={'If-None-Match': etag})
        print(f"Status: {resp3.status_code}")  # 应该是 304
        print(f"Body length: {len(resp3.content)} bytes")  # 应该是 0
    
    print()
    
    # 演示 no-cache 行为
    print("=== 请求 no-cache 资源 ===")
    url_nocache = "https://httpbin.org/response-headers?Cache-Control=no-cache"
    resp4 = session.get(url_nocache)
    print(f"Cache-Control: {resp4.headers.get('Cache-Control')}")
    print("即使设置了 no-cache，响应仍然可以被存储，")
    print("但每次使用前必须向服务器验证。")

demo_cache()
```

这个脚本演示了：正常请求的缓存头部、ETag 协商缓存（304 响应）、以及 `no-cache` 的实际含义。

## 抓包实践：观察浏览器如何利用 304 Not Modified

打开 Wireshark，在浏览器中访问一个已经访问过的网站（比如你经常用的博客）。过滤 `http` 协议，你会看到大量的 `304 Not Modified` 响应：

```
请求：
GET /static/css/main.css HTTP/1.1
Host: blog.example.com
If-None-Match: "7d2-5c8a3f1e2b400"
If-Modified-Since: Thu, 11 Jan 2024 08:20:00 GMT

响应：
HTTP/1.1 304 Not Modified
ETag: "7d2-5c8a3f1e2b400"
Date: Mon, 15 Jan 2024 09:00:00 GMT
Connection: keep-alive
```

注意 304 响应没有 `Content-Length` 和消息体——浏览器直接使用本地缓存的文件。一个包含大量静态资源的页面，如果缓存策略合理，二次访问时大部分请求都会命中 304 或强缓存，网络传输量可能从几 MB 降到几 KB。

在 Wireshark 的 `Statistics > HTTP` 面板中，你可以看到按状态码分类的请求统计。一个优化良好的网站，304 和 200 的比例可能接近 1:1。
