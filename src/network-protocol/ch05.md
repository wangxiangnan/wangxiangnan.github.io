## 5.1 封装的完整过程：以一次 HTTP 请求为例

当你在浏览器中输入 `http://example.com` 并按下回车，一段数据经历了怎样的旅程才变成网线（或无线信号）上的电信号？这个过程叫做**封装（Encapsulation）**——数据从上到下，每经过一层就被包一层信封。让我们跟踪一次 HTTP GET 请求，数清每一层的字节账。

**第 1 步：应用层产生数据**

浏览器构造一个 HTTP 请求：

```
GET / HTTP/1.1\r\n
Host: example.com\r\n
User-Agent: Mozilla/5.0\r\n
Accept: text/html\r\n
\r\n
```

这段文本大约 85 字节。这就是**应用层 PDU**。

**第 2 步：传输层——加上 TCP 报头**

TCP 在数据前加上 20 字节的 TCP 报头（不含选项），包含：

```
Source Port:       52341 (客户端随机选择的端口)
Destination Port:  80    (HTTP 标准端口)
Sequence Number:   1     (字节流的起始序号)
Ack Number:        1     (期望收到的下一个字节序号)
Flags:             PSH, ACK
Window Size:       65535
Checksum:          0x3f4a
```

现在数据变成了 85 + 20 = 105 字节的 **TCP 段（Segment）**。

**第 3 步：网络层——加上 IP 报头**

IP 在 TCP 段前加上 20 字节的 IP 报头：

```
Version:           4
IHL:               5 (20 bytes)
Total Length:      125 (105 + 20)
TTL:               64
Protocol:          6 (TCP)
Source IP:         192.168.1.100
Destination IP:    93.184.216.34
```

现在数据变成了 125 字节的 **IP 数据报（Datagram/Packet）**。

**第 4 步：数据链路层——加上以太网帧头和帧尾**

Ethernet 在 IP 包前加上 14 字节的帧头，末尾加上 4 字节的 FCS：

```
Destination MAC: 00:0c:29:d1:e2:f3 (默认网关的 MAC 地址)
Source MAC:      00:1a:2b:3c:4d:5e (本机网卡 MAC 地址)
EtherType:       0x0800 (IPv4)
... IP 包（125 字节）...
FCS:             0x8a3b5c2d
```

现在数据变成了 14 + 125 + 4 = 143 字节的 **以太网帧（Frame）**。

**第 5 步：物理层——变成信号**

143 字节的帧被转换成 1144 个比特，然后通过物理介质发送出去：

- 如果是铜缆，变成电平变化
- 如果是光纤，变成光脉冲
- 如果是 Wi-Fi，变成调制的电磁波

整个过程可以用一张图概括：

```
应用层:    [GET / HTTP/1.1 ...]                         85 bytes
                ↓
传输层:    [TCP Header | GET / HTTP/1.1 ...]            105 bytes
                ↓
网络层:    [IP Header | TCP Header | GET / ...]          125 bytes
                ↓
链路层:    [ETH Hdr | IP Hdr | TCP Hdr | GET... | FCS]  143 bytes
                ↓
物理层:    01011010011101001011001...（比特流）           1144 bits
```

## 5.2 PDU：每层的「数据单元」叫什么

每层处理的数据有一个专门的名称，叫 **PDU（协议数据单元）**。记住这些名称有助于你在阅读文档和讨论时更精确：

| 层 | PDU 名称 | 英文 |
| ---- | ---------- | ------ |
| 应用层 | 消息（Message） | Message |
| 传输层 | 段（Segment，TCP）/ 数据报（Datagram，UDP） | Segment / Datagram |
| 网络层 | 包/数据报（Packet / Datagram） | Packet |
| 数据链路层 | 帧（Frame） | Frame |
| 物理层 | 比特（Bit） | Bit |

在日常交流中，「包」（Packet）常被用来泛指任何层的数据单元，但严格来说，Packet 特指网络层的 PDU。

## 5.3 MTU 与分片：为什么大包要被拆、拆了怎么重组

**MTU（Maximum Transmission Unit，最大传输单元）**是数据链路层对帧体（Payload）大小的限制。以太网的 MTU 是 1500 字节，这意味着一个以太网帧最多能携带 1500 字节的 IP 数据。

为什么有这个限制？历史原因是：早期的以太网使用同轴电缆作为共享介质，帧越长，占用介质的时间越长，其他设备等待的时间就越长。而且，帧越长，出错的概率越大——如果一个 10000 字节的帧在传输过程中有一个 bit 出错，整个帧都要重传，太浪费了。

如果 IP 包大于 MTU 怎么办？两种处理方式：

**1. IP 分片（Fragmentation）：** IP 层把一个大的 IP 包拆成多个小的 IP 包（分片），每个分片都能装进一个以太网帧。分片在**目的端**重组（注意：不是在中间路由器重组）。

```
原始 IP 包 (3000 字节数据):
[IP Header | 3000 bytes data]

分片 1: [IP Header (MF=1, Offset=0)    | 1480 bytes data]
分片 2: [IP Header (MF=1, Offset=185)  | 1480 bytes data]
分片 3: [IP Header (MF=0, Offset=370)  | 40 bytes data]
```

Offset 以 8 字节为单位：Offset=185 表示这个分片从原始数据的第 185×8 = 1480 字节开始。三个分片共享同一个 Identification（4.2 的分片三兄弟在这里登场）。

分片有一个致命弱点，也是「先猜再读」第一问的答案：**只要丢失任何一个分片，整个原始包就要作废重传**——中间路由器不负责重组，目的端凑不齐所有分片就只能把已收到的全部丢弃。丢 1/3 等于丢 3/3，重传又把 3 个分片全部重发一遍，丢包率被放大。

**2. 路径 MTU 发现（PMTUD）：** 更现代的做法是避免分片。发送方在 IP 报头中设置 DF（Don't Fragment）位，如果某个路由器发现包太大无法转发，就发回一个 ICMP「Fragmentation Needed」消息，告诉发送方「请把包弄小一点」（消息里带上了那一跳的 MTU 值）。发送方收到后减小包的大小，重新发送。

TCP 通常使用 PMTUD 来自动发现路径上的最小 MTU，从而避免 IP 分片。「先猜再读」第三问的答案也在这里：决定包最大能多大的是**整条路径上 MTU 最小的那一段**——这就是「路径 MTU（Path MTU）」，木桶的最短板。

> [!TIP] MTU 家族与它们在本书/本系列的位置
> MTU（链路层上限，1500）、MSS（TCP 分段上限 = MTU − 40，第11章）、路径 MTU（全链路最短板，本章）。它们引发的实操坑——比如 VPN TUN 网卡默认 MTU 9000 撞上 WSL2 镜像链路导致「认证能过、传输卡死」的真实踩坑——完整案例与修复步骤见本系列《手搓 VPN》教程第 7 章（[/vpn/ch07](/vpn/ch07)）；本章只负责把机制讲清：**PMTUD 的命脉是那条 ICMP 消息必须能送回来**。

## 5.4 PMTUD 失效：当「请改小」的信号送不回来

PMTUD 的全部前提是：ICMP「Fragmentation Needed」消息能够穿越网络回到发送方。而现实中，这条消息经常被杀死：

- **防火墙一刀切丢弃 ICMP**：很多管理员把 ICMP 当攻击向量整体屏蔽，PMTUD 的信号随之陪葬。
- **隧道/NAT 链路不转发或改写分片信息**：信号即使回来，携带的 MTU 值也可能已经失真。
- **发送方到不了信号来源**：信号来自路径中间的某台路由器，而有些中间盒会丢弃「非 TCP 会话」的报文。

信号送不回来会发生什么？发送方坚信自己的大包能过，路由器一遍遍丢弃、一遍遍「沉默拒绝」——连接既不报错也不超时，小包一切正常、大包永远卡死。这就是经典的 **PMTUD 黑洞**：你发出去的包掉进了一个不回话的洞。

现实中它相当常见，症状极具迷惑性：SSH 登录正常（小包能过），但 `git push` 传大文件挂死、网页打开一半卡住、大图加载不出来。诊断思路也由此而来——小包通、大包死，先怀疑路径 MTU，手动把 MTU 降下来（比如 1400）再试，往往一击即中。《手搓 VPN》教程 7.2.1 的 WSL2 案例就是此类问题的完整标本。

## 5.5 解封装：接收端的反向过程

数据到达接收端后，经历与封装完全相反的过程：

1. **物理层**接收信号，还原为比特流，交给数据链路层
2. **数据链路层**检查目的 MAC 是否是自己（或广播/组播），检查 FCS 校验，无误后去掉帧头和帧尾，把 IP 包交给网络层
3. **网络层**检查目的 IP 是否是自己，检查 IP 校验和，去掉 IP 报头，根据 Protocol 字段判断上层协议（TCP/UDP/ICMP），把 TCP 段交给传输层
4. **传输层**根据目的端口号判断该交给哪个应用程序，去掉 TCP 报头，把数据交给应用层
5. **应用层**解析 HTTP 请求/响应，完成数据处理

整个过程是严格的「拆信封」链：每层只处理自己的报头，然后把剩下的内容交给上一层。这就像收到一个俄罗斯套娃——拆掉最外面的壳，里面还有一个壳，再拆，再拆，直到拿到最里面的东西。

## 5.6 编程实践：用 Scapy 构造一个 IP 包

Scapy 是 Python 中强大的网络数据包操作库。以下示例展示如何手动构造一个 IP 包并逐层封装（发送需要 root 权限，Linux 环境）：

```python
# pip install scapy
from scapy.all import *

def craft_and_inspect():
    """构造一个自定义 IP 包并检查其结构"""

    # 构造一个 TCP SYN 包
    packet = (
        IP(
            src="192.168.1.100",
            dst="93.184.216.34",
            ttl=64,
            id=0x4a3b,
            flags="DF"          # Don't Fragment
        ) /
        TCP(
            sport=52341,
            dport=80,
            flags="S",          # SYN
            seq=1000,
            window=65535
        )
    )

    # 查看包的结构
    print("=== 包结构 ===")
    packet.show()

    # 将包序列化为字节
    raw_bytes = bytes(packet)
    print(f"\n=== 序列化后的包（{len(raw_bytes)} 字节）===")
    print(raw_bytes.hex())

    # 手动解析 IP 报头
    ip_header = raw_bytes[:20]
    version_ihl = ip_header[0]
    print(f"\n=== IP 报头字段 ===")
    print(f"Version: {(version_ihl >> 4)}")
    print(f"IHL: {version_ihl & 0x0F}")
    print(f"Total Length: {struct.unpack('!H', ip_header[2:4])[0]}")
    print(f"TTL: {ip_header[8]}")
    print(f"Protocol: {ip_header[9]}")

    return packet


def demonstrate_encapsulation():
    """演示封装过程：逐层构建"""

    print("=== 逐层封装演示 ===\n")

    # 第 1 步：应用层数据
    app_data = b"GET / HTTP/1.1\r\nHost: example.com\r\n\r\n"
    print(f"应用层 PDU: {len(app_data)} 字节")

    # 第 2 步：加上 TCP 头
    tcp_segment = TCP(sport=52341, dport=80, flags="PA", seq=1) / Raw(app_data)
    tcp_bytes = bytes(tcp_segment)
    print(f"TCP 段:     {len(tcp_bytes)} 字节 (+{len(tcp_bytes) - len(app_data)} 字节 TCP 头)")

    # 第 3 步：加上 IP 头
    ip_packet = IP(src="192.168.1.100", dst="93.184.216.34", ttl=64) / tcp_segment
    ip_bytes = bytes(ip_packet)
    print(f"IP 包:      {len(ip_bytes)} 字节 (+{len(ip_bytes) - len(tcp_bytes)} 字节 IP 头)")

    # 第 4 步：加上 Ethernet 头
    eth_frame = Ether(src="00:1a:2b:3c:4d:5e", dst="00:0c:29:d1:e2:f3") / ip_packet
    eth_bytes = bytes(eth_frame)
    print(f"以太网帧:   {len(eth_bytes)} 字节 (+{len(eth_bytes) - len(ip_bytes)} 字节帧头/尾)")

    print(f"\n封装开销: {len(eth_bytes) - len(app_data)} 字节 "
          f"({(len(eth_bytes) - len(app_data)) / len(eth_bytes) * 100:.1f}%)")


# 需要 root 权限才能发送原始包
def send_custom_packet():
    """发送自定义包（需要 root/sudo）"""
    packet = IP(dst="127.0.0.1", ttl=64) / ICMP() / "Hello from Python!"
    response = sr1(packet, timeout=2, verbose=False)
    if response:
        print(f"收到回复: {response.summary()}")
    else:
        print("未收到回复（超时）")


if __name__ == '__main__':
    import struct
    craft_and_inspect()
    print()
    demonstrate_encapsulation()
```

运行 `demonstrate_encapsulation()` 的输出：

```
=== 逐层封装演示 ===

应用层 PDU: 38 字节
TCP 段:     58 字节 (+20 字节 TCP 头)
IP 包:      78 字节 (+20 字节 IP 头)
以太网帧:   92 字节 (+14 字节帧头/尾)

封装开销: 54 字节 (58.7%)
```

注意到了吗？只有 38 字节的有效数据，却需要 92 字节的帧来传输——**封装开销高达 58.7%！** 这就是协议栈的代价。当然，实际应用中数据通常远大于 38 字节（一个 HTTP 响应可能有几千到几万字节），此时封装开销占比会大幅降低。

## 5.7 抓包实践：亲眼看一次分片与 PMTUD

第4章埋的实验现在做。第一个实验：发一个超过 MTU 的 ping 包，观察分片：

```bash
# Linux/macOS
ping -s 3000 -c 1 8.8.8.8

# Windows
ping -l 3000 8.8.8.8
```

在 Wireshark 中过滤 `ip.id == <该包的ID>`（或直接看相邻的包），你会看到三个分片：

```
No.  Protocol  Info
1    IPv4      192.168.1.100 → 93.184.216.34  Fragment (offset=0, More Fragments)
2    IPv4      192.168.1.100 → 93.184.216.34  Fragment (offset=1480, More Fragments)
3    IPv4      192.168.1.100 → 93.184.216.34  Fragment (offset=2960)
```

逐个展开验证 5.3 的说法：三个分片 Identification 相同、Fragment Offset 以 8 字节为单位递增、只有最后一个分片的 MF 位为 0。数据 3000 字节被拆成 1480 + 1480 + 40（每个分片的载荷上限是 MTU 1500 减去 20 字节 IP 报头）。

第二个实验：禁止分片，逼出 PMTUD：

```bash
# Linux：-M do 表示设置 DF 位
ping -M do -s 2000 8.8.8.8

# Windows：-f 等价于 DF 位
ping -f -l 2000 8.8.8.8
```

在能正常回 ICMP 的网络里，你会立刻看到 `Message too long`（或 Wireshark 里的 ICMP「Fragmentation Needed」）——这就是 5.3 说的那条「请改小」信号。如果网络恰好屏蔽了 ICMP，ping 会一片安静地超时——恭喜，你亲眼见到了 5.4 的 PMTUD 黑洞雏形。逐渐减小 `-s` 的值直到能通，那个临界值减去 28（IP+ICMP 报头）就是这条路径的实际 Path MTU。

## 本章小结

- 封装是从上到下逐层加信封：85B 消息 → 105B 段 → 125B 包 → 143B 帧 → 1144 bits，接收端严格逆序拆封。
- 每层 PDU 有专名：Message、Segment/Datagram、Packet、Frame、Bit；「包」泛指时别忘它严格属于网络层。
- 封装有开销：38 字节正文要 54 字节信封来运；数据越大开销占比越低。
- MTU 1500 是链路层对载荷的硬限制，根源是共享介质时代「长帧占用久、错一 bit 全帧重传」。
- 分片在源端拆、目的端组：靠共用的 Identification、MF 位与 8 字节粒度的 Offset 重组。
- 分片的致命弱点：丢一个分片等于丢整包，丢包率被成倍放大——所以现代 TCP 首选 PMTUD 避分片。
- PMTUD 靠 ICMP「Fragmentation Needed」把路径最短板（Path MTU）告知发送方；信号被防火墙或隧道链路杀死就形成 PMTUD 黑洞——小包通、大包死的经典病根。
- 诊断口诀：小包通、大包死，先怀疑路径 MTU，降 MTU（如 1400）一试便知。
