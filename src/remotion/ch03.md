## 3.1 音频先行——时间戳是第一公民

「先做动画再配音」和「先配音再做动画」，产出的流程完全不同：

| 维度 | 先动画后配音 | 音频先行（本教程） |
| ---- | ---- | ---- |
| 时长决定者 | 动画做到哪算哪，配音迁就画面 | 音频 8.81 秒，总帧 283 帧由它决定 |
| 字幕同步 | 手动对齐，逐句调 | 词级时间戳直接驱动，天然对齐 |
| 改文案 | 重新对齐所有画面 | 重跑流水线，画面自动适配 |
| 适合 | 艺术创作 | 自动化、批量生产 |

「音频先行」的意思是：**音频及其时间戳是整个项目里唯一的第一手数据，画面全部是它的下游**。贯穿示例的每一个视觉元素都能指回某个时间戳——字幕高亮对应 `word.start`，场景切换对应 `sentence.start / sentence.end`，总帧数对应 `duration`。这条依赖链是 3.3 到 3.6 四个小节的主线。

先修自检：音频从哪来不重要（任何 TTS、任何配音软件，只要能导出逐词时间），本书选 Edge-TTS 是因为一次请求同时返回音频和词级时间戳，流水线最短。

## 3.2 词级时间戳——Edge-TTS 的 100ns 世界

Edge-TTS 对文本「今天是2026年的冬天，来到北京已经接近15年。又到了临近年末的日子，冬天来临了。」返回的 `out/timestamps.json` 结构如下（节选）：

```text
{
  "voice": "zh-CN-XiaoxiaoNeural",
  "duration": 8.81,                    ← 音频总长（秒）
  "words": [                           ← 词级时间戳，共 21 个
    { "text": "今天",   "start": 0.1,    "end": 0.5 },
    { "text": "2026",   "start": 0.7625, "end": 1.4125 },
    { "text": "冬天",   "start": 1.6625, "end": 2.175 },
    ……                                  ← 中间省略 15 个词
    { "text": "了",     "start": 8.025,  "end": 8.2375 }
  ],
  "sentences": [                       ← 句级时间戳，共 2 个
    { "text": "今天是2026年的冬天，来到北京已经接近15年。",
      "start": 0.1,   "end": 5.225,  "words": [ …… ] },
    { "text": "又到了临近年末的日子，冬天来临了。",
      "start": 5.175, "end": 8.75,   "words": [ …… ] }
  ]
}
```

两个工程细节值得注意：

- **精度换算**：TTS 内部用 100 纳秒为单位的 tick 计时（Windows FILETIME 习惯），换算成秒后出现 `0.7625`、`8.2375` 这类四位小数。换算公式只有一行：`秒 = tick ÷ 10⁷`；
- **数据是脏的**。句二起点 5.175 秒早于句一终点 5.225 秒——TTS 的句子边界带 50 毫秒重叠（句尾静音的归属问题）。这个重叠不会自己消失，3.4 的场景划分必须消化它，否则会在某一天算出负时长。

## 3.3 时间戳即 props——--props 与 calculateMetadata

Remotion 的组件不吃特殊的数据格式，就是普通 React props。流水线把 timestamps.json 整个喂给组件：

```bash
npx remotion render remotion/index.ts WinterVideo \
  --props=out/timestamps.json out/video.mp4
```

```tsx
// types.ts —— props 类型与 timestamps.json 逐字段对应
export type Word = { text: string; start: number; end: number };
export type Sentence = { text: string; start: number; end: number; words: Word[] };
export type VideoProps = {
  voice: string;
  duration: number;      // 8.81
  words: Word[];         // 21 个
  sentences: Sentence[]; // 2 个
};
```

时长在第一章出现过一次，现在它有了明确的职责——`calculateMetadata` 用音频时长算总帧数：

```tsx
const TAIL = 0.6;  // 音频播完后定格 0.6 秒再结束

export function getDurationInFrames(props: { duration: number }): number {
  return Math.max(1, Math.ceil((props.duration + TAIL) * FPS));
}
// (8.81 + 0.6) × 30 = 282.3 → 283 帧
```

为什么留 0.6 秒尾帧：字幕与结尾卡需要在语音结束后停留一瞬，否则视频戛然而止。**尾帧时长也进了帧数公式**，于是「音频一秒不多一秒不少地铺满视频」由数学保证，而不是靠手感调。

## 3.4 场景划分——getScenePlan 单一来源

三个场景（标题卡、每句一张大字卡、结尾卡）的边界全部换算成帧：

```text
标题卡终点 = round(句一.end × 30)   = round(5.225 × 30)  = 157
句子卡起点 = round(句二.start × 30) = round(5.175 × 30)  = 155 → 修正为 157
结尾卡起点 = round(句二.end × 30)   = round(8.75 × 30)   = 263
```

第二行出现了本章开头埋的脏数据：句二的原始起帧 155 **早于**标题卡终点 157。直接使用会算出「句子卡比标题卡更早开始」的矛盾，所以场景划分有一条铁律：**每个场景的起点不得早于前一个场景的起点**（单调钳制）——重叠的 50 毫秒按「先到先得」归前一个场景。

完整划分逻辑收敛为一个函数，它是全项目场景帧数的**唯一来源**：

```tsx
export function getScenePlan(sentences: Sentence[], duration = 10): ScenePlan[] {
  const total = getDurationInFrames({ duration });
  const titleEnd = Math.max(1,
    Math.round((sentences[0]?.end ?? duration * 0.4) * FPS));
  let cursor = titleEnd;
  const cards = sentences.slice(1).map((sentence) => {
    cursor = Math.max(cursor, Math.round(sentence.start * FPS));  // 单调钳制
    return { sentence, start: cursor };
  });
  const endStart = Math.max(cursor,
    Math.round((sentences[sentences.length - 1]?.end ?? duration * 0.85) * FPS));
  // ……据此生成 [标题卡, 句子卡×n, 结尾卡] 三段式 plan（含 3.5 的转场时长）
}
```

> [!NOTE] 为什么必须是「单一来源」
> 这个函数救过一次真 bug：早期版本里场景边界在 `getScenePlan` 与主组件各算了一遍——`getScenePlan` 里对重叠句做了钳制（155 → 157），主组件里没有（仍是 155）。句子卡的时长因此多算 2 帧，连锁反应把结尾卡起点从 263 推迟到 265：Studio 里看是「结尾卡晚 0.07 秒出现」，拆帧对比才发现。教训：**凡是「帧数」的推算，全局只允许存在一份实现**，其他地方 import 它，绝不复写。

## 3.5 转场踩点——TransitionSeries 的重叠语义

场景之间用 `@remotion/transitions` 的淡入淡出衔接：

```tsx
<TransitionSeries>
  {plan.flatMap((scene, i) => {
    const seq = (
      <TransitionSeries.Sequence key={scene.kind} durationInFrames={scene.duration}>
        {scene.kind === "title" ? <TitleCard />
          : scene.kind === "sentence" ? <SentenceCard sentence={scene.sentence} />
          : <EndCard />}
      </TransitionSeries.Sequence>
    );
    return i === 0 ? [seq] : [
      <TransitionSeries.Transition key={`tr-${i}`}   // 15 帧线性淡入淡出
        timing={linearTiming({ durationInFrames: TRANSITION_FRAMES })}
        presentation={fade()} />,
      seq,
    ];
  })}
</TransitionSeries>
```

关键在于 TransitionSeries 的计时语义：**转场不额外占用时间，而是让相邻两个场景在重叠期内同时渲染**——前一个场景淡出的那 15 帧，恰好是后一个场景淡入的 15 帧。因此加了转场，总帧数反而变短：283 − 2×15 = …不对，是**各场景的 durationInFrames 已经把转场帧数预先加在里面**：

于是得到踩点公式。设某场景在时间轴上的**名义起点**为 `start`（由 getScenePlan 给出），它的 `durationInFrames` 必须是：

```text
duration = 下一场景名义起点 − 本场景名义起点 + TRANSITION_FRAMES
```

推导只有两步：TransitionSeries 里每个场景的**实际显示起点** = 前序所有场景 duration 之和 − 转场数 × TRANS；要让实际起点等于名义起点，就必须在每个 duration 里预先把被「吃掉」的 TRANS 加回来。逐场景核对贯穿示例：

| 场景 | 名义起点 | duration 计算 | duration | 实际显示区间 |
| ---- | ---- | ---- | ---- | ---- |
| 标题卡 | 0 | 157 − 0 + 15 | 172 | [0, 172) |
| 句子卡 | 157 | 263 − 157 + 15 | 121 | [157, 278) |
| 结尾卡 | 263 | 283 − 263 | 20 | [263, 283) |

 TransitionSeries 还有一条硬约束：**转场帧数不得长于相邻任一场景的 duration**（20 帧的结尾卡容纳 15 帧转场，仅剩 5 帧余量）。若某句只有一两个字导致场景过短，就要按比例压缩 TRANSITION_FRAMES，否则渲染直接报错。取整误差也有预算：`round` 造成的半帧偏差会沿场景链累计，两三个场景内不超过 1 帧（33ms），肉眼不可见——但不加钳制的重叠时间戳会让误差变成负时长，这就是 3.4 单调钳制的意义。

## 3.6 卡拉OK字幕——全局时间 vs 局部时间

`useCurrentFrame()` 有一个本章最重要的细节：**在 Sequence 内部，它返回的是相对该场景起点的局部帧号**——句子卡名义起点 157 帧，内部第 1 帧看到的 `useCurrentFrame()` 是 0 而不是 157。这个设计让卡片内部的入场动画写起来自然（`spring({ frame })` 从 0 开始弹），但也埋了一个坑：**字幕不能放进场景里**。

字幕是全程存在的——转场进行时，旧场景淡出、新场景淡入，字幕必须纹丝不动地高亮到正确的词。所以字幕挂在根组件、用根级的全局 t 驱动：

```tsx
// Subtitle.tsx —— 挂在 WinterVideo 根级，transition 管不到它
export const Subtitle: React.FC<{ sentences: Sentence[]; t: number }> = ({ sentences, t }) => {
  const s = sentences.find((s) => t >= s.start && t < s.end) ?? sentences[sentences.length - 1];
  return (
    <div id="subtitle">
      {s?.words.map((w, i) => (
        <span key={i} className={t >= w.start && t < w.end ? "w current"
          : t >= w.end ? "w spoken" : "w"}>
          {w.text}                          {/* 三态：未读 / 已读 / 正在读 */}
        </span>
      ))}
    </div>
  );
};
```

两行代码对应两张时间表：句子选择用 `sentences`（句级），高亮判断用 `s.words`（词级）——`t >= w.start && t < w.end` 即「这个词正在被读出」，21 个词逐帧判定，与配音的偏差为零，因为**它们本来就是同一份数据**。

| 组件 | 用哪把时间 | 为什么 |
| ---- | ---- | ---- |
| 场景卡（标题/句子/结尾） | Sequence 局部帧 | 入场动画天然从 0 开始，无需关心自己在第几帧 |
| 字幕、进度条、雪花 | 根级全局 t | 必须横跨转场连续存在，不随场景生灭 |

句间隙（5.23 秒前后 50 毫秒两句都不在区间内）用兜底逻辑处理：`?? sentences[last]`——显示最后一个句子的全部已读状态，避免字幕闪空。

## 本章小结

- **音频先行**：音频与词级时间戳是唯一的第一手数据，画面全部是它的下游；改文案 = 重跑流水线
- TTS 时间戳由 100ns tick 换算而来；数据可能脏（句首尾重叠 50ms），场景划分必须单调钳制
- 时间戳整个文件通过 `--props` 注入组件，`calculateMetadata` 据音频时长算总帧（含 0.6 秒尾帧：283 帧）
- 场景帧数全局只允许一份实现（getScenePlan）——两处各算一遍曾造成结尾卡晚 4 帧的真实 bug
- TransitionSeries 的转场是**重叠**而非占用：duration = 下一场景起点 − 本场景起点 + 转场帧数；转场不得长于相邻场景
- Sequence 内的 `useCurrentFrame()` 是局部帧号；字幕、进度条等全程元素挂在根级用全局 t
- 卡拉OK高亮 = `t >= w.start && t < w.end` 的逐帧判定，与配音零偏差因为共用同一份数据
