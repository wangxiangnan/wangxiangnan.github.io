## 14.1 GitHub Actions 工作流设计

### 14.1.1 为什么 Monorepo 的 CI 需要特别设计？

在传统的单仓库项目中，CI 流程通常是线性的：拉代码 → 安装依赖 → 构建 → 测试 → 部署。但在 Monorepo 中，一次 PR 可能只改了 `packages/ui` 里的一个按钮组件，如果还让所有包都跑一遍完整的构建和测试，那就是在浪费 CI 时间和计算资源。

Turborepo 的远程缓存和 `--filter` 参数是我们优化 CI 的两大利器。后面会详细展开。

### 14.1.2 工作流一：PR 检查（Pull Request Check）

这是最频繁触发的工作流——每当有人提交 PR 或推送新 commit 到已有 PR 时都会运行。

```yaml
# .github/workflows/pr-check.yml
name: PR Check

on:
  pull_request:
    branches: [main, develop]

# 同一 PR 的新提交会取消旧的运行
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    name: Lint, Type Check & Test
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          # 拉取完整历史，Turborepo 需要用来计算变更范围
          fetch-depth: 0

      - name: Setup pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9.15.0

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      # 为什么用 --filter？
      # 假设 PR 只改了 packages/ui，那么 apps/api 的 lint 和 test
      # 不需要跑。--filter=...[origin/main] 的意思是：
      # "只选择相对于 main 分支有变更的包及其依赖者"
      - name: Lint
        run: pnpm turbo lint --filter=...[origin/main]

      - name: Type Check
        run: pnpm turbo typecheck --filter=...[origin/main]

      - name: Unit Test
        run: pnpm turbo test --filter=...[origin/main]

      - name: Build affected packages
        run: pnpm turbo build --filter=...[origin/main]
```

**为什么这样做？**

- **`fetch-depth: 0`**：Turborepo 的 `[origin/main]` 语法需要 git 历史来计算哪些包发生了变化。浅克隆（默认 fetch-depth=1）会导致计算失败。
- **`concurrency` + `cancel-in-progress`**：如果开发者连续推送了 3 个 commit 到同一个 PR，前两个 CI 运行会被自动取消，避免资源浪费。
- **`--filter=...[origin/main]`**：三点语法（`...`）不仅选择变更的包，还会选择这些包的**所有下游依赖者**。比如你改了 `packages/shared`，那么依赖它的 `apps/web` 和 `apps/api` 也会被选中。这保证了变更不会悄悄破坏下游。

### 14.1.3 工作流二：主分支构建（Main Branch Build）

合并到主分支后，我们需要做完整的构建验证，并生成可部署的产物。

```yaml
# .github/workflows/main-build.yml
name: Main Build

on:
  push:
    branches: [main]

jobs:
  build:
    name: Full Build & Push Images
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write  # 推送 Docker 镜像到 GHCR 需要此权限

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9.15.0

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      # 主分支做全量构建，确保所有包都能正确编译
      - name: Build all
        run: pnpm turbo build

      - name: Run all tests
        run: pnpm turbo test

      # 登录 GitHub Container Registry
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # 构建并推送 API 镜像
      - name: Build & Push API Image
        uses: docker/build-push-action@v6
        with:
          context: .
          file: ./apps/api/Dockerfile
          push: true
          tags: |
            ghcr.io/${{ github.repository }}/api:latest
            ghcr.io/${{ github.repository }}/api:${{ github.sha }}

      # 构建并推送 Web 镜像
      - name: Build & Push Web Image
        uses: docker/build-push-action@v6
        with:
          context: .
          file: ./apps/web/Dockerfile
          push: true
          tags: |
            ghcr.io/${{ github.repository }}/web:latest
            ghcr.io/${{ github.repository }}/web:${{ github.sha }}
```

**为什么主分支要做全量构建？**

PR 检查可以用 `--filter` 做增量检查来提速，但主分支是发布的源头，必须确保**每一个包**都能正确构建。Turborepo 的本地缓存此时会发挥作用——即使全量构建，没变更的包也会命中缓存，所以实际速度并不慢。

### 14.1.4 工作流三：自动发布（Auto Publish）

当主分支合并了带有 changeset 的 PR 后，我们希望能自动发布 npm 包。

```yaml
# .github/workflows/release.yml
name: Release

on:
  push:
    branches: [main]

concurrency: ${{ github.workflow }}-${{ github.ref }}

jobs:
  release:
    name: Release Packages
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
          # 使用 PAT（Personal Access Token）而不是默认 GITHUB_TOKEN
          # 因为 release 创建的 tag 推送需要触发其他工作流
          token: ${{ secrets.GH_PAT }}

      - name: Setup pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9.15.0

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
          registry-url: 'https://registry.npmjs.org'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build all packages
        run: pnpm turbo build

      # Changesets Action 会自动：
      # 1. 检查是否有待发布的 changeset
      # 2. 如果有，执行 version bump 并创建 git tag
      # 3. 发布到 npm
      # 4. 如果没有待发布的 changeset，则创建一个 "Version Packages" PR
      - name: Create Release Pull Request or Publish
        id: changesets
        uses: changesets/action@v1
        with:
          version: pnpm changeset version
          publish: pnpm changeset publish
          commit: 'chore: version packages'
          title: 'chore: version packages'
        env:
          GITHUB_TOKEN: ${{ secrets.GH_PAT }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**为什么用 Changesets 而不是手动改版本号？**

手动管理版本号在 Monorepo 中是一场噩梦——`packages/ui` 升级到 2.0.0 后，所有依赖它的包都需要更新 `package.json` 中的版本范围。Changesets 自动处理这些依赖关系的级联更新，并且在 PR 阶段就记录了每个变更的类型（major/minor/patch），发布时自动生成 CHANGELOG。

## 14.2 选择性构建：--filter 参数深度解析

### 14.2.1 filter 语法的几种模式

Turborepo 的 `--filter` 参数功能远比"指定一个包名"要强大。下面是常用的几种模式：

```bash
# 1. 指定单个包
pnpm turbo build --filter=@myrepo/ui
# 只构建 packages/ui

# 2. 指定包及其所有依赖
pnpm turbo build --filter=@myrepo/web...
# 构建 web 以及 web 依赖的 shared、ui 等

# 3. 指定包及其所有下游依赖者
pnpm turbo build --filter=...@myrepo/shared
# 构建 shared 以及所有依赖 shared 的包（web、api 等）

# 4. 基于 Git 变更选择（CI 中最常用）
pnpm turbo build --filter=...[origin/main]
# 选择相对于 main 分支有变更的包，及其下游依赖者

# 5. 排除某些包
pnpm turbo build --filter=...[origin/main] --filter=!@myrepo/api
# 选择变更的包及其下游，但排除 api

# 6. 基于文件模式选择
pnpm turbo build --filter=...{src/**}
# 选择 src 目录下有变更的包
```

### 14.2.2 在 CI 中的实际应用

假设你的 Monorepo 有 20 个包，一次 PR 只修改了 `packages/database` 中的 schema。使用 `--filter=...[origin/main]` 的效果是：

```
变更检测：packages/database 有文件变更
         ↓
依赖图分析：
  packages/database
    ├── apps/api (依赖 database) ✓ 选中
    └── apps/web (不依赖 database) ✗ 跳过
         ↓
实际执行：
  packages/database → build, lint, test
  apps/api → build, lint, test
```

这比全量构建 20 个包要快得多。在实际项目中，大多数 PR 只涉及 2-3 个包，使用 `--filter` 可以将 CI 时间从 10 分钟缩短到 1-2 分钟。

### 14.2.3 Turborepo 远程缓存在 CI 中的应用

除了 `--filter`，远程缓存是另一个 CI 加速器。当两个不同的 PR 修改了相同的包并触发相同的构建任务时，第二个 PR 可以直接从远程缓存中获取构建结果，跳过实际构建。

```json
// turbo.json 中的远程缓存配置
{
  "$schema": "https://turbo.build/schema.json",
  "remoteCache": {
    "enabled": true,
    "signature": true
  }
}
```

在 CI 中启用远程缓存需要配置认证 token：

```yaml
# 在 GitHub Actions 的 step 中添加环境变量
- name: Build
  run: pnpm turbo build --filter=...[origin/main]
  env:
    TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
    TURBO_TEAM: ${{ secrets.TURBO_TEAM }}
```

**为什么远程缓存需要 `signature: true`？**

启用签名后，Turborepo 会对缓存产物进行 HMAC 签名验证。这防止了缓存投毒攻击——如果有人篡改了远程缓存中的构建产物，签名验证会检测到并拒绝使用。在生产环境中，这个安全特性不可或缺。

## 14.3 环境变量和 Secrets 管理

### 14.3.1 分层环境变量策略

在 Monorepo 中，环境变量的管理需要分层设计：

```
环境变量层级：
├── 全局变量（所有包共享）
│   ├── NODE_ENV
│   ├── TURBO_TOKEN
│   └── CI
├── 应用级变量（特定应用）
│   ├── apps/web: VITE_API_URL, VITE_APP_TITLE
│   └── apps/api: DATABASE_URL, JWT_SECRET, REDIS_URL
└── 包级变量（内部包）
    └── packages/database: DB_CONNECTION_POOL_SIZE
```

在项目根目录，我们可以用 `.env.example` 文件来记录所有需要的环境变量：

```bash
# .env.example — 放在仓库根目录
# === 全局 ===
NODE_ENV=development

# === apps/web ===
VITE_API_URL=http://localhost:3000/api
VITE_APP_TITLE=My Monorepo App

# === apps/api ===
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
JWT_SECRET=your-jwt-secret-here
REDIS_URL=redis://localhost:6379
```

**为什么用 `.env.example` 而不是直接共享 `.env`？**

`.env` 文件包含真实的密钥和密码，**绝对不能**提交到 Git 仓库。`.env.example` 是一个不含敏感信息的模板，新开发者 clone 项目后，复制一份为 `.env` 然后填入自己的值即可。

```txt
# .gitignore
.env
.env.local
.env.*.local
```

### 14.3.2 CI 中的 Secrets 管理

在 GitHub Actions 中，所有敏感信息都应该通过 Repository Secrets 或 Environment Secrets 注入：

```yaml
# 在 workflow 中使用 secrets
steps:
  - name: Deploy API
    run: pnpm turbo deploy --filter=@myrepo/api
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}
      JWT_SECRET: ${{ secrets.JWT_SECRET }}
      DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}

  - name: Deploy Web
    run: pnpm turbo build --filter=@myrepo/web
    env:
      VITE_API_URL: ${{ vars.VITE_API_URL }}  # vars 用于非敏感配置
```

**Secrets vs Variables**：GitHub 提供了两种配置——Secrets（加密存储，在日志中自动遮蔽）和 Variables（明文存储，适合非敏感的配置项如 API URL）。把密钥放在 Secrets 里，把环境配置放在 Variables 里。

## 14.4 Docker 多阶段构建

### 14.4.1 为什么 Monorepo 的 Docker 构建需要特殊处理？

在单仓库项目中，Dockerfile 通常放在项目根目录，`COPY . .` 就完事了。但在 Monorepo 中，`apps/api` 可能依赖 `packages/shared` 和 `packages/database`，如果只复制 `apps/api` 目录，构建会因为缺少依赖而失败。

解决方案是：**将 Dockerfile 的 context 设为仓库根目录**，然后在 Dockerfile 中精确复制需要的文件。

### 14.4.2 apps/api 的 Dockerfile

```dockerfile
# apps/api/Dockerfile
# 使用多阶段构建：builder 阶段编译，runner 阶段只包含运行时需要的文件

# ====== Stage 1: Builder ======
FROM node:20-alpine AS builder



WORKDIR /app

# 1. 先复制依赖清单文件（利用 Docker 层缓存）
# 为什么先复制这些文件？
# 因为 package.json 变化频率远低于源代码，
# Docker 会缓存这一层，后续构建跳过 pnpm install
COPY pnpm-workspace.yaml pnpm-lock.yaml ./
COPY apps/api/package.json ./apps/api/
COPY packages/shared/package.json ./packages/shared/
COPY packages/database/package.json ./packages/database/
COPY packages/tsconfig/package.json ./packages/tsconfig/

# 2. 安装所有依赖（包括 devDependencies，编译阶段需要）
RUN pnpm install --frozen-lockfile

# 3. 复制源代码
COPY turbo.json ./
COPY packages/shared/ ./packages/shared/
COPY packages/database/ ./packages/database/
COPY packages/tsconfig/ ./packages/tsconfig/
COPY apps/api/ ./apps/api/

# 4. 构建 api 及其依赖
RUN pnpm turbo build --filter=@myrepo/api...

# ====== Stage 2: Runner ======
FROM node:20-alpine AS runner


# 安装 dumb-init 来正确处理信号（避免僵尸进程）
RUN apk add --no-cache dumb-init

WORKDIR /app

# 创建非 root 用户（安全最佳实践）
RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 express

# 只复制生产依赖和构建产物
COPY --from=builder --chown=express:nodejs /app/pnpm-workspace.yaml /app/pnpm-lock.yaml ./
COPY --from=builder --chown=express:nodejs /app/apps/api/package.json ./apps/api/
COPY --from=builder --chown=express:nodejs /app/packages/shared/package.json ./packages/shared/
COPY --from=builder --chown=express:nodejs /app/packages/database/package.json ./packages/database/

# 安装生产依赖
RUN pnpm install --frozen-lockfile --prod

# 复制构建产物
COPY --from=builder --chown=express:nodejs /app/apps/api/dist ./apps/api/dist
COPY --from=builder --chown=express:nodejs /app/packages/shared/dist ./packages/shared/dist
COPY --from=builder --chown=express:nodejs /app/packages/database/dist ./packages/database/dist

USER express

EXPOSE 3000

# dumb-init 作为 PID 1 进程，正确处理 SIGTERM 等信号
CMD ["dumb-init", "node", "apps/api/dist/index.js"]
```

**关键设计决策解析：**

1. **多阶段构建**：builder 阶段安装了所有 devDependencies（TypeScript、构建工具等），但 runner 阶段只安装生产依赖，最终镜像体积从 ~800MB 缩减到 ~150MB。
2. **分层复制**：先复制 `package.json`，再 `pnpm install`，最后复制源代码。这样当只有源代码变更时，`pnpm install` 这一层会命中 Docker 缓存，节省大量时间。
3. **`dumb-init`**：Node.js 默认不处理 Unix 信号（如 SIGTERM），在容器中会导致 `docker stop` 无法优雅关闭进程。`dumb-init` 作为 PID 1 代理信号转发。
4. **非 root 用户**：在容器中以 root 身份运行应用是安全隐患，万一有代码注入漏洞，攻击者会获得 root 权限。

### 14.4.3 apps/web 的 Dockerfile

```dockerfile
# apps/web/Dockerfile
# 前端应用构建后用 nginx 托管静态文件

# ====== Stage 1: Builder ======
FROM node:20-alpine AS builder



WORKDIR /app

COPY pnpm-workspace.yaml pnpm-lock.yaml ./
COPY apps/web/package.json ./apps/web/
COPY packages/shared/package.json ./packages/shared/
COPY packages/ui/package.json ./packages/ui/
COPY packages/tsconfig/package.json ./packages/tsconfig/

RUN pnpm install --frozen-lockfile

COPY turbo.json ./
COPY packages/shared/ ./packages/shared/
COPY packages/ui/ ./packages/ui/
COPY packages/tsconfig/ ./packages/tsconfig/
COPY apps/web/ ./apps/web/

# 构建时注入环境变量
ARG VITE_API_URL
ARG VITE_APP_TITLE
ENV VITE_API_URL=$VITE_API_URL
ENV VITE_APP_TITLE=$VITE_APP_TITLE

RUN pnpm turbo build --filter=@myrepo/web...

# ====== Stage 2: Nginx ======
FROM nginx:1.27-alpine AS runner

# 复制自定义 nginx 配置
COPY apps/web/nginx.conf /etc/nginx/conf.d/default.conf

# 只复制构建产物
COPY --from=builder /app/apps/web/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

配套的 nginx 配置：

```nginx
# apps/web/nginx.conf
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # Gzip 压缩
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml;
    gzip_min_length 1000;

    # 静态资源缓存（Vite 打包的资源带 hash，可以长期缓存）
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # SPA 路由回退：所有未匹配的路径返回 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 安全头
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}
```

**为什么前端用 Nginx 而不是 Node.js 来托管？**

Vite 构建后的产物是纯静态文件（HTML、CSS、JS），用 Nginx 托管比 Node.js 更高效——Nginx 原生支持 Gzip 压缩、静态资源缓存、并发连接处理，而且 Nginx Alpine 镜像只有 ~40MB，远小于 Node.js 镜像。

## 14.5 Docker Compose 编排

### 14.5.1 开发环境

在本地开发时，我们用 Docker Compose 一键启动整个服务栈（包括数据库、Redis 等基础设施）：

```yaml
# docker-compose.dev.yml
version: '3.8'

services:
  # PostgreSQL 数据库
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev_password
      POSTGRES_DB: myapp_dev
    ports:
      - '5432:5432'
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U dev']
      interval: 5s
      timeout: 5s
      retries: 5

  # Redis 缓存
  redis:
    image: redis:7-alpine
    ports:
      - '6379:6379'
    volumes:
      - redis_data:/data

  # API 服务（开发模式：挂载源代码，支持热重载）
  api:
    build:
      context: .
      dockerfile: apps/api/Dockerfile.dev
    ports:
      - '3000:3000'
    environment:
      DATABASE_URL: postgresql://dev:dev_password@postgres:5432/myapp_dev
      REDIS_URL: redis://redis:6379
      JWT_SECRET: dev-jwt-secret-change-in-production
      NODE_ENV: development
    volumes:
      # 挂载源代码目录，支持容器内热重载
      - ./apps/api/src:/app/apps/api/src
      - ./packages/shared/src:/app/packages/shared/src
      - ./packages/database/src:/app/packages/database/src
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started

  # Web 前端（Vite dev server）
  web:
    build:
      context: .
      dockerfile: apps/web/Dockerfile.dev
    ports:
      - '5173:5173'
    environment:
      VITE_API_URL: http://localhost:3000/api
    volumes:
      - ./apps/web/src:/app/apps/web/src
      - ./packages/ui/src:/app/packages/ui/src
      - ./packages/shared/src:/app/packages/shared/src
    depends_on:
      - api

volumes:
  postgres_data:
  redis_data:
```

### 14.5.2 生产环境

生产环境的 Docker Compose 使用预构建的镜像，不挂载源代码：

```yaml
# docker-compose.prod.yml
version: '3.8'

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    restart: always
    # 生产环境不暴露数据库端口到宿主机
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U ${DB_USER}']
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass ${REDIS_PASSWORD}
    volumes:
      - redis_data:/data
    restart: always

  api:
    image: ghcr.io/${GITHUB_REPOSITORY}/api:${IMAGE_TAG:-latest}
    ports:
      - '3000:3000'
    environment:
      DATABASE_URL: postgresql://${DB_USER}:${DB_PASSWORD}@postgres:5432/${DB_NAME}
      REDIS_URL: redis://:${REDIS_PASSWORD}@redis:6379
      JWT_SECRET: ${JWT_SECRET}
      NODE_ENV: production
    depends_on:
      postgres:
        condition: service_healthy
    restart: always
    # 资源限制
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '1.0'

  web:
    image: ghcr.io/${GITHUB_REPOSITORY}/web:${IMAGE_TAG:-latest}
    ports:
      - '80:80'
    depends_on:
      - api
    restart: always

  # Nginx 反向代理（统一管理入口）
  nginx:
    image: nginx:1.27-alpine
    ports:
      - '443:443'
    volumes:
      - ./nginx/ssl:/etc/nginx/ssl:ro
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - api
      - web
    restart: always

volumes:
  postgres_data:
  redis_data:
```

**为什么生产环境用 `deploy.resources` 限制资源？**

在 Monorepo 中，多个服务可能运行在同一台机器上。不设资源限制的话，一个服务的内存泄漏可能会吃掉所有内存，导致其他服务也被 OOM Kill。设置明确的资源上限可以让问题隔离在单个服务内。

## 14.6 部署策略

### 14.6.1 前端部署到 Vercel

Vercel 对 Monorepo 有很好的原生支持，但需要正确配置：

```json
// vercel.json（放在仓库根目录）
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "buildCommand": "pnpm turbo build --filter=@myrepo/web...",
  "installCommand": "pnpm install --frozen-lockfile",
  "outputDirectory": "apps/web/dist",
  "framework": "vite",
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

在 Vercel 的项目设置中：

- **Root Directory** 设为 `apps/web`
- **Framework Preset** 选择 `Vite`
- **Build Command** 会自动使用根目录的 `vercel.json` 配置

**为什么 `buildCommand` 用 `--filter=@myrepo/web...`？**

三点语法（`...`）会先构建 `apps/web` 依赖的所有包（`packages/shared`、`packages/ui`），再构建 `apps/web` 本身。这确保了 Vercel 的构建环境中有所有需要的依赖产物。

### 14.6.2 后端部署到 Railway

Railway 支持从 Dockerfile 部署，非常适合 Monorepo 中的 API 服务：

```toml
# railway.toml（放在 apps/api 目录）
[build]
builder = "DOCKERFILE"
dockerfilePath = "Dockerfile"
# 关键：告诉 Railway 构建上下文是仓库根目录
watchPatterns = [
  "apps/api/src/**",
  "packages/shared/src/**",
  "packages/database/src/**",
  "pnpm-lock.yaml"
]

[deploy]
startCommand = "node apps/api/dist/index.js"
healthcheckPath = "/health"
healthcheckTimeout = 300
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 3
```

**`watchPatterns` 的作用**：Railway 会根据这些模式判断哪些文件变更需要触发重新部署。如果不设置，任何文件的变更（包括只修改了前端代码）都会触发 API 的重新部署，这显然不是我们想要的。

### 14.6.3 Fly.io 部署备选方案

Fly.io 也是一个优秀的后端部署平台，支持全球边缘部署：

```toml
# fly.toml（放在 apps/api 目录）
app = "myrepo-api"
primary_region = "hkg"

[build]
  dockerfile = "Dockerfile"

[env]
  NODE_ENV = "production"
  PORT = "3000"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines = true
  auto_start_machines = true
  min_machines_running = 1

[[vm]]
  cpu_kind = "shared"
  cpus = 1
  memory_mb = 256
```

## 14.7 Monorepo 中多应用部署的缓存优化

### 14.7.1 Docker 层缓存优化策略

在 Monorepo 中构建 Docker 镜像时，最大的痛点是缓存失效范围过大。比如你只改了 `apps/web/src/App.vue`，但由于 Docker 的 `COPY` 指令会检测文件变更，如果复制顺序不合理，可能导致 `pnpm install` 层缓存失效。

**优化原则：按变更频率从低到高排列 COPY 指令**

```dockerfile
# 好的顺序（变更频率：低 → 高）
COPY pnpm-workspace.yaml pnpm-lock.yaml ./     # 几乎不变
COPY packages/*/package.json ./packages/        # 偶尔变
COPY apps/*/package.json ./apps/                # 偶尔变
RUN pnpm install                                # 上面不变就缓存命中
COPY packages/ ./packages/                      # 有时变
COPY apps/ ./apps/                              # 经常变
```

### 14.7.2 Turborepo 远程缓存与 CI 的协同

在 CI 中，Turborepo 的远程缓存可以跨不同的 workflow run 共享构建结果。这意味着：

```
PR #101 修改了 packages/shared
  → 构建 packages/shared（缓存 miss，实际构建）
  → 结果上传到远程缓存

PR #102 也修改了 packages/shared（相同的输入 hash）
  → 构建 packages/shared（缓存 hit，跳过构建）
  → 直接复用 PR #101 的构建结果
```

配置 GitHub Actions 缓存 Turborepo 的本地缓存目录作为补充：

```yaml
- name: Cache Turborepo
  uses: actions/cache@v4
  with:
    path: node_modules/.cache/turbo
    key: ${{ runner.os }}-turbo-${{ hashFiles('**/pnpm-lock.yaml') }}
    restore-keys: |
      ${{ runner.os }}-turbo-
```

### 14.7.3 .dockerignore 的配置

合理的 `.dockerignore` 可以避免不必要的文件进入构建上下文，加速 `docker build`：

```txt
# .dockerignore
node_modules
.git
.github
.vscode
*.md
*.log

# 排除测试文件（构建不需要）
**/__tests__
**/*.test.ts
**/*.spec.ts
coverage/

# 排除其他应用的源代码（按需调整）
# 注意：不能排除当前镜像需要的包
```
