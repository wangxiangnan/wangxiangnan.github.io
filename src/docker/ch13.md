# 第13章：Docker 日志管理与调试技巧 —— 当你的容器"闹情绪"了

## 引言：从"它怎么又挂了"到"我知道为什么"

每个 Docker 用户都经历过这样的场景：容器启动后秒退，你一脸懵逼地看着空荡荡的 `docker ps` 输出，心中默念"它为什么退？它退之前经历了什么？它有什么遗言？"

如果容器是一个人，日志就是它的日记。通过日志，你可以了解容器每天在做什么、遇到了什么问题、什么时候情绪崩溃了。

---

## 13.1 Docker 默认日志驱动（json-file）

Docker 默认使用 `json-file` 日志驱动，将容器的 `stdout` 和 `stderr` 以 JSON 格式写入文件。

```bash
# 查看容器的日志文件位置
docker inspect --format='{{.LogPath}}' my-container

# 每条日志的 JSON 结构：
# {"log":"实际日志内容\n","stream":"stdout","time":"2024-01-15T10:30:00Z"}
```

> [!TIP] 提示
> `json-file` 驱动的日志文件会持续增长，如果不配置轮转，一个高输出的容器可能在几天内吃掉几十 GB 磁盘空间。这就是很多运维同学半夜被磁盘报警叫醒的原因。

---

## 13.2 日志驱动选择

| 日志驱动 | 目标位置 | 适用场景 |
|---------|---------|---------|
| `json-file` | 本地文件 | 开发环境（默认） |
| `journald` | systemd journal | systemd Linux |
| `syslog` | syslog 服务 | 传统运维环境 |
| `fluentd` | Fluentd 收集器 | 灵活日志管道 |
| `awslogs` | CloudWatch Logs | AWS 环境 |
| `gelf` | Graylog / Logstash | GELF 协议 |

```bash
# 指定日志驱动和轮转配置
docker run -d \
  --log-driver json-file \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  my-app

# 使用 syslog 驱动
docker run -d \
  --log-driver syslog \
  --log-opt syslog-address=tcp://log-server:514 \
  my-app
```

```yaml
# docker-compose.yml 中配置
services:
  api:
    image: my-api:latest
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

> [!WARNING] 注意
> 使用非 `json-file` 驱动后，`docker logs` 命令可能不可用。开发环境保持 `json-file`，生产环境再切换。

## 13.3 docker logs 高级用法

```bash
# 基础：查看所有日志
docker logs my-container

# 实时跟踪（类似 tail -f）
docker logs -f my-container

# 只看最后 50 行
docker logs --tail 50 my-container

# 显示时间戳
docker logs -t my-container

# 查看某个时间之后的日志
docker logs --since "2024-01-15T10:00:00" my-container
docker logs --since 30m my-container         # 最近 30 分钟
docker logs --since 2h my-container          # 最近 2 小时

# 查看某个时间之前的日志
docker logs --until "2024-01-15T12:00:00" my-container

# 组合使用
docker logs --since 1h --tail 100 my-container

# 配合 grep 过滤
docker logs my-container 2>&1 | grep -i error

# 实时过滤错误日志
docker logs -f my-container 2>&1 | grep --line-buffered -i "error\|warn\|fatal"
```

> [!TIP] 提示
> `docker logs` 默认只显示 stdout。有些应用的错误日志只输出到 stderr。加上 `2>&1` 合并查看。

## 13.4 结构化日志（JSON 格式输出）

```javascript
// Node.js - 使用 pino 输出 JSON 格式日志
const pino = require('pino');
const logger = pino();

logger.info({ userId: 123, action: 'login' }, 'User logged in');
// 输出：{"level":30,"time":1705312200000,"userId":123,"action":"login","msg":"User logged in"}

logger.error({ err: new Error('DB failed'), service: 'postgres' }, 'Connection failed');
```

```python
# Python - 使用 structlog 输出 JSON 格式日志
import structlog

structlog.configure(
    processors=[
        structlog.processors.add_log_level,
        structlog.processors.TimeStamper(fmt="iso"),
        structlog.processors.JSONRenderer()
    ],
)
logger = structlog.get_logger()

logger.info("user_login", user_id=123, ip="192.168.1.1")
# 输出：{"event": "user_login", "user_id": 123, "level": "info", "timestamp": "2024-01-15T10:30:00Z"}
```

> [!TIP] 提示
> "日志输出到 stdout/stderr"是 Docker 的十二因子应用原则之一。不要把日志写到容器内的文件里——容器是临时的，文件会随容器销毁而丢失。

## 13.5 日志轮转配置

```yaml
# docker-compose.yml —— 为每个服务配置日志轮转
services:
  api:
    image: my-api:latest
    logging:
      driver: json-file
      options:
        max-size: "10m"              # 单个日志文件最大 10MB
        max-file: "5"                # 保留 5 个文件（共 50MB）
        compress: "true"             # 压缩旧日志

  db:
    image: postgres:15-alpine
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
```

```bash
# 全局默认配置（/etc/docker/daemon.json）
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "5",
    "compress": "true"
  }
}

# 重启 Docker daemon 使配置生效
sudo systemctl restart docker
```

> [!WARNING] 注意
> 修改 daemon.json 并重启 Docker 后，**只有新创建的容器**会使用新配置。已有容器需要 `docker compose down && docker compose up -d` 重新创建。

## 13.6 集中式日志方案

### 方案一：ELK Stack（Elasticsearch + Logstash + Kibana）

```yaml
# docker-compose.elk.yml
services:
  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.11.0
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
      - "ES_JAVA_OPTS=-Xms512m -Xmx512m"
    volumes:
      - es-data:/usr/share/elasticsearch/data
    ports:
      - "9200:9200"

  logstash:
    image: docker.elastic.co/logstash/logstash:8.11.0
    volumes:
      - ./logstash/pipeline:/usr/share/logstash/pipeline
    ports:
      - "5044:5044"
    depends_on:
      - elasticsearch

  kibana:
    image: docker.elastic.co/kibana/kibana:8.11.0
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch
    environment:
      - ELASTICSEARCH_HOSTS=http://elasticsearch:9200

volumes:
  es-data:
```

### 方案二：Loki + Grafana（更轻量）

```yaml
# docker-compose.loki.yml
services:
  loki:
    image: grafana/loki:2.9.0
    ports:
      - "3100:3100"
    volumes:
      - loki-data:/loki

  promtail:
    image: grafana/promtail:2.9.0
    volumes:
      - ./promtail-config.yml:/etc/promtail/config.yaml
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
    depends_on:
      - loki

  grafana:
    image: grafana/grafana:10.2.0
    ports:
      - "3000:3000"
    volumes:
      - grafana-data:/var/lib/grafana
    depends_on:
      - loki

volumes:
  loki-data:
  grafana-data:
```

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|---------|
| ELK Stack | 功能强大，全文搜索 | 资源占用大 | 大型企业 |
| Loki + Grafana | 轻量，与 Prometheus 互补 | 基于标签查询 | 中小规模 |

> [!TIP] 提示
> 如果团队已经使用 Grafana + Prometheus 做监控，强烈推荐 Loki。它们共享同一个 UI，可以在一个面板中同时查看指标和日志。

## 13.7 容器调试技巧

### docker exec 进入容器

```bash
# 交互式 shell 进入容器
docker exec -it my-container sh

# 如果容器有 bash
docker exec -it my-container bash

# 运行单个命令
docker exec my-container ls -la /app
docker exec my-container env | grep DATABASE

# 以 root 身份进入（当容器以非 root 运行时）
docker exec -it --user root my-container sh

# 在 Compose 中
docker compose exec api sh
docker compose exec db psql -U postgres -d myapp
```

### 查看容器详细信息

```bash
# 查看容器完整信息
docker inspect my-container

# 查看 IP 地址
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' my-container

# 查看环境变量
docker inspect --format='{{range .Config.Env}}{{println .}}{{end}}' my-container

# 查看挂载信息
docker inspect --format='{{json .Mounts}}' my-container
```

### 复制文件

```bash
# 从容器内复制到宿主机
docker cp my-container:/app/logs/error.log ./error.log

# 从宿主机复制到容器内
docker cp ./config.json my-container:/app/config.json
```

> [!TIP] 提示
> 如果 `docker exec -it my-container sh` 报错 `executable file not found`，说明镜像没有 shell（如 distroless）。此时用 `docker cp` 复制文件出来分析。

## 13.8 常见错误排查

### OOM Killed（内存不足被杀）

```bash
# 现象：容器突然退出
docker ps -a
# STATUS: Exited (137)

# 排查：检查是否被 OOM Killer 杀死
docker inspect --format='{{.State.OOMKilled}}' my-container
# 输出：true

# 查看系统日志确认
dmesg | grep -i "oom\|killed process"

# 解决：增加内存限制
docker update --memory=1g my-container
```

### Exit Code 137（SIGKILL / OOM）

退出码 137 = 128 + 9（SIGKILL）。通常意味着容器被系统强制杀死，最常见原因是 OOM。

### Exit Code 143（SIGTERM）

退出码 143 = 128 + 15（SIGTERM）。容器被"礼貌地"要求退出——通常是 `docker stop` 触发。

```javascript
// Node.js 正确处理 SIGTERM
process.on('SIGTERM', () => {
  console.log('Received SIGTERM, shutting down gracefully...');
  server.close(() => {
    console.log('Server closed');
    process.exit(0);
  });
});
```

### 端口冲突

```bash
# 现象：Error: Bind for 0.0.0.0:3000 failed: port is already allocated

# 排查
sudo lsof -i :3000
docker ps --format "table {{.Names}}\t{{.Ports}}" | grep 3000
```

### 常见退出码速查表

| 退出码 | 含义 | 常见原因 |
|--------|------|---------|
| 0 | 正常退出 | 任务完成 |
| 1 | 应用错误 | 代码 bug、配置错误 |
| 126 | 命令不可执行 | 权限问题 |
| 127 | 命令不存在 | 入口命令路径错误 |
| 137 | SIGKILL (128+9) | OOM Killed、强制杀死 |
| 139 | SIGSEGV (128+11) | 段错误 |
| 143 | SIGTERM (128+15) | `docker stop` 触发 |

## 13.9 实战：排查一个"容器启动就退出"的问题

```bash
# 第1步：发现问题
docker compose up -d
docker compose ps
# api-1       Exited (1)

# 第2步：查看退出码
docker inspect --format='{{.State.ExitCode}}' api-1
# 输出：1（应用错误）

# 第3步：查看日志（最重要的一步！）
docker compose logs api
# Error: Cannot find module 'express'

# 第4步：分析原因
# 找不到 express 模块！npm install 没有正确执行

# 第5步：检查 Dockerfile
# 发现 COPY . . 在 RUN npm ci 之前
# 且 .dockerignore 没有排除 node_modules

# 第6步：修复
```

```dockerfile
# 修复后的 Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --only=production
COPY . .
USER node
CMD ["node", "server.js"]
```

```bash
# 第7步：添加 .dockerignore
echo "node_modules" >> .dockerignore

# 第8步：重新构建并启动
docker compose up -d --build
docker compose ps
# api-1       Up

# 第9步：确认日志正常
docker compose logs -f api
# [INFO] Server started on port 3000
# [INFO] Connected to MongoDB
```

**"容器启动就退出"排查流程图**：

```bash
容器启动就退出
│
├── 1. 查看退出码
│   ├── 0   → 应用正常退出（CMD 错误？）
│   ├── 1   → 应用错误（看日志！）
│   ├── 137 → OOM Killed（增加内存限制）
│   └── 143 → 被 SIGTERM（检查健康检查配置）
│
├── 2. 查看日志
│   ├── 有错误信息 → 根据错误修复
│   └── 无输出 → 应用可能在启动前就崩溃
│
├── 3. 检查配置
│   ├── 环境变量是否正确
│   ├── 依赖服务是否就绪
│   └── 端口是否冲突
│
├── 4. 手动调试
│   ├── docker compose run --rm api sh
│   └── 手动执行启动命令看报错
│
└── 5. 检查 Dockerfile
    ├── 指令顺序是否正确
    └── .dockerignore 是否配置
```

> [!TIP] 提示
> 如果实在找不到原因，临时将启动命令改为 `sleep 3600`，让容器保持运行，然后用 `docker exec -it container sh` 进去手动排查。这就像调试时在最可疑的地方打个断点。

## 本章小结

- Docker 默认使用 `json-file` 日志驱动，日志以 JSON 格式存储
- 生产环境务必配置日志轮转，防止磁盘被日志撑爆
- 结构化日志配合集中式日志系统（ELK / Loki）是生产环境标配
- `docker logs` 的 `--since`、`--until`、`--tail`、`-f` 参数组合是排查利器
- 退出码是调试的第一步：137 看内存，1 看日志，143 看信号处理
- 日志输出到 stdout/stderr 是 Docker 最佳实践

## 练习

1. **基础练习**：为一个 Node.js 应用配置 JSON 格式日志输出 + 日志轮转，确保单服务日志不超过 50MB。
2. **进阶练习**：搭建一个 Loki + Grafana 日志系统，将 3 个服务的日志集中收集。
3. **挑战练习**：故意制造一个会 OOM 的容器（在循环中不断分配内存），然后按照本章流程排查并修复。
