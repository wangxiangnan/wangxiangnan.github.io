# 第7章：数字签名：给发布包盖防伪章

> [!TIP] Part 2: 非对称与证书篇（进阶篇）
> 危机二的主场。第2章的哈希能证明「文件没变过」，但证明不了「发布它的人是谁」——签名把身份钉进完整性，让篡改与冒名同时失效。

第 14 周，云笔记差点出大事：一次例行的客户端更新，发布包在内部中转机上被恶意软件替换成了夹带后门的版本，差最后一步就要推给全量用户。事后复盘，大家发现最让人后背发凉的不是恶意软件本身，而是**当时的发布流程完全无法区分「王哥上传的包」和「恶意软件替换的包」**——校验和有，但校验和也在同一台被感染的机器上重新生成了。缺的东西叫数字签名（Digital Signature）：不只证明文件没变过，还证明**盖章的人是谁**。

阿雪在复盘会上问了一个直击要害的问题：「校验和不是对得上吗？恶意软件是怎么过校验的？」答案让全组沉默：校验和验证的是「文件与算校验和时一致」，而**算校验和的机器已经被攻陷**——基准本身被污染了。这引出本章的核心命题：完整性校验的基准必须存放在攻击者碰不到的地方，而「只有发布者能产出、所有人都可验证」的基准，就是签名。

## 7.1 从哈希到签名：多了「谁」

把第2章和第5章的两个零件拼起来，就是签名：**用私钥对文件的摘要盖章，任何人用对应公钥验章**。和纯哈希比，多了三样东西：

| 能力 | 裸哈希（SHA-256） | 数字签名 |
| ---- | ---- | ---- |
| 完整性（文件没变） | 有 | 有 |
| 认证（谁发布的） | 无 | **有：只有私钥持有者能签** |
| 不可否认（事后抵赖不了） | 无 | **有** |
| 需要密钥 | 不需要 | 需要（私钥签，公钥验） |

第三行「不可否认」值得单独想十秒：HMAC 也能做认证，但它防不了抵赖——密钥双方都有，出了事谁都可以说「签名是你算的」。签名只用私钥持有者才能产出，公钥人人可验，**数学上把「盖章权」收敛到一个人手里**。这就是为什么合同签署、代码发布、安全公告这些「事后要追责」的场景必须用签名，而不是共享密钥的 MAC。

一个必须掰直的误解：签名**不是**「用私钥把文件加密一遍」。技术上签名只处理摘要——先对文件算 SHA-256（吞吐约 GB/s 级，耗时与文件大小成正比），再用私钥对这 32 字节的摘要运算（耗时固定）。如果对几个 GB 的文件整体做非对称运算，既慢又无必要；「先哈希后签名」是效率与安全的双赢。签名文件（.sig）通常只有几十到几百字节，与被签文件大小无关——1MB 的说明书和 1GB 的游戏客户端，Ed25519 的签名都是恒定 64 字节：

```bash
ls -l release.zip release.zip.sig
```

```text
-rw-r--r-- 1 wang wang 1048576000 release.zip
-rw-r--r-- 1 wang wang          64 release.zip.sig
```

恒定长度的直接推论：**签名文件几乎哪儿都贴得下**——发布说明、Git 提交信息、二维码都塞得下。Ed25519 恒定 64 字节、ECDSA P-256 是 70 字节左右、RSA-2048 是 256 字节，同样与被签内容无关。第一次见到「几个 GB 的文件、64 字节的签名」时停一秒，感受一下摘要 + 非对称这个组合的优雅：所有重量都由哈希扛走了，私钥只碰 32 字节。

```text
        发布方（有私钥）                     验收方（只有公钥）
┌─────────────────────────┐        ┌─────────────────────────┐
│ release.zip             │        │ 收到 zip + sig           │
│   │ sha256 摘要          │        │   │ sha256 重算摘要       │
│   ▼                     │  传输   │   ▼                     │
│ 私钥对摘要签名 → .sig ───┼──────► │ 公钥验签                  │
│                         │        │   ├─ 摘要一致：Verified OK │
│ 私钥全程不出门            │        │   └─ 不一致：篡改或冒名    │
└─────────────────────────┘        └─────────────────────────┘
```

读图抓三个要点：两侧的摘要算法与参数完全相同；私钥只出现在左栏；右侧「重算摘要 + 验签」两步分别对应完整性与身份两项检查。左边任何一步少锁、右边任何一步偷懒，防线就从那里开洞。

攻击者的处境就此逆转：他可以改文件、可以伪造 .sig、可以两者都换——但验签用的是**发布方公钥**，没有私钥就造不出能通过验证的签名。这就是「防伪章」三个字的分量。

同时也要诚实地说清签名**不防什么**：它不加密（发布包内容任何人可读，保密是第3章的活）；不防「合法签名的恶意代码」（私钥的主人自己使坏，签名照样合法——防这个靠流程与审计）；不防私钥泄露后的伪造（所以第5章说怀疑泄露立即换钥匙）。技术防线每一条都有边界，边界之内的才是它承诺的世界。

## 7.2 dgst 签名实战

签名与验签还是 `dgst`，只是换了两个参数。用 RSA 或 EC 私钥签（云笔记的正式发布钥匙是 Ed25519，走 7.3 节的另一扇门；本节现造一把一次性 EC 钥匙演示通用流程，两种流程的分工对照见 7.3 的表格）：

```bash
# 先造演示用的一次性 EC 钥匙（正式发布钥匙见 7.3）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out release-ec-key.pem
openssl pkey -in release-ec-key.pem -pubout -out release-ec-pub.pem

# 签名：私钥在，出 .sig（二进制）
openssl dgst -sha256 -sign release-ec-key.pem -out release.zip.sig release.zip

# 验签：公钥在，出结论
openssl dgst -sha256 -verify release-ec-pub.pem -signature release.zip.sig release.zip
```

```text
Verified OK
```

三个工程细节一次交代：

- **哈希算法两侧必须一致**：签名用 `-sha256`，验签也得 `-sha256`，配错会得到莫名的失败——这不是安全机制，是参数配对。
- **.sig 是二进制**：要贴进网页、发布说明、Git commit message 时，用第4章的编码工具转成文本：`openssl base64 -in release.zip.sig -out release.zip.sig.b64`，验收侧 `-d` 解回。
- **验签失败是硬信号**：`Verification failure` 出现，只有两种可能——文件被改过，或者公钥/签名拿错了对象。无论哪种，流程都必须停。

还有个便利特性：不给文件名时 `dgst` 从标准输入读——第2章的管道流式校验在签名场景同样成立，比如给一段 URL 下载内容边下边签。另外注意 `-sign` 产出的是**分离签名**（detached signature）：.sig 是独立文件，不依附原文。相对的「附着签名」（把原文塞进签名结构里，如 PGP 的 .asc 文件）命令行 `dgst` 不做——分离式反而是工程首选：原文怎么分发都行，签名跟不跟随便，验收方两件套合体即验。

## 7.3 Ed25519 与 pkeyutl

第5章给云笔记定的发布钥匙是 Ed25519，它的签名要走另一扇门：`pkeyutl`。原因是算法性质的差异——RSA 和 ECDSA 的签名流程是「先自己算好摘要，交给算法处理」；而 Ed25519 属于「整体签名」一类（PureEdDSA），**对原文直接签名，根本不做预哈希**，所以不能套 `dgst` 的「先 `-sha256` 再签」的模板：

```bash
# Ed25519 签名：-rawin 表示「输入就是原文，剩下的算法自己处理」
openssl pkeyutl -sign -inkey ~/.cloudnote-secrets/release-key.pem -rawin -in release.zip -out release.zip.sig

# Ed25519 验签
openssl pkeyutl -verify -pubin -inkey release-pub.pem -rawin -in release.zip -sigfile release.zip.sig
```

```text
Signature Verified Successfully
```

| 算法 | 签名命令 | 特点 |
| ---- | ---- | ---- |
| RSA / EC | `dgst -sha256 -sign` | 传统流程：摘要先行，命令直观 |
| Ed25519 | `pkeyutl -sign -rawin` | 原文直接进算法，更快更短 |

Ed25519「不做预哈希」还有一个隐藏福利值得知道：它的签名是**确定性**的——同一私钥签同一消息，每次得到的签名完全相同（RSA/ECDSA 的签名里掺有随机数，每次不同）。确定性的好处是签名不再依赖签名时的随机数质量：ECDSA 有个著名的坑，随机数复用或可预测会导致**私钥被直接算出来**（索尼 PS3 的签名私钥就是这样泄露的），而 Ed25519 从算法层面消灭了这类事故。这也是它 2015 年登场即横扫新协议的原因之一——把「随机数质量」这个变量从签名安全里整个移除了。

进阶一笔带过：RSA 签名还有个「填充模式」的讲究，现代标准推荐 PSS 而非老的 PKCS#1 v1.5（`openssl dgst -sign ... -sigopt rsa_padding_mode:pss`）。日常对接老系统时默认模式最省事，新建协议时有条件就上 PSS——记住有这个旋钮即可，展开属于密码学工程课的范围。

## 7.4 公钥怎么发：指纹公示与信任的起点

签名体系有个安静的软肋：**验签用的公钥，你信它吗？** 如果攻击者连发布包带公钥一起换掉，再用新公钥签新包——验签全流程绿灯。防御思路你在第5章见过：**指纹走另一条渠道**。云笔记的做法是把发布公钥的 SHA-256 指纹公示在官网（HTTPS 页面）与团队 Wiki 两处：

```bash
openssl pkey -pubin -in release-pub.pem -outform DER | openssl dgst -sha256
```

验收侧的完整流程：下载 zip 与 .sig → 从官网取公钥与指纹 → 本地核对指纹 → 验签。指纹比对是「这条链上我唯一人工信任的锚点」，其余环节全部自动化。

把这个流程的每一步和它的威胁对应起来，你就拿到了签名体系的完整威胁模型：

| 环节 | 防的威胁 | 防线 |
| ---- | ---- | ---- |
| 下载 zip + .sig | 传输途中被换 | 验签（下一行） |
| 核对公钥指纹 | 公钥被调包 | 渠道 B 的指纹公示 |
| 验签 | 包被篡改或冒名 | 私钥签名 |
| 全流程 | 中间人监看内容 | 下载页本身走 HTTPS（第13章） |

四道防线各管一段，缺一段整条链就断在那里。以后评估任何分发体系（应用商店、插件市场、内部制品库），拿这张表逐行打勾，覆盖不了的就问「这一段的信任从哪来」。

你可能已经嗅到了：这本质上是个「谁为公钥背书」的社会学问题——自己项目公示指纹可以，但软件要分发给成千上万的陌生用户，总不能让每个用户都打电话来核对指纹。**让受信任的第三方为公钥盖章**，那个盖章的产物就叫证书——第8章的主角。签名与证书的关系现在立好：签名靠公私钥对，证书负责让公钥可信，两者一组合，就是 HTTPS 的全部地基。

工业界的现成答案也值得看一眼，你每天都在享受它：Linux 发行版的软件仓库、Homebrew 的 formula、VS Code 扩展市场，都用「包管理器内置信任库」的方案——操作系统的钥匙环里预置了发行方的公钥（安装系统时就有，等于出厂刻上去的），更新包带签名，包管理器用预置公钥自动验签。用户全程无感知，却每一条 `apt install` 都过了验签。这套方案的信任起点是「OS 安装介质本身可信」，再往上追就是供应链安全的大课题了。云笔记的客户端以后要面向普通用户分发，走的也是同一条路：安装包内置发布公钥 + 指纹，而不是让用户手工核对。

把这条思路接到自己身上：云笔记当前的验收方是阿雪这样的内部同事，手工核对指纹够用；哪天产品走向公网用户，就升级成「客户端内置公钥」的自动验签。**信任锚的形态随分发规模升级**——手工公示、内置钥匙环、CA 证书，三级台阶在后面两章全部登场。

签名钥匙的轮换也要提前想好：换了新签名钥匙，**老版本安装包验老签名、新版本验新签名**，过渡期两把公钥并行公示，全部用户拿到新版本后旧钥匙退役。钥匙可以换，**指纹公示渠道的管控权不能丢**——官网被攻破等于信任链整体崩塌，这也是为什么公示页面要纳入第13章 HTTPS 与访问控制的保护范围。

## 7.5 常见错法速查

签名落地时的错法高度重复，反例正例成对摆出：

| 反例 | 后果 | 正确做法 |
| ---- | ---- | ---- |
| 「用私钥加密文件」当签名 | 慢、语义错、大文件直接不可行 | 签摘要，不碰全文 |
| 公钥与签名走同一渠道分发 | 一锅端，防线归零 | 公钥指纹走 HTTPS 官网 / 线下核对 |
| CI 里验签失败仍继续部署 | 防线形同虚设 | 验签命令失败即中止（`set -e` + 显式检查退出码） |
| 更新文件后忘记重签 | 验签失败——**这其实是防线在响** | 把「改动必重签」写进发布脚本 |
| 签名与验签的哈希参数不一致 | 莫名失败 | 算法名写进发布说明，两侧照抄 |
| 用 release.zip 本身当「已知好版本」做比对 | 攻击者连 zip 一起换，比对失去基准 | 指纹/签名基准存发布方之外的地方 |

最后一行是第2章「清单与文件分开存放」纪律在签名场景的翻版：**比对基准不能与被比对对象同源**。签名体系之所以强于校验和，本质就是它把基准（公钥）与对象（文件）的存放位置拆开了。

> [!WARNING] 验签失败不是故障，是防线在工作
> 团队最容易犯的不是技术错，是心态错：看到 `Verification failure` 第一反应是「哪儿配置错了，改到通过为止」。正确的第一反应是**当作事故对待**：先确认文件是不是被改过，再排查参数。把「改到通过」的本能留给格式报错（第6章），把「停下追查」的本能留给安全信号。

> [!NOTE] 你可能每天都在签名：Git 提交签名
> GitHub 上那些带 `Verified` 徽章的提交，就是数字签名的日常化——`git commit -S` 用你的 GPG/SSH 钥匙对提交对象签名，GitHub 用登记的公钥验签后打徽章。《Git 与 SSH 完全教程》第20章登记到 GitHub 的那把公钥，如果开启了签名功能，它同时就是你的「代码防伪章」。原理与本章完全同构：签的是提交内容的哈希，验的是登记公钥，防的是「有人以你的名义提交代码」。

## 7.6 实验：给更新包上签名流水线

动手前先回答一个设计问题：**签什么？** 发布产物往往是一堆文件（zip、校验清单、说明文档），逐个签名要维护一堆 .sig；更专业的做法是只签**一份清单**——把所有产物的指纹列进 SHA256SUMS，对清单签名一把。这正是 Debian 软件源的做法：每个 Release 文件本质上就是「被签名的大清单」，用户验一次签名、比对一次清单，全部产物就有了完整性与身份双重保障。

```bash
# 1. 给全部产物造清单（第2章的老朋友）
cd release-output/
sha256sum release.zip release-notes.md > SHA256SUMS

# 2. 只对清单签名——一把私钥，一处盖章
openssl pkeyutl -sign -inkey ~/.cloudnote-secrets/release-key.pem \
  -rawin -in SHA256SUMS -out SHA256SUMS.sig

# 3. 发布物：所有产物 + SHA256SUMS + SHA256SUMS.sig
```

验收侧三步：验清单签名（一次验签覆盖全部产物）→ 按清单逐一 `sha256sum -c` → 全绿放行。**签名管身份，清单管覆盖面**，两层各司其职——以后在 Debian、npm、Homebrew 的发布机制里看到「签名 + 清单」组合拳，你知道它们是怎么咬合的。

回到云笔记的最小实现，单个 zip 场景的 `sign-release.sh`：

```bash
#!/bin/bash
set -euo pipefail
PKG=release-$1.zip
SIG=$PKG.sig

# 1. 签名（Ed25519）
openssl pkeyutl -sign -inkey ~/.cloudnote-secrets/release-key.pem \
  -rawin -in "$PKG" -out "$SIG"

# 2. 本地自验一遍，签名链路自证
openssl pkeyutl -verify -pubin -inkey release-pub.pem -rawin -in "$PKG" -sigfile "$SIG"

# 3. 签名转 base64 便于贴发布说明
openssl base64 -in "$SIG" -out "$SIG.b64"

echo "发布清单：$PKG + $SIG（b64 版本贴 release notes）"
echo "公钥指纹（公示在官网与 Wiki）："
openssl pkey -pubin -in release-pub.pem -outform DER | openssl dgst -sha256
```

**验收三连**：

1. 正常包验签，输出 `Signature Verified Successfully`；
2. 给 zip 追加一个字节再验签，必须输出 `Signature Verification Failure`——篡改演练通过；
3. 把 release-pub.pem 换成随便一把别的公钥再验，同样失败——冒名演练通过。

三个演练对应三类威胁：无篡改、篡改、冒名——**防线对每一类都必须给出正确反应**，只测「正常路径」的验收是无效验收（攻击者从不走正常路径）。第14章的季度安全演练清单里，这三连会作为固定动作出现。

两个演练都失败、正常包通过，发布签名体系才算上线。CI 里的接入只需一行判断：`openssl pkeyutl -verify ... || exit 1`，把「验签失败即中止」变成流程的一部分。

让阿雪以「陌生验收方」的身份再走一遍完整流程，检验公示体系是否真的自洽：

1. 你只把 `release.zip`、`release.zip.sig` 发到下载页（渠道 A），**不**发公钥文件；
2. 阿雪从官网 HTTPS 页面下载 `release-pub.pem` 与公示的指纹（渠道 B）；
3. 阿雪本地：核对指纹 → 验签 → 两条全绿。

第 2 步是彩排重点：如果阿雪「图省事」让你直接在聊天群里发公钥文件，渠道 B 就被并进渠道 A 了——演一遍「拒绝同渠道递公钥」，纪律才会长在流程里而不是嘴上。彩排合格的标准：阿雪全程没找你要过一次公钥文件，全部信息来自官网与 Wiki。

阿雪侧如果拿到的是 base64 版签名（发布说明里贴的那种），验签前先解回二进制：

```bash
openssl base64 -d -in release.zip.sig.b64 -out release.zip.sig
openssl pkeyutl -verify -pubin -inkey release-pub.pem -rawin \
  -in release.zip -sigfile release.zip.sig
```

编码与签名是两层皮（第4章的军规在此回收）：b64 只是 .sig 的文本马甲，解开再验，别把 b64 直接喂给 `-sigfile`。

演练全部通过后，把两件东西写进发布手册：签名命令与算法参数（第 6 章的教训：参数记档，几年后可复现）；指纹公示页的 URL 与维护责任人（第 4 章的教训：台账记到人）。危机二的完整封口，从此是「签名 + 清单 + 双渠道 + 演练」四件套的组合，而不是一句「以后注意」。

## 本章小结

- 签名 = 哈希的完整性 + 私钥的身份：多了**认证**与**不可否认**两样能力，缺一不可称之为「防伪」
- 危机二的根因是「校验基准与文件同源被一锅端」——签名的本质是把基准（私钥）挪到攻击者碰不到的地方
- 签的是摘要不是全文：先 SHA-256 再签名，.sig 长度恒定（64~256 字节）且几乎哪儿都贴得下，与文件大小无关
- 命令分家：RSA/EC 走 `dgst -sign`，Ed25519 走 `pkeyutl -rawin`——后者是整体签名，不做预哈希，签名确定性还消灭了随机数事故面
- 多产物发布签**清单**不逐个签：签名管身份、SHA256SUMS 管覆盖面，Debian 的 Release 文件就是这套组合
- 公钥真伪是指名要害：**指纹走另一条渠道公示**；「谁为公钥背书」的终极答案叫证书
- 验签失败是安全信号不是故障：先当事故查，再查参数；CI 必须验签失败即中止
- 篡改与冒名两类演练都要做：改文件失败、换公钥失败、正常包通过，三条全绿才算上线

**下一章预告**：签名解决了「包是谁发的」，但公钥本身的信任还吊在一枚手工公示的指纹上。下一章拆开「证书」这个黑盒——那张浏览器地址栏小锁背后的数字身份证，每个字段都值得读一遍；读完后你会重新理解第5章「指纹走另一条渠道」的真正含义。
