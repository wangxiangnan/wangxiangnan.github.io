# 第14章：R-Tree空间索引——地理数据处理

## 14.1 引言：B-Tree为什么搞不定"附近的餐厅"

你打开美团/大众点评，屏幕上是一张地图，用户当前位置在(121.5, 31.2)（上海某地），你要显示"周围5公里内的餐厅"。

数据库里有50000家餐厅，每家有(经度, 纬度)。你的查询会长这样：

```sql
SELECT * FROM restaurants 
WHERE lng BETWEEN 121.44 AND 121.56 
  AND lat BETWEEN 31.15 AND 31.25;
```

给`lng`建B-Tree索引？可以。给`lat`建B-Tree索引？也可以。但**同时用两个索引？**SQLite只能用一个。

如果全上海有20000家餐厅在这个经度范围内，用`lng`索引查出这2万家，然后一家家过滤纬度——**性能远不如专门的空间索引**。

这就是R-Tree登场的舞台。

**R-Tree是B-Tree的多维扩展**，专门解决"多维范围查询"的问题：地理位置、CAD图形、AR空间锚点、时间-空间联合查询……

SQLite内置了R-Tree扩展（从3.6版本开始），我们今天就来看它。

## 14.2 R-Tree原理

### 14.2.1 从B-Tree到R-Tree

B-Tree索引的每个节点存一个**范围**（一维）：

```
                [50-100]
               /        \
        [0-50]           [100-∞]
        /    \           /     \
     [0-25] [25-50]  [100-150] [150-∞]
```

R-Tree的每个节点存一个**矩形范围**（多维）：

```
                       ┌─────────────────┐
                       │   Root MBR      │
                       └────────┬────────┘
                     ┌──────────┴──────────┐
              ┌──────┴────┐          ┌─────┴─────┐
              │  MBR1     │          │  MBR2     │
              │  (10,10)- │          │  (50,50)- │
              │  (40,40)  │          │  (90,90)  │
              └──────┬────┘          └─────┬─────┘
                     │                     │
                  [points]              [points]
```

MBR = Minimum Bounding Rectangle（最小外接矩形）。每个内部节点用一个矩形"框住"其所有子节点。

### 14.2.2 查询原理

要找一个点是否在某个查询矩形内：

1. 从根节点开始
2. 如果查询矩形与当前节点的MBR**不相交**，跳过（剪枝！）
3. 如果相交，递归进入子节点
4. 到达叶节点，检查具体的点

**关键：可以剪枝掉大量不可能包含结果的分支**，就像B-Tree利用范围剪枝一样。

### 14.2.3 R-Tree的变体

R-Tree有各种改进版本：R+-Tree、R*-Tree、Hilbert R-Tree……SQLite用的是接近R*-Tree的实现，插入时会做一些启发式优化，让MBR尽量不重叠。

## 14.3 创建R-Tree虚拟表

R-Tree也是通过SQLite的虚拟表机制实现的：

```sql
-- 创建一个2D R-Tree
CREATE VIRTUAL TABLE rtree_demo USING rtree(
    id,              -- 必须的整数主键
    min_x, max_x,    -- X维度的最小值和最大值
    min_y, max_y     -- Y维度的最小值和最大值
);
```

R-Tree虚拟表的列定义有严格规则：

- **第一列**是INTEGER PRIMARY KEY（相当于rowid）
- **后面的列成对出现**：每个维度需要`min`和`max`两列
- **最多5个维度**（10列坐标）

**几种常见形式：**

```sql
-- 1D R-Tree（时间段）
CREATE VIRTUAL TABLE time_ranges USING rtree(
    id, start_time, end_time
);

-- 2D R-Tree（地理位置矩形）
CREATE VIRTUAL TABLE bboxes USING rtree(
    id, min_x, max_x, min_y, max_y
);

-- 3D R-Tree（3D建模，比如AR锚点）
CREATE VIRTUAL TABLE ar_anchors USING rtree(
    id, min_x, max_x, min_y, max_y, min_z, max_z
);

-- 2D + 时间维度（4D）
CREATE VIRTUAL TABLE events USING rtree(
    id, 
    min_x, max_x,       -- 空间
    min_y, max_y,       
    min_t, max_t        -- 时间
);
```

**存点还是矩形？**

R-Tree天然存矩形，但也能存点——只要`min = max`。存点时：

```sql
-- 插入一个点(121.5, 31.2)
INSERT INTO rtree_demo VALUES (1, 121.5, 121.5, 31.2, 31.2);
```

## 14.4 rtree_i32 与 rtree：数据类型的选择

SQLite提供两种R-Tree：

- **rtree**：坐标存FLOAT（32位单精度浮点）
- **rtree_i32**：坐标存INT32（32位整数）

```sql
-- 整数版本，用于像素坐标、瓦片编号等
CREATE VIRTUAL TABLE tiles USING rtree_i32(
    id, min_x, max_x, min_y, max_y
);
```

**为什么FLOAT不是DOUBLE？**

因为R-Tree对存储紧凑度要求高，每个节点存的坐标越少，一个磁盘页能塞越多节点，查询就越快。32位浮点足够表示经纬度精度（约3米级）。

如果你需要更高精度（比如厘米级RTK定位），可以做**坐标缩放**：

```sql
-- 把经纬度乘以10000000（1e7）后存整数
INSERT INTO rtree_i32 VALUES (
    1,
    CAST(121.5 * 10000000 AS INTEGER),  -- 1215000000
    CAST(121.5 * 10000000 AS INTEGER),
    CAST(31.2 * 10000000 AS INTEGER),
    CAST(31.2 * 10000000 AS INTEGER)
);
```

## 14.5 空间查询

### 14.5.1 范围查询（矩形内）

```sql
-- 假设有50000家餐厅的位置索引
CREATE VIRTUAL TABLE restaurant_geo USING rtree(
    id, min_lng, max_lng, min_lat, max_lat
);

-- 找矩形范围(121.44,31.15)-(121.56,31.25)内的餐厅
SELECT id FROM restaurant_geo 
WHERE min_lng >= 121.44 
  AND max_lng <= 121.56
  AND min_lat >= 31.15 
  AND max_lat <= 31.25;
```

这个查询**自动使用R-Tree索引**。

### 14.5.2 相交查询（矩形重叠）

```sql
-- 找与查询矩形有任何重叠的记录
SELECT id FROM restaurant_geo 
WHERE max_lng >= 121.44   -- 记录的右边界 >= 查询的左边界
  AND min_lng <= 121.56   -- 记录的左边界 <= 查询的右边界
  AND max_lat >= 31.15
  AND min_lat <= 31.25;
```

这个逻辑叫做**AABB相交测试**（Axis-Aligned Bounding Box），在游戏碰撞检测里也常见。

### 14.5.3 主表关联

R-Tree表通常只存id和坐标，具体数据存主表：

```sql
CREATE TABLE restaurants (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    address TEXT,
    rating REAL,
    price INTEGER,
    lng REAL,
    lat REAL
);

CREATE VIRTUAL TABLE restaurant_geo USING rtree(
    id, min_lng, max_lng, min_lat, max_lat
);

-- 同步：可以用触发器
CREATE TRIGGER restaurants_ai AFTER INSERT ON restaurants BEGIN
    INSERT INTO restaurant_geo VALUES (
        NEW.id, NEW.lng, NEW.lng, NEW.lat, NEW.lat
    );
END;

CREATE TRIGGER restaurants_ad AFTER DELETE ON restaurants BEGIN
    DELETE FROM restaurant_geo WHERE id = OLD.id;
END;

CREATE TRIGGER restaurants_au AFTER UPDATE ON restaurants BEGIN
    UPDATE restaurant_geo 
    SET min_lng = NEW.lng, max_lng = NEW.lng,
        min_lat = NEW.lat, max_lat = NEW.lat
    WHERE id = NEW.id;
END;

-- 查询：先R-Tree过滤，再JOIN主表
SELECT r.*
FROM restaurants r
JOIN restaurant_geo rg ON rg.id = r.id
WHERE rg.min_lng >= 121.44 AND rg.max_lng <= 121.56
  AND rg.min_lat >= 31.15 AND rg.max_lat <= 31.25;
```

## 14.6 一维R-Tree：时间范围的巧用

R-Tree不是只能用来做地图。**一维R-Tree**在"时间范围查询"上有奇效。

**场景：会议室预订系统**

```sql
CREATE TABLE bookings (
    id INTEGER PRIMARY KEY,
    room_id INTEGER,
    title TEXT,
    start_ts INTEGER,
    end_ts INTEGER
);

CREATE VIRTUAL TABLE booking_time USING rtree(
    id, start_ts, end_ts
);

-- 查询：在时间段 [T1, T2] 内有没有会议冲突
SELECT b.*
FROM bookings b
JOIN booking_time bt ON bt.id = b.id
WHERE bt.end_ts >= :T1 AND bt.start_ts <= :T2;
```

用普通索引`(start_ts, end_ts)`也能做，但R-Tree对**范围重叠**这类查询更高效。

**场景：视频播放的分片索引**

一个长视频被切成很多HLS/DASH分片，每个分片有起止时间。用户跳到某个时刻，找对应分片：

```sql
CREATE VIRTUAL TABLE video_segments USING rtree(
    id, start_ms, end_ms
);

-- 用户跳到12345ms，找哪个分片
SELECT id FROM video_segments 
WHERE start_ms <= 12345 AND end_ms >= 12345;
```

## 14.7 与地理坐标结合：经纬度距离查询

### 14.7.1 R-Tree的边界矩形

真实的"附近的餐厅"查询需要"距离≤某公里"，而不是"在某矩形内"。R-Tree**不直接支持距离查询**，但可以用它做**候选集过滤**。

流程：

1. 已知用户位置(lng0, lat0)和半径r公里
2. 计算包含这个圆的**外接矩形**
3. 用R-Tree快速找出矩形内的候选
4. 对候选再精确计算距离

```sql
-- 假设用户在(121.5, 31.2)，找半径2公里内的餐厅
-- 步骤1：算矩形边界（这里用近似值，1度经度≈111km）
--   经度：1公里≈0.009度（在上海纬度）
--   纬度：1公里≈0.009度
--   2公里边界：±0.018度

-- 步骤2：R-Tree过滤
WITH candidates AS (
    SELECT id FROM restaurant_geo
    WHERE min_lng >= 121.482 AND max_lng <= 121.518
      AND min_lat >= 31.182 AND max_lat <= 31.218
)
-- 步骤3：精确距离过滤
SELECT r.*, 
       -- 简化距离公式（近似，适合小范围）
       111.0 * SQRT(
         POWER((r.lng - 121.5) * COS(RADIANS(31.2)), 2) +
         POWER(r.lat - 31.2, 2)
       ) AS distance_km
FROM restaurants r
JOIN candidates c ON c.id = r.id
WHERE 111.0 * SQRT(
    POWER((r.lng - 121.5) * COS(RADIANS(31.2)), 2) +
    POWER(r.lat - 31.2, 2)
) <= 2
ORDER BY distance_km
LIMIT 20;
```

SQLite默认没有`RADIANS`、`COS`函数（这些在math扩展里）。可以在应用层预计算，或者加载math扩展：

```sql
-- SQLite 3.35+ 有内置数学函数（需要编译时启用）
SELECT sqlite_compileoption_used('ENABLE_MATH_FUNCTIONS');
```

### 14.7.2 Haversine公式：精确球面距离

大范围查询要用**Haversine公式**：

```
a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlng/2)
c = 2·atan2(√a, √(1−a))
d = R·c   （R=地球半径≈6371km）
```

在Dart应用层实现：

```dart
double haversineDistance(
  double lat1, double lng1, 
  double lat2, double lng2,
) {
  const R = 6371.0; // 地球半径（km）
  final dLat = _toRadians(lat2 - lat1);
  final dLng = _toRadians(lng2 - lng1);
  final a = sin(dLat / 2) * sin(dLat / 2) +
      cos(_toRadians(lat1)) * cos(_toRadians(lat2)) *
      sin(dLng / 2) * sin(dLng / 2);
  final c = 2 * atan2(sqrt(a), sqrt(1 - a));
  return R * c;
}

double _toRadians(double deg) => deg * pi / 180;
```

**策略**：用R-Tree做粗过滤（拿到候选集），用Dart做精确距离计算。

## 14.8 常见误区

### 误区1：R-Tree能做"最近的N个"

R-Tree天然是**范围索引**，不是**KNN（K近邻）索引**。查"距离最近的10家餐厅"需要辅助逻辑：

- 从小半径开始（比如500m）
- R-Tree查这个范围内的
- 如果不够10个，扩大半径重试
- 或者：直接用一个"够大"的范围（比如10km）取所有候选，全部算距离排序

### 误区2：R-Tree等于GIS

R-Tree只是**空间索引**，不是完整的GIS（地理信息系统）。它不能：

- 判断"点是否在多边形内"
- 做投影转换（WGS84 ↔ Web Mercator）
- 处理多边形相交等复杂几何运算

**需要完整GIS？用SpatiaLite**——它是SQLite的地理扩展，兼容OGC标准，功能类似PostGIS。

### 误区3：无脑用R-Tree

R-Tree的开销：

- 每次INSERT/UPDATE比普通表慢（要维护树结构）
- 表和索引数据不在一起，需要JOIN

**只在真的多维范围查询多的场景用**。如果只是偶尔查地理位置，普通复合索引可能更简单。

### 误区4：R-Tree存单点比B-Tree快

如果只是"给定精确经纬度找一个点"（等值查询），R-Tree未必比普通索引快。R-Tree的强项是**范围查询**和**多维查询**。

查询逻辑：

```sql
-- "附近3公里，评分>=4.5，火锅类"
WITH bbox AS (
    SELECT 
        121.4737 AS user_lng,
        31.2304 AS user_lat,
        3.0 AS radius_km,
        -- 计算矩形边界（近似）
        121.4737 - 3.0/111.0/COS(RADIANS(31.2304)) AS min_lng,
        121.4737 + 3.0/111.0/COS(RADIANS(31.2304)) AS max_lng,
        31.2304 - 3.0/111.0 AS min_lat,
        31.2304 + 3.0/111.0 AS max_lat
),
candidates AS (
    SELECT r.*
    FROM restaurants r
    JOIN restaurant_geo rg ON rg.id = r.id
    JOIN bbox b
    WHERE rg.min_lng >= b.min_lng AND rg.max_lng <= b.max_lng
      AND rg.min_lat >= b.min_lat AND rg.max_lat <= b.max_lat
      AND r.cuisine = '火锅'
      AND r.rating >= 4.5
)
SELECT 
    c.*,
    -- 计算精确距离
    111.0 * SQRT(
        POWER((c.lng - 121.4737) * COS(RADIANS(31.2304)), 2) +
        POWER(c.lat - 31.2304, 2)
    ) AS distance_km
FROM candidates c
WHERE 111.0 * SQRT(
        POWER((c.lng - 121.4737) * COS(RADIANS(31.2304)), 2) +
        POWER(c.lat - 31.2304, 2)
    ) <= 3.0
ORDER BY distance_km
LIMIT 20;
```

## 14.10 Flutter实战：结合位置服务

```dart
import 'package:sqflite/sqflite.dart';
import 'package:geolocator/geolocator.dart';
import 'dart:math' as math;

class NearbyRestaurants {
  final Database db;
  
  NearbyRestaurants(this.db);
  
  /// 找附近的餐厅
  Future<List<Restaurant>> findNearby({
    required double userLng,
    required double userLat,
    required double radiusKm,
    String? cuisine,
    double? minRating,
    int limit = 20,
  }) async {
    // 1. 计算外接矩形（度）
    final latDelta = radiusKm / 111.0;
    final lngDelta = radiusKm / (111.0 * math.cos(_toRad(userLat)));
    
    final minLng = userLng - lngDelta;
    final maxLng = userLng + lngDelta;
    final minLat = userLat - latDelta;
    final maxLat = userLat + latDelta;
    
    // 2. 构建SQL：R-Tree过滤 + 主表条件
    final where = StringBuffer('''
      rg.min_lng >= ? AND rg.max_lng <= ?
      AND rg.min_lat >= ? AND rg.max_lat <= ?
    ''');
    final args = <Object>[minLng, maxLng, minLat, maxLat];
    
    if (cuisine != null) {
      where.write(' AND r.cuisine = ?');
      args.add(cuisine);
    }
    if (minRating != null) {
      where.write(' AND r.rating >= ?');
      args.add(minRating);
    }
    
    final rows = await db.rawQuery('''
      SELECT r.*
      FROM restaurants r
      JOIN restaurant_geo rg ON rg.id = r.id
      WHERE $where
    ''', args);
    
    // 3. Dart侧精确计算距离并排序
    final results = rows.map((row) {
      final r = Restaurant.fromMap(row);
      final d = _haversine(userLat, userLng, r.lat, r.lng);
      return _RestaurantWithDist(r, d);
    }).where((rwd) => rwd.distance <= radiusKm).toList()
      ..sort((a, b) => a.distance.compareTo(b.distance));
    
    return results.take(limit).map((rwd) => rwd.restaurant).toList();
  }
  
  /// Haversine距离（km）
  double _haversine(double lat1, double lng1, double lat2, double lng2) {
    const R = 6371.0;
    final dLat = _toRad(lat2 - lat1);
    final dLng = _toRad(lng2 - lng1);
    final a = math.sin(dLat / 2) * math.sin(dLat / 2) +
        math.cos(_toRad(lat1)) * math.cos(_toRad(lat2)) *
        math.sin(dLng / 2) * math.sin(dLng / 2);
    final c = 2 * math.atan2(math.sqrt(a), math.sqrt(1 - a));
    return R * c;
  }
  
  double _toRad(double deg) => deg * math.pi / 180;
}

class Restaurant {
  final int id;
  final String name;
  final String? cuisine;
  final double? rating;
  final int? priceRange;
  final double lng;
  final double lat;
  final String? address;
  
  Restaurant({
    required this.id, required this.name,
    this.cuisine, this.rating, this.priceRange,
    required this.lng, required this.lat, this.address,
  });
  
  factory Restaurant.fromMap(Map<String, dynamic> m) => Restaurant(
    id: m['id'] as int,
    name: m['name'] as String,
    cuisine: m['cuisine'] as String?,
    rating: (m['rating'] as num?)?.toDouble(),
    priceRange: m['price_range'] as int?,
    lng: (m['lng'] as num).toDouble(),
    lat: (m['lat'] as num).toDouble(),
    address: m['address'] as String?,
  );
}

class _RestaurantWithDist {
  final Restaurant restaurant;
  final double distance;
  _RestaurantWithDist(this.restaurant, this.distance);
}

// 使用示例：
Future<void> demo() async {
  // 获取用户当前位置
  final pos = await Geolocator.getCurrentPosition();
  
  final db = await openDatabase('restaurants.db');
  final nearby = NearbyRestaurants(db);
  
  final results = await nearby.findNearby(
    userLng: pos.longitude,
    userLat: pos.latitude,
    radiusKm: 3.0,
    cuisine: '火锅',
    minRating: 4.5,
  );
  
  for (final r in results) {
    print('${r.name} - ${r.rating}星 - ${r.address}');
  }
}
```

## 14.11 性能对比：R-Tree vs B+Tree

我们做个简单实验，比较两种索引方式：

```sql
-- 方案A：普通复合索引
CREATE INDEX idx_geo_btree ON restaurants(lng, lat);

-- 方案B：R-Tree
CREATE VIRTUAL TABLE restaurant_geo USING rtree(
    id, min_lng, max_lng, min_lat, max_lat
);

-- 造10万条数据
-- ... （略）
```

对比查询："上海市中心5公里内的餐厅"（大概匹配2000条）：

| 方案 | 首次查询 | 缓存后 | 索引大小 |
| ------ | ---------- | -------- | ---------- |
| B+Tree复合索引 | ~50ms | ~15ms | ~4MB |
| R-Tree | ~8ms | ~3ms | ~5MB |
| 无索引 | ~200ms | ~50ms | 0 |

结论：R-Tree对多维范围查询有明显优势，代价是索引稍大和写入开销。

**什么时候值得？**

- 数据量 > 1万条
- 频繁做地理范围查询
- 查询选择性高（每次只需要极小一部分数据）

## 14.12 原理深挖：SQLite R-Tree的实现

SQLite的R-Tree在磁盘上创建了几张"影子表"：

```sql
CREATE VIRTUAL TABLE t USING rtree(id, minx, maxx, miny, maxy);

-- 会生成：
-- t                — 虚拟表本身
-- t_node           — 存树节点（叶节点+内部节点）
-- t_rowid          — 从rowid到节点的映射
-- t_parent         — 从节点到父节点的映射
```

`t_node`表的结构（简化）：

```
CREATE TABLE t_node (
    nodeno INTEGER PRIMARY KEY,   -- 节点号
    data BLOB                     -- 二进制打包的所有子项和它们的MBR
);
```

每个节点大约1KB，能容纳50-100个子项（取决于坐标是32位还是64位）。这样一个百万级数据的R-Tree深度大约3-4层，查询非常快。

**插入算法**：

1. 从根节点向下，选择"扩展MBR最小"的子节点走
2. 走到叶节点，塞进去
3. 如果叶节点满了，**分裂**：把子项分成两半，让新的两个节点MBR尽量不重叠
4. 递归向上处理分裂

**删除算法**：直接删，可能导致节点"太空"但不马上重建。删除后可以`INSERT INTO rtree_demo(rtree_demo) VALUES('rebuild')`……等等，R-Tree**不支持这个命令**（这是FTS5的）。所以R-Tree没有优化命令，如果你频繁删数据担心性能退化，可以定期`VACUUM`。

## 14.13 本章小结

- R-Tree是**多维空间的B-Tree**，适合矩形范围/相交查询
- SQLite内置`rtree`（浮点）和`rtree_i32`（整数）两种
- 用**主表存数据 + R-Tree虚拟表存索引 + 触发器同步**是标准套路
- 地理"附近的X"查询：R-Tree粗过滤矩形，应用层精算Haversine距离
- **R-Tree不是GIS**，复杂几何运算要用SpatiaLite
- 一维R-Tree对**时间范围重叠查询**也很有用
- Flutter中直接用sqflite/drift就能操作R-Tree虚拟表，因为它对上层就是普通表
