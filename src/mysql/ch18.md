# 第18章 数据库设计实战

**生活类比：** 盖房子之前要画图纸，写代码之前要做架构设计，建数据库之前也要做"数据库设计"。好的数据库设计就像房子的地基——地基打不好，后面无论怎么装修都会出问题。这一章我们来学习如何设计一个结构合理、性能优秀的数据库。

## 18.1 三大范式

范式(Normal Form)是数据库设计的"标准规范"，目的是减少数据冗余、避免数据异常。

**第一范式(1NF)：列不可再分**

每个字段都是原子值，不能在一个字段中存多个值。

```sql
-- 违反1NF的反面例子：地址字段混在一起
CREATE TABLE bad_customers (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    address VARCHAR(200)  -- '北京市海淀区中关村大街1号' 混在一起
);

-- 符合1NF：地址拆分为多个字段
CREATE TABLE good_customers (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    province VARCHAR(20),
    city VARCHAR(20),
    district VARCHAR(30),
    street VARCHAR(100)
);
```

**第二范式(2NF)：消除部分依赖**

在1NF基础上，所有非主键字段必须完全依赖于主键，不能只依赖主键的一部分。

```sql
-- 违反2NF：order_detail 的联合主键是 (order_id, product_id)
-- 但 product_name 只依赖 product_id，不依赖 order_id
CREATE TABLE bad_order_details (
    order_id INT,
    product_id INT,
    product_name VARCHAR(100),  -- 只依赖 product_id
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- 符合2NF：拆分表
CREATE TABLE order_details (
    order_id INT,
    product_id INT,
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    price DECIMAL(10,2)
);
```

**第三范式(3NF)：消除传递依赖**

在2NF基础上，非主键字段不能依赖于其他非主键字段。

```sql
-- 违反3NF：department_name 依赖 department_id，而 department_id 依赖主键 employee_id
CREATE TABLE bad_employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department_id INT,
    department_name VARCHAR(50)  -- 传递依赖：id -> department_id -> department_name
);

-- 符合3NF：拆出部门表
CREATE TABLE departments (
    id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);

CREATE TABLE employees_3nf (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(id)
);
```

**反范式：有时候冗余是好事**

范式化减少了冗余，但增加了JOIN。在OLAP（分析型）场景下，适当的反范式化能大幅提升查询性能：

```sql
-- 反范式化：把常用查询字段冗余到订单表
CREATE TABLE orders_denormalized (
    id INT PRIMARY KEY,
    user_id INT,
    user_name VARCHAR(50),       -- 冗余字段，避免JOIN users表
    product_id INT,
    product_name VARCHAR(100),   -- 冗余字段，避免JOIN products表
    amount DECIMAL(10,2),
    created_at DATETIME
);

-- 查询时不再需要JOIN
SELECT user_name, product_name, amount
FROM orders_denormalized
WHERE created_at >= '2024-01-01';
```

> [!TIP] 提示
> 没有绝对正确的范式级别。OLTP系统（高并发写入）倾向3NF，OLAP系统（复杂查询分析）倾向反范式。根据实际业务场景做权衡才是真本事。

## 18.2 ER模型与ER图

ER（Entity-Relationship）模型是数据库设计的蓝图。核心概念：

- **实体(Entity)**：现实世界中的对象，对应数据库中的"表"
- **属性(Attribute)**：实体的特征，对应表中的"列"
- **关系(Relationship)**：实体之间的关联

ER图的基本画法（用文字描述）：

- 矩形表示实体
- 椭圆表示属性
- 菱形表示关系
- 连线上的 1、N、M 表示关系的基数

## 18.3 表关系设计

**一对一(1:1)：**

```sql
-- 用户基本信息表
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 用户详细信息表（一对一）
CREATE TABLE user_profiles (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL UNIQUE,  -- UNIQUE 保证一对一
    real_name VARCHAR(50),
    phone VARCHAR(20),
    avatar_url VARCHAR(255),
    bio TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

> [!TIP] 提示
> 一对一通常用于：把不常用的大字段拆分出去（如个人简介），或者把敏感信息隔离（如身份证号）。

**一对多(1:N)：**

```sql
-- 部门表（一方）
CREATE TABLE departments (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
);

-- 员工表（多方）
CREATE TABLE employees_rel (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES departments(id) ON DELETE SET NULL
);
```

**多对多(M:N)：**

```sql
-- 学生表
CREATE TABLE students (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
);

-- 课程表
CREATE TABLE courses (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    teacher VARCHAR(50)
);

-- 中间表：实现多对多
CREATE TABLE student_courses (
    student_id INT,
    course_id INT,
    enrollment_date DATE DEFAULT (CURRENT_DATE),
    grade DECIMAL(5,2),
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE,
    FOREIGN KEY (course_id) REFERENCES courses(id) ON DELETE CASCADE
);
```

## 18.4 外键约束

外键是数据库层面的"关联保护伞"，确保引用关系的完整性：

```sql
CREATE TABLE orders (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    status VARCHAR(20) DEFAULT 'pending',
    total_amount DECIMAL(10,2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    -- 外键约束：级联删除
    FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE CASCADE        -- 删除用户时自动删除其订单
        ON UPDATE CASCADE        -- 用户ID变更时自动更新
);

-- ON DELETE 的选项：
-- CASCADE:    级联删除（删除父记录，子记录也删除）
-- SET NULL:   设为NULL（删除父记录，子记录外键字段设为NULL）
-- RESTRICT:   拒绝删除（有子记录时不允许删除父记录）
-- NO ACTION:  与RESTRICT类似（MySQL中效果相同）
```

## 18.5 外键 vs 应用层维护

| 对比项 | 外键约束 | 应用层维护 |
|--------|---------|-----------|
| 数据一致性 | 数据库强制保证 | 依赖代码正确性 |
| 性能 | 有额外开销（每次写入检查） | 无额外开销 |
| 灵活性 | 修改表结构麻烦 | 修改灵活 |
| 分库分表 | 不支持跨库外键 | 天然支持 |
| 调试 | 报错信息不够友好 | 可以自定义错误信息 |

> [!TIP] 提示
> 在微服务架构和分库分表场景下，外键约束往往力不从心。很多互联网团队选择在应用层维护关联关系，放弃数据库外键。但如果你的系统是单体应用、单库部署，外键约束是保证数据一致性的好帮手。

## 18.6 常用设计模式

**软删除（逻辑删除）：**

```sql
CREATE TABLE posts (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    title VARCHAR(200) NOT NULL,
    content TEXT,
    is_deleted TINYINT(1) DEFAULT 0,  -- 0=正常, 1=已删除
    deleted_at TIMESTAMP NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 查询时自动过滤已删除的记录
SELECT * FROM posts WHERE is_deleted = 0;

-- "删除"操作实际上只是标记
UPDATE posts SET is_deleted = 1, deleted_at = NOW() WHERE id = 123;
```

**乐观锁（版本号机制）：**

```sql
CREATE TABLE products_opt (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100),
    price DECIMAL(10,2),
    stock INT,
    version INT DEFAULT 1  -- 版本号
);

-- 更新时检查版本号
UPDATE products_opt
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;

-- 如果 affected_rows = 0，说明有其他事务已经修改了这条记录
-- 应用层需要重新读取并重试
```

**审计字段（追踪数据的来龙去脉）：**

```sql
CREATE TABLE orders_audit (
    id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,
    total_amount DECIMAL(10,2),
    status VARCHAR(20),

    -- 审计字段四件套
    created_by VARCHAR(50),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_by VARCHAR(50),
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

## 18.7 命名规范

好的命名规范让数据库"可读"：

```sql
-- 表名：小写、下划线分隔、复数形式
CREATE TABLE order_items ( ... );

-- 字段名：小写、下划线分隔、语义明确
-- 好的命名
user_id, order_status, created_at, is_active, total_amount

-- 差的命名
uid, status, ctime, flag, amt

-- 索引命名规范
-- 普通索引：idx_表名_字段名
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 唯一索引：uk_表名_字段名
CREATE UNIQUE INDEX uk_users_email ON users(email);

-- 主键：pk_表名（通常PRIMARY KEY自动命名）
```

## 18.8 常见反模式

**反模式1：万能表（God Table）**
把所有字段塞进一张表，上百列的"超级表"。
解决方案：按业务领域拆分成多张表。

**反模式2：逗号分隔存储多值**

```sql
-- 反面教材
CREATE TABLE bad_tags (
    article_id INT,
    tags VARCHAR(255)  -- 'MySQL,数据库,教程' 逗号分隔存储
);

-- 正确做法：用关联表
CREATE TABLE article_tags (
    article_id INT,
    tag_id INT,
    PRIMARY KEY (article_id, tag_id)
);

CREATE TABLE tags (
    id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);
```

**反模式3：用字符串存日期**

```sql
-- 反面教材
CREATE TABLE bad_events (
    event_date VARCHAR(20)  -- '2024-01-15' 字符串存储
);

-- 正确做法
CREATE TABLE good_events (
    event_date DATE,        -- 用DATE类型
    event_time DATETIME,    -- 需要时间就用DATETIME
    event_ts TIMESTAMP      -- 需要时区就用TIMESTAMP
);
```

**反模式4：主键使用业务字段**

```sql
-- 反面教材：用手机号做主键
CREATE TABLE bad_users (
    phone VARCHAR(11) PRIMARY KEY,  -- 手机号可能变更！
    name VARCHAR(50)
);

-- 正确做法：使用自增ID或UUID
CREATE TABLE good_users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    phone VARCHAR(11) UNIQUE,  -- 手机号作为唯一索引
    name VARCHAR(50)
);
```

## 18.9 完整案例：设计一个电商数据库

让我们把前面学到的知识综合运用，设计一个完整的电商数据库：

```sql
-- =============================================
-- 电商数据库设计：shop_db
-- =============================================

-- 1. 用户表
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    password_hash VARCHAR(255) NOT NULL,
    status ENUM('active', 'inactive', 'banned') DEFAULT 'active',
    is_deleted TINYINT(1) DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE INDEX uk_username (username),
    UNIQUE INDEX uk_email (email),
    INDEX idx_phone (phone),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 2. 用户详情表（一对一）
CREATE TABLE user_profiles (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    real_name VARCHAR(50),
    avatar_url VARCHAR(500),
    gender ENUM('male', 'female', 'other'),
    birthday DATE,
    bio TEXT,

    UNIQUE INDEX uk_user_id (user_id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 3. 收货地址表（一对多）
CREATE TABLE addresses (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    receiver_name VARCHAR(50) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    province VARCHAR(20),
    city VARCHAR(20),
    district VARCHAR(30),
    street VARCHAR(200) NOT NULL,
    is_default TINYINT(1) DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_user_id (user_id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 4. 商品分类表（自关联，支持多级分类）
CREATE TABLE categories (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    parent_id INT NULL,
    level TINYINT DEFAULT 1,
    sort_order INT DEFAULT 0,

    INDEX idx_parent_id (parent_id),
    FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 5. 商品表
CREATE TABLE products (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    category_id INT NOT NULL,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    price DECIMAL(10,2) NOT NULL,
    original_price DECIMAL(10,2),
    stock INT NOT NULL DEFAULT 0,
    sales_count INT DEFAULT 0,
    status ENUM('on_sale', 'off_shelf', 'sold_out') DEFAULT 'on_sale',
    is_deleted TINYINT(1) DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    version INT DEFAULT 1,  -- 乐观锁版本号

    INDEX idx_category_id (category_id),
    INDEX idx_status (status),
    INDEX idx_price (price),
    FULLTEXT INDEX ft_name_desc (name, description),
    FOREIGN KEY (category_id) REFERENCES categories(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 6. 订单表
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(32) NOT NULL,  -- 业务订单号
    user_id BIGINT NOT NULL,
    address_id BIGINT,
    total_amount DECIMAL(10,2) NOT NULL,
    discount_amount DECIMAL(10,2) DEFAULT 0.00,
    pay_amount DECIMAL(10,2) NOT NULL,
    status ENUM('pending', 'paid', 'shipped', 'delivered', 'cancelled', 'refunded') DEFAULT 'pending',
    payment_method VARCHAR(20),
    paid_at TIMESTAMP NULL,
    shipped_at TIMESTAMP NULL,
    completed_at TIMESTAMP NULL,
    remark VARCHAR(500),
    is_deleted TINYINT(1) DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE INDEX uk_order_no (order_no),
    INDEX idx_user_id (user_id),
    INDEX idx_status (status),
    INDEX idx_created_at (created_at),
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (address_id) REFERENCES addresses(id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 7. 订单明细表
CREATE TABLE order_items (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    product_name VARCHAR(200) NOT NULL,   -- 冗余字段：下单时的商品名
    product_price DECIMAL(10,2) NOT NULL, -- 冗余字段：下单时的价格
    quantity INT NOT NULL,
    subtotal DECIMAL(10,2) NOT NULL,

    INDEX idx_order_id (order_id),
    INDEX idx_product_id (product_id),
    FOREIGN KEY (order_id) REFERENCES orders(id),
    FOREIGN KEY (product_id) REFERENCES products(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 8. 购物车表
CREATE TABLE shopping_cart (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL DEFAULT 1,
    selected TINYINT(1) DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE INDEX uk_user_product (user_id, product_id),
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

这个设计体现了几个核心原则：

1. **遵循3NF**：数据冗余控制在合理范围
2. **合理使用冗余**：订单明细中保存下单时的商品名和价格（历史快照）
3. **软删除**：用户、商品、订单都支持软删除
4. **乐观锁**：商品表使用版本号防止并发更新问题
5. **审计字段**：所有核心表都有 created_at 和 updated_at
6. **完善的索引**：为常用查询字段建立索引
7. **合理的外键**：定义了关键的外键关系
8. **清晰的命名**：统一的命名规范

## 小结

数据库设计是一门平衡的艺术。范式化减少冗余但增加JOIN，反范式化提升查询速度但增加维护成本。外键保证一致性但影响灵活性。没有"完美"的设计，只有"最合适"的设计。记住：先理解业务，再画ER图，最后才写建表语句。好的设计让后续的开发和维护都事半功倍。
