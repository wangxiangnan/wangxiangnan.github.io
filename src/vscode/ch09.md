# 第9章：调试系统基础

> "Debugging is twice as hard as writing the code in the first place. Therefore, if you write the code as cleverly as possible, you are, by definition, not smart enough to debug it." —— Brian Kernighan

每位开发者都经历过：代码跑出诡异结果，于是一行行加 `console.log`，改一次、跑一次、再删一次，二十分钟后发现是少写了一个等号。

调试器要解决的就是这件事——**让程序停在你指定的位置，把当时的内存状态摊开给你看**，而不是靠打印去猜。这一章把 VSCode 的调试系统从"能按 F5"讲到"能读懂现场"，为第 10 章的高级玩法打好地基。

## 9.1 调试器到底在做什么

抛开界面，调试器只有三种能力：

1. **暂停（break）**：在满足条件时冻结进程；
2. **观察（inspect）**：读取冻结瞬间的变量、调用栈、作用域；
3. **步进（step）**：以行或函数为单位，控制下一次停在哪。

关键认知：**暂停的是进程，不是编辑器**。你的代码真实地停在了那一行，所以变量值不是"当时的日志"，而是"此刻的事实"。这也是调试器比 `console.log` 可靠的根本原因。

### 为什么 VSCode 能调试所有语言

VSCode 定义了一套 **Debug Adapter Protocol（DAP）**，和 LSP 让编辑器与语言解耦是同一个思路：

```
┌──────────┐   DAP（JSON-RPC）  ┌────────────────┐   原生协议   ┌──────────┐
│  VSCode  │ <────────────────> │ Debug Adapter  │ <──────────> │ Debugger │
│  (UI)    │                    │ (翻译层)       │              │ (底层)   │
└──────────┘                    └────────────────┘              └──────────┘
```

Node.js 的 V8 Inspector、Python 的 debugpy、Go 的 Delve、Java 的 JDI——对 VSCode 来说都只是"会说 DAP 的适配器"。**UI 一套，引擎各异**，所以你学会的断点、变量面板、调试控制台，在所有语言里长得一模一样。

## 9.2 第一次调试：从零到断点

### 先跑起来，再谈配置

1. 打开一个可运行的项目，在任意一行代码左侧点击行号空白处——出现红点，断点已设好；
2. 按 `F5`；
3. 首次运行时 VSCode 会让你**选择调试环境**（Node.js、Python、Chrome…），选中后自动生成 `.vscode/launch.json`；
4. 程序启动并在断点处暂停，编辑器顶部浮现调试工具栏。

如果项目已经有 `launch.json`，`F5` 会直接使用下拉菜单里选中的配置。想换配置：`Ctrl+Shift+D` 打开"运行和调试"视图，在顶部下拉框切换。

### launch 还是 attach？

这是调试配置的第一个岔路口：

| | `request: "launch"` | `request: "attach"` |
| --- | --- | --- |
| 谁启动进程 | VSCode 启动并接管 | 你已手动启动，VSCode 连上去 |
| 典型场景 | 本地开发、跑脚本、跑测试 | 已运行的服务、容器内进程、远程主机 |
| 关键配置 | `program` / `runtimeExecutable` | `port` / `processId` |

新手 90% 的场景用 `launch`。Attach 的细节（远程、容器、nodemon 热重载）放在 10.3 节展开。

### 必备快捷键

| 操作 | Windows / Linux | macOS |
| ------ | ----------------- | ------- |
| 启动 / 继续 | `F5` | `F5` |
| 不调试直接运行 | `Ctrl+F5` | `Ctrl+F5` |
| 停止 | `Shift+F5` | `⇧+F5` |
| 重启 | `Ctrl+Shift+F5` | `⌘+⇧+F5` |
| 切换断点 | `F9` | `F9` |
| 单步跳过 / 进入 / 跳出 | `F10` / `F11` / `Shift+F11` | 同左 |

## 9.3 读懂 launch.json

自动生成的配置通常够用；一旦要传参数、设环境变量、调试 TypeScript，就必须理解它。一个典型配置：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug API Server",
            "type": "node",
            "request": "launch",
            "program": "${workspaceFolder}/src/index.js",
            "args": ["--port", "3000"],
            "cwd": "${workspaceFolder}",
            "env": { "NODE_ENV": "development" },
            "envFile": "${workspaceFolder}/.env",
            "console": "integratedTerminal",
            "stopOnEntry": false,
            "skipFiles": ["<node_internals>/**", "**/node_modules/**"],
            "preLaunchTask": "build"
        }
    ]
}
```

### 核心字段

| 字段 | 作用 | 备注 |
| ------ | ------ | ------ |
| `type` | 调试器类型 | `node`、`python`、`go`、`java`…由扩展提供 |
| `request` | `launch` 或 `attach` | 见 9.2 |
| `program` | 入口文件 | 用绝对路径变量，别写相对路径 |
| `args` / `cwd` / `env` | 参数、工作目录、环境变量 | `envFile` 可整份加载 `.env` |
| `console` | 输出通道 | `internalConsole` 快但不能交互输入；需要 stdin 用 `integratedTerminal` |
| `stopOnEntry` | 启动即暂停在第一行 | 排查"启动阶段就崩"时很好用 |
| `skipFiles` | 步进时跳过的文件 | 不加 `node_modules`，你会在一堆库代码里迷路 |
| `preLaunchTask` | 调试前自动执行任务 | 值必须等于 `tasks.json` 里的 `label` |
| `sourceMaps` / `outFiles` | 源码映射 | 调试编译产物时才需要，见 10.8 |

### 路径与变量

```json
{
    "program": "${workspaceFolder}/src/index.js",  // 工作区根目录
    "args": ["--config", "${fileDirname}/config.json"], // 当前文件所在目录
    "env": { "LOG_PATH": "${env:HOME}/logs" }      // 引用系统环境变量
}
```

常用变量还有 `${file}`（当前文件）、`${relativeFile}`、`${lineNumber}`。`${input:xxx}` 可以弹出输入框，但需要在配置里额外声明 `inputs` 数组——日常调试用得不多，知道有这回事即可。

## 9.4 断点家族：从"停在这里"到"只在此时停"

设断点不等于只会点红点。按控制精度从低到高，共五种常用断点；**数据断点和异常断点**属于进阶，放在 10.5 节。

### 1. 普通断点

行号左侧点击或 `F9`。当行是空行/注释时会自动下移到最近的可执行行——所以你可能会看到断点"跳"了一行，这是正常行为。

### 2. 条件断点

右键行号 → **Add Conditional Breakpoint**，输入一个**由调试器求值的表达式**（Node 用 JavaScript，Python 用 Python）：

```javascript
req.user.id === 'admin-001'   // 只在这个用户的请求上停
items.length > 1000           // 只在异常数据上停
```

表达式的求值发生在**每次到达该行时**，所以别写有副作用的表达式（比如 `counter++`）。

### 3. 日志点（Logpoint）

右键行号 → **Add Logpoint**。它不暂停程序，只往调试控制台打一行消息——**日志点的最佳替代品**：不改代码、不重新编译、不用记得删除。

```text
Processing order {order.id} for user {req.user.name}
Total: {order.items.reduce((s, i) => s + i.price, 0)}
```

`{}` 内是表达式，由当前调试器求值（Node 是 JS，Python 是 Python）。注意：日志点只在**调试会话运行期间**生效，生产环境不会留下任何痕迹。

### 4. 命中次数断点

右键行号 → Add Conditional Breakpoint → 选择 **Hit Count**，填入数字并选择比较方式（等于、大于、大于等于、是否为其倍数）。

调试循环第 1000 次迭代才出问题？让它第 1000 次才停，而不是手动点 999 次"继续"。

### 5. 函数断点

在"运行和调试"视图的 **Breakpoints** 面板点 `+`，输入函数名。适合"我知道哪个函数有问题，但不知道它在哪个文件被调用"的场景：

```text
handleUserLogin
PaymentService.refund      // 具体形式取决于调试适配器
```

### 断点是灰色的？

断点圆圈变成**空心灰圈**表示"未验证"（unverified）——调试器还没找到对应的可执行代码。常见原因：

| 原因 | 处理 |
| ------ | ------ |
| 调试的是编译产物但没开 sourceMap | 开启 `sourceMaps` 并配置 `outFiles` |
| 源码路径与运行路径不一致 | 配置 `pathMappings`（远程/容器场景常见） |
| 断点所在模块尚未加载 | 先让程序执行到该模块，或改用函数断点 |
| 行本身不可执行 | 换到实际语句行 |

## 9.5 暂停之后：读懂现场

程序停在断点处，左侧"运行和调试"视图就是你的现场勘查工具。

### 变量（Variables）

按作用域分组。JS 调试器下通常是 `Local`（当前函数）、`Closure`（闭包捕获）、`Global`（全局）。三个高频操作：

- **双击值直接修改**（Set Variable）——修改变量后继续运行，是验证假设最快的方式；
- 右键 → **Add to Watch**，把关心的变量钉在监视面板；
- 展开对象时，getter 可能被触发，别被"看一眼就变了"吓到。

### 监视（Watch）

添加任意表达式，每次暂停自动求值：

```text
user.isAuthenticated
cart.items.filter(i => i.quantity > 0).length
JSON.stringify(config, null, 2)
```

⚠️ 监视表达式会被真实执行。写 `deleteCache()` 这种有副作用的调用，你会亲手制造一个新 bug。

### 调用堆栈（Call Stack）

显示"我是怎么走到这一行的"。点击任意一帧，编辑器和变量面板都会切到那一层的上下文——**排查"参数在哪一层被改坏了"的标准动作**：从出错帧往上逐层点，看变量在哪一帧开始不对。

### 断点面板（Breakpoints）

集中管理所有语言的断点：启用/禁用单个、全部禁用、删除、按文件分组。调试第三方库时临时全部禁用，比逐个删掉再重设高效得多。

## 9.6 控制执行流与调试控制台

### 步进的三个动作

- **Step Over（F10）**：执行整行，不进入函数——默认动作，别急着往下钻；
- **Step Into（F11）**：进入函数体；
- **Step Out（Shift+F11）**：执行完当前函数并停在调用处。

配一个心智模型：先把可疑范围用 Step Over 缩到某个函数调用，再 Step Into 钻进去，发现不对就 Step Out 退出来。**步进是二分查找，不是逐行朗读。**

### 调试控制台（Debug Console）

暂停状态下它是个带完整上下文的 REPL：

```javascript
user.name                      // 求值
user.role = 'admin'            // 改状态，验证权限分支
await fetch('/api/health')     // 支持顶层 await（js-debug）
Object.keys(config)            // 探查结构
```

它与"终端"的区别：调试控制台运行在**被调试进程的上下文里**，能访问局部变量；终端只是另一个 shell。日志点的输出、程序的标准输出也会汇入这里（取决于 `console` 配置）。

> 想看更高级的用法（变量格式化、`debug.inlineValues`、异常断点）？见 10.6。

## 9.7 实战：Express + TypeScript 调试

目标：让断点准确落在 `.ts` 源码上，而不是编译后的 JS。

### 项目与 tsconfig

```
express-app/
├── .vscode/{launch.json, tasks.json}
├── src/index.ts
├── tsconfig.json
└── package.json
```

```json
{
    "compilerOptions": {
        "target": "ES2020",
        "module": "commonjs",
        "outDir": "./dist",
        "rootDir": "./src",
        "sourceMap": true,
        "strict": true,
        "esModuleInterop": true
    }
}
```

`sourceMap: true` 是 TypeScript 可调试的前提。没有它，调试器只知道 JS 的行号，断点自然对不上源码。

### launch.json：直接跑 TS（ts-node）

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Debug Express (ts-node)",
            "type": "node",
            "request": "launch",
            "program": "${workspaceFolder}/src/index.ts",
            "runtimeArgs": ["-r", "ts-node/register"],
            "cwd": "${workspaceFolder}",
            "env": { "NODE_ENV": "development", "TS_NODE_TRANSPILE_ONLY": "true" },
            "console": "integratedTerminal",
            "skipFiles": ["<node_internals>/**", "**/node_modules/**"]
        }
    ]
}
```

要点：`program` 指向 `.ts` 入口，`runtimeArgs` 里注册 ts-node，VSCode 会自动注入调试器，**不需要手写 `--inspect-brk`**（写了反而容易和自动注入冲突）。

### tasks.json：调试前自动编译（可选）

如果你更愿意调试编译后的 JS（更接近生产），把 `program` 换成 `dist/index.js`，并用 `preLaunchTask` 保证先编译：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "compile",
            "type": "shell",
            "command": "npx tsc -p tsconfig.json",
            "group": "build",
            "problemMatcher": ["$tsc"]
        }
    ]
}
```

对应 `launch.json` 加 `"preLaunchTask": "compile"`、`"sourceMaps": true`、`"outFiles": ["${workspaceFolder}/dist/**/*.js"]`。source map 的排错细节见 10.8。

### 一次完整的调试回合

1. 在 `src/routes/users.ts` 的处理函数里设断点；
2. 选 `Debug Express (ts-node)`，`F5`；
3. 用浏览器或 `curl http://localhost:3000/api/users` 触发请求；
4. 断点命中，先看 **Call Stack** 确认请求经过了哪些中间件；
5. 在 **Watch** 里盯住 `req.params`、`req.user`，用 `F10` 逐行走过业务逻辑；
6. 怀疑数据库层时，`F11` 钻进 service 函数，再 `Shift+F11` 出来；
7. 在调试控制台里试一个候选修复方案，验证通过后再改代码。

## 9.8 调试设置与排错

```json
{
    // 调试时在代码行内联显示变量值（非常有用的"抬头看"功能）
    "debug.inlineValues": "on",
    // 会话开始时自动展开"运行和调试"视图
    "debug.openDebug": "openOnSessionStart",
    // 调试工具栏位置：floating | docked | commandCenter | hidden
    "debug.toolBarLocation": "floating",
    "debug.console.fontSize": 14,
    "debug.console.wordWrap": true
}
```

`debug.inlineValues` 设为 `on` 后，暂停时每个变量旁边直接显示当前值，很多"要不要加监视"的犹豫就此消失。

### 常见故障对照

| 症状 | 大概率原因 | 处理 |
| ------ | ----------- | ------ |
| `F5` 没反应 / 提示选择环境 | 没有 launch.json | 选环境自动生成，或手动创建 |
| 程序闪退看不到输出 | `internalConsole` 不显示部分输出 | 改 `console: "integratedTerminal"` |
| 断点是灰色空心圈 | 源码映射或路径不匹配 | 见 9.4 的排查表 |
| 断点不生效、直接跑完 | 代码被编译/压缩，或调试了错误入口 | 确认 `program` 与实际运行文件一致 |
| 一启动就停在库代码里 | 没配 `skipFiles` | 加 `<node_internals>/**`、`**/node_modules/**` |
| `preLaunchTask` 报找不到任务 | `label` 拼写不一致 | 两处字符串必须完全相同 |

📋 **本章小结**

- 调试器的本质是**暂停、观察、步进**；暂停的是真实进程，所以看到的是事实而非日志
- DAP 把 VSCode 的调试 UI 与各语言调试器解耦，学会一套界面就能调试所有语言
- `launch` 由 VSCode 启动进程，`attach` 连接已运行进程；新手先用 `launch`
- `launch.json` 里最该记住的：`program`、`cwd`、`env`、`console`、`skipFiles`、`preLaunchTask`
- 五种常用断点：普通、条件、日志点、命中次数、函数断点；数据断点与异常断点见第 10 章
- 暂停后的固定动作：看调用堆栈定位"哪一层坏了"，用监视锁定变量，在调试控制台验证假设
- 调试 TypeScript 的关键是 `sourceMap` + 正确的入口；ts-node 方案最省事
- 灰圈断点 = 未验证，优先查 sourceMap、路径映射和模块是否已加载
