# 第23章：性能优化与硬件加速

> 用 CPU 编码一部 4K 电影可能要一天，但用 GPU 可能只要一小时。这不是夸张，这是硬件加速的威力。这一章，我们让 FFmpeg 的速度坐上火箭。

## 23.1 硬件编码概述

视频编码是一个计算密集型任务。CPU 是"全能选手"——什么都能做，但做编码不是最快的。GPU 是"专业选手"——它内部有专门的硬件编码单元（ASIC），专门为视频编码优化。

```
CPU 编码（libx264）：
  - 质量最好（算法最精细）
  - 速度最慢（通用计算单元）
  - CPU 占用高
  - 适合：离线转码、追求极致质量

GPU 编码（NVENC/QSV/AMF）：
  - 质量略逊（但差距在缩小）
  - 速度飞快（专用硬件加速）
  - CPU 占用低
  - 适合：直播、实时转码、批量处理
```

## 23.2 NVIDIA NVENC

NVENC 是 NVIDIA GPU 内置的硬件编码器。从 GTX 600 系列开始，所有 NVIDIA GPU 都支持 NVENC。

**检查系统是否支持 NVENC：**

```bash
# 查看 FFmpeg 是否编译了 NVENC 支持
ffmpeg -encoders 2>/dev/null | grep nvenc

# 预期输出：
# V..... h264_nvenc         NVIDIA NVENC H.264 encoder
# V..... hevc_nvenc         NVIDIA NVENC HEVC encoder
# V..... av1_nvenc          NVIDIA NVENC AV1 encoder (RTX 40系列+)
```

如果没有输出，需要安装带 CUDA 支持的 FFmpeg：

```bash
# Ubuntu：安装 CUDA Toolkit 后重新编译 FFmpeg
sudo apt install nvidia-cuda-toolkit

# 或者直接使用 Docker（最省事）
docker run --gpus all -it --rm \
  -v $(pwd):/workspace \
  jrottenberg/ffmpeg:6-nvidia
```

**NVENC 编码基本命令：**

```bash
# H.264 NVENC 编码
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \
  -b:v 5M \
  -c:a copy \
  output_nvenc.mp4

# HEVC (H.265) NVENC 编码
ffmpeg -i input.mp4 \
  -c:v hevc_nvenc \
  -preset p4 \
  -b:v 3M \
  -c:a copy \
  output_hevc_nvenc.mp4
```

**NVENC 参数调优：**

```bash
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p4 \
  -tune hq \
  -rc vbr \
  -b:v 5M \
  -maxrate 8M \
  -bufsize 10M \
  -rc-lookahead 32 \
  -spatial-aq 1 \
  -temporal-aq 1 \
  -c:a copy \
  output.mp4
```

| 参数 | 说明 | 推荐值 |
| ------ | ------ | -------- |
| `-preset` | 编码预设 | p1（最快）- p7（最慢最好），直播用 p1-p3，离线用 p4-p7 |
| `-tune` | 调优模式 | `hq`（高质量）、`ll`（低延迟）、`ull`（超低延迟） |
| `-rc` | 码率控制 | `cbr`（恒定）、`vbr`（可变）、`constqp`（恒定质量） |
| `-rc-lookahead` | 前瞻帧数 | 0-32，越大质量越好但延迟越高 |
| `-spatial-aq` | 空间自适应量化 | 1 = 开启，提升画面均匀度 |
| `-temporal-aq` | 时间自适应量化 | 1 = 开启，提升运动画面质量 |
| `-cq` | 恒定质量值 | 1-51，越小越好（类似 CRF） |

**NVENC CQ 模式（恒定质量，类似 CRF）：**

```bash
ffmpeg -i input.mp4 \
  -c:v h264_nvenc \
  -preset p5 \
  -tune hq \
  -rc constqp \
  -cq 23 \
  -c:a copy \
  output_cq.mp4
```

**NVENC 直播推流：**

```bash
# NVENC 编码 + RTMP 推流
ffmpeg -re -i input.mp4 \
  -c:v h264_nvenc \
  -preset p2 \
  -tune ll \
  -b:v 3M \
  -maxrate 3M \
  -bufsize 6M \
  -g 60 \
  -c:a aac -b:a 128k \
  -f flv rtmp://server/live/stream
```

## 23.3 Intel QSV（Quick Sync Video）

Intel 核显自带的硬件编码器。如果你用的是 Intel CPU（大部分笔记本和台式机），不用额外买显卡就能享受硬件加速。

```bash
# 检查 QSV 支持
ffmpeg -encoders 2>/dev/null | grep qsv

# QSV 编码
ffmpeg -i input.mp4 \
  -c:v h264_qsv \
  -preset veryfast \
  -b:v 3M \
  -c:a copy \
  output_qsv.mp4

# QSV 高质量模式
ffmpeg -i input.mp4 \
  -c:v h264_qsv \
  -preset slow \
  -look_ahead 1 \
  -look_ahead_depth 30 \
  -b:v 5M \
  -c:a copy \
  output_qsv_hq.mp4

# QSV 直播推流
ffmpeg -re -i input.mp4 \
  -c:v h264_qsv \
  -preset veryfast \
  -b:v 2500k \
  -g 60 \
  -c:a aac -b:a 128k \
  -f flv rtmp://server/live/stream
```

**QSV 的优势：**

- 免费（Intel CPU 自带，不需要额外显卡）
- 功耗低（适合笔记本和嵌入式设备）
- 延迟低（适合直播和实时转码）

**QSV 的局限：**

- 质量不如 NVENC 和 CPU 编码
- 需要 Intel GPU 驱动支持
- Linux 上需要安装 `intel-media-va-driver`

## 23.4 AMD AMF 编码

AMD 显卡用户的硬件加速方案：

```bash
# 检查 AMF 支持
ffmpeg -encoders 2>/dev/null | grep amf

# AMF H.264 编码
ffmpeg -i input.mp4 \
  -c:v h264_amf \
  -quality balanced \
  -b:v 5M \
  -c:a copy \
  output_amf.mp4

# AMF HEVC 编码
ffmpeg -i input.mp4 \
  -c:v hevc_amf \
  -quality balanced \
  -b:v 3M \
  -c:a copy \
  output_hevc_amf.mp4
```

AMF 的 `-quality` 参数：

- `speed`：速度优先
- `balanced`：平衡
- `quality`：质量优先

## 23.5 Apple VideoToolbox（macOS）

macOS 用户的硬件加速方案：

```bash
# VideoToolbox H.264 编码
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -b:v 5M \
  -c:a copy \
  output_vtb.mp4

# VideoToolbox HEVC 编码（macOS 10.13+）
ffmpeg -i input.mp4 \

  -tag:v hvc1 \
  -c:a copy \
  output_hevc_vtb.mp4

# 使用硬件编码的实时质量预设
ffmpeg -i input.mp4 \
  -c:v h264_videotoolbox \
  -realtime true \
  -b:v 2500k \
  -c:a aac -b:a 128k \
  -f flv rtmp://server/live/stream
```

## 23.6 硬件编码性能对比

在决定用哪种编码方案之前，先看看性能数据。以下是在 RTX 3080 / i7-12700K 平台上的实测数据（1080p 视频，目标码率 5Mbps）：

**编码速度对比（fps）：**

| 编码器 | Preset | 编码速度 (fps) | CPU 占用 | GPU 占用 |
| -------- | -------- | --------------- | ---------- | ---------- |
| libx264 | medium | 45 fps | 95% | 0% |
| libx264 | veryfast | 120 fps | 80% | 0% |
| h264_nvenc | p4 | 280 fps | 5% | 35% |
| h264_nvenc | p1 | 500+ fps | 3% | 20% |
| h264_qsv | veryfast | 200 fps | 10% | 30%（iGPU） |
| h264_amf | balanced | 180 fps | 8% | 40% |

**编码质量对比（VMAF 分数）：**

| 编码器 | Preset | VMAF @ 2Mbps | VMAF @ 5Mbps | VMAF @ 8Mbps |
| -------- | -------- | ------------- | ------------- | ------------- |
| libx264 | medium | 82.3 | 92.1 | 95.6 |
| libx264 | veryfast | 78.5 | 89.2 | 93.8 |
| h264_nvenc | p5 | 80.1 | 91.3 | 95.1 |
| h264_nvenc | p4 | 77.8 | 88.9 | 93.2 |
| h264_nvenc | p1 | 72.4 | 84.5 | 90.1 |
| h264_qsv | slow | 76.2 | 87.5 | 92.0 |
| h264_qsv | veryfast | 71.8 | 83.1 | 88.9 |
| h264_amf | quality | 75.0 | 86.2 | 91.5 |

**关键发现：**

1. NVENC p5 的质量已经非常接近 libx264 medium，差距只有 1-2 分 VMAF
2. NVENC 的速度是 CPU 编码的 6-10 倍
3. QSV 在 Intel 平台上性价比最高（不用额外买显卡）
4. AMF 质量稍逊于 NVENC，但差距在可接受范围内

## 23.7 硬件编码选型指南

根据使用场景，推荐以下编码方案：

```
场景一：直播推流
├── 首选：NVENC（p1-p2，tune=ll）
├── 备选：QSV（veryfast）
└── 理由：低延迟 > 极致质量

场景二：离线批量转码
├── 追求质量：libx264（medium/slow，CRF模式）
├── 追求速度：NVENC（p5-p6，tune=hq）
└── 平衡方案：NVENC（p4，CQ模式）

场景三：实时转码（如视频会议后端）
├── 首选：NVENC（p1-p3，tune=ull）
├── 备选：QSV（veryfast）
└── 理由：CPU 留给其他业务逻辑

场景四：低成本个人项目
├── 首选：QSV（如果 Intel CPU）
├── 备选：VideoToolbox（如果 Mac）
└── 理由：免费且足够用
```

**什么时候不该用硬件编码？**

虽然硬件编码速度快，但它并不适合所有场景：

1. **存档级转码**：如果你要把珍贵的家庭录像转为最高质量存档，用 libx264 `-preset slow -crf 18`。虽然慢，但质量最好。这种视频你可能只转一次，值得花时间等。

2. **小文件处理**：处理 10 秒的短视频，硬件编码和 CPU 编码的差距可以忽略不计。硬件编码器的初始化开销在小文件上反而可能是负担。

3. **需要精确质量控制的场景**：libx264 的 CRF 模式比 NVENC 的 CQ 模式有更精细的质量控制。如果你对 VMAF 分数有严格要求（比如要求大于 95 分），CPU 编码更可靠。

4. **没有 GPU 的环境**：云服务器（尤其是通用型实例）通常没有 GPU。这种情况下 QSV 是唯一选择（如果有 Intel CPU），否则只能用 CPU 编码。

5. **编码后的后处理**：如果你需要在编码后做像素级的质量分析（如 VMAF 计算），CPU 编码的中间数据格式更容易处理。

**硬件编码的质量陷阱：**

使用硬件编码时需要注意的质量问题：

- **暗场噪点**：NVENC 在暗场景中可能产生明显的噪点。解决方案：适当提高码率或使用 `-spatial-aq 1`
- **色彩带（Banding）**：低码率下渐变色彩可能出现色带。解决方案：使用 10-bit 编码（如果编码器支持）或增加码率
- **运动模糊**：快速运动场景中，硬件编码的参考帧管理不如软件编码精细。解决方案：增加码率或使用 `-rc-lookahead`
- **首次编码延迟**：硬件编码器在开始编码前需要几秒钟的初始化时间。对于非常短的视频，这个延迟可能是显著的

## 23.8 硬件解码

不仅编码可以用硬件加速，解码也可以：

```bash
# NVIDIA 硬件解码
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -i input.mp4 \
  -c:v h264_nvenc -b:v 3M \
  output.mp4

# Intel QSV 硬件解码
ffmpeg -hwaccel qsv \
  -i input.mp4 \
  -c:v h264_qsv -b:v 3M \
  output.mp4

# 硬件解码 + 硬件编码（全程 GPU，CPU 几乎零负载）
ffmpeg -hwaccel cuda -hwaccel_output_format cuda \
  -i input.mp4 \
  -c:v h264_nvenc -b:v 3M \
  -c:a copy \
  output.mp4

# macOS 硬件解码
ffmpeg -hwaccel videotoolbox \
  -i input.mp4 \
  -c:v h264_videotoolbox -b:v 3M \
  output.mp4
```

> **注意**：硬件解码后再用滤镜处理时，数据需要在 GPU 和 CPU 之间传输（称为"回读"），可能会抵消硬件加速的优势。如果不需要滤镜处理，全程硬件加速效果最好。

## 23.9 多线程与性能优化

```bash
# 多线程编码
ffmpeg -i input.mp4 \
  -c:v libx264 \
  -threads 0 \
  -b:v 5M \
  output.mp4
```

`-threads 0` 让 FFmpeg 自动决定线程数（通常等于 CPU 核心数）。

> **注意**：`-threads` 只影响 CPU 编码（libx264/libx265）。硬件编码器（NVENC/QSV/AMF）不消耗 CPU 线程，所以这个参数对它们无效。

**libx265 的多线程优化：**

```bash
# x265 的多线程参数略有不同
ffmpeg -i input.mp4 \
  -c:v libx265 \
  -x265-params "frame-threads=3:pools=8" \
  -preset medium -crf 28 \
  output.mp4
```

**slice 并行编码：**

```bash
# 把每一帧分成多个 slice，每个 slice 独立编码（提高并行度）
ffmpeg -i input.mp4 \
  -c:v libx264 \
  -x264-params "slices=4:slice-max-size=2000" \
  -threads 0 \
  -preset medium -crf 23 \
  output.mp4
```

> **警告**：增加 slices 会降低压缩效率（因为每个 slice 独立编码，无法跨 slice 共享参考帧）。只在 CPU 是瓶颈时才使用。

**并行处理多个文件：**

```bash
#!/bin/bash
# parallel_encode.sh - 并行批量编码

INPUT_DIR="/data/input"
OUTPUT_DIR="/data/output"
MAX_JOBS=4  # 最大并行任务数

job_count=0

for file in "$INPUT_DIR"/*.mp4; do
    filename=$(basename "$file" .mp4)
    output="$OUTPUT_DIR/${filename}_encoded.mp4"

    # 后台启动编码任务
    ffmpeg -y -i "$file" \
        -c:v libx264 -preset medium -crf 23 \
        -c:a aac -b:a 128k \
        "$output" &

    job_count=$((job_count + 1))

    # 控制并行数
    if [ $job_count -ge $MAX_JOBS ]; then
        wait -n  # 等待任意一个任务完成
        job_count=$((job_count - 1))
    fi
done

wait
echo "全部编码完成！"
```

## 23.10 大规模批处理策略

当你需要处理成百上千个视频时：

```bash
# 使用 xargs 实现并行处理
find /data/input -name "*.mp4" | \
  xargs -P 8 -I {} bash -c '
    input="{}"
    output="/data/output/$(basename "$input" .mp4)_h265.mp4"
    ffmpeg -y -i "$input" \
      -c:v libx265 -preset fast -crf 28 \
      -c:a aac -b:a 96k \
      "$output"
  '
```

**使用 FFmpeg 的 -segment 进行批量切片：**

```bash
# 把大量视频统一切为 HLS
for file in /data/input/*.mp4; do
    name=$(basename "$file" .mp4)
    mkdir -p "/data/hls/$name"
    ffmpeg -y -i "$file" \
        -c:v libx264 -c:a aac \
        -hls_time 10 \
        -hls_list_size 0 \
        -hls_segment_filename "/data/hls/$name/seg%03d.ts" \
        "/data/hls/$name/index.m3u8" &
done
wait
echo "批量 HLS 切片完成"
```

## 23.11 内存与 CPU 优化

大规模处理视频时，内存和 CPU 的优化同样重要：

**内存优化策略：**

```bash
# 限制 FFmpeg 的最大内存使用（通过 ulimit）
ulimit -v 4194304  # 限制为 4GB 虚拟内存

# 使用 -max_muxing_queue_size 避免 muxer 缓冲区溢出
ffmpeg -i input.mp4 \
  -c:v libx264 -c:a aac \
  -max_muxing_queue_size 1024 \
  output.mp4

# 减小解码缓冲区（适用于内存受限环境）
ffmpeg -threads 2 \
  -i input.mp4 \
  -c:v libx264 -preset fast \
  -thread_queue_size 512 \
  output.mp4
```

**CPU 调度优化：**

```bash
# 使用 taskset 绑定 CPU 核心（避免进程在不同核心间迁移）
taskset -c 0,1,2,3 ffmpeg -i input.mp4 -c:v libx264 output.mp4

# 设置进程优先级（在系统负载高时保证编码进程有足够的 CPU 时间）
nice -n 10 ffmpeg -i input.mp4 -c:v libx264 output.mp4

# 使用 cgroups 限制资源（Linux 生产环境推荐）
cgcreate -g cpu,memory:/ffmpeg
cgset -r cpu.cfs_quota_us=400000 /ffmpeg  # 限制为 4 核
cgset -r memory.limit_in_bytes=8G /ffmpeg  # 限制 8GB 内存
cgexec -g cpu,memory:/ffmpeg ffmpeg -i input.mp4 -c:v libx264 output.mp4
```

**磁盘 I/O 优化：**

```bash
# 使用 tmpfs（内存文件系统）加速中间文件的读写
mount -t tmpfs -o size=4G tmpfs /tmp/ffmpeg

# 输出到内存盘，完成后再移到实际位置
ffmpeg -i input.mp4 -c:v libx264 -crf 23 /tmp/ffmpeg/output.mp4
mv /tmp/ffmpeg/output.mp4 /data/final/

# 使用管道避免中间文件（减少磁盘 I/O）
ffmpeg -i input.mp4 -c:v libx264 -f matroska - | \
  ffmpeg -i pipe:0 -c:v copy -f mp4 output.mp4
```

**生产环境的 FFmpeg 服务化：**

在真实的生产环境中，FFmpeg 通常被封装为一个微服务，通过消息队列来调度任务：

```
用户上传视频 → API 服务 → 消息队列（RabbitMQ/Redis）→ Worker 集群
                                                        │
                                                        ├── Worker 1: FFmpeg 转码
                                                        ├── Worker 2: FFmpeg 转码
                                                        └── Worker 3: FFmpeg 转码
                                                        │
                                                        ▼
                                                   对象存储（S3/OSS）→ CDN
```

每个 Worker 进程从队列中取出任务，用 FFmpeg 处理后上传结果。这样可以：

- 水平扩展（加机器就能提高吞吐量）
- 任务重试（失败的任务自动重试）
- 优先级控制（VIP 用户的视频优先处理）
- 资源隔离（每个 Worker 只占用一份 CPU/内存）

## 23.12 编码质量的客观评估

肉眼评价画质太主观了。专业的做法是用**客观指标**来衡量：

**PSNR（峰值信噪比）：**

```bash
# 计算 PSNR（对比原始视频和编码后视频）
ffmpeg -i encoded.mp4 -i original.mp4 \
  -lavfi psnr \
  -f null -

# 输出示例：
# [Parsed_psnr_0 @ 0x...] PSNR y:42.15 u:47.23 v:48.01 average:43.52
# → 值越大越好，>40dB 通常认为质量优秀
```

**SSIM（结构相似度）：**

```bash
ffmpeg -i encoded.mp4 -i original.mp4 \
  -lavfi ssim \
  -f null -

# 输出示例：
# [Parsed_ssim_0 @ 0x...] SSIM Y:0.9912 U:0.9956 V:0.9967 All:0.9936
# → 范围 0-1，越接近 1 越好，>0.95 通常认为质量优秀
```

**VMAF（视频多方法评估融合，Netflix 出品）：**

```bash
# VMAF 需要编译时加入 libvmaf 支持
ffmpeg -i encoded.mp4 -i original.mp4 \
  -lavfi libvmaf=model_path=/usr/share/model/vmaf_v0.6.1.json \
  -f null -

# 输出示例：
# [Parsed_libvmaf_0 @ 0x...] VMAF score: 92.34
# → 范围 0-100，越高越好
# → Netflix 认为 95+ 是"肉眼无法分辨差异"
# → 75+ 是可接受质量
```

**质量评估对比参考：**

| 场景 | PSNR | SSIM | VMAF |
| ------ | ------ | ------ | ------ |
| 肉眼无法分辨 | >45dB | >0.99 | >95 |
| 高质量 | 40-45dB | 0.97-0.99 | 85-95 |
| 可接受 | 35-40dB | 0.93-0.97 | 70-85 |
| 明显劣化 | <35dB | <0.93 | <70 |

## 本章小结

- **NVENC** 是目前最强的 GPU 编码方案（如果你有 NVIDIA 显卡），速度是 CPU 编码的 6-10 倍
- **QSV** 是 Intel CPU 用户的免费福利，不需要额外买显卡
- **AMF** 和 **VideoToolbox** 分别服务 AMD 和 Apple 用户
- 硬件编码速度快但质量略逊于 CPU 编码（差距在不断缩小，NVENC p5 已经非常接近 libx264）
- 直播场景优先用硬件编码（低延迟、低 CPU 占用、可以留出 CPU 给其他业务）
- 离线转码追求极致质量可以用 CPU 编码（libx264 slow preset + CRF 模式）
- **VMAF** 是目前最权威的视频质量评估指标，Netflix 出品，范围 0-100
- 硬件编码不适合所有场景：存档级转码、小文件、精确质量控制时仍应使用 CPU 编码
- 生产环境中，编码服务通常被封装为微服务，通过消息队列调度任务

**关键决策点速记：**

```
速度优先 → NVENC p1-p3
质量优先 → libx264 slow/medium + CRF
平衡方案 → NVENC p4-p5 + CQ 模式
免费方案 → QSV（Intel）或 VideoToolbox（Mac）
```
