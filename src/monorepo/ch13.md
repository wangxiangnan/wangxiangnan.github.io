# Ch13：版本管理与发布

## 本章目标

- 理解 monorepo 中两种版本管理策略的优劣
- 掌握 Changesets 工具的安装、配置和使用
- 学会创建 changeset 并理解版本类型选择
- 实现自动 Changelog 生成
- 掌握完整的版本发布流程
- 在 CI 中实现自动化发布

## 13.1 Monorepo 版本管理策略

在 monorepo 中管理版本比单包项目复杂得多，因为有多个包需要协调版本。业界主要有两种策略：

### 策略一：固定版本（Lockstep / Fixed Version）

所有包共享同一个版本号。每次发布时，所有包同时升级版本。

```
packages/shared:   v2.3.0
packages/ui:       v2.3.0
packages/database: v2.3.0
apps/web:          v2.3.0
apps/api:          v2.3.0
```

**优点**：

- 简单，版本对应关系清晰
- 不需要担心跨包版本兼容性问题

**缺点**：

- 一个包的微小改动会导致所有包升级版本
- 对于发布到 npm 的公共包来说，频繁的不必要版本升级会困扰用户

**代表项目**：Angular、Babel

### 策略二：独立版本（Independent Version）

每个包维护自己的版本号，按需升级。

```txt
packages/shared:   v1.2.0
packages/ui:       v2.0.1
packages/database: v0.5.3
apps/web:          v3.1.0
apps/api:          v1.0.0
```

**优点**：

- 每个包的版本号有意义，反映其自身的变更
- 用户可以只升级需要的包

**缺点**：

- 需要处理包之间的版本依赖关系
- 管理更复杂

**代表项目**：Vue、Vite

### 我们的选择

对于 **内部应用**（`apps/web`、`apps/api`），通常使用固定版本或根本不发布到 npm，所以版本管理不太重要。

对于 **共享包**（`packages/shared`、`packages/ui`、`packages/database`），如果要发布到 npm，建议使用**独立版本**。

**Changesets** 工具天然支持独立版本模式，同时也支持固定版本，是我们推荐的版本管理工具。

## 13.2 Changesets 的安装与配置

```bash
# 安装 Changesets CLI
pnpm add -Dw @changesets/cli

# 初始化配置
pnpm changeset init
```

初始化后会在项目根目录生成 `.changeset/` 目录和 `config.json`：

**.changeset/config.json**：

```json
{
  "$schema": "https://unpkg.com/@changesets/config@3.0.0/schema.json",
  "changelog": [
    "@changesets/changelog-github",
    { "repo": "your-github-username/your-repo" }
  ],
  "commit": false,
  "fixed": [],
  "linked": [],
  "access": "restricted",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": ["@monorepo/web", "@monorepo/api", "@monorepo/e2e"]
}
```

让我们逐项理解这些配置：

### `changelog`

```json
"changelog": [
  "@changesets/changelog-github",
  { "repo": "your-github-username/your-repo" }
]
```

使用 GitHub 风格的 changelog 生成器，它会在 changelog 中包含 PR 链接和贡献者信息。如果不使用 GitHub，可以用 `@changesets/cli/changelog`。

### `commit`

```json
"commit": false
```

设为 `false` 表示 Changesets 不会自动创建 git commit。推荐这样做，因为你可能想在发布前做额外检查。设为 `true` 时，每次 `changeset version` 都会自动提交。

### `fixed` 和 `linked`

```json
"fixed": [],
"linked": []
```

- **`fixed`**：数组中的包共享同一个版本号。例如 `[["@monorepo/shared", "@monorepo/ui"]]` 表示这两个包总是同版本。
- **`linked`**：类似 `fixed`，但当其中一个包升级时，其他关联包至少升级 patch 版本。

对于大多数项目，保持为空（独立版本）就好。

### `access`

```json
"access": "restricted"
```

- **`restricted`**（默认）：发布的包是私有的（scoped 包默认行为）
- **`public`**：发布的包是公开的

如果你的包是 scoped 的（如 `@monorepo/shared`），npm 默认将其设为私有。如果要公开发布，需要改为 `public`。

### `baseBranch`

```json
"baseBranch": "main"
```

Changesets 会基于这个分支来判断哪些 changeset 需要被消费。通常是 `main` 或 `master`。

### `updateInternalDependencies`

```json
"updateInternalDependencies": "patch"
```

当上游包升级时，依赖它的包如何升级。设为 `patch` 意味着如果 `shared` 从 `1.0.0` 升到 `1.1.0`，依赖 `shared` 的 `ui` 至少会升级 patch 版本（如 `1.0.0` → `1.0.1`）。

### `ignore`

```json
"ignore": ["@monorepo/web", "@monorepo/api", "@monorepo/e2e"]
```

**为什么忽略 apps？** 应用通常不发布到 npm，不需要版本管理。它们通过 Git tag 或 Docker image tag 来追踪版本。

## 13.3 创建 Changeset：记录变更

每次你做了一个值得发布版本的改动，都应该创建一个 changeset。

```bash
# 创建一个新的 changeset
pnpm changeset
```

CLI 会交互式地询问：

```
🦋 Which packages would you like to include?
  ◯ changed packages
    ◯ @monorepo/shared
    ◯ @monorepo/ui
    ◯ @monorepo/database

🦋 Which packages should have a major bump?
  ◯ all packages
    ◯ @monorepo/shared

🦋 Which packages should have a minor bump?
  ◯ all packages
    ◯ @monorepo/ui

🦋 Please enter a summary for this change.
  › Add retry utility function to shared package

🦋 Is this your desired changeset? (Y/n) › Y
```

这会在 `.changeset/` 目录下生成一个 markdown 文件：

**.changeset/add-retry-util.md**：

```markdown
---
"@monorepo/shared": major
"@monorepo/ui": minor
---

Add retry utility function to shared package

The new `retry` function allows automatic retrying of async operations
with configurable max attempts and delay. Updated ui components to use
the new retry utility for API calls.
```

> **为什么要手动创建 changeset 而不是自动生成？** 因为开发者最清楚自己的改动是 `patch`（bug 修复）、`minor`（新功能）还是 `major`（破坏性变更）。自动化工具无法判断一个改动的语义影响。

### 版本类型说明

| 类型 | 语义 | 版本变化示例 | 何时使用 |
| ------ | ------ | ------------- | --------- |
| `patch` | 补丁 | 1.0.0 → 1.0.1 | Bug 修复、文档修正、内部重构 |
| `minor` | 次版本 | 1.0.0 → 1.1.0 | 新增功能（向后兼容） |
| `major` | 主版本 | 1.0.0 → 2.0.0 | 破坏性变更（删除 API、改变行为） |

### 在 CI 中检查 changeset

为了防止开发者忘记创建 changeset，可以在 CI 中添加检查：

```yaml
# .github/workflows/changeset-check.yml
name: Changeset Check

on:
  pull_request:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - name: Check for changesets
        run: |
          # 检查 PR 中是否包含 changeset 文件
          pnpm changeset status --since=origin/main
```

> **为什么这个检查很重要？** 忘记创建 changeset 是最常见的发布事故原因之一。没有 changeset，`changeset version` 不会升级任何版本，导致你的改动在发布后被"遗漏"。

## 13.4 自动生成 Changelog

当你运行 `changeset version` 时，Changesets 会：

1. 消费所有 `.changeset/*.md` 文件
2. 根据声明的版本类型升级各包的版本号
3. 更新包之间的内部依赖版本
4. 在每个包的根目录生成或更新 `CHANGELOG.md`

**生成的 CHANGELOG.md 示例**：

```markdown
# @monorepo/shared

## 1.1.0

# Minor Changes

- abc1234: Add retry utility function to shared package

# Patch Changes

- def5678: Fix formatPrice rounding issue
- Updated dependencies [tsconfig@0.2.0]
```

**在 `package.json` 中配置 changelog 的 repository 字段**（让 changelog 包含 PR 链接）：

```json
{
  "name": "@monorepo/shared",
  "repository": {
    "type": "git",
    "url": "https://github.com/your-username/your-repo",
    "directory": "packages/shared"
  }
}
```

## 13.5 版本发布流程

完整的发布流程如下：

### 步骤一：日常开发中创建 changesets

```bash
# 每次做完一个功能/修复后
pnpm changeset
# 按照提示选择包和版本类型，输入变更描述
```

这些 changeset 文件会和代码一起提交到 Git。

### 步骤二：准备发布时，执行版本升级

```bash
# 在 main 分支上执行
git checkout main
git pull origin main

# 消费所有 changesets，升级版本号
pnpm changeset version
```

这个命令会：

- 删除 `.changeset/` 中的 changeset 文件（已被消费）
- 更新各包的 `package.json` 中的 `version` 字段
- 更新依赖该包的其他包的依赖版本
- 生成/更新 `CHANGELOG.md`

### 步骤三：检查并提交版本变更

```bash
# 查看变更
git diff

# 确认无误后提交
git add -A
git commit -m "chore: release new versions"
```

### 步骤四：发布到 npm

```bash
# 发布所有需要发布的包
pnpm changeset publish
```

这个命令会：

- 构建所有包（如果配置了 `prepublishOnly`）
- 将版本高于 npm 上当前版本的包发布到 npm registry
- 为每个发布的包创建 Git tag

### 步骤五：推送变更和 tags

```bash
git push origin main
git push origin --tags
```

## 13.6 完整的发布脚本

为了方便使用，可以在根 `package.json` 中添加发布相关的 scripts：

```json
{
  "scripts": {
    "changeset": "changeset",
    "version": "changeset version",
    "publish": "turbo run build && changeset publish",
    "release": "pnpm version && pnpm publish && git push --follow-tags"
  }
}
```

> **为什么在 publish 前运行 `turbo run build`？** 确保发布的包是最新构建的产物。Turborepo 的缓存机制确保只有需要重新构建的包才会构建，不会浪费太多时间。

## 13.7 私有包 vs 公开包的发布配置

### 私有包（Private Packages）

如果你不想让包公开发布到 npm，在包的 `package.json` 中设置：

```json
{
  "name": "@monorepo/shared",
  "private": true
}
```

或者在 `.changeset/config.json` 中设置 `access: "restricted"`。

> **`private: true` 和 `access: "restricted"` 的区别**：`private: true` 会完全阻止发布到 npm（`npm publish` 会报错），适合内部使用的包。`access: "restricted"` 允许发布但设为私有（只有付费 npm 组织才支持私有包）。

### 公开包（Public Packages）

如果要发布公开包：

```json
{
  "name": "@monorepo/shared",
  "access": "public"
}
```

并在 `.changeset/config.json` 中：

```json
{
  "access": "public"
}
```

### 发布到私有 Registry

如果你的团队使用私有 npm registry（如 Verdaccio、Artifactory），在 `.npmrc` 中配置：

```ini
# 根目录 .npmrc
@monorepo:registry=https://your-registry.com/
//your-registry.com/:_authToken=${NPM_TOKEN}
```

## 13.8 在 CI 中自动化发布（GitHub Actions）

以下是一个完整的 GitHub Actions 发布工作流：

**.github/workflows/release.yml**：

```yaml
name: Release

on:
  push:
    branches:
      - main

concurrency: ${{ github.workflow }}-${{ github.ref }}

jobs:
  release:
    name: Release
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup pnpm
        uses: pnpm/action-setup@v4
        with:
          version: 9

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'pnpm'
          registry-url: 'https://registry.npmjs.org'

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Build
        run: pnpm turbo run build

      - name: Run tests
        run: pnpm turbo run test

      - name: Type check
        run: pnpm turbo run typecheck

      - name: Create Release Pull Request or Publish
        id: changesets
        uses: changesets/action@v1
        with:
          # 当有未消费的 changesets 时，创建 Release PR
          # 当 Release PR 被合并时，自动发布到 npm
          publish: pnpm changeset publish
          version: pnpm changeset version
          commit: 'chore: version packages'
          title: 'chore: version packages'
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**这个工作流的工作原理**：

1. **当 main 分支有新的 push 时触发**
2. **构建、测试、类型检查**：确保代码质量
3. **`changesets/action`**：
   - 如果存在未消费的 changesets，创建一个 "Version Packages" 的 PR
   - 这个 PR 包含版本号升级和 CHANGELOG 更新
   - 当这个 PR 被 review 并合并后，工作流再次触发，这次执行 `publish`，将包发布到 npm

> **为什么通过 PR 来发布？** 这给了团队一个 review 的机会——你可以在合并前检查版本号是否正确、CHANGELOG 是否合理。这比直接在 push 时发布更安全。

### 使用 GitHub Release

如果还想在发布时自动创建 GitHub Release：

```yaml
- name: Create GitHub Release
  if: steps.changesets.outputs.published == 'true'
  uses: softprops/action-gh-release@v2
  with:
    tag_name: ${{ steps.changesets.outputs.publishedPackages[0].name }}@${{ steps.changesets.outputs.publishedPackages[0].version }}
    generate_release_notes: true
```

## 13.9 发布前的构建与测试流程编排

在发布之前，我们需要确保整个 monorepo 处于可发布状态。使用 Turborepo 编排这个流程：

**turbo.json 中添加发布相关任务**：

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json", "package.json"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "inputs": ["src/**", "tests/**", "*.test.*", "*.spec.*"]
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json"]
    },
    "lint": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", ".eslintrc.*"]
    }
  }
}
```

**根 package.json 的发布流程脚本**：

```json
{
  "scripts": {
    "prepublish": "turbo run build lint test typecheck",
    "publish-packages": "pnpm prepublish && pnpm changeset publish",
    "canary": "changeset publish --tag canary"
  }
}
```

### Canary 发布

对于想提前测试的版本，可以使用 canary 发布：

```bash
# 创建一个 canary 版本（不影响正式版本号）
pnpm changeset pre enter alpha

# 发布为 canary 版本（如 1.1.0-alpha.0）
pnpm changeset publish --tag alpha

# 退出 pre-release 模式
pnpm changeset pre exit
```

## 13.10 包的发布配置清单

在发布一个包之前，确保 `package.json` 中有以下字段：

```json
{
  "name": "@monorepo/shared",
  "version": "1.1.0",
  "description": "Shared utilities for the monorepo",
  "main": "./dist/index.js",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.js",
      "types": "./dist/index.d.ts"
    }
  },
  "files": [
    "dist"
  ],
  "sideEffects": false,
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "https://github.com/your-username/your-repo",
    "directory": "packages/shared"
  },
  "keywords": ["utilities", "shared"],
  "publishConfig": {
    "access": "public"
  }
}
```

关键字段说明：

| 字段 | 作用 | 是否必需 |
| ------ | ------ | --------- |
| `main` | CommonJS 入口 | 是 |
| `module` | ESM 入口 | 推荐 |
| `types` | TypeScript 类型声明入口 | 是 |
| `exports` | 现代条件导出 | 推荐 |
| `files` | 指定发布到 npm 的文件 | 推荐（减小包体积） |
| `sideEffects` | 标记是否有副作用（帮助 tree-shaking） | 推荐 |
| `publishConfig` | 发布时的配置覆盖 | 按需 |

> **为什么 `files` 字段很重要？** 如果不指定 `files`，npm 会发布整个包目录（包括 `src/`、`tests/`、配置文件等）。指定 `files: ["dist"]` 确保只发布构建产物，大幅减小发布的包大小。

## 本章小结

1. **版本策略**：独立版本适合大多数 monorepo，Changesets 天然支持
2. **Changesets 工作流**：`changeset`（创建变更记录）→ `changeset version`（升级版本号）→ `changeset publish`（发布到 npm）
3. **Changelog**：Changesets 自动生成，包含变更描述和 PR 链接
4. **CI 自动化**：通过 GitHub Actions + `changesets/action` 实现自动化版本管理和发布
5. **发布前检查**：使用 Turborepo 编排 build → lint → test → typecheck 的完整流程
6. **包配置**：确保 `exports`、`files`、`publishConfig` 等字段正确配置
