# 第5章：事件触发器深度解析——"什么时候开火？"

## 引言

如果 workflow 是一门大炮，那事件触发器（event trigger）就是它的**扳机**。大炮造得再精良，扳机设计不合理，要么该开火时哑弹，要么不该开火时走火——两者同样致命。

在第一章中你已经知道，每个 workflow 的 `on` 字段定义了"什么事件会触发这条流水线"。但"push 就触发"只是冰山一角。GitHub 支持 **30 多种事件类型**，每种事件还有各自的过滤条件和子类型。本章，我们将深入剖析最常用、最实用的触发器，帮你把流水线的"扳机"设计得精准可靠。

---

## 5.1 push vs pull_request：两大核心触发器

这两个是 GitHub Actions 的"面包和黄油"，90% 的 workflow 都会用到它们。但它们的行为差异巨大，搞混是常见的新手坑。

### push 触发器

`push` 事件在**代码被推送到指定分支**时触发。它的特点是：

- 运行在**推送目标分支**的上下文中（不是源分支）
- 可以访问仓库的 secrets
- 对目标分支有写入权限

```yaml
# 推送代码到 main 或 develop 时触发
on:
  push:
    branches: [main, develop]
```

**生活类比**：`push` 就像你直接把行李托运到了目的地——行李（代码）已经正式到达了那个分支（机场），航空公司（GitHub Actions）可以直接在目的地帮你处理一切。

### pull_request 触发器

`pull_request` 事件在 PR 被**创建、更新、重新打开或同步**时触发。它的行为有本质区别：

- 运行在 **PR 源分支和目标分支的合并点**上（不是源分支本身）
- 来自 fork 的 PR **无法访问目标仓库的 secrets**（安全限制）
- 默认只有**只读权限**

```yaml
# PR 指向 main 分支时触发
on:
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]  # 默认就是这几个
```

**生活类比**：`pull_request` 就像你提交了一份租房申请——房东（GitHub）会先审查你的资质（代码质量），但不会把钥匙（secrets）给你，直到你真正签约（merge）为止。

### 最佳实践：组合使用

在真实项目中，通常两者配合使用：

```yaml
name: CI Pipeline

on:
  push:
    branches: [main]           # merge 到 main 时，跑完整测试 + 部署
  pull_request:
    branches: [main, develop]  # PR 阶段，只跑 lint + 测试

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

  deploy:
    if: github.event_name == 'push'  # 只在 push 时部署，PR 时跳过
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying to production..."
```

这里有个精妙的设计：`test` job 在两种事件下都会跑，但 `deploy` job 只在 `push`（即代码真正 merge 进 main）时才执行。这就像一个两阶段审批——先考试（测试），考过了再决定要不要发毕业证（部署）。

## 5.2 分支过滤（branches）与路径过滤（paths）

触发器不加过滤条件，就像设了一个"来者不拒"的门卫——所有客人都得登记，哪怕只是路过送外卖的。

### 分支过滤

```yaml
on:
  push:
    branches:
      - main
      - 'releases/**'     # 匹配 releases/v1.0、releases/2024-holiday 等
      - '!releases/old-*' # 排除 releases/old-xxx 分支
```

注意用**单引号**包裹含通配符的分支名，否则 YAML 解析器会把它当成别的东西。`!` 前缀表示排除——就像"欢迎所有 VIP 客户，但不包括被拉黑的那位"。

### 路径过滤

有时候你修改了 README 或文档，根本不需要跑完整的测试套件。`paths` 过滤可以帮你省下这些宝贵的 CI 分钟（以及真金白银）：

```yaml
on:
  pull_request:
    paths:
      - 'src/**'                    # src 目录下任何文件变动
      - 'tests/**'                  # tests 目录下任何文件变动
      - 'package.json'              # 依赖变动
      - '!src/docs/**'              # 文档变动不触发
      - '!**/*.md'                  # 任何 markdown 文件变动不触发

  push:
    paths-ignore:                   # 更简洁的写法：忽略某些路径
      - '**/*.md'
      - 'docs/**'
```

**编程隐喻**：`paths` 过滤就像 Git 的 `.gitignore`，只不过它过滤的不是"要不要跟踪这个文件"，而是"这个文件的变动要不要触发流水线"。

### paths 和 branches 的 AND 逻辑

当你同时配置了 `branches` 和 `paths` 时，它们是 **AND 关系**——必须同时满足两个条件才会触发：

```yaml
on:
  push:
    branches: [main]
    paths: ['src/**']
# 只有推送到 main 分支 且 src/ 下有文件变动时，才会触发
```

## 5.3 workflow_dispatch：手动触发

有些流水线不需要"自动化触发"，而是"我来决定什么时候跑"。比如：

- 手动执行数据库迁移
- 按需生成测试报告
- 触发一次完整的回归测试

`workflow_dispatch` 就是为此而生的：

```yaml
name: Manual Deploy

on:
  workflow_dispatch:
    inputs:
      environment:
        description: '部署目标环境'
        required: true
        type: choice
        options:
          - staging
          - production
        default: 'staging'
      debug_enabled:
        description: '是否开启调试日志'
        required: false
        type: boolean
        default: false
      version:
        description: '部署版本号'
        required: true
        type: string

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: 打印部署参数
        run: |
          echo "目标环境: ${{ inputs.environment }}"
          echo "版本号: ${{ inputs.version }}"
          echo "调试模式: ${{ inputs.debug_enabled }}"

      - name: 执行部署
        run: |
          echo "正在部署 v${{ inputs.version }} 到 ${{ inputs.environment }}..."
```

这个配置的厉害之处在于：在 GitHub 的 Web UI 上，你会看到一个 **"Run workflow"** 按钮，点击后会弹出一个表单，让你填写 `environment`、`debug_enabled` 和 `version`。这就把 GitHub Actions 变成了一个轻量级的运维控制台——不用写专门的后台管理工具，CI/CD 平台本身就是你的控制面板。

## 5.4 schedule：定时触发（cron 表达式）

有些任务天生就是"到点干活"的：每天凌晨跑数据报表、每周一生成周报、每小时检查服务健康状态。

```yaml
on:
  schedule:
    # 每天 UTC 时间凌晨 2:30 执行
    - cron: '30 2 * * *'
    # 每周一 UTC 时间 9:00 执行
    - cron: '0 9 * * 1'
```

**Cron 表达式速记法**（五字段格式）：

```
┌────────── 分钟 (0-59)
│ ┌──────── 小时 (0-23)
│ │ ┌────── 日期 (1-31)
│ │ │ ┌──── 月份 (1-12)
│ │ │ │ ┌── 星期几 (0-6, 0=周日)
│ │ │ │ │
* * * * *
```

常用特殊符号：

- `*` —— 每个值（every）
- `*/5` —— 每隔5个单位
- `1,15` —— 第1和第15
- `1-5` —— 从1到5
- `15/30` —— 从15开始，每隔30个单位

**重要注意事项**：

1. GitHub Actions 的 cron 使用 **UTC 时区**，不是你的本地时区。北京时间 UTC+8 凌晨 2:30 = UTC 18:30（前一天），所以你得写好 `cron: '30 18 * * *'`。
2. 默认分支是**仓库的默认分支**（通常是 `main`），不是触发时的最新分支。
3. GitHub 可能会在高负载时**延迟定时任务**（最多延迟几分钟到几小时），所以不要依赖秒级精度。如果你的定时任务对时效性要求极高（比如"必须在 9:00 整准时发邮件"），考虑用外部调度器（如 AWS EventBridge）配合 `repository_dispatch`。

```yaml
name: Nightly Report

on:
  schedule:
    - cron: '0 18 * * *'  # 北京时间凌晨 2:00

jobs:
  generate-report:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: node scripts/generate-nightly-report.js
```

## 5.5 repository_dispatch：跨仓库触发

`repository_dispatch` 是一个"远程遥控器"——允许你从**外部**（另一个仓库的 workflow、一个 webhook、甚至你自己的脚本）触发目标仓库的 workflow。

**目标仓库的 workflow：**

```yaml
name: Triggered by External

on:
  repository_dispatch:
    types: [deploy-staging, deploy-production]  # 自定义事件类型

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: 读取外部传来的参数
        run: |
          echo "触发类型: ${{ github.event.action }}"
          echo "自定义数据: ${{ toJson(github.event.client_payload) }}"

      - name: 执行部署
        run: |
          echo "部署版本: ${{ github.event.client_payload.version }}"
```

**触发方（另一个 workflow 或脚本）：**

```yaml
# 从另一个仓库触发
- name: Trigger deploy in target repo
  run: |
    curl -X POST \
      -H "Accept: application/vnd.github+json" \
      -H "Authorization: Bearer ${{ secrets.DEPLOY_TOKEN }}" \
      https://api.github.com/repos/OWNER/TARGET_REPO/dispatches \
      -d '{
        "event_type": "deploy-staging",
        "client_payload": {
          "version": "1.2.3",
          "deployed_by": "ci-bot"
        }
      }'
```

**生活类比**：`repository_dispatch` 就像对讲机——你在 A 地点按下按钮说话（发送触发请求），B 地点的对讲机收到信号后自动执行预定的操作。而 `client_payload` 就是你通过对讲机传递的具体信息。

## 5.6 组合使用多种触发器

真实项目中，一个 workflow 往往需要响应多种事件。GitHub 允许你在一个 `on` 字段中组合多个触发器：

```yaml
name: Comprehensive CI

on:
  push:
    branches: [main]
    paths: ['src/**', 'tests/**']

  pull_request:
    branches: [main, develop]

  workflow_dispatch:
    inputs:
      run_e2e:
        description: '是否运行 E2E 测试'
        type: boolean
        default: false

  schedule:
    - cron: '0 3 * * 1'  # 每周一凌晨 3 点全量回归

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint
      - run: npm test

  e2e:
    # 只在手动触发且勾选了 run_e2e 时执行
    if: github.event_name == 'workflow_dispatch' && inputs.run_e2e == true
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright test
```

在这个配置中，我们用**同一个 workflow 覆盖了四种场景**：日常开发（PR 触发快速检查）、发布（push 触发完整验证）、按需操作（手动触发 E2E）、定期巡检（每周定时回归）。这就是"一鱼四吃"的精髓。

### 关于 workflow_call 的预告

你可能已经注意到，上面的例子虽然能组合触发器，但所有逻辑都写在一个 workflow 文件里，时间长了会变得臃肿。别担心——在第12章（高级篇）中，我们将详细讲解 `workflow_call`，它允许你把 workflow 拆分成可复用的"子模块"，像函数调用一样在多个 workflow 之间共享逻辑。这里先留个悬念。

## 小结

| 触发器 | 触发时机 | 典型用途 |
|--------|---------|---------|
| `push` | 代码推送到分支 | merge 后跑测试、部署 |
| `pull_request` | PR 创建/更新 | PR 阶段代码审查 |
| `workflow_dispatch` | 手动点击 | 按需部署、手动报告 |
| `schedule` | 定时 cron | 定时报告、健康检查 |
| `repository_dispatch` | 外部 API 调用 | 跨仓库触发 |
| `workflow_call` | 被其他 workflow 调用 | 可复用 workflow（第12章详解） |

## 练习题

1. **基础题**：创建一个 workflow，在 `feature/**` 分支上的 push 事件触发，但**只有** `src/components/` 目录下的文件变动时才执行。
2. **进阶题**：设计一个 workflow，支持以下触发方式：PR 到 main 时跑 lint + 单元测试；每周五下午 5 点（北京时间）跑一次完整的集成测试；支持手动触发并选择运行"quick"或"full"测试套件。
3. **思考题**：如果同时配置了 `push` 和 `pull_request` 且都指向 `main`，当你创建一个 PR 并最终 merge 时，workflow 会触发几次？为什么？如何避免重复执行？
