# Ch02: 环境准备与项目初始化

## 本章目标

- 安装并配置 Node.js 版本管理工具
- 安装 pnpm 并通过 corepack 确保版本一致
- 创建 monorepo 根目录并初始化 `pnpm-workspace.yaml`
- 配置根目录 `package.json`、`.gitignore`、`.npmrc` 等基础文件
- 完成一个完整的、可验证的初始化流程

## 2.1 Node.js 版本管理

在 monorepo 中，**所有包共享同一个 Node.js 版本**，因此统一版本至关重要。我们使用 `.nvmrc` 文件来锁定版本，确保团队所有成员和 CI 环境使用相同的 Node.js。

### 安装 nvm（Node Version Manager）

如果你还没安装 nvm，按平台选择安装方式：

**macOS / Linux：**

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
```

安装完成后重启终端，验证安装：

```bash
nvm --version
# 输出类似：0.40.1
```

**Windows：**

Windows 用户推荐使用 [nvm-windows](https://github.com/coreybutler/nvm-windows/releases)，下载安装包后按提示安装。

或者使用更现代的 [fnm](https://github.com/Schniz/fnm)（跨平台，Rust 编写，速度更快）：

```powershell
# Windows (通过 winget)
winget install Schniz.fnm

# 在 PowerShell 配置中添加（用于自动切换版本）
fnm env --use-on-cd | Out-String | Invoke-Expression
```

### 创建 .nvmrc

在项目根目录创建 `.nvmrc` 文件：

```bash
mkdir taskflow && cd taskflow

# 将当前 LTS 版本号写入 .nvmrc
echo "20" > .nvmrc
```

或者更精确地指定版本：

```bash
echo "20.18.1" > .nvmrc
```

> **为什么选择 Node.js 20？** 它是当前 LTS（长期支持）版本，支持到 2026 年 4 月。同时它对 ESM、`fetch` API、`--watch` 模式等现代特性有良好的支持。

使用 `.nvmrc` 后，团队成员只需执行：

```bash
# 进入项目目录后
nvm use
# 输出：Now using node v20.18.1 (npm v10.8.2)
```

如果你用的是 fnm，它甚至会在你 `cd` 进入目录时自动切换版本。

## 2.2 安装 pnpm 与 Corepack

### 为什么选 pnpm

在 Ch01 中已经解释了选择 pnpm 的理由，这里补充一个直观的数据对比：

| 操作 | npm | yarn | pnpm |
| ------ | ----- | ------ | ------ |
| 安装全新依赖 | 基准 | 约 1.2x 更快 | 约 2-3x 更快 |
| 增量安装 | 基准 | 约 1.5x 更快 | 约 3-5x 更快 |
| 磁盘占用（10 个项目共用 react） | 10 份 | 10 份 | 1 份（硬链接） |

在 monorepo 场景下，速度和磁盘的优势会被进一步放大。

### 使用 Corepack 管理 pnpm 版本

**Corepack** 是 Node.js 16.10+ 内置的工具，用于管理包管理器（pnpm、yarn）的版本。它的好处是：团队成员不需要手动安装 pnpm，Corepack 会根据 `package.json` 中的声明自动使用正确的版本。

首先启用 Corepack：

```bash
# 启用 corepack（可能需要管理员权限）
corepack enable

# 验证
corepack --version
```

然后在项目中指定 pnpm 版本。我们会在后面的 `package.json` 中配置。

### 直接安装 pnpm（备选方案）

如果你不想使用 Corepack，也可以直接全局安装：

```bash
npm install -g pnpm

# 验证安装
pnpm --version
# 输出类似：11.21.0
```

## 2.3 初始化 Monorepo 根目录

现在我们开始正式创建项目。以下是一个完整的、可跟做的命令序列。

### 第一步：创建根目录并初始化 package.json

```bash
# 创建项目目录
mkdir taskflow && cd taskflow

# 初始化 package.json
pnpm init
```

这会在当前目录生成一个基础的 `package.json`。我们需要修改它。

### 第二步：编写根目录 package.json

打开 `package.json`，替换为以下内容：

```json
{
  "name": "taskflow",
  "version": "0.0.0",
  "private": true,
  "packageManager": "pnpm@11.21.0",
  "engines": {
    "node": ">=26"
  },
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck",
    "clean": "turbo run clean",
    "format": "prettier --write \"**/*.{ts,tsx,vue,js,json,md}\""
  },
  "devDependencies": {
    "prettier": "^3.9.6",
    "turbo": "^2.10.9"
  }
}
```

逐个字段解释：

- **`"name": "taskflow"`**：项目名称。在 monorepo 中，根目录的 name 通常是项目品牌名。
- **`"private": true`**：**极其重要**。防止根目录的包被意外发布到 npm。Monorepo 的根目录永远不应该被发布。
- **`"packageManager": "pnpm@11.21.0"`**：配合 Corepack 使用，确保所有人使用相同版本的 pnpm。当你执行 `pnpm install` 时，Corepack 会检查这个字段。
- **`"engines"`**：声明最低 Node.js 版本要求。pnpm 会在安装时检查。
- **`scripts`**：根目录的脚本通过 `turbo run` 来编排各子包的脚本执行。后面 Ch05 会详细讲 `turbo.json` 的配置。
- **`devDependencies`**：放在根目录的 devDependencies 中的是整个项目共用的开发工具（Prettier、Turborepo）。

> **为什么 `turbo` 放在 devDependencies 而不是 dependencies？** 因为 Turborepo 只在开发和 CI 时使用，不会被打包到生产产物中。所有构建工具都应放在 devDependencies。

### 第三步：创建 pnpm-workspace.yaml

这是 pnpm workspace 的核心配置文件，它告诉 pnpm 哪些目录是工作区包。

在项目根目录创建 `pnpm-workspace.yaml`：

```yaml
packages:
  - "apps/*"
  - "packages/*"
allowBuilds:
  # 否则pnpm 阻止 esbuild postinstall 
  esbuild: true
```

这个配置的含义是：`apps/` 和 `packages/` 下的每个子目录都是一个独立的包。

> **为什么不用 `"**/package.json"` 这种通配符？** 因为显式列出 `apps/*` 和 `packages/*` 更清晰，也避免了意外把 `node_modules` 或其他目录识别为包。pnpm 要求精确、显式的配置。

**关于 packages 配置的更多选项：**

```yaml
# 如果需要排除某些目录
packages:
  - "apps/*"
  - "packages/*"
  - "!packages/deprecated-*"   # 排除 deprecated 开头的包
allowBuilds:
  esbuild: true

# 如果有不在 apps/packages 下的包
packages:
  - "apps/*"
  - "packages/*"
  - "tools/cli"                # 单独指定一个路径
allowBuilds:
  esbuild: true
```

### 第四步：创建目录结构

```bash
# 创建 apps 和 packages 目录
mkdir -p apps/web apps/api
mkdir -p packages/shared packages/eslint-config packages/tsconfig
```

暂时先创建空目录，后续章节会填充内容。

### 第五步：创建 .gitignore

在项目根目录创建 `.gitignore`：

```gitignore
# 依赖目录
node_modules/

# 构建产物
dist/
build/
.next/
.output/
.turbo/

# 日志
*.log
npm-debug.log*
pnpm-debug.log*

# 环境变量
.env
.env.local
.env.*.local

# 编辑器
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
.idea/

# 操作系统
.DS_Store
Thumbs.db

# 测试覆盖率
coverage/

# 临时文件
*.tmp
.cache/
```

> **为什么 `node_modules/` 要忽略？** 在 monorepo 中，pnpm 会在根目录和每个包下创建 `node_modules`。这些目录包含的是从全局 store 链接过来的文件，不应该提交到 Git。任何人 `git clone` 后只需执行 `pnpm install` 就能恢复。

### 第六步：创建 .npmrc

创建 `.npmrc` 文件来配置 pnpm 的行为：

```ini
# 确保使用严格的依赖解析
shamefully-hoist=false

# 启用 pnpm 的全局 store（节省磁盘）
prefer-workspace-packages=true

# 安装时自动安装 peer dependencies
# 关闭此项可以获得更严格的依赖控制
auto-install-peers=false

# 当依赖版本有冲突时报错（而不是静默忽略）
strict-peer-dependencies=true
```

逐行解释：

- **`shamefully-hoist=false`**：这是 pnpm 的默认值，也是推荐值。它确保包只能访问自己声明的依赖（解决 phantom dependency 问题，Ch04 会详细讲）。如果你从 npm/yarn 迁移过来，某些包可能依赖了 hoisting 行为，这时可以临时设为 `true`，但应该尽快修复依赖声明。
- **`prefer-workspace-packages=true`**：当 workspace 中存在某个包，且 `package.json` 中的版本范围匹配时，优先使用 workspace 本地版本而不是从 registry 下载。
- **`auto-install-peers=false`**：不自动安装 peer dependencies。这意味着如果某个包声明了 `peerDependencies`，你需要显式安装它。这让依赖关系更加透明。
- **`strict-peer-dependencies=true`**：当 peer dependency 版本不匹配时报错而非警告。

### 第七步：创建 .nvmrc（回顾）

```bash
echo "26.1.0" > .nvmrc
```

### 第八步：安装根目录依赖

```bash
pnpm install
```

执行后你会看到 pnpm 在根目录创建了 `node_modules/` 和一个 `pnpm-lock.yaml` 文件。

> **`pnpm-lock.yaml` 必须提交到 Git。** 它确保所有开发者和 CI 环境安装完全相同版本的依赖。

### 第九步：初始化 Git 仓库

```bash
git init
git add .
git commit -m "chore: init monorepo with pnpm workspace"
```

### 验证你的成果

此时你的目录结构应该是：

```
taskflow/
├── .git/
├── .gitignore
├── .npmrc
├── .nvmrc
├── apps/
│   ├── api/
│   └── web/
├── packages/
│   ├── eslint-config/
│   ├── shared/
│   └── tsconfig/
├── node_modules/
├── package.json
├── pnpm-lock.yaml
└── pnpm-workspace.yaml
```

运行以下命令验证 workspace 已被正确识别：

```bash
pnpm ls -r --depth -1
```

目前输出为空是正常的——因为我们还没有在任何子目录中创建 `package.json`。下一章我们会填充这些目录。

## 2.4 Turborepo 配置初探

虽然 Turborepo 的详细配置会在 Part 2 中深入讲解，但我们在这里先创建一个基础配置，确保 `turbo run` 命令可以正常工作。

在项目根目录创建 `turbo.json`：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {
      "dependsOn": ["^build"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "clean": {
      "cache": false
    }
  }
}
```

简单解释：

- **`build`**：`dependsOn: ["^build"]` 表示构建一个包之前，先构建它的所有依赖。`outputs: ["dist/**"]` 告诉 Turborepo 构建产物在 `dist/` 目录，用于缓存判断。
- **`dev`**：`cache: false` 表示开发服务器不缓存。`persistent: true` 表示这是一个长时间运行的进程（如 dev server），Turborepo 不会等待它完成。
- **`lint`** 和 **`typecheck`**：依赖上游包的 build 完成（因为 TypeScript 需要引用上游的类型声明）。
- **`clean`**：清理操作不需要缓存。

验证 Turborepo 是否正常工作：

```bash
npx turbo run build
```

输出应该类似：

```
• Tasks:    0 successful, 0 total
• Cached:   0 cached, 0 total
• Time:     0ms
```

这是正确的——因为我们还没有任何子包定义了 `build` 脚本。

## 2.5 常见问题排查

**Q1: `pnpm install` 报错 "Cannot find module"**

检查你的 Node.js 版本是否符合 `engines` 要求：

```bash
node --version  # 应该 >= 20
```

**Q2: `corepack enable` 后 `pnpm` 命令不可用**

在某些系统上，Corepack 可能需要额外配置 PATH。尝试：

```bash
# 直接用 npm 安装作为备选
npm install -g pnpm@9
```

**Q3: `pnpm-workspace.yaml` 不被识别**

确保 YAML 格式正确（注意缩进用空格而非 tab）。可以用以下命令验证：

```bash
pnpm ls -r
```

如果报 YAML 解析错误，检查文件编码是否为 UTF-8。

**Q4: 安装后出现 peer dependency 警告**

由于我们设置了 `strict-peer-dependencies=true`，某些包的 peer dependency 未安装时会报错。解决方案有两种：

- 安装缺失的 peer dependency
- 在 `.npmrc` 中添加 `strict-peer-dependencies=false`（临时方案）

## 本章小结

- 使用 `.nvmrc` 锁定 Node.js 版本，用 Corepack 锁定 pnpm 版本——两个"锁"确保团队环境一致
- `pnpm-workspace.yaml` 是 workspace 的入口，用 glob 模式声明包的位置
- 根目录 `package.json` 的 `"private": true` 和 `"packageManager"` 字段不可遗漏
- `.npmrc` 中的 `shamefully-hoist=false` 是 pnpm 严格模式的保障
- `turbo.json` 定义了任务编排规则，`dependsOn: ["^build"]` 是最常见的模式
