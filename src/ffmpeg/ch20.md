# 第20章：RTMP 推流实战

> 理论课结束了，是时候卷起袖子干活了。这一章，我们从零搭建一个完整的直播推流系统——包括服务器、推流端、转码端和播放端。

## 20.1 推流的基本概念

直播系统的架构其实很直观：

```
┌──────────┐    RTMP     ┌──────────────┐    RTMP/HLS    ┌──────────┐
│  推流端   │ ──────────→ │  流媒体服务器  │ ←──────────── │  播放端   │
│ (OBS/FFmpeg)│           │ (Nginx/SRS)  │               │ (播放器)  │
└──────────┘             └──────────────┘               └──────────┘
                              │
                              ├── 转码（多码率）
                              ├── 录制（回放）
                              └── 分发（HLS/CDN）
```

- **推流端（Publisher）**：把音视频数据编码后发送到服务器
- **流媒体服务器**：接收、处理、分发流
- **播放端（Player）**：从服务器拉取并播放流

## 20.2 搭建 Nginx + RTMP 服务器

在动手之前，先理解 Nginx-RTMP 的架构。Nginx 本身是一个 Web 服务器，通过加载 `nginx-rtmp-module` 模块，它就能同时处理 HTTP 请求和 RTMP 流。也就是说，一台服务器既能提供网页服务，又能接收和分发直播流——性价比极高。

需要注意的是，`nginx-rtmp-module` 的原作者 arut 已经很久没更新了。如果你需要更活跃的维护版本，可以考虑以下替代分支：

- **nginx-http-flv-module**（winshining）：增加了 HTTP-FLV 支持
- **nginx-rtmp-module-enhanced**：修复了一些已知的 bug

### Nginx 配置文件

这是完整的 `nginx.conf`，直接可以用：

```nginx
worker_processes auto;

events {
    worker_connections 1024;
}

# RTMP 配置
rtmp {
    server {
        listen 1935;
        chunk_size 4096;

        # 直播应用
        application live {
            live on;
            record off;

            # 允许推流的 IP（生产环境要限制）
            allow publish all;

            # 推流时自动转 HLS
            hls on;
            hls_path /tmp/hls;
            hls_fragment 6s;
            hls_playlist_length 60s;

            # 录制（可选）
            # record all;
            # record_path /tmp/recordings;
            # record_suffix _%Y-%m-%d_%H-%M-%S.flv;

            # 转推到其他服务器（可选）
            # push rtmp://backup-server/live;

            # 当有流推入时执行的命令（用于转码）
            # on_publish http://localhost:8080/on_publish;
            # exec ffmpeg -i rtmp://localhost/live/$name
            #     -c:v libx264 -c:a aac -b:v 1500k -s 1280x720
            #     -f flv rtmp://localhost/hls/$name_720p;
        }

        # HLS 专用应用
        application hls {
            live on;
            hls on;
            hls_path /tmp/hls;
            hls_fragment 6s;
            hls_playlist_length 60s;
            hls_nested on;
        }

        # 录制专用应用
        application recording {
            live on;
            record all;
            record_path /tmp/recordings;
            record_max_size 1G;
            record_unique on;
            record_suffix _%Y-%m-%d_%H-%M-%S.flv;
        }
    }
}

# HTTP 配置（用于 HLS 分发和状态监控）
http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile      on;
    keepalive_timeout 65;

    server {
        listen 8080;

        # HLS 切片文件服务
        location /hls {
            types {
                application/vnd.apple.mpegurl m3u8;
                video/mp2t ts;
            }
            root /tmp;
            add_header Cache-Control no-cache;
            add_header Access-Control-Allow-Origin *;
        }

        # RTMP 状态页面
        location /stat {
            rtmp_stat all;
            rtmp_stat_stylesheet stat.xsl;
        }

        location /stat.xsl {
            root /path/to/nginx-rtmp-module;
        }

        # 简单的播放页面
        location / {
            root /var/www/html;
        }
    }
}
```

验证配置并重启：

```bash
sudo /usr/local/nginx/sbin/nginx -t   # 检查配置
sudo /usr/local/nginx/sbin/nginx -s reload  # 重新加载
```

**配置文件逐行解读：**

上面的 Nginx 配置看起来很复杂，但核心只有三个部分：

1. **`rtmp {}` 块**：定义 RTMP 服务器行为
   - `listen 1935`：RTMP 标准端口
   - `application live {}`：定义一个"应用"，推流地址就是 `rtmp://server/live/流名`
   - `hls on`：自动生成 HLS 切片
   - `hls_path /tmp/hls`：切片存放目录

2. **`application recording {}`**：独立的录制应用
   - 你可以把流推到 `rtmp://server/recording/xxx` 来专门录制
   - `record_unique on`：每个录制文件名唯一（防止覆盖）

3. **`http {}` 块**：标准 HTTP 服务
   - `/hls` 路径提供 m3u8 和 ts 文件
   - `/stat` 路径提供 RTMP 状态页面（可以看到当前有多少人在看、推流状态等）

**验证服务器是否正常：**

```bash
# 检查 RTMP 端口是否在监听
netstat -tlnp | grep 1935

# 检查 HTTP 端口
curl http://localhost:8080/stat

# 用 ffprobe 验证 RTMP 流
ffprobe rtmp://localhost/live/test
```

## 20.3 FFmpeg 推流基本命令

最基础的推流命令：

```bash
ffmpeg -re -i input.mp4 \
  -c copy \
  -f flv \
  rtmp://localhost/live/stream
```

参数解析：

- `-re`：按原始帧率读取（**非常重要**，后面详细讲）
- `-i input.mp4`：输入文件
- `-c copy`：不转码，直接复制音视频流
- `-f flv`：输出格式为 FLV（RTMP 要求 FLV 封装）
- `rtmp://localhost/live/stream`：RTMP 地址（服务器/应用/流名称）

## 20.4 神秘的 -re 参数

`-re`（Read at native frame rate）是推流时**最容易忘记但也最重要**的参数。

**不加 -re 会怎样？**

FFmpeg 会以最快的速度把文件"灌"到服务器。一个 5 分钟的视频，可能 3 秒就推完了——服务器收到的是一瞬间的数据洪水，直接崩溃或丢弃大量帧。

**加了 -re 呢？**

FFmpeg 会模拟实时播放的速度，按原始帧率逐帧推送。就像你正常播放视频一样，1 秒的视频数据就在 1 秒内发完。

```bash
# 不加 -re：洪水式推流（错误示范）
ffmpeg -i input.mp4 -c copy -f flv rtmp://server/live/stream
# → 5分钟视频 3秒推完，播放端看到的就是花屏和卡顿

# 加 -re：正常速率推流（正确姿势）
ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream
# → 5分钟视频用 5分钟推，播放端正常播放
```

> **注意**：`-re` 只用于文件推流。如果是摄像头等实时输入源，数据本身就是实时的，不需要 `-re`。

## 20.5 推流参数优化

生产环境中，推流参数需要精心调优：

```bash
ffmpeg -re -i input.mp4 \
  -c:v libx264 \
  -preset veryfast \
  -tune zerolatency \
  -b:v 2500k \
  -maxrate 2500k \
  -bufsize 5000k \
  -g 60 \
  -keyint_min 60 \
  -c:a aac -b:a 128k \
  -f flv \
  rtmp://server/live/stream
```

关键参数解释：

- **`-preset veryfast`**：编码速度。推流要求低延迟，不能用 `slow`，推荐 `veryfast` 或 `superfast`
- **`-tune zerolatency`**：零延迟调优。去掉 B 帧，减少缓冲延迟
- **`-g 60` / `-keyint_min 60`**：关键帧间隔。60 帧一个 GOP（2秒@30fps）。关键帧间隔太长会导致切流延迟，太短会增加码率开销
- **`-b:v 2500k`**：视频码率。直播常用值：720p = 1500-3000k，1080p = 3000-6000k
- **`-bufsize 5000k`**：码率控制缓冲区。通常设为码率的 2 倍

**关键帧间隔的讲究：**

```
GOP = 2秒（推荐）：切流快，但 I 帧多，码率开销大
GOP = 4秒：平衡选择
GOP = 10秒：省码率，但切流慢，HLS 延迟高
```

对于直播，建议 GOP 设为 2-4 秒。如果同时做 HLS，GOP 必须是切片时长的整数倍（比如 HLS 切片 6 秒，GOP 就设 2 秒或 3 秒）。

## 20.7 多路同时推流

想把同一个流同时推到 B站、YouTube、Twitch？没问题：

```bash
# 方法一：-tee 多路输出（推荐，只编码一次）
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 2500k \
  -c:a aac -b:a 128k \
  -f flv \
  "rtmp://bilibili-server/live/stream_key|rtmp://youtube-server/live/stream_key"

# 方法二：使用 -tee muxer（更灵活）
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 2500k \
  -c:a aac -b:a 128k \
  -f tee \
  "[f=flv]rtmp://bilibili/live/key1|[f=flv]rtmp://youtube/live/key2|[f=flv]rtmp://twitch/live/key3"
```

**方法二更好**，因为 `-tee` muxer 可以在某一路失败时不影响其他路：

```bash
# 带错误容忍的 tee 推流
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 2500k \
  -c:a aac -b:a 128k \
  -f tee \
  "[f=flv:onfail=ignore]rtmp://server1/live/key1|[f=flv:onfail=ignore]rtmp://server2/live/key2"
```

## 20.8 推流状态监控与断线重连

生产环境中，推流不能"推了就跑"，你需要监控状态和处理断线：

```bash
#!/bin/bash
# 自动断线重连的推流脚本

STREAM_URL="rtmp://server/live/stream"
INPUT_FILE="input.mp4"
MAX_RETRIES=10
RETRY_DELAY=5

retry_count=0

while [ $retry_count -lt $MAX_RETRIES ]; do
    echo "[$(date)] 开始推流... (尝试 $((retry_count + 1))/$MAX_RETRIES)"

    ffmpeg -re -i "$INPUT_FILE" \
        -c:v libx264 -preset veryfast -b:v 2500k \
        -c:a aac -b:a 128k \
        -f flv \
        -flvflags no_duration_filesize \
        "$STREAM_URL" 2>&1 | tee -a push.log

    exit_code=$?

    if [ $exit_code -eq 0 ]; then
        echo "[$(date)] 推流正常结束"
        break
    fi

    echo "[$(date)] 推流中断 (exit code: $exit_code)，${RETRY_DELAY}秒后重连..."
    sleep $RETRY_DELAY
    retry_count=$((retry_count + 1))
done

if [ $retry_count -ge $MAX_RETRIES ]; then
    echo "[$(date)] 达到最大重试次数，推流失败"
    exit 1
fi
```

**FFmpeg 内置重连参数：**

```bash
ffmpeg -re -i input.mp4 \
  -c copy -f flv \
  -reconnect 1 \
  -reconnect_streamed 1 \
  -reconnect_delay_max 5 \
  "rtmp://server/live/stream"
```

- `-reconnect 1`：连接断开时自动重连
- `-reconnect_streamed 1`：流式传输时也启用重连
- `-reconnect_delay_max 5`：最大重连延迟 5 秒

## 20.9 SRS 替代方案

**SRS（Simple Realtime Server）** 是一个国产的高性能流媒体服务器，比 Nginx-RTMP 更强大：

```bash
# Docker 一键启动 SRS
docker run -d --name srs \
  -p 1935:1935 \
  -p 1985:1985 \
  -p 8080:8080 \
  ossrs/srs:5 ./objs/srs -c conf/docker.conf

# 推流到 SRS
ffmpeg -re -i input.mp4 -c copy -f flv rtmp://localhost/live/stream

# SRS 自动生成 HLS（访问 http://localhost:8080/live/stream.m3u8）
# SRS 自动提供 HTTP-FLV（访问 http://localhost:8080/live/stream.flv）
# SRS 自动提供 HTTP-TS（访问 http://localhost:8080/live/stream.ts）
```

SRS 的优势：

- 原生支持 RTMP、HLS、HTTP-FLV、SRT、WebRTC
- 内置 DVR（录制）功能
- 提供 HTTP API 和 Web 管理界面
- 性能优秀（单机支持数千路并发）
- 配置简单，Docker 一键部署

**SRS 的自定义配置：**

如果你想更精细地控制 SRS 的行为，可以编写自定义配置文件：

```txt
# srs.conf - SRS 自定义配置
listen 1935;
max_connections 1000;
daemon off;
srs_log_tank console;

http_server {
    enabled on;
    listen 8080;
    dir ./objs/nginx/html;
}

http_api {
    enabled on;
    listen 1985;
}

stats {
    network 0;
}

vhost __defaultVhost__ {
    # 直播应用
    hls {
        enabled on;
        hls_fragment 6;
        hls_window 60;
        hls_path ./objs/nginx/hls;
        hls_m3u8_file [app]/[stream].m3u8;
        hls_ts_file [app]/[stream]-[seq].ts;
    }

    # 录制到 MP4
    dvr {
        enabled on;
        dvr_path ./objs/nginx/dvr/[app]/[stream].[timestamp].mp4;
        dvr_plan session;
        dvr_duration 3600;
        dvr_wait_keyframe on;
    }

    # HTTP-FLV 播放
    http_flv {
        enabled on;
    }

    # HTTP-TS 播放
    http_ts {
        enabled on;
    }

    # 安全设置
    security {
        enabled on;
        allow play all;
        allow publish 127.0.0.1 192.168.0.0/16;
    }
}
```

使用自定义配置启动：

```bash
docker run -d --name srs \
  -p 1935:1935 -p 1985:1985 -p 8080:8080 \
  -v /path/to/srs.conf:/usr/local/srs/conf/srs.conf \
  -v /data/recordings:/usr/local/srs/objs/nginx/dvr \
  ossrs/srs:5 ./objs/srs -c conf/srs.conf
```

**SRS 的 HTTP API：**

SRS 提供了丰富的 REST API，可以用脚本监控和管理：

```bash
# 获取所有活跃流
curl http://localhost:1985/api/v1/streams

# 获取特定流的信息
curl http://localhost:1985/api/v1/streams?name=stream

# 获取服务器状态
curl http://localhost:1985/api/v1/summaries

# 踢掉某个推流
curl -X DELETE http://localhost:1985/api/v1/clients/{client_id}

# 获取客户端列表
curl http://localhost:1985/api/v1/clients
```

**SRS + FFmpeg 的完整直播工作流：**

```
推流端（OBS/FFmpeg）
       │
       │ RTMP
       ▼
   SRS 服务器
       │
       ├── HTTP-FLV ──→ 网页低延迟播放（延迟 1-2秒）
       ├── HLS ──→ CDN ──→ 大规模观众（延迟 10-20秒）
       ├── HTTP-TS ──→ 兼容播放器
       └── DVR ──→ MP4 文件 ──→ 点播回放
```

**推流常见问题排查清单：**

在实际推流过程中，你可能会遇到各种问题。这里总结一份排查清单：

1. **推流失败，连接被拒绝**
   - 检查服务器防火墙是否开放了 1935 端口
   - 确认 RTMP 服务器已启动（`netstat -tlnp | grep 1935`）
   - 确认推流地址格式正确：`rtmp://服务器IP/应用名/流名`

2. **推流成功但播放端黑屏**
   - 检查推流端是否正确发送了视频数据（查看 FFmpeg 输出）
   - 确认播放端 URL 是否正确
   - 尝试用 `ffplay rtmp://server/live/stream` 验证

3. **推流过程中画面卡顿**
   - 检查推流端 CPU 使用率（编码可能跟不上了）
   - 降低编码 preset（从 medium 改为 veryfast）
   - 降低视频码率
   - 检查网络带宽是否足够

4. **推流延迟越来越高**
   - 确认使用了 `-tune zerolatency`
   - 确认 GOP 设置合理（2-4 秒）
   - 检查推流端是否有帧率波动

5. **推流断开后无法恢复**
   - 使用 `-reconnect` 系列参数
   - 在脚本层面做断线重连（见 20.8 节）
   - 检查服务器的 `max_connections` 配置

## 本章小结

- 推流的核心架构是**推流端 → 服务器 → 播放端**，三者缺一不可
- `-re` 参数是文件推流的**必选项**，不加它 FFmpeg 会以最快的速度把文件"灌"到服务器，导致服务器崩溃
- 关键帧间隔（GOP）直接影响切流延迟和 HLS 切片质量，直播建议 2-4 秒
- 推流参数调优的核心：`-preset veryfast` + `-tune zerolatency` + `-g 60` + `-b:v 合理码率`
- `-tee` muxer 支持**一次编码、多路推流**，比多开 FFmpeg 进程更省资源
- 生产环境必须有**断线重连**机制，用 `-reconnect` 参数或脚本实现
- **SRS** 是比 Nginx-RTMP 更强大的开源流媒体服务器，支持 RTMP、HLS、HTTP-FLV、SRT、WebRTC
- Nginx + nginx-rtmp-module 是轻量级方案，适合小规模部署和个人学习
- 推流出问题时的排查顺序：端口→服务器→推流地址→编码参数→网络带宽
