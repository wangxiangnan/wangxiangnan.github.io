## 8.1 TCP 的设计目标：在不可靠的网络上提供可靠传输

IP 层是一个「尽力而为」（best-effort）的服务：它不保证数据包能送达，不保证按顺序到达，不保证数据不被篡改。在这种不可靠的基础上，TCP 要提供**完全可靠**的字节流服务。

这就像邮政系统告诉你「我可能会丢信、可能把信送错、可能把信件顺序搞乱」，而 TCP 要在这种邮政系统之上构建一个「绝对不丢、绝对不错、绝对有序」的通信管道。

TCP 的核心设计目标可以概括为四点：

1. **可靠传输**：发送方发出的每一个字节，接收方都能正确收到。如果丢失，自动重传。
2. **有序交付**：接收方看到的数据顺序与发送方发送的顺序完全一致。
3. **完整性校验**：通过校验和检测数据损坏，丢弃损坏的数据并触发重传。
4. **流量控制与拥塞控制**：不让发送方淹没接收方，也不让发送方压垮网络。

为了实现这些目标，TCP 引入了一整套机制。本书的分工是：**连接管理与报头字段语义在本章**；丢失后的重传策略、乱序缓存、SACK 等「可靠性引擎」在第9章；保护网络的拥塞控制在第10章；保护接收方的流量控制在第11章。本章先把「连接的一生」走完，引擎内部留到后面拆开看。

## 8.2 三次握手：为什么是三次不是两次？

TCP 是面向连接的协议。在传输数据之前，双方必须先建立一个「连接」。这个连接的建立过程就是著名的**三次握手（Three-Way Handshake）**：

```
客户端                         服务器
  |                              |
  |---- SYN (seq=x) ----------->|   第一次：客户端说"我想连接"
  |                              |
  |<--- SYN+ACK (seq=y,ack=x+1)-|   第二次：服务器说"好的，我也想连"
  |                              |
  |---- ACK (seq=x+1,ack=y+1)->|   第三次：客户端说"确认，连上了"
  |                              |
  |==== 连接已建立，开始传输 ====|
```

**SYN（Synchronize）** 和 **ACK（Acknowledge）** 是 TCP 报头中的两个标志位（Flag）。SYN=1 表示这是一个连接请求/响应，ACK=1 表示确认号字段有效。

现在回答一个经典面试题：**为什么是三次，不是两次？**「先猜再读」第一问的答案——两次的问题不是「确认不了网络通」，而是**服务器会为一个可能不存在的连接白白分配资源**：

假设只有两次握手，服务器在发送 SYN+ACK 后就认为连接已建立，开始为这个连接分配资源（缓冲区、定时器等）。但如果客户端的 SYN 是一个**滞留的旧报文**（Delayed Duplicate）——比如客户端之前发起过一次连接，那个 SYN 在网络中迷路了，现在才到达服务器——服务器会以为这是一次新的连接请求，分配资源并等待数据。而客户端根本不知道这个连接的存在，不会发送任何数据。结果：服务器白白浪费资源。

三次握手解决了这个问题：客户端收到 SYN+ACK 后，会检查这个 SYN+ACK 是否对应自己当前正在发起的连接。如果是一个「意外」的 SYN+ACK（对应一个旧的、已经放弃的连接请求），客户端会回复 RST（Reset），服务器收到 RST 后释放资源。关键在于：**服务器在收到第三次握手的 ACK 之前，不会进入完全的连接建立状态。**

**那为什么不是四次？** 奥卡姆剃刀原则——三次已经足够在双方之间同步两个关键信息：客户端的初始序号（ISN）和服务器的初始序号（ISN）。三次报文交换刚好够双方各发一次 SYN 并各收一次 ACK。多一次纯属浪费。

## 8.3 TCP 报头详解：序号、确认号、窗口大小、标志位

TCP 的报头比 UDP 复杂得多，最小长度为 **20 字节**（不含选项字段），最大可达 60 字节：

```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|     源端口号     |    目的端口号    |
+--------+--------+--------+--------+
|             序号(Seq)             |
+--------+--------+--------+--------+
|           确认号(Ack)             |
+--------+--------+--------+--------+
|数据偏移| 保留 |U A P R S F|  窗口大小 |
| (4bit) |(4bit)|R C S S Y I| (16bit) |
|        |      |G K H T N N|         |
+--------+--------+--------+--------+
|         校验和      |   紧急指针    |
+--------+--------+--------+--------+
|              选项(可变长)          |
+--------+--------+--------+--------+
```

关键字段详解：

- **序号（Sequence Number，32 位）**：本报文段中第一个数据字节的序号。假设你发送了 1000 字节的数据，起始序号为 5000，那么这 1000 字节的序号范围是 5000~5999。连接建立时，序号从一个随机选择的 **ISN（Initial Sequence Number）** 开始。为什么随机？安全考虑——如果序号可预测，攻击者可以伪造数据包劫持连接（TCP 序列号预测攻击）。

- **确认号（Acknowledgment Number，32 位）**：期望收到的下一个字节的序号。如果确认号是 6000，表示「我已经完整收到了序号 5999 及之前的所有数据，我期望下一个收到的是序号 6000」。这种「一口气确认到某处」的形式叫**累积确认**，它是第9章可靠性机制的基石，那里会讲乱序到达时它如何表现。

- **数据偏移（Data Offset，4 位）**：TCP 报头的长度，以 4 字节为单位。最小值为 5（即 20 字节），最大值为 15（即 60 字节）。之所以叫「数据偏移」，是因为它同时也指示了数据载荷从第几个字节开始。

- **标志位（Flags，6 位）**：
  - **URG**：紧急指针有效。本报文中有紧急数据，接收方应优先处理。
  - **ACK**：确认号字段有效。除了最初的 SYN 报文外，所有 TCP 报文都应该设置此位。
  - **PSH**：推送标志。告诉接收方「不要缓冲，立即把数据交给应用程序」。
  - **RST**：重置连接。表示发生了严重错误，需要立即终止连接。
  - **SYN**：同步序号，用于建立连接。
  - **FIN**：发送方已完成数据发送，请求关闭连接。

- **窗口大小（Window Size，16 位）**：接收方当前还能接收多少字节的数据（即接收窗口 rwnd）。这是 TCP 流量控制的入口字段——保护接收方的完整机制（零窗口、窗口探测、窗口缩放）在第11章展开。

- **校验和（Checksum，16 位）**：强制字段，覆盖 TCP 报头、数据以及 IP 伪首部。

- **紧急指针（Urgent Pointer，16 位）**：配合 URG 标志使用，指出本报文中紧急数据的末尾位置。实际应用中很少使用（Telnet 是少数使用它的协议之一）。

## 8.4 序号与确认号：面向字节的累积确认

序号和确认号是 TCP 可靠传输的基石。理解它们的关键在于认识到：**TCP 是面向字节的协议，不是面向报文的。**

这意味着什么？假设应用程序分三次调用 `send()`：

```python
sock.send(b"Hello")       # 5 字节
sock.send(b" World")      # 6 字节
sock.send(b"!")           # 1 字节
```

TCP 并不关心你调了几次 `send()`。在 TCP 看来，这就是一个连续的字节流：`H-e-l-l-o- -W-o-r-l-d-!`，共 12 字节。如果当前序号是 1000，那么：

- `H` 的序号是 1000
- `e` 的序号是 1001
- `!` 的序号是 1011

接收方可能一次性收到全部 12 字节，也可能分两次收到（比如先收到 8 字节，再收到 4 字节）。TCP 负责把这些数据重新组装成原始的字节流，交给应用程序。「先猜再读」第三问的前半答案就在这里：**三次 `send()` 对应不了三次 `recv()`**——字节流没有边界，这就是 8.7 要动手解决的粘包问题。

确认号的累积性质意味着：如果接收方发送 ACK=1008，它表示序号 1000~1007 的 8 个字节都已正确收到。至于中间出现乱序（序号 1010 的报文先到、1008 的后到）时接收方怎么办、确认号停在哪儿、发送方如何得知空洞位置——这些是第9章「可靠性引擎」的主戏，本章不展开。

## 8.5 数据传输：捎带确认与全双工

握手完成后连接进入数据传输阶段。TCP 是**全双工**的——数据可以同时双向流动，每一方既是发送方也是接收方。看一次双向传输（沿用 8.2 的 ISN，客户端 1000、服务器 5000）：

```
Client                        Server
  |                               |
  |--- PSH+ACK, seq=1001,        |
  |    ack=5001, data="Hello" -->|   客户端发送 5 字节
  |                               |
  |<-- ACK, seq=5001,            |   服务器确认收到
  |    ack=1006 -----------------|
  |                               |
  |<-- PSH+ACK, seq=5001,        |
  |    ack=1006, data="World" ---|   服务器发送 5 字节
  |                               |
  |--- ACK, seq=1006,            |   客户端确认收到
  |    ack=5006 ---------------->|
```

注意 SYN 报文本身「消耗」了一个序号（虽然没有携带应用数据），所以握手后的数据从 seq=1001 开始。

每一方在发送数据时捎带（piggyback）对另一方数据的确认——ACK 字段就挂在数据报文上，不需要单独的 ACK 报文。这是 TCP 的高效之处；只有一方暂时无数据可发时，才会出现独立的纯 ACK 报文。

## 8.6 四次挥手：为什么断开比建立多一次？TIME_WAIT 的意义

TCP 连接的关闭不是简单的「一方说再见，另一方说拜拜」。因为 TCP 是全双工的，**每个方向必须独立关闭**：

```
Client                         Server
  |                              |
  |--- FIN, seq=1006,           |   第一次：客户端说"我发完了"
  |    ack=5006 --------------->|
  |                              |
  |<-- ACK, seq=5006,           |   第二次：服务器说"收到你的FIN"
  |    ack=1007 ---------------|
  |                              |
  |    (服务器可能还在发送剩余数据)   |
  |                              |
  |<-- FIN, seq=5200,           |   第三次：服务器说"我也发完了"
  |    ack=1007 ---------------|
  |                              |
  |--- ACK, seq=1007,           |   第四次：客户端说"收到你的FIN"
  |    ack=5201 -------------->|
  |                              |
  |    [TIME_WAIT: 2*MSL]       |   客户端进入 TIME_WAIT 状态
```

「先猜再读」第二问的答案——服务器**不能**收到 FIN 就立即回 FIN：客户端发 FIN 只表示「我不再发了」，不代表「我不收了」，服务器可能还有数据要发。所以收到 FIN 的一方先回 ACK，等自己把数据发完再发自己的 FIN。这就把建立连接时可以合并的 SYN+ACK 拆成了独立的 ACK 和 FIN，多了一次。（当然，如果收到 FIN 时确实没有数据要发，ACK 和 FIN 也可以合并成一个报文——8.8 的抓包会看到这一幕。）

**TIME_WAIT 的意义：** 发送最后一个 ACK 的一方（本例中是客户端）会进入 **TIME_WAIT** 状态，持续 **2×MSL（Maximum Segment Lifetime，报文最大生存时间，通常合计 4 分钟）**。这不是浪费，而是出于两个重要原因：

1. **确保最后的 ACK 能到达对方**：如果这个 ACK 丢失了，服务器会重发 FIN。处于 TIME_WAIT 状态的客户端可以再次回复 ACK。如果没有 TIME_WAIT，客户端已经关闭了连接，收到重发的 FIN 后会回复 RST，服务器会认为连接异常终止。

2. **防止旧连接的报文干扰新连接**：如果一对 IP+端口立刻建立新连接，旧连接中滞留的报文可能会混入新连接。等待 2×MSL 可以确保旧连接的所有报文都在网络中消亡。

TIME_WAIT 是高并发服务器的一个常见痛点：每秒关闭大量连接时，TIME_WAIT 状态的连接会累积，占用端口资源。常见的调优方法包括启用 `tcp_tw_reuse`、加大可用端口范围等；编程时配一个 `SO_REUSEADDR`（8.7 的代码里就有）可以避免「服务器重启失败」这一 TIME_WAIT 的经典副作用。

## 8.7 编程实践：用长度前缀协议解决粘包

TCP 是字节流协议，这意味着**数据没有边界**。你分两次 `send()` 发送的数据，接收方可能在一次 `recv()` 中全部收到——这就是所谓的**粘包问题**。粘包的本质（8.4 已提）：TCP 把应用数据看作一条连续的字节河流，而应用层的消息是河流中的一段段水；如果不在水段之间做标记，下游就不知道一段水的起止。

**解决方案：长度前缀协议**。在每个消息前面加一个固定长度的字段（这里是 4 字节无符号整数），表示后面消息体的长度。接收方先读 4 字节得到长度 N，再读 N 字节得到一个完整消息。HTTP/2 的帧、gRPC、Redis 的 RESP 协议等都使用了类似思路。

```python
import socket
import struct

HOST = '127.0.0.1'
PORT = 8888

def handle_client(conn, addr):
    """处理单个客户端连接"""
    print(f"新连接来自: {addr}")
    buffer = b""  # 接收缓冲区

    while True:
        data = conn.recv(4096)
        if not data:
            break  # 客户端关闭连接

        buffer += data

        # 长度前缀解包：每个消息 = 4字节长度(网络字节序) + 数据
        while len(buffer) >= 4:
            msg_len = struct.unpack('!I', buffer[:4])[0]

            if len(buffer) < 4 + msg_len:
                break  # 消息不完整，等待更多数据——粘包解法的核心

            msg = buffer[4:4 + msg_len]
            buffer = buffer[4 + msg_len:]  # 移除已处理的数据

            print(f"收到完整消息 ({msg_len} 字节): {msg.decode('utf-8')}")

            reply = f"已收到: {msg.decode('utf-8')}".encode('utf-8')
            reply = struct.pack('!I', len(reply)) + reply
            conn.sendall(reply)

    conn.close()
    print(f"连接关闭: {addr}")

def main():
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    # 允许地址复用，避免 TIME_WAIT 导致的重启失败
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((HOST, PORT))
    server.listen(5)
    print(f"TCP 服务器监听 {HOST}:{PORT}")

    while True:
        conn, addr = server.accept()
        handle_client(conn, addr)

if __name__ == '__main__':
    main()
```

对照第1章 1.5 的 KV 协议（用 `\n` 定界）与本节（用长度前缀定界）：前者是文本协议的定界思路，后者是二进制协议的定界思路——两条路线你都已经亲手实现过了。

## 8.8 抓包实践：完整追踪一条 TCP 连接的一生

用 `tcpdump` 追踪一次完整的 HTTP 请求：

- 三次握手在不到 50ms 内完成（0.001 到 0.046 秒，其中 44ms 是网络往返延迟）——这就是为什么 8.1 说握手成本要用 RTT 来计量。

## 本章小结

- TCP 的四大目标：可靠传输、有序交付、完整性校验、流量控制与拥塞控制——后两者分别在第10、11章展开。
- 三次握手的本质是同步双方 ISN 并防止滞留旧报文白白占用服务器资源；两次的漏洞在「服务器先建链」。
- ISN 随机化是安全设计：可预测的序号等于把连接劫持的钥匙交给攻击者。
- 报头核心字段：序号/确认号驱动累积确认，窗口大小是流量控制入口，六个标志位各管一件事。
- TCP 面向字节而非报文：`send()` 的次数不等于 `recv()` 的次数，边界是应用层自己的责任。
- 全双工捎带确认：ACK 搭数据的便车，只有无数据可发时才出现独立纯 ACK。
- 挥手之所以是四次：FIN 只关闭「我的发送方向」，对方可能还有话要说；无数据可发时 ACK+FIN 可合并。
- TIME_WAIT 等 2×MSL：兜住丢失的最终 ACK、隔离旧连接残留报文；副作用是高并发端口积压。
