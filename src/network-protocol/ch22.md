## 22.1 威胁模型：我们在防御什么

15.1 给 HTTP 画过三大威胁（窃听、篡改、冒充）。网络安全视角下，威胁清单更长：

1. **窃听（Eavesdropping）**：链路上抓包读明文。防御：加密（TLS、IPsec）。
2. **篡改（Tampering）**：修改传输中的数据。防御：完整性校验（HMAC、数字签名）。
3. **重放（Replay）**：录制合法请求稍后重发。防御：Nonce、时间戳、序列号——20.4 的 0-RTT 重放风险就是这类威胁的现役案例。
4. **DDoS（分布式拒绝服务）**：海量请求淹没目标，耗尽带宽或连接表。防御：流量清洗、速率限制、Anycast 分散——第23章会看到 CDN 扛 DDoS 的正面战场。

还有一类更隐蔽的：**侧信道（Side Channel）**——不偷内容本身，偷长度、时间、顺序等元数据。19.4 的 CRIME 攻击通过密文长度猜出 Cookie，就是侧信道家族的成员。威胁模型的意义在于：先明确「防谁、防什么、防到什么程度」，再选工具——跳过这一步的安全配置往往只是在堆砌名词。

## 22.2 防火墙：从包过滤到应用层

防火墙是网络的第一道防线——内外网之间设卡检查。三种类型，一层比一层看得深：

**包过滤（Packet Filter）**：逐包检查 IP/TCP/UDP 头，按规则放行或丢弃：

```bash
# 典型规则（伪代码）
ALLOW TCP src=10.0.1.0/24 dst=* port=22     # 管理网段可 SSH
ALLOW TCP state=ESTABLISHED,RELATED          # 已建立连接的返回流量
DENY ALL                                     # 其余全部拒绝
```

只看 IP 和端口，不懂应用语义。「先猜再读」第一问的答案：攻击者把恶意载荷放在 80 端口的 HTTP 里，包过滤完全看不出问题——端口开着，路就是通的。

**状态检测（Stateful Inspection）**：维护**连接状态表**，跟踪每条 TCP 连接的 SYN_SENT、ESTABLISHED、FIN_WAIT（8 章的连接一生在这里变成了一张表）。只有属于已建立连接的包才放行——防「无中生有」的伪造包。

**应用层防火墙（WAF）**：工作在 HTTP 层，理解请求语义：

```
# 正常请求
GET /user?id=123 HTTP/1.1

# SQL 注入——WAF 应拦截
GET /user?id=123'+OR+'1'='1 HTTP/1.1
```

WAF 用规则引擎或机器学习识别这类攻击模式。三层防线的规律：**越往上越懂语义，也越贵**——包过滤线速转发，WAF 要解析每个请求。12.5 的限速规则（hashlimit）与本节的体系是同一套工具在不同深度的应用。

> [!TIP] iptables 与它的继任者 nftables
> iptables 是 Linux 经典防火墙工具；较新内核的继任者是 nftables（语法更简洁、性能更好），firewalld/ufw 则是更高层的封装。语法在变，「默认拒绝、按需放行、分层检查」的心智模型不变——本节的规则思想全部通用。

## 22.3 VPN 协议族（概念级）：IPsec 与 WireGuard

VPN 的本质：把不可信网络上的流量装进可信的加密管道。18.4 的 SSH 隧道算是一种微型 VPN——单端口转发；本章讲的是成体系的 VPN 协议（本章管概念，实操教程互链 /vpn）。

**IPsec**：IP 层的安全协议，两种工作模式：

- **传输模式**：只加密 IP 载荷，IP 头保持明文——适合端到端通信。「外层」仍是原 IP 头。
- **隧道模式**：整个原始 IP 包被加密，外面再套一个新 IP 头——适合站点到站点 VPN。「外层」是新 IP 头，「内层」整个原包。「先猜再读」第二问的答案就在这里：隧道模式两层 IP 头，明文的外层负责路由，密文的内层保护一切。

IPsec 两个核心协议：

- **AH（协议号 51）**：只提供完整性与认证，不加密。
- **ESP（协议号 50）**：加密 + 完整性 + 认证，主力协议。

```
隧道模式 ESP 封装：
原始包: [IP头][TCP头][数据]
  ↓ 加密 TCP 头和数据
  ↓ 加 ESP 头和尾
  ↓ 加新的外层 IP 头
结果: [新IP头][ESP头][加密的TCP头+数据][ESP尾][ESP认证]
```

**WireGuard**：2020 年合入 Linux 内核的新一代 VPN，代码约 4000 行（OpenVPN 约 10 万行）。哲学是**少即是安全**：

- 固定一种加密方案（ChaCha20-Poly1305 + Curve25519）——20.7 提过它，与 TLS 1.3 的「做减法」如出一辙。
- 没有算法协商，攻击面最小。
- 1-RTT 握手，内核态实现性能接近原生。
- 内置 NAT 穿透与连接迁移——设计动机与 QUIC 的 Connection ID（20.5）同源。

| 特性 | OpenVPN | WireGuard |
| ---- | ------- | --------- |
| 代码量 | ~100K 行 | ~4K 行 |
| 加密算法 | 可协商 | 固定（ChaCha20-Poly1305） |
| 连接建立 | 较慢（基于 TLS） | 极快（Noise 协议） |
| NAT 穿透 | 需额外配置 | 内置支持 |
| 连接迁移 | 不支持 | 支持 |

本节只立概念：如何把云服务器配成 WireGuard 网关、写发放脚本、接入客户端——见站内[《VPN 配置完全教程》](/vpn/ch00)，两处互链不重复。其中 MTU 配置的深坑（隧道头部吃掉 MTU 导致大包黑洞）已在 5.4 剖析过，实操时请回看。

## 22.4 证书管理的运维侧：ACME 与 Let's Encrypt

15.4 讲了证书的验证机制，本节补运维视角：证书从哪来、怎么续。**Let's Encrypt** 提供免费自动化证书，核心流程（**ACME 协议**）：

1. 你向 Let's Encrypt 证明你拥有该域名（在域名下放一个校验文件，或用 DNS 记录）。
2. 验证通过，签发 90 天短期证书——短有效期（15.5 说过）逼出自动化，泄露的证书寿命也短。
3. 服务器自动续期，永不过期。

```bash
# certbot 自动获取证书并配置 nginx
sudo certbot --nginx -d example.com -d www.example.com

# certbot 会自动创建定时任务：每天检查续期、证书更新后自动重载 nginx
```

运维要点：把「证书续期」当作基础设施而非一次性任务——90 天周期意味着任何一次自动化故障都会在 90 天内暴露，监控续期任务是 TLS 站点的标配。

## 22.5 零信任：从「城堡与护城河」到「永不信任」

传统模型是城堡：防火墙外危险，内网安全。VPN 进内网 = 获得信任 = 可以横向访问所有内部服务。「先猜再读」第三问的答案是：零信任模型下**内网也不例外**——恰恰因为它把「位置」当成了「信任」，攻击者攻破一台内网机器后就能横向移动、全域扫荡（很多重大入侵的起点只是一封钓鱼邮件）。

**零信任的核心原则：Never trust, always verify.**

- 没有「内网可信」的概念——每个服务独立认证。
- 每次请求都验证身份、设备状态、权限。
- 哪怕在办公室 WiFi 上，访问内部 API 也要 **mTLS**（双向 TLS）：不只服务器出证书，客户端也出——15.4 的证书链在两个方向各跑一遍。
- 访问控制基于身份而非网络位置：你是谁、用什么设备，决定你能看什么。

```
传统模型:
  Internet → [防火墙] → 内网（一切可信）

零信任模型:
  Internet → [认证网关] → 服务A（独立认证）
                        → 服务B（独立认证）
                        → 服务C（独立认证）
  服务与服务之间也要 mTLS
```

零信任与本章其他机制的关系：防火墙管「端口到端口」，零信任管「身份到身份」；VPN 解决「安全进网」，零信任解决「进来之后」。它们不是替代关系，是纵深的不同层。

## 22.6 编程实践：iptables 最小可用防火墙

```bash
#!/bin/bash
# 简单的 iptables 防火墙配置
# 需要 root 权限，立即生效——生产环境先在可回滚的会话中测试

# 清空现有规则
iptables -F
iptables -X

# 默认策略：入站丢弃，出站放行——「默认拒绝」的起点
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# 允许回环接口（localhost 通信）
iptables -A INPUT -i lo -j ACCEPT

# 允许已建立连接及其关联连接的返回流量
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 允许 SSH，限速防暴力破解（22.2 状态检测 + 12.5 限速的结合）
iptables -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW \
  -m limit --limit 3/min --limit-burst 5 -j ACCEPT

# 允许 HTTP 和 HTTPS
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# 允许 ICMP echo（ping），限速——注意别全禁，否则 5.4 的 PMTUD 会被掐断
iptables -A INPUT -p icmp --icmp-type echo-request \
  -m limit --limit 1/sec -j ACCEPT

# 记录被丢弃的包（审计用）
iptables -A INPUT -m limit --limit 5/min -j LOG \
  --log-prefix "iptables-dropped: " --log-level 4

echo "Firewall rules applied."
```

三个实战教训藏在注释里：ICMP 不能全禁（PMTUD 依赖它，5.4 的黑洞就是教训）；规则顺序即优先级（先放行 ESTABLISHED 再考虑 NEW）；改动防火墙务必保留一个已连接的 SSH 会话——默认拒绝生效的瞬间，最容易锁死自己。

## 22.7 抓包实践：IPsec 隧道内外的报文对比

```bash
# 未启用 IPsec 时抓明文 HTTP
tshark -i eth0 -f "tcp port 80" -c 5 -V | head -30
# 能看到完整的 HTTP 请求内容

# 启用 IPsec 隧道后抓相同流量
tshark -i eth0 -f "esp" -c 5 -V
# 只能看到 ESP 封装：协议号 50
# ESP Header: SPI: 0x12345678, Sequence: 1
# ESP Payload: [encrypted data - 不可读]
```

隧道外抓包只剩 ESP 协议号与密文——内部跑的是 HTTP、SSH 还是别的协议完全不可知。对照 18.6 的 SMTP 明文/加密对比，两个实验说的是同一件事：**加密改变的不是内容，而是旁观者的世界**。想解密看内容，需要拿到 IPsec 的会话密钥（同 15.9 的 SSLKEYLOGFILE 思路——只解自己的密）。

## 本章小结

- 威胁模型先行：窃听、篡改、重放、DDoS 加侧信道——明确「防谁、防什么」再选工具，否则只是堆名词。
- 防火墙三层递进：包过滤看 IP 头、状态检测看连接表、WAF 看 HTTP 语义——越深越懂，也越贵。
- 「先猜再读」第一问的答案：端口开了路就是通的，包过滤拦不住应用层攻击——纵深防御由此而来。
- IPsec 隧道模式双层 IP 头：明文外层管路由、密文内层护一切；ESP 是主力，AH 只有认证。
- WireGuard 的启示：固定算法、砍掉协商、4000 行代码——少即是安全，与 TLS 1.3、QUIC 同一种哲学。
- ACME 短周期证书把安全变成基础设施问题：90 天有效期逼出自动化，续期监控是标配。
- 零信任把信任锚从「网络位置」换成「身份与设备」：mTLS 双向验证，内网也不例外。
- iptables 三戒：默认拒绝保会话、ICMP 别全禁（PMTUD）、规则顺序即优先级。
