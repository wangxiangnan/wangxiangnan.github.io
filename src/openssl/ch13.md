# 第13章：HTTPS 上线：从本地到 nginx

> [!TIP] Part 3: CA 与 TLS 实战篇（实战篇）
> 万事俱备的一章：证书会签（第10章）、链会铺（第11章）、探针在手（第12章）。本章把 api 与内网三服务的 HTTPS 一次性配齐——nginx 配置、mTLS 服务互认、公网证书的真实获取流程。

云笔记的证书台账此刻应该长这样：内部 CA 签了 auth / notify / sync 三张服务器证书，到期监控挂在 cron 里，公网 api 的证书则是另一条路线（本章 13.4 讲它怎么来）。零件全齐，本章做集成：把这些证书装进真实的 web 服务，让 HTTPS 从「实验」变成「生产」。

## 13.1 nginx 的最小 HTTPS 配置

auth 服务的 nginx 配置，从最小可用版起步：

```nginx
# /etc/nginx/sites-available/auth
server {
    listen 80;
    server_name auth.cloudnote.internal;
    return 301 https://$host$request_uri;      # 明文流量一律跳转加密通道
}

server {
    listen 443 ssl;
    http2 on;                             # nginx 1.25.1+ 写法；老版本在 listen 行写 http2
    server_name auth.cloudnote.internal;

    ssl_certificate     /etc/cloudnote/auth/tls.crt;     # 证书（叶子；公网场景放 fullchain）
    ssl_certificate_key /etc/cloudnote/auth/tls.key;     # 私钥（权限必须是 600）

    ssl_protocols TLSv1.2 TLSv1.3;                       # 协议下限 1.2
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    location / {
        proxy_pass http://127.0.0.1:8080;                # TLS 在 nginx 终结，后端走内网明文
    }
}
```

四个容易踩坑的位置，逐一交代：

- **证书与私钥是两条配置**，且文件内容必须配对——配错对就是第6章的 `key values mismatch`，用公钥指纹法两秒钟定位。
- **内网两级 CA 场景配叶子证书即可**（没有中间层）；对接公网 CA 时这里要放 **fullchain**（叶子 + 中间，第11章组装法）——放错成裸叶子，Windows 系的 Chrome/Edge 会靠 AIA 自动补链照样能开，Firefox（不拉 AIA）、curl 和 Java 却报错，又一个经典悬案在此封口。
- **TLS 在 nginx 终结，后端走内网 HTTP** 是最常见的架构（TLS termination）。nginx 到后端这段要靠内网隔离与防火墙保护；若内网也不可信，上 mTLS（13.3）或全程加密。
- **私钥文件权限**：`chmod 600`、属主与 nginx worker 一致——第5章的两道锁在部署环节的延续。

协议下限定在 1.2 而不是更低，是行业共识而非个人口味：TLS 1.0 / 1.1 已于 2020 年被主流浏览器与 CA 体系正式退役（POODLE、BEAST 等一串历史攻击把老协议打穿），现代客户端全部支持 1.2 起步——**对老协议的「兼容」服务的是攻击者，不是用户**。

改完先测再重载：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

`-t` 通过才 reload——`reload` 是平滑换配置（老连接不断），而配置错误时 nginx 会拒绝加载新配置并沿用旧配置继续服务，所以测试要养在 reload 之前；证书续期后的轮换脚本也应该是「换文件 → `-t` → reload」三连，而不是裸重启。

## 13.2 上线前体检：配置检查清单

配置写完不等于上线完成。第12章的探针此刻全员上岗，六项体检对着打勾：

| 检查项 | 命令 | 合格线 |
| ---- | ---- | ---- |
| 总裁决 | `s_client ... \| grep "Verify"` | `Verification: OK` |
| 链张数 | `s_client -showcerts ... \| grep -c BEGIN` | 符合拓扑（内网 1 张，公网 2 张起） |
| SAN 覆盖 | `... \| openssl x509 -noout -ext subjectAltName` | 含服务域名 |
| 协议下限 | `s_client -tls1_2` 成功、`-tls1` 失败 | 该通的通，该拒的拒 |
| 到期余量 | `./cert-expiry.sh auth.cloudnote.internal` | 大于 21 天 |
| 明文跳转 | `curl -sI http://auth... \| head -1` | `301` 且 Location 指向 https |

全绿才切换流量。这套体检动作建议原样写进上线工单模板——它就是第12章「先体检再动刀」的落地形式。

体检不及格时按症状分流，每一项都有章节可回：

| 症状 | 去向 |
| ---- | ---- |
| `unable to get local issuer certificate` | 第11章：链没铺全或信任库没导入 |
| 域名不匹配（`hostname mismatch`） | 第8/9章：SAN 与访问地址对不上 |
| `handshake failure` | 第12章：协议/套件被拒，用 `-tls1_2` 与 `-msg` 定位 |
| 到期余量不足 21 天 | 第12章：先手动续，再查监控为何没早告警 |
| `key values mismatch` | 第6章：证书与私钥配错对，指纹法定位 |

## 13.3 mTLS：服务间互认

单向 TLS 有个盲区：服务器验了客户端的证书（信任链），客户端却对服务器一无所知——浏览器场景无所谓（用户不持证书），但**服务间调用**恰恰相反：auth 需要确认「调我的是 notify 本尊，不是内网里摸进来的任何人」。双向 TLS（mTLS，mutual TLS）补上这一环：客户端也持证书，握手时双方互验。

先在试验台上玩一次最小 mTLS（`s_server` 的 `-Verify` 大写表示**强制**客户端出示证书）：

```bash
# 服务端：-CAfile 指定「我信谁签发的客户端证书」
openssl s_server -www -accept 8443 \
  -cert auth.crt -key auth-key.pem \
  -Verify 1 -CAfile client-ca.crt

# 客户端：出示自己的证书与私钥（-CAfile 用来校验对面的服务器证书）
openssl s_client -connect localhost:8443 \
  -cert notify-client.crt -key notify-client-key.pem \
  -CAfile root.crt
```

```text
depth=1 C = CN, O = CloudNote, CN = CloudNote Internal Root CA
depth=0 C = CN, O = CloudNote, CN = auth.cloudnote.internal
...
Acceptable client certificate CA names
C = CN, O = CloudNote, CN = CloudNote Client CA
...
Verification: OK
Verify return code: 0 (ok)
```

服务端没有客户端证书的连接会直接被拒（`peer did not return a certificate`）。落到 nginx，mTLS 只多两行：

```nginx
    ssl_client_certificate /etc/cloudnote/auth/client-ca.crt;   # 信任哪个 CA 签的客户端证书
    ssl_verify_client on;                                       # 强制校验
```

工程实践上，客户端证书通常由**另一张专用 CA**（Client CA）签发，与服务器证书的 CA 分开——「谁签服务器、谁签客户端」职责分离，撤销某类客户端不牵连服务器证书。云笔记的约定：内部 CA 追加一个 Client CA，notify / sync 调 auth 时各持一张客户端证书；证书有效期 90 天、每 60 天重签（沿用第10章的节奏）。

Client CA 与客户端证书的产出，就是第10章配方换个扩展文件——EKU 从 `serverAuth` 换成 `clientAuth`：

```bash
# 1. 追加一张客户端 CA（照 10.2 的配方，CN 换名即可）
openssl req -x509 -new -key client-ca-key.pem \
  -subj "/C=CN/O=CloudNote/CN=CloudNote Client CA" -days 3650 -sha256 \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:0" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" -out client-ca.crt

# 2. 客户端证书的扩展文件：EKU 是 clientAuth
cat > notify-client.ext <<EOF
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature
extendedKeyUsage = clientAuth
subjectAltName = DNS:notify.cloudnote.internal
EOF

# 3. 签发流程与 10.3 完全相同
openssl x509 -req -in notify-client.csr -CA client-ca.crt \
  -CAkey client-ca-key.pem -CAcreateserial -days 90 -sha256 \
  -extfile notify-client.ext -out notify-client.crt
```

服务端 `-CAfile client-ca.crt`、客户端揣着 `notify-client.crt`——第10章的签发流水线在这里原样复用，只是证书的「岗位说明」从 serverAuth 换成了 clientAuth。

> [!NOTE] mTLS 不是万能药
> mTLS 解决「服务间身份互认」，不解决「服务内部被攻破后横向移动」——拿到 notify 机器 root 权限的攻击者顺手也就拿到了它的客户端私钥。mTLS 是纵深防御的一层，不是全部；密钥落盘的机器越少越好（网关统一持有证书、后端裸内网是另一种常见取舍）。

> [!WARNING] 公网 CA 的配额不是无限的
> Let's Encrypt 对每个域名每周的签发次数有配额（当前「每个注册域名每周 5 张」量级），写循环脚本反复签发会撞墙且要等一周冷却。调试期用 `--staging` 参数走测试环境（签出的是不受信任的测试证书，只验流程）；流程通了再切正式签发。这个纪律和第4章「不在生产环境试命令」同源：**自动化前先在沙箱里把流程跑顺**。

## 13.4 公网证书怎么来：Let's Encrypt 一瞥

内网证书自产自销，公网 api 的证书必须由公共 CA 签发——流程靠 ACME 协议（Automatic Certificate Management Environment）自动化，事实标准工具是 certbot。值得先建立认知：**certbot 干的每一步，都是你第9、10章已经会做的事**——生成密钥、生成 CSR、向 CA 证明域名控制权、收下签好的证书、按时续期；它只是把这套流程对准了公共 CA 并全自动执行：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d api.cloudnote.example
```

certbot 会：验证你对该域名的控制权（HTTP-01 挑战：在站点放一个验证文件让 CA 来读；或 DNS-01 挑战：往 DNS 加一条 TXT 记录）→ CA 核验通过后签发 → 自动改好 nginx 配置 → 装上定时续期（90 天有效期，证书剩 30 天时自动换新）。产物路径：

```text
/etc/letsencrypt/live/api.cloudnote.example/
├── fullchain.pem    ← 就是第11章组装的「叶子+中间」——nginx 直接可用
└── privkey.pem      ← 私钥，权限 600
```

两种挑战方式各有地盘：

| 挑战 | 原理 | 适用 |
| ---- | ---- | ---- |
| HTTP-01 | 在 `http://域名/.well-known/acme-challenge/` 放验证文件，CA 来读 | 有公网 80 端口的常规站点 |
| DNS-01 | 往 `_acme-challenge.域名` 加一条 TXT 记录，CA 查 DNS | 无法开放 80 端口、**通配符证书**、内网域名 |

通配符证书只认 DNS-01——CA 没法「打开 `*.example.com` 这个网页」来验证，只能问 DNS。续期是全自动的：

```text
$ sudo certbot renew --dry-run        # --dry-run 用测试环境演练，不占正式配额
Saving debug log to /var/log/letsencrypt/letsencrypt.log
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Congratulations, all simulated renewals succeeded.
```

到这里全书的知识闭环成型：**certbot 没有任何魔法**，你拆开过它的每一步。以后看到 `certbot renew`、看到 `/etc/letsencrypt/live/` 目录，你看到的不是黑盒，是第9-11章的自动化流水线。

## 13.5 实验：内网三服务 HTTPS 全绿

综合上线演练（实验环境无 DNS，用 hosts 模拟域名；为省事只用一台 s_server 客串 auth，notify / sync 换域名重跑——重点是体检动作本身，不是三台服务同时在场）：

```bash
# 1. 三台服务的证书早已就位（第10章 10.6），本地模拟三域名
echo "127.0.0.1 auth.cloudnote.internal notify.cloudnote.internal sync.cloudnote.internal" \
  | sudo tee -a /etc/hosts

# 2. 逐服务套用 13.1 的 nginx 配置（或用 s_server 快速起一个）
openssl s_server -www -accept 4433 \
  -cert auth.crt -key auth-key.pem &

# 3. 体检复跑（第12章的六个动作）
echo | openssl s_client -connect auth.cloudnote.internal:4433 \
  -servername auth.cloudnote.internal -CAfile root.crt 2>/dev/null | grep "Verify"

# 4. 逐个体检 notify / sync（换域名重跑即可）
for D in notify sync; do
  echo | openssl s_client -connect $D.cloudnote.internal:4433 \
    -servername $D.cloudnote.internal -CAfile root.crt 2>/dev/null | grep "Verify"
done
```

验收标准三条：三个服务的体检六项全绿；`curl https://auth.cloudnote.internal:4433/healthz --cacert root.crt` 返回 200；mTLS 演示中「无证书客户端被拒、持证客户端 OK」两个画面都亲眼见过。实验做完收尾 `kill %1`。

mTLS 的负向验收值得一做（用 13.3 的 s_server 试验台）：

```bash
# 不带客户端证书去连 -Verify 1 的服务端
echo | openssl s_client -connect localhost:8443 2>/dev/null | head -3
```

```text
...
ssl handshake failure
```

「该拒的拒了」与「该通通了」合起来才是 mTLS 的完整验收——单看绿灯验收，你永远不知道拒绝路径是不是也配对了。这个方法论和第7章签名的篡改演练一脉相承：**安全机制的验收必须包含负向用例**。

## 本章小结

- nginx HTTPS 最小配置四要素：`listen 443 ssl`、`ssl_certificate`（公网用 fullchain）、`ssl_certificate_key`（权限 600）、`ssl_protocols TLSv1.2 TLSv1.3`
- 80 跳 443 是明文流量的收容所；上线前六项体检（裁决/链/SAN/协议/到期/跳转）全绿再切流量
- mTLS 给服务间调用补上双向身份：客户端持证书、服务器 `-Verify`/`ssl_verify_client` 强制互验；客户端证书用专用 Client CA 签发，职责分离
- 公网证书 = ACME 自动化：certbot 干的就是你第9-11章学的全套（密钥、CSR、域名核验、签发、续期）——没有黑盒
- TLS termination 让加解密收口在网关，后端内网明文需靠隔离或 mTLS 兜底
- 通配符证书只认 DNS-01 挑战；公网 CA 配额有限，调试用 `--staging` 沙箱先跑通流程
- 「接手 HTTPS 服务」的肌肉记忆：先体检再动刀，改完 `nginx -t` 再 reload
