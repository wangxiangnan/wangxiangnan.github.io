## 17.1 为什么要在命令行搭 Web 服务？

你可能会问：搭网站不是用宝塔面板或者 Docker 就行了吗？没错，但你知道宝塔和 Docker 底层在干什么吗？它们在操作 Nginx/Apache 的配置文件。如果你不理解底层的 Web 服务器，出了问题你就只能"重启试试"——这就像不会游泳的人穿着救生圈下水，能用但心里不踏实。

**本章目标：** 从零搭建一个生产级的 Web 服务器，包括静态文件服务、反向代理、HTTPS 证书、负载均衡——全部在命令行完成。

## 17.2 HTTP 基础：你得先懂"协议"

```bash
# HTTP 请求/响应模型（浏览器和服务器之间的"对话"）
# 请求：客户端 → 服务器
# GET /index.html HTTP/1.1         ← 请求行（方法 + 路径 + 协议）
# Host: example.com                ← 请求头
# User-Agent: curl/7.81.0
# Accept: */*
#
# 响应：服务器 → 客户端
# HTTP/1.1 200 OK                  ← 状态行（协议 + 状态码 + 描述）
# Content-Type: text/html          ← 响应头
# Content-Length: 1234
#
# <html>...</html>                 ← 响应体

# 常见 HTTP 状态码：
# 200 OK          → 成功
# 301 Moved       → 永久重定向
# 302 Found       → 临时重定向
# 304 Not Modified → 缓存命中
# 400 Bad Request → 请求格式错误
# 401 Unauthorized → 未认证
# 403 Forbidden   → 无权限
# 404 Not Found   → 找不到
# 500 Internal Server Error → 服务器内部错误
# 502 Bad Gateway → 反向代理的上游服务器挂了
# 503 Service Unavailable → 服务不可用
# 504 Gateway Timeout → 反向代理的上游超时

# 用 curl 看 HTTP 原始请求/响应
curl -v http://example.com 2>&1 | head -20
# -v 显示详细的请求和响应过程
```

## 17.3 Nginx 安装与基本配置

```bash
# 安装 Nginx
sudo apt update
sudo apt install nginx -y

# 启动并设置开机自启
sudo systemctl start nginx
sudo systemctl enable nginx

# 查看运行状态
sudo systemctl status nginx

# 验证配置文件语法（修改配置后的必做步骤！）
sudo nginx -t
# nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
# nginx: configuration file /etc/nginx/nginx.conf test is successful

# 重新加载配置（不中断服务）
sudo systemctl reload nginx
# 或
sudo nginx -s reload

# Nginx 目录结构
# /etc/nginx/
# ├── nginx.conf          # 主配置文件
# ├── sites-available/    # 所有站点配置（"草稿箱"）
# ├── sites-enabled/      # 启用的站点（软链接到 available）
# ├── conf.d/             # 额外的配置片段
# ├── snippets/           # 可复用的配置片段
# └── mime.types          # MIME 类型映射
#
# /var/www/               # 默认的网站根目录
# /var/log/nginx/         # Nginx 日志
#   ├── access.log        # 访问日志
#   └── error.log         # 错误日志
```

## 17.4 虚拟主机（Virtual Host）

```bash
# 虚拟主机：一台服务器托管多个网站
# 每个网站有自己的域名、目录和配置

# 创建网站目录
sudo mkdir -p /var/www/example.com
sudo mkdir -p /var/www/blog.example.com

# 创建测试页面
echo '<h1>Welcome to example.com!</h1>' | sudo tee /var/www/example.com/index.html
echo '<h1>Welcome to my blog!</h1>' | sudo tee /var/www/blog.example.com/index.html

# 设置目录权限
sudo chown -R www-data:www-data /var/www/example.com
sudo chown -R www-data:www-data /var/www/blog.example.com
sudo chmod -R 755 /var/www/

# 创建虚拟主机配置
sudo nano /etc/nginx/sites-available/example.com
# server {
#     listen 80;
#     listen [::]:80;
#     server_name example.com www.example.com;
#     root /var/www/example.com;
#     index index.html index.htm;
#
#     location / {
#         try_files $uri $uri/ =404;
#     }
#
#     # 自定义错误页面
#     error_page 404 /404.html;
#     error_page 500 502 503 504 /50x.html;
#
#     # 日志
#     access_log /var/log/nginx/example.com.access.log;
#     error_log /var/log/nginx/example.com.error.log;
# }

sudo nano /etc/nginx/sites-available/blog.example.com
# server {
#     listen 80;
#     server_name blog.example.com;
#     root /var/www/blog.example.com;
#     index index.html;
#
#     location / {
#         try_files $uri $uri/ =404;
#     }
# }

# 启用站点（创建软链接）
sudo ln -s /etc/nginx/sites-available/example.com /etc/nginx/sites-enabled/
sudo ln -s /etc/nginx/sites-available/blog.example.com /etc/nginx/sites-enabled/

# 删除默认站点（可选）
sudo rm /etc/nginx/sites-enabled/default

# 测试配置并重新加载
sudo nginx -t && sudo systemctl reload nginx

# 本地测试（不修改 DNS 的情况下）
# 在客户端的 /etc/hosts 中添加：
# 203.0.113.50 example.com www.example.com blog.example.com
curl -H "Host: example.com" http://localhost
curl -H "Host: blog.example.com" http://localhost
```

## 17.5 Nginx 反向代理

```bash
# 反向代理：Nginx 接收请求，转发给后端应用服务器
# 就像餐厅的服务员——客人（浏览器）不直接和厨师（后端）说话

# 基本反向代理配置
sudo nano /etc/nginx/sites-available/app
# server {
#     listen 80;
#     server_name app.example.com;
#
#     location / {
#         proxy_pass http://localhost:3000;   # 后端应用地址
#         proxy_http_version 1.1;
#         proxy_set_header Host $host;
#         proxy_set_header X-Real-IP $remote_addr;
#         proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
#         proxy_set_header X-Forwarded-Proto $scheme;
#
#         # WebSocket 支持
#         proxy_set_header Upgrade $http_upgrade;
#         proxy_set_header Connection "upgrade";
#     }
#
#     # API 路径单独转发到不同的后端
#     location /api/ {
#         proxy_pass http://localhost:8080/;
#         proxy_set_header Host $host;
#     }
#
#     # 静态文件直接由 Nginx 处理（不经过后端）
#     location /static/ {
#         alias /var/www/app/static/;
#         expires 30d;
#     }
# }

# 路径匹配规则
# location = /exact       → 精确匹配（最高优先级）
# location ^~ /prefix     → 前缀匹配（优先于正则）
# location ~ \.php$       → 正则匹配（区分大小写）
# location ~* \.jpg$      → 正则匹配（不区分大小写）
# location /prefix        → 前缀匹配（最低优先级）

# 超时设置
# proxy_connect_timeout 10s;   # 连接后端超时
# proxy_read_timeout 60s;      # 读取后端响应超时
# proxy_send_timeout 60s;      # 发送请求到后端超时
```

## 17.6 Nginx 负载均衡

```bash
# 当一台后端服务器扛不住时，用多台分担压力
# Nginx 可以做"调度员"，把请求分给不同的后端

# 负载均衡配置
sudo nano /etc/nginx/conf.d/upstream.conf
# # 定义后端服务器组
# upstream backend {
#     # 默认轮询（Round Robin）
#     server 10.0.0.10:8080 weight=3;   # 权重 3（性能好的多分配）
#     server 10.0.0.11:8080 weight=2;
#     server 10.0.0.12:8080 weight=1;
#     server 10.0.0.13:8080 backup;      # 备用（其他都挂了我才上）
#
#     # 健康检查
#     # max_fails=3 → 连续失败 3 次标记为不可用
#     # fail_timeout=30s → 30 秒后重试
#     server 10.0.0.14:8080 max_fails=3 fail_timeout=30s;
# }
#
# # IP Hash 负载均衡（同一 IP 总是访问同一后端，适合有 Session 的应用）
# upstream backend_session {
#     ip_hash;
#     server 10.0.0.10:8080;
#     server 10.0.0.11:8080;
#     server 10.0.0.12:8080;
# }
#
# # Least Connections（最少连接数，分给最闲的后端）
# upstream backend_least {
#     least_conn;
#     server 10.0.0.10:8080;
#     server 10.0.0.11:8080;
# }

# 在 server 块中使用上游
# server {
#     listen 80;
#     server_name app.example.com;
#     location / {
#         proxy_pass http://backend;
#     }
# }

# 三种负载均衡策略对比：
# 轮询（默认）  → 简单平均，适合无状态服务
# IP Hash       → 同 IP 同后端，适合有 Session 的服务
# Least Conn    → 给最闲的后端，适合请求处理时间差异大的场景
```

## 17.9 Nginx vs Apache 对比

```bash
# | 特性           | Nginx                    | Apache                   |
# |---------------|--------------------------|--------------------------|
# | 架构           | 事件驱动（异步非阻塞）      | 进程/线程驱动              |
# | 静态文件性能     | 更快（低内存消耗）          | 较慢                      |
# | 动态内容        | 需要 FastCGI/uWSGI        | 内置 mod_php 等模块        |
# | 配置风格        | 集中式配置                 | 分布式 .htaccess          |
# | 内存消耗        | 低                       | 高                        |
# | 并发连接        | 数万连接轻松               | 数百到数千                  |
# | 模块管理        | 编译时加载                 | 运行时动态加载              |
# | 社区生态        | 现代、增长快               | 成熟、历史悠久              |
#
# 选择建议：
# - 静态文件/反向代理/高并发 → Nginx
# - 共享主机/.htaccess/传统 PHP → Apache
# - 现代最佳实践 → Nginx 做前端反向代理 + 后端应用服务器
```

```bash
sudo nano /etc/nginx/nginx.conf

#     text/javascript
#     application/json
#     application/javascript
```

```bash
# Nginx 可以做反向代理缓存，加速后端响应

# proxy_cache_path /var/cache/nginx levels=1:2 \

#   use_temp_path=off;

# location /api/ {
#     proxy_pass http://backend;
#     proxy_cache my_cache;
#     proxy_cache_valid 200 10m;       # 200 响应缓存 10 分钟
#     proxy_cache_valid 404 1m;        # 404 响应缓存 1 分钟
#     proxy_cache_use_stale error timeout updating;  # 后端挂了用旧缓存
#     add_header X-Cache-Status $upstream_cache_status;  # 调试用
# }

# 缓存状态说明（看 X-Cache-Status 响应头）：
# HIT     → 缓存命中（从缓存返回）
# MISS    → 缓存未命中（从后端获取并缓存）
# EXPIRED → 缓存过期（从后端重新获取）
# STALE   → 使用过期缓存（后端不可用时的降级策略）
# BYPASS  → 绕过缓存

# 测试缓存效果
curl -I http://localhost/api/data
# X-Cache-Status: MISS    ← 第一次，未缓存
curl -I http://localhost/api/data
# X-Cache-Status: HIT     ← 第二次，命中缓存！

# 清除缓存
sudo rm -rf /var/cache/nginx/*
sudo systemctl reload nginx
```

## 本章小结

Web 服务器是互联网的基础设施。Nginx 凭借高性能和简洁的配置成为现代首选，但 Apache 在传统场景仍然有用。虚拟主机让你一台服务器跑多个网站，反向代理把请求转发给后端应用，SSL 证书保障通信安全。记住：永远先 `nginx -t` 再 `reload`。

502 Bad Gateway：反向代理的上游服务器挂了（连不上后端）；504 Gateway Timeout：上游超时（连上了但后端迟迟不响应）。两者都说明问题多半在后端应用，而不是 Nginx 本身。见 17.2 节状态码表。

</details>

**2. 写出命令：修改 Nginx 配置后的标准两步（验证语法 + 不中断服务重载）。为什么必须先做第一步？**

<details>
<summary>点击查看答案</summary>

```bash
sudo nginx -t && sudo systemctl reload nginx
```

配置有语法错误时直接 reload 会导致 Nginx 停止服务；`nginx -t` 先验证语法，通过了再重载，reload 不中断现有连接。这是 17.17 节坑 1 的保命习惯。见 17.3 节。

</details>

**3. sites-available 和 sites-enabled 各是什么角色？写出启用 example.com 站点的命令。**

<details>
<summary>点击查看答案</summary>

sites-available 是所有站点配置的"草稿箱"，sites-enabled 只放已启用站点的软链接。启用：

```bash
sudo ln -s /etc/nginx/sites-available/example.com /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

禁用就删掉对应软链接，配置文件仍留在草稿箱里。见 17.4 节。

</details>

**4. 不改 DNS，如何在本地验证虚拟主机按域名分流？写出命令。**

<details>
<summary>点击查看答案</summary>

```bash
curl -H "Host: example.com" http://localhost
curl -H "Host: blog.example.com" http://localhost
```

`-H` 手动指定 Host 请求头，Nginx 按 server_name 匹配到不同站点；也可以在客户端 /etc/hosts 里把域名指到服务器 IP 再直接访问。见 17.4 节。

</details>

**5. 预测：`location /api/ { proxy_pass http://localhost:8080/; }`，请求 /api/users 到达后端时是什么路径？把 proxy_pass 末尾的 / 去掉呢？**

<details>
<summary>点击查看答案</summary>

带末尾 /：后端收到 /users——proxy_pass 带 URI 时，请求中匹配 location 的前缀（/api/）被替换掉。去掉 /：后端收到 /api/users——保留原始 URI。末尾斜杠决定"替换还是保留"，是反向代理最常见的路径坑。见 17.5 节与 17.17 节坑 4。

</details>

**6. 三种负载均衡策略各适合什么场景？backup 服务器什么时候才接流量？**

<details>
<summary>点击查看答案</summary>

轮询（默认）：简单平均，适合无状态服务；ip_hash：同一 IP 固定访问同一后端，适合有 Session 的服务；least_conn：分给最闲的后端，适合请求处理时间差异大的场景。backup 平时挂空不接流量，其他服务器全挂了才顶上；weight 则决定轮询中的分配比例（3:2:1 即每 6 个请求约分 3/2/1 个）。见 17.6 节与图 17-3。

</details>

**7. 写出命令：用 Certbot 为 example.com 和 www.example.com 申请证书并自动配置 Nginx；如何测试自动续期？**

<details>
<summary>点击查看答案</summary>

```bash
sudo certbot --nginx -d example.com -d www.example.com
sudo certbot renew --dry-run
```

`--nginx` 插件会自动修改 Nginx 配置添加 SSL 指令，证书存在 /etc/letsencrypt/live/example.com/；Certbot 安装时已添加 cron/systemd timer 每 12 小时检查续期，`renew --dry-run` 模拟续期验证流程是否可用。见 17.7 节与 17.17 节坑 5。

</details>

**8. Nginx 和 Apache 的架构本质区别是什么？高并发静态文件/反向代理场景选哪个？**

<details>
<summary>点击查看答案</summary>

Nginx 是事件驱动（异步非阻塞），低内存就能扛数万并发连接；Apache 是进程/线程驱动，并发数百到数千、内存消耗更高。高并发静态文件/反向代理选 Nginx；共享主机、依赖 .htaccess 或传统 mod_php 的场景选 Apache。现代最佳实践是 Nginx 做前端反向代理 + 后端应用服务器。见 17.9 节。

</details>

**9. SPA 前端部署为什么用 `try_files $uri $uri/ /index.html` 而不是 `=404`？**

<details>
<summary>点击查看答案</summary>

SPA 的路由由前端 JS 处理：用户直接访问 /user/123 时，服务器上并没有这个文件，`=404` 会真的返回 404。`try_files $uri $uri/ /index.html` 先找真实文件和目录，找不到就兜底返回 index.html，让前端路由接管。带 hash 的静态资源（/assets/）则可以 expires 1y 长期缓存。见 17.10 节。

</details>

**10. 预测：配置了 proxy_cache 后，连续两次 `curl -I http://localhost/api/data`，X-Cache-Status 响应头分别是什么？STALE 又代表什么？**

<details>
<summary>点击查看答案</summary>

第一次 MISS（未命中，从后端获取并写入缓存），第二次 HIT（命中缓存直接返回）。STALE 表示后端不可用时降级使用了过期缓存——对应配置 `proxy_cache_use_stale error timeout updating`。见 17.12 节。

</details>

**11. 写出命令：从 access.log 统计访问量最高的 Top 10 URL。**

<details>
<summary>点击查看答案</summary>

```bash
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
```

日志第 7 列是请求路径：awk 取列 → sort 排序 → uniq -c 计数 → sort -rn 按次数降序 → head -10 取前十。把 $7 换成 $1 就是 Top IP，换成 $9 就是状态码分布。见 17.13 节。

</details>

**12. 站点返回 403 Forbidden，最常见的原因是什么？写出修复命令。**

<details>
<summary>点击查看答案</summary>

最常见是文件权限问题：Nginx 以 www-data 用户运行，读不了网站目录。修复：

```bash
sudo chown -R www-data:www-data /var/www/mysite
sudo chmod -R 755 /var/www/mysite
```

若权限没问题，再查 SELinux/AppArmor 是否拦截（`sudo aa-status | grep nginx`）。见 17.17 节坑 2、坑 3。

</details>
