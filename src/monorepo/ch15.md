## 15.1 Monorepo 性能优化

### 15.1.1 选择性构建（Selective Build）

这是 Monorepo 性能优化的第一优先级。我们在 Ch14 已经详细介绍了 `--filter` 参数，这里补充几个进阶技巧：

```bash
# 在 turbo.json 中定义全局的 filter 默认行为
{
  "globalDependencies": [
    ".env",
    "tsconfig.base.json"
  ]
}
```

**`globalDependencies` 的作用**：这些文件的变更会使**所有包**的缓存失效。比如修改了 `tsconfig.base.json`（所有包的 TypeScript 配置基类），那么所有包的 `typecheck` 和 `build` 任务都需要重新运行，因为编译选项可能已经改变了。

### 15.1.2 增量编译（Incremental Compilation）

TypeScript 支持增量编译，只重新编译变更的文件：

```json
// packages/shared/tsconfig.json
{
  "extends": "@myrepo/tsconfig/base.json",
  "compilerOptions": {
    "composite": true,        // 启用项目引用模式
    "incremental": true,      // 启用增量编译
    "tsBuildInfoFile": "./dist/.tsbuildinfo",
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"]
}
```

配合 TypeScript 的 Project References：

```json
// apps/api/tsconfig.json
{
  "extends": "@myrepo/tsconfig/base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "references": [
    { "path": "../../packages/shared" },
    { "path": "../../packages/database" }
  ],
  "include": ["src/**/*"]
}
```

**为什么 `composite` + `references` 能加速？**

启用后，TypeScript 会将每个包视为独立的编译单元。当 `apps/api` 被编译时，它不会重新编译 `packages/shared` 的源代码，而是直接使用 `packages/shared/dist` 中已有的 `.d.ts` 声明文件。这意味着修改 `apps/api` 的代码不会触发 `packages/shared` 的重新编译。

### 15.1.3 缓存策略矩阵

不同类型的任务应该采用不同的缓存策略：

| 任务类型 | 缓存策略 | 缓存键依赖 | 说明 |
| --------- | --------- | ----------- | ------ |
| `build` | 积极缓存 | inputs + dependencies | 相同输入直接复用产物 |
| `lint` | 积极缓存 | inputs | 代码没变，lint 结果不变 |
| `typecheck` | 积极缓存 | inputs + dependencies | 依赖类型变更时需重跑 |
| `test:unit` | 积极缓存 | inputs + dependencies | 单元测试可缓存 |
| `test:e2e` | 不缓存 | - | E2E 测试依赖运行时环境 |
| `deploy` | 不缓存 | - | 部署必须每次执行 |

```json
// turbo.json — 完整的任务缓存配置
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"],
      "inputs": ["src/**", "package.json", "tsconfig.json"]
    },
    "lint": {
      "inputs": ["src/**", ".eslintrc.*"],
      "outputs": []
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json"],
      "outputs": []
    },
    "test": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "__tests__/**", "*.test.*"],
      "outputs": ["coverage/**"]
    },
    "test:e2e": {
      "cache": false
    },
    "deploy": {
      "cache": false,
      "dependsOn": ["build"]
    }
  }
}
```

**为什么 `inputs` 要精确指定？**

如果 `inputs` 设为 `["**/*"]`（默认值），那么任何文件的变更都会导致缓存失效——包括修改了 README.md 或 .gitignore 这种不影响构建结果的文件。精确指定 `inputs` 可以让缓存在不相关的文件变更时仍然命中。

### 15.1.4 pnpm 层面的优化

```yaml
# .npmrc — pnpm 性能配置
# 使用硬链接而不是复制或符号链接
node-linker=hoisted

# 并行安装（默认已启用）
prefer-frozen-lockfile=true

# 跳过可选依赖的构建脚本（加速安装）
ignore-scripts=false

# 并发网络请求数
network-concurrency=16
```

**关于 `node-linker` 的选择**：pnpm 默认使用隔离的 `node_modules` 结构（通过符号链接），这在 Monorepo 中是最佳实践，因为它能防止幽灵依赖。但某些老旧工具不兼容这种结构，此时可以退而求其次使用 `node-linker=hoisted`（类似 npm 的扁平结构）。不过要注意这会失去幽灵依赖保护。

## 15.2 常见陷阱清单

以下是 Monorepo 开发中最容易踩的坑，每个都附带了原因分析和解决方案。

### 陷阱 1：循环依赖

```
packages/a 依赖 packages/b
packages/b 依赖 packages/a
→ Turborepo 报错：Cycle detected
```

**为什么会发生？** 通常是因为两个包的职责边界不清晰。比如 `shared` 包里引用了 `ui` 包的组件，而 `ui` 包又引用了 `shared` 包的工具函数。

**解决方案：**

```bash
# 检测循环依赖
pnpm turbo build  # Turborepo 会在启动时检测并报错

# 解决方法：提取公共部分到第三个包
# packages/shared → 纯工具函数（不依赖 ui）
# packages/ui → UI 组件（可以依赖 shared）
# packages/shared-ui → 需要同时用到工具函数和 UI 的混合代码
```

### 陷阱 2：幽灵依赖（Phantom Dependencies）

```typescript
// apps/web/src/utils.ts
// 这个 import 能正常工作，但 package.json 中没有声明 lodash 依赖！
import { debounce } from 'lodash';
// 之所以能工作，是因为 lodash 被其他包安装了，
// pnpm 的 hoisting 让它"泄露"到了 web 的 node_modules 中
```

**为什么会发生？** 当使用 `node-linker=hoisted` 或者某些包间接安装了 lodash 时，Node.js 的模块解析算法会沿着 `node_modules` 目录树向上查找，最终找到了别的包安装的 lodash。这在本地开发时"恰好能用"，但在 CI 或生产环境中可能会崩溃。

**解决方案：**

```json
// .npmrc — 强制严格的依赖隔离
public-hoist-pattern[]=*eslint*
# 只提升 ESLint 相关的包（因为 ESLint 插件机制需要）
# 其他包一律不提升
```

```bash
# 使用 pnpm 的 lint 功能检查幽灵依赖
pnpm dlx depcheck

# 或者在 package.json 中显式声明所有直接依赖
# 即使用了别的包的子依赖，也要自己声明
```

### 陷阱 3：构建顺序错误

```
# 错误的 turbo.json 配置
{
  "tasks": {
    "build": {
      // 忘记添加 dependsOn: ["^build"]
      // 结果：apps/web 在 packages/shared 构建完成前就开始构建
      // TypeScript 找不到 @myrepo/shared 的类型声明，编译失败
    }
  }
}
```

**解决方案：**

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],  // ^ 表示"先构建我的依赖"
      "outputs": ["dist/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"],  // 类型检查也需要依赖的构建产物
      "outputs": []
    },
    "lint": {
      // lint 不需要依赖的构建产物
      // 所以不需要 dependsOn
    }
  }
}
```

### 陷阱 4：缓存污染

```bash
# 场景：你在本地设置了 DATABASE_URL=test_db
# 运行了 pnpm turbo test，测试通过，结果被缓存
# 同事拉取代码后运行 pnpm turbo test
# Turborepo 发现缓存命中，跳过了实际测试
# 但同事的环境配置不同，实际运行可能会失败
```

**为什么会发生？** Turborepo 的缓存键是基于 inputs（文件内容）计算的，环境变量不包含在缓存键中。如果测试代码依赖环境变量，那么相同的输入在不同环境下可能产生不同的结果。

**解决方案：**

```json
{
  "tasks": {
    "test": {
      "envMode": "strict",
      // strict 模式下，只有 turbo.json 中显式声明的环境变量
      // 才会影响缓存键。这样你可以明确控制哪些环境变量
      // 需要参与缓存计算。
      "inputs": ["src/**", "__tests__/**"]
    }
  }
}
```

```json
// 或者将关键环境变量声明为 globalDependencies
{
  "globalDependencies": [".env"]
}
```

### 陷阱 5：tsconfig 继承断裂

```json
// packages/ui/tsconfig.json
{
  "extends": "@myrepo/tsconfig/base.json"  // 这个路径在 pnpm 中需要能被解析到
}
```

**为什么会发生？** `extends` 字段中的包名需要在 `node_modules` 中可解析。如果 `packages/tsconfig` 没有被正确链接（比如 `pnpm install` 没运行），TypeScript 会报错找不到配置文件。

**解决方案：**

```json
// packages/tsconfig/package.json — 确保有正确的 exports
{
  "name": "@myrepo/tsconfig",
  "version": "0.0.0",
  "private": true,
  "files": ["base.json", "vue.json", "node.json"],
  "exports": {
    "./base.json": "./base.json",
    "./vue.json": "./vue.json",
    "./node.json": "./node.json"
  }
}
```

```bash
# 如果继承断裂，按以下顺序排查：
# 1. 确认 pnpm install 已运行
pnpm install

# 2. 确认 tsconfig 包在 workspace 协议中
cat apps/web/package.json | grep tsconfig
# 应该看到 "@myrepo/tsconfig": "workspace:*"

# 3. 确认 node_modules 中有正确的符号链接
ls -la node_modules/@myrepo/tsconfig
```

### 陷阱 6：Workspace 协议未正确设置

```json
// 错误：使用固定版本号，发布后依赖的还是旧版本
{
  "dependencies": {
    "@myrepo/shared": "1.0.0"
  }
}

// 正确：使用 workspace 协议，开发时始终链接本地版本
{
  "dependencies": {
    "@myrepo/shared": "workspace:*"
  }
}
```

**为什么 `workspace:*` 是最佳选择？**

在开发阶段，`workspace:*` 意味着直接使用本地包的源代码（通过 pnpm 的符号链接），修改即时生效，无需发布。当 Changesets 发布时，它会自动将 `workspace:*` 替换为实际的版本号（如 `1.2.3`）。

### 陷阱 7：环境变量泄漏到错误的包

```typescript
// packages/shared/src/config.ts
// 危险！shared 包不应该直接读取应用级别的环境变量
export const apiUrl = process.env.VITE_API_URL;  // 在 Node.js 环境中不存在
export const dbUrl = process.env.DATABASE_URL;   // 在前端环境中会暴露
```

**解决方案：**

```typescript
// 正确做法：每个应用自己管理环境变量
// apps/web/src/config.ts
export const config = {
  apiUrl: import.meta.env.VITE_API_URL,
  appTitle: import.meta.env.VITE_APP_TITLE,
};

// apps/api/src/config.ts
import { z } from 'zod';

const envSchema = z.object({
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
  PORT: z.coerce.number().default(3000),
});

export const config = envSchema.parse(process.env);
```

### 陷阱 8：CI 中 pnpm install 未使用 --frozen-lockfile

```yaml
# 错误：可能安装与本地不同版本的依赖
- run: pnpm install

# 正确：确保 CI 安装的版本与本地完全一致
- run: pnpm install --frozen-lockfile
```

**为什么这很重要？** 没有 `--frozen-lockfile`，`pnpm install` 可能会根据 `package.json` 中的版本范围（如 `^1.0.0`）安装更新的小版本。这会导致"在我机器上能跑，CI 上跑不了"的经典问题。

### 陷阱 9：Docker 构建上下文过大

```dockerfile
# 错误：将整个 monorepo 复制进镜像
COPY . /app
# 结果：镜像包含了所有包的源代码、测试文件、文档等
# 镜像大小：2GB+

# 正确：只复制需要的包
COPY packages/shared/ /app/packages/shared/
COPY packages/database/ /app/packages/database/
COPY apps/api/ /app/apps/api/
# 镜像大小：150MB
```

### 陷阱 10：忽视 pnpm-workspace.yaml 的目录匹配

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
  # 忘记添加新的目录，导致新包不被识别为 workspace 包
  # 比如你创建了 tools/ 目录下的包，但这里没有包含
  - 'tools/*'  # 别忘了加！
```

## 15.3 从已有项目迁移到 Monorepo

### 15.3.1 迁移路线图

将一个或多个已有项目迁移到 Monorepo 不是一蹴而就的事情，需要分阶段进行：

```
Phase 1: 准备阶段（1-2 天）
  ├── 分析现有项目的依赖关系
  ├── 确定包划分策略
  └── 创建 monorepo 骨架

Phase 2: 基础设施搭建（2-3 天）
  ├── 初始化 pnpm workspace + Turborepo
  ├── 统一 ESLint / Prettier / TypeScript 配置
  └── 配置 CI/CD 工作流

Phase 3: 渐进式迁移（1-2 周）
  ├── 迁移共享代码到 packages/
  ├── 迁移应用到 apps/
  └── 逐个验证构建和测试

Phase 4: 清理和优化（3-5 天）
  ├── 删除冗余配置
  ├── 优化构建缓存
  └── 团队培训和文档
```

### 15.3.2 迁移步骤详解

**Step 1：创建 Monorepo 骨架**

```bash
# 创建新的 monorepo 目录结构
mkdir my-monorepo && cd my-monorepo
git init

# 初始化 pnpm workspace
cat > pnpm-workspace.yaml << 'EOF'
packages:
  - 'apps/*'
  - 'packages/*'
EOF

# 创建根 package.json
cat > package.json << 'EOF'
{
  "name": "my-monorepo",
  "private": true,
  "scripts": {
    "build": "turbo run build",
    "lint": "turbo run lint",
    "test": "turbo run test"
  }
}
EOF

# 创建目录
mkdir -p apps packages
```

**Step 2：迁移现有项目**

```bash
# 将现有项目移动到 apps/ 或 packages/ 下
mv /path/to/existing-web-app apps/web
mv /path/to/existing-api apps/api
mv /path/to/shared-utils packages/shared

# 清理旧的 node_modules 和 lockfile（重要！）
rm -rf apps/web/node_modules apps/web/pnpm-lock.yaml
rm -rf apps/api/node_modules apps/api/pnpm-lock.yaml
rm -rf packages/shared/node_modules packages/shared/pnpm-lock.yaml

# 更新包名为统一的 scope
# apps/web/package.json → "name": "@myrepo/web"
# apps/api/package.json → "name": "@myrepo/api"
# packages/shared/package.json → "name": "@myrepo/shared"
```

**Step 3：统一内部依赖引用**

```bash
# 将所有内部依赖改为 workspace 协议
# 例如 apps/web/package.json：
# 旧: "my-shared-utils": "^2.1.0"
# 新: "@myrepo/shared": "workspace:*"

# 更新所有 import 语句
# 旧: import { formatDate } from 'my-shared-utils';
# 新: import { formatDate } from '@myrepo/shared';
```

**Step 4：统一构建配置**

```bash
# 创建共享的 TypeScript 配置
mkdir packages/tsconfig
# 将各项目的 tsconfig 公共部分提取到 packages/tsconfig/base.json
# 各项目的 tsconfig 改为 extends 继承
```

**Step 5：安装并验证**

```bash
# 在根目录安装（pnpm 会自动识别 workspace 结构）
pnpm install

# 验证依赖图
pnpm turbo build --dry
# 检查输出的任务执行顺序是否正确

# 运行全量构建
pnpm turbo build

# 运行全量测试
pnpm turbo test
```

### 15.3.3 迁移注意事项

1. **不要一次性迁移所有项目**：先从耦合度最低的项目开始，逐步迁移。每迁移一个项目就验证一次构建和测试。
2. **保持 Git 历史**：使用 `git mv` 而不是 `mv` 来移动文件，这样 Git 能跟踪文件的历史记录。
3. **旧包名做兼容**：如果旧包名被外部项目引用，可以在 `package.json` 中保留旧包名作为 alias，等外部项目也迁移完后再删除。
4. **渐进式统一配置**：不要试图一次性统一所有配置。先让项目能在 Monorepo 中跑起来，再逐步统一 ESLint、TypeScript 等配置。

## 15.4 团队协作规范

### 15.4.1 代码所有权（CODEOWNERS）

在 Monorepo 中，不同团队负责不同的包。`CODEOWNERS` 文件可以自动分配 PR 审查者：

```txt
# .github/CODEOWNERS

# 全局默认审查者
*                           @core-team

# 前端应用
apps/web/                   @frontend-team
packages/ui/                @frontend-team

# 后端应用
apps/api/                   @backend-team
packages/database/          @backend-team

# 共享包需要前后端共同审查
packages/shared/            @frontend-team @backend-team

# 基础设施变更需要 Tech Lead 审批
turbo.json                  @tech-lead
pnpm-workspace.yaml         @tech-lead
.github/                    @tech-lead
```

**为什么需要 CODEOWNERS？**

Monorepo 的一个风险是"谁都能改任何代码"。一个后端开发者可能不小心改了前端组件的样式，或者一个前端开发者可能修改了数据库 schema 而没有意识到影响。CODEOWNERS 确保每次变更都由对应领域的专家审查。

### 15.4.2 PR 审查流程

```yaml
# .github/pull_request_template.md（建议的 PR 模板内容）
## 变更说明
<!-- 描述这次 PR 做了什么，为什么这样做 -->

## 影响的包
<!-- 列出这次 PR 影响了哪些包 -->
- [ ] apps/web
- [ ] apps/api
- [ ] packages/shared
- [ ] packages/ui
- [ ] packages/database

## 变更类型
- [ ] 新功能（feat）
- [ ] Bug 修复（fix）
- [ ] 重构（refactor）
- [ ] 性能优化（perf）
- [ ] 配置变更（chore）

## 测试验证
- [ ] 相关单元测试已添加/更新
- [ ] 本地手动测试通过
- [ ] CI 检查通过

## 截图/录屏（如果是 UI 变更）
```

### 15.4.3 分支策略

推荐适用于 Monorepo 的分支策略：

```
main（生产分支）
  ├── develop（开发分支，所有 feature 合并到这里）
  │   ├── feature/add-user-auth     ← 单个功能分支
  │   ├── feature/redesign-sidebar
  │   └── fix/api-timeout
  ├── hotfix/critical-bug           ← 紧急修复，直接合并到 main
  └── release/v2.0                  ← 发布分支（可选）
```

**分支保护规则：**

```
main:
  - 需要 2 人审查通过
  - 需要 CI 检查通过
  - 禁止直接推送
  - 禁止强制推送

develop:
  - 需要 1 人审查通过
  - 需要 CI 检查通过
  - 禁止直接推送
```

## 15.5 Monorepo 的适用场景与不适用场景

### 适合使用 Monorepo 的场景

| 场景 | 原因 |
| ------ | ------ |
| 前后端紧密耦合的应用 | 共享类型定义、工具函数，修改 API 接口时同步更新前端 |
| 多个应用共享组件库 | UI 组件库、工具库在一个仓库中维护，版本一致性有保障 |
| 微前端架构 | 多个前端子应用需要统一的构建配置和依赖版本 |
| SDK / 库的开发 | 核心包 + 各平台适配包（web、node、mobile）需要协同开发 |
| 小型团队（3-15 人） | 沟通成本低，代码审查效率高 |

### 不适合使用 Monorepo 的场景

| 场景 | 原因 |
| ------ | ------ |
| 完全独立的项目 | 没有共享代码，Monorepo 只会增加复杂度 |
| 超大型团队（50+ 人） | 考虑使用 Bazel 或 Nx 等更适合大规模的工具 |
| 不同技术栈的项目 | Java + Go + Python 混合，pnpm/Turborepo 无法统一管理 |
| 需要严格权限隔离 | Monorepo 中所有人都有所有代码的访问权限 |
| 开源项目集合 | 每个项目需要独立的 issue、release 周期和社区 |

**决策流程图：**

```
你的项目满足以下条件中的 2 个以上吗？
  ├── 多个应用/包共享代码？
  ├── 需要统一的版本管理？
  ├── 团队规模 < 20 人？
  ├── 技术栈主要是 JavaScript/TypeScript？
  └── 跨项目的变更频繁（每周至少 1 次）？

Yes → 使用 Monorepo
No  → 使用独立仓库 + 发布到 npm 的方式共享代码
```

### 深入学习的方向

1. **Turborepo 远程缓存服务器**：如果不使用 Vercel 的托管远程缓存，可以自建缓存服务器（[turbo-remote-cache](https://github.com/ducktors/turborepo-remote-cache)），适合对数据安全有要求的企业。

2. **大规模 Monorepo 工具**：当仓库规模增长到数百个包时，可以考虑迁移到更强大的工具：
   - **Nx**：功能更丰富，支持依赖图可视化、受影响项目分析等
   - **Bazel**：Google 出品，适合超大规模多语言 Monorepo
   - **Lage**（Microsoft）：轻量级替代方案

3. **微前端集成**：如果 `apps/web` 需要拆分为多个独立部署的子应用：
   - **Module Federation**（Vite 插件：`@originjs/vite-plugin-federation`）
   - **qiankun** / **micro-app**：国内流行的微前端框架

4. **API 类型安全**：使用 **tRPC** 或 **Zod** + **OpenAPI** 实现前后端之间的端到端类型安全，消除手动类型同步的负担。

5. **Monorepo 中的 Storybook**：为 `packages/ui` 配置独立的 Storybook 文档站点，方便组件的独立开发和视觉测试。

6. **性能监控**：
   - **Sentry**：错误监控和性能追踪
   - **Grafana + Prometheus**：自建监控面板
   - **Lighthouse CI**：自动化前端性能评分
