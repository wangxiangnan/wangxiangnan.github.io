# 第3章：对称加密：enc 与 AES 实战

> [!TIP] Part 1: 工具箱入门篇（地基篇）
> 上一章的校验和管住了「坏没坏」，本章管住「能不能被看」。`enc` 是全书使用率第二高的子命令，也是坑最密集的一个——三个必须加的参数、一个工具能力的真实边界，本章一次讲透。

校验清单上线四周，王哥的下一个问题就到了：备份文件本身是**明文**躺在云对象存储里的。对象存储的访问凭证管住了「谁能下载」，但管不住两件事——拿到凭证的人（或泄露的凭证）能直接读全部用户数据；云厂商的运维在物理层面上总能触到你的字节。数据出门就该穿衣服，这是隐私保护的基本盘。对称加密（Symmetric Encryption）就是那件衣服：**加密和解密用同一把钥匙**，钥匙不动，数据随便走天下。

## 3.1 对称加密的直觉

一个保险箱的类比足够开场：你用一个密码把箱子锁上，同一个密码开箱。密码就是钥匙，箱子随便运输——只要密码不泄露，箱子里的东西就安全。

工程上真正干活的是 AES（Advanced Encryption Standard，高级加密标准）：

- **分组密码**：把明文切成 128 位（16 字节）一块，逐块加密。AES-256 意思是钥匙长 256 位。
- **流密码**：另一条技术路线，像水流一样逐字节加密，代表是 ChaCha20——TLS 里和 AES 平分天下，本书在套件层面会再遇到它。

选型不必纠结，一张表定案：

| 算法 | 钥匙长度 | 状态 | 本书立场 |
| ---- | ---- | ---- | ---- |
| AES-256-CBC | 256 位 | 现役，需配合完整性校验 | CLI 文件加密的默认选择 |
| AES-128-CBC | 128 位 | 现役 | 性能敏感场景可用，128 位强度足够 |
| ChaCha20 | 256 位 | 现役（流密码） | 无 AES 硬件加速的设备上更快 |
| DES / 3DES | 56 / 112 位 | 淘汰 | 块长 64 位早已不够，禁止新用 |
| RC4 | 可变 | 淘汰 | TLS 套件已全线移除；enc 命令行虽还能点名（default provider 仍编译了它），禁止新用 |

AES-256 与 AES-128 怎么选？对文件加密这种离线场景，性能差异可忽略，**无脑 AES-256**；AES-128 并非不安全——128 位钥匙暴力穷举的代价在可见的算力下依然天方夜谭，选它只是省不出几个百分点。

## 3.2 enc 实战：加解密一个文件

先看完整命令，再拆参数：

```bash
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 \
  -in backup-2026-11-06.sql -out backup-2026-11-06.sql.enc
```

回车后 OpenSSL 会提示你输入加密口令（输两遍确认，屏幕不回显）。解密用 `-d`：

```bash
openssl enc -d -aes-256-cbc -salt -pbkdf2 -iter 600000 \
  -in backup-2026-11-06.sql.enc -out restored.sql
```

口令对了，`restored.sql` 与原文件逐字节一致（用第2章的 `sha256sum` 一验便知）；口令错了，通常会报 `bad decrypt`——但注意 CBC 下约 1/256 的概率填充字节碰巧合法，此时命令不报错、静默解出一堆垃圾，这正是 3.7 节强调「必须配完整性校验」的原因。参数逐个过：

| 参数 | 作用 | 什么时候用 |
| ---- | ---- | ---- |
| `-aes-256-cbc` | 选算法与工作模式 | 本章默认 |
| `-salt` | 加盐（3.x 中默认已开） | 写出来是为了明示意图 |
| `-pbkdf2` | 用 PBKDF2 从口令派生钥匙 | **必须加**，3.3 节讲为什么 |
| `-iter 600000` | PBKDF2 迭代次数 | **必须加**，3.3 节讲为什么 |
| `-in` / `-out` | 输入输出文件 | 缺省时走 stdin/stdout，管道友好 |
| `-d` | 解密方向 | 解密时加 |
| `-pass pass:xxx` 等 | 口令来源 | 脚本里用，3.6 节讲 |

不带 `-in`/`-out` 时 enc 走标准输入输出，这条性质在 3.6 节的备份流水线和日常临时加密里都极好用，比如加密一段管道中间数据：

```bash
pg_dump cloudnote | openssl enc -aes-256-cbc -pbkdf2 -iter 600000 > backup.sql.enc
```

**拆开密文看一眼。** 密文不是黑盒，开头 16 字节里藏着 OpenSSL 的设计痕迹（`xxd` 每行 16 字节，下面截取前两行共 32 字节）。用 `xxd` 看密文：

```bash
xxd backup-2026-11-06.sql.enc | head -3
```

```text
00000000: 5361 6c74 6564 5f5f b8e3 4f1a 92c5 6d7d  Salted__......}.
00000010: 8f2a 4c31 77e9 b054 3d6c 1fa2 48b7 c9e3  .*L1w=...H...
00000020: 6e5d 8f04 2a91 c7b3 55e8 2d4f 9a16 3c70  n-]..*..U.-O..<p
```

前 8 字节是 ASCII 的 `Salted__`——这是 enc 的自描述标记，解密时 OpenSSL 一看便知「有盐、跟在后面」；接着 8 字节就是本次加密随机生成的盐，其余全是密文。两个推论：其一，盐不需要保密（它就是明文写的），需要的是**每次都随机**，这正是 `-salt` 的全部含义；其二，enc 的密文自带格式头，所以文件至少比原文多 16 字节（密文本体还会按 CBC 的补块规则凑满 16 字节的倍数），且**无法辨别里面是什么算法**——算法名记在运行参数里，不记在文件里，这又回到了「参数记进备份文档」的军规。

## 3.3 别省的三个参数：salt、pbkdf2、iter

如果你不加 `-pbkdf2` 直接跑，OpenSSL 3.x 会当场给你一个警告：

```text
*** WARNING : deprecated key derivation used.
Using -iter or -pbkdf2 would be better.
```

这个警告背后是一段真实的黑历史。加密的钥匙是 256 位随机数，而人给的口令是「wang123」这种弱字符串——两者之间需要一个换算步骤，叫密钥派生函数（KDF，Key Derivation Function）。OpenSSL 早期用了一个自制的简陋换算（EVP_BytesToKey），只换算一次，快得几乎免费。快，在这里是**致命缺点**：攻击者拿密文离线暴力试口令时，每秒能试几十亿次，弱口令几秒内沦陷。

现代化解法是 PBKDF2（Password-Based Key Derivation Function 2）：换算时掺入随机盐（salt），并且**故意循环几十万次**，让「正当用户多等一毫秒、攻击者每次猜测多付同样的成本」：

```text
         人记的口令（熵低）
               │
               ▼
   ┌─────────────────────────┐
   │ PBKDF2：加盐 + 迭代 60 万次 │   ← 每次猜测都要付满这 60 万次成本
   └─────────────────────────┘
               │
               ▼
       256 位钥匙（熵补齐）
```

两个参数的分工：

- **`-salt`**：给派生过程掺随机数，让同一口令每次加密出的密文都不同——攻击者无法用「预计算表」（彩虹表）批量攻破一批密文。这是历史上最著名的加密失误来源：早年大量教程命令不带 salt，整批密文被一张彩虹表一锅端。
- **`-iter 600000`**：迭代次数，成本旋钮。60 万次是 OWASP 2023 年针对 PBKDF2-HMAC-SHA256 的建议值——数字会随算力逐年上调，写脚本时别抄死，定期查看当前建议。

两个老参数的地雷顺手排掉，你会在老教程里遇到它们：

- **`-k` 不是「key」的缩写**：它是 `-pass pass:xxx` 的别名，口令照旧参与 PBKDF2 派生，功能上没问题——问题在**形态**：`openssl enc -aes-256-cbc -k mypass` 把口令明文写在命令行上，同机任何用户 `ps` 一眼、shell 历史一翻就拿到；换成 `-pass env:BACKUP_PASS` 才是正道。老教程里这一行同时挂着「口令上命令行」和（不写 `-pbkdf2` 时的）弱 KDF 两个雷，看到就重写。
- **`-nosalt` 只在一个地方合法**：密钥本来就来自 `-K` 直喂的强随机数、盐没有意义时。口令加密场景加 `-nosalt` 等于自废防彩虹表能力——有些嵌入式老系统为了「密文稳定可复现」这么干，属于历史包袱，别学。

> [!WARNING] 一省全丢
> `-pbkdf2` 和 `-iter` 省掉任何一条，你的加密强度都会从「工业级」跌回「玩具级」。**加密后的文件是给几年后的你解密的**——把这两个参数连同算法名一起记进备份说明文档，几年后 `openssl enc -d` 少一个参数都解不开。这不是戏言，是无数备份事故的真实死因。

## 3.4 诚实的边界：enc 不支持 AEAD

按现代密码学标准，最好的模式是 AEAD（Authenticated Encryption with Associated Data，带认证的加密）——加密和完整性校验一步到位，代表是 AES-GCM。于是你自然会想试试：

```bash
openssl enc -aes-256-gcm -pbkdf2 -in f.sql -out f.sql.enc
```

```text
enc: AEAD ciphers not supported
```

报错直接、且没有绕过的方法。这不是你敲错了，是 `enc` 的能力边界：AEAD 模式需要管理额外的认证标签（tag）与随机数（nonce），命令行工具没有承载这些参数的接口。**命令行 `enc` 只能用无认证的传统模式**（CBC、CTR 等），这决定了它的安全边界。

那 CBC 模式缺认证意味着什么？意味着一种阴险的攻击：**位翻转**。CBC 解密有个传播性质——攻击者翻转密文里第 N 块的某些位，解密后第 N+1 块明文的对应位会跟着翻转，而第 N 块明文整块报废。攻击者不需要解开密文，只要知道你文件里某个字段的字节位置（比如金额、权限标志），就能把「0」改成「1」，让解密出的数据朝着他想要的方向变。防御没有捷径，就是把第2章的 HMAC 请回来。

**encrypt-then-MAC**：先加密，后对密文算 HMAC，解密前先验 HMAC——指纹不对，密文根本不碰。两条命令的事：

```bash
# 加密 + 打指纹
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 -in f.sql -out f.sql.enc
openssl dgst -sha256 -hmac "$HMAC_KEY" f.sql.enc > f.sql.enc.hmac

# 解密前先验指纹，再解密
openssl dgst -sha256 -hmac "$HMAC_KEY" f.sql.enc | cmp -s - f.sql.enc.hmac \
  && openssl enc -d -aes-256-cbc -salt -pbkdf2 -iter 600000 -in f.sql.enc -out f.sql \
  || echo "密文被改过，拒绝解密"
```

注意这里加密与 HMAC 用了**两把不同的密钥**（密码学原则叫密钥分离）——一把钥匙干两份活虽然常见做法，但两把钥匙的容错更好：HMAC 钥匙泄露不牵连加密。工程上的严谨做法是从一个主密钥派生出两把，那需要代码级实现；命令行流水线用两把独立密钥已经足够得体。

> [!NOTE] 什么时候可以只加密不验
> 如果密文只在自家服务器之间走、且传输层已有 TLS 保护、文件被篡改的动机又不强——encrypt-then-MAC 可以简化。但备份这种「放出去好几年、出事才发现」的场景，永远值得多敲一条命令。记住因果方向：**先验指纹再解密**，反过来的 encrypt-then-decrypt-then-verify 会把攻击面留给解密器。

## 3.5 口令加密与密钥加密

本章到目前为止都用「人口令 + PBKDF2」的路线，它适合**人要记得住**的场景。但还有另一条路线：钥匙根本不是口令，而是 `openssl rand` 生成的真随机数，直接喂给加密命令：

```bash
# 用 -K（大写）直接喂十六进制钥匙，-iv 喂初始向量，跳过 KDF
openssl enc -aes-256-cbc \
  -K 3f9a1c7e5b2d8f40a6c1e9d3b7f25a80c9d4e7f2a1b8c5d3e6f0917a4b2c8d5e \
  -iv a1b2c3d4e5f60718293a4b5c6d7e8f90 \
  -in f.sql -out f.sql.enc
```

两条路线的分工：

| | 口令加密（-pbkdf2） | 密钥加密（-K -iv） |
| ---- | ---- | ---- |
| 钥匙来源 | 人的口令派生 | `openssl rand` 真随机 |
| 强度上限 | 口令的熵 + 迭代成本 | 满 256 位 |
| 谁来保管 | 人的脑子 | 文件 / 密钥管理系统 |
| 适合 | 个人备份、手动操作 | 脚本自动化、服务间加密 |

注意大写 `-K` 时必须同时给 `-iv`（初始向量，Initialization Vector，CBC 模式每块加密的扰动源）：AES-256 的 `-K` 要 64 个十六进制字符、`-iv` 要 32 个，长度不对命令会当场报错。而口令模式下 PBKDF2 会自动生成 IV——这是口令路线对脚本更友好的原因之一。随机数怎么造才靠谱、随机密钥怎么保管，正是下一章的全部内容。

## 3.6 实验：备份加密双保险流水线

把两章收拢成一个可上线的脚本 `~/cloudnote/backup.sh`：

```bash
#!/bin/bash
set -euo pipefail
STAMP=$(date +%F)
WORK=~/cloudnote/backup-$STAMP.tar.gz
OUT=$WORK.enc

# 1. 打包
tar -czf "$WORK" -C ~/cloudnote data/

# 2. 加密（口令来自环境变量，不进命令行历史）
openssl enc -aes-256-cbc -salt -pbkdf2 -iter 600000 \
  -in "$WORK" -out "$OUT" -pass env:BACKUP_PASS

# 3. 对密文打指纹（HMAC 钥匙与加密口令分离）
# -r 输出可复现格式，cut 只留 64 位十六进制——指纹与文件路径解耦，
# 换台机器、换相对/绝对路径都不会造成假阳性
openssl dgst -r -sha256 -hmac "$BACKUP_HMAC_KEY" "$OUT" | cut -d' ' -f1 > "$OUT.hmac"

# 4. 清理明文中间产物，上传三件套
rm "$WORK"
# scp "$OUT" "$OUT.hmac" backup@203.0.113.10:/srv/backups/
echo "backup done: $OUT"
```

三个工程细节，都是本章知识的直接应用：

- **口令走 `-pass env:BACKUP_PASS`**：口令来源除了交互输入，还有 `pass:xxx`（危险，进程列表可见）、`env:VAR`、`file:路径`、`stdin`。脚本里永远用 `env` 或 `file`，绝不用 `pass:`——命令行参数对所有用户可见。
- **中间产物打包后立刻删除**：加密保护的是「出门的文件」，服务器本地的明文包多活一分钟多一分钟风险。
- **还原演练每季度跑一次**：解密 + 验指纹 + 解 tar 三步走一遍，确认 `BACKUP_PASS` 与迭代参数都还记录在案。没有还原演练的备份是薛定谔的备份。

还原侧的配套脚本 `restore.sh`，与备份脚本镜像对称，第 8 周式的事故再来一次时照着跑：

```bash
#!/bin/bash
set -euo pipefail
IN=${1:?"用法: ./restore.sh backup-2026-11-06.tar.gz.enc"}

# 1. 先验指纹——密文不对，一步都不往下走（-r + cut 与 backup.sh 的存法配对）
openssl dgst -r -sha256 -hmac "$BACKUP_HMAC_KEY" "$IN" | cut -d' ' -f1 | cmp -s - "$IN.hmac" \
  || { echo "HMAC 校验失败，文件疑似被篡改"; exit 1; }

# 2. 解密（参数必须与 backup.sh 完全一致）
openssl enc -d -aes-256-cbc -salt -pbkdf2 -iter 600000 \
  -in "$IN" -out "${IN%.enc}" -pass env:BACKUP_PASS

# 3. 解包
tar -xzf "${IN%.enc}" -C ~/cloudnote-restored/
echo "restored to ~/cloudnote-restored/"
```

脚本里那行 `${IN%.enc}` 是 bash 的参数展开：剥掉结尾的 `.enc`，还原出原文件名。注意第一步不通过就 `exit 1`——「先验后解」的纪律在脚本里用 `||` 写成了硬约束，人手敲命令时容易顺手跳过，机器不惯着人。

`BACKUP_PASS` 与 `BACKUP_HMAC_KEY` 这两把钥匙的出生方式，下一章的 `openssl rand` 亲手生成；它们住在哪里（绝不进 Git）、怎么轮换，也一并交代。加密流水线今天就能跑，但请先读完下一章再把它推上生产。

## 本章小结

- 对称加密 = 一把钥匙管加密解密，文件加密的无脑选择是 **AES-256-CBC**
- `enc` 三件套必须齐：`-pbkdf2`（现代 KDF）+ `-iter 600000`（成本旋钮）+ salt（防彩虹表）——省掉任何一个，强度从工业级跌回玩具级
- 密文头 16 字节 = `Salted__` + 随机盐，盐不保密但要每次随机；算法名不在文件里，记进备份文档
- 老教程的 `-k` 是泄密别名，`-nosalt` 是自废武功，见到就重写
- 老密钥派生只换算一次，攻击者每秒试几十亿次口令；PBKDF2 让每次猜测都付满 60 万次迭代成本
- **`enc` 不支持 AEAD**（`-aes-256-gcm` 直接报错）：命令行加密必须自己补完整性——encrypt-then-MAC，先验指纹再解密
- CBC 位翻转攻击：不解密也能定向篡改明文，这就是完整性校验不是可选项的原因
- 口令来源脚本里用 `-pass env:`，绝不用 `-pass pass:`；口令加密与随机密钥加密是两条并行路线，第4章补齐后者
