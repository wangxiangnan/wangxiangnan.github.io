> **读完本章你将能够**：用 OOP 的视角向任何程序员解释什么是 Agent

## 1.1 开篇：一个对象的故事

你已经写过无数个对象了。今天我们来写一个特别的：

```python
class Agent:
    """一个能自主完成任务的对象"""
    
    def __init__(self, tools: dict):
        self.messages = []     # 状态：对话历史
        self.memory = {}       # 状态：长期记忆
        self.tools = tools     # 方法：可调用的工具
    
    def run(self, user_input: str) -> str:
        """主入口：接收输入 → 循环处理 → 返回结果"""
        self.messages.append({"role": "user", "content": user_input})
        
        while True:
            decision = self.think()          # 思考：该做什么？
            
            if decision.needs_tool:
                result = self.call_tool(     # 行动：调用方法
                    decision.tool_name,
                    decision.tool_args
                )
                self.messages.append(        # 更新状态
                    {"role": "tool", "content": result}
                )
            else:
                return decision.answer       # 输出：最终回答
    
    def think(self):
        """思考：基于当前所有状态，决定下一步"""
        return llm.chat(self.messages)       # LLM 做决策
    
    def call_tool(self, name, args):
        """行动：调用已有方法"""
        return self.tools[name](**args)
```

**这就是 Agent 的全部。** 一个有状态的对象，带一个 while 循环，循环里做三件事：思考、判断、行动。

你现在可能觉得"这也太简单了"——没错，Agent 的概念就是这么简单。整个教程25章做的事情，本质上都是在帮你把这个对象写得更健壮、更灵活、更能上生产。

但正是这个"简单"的对象，能解决传统方案根本解决不了的问题。让我们看看为什么。

## 1.2 降维打击：同一个问题，两种对象

假设你要做一个技术支持系统。用户问：

> "Docker 容器启动后端口映射不生效，报 `bind: address already in use`，怎么排查？"

### 传统方式：一个写死逻辑的对象

```python
class TraditionalBot:
    """传统客服机器人：所有决策逻辑都是 if-else"""
    
    def __init__(self):
        self.knowledge_base = load_faq()  # 状态：FAQ 知识库
    
    def run(self, question: str) -> str:
        q = question.lower()
        
        # 所有"智能"都在这里 —— 一棵巨大的 if-else 树
        if "docker" in q:
            if "端口" in q or "port" in q:
                if "映射" in q:
                    return "请参考端口映射文档: https://docs.docker.com/"
            elif "容器" in q and "启动" in q:
                return "启动失败排查: 1.镜像不存在 2.入口命令错误 3.资源不足"
        # ... 省略 5000 行 elif ...
        else:
            return "抱歉，我不理解您的问题。"
```

这个对象能跑，但它有一个致命问题：**它的 `run()` 方法里没有循环，没有动态决策，只有一条直通到底的 if-else 链。** 它不会"思考"，不会"尝试"，不会"根据结果调整策略"。

结果：它把用户问题匹配到"Docker 端口映射"这个关键词，甩一个文档链接了事。完全忽略了 `address already in use` 这个关键线索——这条错误信息意味着端口被占用，而不仅仅是配置问题。

### Agent 方式：一个会思考的对象

```python
class Agent:
    """AI Agent：决策逻辑由 LLM 动态生成"""
    
    def __init__(self):
        self.messages = []
        self.tools = {
            "check_port": check_port_usage,       # 方法1: 检查端口
            "check_process": check_process_info,   # 方法2: 查看进程
            "search_docs": search_documentation,   # 方法3: 搜索文档
        }
    
    def run(self, question: str) -> str:
        self.messages.append({"role": "user", "content": question})
        
        # === 第 1 轮循环 ===
        # think(): LLM 看到 "address already in use"
        #          → 判断：端口被占用，需要先查哪个进程占了端口
        #          → 决策：调用 check_port(port=8080)
        decision = self.think()
        # decision = { needs_tool: True, tool_name: "check_port", args: {port: 8080} }
        
        result = self.call_tool("check_port", {"port": 8080})
        # result = "端口 8080 被进程 nginx (PID 12345) 占用"
        self.messages.append({"role": "tool", "content": result})
        
        # === 第 2 轮循环 ===
        # think(): LLM 看到工具返回 "nginx PID 12345"
        #          → 判断：找到原因了，可以给方案了
        #          → 决策：不需要工具了，直接回答
        decision = self.think()
        # decision = { needs_tool: False, answer: "端口 8080 被 nginx(PID 12345) 占用..." }
        
        return decision.answer
        # "端口 8080 被 nginx(PID 12345) 占用。
        #  方案: a) sudo kill 12345 释放端口
        #        b) docker run -p 9090:80 换一个端口映射"
```

看到区别了吗？

```
TraditionalBot 的 run():
  输入 → if-else 匹配关键词 → 返回固定文本 → 结束
  （一次调用，一条路径，写死的）

Agent 的 run():
  输入 → 思考 → 调工具 → 更新状态 → 再思考 → 再调工具（或回答）→ 结束
  （while 循环，路径是 LLM 动态决定的）
```

**核心差异不在于"谁更聪明"，而在于 `run()` 方法里有没有循环和动态决策。**

| 维度 | TraditionalBot | Agent |
| ------ | --------------- | ------- |
| 决策逻辑 | `if "端口" in question` | LLM 理解语义后动态推理 |
| 控制流 | 一次 if-else 匹配 | while 循环，可多步推理 |
| 工具调用 | 无（只能返回文本） | 可调用任意方法（检查端口、查进程） |
| 状态更新 | 无（无状态） | 每轮循环更新 messages |
| 新场景 | 加一堆 elif | 加一个 tool，核心循环不变 |

> 用 OOP 的话说：TraditionalBot 是一个只有 getter 的对象（只读数据返回结果），Agent 是一个完整的有状态对象（能读、能写、能循环、能调方法）。

## 1.3 对象模型详解：Agent 的四个组成部分

回到我们的 Agent 对象，它有四个核心组成部分：

```python
class Agent:
    def __init__(self):
        # ① 感知 (Perception) —— 输入接口
        self.input_handler = InputHandler()    # 接收文本/文件/图片
        
        # ② 推理 (Reasoning) —— 决策逻辑
        self.brain = LLM()                     # LLM 做思考和判断
        
        # ③ 行动 (Action) —— 方法集合
        self.tools = {}                        # 可调用的工具/方法
        
        # ④ 记忆 (Memory) —— 状态存储
        self.messages = []                     # 短期：对话上下文
        self.long_term_memory = VectorDB()     # 长期：跨会话知识
```

用 OOP 的术语来翻译：

```
Agent 的概念           OOP 的术语              你熟悉的东西
────────────────────────────────────────────────────────
感知 (Perception)    → 构造函数参数/入口方法  → Controller 的 @PostMapping
推理 (Reasoning)     → 核心业务逻辑          → Service 层的 process()
行动 (Action)        → 可调用方法            → 注入的 Repository/Client
记忆 (Memory)        → 成员变量/字段         → 数据库 + 缓存
```

### ① 感知：对象怎么接收输入

```python
class InputHandler:
    """感知层：把各种输入标准化为 Agent 能处理的格式"""
    
    def parse_text(self, text: str) -> dict:
        """文本输入 → 提取意图和实体"""
        return {"type": "text", "content": text, "language": detect_lang(text)}
    
    def parse_file(self, file_path: str) -> dict:
        """文件输入 → 提取文本内容"""
        content = read_file(file_path)  # PDF/Markdown/CSV...
        return {"type": "file", "content": content, "path": file_path}
    
    def parse_image(self, image: bytes) -> dict:
        """图片输入 → 提取视觉信息（需要多模态模型）"""
        description = vision_model.describe(image)
        return {"type": "image", "description": description}
```

> 类比：就像 Controller 层接收 HTTP 请求，做参数校验和格式转换，然后传给 Service 层。感知层把用户的各种输入统一成 Agent 能理解的格式。

### ② 推理：对象的"大脑"

```python
class Agent:
    def think(self) -> Decision:
        """
        推理：基于当前所有状态，决定下一步做什么
        
        LLM 看到的输入：
        - System Prompt（角色定义）
        - 对话历史（self.messages）
        - 可用工具列表（self.tools 的描述）
        - 检索到的上下文（如果有记忆系统）
        
        LLM 返回的输出（二选一）：
        A. "我需要调用工具 X，参数是 {...}"
        B. "我有足够的信息了，最终回答是：..."
        """
        prompt = self.build_prompt()  # 把所有状态打包成 Prompt
        response = self.brain.chat(prompt)
        
        if response.has_tool_call:
            return Decision(needs_tool=True, tool_name=..., tool_args=...)
        else:
            return Decision(needs_tool=False, answer=response.text)
```

这是 Agent 和 TraditionalBot 的**根本区别**。TraditionalBot 的决策逻辑是程序员写死的 `if-else`，而 Agent 的决策逻辑是 LLM 在运行时动态生成的。

```python
# TraditionalBot 的决策：硬编码，程序员写什么就只能做什么
if "端口" in question and "docker" in question:
    return "请查看文档"

# Agent 的决策：LLM 动态生成，能处理程序员没想到的情况
# LLM 看到 "bind: address already in use"
# → 推理出"端口被占用"（这个规则程序员没写！）
# → 决定"先查端口占用情况"（这个流程程序员没定义！）
# → 调用 check_port 工具（这个工具程序员提供了）
```

> 类比：TraditionalBot 的 Service 层是你写死的业务逻辑。Agent 的"Service 层"是一个 LLM——它能理解你给它的工具列表，自己决定调用哪个、怎么调用、什么时候停止。**程序员从"写逻辑"变成了"提供工具"**。

### ③ 行动：对象的方法

```python
# Agent 的"方法"就是工具 (Tools)
tools = {
    # 每个 tool 就是一个普通函数，有参数、有返回值
    "check_port": lambda port: run_cmd(f"lsof -i :{port}"),
    "search_docs": lambda query: vector_db.search(query),
    "write_file": lambda path, content: open(path, 'w').write(content),
    "send_email": lambda to, subject, body: smtp.send(to, subject, body),
    "query_db": lambda sql: database.execute(sql),
}

# Agent 调用工具和对象调用方法完全一样：
# agent.tools["check_port"](port=8080)
# 等价于
# object.check_port(port=8080)
```

> 关键认知：**Agent 本身不知道端口是什么、怎么检查端口。** 它只知道"我有一个叫 `check_port` 的方法，接受一个 `port` 参数，返回一个字符串"。它通过 LLM 的推理来决定"现在该调用这个方法了"。就像你的 Controller 不需要知道数据库怎么实现——它只知道 Repository 有一个 `findById(id)` 方法。

### ④ 记忆：对象的状态

```python
class Agent:
    def __init__(self):
        # 短期记忆：当前对话的上下文（像 Java 的 ThreadLocal）
        self.messages = [
            {"role": "system", "content": "你是一个技术支持 Agent..."},
            {"role": "user", "content": "Docker 端口映射失败..."},
            {"role": "assistant", "content": "让我检查一下端口..."},
            {"role": "tool", "content": "端口 8080 被 nginx 占用"},
            # ... 每轮循环都在追加
        ]
        
        # 长期记忆：跨会话的知识（像数据库）
        self.long_term_memory = VectorDB()
        # 存储：用户的偏好、历史对话摘要、学到的知识...
```

> 短期记忆 = 实例变量（每次 `run()` 都在用，对话结束可丢）  
> 长期记忆 = 数据库（持久化，跨会话保留）

## 1.4 用对象模型理解 Agent 的进化史

Agent 不是突然冒出来的。从"只会 if-else"到"会自主决策"，走了四个阶段。每个阶段用对象来理解就很清楚：

```python
# === 阶段1：规则引擎 ===
# 一个没有状态、没有循环、只有一堆 if-else 的函数
def rule_bot(question):
    if "docker" in question: return "看文档"
    if "k8s" in question: return "看 k8s 文档"
    # 每加一个场景就要写一个 if

# === 阶段2：状态机 ===
# 有了状态，但状态转换是写死的
class StateBot:
    def __init__(self):
        self.state = "greeting"  # 有状态了！
    
    def run(self, user_input):
        if self.state == "greeting":
            self.state = "collecting"
            return "请描述您的问题"
        elif self.state == "collecting":
            self.state = "answering"
            return f"根据您说的'{user_input}'，建议..."
        # 状态转换路径是程序员定义的，不能动态改变

# === 阶段3：ML 模型 ===
# 有了学习能力的"分类器对象"
class MLBot:
    def __init__(self):
        self.classifier = train_classifier(data)  # 训练出来的
    
    def run(self, question):
        category = self.classifier.predict(question)  # ML 分类
        return templates[category]
        # 比 if-else 聪明，但每个任务需要一个模型，不通用

# === 阶段4：LLM Agent ===
# 完整的对象：状态 + 循环 + 动态决策 + 工具调用
class Agent:
    def __init__(self, tools):
        self.messages = []     # 状态
        self.tools = tools     # 方法
    
    def run(self, question):
        while True:            # 循环！
            decision = llm.decide(self.messages, self.tools)  # 动态决策
            if decision.needs_tool:
                self.messages.append(self.call_tool(decision))  # 更新状态
            else:
                return decision.answer
```

| 阶段 | 对象特征 | 局限 | 类比 |
| ------ | --------- | ------ | ------ |
| 规则引擎 | 无状态函数 | 规则爆炸 | 一个只有 `switch` 的方法 |
| 状态机 | 有状态但路径固定 | 不能应对意外 | `enum State` + 硬编码转换 |
| ML 模型 | 有学习但无通用性 | 一个任务一个模型 | 每个功能一个微服务 |
| LLM Agent | 完整对象+动态决策 | 成本高、延迟大 | 一个通用对象能处理所有情况 |

## 1.5 Agent vs 普通 LLM 调用：有没有循环和工具

很多人分不清"调了一次 ChatGPT API"和"用 Agent 处理任务"的区别。用对象模型一看就明白：

```python
# 普通 LLM 调用：一个无状态的函数调用
def ask_llm(question):
    return llm.chat(question)
    # 调一次，返回一次，结束
    # 没有循环，没有工具，没有状态更新

# Agent：一个有状态的对象的 run() 方法
def run_agent(question):
    agent = Agent(tools=[search, calculate, code_exec])
    return agent.run(question)
    # 内部有 while 循环
    # 可能调 3 次 LLM、2 次工具、循环 5 轮才出结果
```

| 能力 | 普通 LLM 调用 | Agent |
| ------ | ------------- | ------- |
| 回答知识性问题 | 靠训练数据 | 可以调工具查实时数据 |
| 执行多步操作 | 不行（单轮） | while 循环天然支持 |
| 调用外部系统 | 不行 | 通过 tools 调任何 API |
| 跨对话记忆 | 每次都是新对话 | memory 保存跨会话信息 |
| 自我纠错 | 错了就错了 | 循环中可以检查结果并重试 |

> 一句话：**普通 LLM 调用是一个函数调用（无状态、无循环），Agent 是一个对象的 run() 方法（有状态、有循环、有方法调用）。**

## 1.6 Agent vs RAG vs Fine-tuning：三种给对象"加能力"的方式

你已经理解了 Agent 是一个有状态的对象。那 RAG 和 Fine-tuning 是什么？

```python
# Fine-tuning：训练时改变 LLM 的权重
# 类比：换一个"大脑芯片"（改变对象的核心处理器）
class Agent:
    def __init__(self):
        self.brain = FineTunedLLM()  # 换了一个专门训练过的大脑
        # 优点：对特定任务表现更好
        # 缺点：换个任务就不行了，训练成本高

# RAG：给对象加一个"资料库"
class Agent:
    def __init__(self):
        self.brain = LLM()
        self.knowledge = VectorDB()  # 加了一个外部知识库
    
    def think(self):
        context = self.knowledge.search(self.messages[-1])  # 先检索
        return self.brain.chat(self.messages + context)      # 带着上下文思考
        # 优点：知识可更新、可追溯
        # 缺点：只能"查资料回答"，不能执行操作

# Agent：给对象加工具和循环
class Agent:
    def __init__(self):
        self.brain = LLM()
        self.tools = [...]  # 加了一堆工具
        self.messages = []  # 加了状态和循环
    
    def run(self, input):
        while True:         # 循环！
            decision = self.think()
            if decision.needs_tool:
                self.call_tool(decision)  # 执行操作
            else:
                return decision.answer
        # 优点：能执行操作、能多步推理、能自主规划
        # 缺点：复杂度高、延迟大、成本高
```

| | Fine-tuning | RAG | Agent |
| --- | ------------ | ----- | ------- |
| 类比 | 换大脑 | 加资料库 | 加工具+循环 |
| 解决的问题 | 特定风格/领域 | 知识问答 | 自主操作 |
| 能否更新知识 | 需要重新训练 | 更新文档即可 | 通过工具获取实时数据 |
| 能否执行操作 | 不能 | 不能 | 能（通过 tools） |
| 能否多步推理 | 不能 | 不能 | 能（while 循环） |
| 常见组合 | 单独使用 | 常作为 Agent 的一个 tool | Agent + RAG 最常见 |

> **最常见的组合是 Agent + RAG**：Agent 的 while 循环里，有一个 tool 叫 `search_knowledge_base`，它内部用 RAG 检索文档。Agent 负责决策"什么时候该检索"和"怎么用检索结果"，RAG 负责"怎么检索"。各司其职。

## 1.7 一个更大的例子：邮件处理

用对象模型看一个更贴近实际的场景——处理技术支持邮件：

```python
# 传统方式：一个巨型 switch-case 对象
class TraditionalHandler:
    def process(self, email):
        subject = email["subject"].lower()
        
        if "bug" in subject:          # 分支1
            return self._handle_bug(email)
        elif "feature" in subject:    # 分支2
            return self._handle_feature(email)
        elif "billing" in subject:    # 分支3
            return self._handle_billing(email)
        # ... 几十个 elif ...
        else:                         # 兜底
            return self._forward_to_human(email)
    
    # 问题：
    # 1. 一封邮件同时有 bug + feature request → 只走第一个分支
    # 2. 用户说"这里可以改进"而不是"feature request" → 匹配不到
    # 3. 新加一种邮件类型 → 必须改代码（违反开闭原则）

# Agent 方式：一个通用对象，通过工具适配不同邮件
class AgentHandler:
    def __init__(self):
        self.tools = {
            "create_jira": create_jira_ticket,
            "add_backlog": add_to_backlog,
            "forward_finance": forward_to_finance,
            "send_reply": send_email_reply,
        }
    
    def process(self, email):
        return self.run(f"处理邮件:\n{email['subject']}\n{email['body']}")
    
    def run(self, input):
        # while 循环 + LLM 动态决策
        # LLM 能理解：
        # - "这里可以改进" = feature request
        # - 一封邮件两个问题 → 循环两轮，分别处理
        # - 复杂邮件 → 先搜索知识库，再决定行动
        while True:
            decision = self.think()
            if decision.needs_tool:
                self.call_tool(decision)
            else:
                return decision.answer
```

传统方式：每种情况写一个处理分支 → 代码量和情况数成正比。  
Agent 方式：一个 `run()` 方法 + 一组工具 → 新情况只需加新工具，核心循环不变。

**这就是开闭原则的完美体现：对扩展开放（加 tool），对修改关闭（不改 run）。**

class Agent:
    """
    AI Agent = 一个有状态的对象

    """
