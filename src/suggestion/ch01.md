# 学习技术建议

各种教程的分析其实隐含了一个很好的学习框架，我把它显性化一下，这些原则适用于几乎任何技术领域。

## 第一个原则：永远从"它解决了什么问题"开始，而不是从"它是什么"开始

大多数人学习新技术的路径是：看文档 → 背概念 → 记命令 → 做项目。这是反的。更高效的路径是：先搞清楚"没有这个东西之前，人们怎么干活？遇到了什么痛点？"——搞懂了痛点，后面的概念就不是记忆负担，而是"理所当然的答案"。就像你理解了"在我电脑上能跑"这个痛点，Docker 的概念就自然成立了。每学一个新东西，先问自己一个问题：如果这玩意儿不存在，我要多绕几步路？

## 第二个原则：用递进链代替平铺清单

不要把所有知识点当成平级的列表来学，而是找它们的依赖关系。问自己：学 B 之前是不是必须先会 A？如果是，A 就是 B 的前置节点。 把知识组织成一棵树或一条链，而不是一张平面的清单。刚才 Docker 的四个 Part 就是典型的递进链——每个 Part 都在解决上一 Part 留下的"未解之题"。你自己学任何东西的时候，都可以试着画这样的链：这一层解决了什么，留下了什么问题，下一层怎么补上。

## 第三个原则：区分"必学"和"按需学"

任何技术领域都有核心区和扩展区。核心区是你不看就干不了活的，扩展区是"知道了更好，不知道也不耽误事"的。一个实用的判断方法是：如果去掉这个知识点，我还能完成 80% 的日常工作吗？ 如果能，它就是扩展区，可以后面再学。Docker 教程里，Part 1-2 是核心区（镜像、容器、网络、Compose），Part 3 的 CI/CD 是半必修（现代开发基本绑定），Swarm 和 K8s 就是扩展区——除非你的项目真的需要。很多人学不下去，不是因为内容难，而是把所有东西都当必学，结果还没跑到终点就放弃了。

## 第四个原则：每一层都动手，不要"全学完再做项目"

学完 Part 1 就做一个单容器项目部署，学完 Part 2 就用 Compose 搭一个全栈应用，学完 Part 3 就给自己写一条 CI/CD 流水线。不要等到"全部学完"才动手，因为不动手你根本不知道自己学没学会，而且动手过程中暴露的问题会反过来指导你下一层该重点学什么。这就是"螺旋式学习"——每一圈都更深入，但每一圈都有可交付的成果。

## 第五个原则：用类比建立知识桥梁，但要知道类比的边界

用你已知的东西理解未知的东西，这是高效学习的核心技巧。Docker 教程里"容器 = 合租公寓，虚拟机 = 独栋别墅"就是典型类比。但类比有个陷阱：它只在某个角度成立。合租公寓共享地基（内核），但真实合租公寓不会"重启就丢东西"（容器的临时性）。每用一个类比，都要想清楚"这个类比在哪里会失效"，否则你会在错误的地方做错误的推断。

总结一下就是五句话：先问痛点再看概念，画链条别列清单，区分必学和选学，每层都动手做东西，类比好用但要知边界。这五条不挑领域，学编程语言、学框架、学系统设计、甚至学非技术的东西，都能用。
