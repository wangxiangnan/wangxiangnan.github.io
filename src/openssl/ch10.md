# 第10章：自建 CA：给内网服务签发证书

> [!TIP] Part 3: CA 与 TLS 实战篇（实战篇）
> 实战篇开篇。危机三的两处伤口——内网三个服务互相不认识、公网证书到期没人管——解法是同一个：亲手当一回 CA。建过一次根证书、签过一批服务器证书，公网证书体系的每一个行为你都能对上号。

先看危机三的全貌。云笔记的内网跑着三个服务：认证（auth）、通知（notify）、同步（sync），彼此靠 HTTP 裸奔调接口，运维VPN里抓个包就能看光全部令牌；公网的 api 证书则是手动买的、一年一换，第三十周的凌晨它过期了，全站报错 40 分钟。两件事的解法一致：**建一套内部证书体系，批量签发、短周期、自动轮换**。而理解它的最快路径，是亲手把这套体系的「 issuing 端」搭一遍。

## 10.1 当一回 CA 的双重意义

自建 CA（Certificate Authority，证书颁发机构）做两件事：**对外**，它是内网服务的信任中枢——所有服务只认你发的证书，新服务上线签一张就接入；**对内**，它是一台透视机——公网 CA 怎么运作、根证书为什么值得信任、撤销为什么尴尬，你建完就知道。第8章那张「塑封卡」的比喻，本章亲手当一回塑封机。

内部 CA 的最小结构两级：**根 CA**（Root CA）签发一切；生产环境讲究的还会加一层中间 CA（第11章讲它的意义），本教程从简，两级足够看清原理。先定目录与纪律：

```text
/etc/cloudnote-ca/              ← CA 的家（权限 700）
├── private/
│   └── root-key.pem            ← 根私钥：加密保存，权限 600
├── root.crt                    ← 根证书：全员信任锚
├── issued/                     ← 签出的服务器证书
└── csr/                        ← 各服务交上来的申请
```

纪律先立三条，后面每一步都在执行：根私钥加密保存、只在签发时解锁；服务器证书一律 90 天（到期自动轮换，撤销需求自然消失）；每张证书的 SAN 必须与域名一一对应，绝不签通配符图省事。

通配符这一条值得多给一句理由：`*.cloudnote.internal` 一张证覆盖所有内网服务，省事是省事，但**这张证书泄露等于全部内网服务沦陷**——一个服务的私钥出事，攻击者可以直接冒充另外二十九个。逐服务签发、密钥互不相干，爆炸半径就锁死在单个服务里，这与第4章「一把钥匙一个用途」的密钥分离原则一脉相承。

## 10.2 建根 CA

两步：造根私钥，造根证书。根证书是「自己给自己盖章」的自签证书（第8章讲过 Issuer 与 Subject 相同的特征），但必须带两个关键扩展，把自己标定为 CA：

```bash
# 1. 根私钥：EC P-256，口令加密（口令来自第4章的密钥目录）
sudo openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 \
  -aes-256-cbc -passout file:/etc/cloudnote-ca/private/KEY_PASS.txt \
  -out /etc/cloudnote-ca/private/root-key.pem

# 2. 根证书：有效期 10 年，CA:TRUE
sudo openssl req -x509 -new \
  -key /etc/cloudnote-ca/private/root-key.pem \
  -passin file:/etc/cloudnote-ca/private/KEY_PASS.txt \
  -sha256 -days 3650 \
  -subj "/C=CN/O=CloudNote/CN=CloudNote Internal Root CA" \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:0" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -out /etc/cloudnote-ca/root.crt
```

与第9章自签证书相比，两处 `-addext` 是 CA 的身份徽章，含义值得逐词读：

| 扩展 | 值 | 意义 |
| ---- | ---- | ---- |
| basicConstraints | `critical, CA:TRUE, pathlen:0` | 我是 CA，可以签发证书；pathlen:0 表示**只许签一级**，不许再建中间 CA |
| keyUsage | `critical, keyCertSign, cRLSign` | 这把私钥只许干两件事：签证书、签撤销列表 |
| 有效期 | 3650 天 | 根证书 10 年——它是信任的锚点，频繁换锚等于全员重新安装信任 |

用第8章学的 `-text` 自查：`CA:TRUE` 在、`keyCertSign` 在，根证书才算合格。这张 `root.crt` 就是后续要分发给全员、导入信任库的「宪法」——**根私钥从此深藏**，日常签发都用它，但理想的深藏方式是离线（本教程在同一台服务器的加密文件里，注释里说明即可）。

根证书 10 年到期怎么办？这叫根轮换，标准做法是**双根过渡**：到期前 1 年签出新根、新旧两根并行分发，等所有客户端都装了新根，再让旧根退役。你也许认出来了——这正是 2011 年 DigiNotar 之后浏览器「集体换锁」的机制，也解释了为什么根证书敢定 10 年：换锚是大工程，锚要稳。云笔记内网规模小，日历上给根证书设一个「到期前 12 个月」的提醒就够。

## 10.3 签发第一张服务器证书

签发流程三段：收 CSR、写扩展文件、签名。auth 服务那边用第9章的命令交来申请表：

```bash
# auth 服务侧：生成私钥与 CSR（SAN 写自己的域名）
openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout auth-key.pem -out auth.csr \
  -subj "/C=CN/O=CloudNote/CN=auth.cloudnote.internal" \
  -addext "subjectAltName=DNS:auth.cloudnote.internal"
```

CA 侧先为它准备一份扩展文件（每个服务一份，SAN 不同）：

```bash
# /etc/cloudnote-ca/csr/auth.ext
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:auth.cloudnote.internal
```

然后是签发主命令 `x509 -req`——「读申请表、盖章、发证」：

```bash
sudo openssl x509 -req \
  -in /etc/cloudnote-ca/csr/auth.csr \
  -CA /etc/cloudnote-ca/root.crt \
  -CAkey /etc/cloudnote-ca/private/root-key.pem \
  -passin file:/etc/cloudnote-ca/private/KEY_PASS.txt \
  -CAcreateserial -days 90 -sha256 \
  -extfile /etc/cloudnote-ca/csr/auth.ext \
  -out /etc/cloudnote-ca/issued/auth.crt
```

| 参数 | 作用 |
| ---- | ---- |
| `-req` | 输入是 CSR 而不是已有证书 |
| `-CA` / `-CAkey` | 用谁的章盖：根证书 + 根私钥 |
| `-CAcreateserial` | 首次签发自动建立序列号文件（后续签发沿用，号自动递增） |
| `-days 90` | 服务器证书 90 天，与根的 10 年形成短长搭配 |
| `-extfile` | 从文件读入扩展——SAN、CA:FALSE 都由 CA 说了算，**CSR 里申请的扩展不自动生效** |

最后一行值得划重点：CA 出于安全默认不信任 CSR 里带的信息，扩展以 extfile 为准——这就是「审核」在技术上的样子。签完立刻验收：

```bash
openssl verify -CAfile /etc/cloudnote-ca/root.crt /etc/cloudnote-ca/issued/auth.crt
openssl x509 -in /etc/cloudnote-ca/issued/auth.crt -noout -subject -issuer -dates
```

```text
issued/auth.crt: OK
subject=C=CN, O=CloudNote, CN=auth.cloudnote.internal
issuer=C=CN, O=CloudNote, CN=CloudNote Internal Root CA
notAfter=Feb  4 08:00:00 2027 GMT
```

`OK` 加 Issuer 是根 CA、有效期 90 天——第一张内部证书出生。

签发完成后顺手记一笔台账。轻量路线不记数据库，那就手工记——沿用第4章立密钥台账的思路，在 CA 目录放一份 `LEDGER.md`：

```text
| 日期       | 域名                     | 序列号    | 到期日     | 经手人 |
| ---- | ---- | ---- | ---- | ---- |
| 2026-11-06 | auth.cloudnote.internal  | 2a7c9e01  | 2027-02-04 | 你     |
```

别小看这步「体力活」：第8章说过序列号是撤销时定位证书的凭据，台账就是你手工版的签发数据库。哪天某个服务要下线，翻台账就知道要动哪张证；哪天出了「内网有张来历不明的证书」的事故，台账就是审计的起点。

## 10.4 签发流水线：三个服务批量接入

notify 和 sync 重复同样三步。既然步骤固定，把它收进一个签发脚本 `issue-cert.sh`，从此「新服务接入」变成一条命令：

```bash
#!/bin/bash
# 用法: ./issue-cert.sh <域名>   在 /etc/cloudnote-ca 下执行
set -euo pipefail
DOMAIN=$1
CA=/etc/cloudnote-ca

# 扩展文件：只替换 SAN 一行
cat > "$CA/csr/$DOMAIN.ext" <<EOF
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = DNS:$DOMAIN
EOF

sudo openssl x509 -req \
  -in "$CA/csr/$DOMAIN.csr" \
  -CA "$CA/root.crt" -CAkey "$CA/private/root-key.pem" \
  -passin file:"$CA/private/KEY_PASS.txt" \
  -CAcreateserial -days 90 -sha256 \
  -extfile "$CA/csr/$DOMAIN.ext" \
  -out "$CA/issued/$DOMAIN.crt"

openssl verify -CAfile "$CA/root.crt" "$CA/issued/$DOMAIN.crt"
```

跑三遍，签发台账一目了然：

```bash
./issue-cert.sh auth.cloudnote.internal
./issue-cert.sh notify.cloudnote.internal
./issue-cert.sh sync.cloudnote.internal
for C in issued/*.crt; do openssl x509 -in "$C" -noout -subject -enddate; done   # 三张证一览
```

> [!NOTE] 想要台账与撤销？那是 openssl ca 的地盘
> `x509 -req` 是「无状态签发」：快，但不记录签过什么。工程级的 CA 用 `openssl ca` 子命令——它维护 index.txt（签发数据库）与 serial 文件，天然支持撤销与 CRL 生成。本书选轻量路线是为了看清原理；当你的内部证书超过几十张、或确有撤销需求时，再读 `man openssl-ca` 升级到数据库模式，概念你已经全部具备。

既然 extfile 是「审核」，签发前过一遍三问清单，别让审核形同虚设：

| 审核问题 | 怎么查 | 不过关的后果 |
| ---- | ---- | ---- |
| CSR 的域名和申请单一致吗 | `req -noout -subject` 比对 | 给错误的域名发了证 |
| SAN 是否覆盖全部访问地址 | extfile 逐行核对 | 部署后报域名不匹配 |
| 申请方真的持有私钥吗 | `req -noout -verify` | 冒领（第9章的自签章防的就是它） |

## 10.5 撤销：体系的后门与它的替代品

证书签出去就不是你的了——除非撤销。撤销（Revocation）指「这张证虽然没过期，但请所有人不再信任它」，触发场景：服务下线、疑似私钥泄露。轻量路线下撤销的姿势是把相关证书移出信任范围并记录在案；`openssl ca` 路线则可以生成 CRL（Certificate Revocation List，证书撤销列表）分发给客户端校验。撤销机制的完整生态第11章细讲，这里先记工程判断：

- **短有效期是最好的撤销**。90 天的证书，撤销的意义只剩「把 90 天缩到 0 天」；配合自动轮换，绝大多数撤销需求被「等它自然过期」消解。
- **私钥疑似泄露时不要等**。立即作废重签 + 换私钥，即便机制不完美，动作也要快（第7章验签泄露的处理同源）。
- 云笔记的轮换节奏：每 60 天重签一次（提前 30 天留缓冲），挂进 cron——证书到期忘续的事故从流程上消灭。

`openssl ca` 路线的撤销与 CRL 生成，预览两眼即可（第11章用 `verify -crl_check` 消费它）：

```bash
openssl ca -config openssl.cnf -revoke issued/auth.crt      # 登记撤销
openssl ca -config openssl.cnf -gencrl -out crl.pem          # 生成撤销列表
openssl crl -in crl.pem -noout -text                         # 查看列表内容
```

CRL 的本质又是一张 CA 签名的清单——签的仍然是「数据 + 身份」，第7章的签名思想第三次上岗。

> [!WARNING] 根私钥泄露没有「撤销」可救
> 服务器证书泄露，撤销或等过期都能兜住；**根私钥泄露则是灾难级**——攻击者可以签出任何人都无法分辨真伪的证书，唯一解法是换根（全员重新安装信任），相当于内网版的 DigiNotar 破产。所以根私钥的待遇必须是全家最高：加密、离线、最小接触面、使用留痕。第4章那句「随机数生成器是最不该优化的地方」，在 CA 这章可以续一句：根私钥是最不该省纪律的地方。

## 10.6 实验：三张证书下发部署

收尾动作：把 auth 服务的「私钥 + 证书 + 根证书」三件套送到它该在的位置，为第13章的部署做准备：

```bash
# 服务侧约定位置
sudo mkdir -p /etc/cloudnote/auth
sudo cp auth-key.pem /etc/cloudnote/auth/tls.key && chmod 600 /etc/cloudnote/auth/tls.key
sudo cp issued/auth.crt /etc/cloudnote/auth/tls.crt
sudo cp root.crt /etc/cloudnote/auth/root.crt   # 服务做客户端校验时用
```

验收四条，全绿即本关通过：

| 检查项 | 命令 | 期望 |
| ---- | ---- | ---- |
| 链有效 | `openssl verify -CAfile root.crt issued/auth.crt` | `OK` |
| SAN 正确 | `openssl x509 -in issued/auth.crt -noout -ext subjectAltName` | `DNS:auth.cloudnote.internal` |
| 扩展齐全 | `openssl x509 -in issued/auth.crt -noout -text \| grep -A1 "Key Usage"` | `CA:FALSE` + serverAuth |
| 根证书可分发 | 根证书拷给任意同事，verify 依旧 OK | 一致通过 |

最后一项展开说一句：**根证书的分发渠道要走可信路径**。它体积小、不含私钥，随便拷贝没有保密问题，但有「调包」问题——若有人在你分发的路上换成自己的根证书，整个内网信任体系就被人截了胡。云笔记的做法是第5章指纹公示的复用：把 root.crt 的 SHA-256 指纹发在团队 Wiki，每位成员导入前后各算一遍：

```bash
openssl x509 -in root.crt -noout -fingerprint -sha256
```

## 本章小结

- 自建 CA 一箭双雕：内网服务的信任中枢 + 公网证书体系的透视机
- 根证书是自签的 CA:TRUE 证书：`basicConstraints=critical,CA:TRUE,pathlen:0` + `keyUsage=keyCertSign,cRLSign`，有效期 10 年；根私钥加密深藏
- 签发主线 `x509 -req -CA -CAkey -extfile`：扩展以 CA 的 extfile 为准，**CSR 里申请的不自动生效**——这就是「审核」
- 服务器证书 90 天 + cron 轮换：短有效期是最可靠的「撤销」，忘续费事故从流程上消灭
- 轻量签发够教学；台账与撤销需求上来后升级 `openssl ca` 数据库模式，概念已备
- 签发前三问：域名对不对、SAN 全不全、申请方是否真持有私钥——审核不能只看命令跑没跑
- 根证书轮换走双根过渡：新旧并行分发、全员装齐后旧根退役；换锚是大工程，锚要稳
- 三件套下发纪律：私钥 600、证书 644、根证书单独放置——第13章部署的前置条件已就绪
