## 生活类比 - 中央厨房 VS 独立后厨

先设定场景

你是一个餐饮集团的老板，旗下有三个品牌：一家火锅店、一家日料店、一家西餐厅。现在你有两种运营模式。

### 1. 中央厨房模式（Monorepo）

你建了一个中央厨房，所有基础工作在这里完成。

中央厨房负责的事情：熬制基础高汤（共享工具库），统一采购调料和食材（共享依赖），制定食品安全标准（共享 ESLint/tsconfig），预处理半成品——比如把牛肉统一切片、统一腌制（共享类型定义和 DTO）。

三个品牌的前厨只需要做最后的组装和出品。火锅店拿到中央厨房切好的肉片直接摆盘，日料店拿到同一批牛肉做成和牛刺身，西餐厅用它做牛排。食材是同一批，标准是统一的，但最终的菜品形态完全不同。

这种模式下改一道基础配方会发生什么？假设中央厨房觉得酱油供应商不行，换了一家。这个变更只改一次——中央厨房的采购清单改一行，第二天三家店用的就都是新酱油了。不需要通知三个后厨分别去改自己的采购单，也不存在"日料店换了但火锅店忘了换"的情况。

### 2. 独立后厨模式（Multi-repo）

三家店各建自己的后厨，各自采购、各自备料、各自管理。

初期很爽。火锅店老板想研发新锅底，不用跟日料店商量，自己后厨直接搞。日料店想用一种很贵的进口酱油，不用管西餐厅同不同意。每家店完全自治，决策链极短。

但半年后问题开始浮现。首先是重复劳动：三家店都在自己熬高汤，而且因为配方略有不同（每个仓库的 tsconfig 各自维护），口感居然不一样。客户投诉说"你们火锅店的牛肉汤和上次在西餐厅喝到的味道不一样"——这就是 Multi-repo 里的依赖版本不一致。

然后是跨店协作的痛苦。集团决定推一个"三店联名套餐"（跨项目的功能联调），需要三家店共用一种特制酱料。中央厨房模式下，中央厨房出一条新产线就行。独立后厨模式下，你得把酱料配方分别发给三家店，让他们各自在自己的后厨里复刻。火锅店复刻得不错，日料店把糖的量减了（"我们店口味偏淡"），西餐厅直接把配方理解错了——同一个联名套餐，三个味道。这就是跨仓库的类型漂移。

最致命的是升级噩梦。中央厨房发现灶具有新一代产品，效率提升 30%（升级 Node.js 大版本 / TypeScript 大版本）。中央厨房模式下，换一次灶具，三家店同时受益。独立后厨模式下，你得去三家店分别换灶，而且每家店的厨房布局不同（各项目配置有差异），换的过程中可能出现"新灶具和旧排烟系统不兼容"的问题。三家店，三次踩坑，三倍工时。

### 3. 一个容易被忽略的点：中央厨房也有它的痛苦

中央厨房模式并不是完美的。最大的问题是过度耦合。火锅店想尝试一种实验性的低温慢煮工艺，需要改高汤的熬制方式。但中央厨房的高汤是三家店共用的，改了高汤可能影响日料店和西餐厅的出品。所以你要么在中央厨房里搞一条独立的实验产线（monorepo 里的独立构建配置），要么让火锅店的后厨自己单独熬一锅（绕过共享包直接实现）。如果这种"某家店想特立独行"的需求越来越频繁，中央厨房的管理复杂度会急剧上升。

独立后厨在这里的优势就体现出来了——日料店想搞分子料理？随便折腾，炸了厨房也只影响自己一家。

> [!TIP] 怎么选
> 问自己一个问题：你的三家店之间，共享的东西多还是各自独特的东西多？
> 如果三家店 70% 的基础食材和工艺是相同的，只是最后的出品形态不同——中央厨房能帮你省掉大量的重复工作，Monorepo 是对的。
> 如果三家店从食材到工艺到供应链都完全不同，强行共用一个中央厨房反而互相牵制——那就各自独立，Multi-repo 更合适。
> 现实中大多数软件项目介于两者之间，所以你会看到很多人选择 Monorepo 但在内部做好模块边界划分——相当于中央厨房按功能分了好几个独立工区，彼此通过标准接口协作，而不是所有东西搅在一口大锅里。

## pnpm和Turborepo的各自职责

用一个简单的分工来记：pnpm 管"东西在哪"，Turborepo 管"事情怎么做"。

pnpm 负责的是静态层面的组织工作。 它解决的问题是：这个项目有哪些包、它们之间的依赖关系是什么、每个包的 node_modules 里应该装哪些东西。当你在 packages/shared 里写了 export type User，然后在 apps/web 里 import { User } from '@monorepo/shared' 能正确解析到那个文件——这是 pnpm workspace 在做的事情。它通过符号链接把 workspace 内部的包互相串起来，同时保证外部依赖被正确地安装到正确的位置（pnpm 的严格隔离模式）。简单说，pnpm 搭建的是依赖关系的物理拓扑——谁连谁、谁引用谁。

Turborepo 负责的是动态层面的执行调度。 pnpm 把包之间的关系网搭好了，但当你说"帮我构建整个项目"的时候，pnpm 并不知道应该先构建哪个包、后构建哪个包、哪些包可以并行构建、哪些结果可以跳过不构建。这些全是 Turborepo 的事。它读取 turbo.json 里的任务定义和依赖关系图，算出最优执行顺序，并且用内容哈希做缓存——如果某个包及其依赖的源码没有变化，直接复用上一次的构建产物。

用中央厨房的比喻来说

pnpm 是厨房的仓储物流系统。它决定了：冰箱里有哪些食材、哪个调料在哪个架子上、火锅店的肉片和日料店的鱼生分别存放在什么位置、它们之间的存放规则是什么（不能串味 = 依赖隔离）。它不关心你什么时候做菜、做菜的顺序是什么，它只管"东西放对了地方，要的时候能找到"。

Turborepo 是厨房的出餐调度系统。它决定了：先备料再炒菜再装盘（任务依赖顺序），三个灶台可以同时开火（并行执行），上次做过的红烧肉还热着不用重做（缓存命中），今天只有火锅店有订单所以日料和西餐不用开工（--filter 选择性构建）。它不关心食材存在哪里，它只管"用最高效的方式把菜做出来"。

一个具体的例子看两者的交接点

当你在终端输入 turbo run build 的时候，发生的事情是这样的：

第一步，Turborepo 扫描所有包的 package.json，发现 apps/web 的 build 依赖 packages/shared 的 build（因为 turbo.json 里配了 dependsOn: ["^build"]）。这个依赖关系的声明是在 package.json 的 dependencies 里写的 "@monorepo/shared": "workspace:*"——这是 pnpm 的世界。

第二步，Turborepo 算出执行顺序：先构建 shared，再构建 web 和 api（web 和 api 可以并行）。这个排序逻辑完全是 Turborepo 在做，pnpm 不参与。

第三步，Turborepo 检查缓存。shared 包的源码哈希和上次一样，缓存命中，跳过构建。这一步也是 Turborepo 的独有能力，pnpm 完全没有缓存机制。

第四步，Turborepo 执行 pnpm run build（实际上是在各个包目录下调用 pnpm 来触发 scripts）。这里又回到了 pnpm 的领地——pnpm 负责启动 TypeScript 编译器，把 .ts 编译成 .js，输出到正确的目录。

第五步，apps/web 在构建时通过 import '@monorepo/shared' 引用 shared 的产物。这个模块解析走的是 pnpm 建立的符号链接——Turborepo 完全不介入模块解析，它只管"什么时候跑什么命令"。

所以两者的边界很清晰：pnpm 是基础设施层（依赖安装、包链接、脚本执行），Turborepo 是编排层（任务调度、缓存、并行、过滤）。没有 pnpm，Turborepo 不知道包之间的依赖关系，也不知道怎么安装外部库。没有 Turborepo，pnpm 只能一个包一个包地串行构建，没有缓存，没有智能排序。两者配合才是完整的 monorepo 体验。

## Monorepo 与 Docker

表面上它们解决的问题完全不同——Monorepo 管的是"代码怎么放"，Docker 管的是"程序怎么跑"——但在设计哲学上确实有几个深层共鸣。

### 1. 镜像分层 vs 包依赖

Docker 镜像是一层一层叠起来的：base image → 装依赖 → 拷代码 → 配环境变量。每一层只描述"我比上一层多了什么"。Monorepo 里的包也是这个思路：packages/tsconfig 定义基础配置，packages/eslint-config 定义代码规范，各个 app 只写自己"差异化"的部分然后继承。两者都在用"分层复用"来消灭重复。

Docker Compose 编排 vs Turborepo 编排

你用 docker-compose.yml 定义一组服务（web、api、redis、postgres），声明它们之间的依赖关系（depends_on），然后一条命令全部启动。Turborepo 的 turbo.json 做的是几乎同样的事：定义一组任务（build、test、lint），声明依赖（dependsOn: ["^build"]），一条 turbo run build 按拓扑序执行。两者的核心思想都是"声明依赖关系图，让工具帮你算执行顺序"。

### 2. 缓存机制

Docker 的构建缓存是"如果这一层的输入没变，直接复用上一轮的输出"。Turborepo 的缓存也是同一个原理——基于输入文件的内容哈希来判断是否跳过构建。你改了 packages/shared 的一个文件，Turborepo 知道只有依赖 shared 的包需要重新构建，其他的全部走缓存。这和 Docker 的"某一层变了，只重建这一层及其之后的层"是同构的。

### 3. 本质区别

Docker 隔离的是运行时——每个容器是一个独立的进程空间，互不干扰。Monorepo 组织的是开发时——所有代码在同一个仓库里共享同一个开发上下文。

换句话说，Docker 回答的问题是"怎么让多个应用安全地跑在同一台机器上"，Monorepo 回答的问题是"怎么让多个项目高效地共享同一套代码"。一个是运行时的隔离边界，一个是开发时的协作边界。

如果要打个比方：Docker 像是一栋楼里的独立单元——每个住户有自己的水电表、自己的门锁，互不影响。Monorepo 像是这栋楼的物业管理方式——所有住户共用一个管理后台、一套维修团队、一份住户公约。你可以用 Monorepo 管理代码，同时用 Docker 部署每个应用，它们在不同层面解决不同的问题，完全不冲突。

实际上大型项目经常是两者结合：Monorepo 管源码组织和开发工作流，Docker 管每个 app 的构建产物和运行时环境。Turborepo 负责"哪些代码需要重新编译"，Docker 负责"编译完的代码怎么打包成可部署的镜像"。它们是你工程化链条上的上下游关系。
