# 第8章：搜索与替换高级技巧

> "Measuring programming progress by lines of code is like measuring aircraft building progress by weight." —— Bill Gates

但"找到 bug 的速度"呢？那大概才是真正该度量的东西。而搜索能力，正是决定这个速度的核心变量。

如果你只用过 `Ctrl+F` 输入一个字符串，那你大概只用了 VSCode 搜索系统 10% 的功力。这一章我们从**最容易踩坑的地方**讲起：VSCode 里其实藏着两个不同的正则引擎，搞混它们，你会写出"看起来完全正确却搜不到任何东西"的正则。

## 8.1 先搞清楚：你面对的是两个引擎

这是本章最重要的一节。VSCode 的搜索分两个入口，底层引擎**完全不同**：

| | 编辑器内查找 `Ctrl+F` / `Ctrl+H` | 跨文件搜索 `Ctrl+Shift+F` / `Ctrl+Shift+H` |
| --- | --- | --- |
| 引擎 | TypeScript/JavaScript 正则 | ripgrep（Rust `regex` crate） |
| 速度 | 单文件，无感 | 极快，百万行项目秒出 |
| 先行断言 `(?=...)` `(?!...)` | ✅ 支持 | ❌ 默认不支持 |
| 后行断言 `(?<=...)` `(?<!...)` | ✅ 支持 | ❌ 默认不支持 |
| 向后引用 `\1` | ✅ 支持 | ❌ 默认不支持 |
| 跨行匹配 | ✅ 支持 | ⚠️ 有条件支持（见 8.3 陷阱） |
| 捕获组 + 替换引用 `$1` | ✅ | ✅ |

为什么跨文件搜索不用功能更全的 JS 正则？因为 Rust 的 `regex` crate 使用**有限自动机**而非回溯引擎，这保证了线性时间复杂度——代价是牺牲了环视（lookaround）和向后引用这类需要"回头看"的特性。

这是一个典型的工程权衡：**要功能，还是要性能。**

三种应对策略：

1. **单文件重构**：用 `Ctrl+F`，放心写环视和 `\1`
2. **跨文件搜索确实需要环视**：老版本需要显式打开设置

```jsonc
{
    // 旧版本需要显式打开；较新版本已按模式自动选用 PCRE2
    // 让 ripgrep 使用 PCRE2 引擎，启用环视与向后引用（速度会变慢）
    "search.usePCRE2": true
}
```

> ⚠️ 版本差异提示：较新的 VSCode 在检测到模式含环视/向后引用时会自动切到 PCRE2，而老版本直接报"正则无效"。如果你的设置面板里搜不到 `search.usePCRE2`，说明该版本已自动处理，不必纠结。

3. **需要复杂模式的跨文件搜索**：直接用 `rg --pcre2` 命令行（见 8.7）

**一个立即能用的推论**：`\bfoo\b` 这种词边界写法两个引擎都支持，但 `(?<!\w)foo(?!\w)` 只在 `Ctrl+F` 里可靠。写正则前先问自己："我这是在哪个框里？"

## 8.2 搜索面板全功能解析

打开搜索面板：`Ctrl+Shift+F`（macOS：`⌘+Shift+F`）。

### 三个修饰开关

| 图标 | 功能 | 说明 |
| ------ | ------ | ------ |
| `Aa` | 大小写敏感 | 区分 `hello` 与 `Hello` |
| `ab\|` | 全词匹配 | `cat` 不再匹配 `concat` |
| `.*` | 正则表达式 | 快捷键 `Alt+R` |

外加一个藏在设置里的智能模式：

```jsonc
{
    // 全小写时忽略大小写；只要出现大写就区分大小写
    // 比手动切换 Aa 图标舒服得多，强烈建议开启
    "search.smartCase": true
}
```

### 文件过滤：glob 语法，不是正则

`files to include` / `files to exclude` 两个框用的是 **glob 通配符**，规则很简单：

- 多个模式用**英文逗号**分隔
- 路径**必须用正斜杠** `/`，即使在 Windows 上
- `**` 匹配任意层级目录，`*` 只匹配单层
- `!` 前缀表示"在包含里做排除"

```text
# 只搜两个源码目录下的 ts 文件
src/**/*.ts, packages/**/*.ts

# 搜所有 ts，但排除测试和类型声明
**/*.ts, !**/*.test.ts, !**/*.d.ts

# 用 ./ 前缀：只搜"当前工作区文件夹"自己的内容（多根工作区必备）
./src/**

# 排除构建产物与依赖
**/node_modules/**, **/dist/**, **/coverage/**
```

面板右侧的 **`...`** 菜单里还藏着几个关键开关：`Use Exclude Settings and Ignore Files`（是否应用 `search.exclude` 与 `.gitignore`）、`Search On Type`（边输边搜）、`Preserve Case`（替换时保留大小写）。搜不到预期文件时，先来这里检查——这是新手最常踩的坑。

### 值得改的搜索设置

```jsonc
{
    // 跨文件搜索的排除规则（会继承 files.exclude；不控制资源管理器显示）
    "search.exclude": {
        "**/node_modules": true,
        "**/dist": true,
        "**/coverage": true,
        "**/*.min.js": true
    },
    // 是否遵循 .gitignore（默认 true；想搜 node_modules 时把它关掉或关掉那个图标）
    "search.useIgnoreFiles": true,
    // 额外遵循用户全局 gitignore 与父目录的 ignore 文件
    "search.useGlobalIgnoreFiles": false,
    "search.useParentIgnoreFiles": false,
    // 结果数量上限，超出会提示"结果被截断"（默认 20000）
    "search.maxResults": 20000,
    // 是否跟随符号链接——远程/容器开发时这可能是性能杀手（默认 true）
    "search.followSymlinks": false,
    // 边输边搜及其防抖时间
    "search.searchOnType": true,
    "search.searchOnTypeDebouncePeriod": 300,
    // 结果排序：按类型/修改时间/文件名
    "search.sortOrder": "modified",
    // 结果过多时自动折叠，一眼看全局
    "search.collapseResults": "alwaysCollapse",
    // 显示行号，跨文件替换时极有用
    "search.showLineNumbers": true,
    // 替换前显示 diff 预览（默认开启，别关掉它）
    "search.useReplacePreview": true
}
```

> 📌 顺手记一笔：`Ctrl+T`（⌘+T）是全局符号搜索，靠语言服务器而非文本匹配。找 `handleSubmit` 这种函数名，用它比 `Ctrl+Shift+F` 精准得多。

## 8.3 正则搜索的实用模式

下面这些是真实开发中反复用得上的模式。**先说清各自该在哪个框里用**——这是上一版教程里最容易误导人的地方。

### 技术债务清单（跨文件 ✅）

```
(TODO|FIXME|HACK|XXX)\b.{0,80}
```

配合 `files to include` 限定 `src/**`，一次列出全项目的待办。想直接点进去？用后面的搜索编辑器。

### 忘记删除的调试语句（跨文件 ✅）

```
console\.(log|debug|info|warn)\(|debugger\b
```

注意 `\.` 必须转义，否则 `.` 会匹配任意字符，`consolelog` 也算命中。

### 删除行尾空白 / 找空行（单文件 ✅）

```
[ \t]+$        # 行尾空格或制表符，替换框留空
^\s*$\n        # 连续空行，替换为 \n
```

`^` 和 `$` 在两个引擎里都是**按行**锚定，行为符合直觉。

### 硬编码的 URL 与 IP（跨文件 ✅，安全审计常用）

```
https?://[^\s'"`)]+|(\d{1,3}\.){3}\d{1,3}
```

### 找重复代码块（单文件 ✅，跨文件 ❌）

```
(\w+\s*:\s*[^;]+;)[\w\W]*?\1
```

**这一条是本章最重要的反面教材**，它需要向后引用 `\1`，所以只能在 `Ctrl+F` 里用（或开启 PCRE2）。而且注意我写的是 `[\w\W]` 而不是教科书里最常见的 `[\s\S]`——原因见下面这个陷阱。

> ⚠️ **跨行陷阱**：ripgrep 默认按行搜索，VSCode 只在模式里出现 `\n`、`\r`、`\W` 这类明确可能跨行的构造时，才把它切成多行模式。也就是说 **`[\s\S]` 在跨文件搜索里常常匹配不到换行，而 `[\w\W]` 可以**。跨行匹配失败的第一个排查动作：把 `[\s\S]` 换成 `[\w\W]`，或者显式写 `\n`。
>
> 顺带一提，`(?:...)` 非捕获组里如果内含换行，也需要多行模式；`(?:[\w\W]*?)` 是稳妥写法。

### 关于"用正则找未使用的 import"

别这么干。

```
^import\s+.*\s+from\s+['"].*['"];?\s*$
```

这种模式只能列出所有 import，判断"是否被使用"本质上需要作用域分析，正则是做不到的。正确工具是 ESLint 的 `no-unused-vars`、TypeScript 的 `"noUnusedLocals": true`，或者直接用 `Organize Imports`（`Shift+Alt+O`）。**正则搜索的边界是"文本形状"，不是"语义"** ——认清这条边界能省下很多痛苦。

## 8.4 跨文件批量替换的安全操作

批量替换是全章风险最高的操作：一次点击可能改掉 60 个文件。VSCode 提供的安全网，按重要性排序：

**第一，永远在干净的工作区上操作。** `git status` 确认没有未提交改动。改坏了 `git checkout .` 一秒回滚——这比任何编辑器内置的"撤销"都可靠。

**第二，先看预览再点替换。** `search.useReplacePreview`（默认开启）会在你点击全部替换前展示每个文件将要发生的 diff。VSCode 还会在最后弹出"影响 N 个文件"的确认框。

**第三，把范围收到最小。** 先用 `files to include` 限定目录，用 `!` 排除测试和 vendor，再执行替换。宁可分三次替换，也不要一次改掉整个仓库。

**第四，逐条处理而非全量。** 每个结果右侧有单独的替换按钮（鼠标悬停会出现），对不确定的模式逐条点，剩下的一次性处理。

替换框里的引用语法：

| 写法 | 含义 |
| ------ | ------ |
| `$1` … `$99` | 引用第 N 个捕获组 |
| `$&` | 引用整个匹配 |
| `$<name>` | 引用命名捕获组 `(?<name>...)`（跨文件搜索支持；编辑器内查找请改用编号组） |
| `\u$1` | 捕获组首字母大写 |
| `\l$1` | 捕获组首字母小写 |
| `\U$1` | 捕获组全大写 |
| `\L$1` | 捕获组全小写 |
| `\\` | 要插入一个字面反斜杠 |

三个实战改写（都是"简单情形"，务必人工抽查）：

**① `let x =` → `const x =`**

```
搜索：\blet\s+(\w+)\s+=
替换：const $1 =
```

`\b` 防止误伤 `delete`、`let` 出现在字符串里的情况。

**② ESM import → CommonJS require**

```
搜索：^import\s+\{([^}]+)\}\s+from\s+['"]([^'"]+)['"];?
替换：const {$1} = require('$2');
```

**③ 函数声明 → 箭头函数常量**

```
搜索：function\s+(\w+)\s*\(([^)]*)\)\s*\{
替换：const $1 = ($2) => {
```

这个会破坏 `this` 绑定和函数提升，只适合纯工具函数批量转换——**先看 diff，再点全部替换**。

另外，`...` 菜单里的 `Preserve Case` 是个被严重低估的功能：搜索 `Foo` 替换为 `Bar` 时，它会自动把 `foo` 换成 `bar`、`FOO` 换成 `BAR`、`fooBar` 换成 `barBaz`。做重命名时比手写大小写变体快得多。

## 8.5 搜索编辑器：把搜索结果当文件编辑

这是 VSCode 里少有人用的"大杀器"。它的本质是：把搜索结果渲染成一个可读写的临时文件，让你用**编辑器的全部能力**（多光标、查找替换、列选择）去操作搜索结果。

打开方式：

- `Ctrl+Shift+P`（⌘+Shift+P）→ **Search Editor: Open New Search Editor**
- 或在普通搜索面板里 `Ctrl+Enter`（⌘+Enter）把结果丢进搜索编辑器

保存的文件扩展名是 `.code-search`，可以提交进仓库当"技术债务清单"。

### 上下文行数：搜索视图做不到，这里可以

搜索结果默认只显示匹配行，判断不了上下文就得点开文件。搜索编辑器有专门的上下文设置：

```jsonc
{
    // 新建搜索编辑器时，每个匹配默认带出前后各 N 行上下文（默认 1）
    "search.searchEditor.defaultNumberOfContextLines": 3
}
```

也可以用命令 **Search Editor: Increase/Decrease Context Lines** 临时调整，效果类似 ripgrep 的 `-C 3`。

### 编辑后回写：Apply Changes

在搜索编辑器里直接修改内容，然后 `Ctrl+Shift+P` → **Search Editor: Apply Changes**，改动会按文件与行号回写到原始文件。这就是"跨文件精细化重构"最顺手的路径：**先人工筛掉不要的行，再一次性应用。**

其他实用细节：

- `search.searchEditor.reusePriorSearchConfiguration`：新建时沿用上一次的条件，不用重填
- 双击结果行的行为由 `search.searchEditor.doubleClickBehaviour` 控制（`selectLine` 适合配合多光标）
- 搜索编辑器是**一次性快照**，原文件变了它不会自动刷新——先应用再重新搜索

## 8.6 实战：一次真实的重构

场景：接手老项目，要把回调风格迁移到 async/await。

**第一步：只侦察，不动手**

```
搜索：\w+\(\s*(async\s+)?function\s*\(\s*(err|error)\s*,
范围：src/**/*.js，排除 **/*.test.js, **/vendor/**
```

结果直接 `Ctrl+Enter` 开进搜索编辑器，加上 3 行上下文，先在一份文件里看完全部战场。

**第二步：分类**

发现三类模式：`fs.readFile`、`request.get`、`db.query`。分别处理，**不要试图写一个万能正则**——那只会让你不敢点替换。

**第三步：一类一类替换，一类一次提交**

```
搜索：fs\.readFile\(\s*([^,]+),\s*function\s*\(err,\s*(\w+)\)\s*\{
替换：const $2 = await fs.promises.readFile($1);
```

每替换一类就跑一次测试、提交一次 git。出错时能立刻定位是哪一类改坏了。

**第四步：验证残留**

```
搜索：function\s*\(err
```

结果为 0 才算完成。注意这一步是"反向验证"——搜的是**本该消失的东西**，比肉眼检查可靠得多。

**第五步：别忘了函数体本身**

正则只能改函数头和右括号，函数体里的 `if (err) return next(err)` 得人工处理。任何说"正则能全自动完成这次迁移"的方案都值得怀疑。

## 8.7 进阶：直接用 ripgrep 命令行

VSCode 自带 `rg` 二进制（在安装目录的 `@vscode/ripgrep` 模块里，Windows 下为 `rg.exe`），你也可以全局装一个。命令行的价值在于：跨行、环视、输出格式全都可控，而且不受 UI 限制。

```bash
# 前后 3 行上下文（= search.searchEditor.defaultNumberOfContextLines）
rg -C 3 "TODO" src/

# 只要文件名
rg -l "console\.log" -g "*.js"

# 显式启用多行匹配，这时 [\s\S] 才真的跨行
rg -U --multiline-dotall "function\s+\w+\([\s\S]*?\)" src/

# PCRE2：环视与向后引用（= 需要 search.usePCRE2 才能做的事）
rg --pcre2 "(?<=export\s)class\s+\w+"

# 行尾空白：先数一遍，确认影响面
rg -n '[ \t]+$' -g '!*.md' src/ | wc -l

# 原地替换：rg -r 只把替换结果打印到 stdout，不会写回文件；
# 真要跨文件改写，用 VSCode 搜索编辑器 + Apply Changes 更安全
rg -r 'const $1 =' "\blet\s+(\w+)\s+=" src/

# 忽略 .gitignore，把 node_modules 也纳入搜索
rg --no-ignore --hidden "createRequire" node_modules/

# 限制单文件大小，避免把巨型 JSON 读进内存
rg --max-filesize 1M "deprecated" .
```

顺带说明两个 GUI 与 CLI 的行为差异：`rg` 默认不搜 `.hidden` 文件，VSCode 搜索视图也一样；`rg` 的 glob 用 `-g`，VSCode 用 `files to include`，语法一致。

## 8.8 排错速查表

| 现象 | 原因 | 处理 |
| ------ | ------ | ------ |
| 明明有这段代码却搜不到 | 被 `.gitignore` 或 `search.exclude` 排除 | 关掉 `...` 里的 ignore 图标 |
| 正则报红 / "无效的正则" | 跨文件搜索用了环视或 `\1` | 改用 `Ctrl+F`，或开 PCRE2 / `rg --pcre2` |
| `[\s\S]` 匹配不到跨行内容 | 未触发 ripgrep 多行模式 | 换成 `[\w\W]`，或命令行 `-U` |
| 结果只显示 2 万条 | `search.maxResults` 上限 | 缩小 `files to include` 范围，比调大上限更明智 |
| 搜索很慢、CPU 高 | `search.followSymlinks` 或超大文件 | 关掉符号链接跟随，排除构建产物 |
| 替换后少了捕获内容、多出数字 | `$1` 后紧跟数字被解析成更大的组号（如 `$10` 被当成第 10 组）；`$0` / `$&` 表示整个匹配，`$01` 会变成“整个匹配 + 1” | 明确写 `$10` 引用第 10 组；需要“组 1 + 字面数字”时调整替换顺序，或分两次替换 |
| 找不到 node_modules 里的定义 | 同上 ignore 规则 | 临时开启 ignore 图标，或搜 "Open Editors" 范围 |

📋 **本章小结**

- VSCode 有**两个正则引擎**：`Ctrl+F` 用 JS 正则（支持环视和 `\1`），`Ctrl+Shift+F` 用 ripgrep（快，但默认不支持环视和向后引用）
- 跨文件搜索里 `[\s\S]` 常常不能跨行，`[\w\W]` 更可靠；真要跨行就开 PCRE2 或用 `rg -U`
- `files to include/exclude` 是 **glob**，逗号分隔、正斜杠、`!` 取反、`./` 限定当前文件夹
- `search.smartCase`、`search.showLineNumbers`、`search.followSymlinks` 是三个高价值设置
- 批量替换的安全网顺序：干净 git 工作区 → 缩小范围 → 看 Replace Preview → 分类替换、分类提交
- 替换框用 `$1` 引用捕获组，`\U$1` 转大写，`Preserve Case` 自动处理大小写变体
- **搜索编辑器**把结果变成可编辑文件，配合 `Apply Changes` 和上下文行数，是跨文件精细重构的最优解
- 正则只处理"文本形状"，语义级问题（未使用导入、类型错误）交给 linter
