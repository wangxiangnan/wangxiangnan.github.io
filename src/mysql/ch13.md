# 第13章 索引与查询优化

**生活类比：** 想象你有一本50万字的百科全书，没有目录。想找"量子力学"这个词条？你只能从第一页翻到最后一页——这就是没有索引的数据库。索引就是数据库的"目录"，让MySQL能够快速定位数据，而不是傻傻地全表扫描。

## 13.1 索引的本质：B+Tree

数据库索引的核心数据结构是 **B+Tree**（B+树）。你可以把它理解为"二叉搜索树的Pro Max版"——它不是一棵瘦高的树，而是一棵矮胖的树。每个节点可以存放多个键值，树的层数极少（通常3-4层就能索引上亿条记录）。

B+Tree的关键特性：

- **有序存储**：叶子节点按顺序排列，范围查询非常高效
- **叶子节点链表**：所有叶子节点通过指针串联，适合范围扫描
- **非叶子节点只存键**：真正的数据行只存在叶子节点
- **路径等长**：从根到每个叶子节点的距离相同，查询时间稳定

> [!TIP] 提示
> 一棵3层的B+Tree，假设每个节点能存1000个键值，就能索引 1000 x 1000 x 1000 = 10亿条记录，而查找最多只需要3次磁盘I/O。这就是索引的威力。

## 13.2 索引类型一览

MySQL支持多种索引类型，各有用武之地：

**B+Tree索引** —— 最常用的默认索引类型，适用于等值查询和范围查询：

```sql
-- 创建一张示例表
CREATE TABLE employees (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100),
    department VARCHAR(50),
    salary DECIMAL(10,2),
    hire_date DATE
);

-- 创建普通B+Tree索引
CREATE INDEX idx_name ON employees(name);
```

**Hash索引** —— 只适用于等值查询（= 或 IN），不支持范围查询。Memory引擎默认使用Hash索引：

```sql
-- Memory引擎表默认使用Hash索引
CREATE TABLE session_cache (
    session_id VARCHAR(64),
    user_data TEXT,
    INDEX idx_session (session_id) USING HASH
) ENGINE=MEMORY;
```

**全文索引(FULLTEXT)** —— 用于全文搜索，支持自然语言搜索和布尔搜索：

```sql
-- 为文章内容创建全文索引
CREATE TABLE articles (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200),
    content TEXT,
    FULLTEXT INDEX ft_content (title, content)
) ENGINE=InnoDB;

-- 使用全文搜索
SELECT * FROM articles
WHERE MATCH(title, content) AGAINST('MySQL 索引优化' IN NATURAL LANGUAGE MODE);
```

**空间索引(SPATIAL)** —— 用于地理空间数据：

```sql
-- 创建包含地理信息的表
CREATE TABLE locations (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100),
    position POINT NOT NULL,
    SPATIAL INDEX idx_position (position)
) ENGINE=InnoDB;
```

## 13.3 创建索引的多种方式

```sql
-- 方式一：CREATE INDEX
CREATE INDEX idx_email ON employees(email);

-- 方式二：ALTER TABLE ADD INDEX
ALTER TABLE employees ADD INDEX idx_dept (department);

-- 方式三：建表时直接创建
CREATE TABLE products (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10,2),
    INDEX idx_price (price),
    UNIQUE INDEX idx_name (name)
);
```

> [!TIP] 提示
> 这三种方式效果一样，选哪个纯粹看你的习惯。不过在生产环境中，对大表加索引建议使用 `ALTER TABLE ... ADD INDEX` 配合 `ALGORITHM=INPLACE` 来减少锁表时间。

## 13.4 复合索引与最左前缀原则

复合索引（联合索引）是在多个列上建立的索引。这里有一个非常重要的概念：**最左前缀原则**。

打个比方：通讯录是按"姓-名"排序的。你可以通过姓来查找（用到索引），也可以通过"姓+名"来查找（用到索引），但单独通过"名"来查找就用不到索引了。

```sql
-- 创建复合索引：(department, salary, hire_date)
CREATE INDEX idx_dept_salary_date
ON employees(department, salary, hire_date);

-- 能用到索引（遵循最左前缀）
SELECT * FROM employees WHERE department = '技术部';
SELECT * FROM employees WHERE department = '技术部' AND salary > 15000;
SELECT * FROM employees WHERE department = '技术部' AND salary = 20000 AND hire_date > '2023-01-01';

-- 用不到索引（跳过了最左列）
SELECT * FROM employees WHERE salary > 15000;
SELECT * FROM employees WHERE hire_date > '2023-01-01';

-- 特殊情况：用到了索引但效率降低（中间列被跳过）
SELECT * FROM employees WHERE department = '技术部' AND hire_date > '2023-01-01';
```

> [!WARNING] 注意
> 最左前缀原则是复合索引最容易踩坑的地方。建索引时一定要想清楚查询模式，把区分度高的列放左边，经常一起查询的列放在一起。

## 13.5 唯一索引 vs 普通索引

```sql
-- 普通索引：允许重复值
CREATE INDEX idx_dept ON employees(department);

-- 唯一索引：不允许重复值（NULL除外）
CREATE UNIQUE INDEX idx_email ON employees(email);

-- 插入测试
INSERT INTO employees(name, email, department, salary)
VALUES ('张三', 'zhangsan@example.com', '技术部', 15000);

-- 下面这行会报错：Duplicate entry 'zhangsan@example.com'
INSERT INTO employees(name, email, department, salary)
VALUES ('李四', 'zhangsan@example.com', '市场部', 12000);
```

唯一索引不仅是性能优化工具，更是数据完整性的保障。当你需要确保某列（或某几列组合）的值唯一时，唯一索引是最佳选择。

## 13.6 覆盖索引（Covering Index）

当查询所需的所有列都包含在索引中时，MySQL可以直接从索引中返回数据，无需回表查询数据行——这就是覆盖索引。

```sql
-- 假设已有索引 idx_dept_salary_date (department, salary, hire_date)

-- 覆盖索引查询：所需的 department, salary 都在索引中
EXPLAIN SELECT department, salary FROM employees WHERE department = '技术部';
-- Extra 列会显示 "Using index"，说明使用了覆盖索引

-- 非覆盖索引：还需要 name 列，得回表
EXPLAIN SELECT name, salary FROM employees WHERE department = '技术部';
-- Extra 列没有 "Using index"
```

> [!TIP] 提示
> 如果你发现某个查询特别频繁，可以考虑建一个"胖索引"把所有查询列都包进去。覆盖索引能显著减少随机I/O，是性能优化的利器。

## 13.7 EXPLAIN 详解

EXPLAIN 是MySQL的"X光机"，能让你透视查询的执行计划：

```sql
EXPLAIN SELECT * FROM employees WHERE department = '技术部' AND salary > 15000;
```

核心列的含义：

| 列名 | 含义 | 关注点 |
|------|------|--------|
| **type** | 访问类型 | 从好到差：system > const > eq_ref > ref > range > index > ALL |
| **key** | 实际使用的索引 | NULL表示没走索引，赶紧优化 |
| **rows** | 预估扫描行数 | 越小越好 |
| **filtered** | 过滤比例 | 越接近100%越好 |
| **Extra** | 附加信息 | Using index(覆盖索引), Using filesort(需优化), Using temporary(需优化) |

```sql
-- 好的执行计划示例
EXPLAIN SELECT department, salary FROM employees
WHERE department = '技术部' ORDER BY salary;
-- type: ref, key: idx_dept_salary_date, Extra: Using index

-- 差的执行计划示例
EXPLAIN SELECT * FROM employees WHERE name LIKE '%张';
-- type: ALL, key: NULL, rows: 全表行数
```

> [!WARNING] 注意
> 看到 type=ALL 和 rows=全表行数 时，要警觉——这意味着全表扫描。在小表上没关系，但在百万级的大表上就是性能杀手。

## 13.8 索引失效的常见场景

这些是面试高频题，更是生产环境的常见坑：

```sql
-- 场景1：隐式类型转换
-- 假设 phone 是 VARCHAR 类型
SELECT * FROM users WHERE phone = 13800138000;    -- 索引失效！
SELECT * FROM users WHERE phone = '13800138000';   -- 正确写法

-- 场景2：对索引列使用函数
SELECT * FROM employees WHERE YEAR(hire_date) = 2023;     -- 索引失效！
SELECT * FROM employees WHERE hire_date >= '2023-01-01'
                       AND hire_date < '2024-01-01';       -- 正确写法

-- 场景3：LIKE 以通配符开头
SELECT * FROM employees WHERE name LIKE '%三';     -- 索引失效！
SELECT * FROM employees WHERE name LIKE '张%';     -- 可以用索引

-- 场景4：OR 条件中有非索引列
SELECT * FROM employees WHERE department = '技术部' OR salary > 20000;
-- 如果 salary 没有索引，整个条件可能走全表扫描

-- 场景5：NOT IN / NOT EXISTS（部分情况）
SELECT * FROM employees WHERE department NOT IN ('技术部', '市场部');
-- 优化器可能选择全表扫描而不是走索引

-- 场景6：索引列参与运算
SELECT * FROM employees WHERE salary + 1000 > 20000;  -- 索引失效！
SELECT * FROM employees WHERE salary > 19000;           -- 正确写法
```

> [!WARNING] 注意
> 索引失效是SQL性能问题的头号元凶。写完SQL后，养成用EXPLAIN检查执行计划的习惯，就像程序员写完代码要跑单元测试一样。

## 13.9 索引设计原则与权衡

**索引不是越多越好。** 每个索引都是"甜蜜的负担"——查询快了，但写入（INSERT/UPDATE/DELETE）变慢了，磁盘空间也变大了。

核心设计原则：

1. **选择性高的列优先**：选择性 = 不重复值的数量 / 总行数。性别（男/女）选择性差，身份证号选择性好
2. **WHERE、JOIN、ORDER BY、GROUP BY 的列考虑加索引**
3. **复合索引优于多个单列索引**：一个 (a, b, c) 的复合索引胜过 (a)、(b)、(c) 三个单列索引
4. **字符串用前缀索引**：对 VARCHAR(255) 的列，索引前20个字符通常就够了

```sql
-- 前缀索引：只索引字符串的前N个字符，节省空间
CREATE INDEX idx_name_prefix ON employees(name(10));

-- 查看索引的选择性
SELECT COUNT(DISTINCT name) / COUNT(*) AS selectivity FROM employees;

-- 删除不再需要的索引
DROP INDEX idx_dept ON employees;
```

## 小结

本章是性能优化的基础。索引就像一把双刃剑：用好了能让查询飞起，用多了会让写入变慢。关键是要理解B+Tree的工作原理，掌握最左前缀原则，避开索引失效的陷阱，并且养成用EXPLAIN分析执行计划的好习惯。
