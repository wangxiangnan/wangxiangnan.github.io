## 15.1 为什么需要 HTTPS

HTTP 是明文传输的。你和服务器之间的所有数据——密码、银行卡号、私人聊天——都可能在传输途中被看到、被修改、甚至被伪造。这就像在明信片上写情书，邮递员和分拣员都能看到内容。

HTTP 面临三大安全威胁：

1. **窃听（Eavesdropping）**：中间人读取传输内容。咖啡店的免费 Wi-Fi 上，旁边的人可能正用 Wireshark 看你的 HTTP 请求。
2. **篡改（Tampering）**：中间人不仅看，还改。某些运营商就曾在 HTTP 响应中注入广告（俗称「运营商劫持」）。
3. **冒充（Impersonation）**：你以为在跟 `bank.com` 通信，实际对面是伪装成它的钓鱼服务器。

**HTTPS（HTTP over TLS）**用加密解决窃听，用消息认证码解决篡改，用数字证书解决冒充。它是 HTTP 的装甲，而 TLS（Transport Layer Security）就是装甲的主体——一层垫在 TCP 与 HTTP 之间的加密协议。

## 15.2 TLS 1.3 握手详解

逐步骤看 TLS 1.3 的握手过程。

**第一步：ClientHello**

```
ClientHello:
  Version: TLS 1.2 (0x0303)  ← 为了兼容老设备，字段仍写 1.2
  Random: 7a 3f 2b 8c ... (32 bytes)
  Cipher Suites:
    TLS_AES_256_GCM_SHA384 (0x1302)
    TLS_CHACHA20_POLY1305_SHA256 (0x1303)
    TLS_AES_128_GCM_SHA256 (0x1301)
  Supported Groups: x25519, secp256r1, secp384r1
  Key Share: x25519 public key = 4a 2f 8b ... (32 bytes)
  Signature Algorithms: ecdsa_secp256r1_sha256, ...
  SNI: www.example.com
```

两个细节值得咀嚼：真实版本在 `supported_versions` 扩展里声明，版本字段保留 `0x0303` 是兼容性妥协；`Key Share` 直接把密钥交换材料随 ClientHello 发出——不等你表态我先出牌，这是 TLS 1.3 握手加速的关键。

**第二步：ServerHello**

```
ServerHello:
  Version: TLS 1.2 (0x0303)
  Random: 9c 4e 1a 7b ... (32 bytes)
  Cipher Suite: TLS_AES_256_GCM_SHA384
  Supported Versions: TLS 1.3 (0x0304)
  Key Share: x25519 public key = 8b 3e 7c ... (32 bytes)
```

到这里，双方各自手里有：两个随机数、对方的 ECDHE 公钥、自己的 ECDHE 私钥。通过 **ECDHE**（Elliptic Curve Diffie-Hellman Ephemeral，临时椭圆曲线迪菲-赫尔曼），双方**在不传输密钥的前提下**各自算出了相同的预主密钥——这就是 Diffie-Hellman 的魔法：公开交换的材料推不出秘密，配上私钥却都能算出同一个结果。

**第三步：服务器发证书与 Finished**。服务器用私钥对握手上下文签名（Certificate Verify），发出 Finished；客户端验证证书链与签名，确认「对面真是 www.example.com」。

**第四步：客户端发 Finished**。握手完成，双方切换到协商好的对称密钥加密通信。

TLS 1.3 整个握手只需 **1 个 RTT**（TLS 1.2 要 2 个）：延迟 100ms 的网络直接省 100ms——这比 11.7 的 TCP Fast Open 省下的还多，也是 14.4 说「HTTPS 反而更快」的另一重底气。

## 15.3 对称加密 vs 非对称加密

「先猜再读」第一问的答案：不会慢到没法用，因为 TLS 根本不用非对称加密传数据。两种加密各有优劣：

- **对称加密**（AES-256-GCM、ChaCha20）：加解密同一把钥匙，速度快（AES 有 CPU 硬件加速），适合加密大量数据。致命问题：双方怎么安全地共享这把钥匙？
- **非对称加密**（RSA、ECDHE）：公钥加密、私钥解密（或反过来签名验证）。解决了密钥分发问题，但速度慢 100-1000 倍。

TLS 的策略是**握手用非对称、数据用对称**：用 ECDHE 安全地协商出对称密钥，然后所有通信都交给 AES。非对称加密只用一次、只算一小段，性能开销可以忽略——「先猜再读」的担心由此打消。

## 15.4 数字证书与 CA 体系

非对称加密解决了密钥分发，又引入新问题：「先猜再读」第二问——你怎么知道拿到的公钥真是 `bank.com` 的，而不是中间人伪造的？

答案是**数字证书**：包含服务器公钥与身份信息的文件，由可信第三方——**CA（Certificate Authority，证书颁发机构）**——签名背书。就像户口本：你自己说了不算，要有派出所盖章。

**X.509 证书结构**：

```
Certificate:
  Version: 3
  Serial Number: 04:3E:2F:8A:...
  Issuer: C=US, O=Let's Encrypt, CN=R3        ← 签发者（CA）
  Subject: CN=www.example.com                   ← 证书持有者
  Validity:
    Not Before: Jan 15 00:00:00 2024 GMT
    Not After:  Apr 14 23:59:59 2024 GMT
  Subject Public Key: RSA 2048 bits
  Extensions:
    Subject Alternative Name: www.example.com, example.com
  Signature Algorithm: sha256WithRSAEncryption
  Signature: 3a:7b:9c:...                      ← CA 的签名
```

**证书链（Chain of Trust）**：浏览器不直接信任 `bank.com` 的证书，而是验证一条链：

```
Root CA (DigiCert Global Root G2)  ← 操作系统/浏览器预装
  └── Intermediate CA (DigiCert SHA2 Secure Server CA)  ← 由 Root CA 签发
        └── www.bank.com  ← 由 Intermediate CA 签发
```

每一级证书都带着上一级的签名。浏览器逐级验签，直到命中一个**预装的根证书**——信任的锚点来自操作系统和浏览器厂商。链条完整且签名有效，网站才被信任。这也是为什么「给手机装企业根证书」是个危险动作：你亲手往信任锚里加了一个第三方。

## 15.5 证书验证过程

浏览器收到证书后做四项检查：

1. **签名验证**：证书链是否完整？每级签名是否有效？
2. **域名匹配**：Subject 或 SAN 是否包含当前访问的域名？`*.example.com` 匹配 `www.example.com`，但不匹配 `sub.www.example.com`。
3. **有效期**：Let's Encrypt 的证书只有 90 天——不是不靠谱，而是用短有效期逼你自动化续期，泄露的证书寿命也短。
4. **吊销检查**：CA 是否提前吊销？通过 OCSP（在线状态查询）或 CRL（吊销列表）。

任何一步失败，浏览器就弹出那个令人心悸的红色警告：「您的连接不是私密连接」。看到它时不要随手点「继续访问」——那一步等于亲手关闭了整套验证体系。

## 15.6 HSTS：强制 HTTPS 的机制

「先猜再读」第三问的答案：网站支持 HTTPS ≠ 用户访问就是 HTTPS。用户第一次可能输入 `http://`，301 重定向虽然能补救，但**第一次重定向之前是明文的**——攻击者可以在这个窗口期劫持（把你的重定向改到钓鱼站）。之后每次新会话又都有同样的窗口。

**HSTS（HTTP Strict Transport Security）**让服务器声明：「以后访问我这个域名，必须直接用 HTTPS」：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

浏览器收到后，在接下来一年内对 `example.com` 及其所有子域名自动升级 HTTPS，不再发任何 HTTP 请求。`preload` 表示域名已加入浏览器内置的 HSTS 预加载列表——连**第一次访问**也强制 HTTPS，把明文窗口彻底焊死。代价也明确：`includeSubDomains` 一旦生效，子域名想回退 HTTP 就做不到了。

## 15.7 TLS 1.2 vs TLS 1.3

TLS 1.3（2018）相对 TLS 1.2（2008）做了大幅收敛：

| 特性 | TLS 1.2 | TLS 1.3 |
| ------ | --------- | --------- |
| 握手 RTT | 2 RTT | 1 RTT（恢复场景支持 0-RTT） |
| 密钥交换 | RSA、DHE、ECDHE 等 | 仅 ECDHE（前向保密） |
| 对称加密 | AES-CBC、RC4 等 | 仅 AEAD（AES-GCM、ChaCha20-Poly1305） |
| 加密套件数量 | 数十个 | 仅 5 个 |
| 服务器签名 | 签名握手消息 | 签名握手上下文（更严） |
| 密钥派生 | PRF | HKDF |

核心理念：**砍掉所有不安全选项，只保留最好的**。RSA 密钥交换没有前向保密——服务器 RSA 私钥将来泄露，过去的所有通信都能被解密；ECDHE 每次会话用临时密钥，私钥泄露也伤不到历史流量。这种「做减法」的设计哲学会在 QUIC（第20章）里再次出现——QUIC 干脆把 TLS 1.3 整个搬进传输层，本章的握手知识到那里直接复用。

## 15.8 编程实践：用 Python ssl 模块为 TCP 服务器添加 TLS

先生成自签名证书（真实网站用 Let's Encrypt 等CA签发，自签证书只用于实验，浏览器会警告）：

```bash
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes
```

TLS 服务器的骨架：普通 TCP socket 之上包一层 SSL 上下文：

```python
import socket
import ssl
import threading

def handle_client(conn: ssl.SSLSocket, addr):
    """处理一个 TLS 客户端连接"""
    try:
        data = conn.recv(4096).decode('utf-8', errors='replace')
        print(f"[{addr}] Received: {data[:100]}...")

        # 打印协商出来的 TLS 信息
        print(f"  TLS Version: {conn.version()}")
        print(f"  Cipher: {conn.cipher()}")

        response = (
            "HTTP/1.1 200 OK\r\n"
            "Content-Type: text/plain\r\n"
            "Content-Length: 23\r\n"
            "Connection: close\r\n"
            "\r\n"
            "Hello from HTTPS Server!"
        )
        conn.sendall(response.encode('utf-8'))
    finally:
        conn.close()

def main():
    # 底层还是第8章讲的 TCP socket
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind(('127.0.0.1', 8443))
    server.listen(5)

    # SSL 上下文：加载证书，限制最低版本
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    context.load_cert_chain(certfile='cert.pem', keyfile='key.pem')
    context.minimum_version = ssl.TLSVersion.TLSv1_2

    # 用 SSL 上下文包装 TCP socket——「垫层」的具象化
    ssl_server = context.wrap_socket(server, server_side=True)

    print("HTTPS Server listening on https://127.0.0.1:8443")

    try:
        while True:
            conn, addr = ssl_server.accept()
            thread = threading.Thread(target=handle_client, args=(conn, addr))
            thread.start()
    except KeyboardInterrupt:
        print("\nServer shutting down...")
    finally:
        ssl_server.close()

if __name__ == '__main__':
    main()
```

运行后 `curl -k https://127.0.0.1:8443/`（`-k` 表示跳过证书验证——自签证书没有 CA 背书）。注意 `wrap_socket` 这个动作：TLS 在代码层面就是 TCP 之上的一层包装，对应 15.1 说的「垫层」。

用 openssl 查看真实网站的证书：

```bash
# 只看证书的 Subject、Issuer 与有效期
openssl s_client -connect www.example.com:443 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 输出示例：
# subject=CN = www.example.org
# issuer=C = US, O = Let's Encrypt, CN = R3
# notBefore=Jan 15 00:00:00 2024 GMT
# notAfter=Apr 14 23:59:59 2024 GMT
```

## 15.9 抓包实践：捕获 TLS 握手全过程

Wireshark 过滤 `tls`，访问一个 HTTPS 网站：

```
Client Hello:
  Version: TLS 1.2 (0x0303)
  Cipher Suites (5 suites)
  Extensions:
    server_name: www.example.com
    supported_versions: TLS 1.3 (0x0304), TLS 1.2 (0x0303)
    supported_groups: x25519, secp256r1, secp384r1
    key_share: x25519 (32 bytes)

Server Hello:
  Cipher Suite: TLS_AES_256_GCM_SHA384 (0x1302)
  Extensions:
    supported_versions: TLS 1.3 (0x0304)
    key_share: x25519 (32 bytes)

Certificate (encrypted in TLS 1.3)
Certificate Verify (encrypted)
Finished (encrypted)
```

对照 15.2 逐字段核对。重点观察一个现象：**TLS 1.3 中 ServerHello 之后的消息全部是加密的**——你在 Wireshark 里看不到证书内容；TLS 1.2 的证书则是明文。展开 `Handshake Protocol` 树可以看到每个字段的精确值。

> [!TIP] SSLKEYLOGFILE：解自己的密
> 设置环境变量 `SSLKEYLOGFILE=~/sslkeys.log` 后启动浏览器，浏览器会把每次连接的密钥材料写入该文件；在 Wireshark `Preferences > Protocols > TLS` 里指向它即可解密自己的 TLS 流量，看到明文 HTTP。仅用于调试自己控制的客户端——解别人的密既在技术上做不到（ECDHE 的前向保密保证了这一点），也是违法行为。

## 本章小结

- HTTPS = HTTP over TLS，三重护甲各司其职：加密防窃听、消息认证防篡改、证书防冒充。
- TLS 1.3 握手 1-RTT：Key Share 随 ClientHello 抢跑，版本字段装旧只为兼容，真实版本藏在扩展里。
- 握手用非对称（ECDHE 协商）、数据用对称（AES-GCM）——各取所长，性能开销可忽略。
- Diffie-Hellman 的魔法：双方公开交换材料、各自算出同一密钥，全程秘密不上线。
- 证书是「公钥的户口本」，信任链逐级验签，锚点是操作系统/浏览器预装的根证书——装根证书就是在加信任锚。
- 验证四查：链签名、域名匹配、有效期、吊销状态；红色警告意味着某一查失败，别随手「继续访问」。
- HSTS 用一年期声明 + 预加载列表焊死明文窗口，`includeSubDomains` 生效后回不去 HTTP。
- TLS 1.3 的哲学是做减法：只留 ECDHE 与 AEAD，用前向保密保证「今天的私钥泄露，解不了昨天的流量」。
