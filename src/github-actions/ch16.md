# 第16章：Workflow 调试与排错指南

## 16.1 引言：调试是每个 DevOps 工程师的必修课

写 Workflow 的人，大概有一半的时间在写，另一半时间在调试。这不是因为你写得不好——而是因为 CI/CD 环境和你本地开发环境之间总有那么一些"微妙的差异"。路径分隔符不同、环境变量缺失、网络超时、权限不足……这些问题就像程序世界的"小妖精"，让人又爱又恨（主要是恨）。

好消息是，GitHub Actions 提供了丰富的调试工具。本章我们将系统性地学习这些工具，让你在遇到问题时不再手忙脚乱。

## 16.2 调试的十八般武艺

### 16.2.1 act——本地运行工具

`act` 是一个开源工具，让你能在本地用 Docker 运行 GitHub Actions Workflow。它就像一个"CI 模拟器"，在你推送代码之前就能验证 Workflow 是否正确。

```bash
# 安装 act（macOS）
brew install act

# 安装 act（Linux）
curl https://raw.githubusercontent.com/nektos/act/master/install.sh | sudo bash

# 列出所有可运行的 Job
act -l

# 运行默认事件（push）的所有 Job
act

# 只运行指定的 Job
act -j lint

# 模拟 pull_request 事件
act pull_request

# 传入 Secret
act -s MY_SECRET=value
```

`act` 的局限性：它运行在 Docker 中，和真正的 GitHub Runner 有细微差异（比如没有预装某些工具）。但对于快速验证 Workflow 语法和基本逻辑，它已经足够好了。

### 16.2.2 Debug Logging——开启详细日志

GitHub Actions 默认只输出"关键信息"。如果你想看到每一步的详细输出（包括环境变量、系统信息、内部调用过程），可以设置两个 Secret：

- `ACTIONS_RUNNER_DEBUG` 设为 `true`：开启 Runner 级别的调试信息。
- `ACTIONS_STEP_DEBUG` 设为 `true`：开启 Step 级别的调试信息。

设置方法：在仓库的 Settings → Secrets and variables → Actions 中添加，或者在 Workflow 运行时通过"Re-run"对话框勾选"Enable debug logging"。

开启后，你会在日志中看到类似这样的额外信息：

```
##[debug]Evaluating condition for step: 'Run tests'
##[debug]Evaluating: success()
##[debug]Evaluating: success() => true
##[debug]Loading env
##[debug]Set GITHUB_OUTPUT = /home/runner/work/_temp/_runner_file_commands/set_output_abc123
```

### 16.2.3 SSH 到 Runner——直接"钻进去"看

有时候，光看日志还不够——你需要直接登录到 runner 上，亲手敲命令排查问题。`mxschmitt/action-tmate` 就是为此而生的：

```yaml
steps:
  - uses: actions/checkout@v4

  # 在需要调试的步骤之前插入 tmate
  - name: Setup tmate session (debug)
    uses: mxschmitt/action-tmate@v3
    # 可选：限制 SSH 访问，只允许特定 GitHub 用户
    with:
      limit-access-to-actor: true
```

当 Workflow 运行到这一步时，它会在日志中输出一个 SSH 连接地址：

```
SSH: ssh RqXYZ123@nyc1.tmate.io
Web: https://tmate.io/t/RqXYZ123
```

你复制这个命令到终端就能直接连入 runner，然后在上面执行任何命令来排查问题。这就像在远程服务器上开了一个"临时桌面"，你可以自由探索文件系统、查看环境变量、手动运行命令。

**注意**：tmate session 默认会在你断开连接后继续运行 Workflow。如果你想让它等待你手动确认后再继续，可以配置 `detach: false`。

### 16.2.4 日志解读技巧

GitHub Actions 的日志虽然信息量大，但如果不善于"阅读"，很容易迷失在海量输出中。几个实用技巧：

1. **先看红色和黄色**：GitHub 会用颜色标记不同级别的日志。红色的 `##[error]` 和黄色的 `##[warning]` 是你首先要关注的。

2. **看 Exit Code**：每个 step 执行完毕后会报告退出码。`Exit code 0` 表示成功，非零表示失败。有时候命令看起来正常但退出码不对，这通常是"静默失败"。

3. **对比上一次成功的运行**：GitHub 的 Actions 页面支持对比两次运行。如果某次突然失败了，对比日志能快速定位差异。

4. **搜索关键字**：浏览器 `Ctrl+F` 搜索 `error`、`failed`、`timeout` 等关键字，快速定位问题区域。

5. **下载完整日志**：在 Actions 页面右上角有 "Download logs" 按钮，可以下载 ZIP 格式的完整日志文件，方便离线分析和团队分享。

## 16.3 常见错误及解决方案

### 错误1：权限问题——"Permission denied" 或 "Resource not accessible by integration"

**原因**：`GITHUB_TOKEN` 的默认权限可能不够。从 2023 年起，GitHub 将默认权限收紧为 `read-only`。

**解决方案**：在 Workflow 文件顶部或具体 Job 中声明所需权限：

```yaml
# 全局权限
permissions:
  contents: write    # 需要推送代码
  packages: write    # 需要推送镜像
  pull-requests: write  # 需要在 PR 中评论
```

### 错误2：依赖安装失败——"npm ERR!" 或 "pip install error"

**常见原因**：

- `package-lock.json` 或 `requirements.txt` 未提交到仓库
- 需要编译的依赖缺少系统级工具（如 Python 的 `psycopg2` 需要 `libpq-dev`）
- 网络超时（npm/pip 仓库临时不可用）

**解决方案**：

```yaml
# 添加重试逻辑
- name: Install dependencies
  run: |
    for i in 1 2 3; do
      npm ci && break || sleep 15
    done

# 安装系统级依赖
- name: Install system dependencies
  run: |
    sudo apt-get update
    sudo apt-get install -y libpq-dev
```

### 错误3：超时——Job 运行时间过长

GitHub Actions 的 Job 有默认 6 小时的超时限制。如果你的 Job 经常跑很久，检查以下几点：

- 是否有无限循环或死锁？
- 测试是否在等待一个永远不会就绪的服务？给 Services 加上健康检查。
- 是否可以减小 Matrix 的规模？

```yaml
# 设置超时时间（防止 Job 卡住浪费资源）
jobs:
  test:
    timeout-minutes: 15
    steps:
      - name: Run tests
        # 给单个步骤也设置超时
        timeout-minutes: 10
        run: pytest tests/
```

### 错误4：缓存不生效——"Cache not found"

**常见原因**：缓存 Key 与恢复 Key 不匹配。

**解决方案**：理解缓存的工作原理。`key` 是精确匹配，`restore-keys` 是前缀匹配：

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    # 精确 key：操作系统 + Python 版本 + 依赖文件哈希
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}
    # 回退 key：如果精确匹配不到，就用前缀匹配
    restore-keys: |
      ${{ runner.os }}-pip-
```

## 16.4 Workflow 运行性能优化

慢的 Workflow 不仅浪费时间，还浪费金钱（GitHub 按分钟计费）。几个优化方向：

**1. 合理使用缓存**：把依赖安装的时间从每次 2 分钟降到 10 秒。

**2. 缩小 Docker 镜像**：用 `slim` 或 `alpine` 基础镜像，减少下载和构建时间。

**3. 并行化 Job**：利用 `needs` 关键字设计 Job 的依赖图，让不相关的 Job 并行运行。

```yaml
# 好的设计：lint 和 security-scan 可以并行
jobs:
  lint:
    runs-on: ubuntu-latest
    steps: [...]

  security-scan:
    runs-on: ubuntu-latest
    steps: [...]

  # 等两个都完成后再继续
  test:
    needs: [lint, security-scan]
    steps: [...]
```

**4. 减少 Checkout 的 depth**：如果你不需要完整 git 历史，可以浅克隆：

```yaml
- uses: actions/checkout@v4
  with:
    fetch-depth: 1  # 只拉最新一次提交
```

**5. 条件跳过**：对于文档修改，跳过耗时的测试 Job：

```yaml
jobs:
  test:
    # 只在代码文件变更时运行测试
    if: contains(github.event.head_commit.modified, 'src/')
```

## 16.5 小结

调试 Workflow 就像侦探破案：`act` 是你的"模拟现场"，Debug Logging 是你的"放大镜"，tmate SSH 是你的"亲临现场"，日志分析是你的"推理能力"。掌握这些工具，你就能快速定位并修复 CI/CD 中的任何问题。记住一个原则：先理解错误信息，再看日志上下文，最后才上手改代码——不要盲目地"改改看"。
