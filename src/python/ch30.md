# 第 30 章 项目打包与发布

你花了几周写了一个很棒的 Python 工具，同事说："能发给我用用吗？"你自信地发过去一个 `.py` 文件，对方回复："这个怎么运行？我电脑上没装 Python 啊。"——是不是觉得有点尴尬？

把你写的代码从"在我电脑上能跑"变成"任何人都能用"，这个过程叫打包与发布。就像你在家做了一道好菜想分享给朋友，你不能直接把锅端过去——你得打包好，贴上说明标签，告诉别人怎么加热食用。Python 的打包生态提供了好几种"打包方案"：发布为 pip 可安装的包、打包成独立可执行文件、或者放进 Docker 容器。

## 30.1 Python 包结构（src/ 布局）

一个规范的 Python 项目应该有清晰的目录结构。现代 Python 推荐使用 `src/` 布局：

```
my_tool/
├── src/
│   └── my_tool/
│       ├── __init__.py
│       ├── core.py
│       └── utils.py
├── tests/
│   ├── __init__.py
│   └── test_core.py
├── pyproject.toml
├── README.md
├── LICENSE
└── .gitignore
```

`src/` 布局的好处是：测试时导入的是已安装的包，而不是源码目录下的模块，避免了"开发时能跑，安装后跑不了"的诡异问题。

### `__init__.py` 的作用

```python
# src/my_tool/__init__.py
"""my_tool: 一个超级好用的工具库"""

__version__ = "1.0.0"

from .core import main_function
from .utils import helper_function
```

```python
# src/my_tool/core.py
def main_function(data: list) -> dict:
    """核心功能"""
    return {"count": len(data), "sum": sum(data)}

# src/my_tool/utils.py
def helper_function(x: int) -> int:
    """辅助功能"""
    return x * 2
```

## 30.2 pyproject.toml：项目配置的核心

`pyproject.toml` 是现代 Python 项目的配置文件，取代了以前的 `setup.py` 和 `setup.cfg`。

```toml
# pyproject.toml
[build-system]
requires = ["setuptools>=68.0", "wheel"]
build-backend = "setuptools.backends._legacy:_Backend"

[project]
name = "my-tool"
version = "1.0.0"
description = "一个超级好用的 Python 工具库"
readme = "README.md"
license = {text = "MIT"}
requires-python = ">=3.11"
authors = [
    {name = "张三", email = "zhangsan@example.com"},
]
keywords = ["tool", "utility", "python"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]
dependencies = [
    "requests>=2.28",
    "click>=8.0",
]

[project.optional-dependencies]
dev = [
    "pytest>=7.0",
    "black",
    "mypy",
]

[project.scripts]
my-tool = "my_tool.core:main_function"

[project.urls]
Homepage = "https://github.com/yourname/my-tool"
Documentation = "https://my-tool.readthedocs.io"

[tool.setuptools.packages.find]
where = ["src"]
```

## 30.3 构建 wheel 与上传 PyPI

PyPI（Python Package Index）是 Python 的官方包仓库，你用 `pip install` 安装的包都来自这里。把你的包发布到 PyPI，全世界的 Python 开发者都能安装使用。

### 构建包

```bash
# 安装构建工具
pip install build

# 构建（生成 sdist 和 wheel）
python -m build

# 构建完成后，dist/ 目录下会生成：
# dist/
# ├── my_tool-1.0.0.tar.gz      (sdist，源码包)
# └── my_tool-1.0.0-py3-none-any.whl  (wheel，预编译包)
```

### 上传到 PyPI

```bash
# 安装 twine（上传工具）
pip install twine

# 先上传到 TestPyPI（测试环境）
twine upload --repository testpypi dist/*

# 测试从 TestPyPI 安装
pip install --index-url https://test.pypi.org/simple/ my-tool

# 确认没问题后，上传到正式 PyPI
twine upload dist/*
```

上传时需要输入 PyPI 的用户名和密码（推荐使用 API Token）。设置方法：

```bash
# 在 ~/.pypirc 中配置（不推荐）
# 推荐使用环境变量或交互式输入

# 使用 API Token（推荐）
# 用户名设为 __token__，密码填 API Token
```

### 版本号规范

Python 社区遵循语义化版本（Semantic Versioning）：`MAJOR.MINOR.PATCH`

- **MAJOR**：有不兼容的 API 变更（如 1.0 → 2.0）
- **MINOR**：添加新功能但向后兼容（如 1.0 → 1.1）
- **PATCH**：Bug 修复（如 1.0.0 → 1.0.1）

## 30.4 PyInstaller：打包为可执行文件

如果你想让不懂 Python 的人也能用你的程序，PyInstaller 可以把你的 Python 脚本打包成一个独立的可执行文件（`.exe` / macOS app / Linux binary），对方不需要安装 Python。

```bash
pip install pyinstaller
```

### 基本用法

```bash
# 打包为单文件（--onefile）
pyinstaller --onefile my_script.py

# 打包为无控制台窗口（GUI 程序）
pyinstaller --onefile --windowed my_gui_app.py

# 指定图标
pyinstaller --onefile --icon=app.ico my_script.py

# 添加额外数据文件
pyinstaller --onefile --add-data "data_folder;data_folder" my_script.py
```

### 使用 spec 文件进行高级配置

PyInstaller 首次运行会生成一个 `.spec` 文件，你可以编辑它来做更精细的控制：

```python
# my_script.spec
a = Analysis(
    ['my_script.py'],
    pathex=[],
    binaries=[],
    datas=[('config.json', '.'), ('templates/', 'templates/')],
    hiddenimports=['some_module'],  # PyInstaller 没自动检测到的依赖
)

pyz = PYZ(a.pure)

exe = EXE(
    pyz,
    a.scripts,
    a.binaries,
    a.datas,
    [],
    name='MyTool',
    debug=False,
    strip=False,
    upx=True,
    console=True,  # True = 显示控制台，False = 隐藏
    icon='app.ico',
)
```

### 打包后运行

```bash
# 生成的文件在 dist/ 目录
# Windows: dist/MyTool.exe
# macOS: dist/MyTool
# Linux: dist/MyTool

# 直接运行
./dist/MyTool --help
```

### PyInstaller 常见问题

1. **打包体积太大**：使用虚拟环境打包，避免打入不必要的库
2. **杀毒软件误报**：打包的 exe 可能被误认为病毒，可以加数字签名
3. **找不到数据文件**：使用 `sys._MEIPASS` 获取运行时路径

```python
import sys
import os

def resource_path(relative_path: str) -> str:
    """获取资源文件的路径（兼容 PyInstaller 打包）"""
    if hasattr(sys, '_MEIPASS'):
        # PyInstaller 打包后的临时目录
        return os.path.join(sys._MEIPASS, relative_path)
    return os.path.join(os.path.abspath("."), relative_path)

# 使用
config_file = resource_path("config.json")
```

## 30.5 Docker 入门：容器化部署

如果 PyInstaller 是把你的程序打包成一个"包裹"，那 Docker 就是把你的程序连同整个"操作系统环境"一起打包——就像把整个厨房都装进集装箱，保证在任何地方做出来都是同一个味道。

Docker 的核心概念：

- **镜像（Image）**：一个"快照"，包含你的程序、依赖、操作系统配置
- **容器（Container）**：镜像的运行实例，就像一个轻量级虚拟机
- **Dockerfile**：构建镜像的"配方"

### 编写 Dockerfile

```dockerfile
# 选择基础镜像
FROM python:3.12-slim

# 设置工作目录
WORKDIR /app

# 复制依赖文件（利用 Docker 缓存）
COPY requirements.txt .

# 安装依赖
RUN pip install --no-cache-dir -r requirements.txt

# 复制项目代码
COPY . .

# 暴露端口
EXPOSE 8000

# 启动命令
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 构建和运行

```bash
# 构建镜像
docker build -t my-api:latest .

# 查看镜像
docker images

# 运行容器
docker run -d -p 8000:8000 --name my-api my-api:latest

# 查看运行中的容器
docker ps

# 查看日志
docker logs my-api

# 停止容器
docker stop my-api

# 删除容器
docker rm my-api
```

### .dockerignore 文件

就像 `.gitignore` 一样，`.dockerignore` 告诉 Docker 构建时忽略哪些文件：

```
# .dockerignore
__pycache__/
*.pyc
*.pyo
.git/
.venv/
*.egg-info/
dist/
build/
.env
tests/
```

### Docker Compose：多容器编排

当你的项目需要多个服务（Web 服务器 + 数据库 + 缓存）时，Docker Compose 让你用一个 YAML 文件管理所有容器：

```yaml
# docker-compose.yml
version: "3.8"

services:
  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```bash
# 启动所有服务
docker-compose up -d

# 停止所有服务
docker-compose down

# 查看日志
docker-compose logs -f
```

## 30.6 GitHub Actions 简易 CI

CI（Continuous Integration，持续集成）的意思是：每次你推送代码到 GitHub，自动运行测试、构建和发布流程。就像请了一个 24 小时在线的 QA，帮你检查每次提交有没有引入 Bug。

### 基本配置

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11", "3.12"]

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -e ".[dev]"

      - name: Run tests
        run: pytest tests/ -v

      - name: Check code style
        run: black --check src/ tests/
```

### 自动发布到 PyPI

```yaml
# .github/workflows/publish.yml
name: Publish to PyPI

on:
  release:
    types: [published]

jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Build package
        run: |
          pip install build
          python -m build

      - name: Publish to PyPI
        uses: pypa/gh-action-pypi-publish@release/v1
        with:
          password: ${{ secrets.PYPI_API_TOKEN }}
```

使用方式：在 GitHub 仓库的 Settings → Secrets → Actions 中添加 `PYPI_API_TOKEN` 密钥，然后在 GitHub 上创建 Release 时就会自动触发构建和发布。

本章我们学习了如何将 Python 项目从"在自己电脑上能跑"变成"任何人都能用"：

**第 7 题：**

- **sdist（Source Distribution）**：源码包，包含完整的源代码和配置文件。用户安装时需要在本地重新构建（编译 C 扩展等）。兼容性好，但安装速度较慢。
- **wheel（Built Distribution）**：预编译包，已经构建好了，可以直接解压安装。安装速度快，不需要编译环境。但与特定平台和 Python 版本相关。

两种都上传的原因：sdist 是兜底方案，当没有匹配的 wheel 时，pip 会回退到 sdist 安装；wheel 则为常见平台提供快速安装体验。

## 30.10 常见错误与避坑

**1. 版本号忘记更新就发布**

```bash
# 错误：版本号没改就上传，PyPI 会拒绝
python -m build
twine upload dist/*  # 报错：版本已存在

# 正确：先更新版本号
# 在 pyproject.toml 中修改 version = "1.0.1"
# 然后再构建和上传
```

**2. 忘记在 .gitignore 中排除构建产物**

```
# .gitignore 应包含
dist/
build/
*.egg-info/
__pycache__/
*.pyc
.venv/
```

**3. PyInstaller 打包后找不到资源文件**

```python
# 错误：打包后路径失效
config = open("config.json")  # 打包后找不到这个文件

# 正确：使用 resource_path 函数
import sys, os

def resource_path(relative_path):
    if hasattr(sys, '_MEIPASS'):
        return os.path.join(sys._MEIPASS, relative_path)
    return os.path.join(os.path.abspath("."), relative_path)

config = open(resource_path("config.json"))
```

**4. Docker 镜像太大**

```dockerfile
# 错误：使用完整 Python 镜像（~900MB）
FROM python:3.12

# 正确：使用 slim 版本（~150MB）
FROM python:3.12-slim

# 或者更极端的 alpine（~50MB，但某些包编译有问题）
# FROM python:3.12-alpine
```

**5. 环境变量在 Docker 中不生效**

```dockerfile
# 错误：在 Dockerfile 中硬编码环境变量
ENV API_KEY=sk-abc123  # 永远不要这样做！

# 正确：运行时传入
# docker run -e API_KEY=$API_KEY my-app

# 或使用 docker-compose
# environment:
#   - API_KEY=${API_KEY}  # 从宿主机环境变量读取
```

**6. pyproject.toml 中 dependencies 写错**

```toml
# 错误：包名和 import 名不一致
dependencies = [
    "PIL",          # 错误！pip 找不到这个包
    "bs4",          # 错误！应该是 beautifulsoup4
    "cv2",          # 错误！应该是 opencv-python
]

# 正确
dependencies = [
    "Pillow",       # import PIL
    "beautifulsoup4", # import bs4
    "opencv-python",  # import cv2
]
```

## 给读者的最后几句话

学编程这件事，最难的从来不是语法，而是**坚持**。

你可能会在某个深夜被一个 Bug 折磨到怀疑人生，可能会看到别人的项目觉得自己太菜，可能会在学新框架时觉得信息量爆炸。这些感受每个程序员都经历过——包括那些看起来很厉害的人。

记住几个原则：

**1. 项目驱动学习。** 不要只是读教程、看视频。找一个你真正想解决的问题，用 Python 去解决它。在解决问题的过程中学习，效率比"系统学习"高十倍。

**2. 写代码 > 读代码 > 看视频。** 动手实践永远是最重要的。你可以"看懂"一个概念，但只有真正写出来、调通了，它才属于你。

**3. 不要怕犯错。** 每一个报错信息都是一次学习机会。看到 `Traceback` 不要慌，读它，理解它，解决它。

**4. 学会阅读文档和源码。** 官方文档是最准确的学习材料。看别人的源码能让你学到很多教科书不会教的技巧和模式。

**5. 加入社区。** 一个人的学习是孤独的，也是低效的。在 GitHub 上参与开源项目，在社区里回答问题，这些都能加速你的成长。

Python 是一门"入门简单、精通很难"的语言。你已经完成了"入门"的部分，接下来的"精通"之路，需要你用项目和实践去铺就。

但请记住：每一个厉害的程序员，都曾经是一个连 `print("Hello, World!")` 都觉得新奇的人。你已经走过了那一步，接下来的路，只会越来越精彩。

祝你编码愉快。
