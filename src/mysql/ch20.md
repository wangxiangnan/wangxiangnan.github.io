# 第20章 主从复制

如果备份是给数据买保险，那主从复制就是开了一个"实时镜像分身"。想象你在写一份共享文档，每次你修改一行，旁边就有一台电脑自动同步你的修改。当你的电脑突然宕机，同事可以直接从镜像电脑上继续工作——这就是主从复制的核心价值。

## 20.1 复制原理

MySQL 的主从复制本质上是一个"日志回放"的过程，分三步走：

1. **Master**：将数据变更写入二进制日志（Binlog）
2. **Slave IO Thread**：从 Master 读取 Binlog，写入中继日志（Relay Log）
3. **Slave SQL Thread**：读取 Relay Log，重放 SQL 语句

```
┌──────────┐    Binlog     ┌──────────┐
│  Master   │ ──────────→  │  Slave    │
│          │   IO Thread   │ IO Thread │ → Relay Log → SQL Thread → 执行
│ Binlog   │              │          │
└──────────┘              └──────────┘
```

## 20.2 复制格式

MySQL 支持三种 Binlog 格式，各有优劣：

**STATEMENT（基于语句）：** 记录原始 SQL 语句。

```sql
-- 设置 STATEMENT 格式
SET GLOBAL binlog_format = 'STATEMENT';

-- 优点：日志量小
-- 缺点：NOW()、UUID() 等函数在主从可能产生不同结果
```

**ROW（基于行）：** 记录每一行的具体变化。

```sql
-- 设置 ROW 格式（推荐）
SET GLOBAL binlog_format = 'ROW';

-- 优点：精确复制，不会因函数导致数据不一致
-- 缺点：批量更新时日志量巨大
```

**MIXED（混合模式）：** MySQL 自动判断用哪种格式。

```sql
SET GLOBAL binlog_format = 'MIXED';
```

> **Tip：** 生产环境推荐使用 ROW 格式。虽然日志会大一些，但数据一致性更有保障。

## 20.3 搭建主从复制

下面是一个完整的主从搭建流程：

**Step 1：配置 Master**

```sql
-- my.cnf (Master)
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog_format = ROW
binlog-do-db = mydb          -- 可选：只复制指定数据库
expire_logs_days = 7          -- binlog保留天数
```

**Step 2：创建复制用户**

```sql
-- 在 Master 上执行
CREATE USER 'repl_user'@'%' IDENTIFIED BY 'strong_password';
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';
FLUSH PRIVILEGES;
```

**Step 3：获取 Master 的 Binlog 位点**

```sql
-- 在 Master 上执行
FLUSH TABLES WITH READ LOCK;
SHOW MASTER STATUS;
-- 记下 File 和 Position 的值
-- 例如：mysql-bin.000003, 154
```

**Step 4：在 Master 上做数据快照**

```sql
-- 保持锁表状态，新开终端执行
mysqldump -u root -p --single-transaction --all-databases > master_dump.sql

-- 导出完成后解锁
UNLOCK TABLES;
```

**Step 5：配置 Slave**

```sql
-- my.cnf (Slave)
[mysqld]
server-id = 2
relay-log = relay-bin
read_only = 1
log-slave-updates = 1
```

**Step 6：导入数据并启动复制**

```sql
-- 在 Slave 上导入数据
mysql -u root -p < master_dump.sql

-- 配置主从连接
CHANGE MASTER TO
  MASTER_HOST = '192.168.1.100',
  MASTER_USER = 'repl_user',
  MASTER_PASSWORD = 'strong_password',
  MASTER_LOG_FILE = 'mysql-bin.000003',
  MASTER_LOG_POS = 154;

-- 启动复制
START SLAVE;

-- 检查复制状态
SHOW SLAVE STATUS\G
```

> **Warning：** 确保 `SHOW SLAVE STATUS` 中 `Slave_IO_Running` 和 `Slave_SQL_Running` 都是 `Yes`。如果有一个是 `No`，说明复制出问题了。

## 20.4 GTID 复制

GTID（Global Transaction Identifier）是 MySQL 5.6 引入的特性，给每个事务分配一个全局唯一的 ID，让复制管理变得更加简单。在没有 GTID 的时代，DBA 做主从切换需要手动计算 binlog 文件名和偏移量，这就像在一本没有目录的厚书里找特定段落——全靠运气和耐心。GTID 彻底改变了这种状况，它让每个事务都有一个明确的"身份证号"，MySQL 可以自动判断哪些事务已经执行、哪些还没有。

GTID 的一个关键优势体现在故障恢复场景：假设你的主库挂了，需要把一个从库提升为新主库。在传统复制模式下，其他从库需要重新配置复制位点，你必须手动确认每个从库执行到了 binlog 的哪个位置，这个过程既繁琐又容易出错。而 GTID 模式下，从库只需要告诉新主库"我已经执行了哪些 GTID"，MySQL 会自动计算出还需要复制哪些事务，整个过程完全自动化。

```sql
-- GTID 格式：server_uuid:transaction_number
-- 例如：3E11FA47-71CA-11E1-9E33-C80AA9429562:23

-- 开启 GTID（Master 和 Slave 都要配置）
[mysqld]
server-id = 1
gtid_mode = ON
enforce_gtid_consistency = ON
log-bin = mysql-bin
```

**GTID 模式下搭建复制：**

```sql
-- Slave 配置（比传统方式简单很多）
CHANGE MASTER TO
  MASTER_HOST = '192.168.1.100',
  MASTER_USER = 'repl_user',
  MASTER_PASSWORD = 'strong_password',
  MASTER_AUTO_POSITION = 1;  -- 自动定位，不需要手动指定文件和位点

START SLAVE;
```

> **Tip：** GTID 复制的最大好处是故障切换方便。当你需要把 Slave 提升为新 Master 时，其他 Slave 可以自动找到正确的复制位点。

## 20.5 半同步复制

默认的异步复制有一个风险：Master 写完 Binlog 就告诉客户端"事务提交成功"，但 Slave 可能还没来得及同步。如果此时 Master 挂了，数据可能丢失。这就像你寄了一封信，对方还没收到，你就告诉所有人"事情已经办妥了"。

半同步复制要求 Master 至少等待一个 Slave 确认收到了 Binlog，才返回成功。它在性能和数据安全之间找到了一个很好的平衡点。与全同步复制（要求所有 Slave 都确认）不同，半同步只需要一个 Slave 确认即可，这样即使某个 Slave 网络延迟很高，也不会拖慢整个系统。

值得注意的是，半同步复制在超时后会退化为异步复制。如果 Slave 的确认超过设定的超时时间（默认 10 秒），Master 会自动切换回异步模式，以保证服务可用性。当 Slave 恢复后，半同步会自动重新生效。所以你需要监控 `Rpl_semi_sync_master_status` 状态变量，确认半同步是否处于正常工作状态。

```sql
-- 在 Master 上安装半同步插件
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 3000; -- 3秒超时

-- 在 Slave 上安装
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';
SET GLOBAL rpl_semi_sync_slave_enabled = 1;

-- 重启 IO Thread 使配置生效
STOP SLAVE IO_THREAD;
START SLAVE IO_THREAD;

-- 验证半同步状态
SHOW STATUS LIKE 'Rpl_semi_sync%';
```

## 20.6 复制监控

```sql
-- 查看从库复制状态（最常用的监控命令）
SHOW SLAVE STATUS\G

-- 关键字段解读：
-- Seconds_Behind_Master: 从库延迟秒数（0表示同步）
-- Slave_IO_Running: IO线程是否正常
-- Slave_SQL_Running: SQL线程是否正常
-- Last_Error: 最近的错误信息
-- Retrieved_Gtid_Set: 已接收的GTID集合
-- Executed_Gtid_Set: 已执行的GTID集合
```

**用 Performance Schema 监控复制（MySQL 8.0+）：**

```sql
-- 查看复制连接状态
SELECT * FROM performance_schema.replication_connection_status\G

-- 查看复制应用状态
SELECT * FROM performance_schema.replication_applier_status\G

-- 查看各Worker线程状态（并行复制时）
SELECT * FROM performance_schema.replication_applier_status_by_worker\G
```

## 20.7 并行复制

在传统的单线程复制中，Slave 只有一个 SQL Thread 按顺序重放 Relay Log。如果 Master 上有很多并发写入，Slave 很可能跟不上，导致复制延迟越来越大。这就像一个工厂只有一条流水线，而竞争对手有十条。

MySQL 5.7 引入了并行复制（Parallel Replication），MySQL 8.0 进一步增强了这个功能。

**并行复制的演进：**

```sql
-- MySQL 5.7：基于 LOGICAL_CLOCK 的并行复制
-- 同一个 commit group 中的事务可以并行执行
SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL slave_parallel_workers = 8;  -- 开启8个工作线程

-- MySQL 8.0：基于 WRITESET 的并行复制（推荐）
-- 只要两个事务没有写同一行数据，就可以并行
SET GLOBAL binlog_transaction_dependency_tracking = 'WRITESET';
SET GLOBAL transaction_write_set_extraction = 'XXHASH64';
SET GLOBAL slave_parallel_workers = 8;
```

WRITESET 模式的工作原理很巧妙：MySQL 会分析每个事务修改了哪些行（write set），如果两个事务的 write set 没有交集，它们就可以在 Slave 上并行执行。这种方式比 LOGICAL_CLOCK 更加精细，并行度更高。

```sql
-- 查看并行复制的 Worker 状态
SELECT worker_id, thread_id, last_applied_transaction, 
       last_applied_transaction_end_apply_timestamp
FROM performance_schema.replication_applier_status_by_worker;

-- 查看并行复制的延迟情况
SELECT * FROM performance_schema.replication_applier_status_by_coordinator\G
```

> **Tip：** 并行复制能显著降低复制延迟，但要注意 `slave_parallel_workers` 不要设太大。每个 Worker 都是一个独立的连接，太多 Worker 会增加系统开销。通常设为 CPU 核心数的 1-2 倍即可。

## 20.8 复制拓扑变更

在实际运维中，复制拓扑不是一成不变的。你可能需要增加从库、做主从切换、或者调整拓扑结构。

**在线添加从库：**

```sql
-- 从现有的从库克隆数据来搭建新从库（MySQL 8.0.17+）
-- 在新从库上执行
CLONE INSTANCE FROM 'repl_user'@'192.168.1.101':3306 
  IDENTIFIED BY 'strong_password';

-- 克隆完成后配置复制
CHANGE MASTER TO
  MASTER_HOST = '192.168.1.100',
  MASTER_USER = 'repl_user',
  MASTER_PASSWORD = 'strong_password',
  MASTER_AUTO_POSITION = 1;

START SLAVE;
```

**计划内主从切换（维护窗口）：**

```sql
-- Step 1: 停止主库的写入（应用层配合）
-- Step 2: 确保从库已经完全同步
SHOW SLAVE STATUS\G
-- 确认 Seconds_Behind_Master = 0

-- Step 3: 在从库上提升为主库
STOP SLAVE;
RESET SLAVE ALL;
SET GLOBAL read_only = OFF;

-- Step 4: 将其他从库指向新主库
CHANGE MASTER TO 
  MASTER_HOST = '192.168.1.101',  -- 新主库地址
  MASTER_AUTO_POSITION = 1;
START SLAVE;
```

## 20.9 复制故障排查与修复

**问题1：SQL线程报错停止**

```sql
-- 查看具体错误
SHOW SLAVE STATUS\G
-- 关注 Last_SQL_Error 和 Last_SQL_Errno

-- 常见错误 1062：主键冲突
-- 跳过当前错误（谨慎使用）
STOP SLAVE;
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;

-- GTID 模式下跳过错误
STOP SLAVE;
SET GTID_NEXT = '3E11FA47-71CA-11E1-9E33-C80AA9429562:25';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
START SLAVE;
```

> **Warning：** 跳过错误是"治标不治本"的临时方案。跳过后一定要检查主从数据是否一致，并找到根本原因。

**问题2：主从数据不一致**

```sql
-- 使用 pt-table-checksum 检查数据一致性
-- pt-table-checksum --replicate=percona.checksums h=master_host

-- 使用 pt-table-sync 修复不一致
-- pt-table-sync --execute h=master_host,D=mydb,t=users
```

## 20.10 读写分离策略

主从复制最常见的应用场景就是读写分离：写操作走 Master，读操作走 Slave。这个策略听起来简单，但实际落地时会遇到不少坑。最常见的三个问题是：复制延迟导致读到旧数据、从库宕机时的降级策略、以及事务中混合读写时的路由问题。

关于复制延迟，这是读写分离方案中最棘手的问题。即使是并行复制，在高负载时也可能有几秒甚至十几秒的延迟。对于"写后立即读"的场景，必须走主库。对于其他场景，可以根据业务容忍度选择：如果用户可以接受几秒的数据延迟（比如查看个人主页），就走从库；如果必须实时（比如支付完成后查看订单状态），就走主库。一种常见的做法是在应用层维护一个"最近写入列表"，对于最近几秒内有过写入操作的用户，其读请求也路由到主库。

```javascript
// Node.js 读写分离示例
const mysql = require('mysql2/promise');

// 主库连接（写操作）
const masterPool = mysql.createPool({
  host: '192.168.1.100',
  user: 'app_writer',
  password: 'write_pass',
  database: 'mydb',
  waitForConnections: true,
  connectionLimit: 10,
});

// 从库连接（读操作）
const slavePool = mysql.createPool({
  host: '192.168.1.101',
  user: 'app_reader',
  password: 'read_pass',
  database: 'mydb',
  waitForConnections: true,
  connectionLimit: 20, // 读多写少，从库连接数可以多一些
});

// 写操作走主库
async function createUser(name, email) {
  const [result] = await masterPool.execute(
    'INSERT INTO users (name, email) VALUES (?, ?)',
    [name, email]
  );
  return result.insertId;
}

// 读操作走从库
async function getUserById(id) {
  const [rows] = await slavePool.execute(
    'SELECT * FROM users WHERE id = ?',
    [id]
  );
  return rows[0];
}

// 注意：刚写入后立即读取可能读到旧数据（复制延迟）
// 解决方案：关键写入后短时间内走主库读取
async function createAndRead(name, email) {
  const id = await createUser(name, email);
  // 刚从主库写入，立即从主库读取，避免复制延迟
  const [rows] = await masterPool.execute(
    'SELECT * FROM users WHERE id = ?',
    [id]
  );
  return rows[0];
}
```

> **Tip：** 对于"写后立即读"的场景，记得走主库读取，否则可能因为复制延迟读到旧数据。这是一个非常常见的坑。
