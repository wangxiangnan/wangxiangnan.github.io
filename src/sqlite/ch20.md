# 第 20 章：性能调优——PRAGMA 与查询优化

## 20.1 引言：性能优化的三重境界

古人云，性能优化有三种境界：

1. **看山是山**：`慢? 我加个索引！`
2. **看山不是山**：`慢? 让我看看 EXPLAIN QUERY PLAN...`
3. **看山还是山**：`慢? 让我看看这个业务需求真的合理吗？`

这一章我们主要停留在第一、第二境界。第三境界靠悟。

**性能调优最重要的原则**：**测量优于臆测**。任何"我觉得这样更快"都要用 benchmark 打脸自己一遍。

好，操家伙。

## 20.2 性能诊断三板斧

### 20.2.1 EXPLAIN：查看 VDBE 字节码

```sql
EXPLAIN SELECT * FROM users WHERE age > 20;
```

`EXPLAIN` 给你返回 SQLite 编译出的 VDBE 指令列表。指令太底层，一般不用它——除非你在深度优化某个热点查询，或者调查 SQLite bug。

### 20.2.2 EXPLAIN QUERY PLAN：人类友好

```sql
EXPLAIN QUERY PLAN SELECT * FROM users WHERE age > 20;
```

输出：

```
QUERY PLAN
`--SCAN users
```

哦，**SCAN**（全表扫描），要命。加上索引：

```sql
CREATE INDEX idx_age ON users(age);
EXPLAIN QUERY PLAN SELECT * FROM users WHERE age > 20;
```

```
QUERY PLAN
`--SEARCH users USING INDEX idx_age (age>?)
```

**SEARCH** 好多了，用了索引。

关键词：

- **SEARCH**：走索引查找（好）
- **SCAN**：全表/全索引扫描（可能不好）
- **USE TEMP B-TREE**：为排序/去重创建了临时 B 树（可能不好）
- **CORRELATED SCALAR SUBQUERY**：相关子查询，每一行都要跑一次（很不好）

**你的目标**：所有热点查询都是 SEARCH，且不出现 TEMP B-TREE。

### 20.2.3 .timer：测量执行时间

在 sqlite3 CLI 里：

```
.timer ON
SELECT count(*) FROM notes;
```

会看到：

```
Run Time: real 0.023 user 0.020 sys 0.002
```

在 Flutter 里，用 `Stopwatch`：

```dart
final sw = Stopwatch()..start();
final rows = await db.rawQuery('SELECT ...');
print('${sw.elapsedMilliseconds}ms');
```

**记得多跑几次取平均值**，第一次会有 IO 缓存冷启动的干扰。

## 20.3 PRAGMA 参数逐一详解

PRAGMA 是 SQLite 的"调节旋钮"，几十个之多。我们挑最重要的讲。

### 20.3.1 journal_mode

前面第 19 章讲过了。移动端选 `WAL`。

### 20.3.2 synchronous

也讲过了。移动端 `NORMAL`。

### 20.3.3 cache_size：页缓存

```sql
PRAGMA cache_size = 2000;    -- 2000 页（正数：页数）
PRAGMA cache_size = -8000;   -- 8000 KB = 8MB（负数：KB）
```

**默认 2000 页**（约 8MB，按 4KB 页算）。

推荐用负数（KB）表示，避免受 page_size 影响。

- 手机应用：8-16MB 够用
- 桌面应用：32-64MB 起步
- 服务器：几百 MB 到几 GB

**注意**：cache_size 是**每个连接**独立的。你开 10 个连接，就有 10 倍缓存！所以移动端连接池要控制大小。

### 20.3.4 page_size

前面讲过。默认 4096，不建议改。

### 20.3.5 temp_store：临时表存储位置

```sql
PRAGMA temp_store = DEFAULT;  -- 编译时决定，通常是 FILE
PRAGMA temp_store = FILE;     -- 临时表存文件
PRAGMA temp_store = MEMORY;   -- 临时表存内存
```

排序、GROUP BY、临时索引等场景 SQLite 会创建临时表。

**移动端建议 `MEMORY`**：省一次磁盘 IO，代价是稍多点内存。

### 20.3.6 mmap_size：内存映射 I/O

```sql
PRAGMA mmap_size = 268435456;  -- 256MB
```

启用后，SQLite 用 `mmap()` 把数据库文件的一部分映射到进程虚拟内存，读取时直接从内存拿数据，跳过 read() 系统调用。

**优点**：

- 读快，特别是随机读
- 减少内存拷贝（内核缓冲 → 用户缓冲的过程省了）

**缺点**：

- 只读加速，写不加速
- 崩溃时可能损坏（页错误信号处理不当）
- 大 mmap 占用虚拟地址空间

**推荐**：

- iOS/Android：64-256MB
- 桌面：几百 MB
- 数据库 > 可用虚拟内存：别开

### 20.3.7 foreign_keys：外键开关

```sql
PRAGMA foreign_keys = ON;
```

**默认是 OFF**！这是 SQLite 的历史遗留问题——早期没有外键，为了兼容默认关。

**永远手动开启**。不开外键约束基本形同虚设。

### 20.3.8 busy_timeout：忙等待

```sql
PRAGMA busy_timeout = 5000;  -- 5 秒
```

当遇到"database is locked"错误时，SQLite 会自动等待并重试，直到超时。

**移动端建议 3-10 秒**。太短容易报错，太长会阻塞 UI。

### 20.3.9 auto_vacuum

前面讲过。移动端一般 NONE 或 INCREMENTAL。

### 20.3.10 secure_delete

```sql
PRAGMA secure_delete = ON;
```

删除数据时把页填 0，防止敏感信息残留。**代价是每次删除都要多写一次**。安全需求强（比如密码管理器）才开。

### 20.3.11 recursive_triggers

```sql
PRAGMA recursive_triggers = ON;
```

允许触发器递归调用（默认 OFF）。用触发器多层同步时可能需要。

### 20.3.12 case_sensitive_like

```sql
PRAGMA case_sensitive_like = ON;
```

LIKE 变成大小写敏感。**副作用：会禁用某些 LIKE 相关的索引优化**。慎用。

### 20.3.13 移动端推荐组合

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA cache_size = -8000;
PRAGMA temp_store = MEMORY;
PRAGMA busy_timeout = 5000;
PRAGMA mmap_size = 134217728;  -- 128MB
PRAGMA wal_autocheckpoint = 1000;
```

Flutter 代码：

```dart
Future<void> optimizePragmas(Database db) async {
  await db.execute('PRAGMA journal_mode = WAL');
  await db.execute('PRAGMA synchronous = NORMAL');
  await db.execute('PRAGMA foreign_keys = ON');
  await db.execute('PRAGMA cache_size = -8000');
  await db.execute('PRAGMA temp_store = MEMORY');
  await db.execute('PRAGMA busy_timeout = 5000');
  await db.execute('PRAGMA mmap_size = 134217728');
}
```

**记住**：这些设置**要在每个连接**打开时都执行（大部分是 per-connection 的，除了 journal_mode 是 per-database 的）。

## 20.4 索引优化的艺术

### 20.4.1 索引的基本原理

前面第 18 章讲过：SQLite 的索引也是 B-Tree，key 是索引列的值，value 是对应行的 rowid。

查询 `WHERE age = 25`：

1. 在 idx_age B-Tree 里找 25，得到 rowid 列表
2. 用每个 rowid 去表 B-Tree 找完整行

**这就是"回表"**。如果你只 `SELECT age`，就不用回表，效率极高。

### 20.4.2 覆盖索引（Covering Index）

如果索引包含了查询需要的所有列，就不用回表：

```sql
-- 表结构
CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT, age INTEGER, email TEXT);

-- 只查 name 和 age
SELECT name, age FROM users WHERE age > 20;

-- 建覆盖索引：age 在前用于过滤，name 在后用于覆盖
CREATE INDEX idx_age_name ON users(age, name);

EXPLAIN QUERY PLAN SELECT name, age FROM users WHERE age > 20;
-- SEARCH users USING COVERING INDEX idx_age_name (age>?)
```

看到 **COVERING INDEX** 了吗？完美，零回表。

**权衡**：覆盖索引会变大。别贪心把所有列都塞进去，那还不如直接扫表。

### 20.4.3 复合索引的顺序问题

```sql
CREATE INDEX idx_ab ON t(a, b);
```

这个索引能加速：

- `WHERE a = ?` ✓
- `WHERE a = ? AND b = ?` ✓
- `WHERE a = ? AND b > ?` ✓
- `WHERE a > ?` ✓（部分）
- `WHERE b = ?` ✗（前导列没用上）
- `WHERE b = ? AND a = ?` ✓（顺序无关，只要 a 是等值）

**规则**：**复合索引的前缀原则**——只能利用索引的前几列。

顺序怎么定？经验法则：

1. 等值查询列在前，范围查询列在后
2. 选择性高（区分度大）的列在前
3. 常用的列在前

### 20.4.4 索引跳跃扫描（Skip Scan）

SQLite 3.8.11+ 支持**索引跳跃扫描**（Skip Scan）：即使前导列没有出现在 WHERE 里，也可能用到后面的列。

```sql
CREATE INDEX idx_gender_age ON users(gender, age);

-- 尽管 WHERE 里没 gender，但 gender 值很少（只有 M/F/其他），SQLite 可能跳跃扫描
SELECT * FROM users WHERE age > 20;
```

只有前导列**选择性极低**（distinct 值很少）时才会用跳跃扫描。一般不用刻意设计，SQLite 自己判断。

### 20.4.5 部分索引：只索引一部分行

```sql
-- 只索引未删除的笔记
CREATE INDEX idx_active_notes ON notes(updated_at) WHERE deleted = 0;
```

好处：

- 索引更小，查询更快
- 更新更快（不满足条件的行不涉及）

场景：软删除表、状态过滤表。第 22 章笔记应用会用到。

### 20.4.6 表达式索引

```sql
-- 对邮箱的小写值建索引
CREATE INDEX idx_lower_email ON users(LOWER(email));

-- 查询也要用同样的表达式才能命中
SELECT * FROM users WHERE LOWER(email) = 'a@b.com';
```

场景：不区分大小写的匹配、JSON 字段抽取、日期格式化查询等。

### 20.4.7 什么时候**不该**加索引

- 表很小（<1000 行）：全表扫描更快
- 列值很少（比如 gender 只有 3 个值）：索引选择性差，可能不如全表扫
- 写多读少：索引维护开销大于查询收益
- 已经有覆盖前缀的复合索引：别重复
- 频繁 UPDATE 的列：每次改都要更新索引

### 20.4.8 索引的成本

- **空间**：索引 = 一棵额外的 B-Tree，占空间
- **写入**：每次 INSERT/UPDATE/DELETE 要同步更新索引
- **VACUUM**：更多数据要整理

移动端受限于空间，一般单表不超过 3-5 个索引。

## 20.5 查询重写技巧

### 20.5.1 EXISTS 通常比 IN 快

```sql
-- 慢（IN 子查询可能物化整个结果集）
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE total > 100);

-- 快（EXISTS 找到一个就短路）
SELECT * FROM users u WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.total > 100
);
```

但对现代 SQLite（3.30+），查询规划器足够聪明能自己转换。**但显式写更保险**。

### 20.5.2 避免 SELECT *

```sql
SELECT * FROM users WHERE id = 1;  -- 会加载所有列
SELECT id, name FROM users WHERE id = 1;  -- 只加载需要的列
```

好处：

- 少的数据传输
- 有机会命中**覆盖索引**
- 未来加列不影响你的应用逻辑

### 20.5.3 LIMIT + ORDER BY 需要合适的索引

```sql
-- 慢：全表扫描 + 排序 + 取前 20
SELECT * FROM notes ORDER BY updated_at DESC LIMIT 20;

-- 加索引后快很多
CREATE INDEX idx_updated ON notes(updated_at);
-- 现在 SQLite 可以反向扫描索引，取前 20 直接停
```

**关键**：SQLite 索引可以正向或反向扫描。所以 `DESC` 一般不需要建反向索引。

### 20.5.4 避免 OR，用 UNION ALL

```sql
-- 可能扫两遍（有时 SQLite 不能同时利用两个索引）
SELECT * FROM t WHERE a = 1 OR b = 2;

-- 更好，两个查询各自用索引，然后合并
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2 AND a != 1;
```

新版 SQLite 支持 **OR 优化**（把 OR 转成 UNION 内部处理），所以差异变小，但显式写还是保险。

### 20.5.5 避免 LIKE '%xxx%'

```sql
-- 慢：前缀 % 让索引失效
SELECT * FROM t WHERE name LIKE '%alice%';

-- 快：后缀 % 可用索引
SELECT * FROM t WHERE name LIKE 'alice%';
```

真的要全文匹配？用 **FTS5**（第 15 章讲过，第 22 章会实战）。

### 20.5.6 大偏移量分页问题

```sql
-- 慢：需要跳过前 100000 行
SELECT * FROM notes ORDER BY id LIMIT 20 OFFSET 100000;

-- 快：keyset pagination
SELECT * FROM notes WHERE id > :last_id ORDER BY id LIMIT 20;
```

**记住"last_seen_id" 分页法**——记住上一页最后一行的 id，下一页从这个 id 之后开始。这是所有数据库通用的性能救命稻草。

### 20.5.7 用 COUNT(*) 而不是 COUNT(列)

```sql
SELECT COUNT(*) FROM t;       -- 快，可能用索引
SELECT COUNT(id) FROM t;      -- 稍慢，要读 id 列
SELECT COUNT(nullable_col) FROM t;  -- 更慢，要判空
```

除非你真的要"某列非空的行数"，否则用 `COUNT(*)`。

## 20.6 批量操作优化

### 20.6.1 事务包裹

**这是最重要的优化，没有之一。**

```dart
// 慢：每一次 insert 都是一个事务，1000 次 fsync
for (var i = 0; i < 1000; i++) {
  await db.insert('t', {'v': i});
}

// 快：整个 batch 一个事务，1 次 fsync
await db.transaction((txn) async {
  for (var i = 0; i < 1000; i++) {
    await txn.insert('t', {'v': i});
  }
});
```

在 WAL + NORMAL 下，1000 条插入：

- 无事务：~800ms
- 有事务：~40ms

**20 倍差距**。原因是 fsync 是磁盘 I/O 的杀手。

### 20.6.2 Prepared Statement 复用

```dart
// sqflite 里用 batch
final batch = db.batch();
for (var i = 0; i < 1000; i++) {
  batch.insert('t', {'v': i});
}
await batch.commit(noResult: true);  // noResult 更快
```

drift 里天然复用 prepared statement：

```dart
await into(notes).insertAll(
  List.generate(1000, (i) => NotesCompanion.insert(title: 'n$i', body: 'b$i')),
  mode: InsertMode.insertOrReplace,
);
```

`insertAll` 内部会用一个 prepared statement 循环执行。

### 20.6.3 UPSERT（v3.24+）

```sql
INSERT INTO t(id, v) VALUES(1, 100)
ON CONFLICT(id) DO UPDATE SET v = excluded.v;
```

单次操作完成"存在则更新，不存在则插入"，比 SELECT + INSERT/UPDATE 快得多。

Flutter：

```dart
await db.rawInsert('''
  INSERT INTO t(id, v) VALUES(?, ?)
  ON CONFLICT(id) DO UPDATE SET v = excluded.v
''', [1, 100]);
```

## 20.7 ANALYZE 与查询规划器

### 20.7.1 ANALYZE 是干啥的

查询规划器要决定"用索引 A 还是索引 B"，需要知道每个索引的"选择性"（distinct 值比例）。这些统计信息就是 `ANALYZE` 生成的。

```sql
ANALYZE;                     -- 分析所有表
ANALYZE users;               -- 只分析 users 表
ANALYZE idx_email;           -- 只分析某个索引
```

ANALYZE 结果存在 `sqlite_stat1`（还有 `sqlite_stat4` 更精细的）：

```sql
SELECT * FROM sqlite_stat1;
-- tbl        idx         stat
-- users      idx_email   1000 1        -- 1000 行，每个 email 平均 1 行（唯一）
-- users      idx_gender  1000 500      -- 1000 行，每个 gender 平均 500 行
```

`stat` 列是空格分隔的整数：`总行数 平均每个索引值对应几行 ...`。

规划器看到 `idx_email`（唯一）就知道"一次查询平均只返回 1 行"，选择性极高。看到 `idx_gender` 就知道"平均返回 500 行"，选择性差，可能不划算。

### 20.7.2 什么时候跑 ANALYZE

- 数据量发生显著变化后
- 加了新索引后
- 感觉查询规划变差时

**移动端建议**：应用第一次启动填完初始数据后跑一次；此后每次 schema 迁移完成后跑一次。别每次启动都跑。

```sql
-- 更快的增量分析
PRAGMA analysis_limit = 400;  -- 每张表最多分析 400 行样本
ANALYZE;
```

`analysis_limit` 是 SQLite 3.32+ 的功能，避免 ANALYZE 在大表上跑几分钟。

### 20.7.3 查询规划器的工作流程

大致流程：

1. **解析** SQL 得到查询树
2. **展开** VIEW、CTE
3. **枚举** 可能的执行计划（几张表 JOIN 有 N! 种顺序）
4. **代价估算**：用 sqlite_stat 估算每种计划的代价
5. **选择** 代价最小的计划
6. **生成** VDBE 字节码

规划器不是 AI，它靠**代价模型 + 启发式**决策。你可以帮它：

```sql
-- 用 INDEXED BY 强制指定索引
SELECT * FROM users INDEXED BY idx_email WHERE email = 'a@b.com';

-- 用 NOT INDEXED 禁止用索引
SELECT COUNT(*) FROM users NOT INDEXED;
```

**慎用**！规划器 95% 情况比你聪明。手动指定索引通常是"这一版本能提升，下一版本反而慢"。

## 20.8 常见反模式

### 反模式 1：N+1 查询

**症状**：查询列表后，对每一项再查一次。

```dart
// 反面教材
final notes = await db.query('notes');
for (final note in notes) {
  final tags = await db.query('tags', where: 'note_id=?', whereArgs: [note['id']]);
  print('${note['title']}: $tags');
}
// N+1 次查询！100 条笔记 = 101 次查询
```

**正确姿势**：JOIN 或 IN + 内存组合

```dart
// 一次查询搞定
final rows = await db.rawQuery('''
  SELECT notes.id, notes.title, tags.name
  FROM notes
  LEFT JOIN note_tags ON note_tags.note_id = notes.id
  LEFT JOIN tags ON tags.id = note_tags.tag_id
''');
// 然后在内存里按 note_id 分组
```

或者：

```dart
final notes = await db.query('notes');
final ids = notes.map((n) => n['id']).toList();
final tagRows = await db.rawQuery(
  'SELECT * FROM tags WHERE note_id IN (${ids.map((_) => '?').join(',')})',
  ids,
);
// 内存组合
```

### 反模式 2：不用参数化查询

```dart
// 错：SQL 注入 + 不能复用编译结果
final rows = await db.rawQuery("SELECT * FROM users WHERE name = '$name'");

// 对：参数化
final rows = await db.rawQuery('SELECT * FROM users WHERE name = ?', [name]);
```

除了安全，性能上参数化查询能被 SQLite 缓存 prepared statement，重复调用几乎零编译开销。

### 反模式 3：大事务

```dart
// 事务里做了 HTTP 请求，太长
await db.transaction((txn) async {
  final data = await http.get(...);   // 慢！事务期间锁死写者
  await txn.insert(...);
});
```

**规则**：事务里只做数据库操作。IO/网络放事务外。

### 反模式 4：忽略 index-only 查询机会

前面讲过覆盖索引。很多情况下调整索引就能把"回表"消除。

### 反模式 5：过度规范化

第三范式是学院派，实战有时候要反规范化：

- 频繁 JOIN 的两张表：合并
- 常用聚合值：冗余存储 + 触发器维护

比如笔记的"标签数"，如果你要在列表页展示，与其每次 COUNT(*)，不如在 notes 表加个 `tag_count` 列，用触发器维护。

### 反模式 6：LIKE 到处开花

用 FTS5。用 FTS5。用 FTS5。（重要的事说三遍）

## 20.9 Flutter 实战：诊断慢查询

### 20.9.1 诊断工具

```dart
class SqlProfiler {
  final Database db;
  final Duration threshold;
  SqlProfiler(this.db, {this.threshold = const Duration(milliseconds: 50)});

  Future<List<Map<String, Object?>>> query(
    String sql, [
    List<Object?>? args,
  ]) async {
    final sw = Stopwatch()..start();
    final result = await db.rawQuery(sql, args);
    sw.stop();
    if (sw.elapsed > threshold) {
      // 慢查询报警
      print('SLOW QUERY (${sw.elapsedMilliseconds}ms): $sql');
      // 顺便打印 EXPLAIN QUERY PLAN
      final plan = await db.rawQuery('EXPLAIN QUERY PLAN $sql', args);
      print('  Plan: $plan');
    }
    return result;
  }
}
```

### 20.9.2 列表加载优化案例

假设有个笔记列表，每条笔记显示标题、标签数、最后修改时间：

```dart
// 慢的版本：N+1
Future<List<NoteVM>> loadNotesSlow() async {
  final notes = await db.query('notes',
      orderBy: 'updated_at DESC', limit: 50);
  final result = <NoteVM>[];
  for (final n in notes) {
    final tagCount = Sqflite.firstIntValue(
      await db.rawQuery(
        'SELECT COUNT(*) FROM note_tags WHERE note_id = ?', [n['id']]
      )
    );
    result.add(NoteVM(n['title']!, tagCount!, n['updated_at']!));
  }
  return result;
}

// 快的版本：一次 JOIN
Future<List<NoteVM>> loadNotesFast() async {
  final rows = await db.rawQuery('''
    SELECT n.id, n.title, n.updated_at, COUNT(nt.tag_id) AS tag_count
    FROM notes n
    LEFT JOIN note_tags nt ON nt.note_id = n.id
    GROUP BY n.id
    ORDER BY n.updated_at DESC
    LIMIT 50
  ''');
  return rows.map((r) => NoteVM(
    r['title'] as String,
    r['tag_count'] as int,
    r['updated_at'] as int,
  )).toList();
}
```

再加合适的索引：

```sql
CREATE INDEX idx_notes_updated ON notes(updated_at);
CREATE INDEX idx_note_tags_note ON note_tags(note_id);  -- 加速 JOIN
```

测试：100 条笔记，每条 3 个标签，实测：

- 慢版本：~180ms
- 快版本：~5ms

**30 倍差距**。

## 20.10 压测：自己写 benchmark

```dart
import 'dart:math';

class Benchmark {
  final String name;
  final Future<void> Function() setup;
  final Future<void> Function() run;
  final Future<void> Function() teardown;

  Benchmark(this.name, {
    required this.setup,
    required this.run,
    required this.teardown,
  });

  Future<BenchmarkResult> execute({int warmup = 3, int iterations = 10}) async {
    await setup();
    // 预热
    for (var i = 0; i < warmup; i++) {
      await run();
    }
    // 正式测量
    final samples = <double>[];
    for (var i = 0; i < iterations; i++) {
      final sw = Stopwatch()..start();
      await run();
      sw.stop();
      samples.add(sw.elapsedMicroseconds / 1000.0);
    }
    await teardown();
    return BenchmarkResult(name, samples);
  }
}

class BenchmarkResult {
  final String name;
  final List<double> samples;
  BenchmarkResult(this.name, this.samples);

  double get mean => samples.reduce((a, b) => a + b) / samples.length;
  double get min => samples.reduce(math.min);
  double get max => samples.reduce(math.max);
  double get p50 {
    final sorted = List<double>.from(samples)..sort();
    return sorted[sorted.length ~/ 2];
  }

  @override
  String toString() =>
      '$name: mean=${mean.toStringAsFixed(2)}ms p50=${p50.toStringAsFixed(2)}ms '
      'min=${min.toStringAsFixed(2)}ms max=${max.toStringAsFixed(2)}ms';
}
```

## 20.11 本章小结

性能优化的心法：

1. **测量优于臆测**：先 EXPLAIN QUERY PLAN，再优化
2. **索引是双刃剑**：写少读多才划算
3. **覆盖索引** 是消除回表的终极武器
4. **事务包裹批量操作**，20 倍性能提升不是梦
5. **PRAGMA 组合拳** 一次设好，收益终身
6. **反模式** 要认识：N+1、大事务、LIKE 到处开花
7. **ANALYZE** 帮助规划器做出更好的决策
8. **keyset pagination** 拯救大偏移量分页
