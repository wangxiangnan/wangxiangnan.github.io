# 第14章：主从复制——数据的镜像术

## 引言：代码世界的"Ctrl+C / Ctrl+V"

想象一下，你是一个开源项目的作者，你的代码在 GitHub 上只有一个仓库。某天，你的服务器硬盘"啪"地一声挂了——恭喜，你的代码从此消失在了数字黑洞中。如果你之前 fork 了一份到另一个仓库，是不是感觉天都要塌不下来了？

Redis 的主从复制（Master-Slave Replication）就是给数据来了一次"Git Fork"。主节点（Master）就是 upstream 仓库，负责接收所有的写操作；从节点（Replica）就是 fork 出来的 downstream 仓库，自动同步主节点的数据，并且可以承担读请求。

但和 Git fork 不同的是，Redis 的主从复制是**实时自动同步**的——你往 master 写一个 `SET`，replica 那边几乎立刻就能 `GET` 到。就像是给 master 装了一面镜子，所有操作都被"镜像"到了从节点。

> **编程隐喻时间**：主从复制 ≈ Git 的 fork + 自动 pull。Master 是 upstream，Replica 是 fork 出来的 repo，Replication 就是那个永不停歇的 `git pull` 进程。

## 14.1 为什么需要主从复制？

在单节点 Redis 中，你面临三个核心问题：

| 问题 | 描述 | 主从复制如何解决 |
|------|------|------------------|
| **读扩展** | 读请求太多，单节点扛不住 | 将读请求分发到多个从节点 |
| **数据冗余** | 单点故障 = 数据全丢 | 从节点持有完整的数据副本 |
| **容灾备份** | 服务器物理损坏 | 从节点可以部署在不同机房 |

还有一个常被忽略的场景：**在线备份**。在主节点上执行 `BGSAVE` 可能会短暂阻塞写操作，但在从节点上执行就不会影响主节点的性能。

## 14.2 主从复制的工作原理

Redis 的主从复制分为两个阶段：**全量同步**和**增量同步**。

### 14.2.1 全量同步（Full Resynchronization）

全量同步发生在从节点**第一次**连接主节点时，或者无法执行增量同步时。流程如下：

```
Replica                           Master
  |  ------ 1. PSYNC ? -1 ------>  |
  |                                  |  2. 执行 BGSAVE 生成 RDB
  |                                  |  3. 将 RDB 文件发送给 Replica
  |  <----- 4. 接收 RDB 文件 ------  |
  |  5. 加载 RDB 到内存              |
  |                                  |  6. 在 BGSAVE 期间的写命令被缓冲
  |  <----- 7. 发送缓冲区命令 -----  |
  |  8. 执行缓冲的命令               |
  |  ---- 同步完成，进入命令传播 ---> |
```

关键步骤：

1. 从节点发送 `PSYNC ? -1`（表示自己是全新的）
2. 主节点执行 `BGSAVE`，在后台生成 RDB 快照
3. 主节点将 RDB 文件通过网络发送给从节点
4. 从节点加载 RDB 文件到内存
5. 在 `BGSAVE` 期间，主节点的写命令被记录在**复制缓冲区**（replication buffer）中
6. 主节点将缓冲区中的命令发送给从节点
7. 从节点执行这些命令，追赶上主节点

### 14.2.2 增量同步（Partial Resynchronization）

如果从节点只是短暂断线后重连，Redis 会尝试**部分重同步**，避免昂贵的全量复制：

```
Replica                           Master
  |  ---- 连接断开 ----              |
  |                                  |  继续接收写命令，记录在 repl_backlog
  |  ---- 重新连接 ----              |
  |  --- PSYNC <runid> <offset> -->  |
  |                                  |  检查 offset 是否在 backlog 中
  |  <----- +CONTINUE ------------  |
  |  <--- 发送 offset 之后的命令 --- |
  |  执行缺失的命令，恢复同步         |
```

核心机制：

- 每个主节点有一个 **运行ID（runid）**，每次启动时随机生成
- 每个复制操作维护一个 **复制偏移量（offset）**，每传播一个字节就 +1
- 主节点维护一个固定大小的 **复制积压缓冲区（replication backlog）**，默认 1MB

如果从节点断线时间太短，backlog 中的数据还够用，那就执行部分重同步，快如闪电。如果断线太久，backlog 被覆盖了，就只能老老实实做全量同步。

### 14.2.3 复制偏移量（Offset）详解

```bash
# 查看主节点的复制信息
redis> INFO replication
# Keyspace
master_repl_offset:29451
repl_backlog_active:1
repl_backlog_size:1048576
repl_backlog_first_byte_offset:29451
repl_backlog_histlen:0
```

> **Tip**：`repl_backlog_size` 默认 1MB，如果你的写入速度很快（比如每秒 10KB），那从节点最多只能断线约 100 秒还能部分重同步。如果网络不稳定，建议调大这个值。

## 14.3 配置主从复制

### 14.3.1 使用 REPLICAOF 命令（动态配置）

```bash
# 在从节点上执行（运行时动态配置）
redis> REPLICAOF 192.168.1.100 6379
OK

# 查看复制状态
redis> INFO replication
# Replication
role:slave
master_host:192.168.1.100
master_port:6379
master_link_status:up

# 取消复制，将从节点提升为独立主节点
redis> REPLICAOF NO ONE
OK
```

### 14.3.2 配置文件方式（持久化配置）

```bash
# redis-replica.conf
port 6380
replicaof 192.168.1.100 6379

# 如果主节点有密码
masterauth your_master_password

# 复制积压缓冲区大小（默认 1MB，大流量场景建议调大）
repl-backlog-size 10mb

# 从节点是否提供读服务（默认 yes）
replica-read-only yes
```

启动从节点：

```bash
redis-server redis-replica.conf
```

## 14.4 主从拓扑结构

Redis 支持多种复制拓扑，就像组织架构图一样灵活：

### 14.4.1 一主一从（最简配置）

```
  Master (6379)
      |
  Replica (6380)
```

最简单的冗余方案，就像给代码加了一个备份仓库。

### 14.4.2 一主多从（星形结构）

```
           Master (6379)
          /     |     \
  Replica1   Replica2   Replica3
   (6380)     (6381)     (6382)
```

适用于**读多写少**的场景，多个从节点分担读压力。

### 14.4.3 级联复制（树形结构）

```
           Master (6379)
              |
         Replica1 (6380)
          /        \
  Replica2        Replica3
   (6381)          (6382)
```

当从节点很多时，级联复制可以减轻主节点的网络和 CPU 压力。就像 Git 中的"二级 fork"——你从 upstream fork 了一份，你的同事又从你的 fork 再 fork 一份。

```bash
# Replica1 既是 Master 的 replica，又是 Replica2 的 master
# 需要在 Replica1 上开启：
replica-serve-stale-data yes

# Replica2 配置 Replica1 为自己的 master
replicaof 192.168.1.101 6380
```

## 14.5 读写分离策略

### 14.5.1 READONLY / READWRITE 命令

在 Redis Cluster 环境中，从节点默认不接受读请求。需要使用 `READONLY` 命令开启：

```bash
# 在 Cluster 的从节点上执行
redis> READONLY
OK

# 现在可以从从节点读取数据了
redis> GET some_key
"value"

# 恢复为只写模式（不接受读请求）
redis> READWRITE
OK
```

### 14.5.2 从节点的一致性保证

这里有一个**非常重要**的概念：Redis 的主从复制是**异步**的。

```
Client                Master              Replica
  | --- SET x 1 -->    |                     |
  | <-- OK ----------  |                     |
  |                      | -- 异步复制 -->    |
  | --- GET x ------>   |                     |
  |                       \                   |
  |  ------ GET x ------------------------->  |
  |  <-- (nil) ??? -------------------------  |  （数据还没同步过来！）
```

这就是所谓的**复制延迟**（replication lag）。如果你刚写入 master 就立刻从 replica 读，可能读到旧数据。

> **Warning**：对于强一致性要求的场景（比如用户刚修改密码就立刻验证），**必须从 master 读取**。读写分离只适用于对一致性要求不高的场景（比如读文章、读商品列表）。

## 14.6 Node.js 中实现读写分离

### 14.6.1 基础主从连接

```js
const Redis = require('ioredis');

// 连接主节点（负责写）
const master = new Redis({
  host: '192.168.1.100',
  port: 6379,
  password: 'your_master_password',
});

// 连接从节点（负责读）
const replica = new Redis({
  host: '192.168.1.101',
  port: 6380,
});

// 写操作 -> Master
async function writeData(key, value) {
  await master.set(key, value);
  console.log(`写入 Master: ${key} = ${value}`);
}

// 读操作 -> Replica
async function readData(key) {
  const value = await replica.get(key);
  console.log(`从 Replica 读取: ${key} = ${value}`);
  return value;
}

// 使用示例
(async () => {
  await writeData('user:1001', JSON.stringify({ name: '张三', age: 25 }));
  
  // 加一个小延迟，等待复制完成（生产环境可以用其他策略）
  await new Promise(resolve => setTimeout(resolve, 100));
  
  const user = await readData('user:1001');
  console.log('读取结果:', JSON.parse(user));
  
  master.disconnect();
  replica.disconnect();
})();
```

### 14.6.2 自动读写路由器

```js
const Redis = require('ioredis');

/**
 * 读写分离路由器
 * 自动将写操作路由到 Master，读操作路由到 Replica
 * 支持多个 Replica 的负载均衡
 */
class ReadWriteRouter {
  constructor(masterConfig, replicaConfigs) {
    this.master = new Redis(masterConfig);
    this.replicas = replicaConfigs.map(config => new Redis(config));
    this.replicaIndex = 0;

    // 监听连接事件
    this.master.on('connect', () => console.log('[Router] Master 已连接'));
    this.replicas.forEach((r, i) => {
      r.on('connect', () => console.log(`[Router] Replica-${i} 已连接`));
    });
  }

  // 轮询选择 Replica（简单的负载均衡）
  _getReplica() {
    const replica = this.replicas[this.replicaIndex];
    this.replicaIndex = (this.replicaIndex + 1) % this.replicas.length;
    return replica;
  }

  // 写命令集合
  static WRITE_COMMANDS = new Set([
    'set', 'del', 'hset', 'hdel', 'lpush', 'rpush', 'lpop', 'rpop',
    'sadd', 'srem', 'zadd', 'zrem', 'expire', 'incr', 'decr',
    'setnx', 'setex', 'psetex', 'mset', 'append', 'lset', 'linsert',
  ]);

  // 执行命令（自动路由）
  async execute(command, ...args) {
    const cmd = command.toLowerCase();
    if (ReadWriteRouter.WRITE_COMMANDS.has(cmd)) {
      return this.master[cmd](...args);
    } else {
      return this._getReplica()[cmd](...args);
    }
  }

  // 强制从 Master 读（强一致性场景）
  async readFromMaster(command, ...args) {
    const cmd = command.toLowerCase();
    return this.master[cmd](...args);
  }

  // 关闭所有连接
  disconnect() {
    this.master.disconnect();
    this.replicas.forEach(r => r.disconnect());
  }
}

// 使用示例
const router = new ReadWriteRouter(
  { host: '192.168.1.100', port: 6379 },
  [
    { host: '192.168.1.101', port: 6380 },
    { host: '192.168.1.102', port: 6380 },
  ]
);

(async () => {
  // 写操作自动路由到 Master
  await router.execute('set', 'product:100', JSON.stringify({
    name: 'Redis 实战',
    price: 59.9,
  }));

  // 读操作自动路由到 Replica（轮询）
  const product1 = await router.execute('get', 'product:100');
  console.log('第一次读（Replica-0）:', product1);

  const product2 = await router.execute('get', 'product:100');
  console.log('第二次读（Replica-1）:', product2);

  // 强一致性读（强制从 Master 读）
  await router.execute('set', 'stock:100', '50');
  const stock = await router.readFromMaster('get', 'stock:100');
  console.log('强一致性读（Master）:', stock);

  router.disconnect();
})();
```

### 14.6.3 使用 Sentinel 模式自动发现

```js
const Redis = require('ioredis');

// ioredis 内置 Sentinel 支持，自动发现主节点
const redis = new Redis({
  sentinels: [
    { host: '192.168.1.10', port: 26379 },
    { host: '192.168.1.11', port: 26379 },
    { host: '192.168.1.12', port: 26379 },
  ],
  name: 'mymaster',       // Sentinel 监控的主节点名称
  password: 'your_password',
});

redis.on('connect', () => {
  console.log('已通过 Sentinel 自动发现并连接到 Master');
});

redis.on('+master', (msg) => {
  console.log('Master 切换事件:', msg);
});
```

## 14.7 主从复制的限制和注意事项

### 14.7.1 主要限制

1. **异步复制导致的数据不一致**：写入 Master 后立刻 crash，Replica 可能丢失最后几条命令。解决方案：使用 `WAIT` 命令实现同步复制。
2. **Master 宕机时的数据丢失**：如果 Master 在数据复制到 Replica 之前就挂了，数据会丢失。解决方案：配合 Sentinel 实现自动故障转移。
3. **全量同步的性能影响**：`BGSAVE` 生成 RDB 快照时会 fork 子进程，可能导致短暂阻塞。
4. **写扩展不受支持**：所有写操作仍然只能由 Master 处理，写扩展需要使用 Redis Cluster。

### 14.7.2 使用 WAIT 命令提高一致性

```js
const Redis = require('ioredis');
const master = new Redis({ host: '192.168.1.100', port: 6379 });

async function writeWithConfirmation(key, value) {
  await master.set(key, value);
  
  // 等待至少 1 个 Replica 确认收到数据
  const confirmed = await master.wait(1, 5000);
  
  if (confirmed >= 1) {
    console.log(`数据已同步到 ${confirmed} 个 Replica`);
  } else {
    console.warn('数据可能尚未同步，存在丢失风险');
  }
}

writeWithConfirmation('critical:data', 'must_not_lose');
master.disconnect();
```

> **Warning**：`WAIT` 命令虽然提供了更强的一致性保证，但它仍然不是真正的同步复制。在极端情况下（比如 Master 和所有 Replica 同时宕机），数据仍然可能丢失。

## 14.8 主从复制的监控

```js
const Redis = require('ioredis');
const master = new Redis({ host: '192.168.1.100', port: 6379 });

async function monitorReplication() {
  const info = await master.info('replication');
  const lines = info.split('\r\n');
  const replicationInfo = {};
  
  for (const line of lines) {
    const [key, value] = line.split(':');
    if (key && value) replicationInfo[key.trim()] = value.trim();
  }

  console.log('=== 主从复制监控 ===');
  console.log(`角色: ${replicationInfo.role}`);
  console.log(`已连接的 Replica 数: ${replicationInfo.connected_slaves}`);
  console.log(`Master 偏移量: ${replicationInfo.master_repl_offset}`);

  for (let i = 0; i < parseInt(replicationInfo.connected_slaves); i++) {
    const slaveInfo = replicationInfo[`slave${i}`];
    if (slaveInfo) console.log(`\nReplica-${i}: ${slaveInfo}`);
  }

  master.disconnect();
}

monitorReplication();
```

## 小结

主从复制是 Redis 高可用的基石。它就像 Git 的 fork + auto pull 机制——Master 是 upstream 仓库，Replica 是 fork 出来的副本，数据通过异步复制保持同步。

核心要点：

- 全量同步用于首次连接或断线过久的情况
- 增量同步利用复制偏移量和积压缓冲区实现快速恢复
- 读写分离可以分担读压力，但要注意异步复制的一致性问题
- `WAIT` 命令可以在关键操作中提供更强的数据一致性保证

## 练习题

1. **基础题**：搭建一个一主两从的 Redis 环境，验证数据同步是否正常工作。
2. **进阶题**：编写一个 Node.js 脚本，监控主从复制的延迟（通过比较 Master 和 Replica 的 offset），当延迟超过阈值时发出告警。
3. **挑战题**：实现一个带有"写后读一致性保证"的读写路由器——当检测到刚执行过写操作时，后续的读请求自动路由到 Master，直到复制延迟追上来。
