# 第7章 子查询

## 7.1 子查询的概念：SQL里的函数调用

想象你在做菜，菜谱写着"加入适量的盐"。什么叫"适量"？你得先尝一口汤，判断咸淡，然后再决定加多少盐。这个"先尝一口判断"的过程，就是子查询的本质——在一个查询内部，先执行另一个查询来获取中间结果，然后再用这个结果指导外层查询的行为。

子查询（Subquery）就是嵌套在另一个SQL语句中的SELECT语句。你可以把它理解为SQL世界的"函数调用"：主查询是main函数，子查询是被调用的helper函数。子查询先跑完，把结果交回来，主查询拿着这个结果继续处理。这种嵌套结构让你的SQL可以表达更加复杂的逻辑，而不需要把每一步都拆成独立的查询然后手动拼接结果。

从程序设计的角度看，子查询就像是在一个表达式中嵌入了另一个表达式的求值过程。如果你写过JavaScript，这就好比 `array.filter(item => item.price > array.reduce(...))` 这种在一行里嵌套多个操作的写法。优雅、紧凑，但有时候读起来也需要费点脑筋。

子查询可以出现在SQL语句的多个位置：WHERE子句、FROM子句、SELECT子句，甚至HAVING子句中。根据返回结果的形状不同，子查询可以分为四类：标量子查询返回单个值（一行一列），就像函数返回一个数字或字符串；列子查询返回一列多行，像一个数组；行子查询返回一行多列，像一个元组或对象；表子查询返回多行多列，像一张完整的临时表。

首先我们来准备本章的示例数据，后续所有子查询的演示都基于这张员工表：

```sql
-- 创建员工表并插入示例数据
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(50),
    department VARCHAR(30),
    salary DECIMAL(10,2),
    manager_id INT
);

INSERT INTO employees VALUES
(1, '张三', '技术部', 15000, NULL),
(2, '李四', '技术部', 12000, 1),
(3, '王五', '市场部', 10000, 1),
(4, '赵六', '市场部', 8000, 3),
(5, '钱七', '财务部', 11000, 1),
(6, '孙八', '技术部', 18000, 1),
(7, '周九', '市场部', 9500, 3),
(8, '吴十', '财务部', 9000, 5);
```

## 7.2 WHERE子查询：最常见的嵌套方式

WHERE子查询是把子查询放在WHERE条件中，用子查询的结果作为过滤条件。这是最直觉、最容易理解的子查询用法，也是你在实际开发中最常遇到的场景。

**标量子查询**返回一个单独的值，通常和比较运算符（=、>、<、>=、<=、!=）一起使用。比如你想找工资高于平均水平的员工，首先需要知道平均工资是多少——这就是一个标量子查询：

```sql
-- 找出工资高于平均工资的员工
-- 子查询先算出平均工资（约11562.50），然后外层查询筛选高于此值的人
SELECT emp_name, salary
FROM employees
WHERE salary > (
    SELECT AVG(salary) FROM employees
);
-- 结果：张三(15000), 孙八(18000), 李四(12000)
-- 平均工资约为11562.50，高于此值的员工被筛选出来
```

**列子查询**返回一列多行的结果，通常配合IN或NOT IN使用。IN操作符判断某个值是否在子查询返回的"列表"中，就像你在购物时对照购物清单一样：

```sql
-- 找出有下属的管理者（即出现在别人manager_id中的人）
SELECT emp_name FROM employees
WHERE emp_id IN (
    SELECT DISTINCT manager_id FROM employees WHERE manager_id IS NOT NULL
);
-- 结果：张三（1号，是李四、王五、孙八、钱七的领导）
--       王五（3号，是赵六、周九的领导）
--       钱七（5号，是吴十的领导）
```

**行子查询**返回一行多列，你可以同时比较多个字段的组合。这种用法相对少见，但在某些场景下非常简洁：

```sql
-- 找出技术部工资最高的那个人
-- 子查询返回(department, max_salary)这一行，外层匹配这两个条件
SELECT emp_name, department, salary
FROM employees
WHERE (department, salary) = (
    SELECT department, MAX(salary)
    FROM employees
    WHERE department = '技术部'
);
-- 返回：孙八, 技术部, 18000
```

> **Warning:** NOT IN 遇到 NULL 值会踩一个非常隐蔽的坑！如果子查询结果中包含NULL值，整个NOT IN表达式会返回空结果集。原因是SQL中任何值和NULL比较的结果都是UNKNOWN，而UNKNOWN在布尔逻辑中被视为FALSE。比如 `WHERE emp_id NOT IN (1, 3, NULL)`，对于emp_id=2来说，表达式变成 `2!=1 AND 2!=3 AND 2!=NULL`，最后一项 `2!=NULL` 的结果是UNKNOWN，整个AND表达式的结果也就是UNKNOWN，这行数据就被过滤掉了。安全写法是在子查询中加上 `WHERE manager_id IS NOT NULL` 过滤掉NULL值，或者改用NOT EXISTS来替代。

## 7.3 FROM子查询（派生表）

把子查询放在FROM子句中，相当于创建了一张临时的"虚拟表"，专业术语叫**派生表（Derived Table）**。这个子查询先执行，生成一个临时的结果集，然后外层查询像操作普通表一样操作它。

派生表特别适合需要"先聚合、再过滤"的场景。比如你想知道每个部门的最高工资是多少，并且只想看那些最高工资超过15000的部门——你需要先按部门分组算出最高工资，然后再筛选：

```sql
-- 找出每个部门工资最高的员工
-- 先用子查询算出每个部门的最高工资，再和原表JOIN找出对应的人
SELECT e.emp_name, e.department, e.salary, dept_max.max_salary
FROM employees e
INNER JOIN (
    SELECT department, MAX(salary) AS max_salary
    FROM employees
    GROUP BY department
) AS dept_max ON e.department = dept_max.department
              AND e.salary = dept_max.max_salary;
```

> **Warning:** MySQL 严格要求FROM子查询必须有一个别名（上面代码中的 `AS dept_max`）。即使你后面并没有用到这个别名，也必须写上，否则MySQL会报语法错误 `Every derived table must have its own alias`。这是新手最常踩的坑之一，务必记住。

```sql
-- 计算各部门的平均工资，然后找出高于全公司总平均工资的部门
SELECT dept_avg.department, dept_avg.avg_salary
FROM (
    SELECT department, AVG(salary) AS avg_salary
    FROM employees
    GROUP BY department
) AS dept_avg
WHERE dept_avg.avg_salary > (
    SELECT AVG(salary) FROM employees
);
-- 技术部平均工资15000高于公司平均11562.50，所以只有技术部被选中
```

## 7.4 SELECT子查询

子查询也可以放在SELECT列表中，通常用于为每一行计算一些对比值或附加信息。SELECT子查询必须是标量子查询——每行只返回一个值。

需要注意的是，SELECT子查询对外层查询的每一行都会执行一次。如果外层查询返回1000行，子查询就要执行1000次。所以在数据量大的时候，这种方式可能成为性能瓶颈：

```sql
-- 每个员工的工资和全公司平均工资的对比
-- 子查询 (SELECT AVG(salary) FROM employees) 每行都会执行一次
SELECT
    emp_name,
    salary,
    (SELECT AVG(salary) FROM employees) AS company_avg,
    salary - (SELECT AVG(salary) FROM employees) AS diff_from_avg
FROM employees;
```

> **Tip:** SELECT子查询每行都会执行一次，如果外层查询结果集很大，性能会受到明显影响。能用JOIN的场景尽量用JOIN改写。比如上面的例子可以改写为 `CROSS JOIN (SELECT AVG(salary) AS avg_sal FROM employees)` 来避免重复执行。

## 7.5 EXISTS 与 NOT EXISTS

EXISTS是一个非常优雅且常常被低估的子查询操作符。它不关心子查询返回了什么数据，只关心**有没有返回行**。有行就是TRUE，没行就是FALSE。这就像你检查冰箱里有没有牛奶——你不需要知道牛奶的品牌和保质期，只需要确认"有"还是"没有"。

EXISTS的另一个优点是性能好。一旦子查询找到第一行匹配的数据，它就会立即停止扫描（短路求值），不需要把所有匹配的行都找出来。相比之下，IN操作符可能需要把子查询的所有结果都算出来才能判断：

```sql
-- 找出有下属的员工（即出现在别人manager_id中的员工）
SELECT DISTINCT e1.emp_name
FROM employees e1
WHERE EXISTS (
    SELECT 1 FROM employees e2
    WHERE e2.manager_id = e1.emp_id
);
-- 张三有4个直接下属，王五有2个，钱七有1个，所以这三个人会被选出
```

```sql
-- 找出没有下属的员工（叶子节点员工，不带团队的人）
SELECT e1.emp_name
FROM employees e1
WHERE NOT EXISTS (
    SELECT 1 FROM employees e2
    WHERE e2.manager_id = e1.emp_id
);
-- 李四、赵六、孙八、周九、吴十 没有下属
```

> **Tip:** EXISTS子查询中SELECT后面写什么都无所谓（写1、写*、写'hello'、写NULL都行），因为MySQL只检查是否有行返回，根本不关心具体内容。行业惯例写 `SELECT 1`，简洁明了。有些老程序员习惯写 `SELECT *`，虽然功能一样但语义上不够清晰——我们又不需要那行的数据，写* 反而暗示我们需要所有列。

## 7.6 ANY / ALL / SOME 关键字

这三个关键字用在比较运算符和子查询之间，可以改变比较操作符的语义。你可以把它们理解为量词：ANY是"存在"（数学里的存在量词），ALL是"全部"（全称量词），SOME是ANY的别名。

ANY的意思是"只要子查询中有任何一个值满足条件就算通过"。比如"工资比市场部任何人都高"——只要比市场部最低工资高就算满足。ALL的意思是"必须子查询中所有值都满足条件"——要比市场部工资最高的人还高才算满足：

```sql
-- ANY: 只要比子查询中任意一个值大就满足
-- 找出工资比市场部任何人都高的员工
SELECT emp_name, salary, department
FROM employees
WHERE salary > ANY (
    SELECT salary FROM employees WHERE department = '市场部'
);
-- 市场部工资为8000、9500、10000，所以工资>8000的人都满足
-- 张三(15000)、李四(12000)、钱七(11000)、孙八(18000)都满足
```

```sql
-- ALL: 必须比子查询中所有值都大才满足
-- 找出工资比市场部所有人都高的员工
SELECT emp_name, salary, department
FROM employees
WHERE salary > ALL (
    SELECT salary FROM employees WHERE department = '市场部'
);
-- 市场部最高工资是10000，所以工资>10000的人才满足
-- 张三(15000)、李四(12000)、孙八(18000)
```

为了方便记忆，这里有一个等价转换表，帮你理解ANY/ALL和聚合函数之间的关系：

| 表达式 | 含义 | 等价写法 |
|--------|------|----------|
| `> ANY` | 大于最小值 | `> MIN()` |
| `> ALL` | 大于最大值 | `> MAX()` |
| `= ANY` | 等于任一值 | `IN` |
| `!= ALL` | 不等于所有值 | `NOT IN` |

## 7.7 相关子查询 vs 非相关子查询

这是理解子查询性能特征的关键概念。**非相关子查询**可以独立运行，不依赖外层查询的任何变量。它只执行一次，结果缓存起来供外层的所有行使用。就像一个常量——算一次，到处用。

**相关子查询**引用了外层查询的列，每处理外层的一行，子查询就要重新执行一次。就像一个依赖外部变量的函数——每次传入不同的参数，每次都要重新计算。用编程类比的话，非相关子查询是循环外面的预计算，相关子查询是循环里面的重复计算：

```sql
-- 非相关子查询：子查询独立运行，只执行一次
SELECT emp_name FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);
-- 子查询 SELECT AVG(salary) 和外面的 emp_name 无关，只执行一次

-- 相关子查询：找每个部门工资排名前2的员工
-- 子查询中的 e1.department 和 e1.salary 引用了外层的 e1
SELECT emp_name, department, salary
FROM employees e1
WHERE (
    SELECT COUNT(*)
    FROM employees e2
    WHERE e2.department = e1.department
      AND e2.salary > e1.salary
) < 2
ORDER BY department, salary DESC;
-- 对于e1的每一行，子查询都要数一下同部门中有多少人比这个人工资高
-- 如果少于2人（即0人或1人），说明这个人排名前2
```

> **Warning:** 相关子查询的性能问题在于"每行都要执行一次子查询"。如果外层有100万行数据，子查询就要跑100万次，每次可能还要扫描大表。对于大数据量场景，优先考虑用JOIN或窗口函数（第10章）来改写。窗口函数的ROW_NUMBER()可以非常优雅地解决Top-N问题，而且性能好得多。

## 7.8 子查询性能注意事项与JOIN改写

子查询写起来很直观很符合人类的思维习惯，但它不一定是最优解。MySQL的查询优化器有时候对子查询的处理不够聪明，特别是在老版本（5.7及之前）中，很多子查询不会被优化为JOIN。即使到了MySQL 8.0，仍然有些场景下手动改写为JOIN会更快。

以下是一些常见的改写模式，你可以把它当作一个"子查询到JOIN"的转换手册：

```sql
-- 模式1: IN子查询 -> INNER JOIN + DISTINCT
-- 子查询写法
SELECT customer_name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders);

-- 等价的JOIN写法（通常更快，因为有索引可以利用）
SELECT DISTINCT c.customer_name
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- 模式2: NOT IN子查询 -> LEFT JOIN + IS NULL
-- 子查询写法（注意要过滤NULL！）
SELECT emp_name FROM employees
WHERE emp_id NOT IN (SELECT manager_id FROM employees WHERE manager_id IS NOT NULL);

-- JOIN改写
SELECT e1.emp_name
FROM employees e1
LEFT JOIN (SELECT DISTINCT manager_id FROM employees WHERE manager_id IS NOT NULL) e2
  ON e1.emp_id = e2.manager_id
WHERE e2.manager_id IS NULL;

-- 模式3: EXISTS子查询 -> INNER JOIN（需要去重）
-- 子查询写法
SELECT emp_name FROM employees e1
WHERE EXISTS (SELECT 1 FROM employees e2 WHERE e2.manager_id = e1.emp_id);

-- JOIN改写
SELECT DISTINCT e1.emp_name
FROM employees e1
INNER JOIN employees e2 ON e2.manager_id = e1.emp_id;
```

选择子查询还是JOIN，可以参考这个简单的决策流程：如果逻辑简单、数据量小，子查询可读性更好就用子查询；如果涉及大数据量或嵌套层级深，优先用JOIN或CTE（第9章）；如果涉及排名或分组内的计算，用窗口函数（第10章）。

## 小结

子查询是SQL中嵌套查询的利器，可以出现在WHERE、FROM、SELECT等多个位置，让你在一个查询中引用另一个查询的结果。EXISTS适合判断存在性且性能优秀（短路求值），ANY/ALL适合范围比较。相关子查询每行都要重新执行，要注意性能问题。大数据量场景优先考虑JOIN改写或窗口函数替代。
