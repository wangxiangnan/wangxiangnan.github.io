# Ch08: Node.js 后端应用 — apps/api

## 本章目标

> 搭建一个生产就绪的 Express 后端应用，涵盖 RESTful 路由设计、中间件架构、请求验证（Zod + 共享 Schema）、Prisma 数据库集成、以及端到端类型安全。重点讲解 monorepo 环境下后端服务的组织方式和最佳实践。

**为什么用 `tsx` 而不是 `ts-node`？**

`tsx` 基于 esbuild，启动速度比 `ts-node` 快 10 倍以上。在开发阶段，`tsx watch` 能实现毫秒级的文件变更重启，这对后端的开发体验至关重要。`ts-node` 在大型项目中启动可能需要 5-10 秒，而 `tsx` 通常在 200ms 以内。

## 8.2 应用入口和中间件配置

创建 `apps/api/src/index.ts`：

```typescript
import 'dotenv/config';
import express from 'express';
import cors from 'cors';
import helmet from 'helmet';
import morgan from 'morgan';
import { env } from './config/env.js';
import { errorHandler } from './middleware/error-handler.js';
import { userRoutes } from './routes/user.routes.js';
import { authRoutes } from './routes/auth.routes.js';

const app = express();

// ====== 安全中间件 ======
// Helmet 设置各种 HTTP 安全头（XSS 防护、CSP 等）
app.use(helmet());

// CORS 配置 — 开发环境允许前端跨域
app.use(cors({
  origin: env.CORS_ORIGINS,
  credentials: true,
}));

// ====== 解析中间件 ======
app.use(express.json({ limit: '10mb' }));
app.use(express.urlencoded({ extended: true }));

// ====== 日志中间件 ======
// morgan 的 'dev' 格式会在控制台用颜色显示请求信息
app.use(morgan(env.NODE_ENV === 'production' ? 'combined' : 'dev'));

// ====== 健康检查 ======
app.get('/health', (_req, res) => {
  res.json({ status: 'ok', timestamp: new Date().toISOString() });
});

// ====== 路由 ======
app.use('/api/auth', authRoutes);
app.use('/api/users', userRoutes);

// ====== 404 处理 ======
app.use((_req, res) => {
  res.status(404).json({
    success: false,
    error: { code: 'NOT_FOUND', message: '请求的资源不存在' },
  });
});

// ====== 全局错误处理中间件（必须放在最后）======
app.use(errorHandler);

// ====== 启动服务器 ======
app.listen(env.PORT, () => {
  console.log(`API server running on http://localhost:${env.PORT}`);
  console.log(`Environment: ${env.NODE_ENV}`);
});

export default app;
```

**为什么错误处理中间件必须放在最后？**

Express 的中间件是按注册顺序执行的。错误处理中间件（四个参数的函数）只会捕获前面中间件和路由中调用 `next(err)` 传递的错误。如果放在路由前面，它就捕获不到路由中抛出的错误。这是 Express 的核心设计，初学者常在这里犯错。

## 8.3 环境变量管理（dotenv + 类型化的 env）

创建 `apps/api/src/config/env.ts`：

```typescript
import 'dotenv/config';
import { z } from 'zod';

/**
 * 使用 Zod 对环境变量进行运行时验证
 * 
 * 为什么不直接用 process.env？
 * 1. process.env 的所有值都是 string | undefined，需要手动转换类型
 * 2. 缺少的环境变量在运行时才会暴露（通常是在最不该出错的时候）
 * 3. 没有集中管理和文档化的地方
 * 
 * 使用 Zod 验证：
 * - 应用启动时立即检查所有必需的环境变量
 * - 自动转换为正确的类型（数字、布尔值、数组）
 * - 缺少必需变量时立即崩溃并给出清晰的错误信息
 */

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().default(3000),

  // 数据库
  DATABASE_URL: z.string().url('DATABASE_URL 必须是有效的 URL'),

  // JWT
  JWT_SECRET: z.string().min(32, 'JWT_SECRET 至少需要 32 个字符'),
  JWT_REFRESH_SECRET: z.string().min(32, 'JWT_REFRESH_SECRET 至少需要 32 个字符'),

  // CORS
  CORS_ORIGINS: z.string()
    .default('http://localhost:5173')
    .transform((val) => val.split(',').map((s) => s.trim())),
});

// 验证并导出类型化的环境变量
const parsed = envSchema.safeParse(process.env);

if (!parsed.success) {
  console.error('环境变量验证失败:');
  console.error(parsed.error.format());
  process.exit(1);
}

export const env = parsed.data;

// 导出类型，供其他地方使用
export type Env = z.infer<typeof envSchema>;
```

## 8.4 错误处理中间件

创建 `apps/api/src/middleware/error-handler.ts`：

```typescript
import type { Request, Response, NextFunction } from 'express';
import { AppError } from '@monorepo/shared/utils';
import type { ApiResponse } from '@monorepo/shared/types';
import { HTTP_STATUS } from '@monorepo/shared/constants';
import { env } from '../config/env.js';

/**
 * 全局错误处理中间件
 * 
 * 这是 Express 错误处理的"最后一道防线"。
 * 所有路由和中间件中未被捕获的错误都会到达这里。
 */
export function errorHandler(
  err: Error,
  _req: Request,
  res: Response,
  _next: NextFunction,
): void {
  // 默认值
  let statusCode = HTTP_STATUS.INTERNAL_SERVER_ERROR;
  let code = 'INTERNAL_ERROR';
  let message = '服务器内部错误';
  let details: unknown = undefined;

  if (err instanceof AppError) {
    // 业务错误 — 使用错误类中定义的状态码和信息
    statusCode = err.statusCode;
    code = err.code;
    message = err.message;
    details = err.details;
  } else if (err.name === 'ZodError') {
    // Zod 验证错误 — 转换为统一格式
    statusCode = HTTP_STATUS.BAD_REQUEST;
    code = 'VALIDATION_ERROR';
    message = '请求数据验证失败';
    details = (err as any).issues;
  } else if (err.name === 'JsonWebTokenError') {
    statusCode = HTTP_STATUS.UNAUTHORIZED;
    code = 'INVALID_TOKEN';
    message = '无效的认证令牌';
  } else if (err.name === 'TokenExpiredError') {
    statusCode = HTTP_STATUS.UNAUTHORIZED;
    code = 'TOKEN_EXPIRED';
    message = '认证令牌已过期，请重新登录';
  }

  // 构造统一格式的响应
  const response: ApiResponse<never> = {
    success: false,
    error: { code, message, details },
  };

  // 生产环境下记录错误日志（但不暴露内部错误详情给客户端）
  if (env.NODE_ENV !== 'production' || statusCode >= 500) {
    console.error(`[Error] ${code}: ${err.message}`, err.stack);
  }

  // 开发环境下可以在响应中包含错误堆栈（方便调试）
  if (env.NODE_ENV === 'development' && statusCode >= 500) {
    (response.error as any).stack = err.stack;
  }

  res.status(statusCode).json(response);
}
```

创建 `packages/shared/src/schemas.ts`：

```typescript
import { z } from 'zod';
import {
  PASSWORD_MIN_LENGTH,
  USERNAME_MIN_LENGTH,
  USERNAME_MAX_LENGTH,
} from './constants.js';

/**
 * Zod Schema — 运行时验证 + 自动类型推导
 * 
 * 为什么在 shared 中定义 Schema 而不是在 api 中？
 * 1. 前端可以用来做表单验证（同一份 Schema，前后端一致）
 * 2. 从 Schema 自动推导出的类型与手动定义的 DTO 类型保持一致
 * 3. 修改验证规则时，前后端的类型会同步更新
 */

export const createUserSchema = z.object({
  username: z.string()
    .min(USERNAME_MIN_LENGTH, `用户名至少 ${USERNAME_MIN_LENGTH} 个字符`)
    .max(USERNAME_MAX_LENGTH, `用户名最多 ${USERNAME_MAX_LENGTH} 个字符`)
    .regex(/^[a-zA-Z0-9_-]+$/, '用户名只允许字母、数字、下划线和连字符'),

  email: z.string()
    .email('邮箱格式不正确')
    .max(255, '邮箱长度不能超过 255 个字符'),

  password: z.string()
    .min(PASSWORD_MIN_LENGTH, `密码至少 ${PASSWORD_MIN_LENGTH} 个字符`)
    .regex(/[a-z]/, '密码必须包含小写字母')
    .regex(/[A-Z]/, '密码必须包含大写字母')
    .regex(/[0-9]/, '密码必须包含数字'),

  role: z.enum(['admin', 'editor', 'viewer']).optional(),
});

export const updateUserSchema = createUserSchema
  .partial()  // 所有字段变为可选
  .refine(
    (data) => Object.keys(data).length > 0,
    { message: '至少需要提供一个要更新的字段' },
  );

export const loginSchema = z.object({
  email: z.string().email('邮箱格式不正确'),
  password: z.string().min(1, '请输入密码'),
});

export const paginationSchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  pageSize: z.coerce.number().int().min(1).max(100).default(20),
  search: z.string().optional(),
  sortBy: z.enum(['createdAt', 'username', 'email']).default('createdAt'),
  sortOrder: z.enum(['asc', 'desc']).default('desc'),
});

// 从 Schema 自动推导类型 — 不再需要手动写 DTO 接口！
export type CreateUserInput = z.infer<typeof createUserSchema>;
export type UpdateUserInput = z.infer<typeof updateUserSchema>;
export type LoginInput = z.infer<typeof loginSchema>;
export type PaginationInput = z.infer<typeof paginationSchema>;
```

在 API 中创建验证中间件 `apps/api/src/middleware/validate.ts`：

```typescript
import type { Request, Response, NextFunction } from 'express';
import type { ZodSchema } from 'zod';

/**
 * 通用的请求验证中间件工厂
 * 
 * 使用高阶函数模式：传入 Schema，返回中间件函数。
 * 这样每个路由可以灵活地选择验证哪些部分（body、query、params）。
 */
export function validate(schema: ZodSchema, source: 'body' | 'query' | 'params' = 'body') {
  return (req: Request, _res: Response, next: NextFunction) => {
    const result = schema.safeParse(req[source]);

    if (!result.success) {
      // 将 Zod 错误传递给全局错误处理中间件
      next(result.error);
      return;
    }

    // 用验证后的数据替换原始数据（Zod 会做类型转换，如 string -> number）
    req[source] = result.data;
    next();
  };
}
```

## 8.6 RESTful 路由设计

创建用户路由 `apps/api/src/routes/user.routes.ts`：

```typescript
import { Router } from 'express';
import { createUserSchema, updateUserSchema, paginationSchema } from '@monorepo/shared/schemas';
import { API_ROUTES } from '@monorepo/shared/constants';
import { validate } from '../middleware/validate.js';
import * as userController from '../controllers/user.controller.js';

const router = Router();

/**
 * GET /api/users — 获取用户列表
 * 验证 query 参数（分页、搜索、排序）
 */
router.get(
  '/',
  validate(paginationSchema, 'query'),
  userController.listUsers,
);

/**
 * GET /api/users/:id — 获取单个用户
 */
router.get(
  '/:id',
  userController.getUser,
);

/**
 * POST /api/users — 创建用户
 * 验证 body 数据
 */
router.post(
  '/',
  validate(createUserSchema),
  userController.createUser,
);

/**
 * PUT /api/users/:id — 更新用户
 * 验证 body 数据
 */
router.put(
  '/:id',
  validate(updateUserSchema),
  userController.updateUser,
);

/**
 * DELETE /api/users/:id — 删除用户
 */
router.delete(
  '/:id',
  userController.deleteUser,
);

export { router as userRoutes };
```

```prisma
  username  String   @unique
  email     String   @unique
  password  String   // 存储 bcrypt 哈希值，永远不返回给前端
  role      Role     @default(VIEWER)
  avatar    String?
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("users")
}

enum Role {
  ADMIN
  EDITOR
  VIEWER
}
```

**为什么把 Prisma 放在 `packages/database` 而不是 `apps/api`？**

1. **职责分离**：数据库层是独立的关注点，不应该和 HTTP 层耦合。未来如果要添加第二个后端服务（如 WebSocket 服务、定时任务），它们可以共享同一个数据库包
2. **Schema 作为单一数据源**：Prisma Schema 定义了数据的真实结构，生成的 Prisma Client 类型与 `@monorepo/shared` 中的 `User` 类型应该保持一致
3. **迁移管理集中化**：数据库迁移是全局操作，放在独立的包中更清晰

创建 Prisma Client 实例 `packages/database/src/index.ts`：

```typescript
import { PrismaClient } from '@prisma/client';

/**
 * 全局单例 Prisma Client
 * 
 * 为什么使用全局单例？
 * 在开发环境下，Hot Reload 会频繁重启模块，每次都创建新的 PrismaClient
 * 会导致连接池耗尽。通过 globalThis 缓存实例，避免这个问题。
 */
const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const prisma = globalForPrisma.prisma ?? new PrismaClient({
  log: process.env.NODE_ENV === 'development'
    ? ['query', 'error', 'warn']
    : ['error'],
});

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma;
}

// 重新导出 Prisma 类型，方便其他包使用
export { PrismaClient };
export type { User, Role } from '@prisma/client';
```

在 `apps/api` 中添加依赖：

```json
{
  "dependencies": {
    "@monorepo/database": "workspace:*"
  }
}
```

## 8.9 端到端类型安全的完整链路

让我们梳理一下类型是如何在整个 monorepo 中流动的：

```
packages/database (Prisma Schema)
    │
    │  Prisma Client 生成类型
    ▼
packages/shared (TypeScript 接口 + Zod Schema)
    │
    ├──▶ apps/api (使用 shared 的类型构造响应)
    │       │
    │       │  HTTP JSON 响应
    │       ▼
    │    apps/web (使用 shared 的类型解析响应)
    │
    └──▶ 类型一致性由 TypeScript 编译器保证
```

**实际效果：**

```typescript
// ====== packages/shared/src/types.ts ======
interface User {
  id: string;
  username: string;
  email: string;
  role: UserRole;
  createdAt: string;
  updatedAt: string;
}

// ====== apps/api 中 ======
// 后端返回的数据必须符合 User 类型
const user: User = { id: '1', username: 'admin', /* ... */ };
res.json(successResponse(user));  // ✅ 类型安全

// ====== apps/web 中 ======
// 前端解析响应时获得完整的类型推导
const response = await apiClient.get<ApiResponse<User>>('/api/users/1');
const username = response.data.data?.username;  // ✅ 类型是 string | undefined
```

如果某天你决定给 `User` 添加一个 `phone` 字段：

1. 在 `packages/shared/src/types.ts` 的 `User` 接口中添加 `phone?: string`
2. 在 Prisma Schema 中添加 `phone` 字段并运行 `prisma db push`
3. 后端 API 在构造 `User` 对象时如果不包含 `phone`，TypeScript 不会报错（因为是可选字段）
4. 前端组件中使用 `user.phone` 时，类型是 `string | undefined`，提醒你需要处理不存在的情况

**整个过程中没有任何硬编码的字符串，没有类型断言（`as`），所有的一致性都由编译器保证。**

## 本章小结

- Express 后端通过 `tsx watch` 实现开发热重载，启动速度远优于 ts-node
- 类型化的环境变量（Zod 验证）在启动时即暴露配置错误
- 请求验证使用 Zod Schema，前后端共享同一份验证规则
- Prisma 放在独立的 `packages/database` 中，实现数据层的职责分离
- 端到端类型安全的核心链路：Prisma Schema → shared 类型 → API 响应 → 前端解析
