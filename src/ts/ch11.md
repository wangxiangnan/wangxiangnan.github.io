# 第十一章：tsconfig.json 完全指南

`tsconfig.json` 是 TypeScript 项目的核心配置文件。理解它的常用选项，是工程化使用 TypeScript 的关键。

## 概述

常用字段在第三节逐个详解，这里先讲清楚一个最容易混淆的问题。

### 与构建工具的关系

很多人会把 TypeScript 编译器和 Vite、Webpack 混淆。其实它们的职责不同：

- TypeScript 编译器（`tsc`）：做类型检查，也可以做代码转译。
- Vite / Webpack：负责打包、资源处理、开发服务器。

Vite 开发时用 esbuild 做 TypeScript 转译，生产时也可能用 esbuild 或 rollup。这些工具通常不做完整的类型检查。所以一个常见的项目配置是：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build",
    "type-check": "tsc --noEmit"
  }
}
```

`tsc --noEmit` 只做类型检查，不输出文件。这样你可以在构建前单独跑类型检查。

## 一、tsconfig.json 是什么

`tsconfig.json` 是 TypeScript 编译器（`tsc`）的项目配置文件，告诉 tsc 两件事：**哪些文件要编译**，**怎么编译**。

它不是 `.npmrc` 那样的工具行为配置，而是类似 `babel.config.json`、`vite.config.ts` 的编译配置——控制源码如何被转换和输出。

如果项目目录下没有 `tsconfig.json`，`tsc` 会退回默认行为，基本不可用。

---

## 二、编译流水线

tsc 处理代码的顺序是一条五阶段单向流水线，`tsconfig.json` 里的字段分别控制不同环节：

```txt
tsc 启动
  ↓
阶段一：输入与范围
根据 files / include / exclude 确定要处理哪些文件
  ↓
阶段二：模块解析
逐文件解析：遇到 import → 模块解析，找到目标文件，继续解析
  ↓（所有文件解析完毕，形成完整的依赖图和类型信息）
阶段三：语言/类型检查
遍历所有文件的 AST，逐条跑类型规则
  ↓（检查通过，或报 error）
阶段四：代码生成与输出
擦除类型信息 → 按 target 降级语法 → 按 module 转换模块形式 → 写入 outDir
  ↓
阶段五：构建与集成
生成 .d.ts / .d.ts.map / .js.map → 更新 .tsbuildinfo → 处理项目引用
```

五阶段的依赖关系是单向的：

```txt
输入与范围  →  模块解析  →  语言/类型检查  →  代码生成与输出  →  构建与集成
     ↓            ↓              ↓                  ↓                ↓
  include     module           strict             target          composite
  exclude     moduleResolution noImplicitAny      module          references
  files       paths            strictNullChecks   outDir          incremental
  rootDir     baseUrl          skipLibCheck       declaration     tsBuildInfoFile
                              noUnchecked...     declarationMap
```

改一个阶段配置，可能影响下游行为。例如 `moduleResolution` 配错，阶段二就找不到模块；`strict` 没开，阶段三就漏检错误。

## 三、核心字段

按五阶段工作流组织，每个字段标注所属阶段。

### 3.1 阶段一：输入与范围

决定 tsc 处理哪些文件。

#### `include`

用 glob 模式指定哪些文件参与编译：

```json
{
  "include": ["src/**/*"]
}
```

#### `exclude`

从 `include` 的结果中排除：

```json
{
  "exclude": ["node_modules", "dist", "**/*.test.ts"]
}
```

如果没写 `include`，默认编译当前目录下所有 `.ts` 文件（`exclude` 中的除外）。

#### `files`

精确的文件列表，与 `include` 取并集：

```json
{
  "files": ["src/main.ts", "src/app.ts"],
  "include": ["src/utils/**/*"]
}
```

`files` 里列出的文件**不受 `exclude` 影响**，优先级最高。

最常见的用法是在 monorepo 根目录的编排入口中：

```json
{
  "files": [],
  "references": [
    { "path": "apps/web" },
    { "path": "packages/utils" }
  ]
}
```

`"files": []` 表示"这个 tsconfig 自己不编译任何文件"，只做编排。

#### `rootDir`

源码根目录。设了之后，`outDir` 里的目录结构会镜像 `rootDir` 的结构：

```json
{
  "rootDir": "./src",
  "outDir": "./dist"
}
```

`src/utils/date.ts` → `dist/utils/date.js`

#### `types` + `typeRoots`

控制哪些类型声明文件会被加载。`typeRoots` 指定查找目录，`types` 指定要加载的包：

```json
{
  "typeRoots": ["./node_modules/@types"],
  "types": ["node", "jest"]
}
```

不设 `types` 时，`typeRoots` 下所有包都会加载。设为空数组 `[]` 则不自动加载任何类型。

#### `allowJs` + `checkJs`

允许项目中包含 JavaScript 文件。`allowJs` 让 `.js` 文件能被编译，`checkJs` 进一步对它们做类型检查：

```json
{
  "allowJs": true,
  "checkJs": true
}
```

适合渐进式迁移：先把 `.js` 文件纳入项目，再逐步加类型注解或改成 `.ts`。

#### `include` vs import 图

tsc 用 `include` 确定文件集合，而不是像打包工具那样从单一入口沿 import 链构建依赖图。原因是：

1. 有些文件没有被 import（新写的模块、测试文件、`.d.ts` 声明），但需要编译
2. 类型检查需要全局视野，不能只检查被引用的文件
3. 全局类型声明（如 `env.d.ts`）靠"文件存在就生效"，不走 import

但 tsc 内部会建立模块缓存——同一文件只解析一次，不会因为被多个文件 import 就重复解析。

**glob 定边界，import 定关系。**

如果一个文件不在 `include` 范围内，但被已包含的文件 import 了，tsc 会解析它获取类型信息，但**不会输出它的 `.js`**——它是作为依赖被引入的，不是作为项目文件被编译的。

### 3.2 阶段二：模块解析

决定 `import` 路径怎么找到目标文件。

#### `moduleResolution`

控制 `import` 路径怎么解析：

| 值 | 说明 | 适用场景 |
| --- | ------ | --------- |
| `"bundler"` | 兼容打包工具的解析方式，支持省略扩展名 | Vite / webpack 项目 |
| `"NodeNext"` | Node.js 原生解析，要求写完整路径和扩展名 | 纯 Node.js 项目 |
| `"node"` | 旧版 Node.js 解析（不推荐新项目使用） | 遗留项目 |

需要和 `module` 搭配，配错了 import 会找不到模块。

#### `baseUrl` + `paths`

配置路径别名。`baseUrl` 设基准目录，`paths` 设映射关系：

```json
{
  "baseUrl": ".",
  "paths": {
    "@/*": ["src/*"],
    "@utils/*": ["src/utils/*"]
  }
}
```

代码中就可以写：

```ts
import { formatDate } from "@/utils/date";
// 实际解析到 src/utils/date.ts
```

注意：`paths` 只影响 TypeScript 的类型解析，运行时的路径别名需要打包工具（Vite / webpack）单独配置。

#### `esModuleInterop`

让 CommonJS 模块能正确使用 `import` 默认导出：

```json
{ "esModuleInterop": true }
```

比如 `import React from "react"`，`react` 是 CommonJS 模块，没有 `default` 导出，开了这个选项才能正常工作。基本所有项目都需要开。

#### `resolveJsonModule`

允许直接 import `.json` 文件并自动推导类型：

```json
{ "resolveJsonModule": true }
```

```ts
import pkg from "./package.json";
pkg.version; // 类型正确推导为 string
```

#### `resolvePackageJsonExports` + `resolvePackageJsonImports`

控制是否遵循 package.json 的 `exports` 和 `imports` 字段：

```json
{
  "resolvePackageJsonExports": true,
  "resolvePackageJsonImports": true
}
```

现代 Node.js 项目建议开启，确保模块解析与运行时行为一致。

#### `allowSyntheticDefaultImports`

允许从没有默认导出的模块进行默认导入：

```json
{ "allowSyntheticDefaultImports": true }
```

开启 `esModuleInterop` 时会自动开启此选项。单独使用时只影响类型检查，不改变输出。

### 3.3 阶段三：语言/类型检查

决定 tsc 如何检查代码是否符合类型规则。

#### `strict`

严格模式的总开关，一个 `true` 开启所有子选项：

```json
{ "strict": true }
```

它等价于同时开启：

| 子选项 | 作用 |
| -------- | ------ |
| `strictNullChecks` | `null` 和 `undefined` 不再自动兼容其他类型 |
| `noImplicitAny` | 禁止隐式 `any`，必须显式声明类型 |
| `strictFunctionTypes` | 函数参数类型严格检查 |
| `strictBindCallApply` | `bind`/`call`/`apply` 参数严格检查 |
| `alwaysStrict` | 每个文件自动加 `"use strict"` |
| `noImplicitThis` | 禁止 `this` 的隐式 `any` |
| `useUnknownInCatchVariables` | `catch` 中的变量类型为 `unknown` 而非 `any` |
| `strictPropertyInitialization` | 类属性必须在构造函数中初始化 |

新项目建议直接 `strict: true`，老项目迁移时可以逐个开启子选项。

#### `noUncheckedIndexedAccess`

通过索引访问对象属性或数组元素时，类型自动加上 `undefined`：

```ts
const arr: string[] = [];
arr[0]; // 开启后类型为 string | undefined
```

不在 `strict` 里，需要单独开启，但非常实用。

#### `skipLibCheck`

跳过 `.d.ts` 文件的类型检查。大型项目里开着能显著加快编译速度——你不需要替第三方库做类型检查：

```json
{ "skipLibCheck": true }
```

#### `noUnusedLocals` + `noUnusedParameters`

报告未使用的局部变量和参数：

```json
{
  "noUnusedLocals": true,
  "noUnusedParameters": true
}
```

帮助保持代码整洁，避免引入无用变量。参数以下划线开头（如 `_event`）可豁免检查。

#### `noImplicitReturns`

禁止函数有隐式返回路径：

```json
{ "noImplicitReturns": true }
```

```ts
function getStatus(code: number): string {
  if (code === 200) return "ok";
  // 错误：不是所有路径都有返回值
}
```

#### `noFallthroughCasesInSwitch`

报告 switch 语句中的 fallthrough：

```json
{ "noFallthroughCasesInSwitch": true }
```

```ts
switch (action) {
  case "start":
    console.log("starting");
  // 错误：缺少 break 或 fallthrough 注释
  case "stop":
    console.log("stopping");
}
```

如果确实需要 fallthrough，可以添加 `// falls through` 注释。

### 3.4 阶段四：代码生成与输出

决定 tsc 输出什么格式、什么版本的代码。

#### `target`

指定编译产物的 JS 版本。控制语法层面的转换：

```json
{ "target": "ES2022" }
```

设为 `"ES2022"` 保留箭头函数、class、async/await 等现代语法；设为 `"ES5"` 则全部降级。

#### `module`

指定模块系统，控制 `import`/`export` 的输出形式：

| 值 | 输出形式 | 适用场景 |
| --- | --------- | --------- |
| `"ESNext"` | `import`/`export` | 浏览器项目、打包工具 |
| `"CommonJS"` | `require`/`module.exports` | 传统 Node.js |
| `"NodeNext"` | 自动判断（根据 package.json 的 `type` 字段） | 现代 Node.js |

`module` 和 `target` 的区别：`target` 管语法降级（class → function），`module` 管模块转换（import → require）。

#### `lib`

指定编译器可用的内置类型声明环境，比如 `DOM`（浏览器全局 API）、`WebWorker`、各版本 ES 内置对象：

```json
{ "lib": ["ES2022", "DOM"] }
```

不设置时由 `target` 推导默认值，且默认**包含 DOM**。写纯 Node 项目时建议显式设置（如 `["ES2022"]`），避免 `document`、`window` 出现在类型提示里。

#### `outDir`

编译产物的输出目录：

```json
{ "outDir": "./dist" }
```

不设的话，编译产物会和源码放在一起。

#### `declaration`

是否生成 `.d.ts` 类型声明文件。如果你的包要给别的项目使用，必须开启：

```json
{ "declaration": true }
```

#### `declarationMap`

是否生成 `.d.ts.map` 源映射文件，方便其他项目在使用你的包时能跳转到源码：

```json
{ "declarationMap": true }
```

#### `noEmit`

不输出任何文件，只做类型检查：

```json
{ "noEmit": true }
```

适合与 Babel、esbuild、Vite 等工具配合——让它们负责编译输出，tsc 只负责类型检查。常见于 `package.json` 的 scripts：

```json
{
  "scripts": {
    "type-check": "tsc --noEmit"
  }
}
```

#### `removeComments`

移除所有注释（除了以 `/*!` 开头的规则注释）：

```json
{ "removeComments": true }
```

```text
你的项目是否有后续的打包/压缩步骤（如 Webpack, Vite, esbuild）？
  ├── 是 → 强烈建议保持 removeComments: false
  │        将移除注释、压缩代码的工作交给下游工具（如 Terser）
  │
  └── 否 → 如果对输出体积有严格要求，且无保留注释的需求
           → 可以考虑设为 true
```

#### `jsx`

控制 JSX 如何输出（React 项目必需）：

| 值 | 说明 | 适用场景 |
| --- | ------ | --------- |
| `"preserve"` | 保留 JSX 不转换 | 交给 Babel 等工具处理 |
| `"react"` | 转换为 `React.createElement` | React 17 以下 |
| `"react-jsx"` | 转换为 `_jsx()` 调用 | React 17+（推荐） |

```json
{ "jsx": "react-jsx" }
```

#### `experimentalDecorators` + `emitDecoratorMetadata`

启用实验性装饰器支持：

```json
{
  "experimentalDecorators": true,
  "emitDecoratorMetadata": true
}
```

`experimentalDecorators` 启用装饰器语法，`emitDecoratorMetadata` 发出类型元数据（配合 `reflect-metadata` 使用）。Angular、NestJS 等项目必需。

注意：这是旧版装饰器提案。TC39 已推出新版装饰器标准，TypeScript 5.0+ 支持新语法（无需此选项），但生态迁移需要时间。

### 3.5 阶段五：构建与集成

决定 tsc 如何与其他项目、工具协作，支持大型工程。

#### `composite`

启用项目引用模式。开启后：

- 自动强制 `declaration: true`（必须产出 `.d.ts`）
- 生成 `.tsbuildinfo` 文件，记录编译信息用于增量编译
- 要求 `rootDir` 和 `outDir` 必须设置

```json
{ "composite": true }
```

#### `references`

声明当前项目依赖的其他项目。tsc 会读取被引用项目的 `.d.ts`，而不是解析源码：

```json
{
  "references": [
    { "path": "../../packages/utils" }
  ]
}
```

必须配合 `tsc --build`（简写 `tsc -b`）使用，普通 `tsc` 会忽略这个字段。

#### `incremental`

启用增量编译，通过 `.tsbuildinfo` 记录上次编译信息，只重新编译改动的文件：

```json
{ "incremental": true }
```

`composite` 会自动开启 `incremental`。

#### `tsBuildInfoFile`

指定 `.tsbuildinfo` 文件的存放位置：

```json
{ "tsBuildInfoFile": "./.tsbuildinfo" }
```

#### `extends`

继承另一个 tsconfig 的配置，子配置覆盖父配置的同名字段：

```json
// packages/utils/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["src"]
}
```

`compilerOptions` 是浅合并——子配置中出现的字段覆盖父配置的同名字段，未出现的保留。

#### `isolatedModules`

确保每个文件可以单独编译：

```json
{ "isolatedModules": true }
```

使用 Babel、esbuild、Vite 等工具时必须开启——它们不做完整的类型检查，只逐文件转译。开启后，TypeScript 会禁止某些需要跨文件分析才能正确编译的写法（如类型导出必须用 `export type`）。

#### `forceConsistentCasingInFileNames`

强制文件名大小写一致：

```json
{ "forceConsistentCasingInFileNames": true }
```

避免 Windows（不区分大小写）和 Linux（区分大小写）之间的路径问题。`strict` 模式下默认开启。

## 四、项目引用（Project References）

### 4.0 定位：references 与文件范围、模块解析的关系

`references` 不属于文件范围，也不完全属于模块解析——它是一个更高层级的机制，横跨了多个层面。

**与文件范围的区别：** `include` / `files` 定义的是当前项目自己的源码，tsc 负责编译这些文件并输出 `.js` 和 `.d.ts`。`references` 定义的是当前项目依赖的**其他项目**，tsc 不编译它们，而是去读它们已编译好的 `.d.ts`。一个是"我负责编译什么"，一个是"我消费谁的编译产物"，两者不能归为一类。

**与模块解析的关系：** `references` 确实干预了模块解析过程。当项目 A import 了项目 B，tsc 本来要走完整的 `moduleResolution` 流程逐级查找源码；有了 `references`，tsc 直接跳过查找，去 B 的 `outDir` 里读 `.d.ts`。但 `references` 还做了模块解析管不到的事——编排构建顺序（`tsc -b` 先编译被引用项目，再编译引用者）、增量编译判断（通过 `.tsbuildinfo` 判断是否需要重新编译）、强制项目边界（`composite` 要求 `rootDir` 和 `outDir` 必须设置）。这些是编译策略和架构约束，超越了模块解析的范畴。

用比喻来理解：`moduleResolution` 是"怎么找路"，`include` 是"圈定自己的地盘"，`references` 是"这条路指向一个已经建好的建筑，不用再进去施工了，顺便还把施工队（tsc）的干活顺序也安排好了"。

### 4.1 解决什么问题

在 monorepo 中，`apps/web` 依赖 `packages/utils`。如果没有 references，每次编译 `web` 时，tsc 会沿着 import 链去解析 `utils` 的所有源码。`utils` 有 100 个文件，`web` 每次改一行代码，这 100 个文件都要重新解析。

references 的核心思路：**不要每次都解析源码，而是用已编译好的 `.d.ts` 类型声明文件代替。**

### 4.2 配置方式

**第一步，被引用的项目开启 `composite`：**

```json
// packages/utils/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src"]
}
```

`composite` 开启后：

- 自动强制 `declaration: true`（必须产出 `.d.ts`）
- 生成 `.tsbuildinfo` 文件，记录编译信息用于增量编译
- 要求 `rootDir` 和 `outDir` 必须设置

**第二步，引用方声明 `references`：**

```json
// apps/web/tsconfig.json
{
  "compilerOptions": {
    "outDir": "./dist"
  },
  "include": ["src"],
  "references": [
    { "path": "../../packages/utils" }
  ]
}
```

`path` 指向被引用项目的 tsconfig 所在目录。tsc 会读取那个 tsconfig，找到它的 `outDir`，然后用里面的 `.d.ts` 获取类型信息。

### 4.3 tsc --build 模式

配好 references 后，必须用 `tsc --build`（简写 `tsc -b`）来编译：

```bash
tsc -b apps/web
```

`--build` 模式的处理流程：

1. 读取 `web` 的 tsconfig，发现 `references` 里有 `utils`
2. 检查 `utils` 的源码是否比上次编译更新（通过 `.tsbuildinfo` 判断）
3. 如果更新了，先编译 `utils`，产出新的 `.d.ts`
4. 再编译 `web`，此时 `utils` 的类型信息从 `dist/*.d.ts` 读取，不重新解析源码

普通 `tsc` 会**完全忽略** `references` 字段，退回到沿 import 链解析源码的老行为。

| 特性 | `tsc` | `tsc -b` |
| ------ | ------- | ---------- |
| 识别 `references` | 忽略 | 按依赖顺序编译 |
| 跨包类型来源 | 解析源码 | 读 `.d.ts` |
| 增量编译 | 不支持 | 通过 `.tsbuildinfo` 支持 |
| `composite` 项目 | 不生效 | 生效 |

### 4.4 依赖方向

references 只能单向引用，形成有向无环图（DAG）：

```
shared-types  ←  utils  ←  web
（无依赖）     （依赖 shared-types）  （依赖 utils 和 shared-types）
```

A 引用了 B，B 就不能反过来引用 A，否则 tsc 报循环引用错误。

## 七、 TS 的 `module` 与 `moduleResolution`配对规则

### 一句话

**TS 检查代码的方式，必须和 Node 运行代码的方式完全一致，否则就是"检查全绿，一跑就崩"。**

### 三步理解

**第 1 步：Node 怎么找文件？**

Node 加载一个文件前，先问自己："这是 ESM 还是 CJS？"——看 `package.json` 的 `type` 字段。然后按答案选规则：

- CJS 文件 → 宽松规则：`require("./utils")` 不写扩展名也行
- ESM 文件 → 严格规则：`import "./utils"` 必须写成 `./utils.js`

**第 2 步：TS 怎么检查你写得对不对？**

TS 检查 import 时，也得先知道"这个文件是 ESM 还是 CJS"，才能套对规则。**这个判断就是 `module` 选项干的活。**

**第 3 步：两种 `module` 的区别就在"怎么判断"**

- `module: "nodenext"` → TS 和 Node 用**同一套办法**判断（都看 package.json）→ 两边永远一致 ✅
- `module: "esnext"` → TS 不看 package.json，直接假设**所有文件都是 ESM** → 但 Node 不听 TS 的 ❌

### 断掉之后会发生什么

假设 CJS 包里有个文件：

```text
TS 的判断：这是 ESM → 检查放行，编译出 import 语句
Node 的判断：package.json 没写 type → 这是 CJS → 看到 import 直接 SyntaxError
```

编译通过，运行崩溃，而且崩溃点在解析语法那一瞬间。

### 结论

`moduleResolution: "nodenext"` 的规则按"文件是 ESM 还是 CJS"分两套，所以它必须配一个"判断文件类型的方式和 Node 一致"的 `module`——只有 `nodenext` 满足。`esnext` 的判断方式（一律当 ESM）和 Node 的判断方式（看 package.json）不一样，配在一起就自相矛盾。

所以这个组合直接报错 TS5110，编译期就拦下：

```jsonc
// ❌ 报错 TS5110
{ "moduleResolution": "nodenext", "module": "esnext" }

// ✅ 正确
{ "moduleResolution": "nodenext", "module": "nodenext" }
```

### 推荐搭配

| 场景 | module | moduleResolution |
| --- | --- | --- |
| 产物直接跑在 Node 上 | `nodenext` | `nodenext` |
| 用 Vite/webpack/esbuild 打包 | `esnext` | `bundler` |
| 旧行为（不推荐新项目） | `esnext` | `node10` |

### 核心心智模型

.cts 的含义是**“这个文件按 CJS 格式编译”**，不是“你必须手写 CJS 代码”。官方推荐的双格式写法是：源码一律用 ESM 语法，后缀决定转译方向——.cts emit 成 exports.xxx = ...，.mts emit 成纯ESM。这样一份 CJS/ESM 语法通吃，也避开了 exports 重赋值那类 CJS 坑。
