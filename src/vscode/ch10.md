# 第10章：高级调试技巧

> "The most effective debugging tool is still careful thought, coupled with judiciously placed print statements." —— Brian Kernighan (1979)

Kernighan 说这话时是 1979 年。工具进化了四十多年，但"仔细思考"依然是调试的核心。

第 9 章解决的是"一个进程、一种语言、停在某一行"。这一章跨越四条边界：**同时调多个目标**（前后端）、**跨语言**（Node/Python）、**跨编译层**（TypeScript/Source Map）、**跨容器边界**（Docker）。每跨一条，你会多一类"配置正确却连不上"的坑——本章的重点就是把它们讲清楚。

## 10.1 复合调试：一次启动整个系统

全栈开发时，前后端各开一个调试会话太原始。`compounds` 可以把多个配置绑定成一个入口：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Server",
            "type": "node",
            "request": "launch",
            "program": "${workspaceFolder}/server/src/index.ts",
            "runtimeArgs": ["-r", "ts-node/register"],
            "env": { "PORT": "4000" },
            "console": "integratedTerminal",
            "skipFiles": ["<node_internals>/**", "**/node_modules/**"]
        },
        {
            "name": "Client",
            "type": "chrome",
            "request": "launch",
            "url": "http://localhost:5173",
            "webRoot": "${workspaceFolder}/client/src"
        }
    ],
    "compounds": [
        {
            "name": "Full Stack",
            "configurations": ["Server", "Client"],
            "stopAll": true
        }
    ]
}
```

关键字段：

- `configurations`：要一起启动的配置名数组，**顺序即启动顺序**；
- `stopAll`：`true` 时停止任意一个会话就停止全部，避免留下孤儿进程；
- `presentation.group`：把相关配置在下拉菜单里归组，配置多了以后很好用。

一次典型回合：`F5` 启动 Full Stack → 在 React 事件处理和 Express 路由各设一个断点 → 浏览器操作触发前端断点 → 放行后请求发到后端，触发后端断点 → 在调试控制台里核对 `req.body` 与返回值。

> ⚠️ 两个容易误会的地方：
>
> 1. compound 只是**并行管理会话**，不会让前端请求"自动进入"后端断点——你需要两个会话都命中。
> 2. 前端 dev server 往往比后端慢。如果 Chrome 打开时页面还是白的，用 `serverReadyAction` 让后端在打印出就绪地址后再拉起前端会话：
>
> ```json
> "serverReadyAction": {
>     "pattern": "Server ready on (https?://\\S+)",
>     "action": "startDebugging",
>     "name": "Client"
> }
> ```
>
> 注意此时应把 `Client` 从 `compounds.configurations` 里移除，否则会被启动两次。

## 10.2 浏览器调试：launch 与 attach

VSCode 内置的 js-debug 已经覆盖 Chrome 和 Edge，不再需要早年那个 Debugger for Chrome 扩展。

### 启动一个新的浏览器实例

```json
{
    "name": "Debug Client",
    "type": "chrome",
    "request": "launch",
    "url": "http://localhost:5173",
    "webRoot": "${workspaceFolder}/client/src",
    "sourceMaps": true,
    "sourceMapPathOverrides": {
        "webpack:///src/*": "${webRoot}/*",
        "webpack:///*": "*"
    },
    "userDataDir": "${workspaceFolder}/.vscode/chrome-profile"
}
```

- `webRoot`：源码根目录，Source Map 映射的基准。写错就会断点灰圈。
- `sourceMapPathOverrides`：打包工具在 map 里写的虚拟路径与真实路径不一致时，用它改写。
- `userDataDir`：独立的浏览器配置目录，不干扰你日常登录的浏览器。**副作用是没有登录态**，需要登录态的场景请用 attach。
- 调试 Edge 把 `type` 换成 `msedge` 即可。

不要在 `runtimeArgs` 里加 `--disable-web-security` 来解决跨域——那是把浏览器的安全模型关掉来掩盖问题。跨域请用 dev server 代理。

### attach 到已经打开的浏览器

```json
{
    "name": "Attach to Chrome",
    "type": "chrome",
    "request": "attach",
    "port": 9222,
    "webRoot": "${workspaceFolder}/client/src"
}
```

浏览器必须以远程调试模式启动。**Chrome 136 起，`--remote-debugging-port` 必须配合非默认的 `--user-data-dir`**，否则端口不会生效：

```bash
# macOS
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --remote-debugging-port=9222 \
  --user-data-dir=/tmp/chrome-debug

# Windows (PowerShell)
& "C:\Program Files\Google\Chrome\Application\chrome.exe" `
  --remote-debugging-port=9222 `
  --user-data-dir="$env:TEMP\chrome-debug"
```

看到 `DevTools listening on ws://127.0.0.1:9222/...` 才算成功。attach 模式保留你已登录的会话，适合调试登录后的页面。

## 10.3 Node.js：attach、远程与热重载

### Attach 到远程或容器中的进程

服务已经在跑（服务器、容器、另一个终端），只想连上去：

```json
{
    "name": "Attach to Node",
    "type": "node",
    "request": "attach",
    "address": "localhost",
    "port": 9229,
    "localRoot": "${workspaceFolder}",
    "remoteRoot": "/app",
    "restart": true,
    "skipFiles": ["<node_internals>/**"]
}
```

前提是目标进程以调试模式启动：

```bash
node --inspect=0.0.0.0:9229 dist/index.js
# 想在第一行就停住，用 --inspect-brk
```

三个要点：`0.0.0.0` 才允许跨容器/跨机连接；`localRoot`/`remoteRoot` 负责把远端路径映射回本地源码；`restart: true` 让进程重启后自动重连（nodemon、容器重启都靠它）。

如果进程就在本机，更省事的办法是命令面板执行 **Debug: Attach to Node Process**，直接从进程列表里选，不需要写端口。

### nodemon 热重载调试

```json
{
    "name": "Debug with Nodemon",
    "type": "node",
    "request": "launch",
    "runtimeExecutable": "nodemon",
    "runtimeArgs": ["--exec", "ts-node", "src/index.ts"],
    "restart": true,
    "console": "integratedTerminal",
    "skipFiles": ["<node_internals>/**"]
}
```

`restart: true` 是灵魂：nodemon 杀掉旧进程、拉起新进程后，调试器会自动重新连接，你可以一直保留断点。不需要手动传 `--inspect`——VSCode 会替你注入。

## 10.4 Python：解释器、框架与模板断点

```json
{
    "name": "Python: Current File",
    "type": "python",
    "request": "launch",
    "program": "${file}",
    "console": "integratedTerminal",
    "justMyCode": true
}
```

`justMyCode: true` 只在自己的代码里停；排查第三方库时改成 `false`，但要做好在库代码里迷路的准备。

### 解释器别写死路径

原稿常见的坑是写 `"python": "${workspaceFolder}/venv/bin/python"`——Windows 上虚拟环境在 `Scripts\\python.exe`，配置直接失效。正确做法是 `Ctrl+Shift+P` → **Python: Select Interpreter** 选择环境，让扩展自己记录；确实要写进配置时用：

```json
"python": "${command:python.interpreterPath}"
```

### Django 与 Flask

```json
{
    "name": "Django: runserver",
    "type": "python",
    "request": "launch",
    "program": "${workspaceFolder}/manage.py",
    "args": ["runserver", "--noreload"],
    "django": true,
    "justMyCode": true
}
```

```json
{
    "name": "Flask: run",
    "type": "python",
    "request": "launch",
    "module": "flask",
    "args": ["run", "--no-debugger", "--no-reload"],
    "env": { "FLASK_APP": "src/app.py", "FLASK_DEBUG": "1" },
    "jinja": true,
    "justMyCode": true
}
```

`--noreload` / `--no-reload` 必须加：自动重载会 fork 出新进程，调试器跟丢。`"django": true` 和 `"jinja": true` 分别启用 **Django 模板断点**和 **Jinja2 模板断点**——断点可以直接打在 `.html` 里。注意 `FLASK_ENV` 在 Flask 2.3+ 已移除，用 `FLASK_DEBUG=1`。

## 10.5 数据断点与异常断点

### 数据断点：谁改了我的值

在变量面板右键某个属性 → **Break on Value Change**。它监视的不是某一行，而是**某个内存位置**，因此能捕获任何一处的修改——排查"这个字段什么时候被改脏了"的终极武器。部分调试器还提供 Break on Value Read/Access。

支持情况取决于调试适配器，而且差异很大：

| 调试器 | 数据断点 |
| -------- | ---------- |
| js-debug（Node.js/浏览器） | 支持对象属性 |
| C++（GDB/LLDB） | 支持内存地址 |
| Python（debugpy） | 不支持，右键菜单里不会出现该项 |

菜单里找不到，就是当前调试器不支持，别怀疑自己点错了。

### 异常断点：别让异常被悄悄吞掉

"这个接口返回 500，但日志里什么都没有"——通常是异常在某层 `try/catch` 里被吞了。在断点面板底部打开**异常断点**视图：

- **Uncaught Exceptions**：只在没人接住的异常上停，日常默认；
- **All / Raised Exceptions**：连被捕获的也停，用来找"吞异常"的元凶；
- 部分调试器支持按异常类型过滤（如 Python 的 User Uncaught Exceptions、Node 的 Caught/Uncaught 分类）。

用法就三步：打开 All Exceptions → 复现 → 在调用堆栈里找到真正的抛出点 → 查完关掉。一直开着会让正常依赖的异常路径频繁暂停。

## 10.6 调试控制台与求值技巧

调试控制台在第 9 章已经能用了，这里补充三个提高信息密度的动作。

**先选帧，再求值。** 在调用堆栈里点中某一帧后，控制台的表达式按**那一帧的作用域**求值。排查"参数在哪一层被改坏"时，比起反复加监视，直接在每一帧里敲 `JSON.stringify(args)` 更快。

**用运行时 API 整理输出。** 这些是 Node/浏览器 console 的能力，不是 VSCode 特供：

```javascript
console.table(users)                  // 表格化数组
console.dir(config, { depth: null })  // 完整展开
console.time('db'); /* ... */ console.timeEnd('db')
console.assert(total > 0, 'total 异常', total)
```

**接受副作用警告。** 控制台和监视里的表达式会被真实执行。写 `cache.clear()` 或 `counter++`，你是在改运行中的程序，不只是"看一眼"。

## 10.7 Source Maps：读懂编译后的世界

Source Map 记录"编译后第 42 行 ↔ 源码第 35 行"的映射。没有它，调试 TypeScript、JSX、Vue SFC 就是对着编译产物猜。

```
src/index.ts  ──tsc──▶  dist/index.js + dist/index.js.map
```

TypeScript 只需两件事：`tsconfig.json` 开 `"sourceMap": true`，调试配置里给出 `outFiles`：

```json
{
    "sourceMaps": true,
    "outFiles": ["${workspaceFolder}/dist/**/*.js"]
}
```

打包工具（Webpack/Vite）的映射路径通常是虚拟的，需要改写：

```json
"sourceMapPathOverrides": {
    "webpack:///./src/*": "${webRoot}/*",
    "webpack:///src/*": "${webRoot}/*",
    "webpack:///*": "*"
}
```

### 断点为什么是灰的

灰圈 = 调试器没找到对应的可执行代码，按顺序查：

| 排查项 | 检查内容 |
| -------- | ---------- |
| 产物是否带 map | `dist/*.js` 旁有 `.map` 吗？`tsconfig` 开 `sourceMap` 了吗？ |
| `outFiles` 是否命中 | glob 写的是本地路径，且真的匹配到产物 |
| 路径映射 | 远程/容器用 `localRoot`/`remoteRoot`，前端用 `sourceMapPathOverrides` |
| 模块是否已加载 | 懒加载模块尚未执行时断点无法验证，先触发它 |
| 断点行是否可执行 | 空行、注释、类型声明不会生成代码 |

### 只有压缩代码怎么办

先找 `app.min.js.map`。有 map，配好 `sourceMapPathOverrides` 就能在原源码上断点；没有 map，用浏览器 DevTools 的 **Pretty Print** 格式化后，在格式化视图里下断点——注意这只改变显示，变量名依然是压缩过的。

## 10.8 Docker 容器调试

这是 attach 模式最典型的战场，也是最容易"配置看着全对、就是连不上"的地方。先记住一张图：调试器在**宿主机**，进程在**容器**，两者之间需要两条通道：

```
宿主机 VSCode ──应用端口(3000)──▶ 容器
     └────────调试端口(9229/5678)──▶ 容器内调试器
```

三条铁律：

1. 容器内必须监听 **`0.0.0.0`**，只绑 `127.0.0.1` 时宿主机永远连不上；
2. 调试端口必须**发布到宿主机**（`ports`），仅 `expose` 不够；
3. 两边路径要建立映射，否则断点全是灰圈。

### Node.js：用 compose override 打开调试

生产/普通开发镜像不该默认暴露调试器。推荐把调试配置放进独立的 override 文件：

```yaml
# docker-compose.yml
services:
  api:
    build: .
    ports:
      - "3000:3000"
```

```yaml
# docker-compose.debug.yml
services:
  api:
    command: node --inspect=0.0.0.0:9229 dist/index.js
    ports:
      - "127.0.0.1:9229:9229"   # 只绑宿主机回环，避免暴露到局域网
```

```bash
docker compose -f docker-compose.yml -f docker-compose.debug.yml up --build
```

对应的 attach 配置：

```json
{
    "name": "Attach: API in Docker",
    "type": "node",
    "request": "attach",
    "address": "localhost",
    "port": 9229,
    "localRoot": "${workspaceFolder}",
    "remoteRoot": "/app",
    "restart": true,
    "sourceMaps": true,
    "skipFiles": ["<node_internals>/**", "**/node_modules/**"]
}
```

`localRoot` 与 `remoteRoot` 必须对应同一个项目根：容器里代码在 `/app`，本地在项目根，就按上面这样写；如果你只映射了子目录，改到子目录。跑编译产物的项目，再加 `"outFiles": ["${workspaceFolder}/dist/**/*.js"]`。

还有一个更简单的前提检查：`docker exec -it <container> node --version` 能跑通，说明容器活着；`curl http://localhost:9229/json/list` 能返回 JSON，说明调试端口通了——这两步能把"代码问题"和"网络问题"分开。

### Python：debugpy 监听 + pathMappings

在调试镜像里安装 debugpy，并用它启动：

```yaml
# docker-compose.debug.yml
services:
  api:
    command: python -m debugpy --listen 0.0.0.0:5678 --wait-for-client app.py
    ports:
      - "127.0.0.1:5678:5678"
```

```json
{
    "name": "Attach: Python in Docker",
    "type": "python",
    "request": "attach",
    "connect": { "host": "localhost", "port": 5678 },
    "pathMappings": [
        { "localRoot": "${workspaceFolder}", "remoteRoot": "/app" }
    ],
    "justMyCode": true
}
```

`--wait-for-client` 让进程停在入口等你连上，适合排查启动即崩的问题；不需要时去掉它，让服务先跑起来。容器内没装 debugpy 的话，`python -m debugpy` 会直接报 no module——把它放进开发镜像，别放进生产镜像。

### 高频坑对照

| 症状 | 原因 | 处理 |
| ------ | ------ | ------ |
| attach 报 ECONNREFUSED | 只监听了 `127.0.0.1`，或端口没发布 | 改 `--inspect=0.0.0.0`、补 `ports` |
| 连上了但断点灰圈 | 容器路径与本地路径不一致 | 检查 `localRoot/remoteRoot`、`pathMappings` |
| 改了代码行为没变 | 跑的是构建进镜像的旧代码 | `docker compose up --build`，或确认 volume 挂载 |
| 容器重启后调试断掉 | 进程换了，会话没重连 | attach 配置加 `"restart": true` |
| Node 一启动就退出 | 用了 `--inspect-brk` 但没有会话连上 | 改用 `--inspect`，或先启动会话再触发 |
| 调试端口外网可访问 | 发布了 `9229:9229` | 改为 `127.0.0.1:9229:9229`；调试端口无认证 |

### 更省事的替代方案

如果你**长期**在容器里开发，别从宿主机 attach——用 **Dev Containers** 直接在容器内跑 VSCode Server，调试器与进程同处一个文件系统，`localRoot/remoteRoot`、端口映射统统不需要。这正是第 12 章的主题，配置见 12.5 的调试小节。

📋 **本章小结**

- `compounds` 一键管理多个调试会话，`stopAll` 决定是否联动停止；它不会自动打通前后端断点
- 浏览器调试分 launch 与 attach；Chrome 136+ 的 attach 必须指定非默认 `--user-data-dir`
- Node 远程/容器调试靠 `address` + `localRoot/remoteRoot` + `restart`；nodemon 场景同样用 `restart`
- Python 解释器别写死路径，用 Select Interpreter 或 `${command:python.interpreterPath}`；Django/Flask 记得关掉自动重载
- 数据断点按"内存位置"生效，支持情况因调试器而异；异常断点用于抓被吞掉的异常
- 灰圈断点的排查顺序：map 是否存在 → `outFiles` → 路径映射 → 模块是否加载
- Docker 调试三要素：监听 `0.0.0.0`、发布调试端口（最好只绑 127.0.0.1）、路径映射
- 长期容器开发用 Dev Containers，比宿主机 attach 少一整类配置问题
