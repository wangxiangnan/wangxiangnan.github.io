# 第9章 视图与CTE

## 9.1 视图：给查询起个好名字

视图就像你给一段复杂的SQL起了个"函数名"。你在生活中肯定用过类似的东西——手机通讯录里的"老婆"其实是一个手机号的别名，你不需要每次打电话都输入那11位数字。视图的作用一模一样：把一个可能很长很复杂的SELECT语句保存成一个名字，以后只需要查这个名字就行了。

视图（View）本质上是一条**保存了的SELECT查询定义**。它不存储数据本身（这叫"虚拟表"），只存储查询语句。每次你查询视图时，MySQL都会在后台执行底层的SELECT语句，然后返回结果。这意味着视图的数据永远是实时的——底层表的数据变了，视图查出来的结果也会自动变化。

```sql
-- 创建一个视图：技术部员工信息
CREATE VIEW tech_team AS
SELECT emp_id, emp_name, salary
FROM employees
WHERE department = '技术部';

-- 之后可以像查表一样查视图，代码简洁多了
SELECT * FROM tech_team;
SELECT emp_name, salary FROM tech_team WHERE salary > 13000;
```

```sql
-- 更复杂的视图：部门统计概览
-- 把聚合逻辑封装进视图，使用时就像查一张已经算好的统计表
CREATE VIEW dept_summary AS
SELECT
    department,
    COUNT(*) AS emp_count,
    AVG(salary) AS avg_salary,
    MAX(salary) AS max_salary,
    MIN(salary) AS min_salary,
    SUM(salary) AS total_salary
FROM employees
GROUP BY department;

-- 使用视图，一行搞定
SELECT * FROM dept_summary ORDER BY avg_salary DESC;
```

## 9.2 可更新视图 vs 只读视图

有些视图不仅能查（SELECT），还能改（UPDATE、INSERT、DELETE）。但这种"可更新视图"有严格的限制条件——只有当视图可以明确映射到底层表的单行记录时，MySQL才允许你通过视图修改数据。

具体来说，包含聚合函数（SUM、COUNT、AVG等）、DISTINCT、GROUP BY、HAVING、UNION、窗口函数、子查询在SELECT列表中的视图都不可更新。简单地说，只要视图的逻辑涉及到"把多行合并成一行"的操作，它就不可能被更新——因为MySQL不知道该把修改应用到哪一行底层数据上：

```sql
-- 可更新视图：简单的单表过滤，每一行都能明确对应底层表的一行
CREATE VIEW high_salary AS
SELECT emp_id, emp_name, department, salary
FROM employees
WHERE salary > 10000;

-- 通过视图更新数据（实际修改的是底层employees表）
UPDATE high_salary SET salary = salary + 1000 WHERE emp_name = '孙八';

-- 只读视图（包含聚合和GROUP BY，不可能更新）
-- UPDATE dept_summary SET avg_salary = 20000;  -- 会报错！
```

> [!WARNING] 注意
> 虽然可更新视图在技术上是可行的，但在实际生产项目中很少使用。通过视图更新数据容易引发难以排查的bug——比如你更新了一行数据，结果它不满足视图的WHERE条件了，这行数据就会从视图中"消失"，看起来就像数据丢了一样。建议视图只用来读数据，修改数据直接操作底层表。

## 9.3 视图的优缺点

视图的优点主要体现在四个方面。第一是**简化复杂查询**——把涉及多个表JOIN和子查询的复杂SQL封装成一个视图，使用者只需要简单的 `SELECT * FROM my_view` 就能拿到数据。第二是**安全性控制**——你可以创建一个只暴露非敏感列的视图给普通用户，而隐藏工资、身份证号等敏感信息。第三是**逻辑抽象**——当底层表结构发生变化（比如拆分表、重命名列）时，只需要修改视图定义，使用视图的应用程序代码完全不需要改动。第四是**统一数据接口**——不同的应用或报表可以共享同一个视图定义，保证大家看到的数据口径一致。

但视图也有明显的缺点。**性能问题**是最突出的——视图本身不缓存数据（不像物化视图），每次查询都要重新执行底层SQL。如果你嵌套了多层视图（视图A引用视图B，视图B引用视图C），最终展开的SQL可能极其复杂，优化器也很难处理。**调试困难**也是一个痛点——当嵌套视图出了问题，你需要一层一层地剥开视图定义来定位原因，就像剥洋葱一样，每剥一层都可能让你流泪。

```sql
-- 安全视图的实际应用：不同角色看到不同级别的信息
-- 给普通员工看的视图（隐藏工资和管理关系）
CREATE VIEW employee_public AS
SELECT emp_id, emp_name, department FROM employees;

-- 给HR系统用的视图（包含薪资和管理关系）
CREATE VIEW employee_hr AS
SELECT emp_id, emp_name, department, salary, manager_id FROM employees;

-- 给CEO的仪表盘视图（只看汇总数据）
CREATE VIEW employee_dashboard AS
SELECT department, COUNT(*) AS headcount, AVG(salary) AS avg_cost
FROM employees GROUP BY department;
```

## 9.4 ALTER VIEW / DROP VIEW

视图创建后并不是固定不变的，你可以修改它的定义或者直接删除。ALTER VIEW和CREATE OR REPLACE VIEW都可以修改已有的视图，区别在于如果视图不存在，ALTER VIEW会报错而CREATE OR REPLACE VIEW会创建它：

```sql
-- 修改视图定义（增加一列manager_id）
ALTER VIEW tech_team AS
SELECT emp_id, emp_name, salary, manager_id
FROM employees WHERE department = '技术部';

-- CREATE OR REPLACE：如果存在则替换，不存在则创建
CREATE OR REPLACE VIEW tech_team AS
SELECT emp_id, emp_name, salary, manager_id
FROM employees WHERE department = '技术部' ORDER BY salary DESC;

-- 删除视图（IF EXISTS避免视图不存在时报错）
DROP VIEW IF EXISTS tech_team;

-- 查看视图的底层SQL定义
SHOW CREATE VIEW dept_summary;
```

## 9.5 WITH (CTE, Common Table Expression)

CTE（Common Table Expression，公用表表达式）是MySQL 8.0引入的一个重要新特性。如果说视图是"永久保存的查询别名"（存储在数据库里，任何人都可以用），那CTE就是"一次性的临时查询别名"——它只在当前这条SQL语句中有效，语句执行完就没了。

CTE就像是你写作文之前的提纲或草稿——先把大问题拆成几个小问题分别求解，最后组合成完整答案。这种"先定义中间结果，再组合使用"的模式让复杂查询变得清晰可读。

CTE的核心语法非常简洁：`WITH cte_name AS (子查询) SELECT ... FROM cte_name`。你可以在WITH后面定义多个CTE，用逗号分隔，后面的CTE可以引用前面定义的CTE：

```sql
-- 用CTE重写之前的"找高于部门平均工资的员工"
WITH dept_stats AS (
    SELECT department, AVG(salary) AS avg_salary, COUNT(*) AS emp_count
    FROM employees
    GROUP BY department
)
SELECT emp_name, e.department, salary, ds.avg_salary
FROM employees e
JOIN dept_stats ds ON e.department = ds.department
WHERE salary > ds.avg_salary;
```

```sql
-- 多个CTE串联使用（像流水线一样，每一步建立在前一步之上）
WITH
dept_avg AS (
    -- 第一步：计算每个部门的平均工资
    SELECT department, AVG(salary) AS avg_sal
    FROM employees GROUP BY department
),
above_avg AS (
    -- 第二步：找出高于部门平均工资的员工
    SELECT e.emp_name, e.department, e.salary, da.avg_sal
    FROM employees e
    JOIN dept_avg da ON e.department = da.department
    WHERE e.salary > da.avg_sal
)
-- 第三步：统计每个部门有多少人高于平均
SELECT department, COUNT(*) AS above_avg_count
FROM above_avg GROUP BY department;
```

> [!TIP] 提示
> CTE比子查询可读性好得多，因为CTE从上到下线性阅读，每一步都有名字和注释，不需要像嵌套子查询那样"从里向外"理解。经验法则：当你的SQL嵌套超过两层子查询时，就应该考虑用CTE来重构了。

## 9.6 递归CTE（Recursive CTE）：处理层次数据的利器

这是CTE最强大、最令人兴奋的特性——可以引用自身！递归CTE非常适合处理**层次数据**（也叫树形数据），比如公司的组织架构、商品的分类树、论坛的评论回复链、文件系统的目录结构等。

递归CTE的结构由三部分组成：**锚定部分**（Anchor，递归的起点）、**递归部分**（Recursive，自引用的查询）、**UNION ALL**（连接两部分的桥梁）。执行过程是：先执行锚定部分得到初始结果集，然后反复执行递归部分（每次用上一轮的结果作为输入），直到没有新的行被加入为止：

```sql
-- 递归CTE：查询完整的公司组织架构（汇报链）
WITH RECURSIVE org_chart AS (
    -- 锚定部分：找到没有上级的人（最高管理者）
    SELECT emp_id, emp_name, manager_id, 1 AS level,
           CAST(emp_name AS CHAR(200)) AS path
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- 递归部分：每一轮找当前层级所有人的直接下属
    SELECT e.emp_id, e.emp_name, e.manager_id, oc.level + 1,
           CONCAT(oc.path, ' -> ', e.emp_name)
    FROM employees e
    INNER JOIN org_chart oc ON e.manager_id = oc.emp_id
)
SELECT * FROM org_chart ORDER BY level, emp_name;
-- 结果展示每个人的层级和完整的汇报路径
```

递归CTE不仅能处理层次数据，还可以用来生成序列——这在需要做日期填充、数字辅助表等场景时非常方便：

```sql
-- 生成1到100的数字序列（替代传统的数字辅助表）
WITH RECURSIVE numbers AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM numbers WHERE n < 100
)
SELECT * FROM numbers;

-- 生成2025年1月的日期序列（适合做日期维表）
WITH RECURSIVE date_series AS (
    SELECT DATE('2025-01-01') AS dt
    UNION ALL
    SELECT DATE_ADD(dt, INTERVAL 1 DAY) FROM date_series WHERE dt < '2025-01-31'
)
SELECT dt, DAYNAME(dt) AS weekday FROM date_series;
```

> [!WARNING] 注意
> 递归CTE一定要有终止条件！上面的 `WHERE n < 100` 和 `WHERE dt < '2025-01-31'` 就是终止条件。如果忘记写终止条件，MySQL会一直递归下去直到达到最大递归深度（默认1000层）才停下来报错。你可以通过 `SET SESSION cte_max_recursion_depth = 5000;` 来调整上限，但真正需要超过1000层递归的情况很少，遇到时应该先检查是不是终止条件写错了。

## 9.7 CTE vs 子查询 vs 临时表的选择

这三种方式都可以用来处理"中间结果"的需求，但各有适用场景。CTE可读性最好，从上到下线性阅读，而且支持递归。子查询是最传统的方式，适合简单的嵌套。临时表会把中间结果物化到磁盘上，可以建索引，适合大数据量的中间结果。

从性能角度看：如果你的中间结果会被多次引用，临时表更好（只算一次，后面都从磁盘读）。如果中间结果不大且只用一次，CTE和子查询性能差不多。如果涉及树形数据的遍历，递归CTE是唯一的选择。从可读性角度看：CTE优于子查询优于临时表（临时表的逻辑分散在多条语句中，不容易看全貌）。

```sql
-- 临时表方式（适合大数据量的中间结果，因为可以建索引）
CREATE TEMPORARY TABLE temp_dept_avg AS
SELECT department, AVG(salary) AS avg_salary
FROM employees GROUP BY department;

-- 可以在临时表上建索引来加速后续查询
CREATE INDEX idx_avg ON temp_dept_avg(avg_salary);

SELECT e.* FROM employees e
JOIN temp_dept_avg t ON e.department = t.department
WHERE e.salary > t.avg_salary;

-- 用完记得清理（会话结束时也会自动删除）
DROP TEMPORARY TABLE temp_dept_avg;
```

## 9.8 MySQL 8.0 CTE 新特性补充

MySQL 8.0 的CTE还有一些值得注意的细节。比如你可以在CTE定义中直接指定列别名，而不是在子查询内部用AS来命名。这种写法在CTE返回计算列时特别方便：

```sql
-- CTE中直接定义列别名（在AS后面的括号中列出）
WITH monthly_sales(year_val, month_val, total) AS (
    SELECT YEAR(order_date), MONTH(order_date), SUM(amount)
    FROM orders GROUP BY YEAR(order_date), MONTH(order_date)
)
SELECT * FROM monthly_sales WHERE total > 10000;

-- CTE配合窗口函数——MySQL 8.0的最佳组合
WITH ranked AS (
    SELECT emp_name, department, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
)
SELECT * FROM ranked WHERE rn <= 2;
```

## 小结

视图是持久化的查询别名，适合封装常用复杂查询和实现权限控制，但不缓存数据，嵌套多了性能差。CTE是临时的、一次性的查询别名，可读性强且支持递归，是处理复杂查询的首选方式。递归CTE专门处理层次数据（树结构）。临时表适合大数据量的中间结果，因为可以建索引加速查询。
