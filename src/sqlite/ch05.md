# 第 5 章 SQL 基础（下）—— JOIN、子查询与聚合

## 5.1 幽默开场：SQL 的"社交场合"

前四章你都是"独居"—— 一张表自己玩。**但真实项目里没人独居**，表和表之间总要谈恋爱、结婚、生娃（外键关系）。

用户表和文章表想约会，怎么办？—— **JOIN**。
文章想知道自己有多少评论，怎么办？—— **聚合 (COUNT)**。
想找"没写过任何文章的用户"，怎么办？—— **子查询 / LEFT JOIN**。

这一章，我们要学**关系数据库真正的核心能力**：多表关联查询。学不会这章的 SQL 程序员，本质上就是一个"只会键值对存取的"码农，跟用 Redis 差不多，浪费了 SQLite 的关系型灵魂。

## 5.2 关系代数入门：为什么需要 JOIN

**关系数据库的理论基础是"关系代数"**（Relational Algebra），由 E.F. Codd 在 1970 年提出。核心操作有：

- **σ（Selection，选择）** —— 按条件过滤行 → 对应 SQL 的 `WHERE`
- **π（Projection，投影）** —— 选取部分列 → 对应 SQL 的 `SELECT col1, col2`
- **×（Cartesian Product，笛卡尔积）** —— 两张表所有行组合 → 对应 `CROSS JOIN`
- **⋈（Join，连接）** —— 笛卡尔积 + 过滤 → 对应 `INNER JOIN`
- **∪（Union，并集）** → `UNION`
- **∩（Intersection，交集）** → `INTERSECT`
- **－（Difference，差集）** → `EXCEPT`

**JOIN 本质上就是"笛卡尔积 + 过滤"**：把两张表所有行组合一遍，然后按条件筛选。

举个直观例子。假设：

```
users:            posts:
+----+-------+    +----+-----------+-----------+
| id | name  |    | id | author_id | title     |
+----+-------+    +----+-----------+-----------+
| 1  | Alice |    | 10 | 1         | Hello     |
| 2  | Bob   |    | 11 | 1         | World     |
+----+-------+    | 12 | 2         | SQL Rocks |
                  +----+-----------+-----------+
```

**笛卡尔积**（不推荐直接用）会产生 2 × 3 = 6 行：

```sql
SELECT * FROM users, posts;   -- 或 CROSS JOIN
```

```
Alice, 1 | 10, 1, Hello        ← author_id 匹配
Alice, 1 | 11, 1, World        ← 匹配
Alice, 1 | 12, 2, SQL Rocks    ← 不匹配（Alice 没写这篇）
Bob,   2 | 10, 1, Hello        ← 不匹配
Bob,   2 | 11, 1, World        ← 不匹配
Bob,   2 | 12, 2, SQL Rocks    ← 匹配
```

**加个 WHERE 过滤"作者 id 对得上"**：

```sql
SELECT * FROM users, posts WHERE users.id = posts.author_id;
```

**这就是 INNER JOIN 的本质**。现代 SQL 更推荐显式的 JOIN 语法：

```sql
SELECT * FROM users INNER JOIN posts ON users.id = posts.author_id;
```

## 5.3 四大 JOIN

## 5.3.1 INNER JOIN

**只保留两边都匹配的行**：

```sql
SELECT u.id, u.username, p.title
FROM users AS u
INNER JOIN posts AS p ON p.author_id = u.id;
```

结果：

```
1 | Alice | Hello
1 | Alice | World
2 | Bob   | SQL Rocks
```

**注意**：`INNER` 可以省略，`JOIN` 默认就是 INNER。但**强烈建议写全**，可读性好。

## 5.3.2 LEFT (OUTER) JOIN

**保留左表全部行**，右表匹配不上的补 NULL：

```sql
INSERT INTO users VALUES (3, 'Cathy', ...);   -- Cathy 没写过任何文章

SELECT u.id, u.username, p.title
FROM users AS u
LEFT JOIN posts AS p ON p.author_id = u.id;
```

结果：

```
1 | Alice | Hello
1 | Alice | World
2 | Bob   | SQL Rocks
3 | Cathy | NULL          ← Cathy 也被列出，右表补 NULL
```

**经典用途**：找"没有对应关系的行"：

```sql
-- 找出从未发过文章的用户
SELECT u.*
FROM users AS u
LEFT JOIN posts AS p ON p.author_id = u.id
WHERE p.id IS NULL;
```

`OUTER` 可以省略，SQLite 里 `LEFT JOIN` 等价于 `LEFT OUTER JOIN`。

## 5.3.3 RIGHT JOIN（SQLite 3.39+）

对称的：**保留右表全部行**。

```sql
SELECT u.id, u.username, p.title
FROM users AS u
RIGHT JOIN posts AS p ON p.author_id = u.id;
```

**注意**：SQLite **直到 3.39（2022 年 6 月）才支持 RIGHT JOIN**！之前只能用 `LEFT JOIN` + 调换表位置来模拟。

任何 `A RIGHT JOIN B` 都等价于 `B LEFT JOIN A`，所以**很多老代码从来不用 RIGHT JOIN**。

## 5.3.4 FULL (OUTER) JOIN（SQLite 3.39+）

**左表 + 右表全部行都保留**，不匹配的部分补 NULL：

```sql
SELECT u.username, p.title
FROM users AS u
FULL OUTER JOIN posts AS p ON p.author_id = u.id;
```

也是 3.39+ 才有。之前的经典绕法：`LEFT JOIN UNION RIGHT JOIN`（本身 RIGHT JOIN 都没有，就更绕）。

## 5.3.5 CROSS JOIN

**显式的笛卡尔积**：

```sql
SELECT * FROM users CROSS JOIN posts;   -- 2 × 3 = 6 行
```

**用途少**，但有个特殊场景：**给 SQLite 一个提示，让它按你写的顺序驱动嵌套循环**（详见下节原理）。

## 5.3.6 SELF JOIN

**表跟自己 JOIN**：

```sql
-- 找出同一年生的所有用户对
SELECT u1.username, u2.username
FROM users AS u1
INNER JOIN users AS u2 ON u1.birth_year = u2.birth_year AND u1.id < u2.id;
```

关键是**给两个别名**（`u1`、`u2`），SQLite 才能区分。

## 5.4 SQLite 的 JOIN 实现：嵌套循环连接

**这是原理深挖时间**。

大部分数据库对 JOIN 有多种算法（Hash Join、Sort-Merge Join、Nested Loop Join）。**SQLite 只用一种：嵌套循环（Nested Loop Join）**。

伪代码：

```
FOR row1 IN table1:
    FOR row2 IN table2:
        IF join_condition(row1, row2):
            OUTPUT row1 || row2
```

**朴素 nested loop 是 O(N × M)**，两张 1 万行的表 = 1 亿次比较，慢死。

**SQLite 靠"索引"救场**：如果内层循环的 ON 条件字段有索引，就变成：

```
FOR row1 IN table1:               -- 外层扫描
    LOOKUP row2 IN table2         -- 内层走索引，O(log M)
    WHERE row2.key = row1.key
```

复杂度降到 O(N × log M)，快得多。

**这就是为什么 JOIN 字段必须有索引**（大表尤甚）。忘了建索引 → 查询秒变小时。

## 5.4.1 用 `EXPLAIN QUERY PLAN` 查看

```sql
EXPLAIN QUERY PLAN
SELECT u.username, p.title
FROM users u
INNER JOIN posts p ON p.author_id = u.id
WHERE u.username = 'alice';
```

好的执行计划：

```
SEARCH u USING INDEX sqlite_autoindex_users_1 (username=?)
SEARCH p USING INDEX idx_posts_author (author_id=?)
```

坏的执行计划：

```
SCAN u                                  ← 全表扫描 users
SCAN p                                  ← 全表扫描 posts
```

**看到 `SCAN` 就要警觉，看到 `SEARCH ... USING INDEX` 就放心。**

## 5.4.2 SQLite 的 JOIN 顺序策略

SQLite 使用一种基于**成本估算**的查询优化器（Query Planner），会自动决定：

- 哪张表当外层驱动表。
- 用哪个索引。
- 是否需要临时排序。

一般选**估算行数少**的表当外层。你可以用 `CROSS JOIN` 强制固定顺序（3.10+ 起 CROSS JOIN 被特殊对待）：

```sql
-- 强制先扫 small_table，再对每行去 big_table 找
SELECT * FROM small_table CROSS JOIN big_table ON small_table.k = big_table.k;
```

**日常几乎用不着**。信任 planner 就行。

## 5.5 子查询分类

**子查询（Subquery）= 嵌在另一条 SQL 里的 SELECT**。

按"返回什么"分：

## 5.5.1 标量子查询（返回单值）

```sql
SELECT username,
       (SELECT COUNT(*) FROM posts WHERE author_id = users.id) AS post_count
FROM users;
```

- 子查询返回**一行一列**（一个标量）。
- 可以出现在几乎任何标量表达式的位置。

## 5.5.2 行子查询（返回一行多列）

```sql
SELECT * FROM users
WHERE (username, email) = (SELECT username, email FROM archive WHERE id = 1);
```

- 返回一行 N 列。
- SQLite 支持有限。

## 5.5.3 表子查询（返回多行多列）

```sql
SELECT sub.username, sub.total
FROM (
    SELECT u.username, COUNT(p.id) AS total
    FROM users u LEFT JOIN posts p ON p.author_id = u.id
    GROUP BY u.id
) AS sub
WHERE sub.total > 5;
```

- 又叫**派生表（Derived Table）**、**内联视图（Inline View）**。
- 放在 `FROM` 后面，当成一张临时表用。
- **必须有别名**。

## 5.5.4 相关子查询（Correlated Subquery）

**内层引用了外层的列**：

```sql
SELECT username
FROM users u
WHERE EXISTS (
    SELECT 1 FROM posts p
    WHERE p.author_id = u.id      -- ← 引用了外层的 u.id
    AND p.published = 1
);
```

**性能陷阱**：相关子查询对**外层每一行都会重新执行内层**。数据量大时性能可能爆炸。**JOIN 通常更快**，除非查询优化器能把它改写。

## 5.6 IN vs EXISTS 的性能对比

这是面试常考的点。

## 5.6.1 IN

```sql
SELECT * FROM users
WHERE id IN (SELECT author_id FROM posts WHERE published = 1);
```

- 语义：`id` 在子查询返回的集合里。
- SQLite 通常会把 `IN (SELECT ...)` **物化成一个临时表 / 内存集合**，然后 hash 查找。

## 5.6.2 EXISTS

```sql
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM posts p
    WHERE p.author_id = u.id AND p.published = 1
);
```

- 语义：只关心子查询是否返回至少一行。
- **短路**：一旦找到一行就停。
- 通常配合相关子查询使用。

## 5.6.3 性能对比

**经验法则**：

- 子查询结果集**小**（几十几百）→ `IN` 快（一次性物化）。
- 子查询结果集**大**（几十万+）→ `EXISTS` 快（短路 + 内层可以走索引）。
- 现代 SQLite 优化器很多时候会把 `IN (SELECT ...)` 改写成 `EXISTS` 的等价形式，两者差异越来越小。

**看执行计划为准，别凭感觉**。

## 5.6.4 NOT IN 的大坑

```sql
SELECT * FROM users
WHERE id NOT IN (SELECT author_id FROM posts);
```

**如果子查询结果里有 NULL，整个 NOT IN 会返回空集！** 因为 `x NOT IN (a, NULL)` 等价于 `x != a AND x != NULL`，后者永远是 NULL（不是 TRUE），WHERE 整体不通过。

**解决方案**：用 `NOT EXISTS` 或过滤 NULL：

```sql
-- 方案 1
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM posts p WHERE p.author_id = u.id);

-- 方案 2：过滤 NULL
SELECT * FROM users
WHERE id NOT IN (SELECT author_id FROM posts WHERE author_id IS NOT NULL);
```

## 5.7 GROUP BY 与聚合函数

**聚合函数** = 多行 → 一行的函数：

| 函数 | 说明 |
| --- | --- |
| `COUNT(*)` | 计数所有行（含 NULL） |
| `COUNT(col)` | 计数非 NULL 值 |
| `COUNT(DISTINCT col)` | 去重后计数 |
| `SUM(col)` | 求和 |
| `AVG(col)` | 平均值（结果为 REAL） |
| `MIN(col)` / `MAX(col)` | 最小 / 最大 |
| `GROUP_CONCAT(col, sep)` | 字符串拼接，sep 默认 `,` |
| `TOTAL(col)` | 类似 SUM，但空时返回 0 而非 NULL |

## 5.7.1 单表聚合（无 GROUP BY）

```sql
SELECT COUNT(*), AVG(age), MIN(age), MAX(age) FROM users;
-- 一张表整体的聚合，一行结果
```

## 5.7.2 GROUP BY 分组

```sql
-- 每个作者的文章数
SELECT author_id, COUNT(*) AS post_count
FROM posts
GROUP BY author_id;
```

**规则**：`SELECT` 里的非聚合列，必须出现在 `GROUP BY` 里（否则行为未定义）。

```sql
-- ❌ 错误示范：author_id 不在 GROUP BY 里也不是聚合
-- 严格数据库（PostgreSQL）会报错，SQLite 允许但结果不可控
SELECT author_id, title, COUNT(*) FROM posts GROUP BY author_id;
```

## 5.7.3 GROUP_CONCAT：把多行拼成一个字符串

```sql
-- 每个作者的所有文章标题拼起来
SELECT author_id, GROUP_CONCAT(title, ' | ') AS all_titles
FROM posts
GROUP BY author_id;

-- 输出：
-- 1 | Hello | World
-- 2 | SQL Rocks
```

**注意**：MySQL 里叫 `GROUP_CONCAT(...  SEPARATOR '...')`，SQLite 语法略不同。PostgreSQL 里是 `STRING_AGG`。

## 5.8 HAVING vs WHERE

**`WHERE` 在分组之前过滤**，**`HAVING` 在分组之后过滤**。

```sql
-- 找出至少发过 3 篇文章的作者
SELECT author_id, COUNT(*) AS c
FROM posts
WHERE published = 1       -- ← 分组前过滤：只考虑已发布的文章
GROUP BY author_id
HAVING c >= 3;            -- ← 分组后过滤：文章数 ≥ 3
```

**记忆口诀**：

- 单行条件 → WHERE（分组前，可用索引）
- 聚合结果条件 → HAVING（分组后，走不了索引）

**性能提示**：能用 WHERE 就别用 HAVING，尽量把条件"下推"到分组前，减少要分组的数据量。

## 5.9 集合运算：UNION / INTERSECT / EXCEPT

**多个 SELECT 的结果拼在一起**：

## 5.9.1 UNION

**并集（自动去重）**：

```sql
SELECT username FROM users
UNION
SELECT author_name FROM archive_users;
```

**UNION ALL**：**并集（不去重）**。**性能更好**（省去去重步骤）。

```sql
SELECT id FROM users
UNION ALL
SELECT id FROM archive_users;
```

**要求**：两个 SELECT 的**列数、类型（近似）必须一致**。

## 5.9.2 INTERSECT（交集）

```sql
SELECT email FROM users
INTERSECT
SELECT email FROM newsletter_subscribers;
-- 既是用户又是订阅者的邮箱
```

## 5.9.3 EXCEPT（差集）

```sql
SELECT email FROM users
EXCEPT
SELECT email FROM newsletter_subscribers;
-- 是用户但没订阅
```

**注意**：INTERSECT 和 EXCEPT **自动去重**，没有 `INTERSECT ALL` / `EXCEPT ALL`（PostgreSQL 有，SQLite 没有）。

## 5.10 复杂查询案例：博客文章列表

**需求**：给博客首页展示文章列表，每行需要：

- 文章 id / title / created_at
- 作者的 username
- 该文章的评论数
- 该文章的标签（多个，用 `,` 拼接）
- 只显示已发布（published = 1）
- 按 created_at 降序，分页

先建两张新表：

```sql
CREATE TABLE comments (
    id         INTEGER PRIMARY KEY,
    post_id    INTEGER NOT NULL,
    user_id    INTEGER NOT NULL,
    body       TEXT    NOT NULL,
    created_at INTEGER NOT NULL DEFAULT (unixepoch()),
    FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE,
    FOREIGN KEY (user_id) REFERENCES users(id)
) STRICT;

CREATE TABLE tags (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
) STRICT;

CREATE TABLE post_tags (
    post_id INTEGER NOT NULL,
    tag_id  INTEGER NOT NULL,
    PRIMARY KEY (post_id, tag_id),
    FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id)  REFERENCES tags(id)  ON DELETE CASCADE
) STRICT, WITHOUT ROWID;

CREATE INDEX idx_comments_post ON comments(post_id);
CREATE INDEX idx_post_tags_tag ON post_tags(tag_id);
```

## 5.10.1 天真写法

```sql
SELECT
    p.id,
    p.title,
    p.created_at,
    u.username AS author,
    (SELECT COUNT(*) FROM comments WHERE post_id = p.id) AS comment_count,
    (SELECT GROUP_CONCAT(t.name, ',') FROM tags t
     JOIN post_tags pt ON pt.tag_id = t.id
     WHERE pt.post_id = p.id) AS tags
FROM posts p
JOIN users u ON u.id = p.author_id
WHERE p.published = 1
ORDER BY p.created_at DESC
LIMIT 20 OFFSET 0;
```

**这是能跑的写法**。用了两个标量子查询（每行执行一次），文章多的时候会慢。

## 5.10.2 优化写法：JOIN + GROUP BY

```sql
SELECT
    p.id,
    p.title,
    p.created_at,
    u.username AS author,
    COUNT(DISTINCT c.id) AS comment_count,
    GROUP_CONCAT(DISTINCT t.name) AS tags
FROM posts p
JOIN users u             ON u.id  = p.author_id
LEFT JOIN comments c     ON c.post_id = p.id
LEFT JOIN post_tags pt   ON pt.post_id = p.id
LEFT JOIN tags t         ON t.id = pt.tag_id
WHERE p.published = 1
GROUP BY p.id
ORDER BY p.created_at DESC
LIMIT 20 OFFSET 0;
```

**几个关键点**：

1. `LEFT JOIN` 保证没评论 / 没标签的文章也能出现。
2. 因为 JOIN comments 和 tags 会**行数膨胀**（笛卡尔积效应），必须用 `COUNT(DISTINCT c.id)` 和 `GROUP_CONCAT(DISTINCT t.name)` 去重。
3. `GROUP BY p.id` —— 因为 `p.id` 是主键，SQLite 允许 SELECT 里带其他 `p.*` 和 `u.*` 字段（依赖 p.id 的函数）。
4. 大量文章时，标量子查询 vs JOIN+GROUP BY 哪个快？**看数据分布**。评论数极多时，标量子查询可能更好（每行只算一个 count）。**用 `EXPLAIN QUERY PLAN` 实测。**

## 5.10.3 更清晰：CTE（Common Table Expression）

```sql
WITH
comment_counts AS (
    SELECT post_id, COUNT(*) AS c FROM comments GROUP BY post_id
),
post_tag_list AS (
    SELECT pt.post_id, GROUP_CONCAT(t.name) AS names
    FROM post_tags pt JOIN tags t ON t.id = pt.tag_id
    GROUP BY pt.post_id
)
SELECT
    p.id,
    p.title,
    p.created_at,
    u.username AS author,
    COALESCE(cc.c, 0) AS comment_count,
    COALESCE(ptl.names, '') AS tags
FROM posts p
JOIN users u                ON u.id = p.author_id
LEFT JOIN comment_counts cc ON cc.post_id = p.id
LEFT JOIN post_tag_list ptl ON ptl.post_id = p.id
WHERE p.published = 1
ORDER BY p.created_at DESC
LIMIT 20 OFFSET 0;
```

**CTE 的好处**：

- 逻辑分段清晰。
- 每个 CTE 是独立"临时表"，可复用。
- `COALESCE(x, 0)` 处理 LEFT JOIN 后可能的 NULL。

**SQLite 3.34+ 甚至支持递归 CTE**（Part 3 详解，可以查树形结构、图遍历）。

## 5.11 SQL 执行顺序

**很多人写 SQL 出问题，都是因为不懂"逻辑执行顺序"**。

书写顺序是：

```sql
SELECT   ...
FROM     ...
WHERE    ...
GROUP BY ...
HAVING   ...
ORDER BY ...
LIMIT    ...
```

**但实际执行顺序是**：

```
1. FROM       ← 先确定数据源（含 JOIN 展开）
2. WHERE      ← 单行过滤
3. GROUP BY   ← 分组
4. HAVING     ← 分组后过滤
5. SELECT     ← 计算投影列（此时才有列别名！）
6. DISTINCT   ← 去重
7. ORDER BY   ← 排序（可用 SELECT 的别名）
8. LIMIT      ← 分页
```

## 5.11.1 别名的作用范围

```sql
-- ❌ WHERE 用不了别名（别名此时还没定义）
SELECT unixepoch() - created_at AS age FROM users WHERE age > 100;
-- Error: no such column: age

-- ✅ ORDER BY 可以用别名（别名此时已定义）
SELECT unixepoch() - created_at AS age FROM users ORDER BY age DESC;
```

想在 WHERE 里用别名？包一层子查询：

```sql
SELECT * FROM (
  SELECT unixepoch() - created_at AS age, * FROM users
) WHERE age > 100;
```

## 5.11.2 GROUP BY 前后

```sql
SELECT country, AVG(age) AS avg_age
FROM users
WHERE age >= 18           -- 分组前的过滤
GROUP BY country
HAVING avg_age > 30       -- 分组后的过滤，SQLite 允许别名
ORDER BY avg_age DESC     -- 排序用别名
LIMIT 10;
```

## 5.12.2 Feed Repository

```dart
// lib/repos/feed_repo.dart
import '../db.dart';
import '../models/post_feed_item.dart';

class FeedRepo {
  Future<List<PostFeedItem>> fetchPublishedFeed({
    int limit = 20,
    int offset = 0,
  }) async {
    final db = await AppDb.instance;
    final rows = await db.rawQuery('''
      SELECT
        p.id            AS id,
        p.title         AS title,
        p.created_at    AS created_at,
        u.username      AS author,
        COUNT(DISTINCT c.id)              AS comment_count,
        COALESCE(GROUP_CONCAT(DISTINCT t.name), '') AS tags
      FROM posts p
      JOIN users u             ON u.id = p.author_id
      LEFT JOIN comments c     ON c.post_id = p.id
      LEFT JOIN post_tags pt   ON pt.post_id = p.id
      LEFT JOIN tags t         ON t.id = pt.tag_id
      WHERE p.published = 1
      GROUP BY p.id
      ORDER BY p.created_at DESC, p.id DESC
      LIMIT ? OFFSET ?
    ''', [limit, offset]);

    return rows.map(PostFeedItem.fromRow).toList();
  }

  /// Keyset 分页版：更适合无限滚动 List
  Future<List<PostFeedItem>> fetchFeedAfter({
    int? lastCreatedAt,
    int? lastId,
    int limit = 20,
  }) async {
    final db = await AppDb.instance;

    final baseWhere = 'p.published = 1';
    final cursorWhere = (lastCreatedAt != null && lastId != null)
        ? 'AND (p.created_at, p.id) < (?, ?)'
        : '';
    final args = <Object?>[];
    if (lastCreatedAt != null) args.addAll([lastCreatedAt, lastId]);
    args.add(limit);

    final rows = await db.rawQuery('''
      SELECT
        p.id            AS id,
        p.title         AS title,
        p.created_at    AS created_at,
        u.username      AS author,
        COUNT(DISTINCT c.id) AS comment_count,
        COALESCE(GROUP_CONCAT(DISTINCT t.name), '') AS tags
      FROM posts p
      JOIN users u             ON u.id = p.author_id
      LEFT JOIN comments c     ON c.post_id = p.id
      LEFT JOIN post_tags pt   ON pt.post_id = p.id
      LEFT JOIN tags t         ON t.id = pt.tag_id
      WHERE $baseWhere $cursorWhere
      GROUP BY p.id
      ORDER BY p.created_at DESC, p.id DESC
      LIMIT ?
    ''', args);

    return rows.map(PostFeedItem.fromRow).toList();
  }
}
```

## 5.12.3 使用

```dart
final feedRepo = FeedRepo();

// OFFSET 版
final page1 = await feedRepo.fetchPublishedFeed(limit: 20, offset: 0);
for (final item in page1) {
  print('${item.title} by ${item.author} (${item.commentCount} comments) '
        'tags=${item.tags.join(",")}');
}

// Keyset 版（推荐用于无限滚动）
var last = page1.isEmpty ? null : page1.last;
final page2 = await feedRepo.fetchFeedAfter(
  lastCreatedAt: last?.createdAt,
  lastId: last?.id,
  limit: 20,
);
```

## 5.12.4 结果映射的几个细节

1. **`COALESCE(x, '')`** 让 GROUP_CONCAT 为空时返回空串，Dart 端好处理。
2. **列别名要和 `fromRow` 里的 key 完全一致**（大小写、下划线）。
3. sqflite 返回的 Map values 都是 `Object?`，需要类型断言。用 `as int` / `as String` 显式转换。
4. 多表 JOIN 结果映射建议**扁平化为 ViewModel**（如 `PostFeedItem`），而不是嵌套 `Post + User + List<Comment>`。嵌套结构如果需要，可以另外发查询组装（避免 N+1 陷阱 —— 我们下面讲）。

## 5.12.5 N+1 查询陷阱

**"错误"的做法**：先查文章列表，再逐个查作者：

```dart
// ❌ N+1：一次列表查询 + N 次作者查询
final posts = await db.query('posts', where: 'published = 1', limit: 20);
for (final p in posts) {
  final author = await db.query('users', where: 'id = ?', whereArgs: [p['author_id']]);
  // ... 组装
}
```

**问题**：查 20 篇文章 = 1 + 20 = 21 次查询。100 篇 = 101 次。**性能瀑布式下降**。

**"正确"的做法**：**一次 JOIN 搞定**（就像上面 5.12.2 那样）。

**如果 JOIN 结果集太宽，或者关联多张表**，可以用**批量查询 + Dart 端组装**：

```dart
final posts = await db.query('posts', where: 'published = 1', limit: 20);
final authorIds = posts.map((p) => p['author_id']).toSet().toList();
final placeholders = List.filled(authorIds.length, '?').join(',');
final authors = await db.rawQuery(
  'SELECT * FROM users WHERE id IN ($placeholders)', authorIds);
final authorMap = { for (final a in authors) a['id']: a };
// 现在在 Dart 里做 join
```

**核心思想**：**永远不要在循环里做 SQL 查询**，除非只是几条。

## 5.13 原理深挖：一条 JOIN 查询的执行

回到 5.12.2 的 SQL，SQLite 大致这么执行：

1. **解析** 成 AST。
2. **查询优化器（Query Planner）** 决定：
   - 从 `posts` 开始扫描（因为有 WHERE p.published = 1，且有 `idx_posts_published`）。
   - 对每一行，用 `p.author_id` 查 users（走 users 主键索引，1 次 B-Tree 查找）。
   - 用 `p.id` 查 comments（走 `idx_comments_post`）。
   - 用 `p.id` 查 post_tags（走主键，因为 (post_id, tag_id) 是 PK）。
   - 对每个 tag_id 查 tags 主键。
3. **生成 VDBE 字节码**（可以用 `EXPLAIN` 命令看到）。
4. **执行字节码**：
   - 每读一行组合，如果满足 WHERE 就参与 GROUP BY 聚合。
   - GROUP BY 通常靠"排序 + 分组"或"哈希"实现。
   - 最终按 ORDER BY 排序（如果排序字段有索引可跳过）。
   - 应用 LIMIT / OFFSET。

**索引缺失的代价**：

- `idx_posts_published` 缺失 → 全表扫 posts。
- `idx_comments_post` 缺失 → 每查一篇文章都要全表扫 comments。
- **想象一下：1000 篇文章 × 全表扫 10 万条评论 = 1 亿次比较。** 秒变小时。

## 5.14 常见坑点

1. **JOIN 不写 ON 条件** → 变成笛卡尔积，数据爆炸。
2. **忘记 LEFT JOIN 后的 NULL** → 后面 WHERE 意外过滤掉了想保留的行（该用 ON 条件而非 WHERE）。
3. **GROUP BY 里少列** → 结果不可预测。
4. **COUNT(*) vs COUNT(col)** → 后者不算 NULL。
5. **NOT IN 遇上 NULL** → 返回空集，改 NOT EXISTS。
6. **UNION 忘写 ALL** → 无谓的去重开销。
7. **N+1 查询** → 循环里发 SQL，性能瀑布。
8. **JOIN 字段没索引** → 嵌套循环退化为 O(N×M)。
9. **`SELECT * FROM a, b`（隐式笛卡尔）** → 忘写 WHERE 就是灾难。
10. **相关子查询滥用** → 外层多少行，内层执行多少次。
11. **HAVING 里想用 SELECT 别名** → SQLite 支持，MySQL 也支持，但**标准 SQL 不允许**，PostgreSQL 严格模式会拒。

## 5.15 本章小结

- JOIN 的本质：**笛卡尔积 + 过滤**。
- 四大 JOIN：`INNER` / `LEFT [OUTER]` / `RIGHT [OUTER]` / `FULL [OUTER]`（后两者 3.39+）。
- SQLite 只用**嵌套循环连接**，靠索引把 O(N×M) 降到 O(N×log M)。
- 子查询四类：标量 / 行 / 表 / 相关；**相关子查询小心 N 次执行**。
- `IN` 小集合快，`EXISTS` 相关短路快；**`NOT IN` + NULL = 死**。
- 聚合：`COUNT / SUM / AVG / MIN / MAX / GROUP_CONCAT`；**多个 JOIN 引起行数膨胀时用 `DISTINCT`**。
- `WHERE`（分组前）vs `HAVING`（分组后），能下推到 WHERE 的绝不放 HAVING。
- 集合运算：`UNION [ALL] / INTERSECT / EXCEPT`。
- SQL 执行顺序：**FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT**。
- **Flutter 里做多表查询**：一条 SQL + `ViewModel.fromRow`；**警惕 N+1**。
