## 15.1 Tool 的本质：从"只会说"到"能做事"

在前面的章节中，DocMind 已经能对话、有记忆（至于读取文档的 RAG，要到第22-23章才会学习）。但它还缺少一个关键能力：**做事**。

目前 DocMind 的所有回复都是 LLM 直接生成的文本。如果用户说"帮我搜索一下项目文档里关于 Docker 的内容"，LLM 不可能直接访问你的文档数据库——它只能"说"，不能"做"。

Tool（工具）就是让 Agent 从"只会说"变成"能做事"的桥梁。把 Tool 想象成 API endpoint——每个 Tool 有一个名称、一段描述、一个输入格式，Agent 决定何时调用哪个 Tool，然后拿到 Tool 的结果来生成最终回答。

要注意的是：**LLM 从头到尾只做一件事——生成"我想调用某个工具"的请求；真正执行工具的永远是你这边的代码。**"决定调用"与"实际执行"是分离的，这个分离正是第17章 Function Calling 协议要规范化的东西。

在第9章的 Agent 架构全景中，我们了解了 Agent 四大组件中的"行动"（Action）。Tool 就是"行动"的具体实现：

```text
用户："帮我搜一下项目文档里关于 Docker 的内容"
   |
   v
LLM 只能生成文本，访问不了文档数据库
   |
   v (装上 Tool 之后)
search_documents("Docker") 真正执行搜索
   |
   v
工具结果 -> LLM 组织成最终回答
```

## 15.2 Tool 的三要素

每个 Tool 都有三个核心要素：

| 要素 | 说明 | 类比 |
|------|------|------|
| name | 工具名称（英文，简洁） | API endpoint 的路径 |
| description | 工具描述（告诉 LLM 何时使用） | API 文档 |
| args_schema | 输入参数定义（Pydantic 模型） | API 的请求体 Schema |

LLM 通过阅读 `description` 来决定是否使用这个工具——所以描述的质量直接决定了 Agent 会不会在正确的时机调用工具。

> [!WARNING] description 决定调用时机
> - LLM 完全依赖 description 判断"什么时候用这个工具"：写得含糊，Agent 要么不调用，要么在不该调用时调用。
> - 要像写 API 文档一样写 description：清晰、准确，写明使用场景，最好也写明"不用于什么"。

## 15.3 @tool 装饰器：快速创建自定义 Tool

最省事的定义方式——给一个普通函数加 `@tool` 装饰器（decorator），LangChain 会自动从函数签名和 docstring 生成三要素：

```python
from langchain_core.tools import tool

@tool
def search_documents(query: str, k: int = 3) -> str:
    """在文档库中搜索与查询相关的内容。
    当用户询问关于特定技术概念、API 用法或项目文档内容时使用此工具。
    不要用于闲聊或简单问答。

    Args:
        query: 搜索查询关键词
        k: 返回结果数量，默认3条
    """
    # 这里是你的实际搜索逻辑
    # 例如：调用向量数据库的检索功能
    results = f"找到 {k} 条关于 '{query}' 的相关文档"
    return results

# 查看工具信息
print(f"名称: {search_documents.name}")
print(f"描述: {search_documents.description}")
print(f"参数: {search_documents.args}")
```

注意 docstring 的写法：第一段话给模型判断"什么时候用"，`Args:` 部分给模型说明"参数怎么填"——它不是给人看的注释，而是工具契约的一部分。

## 15.4 StructuredTool.from_function()：更精细的定义

当函数实现与工具定义需要分开维护、或参数需要更严格的校验时，用 `StructuredTool.from_function()`：

```python
from langchain_core.tools import StructuredTool
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    """搜索工具的输入参数"""
    query: str = Field(description="搜索查询关键词")
    k: int = Field(default=3, description="返回结果数量", ge=1, le=10)
    category: str = Field(default="all", description="搜索分类：all/python/docker/api")

def search_impl(query: str, k: int = 3, category: str = "all") -> str:
    """搜索实现"""
    return f"在 [{category}] 中找到 {k} 条关于 '{query}' 的结果"

search_tool = StructuredTool.from_function(
    func=search_impl,
    name="search_documents",
    description="在技术文档库中搜索相关内容。当用户询问特定技术概念或查找文档时使用。",
    args_schema=SearchInput,
)

# 调用
result = search_tool.invoke({"query": "Docker", "k": 5, "category": "docker"})
print(result)
```

`Field(ge=1, le=10)` 这类约束会在参数校验阶段直接拦住非法输入。两种定义方式加上现成的内置工具，选型对照如下：

| 维度 | @tool 装饰器 | StructuredTool.from_function() | 内置工具 |
|------|-------------|-------------------------------|---------|
| 适用场景 | 函数已写好，加装饰器即可 | 实现与定义分离、需精细校验 | 常见通用能力 |
| 参数定义 | 从类型注解 + docstring 自动生成 | 显式传入 Pydantic args_schema | 框架自带 |
| 校验能力 | 基础类型 | Field 可加 ge/le/枚举等约束 | 自带 |
| 上手成本 | 最低 | 稍高 | 装包即用 |

## 15.6 Tool 的错误处理

工具运行在真实世界里：查询词可能为空、服务可能超时。错误处理的原则是——**把错误变成工具的正常返回值**：

```python
from langchain_core.tools import tool

@tool
def safe_search(query: str) -> str:
    """安全搜索工具，包含错误处理"""
    try:
        # 模拟可能失败的操作
        if not query.strip():
            raise ValueError("查询不能为空")

        results = f"搜索结果: {query}"
        return results

    except ValueError as e:
        # 返回错误信息而不是抛出异常
        # 这样 Agent 可以理解错误并调整策略
        return f"搜索出错: {e}。请检查查询关键词。"
    except Exception as e:
        return f"搜索服务暂时不可用，请稍后重试。错误: {type(e).__name__}"
```

**关键原则：工具里不要抛出未捕获的异常。**异常会中断整个 Agent 的执行链；捕获之后返回有意义的错误信息，Agent 才能读懂问题并做出调整——比如换一个查询词重试，而不是整个会话崩掉。

@tool
def analyze_code(code: str, language: str = "python") -> str:

## 15.8 Tool 设计最佳实践

1. **名称简洁明确** — `search_documents` 比 `search_for_documents_in_the_database` 好

## 15.9 ToolKit：Tool 的组合和管理

当你的项目有越来越多的 Tool 时，你需要一种方式来组织和管理它们。就像你不会把所有函数都放在一个文件里一样，Tool 也需要分组管理——这就是工具集（Toolkit）的职责：**统一注册、统一取用、统一描述**。

```python
# src/tools/toolkit.py — 工具集管理
"""DocMind 工具集管理器"""

from typing import List
from langchain_core.tools import BaseTool

class DocMindToolkit:
    """DocMind 唯一的工具注册入口"""

    def __init__(self):
        self._tools: List[BaseTool] = []

    def register(self, tool: BaseTool):
        """注册一个工具"""
        self._tools.append(tool)
        print(f"  注册工具: {tool.name}")

    def get_tools(self) -> List[BaseTool]:
        """获取所有工具"""
        return self._tools

    def get_tool_names(self) -> List[str]:
        """获取所有工具名称"""
        return [t.name for t in self._tools]

    def describe_tools(self) -> str:
        """生成工具描述（供 Agent 使用）"""
        lines = ["可用工具："]
        for t in self._tools:
            lines.append(f"- {t.name}: {t.description[:80]}...")
        return "\n".join(lines)

def create_docmind_toolkit() -> DocMindToolkit:
    """创建 DocMind 的标准工具集"""
    from src.tools.search import search_documents
    from src.tools.code_analyzer import analyze_code
    from src.tools.summarizer import generate_summary

    toolkit = DocMindToolkit()
    toolkit.register(search_documents)
    toolkit.register(analyze_code)
    toolkit.register(generate_summary)

    return toolkit

# 使用
toolkit = create_docmind_toolkit()
print(toolkit.describe_tools())
```

### 15.9.1 工具测试

工具和普通函数一样要有单元测试——测试的是"契约"是否成立：能调用、返回字符串、内容非空。

```python
# tests/test_tools.py — 工具单元测试
"""测试 DocMind 的各个工具"""

from src.tools.search import search_documents
from src.tools.code_analyzer import analyze_code
from src.tools.summarizer import generate_summary

def test_search_documents():
    """测试搜索工具"""
    result = search_documents.invoke({"query": "Docker", "k": 3})
    assert isinstance(result, str)
    assert len(result) > 0
    print(f"搜索测试通过: {result[:50]}...")

def test_analyze_code():
    """测试代码分析工具"""
    code = "def add(a, b): return a + b"
    result = analyze_code.invoke({"code": code, "language": "python"})
    assert isinstance(result, str)
    assert len(result) > 50  # 分析结果应该比较详细
    print(f"代码分析测试通过: {result[:50]}...")

def test_generate_summary():
    """测试摘要工具"""
    content = "这是一篇很长的技术文档..." * 20
    result = generate_summary.invoke({"content": content, "style": "concise"})
    assert isinstance(result, str)
    print(f"摘要测试通过: {result[:50]}...")

if __name__ == "__main__":
    test_search_documents()
    test_analyze_code()
    test_generate_summary()
    print("\n所有工具测试通过！")
```

## 15.10 思考题

1. **Tool 设计**：如果让你为 DocMind 再添加一个"代码运行"工具（可以运行用户的 Python 代码），你会如何设计它的安全机制？需要防范哪些风险？
2. **Tool 编排**：假设用户问"帮我分析一下这个项目的架构，并生成一份摘要报告"，这个请求需要多个 Tool 协作完成。你会如何设计 Tool 的调用顺序？如果中间某一步失败了怎么办？

## 本章小结

- Tool 让 Agent 从"只会说"变成"能做事"；分工是明确的——LLM 只生成调用请求，执行永远在你的代码里。
- 三要素 name / description / args_schema 构成工具契约，其中 description 是模型决定"何时调用"的唯一依据。
- 三种来源按需选：`@tool` 装饰器最快，`StructuredTool.from_function()` 最精细，内置工具开箱即用。
- 工具内部必须捕获异常并返回可读的错误信息，让 Agent 能理解失败并调整策略，而不是整个执行链崩溃。
- 设计五原则：名称简洁、描述具体、参数有默认值、返回结构化、错误优雅。
- DocMind 的三个工具（search_documents / analyze_code / generate_summary）已就位，并通过单元测试验证契约。
- 工具多了用 DocMindToolkit 统一注册、按名取用，全项目只保留一个注册入口。
- 至此 DocMind 集齐大脑（Model I/O）、记忆（Memory）、手脚（Tools），还缺一个"指挥官"决定何时调用哪个工具——这正是 Part 5 要解决的问题。
