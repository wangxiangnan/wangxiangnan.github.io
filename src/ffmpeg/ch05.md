# 第5章：编解码器——压缩的魔法

> 上一章我们知道了未压缩视频有多大（1080p 约 5.5GB/分钟），这一章我们来看看"编码"这个魔法是怎么把 5.5GB 压缩到几十 MB 的，以及有哪些不同的编码器可供选择。

## 5.1 为什么需要编码——算一笔账

让我们把"为什么需要压缩"这件事说得再具体一点：

**一段 10 分钟的 1080p 30fps 视频：**

| 项目 | 数值 |
| ------ | ------ |
| 分辨率 | 1920 × 1080 |
| 帧率 | 30 fps |
| 色彩格式 | YUV 4:2:0，8-bit |
| 每帧数据量 | 约 3.1 MB |
| 每秒数据量 | 约 93 MB |
| 10 分钟原始大小 | 约 **55 GB** |

**同样的视频，加上音频（48kHz 16-bit 立体声）：**

```
音频每秒数据量：48000 × 16 × 2 / 8 = 192 KB/s
音频 10 分钟：192 × 600 = 115 MB（相比视频可以忽略）
```

所以总数据量大约是 **55 GB**。

而经过 H.264 编码（CRF 23），同样的视频大约只有 **300-600 MB**，压缩比约为 **100:1**。

如果用 H.265 编码（同等画质），可以进一步压缩到 **200-400 MB**，比 H.264 再节省约 40-50%。

如果用 AV1 编码（同等画质），可能只需要 **150-350 MB**，比 H.264 节省约 50-60%。

这就是编解码器的力量——在不明显损失画质的前提下，把文件压缩到原来的 1/100。

## 5.2 有损压缩 vs 无损压缩

**无损压缩（Lossless）**

压缩后的数据可以完全还原为原始数据，没有任何信息丢失。类似于把文本文件压缩成 ZIP。

- 视频领域：FFV1、HuffYUV、Ut Video
- 压缩比：通常只有 2:1 到 4:1（效果有限）
- 用途：视频编辑中间素材、医学影像、科学记录

**有损压缩（Lossy）**

压缩过程中会丢弃一些人眼/人耳不敏感的信息，无法完全还原。但在合理的参数下，人眼几乎看不出差异。

- 视频领域：H.264、H.265、VP9、AV1
- 压缩比：可达 100:1 甚至更高
- 用途：几乎所有消费级视频（YouTube、Netflix、蓝光光盘）

本教程主要讨论有损压缩，因为它是 99% 的实际使用场景。

## 5.3 视频编解码器全景

**H.264 / AVC（Advanced Video Coding）**

- **发布年份**：2003 年
- **当前地位**：使用最广泛的视频编码标准，几乎所有设备和浏览器都支持
- **编码器实现**：libx264（软件编码，质量最佳）、NVENC（NVIDIA 硬件编码）、QSV（Intel 硬件编码）
- **优势**：兼容性无敌，编码速度合理，质量良好
- **劣势**：压缩效率不如新一代编码器（H.265、AV1）
- **FFmpeg 中使用**：

```bash
# 使用 libx264 软件编码（推荐，质量最好）
ffmpeg -i input.mp4 -c:v libx264 -crf 23 -preset medium output.mp4

# 使用 NVIDIA 硬件编码（速度快，质量略低于软件编码）
ffmpeg -i input.mp4 -c:v h264_nvenc -cq 23 output.mp4
```

**H.265 / HEVC（High Efficiency Video Coding）**

- **发布年份**：2013 年
- **当前地位**：H.264 的继任者，压缩效率提升约 50%，但专利情况复杂
- **编码器实现**：libx265（软件编码）、hevc_nvenc（NVIDIA 硬件编码）
- **优势**：同画质下文件比 H.264 小 40-50%，特别适合 4K 视频
- **劣势**：专利费问题导致部分浏览器和平台不支持；编码速度比 libx264 慢约 3-5 倍
- **FFmpeg 中使用**：

```bash
# 使用 libx265 编码
ffmpeg -i input.mp4 -c:v libx265 -crf 28 -preset medium output.mp4

# 注意：HEVC 的 CRF 28 ≈ H.264 的 CRF 23（同等画质）
# HEVC 的 CRF 默认值是 28，而 H.264 的默认值是 23
```

> **CRF 数值在不同编码器之间不可直接比较！** libx264 的 CRF 23 和 libx265 的 CRF 28 大致代表相同的视觉质量。这是因为两个编码器的 CRF 标尺不同。

**VP9**

- **发布年份**：2013 年
- **开发者**：Google（完全开源免专利费）
- **当前地位**：YouTube 的主要编码格式，WebM 容器的标准视频编码
- **编码器实现**：libvpx-vp9
- **优势**：开源免费，压缩效率接近 H.265，Web 浏览器支持良好
- **劣势**：编码速度比 H.264 慢约 2-3 倍；Apple 生态支持有限
- **FFmpeg 中使用**：

```bash
# VP9 使用 CRF 模式（需要同时设置 -b:v 0 来启用纯 CRF 模式）
ffmpeg -i input.mp4 -c:v libvpx-vp9 -crf 30 -b:v 0 output.webm

# VP9 的两遍编码（质量更好，但需要编码两次）
ffmpeg -i input.mp4 -c:v libvpx-vp9 -b:v 2M -pass 1 -an -f null /dev/null
ffmpeg -i input.mp4 -c:v libvpx-vp9 -b:v 2M -pass 2 -c:a libopus output.webm
```

> **关于 /dev/null**：Windows 用户需要将 `/dev/null` 替换为 `NUL`。

**AV1（AOMedia Video 1）**

- **发布年份**：2018 年
- **开发者**：AOMedia 联盟（包括 Google、Netflix、Microsoft、Apple 等巨头）
- **当前地位**：新一代编码标准，被视为 H.265 和 VP9 的共同继任者
- **编码器实现**：libaom-av1（官方参考编码器）、SVT-AV1（Intel 开发，速度快很多）、libdav1d（仅解码器）
- **优势**：开源免费，压缩效率比 H.265 和 VP9 再提升约 20-30%
- **劣势**：编码速度非常慢（libaom-av1 可能慢 10-50 倍），硬件解码支持仍在普及中
- **FFmpeg 中使用**：

```bash
# 使用 libaom-av1（质量最佳但极慢）
ffmpeg -i input.mp4 -c:v libaom-av1 -crf 30 -b:v 0 output.mkv

# 使用 SVT-AV1（速度快得多，质量略低，更实用）
ffmpeg -i input.mp4 -c:v libsvtav1 -crf 30 output.mkv
```

**四种编码器的实际对比（1080p 10 分钟视频，近似值）：**

| 编码器 | CRF 值 | 文件大小 | 编码时间 | 兼容性 |
| -------- | -------- | --------- | --------- | -------- |
| libx264 | 23 | ~400 MB | ~5 分钟 | 几乎 100% |
| libx265 | 28 | ~250 MB | ~20 分钟 | ~85% |
| libvpx-vp9 | 30 | ~280 MB | ~15 分钟 | Web + Android |
| libsvtav1 | 30 | ~220 MB | ~30 分钟 | ~60%（增长中） |

> **注意**：编码时间基于中端 CPU（如 i5-12400），实际时间因硬件和视频内容差异较大。上表仅供量级参考。

## 5.4 音频编解码器全景

**AAC（Advanced Audio Coding）**

- 当前使用最广泛的有损音频编码格式
- 是 MP3 的继任者，同码率下音质更好
- 几乎所有设备和平台都支持
- 常用码率：128kbps（良好立体声）、192kbps（高质量）、320kbps（接近透明）

```bash
ffmpeg -i input.mp4 -c:a aac -b:a 192k output.mp4
```

**MP3（MPEG-1 Audio Layer III）**

- 曾经的音乐之王，如今已逐渐被 AAC 和 Opus 取代
- 专利已于 2017 年过期，完全免费
- 兼容性极好，但同码率下音质不如 AAC

```bash
ffmpeg -i input.wav -c:a libmp3lame -b:a 192k output.mp3
```

**Opus**

- 由 Xiph.Org 基金会开发的开源音频编码器
- 在低码率（32-96kbps）下表现极佳，是语音和低带宽场景的首选
- YouTube、WhatsApp、Discord 都在使用
- WebM 容器的标准音频编码

```bash
ffmpeg -i input.mp4 -c:a libopus -b:a 128k output.webm
```

**FLAC（Free Lossless Audio Codec）**

- 无损音频压缩，压缩比约 2:1
- 音乐发烧友的最爱
- 不适用于流媒体（文件太大），适合音乐存档

```bash
ffmpeg -i input.wav -c:a flac output.flac
```

**Vorbis**

- Xiph.Org 基金会开发的开源有损音频编码
- 是 Opus 的前身，现在已被 Opus 全面超越
- 主要在 Ogg 容器中使用

```bash
ffmpeg -i input.mp4 -c:a libvorbis -b:a 192k output.ogg
```

**音频编码器推荐：**

| 场景 | 推荐编码器 | 推荐码率 |
| ------ | ----------- | --------- |
| 通用兼容性 | AAC | 192kbps |
| 网页/WebM | Opus | 128kbps |
| 低带宽语音 | Opus | 32-64kbps |
| 音乐存档 | FLAC | 无损 |
| 老旧设备 | MP3 | 192-320kbps |

## 5.5 硬件编码 vs 软件编码

**软件编码**是指用 CPU 来计算编码。优点是质量最佳（编码器实现更精细），缺点是速度慢、CPU 占用高。

**硬件编码**是指利用 GPU 或专用芯片来加速编码。优点是速度极快（可达软件编码的 10-20 倍），缺点是质量略低（同等码率下）。

**三大硬件编码平台：**

| 平台 | FFmpeg 编码器名 | 支持的编码格式 |
| ------ | ---------------- | -------------- |
| NVIDIA GPU（NVENC） | h264_nvenc, hevc_nvenc, av1_nvenc | H.264, H.265, AV1 |
| Intel（QSV / Quick Sync） | h264_qsv, hevc_qsv, av1_qsv | H.264, H.265, AV1 |
| AMD（AMF / VCE） | h264_amf, hevc_amf, av1_amf | H.264, H.265, AV1 |

```bash
# 检查你的系统支持哪些硬件编码器
ffmpeg -encoders | grep nvenc    # NVIDIA
ffmpeg -encoders | grep qsv      # Intel
ffmpeg -encoders | grep amf      # AMD

# 使用 NVIDIA NVENC 编码 H.264（速度极快）
ffmpeg -i input.mp4 -c:v h264_nvenc -cq 23 -preset p5 output.mp4

# 使用 Intel QSV 编码 H.264
ffmpeg -i input.mp4 -c:v h264_qsv -global_quality 23 output.mp4

# 使用 AMD AMF 编码 H.264
ffmpeg -i input.mp4 -c:v h264_amf -quality quality output.mp4
```

**什么时候用硬件编码？**

- 实时录制 / 直播推流（速度是硬需求）
- 批量转码大量视频（节省时间）
- 日常使用中快速处理（不追求极致画质）

**什么时候用软件编码？**

- 最终输出的高质量视频（存档、发布）
- 对画质有严格要求的场景
- 需要精确控制编码参数的场景

## 5.6 编码器的 Preset 概念

大多数编码器都有一个"预设（preset）"参数，用来控制编码速度与质量之间的权衡。

**libx264 的 preset（从快到慢）：**

```
ultrafast → superfast → veryfast → faster → fast → medium → slow → slower → veryslow → placebo
```

- **越快**：编码速度越快，但压缩效率越低（同质量下文件更大）
- **越慢**：编码速度越慢，但压缩效率越高（同质量下文件更小）
- **默认值**：`medium`
- **placebo**：几乎不会带来实际改善，只是让编码慢很多。官方不推荐使用。

```bash
# 快速编码（适合快速预览或批量处理）
ffmpeg -i input.mp4 -c:v libx264 -preset veryfast -crf 23 output.mp4

# 高质量编码（适合最终输出，文件更小）
ffmpeg -i input.mp4 -c:v libx264 -preset slow -crf 23 output.mp4

# 直播推流（需要极快速度）
ffmpeg -i input.mp4 -c:v libx264 -preset ultrafast -tune zerolatency output.mp4
```

**preset 对编码时间和文件大小的影响（近似值，1080p 视频）：**

| Preset | 编码时间（相对） | 文件大小（相对） |
| -------- | --------------- | --------------- |
| ultrafast | 1x | 1.8x |
| veryfast | 1.5x | 1.5x |
| fast | 2x | 1.2x |
| medium（默认） | 3x | 1.0x |
| slow | 5x | 0.9x |
| veryslow | 10x | 0.85x |

> **推荐策略**：日常使用用 `medium`（默认），追求小文件用 `slow`，追求速度用 `veryfast`。除非你有一整晚的时间，否则不要用 `veryslow`。

## 本章小结

- 未压缩的 1080p 视频约 55GB/10分钟，编码后可压缩到几百 MB，压缩比约 100:1
- 有损压缩通过丢弃人眼不敏感的信息来实现高压缩比
- H.264（libx264）是当前最通用的视频编码器，兼容性最好
- H.265（libx265）压缩效率比 H.264 高约 50%，但专利复杂，编码较慢
- VP9 是 Google 的开源替代方案，压缩效率接近 H.265
- AV1 是未来之星，压缩效率最高，但编码速度仍然很慢
- 硬件编码（NVENC/QSV/AMF）速度极快，适合实时场景；软件编码质量更好，适合最终输出
- preset 控制速度与质量的权衡：默认 medium，追求速度用 veryfast，追求小文件用 slow
- 音频推荐 AAC（通用）或 Opus（Web/低码率）
