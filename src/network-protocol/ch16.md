## 16.1 设计动机：从 HOSTS.TXT 到分布式数据库

计算机通信靠 IP 地址，但人类记不住 `142.250.80.46`，更记不住 IPv6 地址。我们需要把人类友好的名字（`google.com`）映射到机器需要的地址（`142.250.80.46`）。

ARPANET 时代的方案是一个文本文件 `HOSTS.TXT`——所有主机名与 IP 的映射存在里面，每个节点定期下载最新副本。网络扩展到成千上万台主机后，这个中心化文件成了瓶颈：每次更新都要同步全网，名字冲突家常便饭。

1983 年，Paul Mockapetris 设计了 DNS（Domain Name System），用**分布式数据库**替代中心化文件——一个全球性、去中心化、层次化的命名系统，每天处理数万亿次查询。它的核心思想与第2章的分层一脉相承：把一个大问题切成很多小问题，每个小问题只归一个机构管。

## 16.2 域名空间：一棵倒置的树

```
                        . (根域)
                       /|\
                     /  |  \
                  com  org  net  cn  edu ...  (顶级域 TLD)
                  /     |     \
              google  wiki  cloudflare  ...  (二级域 SLD)
               / \
           www  mail  api  ...  (子域名)
```

- **根域（Root）**：用 `.` 表示，通常省略。完整域名其实写作 `www.example.com.`——最后那个点就是根。
- **顶级域（TLD）**：`.com`、`.org`、`.net`、`.cn`、`.edu` 等，分通用顶级域（gTLD）和国家代码顶级域（ccTLD），近年新增上千个如 `.app`、`.dev`。
- **二级域（SLD）**：`example.com` 中的 `example`——你注册域名时买的就是这一段。
- **子域名**：`www.example.com`、`mail.example.com`——域主可自由创建。

这棵树的每个节点由不同机构管理：根服务器管 TLD 的指路，注册局管 SLD，域主管自己的子域——权责清晰，没有任何一方需要知道全貌。

## 16.3 查询过程：递归与迭代

在浏览器输入 `www.example.com` 后发生什么？

**1. 本地缓存检查**：浏览器先查自己的缓存（`chrome://net-internals/#dns` 可看），再查操作系统缓存。

**2. 交给本地解析器（Stub Resolver）**：缓存全空，操作系统把查询发给配置的 DNS 服务器——通常是 ISP 的递归解析器，或你手动配置的 `8.8.8.8`、`1.1.1.1`。

**3. 递归查询**：客户端对解析器说：「帮我查到 IP 为止，查不到就报错，别让我自己跑。」——甩手掌柜模式。

**4. 迭代查询**：解析器自己跑腿的过程：

```
解析器 → 根服务器："www.example.com 在哪？"
根服务器 → 解析器："我不管 .com 的事，去找 .com 的服务器：192.5.6.30, ..."

解析器 → .com TLD 服务器："www.example.com 在哪？"
TLD 服务器 → 解析器："example.com 的权威服务器是 ns1.example.com (93.184.216.34)"

解析器 → 权威服务器："www.example.com 的 IP 是什么？"
权威服务器 → 解析器："www.example.com → 93.184.216.34, TTL=3600"

解析器 → 客户端："93.184.216.34"
```

「先猜再读」第一问的答案：不会直接到根。根服务器从不直接面对普通用户，它只回答「.com 在哪」这类指路问题。解析器把结果缓存起来（时长由 TTL 决定），下次同域名的查询就不再跑腿——这正是下一节缓存体系的源头。

> [!TIP] dig 是 DNS 的显微镜
> `dig www.example.com` 看一次查询的完整报文；`dig +trace www.example.com` 从根开始重演整条迭代路径；`dig @8.8.8.8 www.example.com` 指定解析器对比结果。看 TTL、验证缓存，命令行比图形界面快得多。

## 16.4 报文格式与记录类型

DNS 查询和响应共用一套报文格式：

```
DNS Header (12 bytes):
  Transaction ID: 0xa3f2    ← 请求与响应的匹配标识
  Flags: 0x0100             ← 标准查询，期望递归
  Questions: 1
  Answer RRs: 0             ← 响应时为答案数量

Question Section:
  Name: www.example.com
  Type: A (1)               ← 查询类型
  Class: IN (1)             ← 互联网类（几乎总是 IN）

Response Answer Section (响应时):
  Name: www.example.com
  Type: A (1)
  TTL: 3600                  ← 缓存秒数
  Data Length: 4
  Address: 93.184.216.34    ← 解析结果
```

注意域名不是存成字符串，而是**长度前缀编码**：每个标签前加一个长度字节，`\x00` 结尾——`www.example.com` 编码为 `\x03www\x07example\x03com\x00`。

Flags 字段里的关键位：

- **QR**：0 查询 / 1 响应。
- **AA**：Authoritative Answer，权威回答。
- **TC**：Truncated，报文超长被截断——「先猜再读」第二问的答案：DNS 查询-响应是一问一答的短交互，UDP 足矣（7.1 的场景判断在这里具象化）；万一响应超过 512 字节，TC 位置 1，客户端改用 TCP 重发同一查询。UDP 快、TCP 兜底，各干各的活。
- **RD / RA**：期望递归 / 服务器支持递归。
- **RCODE**：0 成功，3 = NXDOMAIN（域名不存在）。

记录类型决定「问的是什么」：

- **A**：域名 → IPv4。`www.example.com → 93.184.216.34`
- **AAAA**：域名 → IPv6（读作 Quad-A）。
- **CNAME**：域名 → 另一个域名（别名），解析器接着追。
- **MX**：邮件服务器，带优先级（越小越优先）。`example.com → 10 mail.example.com`
- **TXT**：任意文本——SPF 防伪造、域名所有权验证都靠它。
- **NS**：域的权威 DNS 服务器是谁。
- **SOA**：域的权威元信息（主服务器、序列号、刷新间隔），每域一条。
- **SRV**：特定服务的地址（优先级、权重、端口、目标）。

## 16.5 DNS 缓存：TTL 的权衡

**TTL（Time To Live）**是记录的保质期：3600 表示可缓存 1 小时。「先猜再读」第三问的答案：把 TTL 设成 10 秒并不能保证万无一失——浏览器、操作系统、企业网关都可能不严格遵守 TTL（有的浏览器固定缓存 60 秒，有的中间盒无视 TTL 强行缓存），所以迁移 IP 的正确姿势是提前把 TTL 调低、等旧 TTL 走完、再切换。

TTL 的工程权衡：

- **太长**（1 天）：查询少、延迟低，但变更生效慢——换 IP 后用户可能一整天访问旧地址。
- **太短**（60 秒）：变更快生效，但查询量暴增、延迟上升。

常见做法：平时 3600，计划迁移前把 TTL 缩到 300，迁移完成后调回来。

缓存分布在多个层次，逐层命中逐层省时：

1. 浏览器缓存
2. 操作系统缓存（Windows DNS Client、systemd-resolved）
3. 递归解析器缓存（ISP、8.8.8.8、1.1.1.1）
4. CDN 边缘节点的 DNS 缓存——第23章会看到，CDN 的调度本身就靠 DNS 记录的 TTL 与解析结果来实现。

## 16.6 DNS 安全：劫持、投毒与 DNSSEC

**DNS 劫持**：攻击者篡改查询结果，把用户导向假网站。2014 年一些 ISP 曾把不存在的域名（NXDOMAIN）劫持到自己的广告页。

**缓存投毒（Cache Poisoning）**：向递归解析器注入虚假记录，成功则所有使用该解析器的用户都被误导。2008 年 Dan Kaminsky 发现的著名漏洞就利用了 Transaction ID 只有 16 位（65536 种可能）这一点——攻击者海量伪造响应来猜中。修复方案是随机化源端口，给响应匹配增加熵源（12.4 的五元组在这里帮了忙：源端口一随机，五元组就更难撞对）。

**DNSSEC**：给 DNS 记录加数字签名——权威服务器用私钥签，解析器用公钥验，签名不匹配即知被篡改。思路与 15.4 的证书链一致，但信任锚换成了 DNS 层级自身的委托链。部署缓慢：报文变大、延迟增加、配置复杂。

## 16.7 DoH 与 DoT：加密 DNS 的争议

传统 DNS 走 UDP 53 明文——你的 ISP、咖啡店 Wi-Fi 的管理员都能看到你在查什么域名。第15章的 TLS 在这里派上了第二用场：

- **DoH（DNS over HTTPS）**：查询封装进 HTTPS，走 443 端口。对中间人来说就是一次普通 HTTPS 请求，Chrome 和 Firefox 已默认启用。
- **DoT（DNS over TLS）**：查询外包一层 TLS，走专用 853 端口。比 DoH 轻量（无 HTTP 开销），但流量特征明显——网管看到 853 就知道是 DNS。

争议在于：DoH 绕过了网络管理员的 DNS 管控。企业 IT 依赖 DNS 过滤拦截恶意站点，DoH 让策略失效；隐私倡导者则认为用户有权加密自己的查询。这是典型的隐私与管控博弈——技术中立，立场在人与人之间。

## 16.8 编程实践：用 Python dnspython 库做 DNS 查询

```python
import dns.resolver
import dns.message
import dns.query
import struct

def demo_dns_query():
    """演示各种记录类型的查询"""
    domain = "example.com"

    for rtype in ('A', 'AAAA', 'MX', 'TXT', 'NS'):
        print(f"=== {rtype} Records for {domain} ===")
        try:
            answers = dns.resolver.resolve(domain, rtype)
            for rdata in answers:
                if rtype == 'MX':
                    print(f"  Priority: {rdata.preference}, Server: {rdata.exchange}")
                elif rtype in ('A', 'AAAA'):
                    print(f"  {rdata.address}  (TTL: {answers.rrset.ttl})")
                else:
                    print(f"  {rdata.to_text()}")
        except dns.resolver.NoAnswer:
            print("  (none)")

    # 手动构建 DNS 查询报文发送到指定服务器
    print("=== Manual DNS Query to 8.8.8.8 ===")
    q = dns.message.make_query(domain, 'A')
    response = dns.query.udp(q, '8.8.8.8', timeout=5)
    print(f"  Response code: {response.rcode()}")
    print(f"  Flags: QR={response.flags & dns.flags.QR}, "
          f"AA={response.flags & dns.flags.AA}")
    for answer in response.answer:
        for item in answer.items:
            print(f"  Answer: {item}  (TTL: {answer.ttl})")

def parse_dns_response_raw(data: bytes):
    """手动解析 DNS 响应报文（教学目的）"""
    # Header：12 字节，6 个 16 位字段
    tx_id, flags, qdcount, ancount, nscount, arcount = struct.unpack('!HHHHHH', data[:12])
    print(f"Transaction ID: 0x{tx_id:04x}")
    print(f"Flags: 0x{flags:04x}")
    print(f"Questions: {qdcount}, Answers: {ancount}")

    # Question Section：长度前缀编码的域名
    offset = 12
    for _ in range(qdcount):
        labels = []
        while data[offset] != 0:
            length = data[offset]
            offset += 1
            labels.append(data[offset:offset+length].decode())
            offset += length
        offset += 1  # 跳过结尾 0x00
        qtype, qclass = struct.unpack('!HH', data[offset:offset+4])
        offset += 4
        print(f"Question: {'.'.join(labels)} Type:{qtype} Class:{qclass}")

demo_dns_query()
```

安装依赖：`pip install dnspython`。手动解析那段代码的价值在于：长度前缀编码不再是文档里的一句话，而是你亲手逐字节走过的偏移量。

## 16.9 抓包实践：捕获 DNS 查询和响应

Wireshark 过滤 `dns`，浏览器访问一个网站：

```
DNS Query:
  Transaction ID: 0xa3f2
  Flags: 0x0100 (Standard query, Recursion desired)
  Queries:
    www.example.com: type A, class IN

DNS Response:
  Transaction ID: 0xa3f2
  Flags: 0x8180 (Response, Recursion desired, Recursion available)
  Answer RRs: 2
  Answers:
    www.example.com: type CNAME, cname example.com   (TTL: 300)
    example.com: type A, addr 93.184.216.34           (TTL: 3600)
```

注意这条 **CNAME 链**：`www.example.com` 先解析为 `example.com`，再解析出 IP。递归解析器把两步结果一起返回——少一次往返，这就是 14.1 强缓存之外 DNS 层自己的「省 RTT」哲学。

在 Wireshark 的 `Domain Name System` 树里逐字段核对 16.4 的格式。特别留意 `Time` 列：命中缓存的查询 10ms 以内，触发完整迭代（根 → TLD → 权威）则可能 200-500ms——这就是缓存层次存在的理由。想看迭代全过程，用 16.3 TIP 的 `dig +trace` 配合抓包。

## 本章小结

- DNS 的本质是全球分布式数据库：HOSTS.TXT 的失败证明中心化命名撑不起互联网，分而治之才是出路。
- 域名空间是倒置的树：根域 → TLD → SLD → 子域名，每层归不同机构管，权责清晰。
- 客户端只发递归查询（甩手掌柜），解析器靠迭代查询逐级问路：根只指路、TLD 指权威、权威给答案。
- 报文 12 字节头 + Question/Answer 区；域名用长度前缀编码而非字符串，Transaction ID 匹配请求与响应。
- 记录类型各司其职：A/AAAA 查地址、CNAME 起别名、MX 找邮局、TXT 存证明、NS/SOA 定权威。
- DNS 默认 UDP 53（一问一答短交互），超长时 TC 位置位改走 TCP——UDP 快、TCP 兜底。
- TTL 是新鲜度与变更速度的跺跷板，且中间层不一定严格遵守——迁移 IP 要提前降 TTL 而不是赌 10 秒生效。
- 威胁与对策：劫持/投毒靠源端口随机化与 DNSSEC 签名缓解，隐私问题由 DoH/DoT 用 TLS 解决——管控与隐私的博弈仍在继续。
