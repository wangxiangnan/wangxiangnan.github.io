# 第23章：CDN、Anycast 与大规模网络协议

## CDN 的工作原理

CDN（Content Delivery Network，内容分发网络）的核心思想很简单：**把内容搬到离用户最近的地方**。

当你在北京访问 `cdn.example.com/video.mp4`，如果没有 CDN，请求要跨洋到达美国服务器，延迟可能 200ms+。有了 CDN，请求被导向北京的边缘节点，延迟降到 10ms。

CDN 的工作流程：

1. **用户请求** `cdn.example.com/image.jpg`
2. **DNS 解析**返回离用户最近的边缘节点 IP（如北京节点 `1.2.3.4`）
3. **边缘节点检查缓存**：如果有 → 直接返回（缓存命中）；如果没有 → 向源服务器请求（回源）
4. **回源获取**后缓存到边缘节点，再返回给用户

缓存策略是 CDN 的核心学问：

- **TTL（Time-To-Live）**：资源在边缘节点缓存多长时间
- **Cache-Control 头部**：`max-age`、`no-cache`、`must-revalidate`
- **缓存键（Cache Key）**：通常由 URL + 部分请求头组成
- **缓存预热**：提前将热门内容推送到边缘节点

## CDN 的 DNS 调度：如何把你引到最近的节点

CDN 利用 DNS 的地理感知能力来做调度：

```
用户（北京） → 本地 DNS → CDN 的权威 DNS
                                ↓
                     根据 DNS 请求来源 IP 判断地理位置
                                ↓
                     返回北京边缘节点的 IP: 1.2.3.4

用户（上海） → 本地 DNS → CDN 的权威 DNS
                                ↓
                     返回上海边缘节点的 IP: 5.6.7.8
```

但这种方式有局限：它基于**DNS 服务器的位置**而非用户的真实位置。如果北京用户用了 Google DNS（8.8.8.8），CDN 可能把他导向美国节点。更精确的方式是 **EDNS Client Subnet**——DNS 请求中携带用户子网信息。

## Anycast：同一个 IP 地址，多个地理位置

Anycast 是 IP 层的一个"魔法"：**多个地理位置的服务器使用同一个 IP 地址**。BGP 路由协议会自动把流量导向"最近"的那个节点。

```
北京服务器宣告: 203.0.113.1/32 (AS 路径较短)
上海服务器宣告: 203.0.113.1/32 (AS 路径较短)
广州服务器宣告: 203.0.113.1/32 (AS 路径较短)

北京用户请求 203.0.113.1 → 路由到北京服务器
上海用户请求 203.0.113.1 → 路由到上海服务器
```

Anycast 的优势：

- 无需 DNS 调度（IP 层自动路由）
- 天然抗 DDoS（流量被分散到多个节点）
- 故障转移自动发生（一个节点挂了，BGP 路由自动切到其他节点）

Cloudflare、Google DNS（8.8.8.8）都大量使用 Anycast。

## BGP 简介：自治系统之间如何交换路由

互联网的骨架不是某一家公司的网络，而是数万个**自治系统（AS，Autonomous System）** 互联而成的。每个 AS 是一个独立管理的网络（如中国电信 AS4134、Google AS15169），它们通过 **BGP（Border Gateway Protocol）** 交换路由信息。

BGP 的核心概念：

- **AS Path**：路由经过的 AS 序列。如 `AS100 → AS200 → AS300` 表示要到达目标网络，需要经过这三个 AS。
- **路由策略**：每个 AS 可以决定接受、拒绝、修改、优选哪些路由。
- **对等关系（Peering）**：AS 之间的互联关系，分为 Transit（付费转接）和 Peering（免费互换）。

BGP 是**路径矢量协议**，不像 OSPF 那样基于最短路径计算。BGP 的路由决策受商业关系影响——有时候"技术上最优"的路径并不是实际使用的路径，因为那条路径要付更多转接费。

## BGP 劫持与安全

BGP 的设计基于**信任**：如果你的 AS 宣告"我能到达某个前缀"，其他 AS 默认相信。这导致了 **BGP 劫持**：

2018 年，某 AS 错误地宣告了 Google 的 `216.58.192.0/19` 前缀，导致大量 Google 流量被导向了错误的网络。

防御手段：

- **RPKI（Resource Public Key Infrastructure）**：用密码学证明某个 AS 有权宣告某个 IP 前缀。类似 DNSSEC 之于 DNS。
- **BGPsec**：对 BGP 路由更新做数字签名，防止伪造。

## 大规模负载均衡：L4 vs L7 负载均衡

当流量大到单台服务器扛不住，就需要负载均衡器分发请求：

**L4 负载均衡（传输层）：**

- 工作在 TCP/UDP 层，只看 IP 和端口
- 根据源 IP 哈希或轮询分配连接
- 性能极高（不需要解析 HTTP）
- 但无法基于 URL、Header 做智能分发

**L7 负载均衡（应用层）：**

- 工作在 HTTP 层，能理解请求内容
- 可以根据 URL 路径、Cookie、Header 分发请求
- 支持 A/B 测试、灰度发布等高级功能
- 性能开销大于 L4

```
用户请求 → L4 负载均衡器（快速分发到后端集群）
         → L7 负载均衡器（智能路由到具体服务）
         → 应用服务器
```

**一致性哈希（Consistent Hashing）** 是负载均衡的经典算法。它的精妙之处在于：增加或删除一台服务器时，只需要迁移 `1/N` 的数据（N 是服务器数量），而不是所有数据重新分配。

## HTTP 代理与反向代理：Nginx 的工作原理

**正向代理**：客户端知道代理的存在，通过代理访问目标服务器（如 VPN、翻墙工具）。
**反向代理**：客户端不知道代理的存在，以为自己在直接访问目标服务器。

Nginx 作为反向代理的典型工作流：

```
用户 → Nginx (反向代理) → 后端 App Server 1
                        → 后端 App Server 2
                        → 后端 App Server 3

Nginx 做的事：
1. 接收用户请求
2. 根据 URL 路径决定转发到哪个后端
3. 转发请求，接收后端响应
4. 返回响应给用户（可以加上缓存、压缩、安全头部等）
```

## 编程实践：Python 实现简易反向代理

```python
"""
简易反向代理服务器
根据请求路径分发到不同的后端服务
运行: python reverse_proxy.py
测试: curl http://localhost:8080/api/users
"""
import asyncio
from aiohttp import web, ClientSession

# 后端服务配置
BACKENDS = {
    "/api/users": "http://localhost:3001",
    "/api/orders": "http://localhost:3002",
    "/static": "http://localhost:3003",
}

async def proxy_handler(request: web.Request) -> web.Response:
    """将请求转发到对应的后端服务"""
    path = request.path

    # 匹配后端服务
    backend_url = None
    for prefix, url in BACKENDS.items():
        if path.startswith(prefix):
            backend_url = url
            break

    if not backend_url:
        return web.Response(status=404, text="No backend found for this path")

    # 构建转发请求
    target_url = f"{backend_url}{path}"
    headers = {k: v for k, v in request.headers.items()
               if k.lower() not in ('host', 'content-length')}

    async with ClientSession() as session:
        try:
            async with session.request(
                method=request.method,
                url=target_url,
                headers=headers,
                data=await request.read(),
                allow_redirects=False,
            ) as resp:
                body = await resp.read()
                response = web.Response(
                    status=resp.status,
                    body=body,
                    headers={k: v for k, v in resp.headers.items()
                             if k.lower() not in ('transfer-encoding',)},
                )
                # 添加代理标识头部
                response.headers['X-Proxy'] = 'MiniProxy/1.0'
                response.headers['X-Backend'] = backend_url
                return response
        except Exception as e:
            return web.Response(status=502, text=f"Backend error: {e}")

app = web.Application()
app.router.add_route('*', '/{path_info:.*}', proxy_handler)

if __name__ == '__main__':
    print("Reverse proxy running on http://localhost:8080")
    web.run_app(app, host='0.0.0.0', port=8080)
```

## 抓包实践：追踪 CDN 路径

```bash
# 使用 curl 观察 CDN 响应头部
curl -sI https://www.cloudflare.com/cdn-cgi/trace

# 更完整的头部信息
curl -sI https://cdnjs.cloudflare.com/ajax/libs/jquery/3.6.0/jquery.min.js
```

典型的 CDN 响应头部：

```
cf-cache-status: HIT           ← Cloudflare 缓存命中
cf-ray: 7a3b2c1d-FRA          ← 请求处理的边缘节点标识
server: cloudflare             ← CDN 提供商
x-cache: Hit from cloudfront   ← AWS CloudFront 的缓存状态
via: 1.1 varnish               ← 经过的代理/CDN 节点
age: 342                       ← 缓存已存在 342 秒
```

`cf-ray` 的 `-FRA` 表示请求被法兰克福节点处理，`-LAX` 表示洛杉矶。你可以通过这个标识了解你的请求被路由到了哪个边缘节点。
