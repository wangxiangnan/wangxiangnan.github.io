## 15.1 性能优化：先测量，再优化

Monorepo 的耗时通常分布在四个环节：**依赖安装、任务执行、缓存命中、镜像构建**。凭直觉优化，很容易花一周把构建从 8 秒压到 6 秒，却没注意到 CI 里 `pnpm install` 要跑 3 分钟。

### 15.1.1 先用 Turborepo 的三件工具定位瓶颈

```bash
# 1. 汇总本次运行：每个任务耗时、命中情况、读取了哪些输入
pnpm turbo run build --summarize
# 结果写入 .turbo/runs/<run-id>.json

# 2. 生成任务图，确认依赖顺序符合预期
pnpm turbo run build --graph=graph.svg

# 3. 只推演不执行：查看每个任务的 hash、inputs、outputs、依赖
pnpm turbo run build --dry=json > turbo-plan.json

# 4. 生成性能火焰图（Chrome Tracing 格式）
pnpm turbo run build --profile
```

配合 Ch11 讲过的 `--output-logs=hash-only`，可以快速看出哪些包在反复 cache miss。

不同症状对应的排查方向：

| 症状 | 先检查 |
| ---- | ------ |
| CI 总时长高，安装占一半 | pnpm store 缓存、lockfile 是否变化、是否用了 `turbo prune` |
| 改一个包却全量重跑 | `--affected` 的 Git 历史是否完整、`globalDependencies` 是否过宽 |
| 命中缓存但产物不对 | `env` / `inputs` 是否漏声明（见 15.2 陷阱 4） |
| 镜像构建慢 | Dockerfile 层顺序、构建上下文大小、BuildKit 缓存是否命中 |
| 本地 `pnpm dev` 慢 | `dev` 是否误加了 `cache`、是否重复构建上游 |

> **不要用 `time pnpm build` 作为唯一指标**。一次运行包含安装、调度、构建、测试，只有 `--summarize` 能告诉你时间具体花在哪个任务、哪个包上。

### 15.1.2 选择性执行：CI 里优先用 `--affected`

`--affected` 等价于 `--filter=...[main...HEAD]`：找出当前分支相对基线变更的包，以及**依赖这些包的所有下游包**。

```bash
# CI（PR）中最常用的写法
pnpm turbo run lint typecheck test build --affected

# 本地只想跑 shared 及其下游
pnpm turbo run build --filter=...@taskflow/shared

# 只想跑 web 及其依赖
pnpm turbo run build --filter=@taskflow/web...
```

两个前提：

- **Git 历史必须足够**。浅克隆会让所有包都被视为"已变更"，`--affected` 退化成全量。CI 里需要 `fetch-depth: 0`，或者至少 `--filter=blob:none --depth=0`。
- **基线和头必须存在**。`--affected` 默认比较 `main...HEAD`；如果团队的基线不是 `main`，用 `TURBO_SCM_BASE` 覆盖，而不是硬编码 `[origin/main]`。

```bash
TURBO_SCM_BASE=develop pnpm turbo run build --affected
```

`--affected` 默认按**包**粒度判断：包内任何一个文件变化，该包的所有任务都会被选中。如果希望按任务的 `inputs` 精确判断，可以开启 `futureFlags.affectedUsingTaskInputs`（Ch11 有说明）。对本项目这种规模，包粒度已经足够。

### 15.1.3 缓存配置的最终形态

把 Ch10、Ch12 的增量配置合并后，根目录的 `turbo.json` 应该长这样：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "globalDependencies": [
    "packages/tsconfig/**",
    "packages/eslint-config/**",
    "vitest.shared.ts"
  ],
  "globalEnv": ["CI", "NODE_ENV"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": [
        "src/**",
        "prisma/**",
        "prisma.config.ts",
        ".env*",
        "tsconfig.json",
        "package.json"
      ],
      "outputs": ["dist/**"],
      "env": ["VITE_APP_TITLE", "VITE_API_ORIGIN"]
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    },
    "lint": {
      "inputs": ["src/**", "tests/**", "eslint.config.js", "package.json"]
    },
    "lint:fix": {
      "cache": false
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json", "package.json"]
    },
    "test": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tests/**", "vitest.config.*", "package.json"]
    },
    "test:e2e": {
      "cache": false
    },
    "clean": {
      "cache": false
    }
  }
}
```

每个选择的理由：

- **`globalDependencies` 里放的是"配置包"和根目录共享测试配置**。它们不在任何一个应用的构建依赖图里，Turborepo 不会自动感知；不显式声明，改了 ESLint 规则或 tsconfig 基础配置后，旧缓存仍会被复用。代价是这些文件一变，所有任务都失效——对全局配置来说，这个代价是正确的。
- **`build.inputs` 包含 `.env*`**。Vite 在构建时把 `VITE_*` 静态替换进产物；`.env` 变了却不参与 hash，就会发布出带旧 API 地址的前端。`prisma/**` 和 `prisma.config.ts` 同理，Schema 改动必须让 database 重新构建。
- **`build.env` 显式列出 `VITE_*`**。Turborepo 会对 Vite 包自动推断 `VITE_*` 前缀，但显式写出来便于审查，也能覆盖自定义前缀的变量。
- **`lint` / `typecheck` 没有 `outputs`**。它们不产出文件，Turborepo 仍会缓存退出码和日志，命中时直接回放，不会真的执行 ESLint 或 tsc。
- **`test:e2e` 不缓存**。它依赖真实浏览器、固定端口和数据库状态，缓存收益低、误导性强。
- **`dev` 必须 `cache: false` + `persistent: true`**。长驻进程没有"完成"状态，缓存它没有意义。

> 如果你更习惯"默认包含包内所有文件，再排除少数"，可以用 `"inputs": ["$TURBO_DEFAULT$", "!src/**/*.test.ts"]`。本项目选择显式枚举，是为了让参与 hash 的文件一眼可见；两种写法没有对错，关键是不要漏掉会影响产物的文件。

### 15.1.4 增量编译：只在该用的地方用

Ch03 明确没有开启 `composite`：本项目的构建顺序由 Turborepo 的 `dependsOn: ["^build"]` 负责，缓存也由 Turborepo 管理，再叠加 Project References 只会让配置更复杂。

真正值得开启的是 `tsc` 层面的增量编译，主要受益者是 `apps/api` 和用 `tsc` 输出的 `packages/*`：

```json
{
  "extends": "@taskflow/tsconfig/base.json",
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "./dist/.tsbuildinfo",
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"]
}
```

两个细节：

- **`tsBuildInfoFile` 放在 `dist` 里**，因为 `dist/**` 是 `build` 的 `outputs`。放进输出目录，本地缓存和远程缓存都会连同 `.tsbuildinfo` 一起保存；放在包根目录却不在 `outputs` 里，缓存恢复后没有构建信息，下一次仍然全量编译，增量收益消失。
- **`incremental` 不替代 Turborepo 缓存**。前者加速同一次编译内部的重复工作，后者跨机器、跨分支复用整个任务的产物。两者叠加才有意义。

什么时候该考虑 Project References？当仓库没有打包器、所有包都由 `tsc --build` 串联，且类型检查时间占主导时。对 Vue + Vite + Express 的全栈项目，Ch06 已经给出结论：不需要。

### 15.1.5 安装层：pnpm 12 的配置都在 `pnpm-workspace.yaml`

pnpm 11 起，`.npmrc` 只保留 registry、认证、TLS、代理和本地地址；`node-linker`、`shamefully-hoist`、`network-concurrency` 这类设置写进 `.npmrc` 会被**静默忽略**。本项目的安装相关配置统一在 workspace 文件里：

```yaml
# pnpm-workspace.yaml（节选，完整版见 Ch02）
packages:
  - "apps/*"
  - "packages/*"

minimumReleaseAge: 1440        # 新包发布满 1 天才允许安装
blockExoticSubdeps: true       # 子依赖不能用 git/file 等奇异源
strictDepBuilds: true          # 未声明的构建脚本直接报错
verifyDepsBeforeRun: install   # 跑脚本前校验 node_modules 与 lockfile 一致

allowBuilds:
  esbuild: true                # esbuild 需要 postinstall 准备平台二进制

autoInstallPeers: false
strictPeerDependencies: true
```

几个常见误区：

- **`nodeLinker=hoisted` 不是"性能优化"**。它会把依赖摊平，破坏 pnpm 的严格隔离，让幽灵依赖重新出现。只有不兼容符号链接结构的老工具才需要它，而且应该配合 `publicHoistPattern` 精确放行，而不是全量摊平。
- **`minimumReleaseAge` 是供应链安全措施，不是安装速度措施**。紧急升级某个包时，用 `minimumReleaseAgeExclude` 单独放行，不要为了省事把整个策略关掉。
- **`networkConcurrency` 不是越大越好**。默认值已经能跑满带宽，调高往往只是让 registry 更容易限流。
- **版本统一交给 catalog**（Ch04）。把 Vue、Express、ESLint 等版本写在 `pnpm-workspace.yaml` 的 `catalog` / `catalogs` 里，各包用 `catalog:` 引用，升级时只改一处，lockfile 的变更也更集中。

在 Docker 里，安装层的优化思路不同：不要复制整个仓库再 `pnpm install`，而是先用 `turbo prune` 裁出目标应用及其依赖，再用裁剪后的 lockfile 安装（Ch14）。CI 里则交给 `pnpm/setup@v3` 的 `cache: true`，不要手写一套缓存路径。

## 15.2 常见陷阱清单

下面 10 个问题，几乎都能在真实项目里找到对应的事故。每条都给出**症状、成因、修复**，并尽量对应到本教程的具体配置。

### 陷阱 1：包之间循环依赖

**症状**：`turbo run build` 启动阶段直接报错，提示任务图存在环；或者某个包永远构建不完。

**成因**：两个包互相 `import`。package.json 里写成了循环依赖，而两个包又都配置了 `dependsOn: ["^build"]`，任务图自然成环。

```bash
# 看任务图，环会非常明显
pnpm turbo run build --graph=graph.svg

# 查是谁引入了这条依赖
pnpm why @taskflow/ui
```

注意：pnpm 本身允许 workspace 包之间循环依赖，`pnpm install` 不会报错，所以这个问题往往要到构建阶段才暴露。

**修复**：按职责重新划分边界。本项目的依赖是：

```
ui        （无内部依赖）
shared    （无内部依赖）
database  （无内部依赖）

web ← ui + shared
api ← database + shared
e2e ← 无内部依赖
```

如果确实存在"既需要工具函数又需要 UI 组件"的混合代码，提取第三个包（例如 `packages/shared-ui`），让它依赖 `shared` 和 `ui`，而不是让 `shared` 反过来依赖 `ui`。

### 陷阱 2：幽灵依赖（Phantom Dependency）

**症状**：代码里 `import` 了一个没有写进 `package.json` 的包，本地能跑，换台机器或 CI 就报 `ERR_MODULE_NOT_FOUND`。

**成因**：依赖被其他包安装后，通过扁平化的 `node_modules` "泄露"到了当前包。pnpm 默认使用隔离的符号链接结构，正常情况下不会出现；从 npm/Yarn 迁移过来、或手动设置了 `nodeLinker: hoisted` 时最容易复发。

```typescript
// apps/web/src/utils/debounce.ts
// package.json 里没有 lodash，能跑只是因为别的包装了它
import { debounce } from 'lodash';
```

**修复**：

```bash
# 1. 查这个包是谁装进来的
pnpm why lodash

# 2. 当前包确实需要，就显式声明
pnpm --filter @taskflow/web add lodash
```

如果某个工具（典型的是 ESLint 插件）确实需要提升，使用 `pnpm-workspace.yaml` 的 `publicHoistPattern` 精确放行，并写清原因：

```yaml
publicHoistPattern:
  - "*eslint*"
```

不要用 `shamefullyHoist: true` 或 `nodeLinker: hoisted` 来"解决"幽灵依赖——那只是把问题藏起来。

### 陷阱 3：构建顺序错误

**症状**：`apps/web` 在 `packages/shared` 产出 `dist` 之前就开始构建，报 `Cannot find module '@taskflow/shared'` 或类型声明缺失。

**成因**：`turbo.json` 漏了 `dependsOn`。下面这份配置看起来"能跑"，但实际上没有任何顺序保证：

```json
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"]
    }
  }
}
```

更隐蔽的后果是**缓存污染**：`web#build` 的 hash 不包含 `shared#build` 的 hash，shared 改了之后 web 仍可能命中旧缓存。

**修复**：

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "lint": {}
  }
}
```

三种 `dependsOn` 的语义（Ch10 详述）：

| 写法 | 含义 | 典型用途 |
| ---- | ---- | -------- |
| `["^build"]` | 先构建**所有上游依赖包** | `build`、`typecheck` |
| `["build"]` | 先跑**同一个包**里的 `build` | `test` 前需要本包产物时 |
| `[]` / 不写 | 无依赖，可立即并行 | `lint`、`format` |

`lint` 不需要上游产物：ESLint 解析的是源码。给它加 `^build` 只会让 CI 多等一轮构建。

### 陷阱 4：环境变量导致的缓存污染

**症状**：本地测试通过，CI 或同事机器上命中缓存后直接"通过"，但实际代码在另一个数据库/API 地址下会失败。

**成因**：任务读取了某个环境变量，但它没有出现在 `env` 或 `globalEnv` 里。Turborepo 的缓存键只包含**声明过的**变量值，未声明的变量既不参与 hash，在默认的 strict 模式下还会被从任务运行时中过滤掉。

```json
{
  "tasks": {
    "test": {
      "env": ["DATABASE_URL"],
      "inputs": ["src/**", "tests/**", "vitest.config.*", "package.json"]
    }
  }
}
```

- **`env`**：变量的值参与 hash。`DATABASE_URL` 指向不同库时，测试必须重跑。
- **strict 模式（默认）**：任务只能看到 `env`、`globalEnv`、`passThroughEnv` 中声明的变量。漏声明时，任务通常会因为变量缺失而**快速失败**——这是好事，比静默命中错误缓存安全得多。
- **`passThroughEnv`**：变量需要传给任务，但不应影响 hash。典型场景是部署任务里的 `GITHUB_TOKEN`：没有它推不了镜像，但它不改变产物内容。本项目的镜像推送在 GitHub Actions 里完成，不经过 turbo，所以暂时用不到；自定义部署任务时再考虑。

本地 `.env` 的处理：本项目把 `.env` 放在各应用目录下，`build.inputs` 里的 `.env*` 会覆盖到它们。不要在图省事在根目录放一个"大而全"的 `.env`——它既容易和 app 级配置漂移，也需要额外的 `globalDependencies` 才能进入 hash（Ch14 已说明）。

调试时用 `pnpm turbo run test --summarize`，对比两次运行的 `environmentVariables` 和 `inputs`，比猜快得多。`--env-mode=loose` 只适合临时定位问题，不要写进 CI 配置。

### 陷阱 5：tsconfig 继承断裂

**症状**：`error TS5083: Cannot read file '.../@taskflow/tsconfig/base.json'`，或者编辑器里所有严格选项突然失效。

**成因**：`extends` 的包名无法解析——通常是 `pnpm install` 没跑、包没被 workspace 识别，或者 `packages/tsconfig/package.json` 的 `files` / `exports` 没有包含目标文件。

本项目的配置包保持极简（Ch03）：

```json
{
  "name": "@taskflow/tsconfig",
  "version": "0.0.0",
  "private": true,
  "files": ["*.json"]
}
```

它**不写 `exports`**，因此 `extends: "@taskflow/tsconfig/base.json"` 会按文件路径直接解析。如果你后来加了 `exports`，必须把 `./base.json`、`./vue-app.json`、`./node-app.json` 全部列进去，否则原本能用的 `extends` 会立刻失败。

排查顺序：

```bash
# 1. 依赖装了吗
pnpm install

# 2. 当前包能看到配置包吗
ls apps/web/node_modules/@taskflow

# 3. 最终解析出的配置是什么
pnpm exec tsc --showConfig -p apps/web/tsconfig.json

# 4. 谁声明了这个依赖
pnpm why @taskflow/tsconfig
```

`tsc --showConfig` 会打印合并后的完整配置，能直接看出 `extends` 是否生效、`include` 是否把文件排除掉了。

### 陷阱 6：内部依赖没有使用 workspace 协议

**症状**：改了 `packages/shared`，`apps/web` 却毫无变化；或者发布后依赖仍指向旧版本。

**成因**：内部依赖写成了固定版本号，pnpm 把它当成普通 npm 包去 registry 下载。

```json
// 错误
{ "dependencies": { "@taskflow/shared": "1.0.0" } }

// 正确
{ "dependencies": { "@taskflow/shared": "workspace:*" } }
```

`workspace:` 协议的三种写法对应不同的发布结果：

| 写法 | `pnpm pack` / `publish` 后变成 | 适用场景 |
| ---- | ------------------------------ | -------- |
| `workspace:*` | `1.2.3`（精确版本） | 私有包、应用 |
| `workspace:^` | `^1.2.3` | 要发布的库，允许消费者升级 patch/minor |
| `workspace:~` | `~1.2.3` | 要发布的库，只允许 patch |

私有包永远不会经历这个替换，仓库里始终保持 `workspace:*`。要发布的包由 Ch13 的 Changesets 负责级联更新版本号，不要手改成固定版本。

### 陷阱 7：环境变量泄漏到错误的包

**症状**：前端 bundle 里出现了数据库地址或密钥；或者共享包在浏览器里读取 `process.env` 得到 `undefined`。

**成因**：把应用级配置塞进了共享包，或者误以为 Vite 会自动注入所有环境变量。

```typescript
// packages/shared/src/config.ts —— 错误示范
export const apiUrl = process.env.VITE_API_ORIGIN; // 浏览器里没有 process.env
export const dbUrl = process.env.DATABASE_URL;     // 一旦被打进前端就是事故
```

正确的边界：

- **`packages/shared` / `packages/ui` 不读环境变量**。需要配置时，由应用通过参数或 props 传入，共享包保持环境无关。
- **Web 只使用 `import.meta.env.VITE_*`**。Vite 只会把 `VITE_` 前缀的变量注入客户端，其他变量即使写在 `.env` 里也不会出现在 bundle 中。任何 `VITE_*` 都会被打进静态文件，**永远不要放密钥**。
- **API 在启动时集中校验**。Ch08 的 `src/config/env.ts` 用 Zod 4 解析 `process.env`，缺变量直接退出：

```typescript
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.url(),
  JWT_SECRET: z.string().min(32),
  JWT_REFRESH_SECRET: z.string().min(32),
  CORS_ORIGINS: z.string().default('http://localhost:5173'),
});

export const env = envSchema.parse(process.env);
```

再强调一次 Ch14 的结论：`VITE_*` 是**构建期**变量，同一个 Web 镜像不能靠换环境变量切换 API 地址；`process.env` 是**运行期**变量，同一个 API 镜像可以在 staging 和 production 复用。

### 陷阱 8：CI 没有冻结 lockfile

**症状**：本地和 CI 装出不同的依赖版本，出现"我这儿能跑"的随机失败；或者 PR 里改了 `package.json` 却忘了提交 `pnpm-lock.yaml`。

**成因**：CI 执行了不带 `--frozen-lockfile` 的安装，pnpm 根据 `^` 范围重新解析了依赖。pnpm 在检测到 `CI=true` 时默认冻结 lockfile，但显式写出来更不容易被环境差异坑到。

```yaml
- uses: pnpm/setup@v3
  with:
    cache: true
    require-lockfile: true
```

`require-lockfile: true` 等价于强制 `--frozen-lockfile`：lockfile 缺失或与 `package.json` 不一致时直接失败。本地偶尔需要重新解析时再显式执行：

```bash
pnpm install --no-frozen-lockfile
```

`verifyDepsBeforeRun: install` 会在跑脚本前检查 `node_modules` 是否与 lockfile 一致，能提前发现"装了一半"或"切分支后没重装"的问题。

### 陷阱 9：Docker 构建上下文过大、镜像里混入开发依赖

**症状**：镜像 2GB、构建要十几分钟、每次改一行前端代码都要重装所有依赖。

**成因**：直接 `COPY . .` 再 `pnpm install`，把 `node_modules`、`.git`、测试产物、所有应用都塞进了构建上下文和镜像。

**修复**：使用 Ch14 的 `turbo prune` + `pnpm deploy` 流程：

```dockerfile
FROM base AS prepare
COPY . .
RUN pnpm dlx turbo@2.11.5 prune @taskflow/api --docker

FROM base AS builder
COPY --from=prepare /app/out/json/ ./
RUN pnpm install --frozen-lockfile
COPY --from=prepare /app/out/full/ ./
RUN pnpm turbo run build --filter=@taskflow/api
RUN pnpm --filter=@taskflow/api --prod deploy /app/deploy
```

配套要点：

- **`.dockerignore` 必须排除 `node_modules`、`.git`、`**/dist`、`coverage`、`.turbo` 和真实 `.env`**。`COPY . .` 本身不是问题，前提是上下文里没有这些目录；最终镜像只复制 `out/` 和 `deploy/`。
- **构建阶段关掉 Husky**。根 `package.json` 有 `"prepare": "husky"`，Docker 上下文里没有 `.git`，钩子装不上。在基础镜像里设置 `ENV HUSKY=0`，让 husky 跳过安装，而不是用 `--ignore-scripts` 把所有依赖的构建脚本一起关掉（esbuild 需要它）。
- **运行时不要装 pnpm、不要 copy 源码**。`pnpm deploy` 生成的目录已经自包含。
- **用 BuildKit 的 GHA 缓存**（Ch14 的 `cache-from/cache-to: type=gha`），不要手工维护缓存目录。

### 陷阱 10：workspace 目录没有被匹配

**症状**：新建了 `tools/cli`，`pnpm install` 不报错，但 `workspace:*` 依赖解析失败，或者 Turborepo 根本看不到这个包。

**成因**：`pnpm-workspace.yaml` 的 `packages` 只写了 `apps/*` 和 `packages/*`，新目录不在花名册里。

```yaml
packages:
  - "apps/*"
  - "packages/*"
  - "tools/*"     # 新增目录必须显式加入
```

排查：

```bash
# 列出 pnpm 识别到的所有 workspace 包
pnpm -r list --depth -1
```

还有一个更容易混淆的问题：**pnpm 11+ 的设置也在这个文件里**。看到"配置没生效"时，先确认它写在了 `pnpm-workspace.yaml` 而不是 `.npmrc`。Ch02 已经给出对照表。

## 15.3 从已有项目迁移到 Monorepo

### 15.3.1 迁移路线图

```
Phase 1：准备（1–2 天）
  ├── 梳理现有项目的依赖关系
  ├── 确定包划分与命名（scope）
  └── 建立 monorepo 骨架与根配置

Phase 2：基础设施（2–3 天）
  ├── pnpm workspace + Turborepo + catalog
  ├── 统一 TypeScript / ESLint / Prettier
  └── CI、缓存、Changesets

Phase 3：渐进迁移（1–2 周）
  ├── 先迁共享代码到 packages/
  ├── 再迁应用到 apps/
  └── 每迁一个就验证构建与测试

Phase 4：清理与固化（3–5 天）
  ├── 删除嵌套 lockfile、重复配置
  ├── 打开分支保护与 CODEOWNERS
  └── 团队培训与文档
```

### 15.3.2 关键步骤

**Step 1：建立骨架，先把"根"配完整**

```bash
mkdir taskflow && cd taskflow
git init

cat > pnpm-workspace.yaml << 'EOF'
packages:
  - "apps/*"
  - "packages/*"
EOF
```

根 `package.json` 至少包含这些字段：

```json
{
  "name": "taskflow",
  "private": true,
  "packageManager": "pnpm@12.0.0",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "^12.0.0",
      "onFail": "error"
    }
  },
  "engines": { "node": ">=24" },
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck",
    "test": "turbo run test"
  },
  "devDependencies": {
    "prettier": "^3.9.10",
    "turbo": "^2.11.0"
  }
}
```

同时按 Ch02 创建 `.nvmrc`、`.npmrc`、`.gitignore`，并把 `minimumReleaseAge`、`strictDepBuilds` 等设置写进 `pnpm-workspace.yaml`。

**Step 2：迁移代码，保留历史**

同一仓库内移动用 `git mv`：

```bash
git mv legacy-web apps/web
git mv legacy-api apps/api
git mv legacy-shared packages/shared
```

如果代码来自独立仓库，用 `git subtree` 或 `git filter-repo` 保留提交历史：

```bash
# 在 monorepo 中合入另一个仓库的历史
git subtree add --prefix apps/web https://github.com/you/legacy-web.git main

# 或者在源仓库中先把历史改写到子目录，再合并
git filter-repo --to-subdirectory-filter apps/web
```

迁移后立刻删除子项目里的 `node_modules` 和 `pnpm-lock.yaml`：

```bash
# macOS / Linux / Git Bash
rm -rf apps/*/node_modules apps/*/pnpm-lock.yaml
rm -rf packages/*/node_modules packages/*/pnpm-lock.yaml

# Windows PowerShell
Get-ChildItem apps, packages -Directory | ForEach-Object {
  Remove-Item -Recurse -Force "$($_.FullName)\node_modules" -ErrorAction SilentlyContinue
  Remove-Item -Force "$($_.FullName)\pnpm-lock.yaml" -ErrorAction SilentlyContinue
}
```

**整个仓库只能有一个 lockfile**，放在根目录。嵌套 lockfile 会让 pnpm 认为是两个独立项目，workspace 链接和缓存都会失效。

**Step 3：统一内部依赖与包名**

```json
// apps/web/package.json
{
  "dependencies": {
    "@taskflow/shared": "workspace:*",
    "@taskflow/ui": "workspace:*"
  }
}
```

```bash
# 改 import 路径
# 旧: import { formatDate } from 'my-shared-utils';
# 新: import { formatDate } from '@taskflow/shared';
```

如果旧包名仍被仓库外的项目使用，可以在过渡期用 npm alias 兼容：

```json
{
  "dependencies": {
    "my-shared-utils": "npm:@taskflow/shared@^1.0.0"
  }
}
```

等外部消费者迁移完再删除 alias。

**Step 4：收敛共享配置**

把各项目的 tsconfig 公共部分提取到 `packages/tsconfig/base.json`，Vue 和 Node 各自继承 `vue-app.json` / `node-app.json`；ESLint 统一到 `packages/eslint-config`；依赖版本统一到 `pnpm-workspace.yaml` 的 catalog。配置的收敛可以分批做，先让项目跑起来，再逐步收紧。

**Step 5：验证，再切 CI**

```bash
pnpm install

# 先看任务计划：顺序、范围、输入是否符合预期
pnpm turbo run build --dry=json > turbo-plan.json

pnpm build
pnpm test
pnpm lint
pnpm typecheck
```

全部通过后再切 CI，并把旧的流水线停掉。两套 CI 并行跑一段时间是可以接受的，但不要长期保留——它们对"什么算通过"的定义迟早会分叉。

### 15.3.3 迁移时的注意事项

1. **不要一次性全迁**。从耦合度最低、依赖最少的模块开始，每迁一个就验证一次。一次迁完再调试，问题会互相掩盖。
2. **保留 Git 历史**。用 `git mv`、`git subtree` 或 `git filter-repo`，不要用 `cp -r`。历史断了，`git blame` 和事故回溯都会失去价值。
3. **从第一天启用 Changesets**。不要等"准备发布"时才补 changelog 和版本流程；迁移期的每一次改动都值得记录。
4. **CI 缓存键要跟着换**。迁移后 lockfile、路径、Node 版本都可能变，旧的缓存键会失效或误命中；迁移完成后清一次缓存，再观察命中率。
5. **先统一"入口"，再统一"细节"**。各包的 `build`、`test`、`lint` 脚本名先对齐，Turborepo 才能编排；代码风格、目录结构可以慢慢统一。

## 15.4 团队协作规范

### 15.4.1 CODEOWNERS：让变更找到对的人

```txt
# .github/CODEOWNERS
# 最后匹配的规则生效，兜底规则放最前面

*                               @core-team

/apps/web/                      @frontend-team
/packages/ui/                   @frontend-team

/apps/api/                      @backend-team
/packages/database/             @backend-team

/packages/shared/               @frontend-team @backend-team
/apps/e2e/                      @frontend-team @backend-team

/turbo.json                     @tech-lead
/pnpm-workspace.yaml            @tech-lead
/packages/tsconfig/             @tech-lead
/packages/eslint-config/        @tech-lead
/.github/                       @tech-lead
```

Monorepo 的风险之一是"谁都能改任何代码"。CODEOWNERS 把审查责任落到具体团队：数据库 Schema 的改动必须由后端审查，共享包的改动前后端都要看，基础设施配置由 Tech Lead 把关。

### 15.4.2 PR 模板：把隐性要求变成勾选项

```markdown
<!-- .github/pull_request_template.md -->
## 变更说明
<!-- 做了什么，为什么 -->

## 影响的包
- [ ] apps/web
- [ ] apps/api
- [ ] apps/e2e
- [ ] packages/shared
- [ ] packages/ui
- [ ] packages/database
- [ ] 配置（tsconfig / eslint-config / turbo.json / workspace）

## 变更类型
- [ ] 新功能（feat）
- [ ] Bug 修复（fix）
- [ ] 重构（refactor）
- [ ] 性能优化（perf）
- [ ] 配置/构建（chore）

## 发布影响
- [ ] 需要 changeset（改动了要发布的包）
- [ ] 不需要 changeset（仅应用、文档或 CI）
- [ ] 涉及数据库迁移（附迁移说明与回滚方案）
- [ ] 涉及部署配置（镜像、环境变量、平台配置）

## 验证
- [ ] 相关测试已添加/更新
- [ ] 本地手动验证通过
- [ ] CI 通过
```

"是否需要 changeset"这一项尤其重要。Ch13 已经说明：忘记 changeset 是最常见的发布事故来源，而 PR 模板是最便宜的提醒方式。

### 15.4.3 分支策略：优先主干开发

对这个规模的仓库，推荐 **trunk-based**：

```
main ← feature/add-user-auth      （生命周期尽量 < 2 天）
     ← fix/api-timeout
     ← changeset-release/main     （Changesets 机器人创建的版本 PR）
```

- 所有功能分支通过 PR 合入 `main`，合并即部署候选。
- 发布用 Git tag 和镜像 SHA 标记，而不是长期维护 `release/*` 分支。
- 版本 PR 由机器人创建，合并后触发 npm 发布（Ch13）。

如果组织强制要求 `develop`，必须同步调整三处，否则发布链路会断：

1. `ci.yml` 的 `pull_request.branches` 加上 `develop`；
2. `.changeset/config.json` 的 `baseBranch` 改成实际发布分支；
3. `images.yml` / `release.yml` 的触发分支与合并路径保持一致。

多一条长期分支，就多一份"哪些提交在哪个分支"的认知负担。能用主干开发就不要引入 `develop`。

**分支保护建议**：

| 分支 | 要求 |
| ---- | ---- |
| `main` | 至少 1–2 人审查、CI 与 Changeset Check 通过、禁止直接推送和强推 |
| 功能分支 | 定期 rebase 到 `main`，避免长期漂移 |

## 15.5 Monorepo 的适用边界

### 适合的场景

| 场景 | 原因 |
| ---- | ---- |
| 前后端紧密耦合 | 共享类型和校验规则，接口变更可以在一个 PR 内完成 |
| 多应用共享组件库 | 组件、工具、配置同仓维护，版本天然一致 |
| 微前端 / 多子应用 | 统一构建配置、依赖版本和发布流程 |
| SDK / 库矩阵 | 核心包 + 各平台适配包协同演进 |
| 中小团队（3–20 人） | 沟通成本低，跨包重构的收益大于仓库变大的成本 |

### 不适合的场景

| 场景 | 原因 |
| ---- | ---- |
| 项目之间没有共享代码 | Monorepo 只增加复杂度，没有收益 |
| 数百个包、数十个团队 | 需要 Bazel、Nx 这类更强的增量构建与边界治理工具 |
| 多语言混合（Java + Go + Python） | pnpm/Turborepo 只能管理 JS/TS 生态 |
| 需要严格的代码隔离与权限 | 单仓意味着默认所有人能读所有代码 |
| 每个项目有独立社区与发布节奏 | 独立仓库的 issue、release、权限模型更合适 |

### 决策清单

```
你的项目满足以下条件中的 2 个以上吗？
  ├── 多个应用/包共享代码？
  ├── 需要统一的版本与发布流程？
  ├── 团队规模 < 20 人？
  ├── 技术栈主要是 JavaScript/TypeScript？
  └── 跨项目的变更频繁（每周至少 1 次）？

是 → Monorepo
否 → 独立仓库 + 发布 npm 包
```

Monorepo 不是银弹。它用"仓库变大、权限变宽、工具链变复杂"换取"原子提交、统一依赖、跨包重构"。只有后者确实是主要矛盾时，这笔交易才划算。

## 15.7 从零到发布的完整 Checklist

### 阶段一：初始化

```
□ 创建仓库，初始化 Git
□ .nvmrc 锁定 Node 24
□ package.json 写入 private / packageManager / devEngines / engines
□ pnpm-workspace.yaml 声明 packages、安装策略与 catalog
□ .npmrc 只保留 registry 与认证
□ .gitignore 覆盖 node_modules、dist、.turbo、coverage、.env
□ 安装 turbo、prettier 等根级 devDependencies
```

```
□ packages/tsconfig：base / vue-app / node-app
□ packages/eslint-config：base / vue / node（flat config）

```

### 可以继续深入的方向

1. **远程缓存**：团队规模扩大后，Vercel Remote Cache 或自建 [`turborepo-remote-cache`](https://github.com/ducktors/turborepo-remote-cache)；签名与权限模型见 Ch11。

## 本章小结

1. **性能优化有顺序**：先用 `--summarize`、`--graph`、`--dry=json`、`--profile` 定位，再决定是优化安装、任务范围、缓存还是镜像层。不要凭感觉调参数。
2. **缓存正确性优先于命中率**：`globalDependencies`、`inputs`、`env` 三者共同决定缓存边界。漏声明换来的"高命中率"，本质是把错误产物复用得更快。
3. **10 个陷阱可以归为三类**：依赖边界（循环依赖、幽灵依赖、workspace 协议）、缓存与环境（构建顺序、缓存污染、环境变量泄漏、lockfile）、交付链路（tsconfig 继承、Docker、workspace 目录）。排查时先归类，再定位。
4. **迁移要渐进**：先搭骨架和共享配置，再逐个迁移模块，每步验证；保留 Git 历史，只保留一个 lockfile，从第一天启用 Changesets。
5. **协作靠机制**：CODEOWNERS 明确审查责任，PR 模板把 changeset 和部署影响变成勾选项，主干开发减少分支漂移。
6. **适用性要诚实**：Monorepo 用复杂度换原子性和一致性。没有共享代码、技术栈分散、权限要求严格的场景，独立仓库更合适。

回顾整个教程：

- **Part 1（Ch01–Ch04）**：概念、环境、目录结构、依赖管理。
- **Part 2（Ch05–Ch09）**：共享包、TypeScript、Web、API、代码规范。
- **Part 3（Ch10–Ch13）**：任务编排、构建缓存、测试策略、版本发布。
- **Part 4（Ch14–Ch15）**：CI/CD 与容器化部署、最佳实践与总结。

到这里，你已经具备从零搭建、开发、测试、发布到部署一个 Monorepo 项目的完整知识。剩下的部分只能在真实项目里补齐：第一次缓存污染、第一次循环依赖、第一次回滚，都会比任何教程记得更牢。
