## 1.1 远程接入的三条路——为什么非 VPN 不可

先用一句话钉死贯穿全书的场景：**你要在外面用笔记本和手机，安全地访问一台云服务器上的服务**——SSH 终端、数据库、管理面板，都只允许内网访问。现在的问题是：人在咖啡馆，怎么够到内网？

三条常见路线，安全性和可维护性差别巨大：

| 路线 | 做法 | 安全性 | 适合 | 不适合 |
| ---- | ---- | ---- | ---- | ---- |
| 直接暴露 | 每个服务自己监听公网 | 靠服务自身认证，攻击面全开 | 没有 | 一切内网服务 |
| SSH 隧道 | `ssh -L` 临时转发单个端口 | 强（复用 SSH 认证） | 一次性救急 | 多设备、多服务、长期使用 |
| VPN 网关 | 先接入网络，再访问服务 | 网络层加密 + 网段隔离 | 多设备长期接入 | —— |

先算路线一的风险账。一台新建服务器把 SSH 端口（22）开放到公网，24 小时内 `/var/log/auth.log` 里就会出现几百条来自陌生 IP 的失败登录尝试——自动化扫描器在全网轮询端口，你的服务器从上线那一刻就在被反复「敲门」。SSH 密钥登录能挡住这些尝试，但数据库（5432）、管理面板（8080）没有这么强的默认防护；每多暴露一个端口，就多一块自己维护认证与补丁的攻击面（Attack Surface）。

路线二的 SSH 隧道（Tunnel）是救急神器：`ssh -L 5432:localhost:5432 server` 一条命令就能把远端数据库映射到本地。但它是**单设备、单端口、会话级**的——换个设备要重来，开五个服务要五条命令，断线要手工重连。站内[《Git 与 SSH 完全教程》](/git-ssh/ch15)讲过它的用法与「它不是 VPN」的边界：它解决「临时够到某一个端口」，不解决「长期接入一张网络」。

路线三就是把问题升级一层：不逐个保护服务，而是**在整张网络外面套一个受控入口**。你通过 VPN 接入内网网段（10.66.66.0/24），接入之后访问 SSH、数据库、管理面板就像在公司局域网里一样——每个服务可以安心只监听内网，公网上只留一个 VPN 端口。安全模型从「每个服务各自防」收敛成「网络入口一处防」，这就是本书选择 VPN 网关的原因。

## 1.2 wg0——把隧道当成一张网卡

WireGuard 自 2020 年起内置于 Linux 内核（5.6+，本文服务器无需另装内核模块），它提供给你的东西不是「一个软件」，而是一张**虚拟网卡**（Virtual Network Interface），默认名 `wg0`。`ip link` 看它的方式与看物理网卡完全一样：

```text
$ ip link show wg0
5: wg0: <POINTOPOINT,NOARP,UP,LOWER_UP> mtu 1420 ...
    link/none
```

这张网卡有三个关键设定，构成 WireGuard 的世界观：

- **它有 IP**。给 `wg0` 配上 `10.66.66.2/24`（笔记本的隧道内地址），你的应用就「住在」10.66.66.0/24 这个网段里——SSH 连 `10.66.66.1` 与连局域网机器在体验上没有任何区别，内核照常按路由表发包，只是这批包的目的地是 `wg0` 而不是 `eth0`。
- **身份是密钥对（Key Pair）**。每个接口持有私钥（Private Key），只把公钥（Public Key）告诉对端；**对端之间不认识 IP、不认识账号，只认公钥**。私钥 32 字节，公钥也是 32 字节（第二章讲它们怎么算出来的）。
- **加密封装在内核里完成**。应用把明文包交给 `wg0`，内核加密后从物理网卡发出 UDP 包；对端内核解密后把明文包塞进自己的 `wg0`。全程应用无感——这也是 2.1 要讲的性能来源。

`wg0` 的名字只是默认值（wg = WireGuard，0 = 第一个接口），你可以叫它 `wg-home`、`wg-office`。本书为了与官方文档和绝大多数教程一致，统一用 `wg0`；多套隧道并存的进阶玩法在第六章末尾会提一句。

「多了一张网卡」这个心智模型是全书最重要的一次抽象：后面配置路由、排查不通、设计分流，本质上都在回答一个问题——**这个包应该从哪张网卡出去**。网卡思维立住了，VPN 就不再神秘。

## 1.3 一条数据包的隧道旅程

把 1.2 的模型跑一遍：在咖啡馆，笔记本（隧道内 10.66.66.2）SSH 到服务器（隧道内 10.66.66.1）的 22 端口。

```text
 笔记本 10.66.66.2                    云服务器 10.66.66.1
+-------------+                     +-------------+
|  SSH 客户端  |                     |   sshd      |
+------+------+                     +------^------+
       | 目标 10.66.66.1:22                | 解密后交付
       v                                  |
+------+------+   加密封装   +-----+ +-----+-----+
|    wg0      | ----------> | UDP | |    wg0    |
+-------------+  内核完成    +-----+ +-----------+
                                |
                          公网只见到 UDP 流
```

外层与内层是两个包，像洋葱一样套着：

```text
外层（公网可见）：我的临时IP:随机端口  →  203.0.113.10:51820
内层（公网不可见）：10.66.66.2:51344  →  10.66.66.1:22
```

三个要点值得钉死：

- **公网链路上只有 UDP 流**。WireGuard 不需要 TCP，也没有「连接」可以断——它是无状态（Stateless）的包级协议。咖啡馆的 Wi-Fi、运营商的网关看到的只是一串目标端口 51820 的 UDP 包，内容全部密文。
- **Endpoint 是外层地址**。对端的公网地址与端口（`203.0.113.10:51820`）叫端点（Endpoint），写在配置里；而 `10.66.66.1` 是内层地址，隧道通了才可达。分不清这两层，是新手最常见的「连不上」根源（第四章 4.7 专治）。
- **回程走同一条隧道**。服务器的应答包内层地址是 `10.66.66.1 → 10.66.66.2`，从服务器 `wg0` 出发反向封装回来。双向性与 ch00 图 0-1 说的完全一致。

还有一个容易忽略的事实：这条隧道**没有「连接」概念**，自然也没有断线重连——每一对包都是独立加密、独立认证的。笔记本合盖半小时再打开，隧道「秒通」，因为根本没有「通」这个状态要恢复，只有下一次握手要发生（握手时机见 2.4）。这与 TCP 隧道方案「断线后要等重连」的体感差异，用久了会很明显。

数据包怎么加密、密钥怎么协商、重放攻击怎么防——这些「为什么安全」的问题留给第二章，本章只立住「洋葱双层 + 只认公钥」的直觉。

## 1.4 工具族谱——wg、wg-quick 与 wg-quick@

动手之前必须分清三个名字，它们在所有文档里反复出现又极易混淆。先交代本书记号约定（全书只此一次）：`**命令格式**` 行采用手册风格——方括号 `[ ]` 表示可省略，`...` 表示可重复，`|` 表示多选一，大写单词是占位符；实际敲命令时把占位符换成具体值。

**wg** 是查看与调试工具，直接读内核状态，不改任何配置：

**命令格式**：`wg [SUBCOMMAND] [OPTIONS]... [INTERFACE]`

全书用到的子命令先混个脸熟：

| 子命令 | 作用 | 出现章 |
| ---- | ---- | ---- |
| `wg show` | 查看接口、对端、握手与流量 | 第三、四章排障 |
| `wg genkey` | 从标准输入产出私钥 | 第三章起反复使用 |
| `wg pubkey` | 从私钥推导公钥 | 与上一条成对出现 |
| `wg syncconf` | 按 conf 热更新运行中的接口（不重建网卡） | 第三、五章 |

```text
$ wg show                       # 服务器视角
interface: wg0
  public key: k5S+1x...=        # 本机（服务器）公钥
  listening port: 51820
peer: 8KxrmP...=                # 对端（笔记本）公钥
  endpoint: 198.51.100.7:41234  # 笔记本的公网出口与随机端口
  allowed ips: 10.66.66.2/32    # 2.5 的白名单
  latest handshake: 12 seconds ago
  transfer: 1.5 KiB received, 2.3 KiB sent
```

**wg-quick** 是配置落地的封装脚本（wrapper），读 `/etc/wireguard/<接口名>.conf`，一次性完成建网卡、配 IP、加路由、设密钥：

**命令格式**：`wg-quick [up|down|save|strip] [INTERFACE]`

**wg-quick@wg0** 则是 systemd 服务单元（systemd service unit），把 `wg-quick up wg0` 变成开机自启的服务——生产环境用这个，而不是每次手工 `wg-quick up`：

**命令格式**：`systemctl [COMMAND] [UNIT]`

| 名字 | 本质 | 什么时候用 |
| ---- | ---- | ---- |
| `wg` | 内核状态的查看/调试口 | 排障时随时敲，**从不改配置** |
| `wg-quick` | 一次性起停配置的脚本 | 手动测试新配置 |
| `wg-quick@wg0` | systemd 服务 | 生产环境，开机自启 |

生成密钥对的管道现在就练一遍手感（第三章会正式大量使用）：

```text
$ wg genkey | tee server_private.key | wg pubkey > server_public.key
```

一条命令产出私钥与公钥：`wg genkey` 生成私钥，`wg pubkey` 从标准输入读私钥、吐出对应公钥。**私钥永不离开本机**，公钥才是发给对端的东西——这个纪律从第一条命令起就要养成。

## 1.5 客户端形态一览

WireGuard 的服务端只有 Linux 一种形态（内核模块 + `wg-quick`），但客户端有四张面孔，本书全部覆盖：

| 形态 | 平台 | 配置来源 | 本教程章节 |
| ---- | ---- | ---- | ---- |
| 内核模块 + wg-quick | Linux 服务器、NAS | `/etc/wireguard/*.conf` | 第三、五、六章 |
| 官方桌面客户端 | Windows / macOS | 导入 `.conf` 文件 | 第四章 |
| 官方移动 App | iOS / Android | 扫二维码 | 第四章 4.4 |
| mihomo 系图形客户端（CordC、Clash Verge 等） | 跨平台 | 自定义配置模板 | 第七、八章 |

关键认知：**形态不同，协议同一**。服务端视角里，无论对面是官方 App 还是 mihomo 内核，都只是一个「公钥 + 虚拟 IP」组成的对端（Peer，对等节点）条目——所以第四章的官方客户端接入流程学完，第七章的 mihomo 接入就只剩「把这个客户端的公钥交给服务端」一件事。反过来说，服务端章节（第三、五章）学一次，四种形态全部适用。

## 1.6 易混概念辨析

VPN 与代理是两个最容易被混为一谈的词——它们都能「访问够不到的资源」，但工作层级完全不同：

| 维度 | VPN | 代理（Proxy） |
| ---- | ---- | ---- |
| 工作层级 | 网络层：接管 IP 包的路由 | 应用层：接管某个应用的请求 |
| 覆盖范围 | 系统路由表，全部应用生效 | 通常单个应用或浏览器 |
| 典型协议 | WireGuard、OpenVPN、IPsec | HTTP 代理、SOCKS5 |
| 本书的位置 | 全书主线 | 第七、八章的客户端形态 |

一个直观的区分办法：VPN 接入后 `ping 10.66.66.1` 是通的——因为「整张网络」接进来了；而浏览器挂上普通代理后，`ping` 依旧走原路——因为只有浏览器的 HTTP 请求被「代购」了。第七章会看到 mihomo 用 TUN 模式把自己升格成一张虚拟网卡，从而获得 VPN 级的接管能力——这正是两种形态在同一个客户端里会师的地方。

现在兑现「先猜再读」第三条的答案：`AllowedIPs` 管的是**「我能访问谁」**——对客户端来说，它是路由表：命中 `10.66.66.0/24` 的包塞进隧道，其余照走物理网卡。但同一个字段在**服务端**还兼任第二语义「谁被允许用这个源地址进来」——白名单，进错源的包直接丢弃。一个字段两种身份，这是 WireGuard 设计里最精巧也最容易踩坑的一笔，第二章 2.5（加密密钥路由）展开机制，第三、四、六章反复用到。

## 1.7 实验环境准备

后续章节的动手环节只需要一台服务器加一个终端，先把环境说清楚：

- **云服务器**：任意有公网 IP 的云主机，Ubuntu 22.04/24.04 或 Debian 12，1 核 1G 足够（WireGuard 的开销远低于业务服务）；本书锚点 IP 为 203.0.113.10。
- **登录方式**：本地终端能 `ssh` 上去即可（Windows 11 自带 OpenSSH 客户端，macOS/Linux 终端同理）。
- **云控制台权限**：能改安全组/防火墙规则——第三章要放行 UDP 51820。

动手前先用 `ip` 命令认清这台服务器自己的网卡布局——第三章配置 NAT 转发时要写外网网卡名，而各云厂商的命名不一（ens3、eth0、ens5 都有），**不写死、现查现用**：

**命令格式**：`ip [OBJECT] [COMMAND] [ARG]...`

```text
$ ip -o link show | awk -F': ' '{print $2}'    # 列出全部网卡
lo
eth0

$ ip route get 1.1.1.1                          # 看默认路由走哪张卡
1.1.1.1 via 172.17.0.1 dev eth0 src 172.17.0.5
```

第二条命令是重点：`dev eth0` 就是访问公网的出口网卡——本书锚点写 `ens3`，你的服务器上查出来是 `eth0` 就用 `eth0`。安全组方面，现在只需在云控制台找到「安全组 / 防火墙规则」入口确认权限即可，具体的放行规则第三章 3.6 给出。

> [!NOTE]
> 家里宽带、公司内网里的机器没有公网 IP，**做不了**本书的服务端；它们是客户端（第四章的笔记本与手机、第六章的 NAS）。服务端必须是公网可达的。

## 本章小结

- 远程接入三条路里，直接暴露把攻击面铺满公网，SSH 隧道是单端口会话级救急，VPN 网关把安全模型收敛成「入口一处防」，是本书主线；
- WireGuard 提供的不是后台软件，而是一张虚拟网卡 `wg0`——「多了一张网卡」是全书的心智模型；
- 身份即密钥对：私钥 32 字节永不外传，公钥就是设备在本隧道里的身份证；
- 加密封装在内核完成，公网链路上只是一条 UDP 51820 的密文流，无连接、无状态；
- Endpoint 是对端公网地址（外层），`10.66.66.x` 是隧道内地址（内层），两层混谈是连不上的头号根源；
- `wg` 只看不改，`wg-quick` 一次性起停，`wg-quick@wg0` 负责开机自启——三兄弟各司其职；
- `AllowedIPs` 在客户端是路由表（我能访问谁），在服务端是白名单（谁配用这个源地址），双重语义贯穿全书；
- 客户端有四张面孔（Linux、桌面、移动、mihomo），服务端视角一律是「公钥 + 虚拟 IP」。
