# 第17章：Swarm 高级运维与故障排查

## 引言：从"能跑"到"跑得好"

上一章我们学会了如何让 Swarm 集群"跑起来"。但"能跑"和"跑得好"之间，还差着一个银河系的距离。就像一个应用能编译通过和能在生产环境稳定运行，完全是两码事。

这一章我们要深入 Swarm 的高级运维技能——高可用、资源管理、监控、故障排查。这些技能在你半夜被报警叫醒时，会是你最好的朋友。

## 17.1 Swarm 高可用架构

单 Manager 节点的集群就像只有一个老板的公司——老板请假了全公司瘫痪。生产环境需要多 Manager 节点来保证高可用。

```bash
高可用 Swarm 集群架构

┌────────────────────────────────────────────────────────────┐
│                     外部负载均衡器                           │
│                   (Nginx / HAProxy / ELB)                   │
│                        ↓           ↓           ↓           │
├────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│  │Manager 1 │    │Manager 2 │    │Manager 3 │              │
│  │ (Leader) │    │(Replica) │    │(Replica) │              │
│  │          │    │          │    │          │              │
│  │ Raft日志  │◄──►│ Raft日志  │◄──►│ Raft日志  │              │
│  │ 集群状态  │    │ 集群状态  │    │ 集群状态  │              │
│  └──────────┘    └──────────┘    └──────────┘              │
│                                                             │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│  │Worker 1  │    │Worker 2  │    │Worker 3  │              │
│  │ 🐳🐳🐳  │    │ 🐳🐳🐳  │    │ 🐳🐳🐳  │              │
│  └──────────┘    └──────────┘    └──────────┘              │
│                                                             │
└────────────────────────────────────────────────────────────┘

Raft 共识算法简要：
  - 所有 Manager 节点通过 Raft 协议保持一致
  - 任何状态变更需要多数节点（quorum）同意
  - 3 个 Manager：允许挂 1 个（需要 2/3 同意）
  - 5 个 Manager：允许挂 2 个（需要 3/5 同意）
  - Leader 由 Raft 自动选举产生
```

```bash
# ====== 添加额外的 Manager 节点 ======

# 在现有 Manager 上获取 Manager join token
docker swarm join-token manager

# 在新节点上执行输出的 join 命令
docker swarm join --token SWMTKN-1-manager-token 192.168.1.100:2377

# 验证集群状态
docker node ls
# 你会看到3个 Manager 节点，其中一个是 Leader

# 查看 Raft 状态
docker info | grep -A 5 "Swarm"
# Swarm: active
#  NodeID: xxx
#  Is Manager: true
#  Managers: 3
#  Nodes: 6
```

> [!TIP] 提示
> Manager 节点同时也能运行容器（默认就是 Active 状态）。在资源有限的小集群中，Manager 节点既当"管理者"又当"执行者"完全没问题。但在大规模集群中（50+ 节点），建议把 Manager 节点设为 `drain`，让它们专心做管理工作。

## 17.2 节点标签与部署约束

节点标签（labels）让你可以精确控制服务运行在哪些节点上——就像你在招聘时写的要求："需要3年以上经验、熟悉 Node.js、能接受出差"。

```bash
# ====== 节点标签 ======

# 给节点打标签
docker node update --label-add env=production worker1
docker node update --label-add env=staging worker2
docker node update --label-add zone=us-east worker1
docker node update --label-add gpu=true worker3
docker node update --label-add storage=ssd worker1

# 查看节点标签
docker node inspect worker1 --pretty | grep -A 10 "Labels"

# ====== 在 Stack 文件中使用约束 ======

# 服务只运行在生产环境的节点上
# deploy:
#   placement:
#     constraints:
#       - node.labels.env == production

# 服务只运行在有 GPU 的节点上
# deploy:
#   placement:
#     constraints:
#       - node.labels.gpu == true

# 服务不能运行在 Manager 节点上
# deploy:
#   placement:
#     constraints:
#       - node.role != manager

# 多个约束条件是 AND 关系（必须同时满足）
# deploy:
#   placement:
#     constraints:
#       - node.labels.env == production
#       - node.labels.zone == us-east
#       - node.labels.storage == ssd
```

```yaml
# 完整示例：按角色分配服务到不同节点

version: '3.8'

services:
  web:
    image: myapp-web:latest
    deploy:
      replicas: 3
      placement:
        constraints:
          - node.labels.role == frontend
          # Web 服务只跑在"前端"节点上

  api:
    image: myapp-api:latest
    deploy:
      replicas: 3
      placement:
        constraints:
          - node.labels.role == backend
          # API 服务只跑在"后端"节点上

  ml-worker:
    image: myapp-ml:latest
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.labels.gpu == true
          # ML 服务需要 GPU，只跑在有 GPU 的节点上
          - node.labels.role == compute
```

除了 constraints（硬性约束），还有 preferences（软性偏好）：

```yaml
services:
  web:
    image: myapp-web:latest
    deploy:
      replicas: 6
      placement:
        preferences:
          - spread: node.labels.zone
          # 尽量在不同 zone 之间均匀分布
          # 比如 us-east 3个，us-west 3个
          # 这不是硬性要求，只是"尽量"这样做
```

## 17.3 资源预留与限制

不限制资源的服务就像不限制预算的实习生——迟早把整个服务器吃光。

```bash
# ====== 命令行方式设置资源限制 ======

docker service create \
  --name api \
  --limit-cpu 0.5 \
  # 最多使用 0.5 个 CPU 核心
  --limit-memory 512M \
  # 最多使用 512MB 内存（超过会被 OOM Kill）
  --reserve-cpu 0.25 \
  # 调度时确保有 0.25 个 CPU 核心可用
  --reserve-memory 256M \
  # 调度时确保有 256MB 内存可用
  myapi:latest

# 理解 limits 和 reservations 的区别：
#
# limits（限制）= 天花板
#   容器最多能用这么多，超过就会被限制
#   - CPU 超过：被限流（throttle），不会杀容器
#   - 内存超过：被 OOM Kill（Out of Memory），容器会被杀死
#
# reservations（预留）= 地板
#   Swarm 在调度时会确保目标节点有这么多资源
#   如果节点资源不够，容器不会被调度到这个节点
#   实际运行时容器可以使用超过预留的资源（但不超过限制）
```

```yaml
# 在 Stack 文件中配置资源
services:
  api:
    image: myapp-api:latest
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 1G
          # 硬限制：最多 1 CPU + 1GB 内存
        reservations:
          cpus: '0.5'
          memory: 512M
          # 软预留：调度时确保有 0.5 CPU + 512MB

  # 实际场景参考值：
  # - Node.js API 服务：   limits 0.5 CPU / 512MB
  # - Python Flask 服务：  limits 0.5 CPU / 256MB
  # - PostgreSQL：         limits 2.0 CPU / 2GB
  # - Redis：              limits 0.5 CPU / 1GB
  # - Nginx 反向代理：     limits 0.25 CPU / 128MB
```

> [!WARNING] 注意
> 内存的 `limits` 设得太低会导致容器被 OOM Kill，日志中会看到 `Killed` 或 `exit code 137`。CPU 的 `limits` 不是硬限制——超过时容器只是变慢，不会被杀。所以调优时优先关注内存限制，CPU 限制设得保守一点没关系。

## 17.4 Swarm 与 CI/CD 集成

将 Swarm 部署集成到 CI/CD 流水线中，实现"提交代码后自动部署到 Swarm 集群"：

```yaml
# .github/workflows/deploy-swarm.yml

name: Deploy to Swarm

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: 登录私有 Registry
        uses: docker/login-action@v3
        with:
          registry: registry.example.com
          username: ${{ secrets.REGISTRY_USER }}
          password: ${{ secrets.REGISTRY_PASSWORD }}

      - name: 构建并推送镜像
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            registry.example.com/myapp-api:${{ github.sha }}
            registry.example.com/myapp-api:latest

      - name: 通过 SSH 部署到 Swarm
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SWARM_MANAGER_HOST }}
          username: ${{ secrets.SWARM_MANAGER_USER }}
          key: ${{ secrets.SWARM_MANAGER_SSH_KEY }}
          script: |
            # 登录 Registry（Manager 节点需要能拉取镜像）
            echo "${{ secrets.REGISTRY_PASSWORD }}" | \
              docker login registry.example.com -u ${{ secrets.REGISTRY_USER }} --password-stdin

            # 更新 Stack
            docker stack deploy \
              -c /opt/myapp/docker-stack.yml \
              --with-registry-auth \
              myapp
            # --with-registry-auth：把 Registry 认证信息传递给 Service
            # 否则 Worker 节点拉取私有镜像时会失败

            # 等待服务更新完成
            docker service update \
              --image registry.example.com/myapp-api:${{ github.sha }} \
              myapp_api

            # 验证部署
            sleep 10
            curl -f http://localhost/health || exit 1
```

> [!TIP] 提示
> 在生产环境中，建议使用 Docker Config 来管理 Stack 文件，而不是在 CI 服务器上维护一份副本。可以通过 `docker config create` 创建配置，然后在部署时引用。或者更好的做法是用 Git 管理 Stack 文件，CI 时拉取最新版本。

## 17.5 Swarm 集群监控

没有监控的集群就像没有仪表盘的汽车——你只知道它在"跑"，但不知道跑多快、油还剩多少、发动机温度是否正常。

### 17.5.1 cAdvisor —— 容器级别的监控

```yaml
# monitoring-stack.yml
# 监控 Stack 部署文件

version: '3.8'

services:
  # cAdvisor：容器资源监控
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.49.1
    ports:
      - "8880:8080"
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
      - /dev/disk/:/dev/disk:ro
    deploy:
      mode: global
      # global 模式：每个节点上运行一个实例
      # 不像 replicated 模式那样指定副本数
      # 就像每个城市都有一个天气预报站
      resources:
        limits:
          memory: 128M
    networks:
      - monitoring

  # Prometheus：指标收集和存储
  prometheus:
    image: prom/prometheus:v2.50.0
    ports:
      - "9090:9090"
    configs:
      - source: prometheus_config
        target: /etc/prometheus/prometheus.yml
    volumes:
      - prometheus-data:/prometheus
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.role == manager
    networks:
      - monitoring

  # Grafana：可视化仪表盘
  grafana:
    image: grafana/grafana:10.3.0
    ports:
      - "3001:3000"
    environment:
      - GF_SECURITY_ADMIN_PASSWORD__FILE=/run/secrets/grafana_password
    secrets:
      - grafana_password
    volumes:
      - grafana-data:/var/lib/grafana
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.role == manager
    networks:
      - monitoring

configs:
  prometheus_config:
    external: true

secrets:
  grafana_password:
    external: true

volumes:
  prometheus-data:
  grafana-data:

networks:
  monitoring:
    driver: overlay
```

```bash
# 部署前创建 Prometheus 配置
cat > prometheus.yml << 'EOF'
global:
  scrape_interval: 15s
  # 每15秒采集一次指标

scrape_configs:
  # 采集 cAdvisor 的指标
  - job_name: 'cadvisor'
    dns_sd_configs:
      - names:
          - 'tasks.cadvisor'
          # Swarm 的 DNS 服务发现
          # tasks.<service_name> 会返回所有实例的 IP
        type: 'A'
        port: 8080

  # 采集 Docker daemon 的指标
  - job_name: 'docker'
    dockerswarm_sd_configs:
      - host: tcp://localhost:2376
        role: nodes
    # 需要在 Docker daemon 中启用 metrics
EOF

# 创建 Config 和 Secret
docker config create prometheus_config prometheus.yml
printf "GrafanaAdmin2024" | docker secret create grafana_password -

# 部署监控 Stack
docker stack deploy -c monitoring-stack.yml monitoring
```

### 17.5.2 Node Exporter —— 节点级别的监控

```yaml
# 添加到监控 Stack 中
services:
  node-exporter:
    image: prom/node-exporter:v1.7.0
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro
    command:
      - '--path.procfs=/host/proc'
      - '--path.rootfs=/rootfs'
      - '--path.sysfs=/host/sys'
      - '--collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($$|/)'
    deploy:
      mode: global
      # 每个节点一个 Node Exporter
      resources:
        limits:
          memory: 64M
    networks:
      - monitoring
```

```bash
监控指标速查表

├─────────────────┼────────────────────────┼──────────────────┤

├─────────────────┼────────────────────────┼──────────────────┤

├─────────────────┼────────────────────────┼──────────────────┤
│ Docker          │ 容器重启次数             │ > 3 次/小时       │

```

> [!TIP] 提示
> 监控系统的"黄金三问"（Google SRE 的四个黄金信号）：延迟（Latency）、流量（Traffic）、错误率（Errors）、饱和度（Saturation）。先监控这四个维度，其他的可以慢慢加。不要一开始就搞了200个告警规则，最后全是噪音，真正的告警反而被淹没了。

## 17.6 故障排查

当集群出问题时，你需要一套系统化的排查方法，而不是到处乱点碰运气。

### 17.6.1 节点失联

```bash
# 症状：docker node ls 显示某个节点状态为 Down

# 步骤1：确认节点是否真的失联
ping worker3
ssh worker3 "docker info"
# 如果 SSH 也连不上，说明是网络或节点本身的问题

# 步骤2：检查 Swarm 通信端口
# Swarm 需要以下端口：
#   2377/tcp - 集群管理通信
#   7946/tcp+udp - 节点间通信
#   4789/udp - Overlay 网络
# 检查防火墙是否放行了这些端口

ssh worker3 "ss -tlnp | grep -E '2377|7946'"
ssh worker3 "ss -ulnp | grep -E '7946|4789'"

# 步骤3：查看 Docker 日志
ssh worker3 "journalctl -u docker --since '1 hour ago'"
# 或者
ssh worker3 "docker logs <容器名> 2>&1 | tail -50"

# 步骤4：如果节点无法恢复，移除它
docker node rm worker3 --force
# --force：即使节点无法联系也强制移除
# 之后在修复后的节点上重新 join 集群
```

### 17.6.2 服务启动失败

```bash
# 症状：服务创建后，副本一直无法达到目标数量
# docker service ls 显示 REPLICAS 为 0/3

# 步骤1：查看任务状态
docker service ps myapp_api --no-trunc
# 关注 STATUS 和 ERROR 列
# 常见状态：
#   "Preparing" - 正在拉取镜像或准备网络
#   "Starting"  - 容器正在启动
#   "Running"   - 正常运行
#   "Failed"    - 启动失败
#   "Rejected"  - 被调度拒绝

# 步骤2：查看具体错误信息
docker service ps myapp_api --no-trunc --filter "desired-state=shutdown"
# 查看最近失败的任务及其错误信息

# 常见错误及解决方案：

# 错误1："No suitable node (scheduling constraints not satisfied)"
# 原因：没有节点满足 placement constraints
# 解决：检查节点标签和约束条件
docker node ls -q | xargs docker node inspect --format '{{.ID}} {{.Hostname}} {{.Spec.Labels}}'

# 错误2："No suitable node (insufficient resources)"
# 原因：节点资源不足以满足 reservations
# 解决：检查节点可用资源
docker node inspect worker1 --format '{{.Description.Resources}}'

# 错误3："image not found" 或 "unauthorized"
# 原因：镜像拉取失败（不存在或未认证）
# 解决：确认镜像名称正确，Registry 认证配置正确
docker stack deploy --with-registry-auth -c stack.yml myapp

# 错误4："container exited with code 137"
# 原因：容器内存超限被 OOM Kill
# 解决：增加 memory limit，或优化应用内存使用
docker service update --limit-memory 1G myapp_api

# 错误5："task: non-zero exit (1)"
# 原因：应用程序本身崩溃了
# 解决：查看应用日志
docker service logs myapp_api --tail 100
```

### 17.6.3 网络不通

```bash
# 症状：Service A 无法通过服务名访问 Service B

# 步骤1：确认两个服务在同一个 overlay 网络中
docker service inspect myapp_api --format '{{json .Spec.Networks}}' | python3 -m json.tool
docker service inspect myapp_web --format '{{json .Spec.Networks}}' | python3 -m json.tool

# 步骤2：检查 overlay 网络状态
docker network inspect myapp_backend
# 查看网络中有哪些容器

# 步骤3：在容器内测试连通性
# 启动一个调试容器加入同一个网络
docker service create \
  --name debug \
  --network myapp_backend \
  --detach \
  alpine sleep 3600

# 进入调试容器
docker exec -it $(docker ps -q -f name=debug) sh

# 在容器内测试
ping api           # 测试 DNS 解析和 ICMP 连通性
nslookup api       # 测试 DNS 解析
wget -qO- http://api:8080/health  # 测试 HTTP 连通性
# 如果 DNS 解析失败，可能是 Swarm 的内置 DNS 出了问题
# 如果 DNS 解析成功但连接失败，检查端口和防火墙

# 清理调试容器
docker service rm debug

# 步骤4：检查 Overlay 网络端口
# Overlay 网络需要 UDP 4789 端口
# 在节点间测试
nc -zvu 192.168.1.101 4789
# 如果不通，检查防火墙和网络配置
```

> [!WARNING] 注意
> Overlay 网络最常见的故障原因是 UDP 4789 端口被防火墙阻挡。很多防火墙默认不开放 UDP 端口。记住：Overlay 用的是 **UDP** 4789，不是 TCP。排查时别测错了协议。

### 17.6.4 故障排查决策树

```bash
服务出问题了？
│
├── docker node ls → 有节点 Down？
│   ├── 是 → 检查节点网络/防火墙/Docker 服务
│   └── 否 → 继续
│
├── docker service ps <service> --no-trunc → 查看任务状态
│   ├── Preparing → 镜像拉取中或慢 → 检查 Registry 连通性
│   ├── Rejected → 资源不足或约束不满足 → 检查节点资源和标签
│   ├── Failed → 容器启动失败 → 查看错误信息和日志
│   └── 反复 Running → Shutdown → 应用崩溃循环 → 查看应用日志
│
├── docker service logs <service> → 查看应用日志
│   ├── OOM Killed → 增加内存限制
│   ├── Connection refused → 依赖服务未就绪
│   ├── Permission denied → 检查用户权限和 Secrets
│   └── 应用错误 → 代码 Bug，修代码
│
└── 网络不通？
    ├── DNS 解析失败 → 检查 overlay 网络配置
    ├── 连接超时 → 检查防火墙和端口（4789/UDP）
    └── 连接被拒绝 → 检查目标服务的监听端口
```

## 17.7 Swarm 数据备份与恢复

集群数据是 Swarm 的"大脑记忆"，丢了就全完了。定期备份是必须的。

```bash
# ====== 备份 Swarm 数据 ======

# Swarm 的 Raft 日志（集群状态数据）存储在 Manager 节点的：
# /var/lib/docker/swarm/

# 备份前停止 Docker daemon（推荐，确保数据一致性）
systemctl stop docker

# 备份 Swarm 数据
tar czf swarm-backup-$(date +%Y%m%d).tar.gz \
  /var/lib/docker/swarm/

# 重新启动 Docker
systemctl start docker

# ====== 自动化备份脚本 ======
cat > /usr/local/bin/backup-swarm.sh << 'SCRIPT'
#!/bin/bash
# Swarm 集群自动备份脚本

BACKUP_DIR="/opt/backups/swarm"
DATE=$(date +%Y%m%d_%H%M%S)
RETENTION_DAYS=30

mkdir -p ${BACKUP_DIR}

# 停止 Docker（短暂停机）
systemctl stop docker

# 备份
tar czf ${BACKUP_DIR}/swarm-${DATE}.tar.gz \
  /var/lib/docker/swarm/ \
  /etc/docker/

# 恢复 Docker
systemctl start docker

# 清理旧备份
find ${BACKUP_DIR} -name "swarm-*.tar.gz" -mtime +${RETENTION_DAYS} -delete

echo "Backup completed: swarm-${DATE}.tar.gz"
SCRIPT

chmod +x /usr/local/bin/backup-swarm.sh

# 添加到 crontab，每天凌晨2点备份
echo "0 2 * * * /usr/local/bin/backup-swarm.sh >> /var/log/swarm-backup.log 2>&1" | crontab -
```

```bash
# ====== 恢复 Swarm 数据 ======

# 警告：恢复操作会覆盖当前集群状态！
# 确保你知道自己在做什么

# 1. 停止 Docker
systemctl stop docker

# 2. 清理现有 Swarm 数据
rm -rf /var/lib/docker/swarm/

# 3. 解压备份
tar xzf swarm-backup-20240115.tar.gz -C /

# 4. 启动 Docker
systemctl start docker

# 5. 验证集群状态
docker node ls
docker service ls
```

> [!WARNING] 注意
> 恢复 Swarm 数据是一个破坏性操作。在多 Manager 集群中，如果你只恢复了一个 Manager 的数据，可能会导致 Raft 共识冲突。最佳实践是：如果要恢复，就在所有 Manager 节点上同时恢复相同的备份。

## 17.8 什么时候该从 Swarm 迁移到 Kubernetes

Swarm 很好用，但它不是万能的。以下是你应该考虑迁移到 K8s 的信号：

```bash
┌────────────────────────────────────────────────────────┐
│              该迁移到 K8s 的信号                         │
├────────────────────────────────────────────────────────┤
│                                                         │
│  ✅ 继续使用 Swarm 的情况：                              │
│                                                         │
│  • 集群规模 < 50 个节点                                 │
│  • 服务数量 < 30 个                                     │
│  • 团队没有专职运维/DevOps                               │
│  • 不需要复杂的自动扩缩容                               │
│  • 不需要 Service Mesh（Istio 等）                      │
│  • 老板没说要迁移到 K8s 😂                              │
│                                                         │
│  ⚠️ 考虑迁移到 K8s 的信号：                              │
│                                                         │
│  • 集群规模持续增长，超过 50 个节点                      │
│  • 需要复杂的自动扩缩容（HPA/VPA/CA）                   │
│  • 需要丰富的生态工具（Helm、ArgoCD、Istio）            │
│  • 团队有专职运维/DevOps 人员                           │
│  • 客户要求或合规要求使用 K8s                           │
│  • 需要跨云部署（多云/混合云策略）                      │
│  • 你想在简历上写"K8s 经验" 😏                          │
│                                                         │
└────────────────────────────────────────────────────────┘
```

迁移不是一夜之间的事。一个务实的迁移路径：

```bash
阶段1：学习和评估（1-2周）
  ├── 在测试环境搭建 K8s 集群
  ├── 将1-2个非核心服务迁移到 K8s
  └── 评估运维复杂度和团队学习成本

阶段2：并行运行（1-3个月）
  ├── 新服务部署到 K8s
  ├── 老服务继续留在 Swarm
  └── 逐步积累 K8s 运维经验

阶段3：全面迁移（3-6个月）
  ├── 将剩余服务逐个迁移
  ├── 迁移完成后下线 Swarm 集群
  └── 统一使用 K8s 生态工具
```

> [!TIP] 提示
> 不要因为"K8s 是行业标准"就急着迁移。技术选型的第一原则是"解决当前问题"，而不是"追最新潮流"。如果你的 Swarm 集群运行得好好的，团队也很熟悉，那完全可以继续用。记住：**最好的架构是能稳定运行且团队能维护的架构**，而不是最复杂的架构。

## 本章小结

| 概念 | 说明 |
|------|------|
| 高可用 | 多 Manager 节点 + Raft 共识，避免单点故障 |
| 节点标签 | 精确控制服务的调度位置 |
| 资源管理 | limits（硬限制）和 reservations（软预留） |
| CI/CD 集成 | 通过 SSH + Stack Deploy 实现自动化部署 |
| 监控 | cAdvisor + Prometheus + Grafana 三件套 |
| 故障排查 | 系统化的排查流程：节点 → 任务 → 日志 → 网络 |
| 数据备份 | 定期备份 `/var/lib/docker/swarm/` |
| 迁移 K8s | 根据实际需求决定，不要为了追潮流而迁移 |

## 练习

1. **入门**：为你的 Swarm 集群部署 cAdvisor + Prometheus + Grafana 监控栈，创建一个 Grafana 仪表盘展示集群 CPU 和内存使用情况。
2. **进阶**：模拟一个 Worker 节点故障（`docker swarm leave --force` 或直接关闭虚拟机），练习完整的故障排查流程，记录从发现问题到恢复的全过程。
3. **挑战**：为你的 Swarm 集群设计并实施一套完整的备份策略：包括 Swarm 状态备份、数据库备份、以及 Secret 备份，并验证恢复流程可行。
