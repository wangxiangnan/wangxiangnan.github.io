# Ch09: 代码规范统一

## 本章目标

> 在 monorepo 中建立一套"不可违反"的代码规范体系：ESLint 保证代码质量，Prettier 保证格式一致，Husky + lint-staged 在提交前自动修复，commitlint 规范提交信息。所有配置集中管理在 packages 中，各项目继承使用。

## 9.1 ESLint 9 Flat Config 架构

ESLint 9 引入了 flat config（扁平化配置）格式，取代了旧版的 `.eslintrc` 文件。在 monorepo 中，我们在 `packages/eslint-config` 中定义共享配置。

首先更新 `packages/eslint-config/package.json`：

```json
{
  "name": "@monorepo/eslint-config",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "exports": {
    "./base": "./base.js",
    "./vue": "./vue.js",
    "./node": "./node.js"
  },
  "dependencies": {
    "@eslint/js": "^9.10.0",
    "typescript-eslint": "^8.5.0",
    "eslint-plugin-vue": "^9.28.0",
    "eslint-config-prettier": "^9.1.0",
    "globals": "^15.9.0"
  },
  "peerDependencies": {
    "eslint": "^9.0.0"
  }
}
```

安装根目录的 ESLint：

```bash
pnpm add -Dw eslint
```

### base.js — 通用规则（所有项目共享）

创建 `packages/eslint-config/base.js`：

```javascript
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import prettierConfig from 'eslint-config-prettier';
import globals from 'globals';

/**
 * 基础 ESLint 配置 — 所有项目继承此配置
 * 
 * 为什么使用 flat config？
 * - 不再需要 .eslintrc 和 extends 的隐式解析
 * - 配置就是普通的 JS 数组，可以 import/export/组合
 * - 类型安全更好（配合 @types/eslint）
 */
export const baseConfig = [
  // 1. ESLint 推荐规则
  js.configs.recommended,

  // 2. TypeScript ESLint 推荐规则
  ...tseslint.configs.recommended,

  // 3. 关闭与 Prettier 冲突的规则
  // Prettier 负责格式化，ESLint 不应该再管格式问题
  prettierConfig,

  // 4. 自定义规则
  {
    languageOptions: {
      ecmaVersion: 'latest',
      sourceType: 'module',
      globals: {
        ...globals.es2022,
      },
    },
    rules: {
      // ====== 代码质量规则 ======

      // 禁止使用 var，强制使用 let/const
      'no-var': 'error',

      // 优先使用 const，只有需要重新赋值时才用 let
      'prefer-const': 'error',

      // 禁止未使用的变量（但允许以 _ 开头的参数，如 _req, _next）
      '@typescript-eslint/no-unused-vars': ['error', {
        argsIgnorePattern: '^_',
        varsIgnorePattern: '^_',
      }],

      // 允许使用 any 但在 CI 中给出警告（渐进式迁移策略）
      '@typescript-eslint/no-explicit-any': 'warn',

      // 强制使用 import type 导入纯类型
      '@typescript-eslint/consistent-type-imports': ['error', {
        prefer: 'type-imports',
        fixStyle: 'inline-type-imports',
      }],

      // 禁止空的 catch 块（至少要注释说明为什么忽略错误）
      'no-empty': ['error', { allowEmptyCatch: false }],

      // 禁止 console.log（但允许 console.warn 和 console.error）
      'no-console': ['warn', { allow: ['warn', 'error'] }],

      // 强制使用 === 和 !==
      eqeqeq: ['error', 'always'],
    },
  },

  // 5. 忽略规则
  {
    ignores: [
      '**/node_modules/**',
      '**/dist/**',
      '**/.turbo/**',
      '**/coverage/**',
    ],
  },
];
```

### vue.js — Vue 前端专用规则

创建 `packages/eslint-config/vue.js`：

```javascript
import pluginVue from 'eslint-plugin-vue';
import globals from 'globals';
import { baseConfig } from './base.js';

/**
 * Vue 项目 ESLint 配置
 * 在 base 基础上增加 Vue 特定规则
 */
export const vueConfig = [
  ...baseConfig,

  // Vue 推荐规则
  ...pluginVue.configs['flat/recommended'],

  {
    languageOptions: {
      globals: {
        ...globals.browser,
      },
    },
    rules: {
      // ====== Vue 特定规则 ======

      // 强制组件使用多单词名称（避免与 HTML 元素冲突）
      'vue/multi-word-component-names': 'off',

      // 强制 <script setup> 风格（Vue 3 推荐）
      'vue/component-api-style': ['error', ['script-setup']],

      // 强制 props 使用类型定义（而不是运行时声明）
      'vue/define-macros-order': ['error', {
        order: ['defineProps', 'defineEmits', 'defineSlots', 'defineModel'],
      }],

      // 组件属性排序：推荐顺序
      'vue/attributes-order': ['error', {
        order: [
          'DEFINITION',   // is, v-is
          'LIST_RENDERING', // v-for
          'CONDITIONALS',  // v-if, v-else-if, v-else, v-show
          'RENDER_MODIFIERS', // v-once, v-pre
          'GLOBAL',        // id
          'UNIQUE',        // ref, key
          'SLOT',          // v-slot, slot
          'TWO_WAY_BINDING', // v-model
          'OTHER_DIRECTIVES', // v-custom
          'OTHER_ATTR',    // 其他属性
          'EVENTS',        // @click 等
          'CONTENT',       // v-html, v-text
        ],
      }],

      // 关闭一些过于严格的规则
      'vue/no-v-html': 'off',
      'vue/require-default-prop': 'off',
    },
  },
];
```

### node.js — Node.js 后端专用规则

创建 `packages/eslint-config/node.js`：

```javascript
import globals from 'globals';
import { baseConfig } from './base.js';

/**
 * Node.js 项目 ESLint 配置
 * 在 base 基础上增加 Node.js 特定规则
 */
export const nodeConfig = [
  ...baseConfig,

  {
    languageOptions: {
      globals: {
        ...globals.node,
      },
    },
    rules: {
      // ====== Node.js 特定规则 ======

      // 允许 console（后端需要日志）
      'no-console': 'off',

      // 强制处理 Promise 的 rejection
      'no-unhandled-rejections': 'off', // 由 TypeScript 的严格模式覆盖

      // 禁止同步的文件系统操作（在请求处理中）
      'no-sync': 'off', // 在 CLI 脚本中可能需要，暂时关闭
    },
  },
];
```

```javascript

  ...baseConfig,
  {
    // shared 包需要最严格的类型检查
    rules: {
      '@typescript-eslint/no-explicit-any': 'error',

    "lint": "turbo lint",
    "lint:fix": "turbo lint:fix"
  }
}
```

```json
// apps/web, apps/api, packages/shared
{
  "scripts": {
    "lint": "eslint . --report-unused-disable-directives",
    "lint:fix": "eslint . --fix --report-unused-disable-directives"
  }

```

## 9.3 Prettier 配置共享

在根目录创建 Prettier 配置，这样所有项目自动继承：

创建 `.prettierrc`（根目录）：

```json
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100,
  "bracketSpacing": true,
  "arrowParens": "always",
  "endOfLine": "lf",
  "htmlWhitespaceSensitivity": "ignore",
  "vueIndentScriptAndStyle": false
}
```

创建 `.prettierignore`（根目录）：

```
node_modules
dist
.turbo
coverage
pnpm-lock.yaml
*.prisma
```

**为什么 Prettier 配置放在根目录而不是 packages 中？**

Prettier 会自动向上查找最近的配置文件。放在根目录确保所有文件（包括根目录的配置文件本身）都使用统一的格式化规则。如果放在 packages 中，根目录的文件就没有 Prettier 配置覆盖。

安装 Prettier：

```bash
pnpm add -Dw prettier
```

在根目录添加格式化脚本：

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

## 9.4 Husky + lint-staged：提交前自动检查

这是整个代码规范体系的"执行层"——无论开发者是否记得运行 lint，提交代码时都会自动执行检查。

安装依赖：

```bash
pnpm add -Dw husky lint-staged
```

初始化 Husky：

```bash
npx husky init
```

这会在项目根目录创建 `.husky/` 目录和 `pre-commit` 钩子文件。

编辑 `.husky/pre-commit`：

```bash
#!/bin/sh
pnpm exec lint-staged
```

**为什么用 lint-staged 而不是直接运行 lint？**

`lint-staged` 只对 **staged 的文件**（即 `git add` 的文件）执行 lint 和格式化。如果直接运行 `eslint .`，在一个有几千个文件的项目中，每次提交都要检查所有文件——慢得让人想跳过。`lint-staged` 只检查你本次改动的文件，通常 1-2 秒就能完成。

在根目录 `package.json` 中配置 lint-staged：

```json
{
  "lint-staged": {
    "*.{ts,tsx,vue}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{js,jsx,mjs,cjs}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{json,yaml,yml,md,css,scss,html}": [
      "prettier --write"
    ]
  }
}
```

**工作流程：**

```
开发者输入 git commit
       │
       ▼
Husky 拦截 pre-commit 钩子
       │
       ▼
lint-staged 获取 staged 文件列表
       │
       ├── *.ts, *.vue 文件 → ESLint --fix → Prettier --write
       │
       ├── *.json, *.md 文件 → Prettier --write
       │
       ▼
如果有任何错误（无法自动修复的）→ 提交失败，显示错误详情
如果全部通过（或自动修复成功）→ 自动 stage 修复后的文件 → 提交成功
```

在 `prepare` 脚本中自动安装 Husky 钩子（这样新人 clone 后 `pnpm install` 就能自动设置）：

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

## 9.5 commitlint：规范 Commit Message

安装依赖：

```bash
pnpm add -Dw @commitlint/cli @commitlint/config-conventional
```

创建根目录 `commitlint.config.js`：

```javascript
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    // type 必须是以下值之一
    'type-enum': [2, 'always', [
      'feat',     // 新功能
      'fix',      // 修复 Bug
      'docs',     // 文档变更
      'style',    // 代码格式（不影响代码含义的修改）
      'refactor', // 代码重构（既不是新功能也不是修复）
      'perf',     // 性能优化
      'test',     // 测试相关
      'build',    // 构建系统或外部依赖变更
      'ci',       // CI 配置变更
      'chore',    // 其他不修改源代码的变更
      'revert',   // 回滚提交
    ]],

    // scope 是可选的（不强制要求）
    'scope-empty': [0],

    // subject 不能为空
    'subject-empty': [2, 'never'],

    // subject 不能以句号结尾
    'subject-full-stop': [2, 'never', '.'],

    // subject 使用小写开头
    'subject-case': [2, 'never', ['sentence-case', 'start-case', 'pascal-case', 'upper-case']],
  },
};
```

在 `.husky/` 中创建 `commit-msg` 钩子：

```bash
#!/bin/sh
pnpm exec commitlint --edit "$1"
```

**Conventional Commits 格式：**

```
<type>(<scope>): <subject>

<body>

<footer>
```

示例：

```bash
# ✅ 正确
feat(shared): add Zod validation schemas for user DTOs
fix(api): handle undefined user in getUser controller
docs(readme): update installation instructions
refactor(web): extract api client into separate module

# ❌ 错误 — 会拒绝提交
added new feature          # 没有 type
fix: something.            # subject 以句号结尾
Update code                # type 不在枚举列表中
```

**为什么 commit message 规范如此重要？**

1. **自动生成 CHANGELOG**：工具如 `standard-version` 可以根据 commit 类型自动生成版本日志
2. **语义化版本**：`feat` 提交触发 minor 版本升级，`fix` 触发 patch 版本升级
3. **快速浏览历史**：`git log --oneline` 时，规范的 commit message 让历史一目了然
4. **团队协作**：统一了所有人的提交风格，减少了 "update" "fix" "wip" 这样的无效提交信息

## 9.7 Turborepo 中的 lint 任务配置

编辑根目录 `turbo.json`，确保 lint 任务被正确配置：

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "lint": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "*.ts", "*.vue", "*.js"]
    },
    "lint:fix": {
      "cache": false
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "*.ts", "*.vue"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
```

**为什么 lint 要 `dependsOn: ["^build"]`？**

因为 ESLint 在检查 TypeScript 文件时需要解析类型信息（`@typescript-eslint` 的类型感知规则需要 `.d.ts` 文件）。如果 shared 包还没有构建，ESLint 在检查 apps/web 时可能无法解析 shared 包的类型。依赖 `^build` 确保 lint 运行时所有依赖包都已构建完毕。

## 9.8 完整的开发工作流

将所有工具串联起来，一个典型的开发流程如下：

```bash
# 1. 克隆项目
git clone <repo-url>
cd monorepo
pnpm install          # 自动执行 prepare 脚本，安装 Husky 钩子

# 2. 日常开发
pnpm dev              # 启动所有开发服务器（Vite + Express）

# 3. 编写代码
# - 保存文件时，VS Code 自动 ESLint fix + Prettier 格式化
# - 类型错误实时在编辑器中标红

# 4. 提交代码
git add .
git commit -m "feat(shared): add user validation schemas"
#   │
#   ├── Husky pre-commit → lint-staged → ESLint + Prettier（仅 staged 文件）
#   ├── Husky commit-msg → commitlint 检查 commit message 格式
#   └── 全部通过 → 提交成功

# 5. CI 流水线（GitHub Actions 等）
# - pnpm install
# - turbo build        → 构建所有包
# - turbo lint         → ESLint 检查所有文件
# - turbo typecheck    → TypeScript 类型检查
# - turbo test         → 运行测试
```

## 9.9 常见配置问题和解决方案

### 问题 1：ESLint 报 "Parsing error: Cannot find module '@monorepo/shared'"

**原因：** ESLint 在类型感知模式下需要解析 import 的模块，但 shared 包还没有构建。

**解决：** 确保 `turbo.json` 中 lint 任务有 `dependsOn: ["^build"]`，或在运行 lint 前先构建：

```bash
turbo build lint  # build 会先于 lint 执行
```

### 问题 2：Husky 钩子不执行

**排查：**

```bash
# 检查 .husky 目录是否存在
ls -la .husky/

# 检查 Git hooks 路径
git config core.hooksPath   # 应该输出 .husky

# 重新初始化
npx husky init
```

### 问题 3：Prettier 和 ESLint 规则冲突

**解决：** 确保 `eslint-config-prettier` 在 ESLint 配置数组的**最后面**（它会关闭所有与 Prettier 冲突的 ESLint 规则）。在我们的配置中，它已经集成在 `base.js` 的第 3 步。

### 问题 4：VS Code 中 ESLint 不工作

**排查：**

```json
// 在 .vscode/settings.json 中确认：
{
  "eslint.useFlatConfig": true   // ESLint 9 flat config 必须开启
}
```

如果仍然不工作，尝试在 VS Code 命令面板中执行 `ESLint: Restart ESLint Server`。

### 问题 5：lint-staged 在大项目中太慢

**优化：** 可以配置 lint-staged 并行执行，并只运行必要的检查：

```json
{
  "lint-staged": {
    "*.{ts,vue}": [
      "eslint --fix --max-warnings 0",
      "prettier --write"
    ]
  }
}
```

如果仍然太慢，考虑使用 `--cache` 标志：

```json
{
  "*.{ts,vue}": [
    "eslint --fix --cache --max-warnings 0",
    "prettier --write"
  ]
}
```

- ESLint 9 flat config 以 JS 模块的形式组织配置，在 monorepo 中更灵活、更可组合
- Prettier 放在根目录确保全局统一的格式化规则
- Husky + lint-staged 形成了"提交门禁"，自动修复可修复的问题，阻止不可修复的问题
- commitlint 规范提交信息，为自动 CHANGELOG 生成和语义化版本打基础
- VS Code 工作区设置和 EditorConfig 确保团队成员"开箱即用"
