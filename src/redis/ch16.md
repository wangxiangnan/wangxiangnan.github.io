# 第16章：Cluster 集群——Redis 的水平扩展之路

## 引言：从单体到微服务

还记得你刚学编程时写的第一个项目吗？所有代码塞在一个文件里，一个数据库搞定一切。随着用户增长，你发现：单文件扛不住了，得分模块、拆服务。

Redis 也有同样的成长烦恼。单机 Redis 受限于：

- 单机内存上限（比如 256GB）
- 单机网络带宽（比如 10Gbps）
- 单机 CPU 处理能力

当你需要存储 1TB 的数据、每秒处理百万请求时，单机 Redis 就像一台被踩满油门的老旧发动机——再怎么调优也力不从心。

Redis Cluster 就是给 Redis 装上了**分布式引擎**——它自动将数据分片到多个节点上，每个节点只负责一部分数据。就像数据库的分库分表，但是 Redis 帮你自动搞定了所有路由逻辑。

> **编程隐喻时间**：Redis Cluster 类似于数据库分库分表 + 自动路由。想象你有一个巨大的 HashMap，Cluster 自动根据 key 的哈希值将数据分配到不同的"桶"（节点）里。当客户端访问了错误的节点时，那个节点会回复"你走错门了，去那边找"（MOVED 重定向）。

## 16.1 为什么单机 Redis 不够用？

| 限制 | 单机表现 | Cluster 解决方案 |
|------|----------|------------------|
| 内存 | 受限于单台服务器的内存 | 数据分布在多个节点 |
| 吞吐量 | 受限于单核 CPU | 多节点并行处理 |
| 网络带宽 | 受限于单网卡 | 多网卡多节点 |
| 高可用 | 单点故障 | 每个分片有 Replica |

## 16.2 Redis Cluster 的设计思想

### 16.2.1 哈希槽（Hash Slot）

Redis Cluster 的核心设计是 **16384 个哈希槽**。为什么是 16384？

- 每个槽在心跳包中需要用 1 bit 表示，16384 个槽 = 2KB 的压缩位图
- Redis 不建议集群超过 1000 个节点，16384 个槽已经足够分配
- 槽的数量是 2 的幂次方，方便计算

```
Key: "user:1001"
    |
CRC16("user:1001") = 12345（0~65535 范围）
    |
12345 % 16384 = 12345（取模得到槽编号）
    |
Slot 12345 属于 Node-B
    |
将请求路由到 Node-B
```

### 16.2.2 CRC16 哈希算法与 Hash Tag

```js
const Redis = require('ioredis');

// 手动计算 key 对应的槽
function calculateSlot(key) {
  const slot = Redis.Cluster.calculateSlot(key);
  return slot;
}

// Hash Tag 机制：强制多个 key 分配到同一个槽
// 使用 {tag} 语法，只计算 tag 部分的哈希
const slot1 = calculateSlot('{user:1001}.following');
const slot2 = calculateSlot('{user:1001}.followers');
console.log(slot1 === slot2); // true

// 这在 Cluster 模式下非常重要：
// 只有同一个槽的 key 才能在同一个 Pipeline/MULTI 中操作
```

### 16.2.3 槽的分配

假设 3 个 Master 节点，16384 个槽平均分配：

```
Node-A (Master-1): 槽 0 ~ 5460
Node-B (Master-2): 槽 5461 ~ 10922
Node-C (Master-3): 槽 10923 ~ 16383

每个 Master 可以有自己的 Replica：
Node-A (Master-1) <--> Node-D (Replica-1)
Node-B (Master-2) <--> Node-E (Replica-2)
Node-C (Master-3) <--> Node-F (Replica-3)
```

## 16.3 搭建 Redis Cluster

### 16.3.1 使用 redis-cli 快速搭建

```bash
# 每个节点的 redis.conf 需要包含：
# port 7001
# cluster-enabled yes
# cluster-config-file nodes-7001.conf
# cluster-node-timeout 5000
# appendonly yes

# 启动所有 6 个节点
redis-server redis-7001.conf &
redis-server redis-7002.conf &
redis-server redis-7003.conf &
redis-server redis-7004.conf &
redis-server redis-7005.conf &
redis-server redis-7006.conf &

# 创建集群（--cluster-replicas 1 表示每个 Master 有 1 个 Replica）
redis-cli --cluster create \
  127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 \
  127.0.0.1:7004 127.0.0.1:7005 127.0.0.1:7006 \
  --cluster-replicas 1
```

### 16.3.2 集群状态检查

```bash
# 查看集群信息
redis-cli -p 7001 CLUSTER INFO
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_ok:16384
# cluster_known_nodes:6
# cluster_size:3

# 查看集群节点详情
redis-cli -p 7001 CLUSTER NODES
```

## 16.4 集群操作

### 16.4.1 数据路由（MOVED / ASK 重定向）

**MOVED 重定向**（永久性迁移）：

```
Client -> Node-A: SET "hello" "world"
Node-A -> Client: MOVED 3999 127.0.0.1:7002
```

意思是："槽 3999 永久属于 Node-B（7002），请你以后直接找它。"

**ASK 重定向**（临时迁移中）：

```
Client -> Node-A: SET "hello" "world"
Node-A -> Client: ASK 3999 127.0.0.1:7002
Client -> Node-B: ASKING
Client -> Node-B: SET "hello" "world"
```

意思是："槽 3999 正在从 Node-A 迁移到 Node-B，这次请去 Node-B 操作，但下次还是先问我。"

> [!TIP] 提示
> ：如果你使用 ioredis 的 Cluster 模式，这些重定向都是自动处理的。

### 16.4.2 槽迁移

```bash
# 将槽 1000 从节点 7001 迁移到节点 7002

# Step 1: 在目标节点设置 IMPORTING 状态
redis-cli -p 7002 CLUSTER SETSLOT 1000 IMPORTING <source-node-id>

# Step 2: 在源节点设置 MIGRATING 状态
redis-cli -p 7001 CLUSTER SETSLOT 1000 MIGRATING <target-node-id>

# Step 3: 迁移该槽的所有 key
redis-cli -p 7001 CLUSTER GETKEYSINSLOT 1000 100
redis-cli -p 7001 MIGRATE 127.0.0.1 7002 "" 0 5000 KEYS key1 key2 ...

# Step 4: 更新槽归属
redis-cli -p 7001 CLUSTER SETSLOT 1000 NODE <target-node-id>
redis-cli -p 7002 CLUSTER SETSLOT 1000 NODE <target-node-id>
```

## 16.5 Node.js 连接 Cluster

### 16.5.1 ioredis 的 Cluster 模式

```js
const Redis = require('ioredis');

// 连接 Redis Cluster
const cluster = new Redis.Cluster([
  { host: '127.0.0.1', port: 7001 },
  { host: '127.0.0.1', port: 7002 },
  { host: '127.0.0.1', port: 7003 },
  // 不需要列出所有节点，ioredis 会自动发现
], {
  scaleReads: 'slave',      // 读请求分发到 Replica
  redisOptions: {
    password: 'your_password',
  },
  retryStrategy(times) {
    return Math.min(times * 200, 5000);
  },
});

cluster.on('connect', () => {
  console.log('[Cluster] 已连接到 Redis Cluster');
});

cluster.on('error', (err) => {
  console.error('[Cluster] 错误:', err.message);
});

// 正常使用，路由完全自动
(async () => {
  await cluster.set('user:1001', JSON.stringify({ name: '张三' }));
  const user = await cluster.get('user:1001');
  console.log('用户信息:', user);

  // Pipeline 在 Cluster 中：所有 key 必须在同一个槽中
  const pipeline = cluster.pipeline();
  pipeline.set('{cart:1001}.item1', 'apple');
  pipeline.set('{cart:1001}.item2', 'banana');
  pipeline.get('{cart:1001}.item1');
  pipeline.get('{cart:1001}.item2');
  const results = await pipeline.exec();
  console.log('Pipeline 结果:', results);

  cluster.disconnect();
})();
```

### 16.5.2 多命令事务在 Cluster 中的限制

```js
const Redis = require('ioredis');
const cluster = new Redis.Cluster([
  { host: '127.0.0.1', port: 7001 },
  { host: '127.0.0.1', port: 7002 },
]);

(async () => {
  // 错误示例：不同 key 可能不在同一个槽
  try {
    const pipeline = cluster.pipeline();
    pipeline.decr('user:1001:balance');
    pipeline.incr('order:2001:amount');
    await pipeline.exec(); // 可能报错！
  } catch (err) {
    console.error('跨槽事务失败:', err.message);
  }

  // 正确示例：使用 Hash Tag 确保 key 在同一个槽
  const pipeline = cluster.pipeline();
  pipeline.decr('{tx:1001}.user_balance');
  pipeline.incr('{tx:1001}.order_amount');
  pipeline.set('{tx:1001}.status', 'completed');
  const results = await pipeline.exec();
  console.log('事务结果:', results);

  cluster.disconnect();
})();
```

## 16.6 Cluster 的限制

### 16.6.1 多 Key 操作的限制

```
支持的操作：
- 所有 key 在同一个槽中的 MULTI/EXEC
- 所有 key 在同一个槽中的 Pipeline
- 使用 Hash Tag 的多 key 操作

不支持的操作：
- 跨槽的 MULTI/EXEC 事务
- 跨多个节点的 MOVE 命令
- 不同槽的 key 之间的 RENAME
- 跨节点的 SORT 命令（除非使用 Hash Tag）
```

### 16.6.2 不支持的命令

```
以下命令在 Cluster 中不支持或有限制：
- KEYS（只返回当前节点的 key）
- SCAN（只扫描当前节点）
- FLUSHDB / FLUSHALL（只影响当前节点）
- DBSIZE（只返回当前节点的 key 数量）
```

> [!WARNING] 注意
> 如果你的应用大量使用跨槽的多 key 操作，或者依赖 `KEYS`、`FLUSHDB` 等命令，可能需要重新设计数据模型，或者考虑使用 Sentinel 模式代替 Cluster。

## 16.7 Cluster vs Sentinel 的选择

| 特性 | Sentinel | Cluster |
|------|----------|---------|
| **数据分片** | 不支持 | 支持（16384 槽） |
| **写扩展** | 不支持 | 支持 |
| **读扩展** | 支持 | 支持 |
| **自动故障转移** | 支持 | 支持（内置） |
| **部署复杂度** | 中等 | 较高 |
| **多 Key 操作** | 完全支持 | 仅限同槽 |
| **内存利用** | 每个节点存储全量数据 | 数据分布在多节点 |
| **适用场景** | 数据量不大，需要高可用 | 数据量大，需要水平扩展 |

**简单决策树**：

- 数据量 < 单节点容量？ -> Sentinel
- 数据量 > 单节点容量？ -> Cluster
- 写 QPS > 单节点上限？ -> Cluster
- 只需要读扩展？ -> Sentinel + 多 Replica

## 小结

Redis Cluster 是 Redis 的水平扩展方案，它通过哈希槽机制将数据自动分片到多个节点。

核心概念：

- **16384 个哈希槽**：每个 key 通过 CRC16 算法映射到一个槽
- **CRC16 哈希**：确定性地将 key 分配到槽
- **MOVED/ASK 重定向**：客户端访问错误节点时的自动路由机制
- **Hash Tag**：使用 `{tag}` 语法强制多个 key 分到同一个槽

就像微服务架构将单体应用拆分成多个服务一样，Cluster 将单体 Redis 拆分成多个分片，每个分片只负责一部分数据。
