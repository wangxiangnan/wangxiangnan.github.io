## 13.1 HTTP 的设计哲学：简单就是力量

1989 年，Tim Berners-Lee 在 CERN 工作期间提出了一个想法：让科学家们能方便地通过超链接共享文档。为了实现这件事，他需要一套规则——浏览器怎么向服务器要一个文件，服务器又该怎么把文件给浏览器。这就是 HTTP（HyperText Transfer Protocol，超文本传输协议）的起源。

HTTP 的设计哲学可以总结为三个关键词：

**无状态（Stateless）**：服务器不记得你是谁。每次请求都是一个全新的交互，就像你去餐厅吃饭，服务员每次都假装第一次见你。这听起来很蠢？但这是一个极其精明的工程决策——服务器不需要为每个客户端维护状态，就能同时服务成千上万个客户端而不会内存爆炸。

**请求-响应模型（Request-Response）**：客户端发请求，服务器回响应，一来一回，干净利落。没有异步回调，没有服务端主动推送（后来才有 WebSocket 来弥补这一点，见第17章）。这种模型让 HTTP 极其容易理解和调试。

**文本可读（Human-Readable）**：HTTP/1.x 的报文是纯文本格式，你甚至可以用 Telnet 手动跟一个 Web 服务器对话。不需要专门的解码工具就能看懂报文——抓个包就能分析，调试起来非常愉快。

## 13.2 HTTP/1.1 报文格式

一个真实的 HTTP 请求报文：

```http
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0.0.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Connection: keep-alive
```

结构分四部分：

1. **请求行（Request Line）**：`GET /index.html HTTP/1.1`——方法 + 路径 + 协议版本，空格分隔。
2. **头部（Headers）**：每行一个键值对，格式 `Name: Value`。
3. **空行**：标志头部的结束。
4. **消息体（Body）**：GET 通常没有；POST 的数据在空行之后。

响应报文同构：

```http
HTTP/1.1 200 OK
Date: Mon, 15 Jan 2024 08:30:00 GMT
Server: Apache/2.4.52 (Ubuntu)
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Connection: keep-alive

<!DOCTYPE html>
<html>
<head><title>Example</title></head>
<body><h1>Hello World</h1></body>
</html>
```

1. **状态行（Status Line）**：`HTTP/1.1 200 OK`——版本 + 状态码 + 原因短语。
2. **头部**：与请求头部格式相同。
3. **空行**。
4. **消息体**：实际内容（HTML、JSON、图片二进制等）。

「先猜再读」第二问的答案：行分隔符是 **`\r\n`（CRLF）**，不是单纯的 `\n`——第1章的 nc 实验里，你少敲的那个回车就是它。很多服务器容错处理了 `\n`，但协议规范写的是 CRLF，报文结尾的空行实际是 `\r\n\r\n`。

> [!TIP] curl -v 是最好的 HTTP 显微镜
> `curl -v http://example.com` 会把「发出去的请求」和「收到的响应」原样打印（`>` 开头是请求、`<` 开头是响应），不用抓包就能看到报文全文。调试 HTTP 的第一反应应该是它，而不是打开浏览器开发者工具。

## 13.3 方法语义：每个动词都有它的脾气

HTTP 用方法（动词）表达客户端想对资源做什么。先记两个关键属性：

- **安全（Safe）**：不会修改服务器状态——只读。
- **幂等（Idempotent）**：请求一次和请求一万次，服务器最终状态一样。

| 方法 | 安全 | 幂等 | 典型用途 |
| ------ | ---- | ---- | -------- |
| GET | 是 | 是 | 获取资源，参数在 URL 查询串：`/search?q=hello&page=2` |
| HEAD | 是 | 是 | 同 GET 但只返回头部，用于探资源大小、是否存在 |
| POST | 否 | 否 | 提交数据：创建资源或触发处理 |
| PUT | 否 | 是 | 整体替换资源 |
| PATCH | 否 | 否* | 局部更新，只发送需要修改的字段 |
| DELETE | 否 | 是 | 删除资源 |
| OPTIONS | 是 | 是 | 询问服务器支持哪些方法 |

「先猜再读」第一问的答案：刷新页面通常没事，因为页面加载用的是 GET——安全且幂等，重复一万次服务器状态也不变。而 POST 不幂等：购物车里加两次商品就真有两件，所以浏览器才敢在刷新 POST 请求时弹出「确认重新提交表单」。

几个容易误解的点：

- **PUT vs POST**：PUT 幂等——用同样的数据 PUT 十次结果和一次一样（不存在就创建，存在就整体覆盖）；POST 每次都可能产生新资源。
- **PUT vs PATCH**：PUT 整体替换，PATCH 局部更新。只改邮箱不需要重发整个用户对象。
- **DELETE 的幂等**：删除一个已删除的资源不报错（返回 200 或 404 都合理）——状态没变，所以幂等。
- **OPTIONS 与 CORS 预检**：浏览器在发「复杂请求」前会先发 OPTIONS 问一声「我能用 PUT 访问你吗」：

```http
OPTIONS /api/users HTTP/1.1
Host: api.example.com
Origin: https://frontend.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization
```

## 13.4 状态码体系：服务器的表情

状态码是三位数字，第一位定类别，五大「家族」各有脾气：

**1xx 信息性**：请求正在处理，还没完。最常见的是 `101 Switching Protocols`——WebSocket 握手时服务器用它表示「好，我们换协议说话」（第17章的主角）。

**2xx 成功**：

- `200 OK`：最常见的成功。
- `201 Created`：资源创建成功（POST 之后常见）。
- `204 No Content`：成功但无消息体（DELETE 之后常见）。
- `206 Partial Content`：部分内容，配合 Range 请求实现断点续传。

**3xx 重定向**：资源在别处。

- `301 Moved Permanently`：永久搬家，浏览器会缓存，下次直接去新地址。
- `302 Found`：临时搬家，搜索引擎不更新索引。
- `304 Not Modified`：资源没变，用你手里的缓存版本——这是状态码层的语义，缓存机制全貌在第14章。
- `307 Temporary Redirect`：严格保持原方法的临时重定向（302 在历史浏览器中会把 POST 偷偷改成 GET，307 不会）。

**4xx 客户端错误**：请求有问题。

- `400 Bad Request`：请求格式有误。
- `401 Unauthorized`：需要认证（更准确的名字其实是 "Unauthenticated"）。
- `403 Forbidden`：认证过了，但你没权限。
- `404 Not Found`：资源不存在。
- `405 Method Not Allowed`：方法不被允许（对只读接口发了 POST）。
- `429 Too Many Requests`：请求太频繁，被限流了。

**5xx 服务器错误**：服务器出了问题。

- `500 Internal Server Error`：内部错误，万能兜底码。
- `502 Bad Gateway`：网关/代理从上游收到无效响应（Nginx 代理的后端挂了）。
- `503 Service Unavailable`：过载或维护中。
- `504 Gateway Timeout`：网关等上游超时。

排查口诀：4xx 先查自己的请求，5xx 先查服务器和它身后的链路——502/504 的「网关」角色会在第23章（反向代理与负载均衡）正式登场。

## 13.5 无状态的代价与收益

为什么 HTTP 选择了无状态？想象一下，如果服务器要记住每个客户端的状态——登录了没、购物车有什么、上次看了什么页面——服务器就得为每个活跃用户维护一个会话对象。1991 年内存昂贵、用户有限，这个选择务实；而且无状态让任意一台服务器都能处理任意一个请求，为第23章的负载均衡铺平了道路——请求扔给哪台机器都行。

但今天的电商网站显然需要「有状态」的用户体验。「先猜再读」第三问的答案是：HTTP 在无状态之上打了一个补丁——服务器在响应里塞一个「身份证」，浏览器存下来，之后每次请求自动带上；服务器拿它去自己的存储里查「这人是谁」。服务器依然无状态（HTTP 本体没变），状态被挪到了服务器自己的后端存储里。

这个补丁的具体实现——`Set-Cookie`/`Cookie` 头部、Session、以及无 Cookie 的替代方案——是典型的工程机制，统一放在第14章展开。本章只需要确立一个本体事实：**无状态是 HTTP 的天性，登录态是后天补上去的**。

## 13.6 持久连接与队头阻塞

HTTP/1.0 有个严重问题：每个请求都要新建一条 TCP 连接。一个含 10 张图片和 5 个 CSS 的网页需要 16 次连接，每次都三次握手（8.3）加慢启动（10.2）——高延迟网络下光这些开销就能让你感到卡顿。

HTTP/1.1 把**持久连接（Persistent Connection）**设为默认：一条 TCP 连接上可以跑多个请求-响应。`Connection: keep-alive` 头部只是显式声明（HTTP/1.1 默认即如此，想关闭才发 `Connection: close`）。

但持久连接有个内置限制：请求必须**按顺序**发送和接收。设想管线化（Pipelining）地连发三个请求，第一个卡住了，后两个即使已经处理完也得排队等它——这就是**队头阻塞（Head-of-Line Blocking）**。HTTP/1.1 的应用层队伍堵在一条 TCP 字节流上（8.1 的「一条连接一个字节流」是根源），浏览器只能靠多开连接绕行（12.4 的五元组给了这个自由）。真正解开这个结要等 HTTP/2 的多路复用——第19章的主场。

## 13.7 编程实践：用 Python 手写一个最简 HTTP 服务器

不用任何框架，从零解析请求并返回响应——写完你对报文格式的理解会扎实一个量级：

```python
import socket

def parse_request(data: str) -> dict:
    """解析 HTTP 请求报文"""
    lines = data.split('\r\n')

    # 解析请求行
    parts = lines[0].split(' ')
    method, path, version = parts[0], parts[1], parts[2]

    # 解析头部：直到空行
    headers = {}
    i = 1
    while i < len(lines) and lines[i]:
        if ':' in lines[i]:
            key, value = lines[i].split(':', 1)
            headers[key.strip().lower()] = value.strip()
        i += 1

    # 消息体（空行之后的内容）
    body = '\r\n'.join(lines[i+1:]) if i + 1 < len(lines) else ''

    return {
        'method': method,
        'path': path,
        'version': version,
        'headers': headers,
        'body': body
    }

def build_response(status_code: int, status_text: str, headers: dict, body: str = '') -> bytes:
    """构建 HTTP 响应报文"""
    response_line = f"HTTP/1.1 {status_code} {status_text}\r\n"
    header_lines = ''.join(f"{k}: {v}\r\n" for k, v in headers.items())
    response = response_line + header_lines + '\r\n' + body
    return response.encode('utf-8')

def handle_client(conn: socket.socket, addr):
    """处理一个客户端连接"""
    try:
        data = conn.recv(4096).decode('utf-8', errors='replace')
        request = parse_request(data)

        print(f"[{addr}] {request['method']} {request['path']}")
        print(f"  Headers: {request['headers']}")

        # 简单的路由
        if request['path'] == '/':
            body = '<html><body><h1>Hello from Python HTTP Server!</h1></body></html>'
            response = build_response(200, 'OK', {
                'Content-Type': 'text/html; charset=UTF-8',
                'Content-Length': str(len(body.encode('utf-8'))),
                'Connection': 'close'
            }, body)
        elif request['path'] == '/api/status':
            import json
            data = json.dumps({'status': 'running', 'method': request['method']})
            response = build_response(200, 'OK', {
                'Content-Type': 'application/json',
                'Content-Length': str(len(data)),
                'Connection': 'close'
            }, data)
        else:
            body = 'Not Found'
            response = build_response(404, 'Not Found', {
                'Content-Type': 'text/plain',
                'Content-Length': str(len(body)),
                'Connection': 'close'
            }, body)

        conn.sendall(response)
    finally:
        conn.close()

def main():
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind(('127.0.0.1', 8080))
    server.listen(5)
    print("HTTP Server listening on http://127.0.0.1:8080")

    try:
        while True:
            conn, addr = server.accept()
            handle_client(conn, addr)
    except KeyboardInterrupt:
        print("\nServer shutting down...")
    finally:
        server.close()

if __name__ == '__main__':
    main()
```

运行后用浏览器访问 `http://127.0.0.1:8080/` 看页面，`/api/status` 返回 JSON，其他路径 404。这个服务器是同步阻塞的——一次只处理一个请求——但它的价值是让你看到 HTTP 报文的真实结构：请求行怎么切、头部到空行为止、`Connection: close` 对应第8章的四次挥手。

## 13.8 抓包实践：捕获完整的 HTTP 请求/响应

Wireshark 过滤 `http`，访问一个简单页面，逐行核对报文结构：

**请求报文：**

```
GET /index.html HTTP/1.1              ← 请求行：方法、路径、版本
Host: www.example.com                  ← HTTP/1.1 强制要求的头部
User-Agent: Mozilla/5.0 ...            ← 客户端标识
Accept: text/html,...                  ← 可接受的内容类型
Accept-Encoding: gzip, deflate, br     ← 支持的压缩算法（第14章的协商机制）
Accept-Language: zh-CN,zh;q=0.9        ← 语言偏好，q 是权重
Connection: keep-alive                 ← 保持连接
```

**响应报文：**

```
HTTP/1.1 200 OK                        ← 状态行：版本、状态码、原因
Date: Mon, 15 Jan 2024 08:30:00 GMT   ← 服务器时间
Server: nginx/1.24.0                   ← 服务器软件
Content-Type: text/html; charset=UTF-8 ← 内容类型
Content-Length: 1256                   ← 消息体长度
Cache-Control: max-age=3600            ← 缓存指令（第14章详述）
Connection: keep-alive                 ← 保持连接
```

在 Wireshark 中展开 `Hypertext Transfer Protocol` 树，每个字段都可点击查看。重点核对一件事：`Content-Length` 与实际消息体长度是否一致——HTTP 靠它声明消息体边界，对不上客户端就不知道内容在哪结束（这是应用层自己定界，与 8.7 的 TCP 粘包问题异曲同工）。

再用 13.7 的服务器做交叉验证：`curl -v http://127.0.0.1:8080/` 观察 `>` 与 `<` 的报文，和 Wireshark 里看到的一一对应。

## 本章小结

- HTTP 的三个设计关键词：无状态、请求-响应、文本可读——简单造就了可调试性和近乎无限的扩展能力。
- 报文四段式：请求行/状态行、头部、空行、消息体；行结尾是 CRLF（`\r\n`），第1章的 nc 实验已经验证过。
- 方法有脾气：GET/HEAD 安全幂等，PUT/DELETE 幂等但不安全，POST 什么都不占；刷新页面无害的根源是 GET 幂等。
- 状态码五大家族：1xx 处理中、2xx 成功、3xx 搬家、4xx 你错、5xx 我错；502/504 是网关在替上游背锅。
- 无状态是天性不是缺陷：它让服务器可任意水平扩展，登录态靠后端存储 + 身份补丁实现（机制在第14章）。
- 持久连接是 HTTP/1.1 默认，但一条 TCP 字节流只能按序跑请求——队头阻塞的根源在第8章，解法在第19章。
- 手写服务器是最好的教材：解析请求行、按空行切头部、拼状态行——40 行代码就是 HTTP 的全部骨架。
- 抓包核对 `Content-Length` 与消息体长度：HTTP 在应用层自己定界，这是它与「裸 TCP 字节流」的本质区别。
