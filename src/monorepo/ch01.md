# Ch01: 什么是 Monorepo

## 本章目标（Part 1：基础入门）

- 理解 Monorepo 的核心理念，以及它与 Multi-repo 的本质区别
- 了解业界大厂的工程实践背景
- 掌握 Node.js 生态中主流 monorepo 工具的定位与差异
- 明确本教程的技术选型和最终要搭建的项目全貌

## 1.1 从一个真实场景说起

假设你正在开发一个 SaaS 产品，项目包含以下组成部分：

- 一个 Vue 3 前端应用（面向终端用户）
- 一个 Node.js / Express 后端 API 服务
- 一套前后端共享的类型定义和工具函数
- 一套统一的 ESLint / TypeScript 配置

在 **Multi-repo（多仓库）** 模式下，你会为每个模块创建独立的 Git 仓库：

```txt
~/projects
├── myapp-web/        # 独立仓库
├── myapp-api/        # 独立仓库
├── myapp-shared/     # 独立仓库
└── myapp-config/     # 独立仓库
```

这看起来很"干净"，但当你真正开始开发时，问题接踵而来：

**场景一：修改共享类型**
你在 `myapp-shared` 中修改了一个接口定义。现在你需要：

1. 发布 `myapp-shared` 的新版本到 npm
2. 切到 `myapp-web`，更新 `package.json` 中的版本号，重新安装依赖
3. 切到 `myapp-api`，重复同样的操作
4. 祈祷三个仓库的 CI 都能通过

**场景二：跨模块重构**
你想把前端的某个 API 调用函数移到共享包中。这涉及三个仓库的同步修改，但你没法在一个 PR 中完成，也没法做一次原子提交。

**场景三：新人上手**
新同事入职，你需要告诉他："先 clone 这 4 个仓库，然后按这个顺序安装依赖，对了，`shared` 包要先 build 一下，版本要切到 `2.3.1-beta`……"

这些痛点，正是 Monorepo 要解决的。

## 1.2 Monorepo vs Multi-repo：概念对比

**Monorepo（单一仓库）** 的核心思想很简单：把多个相关的项目放在同一个 Git 仓库中管理。

```txt
my-monorepo/
├── apps/                    # 应用层：可以独立部署运行的项目
│   ├── web/                 # Vue 3 前端应用
│   └── api/                 # Node.js 后端应用
├── packages/                # 包层：被 apps 引用的共享库
│   ├── shared/              # 共享类型、工具函数、常量
│   ├── ui/                  # 共享 Vue 组件库
│   ├── database/            # Prisma 数据库层
│   ├── eslint-config/       # 共享 ESLint 配置
│   └── tsconfig/            # 共享 TypeScript 配置
├── pnpm-workspace.yaml      # 核心：告诉 pnpm "哪些目录是 workspace 成员"
├── turbo.json               # Turborepo 的任务编排配置
├── package.json             # 根目录的 package.json（不发布，只放全局脚本和共享 devDependencies）
├── pnpm-lock.yaml
├── .npmrc
├── .gitignore
└── .nvmrc
```

monorepo 的**骨架**：pnpm-workspace.yaml

pnpm-workspace.yaml 是花名册——声明"谁是自己人"。package.json（各包的）是个人简历——声明"我依赖什么、我提供什么"。turbo.json 是排班表——声明"什么任务什么时候跑、按什么顺序跑"。

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

包之间的依赖方向是单向的

依赖关系从上往下流动：apps 依赖 packages，packages 之间可以互相依赖（比如 packages/ui 可以依赖 packages/shared 的类型），但 packages 不能反向依赖 apps。这是一个严格的单向图——如果出现了循环依赖（A 依赖 B，B 又依赖 A），pnpm 会报错，Turborepo 也会报错。

用之前的中央厨房比喻来理解：火锅店（apps/web）可以从中央厨房（packages/shared）拿半成品，中央厨房的切配区（packages/ui）可以从调料区（packages/shared）拿调料，但调料区不能反过来要求切配区给它东西——那就成了死循环。

每个子包的标准结构

以 packages/shared 为例：

```txt
packages/shared/
├── src/
│   ├── types.ts          # 共享类型定义
│   ├── utils.ts          # 工具函数
│   ├── constants.ts      # 常量
│   └── index.ts          # 统一导出入口
├── package.json
├── tsconfig.json
└── tsup.config.ts        # 构建配置
```

它的 package.json 关键字段：

```txt
{
  "name": "@monorepo/shared",
  "version": "0.1.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": ["dist"],
  "scripts": {
    "build": "tsup",
    "dev": "tsup --watch"
  }
}
```

下面是两种模式的详细对比：

| 维度 | Multi-repo | Monorepo |
| ------ | ----------- | ---------- |
| **代码共享** | 需要通过 npm 发布/安装 | 直接引用，实时生效 |
| **跨模块修改** | 多个 PR，难以保证同步 | 一个 PR，原子提交 |
| **依赖管理** | 各自独立，版本容易不一致 | 可以集中管理，统一版本 |
| **CI/CD** | 每个仓库独立配置 | 统一配置，按需触发 |
| **代码可见性** | 分散在不同仓库 | 所有人看到所有代码 |
| **构建编排** | 手动管理构建顺序 | 工具自动分析依赖图 |
| **仓库体积** | 每个仓库较小 | 仓库整体较大（但可优化） |
| **权限控制** | 可以按仓库控制 | 需要 CODEOWNERS 等机制 |
| **适用场景** | 独立、无关的项目 | 紧耦合的项目群 |

> **关键认知：** Monorepo 不是银弹。如果你的几个项目之间几乎没有代码共享和联动修改的需求，Multi-repo 可能更合适。Monorepo 的价值在"多个包需要协同演进"的场景中才能充分体现。

## 1.3 为什么大厂都在用

**Google** 是 Monorepo 的先驱。早在 2016 年，Google 就在论文中透露他们 95% 的代码在一个超过 20 亿行的单一仓库中。他们为此开发了内部工具 Piper 和 Forge 来管理这个巨型仓库。为什么？因为在 Google 的规模下，跨团队的代码共享和原子变更是刚需——一个底层库的 API 变更可能同时影响数千个项目，如果不能在一个提交中完成所有适配，系统将无法持续运转。

**Meta（Facebook）** 同样使用 Monorepo，并为开源社区贡献了 Mercurial 的扩展来应对大仓库的性能问题。React、React Native、Jest、Relay 等项目的源码都在同一个仓库中，这也是为什么你经常在这些仓库中看到 `packages/` 目录结构。

**微软** 的许多核心项目也采用了 Monorepo：TypeScript、VS Code、Rush Stack 等。微软还开源了 **Rush** 这个专门为大规模 monorepo 设计的工具。

**Vercel** 开发的 Turborepo 被 Next.js、Vercel 平台自身等广泛使用，现已成为 monorepo 工具链中不可忽视的力量。

这些大厂选择 Monorepo 的共同原因可以归纳为三点：

1. **原子变更（Atomic Changes）**：一次修改可以同时影响多个包，且保证一致性
2. **代码共享（Code Sharing）**：消除"复制粘贴"式的代码复用，用真正的包引用来替代
3. **统一工具链（Unified Tooling）**：一套构建、测试、lint 配置服务于所有项目

## 1.4 Node.js 生态的 Monorepo 工具概览

Node.js 生态中有丰富的 monorepo 工具，了解它们的历史和定位有助于我们做出正确的选择。

### Lerna：先驱与教训

**Lerna** 诞生于 2016 年，是 Node.js 生态最早的 monorepo 工具之一。它的核心功能是：

- 管理多个包的版本（独立版本 or 固定版本）
- 处理包之间的依赖关系
- 批量执行命令（`lerna run build`）
- 自动发布到 npm

但 Lerna 有一个致命的问题：**它不负责依赖安装和构建编排**。它本质上是一个"循环执行 npm install 和 npm run"的脚本工具。当项目变大后，安装依赖和构建的速度会变得极慢，因为它无法并行化，也无法利用缓存。

> 2022 年，Lerna 被 Nrwl（Nx 背后的公司）接管，并在 v6 中集成了 Nx 的能力，算是获得了"第二次生命"。但此时，生态格局已经发生了根本变化。

### pnpm workspace：依赖管理的革命

**pnpm** 从设计上就是为 monorepo 而生的。它的 workspace 功能通过一个 `pnpm-workspace.yaml` 文件就能定义工作区，核心优势包括：

- **硬链接 + 符号链接**：pnpm 使用内容寻址存储（content-addressable store），同一个依赖的多个版本在磁盘上只存一份，通过硬链接共享，极大节省磁盘空间
- **严格的依赖隔离**：包的 `node_modules` 是精确的，不会意外访问到未声明的依赖（这个问题后面会详细讲）
- **原生 workspace 协议**：`workspace:*` 等协议让包之间的引用变得显式且安全

pnpm workspace 解决的是 **"依赖管理"** 这一层问题，但它不负责构建编排。这就需要一个搭档工具。

### Turborepo：构建编排的利器

**Turborepo**（Vercel 出品）专注于解决 **"构建编排"** 问题：

- **智能缓存**：基于文件内容哈希，如果输入没变，直接复用上次的构建产物（包括远程缓存）
- **并行执行**：自动分析包之间的依赖图，最大化并行度
- **增量构建**：只构建变更影响到的包
- **零配置**：只需要一个 `turbo.json` 就能工作

Turborepo 的设计哲学是 **"不侵入你的工作流"**——它不管理依赖安装（交给 pnpm），不关心你的代码结构（只关心 `package.json` 中的脚本），只做一件事：让你重复执行 `turbo run build` 时快得飞起。

### Nx：全能选手

**Nx**（Nrwl 出品）定位更高——它不仅管构建编排，还管代码生成、依赖图可视化、CI 配置等。它更适合大型企业，但学习曲线也更陡峭。Nx 对 Angular 生态的支持尤其深入（Nrwl 团队的核心成员来自 Angular 核心团队）。

### 工具对比总结

| 特性 | Lerna (v6+) | pnpm workspace | Turborepo | Nx |
| ------ | ------------- | ---------------- | ----------- | ----- |
| 依赖安装 | 委托给 npm/yarn/pnpm | 原生支持 | 不负责 | 委托给包管理器 |
| 构建缓存 | 有限 | 不负责 | 核心能力（本地+远程） | 核心能力 |
| 并行执行 | 基础 | 不负责 | 自动依赖图分析 | 自动依赖图分析 |
| 版本管理 | 核心能力 | 不负责 | 不负责 | 不负责（有插件） |
| 代码生成 | 无 | 无 | 无 | 核心能力 |
| 学习曲线 | 低 | 低 | 低 | 中高 |
| 配置复杂度 | 低 | 极低 | 低 | 中 |

### 我们的选择：pnpm workspace + Turborepo

本教程选择 **pnpm workspace + Turborepo** 的组合，原因如下：

1. **职责清晰**：pnpm 管依赖，Turborepo 管构建，各司其职
2. **配置极简**：两者都崇尚"约定大于配置"，学习成本低
3. **性能卓越**：pnpm 的安装速度 + Turborepo 的缓存机制，开发体验极佳
4. **生态活跃**：两者都在快速迭代，社区支持良好
5. **框架无关**：不绑定特定框架，Vue、React、Svelte 都能用

## 1.5 本教程的项目概述

我们将搭建一个名为 **`taskflow`** 的全栈项目管理应用，包含以下模块：

```
taskflow/
├── apps/
│   ├── web/              # Vue 3 + Vite 前端应用
│   │   └── 项目看板、任务列表、用户设置等页面
│   └── api/              # Express.js 后端 API
│       └── RESTful API、数据校验、认证等
├── packages/
│   ├── shared/           # @taskflow/shared
│   │   └── 共享类型定义、常量、工具函数
│   ├── eslint-config/    # @taskflow/eslint-config
│   │   └── 统一的 ESLint 规则
│   └── tsconfig/         # @taskflow/tsconfig
│       └── 统一的 TypeScript 配置
├── turbo.json            # Turborepo 配置
├── pnpm-workspace.yaml   # pnpm workspace 配置
└── package.json          # 根目录配置
```

这个架构的依赖关系如下：

```
┌─────────────────────────────────────────────────┐
│                   apps/web                       │
│            (Vue 3 + Vite 前端)                    │
│                                                  │
│    依赖: @taskflow/shared                        │
│          @taskflow/eslint-config                 │
│          @taskflow/tsconfig                      │
└──────────────┬──────────────────────┬────────────┘
               │                      │
               ▼                      ▼
┌──────────────────────┐  ┌────────────────────────┐
│    apps/api           │  │  packages/shared        │
│  (Express 后端)       │  │  (类型 + 工具函数)       │
│                       │  │                          │
│  依赖: @taskflow/     │  │  无内部依赖              │
│        shared         │  │  外部依赖: zod 等        │
│        eslint-config  │  └────────────────────────┘
│        tsconfig       │
└───────────┬───────────┘
            │
            ▼
┌─────────────────────────────────────────────────┐
│           packages/eslint-config                 │
│           packages/tsconfig                      │
│           (共享开发工具配置)                       │
└─────────────────────────────────────────────────┘
```

在后续章节中，你会亲手从零搭建起这个项目，并逐步添加功能。Part 1 聚焦于基础搭建，完成后你将拥有一个结构清晰、工具链完备的 monorepo 骨架。

## 本章小结

- **Monorepo** 将多个相关项目放在同一个仓库中，解决代码共享、原子变更、统一工具链三大问题
- 它不是万能的，适用于紧耦合的项目群；独立项目仍适合 Multi-repo
- Node.js 生态中，**pnpm workspace** 负责依赖管理，**Turborepo** 负责构建编排，两者组合是当前最流行且高效的方案之一
- 我们将搭建一个包含 Vue 3 前端 + Express 后端 + 共享包的 **taskflow** 项目
