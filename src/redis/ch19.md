# 第19章：性能调优——让 Redis 飞起来

## 引言：F1 赛车 vs 拖拉机

Redis 天生就快——单线程、内存操作、高效数据结构，随随便便就能跑到 10 万 QPS。但"随随便便"三个字是骗人的。

如果你见过以下场景，就知道性能调优的重要性：

- 一个 `KEYS *` 命令把整个 Redis 卡住 30 秒
- 一个大 Hash 对象占用了 2GB 内存，导致其他数据被淘汰
- Pipeline 使用不当，网络延迟吃掉了所有性能优势
- 持久化配置不合理，AOF 文件每秒增长 100MB

这就好比一辆 F1 赛车，发动机（Redis 本身）确实很强，但如果轮胎没气（内存不足）、油箱漏油（持久化开销大）、方向盘歪了（命令选择不当），它照样跑不过一辆精心调校的家用轿车。

> **编程隐喻时间**：Redis 性能调优就像代码优化——首先要用 Profiler 找到瓶颈（SLOWLOG），然后选择正确的算法（O(1) vs O(N) 命令），接着优化数据结构（编码选择），最后调整运行时参数（内存和网络）。

## 19.2 影响 Redis 性能的因素

```
Redis 性能六大因素：

1. 网络延迟    - RTT / 带宽
2. 内存使用    - 碎片 / 淘汰
3. 命令复杂度  - O(1) vs O(N)
4. 持久化开销  - RDB / AOF
5. CPU 使用    - 单线程限制
6. 并发连接数  - 连接管理
```

## 19.3 内存优化

### 19.3.1 内存分配器

```bash
# 检查当前使用的内存分配器
redis-cli INFO server | grep mem_allocator
# mem_allocator:jemalloc-5.2.1
# jemalloc 比 glibc malloc 更适合 Redis：更低碎片率，更好的回收策略
```

### 19.3.2 编码优化

```
数据类型          小数据量编码          大数据量编码
String            int/embstr            raw
Hash              listpack (7.0+)       hashtable
List              quicklist             quicklist + listpack
Set               intset                hashtable
Sorted Set        listpack (7.0+)       skiplist + hashtable
```

```bash
# 查看 key 的内部编码
redis-cli OBJECT ENCODING my_hash
# "listpack" -> 紧凑编码，内存效率高
# "hashtable" -> 标准编码

# 查看 key 占用的实际内存
redis-cli MEMORY USAGE my_hash
```

**优化技巧**：尽量让数据保持在小数据量编码状态，将大 Hash 拆分成多个小 Hash。

### 19.3.3 maxmemory 和淘汰策略

```bash
# redis.conf
maxmemory 8gb
maxmemory-policy allkeys-lfu
# noeviction     -> 不淘汰，内存满时拒绝写入
# allkeys-lru    -> 淘汰最近最少使用的
# allkeys-lfu    -> 淘汰最不常用的（推荐）
# volatile-lru   -> 从有过期时间的 key 中淘汰 LRU
# volatile-ttl   -> 从有过期时间的 key 中淘汰 TTL 最短的
maxmemory-samples 10
```

> [!TIP] 提示
> ：对于缓存场景，推荐使用 `allkeys-lfu`。LFU 比 LRU 更智能——它考虑访问频率而不仅仅是最近访问时间。

### 19.3.4 内存碎片整理

```bash
# redis.conf
activedefrag yes
active-defrag-threshold-lower 10
active-defrag-threshold-upper 100
active-defrag-cycle-min 1
active-defrag-cycle-max 25

# 查看内存碎片率
redis-cli INFO memory | grep mem_fragmentation_ratio
# 1.0 = 没有碎片
# 1.5 = 50% 碎片（需要整理）
# < 1.0 = 内存交换到了磁盘（危险！）
```

## 19.4 命令优化

### 19.4.1 O(1) vs O(N) 命令选择

```
O(1) 命令（常数时间）：GET, SET, HGET, HSET, LINDEX, SISMEMBER, ZSCORE
O(log N) 命令：ZADD, ZRANGE, ZRANGEBYSCORE
O(N) 命令：LRANGE, SMEMBERS, HGETALL, ZRANGE (大范围)
危险命令：KEYS *, SORT, LRANGE 0 -1（大列表）
```

```js
const Redis = require('ioredis');
const redis = new Redis();

// 错误做法：用 KEYS 查找匹配的 key
const keys = await redis.keys('user:*'); // O(N)，N 是总 key 数量

// 正确做法：用 SCAN 逐步迭代
async function scanKeys(pattern) {
  const keys = [];
  let cursor = '0';
  do {
    const [newCursor, matchedKeys] = await redis.scan(
      cursor, 'MATCH', pattern, 'COUNT', 100
    );
    cursor = newCursor;
    keys.push(...matchedKeys);
  } while (cursor !== '0');
  return keys;
}

const userKeys = await scanKeys('user:*');
console.log(`找到 ${userKeys.length} 个用户 key`);
redis.disconnect();
```

### 19.4.2 避免大 Key（Big Key 问题）

```js
const Redis = require('ioredis');
const redis = new Redis();

// 删除大 Key 的正确方式（异步删除，不阻塞）
await redis.unlink('big_hash');  // 推荐！不要用 DEL

// 分批删除大 Hash 的字段
async function safeDeleteBigHash(key, batchSize = 1000) {
  let cursor = '0';
  do {
    const [newCursor, fields] = await redis.hscan(key, cursor, 'COUNT', batchSize);
    cursor = newCursor;
    
    if (fields.length > 0) {
      const fieldNames = fields.filter((_, i) => i % 2 === 0);
      await redis.hdel(key, ...fieldNames);
      await new Promise(r => setTimeout(r, 10));
    }
  } while (cursor !== '0');
  
  await redis.del(key);
  console.log(`安全删除完成: ${key}`);
}

redis.disconnect();
```

### 19.4.3 合理使用 Pipeline

```js
const Redis = require('ioredis');
const redis = new Redis();

// Pipeline 大小要适中：太小没效果，太大占内存
// 推荐：每批 100-500 个命令
async function batchPipeline(operations, batchSize = 200) {
  const results = [];
  for (let i = 0; i < operations.length; i += batchSize) {
    const batch = operations.slice(i, i + batchSize);
    const pipeline = redis.pipeline();
    for (const [cmd, ...args] of batch) {
      pipeline[cmd](...args);
    }
    const batchResults = await pipeline.exec();
    results.push(...batchResults);
  }
  return results;
}

(async () => {
  const ops = [];
  for (let i = 0; i < 10000; i++) {
    ops.push(['set', `batch:${i}`, `value:${i}`]);
  }
  await batchPipeline(ops, 200);
  console.log('批量写入完成');
  redis.disconnect();
})();

// 典型性能对比（本地网络）：
// 不使用 Pipeline: ~3000ms（每次 RTT 约 3ms）
// 使用 Pipeline: ~50ms（一次 RTT + 批量处理）
// 性能提升 60 倍！
```


```js
const Redis = require('ioredis');

// 连接池：大多数情况一个 ioredis 实例就够了
// 公式：连接数 = 期望QPS * 平均命令延迟(秒)
function createPool(size, config) {
  const pool = [];
  for (let i = 0; i < size; i++) {
    pool.push(new Redis(config));
  }
  let index = 0;
  return {
    get() {
      const client = pool[index];
      index = (index + 1) % pool.length;
      return client;
    },
    async closeAll() {
      await Promise.all(pool.map(c => c.quit()));
    },
  };
}

const pool = createPool(5, { host: '127.0.0.1', port: 6379 });

(async () => {
  const client = pool.get();
  await client.set('pool_test', 'hello');
  console.log(await client.get('pool_test'));
  await pool.closeAll();
})();
```

## 19.6 持久化优化

```bash
# 纯缓存场景：可以关闭持久化
save ""
appendonly no

# 缓存 + 需要快速恢复：只用 RDB
save 900 1
save 300 10
save 60 10000
appendonly no

# 重要数据：RDB + AOF
save 900 1
save 300 10
save 60 10000
appendonly yes
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

| 特性 | RDB | AOF |
|------|-----|-----|
| 写入速度 | 快（二进制快照） | 较慢（文本命令） |
| 恢复速度 | 快（直接加载） | 慢（重放命令） |
| 数据安全 | 可能丢数据 | 取决于 fsync |
| 文件大小 | 小 | 大 |

## 19.7 监控和诊断

### 19.7.1 SLOWLOG：慢查询日志

```js
const Redis = require('ioredis');
const redis = new Redis();

async function analyzeSlowQueries() {
  await redis.config('set', 'slowlog-log-slower-than', '10000');
  await redis.config('set', 'slowlog-max-len', '128');

  const logs = await redis.slowlog('get', 20);

  console.log('=== 慢查询日志 ===');
  for (const log of logs) {
    const [id, timestamp, duration, command] = log;
    const date = new Date(timestamp * 1000).toLocaleString();
    console.log(`[${date}] 耗时 ${duration / 1000}ms | 命令: ${command.join(' ')}`);
  }

  const count = await redis.slowlog('len');
  console.log(`\n总慢查询数: ${count}`);
  redis.disconnect();
}

analyzeSlowQueries();
```

## 19.8 Node.js 端性能优化

### 19.8.2 批量操作和序列化优化

```js
const Redis = require('ioredis');
const redis = new Redis();

// Pipeline 批量写入（推荐方式）
async function pipelineImport(items, batchSize = 500) {
  const start = Date.now();
  for (let i = 0; i < items.length; i += batchSize) {
    const batch = items.slice(i, i + batchSize);
    const pipeline = redis.pipeline();
    for (const item of batch) {
      pipeline.set(`item:${item.id}`, JSON.stringify(item));
    }
    await pipeline.exec();
  }
  console.log(`Pipeline 写入: ${Date.now() - start}ms`);
}

// Hash 存储对象（比 JSON 序列化更灵活）
class SerializedRedis {
  constructor(redis) { this.redis = redis; }

  async setHashObject(key, obj) {
    const pipeline = this.redis.pipeline();
    for (const [field, value] of Object.entries(obj)) {
      if (typeof value === 'object' && value !== null) {
        pipeline.hset(key, field, JSON.stringify(value));
      } else {
        pipeline.hset(key, field, String(value));
      }
    }
    return pipeline.exec();
  }

  async getHashObject(key) {
    const fields = await this.redis.hgetall(key);
    const result = {};
    for (const [field, value] of Object.entries(fields)) {
      try { result[field] = JSON.parse(value); }
      catch { result[field] = value; }
    }
    return result;
  }
}

const sredis = new SerializedRedis(redis);

(async () => {
  const user = { name: '张三', age: 25, address: { city: '北京' } };
  await sredis.setHashObject('user:1', user);
  const loaded = await sredis.getHashObject('user:1');
  console.log('读取结果:', loaded);
  redis.disconnect();
})();
```

## 小结

Redis 性能调优是一个系统工程，需要从多个维度综合考虑：

1. **内存**：合理的 maxmemory、淘汰策略、碎片整理
2. **命令**：选择 O(1) 命令，避免大 Key，用 SCAN 替代 KEYS
3. **网络**：Pipeline 批量操作，合理的连接池大小，TCP 参数优化
4. **持久化**：根据场景选择 RDB/AOF/关闭，避免不必要的磁盘 IO
5. **监控**：SLOWLOG + LATENCY + INFO，及时发现和解决问题

记住：**不要盲目优化**。先用 SLOWLOG 和 INFO 找到真正的瓶颈，再针对性地优化。过早优化是万恶之源——这句话在 Redis 性能调优中同样适用。

## 练习题

1. **基础题**：使用 `redis-benchmark` 对你的 Redis 实例进行基准测试，记录 SET/GET 的 QPS 和 P99 延迟。然后开启 Pipeline（-P 16）再次测试，对比性能差异。
2. **进阶题**：编写一个 Node.js 脚本，定期扫描 Redis 中的大 Key（使用 MEMORY USAGE 和 SCAN），输出 Top 10 最大的 Key 及其内存占用。
3. **挑战题**：对一个模拟的生产环境 Redis 进行完整调优：从 SLOWLOG 分析开始，找到慢查询原因，优化命令选择和数据结构，最后用 benchmark 验证优化效果。目标是 QPS 提升 50% 以上。
