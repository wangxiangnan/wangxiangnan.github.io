# 第18章：面向对象编程的Rust风格

## 场景引入

如果你来自 Java 或 C#，你可能习惯了"一切皆对象"的世界——类、继承、多态、封装是四大支柱。所有东西都从 `Object` 继承而来，你写的每个类都有一个父类（哪怕你没写，它也偷偷继承了 `Object`）。来到 Rust，你会发现：Rust 没有 `class`，没有 `extends`，甚至连 `interface` 都没有。

那 Rust 是面向对象语言吗？答案是：**是，也不是**。Rust 吸收了 OOP 的精华（封装、多态），同时摒弃了被认为是"万恶之源"的特性（实现继承），用组合（Composition）和 Trait 系统提供了一套更灵活、更安全的设计方案。

为什么要去掉继承？因为业界已经有大量证据表明，深层继承层次是 bug 和复杂性的主要来源。想想 Java 中 `LinkedList` 继承了 `AbstractSequentialList`，继承了 `AbstractList`，继承了 `AbstractCollection`，最后继承 `Object`——五层继承，你真的理解每一层做了什么吗？这就是所谓的"脆弱基类问题"（Fragile Base Class Problem）：修改父类可能破坏所有子类。

Rust 的态度是：**"组合优于继承"不是建议，而是唯一的选择。** 当你需要共享行为时，用 Trait；当你需要共享数据时，用组合（把一个 struct 嵌入另一个 struct 中）。这种方式一开始可能感觉"啰嗦"，但长期来看，代码更清晰、更容易维护。

## 18.1 Rust 是面向对象语言吗？

让我们用传统 OOP 的三大特性来审视 Rust：

| OOP 特性 | Rust 的支持方式 | 说明 |
| ---------- | ---------------- | ------ |
| 封装 | `pub` 控制可见性 | 结构体 + `pub` 字段/方法 |
| 多态 | Trait + `dyn Trait` | 比 Java 的接口更灵活 |
| 继承 | 不支持 | 用组合 + Trait 替代 |

Rust 没有类继承，这是有意为之。继承带来的"脆弱基类问题"（Fragile Base Class Problem）和深层继承层次是许多 bug 的源头。Rust 选择了"组合优于继承"（Composition over Inheritance）——这是《设计模式》（GoF）一书中就已经提出的原则。

## 18.2 封装：pub 控制可见性

封装（Encapsulation）是 OOP 的核心原则之一——隐藏内部实现细节，只暴露必要的接口。在 Java 中，你通过 `private` 字段 + `public` getter/setter 来实现；在 Python 中，你通过 `_` 前缀约定 + `@property` 装饰器来实现。

Rust 的封装方式更加直接：**默认一切都是私有的，你需要显式地把想公开的部分标记为 `pub`**。这种"默认安全"的设计意味着，你不用担心不小心暴露了不该暴露的内部状态——编译器会帮你把关。

```rust
pub struct BankAccount {
    owner: String,         // 私有：外部无法直接访问
    balance: f64,          // 私有：防止外部直接修改
    account_type: String,  // 私有
}

impl BankAccount {
    // 公开的构造函数——唯一的创建方式
    pub fn new(owner: String, initial_deposit: f64) -> Self {
        if initial_deposit < 0.0 {
            panic!("初始存款不能为负数！");
        }
        BankAccount {
            owner,
            balance: initial_deposit,
            account_type: String::from("savings"),
        }
    }

    // 公开方法——对外暴露的 API
    pub fn deposit(&mut self, amount: f64) {
        if amount > 0.0 {
            self.balance += amount;
            println!("存入 {}, 余额: {}", amount, self.balance);
        }
    }

    pub fn withdraw(&mut self, amount: f64) -> Result<f64, String> {
        if amount > self.balance {
            Err(format!("余额不足！当前余额: {}", self.balance))
        } else {
            self.balance -= amount;
            Ok(self.balance)
        }
    }

    pub fn balance(&self) -> f64 {
        self.balance // 只读访问
    }

    // 私有方法——内部实现细节
    fn validate_transaction(&self, amount: f64) -> bool {
        amount > 0.0 && amount <= self.balance
    }
}

fn main() {
    let mut account = BankAccount::new(String::from("Alice"), 1000.0);
    account.deposit(500.0);
    match account.withdraw(200.0) {
        Ok(new_balance) => println!("取款成功，新余额: {}", new_balance),
        Err(e) => println!("取款失败: {}", e),
    }
    // account.balance = 999999.0; // 编译错误：字段私有
    println!("查询余额: {}", account.balance());
}
```

## 18.3 多态：Trait 对象（dyn Trait）

Trait 对象是 Rust 实现多态的方式，类似于 Java 的接口引用或 Python 的鸭子类型。在 Java 中你可以写 `List<String> list = new ArrayList<>()`——用接口类型引用具体实现。Rust 的 `dyn Trait` 做的是同样的事：用 trait 类型引用任何实现了该 trait 的具体类型。

`dyn` 关键字（dynamic 的缩写）是 Rust 2018 引入的，用来明确标记"这是动态分发的 trait 对象"。在 Rust 2015 中，你可以省略 `dyn`，但这会导致歧义，所以现在必须显式写出。

```rust
use std::fmt;

// 定义 trait——类似 Java 的 interface
trait Drawable {
    fn draw(&self);
    fn area(&self) -> f64;
}

struct Circle {
    radius: f64,
}

impl Drawable for Circle {
    fn draw(&self) {
        println!("画一个半径为 {} 的圆", self.radius);
    }
    fn area(&self) -> f64 {
        std::f64::consts::PI * self.radius * self.radius
    }
}

struct Rectangle {
    width: f64,
    height: f64,
}

impl Drawable for Rectangle {
    fn draw(&self) {
        println!("画一个 {}x{} 的矩形", self.width, self.height);
    }
    fn area(&self) -> f64 {
        self.width * self.height
    }
}

// 使用 Trait 对象——接受任何实现了 Drawable 的类型
fn render(shape: &dyn Drawable) {
    shape.draw();
    println!("面积: {:.2}", shape.area());
}

// Trait 对象也可以放在集合中
fn render_all(shapes: &[Box<dyn Drawable>]) {
    for shape in shapes {
        shape.draw();
    }
}

fn main() {
    let circle = Circle { radius: 5.0 };
    let rect = Rectangle { width: 4.0, height: 6.0 };

    render(&circle);
    render(&rect);

    let shapes: Vec<Box<dyn Drawable>> = vec![
        Box::new(Circle { radius: 3.0 }),
        Box::new(Rectangle { width: 2.0, height: 8.0 }),
    ];
    render_all(&shapes);
}
```

## 18.4 动态分发 vs 静态分发

这是 Rust 性能哲学的核心区分，也是从其他语言转来的开发者最容易困惑的地方。

在 Java 和 Python 中，所有方法调用都是**动态分发**的——运行时通过虚方法表（vtable）查找具体实现。这很灵活但有性能开销（无法内联优化）。

在 C++ 中，你可以通过 `virtual` 关键字选择动态分发，默认是静态分发。

在 Rust 中，你有两个显式的选择：

- **静态分发（泛型）**：编译器为每种类型生成一份代码。零运行时开销，但编译时间更长、二进制文件更大（代码膨胀，monomorphization）。
- **动态分发（Trait 对象）**：运行时通过 vtable 查找方法。有微小的运行时开销，但编译更快、二进制更小。

```rust
// 静态分发（泛型）——编译时确定类型，零成本抽象，代码膨胀
// 编译器为每种类型生成一份代码（类似 C++ 模板）
fn print_area_static<T: Drawable>(shape: &T) {
    println!("面积: {}", shape.area());
}

// 动态分发（Trait 对象）——运行时通过 vtable 查找方法
// 类似 Java 的虚方法调用
fn print_area_dynamic(shape: &dyn Drawable) {
    println!("面积: {}", shape.area());
}

// 对比：
// 静态分发：Vec<T> 中只能放一种类型
// 动态分发：Vec<Box<dyn Trait>> 中可以放不同类型

fn main() {
    let c = Circle { radius: 3.0 };
    let r = Rectangle { width: 4.0, height: 5.0 };

    // 静态分发——编译器生成两份代码：一份给 Circle，一份给 Rectangle
    print_area_static(&c);
    print_area_static(&r);

    // 动态分发——运行时查 vtable
    print_area_dynamic(&c);
    print_area_dynamic(&r);

    // 静态分发不能混合类型
    // let mixed: Vec<&T> = vec![&c, &r]; // 编译错误！

    // 动态分发可以混合类型
    let mixed: Vec<&dyn Drawable> = vec![&c, &r]; // OK！
}
```

**选择原则**：

- 追求性能 + 类型固定 → 静态分发（泛型）
- 需要灵活性 + 异构集合 → 动态分发（`dyn Trait`）

## 18.5 状态模式：用类型系统编码状态机

在很多场景中，对象的行为取决于它的内部状态。传统 OOP 用状态模式（State Pattern）——为每种状态创建一个类，状态转换就是替换对象。而 Rust 可以用**类型系统**来让非法状态无法编译，这叫做**类型状态模式（Type State Pattern）**。

类型状态模式的核心思想是：**把运行时状态编码到编译时类型中**。在传统语言中，你在运行时检查"这个订单是否已经发货"；在 Rust 中，编译器直接保证"你不能对一个已发货的订单调用发货方法"。这是 Rust 类型系统的一大杀器——它让你在编译期就消除一整类 bug。

让我们用一个博客发布工作流的例子来展示这种模式：

```rust
// 博客文章的发布工作流：草稿 -> 待审核 -> 已发布
// 用类型系统在编译期保证状态转换的合法性

struct Draft;
struct PendingReview;
struct Published;

// 用泛型参数编码状态
struct BlogPost<State> {
    title: String,
    content: String,
    _state: std::marker::PhantomData<State>,
}

// 草稿状态的方法
impl BlogPost<Draft> {
    fn new(title: String) -> Self {
        BlogPost {
            title,
            content: String::new(),
            _state: std::marker::PhantomData,
        }
    }

    fn write(mut self, text: &str) -> Self {
        self.content.push_str(text);
        self
    }

    // 提交审核：草稿 -> 待审核（类型转换！）
    fn submit(self) -> BlogPost<PendingReview> {
        BlogPost {
            title: self.title,
            content: self.content,
            _state: std::marker::PhantomData,
        }
    }
}

// 待审核状态的方法
impl BlogPost<PendingReview> {
    // 审批通过：待审核 -> 已发布
    fn approve(self) -> BlogPost<Published> {
        BlogPost {
            title: self.title,
            content: self.content,
            _state: std::marker::PhantomData,
        }
    }

    // 打回修改：待审核 -> 草稿
    fn reject(self) -> BlogPost<Draft> {
        BlogPost {
            title: self.title,
            content: self.content,
            _state: std::marker::PhantomData,
        }
    }
}

// 只有已发布的文章才能显示内容
impl BlogPost<Published> {
    fn display(&self) {
        println!("=== {} ===", self.title);
        println!("{}", self.content);
    }
}

fn main() {
    // 合法的状态转换流程
    let post = BlogPost::new(String::from("Rust 状态模式"))
        .write("Rust 的类型系统非常强大...")
        .write("它可以在编译期捕获状态错误。")
        .submit()        // Draft -> PendingReview
        .approve();      // PendingReview -> Published

    post.display();      // 只有 Published 状态才有 display 方法

    // post.submit(); // 编译错误！Published 状态没有 submit 方法
    // 编译器阻止了非法的状态转换！
}
```

这种方式的威力：**非法的状态转换在编译期就被捕获**，而不是在运行时抛出异常。

## 18.6 组合优于继承

Rust 用组合来代替继承——把一个功能的各个部分"组装"在一起，而不是层层继承。这是《设计模式》（GoF 四人帮）一书中最核心的原则之一："Favor object composition over class inheritance"。Rust 把这个原则提升到了语言层面——你**只能**用组合，因为没有继承可用。

**组合的实现方式**有两种：

1. **数据组合**：在一个 struct 中嵌入另一个 struct（类似 Java 的"有一个"关系）
2. **行为组合**：通过实现不同的 trait 来组合行为（类似"拥有某种能力"）

```rust
// 不要这样想：
// Animal -> Bird -> Penguin（继承层次）

// 要这样想：
// Penguin = { HasName, CanSwim, CannotFly, HasFeathers }（组合）

trait HasName {
    fn name(&self) -> &str;
}

trait CanFly {
    fn fly(&self);
}

trait CanSwim {
    fn swim(&self);
}

struct Penguin {
    name: String,
}

impl HasName for Penguin {
    fn name(&self) -> &str { &self.name }
}

impl CanSwim for Penguin {
    fn swim(&self) {
        println!("{} 在水中游泳", self.name());
    }
}

// 注意：Penguin 没有实现 CanFly——它不会飞！
// 在 Java 中，你可能需要在 Bird.fly() 里抛 UnsupportedOperationException

struct Eagle {
    name: String,
}

impl HasName for Eagle {
    fn name(&self) -> &str { &self.name }
}

impl CanFly for Eagle {
    fn fly(&self) {
        println!("{} 在天空翱翔", self.name());
    }
}

// 函数只关心"能飞"的能力
fn let_it_fly(bird: &dyn CanFly) {
    bird.fly();
}

fn main() {
    let eagle = Eagle { name: String::from("雄鹰") };
    let penguin = Penguin { name: String::from("企鹅") };

    eagle.fly();
    penguin.swim();

    let_it_fly(&eagle);
    // let_it_fly(&penguin); // 编译错误！企鹅不会飞——编译器帮你阻止了荒谬的操作
}
```

## 18.7 设计模式的 Rust 实现

设计模式（Design Patterns）是软件工程中经过验证的解决方案。经典的 GoF 23 种设计模式大多是为 C++/Java 设计的，在 Rust 中需要用不同的方式来实现。好消息是，Rust 的 trait 系统 + 枚举 + 闭包组合起来，往往能比传统 OOP 语言更优雅地实现这些模式。

**策略模式（Strategy Pattern）**——在运行时选择不同的算法实现：

策略模式的核心思想是：把"做什么"（算法）和"怎么用"（上下文）分开。在 Java 中你用接口 + 实现类来实现；在 Rust 中你有两种选择——用 trait 对象（动态分发）或泛型（静态分发）。下面用 trait 对象来实现：

```rust
// 用 trait + 函数指针/闭包实现策略模式
trait SortStrategy {
    fn sort(&self, data: &mut Vec<i32>);
}

struct BubbleSort;
impl SortStrategy for BubbleSort {
    fn sort(&self, data: &mut Vec<i32>) {
        let len = data.len();
        for i in 0..len {
            for j in 0..len - 1 - i {
                if data[j] > data[j + 1] {
                    data.swap(j, j + 1);
                }
            }
        }
    }
}

struct QuickSort;
impl SortStrategy for QuickSort {
    fn sort(&self, data: &mut Vec<i32>) {
        data.sort(); // 标准库排序（实际是 introsort）
    }
}

struct Sorter {
    strategy: Box<dyn SortStrategy>,
}

impl Sorter {
    fn new(strategy: Box<dyn SortStrategy>) -> Self {
        Sorter { strategy }
    }

    fn set_strategy(&mut self, strategy: Box<dyn SortStrategy>) {
        self.strategy = strategy;
    }

    fn sort(&self, data: &mut Vec<i32>) {
        self.strategy.sort(data);
    }
}

fn main() {
    let mut data = vec![64, 34, 25, 12, 22, 11, 90];

    let sorter = Sorter::new(Box::new(BubbleSort));
    sorter.sort(&mut data);
    println!("冒泡排序: {:?}", data);

    let mut data2 = vec![64, 34, 25, 12, 22, 11, 90];
    let sorter = Sorter::new(Box::new(QuickSort));
    sorter.sort(&mut data2);
    println!("快速排序: {:?}", data2);
}
```

**观察者模式（Observer Pattern）**——当一个对象的状态发生变化时，自动通知所有依赖它的对象：

这个模式在前端开发中非常常见：JavaScript 的 `addEventListener`、Vue 的 `watch`、React 的 `useEffect` 都是观察者模式的变体。在 Rust 中，我们可以用闭包 + trait 来优雅地实现它：

```rust
use std::collections::HashMap;

type EventCallback = Box<dyn Fn(&str)>;

struct EventEmitter {
    listeners: HashMap<String, Vec<EventCallback>>,
}

impl EventEmitter {
    fn new() -> Self {
        EventEmitter {
            listeners: HashMap::new(),
        }
    }

    // 注册观察者
    fn on<F: Fn(&str) + 'static>(&mut self, event: &str, callback: F) {
        self.listeners
            .entry(event.to_string())
            .or_insert_with(Vec::new)
            .push(Box::new(callback));
    }

    // 触发事件，通知所有观察者
    fn emit(&self, event: &str, data: &str) {
        if let Some(callbacks) = self.listeners.get(event) {
            for callback in callbacks {
                callback(data);
            }
        }
    }
}

fn main() {
    let mut emitter = EventEmitter::new();

    emitter.on("user_login", |data| {
        println!("[日志] 用户登录: {}", data);
    });

    emitter.on("user_login", |data| {
        println!("[统计] 登录次数 +1: {}", data);
    });

    emitter.on("error", |data| {
        println!("[告警] 发生错误: {}", data);
    });

    emitter.emit("user_login", "Alice");
    // [日志] 用户登录: Alice
    // [统计] 登录次数 +1: Alice

    emitter.emit("error", "连接超时");
    // [告警] 发生错误: 连接超时
}
```

## 常见陷阱

1. **过度使用 `dyn Trait`**：动态分发有运行时开销（vtable 查找）。如果类型在编译时已知，优先用泛型（静态分发）。经验法则：如果你的集合中只放一种类型，用泛型；如果需要放不同类型，用 `dyn Trait`。

2. **Trait 对象的生命周期**：`&dyn Trait` 和 `Box<dyn Trait>` 默认有 `'static` 生命周期的隐式约束（在 `Box` 情况下）。如果你需要引用非静态数据，需要显式标注 `Box<dyn Trait + 'a>`。

3. **对象安全（Object Safety）**：不是所有 trait 都能做 trait 对象。一个 trait 是"对象安全"的，当且仅当它满足两个条件：（a）方法不返回 `Self`；（b）方法没有泛型类型参数。如果 trait 违反了这些规则，你只能用泛型（静态分发），不能用 `dyn`。

4. **误用继承思维**：很多从 Java 来的开发者会试图在 Rust 中"模拟继承"——比如用 enum 来模拟子类、用 trait 默认方法来模拟父类实现。这通常意味着设计出了问题。Rust 鼓励你从"这个类型需要什么能力？"出发，而不是"这个类型是谁的子类？"。

5. **忘记 `dyn` 关键字**：在 Rust 2021 版本中，省略 `dyn` 会导致编译错误。如果你看到 "trait objects without an explicit `dyn` are deprecated" 这样的警告，加上 `dyn` 即可。

## 小结

| Java/C# 概念 | Rust 对应方案 |
| -------------- | -------------- |
| class | struct + impl |
| interface | trait |
| extends（继承） | 组合 + trait |
| abstract class | trait + 默认方法 |
| 多态（虚方法） | `dyn Trait`（动态分发）/ 泛型（静态分发） |
| 状态模式 | 类型状态（Type State） |
