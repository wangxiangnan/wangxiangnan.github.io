## 1.1 幽默开场：数据库界的"扫地僧"

想象一下这样的场景：你走进一家武林大会，MySQL 穿着华丽长袍，PostgreSQL 手持三尺青锋，Oracle 端坐正中打着算盘（叮咚，收费提示到账）。这时角落里有个扫地的老头，穿着朴素、话也不多，你以为是打杂的。

结果人家 GitHub Star 一亮：**"我叫 SQLite，世界上部署最多的数据库软件，全球活跃实例数超过一万亿。"**

你以为它是配角，其实它才是隐藏的大 BOSS。

你手机里的每一个 App、你浏览器的历史记录、你 macOS 的邮件、你飞机上娱乐系统里的电影列表、你汽车仪表盘里的导航数据……几乎都躺着一个 `.db` 文件，安静地跑着 SQLite。它不发朋友圈、不搞市场部、不搞订阅制，但它就在那里，比你女朋友还稳定。

作为一个程序员，你可能装过 MySQL 装到怀疑人生（"密码到底改哪个 my.cnf 啊！"），也可能配 PostgreSQL 配到血压升高（`pg_hba.conf` 你还记得吗），但你很可能从未安装过 SQLite —— 因为它压根就不需要"安装"。

**SQLite 的存在感就像空气：你几乎感觉不到它，但你须臾离不开它。**

## 1.2 SQLite 不是什么

想搞清楚 SQLite 是什么，我们先反着来。理解一样东西"不是什么"，往往比"是什么"更快建立正确心智模型。

### 1.2.1 不是 C/S 架构

来看你熟悉的画面：

```
[你的应用] ──TCP/IP──> [MySQL Server 进程] ──> [数据文件]
     ↑                        ↑
   客户端                   服务器
```

MySQL、PostgreSQL、Oracle、SQL Server —— 全都是这个套路：一个跑得好好的**独立服务器进程**（daemon），监听在 3306、5432 之类的端口上，你的应用通过网络协议跟它通信。

而 SQLite 长这样：

```
[你的应用进程]
   │
   ├── SQLite 库（编译进你的应用）
   │        │
   │        └── 直接读写 → foo.db 文件
```

**注意，没有网络、没有端口、没有独立进程、没有 root 用户。** SQLite 就是一个 C 语言库（`libsqlite3.so` / `sqlite3.dll`），被静态或动态链接进你的应用。你调用它的 API，它就直接去读写磁盘上的 `.db` 文件。

程序员梗时间：`ping localhost:3306` —— MySQL；`ping localhost:???` —— SQLite 说："兄弟你在跟谁通信呢，我就在你隔壁函数栈里坐着呢。"

### 1.2.2 没有独立服务器进程

因为没有服务器进程，所以：

- **没有 `systemctl start sqlite`。** 不需要开机自启，不需要监控服务健康。
- **没有网络配置。** 不需要开放端口，不需要担心防火墙。
- **没有用户/权限系统。** 数据库文件本身的读写权限，就是操作系统文件系统的权限（`chmod 644`）。
- **没有认证。** 谁能读文件谁就能读数据库。（想加密？看后续 SQLCipher 章节。）

### 1.2.3 不是"玩具数据库"

这是最大的误解，尤其在刚工作两年的后端同学口中：

> "SQLite 就是个玩具啦，怎么能上生产？"

来，我们看几个"玩具"用户：

- **Apple iOS**：每一个 iPhone 里，Contacts、Notes、Messages、Photos、Mail 都是 SQLite。
- **Android**：`android.database.sqlite` 是官方 API 的一等公民。
- **Chrome / Firefox / Safari**：书签、Cookie、历史记录、密码、Web SQL（虽然 Web SQL 已废弃但底层还是它）。
- **Windows 10/11**：内置了 SQLite 作为系统库。
- **Airbus A350 / A320neo**：飞控辅助系统使用 SQLite（是的，飞机上）。
- **PHP、Python**：标准库自带 SQLite 支持。

**"玩具"能玩到飞机上，你说这玩具重不重量级。**

## 1.3 SQLite 到底是什么

用一句话概括：

> **SQLite 是一个进程内、零配置、单文件、事务型（ACID）的嵌入式关系数据库引擎。**

我们把这句话拆开：

### 1.3.1 进程内（In-Process）

代码调用 SQLite 就跟调用 `printf` 一样直接。没有 IPC、没有网络、没有序列化，函数调用就完事儿。

**性能含义**：一次查询没有 TCP 三次握手、没有协议解析、没有连接池，延迟极低（微秒级）。这也是为什么 SQLite 在很多场景下比 MySQL 还快 —— 不是因为它引擎多牛，而是因为它省去了大量通信开销。

### 1.3.2 零配置（Zero-Configuration）

- 不需要安装。
- 不需要配置文件。
- 不需要创建用户。
- 不需要初始化数据目录。
- 不需要启动服务。

**"打开文件即数据库"**，这是它的 slogan。

### 1.3.3 单文件（Single-File）

一个数据库 = 一个 `.db` 文件（可能还有 `-wal`、`-shm` 两个辅助文件，后面章节详解）。

- 备份？`cp foo.db backup.db`（生产环境请使用 `.backup` 命令，见后续）。
- 迁移？拷贝文件。
- 版本控制？丢进 Git（虽然不推荐，但技术上可行）。
- 传输？发微信附件都行。

### 1.3.4 事务型（Transactional / ACID）

SQLite 支持完整的 ACID：

- **A**tomicity（原子性）：事务要么全成功，要么全失败，中间断电也不会留下半吊子数据。
- **C**onsistency（一致性）：约束、外键、触发器都会被遵守。
- **I**solation（隔离性）：并发访问下不会互相看到脏数据（依赖 WAL / rollback journal 模式）。
- **D**urability（持久性）：`COMMIT` 后即使断电也不丢（依赖 `fsync`）。

这套 ACID 甚至比很多"号称"支持事务的 NoSQL 数据库还要严格。SQLite 团队甚至写了一篇著名的文章 [How SQLite Is Tested](https://sqlite.org/testing.html)，光测试代码就是产品代码的 640 倍。

## 1.4 数据库家族比喻：一顿饭的解决方案

抽象概念不好记？我们用"吃饭"打比方：

| 数据库 | 类比 | 特点 |
| --- | --- | --- |
| **MySQL** | 大众餐厅 | 服务员（连接）在门口迎宾，厨师（服务进程）在后厨忙活，你排队点单等上菜。适合"顾客量大、菜单标准"的场景。 |
| **PostgreSQL** | 米其林大厨房 | 什么复杂菜（复杂查询、JSON、地理信息、扩展）都能做，功能全、可靠、稍慢一点点，但你就是信它。 |
| **Oracle** | 高档私人会所 | 味道确实好，就是账单让 CFO 想跳楼。 |
| **Redis** | 24 小时便利店 | 门口货架（内存）拿了就走，速度快到起飞。但你想吃个法式煎鹅肝？抱歉便利店没这个。 |
| **MongoDB** | 自助餐 | 你想装什么装什么（Schemaless），灵活自由，代价是有时候会捞出一坨稀奇古怪的东西。 |
| **SQLite** | 你家冰箱 | 就在家里，随开随取，不用打电话预订。存量小但足够日常，一停电就没了？不，是 fsync 后就在硬盘上，别慌。 |

理解了这个比喻，你就明白：**SQLite 不是要跟 MySQL 竞争的**，它俩根本不在一个赛道。你不会因为"隔壁餐厅装修得好"就把家里冰箱拆了 —— 你日常拿瓶可乐总不能打车去餐厅吧。

## 1.5 世界上部署最广的数据库

SQLite 官网有句原话，翻译过来是：

> SQLite 很可能是当今部署和使用最广泛的数据库引擎。全球有超过一万亿（10¹²）个 SQLite 数据库在运行。

一万亿是什么概念？地球上每个人平均有 125 个 SQLite 数据库跟你共存。

具体案例：

- **iOS**：Core Data 底层就是 SQLite。你的每条 iMessage、每张相册照片元数据，都活在 SQLite 里。
- **Android**：`SQLiteOpenHelper`、`Room` 都是包着 SQLite。
- **WhatsApp**：本地聊天记录 `msgstore.db`。
- **微信**：也是 SQLite（加密版本 WCDB，腾讯开源）。
- **Firefox**：书签 `places.sqlite`、Cookies `cookies.sqlite`。
- **Skype、Dropbox、Adobe Lightroom、Evernote……** 名单能列一整章。

**"如果全球所有的 SQLite 数据库同时罢工，人类文明会倒退一个小时。"** —— 我瞎编的名言，但可能是真的。

## 1.6 SQLite 的哲学：Small、Fast、Reliable、Choose Any Three

大部分工程原则告诉你："快、好、便宜，只能选两个。" SQLite 官网印的原话是：

> **Small. Fast. Reliable. Choose any three.**

翻译：**又小、又快、又稳，我全都要。**

这不是嘴硬。SQLite 大致数据：

- 源代码约 15 万行 C（不算测试），编译成库约 700 KB（可裁剪到 400 KB 以下）。
- 查询性能在中小数据集上（GB 级别）几乎完爆一切网络数据库（省了网络开销）。
- 测试覆盖率 100%（MC/DC 覆盖率），航空级别代码质量。

## 1.7 适用场景 vs 不适用场景

### 1.7.1 适合用 SQLite

- **移动端 / 桌面端应用本地存储。** 这是绝对的舒适区。
- **中小型网站** 后端（据说 hn 网页版有段时间用 SQLite 撑着，读多写少完全无压力）。
- **应用文件格式**（比如你要设计一个复杂的项目文件格式，别自己发明二进制协议了，用一个 SQLite 文件当容器）。
- **数据分析 / 临时缓存 / ETL 中间格式。**
- **嵌入式设备**（路由器、机顶盒、汽车）。
- **教学与原型验证。**
- **CI / 测试用的临时数据库**（比 mock 一个 MySQL 快多了）。

### 1.7.2 不适合用 SQLite

- **高并发写入的 Web 服务。** SQLite 的写是"数据库级别"的锁（默认），你要一秒钟并发 1000 次写入，扛不住。（虽然 WAL 模式已经好很多，但仍不建议超过每秒几百写入。）
- **超大数据集**（TB 级）。理论上 SQLite 单库支持 281 TB，但实际操作管理起来很痛苦。
- **需要网络访问的多客户端场景。** SQLite 本质是"进程内"，你要多台机器共享一个 DB，请直接 MySQL。
- **需要复杂用户权限管理的场景。**（SQLite 只有一个用户：能读那个文件的人。）
- **需要主从复制 / 集群的高可用场景。**（虽然有 rqlite、Litestream 这些外挂方案，但那属于"外挂"，不是 SQLite 原生能力。）

**一句话原则**：**读多写少、单机部署、无网络协作 —— SQLite 是神；反之则请出其他选手。**

## 1.8 版本历史与许可证

### 1.8.1 简史

- **2000 年 8 月**：Dwayne Richard Hipp（D. Richard Hipp，人称 "drh"）发布 SQLite 1.0。他本来是给美国海军写导弹驱逐舰上的控制软件，需要一个不需要 DBA 的嵌入式 DB —— 后来这个作品直接改变了世界。
- **2004 年**：3.0 发布，引入了现代 SQLite 的核心格式（后续所有 3.x 版本文件格式向后兼容）。
- **2010 年**：WAL 模式引入（3.7.0），并发性能大幅提升。
- **2018 年**：JSON1 内建（3.9+，实际上更早但 3.38 后成为默认）。
- **2021 年 12 月**：3.37.0 引入 STRICT 表。
- **2022 年 6 月**：3.39.0 引入 RIGHT JOIN 和 FULL OUTER JOIN（是的，你没看错，直到 2022 才有 RIGHT JOIN 😂）。
- **2024 年**：3.45+，我们本教程的基准版本。

### 1.8.2 许可证：Public Domain（公共领域）

SQLite 的代码是 **Public Domain（放弃版权，公共领域）**，比 MIT、Apache、BSD 都要"更自由"。

你可以：

- 商用。免费。
- 修改。免费。
- 闭源二次分发。免费。
- **不需要在你的产品里注明"本产品使用了 SQLite"。**

作者的原话大意是："软件应该像空气和阳光一样。"

**如果你实在过意不去**，SQLite 官方提供了一个可选的付费"祝福认证书（Warranty of Title）"，主要用于大公司法务合规。你要真买了，你会收到 D. Richard Hipp 亲笔签名的证书。据说不少 500 强企业把这个证书裱起来挂墙上。

## 1.9 与 MySQL / PostgreSQL 的核心差异对比

| 特性 | SQLite | MySQL | PostgreSQL |
| --- | --- | --- | --- |
| **架构** | 进程内库 | C/S | C/S |
| **默认端口** | 无 | 3306 | 5432 |
| **安装难度** | 无需安装 | 中等 | 中等 |
| **数据存储** | 单文件 | 多文件 + tablespaces | 多文件 + tablespaces |
| **数据类型系统** | 动态弱类型（类型亲和） | 严格 | 严格 |
| **默认字符集** | UTF-8 | latin1 / utf8mb4 | UTF-8 |
| **并发写** | 数据库级锁（WAL 下改善） | 行级锁 | 行级锁（MVCC） |
| **主从复制** | 无原生（可用 Litestream） | 内建 | 内建 |
| **用户权限系统** | 无 | 有 | 有 |
| **存储过程** | 无 | 有 | 有（PL/pgSQL 强大） |
| **外键默认开启** | 否（需 `PRAGMA foreign_keys=ON`） | 是（InnoDB） | 是 |
| **RIGHT JOIN** | 3.39+ 支持 | 支持 | 支持 |
| **FULL OUTER JOIN** | 3.39+ 支持 | 不支持（要用 UNION） | 支持 |
| **窗口函数** | 3.25+ 支持 | 8.0+ | 支持 |
| **CTE / 递归 CTE** | 支持 | 8.0+ | 支持 |
| **JSON 支持** | 内建（JSON1） | JSON 类型 | JSONB（一流公民） |
| **全文搜索** | FTS5（很强） | 有（较弱） | 有（tsvector 很强） |
| **地理空间** | R*Tree / SpatiaLite | MySQL Spatial | PostGIS（业界之王） |
| **触发器** | 支持 | 支持 | 支持 |
| **视图** | 支持（只读为主） | 支持 | 支持 |
| **物化视图** | 不支持 | 不支持 | 支持 |
| **CHECK 约束** | 支持 | 8.0.16+ | 支持 |
| **STRICT 表** | 3.37+ 支持 | 一直严格 | 一直严格 |
| **代码许可证** | Public Domain | GPL / 商业 | PostgreSQL License |

看完这张表，你应该心里有数：**SQLite 是"够用"级别的关系数据库，PostgreSQL 是"什么都要"级别的关系数据库，MySQL 在两者中间偏向"生态最广"。**

**如果 SQLite 有微信朋友圈**，它的封面大概能这么写："我上过天，下过海，进过手机，装过电脑，除了 24 小时高并发写入以外，我什么都行。"

## 1.11 本章小结

学完本章，你应该建立起对 SQLite 的核心心智模型：

- SQLite 是**嵌入式**、**进程内**、**单文件**、**零配置**的关系数据库；它不是 C/S 架构，没有独立服务器。
- 它是世界上部署最广的数据库，遍布手机、浏览器、桌面软件、飞机、汽车。
- 哲学是 **Small / Fast / Reliable，我全要**。
- 适合本地存储、中小型只读服务、应用文件格式、原型开发；不适合高并发写 Web 服务。
- 许可证是 **Public Domain**，商用无忧。
- 与 MySQL / PostgreSQL 的核心差异是**部署模式**，不是"能力大小"。
