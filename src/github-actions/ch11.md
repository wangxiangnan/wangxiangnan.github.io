# 第11章：Reusable Workflows——不要重复自己

## 引言：DRY 原则在 CI/CD 中的应用

如果你写过超过 5 个 GitHub Actions Workflow，你大概率经历过这种痛苦：

> "等等，这个部署流程我是不是在另一个 Workflow 里也写了一遍？"
> "为什么这个项目的测试流程和那个项目的几乎一样，只是 Node 版本不同？"
> "我改了 3 个 Workflow 里的同一段逻辑，下次改还得改 10 个文件……"

这就是 **Copy-Paste 驱动开发** 的恶果。在代码里我们信奉 DRY（Don't Repeat Yourself），但在 CI/CD 配置里，很多人不知不觉就成了 WET（Write Everything Twice）——甚至是 Write Everything Ten Times。

**Reusable Workflows** 就是 GitHub Actions 给你的一剂解药。它允许你定义一个"模板 Workflow"，然后在其他 Workflow 中像函数调用一样引用它。

## 定义一个 Reusable Workflow

Reusable Workflow 和普通的 Workflow 放在同一个目录（`.github/workflows/`），唯一的区别是触发器使用 `workflow_call`：

```yaml
# .github/workflows/reusable-deploy.yml
# 这是一个可复用的部署 Workflow——别人调用它，就像调用一个函数

name: Reusable Deploy

on:
  workflow_call:                       # 关键：声明这个 Workflow 可被其他 Workflow 调用
    inputs:                            # 定义"函数参数"
      environment:
        description: '部署目标环境'
        required: true
        type: string                   # 类型可以是 string, boolean, number
        default: 'staging'             # 默认值
      node-version:
        description: 'Node.js 版本'
        required: false
        type: string
        default: '20'
      build-command:
        description: '自定义构建命令'
        required: false
        type: string
        default: 'npm run build'
    outputs:                           # 定义"函数返回值"
      deploy-url:
        description: '部署后的 URL'
        value: ${{ jobs.deploy.outputs.url }}
      artifact-id:
        description: '构建产物的 Artifact ID'
        value: ${{ jobs.deploy.outputs.artifact-id }}
    secrets:                           # 定义需要传入的密钥
      DEPLOY_TOKEN:
        required: true
      SLACK_WEBHOOK:
        required: false                # 可选的密钥

# 下面是实际的 Job 定义，和普通 Workflow 没有区别
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}    # 使用传入的环境名
    outputs:
      url: ${{ steps.set-url.outputs.url }}
      artifact-id: ${{ steps.upload.outputs.artifact-id }}
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}

      - run: npm ci
      - run: ${{ inputs.build-command }}

      - name: 上传构建产物
        id: upload
        uses: actions/upload-artifact@v4
        with:
          name: deploy-${{ inputs.environment }}
          path: dist/

      - name: 部署
        id: set-url
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
        run: |
          echo "部署到 ${{ inputs.environment }}..."
          # 模拟部署
          echo "url=https://${{ inputs.environment }}.myapp.com" >> $GITHUB_OUTPUT

      - name: 通知 Slack（可选）
        if: ${{ secrets.SLACK_WEBHOOK != '' }}
        run: |
          curl -X POST "${{ secrets.SLACK_WEBHOOK }}" \
            -d '{"text":"部署到 ${{ inputs.environment }} 完成！"}'
```

## 调用 Reusable Workflow

调用方式和写一个普通的 Job 差不多，只是用 `uses` 指向另一个 Workflow 文件：

```yaml
# .github/workflows/main.yml
name: Main CI/CD Pipeline

on:
  push:
    branches: [main]

jobs:
  # 先跑测试
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

  # 调用可复用的部署 Workflow —— 部署到 Staging
  deploy-staging:
    needs: test
    uses: ./.github/workflows/reusable-deploy.yml    # 同仓库引用：用 ./ 开头
    with:
      environment: staging
      node-version: '20'
      build-command: 'npm run build:staging'
    secrets:
      DEPLOY_TOKEN: ${{ secrets.STAGING_DEPLOY_TOKEN }}
      SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK_URL }}

  # 调用同一个 Workflow —— 部署到 Production
  deploy-production:
    needs: deploy-staging              # 等 Staging 部署成功后再部署 Production
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      environment: production
      node-version: '20'
      build-command: 'npm run build:prod'
    secrets: inherit                   # 偷懒写法：把当前 Workflow 的所有 secrets 都传过去
    # ⚠️ secrets: inherit 虽然方便，但要注意权限范围

  # 使用 Reusable Workflow 的输出
  notify:
    needs: deploy-production
    runs-on: ubuntu-latest
    steps:
      - name: 打印部署结果
        run: |
          echo "部署地址: ${{ needs.deploy-production.outputs.deploy-url }}"
          echo "产物ID: ${{ needs.deploy-production.outputs.artifact-id }}"
```

## 引用其他仓库的 Reusable Workflow

团队共享的 Workflow 通常放在一个专门的仓库中：

```yaml
# 引用其他仓库的 Reusable Workflow
jobs:
  deploy:
    uses: my-org/shared-workflows/.github/workflows/deploy.yml@main
    # 格式：{owner}/{repo}/{path}@{ref}
    # @main 表示使用 main 分支的版本——你也可以用 tag 或 commit SHA
    with:
      environment: production
    secrets:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

## 嵌套限制和注意事项

Reusable Workflows 支持嵌套——一个 Reusable Workflow 可以调用另一个 Reusable Workflow。但 GitHub 设了上限：

- **最大嵌套深度**：4 层（包括最初的调用者）
- **单次运行中的最大 Job 数**：256 个
- **可引用的范围**：同一仓库、同一组织的仓库、公开仓库

```yaml
# 嵌套示例（3层）
# level-1.yml 调用 level-2.yml
# level-2.yml 调用 level-3.yml
# level-3.yml 调用 level-4.yml ← 到这里就到极限了
# level-4.yml 不能再调用任何 Reusable Workflow
```

> **⚠️ 注意：Reusable Workflow 中的 `uses` 只能用 `workflow_call` 触发器。**
> 也就是说，一个 Reusable Workflow 不能同时有 `push` 和 `workflow_call`——如果你想让同一个 Workflow 既能独立运行又能被调用，你需要把它拆成两个文件，或者用下面要讲的 Composite Actions。

## Composite Actions vs Reusable Workflows 的选择

这是一个经典的选择题，就像 `extends` vs `composition`——两种方案都能实现复用，但适用场景不同：

```
什么时候用 Reusable Workflow？
├── 你需要完整的 Workflow（包含多个 Job）
├── 你需要 Matrix 策略
├── 你需要 Environment 保护规则
├── 你需要在 Workflow 之间传递 Secrets
└── 你需要"调用一个完整的流程"

什么时候用 Composite Action？
├── 你只需要复用一组 Steps（在单个 Job 内）
├── 你想要更灵活的组合方式
├── 你不需要 Secrets 传递（Composite 用 env 变通）
├── 你想要更好的"可插拔"体验
└── 你需要"执行一个工具/步骤"
```

简单说：**Reusable Workflow 是"调用一个微服务"，Composite Action 是"调用一个函数"。**

## 实际案例：团队共享的发布流程

```yaml
# 团队共享仓库：my-org/release-workflows
# 文件：.github/workflows/npm-publish.yml
# 标准化的 npm 发布流程，所有团队的项目都可以复用

name: NPM Publish (Reusable)

on:
  workflow_call:
    inputs:
      registry-url:
        description: 'npm registry URL'
        required: false
        type: string
        default: 'https://registry.npmjs.org'
      tag:
        description: '发布标签 (latest, next, beta)'
        required: false
        type: string
        default: 'latest'
      dry-run:
        description: '是否模拟运行（不真正发布）'
        required: false
        type: boolean
        default: false
    secrets:
      NPM_TOKEN:
        required: true

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write        # 如果需要 provenance
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: ${{ inputs.registry-url }}

      - run: npm ci
      - run: npm run build
      - run: npm test

      - name: 发布到 npm
        run: |
          PUBLISH_CMD="npm publish --tag ${{ inputs.tag }}"
          if [ "${{ inputs.dry-run }}" = "true" ]; then
            PUBLISH_CMD="$PUBLISH_CMD --dry-run"
          fi
          echo "执行: $PUBLISH_CMD"
          eval $PUBLISH_CMD
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

然后在各个项目仓库中：

```yaml
# 项目 A 的 Workflow
name: Release
on:
  push:
    tags: ['v*']

jobs:
  publish:
    uses: my-org/release-workflows/.github/workflows/npm-publish.yml@v1
    with:
      tag: latest
    secrets:
      NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

这样一来，团队的所有 npm 包都遵循同一套发布标准。想更新发布流程？改一个地方，所有项目同时受益。这就是 **Infrastructure as Code** 的魅力。

## 小结

Reusable Workflows 是大规模使用 GitHub Actions 时的必备武器：

- **减少重复**：写一次，到处用
- **统一标准**：团队的最佳实践编码到 Workflow 里，而不是靠口口相传
- **降低出错**：修改一处逻辑而不是在 20 个文件里做同样的修改
- **版本管理**：用 tag 引用，可以安全地升级或回退

## 练习题

1. **基础题**：创建一个 Reusable Workflow，接收一个 `message` 输入参数，在 Job 中打印这个消息。然后在另一个 Workflow 中调用它。
2. **进阶题**：设计一个团队共享的"质量门禁"Reusable Workflow，包含 lint、类型检查、单元测试三个步骤，支持通过 inputs 配置 eslint 规则文件和测试命令。
3. **设计题**：你有 5 个微服务，每个都有自己的部署流程，但步骤高度相似（构建 → Docker 镜像 → 推送到 Registry → 更新 K8s）。请设计一个 Reusable Workflow 来统一这个流程，并说明哪些部分应该参数化。
