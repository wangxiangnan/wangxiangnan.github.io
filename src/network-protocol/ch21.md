# 第21章：gRPC 与 Protobuf——高效的 RPC 协议

## RPC 的概念：像调用本地函数一样调用远程服务

想象你有一个微服务架构：用户服务、订单服务、支付服务。订单服务需要查询用户信息，它不可能直接调用用户服务的内存函数——它们在不同的机器上。**RPC（Remote Procedure Call，远程过程调用）** 的目标就是让远程调用看起来像本地调用一样自然。

```python
# 理想中的 RPC 调用——看起来就像调用本地函数
user = user_service.get_user(user_id=12345)
# 但实际上，这个调用跨越了网络，到达了另一台机器
```

实现这个"魔法"需要：序列化（把参数变成字节）、传输（通过网络发送字节）、反序列化（在另一端还原参数）。

## REST vs gRPC：JSON 文本 vs Protobuf 二进制

传统的微服务通信通常使用 REST + JSON。JSON 是人类可读的，但它有几个问题：

1. **体积大**：`{"name": "Alice", "age": 30, "email": "alice@example.com"}` 占了 55 字节，大量键名重复。
2. **类型模糊**：JSON 中 `30` 是整数还是浮点数？`"true"` 是字符串还是布尔值？需要运行时推断。
3. **没有强类型契约**：API 变更时，客户端可能在运行时才发现字段缺失。

gRPC 用 **Protocol Buffers（Protobuf）** 替代 JSON，用 **HTTP/2** 替代 HTTP/1.1，从根本上解决了这些问题。

## Protocol Buffers：Google 的高效序列化格式

Protobuf 的核心思想：**用数字而不是字符串来标识字段**。

先看一个 `.proto` 文件定义：

```protobuf
syntax = "proto3";

message User {
  string name = 1;       // 字段编号 1
  int32 age = 2;         // 字段编号 2
  string email = 3;      // 字段编号 3
  repeated string tags = 4;  // 数组类型
}

message GetUserRequest {
  int32 user_id = 1;
}

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
```

每个字段后面的 `= 1`、`= 2` 不是默认值，而是**字段编号（Field Number）**。序列化时，Protobuf 用这个编号而不是字段名来标识数据。

**Wire Type（线类型）** 告诉解码器如何读取数据：

| Wire Type | 含义 | 用途 |
| --- | --- | --- |
| 0 | Varint | int32, int64, bool, enum |
| 1 | 64-bit | double, fixed64 |
| 2 | Length-delimited | string, bytes, message, repeated |
| 5 | 32-bit | float, fixed32 |

编码过程（以 `age = 30` 为例）：

- 字段编号 2，Wire Type 0（Varint）→ 标签字节 = `(2 << 3) | 0` = `0x10`
- 值 30 的 Varint 编码 = `0x1E`
- 结果：`0x10 0x1E`，只用了 2 字节

同样的数据用 JSON：`"age": 30` 需要 8 字节。字段越多，Protobuf 的优势越明显。

## 为什么 Protobuf 比 JSON 小且快

1. **字段名不传输**：`name`、`email` 这些字符串完全不出现在序列化数据中，只有数字编号。
2. **Varint 编码**：小数字用 1 字节，大数字用更多字节，自适应压缩。
3. **无空白字符**：没有 `{`、`"`、`,` 这些 JSON 的结构字符。
4. **编译时类型检查**：代码生成器在编译时就知道每个字段的类型，不需要运行时解析。

一个实际的基准测试：一个包含 10 个字段的典型消息，JSON 序列化约 300 字节，Protobuf 约 80 字节——缩小了 3.5 倍。序列化/反序列化速度快 5-10 倍。

## gRPC 的四种调用模式

```
1. Unary（一元调用）：
   Client → Request → Server → Response
   例：GetUser(request) → user

2. Server Streaming（服务端流）：
   Client → Request → Server → Response1, Response2, Response3...
   例：WatchStock(symbol) → 持续推送价格

3. Client Streaming（客户端流）：
   Client → Request1, Request2, Request3... → Server → Response
   例：UploadChunks(data...) → 最终返回上传结果

4. Bidirectional Streaming（双向流）：
   Client ⇄ Server（双向独立流）
   例：Chat 应用——客户端和服务器同时发消息
```

```protobuf
service ChatService {
  // 一元调用
  rpc SendMessage (Message) returns (Ack);
  // 服务端流
  rpc SubscribeChannel (ChannelRequest) returns (stream Message);
  // 客户端流
  rpc UploadFile (stream FileChunk) returns (UploadResult);
  // 双向流
  rpc Chat (stream Message) returns (stream Message);
}
```

## gRPC 在微服务架构中的位置

gRPC 最适合**服务间通信（内部 RPC）**——延迟敏感、带宽有限、需要强类型契约的场景。但对于面向外部的 API，REST 仍然是更好的选择，因为：

- 浏览器原生支持 REST/JSON
- REST 的调试工具更成熟
- REST 的语义（GET/POST/PUT/DELETE）更通用

实践中常见的模式是：内部用 gRPC，外部用 REST，中间加一个 API Gateway 做协议转换。

## gRPC-Web：浏览器端的 gRPC

浏览器无法直接发起 gRPC 调用（无法控制 HTTP/2 帧），所以 gRPC-Web 通过一个代理（如 Envoy）将 gRPC-Web 请求转换为标准 gRPC。这保留了 Protobuf 的效率和强类型，同时兼容浏览器环境。

## 编程实践：Python gRPC 实战

```protobuf
// file: greet.proto
syntax = "proto3";

package greet;

message GreetRequest {
  string name = 1;
}

message GreetResponse {
  string message = 1;
}

service Greeter {
  rpc SayHello (GreetRequest) returns (GreetResponse);
}
```

```bash
# 生成 Python 代码
python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. greet.proto
```

```python
# server.py
import grpc
from concurrent import futures
import greet_pb2
import greet_pb2_grpc

class GreeterServicer(greet_pb2_grpc.GreeterServicer):
    def SayHello(self, request, context):
        return greet_pb2.GreetResponse(
            message=f"Hello, {request.name}! Welcome to gRPC."
        )

server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
greet_pb2_grpc.add_GreeterServicer_to_server(GreeterServicer(), server)
server.add_insecure_port('[::]:50051')
server.start()
print("gRPC server running on port 50051...")
server.wait_for_termination()
```

```python
# client.py
import grpc
import greet_pb2
import greet_pb2_grpc

channel = grpc.insecure_channel('localhost:50051')
stub = greet_pb2_grpc.GreeterStub(channel)

response = stub.SayHello(greet_pb2.GreetRequest(name="Alice"))
print(f"Server says: {response.message}")
```

## 抓包实践：对比 gRPC 与 REST 报文

```bash
# 抓取 gRPC 流量（默认在 50051 端口）
tshark -i lo -f "tcp port 50051" -V -c 10

# 对比报文大小
echo "=== REST JSON ==="
curl -s -o /dev/null -w "Response size: %{size_download} bytes\n" \
  http://localhost:8080/api/greet?name=Alice

echo "=== gRPC Protobuf ==="
# gRPC 响应大小可以从抓包中获取
```

在 Wireshark 中，gRPC 消息的 DATA 帧内容看起来是"乱码"——因为它是二进制 Protobuf 编码，不是人类可读的文本。这正是它高效的代价（也是它需要 `.proto` 文件才能解码的原因）。Wireshark 的 gRPC 解析器可以在 Preferences 中配置 proto 文件路径来解码内容。
