# 第10章：TCP 拥塞控制——网络的自我保护

## 为什么需要拥塞控制：公地悲剧

假设一条 100Mbps 的链路连接了 100 台电脑。如果每台电脑都以 100Mbps 的速度发送数据，总需求是 10Gbps，远超链路的 100Mbps 容量。结果：路由器缓冲区溢出，大量丢包，每台电脑都在疯狂重传，进一步加重拥塞——最终所有人都几乎无法通信。

这就是经济学中的 **公地悲剧（Tragedy of the Commons）**：每个个体都追求自身利益最大化（尽可能快地发送数据），最终导致公共资源（网络带宽）被耗尽，所有人的利益都受损。

TCP 的拥塞控制就是一种 **分布式协作机制**——每个 TCP 发送方根据网络状况自主调节发送速率，当检测到拥塞时主动降速，当网络空闲时逐步提速。没有中央控制器，没有全局协调，但数十亿个 TCP 连接就这样和谐地共享着互联网。这堪称分布式系统设计的典范。

## 拥塞窗口（cwnd）与发送者窗口（swnd）的关系

TCP 发送方的实际发送窗口受两个因素约束：

```
发送窗口 swnd = min(rwnd, cwnd)

其中：
  rwnd = 接收方在 TCP 报头中声明的接收窗口（反映接收方能力）
  cwnd = 拥塞控制算法维护的拥塞窗口（反映网络容量）
```

- **rwnd** 由接收方控制：如果接收方处理不过来，它会减小 rwnd，发送方相应减速。
- **cwnd** 由发送方根据网络反馈自主调节：如果检测到拥塞，发送方减小 cwnd；如果网络通畅，发送方增大 cwnd。

发送方取两者的较小值——即使网络带宽充裕（cwnd 很大），如果接收方处理不了（rwnd 很小），也不能发太多；反之亦然。

## 慢启动（Slow Start）：指数增长的智慧

当一条 TCP 连接刚建立时，发送方对网络的容量一无所知。它不知道瓶颈链路是 1Mbps 还是 10Gbps。如果一上来就以很高速率发送，可能会瞬间淹没一条低速链路。

**慢启动** 的策略是：从一个很小的 cwnd 开始，每收到一个 ACK，cwnd 增加一个 MSS。这意味着每经过一个 RTT，cwnd 翻倍（指数增长）。

```
初始 cwnd = 10 MSS（RFC 6928 推荐，Linux 默认）
第 1 个 RTT：发送 10 个段，收到 10 个 ACK → cwnd = 20
第 2 个 RTT：发送 20 个段，收到 20 个 ACK → cwnd = 40
第 3 个 RTT：发送 40 个段，收到 40 个 ACK → cwnd = 80
...
```

虽然是"慢"启动，但指数增长其实非常快！10 个 RTT 后 cwnd 就能达到 10240 MSS。如果 MSS=1460 字节、RTT=50ms，那么 500ms 后 cwnd 就能达到约 14.3MB。

慢启动会一直持续，直到以下任一条件触发：

1. **cwnd 达到 ssthresh（慢启动阈值）**：转入拥塞避免阶段。
2. **检测到丢包（超时或 3 个重复 ACK）**：说明找到了网络瓶颈，需要减速。

## 拥塞避免（Congestion Avoidance）：线性增长

当 cwnd 超过 ssthresh 后，TCP 进入 **拥塞避免** 阶段。此时增长策略从指数变为 **线性**：每经过一个 RTT，cwnd 增加一个 MSS。

```
第 N 个 RTT：cwnd = W
第 N+1 个 RTT：cwnd = W + 1
第 N+2 个 RTT：cwnd = W + 2
```

为什么要从指数变为线性？因为此时 cwnd 已经比较大，继续指数增长可能会很快导致拥塞。线性增长是一种更保守的试探——慢慢逼近网络的真实容量。

当拥塞避免阶段检测到丢包时：

- **超时丢包**：说明拥塞严重。`ssthresh = cwnd / 2`，`cwnd = 1 MSS`，重新进入慢启动。
- **3 个重复 ACK（快速重传触发）**：说明拥塞较轻。`ssthresh = cwnd / 2`，进入快速恢复。

这就产生了经典的 **锯齿形（Sawtooth）窗口变化**：

```
cwnd
  ^
  |     /\        /\
  |    /  \      /  \
  |   /    \    /    \
  |  /      \  /      \
  | /        \/        \
  |/                     → 时间
  +---+---+---+---+---+
  慢启动 拥塞避免 丢包 慢启动 拥塞避免
```

cwnd 缓慢增长，直到丢包，然后骤降，再缓慢增长——像一个不断试探天花板的弹簧。

## Reno vs CUBIC vs BBR：不同算法的设计哲学

TCP 拥塞控制算法在过去几十年经历了多次演进：

**TCP Reno（1990 年代）**

Reno 是经典的拥塞控制算法，核心思想就是上面描述的：慢启动（指数增长）→ 拥塞避免（线性增长）→ 丢包减半 → 快速恢复。

Reno 的问题在于它的 **RTT 公平性**：RTT 较长的连接（如跨国链路）在拥塞避免阶段增长更慢（因为每个 RTT 只增长 1 MSS），所以会"抢不过"RTT 短的连接。此外，在高带宽高延迟的网络（BDP 很大）中，Reno 的线性增长太慢，无法充分利用带宽。

**TCP CUBIC（2005 年，Linux 默认）**

CUBIC 是 Linux 内核自 2.6.13 以来的默认拥塞控制算法。它用一个 **三次函数（cubic function）** 来替代 Reno 的线性增长：

```
cwnd(t) = C × (t - K)³ + W_max

其中：
  C = 常数（默认 0.4）
  K = 三次函数的拐点时间
  W_max = 上一次丢包时的 cwnd 值
  t = 自上次丢包以来经过的时间
```

三次函数的形状像一个 S 曲线：在丢包后初期增长较慢（避免再次触发拥塞），中期快速增长（尽快恢复到之前的吞吐量），接近 W_max 时又变慢（谨慎试探）。

CUBIC 的优势：

- 在高 BDP 网络中比 Reno 更能利用带宽
- 对 RTT 的依赖性更低，公平性更好
- 向后兼容 Reno（在低 BDP 网络中行为接近 Reno）

**TCP BBR（2016 年，Google 开发）**

BBR（Bottleneck Bandwidth and Round-trip propagation time）代表了一种 **全新的思路**：不依赖丢包作为拥塞信号，而是主动测量网络的 **瓶颈带宽（BtlBw）** 和 **最小 RTT（RTprop）**。

BBR 的核心思想：

1. 持续测量 BtlBw（通过观察 ACK 的返回速率）和 RTprop（通过观察最小 RTT）。
2. 以 BtlBw 为发送速率，保持管道"刚好填满"而不溢出。
3. 周期性地在"探测带宽"和"探测 RTT"之间切换。

BBR vs CUBIC 的关键区别：

- CUBIC 需要等到丢包才知道拥塞了——这是 **被动反应**。
- BBR 通过测量带宽变化来预判拥塞——这是 **主动适应**。
- 在有缓冲膨胀（Bufferbloat）的网络中，CUBIC 会填满路由器缓冲区导致高延迟，BBR 则不会。

## ECN（Explicit Congestion Notification）：网络主动告诉你拥塞了

传统 TCP 通过 **丢包** 来推断拥塞——这是一种间接的、滞后的信号。丢包意味着拥塞已经发生并且已经造成了数据丢失。

**ECN** 提供了一种更优雅的方式：路由器在检测到拥塞即将发生时（缓冲区快满了但还没溢出），在 IP 报头中设置一个标记位（ECN-Echo），而不是直接丢包。接收方看到标记后，通过 TCP 报头中的 ECE（ECN-Echo）标志告知发送方减速。

```
传统方式：  拥塞 → 丢包 → 发送方发现 → 减速（已经丢了数据）
ECN 方式：  拥塞 → 标记 → 接收方转发 → 发送方减速（没有丢数据）
```

ECN 需要在两端和中间路由器上都启用。在 Linux 上可以这样开启：

```bash
sudo sysctl -w net.ipv4.tcp_ecn=1
```

ECN 在数据中心网络中效果显著，因为数据中心的交换机缓冲区较小，丢包率较高，ECN 可以有效减少丢包导致的重传。

## 编程实践：用 Python 可视化不同拥塞控制算法的 cwnd 变化曲线

```python
import matplotlib.pyplot as plt
import numpy as np

def simulate_reno(rtt_ms=50, mss=1460, duration_rtt=200, loss_at=None):
    """模拟 TCP Reno 的 cwnd 变化"""
    cwnd = [10]  # 初始窗口 10 MSS
    ssthresh = 65535
    phase = ['slow_start']

    for t in range(1, duration_rtt):
        current = cwnd[-1]

        # 在指定时刻制造丢包
        if loss_at and t in loss_at:
            ssthresh = max(current // 2, 2)
            if t in (loss_at or []):
                # 超时丢包：回到慢启动
                cwnd.append(1)
                phase.append('slow_start')
                continue

        if current < ssthresh:
            # 慢启动：指数增长
            cwnd.append(current * 2)
            phase.append('slow_start')
        else:
            # 拥塞避免：线性增长（每 RTT 加 1）
            cwnd.append(current + 1)
            phase.append('congestion_avoidance')

    return cwnd

def simulate_cubic(rtt_ms=50, mss=1460, duration_rtt=200, loss_at=None):
    """模拟 TCP CUBIC 的 cwnd 变化（简化版）"""
    cwnd = [10]
    ssthresh = 65535
    w_max = 0
    t_since_loss = 0
    C = 0.4

    for t in range(1, duration_rtt):
        current = cwnd[-1]

        if loss_at and t in loss_at:
            w_max = current
            ssthresh = max(int(current * 0.7), 2)
            cwnd.append(1)
            t_since_loss = 0
            continue

        t_since_loss += 1

        if current < ssthresh:
            cwnd.append(min(current * 2, ssthresh))
        else:
            # CUBIC 的三次函数增长（简化）
            K = (w_max * 0.3 / C) ** (1/3) if w_max > 0 else 5
            cubic_cwnd = C * (t_since_loss - K) ** 3 + w_max
            # 取 CUBIC 和 Reno 线性增长的较大值
            reno_cwnd = current + 1
            cwnd.append(int(max(cubic_cwnd, reno_cwnd, current + 1)))

    return cwnd

# 设置丢包点
loss_points_reno = [40, 100, 160]
loss_points_cubic = [40, 100, 160]

reno_cwnd = simulate_reno(loss_at=loss_points_reno)
cubic_cwnd = simulate_cubic(loss_at=loss_points_cubic)

# 绘图
fig, axes = plt.subplots(2, 1, figsize=(12, 8))

t_reno = range(len(reno_cwnd))
axes[0].plot(t_reno, reno_cwnd, 'b-', linewidth=1.5, label='cwnd')
axes[0].axhline(y=0, color='k', linewidth=0.5)
for lp in loss_points_reno:
    axes[0].axvline(x=lp, color='r', linestyle='--', alpha=0.5, label='Packet Loss' if lp == loss_points_reno[0] else '')
axes[0].set_title('TCP Reno: cwnd over time (Slow Start → Congestion Avoidance → Loss)', fontsize=13)
axes[0].set_xlabel('RTT')
axes[0].set_ylabel('cwnd (MSS)')
axes[0].legend()
axes[0].grid(True, alpha=0.3)

t_cubic = range(len(cubic_cwnd))
axes[1].plot(t_cubic, cubic_cwnd, 'g-', linewidth=1.5, label='cwnd')
for lp in loss_points_cubic:
    axes[1].axvline(x=lp, color='r', linestyle='--', alpha=0.5, label='Packet Loss' if lp == loss_points_cubic[0] else '')
axes[1].set_title('TCP CUBIC: cwnd over time (Cubic Growth after Loss)', fontsize=13)
axes[1].set_xlabel('RTT')
axes[1].set_ylabel('cwnd (MSS)')
axes[1].legend()
axes[1].grid(True, alpha=0.3)

plt.tight_layout()
plt.savefig('tcp_congestion_comparison.png', dpi=150)
plt.show()
print("图表已保存为 tcp_congestion_comparison.png")
```

运行这段代码，你会看到：

- **Reno 的曲线**：经典的锯齿形——慢启动阶段指数飙升，丢包后骤降，然后线性缓慢恢复。
- **CUBIC 的曲线**：丢包后的恢复路径呈 S 形（三次函数），初期和末期增长较慢，中间快速增长。这使得 CUBIC 在高带宽网络中能更快地恢复到之前的吞吐量。

## 抓包实践：在大文件传输中观察 TCP 的锯齿形窗口变化

使用 `iperf3` 进行一次长时间的 TCP 传输，并人为引入丢包：

```bash
# 终端1
iperf3 -s

# 终端2：设置 1% 丢包率
sudo tc qdisc add dev lo root netem loss 1% delay 10ms
iperf3 -c 127.0.0.1 -t 30

# 抓包
sudo tcpdump -i lo port 5201 -nn -w congestion.pcap
```

在 Wireshark 中打开 `congestion.pcap`，使用 **Statistics → TCP Stream Graphs → Window Scaling** 或 **Bytes in Flight** 图表。

你会观察到：

1. **Bytes in Flight（在途字节数）** 呈现出明显的锯齿形：
   - 从 0 开始快速增长（慢启动阶段，指数增长）
   - 达到某个峰值后突然下降（检测到丢包）
   - 然后缓慢线性恢复（拥塞避免阶段）
   - 周期大约为 2-5 秒，取决于丢包率和 RTT

2. **接收窗口（rwnd）** 在整个传输过程中保持相对恒定（比如 65535 或更大），说明瓶颈不在接收方，而在网络拥塞控制。

3. **RTT 变化图** 会显示：在 cwnd 增长阶段，RTT 逐渐增加（路由器缓冲区被填满），丢包后 RTT 下降（缓冲区排空），然后再次上升——这就是 Bufferbloat 现象的直观体现。

测试完毕后清理：

```bash
sudo tc qdisc del dev lo root
```
