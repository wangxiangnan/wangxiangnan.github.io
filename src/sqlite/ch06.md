## 6.1 开场白：一个让 Java 程序员血压升高的类型系统

想象一下你是一个从 Java/C# 世界过来的程序员，你打开 SQLite，写下：

```sql
CREATE TABLE user(age TEXT);
INSERT INTO user VALUES (18);
INSERT INTO user VALUES ('eighteen');
INSERT INTO user VALUES (18.5);
INSERT INTO user VALUES (X'DEADBEEF');
```

然后你惊讶地发现——**它全都接受了**。

你的大脑里 MySQL 的严谨小人开始尖叫："TEXT 列怎么能存整数？还能存 BLOB？这不是异端邪说吗？"

欢迎来到 SQLite 的世界。这里不讲究"你说啥类型就是啥类型"的静态类型洁癖，SQLite 信奉的是**动态类型 + 类型亲和性（Type Affinity）** 的社会人哲学："能沟通就行，型不型的，你说了不算，值说了算。"

用编程语言打比方：MySQL/PostgreSQL 像 Java，"你声明是 String 那就必须是 String"；SQLite 像 JavaScript/Python，"这是个 `age` 字段？我猜大概是数字吧，你塞什么我都收着，但我心里有杆秤"。

这一章我们就来搞懂这个"心里的秤"到底是怎么称的。

## 6.2 五种存储类（Storage Class）——SQLite 的"户籍"

SQLite 内部只认识 **5 种存储类**（Storage Class），这才是数据在磁盘上真正的样子：

| 存储类   | 含义                                | 类比            |
| -------- | ----------------------------------- | --------------- |
| NULL     | 空值，什么都没有                    | `null`          |
| INTEGER  | 有符号整数，1/2/3/4/6/8 字节        | `int64_t`       |
| REAL     | IEEE 754 双精度浮点数（8 字节）     | `double`        |
| TEXT     | UTF-8/UTF-16 编码的字符串           | `String`        |
| BLOB     | 二进制大对象，原样存储              | `byte[]`        |

**关键点 1：INTEGER 是变长的**。SQLite 不会用固定的 4 字节存 `1`，它会根据实际值选择 1~8 字节（叫做 varint 编码），存 `1` 只花 1 字节。这就是为什么 SQLite 的数据库文件常常出人意料地小。

**关键点 2：没有 BOOLEAN**。SQLite 3.45 依然没有独立的布尔类型，`TRUE` 是 `1`、`FALSE` 是 `0`（3.23+ 支持 `TRUE`/`FALSE` 关键字，但底层还是整数）。

**关键点 3：没有 DATE/DATETIME**。日期时间在 SQLite 里"以三种身份出现"——TEXT（ISO8601 字符串）、REAL（儒略日）、INTEGER（Unix 时间戳）。到底选哪种？这是本章后面的重头戏。

用 SQL 直接看某个值的存储类：

```sql
SELECT typeof(1), typeof(1.5), typeof('hi'), typeof(NULL), typeof(X'0A');
-- integer|real|text|null|blob
```

## 6.3 声明类型 vs 存储类——一场华丽的骗局

看下面这个建表语句：

```sql
CREATE TABLE weirdo(
  a INTEGER,
  b TEXT,
  c BLOB,
  d REAL,
  e NUMERIC,
  f VARCHAR(255),        -- (255) 会被忽略
  g DECIMAL(10, 2),      -- (10, 2) 会被忽略
  h SUPER_MEGA_TYPE,     -- 你没看错，随便写
  i                      -- 甚至可以不写类型
);
```

**这些声明的类型，SQLite 会全部接受**。因为 SQLite 3（非 STRICT 模式）里，列的"声明类型"只是给它一个**参考建议**，用于计算出一个叫做**类型亲和性（Type Affinity）** 的东西。真正影响存储的是亲和性 + 值本身。

亲和性一共 5 种：**TEXT / NUMERIC / INTEGER / REAL / BLOB**。

## 6.4 亲和性规则：SQLite 的"匹配算法"

给你一个列的声明类型字符串（比如 `VARCHAR2(50)`、`DOUBLE PRECISION`、`FLOATING POINT` 甚至 `什么鬼`），SQLite 按下面这 5 条规则**从上往下匹配**（这是官方文档 3.1 节的原话）：

1. 声明类型里包含 `"INT"` → **INTEGER** 亲和性
2. 声明类型里包含 `"CHAR"` / `"CLOB"` / `"TEXT"` → **TEXT** 亲和性
3. 声明类型里包含 `"BLOB"`，或者根本没有声明类型 → **BLOB** 亲和性
4. 声明类型里包含 `"REAL"` / `"FLOA"` / `"DOUB"` → **REAL** 亲和性
5. 其他（比如 `NUMERIC`、`DECIMAL(10,5)`、`BOOLEAN`、`DATE`、`DATETIME`）→ **NUMERIC** 亲和性

来做几个练习题：

| 声明类型             | 亲和性     | 你猜对了吗？                        |
| -------------------- | ---------- | ----------------------------------- |
| `INT`                | INTEGER    | 显然                                |
| `INTEGER`            | INTEGER    | 显然                                |
| `TINYINT`            | INTEGER    | 含 INT                              |
| `BIGINT`             | INTEGER    | 含 INT                              |
| `UNSIGNED BIG INT`   | INTEGER    | 含 INT                              |
| `INT2`, `INT8`       | INTEGER    | 含 INT                              |
| `CHARACTER(20)`      | TEXT       | 含 CHAR                             |
| `VARCHAR(255)`       | TEXT       | 含 CHAR                             |
| `NCHAR(55)`          | TEXT       | 含 CHAR                             |
| `CLOB`               | TEXT       | 含 CLOB                             |
| `TEXT`               | TEXT       | 显然                                |
| `BLOB`               | BLOB       | 显然                                |
| （不写类型）         | BLOB       | 好玩的坑                            |
| `REAL`               | REAL       | 显然                                |
| `DOUBLE`             | REAL       | 含 DOUB                             |
| `DOUBLE PRECISION`   | REAL       | 含 DOUB                             |
| `FLOAT`              | REAL       | 含 FLOA                             |
| `NUMERIC`            | NUMERIC    | 默认                                |
| `DECIMAL(10, 5)`     | NUMERIC    | 默认                                |
| `BOOLEAN`            | NUMERIC    | 默认，惊喜吧                        |
| `DATE`               | NUMERIC    | 默认，惊喜吧                        |
| `DATETIME`           | NUMERIC    | 默认，惊喜吧                        |

再看两个反直觉的例子：

- `CHARINT`：既含 `CHAR` 又含 `INT`，但 `INT` 排在规则 1，先命中 → **INTEGER 亲和性**。
- `FLOATING POINT`：含 `INT`（POINT 里有 INT？没有。让我们看看：F-L-O-A-T-I-N-G，含 `INT` 吗？**是的**，`INTING` 里的 `INT`），命中规则 1 → **INTEGER 亲和性**，血压瞬间飙升。

结论：**不要给列瞎起名**。老老实实用规范类型名。

## 6.5 亲和性怎么影响存储？

亲和性不是"强制约束"，而是"温柔的建议"。当你 `INSERT` 一个值进去时，SQLite 会**尝试转换**，但只在能转换成功时才转，转不了就原样存进去：

- **INTEGER / REAL / NUMERIC 亲和性**：如果传入的是 TEXT 且看起来像数字，就转成 INTEGER 或 REAL 存；否则原样存 TEXT。
- **TEXT 亲和性**：数值会被转成 TEXT 存。BLOB 保持 BLOB。
- **BLOB 亲和性**：不做任何转换，原样存。

举个例子：

```sql
CREATE TABLE t(a INTEGER, b TEXT);
INSERT INTO t VALUES ('123', 456);
INSERT INTO t VALUES ('abc', 'xyz');
INSERT INTO t VALUES (3.14, 2.71);

SELECT a, typeof(a), b, typeof(b) FROM t;
-- 123 | integer | 456 | text
-- abc | text    | xyz | text
-- 3   | integer | 2.71| text
```

注意第 3 行：3.14 塞进 INTEGER 亲和性的列里，被"温柔地"转成了 3——**小数被砍了！** 这是个非常隐蔽的坑（不过实际上 3.14 会被转成 REAL 存储，因为整数化会丢精度；具体行为要参考 SQLite 3.45 的实现，大多数情况下如果转成 INTEGER 会丢失信息则保留 REAL）。

## 6.6 INTEGER PRIMARY KEY 的特殊性——rowid 别名

在 SQLite 里，`INTEGER PRIMARY KEY`（**一定要是这两个词的组合，且大小写不敏感但顺序敏感**）是个特殊的存在：

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  name TEXT
);
```

这里 `id` 会成为**表的 rowid 别名**。这意味着：

1. `id` 就是这一行在 B-Tree 里的物理键，查询它是 O(log n)，快到飞起。
2. 不用 `AUTOINCREMENT` 也会自动递增（用 `MAX(id)+1`）。
3. 空间上不占额外字节——它本身就是 rowid。

对比 `INT PRIMARY KEY`（少了 `EGER`）——这只是普通主键，会额外建索引，rowid 是另一个隐藏字段。所以：

> **划重点**：想要"高性能自增主键"，就写 `INTEGER PRIMARY KEY`，不要写 `INT PRIMARY KEY`，不要用 `BIGINT PRIMARY KEY`——这些都不会变成 rowid 别名。

关于 `AUTOINCREMENT` 关键字：

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT);
```

加了 `AUTOINCREMENT` 之后，SQLite 会保证 id 单调递增（即使删除了行，id 也不会重用）。代价是维护一个 `sqlite_sequence` 表，写入会稍慢。**大部分场景不需要 `AUTOINCREMENT`**——直接 `INTEGER PRIMARY KEY` 就够了。

## 6.7 布尔值：0 和 1 的哲学

SQLite 里布尔就是 0 和 1。3.23 版本后支持 `TRUE`/`FALSE` 关键字：

```sql
-- 三种等价写法
SELECT * FROM user WHERE active = 1;
SELECT * FROM user WHERE active = TRUE;
SELECT * FROM user WHERE active;    -- 隐式转换：非零即真
```

推荐加个 CHECK 约束防止脏数据：

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  is_admin INTEGER NOT NULL DEFAULT 0 CHECK (is_admin IN (0, 1))
);
```

## 6.8 日期时间：三种存储方式的世纪辩论

SQLite 没有原生日期类型，你有三个选择：

**方案 A：TEXT (ISO8601)** —— 人类可读，推荐新手

```sql
CREATE TABLE event(t TEXT);
INSERT INTO event VALUES ('2024-11-20 15:30:00');
INSERT INTO event VALUES (datetime('now'));           -- 当前 UTC 时间
INSERT INTO event VALUES (datetime('now', 'localtime'));
```

优点：肉眼看得懂、可以直接排序（字典序恰好等于时间序）、跟 JSON API 天然兼容。
缺点：占空间大（19+ 字节），比较慢。

**方案 B：INTEGER (Unix 时间戳)** —— 存储紧凑，性能最好

```sql
CREATE TABLE event(t INTEGER);           -- 秒级
INSERT INTO event VALUES (strftime('%s', 'now'));
INSERT INTO event VALUES (1732000000);
-- 毫秒级：cast(strftime('%f','now')*1000 AS INTEGER) 略绕，通常在应用层算好再传
```

优点：8 字节以内、比较飞快、时区无关。
缺点：人不能一眼看懂（在 CLI 里 debug 时抓狂）。

**方案 C：REAL (儒略日 Julian Day)** —— 天文学家最爱

```sql
CREATE TABLE event(t REAL);
INSERT INTO event VALUES (julianday('now'));   -- 2460634.something
```

优点：精度高、可以做天数加减。
缺点：99% 的场景用不上，还容易看错。

**我的建议**：

- 应用层类型是 `DateTime`、跨语言/跨端交互（比如 API 返回 JSON）→ **TEXT (ISO8601)**
- 高频写入、聚合分析、时序数据 → **INTEGER (毫秒时间戳)**
- 学术项目、天文/物理 → **REAL (儒略日)**

一句话总结：**新手选 TEXT，追求性能选 INTEGER，装 X 选 REAL**。

## 6.9 date/time/datetime 内置函数详解

SQLite 提供了 5 个日期时间函数，全部都返回 TEXT 或 REAL：

```sql
date(timestring, modifier, modifier, ...)      -- 返回 YYYY-MM-DD
time(timestring, ...)                          -- 返回 HH:MM:SS
datetime(timestring, ...)                      -- 返回 YYYY-MM-DD HH:MM:SS
julianday(timestring, ...)                     -- 返回 REAL
strftime(format, timestring, ...)              -- 自定义格式化
unixepoch(timestring, ...)                     -- SQLite 3.38+ 返回秒级 unix
```

**timestring** 可以是：

- `'now'`
- `'2024-11-20'` / `'2024-11-20 15:30:00'` / `'2024-11-20T15:30:00.123Z'`
- `1732000000`（unix 秒时间戳，需要用 `unixepoch` 修饰符）
- `2460634.5`（儒略日，加 `.5` 差异需要 `julianday` 修饰符）

**modifier**（修饰符）非常强大：

```sql
SELECT date('now', '+1 day');                 -- 明天
SELECT date('now', '-1 month');               -- 一个月前
SELECT date('now', 'start of month');         -- 本月第一天
SELECT date('now', 'start of month', '+1 month', '-1 day'); -- 本月最后一天
SELECT datetime('now', 'localtime');          -- 当前本地时间
SELECT datetime('now', 'weekday 0');          -- 下一个周日
SELECT datetime(1732000000, 'unixepoch');     -- Unix 时间戳转 datetime
```

**strftime 格式化**：

| 占位符 | 含义             |
| ------ | ---------------- |
| `%Y`   | 年（4 位）       |
| `%m`   | 月（01-12）      |
| `%d`   | 日（01-31）      |
| `%H`   | 时（00-23）      |
| `%M`   | 分（00-59）      |
| `%S`   | 秒（00-59）      |
| `%f`   | 秒.毫秒（SS.SSS） |
| `%j`   | 一年中第几天     |
| `%w`   | 星期几（0=周日） |
| `%s`   | Unix 秒时间戳    |

```sql
SELECT strftime('%Y-%m-%d %H:%M:%S', 'now');
SELECT strftime('%Y年%m月%d日', 'now');
SELECT strftime('%s', 'now');           -- 相当于 unixepoch()
```

## 6.10 STRICT 模式（3.37+）——给类型洁癖党的救赎

如果你觉得 SQLite 的"什么都能塞"过于放飞自我，3.37 版本引入了 STRICT 表：

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  age INT,
  score REAL,
  data BLOB,
  is_admin INT CHECK (is_admin IN (0, 1))
) STRICT;
```

**STRICT 模式的规则**：

1. 只允许 5 种类型名（且是精确名字）：`INT`、`INTEGER`、`REAL`、`TEXT`、`BLOB`、`ANY`。写 `VARCHAR` 会直接建表失败。
2. 值必须匹配声明类型，否则拒绝插入或转换失败。
3. `ANY` 类型退回旧行为，任意存储类都能塞。

```sql
-- 传统模式：能插入
CREATE TABLE t1(age INTEGER);
INSERT INTO t1 VALUES ('abc');   -- OK，'abc' 原样存 TEXT

-- STRICT 模式：报错
CREATE TABLE t2(age INTEGER) STRICT;
INSERT INTO t2 VALUES ('abc');
-- Error: cannot store TEXT value in INTEGER column t2.age
```

**什么时候用 STRICT？**

- 团队协作、数据质量要求高的项目：**强烈推荐**。
- 迁移自 MySQL/PostgreSQL 的老手：**用了会舒服很多**。
- 需要极限性能、代码全面 review 过的场景：可以不用，多一点灵活性。

STRICT 表还有一个副作用：`INTEGER PRIMARY KEY` 依然是 rowid 别名，但如果你写 `INT PRIMARY KEY`（少了 EGER），STRICT 模式下这就是一个 `INT` 列 + rowid 别名（3.37 之后的特殊照顾），普通模式下则是普通主键 + 隐藏 rowid。

## 6.11 Dart 类型 ↔ SQLite 类型映射表

这是 Flutter 开发者必须刻在 DNA 里的表：

| Dart 类型      | SQLite 存储类  | 推荐声明类型     | 说明                                    |
| -------------- | -------------- | ---------------- | --------------------------------------- |
| `int`          | INTEGER        | `INTEGER`        | Dart int 是 64 位有符号                 |
| `double`       | REAL           | `REAL`           | 8 字节 IEEE 754                         |
| `String`       | TEXT           | `TEXT`           | UTF-16 → UTF-8 转换                     |
| `bool`         | INTEGER (0/1)  | `INTEGER`        | 手动转换 `b ? 1 : 0`                    |
| `Uint8List`    | BLOB           | `BLOB`           | 二进制数据                              |
| `DateTime`     | TEXT/INTEGER   | `TEXT` 或 `INTEGER` | 需要显式转换                       |
| `List<T>` / `Map` | TEXT (JSON) | `TEXT`           | 序列化为 JSON 字符串                    |
| `enum`         | INTEGER 或 TEXT | `INTEGER` 或 `TEXT` | 存 index 或 name                    |
| `null`         | NULL           | 允许 NULL 的列   | 直接映射                                |

**sqflite 的行为**：`insert` 时会自动把 Dart 类型转成对应的 SQLite 值，但 `bool` 和 `DateTime` 需要你自己转。

**drift 的行为**：类型安全的映射器（`TypeConverter`）帮你搞定，代码生成器直接生成对应字段类型。

## 6.12 Flutter 实战：日期字段的正确姿势

场景：Todo 应用里的 `created_at` 字段。

**方案 A：sqflite + TEXT (ISO8601)**

```dart
// 建表
await db.execute('''
  CREATE TABLE todo(
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
  )
''');

// 插入
await db.insert('todo', {
  'title': '学 SQLite',
  'created_at': DateTime.now().toUtc().toIso8601String(),
});

// 查询：从数据库读出后手动 parse
final rows = await db.query('todo');
final todos = rows.map((row) {
  return Todo(
    id: row['id'] as int,
    title: row['title'] as String,
    createdAt: DateTime.parse(row['created_at'] as String),
  );
}).toList();
```

**方案 B：sqflite + INTEGER (毫秒时间戳)**

```dart
await db.execute('''
  CREATE TABLE todo(
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    created_at INTEGER NOT NULL
  )
''');

await db.insert('todo', {
  'title': '学 SQLite',
  'created_at': DateTime.now().millisecondsSinceEpoch,
});

// 查询转换
final createdAt = DateTime.fromMillisecondsSinceEpoch(row['created_at'] as int);
```

**方案 C：drift + 内置 DateTime 转换器**

drift 官方就支持 `DateTime`，可以配置存储为 int 或 iso8601 字符串（在 `build.yaml` 里）：

```yaml
# build.yaml
targets:
  $default:
    builders:
      drift_dev:
        options:
          store_date_time_values_as_text: true    # 默认是 false，即 INTEGER
```

然后在表定义里：

```dart
import 'package:drift/drift.dart';

class Todos extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get title => text().withLength(min: 1, max: 200)();
  DateTimeColumn get createdAt => dateTime().withDefault(currentDateAndTime)();
}
```

drift 生成的 `Todo` 类里 `createdAt` 直接就是 `DateTime`，读写全自动。**这就是类型安全 ORM 的爽点**。

## 6.13 常见坑点合集

**坑 1：`typeof(col)` 返回的是"值的存储类"，不是"列的亲和性"**

```sql
CREATE TABLE t(a INTEGER);
INSERT INTO t VALUES ('abc');
SELECT typeof(a) FROM t;    -- 'text'，不是 'integer'
```

想知道列的亲和性，得看 `PRAGMA table_info(t)` 的 `type` 字段。

**坑 2：时区噩梦**

`datetime('now')` 返回的是 **UTC**，不是本地时间！要本地时间必须加 `'localtime'` 修饰符。但是——**永远推荐存 UTC**，展示时再转本地时区。Flutter 里：

```dart
// 存
DateTime.now().toUtc().toIso8601String()

// 读
DateTime.parse(row['created_at']).toLocal()
```

**坑 3：布尔值查询陷阱**

```sql
-- 假设 active 列有值 1、0、'true'（脏数据）
SELECT * FROM user WHERE active = 1;      -- 只匹配 1
SELECT * FROM user WHERE active;           -- 匹配非零非 NULL 值
SELECT * FROM user WHERE active = 'true';  -- 只匹配字符串 'true'
```

用 CHECK 约束 + STRICT 模式可以避免脏数据。

**坑 4：主键列写错关键字**

```sql
-- 这不是 rowid 别名，是普通主键（多一个索引）
CREATE TABLE bad(id INT PRIMARY KEY, name TEXT);

-- 这才是 rowid 别名
CREATE TABLE good(id INTEGER PRIMARY KEY, name TEXT);
```

**坑 5：NUMERIC 亲和性的隐式转换**

```sql
CREATE TABLE t(a NUMERIC);
INSERT INTO t VALUES ('123abc');    -- 存为 TEXT '123abc'（转换失败）
INSERT INTO t VALUES ('123');       -- 存为 INTEGER 123
INSERT INTO t VALUES ('123.45');    -- 存为 REAL 123.45
INSERT INTO t VALUES ('1e10');      -- 存为 REAL 10000000000.0
```

**同一列的数据类型可能不一样**——排序、比较时会有各种反直觉行为。想避免？用 STRICT 或者 CHECK 约束。

**坑 6：drift 的 boolean 默认存法**

drift 会用 `INTEGER` 存 bool（0/1）。如果你之前用其他框架存了 `'true'`/`'false'` 文本，迁移会翻车。

## 6.14 本章小结

- SQLite 有 5 种存储类（NULL/INTEGER/REAL/TEXT/BLOB）和 5 种亲和性（TEXT/NUMERIC/INTEGER/REAL/BLOB）。
- 亲和性是列的"建议"，存储类是值的"事实"。
- `INTEGER PRIMARY KEY` 是 rowid 别名，写全这两个词才有效。
- 布尔用 INTEGER 0/1；日期时间三选一（推荐 TEXT ISO8601 或 INTEGER 毫秒时间戳）。
- STRICT 表（3.37+）能强制类型检查，团队项目推荐开启。
- Flutter 里 sqflite 要手动转换 `bool` 和 `DateTime`；drift 直接类型安全，用 `DateTimeColumn` 一劳永逸。
- **金句**：SQLite 的类型系统就像"社会人"，表面上没规矩，实际上 5 条亲和性规则藏得深，你越懂它越省心。
