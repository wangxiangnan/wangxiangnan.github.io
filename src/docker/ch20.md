# 第20章：K8s进阶 —— HPA、Helm与GitOps

## 引言：从"手动挡"到"自动驾驶"

到目前为止，我们的 K8s 使用方式还比较"手动"——手动设定副本数、手动写 YAML、手动部署。

这就好比你买了一辆特斯拉，但一直在用手动挡开。本章我们要解锁 K8s 的"自动驾驶"功能：

- **HPA**：流量高峰自动扩容，低谷自动缩容（省钱！）
- **Helm**：K8s 的 `npm`/`pip`，一行命令安装复杂应用
- **GitOps**：Git 是唯一的真相来源，push 代码 = 自动部署

## 20.1 Horizontal Pod Autoscaler（HPA）—— 自动扩缩容

### 为什么需要 HPA？

想象你的电商网站：

```bash
流量曲线：
      ████
      ████
  ████████
  ████████
████████████████
00  06  12  18  24  （小时）
```

凌晨 3 点几乎没人访问，但你的 Deployment 还是跑着 10 个副本——白白浪费资源。晚上 8 点抢购活动，10 个副本又扛不住。

HPA 的作用：**根据实际负载自动调整副本数量**。

### 基于 CPU/内存的 HPA

```yaml
# 前提：集群需要安装 Metrics Server
# Minikube
minikube addons enable metrics-server

# HPA 资源定义
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api                     # 目标 Deployment
  minReplicas: 2                  # 最少 2 个副本（保证可用性）
  maxReplicas: 20                 # 最多 20 个副本（防止资源耗尽）
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70    # CPU 平均使用率超过 70% 时扩容
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80    # 内存平均使用率超过 80% 时扩容
  behavior:                       # 扩缩容行为控制
    scaleUp:
      stabilizationWindowSeconds: 60   # 扩容前等待 60 秒（避免突发流量导致过度扩容）
      policies:
      - type: Pods
        value: 2                  # 每次最多扩 2 个
        periodSeconds: 60         # 每 60 秒评估一次
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容前等待 5 分钟（避免反复震荡）
      policies:
      - type: Pods
        value: 1                  # 每次最多缩 1 个
        periodSeconds: 120        # 每 120 秒评估一次
```

也可以用命令行快速创建：

```bash
# 命令行方式（简单但配置不如 YAML 灵活）
kubectl autoscale deployment api --min=2 --max=20 --cpu-percent=70

# 查看 HPA 状态
kubectl get hpa

# 输出示例：
# NAME      REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
# api-hpa   Deployment/api   45%/70%   2         20        3
```

### HPA 工作原理

```bash
每 15 秒，K8s 会：
1. 从 Metrics Server 获取所有 Pod 的 CPU/内存使用率
2. 计算平均值
3. 与目标值对比
4. 决定是否需要扩缩容

公式：
期望副本数 = ceil[当前副本数 × (当前指标值 / 目标指标值)]

示例：
- 当前 3 个 Pod，CPU 使用率平均 85%，目标 70%
- 期望副本数 = ceil[3 × (85/70)] = ceil[3.64] = 4
- 扩容到 4 个 Pod
```

### 自定义指标扩缩

除了 CPU/内存，你还可以基于自定义指标扩缩（比如请求数、队列长度）：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa-custom
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 50
  metrics:
  # 基于 Prometheus 自定义指标
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second   # 每秒请求数
      target:
        type: AverageValue
        averageValue: "100"              # 每个 Pod 平均 100 QPS 时扩容
  # 基于外部指标（如消息队列长度）
  - type: External
    external:
      metric:
        name: rabbitmq_queue_length
        selector:
          matchLabels:
            queue: "tasks"
      target:
        type: AverageValue
        averageValue: "1000"
```

> [!TIP] 提示
> 自定义指标需要配合 Prometheus Adapter 使用，它把 Prometheus 的指标翻译成 K8s Custom Metrics API。这是生产环境中最常用的方案。

### VPA（Vertical Pod Autoscaler）简介

HPA 是"水平扩缩"（增加/减少 Pod 数量），VPA 是"垂直扩缩"（调整单个 Pod 的资源 requests/limits）。

```yaml
# VPA：自动调整 Pod 的资源配置
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: api-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  updatePolicy:
    updateMode: "Auto"     # Auto: 自动更新 Pod 资源（会重启 Pod）
                           # Initial: 只在创建时设置
                           # Off: 只推荐，不自动修改
```

**HPA vs VPA 选择指南：**

| 场景 | 推荐方案 |
|------|---------|
| 无状态 Web 服务，流量波动大 | HPA |
| 数据库等不易水平扩展的服务 | VPA |
| 两者结合 | 可以同时使用，但不要对同一指标同时用 HPA 和 VPA |

## 20.2 Helm —— K8s 的"包管理器"

写 YAML 是一件痛苦的事情——一个稍微复杂的应用可能需要十几个 YAML 文件，每次部署还要根据不同环境修改参数。

Helm 就是来解决这个问题的。类比：

```bash
Linux 世界：  apt / yum / pacman    → 安装软件包
macOS 世界：  brew                  → 安装软件包
Node.js 世界：npm / yarn            → 安装 npm 包
Python 世界： pip / poetry          → 安装 pip 包
K8s 世界：   Helm                  → 安装 K8s 应用
```

### 安装 Helm

```bash
# macOS
brew install helm

# Linux
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Windows
choco install kubernetes-helm

# 验证
helm version
```

### Helm 核心概念

```bash
Chart = Helm 的"包"（一组 K8s 资源模板 + 默认配置）
  ├── Chart.yaml         # Chart 元数据（名称、版本、描述）
  ├── values.yaml        # 默认配置值
  ├── templates/         # K8s 资源模板（Go template 语法）
  │   ├── deployment.yaml
  │   ├── service.yaml
  │   ├── ingress.yaml
  │   ├── _helpers.tpl   # 模板辅助函数
  │   └── NOTES.txt      # 安装后显示的说明
  └── charts/            # 依赖的子 Chart

Release = Chart 的一次安装实例
  同一个 Chart 可以安装多次（不同名称 = 不同 Release）
  例如：用 MySQL Chart 安装出 mysql-prod 和 mysql-dev 两个 Release
```

### 使用 Helm 安装应用

```bash
# 添加仓库
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# 搜索 Chart
helm search repo nginx
helm search hub prometheus    # 搜索 Artifact Hub

# 安装 Chart
helm install my-nginx bitnami/nginx

# 安装时覆盖配置
helm install my-nginx bitnami/nginx \
  --set replicaCount=3 \
  --set service.type=LoadBalancer

# 使用自定义 values 文件
helm install my-nginx bitnami/nginx -f my-values.yaml

# 指定 Namespace
helm install my-nginx bitnami/nginx -n production --create-namespace

# 查看已安装的 Release
helm list
helm list --all-namespaces

# 升级
helm upgrade my-nginx bitnami/nginx --set replicaCount=5

# 回滚
helm rollback my-nginx 1      # 回滚到第 1 个版本

# 查看历史
helm history my-nginx

# 卸载
helm uninstall my-nginx
```

### 编写自定义 Chart

```bash
# 创建新 Chart
helm create my-nodejs-app

# 生成的目录结构：
# my-nodejs-app/
# ├── Chart.yaml
# ├── values.yaml
# ├── charts/
# └── templates/
#     ├── deployment.yaml
#     ├── service.yaml
#     ├── ingress.yaml
#     ├── hpa.yaml
#     ├── _helpers.tpl
#     └── NOTES.txt
```

**Chart.yaml：**

```yaml
apiVersion: v2
name: my-nodejs-app
description: A Node.js API application for Kubernetes
type: application
version: 0.1.0          # Chart 版本（每次修改 Chart 时递增）
appVersion: "1.0.0"     # 应用版本（镜像标签）
```

**values.yaml：**

```yaml
# 默认配置值（可被 --set 或 -f 覆盖）
replicaCount: 3

image:
  repository: my-nodejs-app
  tag: "1.0.0"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
  targetPort: 3000

ingress:
  enabled: true
  className: nginx
  hosts:
  - host: api.example.com
    paths:
    - path: /
      pathType: Prefix
  tls: []

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi

autoscaling:
  enabled: false
  minReplicas: 2
  maxReplicas: 20
  targetCPUUtilizationPercentage: 70

env:
  NODE_ENV: production
  LOG_LEVEL: info
```

**templates/deployment.yaml：**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "my-nodejs-app.fullname" . }}
  labels:
    {{- include "my-nodejs-app.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "my-nodejs-app.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "my-nodejs-app.selectorLabels" . | nindent 8 }}
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        imagePullPolicy: {{ .Values.image.pullPolicy }}
        ports:
        - containerPort: {{ .Values.service.targetPort }}
        env:
        {{- range $key, $value := .Values.env }}
        - name: {{ $key }}
          value: {{ $value | quote }}
        {{- end }}
        resources:
          {{- toYaml .Values.resources | nindent 12 }}
        livenessProbe:
          httpGet:
            path: /health
            port: {{ .Values.service.targetPort }}
          initialDelaySeconds: 15
        readinessProbe:
          httpGet:
            path: /health
            port: {{ .Values.service.targetPort }}
          initialDelaySeconds: 5
```

```bash
# 测试模板渲染（不实际部署）
helm template my-release ./my-nodejs-app

# 使用自定义值部署
helm install my-api ./my-nodejs-app \
  --set image.tag=v2.0 \
  --set replicaCount=5

# 打包 Chart
helm package ./my-nodejs-app
# 生成 my-nodejs-app-0.1.0.tgz

# 推送到 OCI 仓库（如 Docker Hub）
helm push my-nodejs-app-0.1.0.tgz oci://registry-1.docker.io/myusername
```

## 20.3 Kustomize —— 无模板的配置管理

如果你觉得 Helm 的 Go template 语法太复杂，**Kustomize** 是一个更简单的替代方案。它的核心理念是：**不修改原始 YAML，通过"叠加（overlay）"来定制配置**。

```bash
基础配置（base/）
├── deployment.yaml      # 通用的、不含环境特定信息的 YAML
├── service.yaml
└── kustomization.yaml

叠加层（overlays/）
├── dev/
│   ├── kustomization.yaml   # dev 环境的差异配置
│   └── replica-patch.yaml
└── prod/
    ├── kustomization.yaml   # prod 环境的差异配置
    └── resource-patch.yaml
```

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
- service.yaml

---
# overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namePrefix: dev-              # 给所有资源名加前缀
namespace: development
patches:
- target:
    kind: Deployment
    name: my-app
  patch: |
    - op: replace
      path: /spec/replicas
      value: 1                # dev 环境只要 1 个副本

---
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- ../../base
namePrefix: prod-
namespace: production
patches:
- target:
    kind: Deployment
    name: my-app
  patch: |
    - op: replace
      path: /spec/replicas
      value: 5                # prod 环境 5 个副本
    - op: replace
      path: /spec/template/spec/containers/0/resources/limits/memory
      value: "512Mi"          # prod 环境更多内存
```

```bash
# 预览渲染结果
kubectl kustomize overlays/dev
kubectl kustomize overlays/prod

# 直接部署
kubectl apply -k overlays/dev
kubectl apply -k overlays/prod
```

> [!TIP] 提示
> Kustomize 已经内置在 kubectl 中（`kubectl apply -k`），不需要额外安装。对于不需要复杂模板逻辑的场景，Kustomize 比 Helm 更简洁。两者不是互斥的——很多团队用 Helm 管理第三方应用，用 Kustomize 管理自己的业务应用。

## 20.4 GitOps 工作流

GitOps 的核心理念：**Git 仓库是集群状态的唯一真相来源**。

```bash
传统部署流程：
开发者 → CI/CD Pipeline → kubectl apply → K8s 集群
（CI/CD 有集群权限，安全风险）

GitOps 流程：
开发者 → Git Push → GitOps Controller 检测变更 → 自动同步到 K8s
（只有 Controller 有集群权限，更安全）
```

### ArgoCD 简介

```bash
# 安装 ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 访问 ArgoCD UI
kubectl port-forward svc/argocd-server -n argocd 8080:443
# 浏览器访问 https://localhost:8080
# 用户名：admin
# 密码：kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

```yaml
# ArgoCD Application：声明"我要从哪个 Git 仓库部署什么"
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/my-app-k8s.git  # K8s 配置所在的 Git 仓库
    targetRevision: main                                 # 分支
    path: overlays/production                            # 目录
  destination:
    server: https://kubernetes.default.svc               # 目标集群（当前集群）
    namespace: production
  syncPolicy:
    automated:                                           # 自动同步
      prune: true                                        # 删除 Git 中移除的资源
      selfHeal: true                                     # 手动修改集群后自动恢复
    syncOptions:
    - CreateNamespace=true
```

GitOps 的工作流：

1. 开发者修改 Git 仓库中的 K8s YAML（比如改镜像版本）
2. Git Push 到 main 分支
3. ArgoCD 检测到 Git 变更
4. ArgoCD 自动将变更同步到 K8s 集群
5. 如果同步失败，ArgoCD UI 显示详细错误

> [!TIP] 提示
> GitOps 的最大优势是**审计和回滚**——所有变更都在 Git 历史中，`git revert` 就能回滚生产环境的部署。这对于合规性要求高的团队特别有价值。

## 20.5 K8s RBAC —— 基于角色的访问控制

RBAC 回答了一个问题：**谁能对什么资源做什么操作？**

```yaml
# Role：定义权限（限定在某个 Namespace 内）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: development          # 只在 development Namespace 生效
rules:
- apiGroups: ["", "apps"]        # "" 表示核心 API 组
  resources: ["pods", "deployments", "services", "configmaps"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
- apiGroups: [""]
  resources: ["pods/log"]        # 允许查看日志
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["pods/exec"]       # 允许 exec 进入容器
  verbs: ["create"]

---
# ClusterRole：集群级别的权限
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-viewer
rules:
- apiGroups: [""]
  resources: ["nodes", "namespaces", "persistentvolumes"]
  verbs: ["get", "list", "watch"]

---
# RoleBinding：将 Role 绑定给用户/组
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-binding
  namespace: development
subjects:
- kind: User
  name: alice                    # 用户名
  apiGroup: rbac.authorization.k8s.io
- kind: Group
  name: dev-team                 # 用户组
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
```

**RBAC 的最佳实践：**

```bash
最小权限原则：
- 开发人员：只能查看和操作 dev Namespace 的 Pod、Deployment
- CI/CD 系统：只能 apply 和 rollout
- 监控系统：只能 get、list、watch（只读）
- 运维人员：更广泛的权限，但仍然限制在特定操作

永远不要做的事：
- 给任何人 cluster-admin（除非真的是集群管理员）
- 在 default ServiceAccount 上赋予过多权限
- 使用通配符 "*" 作为 verbs 或 resources
```

## 20.6 Network Policies —— 网络策略

默认情况下，K8s 集群中**所有 Pod 都能互相通信**。这在安全上是一个大问题——如果某个 Pod 被攻破，攻击者可以访问集群内所有服务。

Network Policies 就像 K8s 的"防火墙"：

```yaml
# 默认拒绝所有入站流量（白名单策略的基础）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}              # 匹配所有 Pod
  policyTypes:
  - Ingress                    # 拒绝所有入站

---
# 只允许前端 Pod 访问 API Pod 的 3000 端口
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-network-policy
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api                 # 应用于 API Pod
  policyTypes:
  - Ingress
  - Egress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend        # 只允许 frontend Pod
    - namespaceSelector:
        matchLabels:
          name: monitoring     # 也允许 monitoring Namespace（Prometheus 采集）
    ports:
    - protocol: TCP
      port: 3000
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: mongodb         # API 只能访问 MongoDB
    ports:
    - protocol: TCP
      port: 27017
  - to:
    - podSelector:
        matchLabels:
          app: redis           # 和 Redis
    ports:
    - protocol: TCP
      port: 6379
  # 允许 DNS 查询（否则连域名都解析不了！）
  - to:
    - namespaceSelector: {}
    ports:
    - protocol: UDP
      port: 53
```

> [!WARNING] 注意
> Network Policies 需要 CNI 网络插件支持。Calico、Cilium 支持 NetworkPolicy，但 Flannel（Kind 默认使用）不支持！如果你需要 Network Policies，考虑使用 Calico 或 Cilium 作为 CNI。

## 20.7 实战：用 Helm 部署并管理应用

让我们把之前手写的 Node.js 微服务架构转换为 Helm Chart 并部署：

```bash
# 1. 创建 Chart
helm create my-microservice

# 2. 清理默认模板，创建我们需要的文件
cd my-microservice/templates
rm -f hpa.yaml ingress.yaml

# 3. 编写 values.yaml（参考上面的 values.yaml 示例）

# 4. 编写模板文件（参考上面的 deployment.yaml 模板示例）

# 5. 创建 dev 和 prod 的 values 文件
cat > values-dev.yaml << 'EOF'
replicaCount: 1
image:
  tag: "latest"
resources:
  requests:
    cpu: 50m
    memory: 64Mi
  limits:
    cpu: 200m
    memory: 128Mi
env:
  NODE_ENV: development
  LOG_LEVEL: debug
EOF

cat > values-prod.yaml << 'EOF'
replicaCount: 5
image:
  tag: "v1.0.0"
resources:
  requests:
    cpu: 200m
    memory: 256Mi
  limits:
    cpu: 1000m
    memory: 512Mi
autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 20
env:
  NODE_ENV: production
  LOG_LEVEL: warn
EOF

# 6. 部署到 dev 环境
helm install my-app-dev ./my-microservice \
  -f values-dev.yaml \
  -n development --create-namespace

# 7. 部署到 prod 环境
helm install my-app-prod ./my-microservice \
  -f values-prod.yaml \
  -n production --create-namespace

# 8. 升级 prod 版本
helm upgrade my-app-prod ./my-microservice \
  -f values-prod.yaml \
  --set image.tag=v2.0.0

# 9. 查看发布历史
helm history my-app-prod

# 10. 如果需要回滚
helm rollback my-app-prod 1
```

## 本章小结

- **HPA** 根据 CPU/内存/自定义指标自动调整副本数量，实现弹性伸缩
- **Helm** 是 K8s 的包管理器，通过 Chart 模板化和 values 文件实现配置的复用和管理
- **Kustomize** 通过 overlay 机制管理多环境配置，比 Helm 模板更简单直接
- **GitOps**（ArgoCD/FluxCD）将 Git 作为唯一真相来源，实现声明式的持续部署
- **RBAC** 实现细粒度的权限控制，遵循最小权限原则
- **Network Policies** 实现 Pod 级别的网络隔离，是安全加固的重要手段

## 练习

1. **HPA**：为你的应用配置 HPA，使用 `kubectl run` 生成负载，观察自动扩容
2. **Helm**：将你的一个应用打包为 Helm Chart，支持 dev/prod 两套 values
3. **Kustomize**：用 Kustomize 管理同一应用的 dev/staging/prod 配置
4. **RBAC**：创建一个只有 `get`、`list` 权限的 Role，验证绑定后的用户无法 `create` 资源
5. **综合挑战**：使用 ArgoCD 搭建 GitOps 工作流，实现 push 到 main 分支自动部署到 K8s
