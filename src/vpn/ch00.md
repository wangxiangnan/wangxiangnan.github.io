## 心智模型

### 一、核心模型：密钥即身份的虚拟网卡

传统 VPN 的操作对象是「账号、证书、控制台」：登录管理后台、签发证书、在客户端导入一堆配置。而 WireGuard（本教程的主线协议）把这套东西压缩成一句话：**每台设备就是一对密钥，公钥就是身份**。

你不需要理解任何管理协议——只需要记住一张虚拟网卡（`wg0`）和它的两个输入：

```text
流量 → wg0 虚拟网卡（谁在另一头？看公钥）→ 加密封装成 UDP 包 → 公网 → 对端解密
```

去程与回程各写一遍，双向性一眼可见：

```text
去程：应用 → wg0 → 内核加密 → UDP 51820 出公网 → 对端 wg0 解密 → 内网服务
回程：内网服务 → 对端 wg0 → 内核加密 → UDP 51820 回公网 → 本地 wg0 解密 → 应用
```

**图 0-1｜WireGuard 的核心模型**（自上而下是一次数据包的隧道旅程，节点内蓝字为各环节目的）：

这条模型带来三个传统 VPN 给不了的性质：

- **配置面极小**：没有账号体系、没有证书签发链，一张 `wg0.conf` 文件就是全部配置；
- **身份即密钥**：删掉一个公钥就是注销一台设备，新增一个公钥就是接入一台设备，第五章的脚本把这两个动作自动化；
- **内核态运行**：加密解密发生在内核，性能接近裸网卡（数字见 2.1）。

还有一个读图时要建立的直觉：**图中的四步对回程流量同样成立，只是方向相反**。笔记本访问服务器的数据库时，数据库的应答包从服务器 `wg0` 出发，沿同一条隧道反向回到笔记本——隧道的本质是双向的，不是「请求走加密、响应走明文」。这也是为什么第三、四章反复强调「通了以后 ping 一下对端的 10.66.66.x」：ping 走的就是这条双向链路，能 ping 通说明四个环节全部就位。把「隧道 = 一张双向网卡」刻进直觉，后面所有路由问题的排障都会简单很多。

### 二、易混概念对照表

这本教程涉及协议、工具、服务三层名词，先在这里对齐：

| 概念 | 它是什么 | 它不是什么 |
| ---- | ---- | ---- |
| VPN（虚拟专用网） | 一条加密隧道，把你的设备「接进」另一个网络 | 不是加速器，也不是隐身斗篷 |
| 代理（Proxy） | 应用层的「代购」：替你发请求再转交 | 不是网络层隧道，普通代理不接管系统路由 |
| 隧道（Tunnel） | 把 A 网络的包套壳穿过 B 网络的技术手段 | 不是某款软件，是 VPN 的底层原理 |
| `wg` | 查看与调试 WireGuard 接口的工具 | 不是启动命令 |
| `wg-quick` | 读取 `wg0.conf` 并落地的封装脚本 | 不是协议的一部分，只是配置辅助 |
| `wg-quick@wg0` | systemd 服务单元，负责开机自启 | 不是守护进程本体 |
| AllowedIPs | 路由表 + 白名单的双重语义 | 不是「允许哪些 IP 来访问我」 |
| Endpoint | 对端的公网地址与端口 | 不是 VPN 网段里的地址 |
| PersistentKeepalive | 主动心跳，保住 NAT 映射 | 不是必填项，默认关闭 |
| MTU 1420 | 隧道内网卡的传输单元上限 | 不是随手拍的数，由外层封装开销算出（见 3.2） |
| TUN 模式 | mihomo 创建虚拟网卡、全局接管流量 | 不是 WireGuard 本身的模式（见 7.2） |
| mihomo 的 wireguard 出站 | 把 mihomo 客户端当作一个 WireGuard 接入端 | 不是又一个服务端，服务端仍是第三章那台 |

最常踩的坑是最后三行：AllowedIPs 的双重语义贯穿第三、四、六章；而「mihomo 客户端」与「官方客户端」的关系会在第七章正面讲清——它们是同一台服务器的两种接入端形态，不是两套 VPN。

### 三、贯穿全书的主线场景

全书的示例设定为一套最常见的自建需求：**你有一台云服务器，要带着笔记本和手机在外面安全地访问它背后的内网服务**。

| 设备 | VPN 身份（隧道内） | 家里内网身份 | 角色 |
| ---- | ---- | ---- | ---- |
| 云服务器 | 10.66.66.1 | —— | VPN 网关（第三章搭建） |
| 笔记本 | 10.66.66.2 | —— | 日常接入：SSH、数据库、管理面板 |
| 手机 | 10.66.66.3 | —— | 应急运维：地铁上修故障 |
| 家庭 NAS | 10.66.66.4 | 192.168.1.20 | 第六章的站点网关：顺带访问家里内网 |

三个典型使用瞬间，全部贯穿后续章节：

1. 地铁上手机弹出告警，连上隧道 SSH 到服务器重启服务——第四章的扫码接入就是为这一刻准备的；
2. 咖啡馆里用笔记本直连 `10.66.66.1:5432` 的数据库，免公网暴露——第一章会先算清这笔安全账；
3. 出差时访问家里 NAS 的相册与文件——第六章的站点到站点（Site-to-Site）组网负责把两个内网缝起来。

这三种客户端形态正好覆盖 WireGuard 的全部接入面：

| 客户端形态 | 设备 | 接入章 |
| ---- | ---- | ---- |
| 桌面版官方客户端 | 笔记本 | 第四章 |
| 移动端 App（扫码导入） | 手机 | 第四章 4.4 |
| 无界面 Linux（纯配置文件） | 家庭 NAS | 第六章 |
| mihomo 图形客户端（CordC、Clash 系） | 装了代理内核的设备 | 第七、八章 |

一台服务端加四种客户端形态，全书不用换例子就能把接入面讲全。

### 四、全书数字锚点约定

为了让示例在各章之间可复现，全书统一以下数字（实际操作时把 IP 换成你自己的）：

| 锚点 | 值 | 说明 |
| ---- | ---- | ---- |
| 服务器公网 IP | 203.0.113.10 | RFC 5737 文档专用段，不是真实地址 |
| 服务器外网网卡 | ens3 | 第一章教探测命令，不写死 |
| VPN 网段 | 10.66.66.0/24 | 服务器 .1、笔记本 .2、手机 .3、NAS .4 |

| 客户端花名册 | /etc/wireguard/clients/index | 第五章脚本维护 |
| DNS | 公网 1.1.1.1；隧道内 10.66.66.1 | 分流场景下才用内网 DNS |
| 会话密钥重协商 | 120 秒 | 第二章原理 |
| 旧密钥拒绝时限 | 180 秒 | 第二章原理 |

| mihomo 节点名 | server / laptop / phone | 沿用第四章的 peer 命名 |

### 五、本教程在 VPN 工具版图上的位置

| 方案 | 形态 | 配置复杂度 | 本教程的处理 |
| ---- | ---- | ---- | ---- |
| 服务直接暴露公网 | 无 | 极低 | 第一章算清风险账，不采用 |
| SSH 跳板 / SSH 隧道 | 一条命令 | 低 | 第一章对比；详细用法见站内[《Git 与 SSH 完全教程》](/git-ssh/ch00) |
| 自建 WireGuard | 服务端 + 客户端 | 中 | **全书主线**（第三至五章） |
| 自建 OpenVPN | 服务端 + 客户端 | 中高 | 第六章对照一小节，理解选型差异 |
| Tailscale / ZeroTier | 托管组网 | 低 | 不展开——依赖第三方控制面，本书坚持自建 |
| mihomo 系客户端（CordC、Clash Verge 等） | 图形界面 | 低 | 客户端形态（第七、八章），接入第三章搭好的服务端 |

主线选定 WireGuard 的理由用三个数字就能说完，第二章展开：

- 核心代码约 **4 千行**（OpenVPN 约 10 万行），审计面小一个数量级；
- 加密在**内核态**完成，吞吐接近裸网卡（用户态方案的加解密要在内核与用户进程间来回搬运数据）；
- 握手是 **1-RTT**（一次往返完成密钥协商），弱网环境连隧道几乎无感。

协议层的原理（各家协议怎么设计、RFC 里定了什么）不属于本书重点，站内[《网络协议完全教程》第二十二章](/network-protocol/ch22)已有 WireGuard 与 OpenVPN 的协议对比，本书第二章只把「配置时必须懂的原理」讲透，其余在 2.7 回指深入阅读。

反过来说，也有**不该自建**的情况，先说清楚免得读到一半发现走错了路：服务器没有固定公网 IP（家庭宽带大都是动态 IP，需要额外做内网穿透，复杂度陡增）；团队超过几十台设备、需要审计与统一策略（自建方案没有控制面，托管组网更合适）；或者你只是临时用几天（脚本省下的时间可能还不够搭一遍）。自建 WireGuard 的甜区是「几台到几十台设备、服务端固定公网 IP、长期使用」——正好是个人开发者与小型团队的主场。

- 第五章的脚本只是把第三章的手工命令按顺序固化，读起来应该像「命令的回放」；
- 第七、八章的 mihomo 客户端与第四、五章的官方工具是**同一台服务器的两种接入端**，两边章节可以独立阅读、互相印证。

最后说明本教程的读法：所有命令与配置都取自同一个贯穿场景（第三节的三台设备与一台服务器），可以逐段照抄进你自己的服务器验证；每章末尾的「本章小结」负责收束，「下一章预告」负责衔接——赶时间时只读小结串起全书，也是一种完整的读法。
