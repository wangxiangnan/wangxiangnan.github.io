# Ch11：构建缓存与远程缓存

## 本章目标

- 理解 Turborepo 2.x 本地缓存的存储结构与内容哈希策略
- 掌握缓存命中与失效的判定方式，能定位"为什么没命中"
- 配置 Vercel Remote Cache 或自建远程缓存，并在 CI 中正确使用
- 理解远程缓存的安全边界：token、签名、以及不该缓存的内容
- 制定一套可解释的缓存策略

## 11.1 本地缓存：基于内容哈希

Turborepo 的缓存不是时间戳比对，而是**内容哈希（content hash）**。每个任务执行前，Turborepo 会计算一个 hash；hash 相同就直接复用结果。

### 哈希的输入

一个任务的 hash 大致由以下内容组成：

```txt
hash = SHA256(
  任务的命令（package.json 里的 script 原文）,
  inputs 中声明的文件内容,
  任务的依赖任务产生的 hash（dependsOn 指定）,
  env / globalEnv 中声明的环境变量值,
  globalDependencies 中声明的文件内容,
  pnpm-lock.yaml（全局依赖图）,
  turbo.json 中该任务的配置,
  Turborepo 版本
)
```

因此，以下变化都会导致缓存失效：

- 修改 `src/` 下参与构建的文件
- 修改 `tsconfig.json`、`package.json`
- 依赖升级（`pnpm-lock.yaml` 变化）
- 变更 `turbo.json` 中的任务配置
- 变更声明过的环境变量
- 上游任务的 hash 变化

反过来，修改 `README.md`、`.gitignore` 这类没有进入 `inputs` 的文件，不会让构建缓存失效。

### 缓存存放位置

Turborepo 2.x 把本地缓存放在仓库根目录的 `.turbo/`：

```txt
taskflow/
└── .turbo/
    ├── cache/
    │   ├── 0f3a9c...tar.zst     # 任务产物归档（按 hash 命名）
    │   ├── 7b21e4...tar.zst
    │   └── ...
    └── runs/
        └── <run-id>.json        # turbo run --summarize 生成的运行摘要
```

每个 `.tar.zst` 里包含该任务声明的 `outputs`（如 `dist/`）和日志。缓存命中时，Turborepo 解包归档、恢复产物，并回放日志。

> **`.turbo` 已经在 `.gitignore` 中**（Ch02、Ch10 都配置过）。它不是源码，也不应该被提交。需要清理时直接删除 `.turbo/cache` 即可。

### 缓存命中流程

```txt
1. 计算任务 hash H
2. 查本地 .turbo/cache/H.tar.zst
3. 命中：
   a. 解包并恢复 outputs
   b. 回放 stdout/stderr
   c. 标记 "cache hit, replaying logs"
4. 未命中：
   a. 执行命令
   b. 校验 outputs 是否存在
   c. 打包 outputs + 日志到 H.tar.zst
   d. 若配置了远程缓存，异步上传
```

Turborepo 只缓存**成功退出**的任务。非零退出码的执行结果不会被缓存，避免把失败状态分发给别人。

## 11.2 命中与失效的判定

### 案例一：修改无关文件

```bash
# 第一次
$ pnpm build
# shared / database / api / web 全部 cache miss

# 只改 apps/web/README.md
$ pnpm build
# 全部 cache hit
```

`README.md` 不在 `inputs` 中，不参与 hash。

### 案例二：修改 shared 的源码

```bash
$ pnpm build

@taskflow/shared:build: cache miss      # 源文件变了
@taskflow/database:build: cache hit     # 不依赖 shared
@taskflow/api:build: cache miss         # 依赖 shared
@taskflow/web:build: cache miss         # 依赖 shared
```

注意 `database` 仍然命中：它和 shared 没有依赖关系。`ui` 没有 `build` 任务，不会出现在执行列表里。

### 案例三：环境变量变化

`turbo.json` 中：

```json
"build": {
  "env": ["VITE_APP_TITLE", "VITE_API_ORIGIN"]
}
```

```bash
$ VITE_APP_TITLE=TaskFlow-Dev pnpm build
# web: cache miss（变量值进入 hash）

$ VITE_APP_TITLE=TaskFlow-Dev pnpm build
# web: cache hit

$ VITE_APP_TITLE=TaskFlow v2 pnpm build
# web: cache miss
```

**没声明的变量不会参与 hash。** 在默认 strict 模式下，它还会被过滤掉，任务直接读不到；如果你为了排查临时用了 `--env-mode=loose`，或者变量来自没有纳入 `inputs` 的 `.env` 文件，就可能出现"缓存命中但结果错误"——这是缓存污染的头号原因。

### 案例四：锁文件变化

```bash
pnpm add axios@latest
pnpm build
# 所有任务 cache miss
```

`pnpm-lock.yaml` 是整个依赖图的输入，任何依赖变化都会让所有任务重新计算 hash。

### 案例五：`inputs` 的排除

```json
"build": {
  "inputs": ["src/**", "!src/**/*.test.ts", "tsconfig.json", "package.json"]
}
```

测试文件不参与构建 hash，改测试不会触发构建。但要注意：**测试文件也不参与 test 任务的 hash 吗？** 如果 `test` 任务复用同一个 `inputs`，就会漏掉测试改动。因此 test 必须单独声明包含 `tests/**` 和 `*.test.ts` 的 `inputs`。

## 11.3 远程缓存（Remote Cache）

本地缓存只在当前机器有效。团队成员、CI、部署平台各自构建一遍，浪费的是同一份算力。远程缓存把 `.tar.zst` 放到共享存储里，让所有人按 hash 复用。

### 方案一：Vercel Remote Cache

Vercel 提供的托管远程缓存目前对所有套餐免费，且不要求应用部署在 Vercel 上。

**本地链接：**

```bash
# 安装并登录（会把凭据保存到本地用户配置）
pnpm dlx turbo login

# 将当前仓库链接到 Vercel 团队
pnpm dlx turbo link
```

链接完成后，`turbo run` 产生的缓存会同时写入本地和远程。验证方法：

```bash
rm -rf .turbo/cache
pnpm build
# 如果远程缓存正常，任务不会真正执行，而是 "cache hit, replaying logs"
```

> `turbo link` 把仓库与团队/缓存提供方关联起来，链接信息保存在本地（`.turbo/` 目录已被忽略）。不要把任何凭据提交到 Git。

**在 CI 中使用：**

CI 没有交互式登录，需要用环境变量：

| 变量 | 内容 | 存放位置 |
| --- | --- | --- |
| `TURBO_TEAM` | Vercel 团队 slug | 仓库 Variables（非机密） |
| `TURBO_TOKEN` | 远程缓存访问 token | 仓库 Secrets |

```yaml
env:
  TURBO_TEAM: ${{ vars.TURBO_TEAM }}
  TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
```

`TURBO_TOKEN` 从 Vercel 团队的 Remote Cache 设置页生成。它等同于缓存的读写权限，泄露意味着别人可以读写你的构建产物。

### 方案二：自建远程缓存

需要内网存储、合规隔离或完全掌控数据时，可以自建。社区实现中维护较活跃的是 `ducktors/turborepo-remote-cache`。

**用 Docker Compose 启动：**

```yaml
# docker-compose.yml
services:
  turbo-cache:
    image: ducktors/turborepo-remote-cache:latest
    ports:
      - "3100:3100"
    environment:
      TURBO_TOKEN: ${TURBO_CACHE_TOKEN}
      STORAGE_PROVIDER: local
      STORAGE_PATH: /cache
    volumes:
      - turbo-cache-data:/cache
    restart: unless-stopped

volumes:
  turbo-cache-data:
```

> Compose v2 已经不需要顶层 `version` 字段；写上反而会有警告。

**客户端链接：**

```bash
pnpm dlx turbo login --manual
# 依次输入：
#   API URL: http://your-cache-server:3100
#   Team:    my-team（任意标识，用于隔离不同仓库/团队）
#   Token:   与服务端 TURBO_TOKEN 一致
```

CI 中同样用环境变量，自建缓存还需要 `TURBO_API`：

```yaml
env:
  TURBO_API: https://cache.example.com
  TURBO_TEAM: taskflow
  TURBO_TOKEN: ${{ secrets.TURBO_CACHE_TOKEN }}
```

**不要把 token 写进 `.npmrc`。** `.npmrc` 的 `_authToken` 是 npm registry 的认证机制，与 Turborepo Remote Cache 的 HTTP Bearer 认证无关，写了也不会生效，反而会让密钥进入错误的作用域。

**安全建议：**

- 缓存服务只暴露在内网或经过反向代理 + TLS。
- `TURBO_TOKEN` 使用高强度随机值，定期轮换。
- 不要把缓存目录挂载到公开可读的对象存储；缓存归档里可能包含 source map、构建日志和环境相关字符串。

### 启用产物签名

远程缓存是共享存储。如果服务端被入侵，攻击者可以投放被篡改的构建产物。Turborepo 支持 HMAC-SHA256 签名：

```json
{
  "remoteCache": {
    "signature": true
  }
}
```

然后在开发机和 CI 中设置同一个密钥：

```bash
TURBO_REMOTE_CACHE_SIGNATURE_KEY=<高强度随机值>
```

下载缓存时，Turborepo 会校验签名；校验失败按缓存未命中处理。轮换密钥会让旧缓存全部失效，这是预期行为。

## 11.4 缓存调试技巧

### `--force`：跳过缓存

```bash
turbo run build --force
```

所有任务忽略已有缓存、强制重新执行；执行结果仍会写入缓存（用于覆盖被污染的条目）。适合怀疑缓存污染时做一次性验证。

### `--output-logs`：控制日志

```bash
# 只显示本次真正执行的任务日志
turbo run build --output-logs=new-only

# 显示所有日志（包括命中任务的回放）
turbo run build --output-logs=full

# 不显示任务日志
turbo run build --output-logs=none

# 只显示 hash 相关日志
turbo run build --output-logs=hash-only
```

`hash-only` 会打印参与 hash 的文件与最终 hash，是排查"为什么没命中"最直接的入口。

### `--dry=json`：查看将要执行什么

```bash
turbo run build --dry=json
```

输出是结构化的，可以配合 `jq` 检查：

```bash
turbo run build --dry=json | jq '.tasks[] | {taskId, command, cache}'
```

```json
{
  "taskId": "@taskflow/shared#build",
  "command": "tsc -p tsconfig.json",
  "cache": {
    "status": "MISS",
    "timeSaved": 0,
    "remoteCacheHit": false
  }
}
```

`cache.status` 的取值包括 `HIT`、`MISS`、`SKIPPED`（任务没有可缓存配置）等。

### `--summarize`：生成运行摘要

```bash
turbo run build --summarize
```

摘要写入 `.turbo/runs/<run-id>.json`，包含每个任务的 hash、耗时、缓存状态、依赖关系。排查大型流水线时，比终端输出更完整。

### 清除缓存

```bash
# 清除本地缓存（跨平台写法见下）
rm -rf .turbo/cache        # macOS / Linux / Git Bash
rd /s /q ".turbo\cache"    # Windows CMD
```

Turborepo 没有 `turbo clean` 子命令；缓存目录就是普通文件夹，直接删除即可。

### 一个排查顺序

1. `--dry=json` 确认任务是否在计划中（可能是脚本名拼错）。
2. `--output-logs=hash-only` 看哪些输入进入了 hash。
3. 检查 `env` / `globalEnv` 是否漏声明。
4. 检查 `globalDependencies` 是否覆盖了共享配置文件。
5. 用 `--force` 排除缓存污染。

## 11.5 缓存策略

### 哪些任务可以缓存？

| 任务 | 缓存 | 说明 |
| --- | --- | --- |
| `build` | ✅ | 输入确定时输出确定 |
| `lint` | ✅ | 结果由源码和配置决定 |
| `typecheck` | ✅ | 同上 |
| `test`（纯单元测试） | ✅ | 不依赖外部服务时可缓存 |
| `test`（访问数据库/网络的集成测试） | ❌ | 外部状态不在 hash 里，缓存会掩盖真实问题 |
| `dev` | ❌ | 常驻进程 |
| `db:migrate` / `db:push` | ❌ | 修改数据库，有副作用 |
| `deploy` | ❌ | 修改外部环境 |

判断标准只有两条：

1. **确定性**：相同输入必然产生相同输出。
2. **无副作用**：不修改数据库、文件系统、网络等外部状态。

### 精确配置 `inputs`

```json
// ❌ 太宽泛：改 README 也会让构建失效
"inputs": ["**"]

// ✅ 只监控真正影响构建的文件
"inputs": ["src/**", "tsconfig.json", "package.json"]

// ✅ 构建不关心测试文件
"inputs": ["src/**", "!src/**/*.test.ts", "tsconfig.json", "package.json"]
```

但不要为了"更精确"而漏掉关键文件。漏掉 `prisma/**` 会让 Schema 改动后 database 仍然命中旧产物；漏掉 `.env*` 会让 Vite 用旧的环境变量构建。

## 11.6 CI 中的缓存

### 无远程缓存

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/setup@v3
        with:
          cache: true
          require-lockfile: true
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm build
```

两个 2026 年的关键变化：

- `actions/checkout@v7` 是当前主版本。
- `pnpm/setup@v3` 同时安装 pnpm 和 Node.js（读取 `package.json` 的 `packageManager` 与 `.nvmrc`），并在检测到 `package.json` 时自动执行 `pnpm install`；`require-lockfile: true` 会强制 `--frozen-lockfile`。不再需要 `actions/setup-node` + `pnpm/action-setup` 两步。

### 有远程缓存

```yaml
jobs:
  quality:
    runs-on: ubuntu-latest
    env:
      TURBO_TEAM: ${{ vars.TURBO_TEAM }}
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      # 自建缓存才需要：
      # TURBO_API: ${{ vars.TURBO_API }}
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0        # --affected 需要 Git 历史
      - uses: pnpm/setup@v3
        with:
          cache: true
          require-lockfile: true
      - run: pnpm turbo run lint typecheck build --affected
```

`--affected` 会利用 GitHub Actions 提供的 `GITHUB_BASE_REF` 自动计算变更包及其下游，只执行受影响的任务。配合远程缓存，未受影响的包直接跳过，受影响的包优先命中团队已有的缓存。

> 如果使用浅克隆（`fetch-depth: 1`），Git 历史不足，Turborepo 会把所有包视为已变更。需要 `fetch-depth: 0`。

**效果对比（示例数据，10 个包）：**

| 场景 | 无缓存 | 本地缓存 | 远程缓存 |
| --- | --- | --- | --- |
| 首次全量构建 | 45s | 45s | 45s |
| 无变更重建 | 45s | 1.2s | 2.5s |
| 修改 1 个包 | 45s | 8s | 9s |
| CI 首次构建 | 45s | 45s | 12s（复用开发者上传的缓存） |
| CI 修改 1 个包 | 45s | 45s | 9s |

CI 的价值不在"本机热缓存"，而在于**跨机器复用**：开发者在本地跑过一次的任务，CI 可以直接命中。

### 安全提醒

- `TURBO_TOKEN` 放进 `secrets`，不要放进 `vars` 或日志。
- 第三方 PR 默认拿不到 secrets；不要为了让它命中缓存而把 token 暴露给 `pull_request_target` 的不可信代码。
- 远程缓存归档里可能包含构建产物与日志，日志中不要打印密钥。

## 本章小结

- Turborepo 2.x 的本地缓存在 `.turbo/cache`，以内容 hash 命名的 `.tar.zst` 归档
- 缓存是否命中由命令、输入文件、依赖任务 hash、环境变量、全局依赖共同决定
- 远程缓存解决跨机器复用；Vercel 托管对团队免费，自建可用 `turborepo-remote-cache`
- CI 使用 `TURBO_TEAM` + `TURBO_TOKEN`；自建缓存再加 `TURBO_API`
- 生产级远程缓存应启用 `remoteCache.signature` 与 `TURBO_REMOTE_CACHE_SIGNATURE_KEY`
- `--dry=json`、`--output-logs=hash-only`、`--summarize` 是排查缓存问题的三件套
