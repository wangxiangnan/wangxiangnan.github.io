# 第4章：Key的命名艺术与过期策略

## 引言：给数据取个好名字，给数据设个好寿命

变量命名是程序员永恒的难题——`data1`、`temp`、`xxx` 这些名字你肯定见过。Redis 的 Key 也一样，好的命名让代码自解释，坏的命名让三个月后的你怀疑人生。

而"过期策略"就更有趣了。现实世界有保质期，Redis 的数据也可以有。牛奶过期了不能喝，Redis 数据过期了自动消失——但你可以控制它什么时候消失、消失了怎么办。

本章就来聊聊 Key 的命名规范和 TTL（Time To Live）过期机制。

## 4.1 Key 的命名规范

一个好的 Key 命名应该像一个好的变量名：**看名字就知道它是什么、属于谁、用于何处**。

### 推荐的命名模式

```
{业务模块}:{数据类型}:{唯一标识}
```

示例：

```
user:profile:1001           # 用户1001的个人资料
user:session:abc123def      # 会话ID为abc123def的session
order:detail:20230415001    # 订单详情
product:stock:SKU-12345     # 商品库存
article:content:10086       # 文章内容
cache:api:weather:beijing   # 北京天气的API缓存
rate:limit:user:1001        # 用户1001的限流计数
leaderboard:game:poker      # 扑克游戏排行榜
```

### 命名规则清单

| 规则 | 好例子 | 坏例子 |
|------|--------|--------|
| 使用冒号分层级 | `user:profile:1001` | `userProfile1001` |
| 使用业务前缀 | `shop:cart:1001` | `cart1001` |
| 全小写 | `user:name:1001` | `User:Name:1001` |
| 使用连字符分隔单词 | `user:last-login:1001` | `user:lastLogin:1001` |
| 避免太长 | `u:pf:1001`（可接受的缩写） | `user:complete:profile:information:1001` |
| 不要包含空格 | `user:first-name:1001` | `user first name 1001` |

## 4.2 Key 的命名反模式

以下是你应该**避免**的命名方式：

```bash
# ❌ 反模式1：没有层级
SET userData "..."         # 谁的数据？什么数据？

# ❌ 反模式2：层级太深
SET app:v1:module:user:submodule:profile:field:name:id:1001 "..."  # 读起来像绕口令

# ❌ 反模式3：使用特殊字符
SET "user profile 1001" "..."  # 空格害人
SET "user\nprofile" "..."      # 换行符更可怕

# ❌ 反模式4：Key 太长
SET "this-is-a-very-long-key-that-describes-everything-in-detail-1001" "..."
# Redis 的 Key 最大 512MB，但超过 128 字节就不推荐了

# ❌ 反模式5：没有业务前缀（多应用共享 Redis 时会冲突）
SET "session:abc123" "..."     # 如果两个应用都用这个名字？Boom！

# ✅ 正确做法
SET "myapp:user:profile:1001" "..."
```

## 4.3 TTL（Time To Live）：给数据设置保质期

TTL 是 Redis 最实用的功能之一。就像牛奶包装上的保质期一样，你可以给每个 Key 设定一个"过期时间"，到期后 Redis 会自动删除它。

### 设置过期时间

```js
const Redis = require('ioredis');
const redis = new Redis();

async function ttlDemo() {
  // ========== EXPIRE：设置过期时间（秒） ==========
  await redis.set('temp:data', 'I am temporary');
  await redis.expire('temp:data', 60); // 60秒后过期
  console.log('TTL：', await redis.ttl('temp:data')); // ~60

  // ========== PEXPIRE：设置过期时间（毫秒） ==========
  await redis.set('temp:precise', 'Precise timing');
  await redis.pexpire('temp:precise', 1500); // 1.5秒后过期
  console.log('PTTL：', await redis.pttl('temp:precise')); // ~1500

  // ========== EXPIREAT：设置过期时间点（Unix时间戳，秒） ==========
  const futureTime = Math.floor(Date.now() / 1000) + 3600; // 1小时后
  await redis.set('temp:scheduled', 'Expires at specific time');
  await redis.expireat('temp:scheduled', futureTime);
  console.log('将在以下时间戳过期：', futureTime);

  // ========== SETEX / PSETEX：设置值并同时设置过期时间 ==========
  await redis.setex('temp:combined', 300, 'Set and expire in one command');
  console.log('SETEX TTL：', await redis.ttl('temp:combined')); // ~300

  // ========== TTL / PTTL：查看剩余生存时间 ==========
  // 返回值含义：
  //   > 0 : 剩余秒数/毫秒数
  //   -1  : Key 存在但没有设置过期时间（永久）
  //   -2  : Key 不存在（已过期或被删除）

  await redis.set('permanent:data', 'I live forever');
  console.log('永久Key的TTL：', await redis.ttl('permanent:data')); // -1
  console.log('不存在Key的TTL：', await redis.ttl('nonexistent'));    // -2

  // ========== PERSIST：移除过期时间（让它永久存活） ==========
  await redis.set('was-temporary', 'Now permanent');
  await redis.expire('was-temporary', 100);
  console.log('移除前TTL：', await redis.ttl('was-temporary')); // ~100
  await redis.persist('was-temporary');
  console.log('移除后TTL：', await redis.ttl('was-temporary')); // -1

  // ========== EXPIRETIME（Redis 7.0+）：获取过期时间戳 ==========
  await redis.set('with-expiry', 'test');
  const ts = Math.floor(Date.now() / 1000) + 7200;
  await redis.expireat('with-expiry', ts);
  const expiryTime = await redis.expiretime('with-expiry');
  console.log('过期时间戳：', expiryTime);

  // 清理
  await redis.del('temp:data', 'temp:precise', 'temp:scheduled',
    'temp:combined', 'permanent:data', 'was-temporary', 'with-expiry');
  await redis.quit();
}

ttlDemo();
```

## 4.4 Redis 的过期删除策略

Redis 怎么知道一个 Key 过期了？答案是：**两种策略结合使用**。

**编程比喻**：TTL 过期删除就像 Cookie 的过期。浏览器有两种处理方式：

- 你访问这个 Cookie 时检查它是否过期（惰性删除）
- 浏览器后台定期扫描清理过期 Cookie（定期删除）

### 策略一：惰性删除（Lazy Expiration）

当客户端访问一个 Key 时，Redis 检查它是否已过期。如果过期，直接删除并返回 null。

```
客户端 → GET user:session:abc123
Redis  → 检查 TTL → 已过期！ → 删除 Key → 返回 null
```

优点：省 CPU，不用主动扫描
缺点：如果过期的 Key 没人访问，它会一直"赖在"内存里

### 策略二：定期删除（Active Expiration）

Redis 每 100ms 随机抽取一批设置了 TTL 的 Key 检查，删除已过期的。如果过期比例超过 25%，会继续扫描。

```
Redis 后台 → 随机抽 20 个有 TTL 的 Key → 检查 → 删除过期的
           → 超过 25% 过期了？ → 再抽 20 个检查...
           → 不到 25%？ → 下次再说
```

优点：能及时清理无人访问的过期 Key
缺点：消耗少量 CPU

> **Tip**：两种策略的组合确保了 Redis 既不会因为过期 Key 而内存爆炸，也不会因为清理过期 Key 而卡死。这是一个精妙的工程权衡。

## 4.5 内存淘汰策略（maxmemory-policy）

当 Redis 内存满了（达到 `maxmemory` 限制），新数据写不进来怎么办？这时候就需要"内存淘汰策略"——决定哪些数据该被"请出去"。

**编程比喻**：内存淘汰就像 JavaScript 的垃圾回收（GC）——当内存不够用时，系统自动决定哪些对象可以被回收。区别是 JS 的 GC 看的是"有没有引用"，Redis 看的是你选的策略。

```js
const Redis = require('ioredis');
const redis = new Redis();

async function evictionPolicies() {
  // 查看当前淘汰策略
  const config = await redis.config('get', 'maxmemory-policy');
  console.log('当前淘汰策略：', config);

  // 查看最大内存设置
  const maxmem = await redis.config('get', 'maxmemory');
  console.log('最大内存：', maxmem);

  // 动态修改淘汰策略（谨慎操作）
  // await redis.config('set', 'maxmemory-policy', 'allkeys-lru');
  // await redis.config('set', 'maxmemory', '256mb');

  await redis.quit();
}

evictionPolicies();
```

### 六大淘汰策略详解

| 策略 | 适用范围 | 行为 | 适用场景 |
|------|----------|------|----------|
| **noeviction** | 所有Key | 内存满时拒绝写入（返回错误） | 不能丢数据的关键业务 |
| **allkeys-lru** | 所有Key | 淘汰最近最少使用的Key | **缓存场景首选** |
| **volatile-lru** | 有TTL的Key | 在有TTL的Key中淘汰最近最少使用的 | 部分数据需要持久化 |
| **allkeys-lfu** | 所有Key | 淘汰最不经常使用的Key（Redis 4.0+） | 热点数据缓存 |
| **volatile-lfu** | 有TTL的Key | 在有TTL的Key中淘汰最不经常使用的 | 部分持久+热点缓存 |
| **allkeys-random** | 所有Key | 随机淘汰Key | 数据重要性相同 |
| **volatile-random** | 有TTL的Key | 在有TTL的Key中随机淘汰 | 部分持久+随机淘汰 |
| **volatile-ttl** | 有TTL的Key | 淘汰剩余TTL最短的Key | 让快过期的先走 |

> **Warning**：默认的 `noeviction` 策略在缓存场景下非常危险——内存满了直接报错，你的应用就挂了！缓存场景一定要改成 `allkeys-lru` 或 `allkeys-lfu`。

### LRU vs LFU 的区别

```
LRU (Least Recently Used)：谁最久没被访问，淘汰谁
  时间线：[A访问] [B访问] [C访问] [A访问] [B访问] ...
  淘汰顺序：C最久没被访问 → C先走

LFU (Least Frequently Used)：谁被访问次数最少，淘汰谁
  访问次数：A=100次, B=50次, C=3次
  淘汰顺序：C访问最少 → C先走
```

简单说：LRU 看"最近"，LFU 看"频率"。对于大多数缓存场景，LFU 更合理——因为有些数据虽然最近没被访问，但历史上被访问过很多次（说明它是热点数据）。

## 4.6 实战：带 TTL 的缓存系统

```js
const Redis = require('ioredis');
const redis = new Redis();

class CacheManager {
  constructor(redis, options = {}) {
    this.redis = redis;
    this.prefix = options.prefix || 'cache';
    this.defaultTTL = options.defaultTTL || 300; // 默认5分钟
  }

  // 生成完整的 Key
  _key(name) {
    return `${this.prefix}:${name}`;
  }

  // 获取缓存（自动处理 JSON 解析）
  async get(name) {
    const key = this._key(name);
    const data = await this.redis.get(key);
    if (!data) return null;

    try {
      return JSON.parse(data);
    } catch {
      return data;
    }
  }

  // 设置缓存（自动处理 JSON 序列化）
  async set(name, value, ttl) {
    const key = this._key(name);
    const serialized = typeof value === 'string' ? value : JSON.stringify(value);
    const expiry = ttl || this.defaultTTL;

    if (expiry > 0) {
      await this.redis.setex(key, expiry, serialized);
    } else {
      await this.redis.set(key, serialized);
    }
  }

  // 获取或设置（缓存穿透的标准做法）
  async getOrSet(name, fetchFn, ttl) {
    // 先查缓存
    let data = await this.get(name);
    if (data !== null) {
      console.log(`  [缓存命中] ${name}`);
      return data;
    }

    // 缓存未命中，调用数据获取函数
    console.log(`  [缓存未命中] ${name}，正在获取数据...`);
    data = await fetchFn();

    // 写入缓存
    await this.set(name, data, ttl);
    console.log(`  [已缓存] ${name}，TTL=${ttl || this.defaultTTL}s`);

    return data;
  }

  // 删除缓存
  async del(name) {
    return await this.redis.del(this._key(name));
  }

  // 刷新 TTL（续命）
  async refreshTTL(name, ttl) {
    return await this.redis.expire(this._key(name), ttl || this.defaultTTL);
  }

  // 查看缓存信息
  async info(name) {
    const key = this._key(name);
    const ttl = await this.redis.ttl(key);
    const exists = await this.redis.exists(key);

    return {
      key,
      exists: !!exists,
      ttl: ttl > 0 ? `${ttl}s` : (ttl === -1 ? '永久' : '已过期/不存在'),
    };
  }
}

async function main() {
  const cache = new CacheManager(redis, {
    prefix: 'myapp',
    defaultTTL: 60,
  });

  // 模拟一个耗时的数据库查询
  const fetchUserFromDB = async (userId) => {
    // 模拟数据库查询延迟
    await new Promise(resolve => setTimeout(resolve, 100));
    return {
      id: userId,
      name: `用户${userId}`,
      email: `user${userId}@example.com`,
      fetchedAt: new Date().toISOString(),
    };
  };

  console.log('=== 缓存系统演示 ===\n');

  // 第一次请求：缓存未命中
  console.log('请求1：');
  const user1 = await cache.getOrSet('user:1001', () => fetchUserFromDB(1001), 120);
  console.log('  结果：', user1.name);

  // 第二次请求：缓存命中
  console.log('\n请求2：');
  const user2 = await cache.getOrSet('user:1001', () => fetchUserFromDB(1001), 120);
  console.log('  结果：', user2.name);

  // 查看缓存信息
  console.log('\n缓存信息：', await cache.info('user:1001'));

  // 刷新 TTL
  await cache.refreshTTL('user:1001', 300);
  console.log('续命后：', await cache.info('user:1001'));

  // 手动删除缓存
  await cache.del('user:1001');
  console.log('删除后：', await cache.info('user:1001'));

  // 第三次请求：缓存已删除，重新获取
  console.log('\n请求3：');
  const user3 = await cache.getOrSet('user:1001', () => fetchUserFromDB(1001), 120);
  console.log('  结果：', user3.name);

  await redis.quit();
}

main();
```

## 4.7 小结

> **好命名是自解释的，好TTL是自动清理的**

- Key 命名遵循 `{业务}:{类型}:{标识}` 的层级模式，用冒号分隔
- 避免命名反模式：无层级、太长、含特殊字符、无业务前缀
- TTL 四种设置方式：`EXPIRE`（秒）、`PEXPIRE`（毫秒）、`EXPIREAT`（时间戳）、`SETEX`（设置+过期）
- Redis 用惰性删除 + 定期删除的组合策略来清理过期 Key
- 内存淘汰策略首选 `allkeys-lru`（缓存）或 `allkeys-lfu`（热点缓存）
- 永远不要在生产环境使用默认的 `noeviction`（除非你真的不能丢数据）
