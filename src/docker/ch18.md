# 第18章：Kubernetes核心概念 —— 从Docker到K8s

## 引言：当你的"容器军团"需要一个指挥官

想象一下这个场景：你是一个创业公司的后端开发，老板兴冲冲跑来说——

> "我们的用户从 100 涨到 100 万了！赶紧多开几个服务！"

你信心满满地打开终端，`docker run` 了 10 个容器。然后又手动配了 Nginx 负载均衡。第二天，一个容器挂了，用户投诉。你爬起来手动重启。第三天，又挂了三个……

这时候你大概会想：**我要是有个"运维管家"就好了**——它能自动发现挂掉的容器、自动重启、自动扩容、自动做负载均衡，我只需要告诉它"我要 10 个副本"就行了。

恭喜，你刚刚描述的，就是 **Kubernetes**（简称 K8s，因为 k 和 s 之间有 8 个字母，就像 `i18n` 是 `internationalization` 的缩写一样——程序员的懒癌无处不在）。

如果说 Docker 是"集装箱"，那 Kubernetes 就是"自动化港口管理系统"。Docker 解决了"怎么打包和运输货物"的问题，K8s 解决了"怎么管理成千上万个集装箱"的问题。

## 18.1 为什么需要 K8s？

让我们先看看没有 K8s 的世界有多痛苦：

| 场景 | 手动管理（Docker 单机） | K8s 管理 |
|------|------------------------|---------|
| 容器挂了 | 手动发现，手动重启 | 自动检测，自动重启 |
| 需要扩容 | 手动 `docker run` 更多容器 | 改一下 `replicas: 10`，自动扩容 |
| 滚动更新 | 手动一个一个替换容器 | 自动逐个替换，出问题自动回滚 |
| 负载均衡 | 手动配 Nginx | Service 自动负载均衡 |
| 多机器部署 | SSH 到每台机器手动操作 | 声明式配置，K8s 自动调度 |
| 配置/密钥管理 | 环境变量或文件，到处散落 | ConfigMap / Secret 统一管理 |

这就像你写代码从手动 `new` 每个对象，进化到用 Spring/依赖注入容器一样。K8s 就是容器世界的"依赖注入框架"——你声明你想要什么，它帮你搞定怎么实现。

> **Tip:** K8s 并不是要替代 Docker。Docker 负责构建镜像和运行单个容器，K8s 负责编排和管理大量容器。它们是不同层级的工具。不过在 K8s 生态中，底层容器运行时可以用 `containerd`（Docker 的核心组件之一）来代替完整的 Docker Engine。

## 18.2 K8s 架构概览

K8s 集群由两类节点组成：**Master 节点**（大脑）和 **Worker 节点**（四肢）。

```bash
┌──────────────────── Master 节点（控制平面）────────────────────┐
│                                                                │
│  ┌──────────┐  ┌──────────┐  ┌────────────┐  ┌────────────┐  │
│  │API Server│  │  etcd    │  │ Scheduler  │  │ Controller │  │
│  │ (前台)   │  │(数据库)  │  │ (调度员)   │  │  Manager   │  │
│  │          │  │          │  │            │  │ (管理员)   │  │
│  └──────────┘  └──────────┘  └────────────┘  └────────────┘  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
         │              │              │
         ▼              ▼              ▼
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ Worker 节点1│ │ Worker 节点2│ │ Worker 节点3│
│ ┌─────────┐ │ │ ┌─────────┐ │ │ ┌─────────┐ │
│ │ kubelet │ │ │ │ kubelet │ │ │ │ kubelet │ │
│ │ kube-   │ │ │ │ kube-   │ │ │ │ kube-   │ │
│ │ proxy   │ │ │ │ proxy   │ │ │ │ proxy   │ │
│ │ ┌───┐   │ │ │ │ ┌───┐   │ │ │ │ ┌───┐   │ │
│ │ │Pod│   │ │ │ │ │Pod│   │ │ │ │ │Pod│   │ │
│ │ └───┘   │ │ │ │ └───┘   │ │ │ │ └───┘   │ │
│ └─────────┘ │ │ └─────────┘ │ │ └─────────┘ │
└─────────────┘ └─────────────┘ └─────────────┘
```

### Master 节点组件（控制平面）

| 组件 | 角色 | 类比 |
|------|------|------|
| **API Server** | 所有操作的统一入口（REST API） | 公司前台——所有请求都经过它 |
| **etcd** | 分布式键值数据库，存储集群所有状态 | 公司的"档案室"——集群的唯一真相来源 |
| **Scheduler** | 决定 Pod 运行在哪个 Worker 节点上 | HR 部门——决定新员工分配到哪个工位 |
| **Controller Manager** | 确保集群实际状态 = 期望状态 | 项目经理——"我要 3 个副本"，它就盯着确保有 3 个 |

### Worker 节点组件

| 组件 | 角色 | 类比 |
|------|------|------|
| **kubelet** | 节点上的"代理人"，负责管理 Pod 生命周期 | 每个工位的"监工" |
| **kube-proxy** | 维护网络规则，实现 Service 的负载均衡 | 公司内部的"电话转接系统" |
| **容器运行时** | 实际运行容器的组件（containerd、CRI-O 等） | 真正干活的工人 |

> **Tip:** 对于开发和学习，你不需要真的搭建一个多节点集群。后面我们会介绍 Minikube、Kind 等工具，它们能在你的笔记本上跑一个"迷你 K8s 集群"。

## 18.3 核心资源对象

K8s 的世界是由**资源对象（Resource）**构成的。你可以把它类比为面向对象编程中的类——每种资源都有自己的结构和用途。

### 18.3.1 Pod —— 最小调度单元

Pod 是 K8s 中最小的调度单元。**一个 Pod 可以包含一个或多个容器**，这些容器共享网络和存储。

为什么不直接管理容器？类比一下：

```javascript
// 你不会这样写代码：
container1.start();
container2.start();
container1.connect(container2);

// 你会这样写——把它们封装成一个逻辑单元：
class ApplicationPod {
  constructor() {
    this.app = new AppContainer();     // 主容器
    this.logger = new LogSidecar();    // 日志辅助容器
  }
}
```

一个 Pod 就像一个"容器组"——里面的容器被一起调度、一起启停、共享 `localhost` 网络。99% 的情况下，你的 Pod 里只有一个容器。但当你需要 sidecar 模式（比如日志收集、代理）时，多容器 Pod 就派上用场了。

```yaml
# 一个最简单的 Pod 定义
apiVersion: v1
kind: Pod
metadata:
  name: my-nodejs-app         # Pod 名称
  labels:
    app: nodejs               # 标签，用于 Service 选择器匹配
spec:
  containers:
  - name: app                 # 容器名称（Pod 内的唯一标识）
    image: my-nodejs:v1.0     # 使用的镜像
    ports:
    - containerPort: 3000     # 容器暴露的端口
    resources:                # 资源限制（生产环境必须设置！）
      requests:               # 最低保障资源
        memory: "128Mi"
        cpu: "100m"           # 100m = 0.1 个 CPU 核心
      limits:                 # 最高使用上限
        memory: "256Mi"
        cpu: "500m"
```

> **Warning:** 在实际生产中，你几乎不会直接创建 Pod（就像你不会在生产环境手动 `new` 一个数据库连接而不使用连接池）。你会通过 Deployment 来管理 Pod，这样 K8s 才能帮你处理副本、滚动更新和故障恢复。

### 18.3.2 Deployment —— 声明式管理 Pod 副本

Deployment 是 Pod 的"管理者"。你告诉它"我要 3 个 `my-nodejs:v1.0` 的 Pod 副本"，它就会确保集群中始终有 3 个健康的 Pod 在运行。

```yaml
# Deployment：我要 3 个副本，少一个你补一个，多一个你杀掉
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-deployment
  labels:
    app: nodejs
spec:
  replicas: 3                 # 期望的副本数量
  selector:
    matchLabels:
      app: nodejs             # 通过标签选择器找到"我的 Pod"
  template:                   # Pod 模板（Deployment 用它来创建 Pod）
    metadata:
      labels:
        app: nodejs
    spec:
      containers:
      - name: app
        image: my-nodejs:v1.0
        ports:
        - containerPort: 3000
        readinessProbe:       # 就绪检查（后面会详细讲）
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 10
```

当你执行 `kubectl apply -f deployment.yaml` 后，会发生什么？

1. K8s 创建 Deployment 对象
2. Deployment Controller 发现需要 3 个 Pod
3. 创建 ReplicaSet（Deployment 的"打工人"）
4. ReplicaSet 创建 3 个 Pod
5. Scheduler 把 Pod 分配到不同 Worker 节点
6. 各节点的 kubelet 启动容器

如果某个 Pod 所在的节点突然宕机了？Controller Manager 发现实际 Pod 数量（2 个）< 期望数量（3 个），立刻在其他健康节点上创建新 Pod。**这就是声明式（Declarative）管理的力量**——你只需要声明"我要什么"，K8s 负责"怎么做到"。

```python
# 类比：声明式 vs 命令式
# 命令式（像写菜谱，每一步都要你指定）：
pod1 = create_pod("node1")
pod2 = create_pod("node2")
pod3 = create_pod("node3")
if pod1.crashes():
    pod1_backup = create_pod("node4")  # 你得自己处理所有异常

# 声明式（像写测试用例，只描述期望结果）：
desired_state = {"replicas": 3, "image": "my-nodejs:v1.0"}
# K8s 的 Controller 会不断对比 desired vs actual，自动修正差异
```

### 18.3.3 Service —— 服务发现与负载均衡

问题来了：Pod 有自己的 IP 地址，但 Pod 可能被重建（IP 会变），副本有多个（你该访问哪个？）。Service 就是来解决这个问题的。

Service 为一组 Pod 提供**稳定的访问入口**（固定的 IP 和 DNS 名称），并自动做负载均衡。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nodejs-service        # 服务名称（在集群内可通过 DNS 访问）
spec:
  selector:
    app: nodejs               # 选择所有带 app=nodejs 标签的 Pod
  ports:
  - port: 80                  # Service 暴露的端口
    targetPort: 3000          # 转发到 Pod 的端口
  type: ClusterIP             # 仅集群内可访问（默认类型）
```

创建后，集群内任何 Pod 都可以通过 `http://nodejs-service:80` 访问你的 Node.js 应用，K8s 会自动在 3 个副本之间做负载均衡。就像你不需要知道公司里谁负责某个模块——你只需要知道"前端组"这个入口就行。

### 18.3.4 Namespace —— 资源隔离

Namespace 就像 K8s 集群中的"虚拟机房"。不同的 Namespace 之间的资源相互隔离：

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production            # 生产环境
---
apiVersion: v1
kind: Namespace
metadata:
  name: staging               # 预发布环境
---
apiVersion: v1
kind: Namespace
metadata:
  name: development           # 开发环境
```

为什么需要 Namespace？

- **资源隔离**：dev 环境的 Pod 不会影响 prod 环境
- **权限控制**：开发人员只能访问 dev Namespace
- **资源配额**：限制 dev 环境最多用 4 个 CPU、8GB 内存
- **命名隔离**：不同 Namespace 下可以有同名的 Service

默认有 3 个 Namespace：`default`（默认）、`kube-system`（K8s 系统组件）、`kube-public`（公共资源）。

> **Tip:** 小团队不需要过度使用 Namespace。一个简单的划分就够了：`default` 给日常使用，`kube-system` 不要动，再加一个 `monitoring` 给监控系统就行。

### 18.3.5 ConfigMap & Secret —— 配置与密钥管理

还记得我们在 Docker 里用环境变量传配置吗？K8s 提供了更优雅的解决方案：

```yaml
# ConfigMap：存储非敏感配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DATABASE_URL: "mongodb://mongo-service:27017/mydb"
  LOG_LEVEL: "info"
  NODE_ENV: "production"
  # 也可以存储完整的配置文件
  nginx.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://nodejs-service:80;
      }
    }
---
# Secret：存储敏感信息（Base64 编码，不是加密！）
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
data:
  # 注意：值需要 Base64 编码
  # echo -n "my-secret-key" | base64 → bXktc2VjcmV0LWtleQ==
  JWT_SECRET: bXktc2VjcmV0LWtleQ==
  DB_PASSWORD: c3VwZXItc2VjcmV0
```

在 Pod 中使用：

```yaml
spec:
  containers:
  - name: app
    image: my-nodejs:v1.0
    env:
    - name: DATABASE_URL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: DATABASE_URL
    - name: JWT_SECRET
      valueFrom:
        secretKeyRef:
          name: app-secrets
          key: JWT_SECRET
    volumeMounts:
    - name: config-volume
      mountPath: /etc/nginx/nginx.conf
      subPath: nginx.conf
  volumes:
  - name: config-volume
    configMap:
      name: app-config
```

> **Warning:** Secret 默认只是 Base64 编码，**不是加密**！任何有权限读取 Secret 的人都能看到明文。在生产环境中，建议：
>
> 1. 启用 K8s 的 `EncryptionConfiguration`（静态加密）
> 2. 使用外部密钥管理系统（如 HashiCorp Vault、AWS Secrets Manager）
> 3. 严格限制 RBAC 权限

## 18.4 kubectl 命令速查

`kubectl`（读作 "kube-control" 或 "kube-ect-ell"，K8s 社区对怎么读这个名字也有分歧）是你和 K8s 对话的唯一工具。

```bash
# ===== 查看资源 =====
kubectl get pods                      # 列出所有 Pod
kubectl get pods -o wide              # 列出 Pod，显示更多信息（IP、节点等）
kubectl get pods -n production        # 指定 Namespace
kubectl get pods -l app=nodejs        # 按标签筛选
kubectl get pods --watch              # 实时监控（类似 watch 命令）
kubectl get all                       # 查看所有资源
kubectl get deployments               # 列出所有 Deployment
kubectl get services                  # 列出所有 Service
kubectl get configmaps                # 列出所有 ConfigMap

# ===== 查看详情 =====
kubectl describe pod my-pod           # 查看 Pod 详细信息（事件、状态等）
kubectl describe deployment my-deploy # 查看 Deployment 详情
kubectl describe service my-svc       # 查看 Service 详情

# ===== 创建/更新资源 =====
kubectl apply -f deployment.yaml      # 创建或更新资源（推荐！声明式）
kubectl apply -f ./k8s/               # 应用目录下所有 YAML 文件
kubectl apply -f https://url/to/yaml  # 从 URL 应用

# ===== 删除资源 =====
kubectl delete pod my-pod             # 删除指定 Pod
kubectl delete -f deployment.yaml     # 删除 YAML 中定义的资源
kubectl delete pods --all -n dev      # 删除 dev 命名空间下所有 Pod（慎用！）

# ===== 日志与调试 =====
kubectl logs my-pod                   # 查看 Pod 日志
kubectl logs my-pod -f                # 实时跟踪日志（类似 tail -f）
kubectl logs my-pod --previous        # 查看上一个容器的日志（崩溃后排查用）
kubectl logs -l app=nodejs            # 查看匹配标签的所有 Pod 日志

# ===== 进入容器 =====
kubectl exec -it my-pod -- /bin/sh    # 进入 Pod 执行命令（像 docker exec）
kubectl exec -it my-pod -- cat /etc/config  # 在 Pod 中执行单条命令

# ===== 端口转发 =====
kubectl port-forward pod/my-pod 8080:3000   # 本地 8080 → Pod 3000
kubectl port-forward svc/my-svc 8080:80     # 本地 8080 → Service 80

# ===== 扩缩容 =====
kubectl scale deployment my-deploy --replicas=5  # 手动扩缩容

# ===== 滚动更新 =====
kubectl rollout status deployment/my-deploy  # 查看更新状态
kubectl rollout history deployment/my-deploy # 查看更新历史
kubectl rollout undo deployment/my-deploy    # 回滚到上一版本

# ===== 实用技巧 =====
kubectl get pods -o jsonpath='{.items[*].status.podIP}'  # 提取所有 Pod IP
kubectl top pods                            # 查看 Pod 资源使用（需要 metrics-server）
kubectl explain pod.spec.containers         # 查看字段文档（不用背 YAML！）
```

> **Tip:** `kubectl explain` 是一个被严重低估的命令。当你不确定某个字段怎么写时，直接 `kubectl explain deployment.spec.strategy` 就能查看官方文档，比翻网页快多了。

## 18.5 本地开发环境

在你的笔记本上搭建 K8s 学习环境，有三种主流选择：

| 工具 | 原理 | 启动速度 | 资源占用 | 适合场景 |
|------|------|---------|---------|---------|
| **Minikube** | 虚拟机/容器运行单节点集群 | 中等 | 中等 | 学习、功能测试 |
| **Kind** | 用 Docker 容器模拟 K8s 节点 | 快 | 低 | CI/CD、快速测试 |
| **Docker Desktop** | 内置 K8s（单节点） | 快 | 低 | 已安装 Docker Desktop 的开发者 |

### Minikube 快速上手

```bash
# 安装 Minikube（macOS / Linux / Windows）
# macOS
brew install minikube

# Linux (x86_64)
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube

# Windows (使用 Chocolatey)
choco install minikube

# 启动集群
minikube start

# 如果需要指定资源（避免你的笔记本变砖）
minikube start --cpus=2 --memory=4096

# 验证安装
kubectl cluster-info
kubectl get nodes

# 打开 Minikube 自带的 Dashboard（图形界面，新手友好！）
minikube dashboard

# 在 Minikube 中访问 Service（因为它运行在虚拟机里）
minikube service nodejs-service
```

### Kind（Kubernetes in Docker）

```bash
# 安装 Kind
# macOS
brew install kind
# Linux
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.20.0/kind-linux-amd64
chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind

# 创建集群
kind create cluster --name my-cluster

# 创建多节点集群（模拟真实环境！）
cat <<EOF | kind create cluster --name multi-node --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
EOF

# 加载本地构建的镜像到 Kind 集群
docker build -t my-app:v1 .
kind load docker-image my-app:v1 --name my-cluster
```

## 18.6 实战：将 Docker 应用部署到 Minikube

让我们把一个 Node.js 应用从 Docker 搬到 K8s。

### 第一步：准备应用

```javascript
// app.js - 一个简单的 Express 应用
const express = require('express');
const os = require('os');
const app = express();

// 健康检查端点
app.get('/health', (req, res) => {
  res.json({ status: 'ok', hostname: os.hostname() });
});

// 主页
app.get('/', (req, res) => {
  res.json({
    message: 'Hello from K8s!',
    hostname: os.hostname(),   // 显示 Pod 名称，方便观察负载均衡
    version: process.env.APP_VERSION || '1.0.0'
  });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});
```

```dockerfile
# Dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
# 不要用 root 用户运行（安全最佳实践）
USER node
CMD ["node", "app.js"]
```

### 第二步：构建镜像并加载到 Minikube

```bash
# 方式1：使用 Minikube 的 Docker 环境（推荐）
eval $(minikube docker-env)   # 让 docker build 直接在 Minikube 内部构建
docker build -t my-nodejs:v1.0 .

# 方式2：构建后加载（如果你用 Kind）
docker build -t my-nodejs:v1.0 .
kind load docker-image my-nodejs:v1.0
```

### 第三步：编写 K8s 资源文件

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-app
  labels:
    app: nodejs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nodejs
  template:
    metadata:
      labels:
        app: nodejs
    spec:
      containers:
      - name: nodejs
        image: my-nodejs:v1.0
        imagePullPolicy: IfNotPresent   # 本地镜像不拉取
        ports:
        - containerPort: 3000
        env:
        - name: APP_VERSION
          value: "1.0.0"
        resources:
          requests:
            memory: "64Mi"
            cpu: "50m"
          limits:
            memory: "128Mi"
            cpu: "200m"
        livenessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 10
          periodSeconds: 15
        readinessProbe:
          httpGet:
            path: /health
            port: 3000
          initialDelaySeconds: 5
          periodSeconds: 5
---
# k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nodejs-service
spec:
  selector:
    app: nodejs
  ports:
  - port: 80
    targetPort: 3000
  type: NodePort     # 通过节点端口暴露（开发环境用）
```

### 第四步：部署并验证

```bash
# 部署
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

# 验证
kubectl get pods                    # 应该看到 3 个 Pod，状态为 Running
kubectl get deployment nodejs-app   # 查看 Deployment
kubectl get service nodejs-service  # 查看 Service
kubectl describe pod -l app=nodejs  # 查看详细信息

# 访问服务
# Minikube
minikube service nodejs-service
# 或者手动端口转发
kubectl port-forward svc/nodejs-service 8080:80
# 然后访问 http://localhost:8080

# 测试负载均衡——多次请求应该看到不同的 hostname
for i in {1..10}; do curl -s http://localhost:8080 | jq .hostname; done

# 模拟 Pod 故障——删掉一个 Pod，观察 K8s 自动重建
kubectl delete pod -l app=nodejs --wait=false
kubectl get pods --watch
```

## 18.7 YAML 资源文件编写规范

K8s 资源文件几乎全部用 YAML 编写。这里有一些规范和坑：

```yaml
# 每个 K8s 资源文件都遵循这个通用结构：
apiVersion: v1          # API 版本（不同资源对应不同版本）
kind: Pod               # 资源类型
metadata:               # 元数据（名称、标签、注解等）
  name: my-pod
  labels:
    app: myapp
spec:                   # 规格/期望状态（每种资源的 spec 结构不同）
  # ... 具体配置
```

**常见 `apiVersion` 速查：**

| apiVersion | 资源类型 |
|-----------|---------|
| `v1` | Pod, Service, ConfigMap, Secret, Namespace, PersistentVolume |
| `apps/v1` | Deployment, StatefulSet, DaemonSet, ReplicaSet |
| `batch/v1` | Job, CronJob |
| `networking.k8s.io/v1` | Ingress, NetworkPolicy |
| `autoscaling/v2` | HorizontalPodAutoscaler |

**YAML 编写的常见坑：**

```yaml
# 坑1：缩进必须用空格，不能用 Tab（YAML 通病）
spec:
  containers:
  - name: app       # 正确
 name: app       # 错误！用了 Tab

# 坑2：字符串 vs 数字
spec:
  containers:
  - name: app
    ports:
    - containerPort: 3000     # 数字，不需要引号
    env:
    - name: PORT
      value: "3000"           # env 的 value 必须是字符串！

# 坑3：多文档用 --- 分隔
apiVersion: v1
kind: ConfigMap
metadata:
  name: config1
data:
  key: value
---                           # 三个横杠分隔不同资源
apiVersion: v1
kind: ConfigMap
metadata:
  name: config2
data:
  key: value2
```

> **Tip:** 使用 `kubectl apply --dry-run=client -o yaml` 可以快速生成 YAML 模板，不用从头手写：
>
> ```bash
> kubectl create deployment my-app --image=nginx --dry-run=client -o yaml > deployment.yaml
> ```
>
> 然后在生成的文件基础上修改，比从零开始写高效得多。

## 本章小结

- **K8s 解决了容器编排的核心问题**：自动调度、自动扩缩、自动故障恢复
- **架构分为 Master（控制平面）和 Worker（数据平面）**，各司其职
- **核心资源对象**：Pod（最小单元）、Deployment（副本管理）、Service（服务发现）、Namespace（隔离）、ConfigMap/Secret（配置管理）
- **声明式管理**是 K8s 的核心理念：你告诉它"要什么"，它负责"怎么做"
- **kubectl** 是你和 K8s 交互的主要工具，`apply` 是最推荐的资源管理方式
- **本地学习**可以用 Minikube、Kind 或 Docker Desktop

## 练习

1. **基础**：安装 Minikube 或 Kind，启动一个本地集群，运行 `kubectl get nodes` 确认节点就绪
2. **部署**：将一个你之前 Docker 化的应用部署到 K8s（编写 Deployment + Service YAML）
3. **故障恢复**：手动删除一个 Pod，观察 K8s 是否自动重建。用 `kubectl describe` 查看事件日志
4. **扩容**：将副本数从 3 改为 5，再改回 2，观察 Pod 变化
5. **挑战**：为应用添加 ConfigMap，将数据库 URL 等配置外部化，在 Pod 中通过环境变量引用
