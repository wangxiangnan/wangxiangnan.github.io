## 2.1 为什么 WireGuard 快——内核态与四千行

WireGuard 的快是设计出来的，不是调优调出来的，源头有两处。

第一处是**运行位置**。OpenVPN 是用户态（Userland）进程：一个包的旅程是「内核网卡 → 拷贝到用户态进程 → 加密 → 拷回内核 → 发出」，一来一回要跨内核/用户态边界四次。WireGuard 的加解密直接做在内核模块里：包进 `wg0`，在内核内完成加密，从物理网卡出去——零次用户态往返。系统调用与内存拷贝省下来的，就是吞吐和延迟。

```text
OpenVPN（用户态）:  应用 → 内核 → tap → [拷贝] → openvpn进程加密 → [拷贝] → 内核 socket → 物理网卡
WireGuard（内核态）: 应用 → wg0 → 内核内加密封装 → 物理网卡
```

两条路径一目了然：上排每对 `[拷贝]` 都是一次跨内核边界的开销，高包率下累积成显著延迟；下排全程不出内核。这也是 IPsec 同样快的原因——它的 ESP 加密也在内核——而 OpenVPN 快不起来的根因就是架构上住在用户态。

第二处是**代码量**。WireGuard 核心约 4000 行（Linux 内核内版本），OpenVPN 连同依赖的 OpenSSL 是十万行量级。代码量小不只意味着包小、加载快，更意味着**可审计的面小**——安全圈有句老话：读不完的代码等于读不了的代码。

WireGuard 论文的实测里，同硬件吞吐可达 OpenVPN 的数倍，弱网与移动设备上差距更明显。还有一个容易被忽略的「快」：**握手快**。OpenVPN 建连要 TLS 式的多轮协商，WireGuard 一个来回——下一节就讲这一个来回怎么完成的。

移动设备上还有一笔隐性收益：没有常驻的用户态进程，握手又稀疏（120 秒一次且仅在流量出现时），待机功耗远低于持续轮询的用户态 VPN。手机一整天挂着隧道却不见电量异常，就来自这个架构选择。

## 2.2 密码学套件——每样只选一件

TLS 的设计哲学是「协商」：客户端报出自己支持的十几种套件，双方挑一个。协商灵活，但也带来降级攻击（Downgrade Attack）与实现复杂度——OpenSSL 十万行大半在伺候这些选择。

WireGuard 把哲学反过来：**不协商**。协议直接规定了一套现代算法，想改就得升协议版本：

| 环节 | 套件 | 一句话理由 |
| ---- | ---- | ---- |
| 密钥交换 | Curve25519（椭圆曲线 ECDH） | 同等安全强度下密钥短、计算快 |
| 数据加密 | ChaCha20-Poly1305（AEAD） | 软件实现快，移动端无 AES 硬件加速也飞快 |
| 哈希 / 密钥推导 | BLAKE2s（含 HKDF） | 比 SHA2 快，代码量小 |
| 密钥类型 | 32 字节（256 位） | 公钥私钥都是一行 base64 |

这个「每样只选一件」的设计直接消灭了一整类攻击面：没有套件协商，就没有「诱导对方选弱算法」的降级空间。对你这个用户的影响是具体的——配置文件里**没有任何一行密码学参数**，`wg0.conf` 只有密钥、地址、路由三种东西（第三章解剖全文）。

> 术语说明：AEAD（Authenticated Encryption with Associated Data，带认证的加密）指加密与完整性校验一步完成——密文被篡改一个 bit 都会在解密时被发现并丢弃。

有人会问：AES-GCM 在带硬件加速的 x86 服务器上同样飞快，为什么选 ChaCha20？因为 WireGuard 的目标设备 spectrum 很宽——手机、路由器、树莓派大多没有 AES 硬件加速，ChaCha20 在纯软件实现下反而更快；一套算法通吃所有平台，正符合「每样只选一件」的哲学。你自己的 1 核 1G 云服务器也在这条逻辑里：没有加速器也不吃亏。

## 2.3 Noise_IK 握手——一次往返就开跑

密钥交换采用 Noise 协议框架（Noise Framework，Trevor Perrin 设计）中的 **IK 模式**：I 表示发起方（Initiator）已经知道响应方（Responder）的静态公钥——正是我们的场景（客户端手里攥着服务器公钥），K 表示双方静态密钥互为认证材料。

```text
发起方 A（笔记本）                    响应方 B（203.0.113.10）
     |                                     |
     |  1  握手发起包（148 字节）            |
     |  A 的临时公钥 + 加密的静态公钥        |
     | ----------------------------------->|
     |                                用 B 的私钥解出 A 的公钥
     |                                算出会话密钥
     |  2  握手应答包（92 字节）             |
     |  B 的临时公钥 + 加密的静态公钥        |
     |<------------------------------------|
     | 算出同样的会话密钥                    |
     |  3  立即开始发送加密数据              |
     | ====================================>|
```

三个值得停留的点：

- **一个来回（1-RTT）**。第 2 步结束时双方已经算出同一把会话密钥，第 3 步的数据包本身就是「密钥确认」——密钥不对，包解不开，连接等于不存在。弱网环境连隧道的体感是「瞬间」，就是这 1-RTT 的贡献。
- **静态公钥全程加密传输**。注意两包里的「加密的静态公钥」——身份信息本身就被临时密钥保护着，中间人抓包也拿不到「这是谁」的明文，身份泄露面进一步收窄。
- **包小**。握手两包合计 240 字节；后续每个数据包的头部开销也只有 32 字节级别，对比证书式方案动辄几千字节的握手，移动网络下差距可观。
- **对陌生人静默**。服务器收到无法认证的握手包时，**不回任何错误信息**——端口扫描器扫到 UDP 51820 只会看到沉默，无法确认后面跑的是 WireGuard。这同时解决了 DoS 放大问题：在判定发起方真实持有密钥之前，服务器不消耗任何昂贵的密码学计算，最多回一个让发起方证明 IP 所有权的小 cookie。

「静默」值得多说一句：这与其他 VPN 服务「先响应、再验证」的模式相反。OpenVPN 端口被扫到会回握手指纹，暴露「这里有个 VPN」；WireGuard 在被认证之前对外几乎不存在——安全与隐蔽来自同一个设计决策。

> [!NOTE]
> 防放大攻击（DoS Amplification）的完整机制是 cookie 应答：负载过高时，服务器回一个 64 字节的 cookie 包，要求发起方用它证明「报文源 IP 真实可达」后握手才继续——攻击者伪造源 IP 时收不到 cookie，打不满服务器的 CPU。这个机制对正常用户完全透明，知道存在即可。

## 2.4 会话密钥与前向保密——120 秒的重生

握手产物是会话密钥（Session Key），但 WireGuard 不让它「用一辈子」。时间轴是这样的：

```text
0s    握手完成，会话密钥 A 生效
      .......数据加密传输中（用密钥 A）.......
120s  任一方发起重新握手，会话密钥 B 生效（REKEY_AFTER_TIME）
180s  密钥 A 彻底作废，迟到的 A 加密包直接丢弃（REJECT_AFTER_TIME）
      .......循环往复.......
```

两个数字要记住：**120 秒主动换钥，180 秒旧钥作废**。换钥动作与 2.3 的握手完全相同——临时密钥（Ephemeral Key）每次握手都现生成，会话密钥由静态密钥与临时密钥多轮 ECDH 混合推导（HKDF 链式混合），推导完成立刻烧毁中间值，会话密钥用过即毁（内存中抹除）。

这就是**前向保密**（Forward Secrecy）：会话密钥与静态私钥是「混合」关系而非「派生」关系，知道今天的私钥，也倒推不出过去 120 秒里用过的会话密钥——数学上不可逆。兑现「先猜再读」第一问：私钥被拖走，攻击者拿到的是「未来冒充你的能力」，而不是「解密历史流量的能力」；昨天的抓包永远是密文。

协议里的时间常数不多，值得列成一张表——后文引用时统一以这张表为准：

| 常数 | 值 | 含义 |
| ---- | ---- | ---- |
| REKEY_AFTER_TIME | 120 秒 | 握手后经过此时长，发起方主动重协商新会话密钥 |
| REJECT_AFTER_TIME | 180 秒 | 超过此时长，旧会话密钥作废，迟到的包直接丢弃 |
| REKEY_TIMEOUT | 5 秒 | 重协商失败后等多久再试 |
| KEEPALIVE_TIMEOUT | 10 秒 | 握手后 10 秒无回包则重发握手 |
| PersistentKeepalive | 25 秒（可配置） | 用户态保活间隔，与协议常数无关，见 2.6 |

> [!TIP]
> 为什么主动限制密钥寿命，而不是「没出事就一直用」？单把密钥加密的数据量和时间窗口越小，攻击者可拿到的样本越少、被攻破后的波及面越窄。120/180 秒是 WireGuard 白皮书定死的常数，不需要也不允许你配置。

「用过即毁」还有一个常被忽略的好处：**密钥材料在内存里的存活时间极短**。传统 VPN 进程的长期会话密钥在内存里一躺几小时，冷启动攻击、内存泄露都能捞到；WireGuard 的会话密钥用完立刻从内存抹除（eraser），攻击者连「偷现成会话密钥」这条路都被堵死了。

## 2.5 Cryptokey 路由——AllowedIPs 的双重身份

第一章 1.6 留下的问题现在有了机制层面的答案。AllowedIPs 这个字段**在收发两个方向上是两个东西**：

```ini
# 服务端 wg0.conf 里的一个 Peer 段（第三章逐行解剖）
[Peer]
PublicKey = 8KxrmP...=            # 笔记本的公钥
AllowedIPs = 10.66.66.2/32        # 这个字段的双重身份
```

客户端那边对应的一段长这样：

```ini
# 笔记本 wg0.conf 里的服务端 Peer 段
[Peer]
PublicKey = k5S+1x...=                        # 服务器的公钥
AllowedIPs = 10.66.66.0/24                    # 目的地是 VPN 网段就走隧道
Endpoint = 203.0.113.10:51820                 # 服务器的公网地址（外层）
PersistentKeepalive = 25                      # NAT 保活（2.6 讲原理）
```

两段对照着读，双重身份更直观：服务端那句 `10.66.66.2/32` 是白名单——「公钥 8KxrmP 的持有者只许用 .2 这个源地址」；客户端那句 `10.66.66.0/24` 是路由表——「目的地 10.66.66.x 的包塞进隧道」。同一个字段名，方向相反、语义相反。

- **发包方向：路由表**。内核要发一个包，先查「目标 IP 命中哪个 Peer 的 AllowedIPs」——命中就交给该 Peer 的隧道加密发出。客户端 `AllowedIPs = 10.66.66.0/24` 意思是「目的地 10.66.66.x 的包全塞进隧道」。
- **收包方向：白名单**。收到一个解密后的包，内核检查「源 IP 是否在该 Peer 的 AllowedIPs 内」——不在就**静默丢弃**。

| 视角 | AllowedIPs 的身份 | 配错的后果 |
| ---- | ---- | ---- |
| 客户端 | 我愿意把哪些目的地的包送进隧道 | 配太窄：该走隧道的流量继续走公网，「部分可达」 |
| 服务端 | 这个 Peer 发来的包允许带什么源 IP | 配错网段：对端的包被静默丢弃，「看起来连上了却 ping 不通」 |

兑现「先猜再读」第三问：服务器确认「包来自那台笔记本」，靠的**不是 IP、不是账号，而是密钥**——能通过 2.3 握手认证的才是那把公钥的持有者；AllowedIPs 再收紧「持有者只能用声明的源地址」。密钥认证身份、AllowedIPs 圈定权力，两层合起来叫加密密钥路由（Cryptokey Routing）——路由表与防火墙规则在内核里合二为一，这也是为什么本书几乎不需要为隧道本身写防火墙规则。

特例预告：客户端把 AllowedIPs 配成 `0.0.0.0/0`（全隧道模式）时，`wg-quick` 会有特殊处理（策略路由），普通「小网段」配置反而绕开这套机制——第四章 4.2 专门拆这两种写法。

最后一个设计层面的观察：这套机制把「路由」与「准入」焊死在了一起。传统方案里，路由表决定包去哪、防火墙决定包能不能过，两张表由两个系统维护、时常打架；WireGuard 里 AllowedIPs 一张表同时回答两个问题。副作用是：**改路由就等于改权限**，第五章的脚本在「发放客户端」时改的就是这一行——改动小，责任大。

## 2.6 漫游与保活——端点更新与 25 秒心跳

第一个机制是**端点漫游**（Roaming）：客户端配置里写了服务器的 Endpoint（203.0.113.10:51820），但客户端自己的地址不写死——服务器只信「能通过密钥认证的包」，并且**自动更新该 Peer 的 Endpoint 为最后一个合法包的来源地址**。手机从 Wi-Fi 切到 4G，源 IP 变了，下一个包一到，服务器的记录就跟着更新，隧道无缝续上。这解释了第四章会体验到的「合盖半小时、开盖秒恢复」。

漫游的判定标准依然是密钥而非地址——合法包从哪个地址来，哪个地址就是对端。这带来两个推论：

- 配置里的 Endpoint 其实只是「起点提示」：告诉客户端先往哪里发包；一旦流量开始，双方地址都是自动跟随的；
- 安全上没有新增风险：地址虽然随便换，但每一包都要通过会话密钥认证，换了地址不换密钥照样进不来。

第二个机制是**保活**（Keepalive），处理一个不起眼却致命的问题：客户端多在 NAT（Network Address Translation，网络地址转换）网络里——咖啡馆路由器、手机基站都会为这条 UDP 流建立映射表项，而**映射项有超时**（各家 30 秒到几分钟不等）。超时内不发包，映射被回收，服务器的包就再也进不来——客户端不发起新流量时隧道「单向假死」，正是隧道最常见的疑难杂症。

解法是 `PersistentKeepalive`：客户端每隔 25 秒向服务器发一个极小的保活包，把 NAT 映射续住。选 25 秒的理由：小于常见 NAT 的最短超时（30 秒量级），开销又小到可以忽略（每 25 秒几十字节）。

两个容易混淆的「保活」就此分清：2.4 表里的 `KEEPALIVE_TIMEOUT`（10 秒）是协议自己的握手保活——重发握手包用的；而 `PersistentKeepalive` 是为了续 NAT 映射、写给 NAT 设备看的。前者协议管，后者你配。排查「隧道时通时不通」时先想到后者。

| 场景 | 要不要配 PersistentKeepalive = 25 |
| ---- | ---- |
| 手机 / 笔记本在 NAT 网络里连公网服务器 | **要**，几乎所有真实场景都属于这类 |
| 服务器之间有公网 IP 直连 | 不用，密钥握手本身会按需发起 |
| 两端都在 NAT 后、无公网侧 | WireGuard 不直接支持，需打洞或中转（第六章 6.3 顺带一提） |

记住原则：**谁在 NAT 后，谁配保活**。本书主线场景里，笔记本、手机、NAS 全是 NAT 后的客户端，所以第四章的每份客户端配置都会带上这一行。反过来，第三章的服务器有公网 IP、不在任何 NAT 后面，服务端配置里就不需要它——一个字段该出现在哪一侧，从此有了判断依据。

## 2.7 与 OpenVPN、IPsec 对比——选型数据

原理讲完，把三大主流方案放进一张表（协议层细节站内[《网络协议完全教程》第二十二章](/network-protocol/ch22)有更完整的展开）：

| 维度 | WireGuard | OpenVPN | IPsec/IKEv2 |
| ---- | ---- | ---- | ---- |
| 代码量 | 约 4 千行（内核内） | 十万行量级（含 OpenSSL） | 数万行（内核栈 + strongSwan 等） |
| 运行位置 | 内核态 | 用户态 | 内核态（ESP） |
| 握手 | 1-RTT，240 字节 | TLS 式多轮，数 KB | IKE 多消息交换 |
| 算法协商 | 不协商，套件定死 | TLS 协商 | IKE 协商 |
| 证书体系 | 无，仅密钥对 | 可选证书/账号 | 证书为主 |
| 配置面 | 一张 conf 文件 | 一堆 conf + 证书链 | 策略 + SPD/SAD + 证书 |
| 典型吞吐 | 接近裸网卡（数倍于用户态方案） | 中等 | 高 |
| 客户端生态 | 全平台官方 App | 全平台开源客户端 | 系统内置（IKEv2） |

本书的选型结论一句话说清：**远程接入、自建、长期用——选 WireGuard**；需要兼容不支持 WireGuard 的老设备、或必须借 TCP 443 穿墙越坝时，OpenVPN 作为补充（第六章 6.5 给出对照配置）。IPsec 性能也优秀，但配置复杂度对个人与小型团队不友好，不作为本书选项。

表格里的「配置面」一行值得单独强调：OpenVPN 的 conf 要伺候协议、证书、压缩、路由一长串参数，IPsec 还要理解 SPD/SAD 这类内核策略概念；WireGuard 的全部配置就是一张几十行的 conf 文件——这不是省事，而是 2.2「不协商」哲学的自然结果。可配置项越少，可以配错的地方就越少；第三章你会亲眼看这张 conf 有多小。

## 本章小结

- 快的两个来源：加解密在内核态完成（省用户态往返），核心仅四千行（省审计面与包开销）；
- 密码学套件不协商——Curve25519 + ChaCha20-Poly1305 + BLAKE2s 各一件，消灭降级攻击面，配置文件里因此没有任何算法参数；
- Noise_IK 握手 1-RTT 完成，240 字节换完密钥，数据包自带密钥确认；
- 对未认证的包静默不响应——扫描器探不到、DoS 放大无处着力，安全与隐蔽同源；
- 会话密钥 120 秒重协商、180 秒作废，静态私钥泄露也解不开历史流量（前向保密）；
- AllowedIPs 双重身份：发包方向是路由表，收包方向是白名单——「路由即安全」；
- 端点随合法包自动更新，漫游零配置；NAT 后的客户端配 `PersistentKeepalive = 25` 防映射回收；
- WireGuard 只说 UDP——没有 TCP 模式，这是 UDP 被封环境连不上的根源（第六章选型与第八章链式代理的两处伏笔）；
- 选型口径：自建远程接入选 WireGuard，兼容性与 TCP 穿透场景补 OpenVPN。

原理篇到此收束。本书后续不会再用「因为协议如此」来解释任何现象——所有配置行为都能回到本章：密钥（2.2）、握手（2.3）、换钥（2.4）、AllowedIPs（2.5）、保活（2.6）。带着这五把钥匙进入实操篇。
