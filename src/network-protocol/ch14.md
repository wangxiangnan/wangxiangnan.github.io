## 14.1 HTTP 缓存：强缓存与协商缓存

HTTP 缓存是 Web 性能优化中最有效的手段之一。道理很简单：浏览器本地若有一份未过期的资源副本，就没必要再走一遍网络——省下的不仅是带宽，还有一整个 RTT。

缓存分两种策略：

**强缓存（Freshness）**：浏览器自己判断副本是否「新鲜」，根本不发请求。

- `Expires`：HTTP/1.0 的产物，指定绝对过期时间，如 `Expires: Thu, 18 Jan 2024 12:00:00 GMT`。问题很明显——依赖客户端与服务器时钟同步，客户端时间被改了判断就出错。
- `Cache-Control`：HTTP/1.1 的替代者，相对时间、指令丰富：
  - `max-age=3600`：响应生成起 3600 秒内有效（不怕时钟漂移）。
  - `no-cache`：「先猜再读」第一问的答案——**不是不缓存，是不信任本地缓存**：可以存，但每次使用前必须向服务器验证。
  - `no-store`：完全不存，敏感数据用它。
  - `public` / `private`：允许/禁止中间节点（CDN、代理）缓存。
  - `immutable`：资源永不变化（带哈希文件名的打包产物专用）。

**协商缓存（Validation）**：浏览器不确定是否还新鲜，发一个请求去问服务器：「我这版本还是最新的吗？」

- `Last-Modified` / `If-Modified-Since`：基于最后修改时间。没变则服务器回 `304 Not Modified`，无消息体。
- `ETag` / `If-None-Match`：基于内容「指纹」（通常是哈希）。「先猜再读」第二问的答案：`Last-Modified` 精度只有秒，且只看时间戳——文件被改回原样它也不知道；ETag 基于内容，内容没变指纹就不变，所以更可靠。

一次完整的协商流程：

```
第一次请求：
GET /style.css HTTP/1.1
Host: www.example.com

响应：
HTTP/1.1 200 OK
Content-Type: text/css
Content-Length: 8234
Last-Modified: Fri, 12 Jan 2024 10:00:00 GMT
ETag: "a3f2b8c"
Cache-Control: max-age=0

第二次请求（协商缓存）：
GET /style.css HTTP/1.1
Host: www.example.com
If-Modified-Since: Fri, 12 Jan 2024 10:00:00 GMT
If-None-Match: "a3f2b8c"

响应：
HTTP/1.1 304 Not Modified
ETag: "a3f2b8c"
```

304 响应没有消息体，浏览器直接用本地副本——13.4 说过 304 只是状态码语义，这里的 `If-*` 头部才是它的配套机制。用几百字节的往返，验证了几 MB 的资源没变。

> [!TIP] 用 DevTools 直接观察缓存命中
> 浏览器开发者工具的 Network 面板里刷新页面：Size 列显示 `(disk cache)` / `(memory cache)` 是强缓存命中，显示 `304` 是协商缓存命中——不用抓包就能区分两种策略。

## 14.2 缓存策略的工程权衡

为什么不能把所有东西都缓存到天荒地老？因为**一致性**：服务器更新了页面，用户看到的还是旧版本——缓存就从优化变成了 Bug。

工程中的典型策略：

- **HTML 页面**：`Cache-Control: no-cache`——每次验证，确保最新。
- **带哈希的静态资源**（`app.a3f2b8c.js`）：`max-age=31536000, immutable`——内容变了文件名就变，放心缓存一年。这是现代前端的「指纹命名法」：把一致性难题转化为「换 URL」。
- **API 响应**：`no-store` 或 `private, no-cache`——动态数据通常不该缓存。
- **图片和视频**：适度缓存，如 `max-age=86400`。

「新鲜度（Freshness）」是核心概念：`max-age` 时间内响应是「新鲜的」，可直接使用；过期后变「陈旧的（Stale）」，必须重新验证——两种缓存的分界线就在这里。

## 14.3 内容协商：一个 URL 多副面孔

同一个 URL，不同客户端想要不同内容：手机要移动版页面、法国用户要法语内容、新浏览器要 WebP 而旧的只能要 JPEG。HTTP 用**内容协商**解决这个问题。

客户端通过请求头部声明偏好：

```http
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Accept-Encoding: gzip, deflate, br
```

`q` 值是权重（0~1，默认 1）：上面表示最想要 `text/html`，`application/xml` 次之（0.9），`*/*` 兜底（0.8）。

服务器选择后用响应头部说明「我给了你什么」：

```http
Content-Type: text/html; charset=UTF-8
Content-Language: zh-CN
Content-Encoding: gzip
Vary: Accept, Accept-Language, Accept-Encoding
```

`Vary` 是给缓存系统的指令：同一个 URL，这些头部不同就可能得到不同响应——缓存时必须按这些头部的组合分别存副本。没有 `Vary`，缓存可能把 gzip 版本发给不支持压缩的客户端。第23章讲 CDN 时会再次遇到它：CDN 节点缓存的命中率高度依赖 `Vary` 的设计。

## 14.4 压缩传输：拿 CPU 换流量

文本资源（HTML/CSS/JS/JSON）压缩后体积常常只剩三成。主流算法：

- **gzip**：最古老最广泛，几乎所有浏览器和服务器都支持，压缩率中等。
- **deflate**：zlib 实现的压缩格式，比 gzip 略小但历史兼容性问题多一些。
- **br（Brotli）**：Google 的现代算法，对文本类比 gzip 再省 15-25%；浏览器只在 HTTPS 连接上启用——这也是「HTTPS 不仅安全还更快」的一个注脚，机制见第15章。

协商过程你在 14.3 已经见过：请求 `Accept-Encoding: gzip, br`，响应 `Content-Encoding: gzip`。

一个常见误区：压缩只对文本类资源有效。图片和视频本身已是压缩格式（JPEG/WebP/H.264），再压一遍不会更小，纯浪费 CPU——正确做法是为图片选更合适的格式与质量参数。

## 14.5 Cookie 与 Session：无状态之上的身份

13.5 留下的承诺在这里兑现：无状态是天性，登录态是补丁。补丁的完整机制如下。

**Cookie 的工作流程**：

1. 服务器在响应中设置：

```http
Set-Cookie: session_id=abc123; Path=/; Domain=.example.com; HttpOnly; Secure; SameSite=Lax
```

2. 浏览器存储它，后续所有匹配 `Domain` 和 `Path` 的请求自动附带：

```http
Cookie: session_id=abc123
```

**Set-Cookie 的关键属性**：

- **Domain**：对哪些域名有效。`.example.com` 让所有子域名都能读；不设置则默认当前域名（不含子域名）。
- **Path**：对哪些路径有效。`Path=/` 全站可读，`Path=/api` 只有 `/api` 开头的请求会带上。
- **HttpOnly**：禁止 JavaScript 通过 `document.cookie` 读取——防 XSS 窃取身份的第一道闸，Session ID 必须设置。
- **Secure**：只经 HTTPS 传输。
- **SameSite**：控制跨站请求是否携带，防 CSRF（跨站请求伪造）：
  - `Strict`：任何跨站请求都不带。
  - `Lax`（现代默认）：点击链接的顶级导航携带，跨站 AJAX 不带。
  - `None`：全带，但必须同时设 `Secure`。

**Session 的实现**：Cookie 里只放一个 `session_id`，真正的用户数据在服务器端（内存、数据库、Redis）。经典分工——客户端轻量，服务端掌控。「先猜再读」第三问的答案：Session 把状态存在**服务器**；而 **JWT（JSON Web Token）**把状态放在**客户端**——一个经签名的 JSON 对象，自带用户信息与过期时间，服务器什么都不存。

两种方案各有代价：

| 维度 | Session | JWT |
| ------ | ------- | --- |
| 状态存储 | 服务器端（要共享存储） | 客户端（令牌自带） |
| 水平扩展 | 需要共享 Session 存储 | 天然无状态，多机友好 |
| 主动撤销 | 删掉服务端记录即可 | 签发后难以撤销，只能等过期 |
| 典型场景 | 传统 Web 应用 | 开放 API、微服务间认证 |

Cookie 承载 Session ID 只是身份管理的一种载体；HTTP 头部里的 `Authorization: Bearer <token>` 是另一种（JWT 常配它）。安全攻防（XSS/CSRF 的完整攻防、HTTPS 为什么能保护 Cookie）属于第15章和第22章的地盘，本章只管机制本身。

## 14.6 编程实践：用 Python requests 演示缓存行为

```python
import requests

def demo_cache():
    """演示 HTTP 缓存行为"""
    session = requests.Session()

    # 目标 URL - 使用 httpbin 的缓存接口
    url = "https://httpbin.org/cache/60"  # 服务器设置 max-age=60

    print("=== 第一次请求 ===")
    resp1 = session.get(url)
    print(f"Status: {resp1.status_code}")
    print(f"Cache-Control: {resp1.headers.get('Cache-Control')}")
    print(f"Date: {resp1.headers.get('Date')}")
    print(f"Body length: {len(resp1.content)} bytes")

    print("=== 第二次请求 ===")
    print("注意：requests 默认不做客户端缓存，仍会完整请求——")
    print("缓存是浏览器（客户端）的自觉行为，不是服务器强制的。")
    resp2 = session.get(url)
    print(f"Status: {resp2.status_code}")

    # 手动实现条件请求
    print("=== 手动发送条件请求（If-None-Match） ===")
    etag = resp1.headers.get('ETag')
    if etag:
        print(f"Using ETag: {etag}")
        resp3 = session.get(url, headers={'If-None-Match': etag})
        print(f"Status: {resp3.status_code}")  # 304
        print(f"Body length: {len(resp3.content)} bytes")  # 0

    print("=== 请求 no-cache 资源 ===")
    url_nocache = "https://httpbin.org/response-headers?Cache-Control=no-cache"
    resp4 = session.get(url_nocache)
    print(f"Cache-Control: {resp4.headers.get('Cache-Control')}")
    print("no-cache 的响应仍可存储，但每次使用前必须验证。")

demo_cache()
```

这个脚本揭示了一个容易被忽略的事实：**缓存是客户端的自觉，不是服务器的强制**。requests 库懒得实现缓存，所以同样的请求发了两次都是 200；浏览器则忠实地实现了整套 RFC 缓存规范。手动带上 `If-None-Match` 后才能看到 304——协议机制就在那里，用不用是客户端的事。

## 14.7 抓包实践：观察浏览器如何利用 304 Not Modified

打开 Wireshark 过滤 `http`，在浏览器中访问一个访问过的网站，会看到大量 304：

```
请求：
GET /static/css/main.css HTTP/1.1
Host: blog.example.com
If-None-Match: "7d2-5c8a3f1e2b400"
If-Modified-Since: Thu, 11 Jan 2024 08:20:00 GMT

响应：
HTTP/1.1 304 Not Modified
ETag: "7d2-5c8a3f1e2b400"
Date: Mon, 15 Jan 2024 09:00:00 GMT
Connection: keep-alive
```

注意 304 响应没有 `Content-Length` 和消息体——浏览器直接使用本地副本。一个含大量静态资源的页面，若缓存策略合理，二次访问时大部分请求命中 304 或强缓存，网络传输量可以从几 MB 降到几 KB。

Wireshark 的 `Statistics > HTTP` 面板提供按状态码分类的统计：优化良好的网站，304 与 200 的比例可能接近 1:1。若想观察强缓存命中，Wireshark 反而看不到——强缓存压根不发请求，这正是 14.6 TIP 里 DevTools 的用武之地：抓包看协商缓存，面板看强缓存。

## 本章小结

- 缓存两策略：强缓存（`max-age` 内根本不发请求）与协商缓存（带 `If-*` 头部问一句，304 则用本地副本）。
- `no-cache` ≠ 不缓存：可以存，但每次使用前必须验证；真不缓存的是 `no-store`。
- 时间戳会骗人（秒级精度、改回原样不知情），ETag 内容指纹更可靠——但两者常常搭配使用。
- 现代缓存设计的关键一手是「指纹命名」：内容哈希进文件名 + `immutable`，把一致性难题变成换 URL。
- 内容协商靠 `Accept-*` 头部的 q 权重，服务器的选择记在 `Content-*` 里，`Vary` 告诉缓存按头部组合分别存。
- 压缩只对文本有效，图片视频再压是浪费 CPU；Brotli 只在 HTTPS 上启用——安全协议反而更快。
- Cookie/Session 把状态放服务端（可撤销、需共享存储），JWT 把状态放客户端（无状态扩展、难撤销）——按场景选。
- 缓存是客户端的自觉而非服务器强制：requests 不缓存，浏览器忠实实现——机制写在协议里，用不用看实现。

**下一章预告**：`Secure` 属性让 Cookie 只走 HTTPS，Brotli 只在 HTTPS 上启用——「安全连接」反复露脸，但它究竟怎么保证安全？下一章拆开 HTTPS 的外壳，讲 TLS 1.3 的握手、加密体系与证书信任链。
