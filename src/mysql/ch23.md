# 第23章 性能调优与Node.js实战

你买了一辆跑车，但如果只在小区里以20km/h的速度开，那跟骑自行车有什么区别？MySQL 也一样——默认配置是为"通用场景"设计的，就像跑车的"经济模式"。要发挥全部性能，你需要学会"踩油门"和"换挡"。这一章，我们就来学习如何让 MySQL 真正跑起来，并且用 Node.js 把它接入到你的应用中。

## 23.1 慢查询日志

慢查询日志是性能优化的起点——找到慢查询，才知道该优化什么。很多开发者在性能问题上犯的最大错误是"凭感觉优化"——花了好几天优化一个其实只需要 50 毫秒的查询，而真正需要优化的那个 5 秒的查询却被忽略了。慢查询日志让你用数据说话，而不是靠猜。

需要注意的是，开启慢查询日志会带来一定的性能开销（通常 1-3%），因为 MySQL 需要为每个超过阈值的查询记录详细的执行信息。在高并发的生产环境中，慢查询日志文件可能增长得非常快——如果每秒有 10 个慢查询，每个记录 500 字节，一天就是 432MB。所以一定要配合日志轮转（log rotation）策略，定期归档和清理旧的日志文件，防止磁盘被撑爆。

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;         -- 超过1秒的查询记录下来
SET GLOBAL log_queries_not_using_indexes = ON;  -- 没用索引的查询也记录

-- 查看慢查询日志路径
SHOW VARIABLES LIKE 'slow_query_log_file';

-- 查看当前慢查询数量
SHOW GLOBAL STATUS LIKE 'Slow_queries';
```

**分析慢查询日志：**

```sql
-- 使用 mysqldumpslow 工具分析
-- mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
-- -s t: 按总耗时排序
-- -t 10: 只看前10条

-- 输出示例：
-- Count: 1523  Time=2.34s (3563s)  Lock=0.00s (0s)
-- SELECT * FROM orders WHERE user_id=12345 AND status='pending'
```

> [!TIP] 提示
> 在开发环境中，可以把 `long_query_time` 设低一点（比如 0.1 秒），更容易发现潜在的性能问题。

## 23.2 Performance Schema 与 sys 库

Performance Schema 是 MySQL 内置的性能诊断引擎，它在服务器运行时收集各种性能指标数据，包括 SQL 执行时间、锁等待、IO 操作、网络流量等。你可以把它想象成一个安装在 MySQL 内部的"行车记录仪"——它默默记录着一切发生的事情，等你需要排查问题时，这些记录就是最宝贵的线索。

不过 Performance Schema 的原始数据表非常多（超过 100 张），而且表结构复杂，直接查询不太友好。这就是 `sys` 库的价值所在——它是 Performance Schema 的一层友好封装，把复杂的原始数据转化为更易读的视图。就好比汽车仪表盘把发动机的各种传感器数据转化为速度、转速、油量这些你能看懂的数字。

使用 Performance Schema 会有一定的性能开销（通常在 5-10% 之间），但在生产环境中这个开销通常是值得的。如果你发现某些采集项确实影响了性能，可以选择性地关闭特定的 instrument（采集器）或 consumer（消费者）。

```sql
-- Performance Schema 是 MySQL 内置的性能诊断工具
-- sys 库是对 Performance Schema 的友好封装

-- 查看消耗资源最多的 SQL
SELECT * FROM sys.statements_with_runtimes_in_95th_percentile LIMIT 10;

-- 查看哪些表在做全表扫描
SELECT * FROM sys.tables_with_full_table_scans;

-- 查看等待事件排名（找瓶颈）
SELECT * FROM sys.waits_global_by_latency LIMIT 10;

-- 查看冗余索引
SELECT * FROM sys.redundant_indexes;

-- 查看未使用的索引
SELECT * FROM sys.unused_indexes;
```

**实战诊断流程：**

```sql
-- Step 1: 查看当前运行的查询
SELECT * FROM sys.processlist WHERE command != 'Sleep';

-- Step 2: 查看某个查询的执行详情
SELECT * FROM sys.statement_analysis 
WHERE digest_text LIKE '%orders%' 
ORDER BY total_latency DESC;

-- Step 3: 查看 InnoDB 缓冲池命中率
SELECT * FROM sys.innodb_buffer_stats_by_schema;
```

## 23.3 EXPLAIN ANALYZE

MySQL 8.0.18 引入了 `EXPLAIN ANALYZE`，它不仅显示执行计划，还会实际执行查询并显示每一步的真实耗时。

```sql
-- 传统 EXPLAIN：只看计划，不执行
EXPLAIN SELECT * FROM orders WHERE user_id = 123;

-- EXPLAIN ANALYZE：执行并显示真实耗时
EXPLAIN ANALYZE 
SELECT o.*, u.name 
FROM orders o 
JOIN users u ON o.user_id = u.id 
WHERE o.status = 'shipped' AND o.create_time > '2024-01-01';

-- 输出示例（树形结构）：
-- -> Nested loop inner join  (cost=1234.56 rows=567)
--      (actual time=2.345..45.678 rows=1234 loops=1)
--    -> Index lookup on o using idx_status (status='shipped')
--         (cost=456.78 rows=890)
--         (actual time=1.234..12.345 rows=2345 loops=1)
--    -> Single-row index lookup on u using PRIMARY (id=o.user_id)
--         (cost=0.25 rows=1)
--         (actual time=0.012..0.013 rows=1 loops=2345)
```

> [!TIP] 提示
> `EXPLAIN ANALYZE` 中的 `actual time` 和 `rows` 比传统 EXPLAIN 的估算值更可靠。优化查询时以实际执行数据为准。

**读懂传统 EXPLAIN 的关键字段：**

EXPLAIN 的输出有十几个字段，但真正需要重点关注的是以下几个：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123 AND status = 'pending'\G

-- 重点字段解读：
-- type: 访问类型，从好到坏排序：
--   system > const > eq_ref > ref > range > index > ALL
--   ALL = 全表扫描（最差的，需要优化）
--   ref = 使用了索引的等值查询（不错）
--   range = 使用了索引的范围查询（还行）
--   index = 全索引扫描（比全表扫描好一点）

-- possible_keys: 可能使用的索引
-- key: 实际使用的索引（NULL表示没用到索引）
-- key_len: 使用的索引长度（字节），越长说明用的索引列越多
-- rows: 预估需要扫描的行数（越小越好）
-- filtered: 经过条件过滤后剩余的行比例
-- Extra: 额外信息，重点关注以下几种：
--   Using index: 使用了覆盖索引（非常好）
--   Using filesort: 需要额外排序（可能很慢）
--   Using temporary: 使用了临时表（通常很慢）
--   Using where: 在存储引擎返回后还需要进行过滤
```

**EXPLAIN 的 type 字段是优化的指南针：**

如果你看到 `type = ALL`，意味着 MySQL 在做全表扫描。对于大表来说，这几乎等于灾难。你需要检查 WHERE 条件是否有合适的索引。如果看到 `type = ref` 或 `type = range`，说明索引被正确使用了。看到 `type = const` 意味着通过主键或唯一索引直接定位到一行，这是最理想的情况。

```sql
-- 对比不同查询的执行计划
-- 差：全表扫描
EXPLAIN SELECT * FROM orders WHERE DATE_FORMAT(create_time, '%Y-%m') = '2024-01';
-- type: ALL, rows: 5000000 (扫500万行)

-- 好：索引范围扫描
EXPLAIN SELECT * FROM orders WHERE create_time >= '2024-01-01' AND create_time < '2024-02-01';
-- type: range, key: idx_create_time, rows: 85000 (只扫8.5万行)
```

## 23.4 查询优化技巧

**索引优化：**

```sql
-- 联合索引遵循最左前缀原则
-- 索引 (a, b, c) 可以用于查询：
-- WHERE a = 1              ✓
-- WHERE a = 1 AND b = 2    ✓
-- WHERE a = 1 AND b = 2 AND c = 3  ✓
-- WHERE b = 2              ✗（缺少最左列）
-- WHERE a = 1 AND c = 3    ✓（用到 a，c 不走索引）

-- 覆盖索引：查询的列全在索引中，不需要回表
-- 索引 (status, user_id)
SELECT user_id FROM orders WHERE status = 'pending';  -- 覆盖索引，极快

-- 避免索引失效的常见陷阱
SELECT * FROM users WHERE YEAR(create_time) = 2024;  -- 索引失效！
SELECT * FROM users WHERE create_time >= '2024-01-01' 
  AND create_time < '2025-01-01';  -- 索引生效

SELECT * FROM users WHERE name LIKE '%张';  -- 前缀模糊，索引失效
SELECT * FROM users WHERE name LIKE '张%';  -- 前缀匹配，索引生效
```

**查询改写：**

查询改写是性能优化中最有成就感的工作——有时候仅仅改写一条 SQL，就能让响应时间从几秒降到几毫秒。核心原则是：让 MySQL 尽量少扫描数据、尽量利用索引、尽量避免临时表和文件排序。

```sql
-- 优化前：子查询（可能很慢）
SELECT * FROM users WHERE id IN (
  SELECT user_id FROM orders WHERE amount > 1000
);

-- 优化后：JOIN
SELECT DISTINCT u.* 
FROM users u 
INNER JOIN orders o ON u.id = o.user_id 
WHERE o.amount > 1000;

-- 优化前：分页偏移量大时很慢
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;

-- 优化后：延迟关联（先查ID，再回表）
SELECT o.* FROM orders o
INNER JOIN (
  SELECT id FROM orders ORDER BY id LIMIT 100000, 10
) AS t ON o.id = t.id;

-- 或者使用游标分页（推荐）
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 10;

-- 优化前：COUNT(*) 大表计数
SELECT COUNT(*) FROM orders WHERE status = 'completed';
-- 对于数百万行的大表，即使用到索引也需要扫描大量数据

-- 优化后：维护一个计数表，通过触发器或定时任务更新
CREATE TABLE table_counts (
  table_name VARCHAR(64) PRIMARY KEY,
  condition_key VARCHAR(64),
  count_value BIGINT,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 优化前：OR 条件导致索引失效
SELECT * FROM users WHERE name = '张三' OR email = 'zhangsan@test.com';
-- 如果 name 和 email 没有联合索引，MySQL 可能做全表扫描

-- 优化后：UNION ALL
SELECT * FROM users WHERE name = '张三'
UNION ALL
SELECT * FROM users WHERE email = 'zhangsan@test.com';
```

> [!TIP] 提示
> 每次改写查询后，务必用 EXPLAIN 和 EXPLAIN ANALYZE 验证优化效果。有时候你"以为更好"的写法，实际上可能更慢——数据库优化器的行为不总是符合直觉。

## 23.5 服务器参数调优

MySQL 的默认配置是为"最小化资源占用"设计的，目的是让它在任何机器上都能跑起来——哪怕是一台只有 512MB 内存的小机器。这意味着在生产环境中，默认配置往往远未达到最优。参数调优的核心思路是：根据你的硬件配置和业务特点，让 MySQL 充分利用系统资源。

调优之前，你需要先回答几个问题：你的服务器有多少内存？是 SSD 还是机械硬盘？业务是读多写少还是写多读少？并发连接数大概是多少？这些答案会直接影响参数的选择。

参数调优有一个基本原则：每次只改一个参数，改完后跑一段时间观察效果，然后再改下一个。一次性改太多参数，出了问题你根本不知道是哪个参数导致的。同时，每次修改都要记录下来，形成一个"调优日志"，方便回退和团队知识共享。

```sql
-- 查看当前配置
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- InnoDB 缓冲池：最重要的参数
-- 建议设为物理内存的 70-80%
SET GLOBAL innodb_buffer_pool_size = 8 * 1024 * 1024 * 1024; -- 8GB

-- 最大连接数
-- 根据应用实际并发调整，不要设太大
SET GLOBAL max_connections = 500;

-- 缓冲池实例数（减少锁竞争）
-- 建议设为 CPU 核心数，最大 64
-- innodb_buffer_pool_instances = 8  (需要重启)

-- InnoDB 日志文件大小
-- 越大 = checkpoint 越少 = 写入越快，但恢复越慢
-- innodb_log_file_size = 1G  (需要重启)

-- 刷盘策略
-- 1 = 每次提交都刷盘（最安全，默认）
-- 2 = 每次提交写OS缓存，每秒刷盘（高性能，可能丢1秒数据）
SET GLOBAL innodb_flush_log_at_trx_commit = 1;

-- IO 容量（SSD vs HDD）
SET GLOBAL innodb_io_capacity = 2000;       -- SSD 推荐 2000+
SET GLOBAL innodb_io_capacity_max = 4000;   -- SSD 推荐 4000+
```

> [!WARNING] 注意
> `query_cache`（查询缓存）在 MySQL 8.0 中已被完全移除。在高并发写入场景下，查询缓存反而会降低性能（每次写操作都要失效缓存）。不要再尝试配置它了。

**配置模板（8核16GB服务器）：**

```sql
[mysqld]
# 连接配置
max_connections = 500
max_connect_errors = 1000

# InnoDB 核心配置
innodb_buffer_pool_size = 12G
innodb_buffer_pool_instances = 8
innodb_log_file_size = 1G
innodb_flush_log_at_trx_commit = 1
innodb_io_capacity = 2000
innodb_io_capacity_max = 4000
innodb_flush_method = O_DIRECT

# 日志配置
slow_query_log = 1
long_query_time = 1
log_queries_not_using_indexes = 1

# 二进制日志
binlog_format = ROW
expire_logs_days = 7
sync_binlog = 1
```

## 23.6 生产环境监控与告警

性能调优不是一次性的工作，而是需要持续监控和调整。一个没有监控的 MySQL 实例，就像一辆没有仪表盘的跑车——你不知道油还剩多少、水温是否正常、发动机有没有过热。

**核心监控指标：**

```sql
-- 1. 连接数监控
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Max_used_connections';
SHOW VARIABLES LIKE 'max_connections';

-- 连接使用率 = Threads_connected / max_connections
-- 当使用率超过 80% 时需要告警

-- 2. InnoDB 缓冲池命中率
SELECT 
  (1 - (SELECT variable_value FROM performance_schema.global_status 
        WHERE variable_name = 'Innodb_buffer_pool_reads')
  / (SELECT variable_value FROM performance_schema.global_status 
     WHERE variable_name = 'Innodb_buffer_pool_read_requests')) * 100 
  AS buffer_pool_hit_rate;
-- 命中率低于 99% 说明缓冲池可能太小

-- 3. 临时表使用情况
SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables';
SHOW GLOBAL STATUS LIKE 'Created_tmp_tables';
-- 磁盘临时表比例高说明 tmp_table_size 可能太小

-- 4. 锁等待监控
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock%';
-- Innodb_row_lock_waits 高说明锁竞争严重

-- 5. 复制延迟监控（从库）
SHOW SLAVE STATUS\G
-- 关注 Seconds_Behind_Master
```

**用 Node.js 构建简单的监控服务：**

```javascript
const mysql = require('mysql2/promise');

class MySQLMonitor {
  constructor(pool, alertThresholds) {
    this.pool = pool;
    this.thresholds = {
      connectionUsagePercent: 80,  // 连接使用率告警阈值
      bufferPoolHitRate: 99,       // 缓冲池命中率告警阈值
      slowQueryCount: 100,         // 慢查询数量告警阈值
      replicationLagSeconds: 10,   // 复制延迟告警阈值
      ...alertThresholds,
    };
  }

  async collectMetrics() {
    const [statusRows] = await this.pool.query(
      "SELECT variable_name, variable_value FROM performance_schema.global_status WHERE variable_name IN (" +
      "'Threads_connected','Max_used_connections','Slow_queries'," +
      "'Innodb_buffer_pool_reads','Innodb_buffer_pool_read_requests'," +
      "'Innodb_row_lock_waits','Innodb_row_lock_time_avg')"
    );

    const metrics = {};
    statusRows.forEach(row => {
      metrics[row.variable_name] = parseInt(row.variable_value);
    });

    const [maxConn] = await this.pool.query(
      "SELECT @@max_connections AS max_connections"
    );

    metrics.max_connections = maxConn[0].max_connections;
    metrics.connection_usage_percent = 
      (metrics.Threads_connected / metrics.max_connections * 100).toFixed(1);
    metrics.buffer_pool_hit_rate = 
      ((1 - metrics.Innodb_buffer_pool_reads / metrics.Innodb_buffer_pool_read_requests) * 100).toFixed(2);

    return metrics;
  }

  async checkAlerts(metrics) {
    const alerts = [];

    if (parseFloat(metrics.connection_usage_percent) > this.thresholds.connectionUsagePercent) {
      alerts.push({
        level: 'WARNING',
        message: `Connection usage at ${metrics.connection_usage_percent}%`,
        metric: 'connection_usage_percent',
        value: metrics.connection_usage_percent,
      });
    }

    if (parseFloat(metrics.buffer_pool_hit_rate) < this.thresholds.bufferPoolHitRate) {
      alerts.push({
        level: 'CRITICAL',
        message: `Buffer pool hit rate dropped to ${metrics.buffer_pool_hit_rate}%`,
        metric: 'buffer_pool_hit_rate',
        value: metrics.buffer_pool_hit_rate,
      });
    }

    return alerts;
  }

  async run() {
    try {
      const metrics = await this.collectMetrics();
      const alerts = await this.checkAlerts(metrics);

      if (alerts.length > 0) {
        alerts.forEach(alert => {
          console.error(`[${alert.level}] ${alert.message}`);
          // 这里可以接入钉钉/企业微信/邮件等告警通道
        });
      } else {
        console.log('All metrics normal.');
      }

      return { metrics, alerts };
    } catch (err) {
      console.error('Monitor error:', err.message);
      return { metrics: null, alerts: [{ level: 'ERROR', message: err.message }] };
    }
  }
}

// 使用示例
// const monitor = new MySQLMonitor(pool);
// setInterval(() => monitor.run(), 60000); // 每分钟检查一次
```

> [!TIP] 提示
> 监控数据最好保存到时序数据库（如 Prometheus），配合 Grafana 做可视化。这样你可以看到各项指标的历史趋势，比如缓冲池命中率是否在逐渐下降、慢查询数量是否在增长等。

## 23.7 连接池原理与配置

每次建立 MySQL 连接都需要 TCP 三次握手 + 认证，开销不小。连接池就是预先创建好一批连接，用的时候取，用完放回去。这就像一家餐厅的桌椅——如果每个客人来了都要现搬一套桌椅来，吃完再把桌椅搬走，那效率就太低了。更好的做法是提前摆好一批桌椅，客人来了直接坐，吃完走人后清理干净给下一位客人用。

连接池的内部运作比看上去复杂得多。当一个查询请求到来时，连接池首先检查是否有空闲连接可用。如果有，直接分配一个空闲连接；如果没有，且当前连接数还没达到上限（connectionLimit），就创建一个新的连接；如果连接数已经达到上限，请求就进入等待队列（如果 waitForConnections 为 true），排队等到有空闲连接释放出来。如果等待时间超过了设定的超时时间，请求就会被拒绝并抛出错误。

连接池还需要处理连接的"健康检查"。一个连接可能在空闲期间因为网络波动、服务器重启等原因而断开。好的连接池会在分配连接之前检查连接是否仍然有效，如果连接已经断开，就自动丢弃它并创建新连接。mysql2 连接池已经内置了这个机制，你不需要手动处理。

```javascript
// 不使用连接池（每次查询都新建连接，性能差）
const mysql = require('mysql2');

async function badWay() {
  const conn = mysql.createConnection({
    host: 'localhost',
    user: 'root',
    password: 'pass',
    database: 'mydb',
  });
  const [rows] = await conn.promise().query('SELECT 1');
  conn.end(); // 用完关闭，下次又要新建
  return rows;
}

// 使用连接池（推荐）
const pool = mysql.createPool({
  host: 'localhost',
  user: 'root',
  password: 'pass',
  database: 'mydb',
  waitForConnections: true,  // 连接满了就排队等待
  connectionLimit: 10,       // 最大连接数
  queueLimit: 0,             // 0 = 排队无上限
  idleTimeout: 60000,        // 空闲连接60秒后回收
  enableKeepAlive: true,     // 保持TCP连接活跃
});
```

> [!TIP] 提示
> `connectionLimit` 不是越大越好。MySQL 每个连接都会消耗内存（约 10-20MB），连接太多反而降低性能。一般 10-30 个连接足够应对大部分场景。

## 23.8 Node.js + mysql2 完整实战

终于到了最激动人心的部分——把前面所有的知识整合起来，用 Node.js 写一个完整的数据库访问层。

**安装与基础连接：**


**事务处理：**

```javascript
const pool = require('./db');

// 转账功能：经典的分布式事务场景
async function transfer(fromUserId, toUserId, amount) {
  // 从连接池获取一个连接（事务必须在同一个连接上）
  const conn = await pool.getConnection();

  try {
    // 开启事务
    await conn.beginTransaction();

    // 扣款（使用 FOR UPDATE 加行锁）
    const [fromResult] = await conn.execute(
      'SELECT balance FROM accounts WHERE user_id = ? FOR UPDATE',
      [fromUserId]
    );

    if (fromResult.length === 0 || fromResult[0].balance < amount) {
      throw new Error('Insufficient balance');
    }

    await conn.execute(
      'UPDATE accounts SET balance = balance - ? WHERE user_id = ?',
      [amount, fromUserId]
    );

    // 加款
    await conn.execute(
      'UPDATE accounts SET balance = balance + ? WHERE user_id = ?',
      [amount, toUserId]
    );

    // 记录转账日志
    await conn.execute(
      'INSERT INTO transfer_logs (from_user, to_user, amount) VALUES (?, ?, ?)',
      [fromUserId, toUserId, amount]
    );

    // 提交事务
    await conn.commit();
    console.log(`Transfer success: ${amount} from ${fromUserId} to ${toUserId}`);

  } catch (err) {
    // 出错回滚
    await conn.rollback();
    console.error('Transfer failed, rolled back:', err.message);
    throw err;
  } finally {
    // 释放连接回连接池（无论成功失败都要释放！）
    conn.release();
  }
}

// 使用示例
transfer(1, 2, 100.00)
  .then(() => console.log('Done'))
  .catch(err => console.error('Error:', err.message));
```

> [!TIP] 提示
> 事务中一定要在 `finally` 块里释放连接。如果忘记释放，连接池会被耗尽，应用会卡死。

**流式查询(Streaming)：**

当你需要从数据库读取大量数据时（比如导出报表、数据迁移、批量处理），普通查询会把所有结果一次性加载到内存中。如果查询返回 100 万行数据，每行 1KB，那就是 1GB 的内存占用——你的 Node.js 进程很可能会因为内存溢出而崩溃。流式查询就是解决这个问题的利器：它像一条水管一样，让数据一行一行地流过来，你可以边读边处理，内存中始终只保留少量数据。

```javascript
const mysql = require('mysql2');

// 当查询结果集很大时（比如100万行），用流式查询避免内存爆炸
function streamLargeQuery() {
  const connection = mysql.createConnection({
    host: 'localhost',
    user: 'root',
    password: 'pass',
    database: 'mydb',
  });

  // 使用 query 返回流
  const stream = connection.query('SELECT * FROM big_table');

  let rowCount = 0;

  stream
    .on('result', (row) => {
      // 逐行处理，不会一次性加载到内存
      rowCount++;
      processRow(row);

      // 如果处理不过来，可以暂停流
      if (rowCount % 10000 === 0) {
        connection.pause();
        setTimeout(() => connection.resume(), 100);
      }
    })
    .on('end', () => {
      console.log(`Processed ${rowCount} rows`);
      connection.end();
    })
    .on('error', (err) => {
      console.error('Stream error:', err);
      connection.end();
    });
}

function processRow(row) {
  // 处理每一行数据
  // 比如写入文件、发送到消息队列等
}

// 用 Async Iterator 处理（更优雅，需要 mysql2 2.x+）
async function streamWithAsyncIterator() {
  const pool = mysql.createPool({
    host: 'localhost',
    user: 'root',
    password: 'pass',
    database: 'mydb',
  });

  const connection = await pool.getConnection();
  const [stream] = await connection.query('SELECT * FROM big_table');

  for await (const row of stream) {
    await processRowAsync(row);
  }

  connection.release();
}
```

**错误处理与重连策略：**

```javascript
const mysql = require('mysql2/promise');

class DatabaseManager {
  constructor(config) {
    this.config = config;
    this.pool = null;
    this.initPool();
  }

  initPool() {
    this.pool = mysql.createPool({
      ...this.config,
      waitForConnections: true,
      connectionLimit: 15,
    });

    // 连接错误事件
    this.pool.on('connection', (conn) => {
      conn.on('error', (err) => {
        console.error('Connection error:', err.code);
        if (err.code === 'PROTOCOL_CONNECTION_LOST') {
          console.log('Connection lost, will be auto-recreated by pool');
        }
      });
    });
  }

  // 带重试的查询
  async queryWithRetry(sql, params, maxRetries = 3) {
    for (let i = 0; i < maxRetries; i++) {
      try {
        const [rows] = await this.pool.execute(sql, params);
        return rows;
      } catch (err) {
        // 只重试可恢复的错误
        if (this.isRetryableError(err) && i < maxRetries - 1) {
          const delay = Math.pow(2, i) * 1000; // 指数退避
          console.log(`Retry ${i + 1}/${maxRetries} after ${delay}ms`);
          await new Promise(r => setTimeout(r, delay));
          continue;
        }
        throw err;
      }
    }
  }

  isRetryableError(err) {
    const retryableCodes = [
      'PROTOCOL_CONNECTION_LOST',
      'ECONNREFUSED',
      'ECONNRESET',
      'ETIMEDOUT',
    ];
    const retryableSqlStates = [
      '40001', // 死锁
      'HY000', // 服务器关闭
    ];
    return retryableCodes.includes(err.code) 
      || retryableSqlStates.includes(err.sqlState);
  }

  // 健康检查
  async healthCheck() {
    try {
      const [rows] = await this.pool.query('SELECT 1');
      return { status: 'healthy', timestamp: new Date() };
    } catch (err) {
      return { status: 'unhealthy', error: err.message };
    }
  }

  // 优雅关闭
  async shutdown() {
    await this.pool.end();
    console.log('Database pool closed');
  }
}

module.exports = DatabaseManager;
```

```javascript
// UserRepository.js - 完整的数据库访问层封装
const pool = require('./db');

class UserRepository {
  // 创建
  async create(userData) {
    const { name, email, age, department } = userData;
    const [result] = await pool.execute(
      `INSERT INTO users (name, email, age, department, created_at) 
       VALUES (?, ?, ?, ?, NOW())`,
      [name, email, age, department]
    );
    return { id: result.insertId, ...userData };
  }

  // 批量创建
  async createBatch(users) {
    const conn = await pool.getConnection();
    try {
      await conn.beginTransaction();

      const values = users.map(u => [u.name, u.email, u.age, u.department]);
      const placeholders = values.map(() => '(?, ?, ?, ?)').join(', ');

      const [result] = await conn.execute(
        `INSERT INTO users (name, email, age, department) VALUES ${placeholders}`,
        values.flat()
      );

      await conn.commit();
      return { insertedCount: result.affectedRows };
    } catch (err) {
      await conn.rollback();
      throw err;
    } finally {
      conn.release();
    }
  }

  // 查询（带分页和过滤）
  async find(filters = {}, pagination = { page: 1, pageSize: 20 }) {
    const conditions = [];
    const params = [];

    if (filters.name) {
      conditions.push('name LIKE ?');
      params.push(`%${filters.name}%`);
    }
    if (filters.department) {
      conditions.push('department = ?');
      params.push(filters.department);
    }
    if (filters.minAge) {
      conditions.push('age >= ?');
      params.push(filters.minAge);
    }
    if (filters.maxAge) {
      conditions.push('age <= ?');
      params.push(filters.maxAge);
    }

    const where = conditions.length > 0 
      ? 'WHERE ' + conditions.join(' AND ') 
      : '';

    // 查总数
    const [countRows] = await pool.execute(
      `SELECT COUNT(*) as total FROM users ${where}`,
      params
    );
    const total = countRows[0].total;

    // 查数据
    const offset = (pagination.page - 1) * pagination.pageSize;
    const [rows] = await pool.execute(
      `SELECT id, name, email, age, department, created_at 
       FROM users ${where} 
       ORDER BY id DESC LIMIT ? OFFSET ?`,
      [...params, pagination.pageSize, offset]
    );

    return {
      data: rows,
      pagination: {
        page: pagination.page,
        pageSize: pagination.pageSize,
        total,
        totalPages: Math.ceil(total / pagination.pageSize),
      },
    };
  }

  // 按ID查询
  async findById(id) {
    const [rows] = await pool.execute(
      'SELECT * FROM users WHERE id = ?',
      [id]
    );
    return rows[0] || null;
  }

  // 更新
  async update(id, updates) {
    const fields = [];
    const params = [];

    const allowedFields = ['name', 'email', 'age', 'department'];
    for (const key of allowedFields) {
      if (updates[key] !== undefined) {
        fields.push(`${key} = ?`);
        params.push(updates[key]);
      }
    }

    if (fields.length === 0) {
      throw new Error('No valid fields to update');
    }

    fields.push('updated_at = NOW()');
    params.push(id);

    const [result] = await pool.execute(
      `UPDATE users SET ${fields.join(', ')} WHERE id = ?`,
      params
    );

    if (result.affectedRows === 0) {
      throw new Error(`User ${id} not found`);
    }

    return this.findById(id);
  }

  // 删除（软删除）
  async softDelete(id) {
    const [result] = await pool.execute(
      'UPDATE users SET deleted_at = NOW(), status = 0 WHERE id = ?',
      [id]
    );
    return result.affectedRows > 0;
  }

  // 硬删除
  async delete(id) {
    const [result] = await pool.execute(
      'DELETE FROM users WHERE id = ?',
      [id]
    );
    return result.affectedRows > 0;
  }
}

module.exports = new UserRepository();
```

## 23.9 SQL注入防护最佳实践

SQL 注入是 Web 应用最常见的安全漏洞之一，在 OWASP Top 10 中常年名列前茅。一次成功的 SQL 注入攻击，轻则泄露用户数据，重则让攻击者完全控制数据库服务器。根据 Verizon 的数据泄露调查报告，SQL 注入仍然是导致数据泄露的主要原因之一。

防御 SQL 注入需要"纵深防御"的思维——不能只靠一道防线。第一道防线是参数化查询，这是最有效的防御手段；第二道防线是输入验证，确保用户输入符合预期格式；第三道防线是最小权限原则，即使注入成功也限制攻击者能做的事情；第四道防线是 Web 应用防火墙（WAF），作为最后的安全网。

```javascript
// ❌ 危险：字符串拼接
const sql = `SELECT * FROM users WHERE name = '${req.body.name}'`;
// 如果 name = "' OR 1=1 --"
// SQL 变成：SELECT * FROM users WHERE name = '' OR 1=1 --'
// 这会返回所有用户！

// ✅ 安全：参数化查询
const [rows] = await pool.execute(
  'SELECT * FROM users WHERE name = ?',
  [req.body.name]
);

// ✅ 安全：使用 escape 方法（用于不能参数化的场景，如表名）
const table = mysql.escapeId('user-data'); // `user-data`
const sql2 = `SELECT * FROM ${table}`;

// ✅ 安全：白名单验证排序字段
const ALLOWED_SORT_FIELDS = ['id', 'name', 'created_at', 'age'];
function buildOrderBy(sortField, sortOrder = 'ASC') {
  if (!ALLOWED_SORT_FIELDS.includes(sortField)) {
    throw new Error('Invalid sort field');
  }
  const order = sortOrder.toUpperCase() === 'DESC' ? 'DESC' : 'ASC';
  return `ORDER BY ${sortField} ${order}`;
}
```

> [!WARNING] 注意
> Prepared Statements 无法参数化的地方：表名、列名、ORDER BY 字段、LIMIT 值（某些驱动）。这些地方必须用白名单验证或手动转义，绝不能直接拼接用户输入。
