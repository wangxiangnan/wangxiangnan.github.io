# 第6章：多阶段构建与高级Dockerfile技巧

## 引言：为什么构建的镜像这么大？

想象一下：你用 React 写了一个前端项目。构建时你需要 Node.js、npm、webpack、babel、typescript 等一堆工具，但运行时只需要编译好的静态文件（HTML/CSS/JS）。如果你把所有构建工具都装进生产镜像，就像搬家时把整个工具箱都带到新公寓——其实你只需要装好的画框。

多阶段构建就是来解决这个问题的："在工厂里把画框装好，只把成品搬到公寓。"

## 6.1 多阶段构建（Multi-stage Build）

**没有多阶段构建的痛苦**：

```dockerfile
# ❌ 单阶段构建：所有构建工具都留在最终镜像里
FROM node:18
WORKDIR /app
COPY . .
RUN npm install            # 安装了 devDependencies（webpack, babel, typescript...）
RUN npm run build          # 编译 TypeScript → JavaScript
# 最终镜像包含了所有构建工具 + 源代码 + 编译产物
# 镜像大小：~1.5GB 😱
CMD ["node", "dist/server.js"]
```

**多阶段构建的优雅方案**：

```dockerfile
# ========== 阶段 1：构建 ==========
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                 # 安装所有依赖（包括开发依赖）
COPY . .
RUN npm run build          # 编译 TypeScript → JavaScript
# 此时 /app/dist 目录有编译好的 JS 文件

# ========== 阶段 2：生产 ==========
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production  # 只安装生产依赖
COPY --from=builder /app/dist ./dist  # 只复制编译产物！
EXPOSE 3000
CMD ["node", "dist/server.js"]
# 最终镜像：只有运行时 + 生产依赖 + 编译产物
# 镜像大小：~200MB 🎉
```

## 6.2 实战：React 应用的二阶段构建

```dockerfile
# ========== 阶段 1：构建 React 应用 ==========
FROM node:18-alpine AS builder

WORKDIR /app

# 复制依赖文件并安装
COPY package*.json ./
RUN npm ci

# 复制源代码并构建
COPY . .
RUN npm run build
# 构建产物在 /app/build 目录（create-react-app 默认）
# 或者 /app/dist（如果用 Vite）

# ========== 阶段 2：用 Nginx 服务静态文件 ==========
FROM nginx:alpine

# 删除 Nginx 默认配置
RUN rm /etc/nginx/conf.d/default.conf

# 复制自定义 Nginx 配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 从构建阶段复制静态文件
COPY --from=builder /app/build /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

对应的 `nginx.conf`：

```nginx
server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由：所有路径都返回 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反向代理
    location /api/ {
        proxy_pass http://api-server:3000/;
    }

    # 静态资源缓存
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

## 6.3 实战：Go 应用的多阶段构建

Go 的多阶段构建效果最震撼，因为 Go 编译出的是静态二进制文件：

```dockerfile
# ========== 阶段 1：编译 Go 程序 ==========
FROM golang:1.21-alpine AS builder

WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .
# CGO_ENABLED=0 生成纯静态二进制
# -ldflags="-s -w" 去除调试信息，减小体积
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server .

# ========== 阶段 2：运行 ==========
# 用 scratch（空镜像，0MB！）
FROM scratch

# 复制 CA 证书（如果需要 HTTPS）
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

# 只复制编译好的二进制文件
COPY --from=builder /app/server /server

EXPOSE 8080
ENTRYPOINT ["/server"]

# 最终镜像大小：~10-20MB（只有你的二进制文件！）
# 对比单阶段构建：~1GB（包含了整个 Go 工具链）
```

## 6.4 BuildKit：新一代构建引擎

BuildKit 是 Docker 的新一代构建引擎，从 Docker 18.09 开始引入，Docker 23.0 开始成为默认引擎：

```bash
# 检查 BuildKit 是否启用
docker buildx version

# 如果没有默认启用，手动启用
export DOCKER_BUILDKIT=1

# BuildKit 的主要优势：
# 1. 并行构建（多个独立的构建阶段可以同时执行）
# 2. 更好的缓存管理
# 3. 构建时密钥传递（Secrets）
# 4. 更详细的构建输出
```

## 6.5 docker build 高级选项

```bash
# --cache-from：使用外部缓存
# 在 CI/CD 中特别有用：先拉取之前构建的镜像作为缓存源
docker pull myapp:latest || true
docker build --cache-from myapp:latest -t myapp:new-version .

# --target：只构建到指定阶段
# 比如只构建测试阶段，不构建生产阶段
docker build --target test -t myapp:test .

# --build-arg：传递构建参数
docker build \
  --build-arg NODE_ENV=production \
  --build-arg API_URL=https://api.example.com \
  --build-arg VERSION=1.2.3 \
  -t myapp:1.2.3 .

# --no-cache：不使用任何缓存（排查构建问题时使用）
docker build --no-cache -t myapp:latest .

# --platform：构建指定平台的镜像
docker build --platform linux/amd64 -t myapp:latest .
# 在 M1/M2 Mac 上构建 x86 镜像时需要这个
```

## 6.6 BuildKit Secrets：构建时安全传递密钥

有些场景需要在构建过程中访问私有资源（比如私有 npm 包、私有 Git 仓库），需要传递认证信息：

```dockerfile
# syntax=docker/dockerfile:1

# ========== 传统方式（不安全！密钥会留在镜像层中） ==========
# ❌ 密钥会出现在镜像的历史记录中
RUN echo "//registry.npmjs.org/:_authToken=MY_SECRET_TOKEN" > ~/.npmrc
RUN npm install
RUN rm ~/.npmrc    # 删了也没用！上一层已经有了

# ========== BuildKit Secrets（安全方式） ==========
# ✅ 密钥只在构建时可用，不会留在任何镜像层中

# 复制 package.json
COPY package*.json ./

# 使用 secret 挂载 .npmrc
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci

# 或者在构建时传递 SSH 密钥（访问私有 Git 仓库）
RUN --mount=type=ssh \
    npm install git+ssh://git@github.com/private-org/private-pkg.git
```

构建命令：

```bash
# 传递 secret
docker build \
  --secret id=npmrc,src=$HOME/.npmrc \
  -t myapp:latest .

# 传递 SSH 密钥
docker build \
  --ssh default=$HOME/.ssh/id_rsa \
  -t myapp:latest .
```

## 6.7 HEALTHCHECK 指令

HEALTHCHECK 让 Docker 知道你的应用是否真的在正常工作：

```dockerfile
# 基本用法
HEALTHCHECK --interval=30s \     # 每 30 秒检查一次
            --timeout=3s \       # 超时时间 3 秒
            --start-period=5s \  # 启动宽限期 5 秒（刚启动时不检查）
            --retries=3 \        # 连续失败 3 次标记为 unhealthy
  CMD curl -f http://localhost:3000/health || exit 1

# 对于没有 curl 的 Alpine 镜像
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

# Python 应用的健康检查
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:5000/health')" || exit 1

# 禁用健康检查（继承自基础镜像的健康检查）
HEALTHCHECK NONE
```

查看健康状态：

```bash
docker ps
# CONTAINER ID  IMAGE        STATUS                   
# a1b2c3d4      myapp:latest Up 2 minutes (healthy)   ← 看这里！

# 查看详细健康检查日志
docker inspect --format='{{json .State.Health}}' my-app | python -m json.tool
```

## 6.8 USER 指令与安全最佳实践

```dockerfile
# ❌ 以 root 运行（默认行为）
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm ci --only=production
CMD ["node", "server.js"]
# 容器内的进程拥有 root 权限，如果被入侵后果很严重

# ✅ 以非 root 用户运行
FROM node:18-alpine
WORKDIR /app

# 创建专用用户
RUN addgroup -g 1001 -S nodejs && \
    adduser -S appuser -u 1001 -G nodejs

COPY package*.json ./
RUN npm ci --only=production

COPY --chown=appuser:nodejs . .

# 切换用户（之后所有指令都以这个用户运行）
USER appuser

EXPOSE 3000
CMD ["node", "server.js"]
```

安全最佳实践清单：

```dockerfile
# 1. 使用最小基础镜像（减少攻击面）
FROM node:18-alpine     # ✅ 而不是 FROM node:18

# 2. 固定镜像版本（避免意外更新）
FROM node:18.17.0-alpine3.18  # ✅ 精确到补丁版本

# 3. 非 root 用户
USER appuser

# 4. 不要在镜像中存储敏感信息
# ❌ COPY .env .env
# ❌ ENV API_KEY=sk-xxx

# 5. 只安装必要的包
RUN apk add --no-cache curl  # ✅ 而不是 apk add curl git vim wget ...

# 6. 使用 .dockerignore 排除敏感文件
```

> **Tip:** 使用 `docker scan`（Docker Desktop 内置）或 `trivy` 扫描镜像中的已知漏洞：
>
> ```bash
> docker scan myapp:latest
> # 或使用 trivy（更强大）
> # trivy image myapp:latest
> ```

## 本章小结

- 多阶段构建将"构建环境"和"运行环境"分离，大幅减小最终镜像体积
- 典型模式：builder 阶段安装工具+编译 → production 阶段只复制产物
- BuildKit 带来了并行构建、安全密钥传递等现代特性
- HEALTHCHECK 让 Docker 能自动检测应用是否健康
- 安全三板斧：最小镜像 + 非 root 用户 + 不存储敏感信息

## 练习

1. 为一个 TypeScript Node.js 项目编写多阶段 Dockerfile，对比单阶段和多阶段的镜像大小
2. 为一个 React（或 Vue）项目编写多阶段 Dockerfile：构建阶段用 Node.js，运行阶段用 Nginx
3. 在你的 Dockerfile 中添加 HEALTHCHECK，运行容器后用 `docker ps` 查看健康状态
4. 使用 BuildKit 的 `--mount=type=secret` 安全地传递一个 API Key，验证它不会出现在镜像层中
