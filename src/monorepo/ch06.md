# Ch06: TypeScript 配置策略

## 本章目标

> 设计一套分层、可继承的 TypeScript 配置体系，让 monorepo 中的所有项目共享核心编译规则，同时允许各项目根据自身环境（浏览器 vs Node.js）进行差异化覆盖。理解每个配置项"为什么这样设置"，而不是盲目复制。

## 6.1 共享 tsconfig 包的设计

`packages/tsconfig` 是纯配置包，不需要构建步骤。它的作用是提供一组"预设"供其他项目继承。

首先创建 `packages/tsconfig/package.json`：

```json
{
  "name": "@monorepo/tsconfig",
  "version": "0.1.0",
  "private": true,
  "files": ["*.json"]
}
```

`private: true` 确保这个包不会被意外发布到 npm。`files` 字段只包含 JSON 文件，因为配置文件不需要编译。

### base.json — 所有项目的共同基础

创建 `packages/tsconfig/base.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "compilerOptions": {
    /* ====== 语言和 emit 行为 ====== */
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "lib": ["ES2022"],
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,

    /* ====== 类型检查严格性 ====== */
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "forceConsistentCasingInFileNames": true,

    /* ====== 模块解析 ====== */
    "resolveJsonModule": true,
    "allowImportingTsExtensions": false,
    "esModuleInterop": true,

    /* ====== 代码质量 ====== */
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "exactOptionalPropertyTypes": false
  },
  "exclude": ["node_modules", "dist"]
}
```

**逐个解释关键配置：**

- **`target: "ES2022"`**：编译目标是现代 JavaScript。2022 年的特性（如 `Array.at()`、顶层 `await`、类字段）在所有现代浏览器和 Node 18+ 中都已原生支持，不需要降级转译。
- **`module: "ESNext"` + `moduleResolution: "bundler"`**：这是现代工具链的最佳组合。`bundler` 解析策略让 TypeScript 理解 Vite/Webpack 等打包器的模块解析行为（比如自动解析 `package.json` 的 `exports` 字段），同时不要求文件扩展名完全匹配。
- **`isolatedModules: true`**：强制每个文件可以独立编译。这不是限制，而是要求——它确保你的代码兼容 esbuild、SWC、Babel 等只能逐文件编译的工具。如果你用过 `const enum` 在非 `tsc` 编译时的坑，就知道这个选项的价值。
- **`verbatimModuleSyntax: true`**：替代了旧的 `importsNotUsedAsValues` 和 `isolatedModules` 的部分功能。它强制你使用 `import type` 来导入纯类型，使用 `export type` 来导出纯类型。这消除了"这个 import 到底会不会出现在运行时代码中"的歧义。
- **`noUncheckedIndexedAccess: true`**：这是最容易被忽视但最重要的选项。开启后，通过索引访问对象或数组时，返回值会自动加上 `| undefined`。比如 `obj[key]` 的类型变成 `T | undefined` 而不是 `T`——这能捕获大量"我以为这个 key 一定存在"的运行时错误。
- **`noUnusedLocals` / `noUnusedParameters`**：防止死代码堆积。在 monorepo 中尤其重要，因为重构时跨包改动频繁，遗留的未使用变量是潜在的混淆源。

### vue.json — Vue 前端项目专用

创建 `packages/tsconfig/vue.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "extends": "./base.json",
  "compilerOptions": {
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "jsx": "preserve",
    "jsxImportSource": "vue",
    "types": ["vite/client"]
  }
}
```

**与 base 的差异：**

- 增加了 `DOM` 和 `DOM.Iterable` 库——前端代码需要 `document`、`window`、`HTMLElement` 等 DOM 类型
- `jsx: "preserve"` 让 TypeScript 保留 JSX 语法，由 Vite 的 Vue 插件处理 `<script setup>` 中的模板编译
- `types: ["vite/client"]` 引入 Vite 的客户端类型，提供 `import.meta.env` 等类型定义

### node.json — Node.js 后端项目专用

创建 `packages/tsconfig/node.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "extends": "./base.json",
  "compilerOptions": {
    "lib": ["ES2022"],
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "types": ["node"]
  }
}
```

**与 base 的差异：**

- **没有** `DOM` 库——后端代码不应该访问 `window`、`document` 等浏览器 API。如果后端代码中不小心写了 `document.querySelector`，TypeScript 会直接报错。
- **`module: "NodeNext"` + `moduleResolution: "NodeNext"`**：Node.js 原生支持的模块系统。它要求显式的文件扩展名（`.js`），严格区分 ESM 和 CJS，并正确解析 `package.json` 的 `exports` 字段。

## 6.2 各项目的 tsconfig 继承与覆盖

### apps/web 的 tsconfig

```json
{
  "extends": "@monorepo/tsconfig/vue.json",
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    },
    "types": ["vite/client"]
  },
  "include": [
    "src/**/*.ts",
    "src/**/*.tsx",
    "src/**/*.vue",
    "env.d.ts"
  ],
  "exclude": ["node_modules", "dist"]
}
```

### apps/api 的 tsconfig

```json
{
  "extends": "@monorepo/tsconfig/node.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    },
    "sourceMap": true
  },
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist"]
}
```

### packages/shared 的 tsconfig

```json
{
  "extends": "@monorepo/tsconfig/base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src",
    "declaration": true,
    "declarationMap": true
  },
  "include": ["src/**/*.ts"],
  "exclude": ["node_modules", "dist"]
}
```

**覆盖策略的原则：**

1. **编译目标（target）和严格性选项（strict）**——在 base 中统一定义，各项目不应该覆盖
2. **环境相关的 lib 和 types**——在 vue.json / node.json 中设置，这是"前端 vs 后端"的本质差异
3. **路径别名（paths）**——在每个项目中单独设置，因为各项目的目录结构不同
4. **输出目录（outDir）和 include 范围**——每个项目必须自己定义

## 6.3 路径别名配置

路径别名让你用 `@/components/Button.vue` 代替 `../../../components/Button.vue`。在 monorepo 中需要特别注意：路径别名需要在**两个地方**同步配置——TypeScript（`tsconfig`）和构建工具（Vite / tsx）。

在 `apps/web/tsconfig.json` 中：

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

在 `apps/web/vite.config.ts` 中同步：

```typescript
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
});
```

**为什么两处都要配？**

TypeScript 的 `paths` 只影响类型检查和 IDE 补全，它不会修改实际的模块解析路径。Vite 的 `resolve.alias` 才是真正在运行时（开发服务器和构建时）解析路径的地方。只配一个，要么 IDE 报错，要么运行时找不到模块。

## 6.4 TypeScript Project References 简介

Project References 是 TypeScript 提供的一种"将大项目拆分成多个小项目并声明它们之间依赖关系"的机制。

```json
// apps/web/tsconfig.json
{
  "extends": "@monorepo/tsconfig/vue.json",
  "references": [
    { "path": "../../packages/shared" }
  ],
  "compilerOptions": {
    "composite": true
  }
}
```

```json
// packages/shared/tsconfig.json
{
  "extends": "@monorepo/tsconfig/base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "outDir": "dist",
    "rootDir": "src"
  }
}
```

**Project References 解决了什么问题？**

当你运行 `tsc --build` 时，TypeScript 会根据 `references` 声明自动构建依赖包，并利用 `.d.ts` 文件进行类型检查——而不是重新编译 shared 包的源码。这在大型 monorepo 中能显著加速类型检查。

**但是，在 pnpm + Turborepo 的项目中，你真的需要 Project References 吗？**

大多数情况下，**不需要**。原因如下：

1. **Turborepo 已经在做构建编排**——它知道 `apps/web` 依赖 `packages/shared`，会先构建 shared，再构建 web
2. **Vite / tsx 直接解析源码**——在开发模式下，Vite 通过 workspace 链接直接读取 shared 的 `.ts` 文件，不需要 `.d.ts`
3. **Project References 增加了配置复杂度**——`composite: true` 要求所有文件都在 `include` 范围内，且要求 `rootDir` 下的所有 `.ts` 文件都被编译

如果你确实需要（比如在纯 Node.js 的 monorepo 中不使用 Vite），Project References 是一个很好的选择。但对于 Vue + Express 的全栈项目，Turborepo + workspace 链接已经足够了。

## 6.5 增量编译配置

对于需要频繁编译的项目（特别是 apps/api 这种用 `tsc` 编译的 Node.js 项目），增量编译可以显著加速：

```json
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "./dist/.tsbuildinfo"
  }
}
```

**工作原理：** 第一次编译时，TypeScript 会将编译状态保存到 `.tsbuildinfo` 文件中。后续编译时，只重新检查发生变化的文件及其依赖。在大型项目中，这能将编译时间从 30 秒降到 2-3 秒。

**注意：** 如果使用 `composite: true`（Project References 模式），`incremental` 会自动启用，不需要额外配置。

## 6.6 常见 tsconfig 陷阱和解决方案

### 陷阱 1：`esModuleInterop` 缺失导致默认导入失败

```typescript
// 没有 esModuleInterop 时，这样导入会报错：
import express from 'express';
// 必须写成：
import * as express from 'express';
```

**解决方案：** 在 `base.json` 中设置 `"esModuleInterop": true`。

### 陷阱 2：`skipLibCheck` 未开启导致第三方库类型冲突

当多个包依赖了不同版本的同一类型库时（如 `@types/node` v18 和 v20），会产生大量类型冲突。

**解决方案：** 在 `base.json` 中设置 `"skipLibCheck": true`。这会跳过 `node_modules` 中 `.d.ts` 文件的类型检查，既解决冲突又加速编译。

### 陷阱 3：`verbatimModuleSyntax` 导致运行时报错

```typescript
// 错误：纯类型被当作值导入，编译后 import 语句被删除但代码仍在引用
import { UserRole } from './types';
const role: UserRole = UserRole.ADMIN; // 运行时 undefined！

// 正确：枚举是值，不应该用 import type
import { UserRole } from './types';     // 值导入 ✓
import type { User } from './types';    // 类型导入 ✓
```

**解决方案：** 理解 `type` 和 `value` 的区别。接口（interface）、类型别名（type alias）是纯类型；枚举（enum）、类（class）是值。`verbatimModuleSyntax` 要求你显式区分。

### 陷阱 4：`noUncheckedIndexedAccess` 导致大量 `undefined` 检查

```typescript
const map: Record<string, number> = { a: 1, b: 2 };

// 开启 noUncheckedIndexedAccess 后：
const val = map['a']; // 类型是 number | undefined，而不是 number

// 你需要显式处理 undefined：
const val = map['a'] ?? 0; // 类型变成 number
// 或者：
if (map['a'] !== undefined) {
  const val = map['a']; // 类型收窄为 number
}
```

**这是特性，不是 bug。** 它强制你考虑"key 可能不存在"的情况，避免了 `undefined` 悄悄传播到下游代码中。

### 陷阱 5：monorepo 中找不到 shared 包的类型

```typescript
import type { User } from '@monorepo/shared';
// 报错：Cannot find module '@monorepo/shared' or its corresponding type declarations
```

**排查清单：**

1. 确认 `packages/shared/package.json` 中有正确的 `types` 字段指向 `.d.ts` 文件
2. 确认 `packages/shared` 已经执行了 `pnpm build` 生成了 `dist/` 目录
3. 确认 `apps/web/package.json` 中有 `"@monorepo/shared": "workspace:*"` 依赖
4. 确认根目录执行了 `pnpm install` 建立了 workspace 链接
5. 如果是新加的类型，确认 `src/index.ts` 中有对应的 `export`

## 本章小结

- 共享 tsconfig 通过继承机制消除了配置重复，base.json 定义通用规则，vue.json / node.json 定义环境差异
- 路径别名需要在 TypeScript 和构建工具中同步配置
- Project References 适合纯 Node.js 场景，但在 Turborepo + Vite 的全栈项目中通常不需要
- `strict`、`noUncheckedIndexedAccess`、`verbatimModuleSyntax` 是现代 TypeScript 项目的标配
- 遇到类型问题先看 `exports`、`types`、`workspace:*` 三个配置是否正确
