# Ch11：构建缓存与远程缓存

## 本章目标

- 理解 Turborepo 本地缓存的内部机制（内容哈希策略）
- 掌握缓存命中和失效的原理
- 学会配置 Vercel Remote Cache 和自建远程缓存服务器
- 掌握缓存调试技巧
- 制定合理的缓存策略

## 11.1 本地缓存机制：基于内容哈希

Turborepo 的缓存不是简单的"时间戳比对"或"文件修改时间检查"，而是基于**内容哈希（Content Hash）**的精确策略。

### 哈希的计算输入

当你运行 `turbo run build` 时，Turborepo 会计算一个哈希值，参与计算的因素包括：

```txt
hash = SHA256(
  任务的脚本命令 (如 "tsup src/index.ts --format esm,cjs --dts"),
  所有 inputs 文件的内容 (src/** 下的每个文件),
  所有上游依赖的哈希 (如果是 ^build 模式),
  相关环境变量的值 (env 中声明的变量),
  globalDependencies 文件的内容,
  globalEnv 环境变量的值,
  Turborepo 的版本号
)
```

这意味着以下任何变化都会导致缓存失效：

- 修改了 `src/` 下的任何一个文件
- 升级了依赖版本（`package.json` 或 `pnpm-lock.yaml` 变化）
- 修改了 `tsconfig.json`
- 环境变量值发生了变化
- 上游依赖的构建输入发生了变化

### 缓存存储位置

```
monorepo-root/
├── node_modules/.cache/turbo/    # 本地缓存目录
│   ├── a1b2c3d4e5f6/             # 以哈希值为目录名
│   │   ├── meta.json             # 任务元数据（耗时、退出码等）
│   │   └── stdout.log            # 任务的标准输出
│   ├── f6e5d4c3b2a1/
│   │   ├── meta.json
│   │   └── dist/                 # 如果配置了 outputs，产物也会被缓存
│   └── ...
```

> **为什么缓存在 `node_modules` 里？** 因为 `node_modules` 通常已经在 `.gitignore` 中，而且当你重新安装依赖时，缓存会被自然清除，避免陈旧缓存占用空间。

### 缓存命中流程

```
1. 计算当前任务的哈希值 H
2. 检查本地缓存中是否存在 H 对应的条目
3. 如果存在（缓存命中）：
   a. 恢复 outputs 中声明的文件（如 dist/）
   b. 回放缓存的 stdout/stderr 输出
   c. 标记为 "cache hit, skipping"
4. 如果不存在（缓存未命中）：
   a. 执行任务的实际命令
   b. 将 stdout/stderr 保存到缓存
   c. 将 outputs 中声明的文件复制到缓存
   d. 写入 meta.json（记录执行时间、退出码等）
```

## 11.2 缓存命中和失效的原理

让我们通过几个例子来理解缓存的行为：

### 案例一：修改无关文件

```bash
# 第一次构建
$ turbo run build
# shared: cache miss, 执行构建, 耗时 3.2s
# web: cache miss, 执行构建, 耗时 8.1s

# 只修改 apps/web/README.md
$ turbo run build
# shared: cache hit ✓（README 不在 inputs 中）
# web: cache hit ✓（README 不在 inputs 中）
```

因为 `README.md` 不在 `inputs` 配置中，所以缓存仍然命中。

### 案例二：修改 shared 包

```bash
# 修改 packages/shared/src/utils.ts
$ turbo run build
# shared: cache miss（源文件变了）
# ui: cache miss（依赖 shared，上游哈希变了）
# database: cache miss（依赖 shared）
# web: cache miss（依赖 ui 和 shared）
# api: cache miss（依赖 database 和 shared）
# tsconfig: cache hit ✓（不依赖 shared）
```

### 案例三：修改环境变量

```bash
# 假设 build 配置了 env: ["API_BASE_URL"]
$ API_BASE_URL=https://dev.api.com turbo run build
# web: cache miss, 使用 dev API 构建

$ API_BASE_URL=https://dev.api.com turbo run build
# web: cache hit ✓（相同的环境变量值）

$ API_BASE_URL=https://prod.api.com turbo run build
# web: cache miss（API_BASE_URL 变了，哈希不同）
```

## 11.3 远程缓存（Remote Cache）

本地缓存很好，但它有一个局限：**只对本机有效**。当你的团队成员 clone 了项目并执行 `turbo run build` 时，他们无法使用你机器上的缓存，必须从头构建。同样，CI 每次都是全新的环境，无法利用本地缓存。

远程缓存就是为了解决这个问题——它让缓存在团队和 CI 之间共享。

### 方案一：Vercel Remote Cache

Vercel 提供了官方的远程缓存服务，对开源项目免费，商业项目需要付费。

**配置步骤**：

1. 在 [Vercel](https://vercel.com) 注册账号
2. 创建一个 Team
3. 在项目中登录：

```bash
# 登录 Vercel 账户
npx turbo login

# 关联到远程缓存
npx turbo link
```

`turbo link` 会在项目根目录生成 `.turbo/config.json`：

```json
{
  "teamid": "team_xxxxx",
  "apiurl": "https://vercel.com/api",
  "token": "xxxxx",
  "slug": "your-team-name"
}
```

> **安全提示**：`.turbo/config.json` 包含认证 token，应该添加到 `.gitignore`。在 CI 中，通过环境变量 `TURBO_TEAM` 和 `TURBO_TOKEN` 来配置。

**在 CI 中使用 Vercel Remote Cache**：

```yaml
# .github/workflows/ci.yml
env:
  TURBO_TEAM: ${{ secrets.TURBO_TEAM }}
  TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
```

### 方案二：自建远程缓存服务器

如果你不想依赖 Vercel 的服务，或者需要缓存存储在内网，可以使用 `turborepo-remote-cache` 这个开源项目。

**安装和运行**：

```bash
# 全局安装
npm install -g turborepo-remote-cache

# 创建存储目录
mkdir -p /data/turbo-cache

# 启动服务（使用文件系统存储）
TURBO_TOKEN=your-secret-token \
STORAGE_PROVIDER=local \
STORAGE_PATH=/data/turbo-cache \
PORT=3100 \
turborepo-remote-cache
```

**在项目中使用自建缓存**：

在 `.turbo/config.json` 中配置：

```json
{
  "teamid": "my-team",
  "apiurl": "http://your-cache-server:3100",
  "token": "your-secret-token"
}
```

或者在 `.npmrc` 中配置（推荐，可以提交到版本控制）：

```ini
//your-cache-server:3100/:_authToken=your-secret-token
```

**使用 Docker 部署自建缓存**：

```yaml
# docker-compose.yml
version: '3.8'
services:
  turbo-cache:
    image: ducktors/turborepo-remote-cache:latest
    ports:
      - "3100:3100"
    environment:
      TURBO_TOKEN: your-secret-token
      STORAGE_PROVIDER: local
      STORAGE_PATH: /cache
    volumes:
      - turbo-cache-data:/cache
    restart: unless-stopped

volumes:
  turbo-cache-data:
```

> **为什么选择自建？** 自建缓存服务器有几个优势：数据完全掌控在自己手中、可以存储在内网、没有外网传输延迟、不受 Vercel 的服务限制。对于企业团队来说，自建通常是更好的选择。

## 11.4 缓存调试技巧

当缓存行为不符合预期时，以下技巧能帮你快速定位问题。

### `--force`：跳过缓存，强制重新执行

```bash
# 忽略所有缓存，强制重新执行所有任务
turbo run build --force
```

**使用场景**：当你怀疑缓存有问题，或者环境变量配置变更但没有正确触发缓存失效时。

### `--output-logs`：控制日志输出

```bash
# 只显示缓存未命中的任务的日志
turbo run build --output-logs=new-only

# 显示所有任务的日志（包括缓存命中的回放日志）
turbo run build --output-logs=full

# 不显示任何日志
turbo run build --output-logs=none

# 仅显示哈希计算的详细信息
turbo run build --output-logs=hash-only
```

**`hash-only` 模式示例**：

```
@monorepo/shared:build: Inputs:
@monorepo/shared:build:   - packages/shared/src/index.ts [abc123]
@monorepo/shared:build:   - packages/shared/src/utils.ts [def456]
@monorepo/shared:build:   - packages/shared/tsconfig.json [ghi789]
@monorepo/shared:build: Resolved task hash: xyz789abc
@monorepo/shared:build: cache hit, skipping
```

这能帮你理解哪些文件参与了哈希计算，以及最终的哈希值是什么。

### `--dry-run`：模拟运行，不实际执行

```bash
# 模拟运行，显示哪些任务会执行，但不实际执行
turbo run build --dry-run

# JSON 格式输出，适合程序化处理
turbo run build --dry=json
```

**输出示例**：

```json
{
  "packages": ["@monorepo/shared", "@monorepo/ui", "@monorepo/web"],
  "tasks": [
    {
      "taskId": "@monorepo/shared#build",
      "cache": false,
      "command": "tsup src/index.ts --format esm,cjs --dts"
    },
    {
      "taskId": "@monorepo/ui#build",
      "cache": true,
      "command": "tsup src/index.ts --format esm,cjs --dts --external vue"
    }
  ]
}
```

### 清除缓存

```bash
# 清除本地缓存
rm -rf node_modules/.cache/turbo

# 或者使用 turbo 自带命令
turbo clean
```

## 11.5 缓存策略最佳实践

### 哪些任务应该缓存？

| 任务类型 | 是否缓存 | 原因 |
| ---------- | --------- | ------ |
| `build` | ✅ 缓存 | 构建是纯函数——相同输入总是产生相同输出 |
| `lint` | ✅ 缓存 | lint 结果也完全由源码决定 |
| `typecheck` | ✅ 缓存 | 类型检查的结果只依赖源码 |
| `test` | ✅ 缓存（有条件） | 单元测试可以缓存，但涉及外部服务的集成测试不应缓存 |
| `dev` | ❌ 不缓存 | 开发服务器是长期运行的，缓存无意义 |
| `db:migrate` | ❌ 不缓存 | 数据库迁移是有副作用的操作 |
| `deploy` | ❌ 不缓存 | 部署也是有副作用的操作 |

**判断标准**：一个任务如果满足以下两个条件，就可以缓存：

1. **幂等性**：相同输入总是产生相同输出
2. **无副作用**：不会修改外部状态（数据库、文件系统、网络等）

### 精确配置 inputs

```json
// ❌ 太宽泛：任何文件变化都会导致缓存失效
"inputs": ["**"]

// ✅ 精确：只有相关文件变化才影响缓存
"inputs": ["src/**", "tsconfig.json", "package.json"]

// ✅ 排除测试文件对 build 的影响
"inputs": ["src/**", "!src/**/*.test.ts", "tsconfig.json"]
```

## 11.6 Monorepo CI 中缓存的实际效果对比

### 无缓存的 CI 构建

```yaml
# .github/workflows/ci-no-cache.yml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo run build
      # 每次都需要完整构建，耗时 ~45s
```

### 有远程缓存的 CI 构建

```yaml
# .github/workflows/ci-with-cache.yml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm turbo run build
        env:
          TURBO_TEAM: ${{ secrets.TURBO_TEAM }}
          TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      # 首次构建 ~45s，后续如果只改了 1 个包，可能只需 ~5s
```

**实际效果对比**（基于一个包含 10 个包的 monorepo）：

| 场景 | 无缓存 | 有本地缓存 | 有远程缓存 |
| ------ | -------- | ----------- | ----------- |
| 全量构建（首次） | 45s | 45s | 45s |
| 全量构建（无变化） | 45s | 1.2s | 2.5s |
| 修改 1 个包 | 45s | 8s | 9s |
| CI 全量构建（首次） | 45s | 45s | 12s（从其他开发者机器上传的缓存） |
| CI 修改 1 个包 | 45s | 45s（CI 无本地缓存） | 9s |

关键差异在最后一行：CI 环境每次都是全新的，没有本地缓存。但有了远程缓存，CI 可以利用团队其他成员构建时上传的缓存，大幅缩短构建时间。

## 本章小结

1. **本地缓存**：基于内容哈希，精确到每个文件的内容变化，缓存在 `node_modules/.cache/turbo/` 下
2. **远程缓存**：让缓存在团队和 CI 之间共享，Vercel 提供官方服务，也可以用 `turborepo-remote-cache` 自建
3. **调试技巧**：`--force` 强制重新执行、`--output-logs=hash-only` 查看哈希详情、`--dry-run` 模拟运行
4. **缓存策略**：幂等且无副作用的任务应该缓存，有副作用的任务不应缓存；`inputs` 配置要精确
