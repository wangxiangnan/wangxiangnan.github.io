# 第3章：三个区域：工作区、暂存区与版本库

> [!TIP] Part 1: 基础概念篇（地基篇）
> 本篇 Git 地基的最后一章。配置已就位，第一连击已跑通，接下来要回答整个 Git 体系里最核心的问题：一次提交到底发生在哪里？理解了三区模型，此后每一条 Git 命令都会变成一张清晰的搬运工路线图。

上一章你配好了三件套，第一次提交畅通无阻。但如果我追问一句——`git add` 和 `git commit` 明明可以合成一条命令，Git 为什么要设计成两步？大部分教程跳过这个问题，于是初学者背下「add 再 commit」的咒语，却永远在关键时刻犯迷糊：为什么有的改动提交了，有的没有？为什么明明改了文件，commit 却说没有东西可提交？

这一章用云笔记开发中最真实的节奏，把 Git 的心脏——三个区域（Three Areas）——彻底拆开。学完你会发现：**Git 的一切命令，都是在三个区域之间搬运内容**。

## 3.1 云笔记的三天

先看三天的工作日志，注意每次「想存档」的时机：

- **周一**：给笔记列表加了搜索框。晚上想存档——但顺手改的两处错别字不想和搜索框混在一个存档里。
- **周二**：修复滚动闪烁，中途还调整了一个文案。闪烁修复想单独存档，文案另算。
- **周三**：滚动性能优化写了一半，跑不起来。想先存个档再回家——但半成品不能算一次正式提交。

把三天的诉求列成表，你会发现它们指向同一种能力：

| 时刻 | 诉求 | 复制粘贴世界 | 三区模型 |
|------|------|-------------|---------|
| 周一晚 | 搜索框和错别字分开存档 | 做不到，整个目录一把梭 | `add` 搜索框，先提交；错别字后提交 |
| 周二 | 修复与文案分开存档 | 做不到 | 两次 `add`、两次 `commit` |
| 周三晚 | 半成品留个底，但不污染历史 | 只能复制整个目录 | 存进暂存区，不提交 |

对照第1章的「复制粘贴三宗罪」，你会发现还有第四宗罪没提：**存档粒度只能是一整个目录**。你永远无法说「只存这个文件的一半改动」——而这对编程是刚需：一次提交应该是一个完整的、有意义的单元，而不是「今天下午改的所有东西」的大杂烩。

Git 的答案是把「存档」拆成两步，两步之间隔着一块缓冲地。这就是三区模型。

## 3.2 三区模型：Git 的心脏

云笔记仓库里的内容，同一时刻存在于最多三个区域（Three Areas）：

| 区域 | 英文 | 本体 | 装的是什么 |
|------|------|------|-----------|
| 工作区 | Working Directory | `~/cloudnote` 下除 `.git` 外的所有文件 | 你正在编辑的真实文件 |
| 暂存区 | Staging Area | `.git` 目录里的 `index` 文件 | 下一次提交的候选清单 |
| 版本库 | Repository | `.git` 目录里的 `objects` 目录 | 历次提交的永久快照 |

三个区域之间，是一条单向主干道加两条回退小路：

```text
 工作区                 暂存区                 版本库
(Working Dir)       (Staging Area)        (Repository)
 你正在编辑的文件       下次提交的候选名单      .git 里的永久快照
    │                     │                     │
    │ ─── git add ─────►  │ ─── git commit ──► │
    │                     │                     │
    │ ◄── git restore ─── │ ◄── git reset ───── │
```

两个方向的动词完全对称：`add` 和 `commit` 往前送，`restore` 和 `reset` 往回撤（这两个命令第8章细讲，现在只求眼熟）。

这张图里藏着一个颠覆直觉的事实：**`git commit` 拍的不是工作区的照，而是暂存区的照**。暂存区是提交的「候选名单」，`git add` 就是把改动报上名。工作区里改了十处、只报名三处，那次提交就只包含三处——周三晚上「半成品不污染历史」的诉求，靠的正是这道闸门。

用 mermaid 把流动关系画全：

```mermaid
graph LR
  W["工作区\n你正在编辑"] -->|"git add 报名"| S["暂存区\n候选清单"]
  S -->|"git commit 拍照"| R["版本库\n永久快照"]
  S -->|"git restore 弃改"| W
  R -->|"git reset 回退"| S
```

对照第1章的「覆盖即永别」：复制粘贴世界里，存档动作直接覆盖上一份；三区世界里，**写入版本库的每次 commit 都是追加一个新快照，历史只增不减**。这是 Git 敢承诺「几乎不可能丢失」的物理基础。

> [!NOTE] 暂存区不是概念，是文件
> 暂存区的本体是 `.git` 目录下一个名为 `index` 的二进制文件，所以老资料也叫它「索引（Index）」。3.6 节你会亲眼见到它。

## 3.3 git add 的细粒度

`git add` 看似只会一招，实际上档位很细。按从粗到细排序：

```bash
git add notes.md        # 单个文件：只报它一个
git add src/            # 整个目录：src 下所有改动
git add .               # 当前目录：所有新文件 + 修改
git add -A              # 全仓库：所有改动（等价于新版 git 的 git add .）
git add -u              # 只更新已跟踪的文件，不收新文件
```

日常主力是「单文件」和「git add .」两档，但真正体现两步设计价值的，是交互式选段——`git add -p`：

```text
$ git add -p src/scroll.js
@@ -12,6 +12,9 @@ function onScroll() {
   const list = document.querySelector(".notes")
+  if (!list) return
   list.scrollTop = 0
Stage this hunk [y,n,q,a,d,s,e,?]?
```

Git 把改动切成一个一个「块」（Hunk），逐块问你收不收。按键含义一张表说清：

| 按键 | 含义 | 记忆 |
|------|------|------|
| `y` | 这一块收进暂存区 | yes |
| `n` | 这一块跳过 | no |
| `s` | 把当前块拆成更小的块 | split |
| `q` | 退出，剩下的都不问 | quit |
| `a` | 收进这一块及本文件剩余全部 | all |
| `d` | 跳过这一块及本文件剩余全部 | done |
| `e` | 手工编辑这一块 | edit |

回到 3.1 的场景：周一晚上搜索框和错别字改在同一个文件里，复制粘贴世界无解，`git add -p` 却能 `y` 收搜索框那块、`n` 跳过错别字那块——两次提交，干干净净。

反例也配一对。新手最爱 `git add .` 一把梭，某天顺手把调试用的 `debug.log`、两张临时截图一起提交进历史，仓库从此带着垃圾生活。**按功能分次 add、分次 commit**，是三区模型送给你的第一个纪律。

## 3.4 status 与 diff 的日常解读

两个区域之间有差异，Git 就得有仪器。`git status` 是仪表盘，`git diff` 是放大镜。

先看仪表盘。`git status` 用颜色区分状态：**红色代表「还没报名」——未跟踪（Untracked）的新文件或改了没 add 的文件；绿色代表「已报名」——已在暂存区等待提交**：

| status 显示 | 颜色 | 含义 | 下一步动作 |
|------------|------|------|-----------|
| Untracked files | 红 | Git 没见过的新文件 | `git add` 收编 |
| Changes not staged | 红 | 已跟踪文件改了未 add | `git add` 报名 |
| Changes to be committed | 绿 | 已在暂存区候审 | `git commit` 存档 |
| nothing to commit | — | 三区一致，无故事 | 继续写代码 |

加 `-s` 参数切到短格式，两列状态码更快：

```text
$ git status -s
 A notes.md        ← 第一列 A：新文件已暂存
 M src/scroll.js   ← 第二列 M：已跟踪文件改了未暂存
?? debug.log       ← ??：未跟踪
```

口诀：**第一列管暂存区，第二列管工作区**，没变的位置用空格占位。

再看放大镜。`git diff` 有四种比较方向，问的问题各不相同：

| 命令 | 比较对象 | 回答的问题 |
|------|---------|-----------|
| `git diff` | 工作区 vs 暂存区 | 还有哪些改动没报名？ |
| `git diff --staged` | 暂存区 vs 版本库 | 已报名的改动长什么样？ |
| `git diff HEAD` | 工作区 vs 版本库 | 从上次提交到现在总共改了什么？ |
| `git diff c1 c2` | 提交 c1 vs 提交 c2 | 两个历史快照差在哪？ |

> [!NOTE] --staged 和 --cached 是一回事
> 老资料里写 `git diff --cached`，因为暂存区的本体文件叫 index（索引），「cached」是历史的叫法。git 1.6.1 起提供了更达意的 `--staged`，两者完全等价，本书统一用后者。

diff 的输出有固定解剖结构，第一次看时对号入座：

```text
diff --git a/src/scroll.js b/src/scroll.js
--- a/src/scroll.js
+++ b/src/scroll.js
@@ -12,4 +12,5 @@ function onScroll() {
   const list = document.querySelector(".notes")
+  if (!list) return
   list.scrollTop = 0
```

`-` 开头的行是旧版删掉的，`+` 开头是新版新增的；`@@ -12,4 +12,5 @@` 是块头，意思是旧版从第 12 行起 4 行，新版从第 12 行起 5 行。**先看 `--staged` 的 diff 再 commit，是避免「提交了不想要的东西」的最便宜保险**。

## 3.5 提交信息的写法

提交信息（Commit Message）是写给三个月后的自己的。三个月后的你什么都不记得，只记得骂骂咧咧打开 `git log`。于是写法的高下立判：

| 反例 | 病因 | 正例 |
|------|------|------|
| `fix bug` | 什么 bug？在哪？修了啥？ | `修复笔记列表滚动时的闪烁问题` |
| `update` | 万能废话，信息量为零 | `用 requestAnimationFrame 重写滚动监听` |
| `修改了一些文件` | 等于没说 | `为空笔记添加占位提示` |
| `改了改` | 三个月后的你会骂三个月前的你 | `调整笔记排序：按更新时间倒序` |

三条军规，全部来自社区通行的实践：

1. **用祈使句**。标题写「add」而不是「added」或「adds」——检验方法是默念「这个提交应用之后，会＿＿」：「会修复闪烁」通顺，「会修复了闪烁」别扭。
2. **标题不超过 50 字符**。`git log --oneline` 只显示标题一行，超长的会被截断；50 字符也强迫你想清楚「这次提交只干了一件事是什么」。
3. **标题后空一行再写正文，正文每行不超过 72 字符**。空行是解析的约定；72 字符保证老终端不折行。正文回答 why（为什么这么改），而不是 how（怎么改的——diff 自己会说）。

一个符合军规的完整示例：

```text
用 requestAnimationFrame 重写滚动监听

滚动事件在部分机型上每秒触发 120 次，直接改 DOM 造成闪烁。
改用 rAF 合帧后，每帧只重排一次。
```

此后 `git log --oneline` 一眼即明，第 3.1 节周二的那个悬案有了户口。

> [!TIP] 团队里最常见的变体：Conventional Commits
> 开源圈流行在标题前加类型前缀：`fix: 修复滚动闪烁`、`feat: 新增搜索框`。个人项目用不用随意，团队项目统一即可——**一致性比格式本身重要**。

## 3.6 .git 目录速览

第1章初见过 `.git`，现在可以给它补上三区的位置。在 `~/cloudnote` 执行 `ls .git`：

```text
~/cloudnote/.git/
├── HEAD        # 一行文本：指向当前分支（第9章拆开）
├── index       # 暂存区本体：候选清单（二进制，别手改）
├── objects/    # 版本库本体：所有快照按哈希值存放
└── refs/       # 分支与标签的书签，refs/heads/main 是个 41 字节文件
```

一句话定位三区在文件系统的落点：

- **工作区**在 `.git` 之外，是你肉眼可见的普通文件；
- **暂存区**是 `index` 这一个文件；
- **版本库**是 `objects` 目录——第1章说「提交过的东西几乎不可能真正丢失」，指的就是 objects 里的快照不受工作区风浪影响。

`objects` 与 `refs` 的内部构造是 Git 最优雅的设计，但本章按下不表：`HEAD` 和 `refs` 留给第9章（分支的本质是指针），`objects` 会在第19章解剖 `git pull` 时与你重逢。现在只需记住一条红线：**可以 `ls`、`cat` 好奇围观，不要手动修改 `.git` 里的任何文件**。

## 3.7 实验：模拟一天的开发

把周一的场景完整演一遍，所有仪器都用上。目标：搜索框和错别字分成两次提交。

```bash
cd ~/cloudnote
echo "<input id='search' placeholder='搜索笔记'>" > search.html
git status -s                  # ?? search.html，未跟踪
git add search.html            # 只报名搜索框
git diff --staged              # 确认暂存区里只有搜索框
git commit -m "新增笔记搜索框"
```

第二段：错别字修复，混在同一个文件也不怕——这里用新文件模拟：

```bash
echo "修正：'笔记' 拼写" > typo-fix.md
git add typo-fix.md
git commit -m "修正两处错别字"
git lg
```

`git lg`（上一章配的别名）此刻正好展示成果：

```text
$ git lg
* 9f4e2b1 (HEAD -> main) 修正两处错别字
* c7d8a2f 新增笔记搜索框
* c48d9e2 修复笔记列表滚动闪烁
```

最后一组对照实验，感受 diff 的四种比较：改一行但不 add，`git diff` 有输出、`git diff --staged` 没输出；`git add` 之后再反过来。**哪个命令有输出，差异就活在哪两个区域之间**——这句话就是本节的全部考点。

## 本章小结

- Git 的心脏是三区模型：工作区（你编辑的文件）、暂存区（候选清单）、版本库（永久快照）
- **commit 拍的是暂存区的照**：add 是报名，报多少交多少，半成品可以只停在暂存区
- `git add -p` 能按块（Hunk）挑改动，同文件里的多个修改也能分开提交
- status 红/绿即报名状态：红是没报名，绿是候审中；`-s` 短格式第一列管暂存区、第二列管工作区
- diff 四种比较：默认（工作区 vs 暂存区）、`--staged`（暂存区 vs 版本库）、`HEAD`（工作区 vs 版本库）、两提交之间
- 提交信息三军规：祈使句、标题 50 字符内、正文 72 字符内并解释 why
- 三区落点：暂存区是 `.git/index` 文件，版本库是 `.git/objects` 目录，都别手动修改
