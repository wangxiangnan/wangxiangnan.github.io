## 10.2 为什么需要 Turborepo？

在 Part 1-2 中，我们的 monorepo 已经有了多个包和应用。假设你要执行一次完整构建，你可能会这样做：

```bash
# 先构建基础包
cd packages/tsconfig && pnpm build
cd ../shared && pnpm build
cd ../ui && pnpm build
cd ../database && pnpm build
# 再构建应用
cd ../../apps/api && pnpm build
cd ../web && pnpm build
```

这种方式有三个严重问题：

1. **手动管理顺序**：你必须自己记住谁依赖谁，一旦依赖关系变复杂就会出错
2. **完全串行**：`shared` 和 `ui` 之间如果没有依赖关系，它们完全可以并行构建，但手动操作做不到
3. **没有缓存**：即使你只改了一行代码，所有包都要重新构建

Turborepo 就是为了解决这三个问题而生的。它是一个**任务编排引擎**，能够自动分析包之间的依赖关系，以最优顺序和最大并行度执行任务，并且通过内容哈希实现智能缓存。

## 10.3 安装 Turborepo

```bash
# 在 monorepo 根目录执行
pnpm add -Dw turbo
```

> **为什么用 `-Dw`？** `turbo` 是开发时工具，不需要出现在生产依赖中。`-w`（`--workspace-root`）表示安装到 workspace 根目录，这样所有子包都能通过 `turbo` 命令来编排任务。

安装完成后，将 `turbo` 添加到根 `package.json` 的 scripts 中：

```json
{
  "scripts": {
    "build": "turbo run build",
    "dev": "turbo run dev",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "typecheck": "turbo run typecheck"
  }
}
```

同时，把 `turbo` 加入 `.gitignore`：

```gitignore
# Turborepo
.turbo
```

> **为什么要忽略 `.turbo`？** Turborepo 会在每个包下生成 `.turbo` 目录来存放缓存和日志元数据。这些是本地产物，不应该提交到版本控制。

## 10.4 turbo.json 核心配置

在 monorepo 根目录创建 `turbo.json`，这是 Turborepo 的核心配置文件：

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json", "package.json"],
      "outputs": ["dist/**"]
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    },
    "lint": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", ".eslintrc.*"]
    },
    "test": {
      "dependsOn": ["build"],
      "inputs": ["src/**", "tests/**", "__tests__/**", "*.test.*", "*.spec.*"]
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json"]
    }
  }
}
```

让我们逐行解读这个配置。

### `$schema`

```json
"$schema": "https://turbo.build/schema.json"
```

这个字段让 IDE（如 VS Code）能够验证你的配置并提供自动补全。**始终保留它**，能避免很多配置错误。

### `tasks` 对象

`tasks` 是 `turbo.json` 的核心，定义了所有可执行的任务类型。每个 key（如 `build`、`dev`）对应各包 `package.json` 中 `scripts` 的脚本名。当你在根目录运行 `turbo run build` 时，Turborepo 会查找所有包含 `build` 脚本的包，并根据这里的配置来编排执行。

## 10.5 深入理解 `dependsOn`：三种依赖模式

`dependsOn` 是 Turborepo 最强大的特性之一，它定义了任务之间的执行顺序。理解它的三种模式至关重要。

### 模式一：`"^build"` — 先构建依赖

```json
"build": {
  "dependsOn": ["^build"]
}
```

**含义**：在构建当前包之前，先构建它所依赖的所有上游包。

**为什么这样做？** 考虑这个依赖链：

```
apps/web → packages/ui → packages/shared
```

当运行 `turbo run build` 时，执行顺序为：

1. 先构建 `packages/shared`（没有上游依赖）
2. 再构建 `packages/ui`（依赖 `shared`）
3. 最后构建 `apps/web`（依赖 `ui` 和 `shared`）

如果没有 `^`，Turborepo 不会自动处理依赖顺序，你的构建可能会因为找不到类型定义或编译产物而失败。

**实际执行过程演示**：

```bash
$ turbo run build

• Packages in scope: web, api, shared, ui, database, eslint-config, tsconfig
• Running build in 7 packages
• Remote caching disabled

  ↓ shared:build     # 没有上游依赖，最先执行
  ↓ ui:build         # 等 shared 完成后执行
  ↓ database:build   # 与 ui 并行执行（无依赖关系）
  ↓ api:build        # 等 database 和 shared 完成后执行
  ↓ web:build        # 等 ui 和 shared 完成后执行

Tasks:    5 successful, 5 total
Cached:   0 cached, 5 total
Time:     12.3s
```

注意 `database` 和 `ui` 是**并行执行**的——因为它们之间没有依赖关系。这正是 Turborepo 的价值所在。

### 模式二：`"build"`（不带 `^`）— 只依赖自身

```json
"test": {
  "dependsOn": ["build"]
}
```

**含义**：在运行当前包的 `test` 之前，先运行**同一个包**的 `build`。

**为什么不用 `^build`？** 测试只需要当前包自己构建好就行，不需要等上游包构建完。上游包的 `dist` 在之前运行 `turbo run build` 时已经生成了（或者有缓存），不需要重新构建。这样可以节省时间。

> **细微差别**：`"build"` 是指当前包的 build，`"^build"` 是指上游包的 build。理解这个区别能帮你写出更高效的任务配置。

### 模式三：`[]` — 无依赖

```json
"lint": {
  "dependsOn": []
}
```

**含义**：这个任务不依赖任何其他任务，可以立即开始。

但实际上，lint 通常需要 TypeScript 类型信息才能正确运行（比如 `@typescript-eslint` 的规则需要类型检查），所以我们通常会写成 `"dependsOn": ["^build"]`。只有在任务确实不需要任何构建产物时，才使用空数组。

一个典型的使用空数组的场景是 `format`（代码格式化）：

```json
"format": {
  "dependsOn": [],
  "cache": false
}
```

格式化不需要构建产物，也不依赖其他包，可以立即并行运行。

## 10.6 `inputs` 和 `outputs` 配置

### `inputs`：告诉 Turborepo 哪些文件影响任务结果

```json
"build": {
  "inputs": ["src/**", "tsconfig.json", "package.json"]
}
```

**含义**：只有当这些文件发生变化时，Turborepo 才认为需要重新执行构建。如果你只改了 `README.md`，缓存仍然命中，构建会被跳过。

**为什么 `package.json` 也在 inputs 里？** 因为依赖版本的变化（比如升级了 Vue 的版本）也会影响构建结果。如果不监控 `package.json`，升级依赖后缓存仍然命中，就会导致产物不一致。

### `outputs`：告诉 Turborepo 任务会产出什么

```json
"build": {
  "outputs": ["dist/**"]
}
```

**含义**：构建任务会在 `dist/` 目录下生成文件。Turborepo 会把这些文件缓存起来，下次缓存命中时直接恢复 `dist/` 的内容，而不需要重新构建。

> **如果忘记配置 outputs 会怎样？** Turborepo 仍然会缓存任务的日志输出（stdout/stderr），但不会缓存文件产物。这意味着缓存命中时 `dist/` 目录不会被恢复，下游包的构建会失败。

## 10.7 `cache` 和 `persistent`

```json
"dev": {
  "cache": false,
  "persistent": true
}
```

- **`cache: false`**：`dev` 任务（如 `vite dev`、`nodemon`）是长期运行的开发服务器，每次启动都是新鲜的，缓存没有意义。
- **`persistent: true`**：告诉 Turborepo 这是一个长期运行的进程（不会自动退出）。当你对 `turbo run dev` 按下 `Ctrl+C` 时，所有子进程会一起终止。

> **为什么 dev 需要 persistent？** 如果不设置，Turborepo 会认为 dev 任务应该在有限时间内完成，可能会在超时后强制终止。更重要的是，`persistent` 任务不会被并行调度——Turborepo 知道它们会一直占用进程。

## 10.8 `globalDependencies` 和环境变量

```json
{
  "$schema": "https://turbo.build/schema.json",
  "globalDependencies": [".env", "tsconfig.base.json"],
  "globalEnv": ["NODE_ENV", "CI"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "env": ["API_BASE_URL", "DATABASE_URL"],
      "inputs": ["src/**", "tsconfig.json", "package.json"],
      "outputs": ["dist/**"]
    }
  }
}
```

### `globalDependencies`

```json
"globalDependencies": [".env", "tsconfig.base.json"]
```

**含义**：这些文件的变化会导致**所有任务**的缓存失效。

**为什么需要？** 根目录的 `.env` 文件可能包含影响所有包的环境变量（如 API 密钥），`tsconfig.base.json` 是所有包共享的 TypeScript 配置。它们的变化会影响所有构建结果，所以必须被监控。

### `globalEnv` 和任务级 `env`

```json
"globalEnv": ["NODE_ENV", "CI"],
"tasks": {
  "build": {
    "env": ["API_BASE_URL", "DATABASE_URL"]
  }
}
```

**含义**：环境变量的值也会参与缓存哈希的计算。

**为什么需要？** 考虑这个场景：你在 `NODE_ENV=development` 下构建了项目，然后切换到 `NODE_ENV=production` 重新构建。如果不声明 `env`，Turborepo 会认为源码没变，直接返回 development 模式的缓存产物——这在生产中是致命的。

`globalEnv` 影响所有任务，任务级 `env` 只影响特定任务。建议将通用的环境变量（`NODE_ENV`、`CI`）放在 `globalEnv`，将业务相关的放在任务级。

## 10.9 实际运行：执行顺序和输出

让我们看看几个典型的运行场景。

### 场景一：`turbo run build`

```bash
$ turbo run build

turbo 2.4.0

• Packages in scope: @monorepo/web, @monorepo/api, @monorepo/shared,
  @monorepo/ui, @monorepo/database, @monorepo/eslint-config, @monorepo/tsconfig
• Running build in 7 packages
• Remote caching disabled

@monorepo/tsconfig:build: cache miss
@monorepo/tsconfig:build: > @monorepo/tsconfig@0.1.0 build
@monorepo/tsconfig:build: > tsc -p tsconfig.json

@monorepo/shared:build: cache miss
@monorepo/shared:build: > @monorepo/shared@0.1.0 build
@monorepo/shared:build: > tsup src/index.ts --format esm,cjs --dts

@monorepo/ui:build: cache miss, depends on @monorepo/shared
@monorepo/database:build: cache miss, depends on @monorepo/shared
  # ui 和 database 并行构建

@monorepo/api:build: cache miss, depends on @monorepo/database, @monorepo/shared
@monorepo/web:build: cache miss, depends on @monorepo/ui, @monorepo/shared

Tasks:    6 successful, 6 total
Cached:   0 cached, 6 total
Time:     18.7s
```

### 场景二：再次运行 `turbo run build`（缓存命中）

```bash
$ turbo run build

turbo 2.4.0

• Running build in 7 packages

@monorepo/tsconfig:build: cache hit, skipping
@monorepo/shared:build: cache hit, skipping
@monorepo/ui:build: cache hit, skipping
@monorepo/database:build: cache hit, skipping
@monorepo/api:build: cache hit, skipping
@monorepo/web:build: cache hit, skipping

Tasks:    6 successful, 6 total
Cached:   6 cached, 6 total
Time:     0.8s    # 从 18.7s 降到 0.8s！
```

**这就是 Turborepo 的魔力**：第二次运行时，所有任务都命中缓存，执行时间从 18.7 秒降到 0.8 秒。

### 场景三：只改了 shared 包的一个文件

```bash
$ turbo run build

@monorepo/shared:build: cache miss     # shared 源码变了，缓存失效
@monorepo/ui:build: cache miss         # 依赖 shared，也需要重新构建
@monorepo/database:build: cache miss   # 依赖 shared，也需要重新构建
@monorepo/api:build: cache miss        # 依赖 database 和 shared
@monorepo/web:build: cache miss        # 依赖 ui 和 shared
@monorepo/tsconfig:build: cache hit    # tsconfig 没变，缓存命中

Tasks:    6 successful, 6 total
Cached:   1 cached, 6 total
Time:     15.2s
```

修改 `shared` 会导致所有依赖它的包重新构建，这是正确的行为——因为它们的输入确实变了。

### 场景四：使用 `--filter` 只构建特定包

```bash
# 只构建 web 及其依赖
$ turbo run build --filter=@monorepo/web

• Packages in scope: @monorepo/web, @monorepo/shared, @monorepo/ui
• Running build in 3 packages

@monorepo/shared:build: cache hit
@monorepo/ui:build: cache hit
@monorepo/web:build: cache miss

Tasks:    3 successful, 3 total
```

`--filter` 让你只构建需要的包及其依赖，在大型 monorepo 中非常有用。

## 10.10 与 npm scripts 的对比

| 特性 | npm scripts | Turborepo |
| ------ | ------------- | ----------- |
| 执行顺序 | 手动管理，容易出错 | 自动分析依赖关系 |
| 并行度 | 串行执行 | 最大化并行 |
| 缓存 | 无 | 基于内容哈希的自动缓存 |
| 过滤 | 需要手动 `cd` 到目录 | `--filter` 精确控制 |
| 增量构建 | 不支持 | 只运行受影响的包 |
| 远程缓存 | 不可能 | 原生支持 |
| 执行图可视化 | 无 | `turbo run build --graph` |

一个实际的对比数据：在一个包含 15 个包的 monorepo 中，全量构建从 npm scripts 的 45 秒降低到 Turborepo 的 12 秒（首次），后续运行降至 1 秒以内。

## 10.11 为各个包添加构建脚本

为了让 Turborepo 能够编排任务，每个包都需要在 `package.json` 中定义对应的 scripts。

**packages/shared/package.json**：

```json
{
  "name": "@monorepo/shared",
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts",
    "dev": "tsup src/index.ts --format esm,cjs --dts --watch",
    "lint": "eslint src/",
    "test": "vitest run",
    "typecheck": "tsc --noEmit"
  }
}
```

**packages/ui/package.json**：

```json
{
  "name": "@monorepo/ui",
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts --external vue",
    "dev": "tsup src/index.ts --format esm,cjs --dts --external vue --watch",
    "lint": "eslint src/",
    "test": "vitest run",
    "typecheck": "tsc --noEmit"
  }
}
```

**apps/web/package.json**：

```json
{
  "name": "@monorepo/web",
  "scripts": {
    "build": "vite build",
    "dev": "vite",
    "lint": "eslint src/",
    "typecheck": "vue-tsc --noEmit"
  }
}
```

**apps/api/package.json**：

```json
{
  "name": "@monorepo/api",
  "scripts": {
    "build": "tsup src/index.ts --format cjs --clean",
    "dev": "tsx watch src/index.ts",
    "lint": "eslint src/",
    "test": "vitest run",
    "typecheck": "tsc --noEmit"
  }
}
```

## 10.12 使用 `--graph` 可视化任务依赖

```bash
# 生成任务依赖图（输出 DOT 格式）
turbo run build --graph

# 或者生成可交互的 HTML 页面（Turborepo 2.x）
turbo run build --graph=build-graph.html
```

输出的 DOT 格式可以粘贴到 [Graphviz Online](https://dreampuf.github.io/GraphvizOnline/) 查看，或者直接在浏览器中打开生成的 HTML 文件。这对于理解大型 monorepo 的依赖关系非常有帮助。

## 本章小结

本章我们学习了 Turborepo 的核心概念和配置方法：

1. **为什么需要 Turborepo**：手动管理 monorepo 中的任务顺序既低效又容易出错，Turborepo 自动分析依赖、最大化并行、智能缓存
2. **三种 `dependsOn` 模式**：`^build`（先构建上游依赖）、`build`（先构建自身）、`[]`（无依赖）
3. **`inputs` 和 `outputs`**：精确控制哪些文件影响任务结果，哪些文件需要被缓存
4. **环境变量**：通过 `env` 和 `globalEnv` 确保环境变量变化时缓存正确失效
5. **实际运行**：Turborepo 会根据依赖图自动安排执行顺序，并通过缓存大幅加速后续构建
