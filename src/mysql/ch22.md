# 第22章 InnoDB Cluster 与高可用

想象你是一个快递公司的调度中心经理。你不可能只有一个分拣中心——万一停电了，所有快递都发不出去。你需要多个分拣中心，而且当一个中心出问题时，包裹要能自动路由到其他中心。MySQL 的高可用架构，就是给你的数据建一套"智能分拣网络"。

## 22.1 MySQL 高可用架构概览

高可用（High Availability, HA）的核心目标是：当主节点故障时，能自动切换到备用节点，尽量减少服务中断时间。在高可用的世界里，有一个重要的指标叫"几个9"。99.9% 的可用性意味着一年最多停机 8.76 小时；99.99% 意味着最多停机 52.6 分钟；99.999% 意味着最多停机 5.26 分钟。每多一个9，背后的技术复杂度和成本都是指数级增长的。

MySQL 的高可用方案经历了漫长的演进过程。最早大家用简单的主从复制加手动切换，出了问题 DBA 半夜爬起来手动操作，从发现问题到恢复服务可能需要半小时甚至更久。后来出现了 MHA 这样的自动化工具，把故障切换时间缩短到几十秒。再到 MySQL 5.7，官方推出了 Group Replication，从根本上改变了 MySQL 的复制模型，用 Paxos 共识协议保证了数据一致性。最终在 MySQL 8.0，InnoDB Cluster 成为了官方推荐的高可用方案，集成了管理、路由和复制三大组件。

常见的高可用方案：

| 方案 | 自动故障切换 | 数据一致性 | 复杂度 | 适用场景 |
|------|-------------|-----------|--------|---------|
| 主从 + MHA | 是 | 半同步 | 中 | 传统架构 |
| InnoDB Cluster | 是 | 强一致 | 中 | 官方推荐 |
| Orchestrator | 是 | 取决于复制 | 高 | 大规模集群 |
| 云数据库RDS | 自动 | 强一致 | 低 | 云环境 |

## 22.2 MySQL Group Replication（MGR）

MGR 是 MySQL 官方提供的组复制功能，基于 Paxos 协议实现多节点数据一致性。你可以把 MGR 想象成一个"民主投票系统"——每当有数据变更发生时，所有节点通过投票来达成一致意见，而不是由某个节点"独裁"决定。

Paxos 协议的核心思想其实并不复杂：一个事务要想被提交，必须获得集群中超过半数节点的同意。这意味着在三节点集群中，至少需要两个节点同意；在五节点集群中，至少需要三个节点同意。这个"多数派"原则保证了即使部分节点故障，只要多数节点还在，集群就能继续工作。

**MGR 的核心特性：**

- 多节点数据强一致性（基于 Paxos 共识）
- 自动成员管理（节点加入/离开）
- 自动冲突检测和处理
- 支持单主模式和多主模式

```sql
-- 配置 Group Replication（每个节点都需要）
[mysqld]
# 基础复制配置
server-id = 1
gtid_mode = ON
enforce_gtid_consistency = ON
binlog_checksum = NONE

# Group Replication 专用配置
plugin_load_add = 'group_replication.so'
group_replication_group_name = "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee"
group_replication_start_on_boot = OFF
group_replication_local_address = "192.168.1.100:33061"
group_replication_group_seeds = "192.168.1.100:33061,192.168.1.101:33061,192.168.1.102:33061"

# 单主模式（推荐）
group_replication_single_primary_mode = ON
```

**启动 Group Replication：**

```sql
-- 在第一个节点（Primary）上
SET GLOBAL group_replication_bootstrap_group = ON;
START GROUP_REPLICATION;
SET GLOBAL group_replication_bootstrap_group = OFF;

-- 在其他节点上
START GROUP_REPLICATION;

-- 查看集群成员状态
SELECT * FROM performance_schema.replication_group_members;
```

## 22.3 InnoDB Cluster 架构

InnoDB Cluster 是 MySQL 官方的完整高可用解决方案，由三个组件组成：

```
┌─────────────────────────────────────────┐
│           InnoDB Cluster                 │
│                                          │
│  ┌─────────┐  ┌──────────┐  ┌────────┐ │
│  │ MySQL   │  │ MySQL    │  │ MySQL  │ │
│  │ Server  │  │ Server   │  │ Server │ │
│  │(Primary)│  │(Secondary)│ │(Second)│ │
│  │  MGR    │  │  MGR     │  │  MGR   │ │
│  └────┬────┘  └────┬─────┘  └───┬────┘ │
│       └──────────┬──┴────────────┘      │
│                  │                       │
│           ┌──────┴──────┐               │
│           │MySQL Router │               │
│           └──────┬──────┘               │
│                  │                       │
│           ┌──────┴──────┐               │
│           │ MySQL Shell │               │
│           └─────────────┘               │
└─────────────────────────────────────────┘
```

- **MGR**：负责数据复制和自动故障切换
- **MySQL Shell**：管理工具，用于配置和管理集群
- **MySQL Router**：透明路由层，应用连接 Router 即可，不需要知道哪个节点是 Primary

## 22.4 MySQL Shell 简介

MySQL Shell 是一个高级客户端工具，支持 SQL、JavaScript 和 Python 三种模式。与传统的 mysql 命令行客户端相比，MySQL Shell 更像是一个"全能的遥控器"——你不仅可以用它执行 SQL 查询，还可以用它管理 InnoDB Cluster、执行自动化运维脚本、甚至编写 Python 脚本来批量处理数据。它是 InnoDB Cluster 生态系统中不可或缺的管理工具，所有的集群创建、节点添加、状态检查等操作都通过 MySQL Shell 来完成。

```javascript
// 启动 MySQL Shell
// mysqlsh

// 连接到 MySQL 实例
\connect root@192.168.1.100:3306

// 检查实例是否满足 InnoDB Cluster 的要求
dba.checkInstanceConfiguration('root@192.168.1.100:3306')

// 自动配置实例（修复不满足条件的配置）
dba.configureInstance('root@192.168.1.100:3306')
```

## 22.5 InnoDB Cluster 搭建步骤

```javascript
// Step 1：配置所有节点
// 在每个节点上执行
dba.configureInstance('root@192.168.1.100:3306')
dba.configureInstance('root@192.168.1.101:3306')
dba.configureInstance('root@192.168.1.102:3306')

// Step 2：创建集群（在第一个节点上）
shell.connect('root@192.168.1.100:3306')
var cluster = dba.createCluster('myCluster')

// Step 3：添加其他节点
cluster.addInstance('root@192.168.1.101:3306')
cluster.addInstance('root@192.168.1.102:3306')

// Step 4：检查集群状态
cluster.status()

// 输出示例：
// {
//   "clusterName": "myCluster",
//   "status": "OK",
//   "topology": {
//     "192.168.1.100:3306": { "mode": "R/W", "status": "ONLINE" },
//     "192.168.1.101:3306": { "mode": "R/O", "status": "ONLINE" },
//     "192.168.1.102:3306": { "mode": "R/O", "status": "ONLINE" }
//   }
// }
```

**集群管理操作：**

```javascript
// 移除节点
cluster.removeInstance('root@192.168.1.102:3306')

// 重新加入节点
cluster.rejoinInstance('root@192.168.1.102:3306')

// 手动切换 Primary
cluster.setPrimaryInstance('root@192.168.1.101:3306')

// 解散集群
cluster.dissolve()

// 从集群获取连接信息
cluster.listRouters()
```

## 22.6 MySQL Router

MySQL Router 是一个轻量级中间件，负责将应用的连接路由到正确的 MySQL 节点。你可以把它想象成一个智能邮递员——你只需要把信交给邮递员，他负责找到正确的收件人。应用代码不需要知道集群有几个节点、哪个是主节点、哪个是从节点，Router 会自动维护一份集群拓扑的缓存，并在拓扑发生变化时自动更新。

MySQL Router 的最佳实践是部署在应用服务器上（与应用程序同机部署），而不是单独部署一台 Router 服务器。这样做的好处是减少了网络跳数，降低了延迟。同时，即使 Router 进程挂了，也只影响本机上的应用，不会影响整个集群。Router 的资源消耗非常低，通常只需要很少的 CPU 和内存，不会和应用争抢资源。

```sql
-- 部署 MySQL Router（在应用服务器上）
-- mysqlrouter --bootstrap root@192.168.1.100:3306 --directory /opt/mysqlrouter

-- 启动 Router
-- /opt/mysqlrouter/start.sh

-- Router 默认端口：
-- 6446：读写端口（路由到 Primary）
-- 6447：只读端口（路由到 Secondary，轮询负载均衡）
```

**应用连接配置：**

```javascript
// Node.js 应用通过 MySQL Router 连接
const mysql = require('mysql2/promise');

// 写操作 → 6446 端口 → 自动路由到 Primary
const writePool = mysql.createPool({
  host: '192.168.1.200', // Router 所在地址
  port: 6446,
  user: 'app_user',
  password: 'app_pass',
  database: 'mydb',
  connectionLimit: 10,
});

// 读操作 → 6447 端口 → 轮询路由到 Secondary
const readPool = mysql.createPool({
  host: '192.168.1.200',
  port: 6447,
  user: 'app_user',
  password: 'app_pass',
  database: 'mydb',
  connectionLimit: 20,
});

// 当 Primary 故障时，MGR 自动选举新 Primary
// Router 自动感知拓扑变化，更新路由
// 应用代码完全不需要修改！
```

> **Tip：** MySQL Router 的"透明路由"是 InnoDB Cluster 最大的优势之一。应用程序不需要关心哪个节点是主节点，Router 会自动处理一切。

**MySQL Router 的高级配置：**

```sql
-- mysqlrouter.conf 核心配置
[routing:primary]
bind_address = 0.0.0.0
bind_port = 6446
destinations = metadata-cache://myCluster/?role=PRIMARY
routing_strategy = first-available
protocol = classic

[routing:secondary]
bind_address = 0.0.0.0
bind_port = 6447
destinations = metadata-cache://myCluster/?role=SECONDARY
routing_strategy = round-robin-with-fallback
protocol = classic

-- round-robin-with-fallback 策略：
-- 正常情况下轮询所有 Secondary 节点
-- 当所有 Secondary 都不可用时，回退到 Primary 节点
-- 这保证了即使所有从库都挂了，读请求仍然能被处理
```

## 22.7 MGR 冲突检测与处理

Group Replication 使用"认证"(Certification)机制来检测事务冲突。当一个事务准备提交时，MGR 会检查这个事务修改的数据行（write set）是否与其他正在进行的事务冲突。

```sql
-- 查看认证相关的统计信息
SELECT * FROM performance_schema.group_replication_flow_control;

-- 查看冲突检测统计
SELECT count_transactions_in_queue,
       count_transactions_checked,
       count_conflicts_detected
FROM performance_schema.replication_group_member_stats\G

-- 查看当前在队列中等待认证的事务数量
SELECT COUNT(*) AS pending_certification 
FROM performance_schema.group_replication_certification_queue;
```

MGR 冲突检测的原理：每个事务在提交前会被广播到所有节点。每个节点独立执行认证检查——将当前事务的 write set 与最近已认证事务的 write set 进行比对。如果两个事务修改了同一行数据，后到达的事务会被拒绝。这种方式确保了所有节点的数据最终一致。

```sql
-- 调整认证窗口大小
-- group_replication_certification_window 控制保留多少个历史事务用于冲突检测
-- 默认值为 0（自动调整），通常不需要手动设置
SET GLOBAL group_replication_certification_window = 0;

-- 流控（Flow Control）
-- 当某个节点落后太多时，MGR 会主动降低整体写入速度
-- 这防止了快节点把慢节点远远甩开
SHOW STATUS LIKE 'group_replication_flow_control%';
```

> **Warning：** 如果你的业务有大量并发更新同一行数据的场景（比如热门商品的库存扣减），MGR 的冲突检测可能导致大量事务被拒绝。这种情况下，需要在应用层做排队或合并处理。

## 22.8 集群故障场景与应对

理解各种故障场景下集群的行为，对于运维人员来说至关重要。

**场景1：Primary 节点宕机**

当 Primary 节点突然宕机时，MGR 会自动触发选举流程。剩余的 Secondary 节点通过 Paxos 协议投票选出新的 Primary。这个过程通常需要 10-30 秒。在此期间，写操作会暂时失败，读操作可能被路由到旧的 Primary（Router 尚未更新拓扑）。MySQL Router 会在检测到拓扑变化后自动更新路由表。

**场景2：网络分区（脑裂）**

当集群发生网络分区时，节点被分成两个或多个互相不可见的组。MGR 基于 Paxos 协议的多数派原则，只有包含多数节点的分区才能继续工作。例如，三节点集群发生 2:1 分区时，拥有两个节点的分区继续服务，孤立的单节点会自动退出集群。

```javascript
// 监控集群状态的脚本
async function monitorCluster(cluster) {
  const status = cluster.status();
  
  // 检查是否有节点离线
  for (const [addr, info] of Object.entries(status.topology)) {
    if (info.status !== 'ONLINE') {
      console.warn(`Node ${addr} is ${info.status}`);
      // 发送告警通知
      await sendAlert(`MySQL Cluster node ${addr} is ${info.status}`);
    }
  }

  // 检查集群整体状态
  if (status.status !== 'OK') {
    console.error('Cluster status:', status.status);
    // 可能需要人工介入
    await sendAlert('MySQL Cluster status is not OK: ' + status.status);
  }
}

// 每30秒检查一次
setInterval(() => monitorCluster(cluster), 30000);
```

**场景3：Secondary 节点数据落后**

当某个 Secondary 节点因硬件性能差或网络带宽不足而严重落后时，MGR 的流控机制会降低整个集群的写入速度。如果落后太多，该节点可能被自动驱逐出集群。此时需要在修复节点后重新加入。

```javascript
// 重新加入被驱逐的节点
// 在 MySQL Shell 中执行
cluster.rejoinInstance('root@192.168.1.102:3306', {
  recoveryMethod: 'clone'  // 使用 Clone 插件快速同步数据
});

// 如果 rejoin 失败，可能需要完全重建节点
// 1. 重置节点
// RESET MASTER; RESET SLAVE ALL;
// 2. 使用 CLONE 从现有节点获取数据
// CLONE INSTANCE FROM 'donor'@'192.168.1.100':3306 IDENTIFIED BY 'pass';
// 3. 重新加入集群
```

> **Tip：** 生产环境中建议部署监控系统（如 Prometheus + Grafana），实时追踪集群各节点的状态、复制延迟、认证冲突次数等关键指标。当出现异常时能第一时间收到告警。

## 22.9 InnoDB ReplicaSet vs InnoDB Cluster

MySQL 8.0.19 引入了 InnoDB ReplicaSet，它是一个简化版的高可用方案。

```javascript
// InnoDB ReplicaSet：基于异步复制，不使用 MGR
// 适合小规模、对一致性要求不高的场景

// 创建 ReplicaSet
shell.connect('root@192.168.1.100:3306')
var rs = dba.createReplicaSet('myReplicaSet')
rs.addInstance('root@192.168.1.101:3306')

// 主要区别：
// InnoDB Cluster: 基于 MGR，数据强一致，自动故障切换
// ReplicaSet:     基于异步复制，可能丢数据，需要手动切换
```

| 特性 | InnoDB Cluster | InnoDB ReplicaSet |
|------|---------------|-------------------|
| 复制方式 | Group Replication | 异步复制 |
| 数据一致性 | 强一致 | 最终一致 |
| 故障切换 | 自动 | 手动/半自动 |
| 复杂度 | 中 | 低 |
| 性能开销 | 较高 | 低 |

## 22.10 高可用方案对比

**MHA（Master High Availability）：**

```sql
-- MHA 是经典的 MySQL 高可用方案
-- 由日本 DeNA 公司开发
-- 核心功能：监控 Master 状态，自动故障切换

-- 优点：成熟稳定，社区资料丰富
-- 缺点：需要额外部署 MHA Manager 节点
--       不支持多主，不支持读写分离路由
--       项目已停止活跃维护
```

**Orchestrator：**

```sql
-- GitHub 开源的 MySQL 高可用管理工具
-- 支持拓扑可视化、自动故障检测与恢复
-- 适合大规模 MySQL 集群管理

-- 优点：功能强大，拓扑可视化，支持多种故障切换策略
-- 缺点：配置复杂，学习曲线陡峭
```

> **Tip：** 如果你是新项目，推荐直接使用 InnoDB Cluster。它是 MySQL 官方的主推方案，集成度高，维护成本低。
