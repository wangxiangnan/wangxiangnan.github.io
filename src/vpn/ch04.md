## 4.1 客户端配置解剖——[Interface] 与 [Peer]

客户端 conf 与服务端结构相同、内容镜像，先看笔记本的全文（`/etc/wireguard/clients/laptop.conf`）：

```ini
[Interface]
# 本机在 VPN 网段的地址：必须与服务器 [Peer] 段的 AllowedIPs 一致
Address = 10.66.66.2/24
# 本机私钥：3.7 在服务器生成的那份
PrivateKey = 8HfD...(laptop_private.key 的内容)
# DNS：本机解析域名用哪个服务器（4.5 详解）
DNS = 1.1.1.1

[Peer]
# 对面那台服务器
PublicKey = k5S+1x...(server_public.key 的内容)
# 服务器的公网地址与端口（外层）
Endpoint = 203.0.113.10:51820
# 目的地是 VPN 网段的包走隧道（分流模式）
AllowedIPs = 10.66.66.0/24
# NAT 保活（2.6 的原理在这里落地）
PersistentKeepalive = 25
```

镜像关系一目了然，也是排错时的核对表：

| 字段 | 客户端侧的值 | 服务端侧的对应 | 必须一致吗 |
| ---- | ---- | ---- | ---- |
| PublicKey（Peer） | 服务器公钥 | 客户端公钥（3.7） | 互换——我信你的公钥，你信我的 |
| Address / AllowedIPs | 10.66.66.2/24 | 10.66.66.2/32 | **严格一致**，/24 与 /32 不冲突（掩码方向相反） |
| PrivateKey | laptop 私钥 | laptop 公钥 | 数学上配对 |
| Endpoint | 服务器公网地址 | ——（客户端地址自动漫游） | 客户端单侧写 |

先修提醒：「Address 里的 /24」是**本机在网段内的掩码**，「AllowedIPs 里的 /32」是**白名单的精确度**——两者不矛盾，2.5 的双重语义还记得吧？地址写错（比如两台客户端都用 .2）不会有任何报错，只有「时通时断」这种慢性症状，4.7 的排障表里有它。

## 4.2 AllowedIPs 的抉择——分流还是全隧道

这是每个客户端都要面对的一次性决策，两种写法的差别：

| 写法 | 行为 | 适用 | 代价 |
| ---- | ---- | ---- | ---- |
| `AllowedIPs = 10.66.66.0/24` | **分流**：只有 VPN 网段的包进隧道 | 日常办公：只访问内网服务，其余照常上网 | 内网之外的服务不受保护 |
| `AllowedIPs = 0.0.0.0/0` | **全隧道**：所有流量都进隧道 | 咖啡馆公共 Wi-Fi 全防护、出网审计 | 全部流量绕道服务器，速度受限于服务器带宽 |

分流模式的路由决策，用一张 text 图钉死：

```text
目标 10.66.66.1   → 命中 AllowedIPs 10.66.66.0/24 → 进 wg0 隧道
目标 192.168.1.20 → 不命中（家里内网 ≠ VPN 网段）  → 走物理网卡（原路）
目标 8.8.8.8      → 不命中                        → 走物理网卡（原路）
```

全隧道模式有两个专属细节，正是「先猜再读」第一问的答案：`0.0.0.0/0` 时连 `1.1.1.1` 也进隧道——所有流量。这时 `wg-quick` 会悄悄做一件大事：**策略路由**。它加一组 `ip rule`，把「目的地是 Endpoint 公网地址的包」排除在隧道之外，只走物理网卡——否则加密后的握手包自己也要进隧道，形成死循环，隧道永远起不来。分流模式没有这套机制，因为不存在循环风险。

想亲眼看到这套机制，全隧道建立后跑 `ip rule show`：会多出三条规则、一张以端口号命名的独立路由表（常见为 table 51820），Endpoint 的公网地址在其中指向物理网卡。**不需要背诵这些数字**——只要知道「全隧道起得来，是 wg-quick 替你处理了 Endpoint 死循环」，排障时看到 `ip rule` 里多出来的东西不惊慌即可。

另外一个实用差异：**全隧道下 DNS 也被接管**（见 4.5），而分流下 DNS 查询按路由表走物理网卡——咖啡馆里想防 DNS 泄漏，就得选全隧道，或者接受 4.5 的折中方案。

建议默认分流：内网服务才是自建 VPN 的主业，全隧道的代价（绕远、耗服务器带宽）通常不值得。两个场景各存一份 conf（`laptop.conf` 与 `laptop-full.conf`），按需切换——第五章的发放脚本支持这种一设备多配置。

## 4.3 三端官方客户端

conf 有了，交给设备。三个平台的官方客户端，导入方式不同、语义完全一致：

| 平台 | 安装 | 导入方式 |
| ---- | ---- | ---- |
| Linux | 发行版包管理器（第三章装服务端时已含） | `wg-quick up /etc/wireguard/clients/laptop.conf`，或把文件放到 `/etc/wireguard/wg0.conf` 后 `wg-quick@wg0` |
| Windows | 官方 MSI（wireguard.com/install） | 「Import tunnel(s) from file」选 conf；或「Add empty tunnel」粘贴 |
| macOS | App Store「WireGuard」 | 同 Windows，文件导入或粘贴 |

Linux 的用法有一个细节：`wg-quick up <路径>` 任意路径皆可起，但 `systemctl enable wg-quick@<名字>` 只认 `/etc/wireguard/<名字>.conf`——笔记本长期用就把文件放标准位置。Windows/macOS 客户端是常驻托盘程序，conf 导入后变成一个可开关的「隧道」条目，Activate 即通，语义与 `wg-quick up` 相同。

导入后，桌面客户端里能看到与 `wg show` 一致的信息（公钥、Endpoint、握手状态）——同一内核协议，只是穿了 GUI 外衣。

下载渠道统一认官方（wireguard.com/install 或系统应用商店）：这类管理隧道的软件权限极高（装虚拟网卡、改系统路由），第三方分发渠道的安装包没有理由去冒这个险。第七章的 mihomo 系客户端同理——它在更高权限上接管流量，来源更要干净。

## 4.4 手机扫码——qrencode 与密钥安全

手机没有方便的文件传输，官方 App 提供二维码导入。服务器上装一个生成器：

**命令格式**：`qrencode [OPTIONS] [TEXT|FILE]`

```text
$ sudo apt install -y qrencode
$ qrencode -t ansiutf8 < /etc/wireguard/clients/laptop.conf
```

终端里会打印出一个 ASCII 二维码，手机 WireGuard App（iOS/Android）点「+」→「Scan from QR code」扫描，隧道条目立即出现。conf 里包含私钥与全部配置，二维码即整份配置——比 AirDrop、微信传文件都干净：**私钥全程不出服务器终端**，不经过任何第三方通道。

然后是「先猜再读」第二问的答案：扫码完成之后，服务器上的 `laptop_private.key` 就**完成了历史使命**——它的唯一用途是生成这份 conf，conf 已进入手机，私钥「本体」就该被归档或删除（第五章 5.4 的 revoke 脚本做同样的归档动作）。保留一份私钥多留一份泄露面；真要重装，重新生成一对密钥、更新服务端 Peer 公钥即可，全程两分钟。

同理，二维码本身是敏感物：投屏会议、远程共享屏幕时绝不能开着它。生成 → 扫码 → 关闭窗口，一气呵成。

一张 conf 的泄露面清单，发放前过一遍：

- conf 文件包含**私钥**——泄露等价于设备被冒充（2.4 讲过：冒充的是「未来」，不是历史流量，但同样致命）；
- 传输路径只有两条是干净的：面对面扫码、加密通道（SSH）传文件；聊天软件、邮件、网盘都不合格；
- 服务器侧的 `clients/` 目录权限 700、私钥文件 600（第三章已设）——目录本身是防线的一部分。

## 4.5 DNS 与内网解析

`DNS = 1.1.1.1` 这行让客户端把系统 DNS 指向 1.1.1.1。注意它的路由归属与 AllowedIPs 联动：

| 需求 | DNS 填什么 | 实际效果 |
| ---- | ---- | ---- |
| 只要能解析公网域名 | `1.1.1.1`（或 8.8.8.8） | 分流模式下查询包走物理网卡明文发出——正常，但公共 Wi-Fi 里 DNS 可见 |
| 公共 Wi-Fi 全防护（全隧道） | `1.1.1.1` | 查询包进隧道，从服务器发出——DNS 也被保护 |
| 要解析内网域名（如 `nas.home.lan`） | `10.66.66.1` | 查询进隧道打给服务器——前提是 6.4 的 dnsmasq 已部署 |

三条路线的选择规则一句话：**DNS 的保护级别要跟着 AllowedIPs 走**。分流 + 公网 DNS 是日常默认；全隧道模式下若 DNS 仍指本地运营商 DNS，查询会被强制送进隧道并因为「目的地不在 AllowedIPs」而失败——这是全隧道配完「能 ping IP 不能开网页」的经典原因，改 DNS 即愈。

第六章 6.4 会给服务器装 dnsmasq，让 `DNS = 10.66.66.1` 解析内网域名；现在用 `1.1.1.1` 保持最小依赖。

## 4.6 漫游实测与保活的体感

配置导入、状态亮起之后，专门花五分钟实测 2.6 讲过的两个机制——它们的体感值得亲眼确认：

**漫游实测**，四步走：

1. 手机连家里 Wi-Fi，服务器上 `wg show` 记下当前 `endpoint` 地址；
2. 手机关 Wi-Fi 切 4G，立即 `ping 10.66.66.1`——第一个包就通，没有「重连」等待；
3. 服务器再看 `wg show`：`endpoint` 已自动变成新的运营商出口地址；
4. 结论：2.6 的「端点自动跟随」成立，漫游零配置。

**保活实测**，对照组设计：

1. 把手机 conf 里的 `PersistentKeepalive = 25` 临时删掉并重新导入；
2. 手机锁屏静置十分钟（无后台拉数据的 App）；
3. 解锁访问 `10.66.66.1`——大概率超时或高延迟：NAT 映射已回收，等下一次握手重建；
4. 把保活加回来重复同样流程——秒通。两相对比，这行小配置守护的东西一目了然。

局限也要交代：**两端都在 NAT 后**（比如家里和公司都没有公网 IP）时，谁也主动够不着谁，保活救不了——需要中转或打洞，第六章 6.3 顺带给出方案。本书主线（公网服务器做网关）天然没有这个问题。

## 4.7 验证清单与抓包排障

接入完成的验证三连：

```text
手机/笔记本:  ping 10.66.66.1                 # 隧道内连通
服务器:       wg show                          # latest handshake 不再是 never
服务器:       tcpdump -ni ens3 'udp port 51820' -c 5   # 公网侧见到客户端的包
```

第三条的抓包是排障的关键入口——它把「客户端发没发包」和「服务器收没收包」隔离开。工具速成：

**命令格式**：`tcpdump [OPTIONS] [FILTER]`

```text
$ sudo tcpdump -ni ens3 'udp port 51820' -c 5
15:42:01.113 IP 198.51.100.7.41234 > 203.0.113.10.51820: UDP, length 148
```

`length 148` 正是 2.3 的握手包尺寸——见到它，说明握手已经到达服务器，链路物理层完好；**抓不到包**则问题在两道防火墙门或客户端侧。

物理链路验证之后，还有第二层抓包：**隧道内侧看明文**。服务器上再开一个终端抓 wg0：

```text
$ sudo tcpdump -ni wg0 'icmp' -c 4
15:43:10.882 IP 10.66.66.2 > 10.66.66.1: ICMP echo request
```

看到 `10.66.66.2` 的明文 ICMP 说明解密与路由全部正常。两层抓包的位置不同、读法不同：`ens3` 上看到的是**加密外层**（证明包到得了），`wg0` 上看到的是**明文内层**（证明密钥对得上、AllowedIPs 放行了）。两层对照，任何「连得上但走不通」的问题都能定位到具体环节——这正是 2.5 cryptokey 路由的现场教学。

完整排障表（按症状查行）：

| 症状 | 最可能原因 | 检查动作 |
| ---- | ---- | ---- |
| 客户端一直转圈，无握手 | 两道门没全开（3.6） | 服务器抓包；空则查安全组与 ufw |
| 有握手，ping 10.66.66.1 不通 | 客户端 AllowedIPs 没含 VPN 网段 | 客户端 conf 对 4.1 核对 |
| ping .1 通，访问内网服务不通 | 服务端转发/NAT 未生效（3.3/3.4） | `sysctl net.ipv4.ip_forward`；`iptables -L FORWARD` |
| 全隧道后能 ping IP、开不了网页 | DNS 没跟上（4.5） | DNS 改 1.1.1.1 或 10.66.66.1 |
| 手机待机一阵后假死 | 缺 PersistentKeepalive（2.6） | conf 补 `= 25` |
| 两台设备时通时断、互踢 | AllowedIPs 地址重叠 | 服务端 [Peer] 段 /32 唯一 |
| 切换网络后高延迟数秒 | 正常漫游开销 | 无需处理，一次握手自动恢复 |

排查纪律：**从外到内、从物理到配置**——先抓包确认物理链路，再核对路由（AllowedIPs），最后查服务端转发。跳层排障（上来就改 conf）是新手最常见的浪费时间。

## 本章小结

- 客户端 conf 与服务端镜像：Peer 公钥互换，Address/AllowedIPs 两侧严格对应；
- AllowedIPs 的一次性抉择：分流（默认）保日常顺畅，全隧道护公共 Wi-Fi，两份 conf 按需切换；
- 全隧道模式由 wg-quick 自动加策略路由，Endpoint 流量永远走物理网卡防死循环——机制存在，你无需手配；
- 三端客户端导入语义一致，Linux 的 `wg-quick up` 与桌面 App 的 Activate 是同一件事；
- 手机扫码 = 配置直送，私钥不经过第三方通道；扫码完成即归档私钥，少留一份泄露面；
- DNS 的保护级别跟着 AllowedIPs 走：全隧道配公网 DNS 会「能 ping 不能开网页」；
- 漫游零配置（端点自动更新）、保活防 NAT 回收——五分钟实测远胜十行文档；
- 排障纪律：先抓包验链路，再核路由，最后查转发——tcpdump 的 `length 148` 就是握手到了。
