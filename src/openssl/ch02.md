# 第2章：哈希与完整性：给文件验明正身

> [!TIP] Part 1: 工具箱入门篇（地基篇）
> 工具箱里的第一件家伙事。上一章认识了 OpenSSL 的三副面孔，本章从全书最简单的命令 `dgst` 开始，解决王哥的第一个问题——怎么知道一份 200MB 的备份文件没坏。

第 8 周，云笔记出了第三幕的第一场事故：恢复演练时，两周前的备份文件解出来一半是零字节——存储系统悄悄损坏了数据，而所有人都以为「备份嘛，有就行了」。更麻烦的是没人说得清**从哪一天开始坏的**，因为根本没有手段判断「这份文件还是不是当初那份」。本章要造的就是这个手段：给每个文件发一枚身份证指纹，任何一丝改动都逃不过比对。

## 2.1 哈希是什么

哈希函数（Hash Function，也叫摘要函数、散列函数）做的事一句话说完：**把任意大小的输入，压成一段固定长度的指纹**。给一个 1 字节的文件和一部 8GB 的电影，SHA-256 都吐出 256 位——用十六进制写出来恒定 64 个字符。

好指纹有四条纪律，每条都对应一个真实需求：

| 性质 | 含义 | 对应的需求 |
| ---- | ---- | ---- |
| 确定性 | 同一输入永远得到同一输出 | 今天算的和下周算的必须能比 |
| 单向性 | 从指纹反推不出原文 | 指纹泄露不等于内容泄露 |
| 雪崩效应 | 原文改 1 个比特，指纹面目全非 | 哪怕只坏一个字节也必被发现 |
| 抗碰撞性 | 找到两个不同输入同指纹，计算上不可行 | 攻击者无法造「替身文件」 |

雪崩效应值得亲手看一次，比任何描述都直观：

```bash
echo -n "cloudnote backup v1" > a.txt
echo -n "cloudnote backup v2" > b.txt
openssl dgst -sha256 a.txt b.txt
```

```text
SHA2-256(a.txt)= e8efd891709aed6ebf0866c31e666b28cbc8564b7c48e483b41b50fbe32bebb5
SHA2-256(b.txt)= 4c1047a5fd4aecdb6705e06599813be577e3afeacf0aa6c3d0a1267e469d67b4
```

原文只差一个字符，两条指纹天差地别——这就是为什么哈希能当「改动探测器」：**不存在悄悄改一点而不被发现的可能**（在抗碰撞成立的前提下，2.3 节会讲这个前提何时被打破）。

> 说明：凡是正文给出了完整命令与输入内容的示例（比如上面这两条），输出都是真实计算结果，可以照抄复现；凡是示例文件（如 `cloudnote-export.sql`）内容未在正文给出的地方，输出的指纹只是**格式示意**，在你机器上必然不同——看格式，别对数值。

> [!NOTE] 术语三胞胎
> 哈希（Hash）、摘要（Digest）、校验和（Checksum）在日常语境里几乎混用。本书的口径：哈希指函数本身，摘要指函数的输出（`dgst` 就是 digest 的缩写），校验和指「用摘要做完整性比对」这个用途。另外注意：Git 的提交号本质也是 SHA 系哈希——你在 Git 教程里其实已经天天用密码学了。

## 2.2 dgst 实战：校验文件

干活的命令是 `openssl dgst`，用法一横排：

```bash
openssl dgst -sha256 cloudnote-export.sql
```

```text
SHA2-256(cloudnote-export.sql) = 9f2c8e7a6d5b4c3a2f1e0d9c8b7a6f5e4d3c2b1a0f9e8d7c6b5a4f3e2d1c0b9
```

几个常用参数一次配齐：

| 参数 | 作用 | 什么时候用 |
| ---- | ---- | ---- |
| `-sha256` | 指定算法（默认可能是 sha256，但显式写出是好习惯） | 任何时候都显式写 |
| `-sha512` | 更长的指纹 | 对超长期存档 |
| `-md5` / `-sha1` | 老算法 | **只为了对接老系统，不要主动用** |
| `-r` | 输出换成 `hash filename` 格式 | 和 coreutils 工具对齐 |
| `-hex` / `-binary` | 输出十六进制 / 原始字节 | 默认 hex；binary 给程序用 |

它和一个你更眼生的工具是同行——Linux 自带的 `sha256sum`。两者算出来的指纹完全相同（都遵循同一算法标准），差别只在输出格式与平台可得性：

```bash
sha256sum cloudnote-export.sql
openssl dgst -r -sha256 cloudnote-export.sql
```

```text
9f2c8e7a6d5b4c3a2f1e0d9c8b7a6f5e4d3c2b1a0f9e8d7c6b5a4f3e2d1c0b9  cloudnote-export.sql
9f2c8e7a6d5b4c3a2f1e0d9c8b7a6f5e4d3c2b1a0f9e8d7c6b5a4f3e2d1c0b9  cloudnote-export.sql
```

注意 `-r` 之后两边格式一致了。那 OpenSSL 版本存在的意义是什么？**跨平台**：macOS 没有 `sha256sum`（只有 `shasum -a 256`），Windows 原生环境两者都没有，而 Git Bash 里 `openssl` 永远在。本书的立场：日常在 Linux 用 `sha256sum`，写文档、写脚本时用 `openssl dgst`，走到哪都能跑。

**真实场景一：校验从官网下载的软件包。** 这个套路你以后会天天用——正规软件发布页都会随包附一份指纹文件，下载完先验指纹再解压：

```bash
curl -LO https://example.com/cloudnote-cli-1.4.2.tar.gz
curl -LO https://example.com/cloudnote-cli-1.4.2.tar.gz.sha256
sha256sum -c cloudnote-cli-1.4.2.tar.gz.sha256
```

```text
cloudnote-cli-1.4.2.tar.gz: OK
```

看到 `OK` 再动手解压。`-c` 是 `--check`，自动读取清单文件逐条核对。如果发布方只给了指纹没给清单文件，手动对比也行——但两边都要复制全文比对，肉眼只看前几位是掩耳盗铃。

**真实场景二：管道流式校验。** `dgst` 不给文件名时从标准输入读，所以可以边下载边算，不必先落盘：

```bash
curl -sL https://example.com/cloudnote-cli-1.4.2.tar.gz \
  | openssl dgst -sha256
```

这条在「文件很大、磁盘很紧、只是想核对一下」的场景里特别顺手。注意输出里没有文件名，只有指纹——stdin 进来的东西没名字。

## 2.3 算法座次：MD5 与 SHA-1 为什么淘汰

不是所有指纹都值得信任。给密码学界的「塌房史」排个座次，这张表值得存进收藏夹：

| 算法 | 指纹长度 | 状态 | 塌房事件 |
| ---- | ---- | ---- | ---- |
| MD5 | 128 位 | **彻底淘汰** | 2004 年被攻破理论；2008 年研究者用它伪造出合法 CA 证书；2012 年 Flame 病毒用它伪造微软签名 |
| SHA-1 | 160 位 | **淘汰中** | 2017 年 Google 宣布实际碰撞成本已可承受（约 6500 CPU 年 + 110 GPU 年） |
| SHA-256 | 256 位 | 现役主力 | 无已知实际攻击，本书默认选择 |
| SHA-512 | 512 位 | 现役加强 | 64 位机器上反而比 SHA-256 更快，适合大文件 |
| SHA3 | 可变 | 新一代 | OpenSSL 3.x 已内置（`dgst -sha3-256`），但生态尚在铺开；BLAKE3 更快但不属 OpenSSL，`dgst` 点不出来 |

两个概念要分清：**理论攻破**（找到方法，但成本可能天文数字）与**实际可伪造**（成本降到攻击者付得起）。MD5 早已跨过第二阶段——你下载一个 MD5 校验的软件包，攻击者可以造出一个「指纹完全相同」的恶意版本，校验形同虚设。SHA-1 目前卡在两者之间：碰撞技术已公开，所以浏览器与主流证书体系已全面弃用。

为什么 SHA-256 的 256 位就够、而 MD5 的 128 位不够？直觉来自**生日悖论**：随机找两个人生日相同，23 人里就有五成概率——找哈希碰撞同理，「碰上一次」的概率增长远快于直觉。n 位指纹大约尝试 2^(n/2) 次就可能**随机撞出**碰撞：256 位的 SHA-256 需要 2^128 次——按现有全球算力堆上去，宇宙热寂也轮不到。而 MD5 早已跌到这条底线以下，且比「暴力 2^64 次」更糟：它有**构造性碰撞**——不需要大海捞针，按 2004 年公开的方法能定向造出碰撞，个人设备秒级完成。这就是「指纹长度每加一倍，安全感指数级上涨」的直观版本，第5章挑非对称算法时这张直觉还会再用一次。

实用军规只有一条：**新场景一律 SHA-256 起步**。遇到还要求 MD5/SHA-1 的场景（老 CDN、某些下载站），说明对方的信任体系需要更新，而不是你将就。

一个和你学过的 Git 直接相关的注脚：Git 的对象库用的正是 SHA-1——还记得《Git 与 SSH 完全教程》里每次提交那一串 40 位十六进制吗？那就是 SHA-1 指纹。Git 用 SHA-1 的方式和证书体系不同（内容寻址而非身份认证，攻击面小很多），但 SHA-1 塌房还是推动了 Git 社区：Git 2.29 起实验性支持 SHA-256 仓库，`git init --object-format=sha256` 即可启用。这套迁移还在推进期，日常项目暂时不必跟进——但「算法有寿命」这件事，连 Git 都在为之准备，值得记一笔。

## 2.4 校验和的盲区：谁都能改

现在设计云笔记的备份校验方案，第一版直觉方案是：每周导出文件后算一份 SHA-256 清单，存下来，每周比对。

```text
backup/2026-11-06.sql            9f2c8e7a...0b9
backup/2026-11-13.sql            1c6f4e2a...e3f
```

这能抓住**静默损坏**——存储系统的零字节塌陷会让指纹对不上，第 8 周的事故再也不会潜伏两周。但它抓不住另一种威胁：**主动篡改**。指纹本身是明文存的，攻击者改完文件后，顺手把清单里的指纹也改成新文件的指纹——两边永远「对得上」。

问题的本质：**没有秘密参与，就谈不上认证**。指纹只能证明「文件和算指纹时一样」，不能证明「算指纹的是你信任的人、指纹没被换」。要补上这层，就要把指纹和一把只有你有的钥匙绑在一起——这就是 HMAC。

## 2.5 HMAC：带密钥的指纹

HMAC（Keyed-Hash Message Authentication Code，密钥相关哈希消息认证码）做的事：把密钥揉进哈希运算，**不知道密钥的人，连指纹都算不出来**，更别提伪造。

```bash
openssl dgst -sha256 -hmac "backup-secret-2026" cloudnote-export.sql
```

```text
HMAC-SHA2-256(cloudnote-export.sql) = 4d8a2c6e0b9f3a7c5e1d8b4f6a2c0e9d7b5a3f1c8e6d4b2a0c9e7f5d3b1a8c6e
```

和上一节对比，输出从 `SHA2-256(...)` 变成了 `HMAC-SHA2-256(...)`——密钥参与了运算。验证时用同一把密钥重算，对得上才算数。攻防格局就此逆转：

| 威胁 | 裸校验和 | HMAC |
| ---- | ---- | ---- |
| 存储静默损坏 | 能发现 | 能发现 |
| 攻击者改文件 | 能发现（指纹对不上） | 能发现 |
| 攻击者连清单一起改 | 抓瞎 | 能发现（没密钥，伪造不出能对上的新指纹） |
| 攻击者有清单但没密钥 | 抓瞎 | **改了也伪造不出新指纹** |

HMAC 在工业界的出镜率远比想象高：你调云对象存储的 API 时请求头里那串签名（AWS S3 的 `Authorization` 头）、JWT 令牌里最常用的 HS256 算法、银行回调接口的验签——底层全是 HMAC-SHA256。学会这一条命令，你看懂了一大类 API 鉴权协议的骨架。

顺手认识一下 3.x 的新通用入口 `openssl mac`——它是 HMAC、CMAC、GMAC 等各类 MAC 的统一接口，参数更啰嗦但更「正经」：

```bash
openssl mac -macopt digest:SHA256 -macopt hexkey:$(echo -n "backup-secret-2026" | xxd -p -c 64) \
  -in cloudnote-export.sql HMAC
```

输出与 `dgst -hmac` 完全等价。日常用 `dgst -hmac` 就够；读别人脚本遇到 `mac` 命令时别慌——那是同一件事的另一种拼法。GMAC（基于 AES-GCM 的 MAC）会在第3章谈 AEAD 时再提一嘴。

什么时候用裸哈希、什么时候上 HMAC、什么时候升级到数字签名（Part 2 的主角），一张表定界：

| 对手是谁 | 该用什么 | 原因 |
| ---- | ---- | ---- |
| 存储静默损坏 | 裸 SHA-256 | 没人有恶意，指纹公开无妨 |
| 同事误操作覆盖文件 | 裸 SHA-256 | 同上，比对即可 |
| 有动机的攻击者改文件 | HMAC | 指纹清单本身可能被改，需要密钥参与 |
| 攻击者还想冒充你本人 | 数字签名 | HMAC 双方共享密钥，无法向第三方证明出处（第7章） |

这张表也是全书的地图之一：第3章的加密流水线会用 HMAC 做完整性防线，第7章的发布包签名会补上最后一块拼图。

密钥本身的生成与保管是个独立课题——口令太弱会被暴力猜出，随手 `openssl rand` 造的才够格，这正是下一章的主题。这里先把军规立好：**HMAC 的密钥只存在两个地方——生成方与验证方，绝不进 Git、绝不进日志**（参考《Git 与 SSH 完全教程》第12章的仓库卫生纪律）。

## 2.6 实验：给云笔记备份上校验清单

把本章收拢成一条可复制的流水线。目标：每周备份自动生成「文件 + 校验清单」，还原演练时一步核对。四步走完大约五分钟，每步都有可见的输出验收。

**第一步：导出并生成清单。**

```bash
cd ~/cloudnote
pg_dump cloudnote > backup-2026-11-06.sql
openssl dgst -r -sha256 backup-2026-11-06.sql > SHA256SUMS
cat SHA256SUMS
```

**第二步：每周核对（可挂进 cron）。** 有密钥版与无密钥版按需选：

```bash
# 无密钥版：抓静默损坏
sha256sum -c SHA256SUMS

# 有密钥版：连篡改一起抓（密钥放在不会被提交的环境变量里）
openssl dgst -sha256 -hmac "$BACKUP_HMAC_KEY" backup-2026-11-06.sql \
  | cmp -s - backup.hmac && echo "OK" || echo "TAMPERED"
```

无密钥版跑起来一行搞定。有密钥版的生成侧同样简单：核对清单不是文本文件，而是一次 HMAC 计算的输出，`openssl dgst -sha256 -hmac "$BACKUP_HMAC_KEY" backup-2026-11-06.sql > backup.hmac` 存下来即可。完整脚本第3章做完加密流水线后一并交付——校验和密钥怎么存、加密密钥怎么管，属于同一个「密钥管理」问题，两章打通后才是一套完整方案。

清单文件本身支持批量：`sha256sum *.sql > SHA256SUMS` 一次登记整个目录，`-c` 逐条核对并汇总通过率。清单行数会随文件数增长，但 64 字符一行的指纹便宜得可以忽略——**清单宁多勿缺，漏掉的那一个文件往往就是坏的那个**。

**第三步：故意改一个字节，看指纹翻脸。**

```bash
echo " " >> backup-2026-11-06.sql
sha256sum -c SHA256SUMS
```

```text
backup-2026-11-06.sql: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
```

`FAILED` 出现，说明探测网生效。注意我们只追加了一个空格——雪崩效应下指纹照样翻脸。第 8 周那种「静默损坏两周无人知」的事故，从此在流程上不可能再发生。

**第四步：换错密钥验 HMAC，体会「没钥匙连验证都做不了」。**

```bash
openssl dgst -sha256 -hmac "wrong-key" backup-2026-11-06.sql \
  | cmp -s - backup.hmac && echo "OK" || echo "MISMATCH"
```

```text
MISMATCH
```

同一个文件、同样的算法，只换了密钥，结果就变成 `MISMATCH`——HMAC 的验证方必须持有同一把密钥，这不是缺陷而是设计：**验证权本身就是秘密的一部分**。企业里交接备份系统时最常翻车的就是这一步：文件和清单都在，密钥随离职同事的脑子里退休了。密钥的生成与托管纪律，下一章正式立规矩。

> [!WARNING] 校验和不是备份
> 给文件配校验清单，解决的是「坏没坏」；文件本身还得备份（参考 3-2-1 原则：三份副本、两种介质、一份异地）。校验和让你**及早发现**损失，不让你**避免**损失——两者从来不是一回事。同理，清单文件要和文件本体分开存放——放在同一个目录里被一锅端时，它连报警的机会都没有。

## 本章小结

- 哈希四性质：确定、单向、雪崩、抗碰撞——缺一条，指纹就不是指纹
- `openssl dgst -sha256 文件` 是跨平台的指纹工具；Linux 日常用 `sha256sum`，`-r` 可对齐格式；管道流式校验不必落盘
- 下载软件包先验指纹再解压：`sha256sum -c 清单文件` 看到 `OK` 才动手
- 算法军规：新场景一律 SHA-256 起步；MD5 彻底淘汰，SHA-1 淘汰中——校验一个没人能伪造的指纹才有意义
- 裸校验和防静默损坏，防不了主动篡改：**没有秘密参与，就谈不上认证**
- HMAC 把密钥揉进指纹，S3 签名、JWT 的 HS256 底层全是它；3.x 还有统一入口 `openssl mac`
- 裸哈希 → HMAC → 数字签名，对应三级对手模型，本书按这条线递进
- 校验和让你及早发现损失，不让你避免损失——备份策略与校验策略缺一不可
