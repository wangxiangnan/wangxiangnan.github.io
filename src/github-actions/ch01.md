# 第1章：什么是 GitHub Actions？为什么你需要它

## 引言：你是不是也经历过这些？

让我们来还原一个"经典"的开发场景——

你写好了代码，本地 `npm test` 跑通了，心满意足地 `git push`。然后呢？

然后你打开终端，开始一段"人肉 CI"之旅：

1. SSH 到测试服务器，`git pull` 最新代码
2. 跑一遍 `npm install && npm test`，祈祷不要报错
3. 测试通过了，手动 `npm run build`
4. 把构建产物拷贝到生产服务器
5. 重启服务，打开网页看看有没有白屏
6. 发现问题了？回滚，重来

这套流程，跟在没有洗衣机的年代手洗衣服没什么区别——先泡、再搓、再拧、再晾，每一步都得亲力亲为。

**如果你受够了当"人肉发布机器"，恭喜你，GitHub Actions 就是你的全自动洗衣机。**

## 1.1 CI/CD 的概念：餐厅后厨类比

CI/CD 这两个缩写，听起来很高大上，其实道理非常朴素。

**CI（Continuous Integration，持续集成）** 的意思是：每个开发者的代码改动，都要频繁地、自动地合并到主干分支，并且每次合并后都自动跑一遍测试。

打个比方：想象你经营一家餐厅，后厨有好几个厨师。每个厨师做完自己的菜之后，不是直接端给客人，而是先让"质检员"尝一口——味道没问题、跟其他菜不冲突，才允许上桌。

这个"质检员"就是 CI 系统。它干的事情就是：

- **你推了代码？** 自动拉取最新代码
- **自动编译** —— 看看语法有没有炸
- **自动测试** —— 看看逻辑有没有崩
- **告诉你结果** —— 通过就亮绿灯，失败就亮红灯

**CD（Continuous Delivery / Continuous Deployment，持续交付/持续部署）** 更进一步：测试通过之后，自动把代码部署到生产环境。

还是那个餐厅的比喻——CI 是"质检员尝菜"，CD 就是"质检通过后直接让服务员端给客人"。整个过程不需要人工干预，从下单到上桌，全链路自动化。

## 1.2 GitHub Actions 的定位和优势

市面上 CI/CD 工具很多，GitHub Actions 凭什么出圈？

简单来说，GitHub Actions 是 GitHub 官方出品的、内置在 GitHub 平台里的 CI/CD 服务。它的核心卖点是：

**1. 零配置集成**

不需要额外搭建 Jenkins 服务器，不需要注册 CircleCI 账号，不需要配置 Webhook——你的代码在 GitHub 上，Actions 就在 GitHub 上。就像你买了个手机，自带相机、地图、天气 App，开箱即用。

**2. 与 GitHub 生态深度绑定**

Pull Request 的状态检查、Issue 的自动回复、Release 的自动发布……这些场景用 GitHub Actions 实现起来，顺滑得就像德芙巧克力。因为它们是同一个平台上的"一家人"，数据互通，API 互调。

**3. 丰富的 Marketplace**

GitHub Marketplace 里有上万个社区贡献的 Action，从"部署到 AWS"到"发送到 Slack 通知"，基本上你能想到的场景，都有现成的轮子。就像 npm 之于 Node.js 开发者——你不需要从零造轮子。

**4. 免费额度慷慨**

对于公开仓库，GitHub Actions 完全免费。对于私有仓库，每月也有 2000 分钟的免费额度（标准 runner）。对于个人开发者和小团队来说，基本够用。

## 1.3 与其他 CI/CD 工具的对比

| 特性 | GitHub Actions | Jenkins | CircleCI |
|------|---------------|---------|----------|
| **部署方式** | 云端托管，开箱即用 | 需要自己搭建服务器 | 云端托管 |
| **与 GitHub 集成** | 原生集成，丝滑无比 | 需要配置 Webhook 和插件 | 需要授权连接 |
| **学习曲线** | 中等（YAML 配置） | 陡峭（Groovy Pipeline） | 中等（YAML 配置） |
| **社区生态** | Marketplace 上万 Action | 插件极其丰富但质量参差 |  orbs 生态较小 |
| **免费额度** | 公开仓库免费，私有 2000min/月 | 完全免费（但服务器成本自理） | 6000min/月（免费层） |
| **自定义 Runner** | 支持 | 支持（天然特性） | 有限支持 |

**一句话总结**：如果你的代码在 GitHub 上，GitHub Actions 就是阻力最小的选择。就像你住在超市楼上，干嘛还要开车去另一个超市买菜呢？

## 1.4 一个真实的场景：手动发版 vs 自动化发版

假设你维护一个 npm 包 `awesome-utils`，每次发新版你需要：

**手动发版的噩梦：**

```bash
# 1. 确认本地是最新代码
git pull origin main

# 2. 跑测试（手动）
npm test
# 等啊等…… 3 分钟过去了，还好全绿

# 3. 修改版本号
# 打开 package.json，手动改 "version": "1.2.3" → "1.3.0"

# 4. 构建
npm run build

# 5. 发布到 npm
npm publish

# 6. 打 tag
git tag v1.3.0
git push origin v1.3.0

# 7. 去 GitHub 页面手动创建 Release，写 changelog
```

这个过程，每次大概 10-15 分钟。如果你一个月发 10 次版，一年就是 20-25 个小时——整整三天，你都在做机器能做的事情。

**用 GitHub Actions 自动化发版：**

你只需要在代码合并到 `main` 分支时，给 PR 打上 `release` 标签。剩下的一切——跑测试、构建、修改版本号、发布到 npm、创建 GitHub Release——全部自动完成。

你要做的事情只有一件：**写好代码，合并 PR。** 其他的，交给 Actions。

这就是 CI/CD 的魅力：**把重复的、机械的、容易出错的流程，变成一段自动执行的脚本。** 你可以把省下来的时间用来做更有价值的事——比如写更好的代码，或者去喝杯咖啡。

## 小结

- CI/CD 的本质是"自动化一切重复流程"，就像餐厅的标准化出餐流程
- GitHub Actions 是 GitHub 官方的 CI/CD 服务，优势在于零配置、深度集成、丰富生态
- 选择 CI/CD 工具的核心原则：代码在哪，CI/CD 就在哪
- 自动化不是偷懒，是把时间花在更有价值的事情上
