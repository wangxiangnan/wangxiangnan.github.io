# 第17章：最佳实践与安全

## 17.1 引言：安全和效率不是二选一

很多人觉得"安全"和"效率"是对立的——为了安全就要牺牲开发速度，为了效率就要放松安全管控。但在 CI/CD 的世界里，最佳实践恰恰是两者的"联姻"：好的安全实践不仅不会拖慢你，反而会让整个团队更自信、更高效地交付。

本章我们将覆盖 GitHub Actions 的最佳实践清单，从权限控制到成本优化，从代码组织到团队协作，为你构建一条"既快又稳"的 CI/CD 流水线。

## 17.2 权限最小化原则

"最小权限原则"（Principle of Least Privilege）是信息安全的基石——就像酒店前台的钥匙，只给你进入你房间所需的权限，而不是整栋楼的主钥匙。

从 2023 年 2 月起，GitHub 默认将 `GITHUB_TOKEN` 的权限设为 `read-only`。你需要显式声明所需的写权限：

```yaml
# 推荐的写法：在 Workflow 级别设置默认权限
permissions:
  contents: read  # 默认只读

jobs:
  lint:
    # lint 不需要写权限，用默认的 read 就够了
    permissions:
      contents: read
    steps: [...]

  deploy:
    # 只有部署 Job 才需要写权限
    permissions:
      contents: read
      packages: write
      deployments: write
    steps: [...]
```

**核心原则**：永远不要使用 `permissions: write-all` 这种"万能钥匙"。如果一个 Workflow 被恶意代码利用，过大的权限会导致灾难性的后果。

## 17.3 依赖安全扫描

供应链攻击已经成为当今软件开发中最严重的威胁之一。一个被劫持的 npm 包或 PyPI 包，可能会在你的 CI 环境中执行恶意代码。GitHub 提供了两个强大的安全工具：

**Dependabot**：自动检测你的依赖中是否有已知漏洞，并创建 PR 来更新它们。

```yaml
# .github/dependabot.yml
version: 2
updates:
  # 监控 npm 依赖
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    # 限制同时打开的 PR 数量，避免 PR 爆炸
    open-pull-requests-limit: 10
    # 对安全更新自动合并（配合 CI 通过后自动合并）
    labels:
      - "dependencies"
      - "automerge"

  # 监控 GitHub Actions 本身使用的 Actions 版本
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"

  # 监控 Docker 镜像
  - package-ecosystem: "docker"
    directory: "/"
    schedule:
      interval: "weekly"
```

**CodeQL 安全扫描**：GitHub 的代码扫描工具，能检测代码中的安全漏洞（如 SQL 注入、XSS）：

```yaml
name: CodeQL Analysis

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    # 每周一凌晨扫描一次，捕获新发现的漏洞模式
    - cron: '0 3 * * 1'

jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: javascript
      - uses: github/codeql-action/analyze@v3
```

## 17.4 成本控制

GitHub Actions 按分钟计费（公开仓库免费，私有仓库有每月免费额度）。几个省钱的小技巧：

**1. 避免无限循环**：如果你的 Workflow 在 push 事件中触发了代码修改并 push，就会形成无限循环。解决方案：

```yaml
# 方法一：使用 [skip ci] 标记
- name: Update version
  run: |
    npm version patch
    git push origin main -m "chore: bump version [skip ci]"

# 方法二：在触发条件中排除特定路径
on:
  push:
    paths-ignore:
      - 'CHANGELOG.md'
      - 'package.json'  # 版本号变更不触发 CI
```

**2. 合理使用 Matrix**：4 个 Python 版本 × 3 个操作系统 = 12 个 Job。你真的需要这么多吗？问自己："我的用户真的会在 Windows + Python 3.9 上跑这个吗？"如果不是，就砍掉不必要的组合。

**3. 使用 `timeout-minutes` 防止"僵尸 Job"**：一个卡住的 Job 如果不设超时，可能会跑满 6 小时（360 分钟），白白烧钱。

**4. 在非关键分支上关闭 Actions**：对于实验性分支，不需要跑完整的 CI。

## 17.5 代码组织：`.github` 仓库集中管理

当你的组织有多个仓库时，每个仓库都复制一份 Workflow 文件是低效的。GitHub 支持一种特殊机制：在组织级别的 `.github` 仓库中定义 Reusable Workflows，其他仓库直接引用。

```yaml
# 在 .github 仓库中定义:
# .github/workflows/reusable-node-ci.yml
name: Reusable Node.js CI

on:
  workflow_call:
    inputs:
      node-version:
        description: 'Node.js version'
        required: false
        type: string
        default: '20'
      run-e2e:
        description: 'Whether to run E2E tests'
        required: false
        type: boolean
        default: false
    secrets:
      npm-token:
        required: false

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
      - run: npm ci
      - run: npm run lint
      - run: npm test
```

```yaml
# 在其他仓库中引用：
name: CI
on: [push, pull_request]

jobs:
  ci:
    uses: my-org/.github/.github/workflows/reusable-node-ci.yml@main
    with:
      node-version: '20'
      run-e2e: true
    secrets:
      npm-token: ${{ secrets.NPM_TOKEN }}
```

这种方式的好处是"一处修改，处处生效"——就像修改了公司模板后，所有使用模板的文档都会自动更新。

## 17.6 团队协作规范

CI/CD 不仅仅是技术问题，更是团队协作问题。以下是几个推荐实践：

**1. 分支保护规则 + CI 结合**：

在仓库的 Settings → Branches → Branch protection rules 中设置：

- `Require status checks to pass before merging`：合并前必须通过 CI。
- `Require branches to be up to date before merging`：合并前分支必须是最新的（避免合并冲突）。
- `Require pull request reviews before merging`：合并前必须有 Code Review。

这三条规则组合起来，确保了"没有经过 CI 验证和人工审查的代码，不能进入 main 分支"。

**2. PR 模板 + CI 检查清单**：

创建 `.github/pull_request_template.md`，在 PR 描述中嵌入检查清单。CI 的 Status Check 会显示在 PR 页面上，让审查者一目了然：

```
## 检查清单
- [ ] 代码已自测
- [ ] 已更新文档（如适用）
- [ ] 已添加测试用例（如适用）

## CI 状态
所有 Status Check 必须为绿色才能合并。
```

**3. Commit 规范**：使用 Conventional Commits（如 `feat:`, `fix:`, `chore:`），配合 `commitlint` 在 CI 中自动检查：

```yaml
- name: Check commit messages
  run: npx commitlint --from HEAD~1 --to HEAD
```

## 17.7 未来展望：GitHub Copilot + Actions、Attestations

GitHub 正在持续进化 Actions 的能力：

**GitHub Copilot for Actions**：你可以用自然语言描述你想做的事，Copilot 帮你生成 Workflow YAML。虽然目前生成的代码还需要人工审查和调整，但它极大地降低了入门门槛——就像有一个"老司机"在旁边随时给你写草稿。

**Attestations（制品签名）**：这是一个正在发展中的安全特性。它为 CI/CD 产物添加密码学签名，证明"这个镜像确实是由某个 Workflow 在某个 commit 上构建的"。在供应链攻击频发的今天，Attestations 为你的部署链条增加了一层"信任验证"。

**Actions 的 AI 集成**：想象一下，CI 失败后 Actions 自动分析错误日志并生成修复建议，甚至自动创建修复 PR。这不是科幻，GitHub 已经在探索这个方向。

## 17.8 最佳实践速查清单

最后，给你一份可以随时翻阅的最佳实践速查表：

| 类别 | 最佳实践 | 原因 |
|------|----------|------|
| 权限 | 始终声明 `permissions: read` | 最小权限原则 |
| 安全 | Pin Actions 版本到 commit SHA | 防止供应链攻击 |
| 性能 | 使用 `actions/cache` | 减少依赖安装时间 |
| 性能 | 使用 `fetch-depth: 1` | 减少 checkout 时间 |
| 成本 | 设置 `timeout-minutes` | 防止僵尸 Job |
| 成本 | 合理设计 Matrix | 避免无意义的排列组合 |
| 组织 | 使用 Reusable Workflows | DRY 原则 |
| 质量 | 要求 Status Check 通过才能合并 | 代码质量门禁 |
| 安全 | 启用 Dependabot | 自动修复依赖漏洞 |
| 调试 | 设置 `ACTIONS_STEP_DEBUG` | 快速定位问题 |

## 17.9 小结

最佳实践不是一成不变的教条，而是从无数项目经验中提炼出来的"集体智慧"。权限最小化保护你免受安全事故的影响，成本控制保护你的钱包，代码组织保护你的维护效率，团队规范保护代码质量。把这些实践融入你的 CI/CD 流水线，你的自动化之路就会走得又稳又远。

## 17.10 练习题

1. 审计一个现有的 Workflow 文件，检查它是否遵循了最小权限原则。哪些权限可以收紧？
2. 为你的组织设计一个 Reusable Workflow，支持 Node.js 和 Python 两种技术栈。如何设计输入参数？
3. 实现一个"安全门禁"Workflow：在 PR 中自动运行 `npm audit` 和依赖漏洞扫描，如果有高危漏洞则阻止合并。
