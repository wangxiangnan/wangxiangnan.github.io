## 24.1 Redis 生产环境部署 Checklist

### 24.1.1 硬件选择

```bash
Redis 是内存数据库，硬件优先级：内存 > CPU > 网络 > 磁盘

推荐配置（中等规模）：
  - 内存：16-32GB（Redis 使用不超过 75%）
  - CPU：4-8 核（fork 等操作需要多核）
  - 网络：千兆网卡（低延迟比高带宽更重要）
  - 磁盘：SSD（RDB/AOF 持久化）
```

> **Tip：内存规划**
>
> 永远不要让 Redis 使用超过物理内存的 75%。剩下的留给操作系统页缓存、fork 时 COW 开销、内存碎片。

### 24.1.2 操作系统优化

```bash
# 1. 内存过量分配（允许 fork 分配超额虚拟内存）
echo "vm.overcommit_memory = 1" >> /etc/sysctl.conf && sysctl -p

# 2. 关闭透明大页（THP 导致 fork 延迟飙升）
echo never > /sys/kernel/mm/transparent_hugepage/enabled

# 3. 增大 TCP backlog
echo "net.core.somaxconn = 2048" >> /etc/sysctl.conf && sysctl -p

# 4. 文件描述符限制
echo "* soft nofile 65536" >> /etc/security/limits.conf
echo "* hard nofile 65536" >> /etc/security/limits.conf

# 5. 关闭或降低 swap
echo "vm.swappiness = 1" >> /etc/sysctl.conf && sysctl -p
```

## 24.2 监控与告警

### 关键监控指标

```bash
1. 内存：used_memory, mem_fragmentation_ratio, evicted_keys
2. 连接：connected_clients, blocked_clients, rejected_connections
3. 性能：instantaneous_ops_per_sec, keyspace_hits/misses
4. 持久化：rdb_last_save_time, aof_rewrite_in_progress
```

### Node.js 监控采集器

```js
class RedisMonitor {
  constructor(redisClient, options = {}) {
    this.redis = redisClient;
    this.interval = options.interval || 10000;
    this.alertCallbacks = [];
    this._timer = null;
  }

  async collectMetrics() {
    const info = await this.redis.info();
    const metrics = {};
    info.split('\r\n').filter((l) => l && !l.startsWith('#')).forEach((line) => {
      const [key, value] = line.split(':');
      if (key && value) metrics[key] = isNaN(value) ? value : parseFloat(value);
    });

    const hits = metrics.keyspace_hits || 0;
    const misses = metrics.keyspace_misses || 0;
    const hitRate = (hits + misses) > 0 ? (hits / (hits + misses) * 100).toFixed(2) : '0';

    return {
      timestamp: Date.now(),
      memory: {
        used: metrics.used_memory,
        rss: metrics.used_memory_rss,
        fragmentationRatio: metrics.mem_fragmentation_ratio,
      },
      connections: {
        connected: metrics.connected_clients,
        blocked: metrics.blocked_clients,
        maxClients: metrics.maxclients,
      },
      performance: {
        opsPerSec: metrics.instantaneous_ops_per_sec,
        hitRate: parseFloat(hitRate),
        inputKbps: metrics.instantaneous_input_kbps,
        outputKbps: metrics.instantaneous_output_kbps,
      },
    };
  }

  onAlert(callback) { this.alertCallbacks.push(callback); }

  async _checkAlerts(metrics) {
    const alerts = [];

    if (metrics.memory.fragmentationRatio > 1.5) {
      alerts.push({ level: 'warning', message: `内存碎片率过高: ${metrics.memory.fragmentationRatio}` });
    }

    const connPercent = (metrics.connections.connected / metrics.connections.maxClients) * 100;
    if (connPercent > 80) {
      alerts.push({ level: 'critical', message: `连接数即将耗尽: ${metrics.connections.connected}` });
    }

    if (metrics.performance.hitRate < 90 && metrics.performance.hitRate > 0) {
      alerts.push({ level: 'warning', message: `缓存命中率偏低: ${metrics.performance.hitRate}%` });
    }

    for (const alert of alerts) {
      for (const cb of this.alertCallbacks) await cb(alert);
    }
  }

  start() {
    this._timer = setInterval(async () => {
      try {
        const m = await this.collectMetrics();
        await this._checkAlerts(m);
        console.log(`[${new Date().toISOString()}] OPS:${m.performance.opsPerSec} 命中率:${m.performance.hitRate}% 连接:${m.connections.connected}`);
      } catch (err) {
        console.error('监控采集失败:', err.message);
      }
    }, this.interval);
  }

  stop() { if (this._timer) clearInterval(this._timer); }
}

const monitor = new RedisMonitor(redis, { interval: 10000 });
monitor.onAlert((alert) => console.log(`[告警] [${alert.level}] ${alert.message}`));
monitor.start();
```

### 24.3.2 大 Key 问题

```bash

redis-cli --scan --pattern '*' | xargs -I{} redis-cli debug object {}
```

```js
// 找出大 Key
async function findBigKeys(redisClient, threshold = 10000) {
  let cursor = '0';
  const bigKeys = [];

  do {
    const [nextCursor, keys] = await redisClient.scan(cursor, 'COUNT', 100);
    cursor = nextCursor;

    for (const key of keys) {
      const type = await redisClient.type(key);
      let size = 0;

      switch (type) {
        case 'string':
          size = await redisClient.strlen(key);
          break;
        case 'list':
          size = await redisClient.llen(key);
          break;
        case 'set':
          size = await redisClient.scard(key);
          break;
        case 'zset':
          size = await redisClient.zcard(key);
          break;
        case 'hash':
          size = await redisClient.hlen(key);
          break;
      }

      if (size > threshold) {
        bigKeys.push({ key, type, size });
      }
    }
  } while (cursor !== '0');

  bigKeys.sort((a, b) => b.size - a.size);
  return bigKeys.slice(0, 20); // Top 20
}
```

### 24.3.3 热 Key 问题

```bash
# Redis 7.0+ 热点 key 检测
redis-cli --hotkeys
```

```js
// 手动检测热 Key（通过采样）
async function detectHotKeys(redisClient, sampleSize = 1000) {
  const accessCount = {};

  // 在应用中记录 key 的访问次数
  // 这里使用 Redis 自身来统计
  let cursor = '0';
  do {
    const [nextCursor, keys] = await redisClient.scan(cursor, 'COUNT', 100);
    cursor = nextCursor;
    for (const key of keys) {
      // 使用 OBJECT FREQ（需要 maxmemory-policy 包含 LFU）
      try {
        const freq = await redisClient.call('OBJECT', 'FREQ', key);
        if (freq > 200) {
          accessCount[key] = freq;
        }
      } catch { /* ignore */ }
    }
  } while (cursor !== '0');

  return Object.entries(accessCount)
    .sort(([, a], [, b]) => b - a)
    .slice(0, 10);
}
```

**热 Key 解决方案**：

1. 本地缓存（node-cache）
2. 读写分离（读从节点）
3. Key 分片（将热 key 分散到多个 key）

## 24.4 Redis 版本升级策略

```bash
升级原则：
1. 永远先在测试环境验证
2. 使用主从切换方式升级（先升级从节点，再切换主从）
3. 阅读 CHANGELOG 关注 breaking changes
4. 备份 RDB/AOF 后再升级

升级步骤（主从架构）：
1. 升级所有从节点
2. 执行主从切换（SLAVEOF NO ONE）
3. 升级原主节点（现在是新的从节点）
4. 验证集群状态
```

## 24.5 Redis vs 其他方案

### Redis vs Memcached

| 维度 | Redis | Memcached |
|------|-------|-----------|
| 数据结构 | 丰富（String/List/Hash/Set/ZSet/Stream） | 仅 String |
| 持久化 | RDB + AOF | 不支持 |
| 集群 | 原生 Cluster | 客户端分片 |
| 发布订阅 | 支持 | 不支持 |
| 线程模型 | 单线程（6.0 IO多线程） | 多线程 |
| Lua 脚本 | 支持 | 不支持 |
| 适用场景 | 通用 | 纯缓存 |

### Redis vs 本地缓存（Caffeine/Guava/node-cache）

| 维度 | Redis | 本地缓存 |
|------|-------|----------|
| 延迟 | ~1ms（网络） | ~0.001ms（内存） |
| 容量 | GB-TB 级 | MB 级 |
| 共享 | 多进程/多机器共享 | 单进程独占 |
| 一致性 | 集中一致 | 各节点独立 |
| 适用 | 共享缓存、分布式锁 | 热点数据、配置缓存 |

**最佳实践**：本地缓存 + Redis 多级缓存。

### Redis vs 专业消息队列（Kafka/RabbitMQ）

| 维度 | Redis (Stream/List) | Kafka | RabbitMQ |
|------|-------|-------|----------|
| 吞吐量 | 10万/s | 100万/s | 10万/s |
| 持久化 | AOF/RDB | 磁盘顺序写 | 可选 |
| 消息回溯 | 有限 | 完整 | 不支持 |
| 适用 | 轻量级消息 | 大数据管道 | 企业消息 |

**结论**：简单的通知/任务队列用 Redis，复杂的流处理用 Kafka。

## 最后的寄语

写到这里，《Redis 完全教程》就正式完结了。

回顾整个学习旅程，我们从最基础的 `SET` 和 `GET` 开始，一路走到分布式锁、缓存架构、生产运维。就像学骑自行车一样——刚开始你可能会摔倒（缓存穿透！内存爆了！主从不同步！），但每一次跌倒都让你对 Redis 的理解更深一层。

Redis 的魅力在于它的"简单但不简陋"。它的核心只有 5 种数据结构，但这 5 种结构组合起来，几乎能解决你在后端开发中遇到的所有数据管理问题。正如 Unix 哲学所说："Do one thing and do it well."

记住这几条黄金法则：

1. **选择合适的缓存模式**，不要一刀切
2. **能用 Lua 脚本就不用分布式锁**
3. **监控是生命线**，没有监控的 Redis 就像没有仪表盘的赛车
4. **备份、备份、备份**，数据丢了什么都白搭
5. **简单优先**，不要过度设计

祝你在 Redis 的世界里越走越远，从使用者成为专家，从专家成为布道者。我们下一本教程见！
