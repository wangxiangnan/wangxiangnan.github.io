# 第8章：事务与 ACID——并发的秘密

## 8.1 开场白：为什么"转账"必须要事务？

经典面试题：A 给 B 转账 100 块，怎么保证不出错？

分两步：

1. A 账户 - 100
2. B 账户 + 100

如果步骤 1 成功、步骤 2 之前程序崩溃/断电——A 少了 100，B 没多，那 100 块消失在数字宇宙里。银行会赔？银行程序员被祭天。

**事务**（Transaction）就是把多个操作打包成"要么全成功、要么全失败"的原子单元。这是数据库最重要的抽象之一，也是"你以为你懂了但其实没懂"的坑王之王。

这一章我们从 ACID 讲到锁机制，从事务模式讲到 WAL，最后落到 Flutter 的 Batch 和 Transaction。

## 8.2 ACID：数据库教科书四大天王

- **A**tomicity（原子性）：事务里的操作要么全做，要么全不做。中途崩了自动回滚。
- **C**onsistency（一致性）：事务前后数据库都满足约束（NOT NULL、FK、CHECK 等）。
- **I**solation（隔离性）：并发事务互不干扰，就像各自独占数据库。
- **D**urability（持久性）：事务提交后，即使断电，数据也不会丢。

SQLite 是**完整支持 ACID** 的（这是它能在飞机、火车、手机上活下来的关键原因）。别看它是"嵌入式"数据库，可靠性比很多所谓的"企业级"数据库还高。

**冷知识**：SQLite 是航空业官方认证的持久化格式（DO-178B），也是美国国会图书馆推荐的长期归档格式之一。

## 8.3 SQL 层：BEGIN / COMMIT / ROLLBACK

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

出错回滚：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
-- 发现 B 账户不存在
ROLLBACK;
```

只有 `COMMIT` 之后，改动才真正落盘。`ROLLBACK` 会把所有改动扔掉，数据库回到 `BEGIN` 之前的样子。

## 8.4 三种事务模式：DEFERRED / IMMEDIATE / EXCLUSIVE

`BEGIN` 有三种"心机"：

```sql
BEGIN;                    -- 或 BEGIN DEFERRED，默认
BEGIN IMMEDIATE;
BEGIN EXCLUSIVE;
```

区别在于**什么时候获取锁**：

**DEFERRED（默认）**：`BEGIN` 时不加锁。第一次读加 SHARED 锁，第一次写加 RESERVED 锁。**读读并发好，但可能后期升级锁失败（SQLITE_BUSY）**。

**IMMEDIATE**：`BEGIN` 时立刻加 RESERVED 锁。别的连接不能写，但可以读。**如果你知道自己要写，用这个**。

**EXCLUSIVE**：`BEGIN` 时加 EXCLUSIVE 锁（在非 WAL 模式下）。别的连接读也不能读。极少用。

**实战建议**：

- 只读事务 → `BEGIN`（DEFERRED）
- 有写操作 → `BEGIN IMMEDIATE`（避免中途 SQLITE_BUSY）
- 特殊情况全独占 → `BEGIN EXCLUSIVE`

## 8.5 SAVEPOINT——嵌套事务

SQLite 支持"事务里的事务"，叫 SAVEPOINT：

```sql
BEGIN;
INSERT INTO log VALUES ('start');

SAVEPOINT sp1;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
-- 发现问题，撤销这一段但不撤销 log
ROLLBACK TO sp1;

INSERT INTO log VALUES ('failed');
COMMIT;
```

SAVEPOINT 常用来实现"部分回滚"，比如批处理里某条失败了，只回滚这条而不影响之前的。

**释放 SAVEPOINT**：`RELEASE sp1`，标记 SAVEPOINT 完成（但不提交整个事务）。

## 8.6 隔离级别：SQLite 只有 SERIALIZABLE？

标准 SQL 定义了 4 个隔离级别（脏读、不可重复读、幻读的组合）：

| 级别             | 脏读 | 不可重复读 | 幻读 |
| ---------------- | ---- | ---------- | ---- |
| READ UNCOMMITTED | 可能 | 可能       | 可能 |
| READ COMMITTED   | 不   | 可能       | 可能 |
| REPEATABLE READ  | 不   | 不         | 可能 |
| SERIALIZABLE     | 不   | 不         | 不   |

**教科书答案**：SQLite 默认是 SERIALIZABLE，因为它用文件锁——同一时刻只有一个写事务。

**真实答案（WAL 模式下）**：更复杂。在 WAL 模式，读事务和写事务可以并发（读读、读写都行，只有写写互斥），读事务看到的是**开始时刻的快照**（snapshot isolation）——这更像 PostgreSQL 的 REPEATABLE READ。

**冷门知识**：SQLite 有个 `PRAGMA read_uncommitted = 1`，可以让共享缓存的连接读到未提交数据。**几乎从不用**，知道就行。

## 8.7 锁机制：五段升级

传统 rollback journal 模式下，SQLite 的锁有 5 个级别（同一时刻只能有一个连接持有 EXCLUSIVE）：

1. **UNLOCKED**：没锁，起点。
2. **SHARED**：共享锁。可以读，别人也能读。开始读时获取。
3. **RESERVED**：预留锁。想写的意向锁。别人还能读，但不能升级。
4. **PENDING**：等待锁。宣告"我要 EXCLUSIVE，新来的 SHARED 别进"。
5. **EXCLUSIVE**：独占锁。真正写盘。

升级路径：`UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE`。

**WAL 模式下不一样**：读事务用 shared 锁读 WAL 快照，写事务只需要 EXCLUSIVE 锁写 WAL 文件末尾，checkpoint 时才需要 EXCLUSIVE 锁把 WAL 合并回主库。**读写并发就是靠 WAL**。

## 8.8 SQLITE_BUSY——死锁与优雅重试

SQLite 里没有"死锁检测"（因为它太简单：所有事务都要拿主库锁），但会有 `SQLITE_BUSY` 错误——想加锁但别人拿着。

**触发场景**：

1. 两个写事务想同时 IMMEDIATE。
2. DEFERRED 事务想升级锁（RESERVED→EXCLUSIVE），但另一个连接持有 SHARED。
3. 长事务阻塞后续操作。

**解决方案**：

**1. 设置 busy_timeout**

```sql
PRAGMA busy_timeout = 5000;    -- 毫秒
```

或者用 API 层：

```dart
// sqflite
await db.execute('PRAGMA busy_timeout = 5000');
```

SQLite 在拿不到锁时会**自旋等待**这么久，超时才报错。**大部分场景 5 秒足够**。

**2. 应用层重试**

```dart
Future<T> withRetry<T>(Future<T> Function() action, {int maxAttempts = 3}) async {
  for (int i = 0; i < maxAttempts; i++) {
    try {
      return await action();
    } on DatabaseException catch (e) {
      if (e.isDatabaseBusyError() && i < maxAttempts - 1) {
        await Future.delayed(Duration(milliseconds: 100 * (1 << i))); // 指数退避
        continue;
      }
      rethrow;
    }
  }
  throw StateError('unreachable');
}
```

**3. 用 WAL 模式**（下一章会深讲）：多读少写场景直接消除大部分 BUSY。

## 8.9 长事务的三宗罪

一个事务持续几秒到几分钟叫"长事务"。危害：

1. **阻塞别人**：拿着锁不放，其他写事务只能等。
2. **占用资源**：内存里缓存的更改越来越多，磁盘 WAL 文件膨胀。
3. **回滚代价大**：如果最后要回滚，前面做的都白做。

**别在事务里做什么**：

- 网络请求
- 用户交互（等待输入）
- 长时间计算
- 大量日志打印

**事务应该像相亲**：进去就是为了办事，别磨叽。

## 8.10 性能实战：无事务 vs 单事务 vs 批量

看下面这个 benchmark：插入 10000 条记录。

**无事务（每条自动 COMMIT）**：

```sql
INSERT INTO t VALUES (1, 'a');
INSERT INTO t VALUES (2, 'b');
-- ... 10000 次
```

在普通机械硬盘上，每次 COMMIT 都要 `fsync`（把 buffer 刷到磁盘），一次大概 5~30ms。10000 次 = **50~300 秒**。

**单事务包裹**：

```sql
BEGIN;
INSERT INTO t VALUES (1, 'a');
-- ... 10000 次
COMMIT;
```

只有最后一次 fsync。10000 次插入大概 **0.5~2 秒**。**性能提升 100 倍以上**。

**Prepared Statement + 单事务**：

```sql
BEGIN;
-- 用参数化语句，避免重复解析 SQL
COMMIT;
```

进一步减少 SQL 解析开销。**性能提升 200 倍以上**。

**教训**：任何批量操作**一定要用事务包起来**。这是最容易见效的性能优化。

## 8.11 Flutter 实战：sqflite 的 Batch 和 Transaction

**Transaction**：多条 SQL 打包成一个事务。

```dart
await db.transaction((txn) async {
  await txn.rawUpdate('UPDATE account SET balance = balance - ? WHERE id = ?', [100, 1]);
  await txn.rawUpdate('UPDATE account SET balance = balance + ? WHERE id = ?', [100, 2]);
});
// 任何异常都会自动 ROLLBACK
```

事务里必须用 `txn`，**不能用外层的 `db`**！用了会死锁（等待自己的锁）。

**Batch**：批量 SQL 语句，可以选择要不要放在事务里。

```dart
final batch = db.batch();
for (int i = 0; i < 10000; i++) {
  batch.insert('t', {'id': i, 'name': 'item_$i'});
}
await batch.commit(noResult: true);        // 默认在事务里执行
```

**Batch vs Transaction 的区别**：

| 特性       | Batch                             | Transaction                     |
| ---------- | --------------------------------- | ------------------------------- |
| 用途       | 批量执行多条 SQL                  | 保证原子性                      |
| 减少通信   | 只跟 Native 层通信一次            | 每条 SQL 单独通信               |
| 事务性     | 默认在事务里（可关）              | 必须在事务里                    |
| 使用场景   | 大批量插入/更新                   | 需要根据中间结果决定后续操作    |

**为什么 Batch 快？** 因为 sqflite 是 Dart 通过 MethodChannel 调用 Native 的 SQLite——每次调用都有跨语言开销。Batch 把 N 次调用打包成 1 次，节省 N-1 次跨语言桥接。

`batch.commit(noResult: true)` 里的 `noResult: true` 表示"我不需要每条 SQL 的返回值"，可以进一步减少内存和通信开销。

**Batch 里嵌事务**：

```dart
await db.transaction((txn) async {
  final batch = txn.batch();
  for (int i = 0; i < 10000; i++) {
    batch.insert('t', {'id': i, 'name': 'item_$i'});
  }
  await batch.commit(noResult: true);
});
```

这样保证批量操作原子性 + 通信效率双高。

## 8.12 sqflite 事务隔离与 isolate

sqflite 的默认数据库是**单连接、单 isolate**。所有查询/事务串行执行。

**问题**：Flutter 主 isolate 上做重查询会卡 UI。

**解决**：用 `sqflite_common_ffi` + isolate（桌面）或者 `sqflite_sqlcipher` 的多 isolate 支持。或者用 `compute()` 把查询甩到 isolate 里，但 sqflite 的 Database 对象不能跨 isolate。

**drift 的方案**：内置了 isolate 支持（`DriftIsolate`），主 isolate 只做 UI，数据库跑在后台 isolate。下一章详细讲。

## 8.13 drift 的事务 API

```dart
await database.transaction(() async {
  await database.into(database.users).insert(UsersCompanion.insert(name: 'Alice'));
  await database.into(database.posts).insert(PostsCompanion.insert(
    userId: userId,
    title: 'hello',
  ));
});
```

drift 的事务比 sqflite 更"隐形"——你直接用 `database.xxx`，drift 会自动路由到当前事务。**不用像 sqflite 一样传 txn**。

**批量插入**：

```dart
await database.batch((batch) {
  batch.insertAll(database.users, [
    UsersCompanion.insert(name: 'Alice'),
    UsersCompanion.insert(name: 'Bob'),
    UsersCompanion.insert(name: 'Carol'),
  ]);
});
```

drift 的 `batch` 也是事务里执行的。

**嵌套事务（用 SAVEPOINT 实现）**：

```dart
await db.transaction(() async {
  await insertUser(...);
  try {
    await db.transaction(() async {
      await insertPost(...);
      throw Exception('rollback inner');
    });
  } catch (e) {
    // 内层 SAVEPOINT 回滚，外层继续
  }
  await insertLog(...);
});
```

## 8.14 常见坑点合集

**坑 1：事务里用错了对象**

```dart
// sqflite 错误示范
await db.transaction((txn) async {
  await db.insert('t', {...});   // 用了 db 而不是 txn，死锁！
});
```

**坑 2：忘了在 WAL 模式下 checkpoint**

WAL 模式下，写入先追加到 `-wal` 文件，定期由 checkpoint 合并回主库。如果长时间不 checkpoint，`-wal` 文件会膨胀到几百 MB。默认 SQLite 会自动做，但极端情况需要手动：

```sql
PRAGMA wal_checkpoint(TRUNCATE);
```

**坑 3：DEFERRED 事务里升级锁失败**

```dart
await db.transaction((txn) async {
  final result = await txn.query('t');   // SHARED lock
  // 别的连接在这中间插入...
  await txn.insert('t', {...});           // 想升级 RESERVED，可能 BUSY
});
```

改用 `IMMEDIATE`：sqflite 不直接支持指定事务模式，但可以在事务开头先做一次写来隐式升级；或者用 drift 的 `TransactionMode.immediate`（不同版本支持不同，看文档）。

**坑 4：异常没让事务回滚**

如果你在事务里 `try-catch` 吃掉了异常，事务不会回滚：

```dart
await db.transaction((txn) async {
  await txn.insert(...);
  try {
    await txn.insert(...);   // 抛异常
  } catch (e) {
    print(e);   // 吃掉了！
  }
  // 事务会 COMMIT！
});
```

想部分失败继续走，用 SAVEPOINT，别吞异常。

**坑 5：事务里做异步操作**

```dart
await db.transaction((txn) async {
  await txn.insert(...);
  await http.get(url);   // 网络请求！事务持有锁 5 秒！
  await txn.insert(...);
});
```

**永远不要在事务里做非数据库的异步操作**。先把数据准备好，再进事务。

**坑 6：Batch 里做 SELECT**

```dart
final batch = db.batch();
batch.query('t');   // 不建议
```

Batch 的返回值处理很别扭。SELECT 应该用普通的 `query`。

## 8.15 本章小结

- ACID 是数据库的灵魂，SQLite 完整支持。
- `BEGIN`（DEFERRED）适合只读；写事务用 `BEGIN IMMEDIATE` 避免 BUSY。
- SAVEPOINT 实现嵌套事务/部分回滚。
- SQLite 默认 SERIALIZABLE，WAL 模式下读写并发（snapshot isolation）。
- 锁机制：UNLOCKED → SHARED → RESERVED → PENDING → EXCLUSIVE。
- `busy_timeout` + 应用层重试 + WAL 模式 = 消灭 SQLITE_BUSY。
- 长事务是万恶之源，别做异步/网络/用户交互。
- 批量操作 **必须** 用事务包裹（性能差 100 倍）。
- sqflite 的 Batch 减少跨语言桥接开销；drift 的 batch/transaction 更类型安全。
- **金句**：事务就像相亲——目的明确、快进快出、别磨叽。
