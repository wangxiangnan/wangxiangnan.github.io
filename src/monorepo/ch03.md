# Ch03: 项目结构设计

## 本章目标

- 理解 `apps/` 和 `packages/` 的职责区别
- 掌握包的命名约定和作用域（scope）的使用
- 为每个子包创建完整的 `package.json` 和基础文件
- 理解配置文件的集中 vs 分散策略
- 获得一个完整、可运行的目录结构

## 3.1 apps/ vs packages/：职责划分

在 monorepo 中，我们通常将代码分为两大类：

### apps/ — 应用层

`apps/` 目录存放**可独立部署和运行的应用**。它们的特点：

- 有入口文件（`main.ts`、`index.html`）
- 可以独立启动（`pnpm dev` 能跑起来）
- 不会被其他包引用（它们是依赖图的"叶子节点"）
- 有各自的路由、页面、中间件等

在我们的项目中：

- `apps/web`：Vue 3 前端应用
- `apps/api`：Express 后端应用

### packages/ — 共享层

`packages/` 目录存放**被多个 app 引用的共享代码**。它们的特点：

- 不独立运行，而是被 import 使用
- 需要 build 步骤（TypeScript 编译为 JavaScript）
- 导出具名接口（函数、类型、组件等）
- 应该保持精简，避免包含不必要的依赖

在我们的项目中：

- `packages/shared`：共享类型定义和工具函数
- `packages/eslint-config`：共享 ESLint 配置
- `packages/tsconfig`：共享 TypeScript 配置

> **核心原则：** apps 消费 packages，packages 之间可以互相依赖，但 apps 之间不应该互相依赖。

```
依赖方向（单向）：

  apps/web ──────► packages/shared
  apps/api ──────► packages/shared
  apps/web ──────► packages/eslint-config
  apps/api ──────► packages/eslint-config
  apps/web ──────► packages/tsconfig
  apps/api ──────► packages/tsconfig

  apps/web ──✕──► apps/api    （应用之间不互相引用）
```

## 3.2 包命名约定

在 monorepo 中，所有包都建议使用 **npm scope（作用域）** 来组织：

```
@taskflow/shared
@taskflow/eslint-config
@taskflow/tsconfig
```

使用 scope 的好处：

1. **避免命名冲突**：`shared` 这个名字在 npm 上早就被注册了，但 `@taskflow/shared` 只要 scope 可用就行
2. **语义清晰**：看到 `@taskflow/` 就知道这是 taskflow 项目的包
3. **workspace 引用方便**：在 `package.json` 中一眼就能区分内部包和外部依赖

```json
{
  "dependencies": {
    "@taskflow/shared": "workspace:*",    // ← 一看就是内部包
    "express": "^4.21.0",                 // ← 外部依赖
    "zod": "^3.24.0"                      // ← 外部依赖
  }
}
```

> **scope 名怎么选？** 通常使用项目名或组织名。如果是开源项目，scope 就是你的 npm 组织名。如果是内部项目，虽然不会发布到 npm，使用 scope 仍然是好的实践——它让代码更具组织性。

## 3.3 创建各子包

现在我们为每个子包创建完整的配置文件和基础代码。

### packages/tsconfig — TypeScript 共享配置

这个包存放所有包共用的 TypeScript 配置，每个包通过 `extends` 来继承。

创建 `packages/tsconfig/package.json`：

```json
{
  "name": "@taskflow/tsconfig",
  "version": "0.0.0",
  "private": true,
  "files": ["*.json"]
}
```

> **为什么 `"private": true`？** 共享配置包通常不需要发布到 npm（除非你想开源你的配置集）。标记为 private 可以防止意外发布。

创建基础 TypeScript 配置 `packages/tsconfig/base.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "isolatedModules": true,
    "module": "ESNext",
    "moduleResolution": "bundler",
    "noUncheckedIndexedAccess": true,
    "resolveJsonModule": true,
    "skipLibCheck": true,
    "sourceMap": true,
    "strict": true,
    "target": "ES2022"
  },
  "exclude": ["node_modules", "dist"]
}
```

关键选项解释：

- **`composite: true`**：启用 TypeScript 项目引用（Project References），这对于 monorepo 非常重要——它允许 TypeScript 理解包之间的依赖关系，实现增量编译。
- **`declaration: true` + `declarationMap: true`**：生成 `.d.ts` 声明文件和 source map。当 `packages/shared` 被 `apps/web` 引用时，前端需要 `.d.ts` 文件来获得类型提示。
- **`moduleResolution: "bundler"`**：使用 bundler 模式的模块解析，兼容 Vite、Turbopack 等现代打包工具。
- **`noUncheckedIndexedAccess: true`**：对通过索引访问的对象属性添加 `undefined` 类型，这是更安全的类型检查。
- **`strict: true`**：开启全部严格模式检查。

创建面向 Vue 应用的配置 `packages/tsconfig/vue-app.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "extends": "./base.json",
  "compilerOptions": {
    "jsx": "preserve",
    "jsxImportSource": "vue",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "noEmit": true
  }
}
```

创建面向 Node.js 应用的配置 `packages/tsconfig/node-app.json`：

```json
{
  "$schema": "https://json.schemastore.org/tsconfig",
  "extends": "./base.json",
  "compilerOptions": {
    "lib": ["ES2022"],
    "outDir": "dist",
    "rootDir": "src"
  }
}
```

> **为什么把 tsconfig 拆成多个？** 因为前端（Vue）和后端（Node.js）的 TypeScript 配置有本质区别：前端需要 DOM 类型、JSX 支持，不需要 emit（由 Vite 处理）；后端需要 emit 输出到 `dist/`，不需要 DOM 类型。通过 `extends` 继承公共配置，再覆盖差异部分，避免了大量重复配置。

### packages/eslint-config — 共享 ESLint 配置

创建 `packages/eslint-config/package.json`：

```json
{
  "name": "@taskflow/eslint-config",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": {
    "./base": "./base.js",
    "./vue": "./vue.js"
  },
  "dependencies": {
    "@eslint/js": "^9.39.5",
    "eslint-plugin-import": "^2.32.0",
    "eslint-plugin-vue": "^10.10.0",
    "typescript-eslint": "^8.67.0"
  },
  "peerDependencies": {
    "eslint": "^9.0.0"
  },
  "devDependencies": {
    "eslint": "^9.39.5"
  }
}
```

> **为什么用 `"exports"` 字段？** 这是 Node.js 的包导出映射（Package Exports），它定义了包的公共 API。`"./base"` 和 `"./vue"` 让使用方可以这样导入：`import baseConfig from "@taskflow/eslint-config/base"`。

创建基础 ESLint 配置 `packages/eslint-config/base.js`：

```js
import js from "@eslint/js";

      "@typescript-eslint/no-unused-vars": [
        "error",
        {
          argsIgnorePattern: "^_",
          varsIgnorePattern: "^_",
        },

      "@typescript-eslint/consistent-type-imports": "error",
      "import/order": [
        "error",
        {
          groups: [
            "builtin",
            "external",
            "internal",
            "parent",
            "sibling",
            "index",
          ],
          "newlines-between": "always",
        },
      ],
    },
  },
  {
    ignores: ["dist/", "node_modules/", "coverage/"],
  }
);
```

创建 Vue 专用配置 `packages/eslint-config/vue.js`：

```js
import baseConfig from "./base.js";

// 这里先导出基础配置，后续可以添加 vue-eslint-plugin 等

  ...baseConfig,
  {
    files: ["**/*.vue"],
    rules: {
      // Vue 特定规则将在 Part 2 中添加
    },
  },

```

### packages/shared — 共享类型和工具

创建 `packages/shared/package.json`：

```json
{
  "name": "@taskflow/shared",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./types": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/types/index.js"
    },
    "./utils": {
      "types": "./dist/utils/index.d.ts",
      "import": "./dist/utils/index.js"
    }
  },
  "scripts": {
    "build": "tsc --build",
    "dev": "tsc --build --watch",
    "clean": "rm -rf dist .turbo",
    "typecheck": "tsc --noEmit"
  },
  "dependencies": {
    "zod": "^4.4.3"
  },
  "devDependencies": {
    "@taskflow/tsconfig": "workspace:*",
    "typescript": "^5.9.3"
  }
}
```

> **为什么 `exports` 中要分别指定 `types` 和 `import`？** 这被称为"条件导出"（Conditional Exports）。当 TypeScript 解析这个包时，它使用 `types` 路径来找到 `.d.ts` 文件；当 JavaScript 运行时，使用 `import` 路径来找到 `.js` 文件。**`types` 必须放在 `import` 之前**，否则 TypeScript 会找不到类型。

创建 `packages/shared/tsconfig.json`：

```json
{
  "extends": "@taskflow/tsconfig/base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"],
  "exclude": ["dist", "node_modules"]
}
```

创建源代码文件。首先是 `packages/shared/src/types/index.ts`：

```typescript
/**
 * 任务状态枚举
 */
export enum TaskStatus {
  Todo = "todo",
  InProgress = "in_progress",
  Done = "done",
  Archived = "archived",
}

/**
 * 任务优先级
 */
export enum TaskPriority {
  Low = "low",
  Medium = "medium",
  High = "high",
  Urgent = "urgent",
}

/**
 * 任务接口定义
 */
export interface Task {
  id: string;
  title: string;
  description: string;
  status: TaskStatus;
  priority: TaskPriority;
  assigneeId: string | null;
  projectId: string;
  createdAt: string;
  updatedAt: string;
}

/**
 * 创建任务的输入类型
 * 使用 Omit 排除自动生成的字段
 */
export type CreateTaskInput = Omit<Task, "id" | "createdAt" | "updatedAt">;

/**
 * 更新任务的输入类型
 * 所有字段可选
 */
export type UpdateTaskInput = Partial<CreateTaskInput> & { id: string };

/**
 * 用户接口定义
 */
export interface User {
  id: string;
  name: string;
  email: string;
  avatarUrl: string | null;
  createdAt: string;
}
```

然后是 `packages/shared/src/utils/index.ts`：

```typescript
import type { Task, TaskPriority, TaskStatus } from "../types/index.js";

/**
 * 生成唯一 ID
 * 简单版本，生产环境建议使用 nanoid 或 uuid
 */
export function generateId(): string {
  return `${Date.now()}-${Math.random().toString(36).slice(2, 11)}`;
}

/**
 * 获取任务状态的显示标签
 */
export function getStatusLabel(status: TaskStatus): string {
  const labels: Record<TaskStatus, string> = {
    [TaskStatus.Todo]: "待办",
    [TaskStatus.InProgress]: "进行中",
    [TaskStatus.Done]: "已完成",
    [TaskStatus.Archived]: "已归档",
  };
  return labels[status];
}

/**
 * 获取任务优先级的颜色标识
 */
export function getPriorityColor(priority: TaskPriority): string {
  const colors: Record<TaskPriority, string> = {
    [TaskPriority.Low]: "#8b8b8b",
    [TaskPriority.Medium]: "#1890ff",
    [TaskPriority.High]: "#fa8c16",
    [TaskPriority.Urgent]: "#f5222d",
  };
  return colors[priority];
}

/**
 * 按优先级对任务排序（高优先级在前）
 */
export function sortTasksByPriority(tasks: Task[]): Task[] {
  const priorityOrder: Record<TaskPriority, number> = {
    urgent: 0,
    high: 1,
    medium: 2,
    low: 3,
  };
  return [...tasks].sort(
    (a, b) => priorityOrder[a.priority]! - priorityOrder[b.priority]!
  );
}
```

最后是入口文件 `packages/shared/src/index.ts`：

```typescript
export * from "./types/index.js";
export * from "./utils/index.js";
```

> **注意 `.js` 后缀**：在 TypeScript 的 `import` 语句中，我们写的是 `"../types/index.js"` 而不是 `"../types/index"` 或 `"../types/index.ts"`。这是因为 `moduleResolution: "bundler"` 模式下，TypeScript 期望导入路径反映编译后的实际路径（`.js`），而非源码路径（`.ts`）。这是一个常见的困惑点，但记住这个规则就好。

```json

      "@/*": ["src/*"]

app.use(cors());

    value: status,
    label: getStatusLabel(status),
  }));
  res.json(statuses);

app.listen(PORT, () => {
  console.log(`[API] Server running on http://localhost:${PORT}`);
});

export default app;
```

## 3.4 配置文件的组织策略

在 monorepo 中，配置文件有两种组织方式：

### 策略一：集中管理（推荐用于强一致性配置）

适用于：TypeScript、ESLint、Prettier 等**需要全项目统一**的配置。

做法是：创建一个专门的配置包（如 `packages/tsconfig`），其他包通过 `extends` 或 `import` 来继承。

```
packages/tsconfig/base.json      ← 所有包继承这个
packages/eslint-config/base.js   ← 所有包使用这个
```

优点：修改一处，全项目生效。确保代码风格和质量标准一致。

### 策略二：分散管理（适用于应用特有配置）

适用于：Vite 配置、Express 中间件、路由等**与应用强相关**的配置。

做法是：配置直接放在应用目录下。

```
apps/web/vite.config.ts     ← 前端特有
apps/api/src/index.ts       ← 后端特有
```

### 本教程的策略

| 配置类型 | 策略 | 位置 |
| --------- | ------ | ------ |
| TypeScript | 集中 | `packages/tsconfig` |
| ESLint | 集中 | `packages/eslint-config` |
| Prettier | 集中 | 根目录 `.prettierrc` |
| Vite | 分散 | `apps/web/vite.config.ts` |
| Express | 分散 | `apps/api/src/` |
| Turborepo | 集中 | 根目录 `turbo.json` |

创建根目录的 `.prettierrc`：

```json
{
  "semi": true,
  "singleQuote": false,
  "trailingComma": "es5",
  "printWidth": 80,
  "tabWidth": 2,
  "endOfLine": "lf"
}
```

## 3.6 安装依赖并验证

创建完所有文件后，在根目录执行：

```bash
pnpm install
```

pnpm 会自动分析所有子包的依赖，统一安装。你会看到 `node_modules/` 出现在根目录和各个包目录下（通过符号链接指向全局 store）。

然后构建共享包：

```bash
# 只构建 shared 包
pnpm --filter @taskflow/shared build
```

最后验证 workspace 列表：

```bash
pnpm ls -r --depth -1
```

应该输出类似：

```
@taskflow/api@0.0.0
@taskflow/eslint-config@0.0.0
@taskflow/shared@0.0.0
@taskflow/tsconfig@0.0.0
@taskflow/web@0.0.0
```

## 本章小结

- **apps/** 存放可独立运行的应用，**packages/** 存放被引用的共享代码
- 使用 `@scope/name` 的命名约定来组织包，提高可读性和避免冲突
- TypeScript 配置通过"基础配置 + extends"的模式实现集中管理
- ESLint 配置通过 `exports` 字段暴露不同的预设（base、vue）
- 每个包的 `package.json` 中的 `workspace:*` 引用是 monorepo 内部依赖的核心机制
