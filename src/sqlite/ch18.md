## 18.1 引言：拆开 SQLite 这个"俄罗斯套娃"

如果说数据库是程序员的黑盒，那 SQLite 就是那种"你以为它是黑盒，其实源码就 15 万行 C，你可以拆开看"的黑盒。别的数据库告诉你："别管里面怎么实现，你用 SQL 就行了。" SQLite 告诉你："来，把我拆开吧，我不介意。"

想象一下：你面前有一栋楼（数据库文件），楼里有很多层（页，Page），每一层有很多房间（记录，Record）。房间里放着家具（字段值），家具上贴着标签（类型信息）。楼的一楼大厅（Page 1）挂着整栋楼的地图（Schema），告诉你"3 楼是仓库，5 楼是办公室"。

这一章我们要做的事情，就是——**把这栋楼的图纸摊在桌上，一页一页翻给你看**。

准备好了吗？系好安全带，我们要跳进 SQLite 的兔子洞了。

## 18.2 数据库文件的宏观结构

### 18.2.1 一个文件搞定一切

SQLite 最让人拍案叫绝的设计是：**一个数据库 = 一个文件**。你没看错，就是一个普通的文件。你可以用 `cp`、`scp`、`rsync` 复制它，可以用 U 盘拷贝它，可以把它塞进邮件附件发给同事。

对比一下 PostgreSQL：一个数据库可能对应几十上百个文件，散落在 `pgdata` 目录的角落里，你敢直接 `cp` 试试？分分钟数据损坏给你看。

这个"单文件"设计对移动端简直是量身定制。你想，Flutter 应用要在 iOS 沙盒里存数据，如果 SQLite 也搞成一堆文件，那管理起来得多头疼。

### 18.2.2 文件的整体结构

一个 SQLite 数据库文件长这样：

```
+--------------------------------------+
| Page 1 (含 100 字节 Database Header) | 首页固定，特殊地位
+--------------------------------------+
| Page 2                               |
+--------------------------------------+
| Page 3                               |
+--------------------------------------+
| ...                                  |
+--------------------------------------+
| Page N                               |
+--------------------------------------+
```

关键点：

- **所有数据都被切成大小相等的页（Page）**
- **默认每页 4096 字节（4KB）**，SQLite 3.12 之后的默认值。之前是 1024 字节
- **页的编号从 1 开始**（不是从 0！这是 SQLite 的一个"梗"）
- **文件大小永远是页大小的整数倍**

一个数据库最多可以有多少页？$2^{31} - 2$，也就是约 21 亿页。按 4KB 算，单个数据库文件最大 8TB 左右。够你存到公司倒闭了。

## 18.3 页（Page）：SQLite 的最小 I/O 单元

### 18.3.1 为什么要有"页"这种东西？

想象你在图书馆借书。图书管理员会一次给你一整本书，而不是一页一页撕给你，对吧？操作系统读磁盘也一样——一次至少读一个"块"（block），通常 4KB。

如果 SQLite 每次只读 8 字节的一个整数，那操作系统底层还是要读 4KB，其余的 4088 字节就浪费了。所以 SQLite 干脆自己也按 4KB 组织数据，一次读一整页，读回来的数据尽量多用。

**页 = I/O 的原子单位，也是缓存的最小单位。**

### 18.3.2 页大小的选择

你可以在建库时指定页大小：

```sql
PRAGMA page_size = 8192;  -- 必须在创建任何表之前设置
VACUUM;                   -- 或者用 VACUUM 重建来改变现有库的页大小
```

页大小必须是 512 到 65536 之间的 2 的幂（512, 1024, 2048, 4096, 8192, 16384, 32768, 65536）。

**怎么选？**

- **移动端/桌面端**：默认 4096 就好，跟主流文件系统的块大小对齐
- **SSD/服务器**：8192 或 16384 可能有更好的吞吐
- **大 BLOB 场景**：更大的页可以减少 overflow，8192+ 合适
- **纯 key-value 小值**：小页（1024）可能省内存

**别乱改！** 除非你有性能测试数据支撑，否则请老老实实用默认值。

### 18.3.3 页的类型

SQLite 里的页分好几种角色，就像一个公司里有 CEO、销售、程序员、保洁：

| 页类型 | 作用 | 类比 |
| --- | --- | --- |
| Table B-Tree Interior Page | 表 B 树的内部节点 | 目录树 |
| Table B-Tree Leaf Page | 表 B 树的叶子节点，存实际数据 | 存货的仓库 |
| Index B-Tree Interior Page | 索引 B 树的内部节点 | 图书目录 |
| Index B-Tree Leaf Page | 索引 B 树的叶子节点 | 图书索引 |
| Overflow Page | 存放超长记录的溢出数据 | 备用仓库 |
| Freelist Trunk Page | 空闲页链表的干节点 | 空房登记册 |
| Freelist Leaf Page | 空闲页 | 空房 |
| Pointer Map Page | 记录页父页指针（仅 auto_vacuum 开启时） | 楼层反向索引 |
| Lock-byte Page | 特殊的锁字节页（仅在 1GB 位置附近） | 门锁 |

第一页最特殊——它同时是"数据库大堂"（含 100 字节 header）和一个表 B-Tree 页。SQLite 硬把它俩塞一块了，节省空间。

## 18.4 数据库头（Database Header）：100 字节的秘密

数据库文件的前 100 字节就是 header，它承载了整个数据库的"身份证信息"。

### 18.4.1 Header 字段解剖

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 16 | Magic Header String | 固定为 `SQLite format 3\000` |
| 16 | 2 | Page Size | 页大小（1 表示 65536） |
| 18 | 1 | File format write version | 写入格式版本（1=legacy, 2=WAL） |
| 19 | 1 | File format read version | 读取格式版本 |
| 20 | 1 | Reserved space per page | 每页保留字节（一般 0，加密用） |
| 21 | 1 | Max embedded payload fraction | 固定 64 |
| 22 | 1 | Min embedded payload fraction | 固定 32 |
| 23 | 1 | Leaf payload fraction | 固定 32 |
| 24 | 4 | File change counter | 文件改动计数器 |
| 28 | 4 | Database size in pages | 数据库总页数 |
| 32 | 4 | First freelist trunk page | 第一个空闲页链表 |
| 36 | 4 | Freelist page count | 空闲页数量 |
| 40 | 4 | Schema cookie | Schema 版本号 |
| 44 | 4 | Schema format number | Schema 格式（1-4） |
| 48 | 4 | Default page cache size | 默认页缓存大小 |
| 52 | 4 | Largest root b-tree page | auto_vacuum 相关 |
| 56 | 4 | Text encoding | 1=UTF-8, 2=UTF-16le, 3=UTF-16be |
| 60 | 4 | User version | 用户自定义版本（PRAGMA user_version） |
| 64 | 4 | Incremental vacuum mode | 增量 vacuum 标志 |
| 68 | 4 | Application ID | 应用标识（PRAGMA application_id） |
| 72 | 20 | Reserved | 保留 |
| 92 | 4 | Version-valid-for number | 有效性检查 |
| 96 | 4 | SQLITE_VERSION_NUMBER | 最后修改的 SQLite 版本 |

### 18.4.2 亲自动手看一看

我们用 `xxd` 把数据库前 100 字节的十六进制看一眼：

```bash
# 创建一个测试库
sqlite3 test.db "CREATE TABLE t(id INTEGER, name TEXT); INSERT INTO t VALUES(1, 'hello');"

# 查看前 100 字节
xxd -l 100 test.db
```

你会看到类似的输出：

```
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
00000010: 1000 0101 0040 2020 0000 0002 0000 0002  .....@  ........
00000020: 0000 0000 0000 0000 0000 0000 0000 0001  ................
...
```

看到那个 `SQLite format 3` 了吗？这就是所有 SQLite 数据库的"接头暗号"。

用 SQL 也能读：

```sql
-- 用户版本
PRAGMA user_version;

-- 应用 ID（可用来区分你的应用生成的库）
PRAGMA application_id;

-- 文本编码
PRAGMA encoding;

-- Schema 版本（每次 DDL 会变）
PRAGMA schema_version;
```

### 18.4.3 application_id 是什么鬼？

`application_id` 是一个 4 字节整数，作用类似文件的"magic number"。你可以用它来标识"这个数据库是我 X 应用的"。

```sql
PRAGMA application_id = 0x4E4F5445;  -- 'NOTE' 的 ASCII
```

`file` 命令用它来识别 SQLite 数据库类型：

```bash
$ file mynotes.db
mynotes.db: SQLite 3.x database, application id 1313817413, ...
```

这是个小技巧，第 22 章我们做笔记应用时会用上。

## 18.5 B-Tree：SQLite 数据结构的灵魂

### 18.5.1 B-Tree 复习课

B-Tree（Balanced Tree）是一种自平衡多叉搜索树。特点：

- 每个节点可以有多个 key（不像二叉树只有一个）
- 树是平衡的，所有叶子到根的路径长度相同
- 时间复杂度 O(log N)

为什么数据库爱用 B-Tree？因为**磁盘 I/O 昂贵**。二叉树太"瘦高"，找一个数据要访问 log₂(N) 次；B-Tree 又"矮又胖"，一次读一页能同时比较很多 key，减少磁盘访问次数。

如果 N = 10 亿：

- 二叉树深度 ≈ 30
- B-Tree 深度 ≈ 4~5

这就是差距。**磁盘上，扁平就是快。**

### 18.5.2 B-Tree vs B+Tree：SQLite 选了哪个？

这是一个经典的"面试送分题"（或者送命题）。

- **B-Tree**：内部节点和叶子节点都存 key 和数据
- **B+Tree**：数据只存在叶子节点，内部节点只存 key 用于导航；叶子节点通常还用链表串起来方便范围扫描

SQLite 的实现有点"混血"：

> **表用 B+Tree 风格（数据只在叶子），索引用 B-Tree 风格（内部节点也存 key）。**

准确说法：

- **Table B-Tree**：以 rowid 为 key，只有叶子节点存实际的行数据。这实际上就是 B+Tree 的结构。
- **Index B-Tree**：以索引列为 key，所有节点都存 key 和被索引行的 rowid。这更接近传统 B-Tree。

MySQL 的 InnoDB 也是类似的路线——**聚簇索引**（clustered index），主键 B+Tree 直接存整行数据。SQLite 里 rowid 就是"隐式的聚簇索引"。

### 18.5.3 Rowid 的物理意义

每一张普通表（不带 `WITHOUT ROWID` 的）都有一个隐式的 64 位整数 rowid：

```sql
CREATE TABLE users(name TEXT);
INSERT INTO users(name) VALUES('Alice'), ('Bob');
SELECT rowid, name FROM users;
-- 1|Alice
-- 2|Bob
```

如果你定义了 `INTEGER PRIMARY KEY`，它就是 rowid 的别名：

```sql
CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO users(id, name) VALUES(100, 'Alice');
SELECT rowid, id, name FROM users;
-- 100|100|Alice   -- rowid 和 id 是同一个东西
```

**这就是为什么 `INTEGER PRIMARY KEY` 比 `INT PRIMARY KEY` 快**——前者是 rowid 本身，后者要额外维护一棵索引 B-Tree。

**关键理解**：Table B-Tree 按 rowid 排序。所以：

- 按 rowid（或 INTEGER PRIMARY KEY）查询极快，直接 B-Tree 定位
- 按 rowid 范围扫描是顺序 I/O，非常快
- 插入自增 rowid 是尾部追加，几乎不用调整树结构

顺便，`AUTOINCREMENT` 关键字会额外维护 `sqlite_sequence` 表来保证 rowid 严格递增（不会重用已删除的）。它有性能开销。**没有强需求就别用 AUTOINCREMENT**，普通的 `INTEGER PRIMARY KEY` 就足够了。

### 18.5.4 WITHOUT ROWID 表

有时候，rowid 是"多余的"。比如你的表有一个天然的字符串主键：

```sql
CREATE TABLE dict(
  word TEXT PRIMARY KEY,
  meaning TEXT
) WITHOUT ROWID;
```

`WITHOUT ROWID` 表的差别：

- 没有隐式的 rowid
- 主键就是 B-Tree 的 key，数据直接存在主键 B-Tree 的叶子上
- 没有"主键 → rowid → 行数据"的两次查找

**什么时候用 WITHOUT ROWID？**

官方推荐：

- 主键是非整数或复合的
- 每行数据比较小（否则 overflow 惩罚会加大）
- 你不需要 rowid（比如你不用 `last_insert_rowid`）

**不适合的场景**：

- 表的行很大（比如包含大 TEXT/BLOB），因为 rowid 表有"row split" 优化，而 WITHOUT ROWID 没有
- 你频繁需要 `INTEGER PRIMARY KEY` 的极致性能

移动端一般用普通的 `INTEGER PRIMARY KEY` 就够，除非你在做字典类应用。

## 18.6 记录格式（Record Format）：字节级探秘

一条记录（Row）在页上到底是怎么存的？这里就要引入 SQLite 的"变长编码"设计了。

### 18.6.1 记录的物理结构

每条记录由两部分组成：

```
+------------------+------------------+
| Header           | Body             |
| (类型序列)        | (值序列)          |
+------------------+------------------+
```

- **Header**：一个 varint 表示 header 长度，然后是每一列的"类型码"（也是 varint）
- **Body**：按 header 里的类型码顺序，存放实际的值

### 18.6.2 varint：可变长度整数

varint 是 SQLite 用来节省空间的杀手锏。一个整数按其大小占用 1~9 字节：

- 值 0~127：1 字节
- 值 128~16383：2 字节
- ...
- 值极大：最多 9 字节

规则：每字节的最高位是"续位标志"，为 1 表示"下面还有一字节"。跟 Protocol Buffers 的 varint 类似。

例子：

- 数字 5 → `0x05`（1 字节）
- 数字 300 → `0x82 0x2C`（2 字节）

这样，一列存 0~127 的小数字只用 1 字节，比固定 4 字节整数省 3 字节。数据量大时这个优化很可观。

### 18.6.3 类型码（Serial Type）

SQLite 的每列值都带一个类型码，规则：

| Serial Type | 长度 | 含义 |
| --- | --- | --- |
| 0 | 0 | NULL |
| 1 | 1 | 8 位有符号整数 |
| 2 | 2 | 16 位大端整数 |
| 3 | 3 | 24 位大端整数 |
| 4 | 4 | 32 位大端整数 |
| 5 | 6 | 48 位大端整数 |
| 6 | 8 | 64 位大端整数 |
| 7 | 8 | IEEE 754 双精度浮点 |
| 8 | 0 | 常量 0（BOOL false） |
| 9 | 0 | 常量 1（BOOL true） |
| 10, 11 | - | 保留 |
| N ≥ 12 且 N 为偶数 | (N-12)/2 | BLOB |
| N ≥ 13 且 N 为奇数 | (N-13)/2 | TEXT |

看出来了吗？**类型码本身就编码了长度**。SQLite 通过这种方式实现"每一行的每一列可以是不同类型"（这就是所谓的 **manifest typing** 或 **动态类型**）。

例子：一列存值 `42`：

- 42 < 128，能用 8 位整数
- Serial Type = 1，值占 1 字节
- 存储：`01 2A`（类型 1，值 0x2A=42）

一列存字符串 `"hi"`：

- TEXT 长度 2，Serial Type = 13 + 2×2 = 17
- 存储：`11 68 69`（类型 17，然后 'h'=0x68, 'i'=0x69）

**结论**：SQLite 的一行数据非常紧凑。小整数只占 1 字节，NULL 0 字节，BLOB/TEXT 自带长度。这就是为什么 SQLite 数据库通常比同等数据的 CSV 还小。

### 18.6.4 亲手拆一条记录

创建一个简单表：

```sql
CREATE TABLE demo(a INTEGER, b TEXT, c REAL);
INSERT INTO demo VALUES(5, 'hi', 3.14);
```

理论上这条记录的 header：

- header 长度：4（1 字节的 header 长度 + 3 个类型码）
- 类型码：01（int8）、11（TEXT 长度 2）、07（REAL）

body：

- 5 → 0x05
- 'hi' → 0x68 0x69
- 3.14 → 0x40 09 1E B8 51 EB 85 1F

整条记录约 13 字节。够小吧？

## 18.7 Overflow 页：超长记录的处理

### 18.7.1 一页装不下怎么办？

假设默认页 4KB，除去页头和其他开销，一页大约能装 4050 字节的数据。如果你有一个 100KB 的 BLOB 怎么办？

SQLite 的策略：**部分数据存本页，剩下的存到 Overflow 页**。Overflow 页彼此用链表串起来，每页开头 4 字节指向下一个 Overflow 页，剩下的存数据。

```
Leaf Page: [header | ... | prefix bytes | overflow_page_number ]
                                              |
                                              v
Overflow Page 1: [next_page_number | data...]
                       |
                       v
Overflow Page 2: [next_page_number | data...]
                       |
                       v
Overflow Page N: [0 (末尾标志) | data...]
```

### 18.7.2 触发 Overflow 的条件

有个公式（简化版）：**payload > U - 35 时开始 overflow**，其中 U = 页大小 - 保留字节。

大致规则：

- **默认 4KB 页**：单行超过约 4050 字节就开始 overflow
- 前部分数据尽量塞满本页
- 剩下的进 Overflow 链表

### 18.7.3 Overflow 的代价

访问一条 overflow 的记录需要多次 I/O：

- 读主页 → 得到本页部分数据和第一个 overflow 页号
- 读 overflow 页 1 → 得到部分数据和下一页号
- ...

**大 BLOB 存 SQLite 里性能会掉**。经验法则：

- 小于 1KB 的 BLOB：直接存 SQLite 里，方便
- 1KB ~ 100KB：可以存，但注意性能
- 大于 100KB：**存文件系统，SQLite 里只存文件路径**

有个著名的 SQLite 官方 benchmark 叫 [35% Faster Than The Filesystem](https://www.sqlite.org/fasterthanfs.html)，表明存 <100KB 的 BLOB 到 SQLite 反而比文件系统还快。所以别一竿子打死，看场景。

## 18.8 空闲列表（Freelist）与 auto_vacuum

### 18.8.1 页面的生生死死

删除数据时，SQLite 并不会立刻缩小文件。想想看，如果你删了 1000 行然后又要插入 900 行，反复缩放文件多累。所以：

**删除的页会加入"空闲列表"（Freelist），下次分配时优先复用。**

Freelist 由两种页组成：

- **Freelist Trunk Page**：主干页，本身也是空闲页，但存着其他空闲页的编号
- **Freelist Leaf Page**：完全空的空闲页

Header 里的偏移 32（First freelist trunk page）指向第一个 Trunk 页。

### 18.8.2 VACUUM：手动整理

`VACUUM` 命令会重建整个数据库，把碎片清理掉，文件也会缩小：

```sql
VACUUM;
```

VACUUM 的原理：

1. 把当前数据库的所有内容复制到临时数据库
2. 用临时数据库替换原数据库

**代价：需要 2 倍数据库大小的临时空间**。所以移动端要谨慎。

### 18.8.3 auto_vacuum 模式

```sql
PRAGMA auto_vacuum = FULL;     -- 每次事务提交自动整理，回收空间
PRAGMA auto_vacuum = INCREMENTAL; -- 空间进入待回收，需手动 PRAGMA incremental_vacuum
PRAGMA auto_vacuum = NONE;     -- 默认，不自动整理
```

**必须在创建任何表之前设置**，否则要 VACUUM 一次才能生效。

`FULL` 模式会引入额外开销（每个事务都要整理）。建议：

- 数据频繁增删的应用：`INCREMENTAL`，定期手动 `PRAGMA incremental_vacuum(N)`
- 数据稳定或纯增长：`NONE`，不需要 auto_vacuum

FULL 模式还会引入一种页——**Pointer Map Page**，用来做逆向查找。每 K 个页有一个 pointer map 页，记录哪个页是别人的孩子。开启 auto_vacuum 有轻微空间开销。

## 18.9 用 dbstat 虚拟表看内部

SQLite 内置了一个"透视法宝"——`dbstat` 虚拟表，可以窥探每一页的信息。前提是 SQLite 编译时开启了 `SQLITE_ENABLE_DBSTAT_VTAB`（大多数发行版都开了）。

```sql
-- 看看每一页的类型和大小
SELECT pageno, pagetype, ncell, payload, unused FROM dbstat;

-- 统计不同类型的页数量
SELECT pagetype, COUNT(*) FROM dbstat GROUP BY pagetype;

-- 看某张表占了几页
SELECT SUM(pgsize) FROM dbstat WHERE name = 'users';
```

字段含义：

- `pageno`：页号
- `pagetype`：`internal`/`leaf`/`overflow`
- `ncell`：这一页有多少条记录
- `payload`：实际数据字节
- `unused`：未使用字节（碎片）
- `mx_payload`：最大记录长度
- `pgsize`：页大小

**这个虚拟表能帮你回答**：

- 我的数据库有多少碎片？
- 某张表实际占多大空间？
- 哪张表的 overflow 最多？

## 18.10 sqlite_master：Schema 的档案室

所有的 Schema 信息（表定义、索引定义等）都存在 `sqlite_master` 表里（新版叫 `sqlite_schema`）：

```sql
SELECT type, name, tbl_name, rootpage, sql FROM sqlite_master;
```

结果示例：

```
type   name          tbl_name  rootpage  sql
-----  ------------  --------  --------  ----------------------------------
table  users         users     2         CREATE TABLE users(...)
index  idx_email     users     3         CREATE INDEX idx_email ON users(email)
table  posts         posts     4         CREATE TABLE posts(...)
```

字段解读：

- `type`：`table` / `index` / `view` / `trigger`
- `name`：对象名字
- `tbl_name`：所属表
- `rootpage`：B-Tree 根页号（对 view/trigger 为 0）
- `sql`：创建它的 SQL 语句

**梗**：这个表其实自己就是一个 B-Tree，根页永远是 Page 1。启动时 SQLite 读第 1 页就能拿到整个 Schema。

有几个"影子表"：

- `sqlite_sequence`：AUTOINCREMENT 用的序列表
- `sqlite_stat1/2/3/4`：ANALYZE 命令产生的统计信息
- `sqlite_temp_master`：临时对象

## 18.11 SQLite 架构分层

来看看 SQLite 内部代码是怎么组织的。官方文档有一张经典架构图，我给你画个 ASCII 版：

```
+-----------------------------------------------+
|                Interface (SQL API)            |  你调用的 sqlite3_exec 等函数
+-----------------------------------------------+
|                  Tokenizer                    |  SQL 分词
+-----------------------------------------------+
|                  Parser                       |  SQL 语法分析
+-----------------------------------------------+
|              Code Generator                   |  生成 VDBE 字节码
+-----------------------------------------------+
|         Virtual Machine (VDBE)                |  执行字节码
+-----------------------------------------------+
|                B-Tree                         |  管理 B-Tree
+-----------------------------------------------+
|                Pager                          |  管理页缓存、事务、锁
+-----------------------------------------------+
|                OS Interface (VFS)             |  跨平台 I/O 抽象
+-----------------------------------------------+
|         OS (文件系统、mmap、锁)                |
+-----------------------------------------------+
```

分层职责：

1. **Tokenizer**：把 `SELECT * FROM users` 切成 `[SELECT, *, FROM, users]`
2. **Parser**：把 tokens 变成 AST
3. **Code Generator**：把 AST 变成 VDBE 字节码（可以用 `EXPLAIN` 看到）
4. **VDBE**：一个字节码虚拟机，逐条执行指令
5. **B-Tree**：提供有序 key-value 存储
6. **Pager**：管理页、缓存、事务、WAL、锁
7. **VFS**：Virtual File System，抽象各种操作系统的文件 I/O

**VDBE 是 SQLite 的心脏**。它是一个专门为 SQL 设计的字节码 VM，就像 Java 的 JVM。你可以看到它执行的指令：

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;
```

输出（简化）：

```
addr  opcode         p1  p2  p3  p4      p5  comment
----  -------------  --  --  --  ------  --  -------
0     Init           0   9   0           00
1     OpenRead       0   2   0   2       00  root=2
2     Integer        1   1   0           00  r[1]=1
3     SeekRowid      0   8   1           00  intkey=r[1]
4     Rowid          0   2   0           00  r[2]=rowid
5     Column         0   1   3           00  r[3]=name
6     ResultRow      2   2   0           00  output
7     Close          0   0   0           00
8     Halt           0   0   0           00
9     Transaction    0   0   1           01
10    Goto           0   1   0           00
```

看，每条指令都是一个"微操作"，跟 CPU 指令类似。SQLite 的所有 SQL 最终都变成这样的字节码执行。理解 VDBE 是深度优化 SQL 的钥匙。

## 18.12 常见坑点

### 坑 1：修改 page_size 不生效

`PRAGMA page_size = 8192` 必须在**创建任何表之前**执行，或者执行后 `VACUUM` 一次才生效。很多同学改完发现没变化，就是忘了这一步。

### 坑 2：删除数据文件不缩小

初学者的常见困惑：删了一半数据，文件为什么没变小？答：加入 Freelist 复用了。想缩小，`VACUUM` 或 `PRAGMA incremental_vacuum`。

### 坑 3：过度用大 BLOB

前面说了，>100KB 的 BLOB 建议存文件系统。别把用户头像这种东西一股脑塞库里，除非有强需求。

### 坑 4：INTEGER PRIMARY KEY vs INT PRIMARY KEY

```sql
CREATE TABLE t1(id INT PRIMARY KEY);         -- 慢，多一棵索引 B-Tree
CREATE TABLE t2(id INTEGER PRIMARY KEY);     -- 快，id 就是 rowid
```

只有 `INTEGER PRIMARY KEY`（完全匹配大小写和拼写）才是 rowid 别名。`INT`、`Integer`（新版本兼容）需要注意。

### 坑 5：rowid 会被复用

不用 AUTOINCREMENT 时，删除一行后其 rowid 可能被新行复用。别把 rowid 当"永久 ID"用于外键之类的场景，除非你用 AUTOINCREMENT。

## 18.13 本章小结

呼——我们把 SQLite 拆开看了整整一章。核心记忆点：

- **文件 = 页序列**，默认 4KB 一页
- **前 100 字节** 是 header，含 magic number、页大小、用户版本等
- **表用 B+Tree**（数据在叶子），**索引用 B-Tree**
- **rowid** 是普通表的隐式主键，`INTEGER PRIMARY KEY` 就是它的别名
- **记录用 varint 编码**，字节级紧凑
- **大数据用 Overflow 页链表**
- **删除的页进 Freelist**，`VACUUM` 收缩
- **dbstat 虚拟表** 是你的透视镜
- **架构分层**：SQL → VDBE → B-Tree → Pager → VFS

理解了这些，你以后看 SQLite 就不再是黑盒。你会知道"为什么加索引快"，"为什么 BLOB 别塞太大"，"为什么 rowid 查询这么屌"。

下一章我们要讲 SQLite 现代化的一大革命——**WAL 模式**。这是移动端和高并发场景的必修课。
