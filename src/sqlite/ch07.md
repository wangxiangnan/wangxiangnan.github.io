# 第7章：约束与索引——数据完整性护城河

## 7.1 开场白：为什么要给数据库立规矩？

想象你在做一个用户注册系统，早晨版本 v1 上线。

- 有个用户注册时没填邮箱，代码里没校验，数据库里就存了 `NULL`。
- 又来一个用户，邮箱填的是 `null`（字符串）。
- 第三个用户的邮箱是 `''`（空字符串）。
- 第四个用户注册了两次，同一个邮箱写了两条记录。
- 第五个用户注册后被删了，但他发的帖子还挂在他名下——查用户时报"用户不存在"。

一天之内，你的数据库就变成了垃圾场。**这不是用户的错，是你没立规矩。**

数据完整性约束（Integrity Constraints）就是数据库的**护城河**——用户/程序/你自己写的 bug 都进不来。索引则是**高速公路**——立完规矩之后还能查得飞快。

这一章我们把约束和索引一起讲，因为它们像双胞胎——一个保证正确，一个保证快。

## 7.2 完整性约束的三大分类

从关系数据库理论角度看，约束分三类：

1. **域约束（Domain Constraint）**：单个字段的取值范围。比如"年龄必须是正数"、"性别只能是 M/F/N"。→ CHECK、NOT NULL、DEFAULT
2. **实体约束（Entity Constraint）**：一行数据的唯一性。比如"每个用户 id 唯一"。→ PRIMARY KEY、UNIQUE
3. **参照约束（Referential Constraint）**：跨表的引用关系。比如"订单里的用户 id 必须在用户表存在"。→ FOREIGN KEY

SQLite 支持全部三类。下面挨个说。

## 7.3 NOT NULL——最基础的护城河

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,               -- 必填
  email TEXT NOT NULL DEFAULT '',   -- 必填但有默认值
  bio  TEXT                          -- 可空
);
```

**冷知识**：在 SQLite 里，`INTEGER PRIMARY KEY` **允许 NULL**（会被自动分配 rowid）。这是历史包袱，别的关系数据库都不允许。如果你不想要这个"惊喜"，加上 `NOT NULL`：

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY NOT NULL, ...);
```

## 7.4 UNIQUE——唯一性

```sql
-- 单列 UNIQUE
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  email TEXT UNIQUE NOT NULL
);

-- 多列组合 UNIQUE
CREATE TABLE enrollment(
  student_id INTEGER,
  course_id  INTEGER,
  UNIQUE(student_id, course_id)
);
```

**UNIQUE 允许多个 NULL**（因为 NULL 不等于 NULL）。这跟 MySQL 一致，跟 SQL Server 不同。

**UNIQUE 会自动创建索引**，所以 UNIQUE 列的查询是快的。

## 7.5 CHECK——自定义规则

```sql
CREATE TABLE product(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  price REAL NOT NULL CHECK (price >= 0),
  discount REAL DEFAULT 0 CHECK (discount BETWEEN 0 AND 1),
  status TEXT CHECK (status IN ('active', 'inactive', 'archived')),
  -- 表级 CHECK：可以引用多列
  CHECK (price * (1 - discount) >= 0)
);
```

**CHECK 里能写什么？** 任何非确定性以外的表达式：算术、比较、`IN`、`LIKE`、`BETWEEN`、`CASE`、SQLite 内置函数……

**不能用什么？** 子查询（3.32 之前）、随机函数、`datetime('now')` 这种非确定性函数（会有警告但不会拒绝）。

## 7.6 DEFAULT——默认值

```sql
CREATE TABLE post(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  views INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),      -- 表达式默认值要加括号
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP        -- 特殊关键字
);
```

三种特殊 DEFAULT 关键字（不加括号）：

- `CURRENT_TIME` → `HH:MM:SS`
- `CURRENT_DATE` → `YYYY-MM-DD`
- `CURRENT_TIMESTAMP` → `YYYY-MM-DD HH:MM:SS`（UTC）

想用其他表达式（比如 `datetime('now', 'localtime')`、`RANDOM()`）必须**加括号**。

## 7.7 PRIMARY KEY——主键

我们在第 6 章讲过 `INTEGER PRIMARY KEY` 是 rowid 别名。这里补充其他细节：

**单列主键**：

```sql
CREATE TABLE user(id INTEGER PRIMARY KEY, ...);
CREATE TABLE user(uuid TEXT PRIMARY KEY, ...);            -- 非整数主键（额外索引）
```

**复合主键**：

```sql
CREATE TABLE enrollment(
  student_id INTEGER,
  course_id  INTEGER,
  grade REAL,
  PRIMARY KEY(student_id, course_id)
);
```

**WITHOUT ROWID 表**（3.8.2+）：

```sql
CREATE TABLE cache(
  key TEXT PRIMARY KEY,
  value BLOB
) WITHOUT ROWID;
```

`WITHOUT ROWID` 表用主键做 B-Tree 的键（而不是 rowid），适合：

- 主键不是整数（比如 UUID 字符串）
- 主键就是查询主体（比如 KV 缓存）
- 每行数据都很小

不适合：主键很长、行数据很大、频繁按非主键查询的场景。

## 7.8 FOREIGN KEY——参照约束

外键是"跨表的规矩"，比如订单的 `user_id` 必须在用户表存在。

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE post(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  user_id INTEGER NOT NULL,
  FOREIGN KEY(user_id) REFERENCES user(id)
);
```

**惊喜时刻**：SQLite 默认**不启用外键约束**！你以为你写了 FOREIGN KEY 就会检查，然而没有。

为什么？历史原因：SQLite 3.6.19 之前根本不支持外键，只是解析不报错。为了向后兼容，之后默认关闭。

**怎么开启？**

```sql
PRAGMA foreign_keys = ON;
```

这个 PRAGMA **是连接级的**——每个数据库连接都要单独开启。而且不能在事务里改。

**在 Flutter 里怎么开启？**

sqflite:

```dart
final db = await openDatabase(
  path,
  onConfigure: (db) async {
    await db.execute('PRAGMA foreign_keys = ON');
  },
);
```

drift（默认帮你开）：

```dart
class MyDatabase extends _$MyDatabase {
  MyDatabase() : super(_openConnection());

  @override
  MigrationStrategy get migration => MigrationStrategy(
    beforeOpen: (details) async {
      await customStatement('PRAGMA foreign_keys = ON');
    },
  );
}
```

## 7.9 级联操作：CASCADE / SET NULL / RESTRICT / NO ACTION

外键约束的重头戏是**当被引用的记录发生变化时，引用方怎么办**：

```sql
CREATE TABLE post(
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  FOREIGN KEY(user_id) REFERENCES user(id)
    ON DELETE CASCADE      -- 用户被删，帖子跟着删
    ON UPDATE CASCADE      -- 用户 id 变了，帖子里的 user_id 跟着变
);
```

四种动作：

| 动作          | 含义                                        | 场景                     |
| ------------- | ------------------------------------------- | ------------------------ |
| `CASCADE`     | 级联执行：父行删/改，子行跟着删/改          | 强关联，如帖子跟着用户   |
| `SET NULL`    | 子行的外键列设为 NULL                       | 弱关联，如订单的推荐人   |
| `SET DEFAULT` | 子行外键列设为默认值                        | 少用                     |
| `RESTRICT`    | 立即报错，阻止父行操作                      | 严格保护                 |
| `NO ACTION`   | 默认，事务结束时才检查（几乎等同 RESTRICT） | 默认                     |

`RESTRICT` vs `NO ACTION` 的区别：`RESTRICT` 立即报错，`NO ACTION` 允许在事务里临时违反、但事务结束时必须恢复合法状态。日常用 `NO ACTION`（默认）或 `CASCADE` 就够了。

## 7.10 索引——数据库的目录

想象你有一本 1000 页的书，要找"关系代数"这个词。

- **没索引**：从第一页翻到最后一页，O(n)。
- **有索引**：翻到目录，找到"关系代数 P.487"，直接翻到 487 页，O(log n)。

SQLite 用的是 **B-Tree**（准确说是 B+Tree 的变种）作为索引结构。每个索引都是一棵独立的 B-Tree，键是索引列的值，"值"是指向原表的 rowid（或主键，对于 WITHOUT ROWID 表）。

## 7.11 B-Tree 的直观理解

一棵 B-Tree 长这样（简化到 3 阶）：

```
              [ 30 | 60 ]
             /     |     \
       [10,20] [40,50] [70,80,90]
```

查找 40：

1. 根节点：40 在 30 和 60 之间 → 走中间分支
2. 中间节点：找到 40 → 返回

查找的关键：**每一层做 O(log n) 的比较**。10 亿行数据大概只需要 30 次左右比较。

B-Tree 的特点：

- **有序**：这就是为什么索引能加速 `ORDER BY` 和范围查询。
- **平衡**：不会像普通二叉树那样退化成链表。
- **多路**：一个节点存多个键，减少磁盘 IO。

## 7.12 单列索引

```sql
CREATE INDEX idx_user_email ON user(email);

-- 唯一索引
CREATE UNIQUE INDEX idx_user_phone ON user(phone);
```

**什么时候建索引？**

- 频繁在 WHERE 里做等值/范围查询的列。
- 频繁 JOIN 的关联列。
- 频繁 ORDER BY 的列。

**什么时候不建？**

- 数据量很小（<1000 行）。
- 列值区分度极低（比如 `gender` 只有男/女）。
- 频繁 UPDATE 且写多读少。

## 7.13 多列索引（复合索引）

```sql
CREATE INDEX idx_post_user_time ON post(user_id, created_at);
```

**最左前缀原则**：这个索引能加速下面这些查询：

- `WHERE user_id = ?`
- `WHERE user_id = ? AND created_at > ?`
- `WHERE user_id = ? ORDER BY created_at`
- `ORDER BY user_id, created_at`

但**不能**加速：

- `WHERE created_at > ?`（跳过了最左的 user_id）
- `ORDER BY created_at`

想象成一个电话簿按"姓+名"排序：你能快速找"张三"，但要找所有叫"三"的人就得全本翻。

**列顺序的选择原则**：

1. 等值查询列放前面。
2. 区分度高的列放前面。
3. 排序列放后面。

## 7.14 覆盖索引（Covering Index）

如果一个查询要的**所有列**都在索引里，SQLite 就不用回表（去原表查 rowid 对应的其他列）了——这叫覆盖索引：

```sql
-- 表结构
CREATE TABLE post(id INTEGER PRIMARY KEY, user_id INT, title TEXT, content TEXT);

-- 索引
CREATE INDEX idx1 ON post(user_id, title);

-- 覆盖！只读索引就够了
SELECT user_id, title FROM post WHERE user_id = 5;

-- 不覆盖！要回表读 content
SELECT user_id, title, content FROM post WHERE user_id = 5;
```

覆盖索引的性能提升可能是数量级的（省了一次树查找）。但索引越"胖"，写入越慢，磁盘占用越大——权衡。

## 7.15 索引的排序方向

```sql
CREATE INDEX idx_post_time ON post(created_at DESC);
```

指定 `DESC` 后，索引本身按倒序存储。这对 `ORDER BY created_at DESC LIMIT 10`（比如"最新 10 条"）非常有效。SQLite 3.14+ 会智能识别，即使你写 `ORDER BY created_at DESC` 且索引是 ASC，也能反向扫描，但对复合索引的排序方向匹配更严格。

## 7.16 部分索引（Partial Index）

只对满足条件的行建索引：

```sql
-- 只给"未完成"的 todo 建索引
CREATE INDEX idx_active_todo ON todo(user_id)
WHERE completed = 0;
```

**好处**：索引更小、更新更快。
**代价**：只有 WHERE 条件匹配的查询才能用上这个索引。

**经典场景**：软删除表。90% 的查询都是 `WHERE deleted_at IS NULL`，那就建个只对未删除行的部分索引：

```sql
CREATE INDEX idx_active_user_email ON user(email)
WHERE deleted_at IS NULL;
```

## 7.17 表达式索引

给列的**表达式**建索引，而不是列本身：

```sql
-- 忽略大小写查邮箱
CREATE INDEX idx_user_email_lower ON user(LOWER(email));

-- 查询时表达式必须一模一样才用到索引
SELECT * FROM user WHERE LOWER(email) = 'foo@bar.com';   -- 用到索引
SELECT * FROM user WHERE email = 'foo@bar.com';           -- 用不到
```

**用途**：

- 大小写不敏感搜索
- 从 JSON 字段提取值：`CREATE INDEX ... ON tbl(json_extract(data, '$.name'))`
- 计算列：`CREATE INDEX ... ON order(price * quantity)`

## 7.18 索引什么时候会失效？

即使建了索引，下面这些写法会让索引形同虚设：

**1. 在索引列上用函数**

```sql
-- 索引在 email 列
SELECT * FROM user WHERE UPPER(email) = 'FOO@BAR.COM';   -- 失效！
```

除非你建了表达式索引。

**2. 隐式类型转换**

```sql
CREATE TABLE t(a TEXT);
CREATE INDEX idx ON t(a);
SELECT * FROM t WHERE a = 123;    -- 123 会被转成 '123'，但类型不匹配可能导致索引失效
```

**3. LIKE 通配符前缀**

```sql
SELECT * FROM user WHERE name LIKE 'zhang%';    -- 索引有效（前缀匹配）
SELECT * FROM user WHERE name LIKE '%zhang';    -- 索引无效
SELECT * FROM user WHERE name LIKE '%zhang%';   -- 索引无效
```

要模糊搜中间/后缀？考虑 FTS5 全文索引（Part 3 会讲）。

**4. OR 连接不同列**

```sql
CREATE INDEX idx_a ON t(a);
CREATE INDEX idx_b ON t(b);
SELECT * FROM t WHERE a = 1 OR b = 2;    -- 3.8+ 可以用 OR 优化（Index OR），但不保证
```

改写为 `UNION ALL` 通常更稳：

```sql
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2 AND a != 1;
```

**5. NOT / != 通常不走索引**

```sql
SELECT * FROM user WHERE age != 18;    -- 失效
```

改成 `age < 18 OR age > 18` 也没用（区分度太低）。这种查询通常本身就该全表扫。

**6. 多列索引跳过最左列**

前面讲过，不再赘述。

## 7.19 EXPLAIN QUERY PLAN——查询计划的显微镜

想知道一个查询到底用没用上索引？加上 `EXPLAIN QUERY PLAN`：

```sql
EXPLAIN QUERY PLAN
SELECT * FROM post WHERE user_id = 5 ORDER BY created_at DESC LIMIT 10;
```

输出可能长这样：

```
QUERY PLAN
`--SEARCH post USING INDEX idx_post_user_time (user_id=?)
```

关键词解读：

- `SCAN table` → 全表扫描，通常不好。
- `SEARCH table USING INDEX idx_xxx` → 走了索引，好。
- `SEARCH table USING COVERING INDEX idx_xxx` → 覆盖索引，最好。
- `USE TEMP B-TREE FOR ORDER BY` → 需要额外排序，可优化。
- `USE TEMP B-TREE FOR GROUP BY` → 需要额外分组，可优化。

看到 `SCAN` 就要警惕，看到 `TEMP B-TREE` 就要想想是不是能加索引消除它。

## 7.20 索引的代价——写入放大与磁盘占用

天下没有免费的午餐。每加一个索引，你就要为以下代价买单：

**1. 写入放大**：每次 INSERT/UPDATE/DELETE，索引都要跟着更新。一张有 5 个索引的表，一次插入实际上是 6 次 B-Tree 写入（表本身 + 5 个索引）。

**2. 磁盘占用**：索引也要存储空间，尤其是大表 + 长文本索引 + 覆盖索引，可能索引比原表还大。

**3. 内存占用**：SQLite 的 page cache 要缓存索引页。

**4. VACUUM/ANALYZE 时间**：维护成本增加。

**经验法则**：

- 索引数量控制在 5 个以内（超过就要 review）。
- 优先建覆盖索引，而不是给每列都建单列索引。
- 定期用 `ANALYZE` 更新统计信息，让查询优化器做出好决策。

## 7.21 drift 实战：类型安全定义约束和索引

用 drift 定义带约束的表：

```dart
import 'package:drift/drift.dart';

class Users extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get name => text().withLength(min: 1, max: 100)();
  TextColumn get email => text().customConstraint('NOT NULL UNIQUE')();
  IntColumn get age => integer().check(age.isBiggerOrEqualValue(0))();
  TextColumn get status => textEnum<UserStatus>()();          // 枚举
  DateTimeColumn get createdAt => dateTime().withDefault(currentDateAndTime)();
  BoolColumn get isAdmin => boolean().withDefault(const Constant(false))();
}

class Posts extends Table {
  IntColumn get id => integer().autoIncrement()();
  IntColumn get userId => integer().references(Users, #id, onDelete: KeyAction.cascade)();
  TextColumn get title => text()();
  TextColumn get content => text().nullable()();
  DateTimeColumn get createdAt => dateTime().withDefault(currentDateAndTime)();
}

enum UserStatus { active, inactive, banned }

@DriftDatabase(tables: [Users, Posts])
class AppDatabase extends _$AppDatabase {
  // ...
}
```

定义索引：

```dart
@DriftDatabase(
  tables: [Users, Posts],
  include: {'schema.drift'},        // 或者用 .drift 文件写索引
)
class AppDatabase extends _$AppDatabase { }
```

或者在 `.drift` 文件里：

```sql
-- lib/database/schema.drift
CREATE INDEX idx_post_user_time ON posts(user_id, created_at DESC);
CREATE UNIQUE INDEX idx_user_email ON users(email);
CREATE INDEX idx_active_user ON users(email) WHERE status = 'active';
```

drift 的爽点：**编译时就能校验列名、约束语法**，改字段名 IDE 直接标红。

## 7.22 常见坑点合集

**坑 1：忘了开外键**

`PRAGMA foreign_keys = ON` 必须每个连接执行。sqflite 的连接池、drift 的迁移都要注意在 `onConfigure` / `beforeOpen` 里执行。

**坑 2：CHECK 约束里用了非确定性函数**

```sql
CHECK (created_at <= datetime('now'))    -- 不推荐！
```

`datetime('now')` 每次调用值都不同，逻辑上没问题，但触发 CHECK 的时机可能带来意外。用 `AFTER INSERT` 触发器更好。

**坑 3：索引在 NULL 值上的表现**

SQLite 的索引默认把 NULL 排在最前（ASC）或最后（DESC）。`WHERE col IS NULL` 能用索引，`WHERE col = NULL` 永远不匹配。

**坑 4：为主键单独建索引**

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, ...);
CREATE INDEX idx_id ON t(id);        -- 完全多余！
```

主键本身就是索引（或 rowid 别名）。

**坑 5：给低区分度列建索引**

```sql
CREATE INDEX idx_gender ON user(gender);    -- 通常没用
```

除非配合其他列做复合索引，或者做部分索引（比如只索引某种性别）。

**坑 6：drift 的 `references` 默认不开 CASCADE**

```dart
IntColumn get userId => integer().references(Users, #id)();                          // 默认 NO ACTION
IntColumn get userId => integer().references(Users, #id, onDelete: KeyAction.cascade)();   // 明确
```

想要级联删除必须显式声明。

## 7.23 本章小结

- 约束三大类：域（NOT NULL/CHECK/DEFAULT）、实体（PK/UNIQUE）、参照（FK）。
- SQLite 默认**不启用外键**，必须 `PRAGMA foreign_keys = ON`（每个连接）。
- 索引 = B-Tree = 从 O(n) 到 O(log n)。
- 复合索引遵循最左前缀，列顺序按等值→区分度→排序来排。
- 覆盖索引省一次回表，性能飞起。
- 部分索引 + 表达式索引是高级玩家的必备武器。
- 索引失效场景要背下：函数、隐式转换、`LIKE '%x'`、OR、跳过最左列。
- 用 `EXPLAIN QUERY PLAN` 检查执行计划，看到 `SCAN` 就警惕。
- drift 用类型安全 API 定义约束和索引，编译期就发现错误。
- **金句**：约束是护城河，索引是高速公路，两者一起用才能让数据库既安全又快。
