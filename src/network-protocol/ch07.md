# 第7章：UDP——最小化的传输层

Part II：可靠传输——TCP 与 UDP

网络层把数据包从一台机器送到另一台机器，这件事本身已经足够复杂了。但当你打开浏览器、发送一条微信、看一段直播视频的时候，你其实并不关心"数据包是怎么路由过来的"——你关心的是：消息有没有丢？顺序对不对？会不会把我的"你好"和"再见"混在一起？

这些问题，IP 层一概不管。IP 只负责"尽力送达"，至于送达的质量——丢不丢包、乱不乱序、重不重复——那是传输层（Transport Layer）的事。

传输层有两位主角：**TCP**（Transmission Control Protocol）和 **UDP**（User Datagram Protocol）。一个严谨到近乎强迫症，一个洒脱到近乎放任。它们看似对立，实则各有所长，共同撑起了互联网上层应用的数据传输需求。

接下来的六章，我们将深入这两个协议的每一个细节。不是背定义、记字段——而是追问每一个设计决策背后的"为什么"。

## UDP 的设计哲学：少即是多

在设计一个传输层协议时，最容易想到的思路是："我要保证数据可靠到达，所以要加序号、加确认、加重传、加流量控制……" TCP 走的就是这条路，它把能想到的保障全给你堆上了。

但 UDP 的设计者 David Reed 在 1980 年提出了一个反直觉的问题：**如果有些应用根本不需要这些保障呢？**

想象一下你在看一场直播。如果中间丢了一帧画面，你希望播放器停下来等那一帧重传吗？当然不。你宁愿跳过那一帧继续播放，因为直播的实时性远比完整性重要。再比如 DNS 查询——你只是想问"www.google.com 的 IP 地址是什么"，这个问题本身只有几十字节，如果为了这几十字节搞一套握手、确认、断开的流程，未免小题大做。

UDP 的哲学就是：**把传输层能砍掉的东西全砍掉，只留下最基本的多路复用和数据完整性校验。** 你得到的是一个极其轻量的协议——没有连接建立，没有重传，没有拥塞控制，没有排序。应用程序拿到 UDP 的接口后，想怎么折腾就怎么折腾。

这种设计思路在软件工程中有一个名字：**KISS 原则（Keep It Simple, Stupid）**。UDP 把它贯彻到了极致。

## UDP 报头结构：只有 4 个字段，8 字节

TCP 的报头最少 20 字节，而 UDP 的报头固定 **8 字节**，堪称传输层最精简的协议。我们来看看它的结构：

```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|     源端口号     |    目的端口号    |
+--------+--------+--------+--------+
|       长度       |      校验和     |
+--------+--------+--------+--------+
|              数据载荷              |
+-----------------------------------+
```

四个字段，逐一解释：

- **源端口（Source Port，16 位）**：发送方的端口号。在某些场景下可以填 0，表示不期望对方回复。
- **目的端口（Destination Port，16 位）**：接收方的端口号，用于多路分解——让操作系统知道这个报文应该交给哪个应用程序。
- **长度（Length，16 位）**：整个 UDP 数据报（报头 + 数据）的总长度，单位为字节。最小值为 8（即没有数据载荷时）。理论最大值为 65535 字节，但实际受限于 IP 层的 MTU。
- **校验和（Checksum，16 位）**：用于检测数据在传输过程中是否损坏。IPv4 中校验和是可选的（可以填 0 表示不计算），但 **IPv6 中是强制的**。校验和的计算范围包括 UDP 报头、数据内容以及一个来自 IP 报头的"伪首部"（Pseudo Header），后者包含源 IP、目的 IP、协议号等信息，这样可以同时验证数据确实是从预期的源发往预期的目的地。

8 字节报头意味着什么？意味着 UDP 的开销极低。如果你发送 100 字节的应用数据，UDP 只额外增加 8 字节，开销 8%；而 TCP 至少增加 20 字节，开销 20%。对于高频小包的应用（比如在线游戏的每秒几十个位置更新），这个差距是有意义的。

## UDP 为什么存在：哪些场景不需要可靠性

很多人初学网络时会产生一个误解："TCP 比 UDP 高级，所以应该尽量用 TCP。"这是不对的。TCP 和 UDP 不是高低之分，而是适用场景不同。

以下场景特别适合 UDP：

1. **查询-响应型协议（DNS、DHCP）**：一次 DNS 查询通常只有一两包，请求和响应之间有严格的因果关系。如果用 TCP，光握手就要一个 RTT（Round-Trip Time），而 UDP 直接发包、等回复，一个 RTT 搞定。如果丢了，重发一次就是了。

2. **实时音视频（VoIP、视频会议、直播）**：这些应用对延迟极其敏感。一帧音频如果迟到了 200ms，它已经没有播放的意义了——用户已经听到了后面的内容。重传一个过时的数据包，不如丢弃它继续处理后续数据。

3. **在线游戏**：玩家的位置每秒更新几十次。丢一次位置更新无所谓，因为下一个更新马上就到。但如果你停下来等重传，玩家会明显感到"卡顿"。

4. **网络文件系统（NFS v3、TFTP）**：这些协议自己在应用层实现了可靠性机制（超时重传等），不需要传输层再来一套。

5. **路由协议（RIP、OSPF）**：路由器之间交换路由信息，通常是周期性的广播或组播。TCP 是点对点的，无法支持一对多的通信模式。

## 基于 UDP 的应用：DNS、DHCP、视频流、游戏

让我们具体看几个经典的 UDP 应用：

**DNS（Domain Name System）**：DNS 查询默认使用 UDP，端口 53。一个典型的 DNS 查询报文只有 30-60 字节。客户端发出查询，服务器返回结果，整个过程一个 RTT。但如果响应数据超过 512 字节（在使用 EDNS0 扩展之前），DNS 会回退到 TCP——因为 UDP 的 16 位长度字段虽然允许最大 65535 字节，但早期 DNS 规范将 UDP 报文限制在 512 字节以内以确保不被 IP 分片。

**DHCP（Dynamic Host Configuration Protocol）**：当你的电脑连上 WiFi 时，它需要自动获取 IP 地址。DHCP 使用 UDP 端口 67（服务器）和 68（客户端）。整个 DORA 过程（Discover-Offer-Request-Acknowledge）涉及 4 个 UDP 报文。之所以用 UDP 而不是 TCP，原因很直接：**客户端此时还没有 IP 地址**，而 TCP 需要完整的 IP 地址来建立连接。UDP 允许使用 0.0.0.0 作为源地址、255.255.255.255 作为目的地址进行广播。

**视频流（如 RTP over UDP）**：实时传输协议 RTP（Real-time Transport Protocol）运行在 UDP 之上，为每一帧音视频数据打上时间戳和序列号。时间戳告诉播放器何时显示这一帧，序列号帮助检测丢包。注意：即使检测到丢包，RTP 也不会重传——它只是让播放器用"插值"或"重复上一帧"的策略来掩盖丢失。

**在线游戏**：现代多人在线游戏（如 FPS 游戏）通常使用自定义的 UDP 协议。以 Valve 的 Source 引擎为例，它在 UDP 上构建了一套轻量级的可靠性层：对关键消息（如玩家射击）提供可靠传输，对非关键消息（如玩家位置更新）则允许丢失。这种"选择性可靠"的设计是 TCP 无法提供的。

## UDP 的"不可靠"到底意味着什么

"不可靠"这个词容易让人误解为"UDP 经常丢数据"。实际上，UDP 的"不可靠"是一个精确的技术术语，它有三层含义：

1. **不保证送达**：UDP 没有确认机制。发送方把数据报交给 IP 层后，就再也不管了。如果中间路由器因为拥塞而丢弃了这个包，发送方不会知道，也不会重传。

2. **不保证顺序**：UDP 没有序号字段。如果你连续发送报文 A、B、C，接收方可能收到 B、A、C 或 C、A、B——这取决于网络中每个包走的路径和经历的延迟。

3. **不拥塞控制**：TCP 会在网络拥塞时主动降低发送速率，而 UDP 不会。你让 UDP 以 1Gbps 的速率发包，它就会以 1Gbps 的速率发包，不管网络是否已经不堪重负。这也是为什么大规模 UDP 流量（如 DDoS 攻击）对网络的破坏性特别大。

但要注意：UDP **并非完全不检错**。校验和字段可以检测数据在传输过程中是否被损坏（bit flip），只是检测到错误后，UDP 的默认行为是直接丢弃该报文（某些实现会通知上层应用），不会请求重传。

还有一点容易被忽略：UDP **不提供流控制**。TCP 是一个字节流协议，发送方需要根据接收方的处理能力来调节发送速率。而 UDP 是报文协议——应用程序每次调用 `sendto()` 发送一个完整的报文，接收方要么完整收到，要么完全没收到，不存在"收到半截"的情况（不考虑 IP 分片）。

## 编程实践：用 Python 写一个 UDP Echo 客户端/服务器

让我们动手写代码。Echo 服务器是最简单的网络服务：收到什么就原样返回。

**UDP Echo 服务器：**

```python
import socket

SERVER_HOST = '127.0.0.1'
SERVER_PORT = 9999
BUFFER_SIZE = 1024

def main():
    # SOCK_DGRAM 表示使用 UDP
    server_socket = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    server_socket.bind((SERVER_HOST, SERVER_PORT))
    print(f"UDP Echo 服务器已启动，监听 {SERVER_HOST}:{SERVER_PORT}")

    while True:
        # recvfrom 返回 (数据, 客户端地址)
        data, client_addr = server_socket.recvfrom(BUFFER_SIZE)
        print(f"收到来自 {client_addr} 的数据: {data.decode('utf-8')}")

        # 将数据原样返回
        server_socket.sendto(data, client_addr)

if __name__ == '__main__':
    main()
```

**UDP Echo 客户端：**

```python
import socket
import time

SERVER_HOST = '127.0.0.1'
SERVER_PORT = 9999
BUFFER_SIZE = 1024
TIMEOUT = 2.0  # 超时 2 秒

def main():
    client_socket = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    client_socket.settimeout(TIMEOUT)

    messages = ["Hello UDP!", "第二条消息", "Third message"]

    for msg in messages:
        data = msg.encode('utf-8')
        client_socket.sendto(data, (SERVER_HOST, SERVER_PORT))
        print(f"已发送: {msg}")

        try:
            response, server_addr = client_socket.recvfrom(BUFFER_SIZE)
            print(f"收到回复: {response.decode('utf-8')}")
        except socket.timeout:
            print(f"超时：未收到服务器回复（UDP 不保证送达！）")
        print()
        time.sleep(0.5)

    client_socket.close()

if __name__ == '__main__':
    main()
```

注意几个关键点：

- UDP 服务器 **不需要 `listen()` 和 `accept()`**。没有连接的概念，服务器就是一个"收件箱"，谁都可以往里投信。
- `recvfrom()` 返回发送方的地址，这样服务器才知道该回复给谁。在 TCP 中，这个信息在 `accept()` 返回的 socket 对象里就已经隐含了。
- 客户端设置了 **超时**。这在 UDP 编程中非常重要——因为你不知道对方是否会回复，如果无限等待，程序就会永远挂起。

## 抓包实践：捕获 DNS 查询的 UDP 报文

让我们用 Wireshark 或 `tcpdump` 来观察真实的 DNS UDP 报文。

**捕获命令：**

```bash
# Linux/macOS: 使用 tcpdump 捕获 DNS 流量
sudo tcpdump -i any port 53 -vv -X

# 或者使用 tshark（Wireshark 的命令行版本）
tshark -i any -f "port 53" -V
```

然后在另一个终端执行一次 DNS 查询：

```bash
nslookup www.example.com
```

你会看到类似这样的输出（关键信息已标注）：

```
14:23:45.123456 IP 192.168.1.100.54321 > 8.8.8.8.53:
  [UDP]
  源端口: 54321 (随机分配的高端口)
  目的端口: 53 (DNS)
  长度: 40 (8字节UDP头 + 32字节DNS数据)
  校验和: 0x3a7f (正确)

  DNS Flags: 0x0100 (Standard query)
    QR: 0 (Query)
    Opcode: 0 (Standard query)
    RD: 1 (Recursion desired)
  Questions: 1
  Transaction ID: 0xab12

  Queries:
    www.example.com: type A, class IN
```

让我们逐字段分析：

**UDP 报头字段：**

- 源端口 `54321`：操作系统从动态端口范围中随机选取，用于接收 DNS 响应。
- 目的端口 `53`：DNS 服务的知名端口。
- 长度 `40`：8 字节 UDP 报头 + 32 字节 DNS 查询数据。
- 校验和 `0x3a7f`：覆盖 UDP 报头、DNS 数据和伪首部。

**关键观察：**

- 整个 DNS 查询只有一个 UDP 报文，没有握手过程。发出查询、等待响应，完毕。
- 如果我们在 Wireshark 中查看 DNS 响应，会发现它的目的端口变成了 `54321`——正好对应客户端的源端口，这样操作系统就知道把这个响应交给发起查询的那个进程。
- 从查询到响应的时间差通常只有几十毫秒（取决于你到 DNS 服务器的距离），这就是 UDP "一问一答"模式的高效之处。

如果你做一个有趣的实验——用防火墙阻断 DNS 服务器的响应（例如 `iptables -A INPUT -p udp --sport 53 -j DROP`），你会发现客户端在等待约 5 秒后超时，然后可能自动重试。这个重试机制不是 UDP 提供的——它是 DNS 应用层自己实现的超时重传。这正是"在 UDP 上构建可靠性"的典型模式。
