# 第4章：你的第一个 Workflow

## 引言：Talk is cheap, show me the workflow

前面三章我们讲了"为什么需要 CI/CD"、"YAML 怎么写"、"GitHub Actions 的核心概念"。

这一章，我们要动真格的了——从零开始，为一个 Node.js 项目创建一个完整的 CI Workflow，并且让它在 GitHub 上真正跑起来。

我们会创建一个名叫 `node-ci.yml` 的工作流文件，实现以下目标：

- 当有人 push 代码到 `main` 分支，或者提交 Pull Request 到 `main` 分支时，自动触发
- 在 Ubuntu 虚拟机上执行
- 检出代码 → 设置 Node.js 环境 → 安装依赖 → 跑测试
- 支持多个 Node.js 版本的矩阵测试

## 4.1 完整代码：先睹为快

先把完整代码贴出来，让你有个整体印象，然后我们逐行拆解：

```yaml
# .github/workflows/node-ci.yml

name: Node.js CI                           # [1] 工作流名称

on:                                        # [2] 触发条件
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]

jobs:                                      # [3] 作业定义
  build:                                   # [4] 作业名称（自定义）
    runs-on: ubuntu-latest                 # [5] 使用 Ubuntu 最新版 Runner

    strategy:                              # [6] 矩阵策略
      matrix:
        node-version: [18.x, 20.x, 22.x]  # [7] 在三个 Node.js 版本上测试

    steps:
      - name: Checkout repository          # [8] 步骤名称
        uses: actions/checkout@v4          # [9] 使用 checkout Action 检出代码

      - name: Use Node.js ${{ matrix.node-version }}   # [10] 步骤名称（含变量）
        uses: actions/setup-node@v4                    # [11] 使用 setup-node Action
        with:
          node-version: ${{ matrix.node-version }}     # [12] 传入矩阵变量
          cache: 'npm'                                 # [13] 自动缓存 npm 依赖

      - name: Install dependencies         # [14] 步骤名称
        run: npm ci                        # [15] 安装依赖（ci 比 install 更适合 CI）

      - name: Run tests                    # [16] 步骤名称
        run: npm test                      # [17] 跑测试
```

看起来没多少行对吧？别急，我们一行一行来拆解。

## 4.2 逐行解析

**`[1] name: Node.js CI`**

工作流的名称，会显示在 GitHub 仓库的 "Actions" 页面上。取一个有意义的名字，方便你在多个 Workflow 中快速识别。就像给文件取名字一样——`untitled.yml` 不是不可以，但你会在三天后忘了它是干嘛的。

**`[2] on:` —— 触发条件**

```yaml
on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]
```

这段的意思是：

- 当有人 **push 代码到 `main` 分支**时触发
- 当有人 **提交 Pull Request 到 `main` 分支**时触发

注意 `branches` 的值是一个列表（用 `[]` 内联写法），你可以指定多个分支：

```yaml
on:
  push:
    branches: ["main", "develop", "release/*"]   # * 是通配符
```

**`[3] jobs:` —— 作业定义**

所有 Job 都定义在 `jobs` 下面。我们这个 Workflow 只有一个 Job：`build`。

**`[4] build:` —— 作业名称**

这个名字是你自己取的，可以是任何东西：`test`、`lint-and-test`、`do-the-thing`。它会显示在 GitHub UI 的 Job 列表中。

**`[5] runs-on: ubuntu-latest`**

指定 Runner 环境。`ubuntu-latest` 是最常用的选择——便宜（免费）、快、预装工具多。

**`[6] strategy.matrix` —— 矩阵策略**

这是一个非常强大的功能。矩阵策略让你可以用同一组步骤，在多个不同环境上运行：

```yaml
strategy:
  matrix:
    node-version: [18.x, 20.x, 22.x]
```

这行配置的效果是：**这个 Job 会被执行 3 次**，分别是 Node.js 18.x、20.x、22.x 环境。就像你做了一个蛋糕配方，分别在三个不同温度的烤箱里试烤，看看哪个温度效果最好。

你也可以做二维矩阵：

```yaml
strategy:
  matrix:
    node-version: [18.x, 20.x]
    os: [ubuntu-latest, windows-latest]
```

这样就是 2 × 2 = 4 个 Job 并行执行。

**`[7] node-version: [18.x, 20.x, 22.x]`**

::: v-pre
定义了 `node-version` 这个矩阵维度。后面的步骤可以通过 `${{ matrix.node-version }}` 引用这个值。
:::

**`[8]-[9] Checkout 步骤**

```yaml
- name: Checkout repository
  uses: actions/checkout@v4
```

这几乎是每个 Workflow 的第一步。`actions/checkout` 会把你的仓库代码"检出"（clone）到 Runner 的工作目录中。

为什么要单独一步？因为 Runner 是一台全新的虚拟机，上面什么都没有——没有你的代码、没有你的配置文件。Checkout 就是把你的代码"快递"到 Runner 上。

**`[10]-[13] Setup Node.js 步骤**

```yaml
- name: Use Node.js ${{ matrix.node-version }}
  uses: actions/setup-node@v4
  with:
    node-version: ${{ matrix.node-version }}
    cache: 'npm'
```

::: v-pre
`${{ matrix.node-version }}` 是一个**表达式**，会被矩阵中的实际值替换。比如在 Node.js 20.x 的那次运行中，步骤名称会变成 `Use Node.js 20.x`
:::

`with` 是传递给 Action 的参数：

- `node-version`: 指定要安装的 Node.js 版本
- `cache: 'npm'`: 自动缓存 npm 的依赖包。第二次运行时，如果 `package-lock.json` 没变，就直接用缓存，不用重新下载——能节省 30 秒到几分钟不等。

**`[14]-[15] 安装依赖**

```yaml
- name: Install dependencies
  run: npm ci
```

注意这里用的是 `npm ci` 而不是 `npm install`。区别在于：

| 命令 | 行为 |
|------|------|
| `npm install` | 根据 `package.json` 安装，可能会更新 `package-lock.json` |
| `npm ci` | 严格按照 `package-lock.json` 安装，不会修改任何文件 |

在 CI 环境中，**你应该始终使用 `npm ci`**。原因：

1. 更快（跳过一些 `npm install` 的检查逻辑）
2. 更可靠（保证每次安装的依赖版本完全一致）
3. 如果 `package-lock.json` 和 `package.json` 不匹配，会直接报错而不是默默修复

**`[16]-[17] 运行测试**

```yaml
- name: Run tests
  run: npm test
```

最后一步，运行测试。`npm test` 会执行 `package.json` 中 `scripts.test` 定义的命令。如果测试全部通过（退出码为 0），这个 Step 就标记为成功；如果有任何测试失败（退出码非 0），这个 Step 就标记为失败，整个 Job 也就失败了。

## 4.3 如何把这个 Workflow 添加到你的项目

**Step 1：创建目录结构**

在你的项目根目录下，创建 `.github/workflows/` 目录：

```bash
mkdir -p .github/workflows
```

**Step 2：创建 Workflow 文件**

```bash
touch .github/workflows/node-ci.yml
```

然后把上面的完整代码粘贴进去。

**Step 3：确保你的项目有 `package.json` 和测试脚本**

一个最简单的 `package.json`：

```json
{
  "name": "my-node-project",
  "version": "1.0.0",
  "scripts": {
    "test": "jest"
  },
  "devDependencies": {
    "jest": "^29.0.0"
  }
}
```

当然，你也可以用 Mocha、Vitest 或者 Node.js 内置的 `node:test` 模块，只要 `npm test` 能正确运行测试就行。

**Step 4：提交并推送到 GitHub**

```bash
git add .github/workflows/node-ci.yml
git commit -m "ci: add Node.js CI workflow"
git push origin main
```

推送之后，GitHub 会自动检测到新的 Workflow 文件，并开始运行。

## 4.4 如何查看运行结果

推送代码后，有几种方式查看 Actions 的运行状态：

**方式 1：通过仓库的 Actions 页面**

1. 打开你的 GitHub 仓库页面
2. 点击顶部的 **"Actions"** 标签
3. 你会看到所有 Workflow 的运行历史
4. 点击某次运行，可以看到每个 Job 和 Step 的详细日志

**方式 2：通过 Commit 状态**

在仓库的 Commits 页面，每个 Commit 旁边会有一个状态图标：

- ✅ 绿色勾：所有 Workflow 通过
- ❌ 红色叉：至少一个 Workflow 失败
- 🟡 黄色圈：正在运行中

**方式 3：通过 PR 检查**

如果你是在 Pull Request 中提交的 Workflow，PR 页面底部会显示所有检查的状态：

- 所有检查通过 → 可以合并
- 有检查失败 → PR 作者需要修复

## 4.5 常见第一次运行的报错及解决

**报错 1：`No tests found`**

```
Error: No tests found, exiting with code 1
```

**原因**：你的项目里没有测试文件，或者测试框架找不到测试文件。

**解决**：确保你的测试文件放在正确的位置，并且测试框架能识别它们。比如用 Jest 时，测试文件应该命名为 `*.test.js` 或 `*.spec.js`，或者放在 `__tests__/` 目录下。

**报错 2：`npm ci` 失败**

```
npm ERR! `npm ci` can only install packages when your package.json and package-lock.json are in sync.
```

**原因**：`package.json` 和 `package-lock.json` 不一致。通常是因为你手动修改了 `package.json` 中的依赖版本，但没有重新运行 `npm install` 来更新 lock 文件。

**解决**：在本地运行 `npm install`，然后把更新后的 `package-lock.json` 一起提交。

```bash
npm install
git add package-lock.json
git commit -m "chore: update package-lock.json"
git push
```

**报错 3：权限不足**

```
Error: Resource not accessible by integration
```

**原因**：Workflow 默认对仓库的写权限有限（这是安全设计）。

**解决**：如果你的 Workflow 需要写入权限（比如给 PR 打标签），需要在 Workflow 中添加：

```yaml
permissions:
  contents: read        # 读取代码的权限
  pull-requests: write  # 写入 PR 的权限（如果需要）
```

**报错 4：YAML 语法错误**

```
Error: .github#L1
YAML syntax error
```

**原因**：YAML 格式有问题——缩进不对、冒号后没空格、引号没闭合等。

**解决**：用 YAML 校验工具检查（推荐 VS Code 的 YAML 扩展），修复后重新提交。

**报错 5：Action 版本不存在**

```
Error: Unable to resolve action `actions/checkout@v99`, unable to find version
```

**原因**：指定的 Action 版本不存在。

**解决**：去对应 Action 的 GitHub 页面，查看最新的版本号。一般来说 `@v4` 是大多数主流 Action 的当前主版本。

## 4.6 加分项：添加缓存和构建步骤

如果你想在测试之外再加上"构建"步骤，并且启用缓存来加速，可以这样扩展：

```yaml
# .github/workflows/node-ci.yml（增强版）

name: Node.js CI

on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18.x, 20.x, 22.x]

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Use Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

  build:
    needs: test                         # 测试通过后才构建
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Use Node.js 20.x
        uses: actions/setup-node@v4
        with:
          node-version: '20.x'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Build project
        run: npm run build              # 确保你的 package.json 里有 build 脚本

      - name: Upload build artifacts
        uses: actions/upload-artifact@v4
        with:
          name: build-output            # 产物名称
          path: dist/                   # 构建输出目录
          retention-days: 7             # 保留 7 天
```

这个增强版做了两件事：

1. 把 `test` 和 `build` 分成两个 Job，构建只在测试全部通过后执行
2. 把构建产物上传为 Artifact，你可以在 GitHub 页面上直接下载

## 小结

- 创建 Workflow 只需三步：建目录、写 `.yml` 文件、推送代码
- `actions/checkout` 检出代码，`actions/setup-node` 设置 Node.js 环境——这两步几乎是 Node.js 项目的标配
- CI 环境中用 `npm ci` 而不是 `npm install`，更快更可靠
- 矩阵策略让你一次测试多个 Node.js 版本，覆盖面更广
- 查看运行结果可以在仓库的 Actions 页面、Commit 状态或 PR 检查中
- 第一次运行出错不要慌，看日志、找原因、修好再推——Debug 是程序员的基本功

## 练习题

1. **动手实践**：创建一个新的 GitHub 仓库，初始化一个简单的 Node.js 项目（带 Jest 测试），然后按照本章的步骤添加 CI Workflow，确保它在 GitHub 上跑通并且全绿。
2. **矩阵扩展**：在矩阵中加入 Node.js 16.x 版本，观察它是否能跑通你的测试。如果不能，想想为什么，以及如何配置 `continue-on-error` 让 16.x 的失败不影响整体状态。
3. **自定义 Workflow**：在你的 Workflow 中添加一个 `lint` Job（运行 `npx eslint .`），让它和 `test` Job 并行执行，然后在 `build` Job 中同时依赖 `test` 和 `lint`。
4. **探索日志**：在 GitHub Actions 页面上点开一次运行的详细日志，找到以下信息：Runner 的操作系统版本、Node.js 的确切版本、`npm ci` 花了多长时间。
