# 第15章：HTTPS 与 TLS——给 HTTP 穿上铠甲

## 为什么需要 HTTPS

HTTP 是明文传输的。这意味着你和服务器之间所有的数据——密码、银行卡号、私人聊天——都可能在传输途中被看到、被修改、甚至被伪造。这就像在明信片上写情书，邮递员和分拣员都能看到你的内容。

HTTP 面临的三大安全威胁：

1. **窃听（Eavesdropping）**：中间人可以读取传输内容。你在咖啡店连的免费 Wi-Fi，旁边的人可能正在用 Wireshark 看你的 HTTP 请求。
2. **篡改（Tampering）**：中间人不仅看，还修改内容。某些运营商就在 HTTP 响应中注入过广告（俗称"运营商劫持"）。
3. **冒充（Impersonation）**：你以为你在跟 `bank.com` 通信，实际上你在跟一个伪装成 `bank.com` 的钓鱼服务器通信。

**HTTPS（HTTP over TLS）**用加密解决窃听，用消息认证码（MAC）解决篡改，用数字证书解决冒充。它是 HTTP 的装甲。

## TLS 1.3 握手详解

TLS（Transport Layer Security）是 HTTPS 的核心协议。它在 TCP 和 HTTP 之间加了一层加密层。让我们逐步骤看 TLS 1.3 的握手过程：

**第一步：ClientHello**

客户端发送支持的 TLS 版本、随机数（Client Random）、支持的加密套件列表、以及预共享密钥扩展（如果之前连接过的话）。

```
ClientHello:
  Version: TLS 1.2 (0x0303)  ← 为了兼容老设备，字段仍写 1.2
  Random: 7a 3f 2b 8c ... (32 bytes)
  Cipher Suites:
    TLS_AES_256_GCM_SHA384 (0x1302)
    TLS_CHACHA20_POLY1305_SHA256 (0x1303)
    TLS_AES_128_GCM_SHA256 (0x1301)
  Supported Groups: x25519, secp256r1, secp384r1
  Key Share: x25519 public key = 4a 2f 8b ... (32 bytes)
  Signature Algorithms: ecdsa_secp256r1_sha256, rsa_pss_rsae_sha256, ...
  SNI: www.example.com
```

注意 TLS 1.3 在 `supported_versions` 扩展中声明真实版本，而版本字段保留 `0x0303`（TLS 1.2）是为了兼容性。`Key Share` 直接在 ClientHello 中就发送了密钥交换信息——这是 TLS 1.3 握手加速的关键。

**第二步：ServerHello**

服务器选择加密套件，发送自己的随机数（Server Random）和密钥交换参数：

```
ServerHello:
  Version: TLS 1.2 (0x0303)
  Random: 9c 4e 1a 7b ... (32 bytes)
  Cipher Suite: TLS_AES_256_GCM_SHA384
  Supported Versions: TLS 1.3 (0x0304)
  Key Share: x25519 public key = 8b 3e 7c ... (32 bytes)
```

到这一步，双方都有了：

- Client Random
- Server Random
- 客户端的 ECDHE 私钥 + 服务器的 ECDHE 公钥 → 计算出共享密钥
- 服务器的 ECDHE 私钥 + 客户端的 ECDHE 公钥 → 计算出同一个共享密钥

通过 ECDHE（Elliptic Curve Diffie-Hellman Ephemeral），双方在不传输密钥的情况下，各自算出了相同的**预主密钥（Pre-Master Secret）**。这就是 Diffie-Hellman 密钥交换的魔法。

**第三步：服务器发送证书和 Finished**

服务器用自己的私钥对握手消息进行签名（Certificate Verify），并发送 Finished 消息，表示握手完成。客户端验证证书链和签名，确认服务器身份。

**第四步：客户端发送 Finished**

客户端也发送 Finished 消息。至此，握手完成，双方开始使用协商好的对称密钥加密后续通信。

TLS 1.3 的握手只需要 **1 个 RTT（Round Trip Time）**，而 TLS 1.2 需要 2 个 RTT。对于延迟 100ms 的网络，这就省了 100ms。

## 对称加密 vs 非对称加密

为什么 TLS 两种加密都用？因为它们各有优劣：

**对称加密**（如 AES-256-GCM）：加密和解密用同一个密钥。速度快（AES 有硬件加速），适合大量数据加密。但问题是：双方怎么安全地共享密钥？

**非对称加密**（如 RSA、ECDHE）：公钥加密、私钥解密（或签名验证）。解决了密钥分发问题，但速度比对称加密慢 100-1000 倍。

TLS 的策略是：用非对称加密（ECDHE）安全地协商出一个对称密钥，然后用对称加密（AES）加密后续的所有通信。**握手阶段用非对称，数据传输用对称**——各取所长。

## 数字证书与 CA 体系

非对称加密解决了一个问题但又引入了另一个：你怎么知道你拿到的公钥真的是 `bank.com` 的，而不是中间人伪造的？

答案是**数字证书**。证书就是一个包含服务器公钥和身份信息的文件，由一个可信的第三方——**CA（Certificate Authority，证书颁发机构）**——签名背书。

**X.509 证书结构**：

```
Certificate:
  Version: 3
  Serial Number: 04:3E:2F:8A:...
  Issuer: C=US, O=Let's Encrypt, CN=R3        ← 签发者（CA）
  Subject: CN=www.example.com                   ← 证书持有者
  Validity:
    Not Before: Jan 15 00:00:00 2024 GMT
    Not After:  Apr 14 23:59:59 2024 GMT
  Subject Public Key: RSA 2048 bits
  Extensions:
    Subject Alternative Name: www.example.com, example.com
    Authority Information Access: http://r3.i.lencr.org/
    CRL Distribution Points: ...
  Signature Algorithm: sha256WithRSAEncryption
  Signature: 3a:7b:9c:...                      ← CA 的签名
```

**证书链（Chain of Trust）**：浏览器不会直接信任 `bank.com` 的证书。它需要验证一个信任链：

```
Root CA (DigiCert Global Root G2)  ← 操作系统/浏览器预装
  └── Intermediate CA (DigiCert SHA2 Secure Server CA)  ← 由 Root CA 签发
        └── www.bank.com  ← 由 Intermediate CA 签发
```

每一级证书都包含上一级的签名。浏览器沿着链条逐级验证，直到找到一个它已经预装的**根证书（Root Certificate）**。如果链条完整且所有签名有效，浏览器就信任这个网站。

## 证书验证过程

浏览器在收到服务器证书时，会进行以下检查：

1. **签名验证**：证书链是否完整？每一级的签名是否有效？
2. **域名匹配**：证书的 Subject 或 SAN（Subject Alternative Name）是否包含当前访问的域名？`*.example.com` 的通配符证书匹配 `www.example.com`，但不匹配 `sub.www.example.com`。
3. **有效期**：证书是否在有效期内？（Let's Encrypt 的证书有效期只有 90 天，鼓励自动续期）
4. **吊销检查**：证书是否被 CA 提前吊销了？通过 OCSP（Online Certificate Status Protocol）或 CRL（Certificate Revocation List）检查。

如果任何一步失败，浏览器就会显示那个令人心悸的红色警告："您的连接不是私密连接"。

## HSTS：强制 HTTPS 的机制

即使网站支持 HTTPS，用户第一次访问时可能还是输入 `http://`。301 重定向可以解决，但第一次重定向之前是明文的——攻击者可以在这个窗口期劫持。

**HSTS（HTTP Strict Transport Security）**让服务器告诉浏览器："以后访问我这个域名，必须直接用 HTTPS"：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

浏览器收到这个头部后，在接下来的一年（31536000 秒）内，对 `example.com` 及其所有子域名的访问都会自动升级为 HTTPS，不再发送任何 HTTP 请求。`preload` 表示该域名已申请加入浏览器的 HSTS 预加载列表——即使用户第一次访问也能强制 HTTPS。

## TLS 1.2 vs TLS 1.3

TLS 1.3（2018 年发布）相比 TLS 1.2（2008 年发布）做了大幅改进：

| 特性 | TLS 1.2 | TLS 1.3 |
| ------ | --------- | --------- |
| 握手 RTT | 2 RTT | 1 RTT（支持 0-RTT 恢复） |
| 密钥交换 | RSA, DHE, ECDHE 等 | 仅 ECDHE（前向保密） |
| 对称加密 | AES-CBC, AES-GCM, RC4 等 | 仅 AEAD（AES-GCM, ChaCha20-Poly1305） |
| 加密套件数量 | 数十个 | 仅 5 个 |
| 服务器签名 | 签名整个握手消息 | 签名握手上下文（更安全） |
| 密钥派生 | PRF | HKDF |

TLS 1.3 的核心理念：**砍掉所有不安全的选项，只保留最好的**。RSA 密钥交换没有前向保密性（Forward Secrecy）——如果服务器的 RSA 私钥未来被泄露，之前所有通信都能被解密。ECDHE 密钥交换每次会话生成新的临时密钥，即使服务器私钥泄露，过去的通信仍然安全。

## 编程实践：用 Python ssl 模块为 TCP 服务器添加 TLS

```python
import socket
import ssl
import threading

def create_self_signed_cert():
    """
    提示：实际使用时请用 openssl 生成自签名证书：
    openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes
    """
    pass

def handle_client(conn: ssl.SSLSocket, addr):
    """处理一个 TLS 客户端连接"""
    try:
        data = conn.recv(4096).decode('utf-8', errors='replace')
        print(f"[{addr}] Received: {data[:100]}...")
        
        # 显示 TLS 连接信息
        print(f"  TLS Version: {conn.version()}")
        print(f"  Cipher: {conn.cipher()}")
        
        response = (
            "HTTP/1.1 200 OK\r\n"
            "Content-Type: text/plain\r\n"
            "Content-Length: 23\r\n"
            "Connection: close\r\n"
            "\r\n"
            "Hello from HTTPS Server!"
        )
        conn.sendall(response.encode('utf-8'))
    finally:
        conn.close()

def main():
    # 创建 TCP socket
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind(('127.0.0.1', 8443))
    server.listen(5)
    
    # 创建 SSL 上下文
    context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
    context.load_cert_chain(certfile='cert.pem', keyfile='key.pem')
    # 只允许 TLS 1.2 和 1.3
    context.minimum_version = ssl.TLSVersion.TLSv1_2
    
    # 用 SSL 上下文包装 TCP socket
    ssl_server = context.wrap_socket(server, server_side=True)
    
    print("HTTPS Server listening on https://127.0.0.1:8443")
    
    try:
        while True:
            conn, addr = ssl_server.accept()
            thread = threading.Thread(target=handle_client, args=(conn, addr))
            thread.start()
    except KeyboardInterrupt:
        print("\nServer shutting down...")
    finally:
        ssl_server.close()

if __name__ == '__main__':
    main()
```

运行前需要先用 `openssl` 生成自签名证书：

```bash
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes
```

用 `openssl` 命令行工具查看网站的证书：

```bash
# 查看网站的证书信息
openssl s_client -connect www.example.com:443 -showcerts

# 只看证书的 Subject 和 Issuer
openssl s_client -connect www.example.com:443 2>/dev/null | openssl x509 -noout -subject -issuer -dates

# 输出示例：
# subject=CN = www.example.org
# issuer=C = US, O = Let's Encrypt, CN = R3
# notBefore=Jan 15 00:00:00 2024 GMT
# notAfter=Apr 14 23:59:59 2024 GMT
```

## 抓包实践：捕获 TLS 握手全过程

在 Wireshark 中过滤 `tls`，访问一个 HTTPS 网站。你会看到：

```
Client Hello:
  TLS Version: TLS 1.2 (0x0303)
  Random: ...
  Session ID Length: 32
  Cipher Suites (5 suites):
    TLS_AES_256_GCM_SHA384 (0x1302)
    TLS_CHACHA20_POLY1305_SHA256 (0x1303)
    TLS_AES_128_GCM_SHA256 (0x1301)
    TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 (0xc030)
    TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 (0xc02f)
  Extensions:
    server_name: www.example.com
    supported_versions: TLS 1.3 (0x0304), TLS 1.2 (0x0303)
    supported_groups: x25519, secp256r1, secp384r1
    key_share: x25519 (32 bytes)

Server Hello:
  TLS Version: TLS 1.2 (0x0303)
  Cipher Suite: TLS_AES_256_GCM_SHA384 (0x1302)
  Extensions:
    supported_versions: TLS 1.3 (0x0304)
    key_share: x25519 (32 bytes)

Certificate (encrypted in TLS 1.3)
Certificate Verify (encrypted)
Finished (encrypted)
```

注意在 TLS 1.3 中，从 ServerHello 之后的消息都是加密的——你在 Wireshark 中看不到证书内容（除非配置了密钥日志文件）。而在 TLS 1.2 中，证书是明文传输的。在 Wireshark 中展开 `Handshake Protocol` 树，你可以看到每个字段的精确值。

配置 Wireshark 解密 TLS 流量（用于开发调试）：设置环境变量 `SSLKEYLOGFILE` 指向一个文件路径，浏览器会把每次连接的 Pre-Master Secret 写入该文件。在 Wireshark 的 `Preferences > Protocols > TLS` 中配置这个文件路径，Wireshark 就能解密 TLS 流量，让你看到明文 HTTP 内容。
