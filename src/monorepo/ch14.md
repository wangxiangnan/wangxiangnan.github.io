# Ch14：CI/CD 与部署

## 本章目标

- 把 PR 检查、npm 发布、镜像构建三条流水线串成完整交付链路
- 用 `turbo prune --docker` 和 `pnpm deploy` 构建最小、可复现的生产镜像
- 用 Docker Compose 编排开发依赖与生产服务
- 将 Web 部署到 Vercel，将 API 部署到 Railway / Fly.io
- 理解镜像层缓存、构建产物复用与部署安全

## 14.1 部署流水线全景

到本章为止，仓库里已经有三类自动化，它们解决不同的问题，不应该塞进同一个工作流：

| 流水线 | 触发时机 | 负责内容 | 所在章节 |
| ------ | -------- | -------- | -------- |
| PR 检查 | `pull_request` | lint、typecheck、test、build | Ch11 |
| npm 发布 | push 到 `main` | Changesets 版本 PR、发布共享包 | Ch13 |
| 镜像构建 | push 到 `main`（或 tag） | 构建 API / Web 镜像并推送到 GHCR | 本章 |

拆开的原因很实际：

- **权限不同**。PR 检查只需要 `contents: read`；镜像构建需要 `packages: write`；npm 发布需要 `contents: write` + `pull-requests: write`。合在一起会让每个 PR 都拿到写权限。
- **触发条件不同**。不是每次合并都要发 npm 包，但通常每次合并都应该产出可部署镜像。
- **失败影响不同**。npm 发布失败不应该阻止镜像构建，反之亦然。

### 14.1.1 PR 检查

直接复用 Ch11 的工作流即可，核心只有三步：

```yaml
# .github/workflows/ci.yml（Ch11 已创建，这里仅示意）
name: CI

on:
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0        # --affected 需要 Git 历史
      - uses: pnpm/setup@v3
        with:
          cache: true
          require-lockfile: true
      - run: pnpm turbo run lint typecheck test build --affected
```

`pnpm/setup@v3` 会安装 pnpm 和 Node（读取 `packageManager` 与 `.nvmrc`），并自动执行 `pnpm install`。`--affected` 会把范围缩小到本次变更的包及其下游，具体语义见 Ch11 和 14.2。

### 14.1.2 主分支镜像构建与推送

main 分支上做全量验证，然后构建两个镜像推送到 GitHub Container Registry：

```yaml
# .github/workflows/images.yml
name: Images

on:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
  packages: write        # 推送 GHCR 镜像

jobs:
  images:
    runs-on: ubuntu-latest
    env:
      TURBO_TEAM: ${{ vars.TURBO_TEAM }}
      TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
      IMAGE_PREFIX: ghcr.io/${{ github.repository }}
    steps:
      - name: Checkout
        uses: actions/checkout@v7

      - name: Setup pnpm and Node.js
        uses: pnpm/setup@v3
        with:
          cache: true
          require-lockfile: true

      # 主分支是发布源头，跑全量而不是 --affected
      - name: Verify
        run: pnpm turbo run lint typecheck test build

      - name: Setup Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Login to GHCR
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build & Push API
        uses: docker/build-push-action@v7
        with:
          context: .
          file: apps/api/Dockerfile
          push: true
          tags: |
            ${{ env.IMAGE_PREFIX }}/api:${{ github.sha }}
            ${{ env.IMAGE_PREFIX }}/api:latest
          cache-from: type=gha,scope=api
          cache-to: type=gha,mode=max,scope=api
          build-args: |
            TURBO_TEAM=${{ vars.TURBO_TEAM }}
          secrets: |
            turbo_token=${{ secrets.TURBO_TOKEN }}

      - name: Build & Push Web
        uses: docker/build-push-action@v7
        with:
          context: .
          file: apps/web/Dockerfile
          push: true
          tags: |
            ${{ env.IMAGE_PREFIX }}/web:${{ github.sha }}
            ${{ env.IMAGE_PREFIX }}/web:latest
          cache-from: type=gha,scope=web
          cache-to: type=gha,mode=max,scope=web
          build-args: |
            TURBO_TEAM=${{ vars.TURBO_TEAM }}
            VITE_APP_TITLE=TaskFlow
            VITE_API_ORIGIN=${{ vars.VITE_API_ORIGIN }}
          secrets: |
            turbo_token=${{ secrets.TURBO_TOKEN }}
```

几个关键点：

- **`IMAGE_PREFIX` 放在 job 级 `env`**，两个构建步骤复用，避免 tag 写错。
- **同时打 `github.sha` 和 `latest`**。部署时用 SHA tag 保证可追溯，`latest` 只方便人工拉取。
- **`cache-from/cache-to: type=gha`** 把 Buildx 的层缓存存到 GitHub Actions 缓存，跨 workflow run 复用。
- **`secrets` 而不是 `build-args` 传 `TURBO_TOKEN`**。build-arg 会出现在镜像构建历史里，secret 走 BuildKit 的临时挂载，不会留在最终镜像中。

> **为什么不在这个工作流里发布 npm 包？** Ch13 的 `changesets/action@v2` 已经负责版本 PR 和发布。镜像与 npm 包的发布节奏、权限和失败处理都不同，合并会让两件事互相拖累。

## 14.2 选择性构建：`--filter` 与 `--affected`

Turborepo 的过滤器决定了"哪些包参与本次任务"。CI 里最常用的有四种写法。

### 14.2.1 四种常用模式

```bash
# 1. 指定单个包
pnpm turbo build --filter=@taskflow/shared

# 2. 包及其所有依赖（... 在后）
pnpm turbo build --filter=@taskflow/web...
# 范围包含 web 依赖的 shared、ui；ui 没有 build 脚本，实际执行 shared 和 web

# 3. 包及其所有下游依赖者（... 在前）
pnpm turbo build --filter=...@taskflow/shared
# 构建 shared 以及所有依赖 shared 的包

# 4. 基于 Git 变更（CI 最常用）
pnpm turbo build --filter=...[origin/main]
# 变更的包及其下游依赖者
```

`...` 的位置非常关键：放在包名**后面**表示依赖，放在**前面**表示下游。写反了不会报错，但会构建完全错误的一组包。

### 14.2.2 `--affected`：CI 里更省心的写法

```bash
pnpm turbo run lint typecheck test build --affected
```

`--affected` 等价于 `--filter=...[main...HEAD]`，由 Turborepo 根据 `GITHUB_BASE_REF` 等环境变量自动确定基线。相比手写 `[origin/main]`，它不依赖分支名，也不会在默认分支上误判。

两者都需要**完整的 Git 历史**：

```yaml
- uses: actions/checkout@v7
  with:
    fetch-depth: 0
```

浅克隆（`fetch-depth: 1`）时，Turborepo 无法计算差异，会把所有包视为已变更——不会出错，但会失去增量加速。

`--affected` 是包级别的判断：一个包里有任何文件变化，它的所有任务都会被选中。如果你希望精确到任务输入，可以启用 Ch11 提到的 `futureFlags.affectedUsingTaskInputs`。

### 14.2.3 按目录过滤

```bash
# 所有 apps 下的包
pnpm turbo build --filter=./apps/*

# packages 下自上次提交以来有变更的包
pnpm turbo build --filter={./packages/*}[HEAD^1]

# 排除某个包
pnpm turbo build --filter=...[origin/main] --filter=!@taskflow/api
```

目录过滤器与 Git 过滤器组合时必须用 `{}` 包起来；单独的 `--filter=./apps/*` 不需要。`{src/**}` 这类写法不是合法的目录过滤器——花括号里必须是**包目录的 glob**，不是包内文件路径。

### 14.2.4 一个具体例子

假设 PR 只改了 `packages/shared` 的类型：

```txt
变更检测：packages/shared 有文件变更
         ↓
依赖图分析：
  packages/shared
    ├── apps/web（依赖 shared）✓
    ├── apps/api（依赖 shared）✓
    ├── packages/ui（不依赖 shared）✗
    └── packages/database（不依赖 shared）✗
         ↓
实际执行：shared → web / api
```

`--affected` 会把下游一起选中，正是为了避免"改共享包，只测共享包"这种漏测。

## 14.3 环境变量与 Secrets

### 14.3.1 三类变量

```txt
全局（根目录 / CI）
├── CI、TURBO_TOKEN、TURBO_TEAM

构建期变量（Vite）
├── apps/web: VITE_API_ORIGIN、VITE_APP_TITLE
│   └── 在 vite build 时被静态替换进产物

运行期变量（Node）
├── apps/api: DATABASE_URL、JWT_SECRET、JWT_REFRESH_SECRET、CORS_ORIGINS、PORT
└── packages/database: 复用 DATABASE_URL
```

这个区分非常重要：

- **Vite 的 `VITE_*` 变量在构建时就被写死**。同一个 Web 镜像无法通过"换个环境变量"切换到另一个 API 地址，必须重新构建，或者让前端走同源代理。
- **Node 的 `process.env` 在启动时读取**。同一个 API 镜像可以在 staging 和 production 复用，只需要注入不同的环境变量。

### 14.3.2 `.env` 的放置

Ch07 和 Ch08 已经在各自的 app 目录下建立了 `.env.example`。根目录不需要再维护一份"大而全"的 `.env`，否则两处容易漂移。部署时统一用平台的环境变量功能注入。

```txt
apps/api/.env.example
├── NODE_ENV=development
├── PORT=3000
├── DATABASE_URL=postgresql://postgres:postgres@localhost:5432/taskflow?schema=public
├── JWT_SECRET=change-me-to-at-least-32-characters
├── JWT_REFRESH_SECRET=change-me-to-at-least-32-characters
└── CORS_ORIGINS=http://localhost:5173
```

`.env`、`.env.local`、`.env.*.local` 必须在 `.gitignore` 中；`.env.example` 提交到仓库作为模板。**不要**把真实密钥写进 Dockerfile、Compose 文件或 `vercel.json`。

### 14.3.3 GitHub Secrets 与 Variables

| 类型 | 用途 | 示例 |
| ---- | ---- | ---- |
| Secrets | 加密、日志自动脱敏 | `TURBO_TOKEN`、`NPM_TOKEN`、`JWT_SECRET` |
| Variables | 明文、非敏感配置 | `TURBO_TEAM`、`VITE_API_ORIGIN` |

```yaml
env:
  TURBO_TEAM: ${{ vars.TURBO_TEAM }}
  TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
```

> 第三方 PR 默认拿不到 secrets。不要为了让 fork PR 命中远程缓存而改用 `pull_request_target` 并暴露 token——那等于把仓库密钥交给不可信代码。

## 14.4 Docker 多阶段构建

### 14.4.1 为什么不能直接 `COPY . .` 后安装

Monorepo 的 Docker 构建有三个坑：

1. **lockfile 是全局的**。改一下 `apps/web` 的依赖，`apps/api` 的镜像层也会失效。
2. **workspace 依赖不在 `apps/api` 目录里**。只复制 `apps/api` 会缺 `packages/shared`、`packages/database`。
3. **构建产物散落在多个包**。API 运行时需要自己的 `dist`、shared 的 `dist`、database 的 `dist`，以及对应的生产依赖。

Turborepo 的 `turbo prune` 解决前两个问题，`pnpm deploy` 解决第三个。

```bash
turbo prune @taskflow/api --docker
```

它会在 `out/` 下生成两份内容：

```txt
out/
├── json/          # 目标包及其依赖的 package.json + 裁剪后的 lockfile
│   ├── package.json
│   ├── pnpm-lock.yaml
│   ├── pnpm-workspace.yaml
│   ├── apps/api/package.json
│   └── packages/{shared,database}/package.json
└── full/          # 同样的结构，但包含源代码
```

Docker 先复制 `out/json` 并安装依赖，再复制 `out/full` 构建源码。这样只有依赖清单变化时才会重装，源代码变化只影响后面的构建层。

### 14.4.2 apps/api 的 Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

# ====== 公共基础 ======
FROM node:24-alpine AS base
RUN apk add --no-cache libc6-compat
RUN corepack enable

# 镜像里没有 .git，根 package.json 的 "prepare": "husky" 无法安装钩子。
# HUSKY=0 让 husky 安静跳过；不要用 --ignore-scripts，那会连 esbuild 的构建脚本一起关掉。
ENV HUSKY=0

WORKDIR /app

# ====== 裁剪 workspace ======
FROM base AS prepare
ARG TURBO_VERSION=2.11.5
COPY . .
RUN pnpm dlx turbo@${TURBO_VERSION} prune @taskflow/api --docker

# ====== 安装依赖并构建 ======
FROM base AS builder
COPY --from=prepare /app/out/json/ ./
RUN pnpm install --frozen-lockfile

COPY --from=prepare /app/out/full/ ./

ARG TURBO_TEAM
ENV TURBO_TEAM=$TURBO_TEAM
RUN --mount=type=secret,id=turbo_token \
    if [ -f /run/secrets/turbo_token ]; then \
      export TURBO_TOKEN="$(cat /run/secrets/turbo_token)"; \
    fi; \
    pnpm turbo run build --filter=@taskflow/api

# 把 api 及其生产依赖打包成一个自包含目录
RUN pnpm --filter=@taskflow/api --prod deploy /app/deploy

# ====== 运行时 ======
FROM node:24-alpine AS runner

ENV NODE_ENV=production
ENV PORT=3000

# dumb-init 作为 PID 1，正确转发 SIGTERM
RUN apk add --no-cache dumb-init

RUN addgroup --system --gid 1001 nodejs \
 && adduser --system --uid 1001 nodejs

WORKDIR /app
COPY --from=builder --chown=nodejs:nodejs /app/deploy ./

USER nodejs

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=3s --start-period=20s \
  CMD wget -qO- http://127.0.0.1:3000/api/health || exit 1

CMD ["dumb-init", "node", "dist/index.js"]
```

**关键设计解析：**

1. **`turbo prune` 而不是手动复制 package.json**。裁剪后的 lockfile 只包含 API 及其依赖，改 Web 的依赖不会让 API 镜像重装。
2. **`pnpm dlx turbo@2.11.5`**。prepare 阶段还没安装 workspace 依赖，用 `dlx` 临时获取指定版本的 turbo，避免"用旧 turbo 裁剪新仓库"。
3. **`pnpm deploy`**。它在 `/app/deploy` 生成一个独立目录：API 的源码/产物 + 所有生产依赖（包括 workspace 包）。pnpm 12.2 起不再要求 `injectWorkspacePackages`，workspace 依赖会写成 `file:` 依赖装进部署目录。
4. **生产镜像不含 pnpm**。runner 只复制 deploy 目录，不复制 store、源码和 devDependencies，镜像体积和攻击面都更小。
5. **`dumb-init` + 非 root 用户**。Node 作为 PID 1 不会自动回收僵尸进程；非 root 运行则限制了代码注入后的破坏范围。
6. **`HEALTHCHECK` 打 `/api/health`**。这个路由在 Ch08 中已实现，返回 `{ success: true, data: { status: 'ok', ... } }`。
7. **`ENV HUSKY=0`**。根 `package.json` 的 `prepare` 会在每次 `pnpm install` 后执行 `husky`，而镜像里没有 `.git`。`HUSKY=0` 让 husky 跳过安装；相比 `--ignore-scripts`，它不会影响 esbuild 等依赖的构建脚本。

> **Prisma 7 不需要额外复制引擎**。Ch08 的 `prisma-client` 生成器把客户端生成为 TypeScript 源码，`pnpm turbo run build` 会在构建 database 包时执行 `prisma generate && tsc`，产物就在 `packages/database/dist` 里，由 `pnpm deploy` 一并打包。运行时只需要 `@prisma/adapter-pg` 和 `pg`，没有 Rust 查询引擎。

### 14.4.3 apps/web 的 Dockerfile

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-alpine AS base
RUN corepack enable

ENV HUSKY=0

WORKDIR /app

FROM base AS prepare
ARG TURBO_VERSION=2.11.5
COPY . .
RUN pnpm dlx turbo@${TURBO_VERSION} prune @taskflow/web --docker

FROM base AS builder
COPY --from=prepare /app/out/json/ ./
RUN pnpm install --frozen-lockfile
COPY --from=prepare /app/out/full/ ./

ARG TURBO_TEAM
ENV TURBO_TEAM=$TURBO_TEAM

# Vite 在构建时读取这些变量
ARG VITE_APP_TITLE=TaskFlow
ARG VITE_API_ORIGIN
ENV VITE_APP_TITLE=$VITE_APP_TITLE
ENV VITE_API_ORIGIN=$VITE_API_ORIGIN

RUN --mount=type=secret,id=turbo_token \
    if [ -f /run/secrets/turbo_token ]; then \
      export TURBO_TOKEN="$(cat /run/secrets/turbo_token)"; \
    fi; \
    pnpm turbo run build --filter=@taskflow/web

FROM nginx:1.29-alpine AS runner

COPY apps/web/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/apps/web/dist /usr/share/nginx/html

EXPOSE 80
```

配套的 `apps/web/nginx.conf`：

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml;
    gzip_min_length 1000;

    # Vite 产物带 hash，可以长期缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # history 模式路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }

    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}
```

前端用 Nginx 托管静态文件，而不是在 Node 里跑 `vite preview`：Nginx 处理并发、Gzip、缓存更高效，Alpine 镜像也只有几十 MB。

> **`VITE_API_ORIGIN` 在构建时就固定了。** 如果希望 Web 和 API 同源（例如都由同一个域名提供），把 `VITE_API_ORIGIN` 设为空字符串，并在 Nginx 增加 `location /api/ { proxy_pass http://api:3000; }`。这会把这个镜像和 Compose 的服务名耦合在一起，按需选择。

### 14.4.4 `.dockerignore`

```txt
# .dockerignore
node_modules
**/node_modules
.git
.github
.vscode
.turbo
**/dist
**/coverage
playwright-report
test-results

# 密钥绝不进入构建上下文
```

`**/dist` 必须排除：本地构建的旧产物会混进 prepare 阶段，`turbo prune` 之后可能带着过期文件进入镜像。测试文件可以保留，`tsc` 的 `exclude` 和 Vitest 的 `include` 已经决定了它们是否参与构建。

## 14.5 Docker Compose 编排

### 14.5.1 开发环境：只容器化基础设施

本地开发不需要把 Web 和 API 也塞进容器。宿主机上由 `pnpm dev` 启动 Turbo，Vite HMR 和 tsx watch 都比容器内更顺畅；Compose 只负责 PostgreSQL：

```yaml
# docker-compose.dev.yml
name: taskflow-dev

services:
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: taskflow
    ports:
      - '5432:5432'
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U postgres -d taskflow']
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  postgres_data:
```

```bash
docker compose -f docker-compose.dev.yml up -d
pnpm dev
```

Ch08 的 `DATABASE_URL` 默认就是 `postgresql://postgres:postgres@localhost:5432/taskflow`，与上面的账号、密码、库名一致。

> **不要用 `version: '3.8'`。** Compose V2 已忽略这个字段并会打印警告，新文件直接省略。

### 14.5.2 生产环境

生产环境使用 CI 推送的不可变镜像：

```yaml
# docker-compose.prod.yml
name: taskflow

services:
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U ${DB_USER} -d ${DB_NAME}']
      interval: 10s
      timeout: 5s
      retries: 5

  api:
    image: ghcr.io/${GITHUB_REPOSITORY}/api:${IMAGE_TAG:-latest}
    environment:
      NODE_ENV: production
      PORT: '3000'
      DATABASE_URL: postgresql://${DB_USER}:${DB_PASSWORD}@postgres:5432/${DB_NAME}?schema=public
      JWT_SECRET: ${JWT_SECRET}
      JWT_REFRESH_SECRET: ${JWT_REFRESH_SECRET}
      CORS_ORIGINS: ${CORS_ORIGINS}
    ports:
      - '3000:3000'
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://127.0.0.1:3000/api/health']
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 20s
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '1.0'

  web:
    image: ghcr.io/${GITHUB_REPOSITORY}/web:${IMAGE_TAG:-latest}
    ports:
      - '80:80'
    depends_on:
      api:
        condition: service_healthy
    restart: unless-stopped

volumes:
  postgres_data:
```

启动：

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production up -d
```

**几个容易出错的地方：**

- **`DB_PASSWORD` 含特殊字符时要 URL 编码**。`DATABASE_URL` 是 URL，密码里的 `@`、`:`、`#` 必须转义，否则连接串会被截断。更稳妥的做法是把密码限制为字母数字，或使用 `PGPASSWORD` + 非 URL 形式的连接配置。
- **`IMAGE_TAG` 用 `github.sha`**。`latest` 只适合本地试跑，生产回滚依赖明确的 SHA tag。
- **`CORS_ORIGINS` 必须是 Web 的实际来源**。Ch08 用逗号分隔允许多个来源；漏配会导致浏览器端所有 API 请求被 CORS 拦截。
- **数据库迁移不要放进 API 容器启动命令**。并发启动多个副本会重复执行迁移。迁移应该在部署流水线里单独执行（见下）。

数据库迁移需要一个带 `prisma` CLI 的环境。给 `packages/database` 增加生产迁移脚本：

```json
{
  "scripts": {
    "db:deploy": "prisma migrate deploy"
  }
}
```

然后在 CI 的部署阶段（或一次性任务）执行：

```bash
pnpm --filter @taskflow/database db:deploy
```

不要在生产 API 镜像里内置 `prisma migrate deploy`：`pnpm deploy --prod` 不含 `prisma` CLI，而且把迁移和进程启动绑在一起会让扩容变得危险。

## 14.6 平台部署

### 14.6.1 Web 部署到 Vercel

Vercel 对 pnpm workspace 有原生支持，关键是**路径基准只能选一套**。推荐把 Root Directory 设为**仓库根目录**，把配置放在根 `vercel.json`：

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "vite",
  "installCommand": "pnpm install --frozen-lockfile",
  "buildCommand": "pnpm turbo run build --filter=@taskflow/web",
  "outputDirectory": "apps/web/dist",
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

项目设置：

- **Root Directory**：仓库根目录（留空或填 `.`）
- **Environment Variables**：`VITE_APP_TITLE`、`VITE_API_ORIGIN`

**常见的错误配置**是把 Root Directory 设成 `apps/web`，却仍然使用根目录的 `vercel.json` 和 `outputDirectory: "apps/web/dist"`。此时 Vercel 以 `apps/web` 为基准：

- 找不到根目录的 `vercel.json`
- `apps/web/dist` 会被解析成 `apps/web/apps/web/dist`

如果确实想以 `apps/web` 为 Root Directory，需要把 `vercel.json` 放进 `apps/web`，并把配置改成：

```json
{
  "buildCommand": "cd ../.. && pnpm turbo run build --filter=@taskflow/web",
  "outputDirectory": "dist"
}
```

两种方式都可行，但**不要混用**。

Vercel 每次 push 都会构建。如果只想在 Web 相关代码变化时构建，可以加 `ignoreCommand`（基于 `turbo-ignore`），或接受少量无效构建——对大多数项目来说，后者更简单。

### 14.6.2 API 部署到 Railway

Railway 的 Docker 构建需要能访问整个仓库，因此 **Root Directory 设为仓库根目录**，`railway.toml` 也放在根目录：

```toml
# railway.toml
[build]
builder = "DOCKERFILE"
dockerfilePath = "apps/api/Dockerfile"
watchPatterns = [
  "apps/api/**",
  "packages/shared/**",
  "packages/database/**",
  "pnpm-lock.yaml",
  "pnpm-workspace.yaml",
  "turbo.json"
]

[deploy]
healthcheckPath = "/api/health"
healthcheckTimeout = 300
restartPolicyType = "ON_FAILURE"
restartPolicyMaxRetries = 3
```

- **不要设置 `startCommand`**。镜像的 `CMD` 已经正确指向 `dist/index.js`；覆盖它容易把工作目录搞错（deploy 目录的根就是 `apps/api`）。
- **`healthcheckPath` 是 `/api/health`**，不是 `/health`。Ch08 的所有路由都挂在 `/api` 前缀下。
- **`watchPatterns` 必须包含 workspace 文件**。只写 `apps/api/**` 会漏掉 shared 类型变更和 lockfile 变更。

环境变量在 Railway 控制台注入：`DATABASE_URL`、`JWT_SECRET`、`JWT_REFRESH_SECRET`、`CORS_ORIGINS`、`NODE_ENV=production`。

### 14.6.3 API 部署到 Fly.io（备选）

Fly.io 适合需要多区域部署或更低延迟的场景。`fly.toml` 放在仓库根目录，构建上下文才是整个 monorepo：

```toml
# fly.toml
app = "taskflow-api"
primary_region = "hkg"

[build]
  dockerfile = "apps/api/Dockerfile"

[env]
  NODE_ENV = "production"
  PORT = "3000"

[http_service]
  internal_port = 3000
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 1

[[http_service.checks]]
  interval = "15s"
  timeout = "2s"
  grace_period = "10s"
  method = "GET"
  path = "/api/health"

[[vm]]
  size = "shared-cpu-1x"
  memory = "512mb"
```

`memory` 用字符串（如 `"512mb"`），旧的 `memory_mb` 数值字段已废弃。256MB 对 Node + Prisma 连接池偏紧，512MB 是更安全的起点。

```bash
fly secrets set DATABASE_URL=... JWT_SECRET=... JWT_REFRESH_SECRET=... CORS_ORIGINS=...
fly deploy
```

## 14.7 多应用部署的缓存与产物优化

### 14.7.1 镜像层缓存

`turbo prune` 已经把"依赖层"和"源码层"分开：

```dockerfile
COPY --from=prepare /app/out/json/ ./     # 只有依赖变化时失效
RUN pnpm install --frozen-lockfile
COPY --from=prepare /app/out/full/ ./     # 源码变化只影响后面的层
RUN pnpm turbo run build ...
```

配合 workflow 里的 `cache-from/cache-to: type=gha`，跨 CI run 也能复用层缓存。不要再用 `COPY packages/*/package.json ./packages/` 这种写法：多个源文件复制到同一目录会**扁平化**，后一个 `package.json` 覆盖前一个。`turbo prune` 生成的目录结构是唯一可靠的版本。

### 14.7.2 Turborepo 远程缓存

镜像构建同样能命中 Turborepo 远程缓存：Dockerfile 里的 `turbo run build` 只要拿到 `TURBO_TOKEN`（以及 Vercel Remote Cache 需要的 `TURBO_TEAM`），就会复用 Ch11 配置的远程缓存。上面的 Dockerfile 用 BuildKit secret 注入 token、用 build-arg 传入 team，避免把凭据写进镜像层。

这带来一个实际收益：CI 里已经构建过的包，在镜像构建阶段可以直接下载缓存产物，不必重新编译。前提是**环境变量参与 hash**——Ch10 的 `build.env` 已经声明了 `VITE_APP_TITLE` 和 `VITE_API_ORIGIN`，所以不同 API 地址的 Web 镜像不会错误复用缓存。

### 14.7.3 构建一次，处处部署

推荐的做法是：

1. CI 构建一次镜像，推送 `api:<sha>`、`web:<sha>`。
2. staging 和 production 都引用**同一个 SHA tag**。
3. 回滚时把 `IMAGE_TAG` 指回上一个 SHA。

不要在每个环境重新 `docker build`。重复构建不仅慢，还会让"staging 验证过的镜像"和"production 运行的镜像"产生不可控的差异。

### 14.7.4 部署检查清单

- [ ] 镜像以非 root 用户运行
- [ ] 健康检查路径与实际路由一致（`/api/health`）
- [ ] `DATABASE_URL` 等敏感变量通过平台 Secrets 注入，未写进镜像
- [ ] 数据库迁移在部署前单独执行，未绑定到容器启动
- [ ] Web 的 `VITE_API_ORIGIN` 指向正确的 API 地址，且 API 的 `CORS_ORIGINS` 包含 Web 来源
- [ ] 生产使用 SHA tag，`latest` 仅用于本地或临时环境
- [ ] 日志输出到 stdout/stderr，由平台收集，不写容器内文件

## 本章小结

1. **流水线拆分**：PR 检查（Ch11）、npm 发布（Ch13）、镜像构建（本章）各自独立，权限和触发条件互不干扰
2. **镜像最小化**：`turbo prune` 裁剪 workspace，`pnpm deploy` 生成自包含运行目录，runner 阶段不含 pnpm、源码和 devDependencies
3. **安全**：非 root 用户、`dumb-init`、BuildKit secret 注入 token、健康检查打真实路由
4. **Compose**：开发只容器化 PostgreSQL，应用在宿主机跑；生产使用不可变 SHA 镜像并限制资源
5. **平台**：Vercel 的 Root Directory 与 `vercel.json` 路径基准必须一致；Railway/Fly 的构建上下文必须是仓库根目录
6. **缓存**：prune 分层 + Buildx GHA cache + Turborepo 远程缓存，三层叠加缩短构建时间

核心原则仍然是：**一次构建，处处部署；只做必要的工作，只给必要的权限。**
