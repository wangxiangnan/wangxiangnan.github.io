# 第 3 章 SQL 基础（上）—— DDL 表结构设计

## 3.1 幽默开场：数据库版的"装修"

如果说数据是家具，那**表结构就是户型图**。你敢在没画户型图的情况下往新房里搬家具吗？搬完 3 天你发现，卧室没门、厕所在客厅中央、餐厅没有电源 —— 崩溃。

数据库也是同理。**"能跑就行"式表设计**会在项目做大后变成灾难：字段名叫 `f1 f2 f3`、类型全是 TEXT、外键全靠约定、索引一个都没有 …… 后端接手时的表情，堪比看到甲方朋友帮忙"设计"的婚房。

这一章我们来学"数据库装修"—— **DDL（Data Definition Language，数据定义语言）**。

## 3.2 DDL 概览

SQL 按功能大致分四类：

| 类别 | 全称 | 干什么 | 关键字 |
| --- | --- | --- | --- |
| **DDL** | Data Definition Language | 定义/修改结构 | CREATE / ALTER / DROP / TRUNCATE |
| **DML** | Data Manipulation Language | 增删改数据 | INSERT / UPDATE / DELETE |
| **DQL** | Data Query Language | 查询数据 | SELECT |
| **DCL** | Data Control Language | 权限控制 | GRANT / REVOKE |
| **TCL** | Transaction Control | 事务控制 | BEGIN / COMMIT / ROLLBACK |

SQLite 因为没有用户系统，**没有 DCL**。DML / DQL / DDL / TCL 都完整支持。

本章聚焦 **DDL**：`CREATE TABLE`、`ALTER TABLE`、`DROP TABLE`。

## 3.3 `CREATE TABLE` 完整语法解剖

先看最简单的：

```sql
CREATE TABLE users (
    id   INTEGER PRIMARY KEY,
    name TEXT
);
```

然后是"接近生产可用"的：

```sql
CREATE TABLE IF NOT EXISTS users (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    username   TEXT    NOT NULL UNIQUE COLLATE NOCASE,
    email      TEXT    NOT NULL UNIQUE,
    age        INTEGER CHECK (age BETWEEN 0 AND 150),
    balance    REAL    NOT NULL DEFAULT 0.0,
    avatar     BLOB,
    created_at INTEGER NOT NULL DEFAULT (unixepoch()),
    updated_at INTEGER NOT NULL DEFAULT (unixepoch()),
    is_deleted INTEGER NOT NULL DEFAULT 0 CHECK (is_deleted IN (0, 1))
);
```

这里几乎覆盖了所有常见语法元素，我们逐一拆解。

### 3.3.1 `IF NOT EXISTS`

如果表已存在，不报错、不覆盖，静默跳过。**初始化脚本一定要用，幂等性。**

### 3.3.2 列定义：`列名 类型 [约束...]`

**列名规则**：

- 由字母、数字、下划线组成。
- 不能以数字开头。
- 关键字（如 `order`、`select`）需要用反引号 `` `name` ``、双引号 `"name"` 或方括号 `[name]` 包起来。
- **建议**：`snake_case`，全小写，语义清晰。

**类型名**：可以是 `INTEGER / TEXT / REAL / BLOB / NUMERIC`，也可以是 `VARCHAR(255) / DECIMAL(10,2) / DATETIME / BOOLEAN` 这种**从 MySQL 借来的名字**。SQLite 会根据"类型亲和性（Type Affinity）"规则自动映射（详见第 6 章）。

### 3.3.3 列级约束

**`NOT NULL`** —— 不允许 NULL：

```sql
name TEXT NOT NULL
```

**`DEFAULT`** —— 默认值：

```sql
created_at INTEGER NOT NULL DEFAULT (unixepoch())
balance    REAL    DEFAULT 0.0
status     TEXT    DEFAULT 'pending'
```

`DEFAULT` 后可以跟：

- 字面量（数字、字符串、NULL）。
- 特殊常量：`CURRENT_TIME` / `CURRENT_DATE` / `CURRENT_TIMESTAMP`。
- **表达式（外层要加括号）**：`DEFAULT (unixepoch())`、`DEFAULT (lower('Hello'))`。

**`UNIQUE`** —— 唯一约束：

```sql
email TEXT NOT NULL UNIQUE
```

底层会自动创建一个 UNIQUE 索引。

**`CHECK`** —— 检查约束：

```sql
age INTEGER CHECK (age BETWEEN 0 AND 150)
gender TEXT CHECK (gender IN ('M', 'F', 'X'))
```

`CHECK` 表达式插入 / 更新时评估，为假（0）则拒绝写入。

**`COLLATE`** —— 排序规则：

```sql
username TEXT COLLATE NOCASE
```

SQLite 内建三种：

- `BINARY`（默认）：字节比较。
- `NOCASE`：ASCII 大小写不敏感。**只处理 ASCII！中文大小写不管。**
- `RTRIM`：忽略末尾空格。

想要 UTF-8 大小写不敏感？需要注册自定义 collation 或用 ICU 扩展。

**`REFERENCES`** —— 外键（列级）：

```sql
author_id INTEGER REFERENCES users(id)
```

**注意**：SQLite 的外键**默认不开启**！要执行：

```sql
PRAGMA foreign_keys = ON;
```

**每次连接都要设**（因为它是连接级别的 PRAGMA）。我知道，这是 SQLite 最反直觉的默认设置之一。稍后详解。

### 3.3.4 表级约束

表定义最后可以加表级约束，用逗号分隔：

```sql
CREATE TABLE posts (
    id         INTEGER PRIMARY KEY,
    author_id  INTEGER NOT NULL,
    title      TEXT    NOT NULL,
    slug       TEXT    NOT NULL,
    category   TEXT    NOT NULL,
    published  INTEGER NOT NULL DEFAULT 0,

    -- 表级 UNIQUE：多列组合
    UNIQUE (author_id, slug),

    -- 表级 CHECK：跨字段验证
    CHECK (length(title) BETWEEN 1 AND 200),

    -- 表级外键
    FOREIGN KEY (author_id) REFERENCES users(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);
```

**`ON DELETE` / `ON UPDATE`** 的动作：

- `NO ACTION`（默认）：延迟到事务提交时校验。
- `RESTRICT`：立即校验，父表被删/改则拒绝。
- `CASCADE`：级联，父表变化时子表跟着变。
- `SET NULL`：置空。
- `SET DEFAULT`：置为默认值。

## 3.4 SQLite 的 5 种存储类

**这是 SQLite 最反常识的地方。请系好安全带。**

传统数据库（MySQL、PostgreSQL）是**静态类型**：你声明 `age INT`，就永远存 INT，你 `INSERT` 一个字符串进去会报错。

SQLite 是 **动态类型**：**类型是绑定在"值"上的，不是"列"上的**。这就是所谓的"**类型亲和性（Type Affinity）**"。

SQLite 只有 **5 种存储类（Storage Class）**：

| 存储类 | 说明 | 类似 |
| --- | --- | --- |
| `NULL` | 空值 | NULL |
| `INTEGER` | 变长整数，1/2/3/4/6/8 字节 | int8 ~ int64 |
| `REAL` | 8 字节 IEEE 754 双精度浮点 | double |
| `TEXT` | UTF-8 / UTF-16 字符串 | string |
| `BLOB` | 二进制原样存储 | bytes |

**注意，没有 BOOLEAN、没有 DATE、没有 DATETIME、没有 DECIMAL、没有 UUID！** 它们都是"逻辑类型"，在物理上映射到上面 5 种。

- `BOOLEAN` → 存 `0` / `1` 的 INTEGER。
- `DATE` / `DATETIME` → 通常存 UTC 秒（INTEGER）或 ISO 8601 字符串（TEXT）。
- `DECIMAL` → 存 TEXT 或 REAL（要精度就 TEXT）。
- `UUID` → 存 TEXT 或 16 字节 BLOB。

### 3.4.1 类型亲和性（预告）

你声明的"类型"，SQLite 只是当作一个**建议**（叫做"亲和性"），决定它更倾向于把值转成什么。规则大致：

- 类型名包含 `INT` → **INTEGER 亲和性**。
- 包含 `CHAR` / `TEXT` / `CLOB` → **TEXT 亲和性**。
- 包含 `BLOB` 或没声明类型 → **BLOB 亲和性（无亲和）**。
- 包含 `REAL` / `FLOA` / `DOUB` → **REAL 亲和性**。
- 其他（含 `NUMERIC` / `DECIMAL`） → **NUMERIC 亲和性**。

演示："能塞就塞"的哲学：

```sql
CREATE TABLE demo (x INTEGER);

INSERT INTO demo VALUES ('123');     -- 字符串 "123" 会被自动转成 INTEGER 123
INSERT INTO demo VALUES ('hello');   -- 转不了，就当 TEXT 存进去了！
INSERT INTO demo VALUES (3.14);      -- REAL 存进去

SELECT x, typeof(x) FROM demo;
-- 123    | integer
-- hello  | text     ← 卧槽，INTEGER 列里居然存了 text！
-- 3.14   | real
```

这就是"能跑就行"的 SQLite。它是**优点也是坑**。第 6 章会专门讲。

## 3.5 主键详解：`INTEGER PRIMARY KEY` 与 rowid 的秘密

这是 SQLite 独有的高级黑魔法，学好之后你会觉得"MySQL 的自增主键真弱鸡"。

### 3.5.1 rowid 是什么

**每一张普通 SQLite 表都有一个隐含的 64 位整数字段 `rowid`**（除非你显式建 `WITHOUT ROWID` 表）。它是这张表的**物理定位符** —— B-Tree 就是按 rowid 组织的。

你随便建个表：

```sql
CREATE TABLE t (a TEXT, b TEXT);
INSERT INTO t VALUES ('x', 'y');

SELECT rowid, a, b FROM t;
-- 1 | x | y
```

看，即使你没定义 id，也有 rowid！它还有别名 `_rowid_` 和 `oid`。

### 3.5.2 `INTEGER PRIMARY KEY` 的魔法

**如果你把主键声明为 `INTEGER PRIMARY KEY`（注意大小写不敏感，但类型必须是 INTEGER，不是 INT）**，SQLite 会把这个字段变成 **`rowid` 的别名**。

```sql
CREATE TABLE users (
    id   INTEGER PRIMARY KEY,   -- ← 这行的 id 就是 rowid
    name TEXT
);

INSERT INTO users (name) VALUES ('Alice');
SELECT id, rowid FROM users;
-- 1 | 1     ← id 和 rowid 是同一个东西
```

**含义 & 好处**：

1. 主键查询极快（B-Tree 直接按 rowid 走）。
2. 主键**自动递增**（默认 max(rowid)+1）。
3. 不需要建额外索引来支持主键查询（rowid 本身就是 B-Tree 的 key）。
4. 占用空间小（跟数据一起存，无冗余）。

**这是 SQLite 表设计的黄金准则**：**主键 99% 的情况都应该用 `INTEGER PRIMARY KEY`**。

### 3.5.3 `AUTOINCREMENT` 的秘密

你可能见过：

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
```

和：

```sql
id INTEGER PRIMARY KEY
```

它们**不完全一样**。默认行为（无 `AUTOINCREMENT`）：

- 新行 id = `max(rowid) + 1`。
- **如果你删了最大的 id 又插入新行，id 会被复用！**
- 极端情况 rowid 满了（2^63 - 1）之后，会去找**空闲的**行号复用。

带 `AUTOINCREMENT`：

- id 严格单调递增，**永不复用**。
- 靠一个隐藏表 `sqlite_sequence` 记录每张表的下一个 id。
- 每次插入都要读写这个表，**性能稍差**。
- rowid 满了会**报错**而不是复用。

**结论**：

- **99% 场景用不带 AUTOINCREMENT 的 `INTEGER PRIMARY KEY` 就够了。**
- 只有当你**绝对不能容忍 id 复用**（比如作为对外的稳定标识符），才加 `AUTOINCREMENT`。

### 3.5.4 其他主键形式

**多列主键（联合主键）**：

```sql
CREATE TABLE order_items (
    order_id   INTEGER,
    product_id INTEGER,
    quantity   INTEGER NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

**非 INTEGER 主键**（比如 UUID）：

```sql
CREATE TABLE sessions (
    id       TEXT PRIMARY KEY,      -- UUID 字符串
    user_id  INTEGER NOT NULL,
    expires  INTEGER NOT NULL
);
```

**这里 id 就不是 rowid 别名了**！表还是有一个隐藏的 rowid，主键索引是额外维护的。这可能不是你想要的（详见下节 WITHOUT ROWID）。

## 3.6 `WITHOUT ROWID` 表：什么时候用

**普通表 = rowid 表**：数据按 rowid 的 B-Tree 存储，主键索引（如果不是 INTEGER PRIMARY KEY）是**外挂的**辅助索引，查询要先查索引 → 拿到 rowid → 再查数据。**两次查找。**

**`WITHOUT ROWID` 表**：数据直接按主键 B-Tree 存储，**没有 rowid**。主键查询**一次搞定**。

```sql
CREATE TABLE kv_store (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
) WITHOUT ROWID;
```

**适用场景**：

- 主键**不是 INTEGER**（比如 TEXT UUID、字符串 key）。
- 表**行较小**（几十字节到几百字节，主要是短字符串主键 + 小 payload）。
- 主键**远小于整行**总大小。

**不适用场景**：

- 主键就是 `INTEGER PRIMARY KEY`（这时 rowid 表已经最优，别折腾）。
- 单行数据很大（B-Tree 分裂会变慢）。
- 需要 rowid 特性（一些扩展依赖它）。

**注意**：`WITHOUT ROWID` 表必须有 `PRIMARY KEY`，否则报错。

## 3.7 严格类型表：STRICT tables（SQLite 3.37+）

3.37 版本终于加了 "严格类型"选项，一句 `STRICT` 就治好了动态类型强迫症：

```sql
CREATE TABLE users (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL,
    age   INTEGER,
    score REAL,
    data  BLOB,
    tag   ANY                -- STRICT 独有：显式接受任意类型
) STRICT;
```

**行为**：

- 每一列的声明类型必须是：`INT` / `INTEGER` / `REAL` / `TEXT` / `BLOB` / `ANY`（**只能是这 6 种**，别的名字如 `VARCHAR(255)` 会报错）。
- 插入 / 更新的值必须匹配声明类型，**否则拒绝**。
- 只有 `ANY` 列允许存任何类型。

对比：

```sql
-- 普通表（宽松）
CREATE TABLE loose (age INTEGER);
INSERT INTO loose VALUES ('hello');   -- 允许！

-- STRICT 表
CREATE TABLE strict1 (age INTEGER) STRICT;
INSERT INTO strict1 VALUES ('hello'); -- Error: cannot store TEXT value in INTEGER column strict1.age
```

**推荐**：**新项目都用 STRICT**，除非你有特别理由需要动态类型。

`STRICT` 也可以和 `WITHOUT ROWID` 一起：

```sql
CREATE TABLE kv (
    key   TEXT NOT NULL PRIMARY KEY,
    value BLOB
) STRICT, WITHOUT ROWID;
```

## 3.8 `ALTER TABLE` 的限制与解决方案

SQLite 的 `ALTER TABLE` 是最"残废"的部分之一。它**只支持四种操作**：

```sql
-- 1. 重命名表
ALTER TABLE old_name RENAME TO new_name;

-- 2. 重命名列（3.25+）
ALTER TABLE users RENAME COLUMN old_col TO new_col;

-- 3. 增加列
ALTER TABLE users ADD COLUMN nickname TEXT;

-- 4. 删除列（3.35+）
ALTER TABLE users DROP COLUMN nickname;
```

**不支持**：

- ❌ 修改列类型
- ❌ 修改列约束（如加 NOT NULL、改 DEFAULT）
- ❌ 修改主键
- ❌ 加/删外键

### 3.8.1 加列的限制

`ADD COLUMN` 有几个坑：

- 新列不能是 `PRIMARY KEY`。
- 新列不能是 `UNIQUE`。
- 如果加 `NOT NULL`，必须给一个 `DEFAULT`（非 NULL 值）。
- `DEFAULT` 必须是常量（不能是 `CURRENT_TIMESTAMP`，因为这在 ALTER 时求值会导致旧行取到相同值不合理 —— 具体规则见文档）。

### 3.8.2 12 步修改法

想改列类型/约束怎么办？官方给了一个仪式感很强的 **12 步表重建法**（见 <https://sqlite.org/lang_altertable.html）。简化版：>

```sql
BEGIN TRANSACTION;

-- 1. 关外键
PRAGMA foreign_keys = OFF;

-- 2. 建新表（用新结构）
CREATE TABLE users_new (
    id         INTEGER PRIMARY KEY,
    name       TEXT NOT NULL,
    email      TEXT NOT NULL UNIQUE,
    -- 新增字段
    updated_at INTEGER NOT NULL DEFAULT 0
);

-- 3. 复制数据
INSERT INTO users_new (id, name, email)
    SELECT id, name, email FROM users;

-- 4. 删旧表
DROP TABLE users;

-- 5. 改名
ALTER TABLE users_new RENAME TO users;

-- 6. 重建索引 / 触发器 / 视图
CREATE INDEX idx_users_email ON users(email);

-- 7. 校验外键
PRAGMA foreign_key_check;

-- 8. 开外键
PRAGMA foreign_keys = ON;

COMMIT;
```

**这就是数据库迁移工具（drift、Room、Alembic）帮你干的活。**

## 3.9 `DROP TABLE` 与临时表

**删表**：

```sql
DROP TABLE users;              -- 表不存在会报错
DROP TABLE IF EXISTS users;    -- 安全删除
```

**删表会**：

- 删除表数据 + 表结构。
- 删除该表所有索引、触发器。
- **不会**级联删除关联表（除非目标表被外键 `ON DELETE CASCADE` 引用）。

**临时表 TEMP**：

```sql
CREATE TEMP TABLE tmp_result AS
    SELECT user_id, COUNT(*) AS c
    FROM posts
    GROUP BY user_id;

-- 用完可以不管，连接关闭自动销毁
```

TEMP 表的特点：

- 只在**当前连接**可见。
- 连接关闭自动销毁。
- 存储在**独立的临时数据库文件**中（或内存，取决于 `PRAGMA temp_store`）。
- 名字可以和普通表重名（TEMP 优先）。

**用途**：

- 存储中间计算结果，多次复用。
- 复杂 ETL 场景。
- 测试 / 试错。

## 3.10 命名规范与最佳实践

个人品味见仁见智，但社区约定成俗：

**表名**：

- 复数：`users`, `posts`, `comments`。
- snake_case：`user_profiles`, `blog_posts`。
- 中间表：`user_roles`（或 `users_roles`）。
- 前缀（可选）：`t_users`（老 Oracle 风格，现代少见）。

**列名**：

- 主键：`id`。
- 外键：`{referenced_table_singular}_id`，如 `user_id`、`post_id`。
- 布尔：`is_xxx` / `has_xxx`，值存 0/1。
- 时间戳：`created_at` / `updated_at` / `deleted_at`（软删除）。
- 计数：`xxx_count`。
- 避免使用 SQL 关键字（`order`, `group`, `key`, `select`）。

**避免的坑**：

- **驼峰命名**（`userName`）：SQLite 大小写不敏感对 unquoted 标识符，但很多工具会规范化，容易产生疑惑。
- **拼音命名**（`yonghubiao`）：接手的下一位程序员会诅咒你。
- **中文命名**（`用户表`）：技术上可行，实际全是坑。

## 3.11 Flutter 实战：创建用户 / 文章两张表

我们做一个博客 App 的基础表：

### 3.11.1 表设计

```sql
-- 用户表
CREATE TABLE IF NOT EXISTS users (
    id         INTEGER PRIMARY KEY,
    username   TEXT    NOT NULL UNIQUE COLLATE NOCASE,
    email      TEXT    NOT NULL UNIQUE,
    avatar_url TEXT,
    bio        TEXT,
    created_at INTEGER NOT NULL DEFAULT (unixepoch()),
    updated_at INTEGER NOT NULL DEFAULT (unixepoch())
) STRICT;

-- 文章表
CREATE TABLE IF NOT EXISTS posts (
    id         INTEGER PRIMARY KEY,
    author_id  INTEGER NOT NULL,
    title      TEXT    NOT NULL,
    slug       TEXT    NOT NULL,
    content    TEXT    NOT NULL DEFAULT '',
    published  INTEGER NOT NULL DEFAULT 0 CHECK (published IN (0, 1)),
    view_count INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL DEFAULT (unixepoch()),
    updated_at INTEGER NOT NULL DEFAULT (unixepoch()),

    UNIQUE (author_id, slug),
    FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE CASCADE
) STRICT;

-- 索引（虽然 UNIQUE 已经建了索引，业务查询可能还需要）
CREATE INDEX IF NOT EXISTS idx_posts_author       ON posts(author_id);
CREATE INDEX IF NOT EXISTS idx_posts_created_at   ON posts(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_posts_published    ON posts(published);
```

### 3.11.2 Flutter 代码

上一章的 `db.dart` 升级：

```dart
import 'package:path/path.dart' as p;
import 'package:path_provider/path_provider.dart';
import 'package:sqflite/sqflite.dart';

class AppDb {
  static Database? _instance;

  static Future<Database> get instance async =>
      _instance ??= await _open();

  static Future<Database> _open() async {
    final dir = await getApplicationDocumentsDirectory();
    final dbPath = p.join(dir.path, 'blog.db');

    return openDatabase(
      dbPath,
      version: 1,
      onConfigure: _onConfigure,
      onCreate: _onCreate,
    );
  }

  /// 每次打开连接都调用 —— 用来开启外键
  static Future<void> _onConfigure(Database db) async {
    await db.execute('PRAGMA foreign_keys = ON;');
  }

  static Future<void> _onCreate(Database db, int version) async {
    // 使用 Batch 一次执行多条 DDL
    final batch = db.batch();

    batch.execute('''
      CREATE TABLE users (
        id         INTEGER PRIMARY KEY,
        username   TEXT    NOT NULL UNIQUE COLLATE NOCASE,
        email      TEXT    NOT NULL UNIQUE,
        avatar_url TEXT,
        bio        TEXT,
        created_at INTEGER NOT NULL DEFAULT (unixepoch()),
        updated_at INTEGER NOT NULL DEFAULT (unixepoch())
      ) STRICT;
    ''');

    batch.execute('''
      CREATE TABLE posts (
        id         INTEGER PRIMARY KEY,
        author_id  INTEGER NOT NULL,
        title      TEXT    NOT NULL,
        slug       TEXT    NOT NULL,
        content    TEXT    NOT NULL DEFAULT '',
        published  INTEGER NOT NULL DEFAULT 0 CHECK (published IN (0, 1)),
        view_count INTEGER NOT NULL DEFAULT 0,
        created_at INTEGER NOT NULL DEFAULT (unixepoch()),
        updated_at INTEGER NOT NULL DEFAULT (unixepoch()),

        UNIQUE (author_id, slug),
        FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE CASCADE
      ) STRICT;
    ''');

    batch.execute('CREATE INDEX idx_posts_author     ON posts(author_id);');
    batch.execute('CREATE INDEX idx_posts_created_at ON posts(created_at DESC);');
    batch.execute('CREATE INDEX idx_posts_published  ON posts(published);');

    await batch.commit(noResult: true);
  }
}
```

**几个 sqflite 的重点**：

1. **`onConfigure` 每次打开连接调用**，是设置 `foreign_keys = ON` 的正确位置。放 `onCreate` 里只有首次创建时生效，跳过 `onCreate` 就没了。
2. **`onCreate` 只在数据库首次创建时调用**。已有数据库要改结构，走 `onUpgrade`（Part 2 迁移章节详解）。
3. **`Batch`** 一次性发多条 SQL，减少 IPC 开销（对 sqflite 而言是 platform channel 开销）。
4. **`STRICT` 关键字** sqflite 完全支持，只要底层 SQLite 版本够。

## 3.12 原理深挖：SQLite 是如何存表结构的？

SQLite 有一张系统表叫 `sqlite_schema`（旧名 `sqlite_master`），存了所有对象的元信息：

```sql
SELECT type, name, tbl_name, sql FROM sqlite_schema;
```

输出大概：

```
table  users              users     CREATE TABLE users (...)
index  idx_posts_author   posts     CREATE INDEX idx_posts_author ON posts(...)
table  posts              posts     CREATE TABLE posts (...)
```

- 每一个用户建的表、索引、视图、触发器，都在 `sqlite_schema` 有一行。
- `sql` 字段直接存的**原始 CREATE 语句**！**这是 SQLite 极其特别的设计**——表结构是"文本 + 解析"，不是"编译后的二进制格式"。
- 好处：数据库文件跨版本兼容极好，只要能解析 SQL 就能读。
- 副作用：**修改结构 = 修改 sqlite_schema 里那段 SQL 文本**（这就是 ALTER TABLE 受限的根本原因，SQLite 不敢在文本级别做太多复杂修改）。

## 3.13 常见坑点

1. **忘开外键**：`PRAGMA foreign_keys = ON;` 每次连接都得设。**用 sqflite 的 `onConfigure`。**
2. **`INT PRIMARY KEY` ≠ `INTEGER PRIMARY KEY`**：只有精确匹配 `INTEGER PRIMARY KEY` 才成为 rowid 别名。`INT` / `BIGINT` 不行！
3. **STRICT 表里 `VARCHAR(255)` 会报错**：STRICT 表只认 6 种类型名。
4. **`AUTOINCREMENT` 性能损耗**：不需要就别加。
5. **CHECK 约束跨列引用**：只能放表级，不能放列级。
6. **`DEFAULT (expr)` 中的表达式必须加括号**：`DEFAULT unixepoch()` 是错的，`DEFAULT (unixepoch())` 才对。
7. **DEFAULT 为函数时的求值时机**：每次插入求值，不是建表时求值一次。
8. **UNIQUE + NULL**：多个 NULL 值不算重复，UNIQUE 列允许多行 NULL。（SQL 标准如此。）
9. **改列类型没有直接语法**：得走 12 步重建。

## 3.14 本章小结

- DDL 是"数据库装修"，房子结构决定后面家具怎么摆。
- 5 种存储类：NULL / INTEGER / REAL / TEXT / BLOB；类型是动态的（除非 STRICT）。
- 主键黄金法则：**`INTEGER PRIMARY KEY`**，99% 场景够用。
- 需要非整数主键 + 高性能主键查询：考虑 **`WITHOUT ROWID`**。
- 想要严格类型：**`STRICT` 表**（3.37+），强烈推荐新项目使用。
- `ALTER TABLE` 只能加/删/改名列，改类型/约束要走 12 步重建。
- 外键**默认关闭**，在 `onConfigure` 里开。
- Flutter 里表结构 DDL 通常放在 `onCreate` 里，用 `Batch` 批量执行。
