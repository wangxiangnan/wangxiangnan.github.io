# 第9章：CSR 与自签名证书：从密钥到证书

> [!TIP] Part 2: 非对称与证书篇（进阶篇）
> Part 2 收官章。密钥会造了、格式认全了、签名会签了，本章把零件组装成第一张证书——走通「密钥 → CSR → 签发」的出生线，并直面那个所有人都遇到过的问题：浏览器为什么不信任自签证书。

api.cloudnote.example 要上 HTTPS 了。经过前八章，你手里的零件已经齐了：一把 EC 私钥（第5章）、对证书字段的完整认知（第8章）。缺的只是「出生」这一步。证书从哪来？本章先走通最容易上手的一条线——**自签名**，把整条出生流程跑通；第10章再把签发者升级成自建的 CA。

## 9.1 证书的三条出生路线

同一把私钥，证书有三条出生路线，区别只在「谁盖的章」：

| 路线 | 谁盖章 | 信任来源 | 适用场景 | 成本 |
| ---- | ---- | ---- | ---- | ---- |
| 公网 CA 签发 | Let's Encrypt 等公共 CA | 操作系统预装的信任锚 | 公网网站、对外 API | 免费（Let's Encrypt）到每年几百元 |
| 自建内部 CA | 你自己当 CA（第10章） | 你手动分发并安装的根证书 | 内网服务、服务间 mTLS | 一次建置 + 持续运维 |
| 自签名 | 证书自己给自己盖章 | 没有信任链，逐台手动信任 | 本地开发、一次性测试 | 零 |

本章走第三条。先把它的定位说破：**自签证书的加密强度与 CA 签发的完全相同**——都是同一套算法、同样的 2048/256 位强度。差别只有一个：没有人替它背书，所以每个客户端都要单独被告知「请相信这一张」。理解了这个差别，「浏览器红牌警告」就从玄学变成了逻辑必然。

公网路线有个值得记住的转折点：2015 年底 Let's Encrypt 开始免费签发。在那之前，一张公网证书每年要花几百到几千元，个人开发者与小团队普遍裸奔 HTTP；免费 CA 上线后签发流程彻底自动化（ACME 协议自动验证域名、自动续期），全球 HTTPS 流量占比从约四成一路涨到今天的九成以上。你在《网络协议完全教程》第15章看到的「全网 HTTPS 化」，最大推手就是它。云笔记的公网站点走的也是这条路线。

## 9.2 req：生成 CSR

从私钥到证书，中间隔一张申请表：CSR（Certificate Signing Request，证书签名请求，标准号 PKCS#10）。它把「我要一张证书」所需的材料打包——身份信息 + 公钥 + 一枚自签章。生成命令是 `req`：

```bash
openssl req -new -key api-key.pem \
  -passin file:~/.cloudnote-secrets/KEY_PASS.txt \
  -subj "/C=CN/O=CloudNote/CN=api.cloudnote.example" \
  -addext "subjectAltName=DNS:api.cloudnote.example" \
  -out api.csr
```

参数逐个过：`-new` 新建 CSR；`-key` 指定私钥（加密私钥用 `-passin` 提供口令）；`-subj` 一口气填完身份信息，免去逐项交互问答——格式是斜杠分隔的 `键=值`；`-addext` 附加扩展字段，**SAN 必须在这一步写好**（第8章讲过：现代客户端只认 SAN）。

试试不带 `-subj` 会发生什么：

```bash
openssl req -new -key dev-key.pem
```

`req` 转入交互问答模式，逐项问你：

```text
You are about to be asked to enter information that will be incorporated
into your certificate request.
-----
Country Name (2 letter code) [AU]:CN
State or Province Name (full name) [Some-State]:Shanghai
Locality Name (eg, city) []:Shanghai
Organization Name (eg, company) [Internet Widgits Pty Ltd]:CloudNote
Organizational Unit Name (eg, section) []:API Team
Common Name (e.g. server FQDN or YOUR name) []:api.cloudnote.example
Email Address []:
```

交互模式一次一问，手工造一张无妨；但注意方括号里的默认值——它们来自一个编译进二进制的配置文件（`openssl.cnf`，默认国家是 AU 澳大利亚），网上照抄常抄出一堆澳洲公司。脚本和 CI 里逐问答更不可行，多一次交互就多一次卡住的机会：**自动化场景一律 `-subj`**。

拆开看看 CSR 里装了什么：

```bash
openssl req -in api.csr -noout -text
```

```text
Certificate Request:
    Data:
        Version: 1 (0x0)
        Subject: C=CN, O=CloudNote, CN=api.cloudnote.example
        Subject Public Key Info:
            Public Key Algorithm: id-ecPublicKey
                ...
        Attributes:
            requestedExtensions:
                X509v3 Subject Alternative Name:
                    DNS:api.cloudnote.example
    Signature Algorithm: ecdsa-with-SHA256
```

三个观察，每一个都有深意：

- **CSR 里没有私钥**。公钥上交、私钥自留——申请表的本质是「公示锁，不上交钥匙」，整个体系的安全底线在这张表里就定了。
- **CSR 自带一枚签名**。这枚签名用的是配对私钥，作用是向 CA 证明「提交这张表的人确实持有私钥」——防止有人拿着别人的公钥来冒领证书。
- **SAN 在这里是「请求」不是「承诺」**。最终 SAN 写成什么样，由签发方决定。公网 CA 会核验你对域名的控制权后才批准；自己签发时你就是自己的审核员。

验收 CSR 的完整性用 `-verify`（检查自签章是否有效）：

```bash
openssl req -in api.csr -noout -verify
```

```text
Certificate request self-signature verify OK
```

CSR 不含私钥，本身不敏感——发给 CA、贴工单都安全。但生成 CSR 的**配置**值得当回事：SAN 布局、内部域名清单都在命令与配置文件里，别把内网域名结构随手提交进公开仓库。另一个易错点：CSR 是「一次性门票」，CA 签发后它就完成使命了——不要复用老 CSR 反复签发，每次续期重新生成，顺便把密钥也轮换了。

## 9.3 一条命令自签证书

CSR 准备好，签发本来是 CA 的活——但自签路线里 CA 就是你自己，`req` 用 `-x509` 参数一步到位（跳过 CSR，直接从私钥造证书）：

```bash
openssl req -x509 -new -key api-key.pem \
  -passin file:~/.cloudnote-secrets/KEY_PASS.txt \
  -sha256 -days 90 \
  -subj "/C=CN/O=CloudNote/CN=api.cloudnote.example" \
  -addext "subjectAltName=DNS:api.cloudnote.example" \
  -out api-self.crt
```

与 9.2 的差别只有两处：`-x509` 表示「输出证书而非 CSR」；`-days 90` 设有效期（沿用云笔记的 90 天纪律）。如果你连私钥都还没有，`-newkey` 顺手生成：

```bash
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout dev-key.pem -out dev.crt -sha256 -days 90 \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

`-newkey ec` 指定算法家族、`-nodes` 表示生成的私钥不加密（本地开发钥匙，加密反而碍事）。OpenSSL 3.x 的 `req -x509` 默认会带上 Basic Constraints（`CA:FALSE`）与密钥标识符（SKID/AKID），恰好就是一张合格服务器证书的最小配置——用第8章的 `-text` 验货，确认 SAN 与 `CA:FALSE` 都在：

```bash
openssl x509 -in api-self.crt -noout -text | grep -A1 -E "Alternative|Basic"
```

证书到手后还有一个值得养成的验收动作：确认「签出来的证书用的确实是我这把钥匙」。第6章的公钥指纹法在这里原样适用，只是比对对象换成 CSR 与证书：

```bash
openssl req -in api.csr -noout -pubkey | openssl dgst -sha256
openssl x509 -in api-self.crt -noout -pubkey | openssl dgst -sha256
```

两行一致 → 证书确实封进了这把钥匙的公钥。这个动作在对接外部 CA 时尤其重要：万一提交错了 CSR（比如拿测试环境的表申请了生产域名），指纹一比立刻现形，不用等部署时才报 `key values mismatch`。

## 9.4 浏览器为什么翻脸：信任的经济学

证书造好了，起一个本地 TLS 服务试一把（工具是 `s_server`，第13章还会正式介绍）：

```bash
openssl s_server -www -accept 8443 \
  -cert api-self.crt -key api-key.pem \
  -passin file:~/.cloudnote-secrets/KEY_PASS.txt
```

浏览器访问 `https://localhost:8443`，迎接你的不是小锁，而是一整页红牌警告（`NET::ERR_CERT_AUTHORITY_INVALID`）。这个红牌**不是故障，是体系在正确工作**：浏览器核验证书时的第一问是「Issuer 是谁？我预装的信任锚里有它吗？」——`CloudNote`（自签）不在名单里，红牌合情合理。红牌页面上那个「继续前往」的按钮，本质是你在说「这次我人工信任它」——每台机器、每个浏览器都要点一次，这就是自签的运维成本。

正经的解法按规模分三档：

| 浏览器错误码 | 真实病因 |
| ---- | ---- |
| `ERR_CERT_AUTHORITY_INVALID` | 签发者不在信任锚里——自签/内部 CA 的必然现象 |
| `ERR_CERT_DATE_INVALID` | 证书过期，或本机时间不对（GMT 陷阱第8章见过） |
| `ERR_CERT_COMMON_NAME_INVALID` | 访问的地址不在 SAN 列表里 |
| `ERR_CERT_REVOKED` | 证书被撤销（第11章的 CRL/OCSP） |

| 解法 | 做法 | 适合 |
| ---- | ---- | ---- |
| 命令行单点信任 | `curl --cacert api-self.crt https://localhost:8443/` | 脚本、API 测试 |
| 逐台导入信任库 | 把证书导入 macOS 钥匙串 / Windows 证书管理器 / Linux `update-ca-certificates` | 单个开发者 |
| 本地 CA | 用 mkcert 这类工具生成「本地根证书」并导入，之后签的证书全部被信任 | 团队开发环境 |

第二档与第三档是同一个思想的两个规模：**把你造的证书（或 CA 根证书）塞进客户端的信任锚列表**。mkcert 之所以「一键绿锁」，正是它在后台做了第三档的全部动作。云笔记的做法：第10章自建内部 CA，把**根证书**导入团队成员的信任库——之后 CA 签发的每一张证书自动被信任，这是规模化后的正解。

红牌页面本身也是练习场：点开「连接不安全 → 证书」，用第8章练出的眼睛反看这张证书——Issuer 是你亲手写的 `CloudNote`、有效期 90 天、SAN 列着 `localhost`。浏览器展示的字段与 `openssl x509 -text` 一一对应，这是从消费端回看供给端的一次免费复习。

> [!WARNING] -k 的使用纪律
> `curl -k`（以及各语言的「跳过证书校验」选项）直接放弃验证，红牌问题确实消失了——连同中间人攻击的防线一起消失。它只允许出现在一次性调试里；写进脚本或代码的每一处 `-k` / `InsecureSkipVerify` 都是给攻击者留的后门。需要「校验但换信任锚」时，永远用 `--cacert` 这类参数。

## 9.5 自签与 CA 签发的边界

什么时候自签够用、什么时候必须找 CA？一张边界表定案：

| 场景 | 结论 | 理由 |
| ---- | ---- | ---- |
| 本地开发（localhost） | 自签够用 | 用户只有你自己 |
| 内网固定设备间 | 自签勉强，内部 CA 更好 | 机器一多，逐台信任受不了 |
| 服务间 mTLS（微服务） | 内部 CA | 服务数量增长快，信任要自动化 |
| 公网网站、对外 API | **必须公网 CA** | 用户不会、也不该手动信任你 |

一句话总结边界：**信任的受众超过「你亲手配置的机器清单」，就该升级到 CA**。公网用公共 CA（它们替你完成了域名所有权核验），内网用自建 CA（第10章亲手当一回 CA，把公网体系的工作原理看穿）。

> [!TIP] 公网 CA 验什么：DV、OV、EV
> 向公网 CA 申请证书按核验强度分三档：DV（Domain Validation，只验证你控制该域名，几分钟自动完成，Let's Encrypt 只做这一档）、OV（Organization Validation，额外核验组织真实性）、EV（Extended Validation，最严格的人工审核）。一个常见误解要掰正：**三档的加密强度完全相同**，差别只是 Issuer 栏里组织信息的可信度——EV 证书曾让地址栏变绿，后来浏览器统一取消了特殊展示。日常选 DV 足够，这正是「证书验证的是控制权，不是商业信用」的体现。

## 9.6 实验：本地开发证书三连

Part 2 收官实验，产出云笔记开发环境的正式配具：

```bash
# 1. 生成开发证书（不加密私钥，SAN 覆盖 localhost 与 127.0.0.1）
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout ~/cloudnote/dev/dev-key.pem -out ~/cloudnote/dev/dev.crt \
  -sha256 -days 90 -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"

# 2. 起本地 TLS 服务（后台运行，8443 端口）
openssl s_server -www -accept 8443 \
  -cert ~/cloudnote/dev/dev.crt -key ~/cloudnote/dev/dev-key.pem &

# 3. 验收一：不信任时 curl 翻脸
curl https://localhost:8443/ 2>&1 | head -2

# 4. 验收二：--cacert 指定信任锚后通过
curl --cacert ~/cloudnote/dev/dev.crt https://localhost:8443/ | head -3
```

验收四的输出会是一页服务状态文本（s_server 的标志）。终端里这一路绿灯，浏览器里却要手动点一次「继续前往」——两边的差异正是 9.4 的信任经济学在现实中的样子。实验做完收尾：

```bash
kill %1   # 停掉 s_server
```

实验之外多练一步——**轮换演练**：假设 90 天到期，重新执行第 1 步命令再起一遍 s_server。旧证书被新文件直接覆盖，curl 依旧绿灯（`--cacert` 指向的就是新证书）。这暴露了自签的一个隐藏坑：**覆盖证书文件并不会让旧证书失效**——旧证书在有效期内依然能通过验签，只是你不再用它了。这正是第8章「撤销机制尴尬」的现场重演：轮换的最后一环是停用旧证书——撤下旧进程、回收旧文件，才算闭环。

验收三条：不带 `--cacert` 的 curl 必须报证书错误；带 `--cacert` 的 curl 输出 s_server 状态页；浏览器访问一次并点开证书详情，把字段从头读一遍。

顺带一条纪律：`dev-key.pem` 虽是本地开发钥匙，也照第4章的规矩收进 `~/.cloudnote-secrets/` 或加进 `.gitignore`——本地钥匙泄露的后果轻，但「私钥不进 Git」这条军规没有例外条款。

至此 Part 2 完工。回 ch00 打个勾：**M2（不查文档完成密钥、CSR、自签证书三连）应该已过线**——`genpkey`、`req -new`、`req -x509`、`pkey`、`pkeyutl` 这条链你已经各走过一遍。

带着一个问题进入 Part 3：本章的自签证书是「自己给自己盖章」，Issuer 与 Subject 同名。如果云笔记内网有 30 个服务，难道要给每个服务的证书都挨个发信任库？显然不行——需要一个**只盖一次章就能让 30 张证书全被信任**的东西。它就是 CA，下一章亲手造。

## 本章小结

- 证书三条出生路线：公网 CA（公网场景）、自建内部 CA（内网规模化，第10章）、自签名（本地开发）——**加密强度三者相同，差别只在信任从哪来**
- CSR 是申请表：身份 + 公钥 + 自签章，**没有私钥**；`req -new -subj -addext` 生成，`-verify` 验自签章
- CSR 是一次性门票：签发完成即使命结束，续期时重新生成 CSR 并顺手轮换密钥
- SAN 必须在生成时写好：`-addext "subjectAltName=DNS:...,IP:..."`；现代客户端只认 SAN
- `req -x509` 一条命令自签：`-days` 定有效期，3.x 默认自带 `CA:FALSE` 与 SKID/AKID
- 浏览器红牌是体系正确工作的表现：解法按规模升级——`--cacert` 单点信任、导入信任库、本地 CA；`-k` 只许一次性调试
- 证书、CSR、私钥的配对用公钥指纹法验收：`req -pubkey` 与 `x509 -pubkey` 的指纹一致才算「钥匙封进了卡」
- 交互问答模式只适合手工造一张：默认值来自 `openssl.cnf`（默认国家 AU），自动化场景一律 `-subj`
- 续期 = 重新生成 + 重启服务；覆盖文件不会让旧证书失效，轮换要连「停用旧证书」一起做完
- 边界一句话：信任受众超出「你亲手配置的机器清单」，就该上 CA
