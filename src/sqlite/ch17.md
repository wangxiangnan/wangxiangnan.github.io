# 第17章：备份、恢复与数据迁移

## 17.1 引言：数据丢了，你就是"事故"本身

程序员的一天分三种：

1. 一切正常，喝咖啡
2. Bug频出，改代码
3. **数据丢了**，写辞职信

有一句古老的Unix名言：

> "There are two types of people in the world: those who have lost data, and those who will."
>
> 世界上有两种人：**丢过数据的**，和**将要丢数据的**。

前面章节我们讨论了各种"让SQLite更强大"的话题。这一章我们讨论"**让SQLite的数据不会消失**"——备份、恢复、迁移。这可能是你**最不希望需要**、但**一旦需要就万分感激**的一章。

## 17.2 SQLite文件损坏的场景

在讨论备份前，先看看什么情况会让你的.db文件损坏：

### 17.2.1 物理层原因

- **磁盘坏道**：机械硬盘老化，SSD写入次数用尽
- **突然断电**（且没开WAL或journal）
- **强制拔U盘**、强制关手机
- **文件系统崩溃**

### 17.2.2 SQLite使用不当

- **多进程同时写**且没用适当锁机制
- **网络文件系统**（NFS/SMB）上放SQLite数据库——臭名昭著地容易损坏
- **在OS层复制正在写入的数据库**——可能得到"半熟"的数据库
- **进程崩溃且rollback journal被误删**

### 17.2.3 应用bug

- 应用崩溃时正好在写入
- 事务中途异常没rollback
- 手动改了数据库内部页导致校验和错误

**核心结论：备份不是"以防万一"，是"迟早会用到"。**

## 17.3 三种备份方案对比

| 方案 | 需要停机 | 支持WAL | 简单度 | 用途 |
| ------ | ---------- | --------- | -------- | ------ |
| 拷贝文件 | 是（或很小心） | 麻烦 | ★★★★★ | 冷备份 |
| .backup / VACUUM INTO | 否 | 是 | ★★★★ | 在线备份 |
| .dump / SQL转储 | 否 | 是 | ★★★ | 跨版本迁移 |

## 17.4 方案1：拷贝文件

最直觉的方法：把.db文件复制到另一个地方。

```bash
# Linux/macOS
cp mydata.db mydata.db.backup

# Windows
copy mydata.db mydata.db.backup
```

**问题**：如果应用正在写数据库，你复制到一半，可能得到一个损坏文件。**必须保证复制时没有写入**。

### 17.4.1 安全拷贝：先加锁

```sql
BEGIN IMMEDIATE;   -- 或 BEGIN EXCLUSIVE
-- 此时其他进程不能写
-- 在OS层复制文件
COMMIT;            -- 释放锁
```

在Dart里：

```dart
await db.transaction((txn) async {
  // 事务中，其他进程/线程不能写
  // 在这里做OS级文件拷贝
  await File('mydata.db').copy('mydata.db.backup');
});
// 事务结束后其他人可以写了
```

**WAL模式下的额外考虑**：WAL模式的数据库其实是**两个文件**——`mydata.db`和`mydata.db-wal`（甚至还有`-shm`）。只复制`.db`会漏掉最近的写入。

正确做法：先checkpoint把WAL合并回主库，再复制：

```sql
PRAGMA wal_checkpoint(TRUNCATE);  -- 把WAL全并回主库并清空
-- 然后复制 mydata.db
```

## 17.5 方案2：在线备份API（.backup）

SQLite提供**在线备份API**（Online Backup API），可以在数据库运行时安全备份，甚至可以跨越两个不同的连接。

### 17.5.1 命令行

```bash
# 使用SQLite命令行工具
sqlite3 mydata.db ".backup 'mydata.db.backup'"

# 或者交互模式
$ sqlite3 mydata.db
sqlite> .backup mydata.db.backup
```

背后调用的就是`sqlite3_backup_init`系列API。

### 17.5.2 编程接口（C）

```c
sqlite3 *src, *dst;
sqlite3_open("mydata.db", &src);
sqlite3_open("mydata.db.backup", &dst);

sqlite3_backup *backup = sqlite3_backup_init(dst, "main", src, "main");
if (backup) {
    sqlite3_backup_step(backup, -1);  // -1 = 一次性拷贝所有页
    sqlite3_backup_finish(backup);
}
sqlite3_close(dst);
sqlite3_close(src);
```

或者**分批拷贝**（避免长时间锁定源库）：

```c
sqlite3_backup_step(backup, 100);  // 每次拷100页
sqlite3_sleep(250);                // 睡250ms
sqlite3_backup_step(backup, 100);
// ...
```

分批拷贝时，如果源库被修改，SQLite会自动**重启**备份（丢弃已拷贝的，重来）。所以繁忙数据库上分批备份可能拖很久。

### 17.5.3 备份API的优点

- **在线**：不停机、不锁死其他连接
- **一致性**：得到的备份是一个原子快照
- **WAL友好**：自动处理WAL文件
- **可跨版本**：源和目标可以是不同SQLite版本
- **可跨连接**：内存库→文件、文件→内存都行

### 17.5.4 定期备份的策略

```bash
#!/bin/bash
# 每小时备份，保留最近24小时
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
sqlite3 /path/to/app.db ".backup '/backups/app_${TIMESTAMP}.db'"

# 删除24小时前的备份
find /backups -name "app_*.db" -mtime +1 -delete
```

## 17.6 VACUUM INTO：备份的新姿势

从**SQLite 3.27（2019）**开始，有了`VACUUM INTO`命令：

```sql
VACUUM INTO 'mydata.db.backup';
```

**它做了两件事**：

1. 备份到新文件
2. **同时VACUUM**——新文件是**紧凑**的，没有碎片

对比：

- `.backup`：保留原始页面布局（快）
- `VACUUM INTO`：重建、紧凑（慢，但输出更小）

**推荐**：定期用`VACUUM INTO`做"完全备份"，日常用`.backup`做"快速备份"。

## 17.7 VACUUM：磁盘空间回收

顺便讲讲VACUUM本身。SQLite的数据文件**只增不减**（默认）——你删了1GB数据，文件还是那么大，删的空间标记为可复用。

要真正把磁盘还给操作系统：

```sql
VACUUM;
```

VACUUM过程：

1. 创建一个新的临时数据库
2. 把当前库的所有数据按顺序写入新库（自动整理）
3. 用新库替换旧库

**开销**：

- 需要**接近2倍**的磁盘空间（临时）
- **加锁**：VACUUM期间数据库被独占
- **慢**：数据量大时几秒到几分钟

**什么时候需要VACUUM？**

- 删除了大量数据后想回收空间
- 数据库长期使用后碎片化严重
- 用了`auto_vacuum`但没达到理想效果

### 17.7.1 auto_vacuum：自动回收

```sql
-- 建库时设置
PRAGMA auto_vacuum = FULL;    -- 或 INCREMENTAL 或 NONE

-- FULL: 每次DELETE后自动回收（有性能开销）
-- INCREMENTAL: 手动触发 PRAGMA incremental_vacuum
-- NONE: 不自动回收（默认）
```

**注意**：`auto_vacuum`只能在**建库时**或**空数据库**上设置。已经有数据的库要改，得先VACUUM。

## 17.8 方案3：SQL转储（.dump）

SQL转储把整个数据库导出为CREATE + INSERT语句：

```bash
sqlite3 mydata.db .dump > backup.sql

# 恢复
sqlite3 new.db < backup.sql
```

生成的.sql文件是**纯文本**，类似：

```sql
PRAGMA foreign_keys=OFF;
BEGIN TRANSACTION;
CREATE TABLE users(id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO users VALUES(1,'Alice');
INSERT INTO users VALUES(2,'Bob');
CREATE INDEX idx_users_name ON users(name);
COMMIT;
```

### 17.8.1 SQL转储的优势

- **人类可读**：能用文本编辑器打开、grep、修改
- **跨版本兼容**：SQLite 3.6导出的.sql，能在SQLite 3.45导入
- **跨数据库迁移**：稍加修改能导入MySQL/Postgres
- **可版本控制**：把schema.sql放Git里

### 17.8.2 SQL转储的缺点

- **慢**：INSERT一条条执行
- **文件大**：文本膨胀
- **可能不完整**：某些SQLite特性（比如VACUUM设置）不会导出

### 17.8.3 只dump某些表/schema

```bash
# 只dump users表
sqlite3 mydata.db ".dump users" > users.sql

# 只dump schema，不dump数据
sqlite3 mydata.db ".schema" > schema.sql

# dump为INSERT（默认）还是CSV？
sqlite3 -csv mydata.db "SELECT * FROM users" > users.csv
```

## 17.9 WAL模式下的备份考虑

WAL模式的备份需要特别小心。WAL模式的写入实际写到`.db-wal`文件，`.db`文件只在checkpoint时才更新。

### 17.9.1 WAL备份的正确姿势

**方式1：用备份API**（自动处理）：

```sql
-- 命令行
.backup backup.db

-- API会正确处理WAL
```

**方式2：先checkpoint再拷贝**：

```sql
PRAGMA wal_checkpoint(TRUNCATE);  -- 强制把WAL并回主库
-- 然后拷贝 .db 文件
```

**方式3：把三个文件一起拷贝**（最保险但最麻烦）：

- `mydata.db`
- `mydata.db-wal`
- `mydata.db-shm`

## 17.10 数据导入导出

### 17.10.1 CSV导入导出

```sql
-- 导出到CSV
.headers on
.mode csv
.output users.csv
SELECT * FROM users;
.output stdout

-- 从CSV导入
.mode csv
.import users.csv users_new
-- （users_new会自动创建，第一行作为列名）
```

在程序里：

```dart
// Dart示例：导出为CSV
Future<void> exportToCsv(Database db, String path) async {
  final rows = await db.query('users');
  final buffer = StringBuffer();
  
  if (rows.isEmpty) return;
  
  // 表头
  buffer.writeln(rows.first.keys.join(','));
  
  // 数据行
  for (final row in rows) {
    buffer.writeln(row.values.map((v) => 
      v is String ? '"${v.replaceAll('"', '""')}"' : v.toString()
    ).join(','));
  }
  
  await File(path).writeAsString(buffer.toString());
}
```

### 17.10.2 JSON导入导出

## 17.12 版本升级迁移：drift的MigrationStrategy

App发版了1.0，用了一段时间要发2.0，schema变了怎么办？直接改建表SQL？那老用户的数据全没了。**Schema迁移**是必须的。

drift提供了`MigrationStrategy`：

```dart
@DriftDatabase(tables: [Users, Posts])
class AppDatabase extends _$AppDatabase {
  AppDatabase() : super(_openConnection());
  
  @override
  int get schemaVersion => 3;  // 每次改schema就+1
  
  @override
  MigrationStrategy get migration => MigrationStrategy(
    // 全新安装：直接创建最新schema
    onCreate: (m) async {
      await m.createAll();
    },
    
    // 升级：从旧版逐步升到新版
    onUpgrade: (m, from, to) async {
      if (from < 2) {
        // 1 -> 2：给users表加email列
        await m.addColumn(users, users.email);
        
        // 或用原始SQL
        await customStatement('UPDATE users SET email = ? WHERE id = ?', 
                              ['unknown@example.com', 1]);
      }
      
      if (from < 3) {
        // 2 -> 3：新增posts表
        await m.createTable(posts);
        
        // 数据迁移：把老的meta字段拆到JSON
        final oldRows = await customSelect('SELECT * FROM users').get();
        for (final row in oldRows) {
          final meta = row.data['legacy_meta'] as String?;
          if (meta != null) {
            await customStatement(
              "UPDATE users SET profile = json_object('meta', ?) WHERE id = ?",
              [meta, row.data['id']],
            );
          }
        }
      }
    },
    
    // 打开数据库前的回调（每次都执行）
    beforeOpen: (details) async {
      await customStatement('PRAGMA foreign_keys = ON');
      
      if (details.wasCreated) {
        // 全新库，插入种子数据
        await into(users).insert(UsersCompanion.insert(name: 'admin'));
      }
    },
  );
}
```

### 17.12.1 迁移最佳实践

1. **永远只加不删**：老版本app可能还在跑，删列会让老版本崩
2. **给新列设DEFAULT**：不然UPDATE老数据时报错
3. **在事务里迁移**：确保原子性
4. **备份再升级**：迁移前先.backup
5. **测试！测试！测试**：模拟从每个历史版本升级

```dart
// 测试迁移
test('migrates from v2 to v3', () async {
  // 用sqlite3包直接创建v2 schema的数据库
  final db = sqlite3.openInMemory();
  db.execute('''
    CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, email TEXT);
  ''');
  db.execute("INSERT INTO users VALUES (1, 'Alice', 'a@b.com')");
  db.dispose();
  
  // 用当前版本代码打开，触发迁移
  final drift = AppDatabase(NativeDatabase.opened(db));
  
  // 验证：新表存在，老数据保留
  final users = await drift.select(drift.users).get();
  expect(users.length, 1);
  expect(users.first.name, 'Alice');
});
```

### 17.12.2 复杂迁移：用中间表

有时候要改列类型或约束，SQLite不支持直接ALTER。**12步安全迁移**：

```sql
-- 假设要给users表的name列加NOT NULL
BEGIN TRANSACTION;

-- 1. 创建新表
CREATE TABLE users_new (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT
);

-- 2. 拷贝数据（填充NULL的name为默认值）
INSERT INTO users_new(id, name, email)
SELECT id, COALESCE(name, 'unknown'), email FROM users;

-- 3. 删掉旧表
DROP TABLE users;

-- 4. 重命名新表
ALTER TABLE users_new RENAME TO users;

-- 5. 重建索引/触发器
CREATE INDEX idx_users_name ON users(name);

COMMIT;
```

drift的`m.alterTable(TableMigration(users, ...))`能自动做这些事。

## 17.13 从其他DB迁移到SQLite

### 17.13.1 从MySQL迁移

MySQL和SQLite的方言有差异，直接dump导入不行：

```bash
# 1. MySQL dump
mysqldump -u root db_name --compact --no-create-info > data.sql

# 2. 转换（写脚本或用工具）
# - AUTO_INCREMENT → AUTOINCREMENT
# - ENGINE=InnoDB → 删除
# - TINYINT(1) → INTEGER
# - DATETIME → TEXT或INTEGER

# 3. 导入
sqlite3 mydata.db < converted.sql
```

或者用`mysql2sqlite`脚本（GitHub有开源实现）。

**推荐流程**：

1. 在SQLite里手动创建目标schema
2. 用Python/Node.js脚本从MySQL读数据、写SQLite
3. 用**事务**批量插入（10000条一批）

```python
import mysql.connector, sqlite3

mysql_conn = mysql.connector.connect(...)
sqlite_conn = sqlite3.connect('output.db')

mysql_cur = mysql_conn.cursor(dictionary=True)
sqlite_cur = sqlite_conn.cursor()

mysql_cur.execute("SELECT * FROM users")

sqlite_cur.execute("BEGIN")
batch = []
for row in mysql_cur:
    batch.append((row['id'], row['name'], row['email']))
    if len(batch) >= 10000:
        sqlite_cur.executemany(
            "INSERT INTO users VALUES (?, ?, ?)", batch)
        batch.clear()
if batch:
    sqlite_cur.executemany(
        "INSERT INTO users VALUES (?, ?, ?)", batch)
sqlite_conn.commit()
```

## 17.14 数据完整性检查

### 17.14.1 integrity_check

```sql
PRAGMA integrity_check;
-- 如果没问题，返回一行 "ok"
-- 有问题，会列出所有错误
```

**做了什么？**

- 检查每一页的B-Tree结构是否正确
- 检查索引是否与表数据一致
- 检查唯一约束、外键（如果开启了）
- 检查记录是否损坏

**代价**：**扫描整个数据库**。大库上可能几分钟。

### 17.14.2 quick_check

`quick_check`是`integrity_check`的简化版，不检查索引一致性，快得多：

```sql
PRAGMA quick_check;
```

**建议**：

- 应用启动时跑一次`quick_check`
- 定期（每天/每周）跑一次完整`integrity_check`
- 备份前后各跑一次做对比

### 17.14.3 foreign_key_check

```sql
PRAGMA foreign_key_check;
```

专门检查外键约束是否有孤立引用。有问题时返回：

```
表名 | rowid | 引用的表 | 外键索引
```

## 17.15 损坏修复

### 17.15.1 .recover命令

**SQLite 3.31+** 的CLI提供了`.recover`命令，能从损坏的数据库里尽可能救出数据：

```bash
sqlite3 corrupted.db .recover > recovered.sql
sqlite3 new.db < recovered.sql
```

`.recover`的原理：

1. 扫描所有页面
2. 尽力解析出行数据
3. 忽略损坏的部分
4. 输出为SQL语句

不保证100%恢复，但通常能救出大部分数据。

### 17.15.2 dump/reload方案

如果`.recover`不可用（老版本），用`.dump`加`ignore-errors`：

```bash
# 老方案：容忍错误dump
sqlite3 corrupted.db
.output backup.sql
.dump  
-- 可能中途报错，但输出的部分是有效的

sqlite3 new.db < backup.sql
```

### 17.15.3 预防胜于治疗

- **打开WAL模式**：`PRAGMA journal_mode = WAL`
- **同步级别**：`PRAGMA synchronous = NORMAL`（WAL下够用）或`FULL`
- **定期备份**：至少每天一次
- **验证备份**：备份完立刻打开一次做integrity_check
- **多份备份**：本地+云端

## 17.16 Flutter实战：应用内导入/导出数据库

用户想把数据备份到云盘，或者从旧手机迁移到新手机——App里应该提供导入/导出功能。

```dart
import 'package:sqflite/sqflite.dart';
import 'package:path/path.dart' as p;
import 'package:path_provider/path_provider.dart';
import 'package:share_plus/share_plus.dart';
import 'package:file_picker/file_picker.dart';

class BackupManager {
  final Database db;
  final String dbFileName;
  
  BackupManager({required this.db, required this.dbFileName});
  
  /// 导出数据库到外部存储，返回文件路径
  Future<String> exportDatabase() async {
    // 1. 关闭WAL（合并到主库）
    await db.execute('PRAGMA wal_checkpoint(TRUNCATE)');
    
    // 2. 获取应用文档目录
    final appDir = await getApplicationDocumentsDirectory();
    final srcPath = p.join(appDir.path, dbFileName);
    
    // 3. 复制到临时目录以便分享
    final tempDir = await getTemporaryDirectory();
    final ts = DateTime.now().toIso8601String().replaceAll(':', '-');
    final backupPath = p.join(tempDir.path, 'backup_$ts.db');
    
    // 4. 用VACUUM INTO获得紧凑的备份
    // 注意：VACUUM INTO需要在db对象上执行，且路径要转义
    await db.execute("VACUUM INTO ?", [backupPath]);
    
    // 5. 检查完整性
    final checkResult = await db.rawQuery('PRAGMA integrity_check');
    final ok = checkResult.first.values.first == 'ok';
    if (!ok) {
      throw Exception('Database integrity check failed');
    }
    
    return backupPath;
  }
  
  /// 分享备份文件（调用系统分享面板）
  Future<void> shareBackup() async {
    final path = await exportDatabase();
    await Share.shareXFiles(
      [XFile(path)],
      subject: 'MyApp Database Backup',
    );
  }
  
  /// 从用户选择的文件导入数据库
  Future<void> importDatabase() async {
    // 1. 让用户选文件
    final result = await FilePicker.platform.pickFiles(
      type: FileType.custom,
      allowedExtensions: ['db', 'sqlite'],
    );
    if (result == null || result.files.single.path == null) return;
    
    final importPath = result.files.single.path!;
    
    // 2. 验证是否是合法SQLite
    Database? testDb;
    try {
      testDb = await openDatabase(importPath, readOnly: true);
      final check = await testDb.rawQuery('PRAGMA integrity_check');
      if (check.first.values.first != 'ok') {
        throw Exception('Corrupted database');
      }
      
      // 检查版本兼容性（比如通过version表或user_version pragma）
      final version = await testDb.rawQuery('PRAGMA user_version');
      final v = version.first.values.first as int;
      if (v > _maxSupportedVersion) {
        throw Exception('Database version $v is newer than supported');
      }
    } finally {
      await testDb?.close();
    }
    
    // 3. 关闭当前数据库
    await db.close();
    
    // 4. 备份当前数据库（以防导入失败）
    final appDir = await getApplicationDocumentsDirectory();
    final currentPath = p.join(appDir.path, dbFileName);
    final currentFile = File(currentPath);
    
    if (await currentFile.exists()) {
      await currentFile.rename('$currentPath.before_import');
    }
    
    // 5. 复制新数据库
    await File(importPath).copy(currentPath);
    
    // 6. 重新打开，让drift/sqflite触发迁移逻辑
    // ... 调用你的 openDatabase 逻辑
  }
  
  static const int _maxSupportedVersion = 3;
}
```

## 17.17 应用启动时的健康检查

生产App里，每次启动做一次快速健康检查：

```dart
Future<Database> openDbSafely(String path) async {
  Database? db;
  try {
    db = await openDatabase(path);
    
    // 快速完整性检查
    final result = await db.rawQuery('PRAGMA quick_check');
    if (result.first.values.first != 'ok') {
      await db.close();
      throw DatabaseCorruptionException();
    }
    
    return db;
  } on DatabaseCorruptionException {
    // 尝试恢复：先备份损坏文件，再尝试恢复
    await File(path).rename('$path.corrupted');
    
    // 尝试从最近的自动备份恢复
    final autoBackup = File('$path.auto_backup');
    if (await autoBackup.exists()) {
      await autoBackup.copy(path);
      return await openDatabase(path);
    }
    
    // 没备份就重建
    return await openDatabase(path);
  }
}

class DatabaseCorruptionException implements Exception {}
```

### 17.17.1 定期自动备份

```dart
class AutoBackup {
  final Database db;
  final Duration interval;
  final int keepCount;
  Timer? _timer;
  
  AutoBackup({
    required this.db,
    this.interval = const Duration(hours: 6),
    this.keepCount = 5,
  });
  
  void start() {
    _timer = Timer.periodic(interval, (_) => _doBackup());
  }
  
  void stop() {
    _timer?.cancel();
  }
  
  Future<void> _doBackup() async {
    try {
      final dir = await getApplicationDocumentsDirectory();
      final backupDir = Directory(p.join(dir.path, 'backups'));
      if (!await backupDir.exists()) {
        await backupDir.create();
      }
      
      final ts = DateTime.now().millisecondsSinceEpoch;
      final backupPath = p.join(backupDir.path, 'auto_$ts.db');
      
      await db.execute("VACUUM INTO ?", [backupPath]);
      
      // 清理老备份
      final files = await backupDir.list()
          .where((e) => e.path.endsWith('.db'))
          .toList();
      files.sort((a, b) => b.path.compareTo(a.path));  // 新的在前
      
      if (files.length > keepCount) {
        for (int i = keepCount; i < files.length; i++) {
          await files[i].delete();
        }
      }
    } catch (e) {
      // 备份失败不影响应用运行
      print('Auto backup failed: $e');
    }
  }
}
```

## 17.19 常见坑点

### 坑1：拷贝正在使用的.db

前面反复强调：OS级拷贝正在写入的数据库=拷坏。用`.backup`或先关闭数据库。

### 坑2：VACUUM在事务内

`VACUUM`不能在事务内执行，必须在自动提交模式下。

### 坑3：迁移不测试就上线

改了schema，代码在开发机上跑通了就发版——用户升级App后崩溃/数据丢失。**必须**用真实的老版本数据库做迁移测试。

### 坑4：忘了备份WAL文件

只备份.db，忘了.db-wal，导致丢失最近的写入。用`.backup`或先checkpoint。

### 坑5：备份路径不可写

Android上应用只能写自己的沙盒目录。分享出去要用`share_plus`之类的插件走系统分享通道。iOS更严，得走文件分享/iCloud接口。

### 坑6：备份文件泄露隐私

数据库里可能有用户密码、token。分享/上传前**加密**：

```dart
// 用sqlcipher或者应用层AES加密.db文件
final encrypted = await encryptFile(backupPath, userPassword);
await Share.shareXFiles([XFile(encrypted)]);
```

### 坑7：迁移中崩溃

如果迁移到一半App崩了，数据库可能处于不一致状态。**一定用事务包裹整个迁移**，让它要么全成功要么全回滚。drift的MigrationStrategy默认就在事务里。

### 坑8：把user_version搞错

drift用`user_version` PRAGMA记录当前schema版本。**手动改这个字段会导致迁移逻辑错乱**。除非你完全清楚自己在做什么，别碰它。

## 17.21 本章小结

- SQLite的数据不是天然安全的——**备份是必需的**
- 三种备份方案：
  - **拷贝文件**：简单，但要注意锁定和WAL
  - **`.backup` / 备份API**：在线、安全、推荐
  - **`.dump` / SQL转储**：文本、跨版本、慢
- **`VACUUM INTO`** 是备份+紧凑的一步搞定
- **`PRAGMA integrity_check`** 定期跑，发现问题
- **`.recover`** 命令能救回损坏数据库的大部分数据
- Schema迁移用drift的**MigrationStrategy**，测试再测试
- 从其他DB迁移到SQLite：手写脚本 + 批量事务是稳妥的选择
- Flutter App里提供**导入导出功能**是良好的用户体验
