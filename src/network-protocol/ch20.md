# 第20章：QUIC 与 HTTP/3——从 TCP 到 UDP 的跨越

## TCP 的局限：为什么需要换掉 TCP？

TCP 用了四十多年，是个了不起的协议。但它有几个根深蒂固的问题，对于现代 Web 来说越来越致命：

**1. TCP 层的队头阻塞。** 这是 HTTP/2 无法解决的。TCP 保证字节流的有序交付，一旦某个包丢失，后续所有数据都要等重传。假设 Stream 3 的某个包丢了，Stream 5 和 Stream 7 的数据即使已经完整到达，也无法交付给应用层——它们必须等 Stream 3 的包补上。

**2. 握手延迟。** TCP 三次握手（1 RTT）+ TLS 1.3 握手（1 RTT）= 2 RTT 才能开始传数据。对于跨洋连接，一个 RTT 可能就是 200ms，用户还没看到第一个字节就已经等了 400ms。

**3. 连接迁移困难。** TCP 连接由四元组（源IP、源端口、目的IP、目的端口）标识。当你的手机从 WiFi 切到 4G，IP 变了，连接就断了——所有数据要重新建立连接、重新握手。

## QUIC 的设计选择：为什么是 UDP？

Google 的工程师面对这些问题，做了一个大胆决定：**不用 TCP，基于 UDP 重新造轮子**。

为什么不在 TCP 上改？因为 TCP 是内核实现的，改 TCP 需要更新全球数十亿设备的操作系统内核——这不现实。而 UDP 是"最薄的传输层"，几乎不做任何事情。在 UDP 之上构建新的传输逻辑，只需在用户空间实现，无需修改内核。

QUIC（Quick UDP Internet Connections）在 UDP 之上加了：

- 可靠传输（选择性重传，而非 TCP 的有序重传）
- 拥塞控制
- 加密（内置 TLS 1.3）
- 流多路复用（每个流独立的丢包恢复）

**关键区别：** TCP 的丢包恢复影响整个连接，QUIC 的丢包恢复只影响单个流。Stream 3 丢了包？只有 Stream 3 重传，Stream 5 和 7 照常交付。这就是 QUIC 解决队头阻塞的核心机制。

## QUIC 的内置加密：比 TLS 更早的安全

QUIC 的设计中，**几乎所有内容都是加密的**——包括大部分包头。传统 TCP+TLS 中，TCP 包头是明文可见的，中间设备可以观察到序列号、确认号等信息。QUIC 把这些也加密了，中间设备只能看到 UDP 包头和 QUIC 的连接 ID。

这不仅是隐私保护，还防止了**协议僵化（Protocol Ossification）**——中间设备因为看不懂加密内容，就无法基于特定字段的值来做"优化"或拦截，从而保持了网络的端到端特性。

## 0-RTT 连接建立：比 TCP+TLS 快在哪

```
TCP + TLS 1.3:
  Client → Server: SYN                  (1/3 RTT)
  Server → Client: SYN-ACK
  Client → Server: ACK + ClientHello    (2/3 RTT)
  Server → Client: ServerHello + ...
  Client → Server: Finished             (3/3 RTT)
  → 可以发送应用数据（总计约 2 RTT）

QUIC（首次连接）:
  Client → Server: Initial (ClientHello + 加密参数 + 第一个请求)
  Server → Client: Handshake + 响应
  → 可以发送应用数据（总计约 1 RTT）

QUIC（0-RTT 重连）:
  Client → Server: 0-RTT 数据（直接带上之前的会话密钥加密的请求）
  → 0 RTT 即可发送数据！
```

0-RTT 的实现原理：客户端缓存了上次连接的传输参数和密钥材料。重连时，直接用这些材料加密并发送数据。服务器验证通过后，数据已经被处理了。当然，0-RTT 数据有重放攻击风险，需要应用层做幂等性保护。

## 连接迁移：Connection ID 取代四元组

TCP 用四元组标识连接，网络切换就断。QUIC 引入了 **Connection ID**——一个由通信双方协商的标识符，与 IP 地址无关。

当你从 WiFi 切到 4G，IP 地址变了，但 Connection ID 没变。QUIC 客户端用同一个 Connection ID 继续通信，服务器识别出这是同一个连接，无缝继续。

```
WiFi 场景:
  Client (192.168.1.100:54321) → Server (93.184.216.34:443)
  Connection ID: 0x3a7f2c91

切换到 4G:
  Client (10.45.67.89:12345) → Server (93.184.216.34:443)
  Connection ID: 0x3a7f2c91  ← 同一个 ID，连接继续
```

## HTTP/3：在 QUIC 上运行 HTTP

HTTP/3 本质上是 HTTP/2 语义在 QUIC 传输层上的映射：

| HTTP/2 概念 | HTTP/3 对应 |
| --- | --- |
| TCP 连接 | QUIC 连接 |
| Stream | QUIC Stream（每个方向独立） |
| HEADERS 帧 | HEADERS 帧（QPACK 压缩） |
| HPACK 头部压缩 | QPACK（避免队头阻塞的头部压缩） |

QPACK 是 HPACK 的改进版。HPACK 依赖头部按序到达来维护字典状态，但 QUIC 的流可以乱序交付，所以 QPACK 允许头部在独立的流上传输，避免了头部压缩导致的队头阻塞。

## HTTP/1.1 → HTTP/2 → HTTP/3 的演进逻辑

```
HTTP/1.1: 文本协议，单路复用 → 多连接弥补
HTTP/2:   二进制帧，多路复用 → 但 TCP 层仍然队头阻塞
HTTP/3:   QUIC on UDP → 彻底解决队头阻塞 + 0-RTT + 连接迁移
```

每一代的改进都在解决上一代遗留的最痛问题，同时保持 HTTP 语义（请求、响应、头部、方法）不变。这就是为什么我们还在叫它"HTTP"——应用层协议没变，变的是传输层。

## 编程实践：测试 HTTP/3

```bash
# 使用支持 HTTP/3 的 curl 测试
# 需要 curl 编译时启用了 HTTP/3 支持
curl --http3 https://cloudflare-quic.com/ -v

# 对比不同版本的延迟
echo "=== HTTP/1.1 ==="
curl -o /dev/null -s -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" \
  --http1.1 https://www.google.com

echo "=== HTTP/2 ==="
curl -o /dev/null -s -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" \
  --http2 https://www.google.com

echo "=== HTTP/3 ==="
curl -o /dev/null -s -w "DNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" \
  --http3 https://www.google.com
```

你会观察到 HTTP/3 的 `time_connect` 和 `time_appconnect` 明显更短，因为 QUIC 握手比 TCP+TLS 更快。

## 抓包实践：对比 QUIC 与 TLS 1.3 握手

捕获 QUIC 流量需要注意：QUIC 运行在 UDP 端口 443 上。在 Wireshark 中使用过滤器 `quic` 或 `udp.port == 443`。

**QUIC 握手观察要点：**

1. 客户端发送 `Initial` 包（包含 ClientHello），包大小通常 ≥ 1200 字节（QUIC 要求 Initial 包至少 1200 字节，防止放大攻击）。
2. 服务器回复 `Handshake` 包（包含 ServerHello、证书等）。
3. 客户端发送 `Handshake Finished`，同时可能已经带上 0-RTT 应用数据。
4. 观察包头的 `DCID`（Destination Connection ID）和 `SCID`（Source Connection ID）字段。

**对比 TLS 1.3 over TCP：**

```bash
# 分别抓取 HTTP/2 (TCP+TLS) 和 HTTP/3 (QUIC) 的握手
tshark -i eth0 -f "tcp port 443" -w tcp_tls.pcap -c 100
tshark -i eth0 -f "udp port 443" -w quic.pcap -c 100
```

你会看到 TCP+TLS 的握手至少需要 5-6 个包交换（SYN、SYN-ACK、ACK、ClientHello、ServerHello、Finished），而 QUIC 只需 2-3 个包。
