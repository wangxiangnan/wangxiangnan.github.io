# 第3章：Workflow 核心概念

## 引言：用做菜理解一切

如果前两个章节是"认识食材和厨具"，那从这一章开始，我们要正式"下厨做菜"了。

GitHub Actions 的世界里有六个核心概念，听起来很多，但如果用"做菜"来类比，一切就清晰了：

| GitHub Actions 概念 | 做菜类比 |
|---------------------|----------|
| **Workflow（工作流）** | 整份菜谱 |
| **Event（事件）** | 什么时候开始做饭（比如"客人下单了"） |
| **Job（作业）** | 菜谱里的一道菜 |
| **Step（步骤）** | 做这道菜的具体步骤 |
| **Runner（运行器）** | 厨房（提供灶台、锅碗瓢盆） |
| **Action（动作）** | 预制菜 / 半成品（省得你从零切菜） |

下面我们逐个展开讲。

## 3.1 Workflow（工作流）= 整份菜谱

Workflow 是 GitHub Actions 的顶层概念，它是一个定义在 `.github/workflows/` 目录下的 `.yml` 文件。

一个仓库可以有**多个** Workflow 文件——就像一个餐厅有好多份菜谱，川菜一份、粤菜一份、甜品一份。

```
my-project/
├── .github/
│   └── workflows/
│       ├── ci.yml          # CI 工作流：跑测试
│       ├── deploy.yml      # 部署工作流：发布到生产
│       └── codeql.yml      # 代码扫描工作流
├── src/
├── package.json
└── ...
```

一个 Workflow 文件的骨架大概长这样：

```yaml
name: CI                    # 工作流的名字（显示在 GitHub UI 上）
on:                         # 触发条件（什么时候开始做饭）
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:                       # 作业列表（菜谱里有哪些菜）
  build:                    # 作业的名字
    runs-on: ubuntu-latest  # 在哪个厨房做
    steps:                  # 步骤列表（做菜的具体步骤）
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
```

## 3.2 Event（事件）= 什么时候开始做饭

Event 是触发 Workflow 的条件。就像餐厅不是 24 小时都在做菜——得等客人下单（push 代码）、有人预约（定时任务）、或者老板突然要加菜（手动触发）。

GitHub Actions 支持的事件类型非常丰富，常用的有：

```yaml
# 代码 push 到指定分支时触发
on:
  push:
    branches: [main, develop]
    tags: ['v*']              # tag 以 v 开头时触发

# Pull Request 相关事件
on:
  pull_request:
    branches: [main]          # PR 目标分支是 main 时触发

# 定时触发（Cron 表达式，UTC 时间）
on:
  schedule:
    - cron: '0 8 * * *'       # 每天 UTC 8:00（北京时间 16:00）

# 手动触发
on:
  workflow_dispatch:           # 在 GitHub UI 上出现一个 "Run workflow" 按钮

# 其他仓库事件
on:
  issues:
    types: [opened, labeled]  # Issue 被创建或打标签时
  release:
    types: [published]        # Release 被发布时
```

**一个 Workflow 可以同时监听多个事件：**

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:           # 也支持手动触发
```

## 3.3 Job（作业）= 一道菜

Job 是 Workflow 中的一个独立执行单元。一个 Workflow 可以有多个 Job，就像一个菜谱里可以有多道菜。

**关键特性：**

- **默认并行执行**：多个 Job 默认同时开始跑，互不干扰——就像餐厅后厨里，炒菜的厨师和煲汤的厨师各忙各的。
- **可以设置依赖**：用 `needs` 关键字指定 Job 之间的依赖关系——"汤得在菜炒好之后才能端上去"。

```yaml
jobs:
  # Job 1：跑测试
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test

  # Job 2：代码质量检查（和 test 并行执行）
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm run lint

  # Job 3：部署（必须等 test 和 lint 都通过才执行）
  deploy:
    needs: [test, lint]       # 依赖 test 和 lint 都成功
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run build
      - run: npm run deploy
```

每个 Job 运行在**独立的虚拟机或容器**中，所以 Job 之间不能直接共享文件——需要通过 Artifacts（产物）或者 Cache（缓存）来传递数据。这就像每个厨师有自己的独立工位，要传递食材得通过传菜窗口。

## 3.4 Step（步骤）= 做菜的具体步骤

Step 是 Job 中的最小执行单元。每个 Step 要么运行一个命令（`run`），要么使用一个 Action（`uses`）。

```yaml
steps:
  # 使用一个 Action（预制菜）
  - name: Checkout code           # 给这一步起个名字（可选但推荐）
    uses: actions/checkout@v4     # 使用 GitHub 官方的 checkout action

  # 运行一个命令（自己炒菜）
  - name: Install dependencies
    run: npm install              # 在 Runner 的 Shell 中执行

  # 运行多行命令
  - name: Build and verify
    run: |
      npm run build
      ls -la dist/
      echo "Build completed!"

  # 带环境变量的步骤
  - name: Run tests with coverage
    run: npm test -- --coverage
    env:
      CI: true
      NODE_ENV: test
```

**Step 的执行是顺序的**——从上到下，一步一步来。如果某一步失败了（比如 `npm test` 返回了非零退出码），后面的步骤默认不会执行。就像做菜做到一半发现盐放多了，后面的步骤就没意义了。

**每个 Step 都有一个 `name`（可选）和具体的操作。** 强烈建议给每个 Step 都加上 `name`——在 GitHub UI 上查看运行日志时，有名字的 Step 一目了然，没名字的只能看到一行干巴巴的命令。

## 3.5 Runner（运行器）= 厨房

Runner 是执行 Job 的虚拟机环境。你可以把它理解成一个"临时厨房"——GitHub 帮你搭好灶台、准备好锅碗瓢盆（预装各种工具），你只管做菜就行。做完之后，厨房就会被拆掉。

GitHub 提供了几种官方 Runner：

| Runner | 操作系统 | 适用场景 |
|--------|----------|----------|
| `ubuntu-latest` | Ubuntu Linux（目前是 22.04） | 大多数场景，默认选择 |
| `windows-latest` | Windows Server | 需要 Windows 环境的场景 |
| `macos-latest` | macOS | 需要 macOS 环境的场景（比如 iOS 构建） |

```yaml
jobs:
  build:
    runs-on: ubuntu-latest    # 在 Ubuntu 虚拟机上跑
```

**官方 Runner 的特点：**

- 每次运行都是全新的虚拟机（干净环境，不会有上次运行的残留）
- 预装了常用工具：Git、Node.js（多个版本）、Python、Docker、各种 CLI
- 每个 Job 最多运行 6 小时
- 每个 Step 的输出最多 10MB（超过会被截断）

**Self-hosted Runner（自托管运行器）：**

如果你需要特殊的硬件环境（比如 GPU 服务器）或者公司内部网络，可以自己搭建 Runner。就像自己建一个私人厨房——想装什么设备就装什么设备，但维护成本也归你。

## 3.6 Action（动作）= 预制菜/半成品

Action 是 GitHub Actions 中可复用的代码模块。你可以把它理解成"预制菜"——别人已经帮你把菜洗好、切好、调好味了，你只需要热一下就能上桌。

**使用 Action 的语法：**

```yaml
- uses: actions/checkout@v4          # 官方 Action
- uses: actions/setup-node@v4        # 官方 Action
- uses: docker/build-push-action@v5  # 社区 Action
- uses: ./.github/actions/my-action  # 自定义 Action（本地）
```

`@` 后面是版本标识，可以是：

- 主版本号：`@v4`（推荐，自动获取 v4.x.x 的最新版本）
- 精确版本号：`@v4.1.2`
- commit SHA：`@abc123def`（最安全但最不方便）
- 分支名：`@main`（不推荐，因为 main 分支会变）

**常用的官方 Action：**

| Action | 用途 |
|--------|------|
| `actions/checkout` | 检出仓库代码（几乎是必选的第一步） |
| `actions/setup-node` | 设置 Node.js 环境 |
| `actions/setup-python` | 设置 Python 环境 |
| `actions/cache` | 缓存依赖，加速后续运行 |
| `actions/upload-artifact` | 上传构建产物 |
| `actions/download-artifact` | 下载构建产物 |

## 3.7 概念关系图：一图看懂全局

下面是这些核心概念的关系图：

```
┌─────────────────────────────────────────────────────────┐
│  Workflow (.github/workflows/ci.yml)                    │
│  "整份菜谱"                                              │
│                                                         │
│  Triggered by Event (事件)                               │
│  "客人下单了！"                                           │
│  (e.g., push to main, pull_request opened)              │
│                                                         │
│  ┌───────────────────────────────────────────────────┐  │
│  │  Job 1: test  "第一道菜：凉菜"                     │  │
│  │  Runner: ubuntu-latest  "厨房：Ubuntu 虚拟机"      │  │
│  │                                                   │  │
│  │  ┌─────────────────────────────────────────────┐  │  │
│  │  │ Step 1: checkout    "把食材从冰箱拿出来"      │  │  │
│  │  │   uses: actions/checkout@v4  (预制菜)        │  │  │
│  │  ├─────────────────────────────────────────────┤  │  │
│  │  │ Step 2: install     "洗菜、切菜"             │  │  │
│  │  │   run: npm install                          │  │  │
│  │  ├─────────────────────────────────────────────┤  │  │
│  │  │ Step 3: test        "下锅炒！"               │  │  │
│  │  │   run: npm test                             │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│  ┌───────────────────────────────────────────────────┐  │
│  │  Job 2: build  "第二道菜：主菜"                    │  │
│  │  needs: [test]  "等凉菜上完再上主菜"               │  │
│  │  Runner: ubuntu-latest                            │  │
│  │                                                   │  │
│  │  ┌─────────────────────────────────────────────┐  │  │
│  │  │ Step 1: checkout                            │  │  │
│  │  │ Step 2: setup-node  (预制菜)                 │  │  │
│  │  │ Step 3: install                             │  │  │
│  │  │ Step 4: build       "大火收汁！"             │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**总结一下层级关系：**

```
Workflow (工作流)
  ├── triggered by → Event (事件)
  └── contains → Job (作业) [可以有多个，可并行/串行]
                   ├── runs on → Runner (运行器)
                   └── contains → Step (步骤) [按顺序执行]
                                  ├── uses → Action (动作/预制菜)
                                  └── run → Shell Command (命令)
```

## 小结

- **Workflow** 是定义在 `.github/workflows/` 下的 `.yml` 文件，代表一个完整的自动化流程
- **Event** 是触发条件，常用 `push`、`pull_request`、`schedule`、`workflow_dispatch`
- **Job** 是 Workflow 中的独立执行单元，默认并行，可用 `needs` 设置依赖
- **Step** 是 Job 中的最小执行单元，按顺序执行，要么 `run` 命令要么 `uses` Action
- **Runner** 是执行 Job 的虚拟机环境，默认用 GitHub 提供的官方 Runner
- **Action** 是可复用的代码模块，来自 Marketplace 或自己编写
