# 第17章：无畏并发

## 场景引入

在 Python 中写多线程，你可能经历过 GIL（全局解释器锁）的绝望——线程不能真正并行执行，多线程只是"轮流干活"的假并行。在 Java 中写多线程，你可能经历过 `ConcurrentModificationException` 的惊恐——两个线程同时修改一个 ArrayList，程序直接崩溃。在 JavaScript 中，你习惯了事件循环和 Promise，根本不用想线程。

Rust 的并发哲学叫做**无畏并发（Fearless Concurrency）**：编译器在编译期就帮你抓住数据竞争，而不是在凌晨三点的生产环境中才暴露 bug。Rust 的格言是："如果代码能编译，那它就没有数据竞争。"

这不是夸大其词。在其他语言中，并发 bug 是最难调试的——它们可能只在特定的线程调度顺序下出现，在测试环境中一切正常，在生产环境中随机崩溃。Rust 的做法是把这些运行时错误变成编译时错误——如果你的代码有潜在的数据竞争，它根本无法编译通过。

本章我们将学习 Rust 并发的三大模型：**线程创建**（最基础）、**消息传递**（最安全）、**共享状态**（最高效）。

## 17.1 线程创建：thread::spawn

```rust
use std::thread;
use std::time::Duration;

fn main() {
    // 创建新线程
    let handle = thread::spawn(|| {
        for i in 1..=5 {
            println!("子线程: 第 {} 次迭代", i);
            thread::sleep(Duration::from_millis(100));
        }
    });

    // 主线程继续执行
    for i in 1..=3 {
        println!("主线程: 第 {} 次迭代", i);
        thread::sleep(Duration::from_millis(100));
    }

    // 等待子线程完成（类似 Java 的 thread.join()）
    handle.join().unwrap();
    println!("所有线程完成！");
}
```

## 17.2 move 闭包与线程

线程闭包默认尝试借用外部变量，但线程的生命周期不确定——外部变量可能在线程运行期间被销毁。所以通常需要用 `move` 将所有权转移到线程中。

为什么 Rust 对线程闭包这么严格？因为线程可能比创建它的函数活得更久。假设函数 `foo()` 创建了一个线程，然后 `foo()` 返回了——如果线程还在运行并且引用着 `foo()` 的局部变量，那就是悬垂引用（dangling reference），Rust 绝不允许这种事情发生。`move` 关键字告诉编译器："别担心，我把数据的所有权转给线程了，它自己负责。"

对于实现了 `Copy` trait 的类型（如 `i32`、`bool`、`&T`），`move` 会把值复制进闭包，外部仍然可以使用原值。对于不实现 `Copy` 的类型（如 `String`、`Vec`），`move` 会转移所有权，外部就不能再用了。

```rust
use std::thread;

fn main() {
    let greeting = String::from("你好");
    let count = 42; // Copy 类型会被复制进闭包

    // move 将所有权移入闭包
    let handle = thread::spawn(move || {
        println!("{}! 数字是 {}", greeting, count);
        // greeting 和 count 现在属于这个线程
    });

    // println!("{}", greeting); // 编译错误：greeting 已被 move 进线程

    // count 是 Copy 类型，所以 move 后外部还能用
    println!("外部 count: {}", count); // OK

    handle.join().unwrap();
}
```

## 17.3 消息传递：mpsc 通道

Rust 提供**多生产者、单消费者（Multiple Producer, Single Consumer）**通道来实现线程间通信。这和 Go 的 channel 理念类似："不要通过共享内存来通信，而是通过通信来共享内存。"

如果你用过 Go 的 channel 或者 JavaScript 的 `postMessage`（Web Workers），这个概念应该很熟悉。想象一条传送带：生产者往传送带上放东西，消费者从传送带上拿东西，双方不需要直接接触。

`mpsc` 的"多生产者、单消费者"意味着：可以有多个线程往通道里发消息，但只能有一个线程接收消息。如果你需要多个消费者，可以用多个通道。

```rust
use std::sync::mpsc; // Multi-Producer, Single-Consumer
use std::thread;

fn main() {
    // 创建通道
    let (tx, rx) = mpsc::channel();

    // 生产者线程
    thread::spawn(move || {
        let messages = vec!["你好", "来自", "子线程", "的问候"];
        for msg in messages {
            tx.send(msg).unwrap(); // 发送消息
            thread::sleep(std::time::Duration::from_millis(200));
        }
        // tx 在这里被 drop，通道关闭
    });

    // 主线程作为消费者接收消息
    // rx 实现了 Iterator，可以逐个接收
    for received in rx {
        println!("收到: {}", received);
    }
    println!("通道已关闭");
}
```

**多生产者**——克隆发送端：

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    // 生产者 1
    let tx1 = tx.clone();
    thread::spawn(move || {
        tx1.send("来自线程1").unwrap();
    });

    // 生产者 2（使用原始 tx）
    thread::spawn(move || {
        tx.send("来自线程2").unwrap();
    });

    // 接收两条消息
    for _ in 0..2 {
        println!("收到: {}", rx.recv().unwrap());
    }
}
```

## 17.4 共享状态：Mutex\<T\>

当多个线程需要读写同一份数据时，你需要**互斥锁（Mutex，Mutual Exclusion 的缩写）**。`Mutex<T>` 保证同一时刻只有一个线程能访问数据——就像公共厕所的门锁：进去的人锁门，其他人排队，出来后才能轮到下一个。

如果你来自 Java，可以把 `Mutex<T>` 想象成 `synchronized` 关键字的更细粒度版本。Java 的 `synchronized` 锁住整个对象或方法，而 Rust 的 `Mutex` 只锁住它包裹的那一块数据，粒度更小，并发效率更高。

**使用 Mutex 的黄金法则**：

1. 获取锁（`lock()`）
2. 做你要做的事
3. 尽快释放锁（让守卫变量离开作用域）
4. 不要在持有锁的时候做耗时操作（I/O、网络请求等）

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);

    {
        // 获取锁——返回一个智能守卫（类似 Python 的 with lock:）
        let mut num = m.lock().unwrap();
        *num = 6; // 修改数据
        // 离开作用域时自动释放锁
    }

    println!("m = {:?}", m); // m = Mutex { data: 6, ... }
}
```

## 17.5 Arc\<Mutex\<T\>\>：多线程共享可变状态

`Mutex<T>` 本身不能在线程间共享（因为不是线程安全的引用计数），需要搭配 `Arc<T>`。`Arc<Mutex<T>>` 是 Rust 多线程编程中最常见的组合之一，可以说是 Rust 版的"全局可变状态"。

为什么不直接用 `Rc<Mutex<T>>`？因为 `Rc` 不是线程安全的。为什么不直接用 `Arc<T>`？因为 `Arc` 只提供不可变引用。只有 `Arc<Mutex<T>>` 才能同时满足：多线程共享 + 安全修改。

这个组合的工作方式：

- `Arc` 负责管理"有多少个线程在共享这份数据"（引用计数）
- `Mutex` 负责管理"同一时刻只让一个线程修改数据"（互斥锁）
- 两者配合，实现了安全的多线程共享可变状态

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Arc: 线程安全的引用计数
    // Mutex: 互斥锁保护内部数据
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            // 获取锁、修改、自动释放
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("最终结果: {}", *counter.lock().unwrap()); // 10
}
```

## 17.6 Send 与 Sync Trait

Rust 用两个 marker trait 来标记类型的并发安全性。这两个 trait 是 Rust 并发安全体系的基石，理解它们非常重要：

- **`Send`**：可以安全地在线程间**转移所有权**。几乎所有类型都是 `Send`，除了 `Rc<T>` 等。这意味着你可以把一个 `String` 从线程 A 发送到线程 B，编译器确认这是安全的。
- **`Sync`**：可以安全地在多个线程间**共享引用**（即 `&T` 是 `Send` 的）。几乎所有类型都是 `Sync`，除了 `RefCell<T>`、`Rc<T>` 等。这意味着如果 `T: Sync`，那么 `&T` 可以安全地跨线程使用。

一个简单的记忆方法：

- `Send` = "我能把这个东西**送到**另一个线程去"
- `Sync` = "我能让多个线程同时**看到**这个东西"

| 类型 | Send? | Sync? | 原因 |
| ------ | ------- | ------- | ------ |
| `i32`, `String`, `Vec<T>` | 是 | 是 | 基本类型都安全 |
| `Box<T>` | 是（若 T: Send） | 是（若 T: Sync） | 单所有者，安全 |
| `Rc<T>` | 否 | 否 | 引用计数不是原子的 |
| `Arc<T>` | 是（若 T: Send+Sync） | 是（若 T: Send+Sync） | 原子引用计数 |
| `RefCell<T>` | 是 | 否 | 运行时检查不安全跨线程 |
| `Mutex<T>` | 是（若 T: Send） | 是 | 锁保证安全 |

```rust
// 你通常不需要手动实现 Send/Sync——编译器自动推导
// 但你可以用它们作为 trait bound

use std::thread;

fn spawn_with_data<F>(f: F)
where
    F: FnOnce() + Send + 'static, // 闭包必须是 Send 且拥有 'static 生命周期
{
    thread::spawn(f);
}

fn main() {
    let data = String::from("线程安全的数据");
    spawn_with_data(move || {
        println!("{}", data);
    });

    thread::sleep(std::time::Duration::from_millis(100));
}
```

## 17.7 数据竞争：Rust 的保证

数据竞争（Data Race）是并发编程中最可怕的 bug 类型。它需要同时满足三个条件：

1. 两个或更多指针同时访问同一数据
2. 至少有一个指针在写入
3. 没有同步机制（比如锁）

数据竞争之所以可怕，是因为它的表现是**不确定的**——同样的代码，运行1000次可能999次正常，第1000次崩溃。这种 bug 在测试环境中几乎不可能复现，往往在生产环境的深夜才冒出来，被程序员们称为"海森堡 bug"（Heisenbug，观察它时它就消失了）。

Rust 的所有权系统在编译期就消除了数据竞争——要么只有一个可变引用（独占访问），要么有多个不可变引用（只读访问），不存在"又有读又有写"的情况。如果你需要在多线程中同时读写数据，Rust 要求你显式使用同步原语（`Mutex`、`RwLock` 等），这等于在第三条规则上打了个勾："有同步机制"。

```rust
// 这段代码无法编译——Rust 在编译期就阻止了潜在的数据竞争
use std::thread;

fn main() {
    let mut data = vec![1, 2, 3];

    // thread::spawn(move || {
    //     data.push(4);  // 线程1：写
    // });

    // thread::spawn(move || {
    //     println!("{:?}", data); // 线程2：读
    // });
    // 编译错误：data 被 move 了两次！

    // 正确做法：使用 Arc<Mutex<Vec<i32>>>
    use std::sync::{Arc, Mutex};
    let data = Arc::new(Mutex::new(vec![1, 2, 3]));

    let d1 = Arc::clone(&data);
    let h1 = thread::spawn(move || {
        d1.lock().unwrap().push(4);
    });

    let d2 = Arc::clone(&data);
    let h2 = thread::spawn(move || {
        let locked = d2.lock().unwrap();
        println!("{:?}", *locked);
    });

    h1.join().unwrap();
    h2.join().unwrap();
}
```

## 17.8 线程池简介

频繁创建和销毁线程开销很大。每次创建线程，操作系统都需要分配栈空间、设置线程上下文，这些操作虽然快，但在高并发场景下累积起来也不可忽视。**线程池（Thread Pool）**预先创建一组工作线程，按需分配任务——就像一个餐厅不临时招聘服务员，而是保持一个固定团队，有客人来了就分配去服务。

线程池的优势：

- **减少线程创建开销**：复用已有线程，避免反复创建/销毁
- **控制并发数量**：防止同时创建太多线程导致系统资源耗尽
- **任务排队**：当所有线程都忙时，新任务自动排队等待

在 Java 中有 `ExecutorService`，在 Python 中有 `ThreadPoolExecutor`，在 Rust 标准库中没有内置线程池，但我们可以自己实现一个简化版（实际项目推荐使用 `rayon` 或 `tokio` 等库）：

下面是一个简化版的线程池实现，它展示了 Rust 并发原语如何协同工作：

```rust
use std::sync::{Arc, Mutex, mpsc};
use std::thread;

// 简化版线程池实现
// 设计思路：
// 1. 主线程通过 mpsc 通道向工作线程发送任务
// 2. 工作线程共享一个接收端（用 Arc<Mutex<>> 包装）
// 3. 当发送端被 drop 时，通道关闭，工作线程退出循环
struct ThreadPool {
    workers: Vec<Worker>,
    sender: Option<mpsc::Sender<Job>>,
}

type Job = Box<dyn FnOnce() + Send + 'static>;

struct Worker {
    id: usize,
    thread: Option<thread::JoinHandle<()>>,
}

impl ThreadPool {
    fn new(size: usize) -> ThreadPool {
        let (sender, receiver) = mpsc::channel();
        let receiver = Arc::new(Mutex::new(receiver));
        let mut workers = Vec::with_capacity(size);

        for id in 0..size {
            let receiver = Arc::clone(&receiver);
            let thread = thread::spawn(move || loop {
                let message = receiver.lock().unwrap().recv();
                match message {
                    Ok(job) => {
                        println!("Worker {} 正在执行任务", id);
                        job();
                    }
                    Err(_) => {
                        println!("Worker {} 收到关闭信号", id);
                        break;
                    }
                }
            });
            workers.push(Worker { id, thread: Some(thread) });
        }

        ThreadPool {
            workers,
            sender: Some(sender),
        }
    }

    fn execute<F>(&self, f: F)
    where
        F: FnOnce() + Send + 'static,
    {
        self.sender.as_ref().unwrap().send(Box::new(f)).unwrap();
    }
}

impl Drop for ThreadPool {
    fn drop(&mut self) {
        drop(self.sender.take()); // 关闭通道
        for worker in &mut self.workers {
            if let Some(thread) = worker.thread.take() {
                println!("等待 Worker {} 关闭", worker.id);
                thread.join().unwrap();
            }
        }
    }
}

fn main() {
    let pool = ThreadPool::new(4);

    for i in 0..8 {
        pool.execute(move || {
            println!("任务 {} 在线程 {:?} 中执行", i, thread::current().id());
            thread::sleep(std::time::Duration::from_millis(100));
        });
    }

    thread::sleep(std::time::Duration::from_secs(1));
    println!("主线程准备退出，线程池将自动关闭");
}
```

## 常见陷阱

1. **忘记 `join()`**：不 `join()` 的话，主线程可能在子线程完成前退出。子线程会被强制终止，正在执行的操作可能只完成了一半。在生产代码中，几乎总是需要 `join()` 或使用其他同步机制来确保子线程完成。

2. **死锁**：两个线程各自持有一把锁，然后互相等对方的锁——经典的"哲学家就餐问题"。避免方法：（a）总是以相同顺序获取锁；（b）使用 `try_lock()` 配合超时；（c）减少锁的粒度，让每个锁保护更小的数据范围。

3. **在 `Mutex` 守卫持有期间做耗时操作**：锁的持有时间越长，并发性能越差。最佳实践是：获取锁 → 拷贝需要的数据 → 释放锁 → 用拷贝的数据做耗时操作。

4. **unwrap() panic 传播**：`Mutex::lock()` 返回 `Result`——如果持有锁的线程 panic 了，锁会"中毒"（poisoned）。后续尝试获取锁的线程会收到 `PoisonError`。生产环境应该妥善处理这个错误，而不是简单 `unwrap()`。

5. **闭包捕获过多数据**：`move` 闭包会把所有捕获的变量都移入线程。如果你只需要一个字段，不要把整个结构体都 move 进去——先提取需要的字段，再 move 进闭包。

## 小结

| 工具 | 用途 | 类比 |
| ------ | ------ | ------ |
| `thread::spawn` | 创建线程 | Java `new Thread().start()` |
| `move` 闭包 | 转移所有权到线程 | 把数据"打包寄走" |
| `mpsc::channel` | 线程间消息传递 | Go 的 channel |
| `Mutex<T>` | 互斥锁保护共享数据 | Java `synchronized` |
| `Arc<T>` | 线程安全引用计数 | Java `AtomicReference` |
| `Send` / `Sync` | 并发安全标记 | 编译器的"安全认证标签" |
