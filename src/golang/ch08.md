## 8.1 项目规划与架构设计

在写第一行代码之前，先想清楚我们要做什么。这就像盖房子之前需要一张图纸——没有规划的代码注定走向混乱。

### 项目需求分析

一个待办事项 API 需要哪些功能？我们可以用 CRUD（增删改查）这个经典缩写来梳理：

| 操作 | HTTP 方法 | 路径 | 说明 |
|------|----------|------|------|
| 创建 | POST | /todos | 创建一个新待办事项 |
| 查询全部 | GET | /todos | 获取待办事项列表（支持搜索和分页） |
| 查询单个 | GET | /todos/{id} | 根据 ID 获取某个待办事项 |
| 更新 | PUT | /todos/{id} | 更新某个待办事项 |
| 删除 | DELETE | /todos/{id} | 删除某个待办事项 |

> **什么是 RESTful？** 简单来说，REST 是一种 API 设计风格。它把服务器上的一切数据都看作"资源"（Resource），用 HTTP 的标准方法（GET、POST、PUT、DELETE）来操作资源。就像用统一的"动词"来描述所有动作，简洁而一致。

### 项目目录结构

Go 社区推荐的项目布局遵循"按职责分层"的原则。以下是我们的目录结构：

```
todo-api/
├── main.go              # 程序入口
├── go.mod               # 模块定义
├── Makefile             # 构建命令
├── Dockerfile           # 容器化部署
├── handler/             # HTTP 处理层
│   └── handler.go
├── service/             # 业务逻辑层
│   └── service.go
├── repository/          # 数据存储层
│   └── repository.go
├── model/               # 数据模型
│   └── model.go
└── middleware/           # 中间件
    └── middleware.go
```

### 分层架构：handler → service → repository

为什么要分这么多层？想象一个餐厅的运作方式：

- **Handler 层（服务员）**：负责接待客人，理解客人的需求（解析 HTTP 请求），把需求翻译成厨房能理解的格式（调用 Service），最后把菜品端给客人（返回 HTTP 响应）。
- **Service 层（主厨）**：负责核心业务逻辑——验证订单是否合理、决定烹饪流程。它不关心客人长什么样（不关心 HTTP 细节），也不关心食材从哪里来（不关心存储细节）。
- **Repository 层（仓库管理员）**：负责管理食材的存取——从冰箱拿食材（读取数据）、把新食材放进冰箱（写入数据）。

> **为什么要分层？** 最核心的原因是"关注点分离"。当你想从内存存储切换到数据库时，只需要改 Repository 层；当你想从 HTTP 切换到 gRPC 时，只需要改 Handler 层。每一层的变化不会波及其他层，这就是软件工程中最重要的"解耦"思想。

Go 项目与 Java/Python 的区别在于：Go 不喜欢过度抽象。Java 喜欢用注解、XML 配置、庞大的 IoC 容器来管理层的依赖；Python 的 Web 框架（如 Django）自带一套固定的项目结构。而 Go 的哲学是"简单直接"——用接口来定义层与层的边界，不需要框架，不需要反射，一切透明可见。

## 8.2 数据模型与存储层

### 定义 Todo 数据模型

数据模型是整个系统的基石。我们用一个结构体来描述一条待办事项：

```go
// model/model.go
package model

import "time"

// Status 是待办事项状态的类型别名
// 使用 string 类型是为了方便 JSON 序列化（人类可读）
type Status string

const (
    StatusPending    Status = "pending"    // 待完成
    StatusInProgress Status = "in_progress" // 进行中
    StatusCompleted  Status = "completed"  // 已完成
)

// Todo 表示一条待办事项
type Todo struct {
    ID          string    `json:"id"`                    // 唯一标识符，使用 UUID
    Title       string    `json:"title"`                 // 标题（必填，1-200 字符）
    Description string    `json:"description,omitempty"` // 描述（可选）
    Status      Status    `json:"status"`                // 当前状态
    CreatedAt   time.Time `json:"created_at"`            // 创建时间
    UpdatedAt   time.Time `json:"updated_at"`            // 最后更新时间
}

// CreateTodoRequest 是创建待办事项的请求体
// 为什么单独定义一个请求结构体？因为请求体和完整模型的字段是不同的——
// 客户端不需要传 ID 和时间，这些由服务端生成。
// 这叫 DTO（Data Transfer Object）模式，用于隔离"外部输入"和"内部模型"。
type CreateTodoRequest struct {
    Title       string `json:"title"`
    Description string `json:"description"`
    Status      Status `json:"status"`
}

// UpdateTodoRequest 是更新待办事项的请求体
// 使用指针类型（*string）来区分"客户端没传这个字段"和"客户端传了空字符串"
type UpdateTodoRequest struct {
    Title       *string `json:"title"`
    Description *string `json:"description"`
    Status      *Status `json:"status"`
}
```

> **为什么用单独的请求结构体？** 这就像快递单和包裹的关系——快递单只包含寄件人需要填写的信息（地址、姓名、电话），而包裹本身还包含重量、体积等仓库计算出来的属性。把请求体和内部模型分开，可以让 API 更清晰，也更容易做输入验证。

### 设计 Repository 接口

在 Go 中，我们习惯"先定义接口，再写实现"。这就像先签好合同（接口定义了"能做到什么"），再去找施工队（具体实现）。这样做的好处是，Handler 层和 Service 层只需要知道合同内容，不需要关心具体是谁在施工。

```go
// repository/repository.go
package repository

import (
    "fmt"
    "sync"
    "time"

    "todo-api/model"
)

// Repository 定义了数据存取的操作契约
// 任何实现了这些方法的结构体都可以当作 Repository 使用
type Repository interface {
    Create(todo model.Todo) error
    GetByID(id string) (model.Todo, error)
    GetAll(offset, limit int, search string) ([]model.Todo, int, error)
    Update(todo model.Todo) error
    Delete(id string) error
}
```

### 实现内存存储

现在，我们用内存中的 map 来实现这个接口。为了让存储并发安全（多个请求同时访问不会出错），我们使用 `sync.RWMutex`——一种读写锁。

```go
// memoryRepo 是基于内存的 Repository 实现
type memoryRepo struct {
    mu    sync.RWMutex        // 读写锁，保护并发访问
    todos map[string]model.Todo // 用 map 存储，key 是 ID
}

// NewMemoryRepo 创建一个新的内存仓库
// 注意：函数名以小写开头（NewMemoryRepo），返回的是接口类型。
// 这是 Go 的惯用模式——对外暴露接口，对内隐藏实现细节。
func NewMemoryRepo() Repository {
    return &memoryRepo{
        todos: make(map[string]model.Todo),
    }
}

// Create 创建一条待办事项
func (r *memoryRepo) Create(todo model.Todo) error {
    r.mu.Lock()         // 加写锁：同一时刻只允许一个写入操作
    defer r.mu.Unlock() // 函数返回时自动释放锁

    // 检查 ID 是否已存在（防止重复创建）
    if _, exists := r.todos[todo.ID]; exists {
        return fmt.Errorf("todo with id %s already exists", todo.ID)
    }

    r.todos[todo.ID] = todo
    return nil
}

// GetByID 根据 ID 查询单条待办事项
func (r *memoryRepo) GetByID(id string) (model.Todo, error) {
    r.mu.RLock()         // 加读锁：允许多个读操作同时进行
    defer r.mu.RUnlock() // 这就是"读写锁"比"普通互斥锁"高效的地方

    todo, exists := r.todos[id]
    if !exists {
        return model.Todo{}, fmt.Errorf("todo not found: %s", id)
    }

    return todo, nil
}

// GetAll 分页查询待办事项，支持按标题搜索
// offset 是跳过的条数，limit 是每页的条数，search 是搜索关键词
// 返回结果列表和总数（用于分页计算）
func (r *memoryRepo) GetAll(offset, limit int, search string) ([]model.Todo, int, error) {
    r.mu.RLock()
    defer r.mu.RUnlock()

    // 第一步：收集所有符合条件的待办事项
    var all []model.Todo
    for _, todo := range r.todos {
        // 如果 search 不为空，按标题关键词过滤
        if search != "" && !containsIgnoreCase(todo.Title, search) {
            continue
        }
        all = append(all, todo)
    }

    total := len(all)

    // 第二步：分页——先跳过 offset 条，再取 limit 条
    if offset >= total {
        return []model.Todo{}, total, nil
    }
    end := offset + limit
    if end > total {
        end = total
    }

    return all[offset:end], total, nil
}

// Update 更新一条待办事项
func (r *memoryRepo) Update(todo model.Todo) error {
    r.mu.Lock()
    defer r.mu.Unlock()

    // 先检查是否存在
    if _, exists := r.todos[todo.ID]; !exists {
        return fmt.Errorf("todo not found: %s", todo.ID)
    }

    r.todos[todo.ID] = todo
    return nil
}

// Delete 删除一条待办事项
func (r *memoryRepo) Delete(id string) error {
    r.mu.Lock()
    defer r.mu.Unlock()

    if _, exists := r.todos[id]; !exists {
        return fmt.Errorf("todo not found: %s", id)
    }

    delete(r.todos, id)
    return nil
}

// containsIgnoreCase 判断 s 是否包含 substr（忽略大小写）
func containsIgnoreCase(s, substr string) bool {
    return len(substr) > 0 && len(s) > 0 &&
        (s == substr || len(s) >= len(substr) && findSubstring(s, substr))
}

func findSubstring(s, substr string) bool {
    for i := 0; i <= len(s)-len(substr); i++ {
        if s[i:i+len(substr)] == substr {
            return true
        }
    }
    return false
}
```

> **为什么用 `sync.RWMutex` 而不是 `sync.Mutex`？** 在读多写少的场景下（大多数 API 都是这样），读写锁允许多个读操作同时进行，只有写操作需要独占锁。这大大提升了并发性能。就像图书馆——多个人可以同时看书（读锁），但每次只能有一个人修改书架上的书（写锁）。

## 8.3 业务逻辑层

Service 层是整个系统的"大脑"——所有的业务规则、输入验证、错误处理都在这里完成。

### 自定义错误类型

先定义错误类型。为什么不用普通的 `errors.New`？因为 Handler 层需要根据错误的"种类"来返回不同的 HTTP 状态码（404 表示"找不到"，400 表示"输入有误"）。自定义错误类型就像给错误贴了标签，让上层处理更方便。

```go
// service/service.go
package service

import (
    "errors"
    "fmt"
    "strings"
    "time"

    "todo-api/model"
    "todo-api/repository"
)

// 自定义哨兵错误（Sentinel Errors）
// 哨兵错误是全局可比较的错误值，用于在 Service 层和 Handler 层之间传递错误语义
var (
    ErrNotFound     = errors.New("todo not found")      // 资源不存在
    ErrValidation   = errors.New("validation failed")    // 输入验证失败
    ErrInvalidID    = errors.New("invalid todo id")      // ID 格式不合法
)
```

### 实现 Service 结构体

```go
// Service 封装了待办事项的核心业务逻辑
type Service struct {
    repo repository.Repository // 依赖 Repository 接口，不依赖具体实现
}

// NewService 创建一个新的 Service 实例
// 接收 Repository 接口作为参数——这就是"依赖注入"
func NewService(repo repository.Repository) *Service {
    return &Service{repo: repo}
}

// Create 创建一条新的待办事项
func (s *Service) Create(req model.CreateTodoRequest) (model.Todo, error) {
    // 输入验证：标题是必填字段，且长度不能超过 200
    if err := validateTitle(req.Title); err != nil {
        return model.Todo{}, err
    }

    // 设置默认状态
    status := req.Status
    if status == "" {
        status = model.StatusPending
    }
    if !isValidStatus(status) {
        return model.Todo{}, fmt.Errorf("%w: invalid status '%s'", ErrValidation, status)
    }

    now := time.Now()
    todo := model.Todo{
        ID:          generateID(),          // 生成唯一 ID
        Title:       req.Title,
        Description: req.Description,
        Status:      status,
        CreatedAt:   now,
        UpdatedAt:   now,
    }

    if err := s.repo.Create(todo); err != nil {
        return model.Todo{}, fmt.Errorf("failed to create todo: %w", err)
    }

    return todo, nil
}

// GetByID 根据 ID 查询单条待办事项
func (s *Service) GetByID(id string) (model.Todo, error) {
    if strings.TrimSpace(id) == "" {
        return model.Todo{}, ErrInvalidID
    }

    todo, err := s.repo.GetByID(id)
    if err != nil {
        // 将 Repository 层的错误转换为 Service 层的错误
        // 这样 Handler 层只需要认识 ErrNotFound，不需要知道存储层的实现细节
        return model.Todo{}, ErrNotFound
    }
    return todo, nil
}

// List 分页查询待办事项
func (s *Service) List(page, pageSize int, search string) ([]model.Todo, int, error) {
    // 参数校正：防止非法的分页参数
    if page < 1 {
        page = 1
    }
    if pageSize < 1 || pageSize > 100 {
        pageSize = 10 // 默认每页 10 条
    }

    offset := (page - 1) * pageSize
    todos, total, err := s.repo.GetAll(offset, pageSize, search)
    if err != nil {
        return nil, 0, fmt.Errorf("failed to list todos: %w", err)
    }

    return todos, total, nil
}

// Update 更新一条待办事项
func (s *Service) Update(id string, req model.UpdateTodoRequest) (model.Todo, error) {
    // 先查询是否存在
    todo, err := s.GetByID(id)
    if err != nil {
        return model.Todo{}, err
    }

    // 按需更新：只更新客户端传了的字段
    // 这里就用到了指针类型的好处——nil 表示"客户端没有传这个字段"
    if req.Title != nil {
        if err := validateTitle(*req.Title); err != nil {
            return model.Todo{}, err
        }
        todo.Title = *req.Title
    }
    if req.Description != nil {
        todo.Description = *req.Description
    }
    if req.Status != nil {
        if !isValidStatus(*req.Status) {
            return model.Todo{}, fmt.Errorf("%w: invalid status '%s'", ErrValidation, *req.Status)
        }
        todo.Status = *req.Status
    }

    todo.UpdatedAt = time.Now()

    if err := s.repo.Update(todo); err != nil {
        return model.Todo{}, fmt.Errorf("failed to update todo: %w", err)
    }

    return todo, nil
}

// Delete 删除一条待办事项
func (s *Service) Delete(id string) error {
    // 先检查是否存在
    if _, err := s.GetByID(id); err != nil {
        return err
    }
    return s.repo.Delete(id)
}

// ---- 辅助函数 ----

func validateTitle(title string) error {
    title = strings.TrimSpace(title)
    if title == "" {
        return fmt.Errorf("%w: title is required", ErrValidation)
    }
    if len(title) > 200 {
        return fmt.Errorf("%w: title must be 200 characters or less", ErrValidation)
    }
    return nil
}

func isValidStatus(s model.Status) bool {
    switch s {
    case model.StatusPending, model.StatusInProgress, model.StatusCompleted:
        return true
    }
    return false
}

// generateID 生成一个简单的唯一 ID
// 生产环境建议使用 UUID 库（如 github.com/google/uuid）
func generateID() string {
    return fmt.Sprintf("%d", time.Now().UnixNano())
}
```

> **为什么 Service 层不直接操作 HTTP？** 因为业务逻辑应该是"协议无关"的。今天你通过 HTTP 提供服务，明天可能要通过 gRPC、消息队列、甚至命令行来调用同一套逻辑。如果把 HTTP 代码混进 Service 层，这个目标就无法实现了。

## 8.4 HTTP Handler 层

Handler 层是整个系统的"门面"——它接收 HTTP 请求、调用 Service、返回 HTTP 响应。

### 统一响应格式

一个好的 API 应该有统一的响应格式，这样前端开发者可以写一套通用的解析代码。我们定义两种响应结构：成功时返回数据，失败时返回错误信息。

```go
// handler/handler.go
package handler

import (
    "encoding/json"
    "errors"
    "net/http"
    "strconv"
    "strings"

    "todo-api/model"
    "todo-api/service"
)

// Handler 处理所有 HTTP 请求
type Handler struct {
    svc *service.Service // 依赖 Service 层
}

// NewHandler 创建一个新的 Handler
func NewHandler(svc *service.Service) *Handler {
    return &Handler{svc: svc}
}

// ---- 统一响应格式 ----

// Response 是成功的响应
type Response struct {
    Data interface{} `json:"data"`          // 返回的数据
    Meta *Meta       `json:"meta,omitempty"` // 分页元数据（可选）
}

// Meta 是分页信息
type Meta struct {
    Page      int `json:"page"`       // 当前页码
    PageSize  int `json:"page_size"`  // 每页条数
    Total     int `json:"total"`      // 总条数
    TotalPage int `json:"total_page"` // 总页数
}

// ErrorResponse 是错误响应
type ErrorResponse struct {
    Error   string `json:"error"`            // 错误类型（如 "not_found"）
    Message string `json:"message"`          // 人类可读的错误描述
}

// writeJSON 写入 JSON 响应的辅助函数
func writeJSON(w http.ResponseWriter, status int, v interface{}) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)          // 设置 HTTP 状态码
    json.NewEncoder(w).Encode(v)   // 将数据编码为 JSON 并写入响应体
}

// writeError 写入错误响应
func writeError(w http.ResponseWriter, status int, errType, message string) {
    writeJSON(w, status, ErrorResponse{
        Error:   errType,
        Message: message,
    })
}
```

### 路由注册

Go 1.22 对标准库 `net/http` 的路由能力做了重大增强，支持了 HTTP 方法和路径参数模式匹配，这意味着我们不再需要 Gorilla Mux 或 Gin 等第三方路由库。

```go
// RegisterRoutes 注册所有路由
// 这里使用 Go 1.22+ 增强的路由模式：METHOD /path/{param}
func (h *Handler) RegisterRoutes(mux *http.ServeMux) {
    mux.HandleFunc("GET /todos", h.ListTodos)
    mux.HandleFunc("POST /todos", h.CreateTodo)
    mux.HandleFunc("GET /todos/{id}", h.GetTodo)
    mux.HandleFunc("PUT /todos/{id}", h.UpdateTodo)
    mux.HandleFunc("DELETE /todos/{id}", h.DeleteTodo)
}
```

### 实现各个 Handler 方法

```go
// CreateTodo 处理 POST /todos 请求——创建一条待办事项
func (h *Handler) CreateTodo(w http.ResponseWriter, r *http.Request) {
    var req model.CreateTodoRequest

    // 解析请求体中的 JSON 数据
    // json.NewDecoder 比 ioutil.ReadAll + json.Unmarshal 更高效，
    // 因为它直接从 io.Reader 流式读取，不需要把整个请求体读到内存
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "bad_request", "Invalid JSON in request body")
        return
    }
    defer r.Body.Close() // 确保请求体被关闭，释放资源

    todo, err := h.svc.Create(req)
    if err != nil {
        handleError(w, err)
        return
    }

    writeJSON(w, http.StatusCreated, Response{Data: todo})
}

// GetTodo 处理 GET /todos/{id} 请求——获取单条待办事项
func (h *Handler) GetTodo(w http.ResponseWriter, r *http.Request) {
    // 从 URL 路径中提取 id 参数（Go 1.22+ 的新特性）
    id := r.PathValue("id")

    todo, err := h.svc.GetByID(id)
    if err != nil {
        handleError(w, err)
        return
    }

    writeJSON(w, http.StatusOK, Response{Data: todo})
}

// ListTodos 处理 GET /todos 请求——分页查询待办事项
func (h *Handler) ListTodos(w http.ResponseWriter, r *http.Request) {
    // 从 URL 查询参数中获取分页和搜索条件
    // 例如：GET /todos?page=2&page_size=10&search=buy
    query := r.URL.Query()

    page, _ := strconv.Atoi(query.Get("page"))
    pageSize, _ := strconv.Atoi(query.Get("page_size"))
    search := query.Get("search")

    todos, total, err := h.svc.List(page, pageSize, search)
    if err != nil {
        handleError(w, err)
        return
    }

    // 计算总页数
    if pageSize < 1 {
        pageSize = 10
    }
    totalPage := (total + pageSize - 1) / pageSize

    writeJSON(w, http.StatusOK, Response{
        Data: todos,
        Meta: &Meta{
            Page:      page,
            PageSize:  pageSize,
            Total:     total,
            TotalPage: totalPage,
        },
    })
}

// UpdateTodo 处理 PUT /todos/{id} 请求——更新待办事项
func (h *Handler) UpdateTodo(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")

    var req model.UpdateTodoRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "bad_request", "Invalid JSON in request body")
        return
    }
    defer r.Body.Close()

    todo, err := h.svc.Update(id, req)
    if err != nil {
        handleError(w, err)
        return
    }

    writeJSON(w, http.StatusOK, Response{Data: todo})
}

// DeleteTodo 处理 DELETE /todos/{id} 请求——删除待办事项
func (h *Handler) DeleteTodo(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id")

    if err := h.svc.Delete(id); err != nil {
        handleError(w, err)
        return
    }

    // 删除成功返回 204 No Content——告诉客户端"操作成功了，但没有返回内容"
    w.WriteHeader(http.StatusNoContent)
}

// handleError 根据错误类型返回对应的 HTTP 状态码
// 这个函数是连接 Service 层错误和 HTTP 状态码的桥梁
func handleError(w http.ResponseWriter, err error) {
    switch {
    case errors.Is(err, service.ErrNotFound):
        writeError(w, http.StatusNotFound, "not_found", err.Error())
    case errors.Is(err, service.ErrValidation):
        writeError(w, http.StatusBadRequest, "validation_error", err.Error())
    case errors.Is(err, service.ErrInvalidID):
        writeError(w, http.StatusBadRequest, "bad_request", err.Error())
    default:
        writeError(w, http.StatusInternalServerError, "internal_error", "An unexpected error occurred")
    }
}

// trimSpace 在比较前去除字符串的首尾空格（辅助方法）
func trimSpace(s string) string {
    return strings.TrimSpace(s)
}
```

> **`errors.Is` vs `==` 比较错误？** 在 Go 中，推荐使用 `errors.Is(err, target)` 而不是 `err == target` 来比较错误。因为 `errors.Is` 会沿着错误链（error chain）向上查找，即使错误被 `fmt.Errorf("... %w", err)` 包装了一层也能正确匹配。这是一种更健壮的写法。

## 8.5 中间件机制

### 什么是中间件？

中间件（Middleware）是请求处理链中的"拦截器"。想象你寄快递：包裹先经过"安检"（检查是否违禁），然后经过"称重"（记录重量），再经过"贴单"（打印快递单）。每个环节只做一件事，但它们串在一起完成了完整的预处理流程。

中间件就是这个思想在代码中的体现。每个中间件是一个函数，它接收一个 `http.Handler`，返回一个新的 `http.Handler`。新的 Handler 在调用原始 Handler 之前或之后，可以插入自己的逻辑。

```go
// middleware/middleware.go
package middleware

import (
    "log"
    "net/http"
    "time"
)
```

### 日志中间件

```go
// Logger 是日志中间件
// 它记录每个请求的方法、路径、状态码和耗时
// 函数签名 func(http.Handler) http.Handler 是 Go 中间件的标准形式
func Logger(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now() // 记录请求开始时间

        // 使用 responseWriter 包装器来捕获状态码
        // 因为标准的 ResponseWriter 不提供获取状态码的方法
        rw := &responseWriter{ResponseWriter: w, statusCode: http.StatusOK}

        next.ServeHTTP(rw, r) // 调用下一个处理器

        // 计算耗时并记录日志
        duration := time.Since(start)
        log.Printf("%s %s %d %v",
            r.Method,      // HTTP 方法：GET、POST 等
            r.URL.Path,    // 请求路径
            rw.statusCode, // HTTP 状态码
            duration,      // 请求耗时
        )
    })
}

// responseWriter 包装了 http.ResponseWriter，用于捕获状态码
type responseWriter struct {
    http.ResponseWriter
    statusCode int
}

// WriteHeader 重写 WriteHeader 方法，在写入状态码的同时记录下来
func (rw *responseWriter) WriteHeader(code int) {
    rw.statusCode = code
    rw.ResponseWriter.WriteHeader(code)
}
```

### Panic Recovery 中间件

```go
// Recovery 是 Panic 恢复中间件
// 当 Handler 中发生 panic（未捕获的异常）时，
// 它会自动恢复，返回 500 错误，而不是让整个服务器崩溃
func Recovery(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // defer + recover 是 Go 中处理 panic 的标准模式
        defer func() {
            if err := recover(); err != nil {
                log.Printf("PANIC recovered: %v", err)
                http.Error(w, `{"error":"internal_error","message":"Internal server error"}`,
                    http.StatusInternalServerError)
            }
        }()

        next.ServeHTTP(w, r)
    })
}
```

> **为什么需要 Recovery 中间件？** Go 的 goroutine 中如果发生未捕获的 panic，整个程序都会退出。在 HTTP 服务器中，一个用户的请求不应该导致整个服务挂掉。Recovery 中间件就像一张安全网——即使某个请求处理出了问题，也能优雅地返回错误响应，服务继续运行。

### CORS 中间件

```go
// CORS 是跨域资源共享中间件
// 浏览器的"同源策略"会阻止前端 JS 请求不同域名的 API。
// CORS 中间件通过设置特定的 HTTP 头来告诉浏览器"我允许跨域请求"。
func CORS(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Access-Control-Allow-Origin", "*")
        w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
        w.Header().Set("Access-Control-Allow-Headers", "Content-Type, Authorization")

        // 处理预检请求（OPTIONS）
        // 浏览器在发送复杂请求之前，会先发送一个 OPTIONS 请求来"探路"
        if r.Method == http.MethodOptions {
            w.WriteHeader(http.StatusOK)
            return
        }

        next.ServeHTTP(w, r)
    })
}
```

### 中间件链式组合

```go
// Chain 将多个中间件组合成一个链
// 中间件的执行顺序是"洋葱模型"：最后一个加入的中间件最先执行
// 所以 Chain(Recovery, Logger, CORS, handler) 的执行顺序是：
// Recovery → Logger → CORS → handler（请求进入）→ handler → CORS → Logger → Recovery（响应返回）
func Chain(middlewares ...func(http.Handler) http.Handler) func(http.Handler) http.Handler {
    return func(final http.Handler) http.Handler {
        for i := len(middlewares) - 1; i >= 0; i-- {
            final = middlewares[i](final)
        }
        return final
    }
}
```

> **为什么链式组合如此优雅？** 每个中间件只做一件事（日志、恢复、跨域），它们可以像积木一样自由组合。需要添加新功能？写一个新中间件插进去即可。需要暂时关闭某个功能？把它从链中移除。这就是"关注点分离"的威力——每个模块都独立、可测试、可替换。

## 8.6 整合与测试

### main 函数：组装各层

`main` 函数是整个应用的"组装车间"——在这里，我们把 Repository、Service、Handler 各层连接起来，启动 HTTP 服务器。

```go
// main.go
package main

import (
    "fmt"
    "log"
    "net/http"
    "os"

    "todo-api/handler"
    "todo-api/middleware"
    "todo-api/repository"
    "todo-api/service"
)

func main() {
    // 第一层：创建数据存储（Repository）
    repo := repository.NewMemoryRepo()

    // 第二层：创建业务逻辑（Service），注入 Repository
    svc := service.NewService(repo)

    // 第三层：创建 HTTP 处理器（Handler），注入 Service
    h := handler.NewHandler(svc)

    // 创建路由多路复用器并注册路由
    mux := http.NewServeMux()
    h.RegisterRoutes(mux)

    // 应用中间件链：Recovery → Logger → CORS → 路由
    // 注意：Recovery 放在最外层，这样任何层的 panic 都能被捕获
    chain := middleware.Chain(
        middleware.Recovery,
        middleware.Logger,
        middleware.CORS,
    )
    wrappedMux := chain(mux)

    // 从环境变量获取端口，默认 8080
    port := os.Getenv("PORT")
    if port == "" {
        port = "8080"
    }

    addr := fmt.Sprintf(":%s", port)
    log.Printf("Server starting on %s", addr)

    // 启动 HTTP 服务器
    // &http.Server 允许我们配置超时、最大请求头等参数
    server := &http.Server{
        Addr:    addr,
        Handler: wrappedMux,
    }

    if err := server.ListenAndServe(); err != nil {
        log.Fatalf("Server failed to start: %v", err)
    }
}
```

> **Go 的依赖注入不需要框架。** 在 Java 世界里，Spring 框架通过注解（@Autowired）和反射来自动注入依赖。而 Go 的哲学是"显式优于隐式"——我们直接在 main 函数中手动创建对象并传递依赖，代码清晰透明，没有任何"魔法"。对于一个中等规模的项目来说，这种方式完全够用。

### 编写单元测试

Go 的测试哲学是"简单、内置、够用"。不需要 JUnit 或 pytest，标准库的 `testing` 包就足够强大。我们使用"表驱动测试"（Table-Driven Tests）来组织多个测试用例。

```go
// handler/handler_test.go
package handler

import (
    "bytes"
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "testing"

    "todo-api/model"
    "todo-api/repository"
    "todo-api/service"
)

// setupTest 创建测试用的 Handler（带独立的内存存储）
func setupTest() *Handler {
    repo := repository.NewMemoryRepo()
    svc := service.NewService(repo)
    return NewHandler(svc)
}

// TestCreateTodo 测试创建待办事项
// 使用表驱动测试：一个测试函数覆盖多个场景
func TestCreateTodo(t *testing.T) {
    h := setupTest()

    // 定义测试用例表
    tests := []struct {
        name       string           // 测试用例名称
        body       interface{}      // 请求体
        wantStatus int              // 期望的 HTTP 状态码
    }{
        {
            name:       "成功创建",
            body:       model.CreateTodoRequest{Title: "学习 Go"},
            wantStatus: http.StatusCreated,
        },
        {
            name:       "缺少标题",
            body:       model.CreateTodoRequest{Title: ""},
            wantStatus: http.StatusBadRequest,
        },
        {
            name:       "无效 JSON",
            body:       "invalid json",
            wantStatus: http.StatusBadRequest,
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // 将请求体序列化为 JSON
            body, _ := json.Marshal(tt.body)

            // httptest.NewRequest 创建一个模拟的 HTTP 请求
            // 它不会真正发送网络请求，只是在内存中构造一个 *http.Request
            req := httptest.NewRequest(http.MethodPost, "/todos", bytes.NewReader(body))
            req.Header.Set("Content-Type", "application/json")

            // httptest.NewRecorder 创建一个模拟的 ResponseWriter
            // 它会把响应记录在内存中，方便我们检查
            rec := httptest.NewRecorder()

            // 调用 Handler
            h.CreateTodo(rec, req)

            // 验证状态码
            if rec.Code != tt.wantStatus {
                t.Errorf("expected status %d, got %d", tt.wantStatus, rec.Code)
            }
        })
    }
}

// TestGetTodo 测试获取单条待办事项
func TestGetTodo(t *testing.T) {
    h := setupTest()

    // 先创建一条待办事项
    body, _ := json.Marshal(model.CreateTodoRequest{Title: "测试项目"})
    req := httptest.NewRequest(http.MethodPost, "/todos", bytes.NewReader(body))
    rec := httptest.NewRecorder()
    h.CreateTodo(rec, req)

    // 解析创建响应，获取 ID
    var createResp Response
    json.Unmarshal(rec.Body.Bytes(), &createResp)
    // Data 是 interface{}，需要类型断言后提取 ID
    dataMap, ok := createResp.Data.(map[string]interface{})
    if !ok {
        t.Fatal("failed to parse response data")
    }
    id := dataMap["id"].(string)

    // 测试：获取存在的待办事项
    t.Run("获取存在的记录", func(t *testing.T) {
        req := httptest.NewRequest(http.MethodGet, "/todos/"+id, nil)
        // 模拟路由参数（因为在测试中不经过 ServeMux 路由）
        req.SetPathValue("id", id)
        rec := httptest.NewRecorder()

        h.GetTodo(rec, req)

        if rec.Code != http.StatusOK {
            t.Errorf("expected status 200, got %d", rec.Code)
        }
    })

    // 测试：获取不存在的待办事项
    t.Run("获取不存在的记录", func(t *testing.T) {
        req := httptest.NewRequest(http.MethodGet, "/todos/nonexistent", nil)
        req.SetPathValue("id", "nonexistent")
        rec := httptest.NewRecorder()

        h.GetTodo(rec, req)

        if rec.Code != http.StatusNotFound {
            t.Errorf("expected status 404, got %d", rec.Code)
        }
    })
}
```

> **`httptest` 包的精髓。** `httptest.NewRecorder` 创建了一个"假的"ResponseWriter，它把所有响应数据（状态码、Header、Body）都记录在内存中。结合 `httptest.NewRequest`，我们可以在不启动真正 HTTP 服务器的情况下测试 Handler，速度极快，也不依赖网络。

go test ./... -v

# 运行测试并显示覆盖率

## 8.7 编译、运行与部署

### Makefile 编写

Makefile 是项目的"操作手册"——把所有常用命令集中在一个文件里，团队成员不需要记住复杂的命令参数。

```makefile
# Makefile
# .PHONY 声明这些是"伪目标"，不是真正的文件名
.PHONY: build run test clean

# 应用名称和版本
APP_NAME = todo-api
VERSION = 1.0.0

# 编译项目
build:
	go build -ldflags "-X main.version=$(VERSION)" -o bin/$(APP_NAME) .

# 运行项目
run:
	go run .

# 运行测试（带覆盖率）
test:
	go test ./... -v -cover

# 清理编译产物
clean:
	rm -rf bin/

# 交叉编译：编译为 Linux 可执行文件（用于 Docker 部署）
build-linux:
	GOOS=linux GOARCH=amd64 go build -o bin/$(APP_NAME)-linux .

# 交叉编译：编译为 Windows 可执行文件
build-windows:
	GOOS=windows GOARCH=amd64 go build -o bin/$(APP_NAME).exe .

# 交叉编译：编译为 macOS（Apple Silicon）可执行文件
build-darwin:
	GOOS=darwin GOARCH=arm64 go build -o bin/$(APP_NAME)-darwin .
```

> **什么是交叉编译？** Go 的一个杀手级特性是可以在你的电脑上编译出任何平台的可执行文件。在 Windows 上设置 `GOOS=linux` 就能编译出 Linux 程序，不需要一台 Linux 机器。这在部署到服务器或容器时极其方便。

### Docker 化：多阶段构建

Docker 多阶段构建的思想是：用一个"大"镜像来编译代码，然后把编译出的二进制文件复制到一个"小"镜像中运行。最终的镜像只有几十 MB，安全又轻量。

```dockerfile
# Dockerfile

# ===== 第一阶段：编译 =====
# 使用完整的 Go 镜像（约 800MB），包含编译器和工具链
FROM golang:1.22-alpine AS builder

WORKDIR /app

# 先复制 go.mod 和 go.sum，利用 Docker 缓存层
# 如果依赖没变，下次构建会直接使用缓存，跳过 go mod download
COPY go.mod go.sum ./
RUN go mod download

# 再复制源代码并编译
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o todo-api .

# ===== 第二阶段：运行 =====
# 使用极小的 Alpine 镜像（约 5MB）作为运行时
FROM alpine:latest

RUN apk --no-cache add ca-certificates

WORKDIR /root/

# 只从 builder 阶段复制编译好的二进制文件
COPY --from=builder /app/todo-api .

# 暴露服务端口
EXPOSE 8080

# 设置环境变量
ENV PORT=8080

# 启动服务
CMD ["./todo-api"]
```

## 8.8 项目总结与进阶方向

### 回顾项目架构

让我们站高一点，俯瞰整个项目的架构：

```
客户端请求
    ↓
[CORS 中间件] → 处理跨域
    ↓
[Logger 中间件] → 记录日志
    ↓
[Recovery 中间件] → 捕获 panic
    ↓
[Router (ServeMux)] → 路由匹配
    ↓
[Handler] → 解析请求、格式化响应
    ↓
[Service] → 业务逻辑、输入验证
    ↓
[Repository] → 数据存储
```

每一层都有清晰的职责边界：Handler 管 HTTP 细节，Service 管业务规则，Repository 管数据存取。这种设计让代码易于理解、易于测试、易于扩展。

### 关键设计决策回顾

1. **面向接口编程**：Repository 定义了接口，使得 Service 层不依赖具体的存储实现。未来要换数据库？实现一个新的 Repository 即可。
2. **分层架构**：每一层只知道上一层和下一层的接口，降低了模块之间的耦合。
3. **统一错误处理**：Service 层定义语义化的错误类型，Handler 层负责将错误映射为 HTTP 状态码。
4. **中间件链**：把日志、恢复、跨域等"横切关注点"抽取为中间件，不污染业务代码。
5. **依赖注入**：在 main 函数中显式组装各层依赖，代码透明无魔法。

### 推荐的第三方库

当你准备将这个项目用于生产环境时，以下库可以大幅提升开发效率：

| Web 框架 | [Echo](https://github.com/labstack/echo) | 极简设计，文档友好 |
| ORM | [GORM](https://gorm.io/) | Go 最流行的 ORM，支持多种数据库 |
| 日志 | [Zap](https://github.com/uber-go/zap) | Uber 出品，极速结构化日志库 |
| 配置 | [Viper](https://github.com/spf13/viper) | 支持 YAML/JSON/环境变量等多种配置源 |
| 验证 | [Validator](https://github.com/go-playground/validator) | 基于 struct tag 的输入验证 |
| UUID | [UUID](https://github.com/google/uuid) | Google 出品的 UUID 生成库 |

> **什么时候该用框架？** 当你发现自己在重复造轮子——写路由、写参数绑定、写错误处理——的时候。标准库是学习的好材料，但生产环境中框架能节省大量时间。不过要记住：框架是工具，不是信仰。理解底层原理之后，选择最适合的工具即可。

### 进阶学习方向

完成这个项目只是起点。以下是你可以继续探索的方向：

1. **数据库集成**：将内存存储替换为 PostgreSQL 或 MySQL，学习 SQL 和 ORM 的使用。
2. **认证与授权**：实现 JWT（JSON Web Token）认证，保护 API 不被未授权访问。
3. **微服务架构**：将 Todo 服务拆分为更小的服务，通过 gRPC 或消息队列通信。
4. **gRPC**：Google 的高性能 RPC 框架，比 REST 更快、类型更安全。
5. **消息队列**：使用 NATS 或 RabbitMQ 实现异步处理，解耦服务之间的通信。
6. **容器编排**：学习 Kubernetes，将多个服务编排成一个可伸缩的系统。

### 从"学习语言"到"用语言构建系统"

到这里，你已经不再是一个"学习 Go 语法"的初学者了。你构建了一个具有完整分层架构、中间件机制、错误处理、单元测试和容器化部署的 API 服务。这个过程中，你学到的不仅是 Go 语言的语法，更是软件工程的思维方式：

- **接口是契约**：定义好边界，让模块之间松耦合。
- **简单优于复杂**：Go 不追求花哨的特性，而是追求清晰可维护的代码。
- **关注点分离**：每一层只做一件事，做好一件事。
- **显式优于隐式**：没有魔法，没有注解驱动的黑盒，一切清晰透明。

编程的真正乐趣不在于记住了多少语法，而在于用代码解决真实问题的能力。希望这个项目能成为你 Go 语言之旅的一个里程碑——从这里开始，去构建更大的系统吧。
