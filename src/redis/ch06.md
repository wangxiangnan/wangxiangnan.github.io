# 第6章：持久化——让数据活过重启

## 引言：给内存数据买个"保险"

Redis 的数据在内存里，快是真的快，但有个致命问题：**断电即失**。

想象你写了一天的代码忘记 Ctrl+S，然后电脑蓝屏了。Redis 如果不做持久化，重启服务器后所有数据清零——就像那个没保存的文档。

Redis 提供了两种持久化方式，就像两种不同的"存档"策略：

- **RDB**：定期拍快照，就像游戏里的"存档点"
- **AOF**：记录每一条写操作，就像游戏的"自动录像"
- **混合持久化**：两种策略结合，取长补短

## 6.1 RDB（Redis Database Snapshot）

RDB 是最传统的持久化方式——在某个时间点，把内存中的所有数据"拍一张照片"保存到磁盘。

**编程比喻**：RDB 就像 Git 的 `commit`——每次 `commit` 都是一个完整的快照。你不需要知道每次修改了什么，只需要知道最终状态。

### 手动触发

```js
const Redis = require('ioredis');
const redis = new Redis();

async function rdbDemo() {
  // 写入一些数据
  await redis.set('persist:test1', 'value1');
  await redis.set('persist:test2', 'value2');
  await redis.hset('persist:user', 'name', 'Alice', 'age', '25');

  // ========== SAVE：同步保存（会阻塞 Redis！） ==========
  // 注意：生产环境千万不要用 SAVE，会阻塞所有请求！
  // await redis.save();

  // ========== BGSAVE：异步保存（推荐） ==========
  // Redis 会 fork 一个子进程来做快照，主进程继续处理请求
  const result = await redis.bgsave();
  console.log('BGSAVE 结果：', result); // "Background saving started"

  // ========== LASTSAVE：查看最后一次成功保存的时间戳 ==========
  const lastSave = await redis.lastsave();
  console.log('最后保存时间：', new Date(lastSave * 1000).toISOString());

  // ========== DBSIZE：查看当前数据库的 Key 数量 ==========
  const dbSize = await redis.dbsize();
  console.log('当前 Key 数量：', dbSize);

  // ========== FLUSHDB / FLUSHALL：清空数据（危险操作！） ==========
  // await redis.flushdb();  // 清空当前数据库
  // await redis.flushall(); // 清空所有数据库

  // 等待一下让 BGSAVE 完成
  await new Promise(resolve => setTimeout(resolve, 2000));

  // 再次检查 LASTSAVE
  const newLastSave = await redis.lastsave();
  console.log('BGSAVE 后保存时间：', new Date(newLastSave * 1000).toISOString());

  // 清理
  await redis.del('persist:test1', 'persist:test2', 'persist:user');
  await redis.quit();
}

rdbDemo();
```

### 自动触发条件（save 配置）

Redis 可以在 `redis.conf` 中配置自动触发 RDB 的条件：

```bash
# redis.conf 中的 save 配置
# 格式：save <seconds> <changes>
# 含义：在 <seconds> 秒内，如果有 <changes> 个 Key 发生变化，就自动执行 BGSAVE

save 900 1       # 900秒（15分钟）内至少有1个Key变化
save 300 10      # 300秒（5分钟）内至少有10个Key变化
save 60 10000    # 60秒（1分钟）内至少有10000个Key变化

# 多个条件是"或"的关系——满足任意一个就触发
```

> [!TIP] 提示
> ：如果你只想用 AOF 而不需要 RDB，可以配置 `save ""` 来禁用自动 RDB。

### RDB 的优点和缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑，适合备份和灾难恢复 | 两次快照之间的数据可能丢失 |
| 恢复速度快（直接加载到内存） | fork 大内存进程时可能卡顿 |
| 对主进程性能影响小（子进程处理） | 不是实时的，有数据丢失风险 |
| 文件可以传输到其他服务器 | - |

## 6.2 AOF（Append Only File）

AOF 的思路完全不同——它不拍快照，而是**记录每一条写命令**。

**编程比喻**：AOF 就像数据库的操作日志（Operation Log）或 Git 的 reflog——它记录了"你做了什么"，而不是"现在是什么"。通过回放所有操作，就能还原出最终状态。

```
# AOF 文件内容示例（实际格式）
*2\r\n$6\r\nSELECT\r\n$1\r\n0\r\n
*3\r\n$3\r\nSET\r\n$4\r\nname\r\n$5\r\nAlice\r\n
*3\r\n$3\r\nSET\r\n$3\r\nage\r\n$2\r\n25\r\n
*2\r\n$4\r\nINCR\r\n$3\r\nage\r\n
```

### AOF 的工作原理

```
客户端 → SET name "Alice" → Redis
                              ├── 写入内存 ✅
                              ├── 追加到 AOF 文件 ✅
                              └── 返回 OK ✅

重启时：
Redis 启动 → 读取 AOF 文件 → 逐条执行命令 → 内存恢复到关闭前的状态
```

### appendfsync 策略

AOF 的写入策略决定了"多实时"和"多安全"之间的权衡：

| 策略 | 行为 | 性能 | 数据安全性 |
|------|------|------|-----------|
| **always** | 每条命令都立即写入磁盘 | 最慢 | 最安全（最多丢1条） |
| **everysec** | 每秒写入一次 | 中等 | 较安全（最多丢1秒） |
| **no** | 由操作系统决定何时写入 | 最快 | 最不安全（可能丢很多） |

```bash
# redis.conf
appendonly yes              # 开启 AOF
appendfsync everysec        # 推荐：每秒同步一次
# appendfsync always        # 最安全但最慢
# appendfsync no            # 最快但最不安全
```

> [!TIP] 提示
> ：绝大多数场景使用 `everysec` 就够了。它在性能和安全性之间取得了很好的平衡——最多丢失 1 秒的数据，对大多数应用来说可以接受。

### AOF 重写（BGREWRITEAOF）

随着时间推移，AOF 文件会越来越大。比如你对同一个 Key 执行了 100 次 INCR，AOF 里就记录了 100 条命令，但实际上只需要最后一条 SET 就够了。

AOF 重写就是 Redis 的"压缩"操作——它在后台 fork 一个子进程，根据当前内存状态生成一个"最精简"的 AOF 文件。

```js
const Redis = require('ioredis');
const redis = new Redis();

async function aofDemo() {
  // 写入一些数据
  for (let i = 0; i < 100; i++) {
    await redis.incr('aof:counter');
  }
  // 此时 AOF 文件里有 100 条 INCR 命令

  // 触发 AOF 重写
  const result = await redis.bgrewriteaof();
  console.log('AOF 重写结果：', result);

  // 重写后，AOF 文件里只有 1 条命令：SET aof:counter 100
  // 文件大小大幅减小！

  // 查看 AOF 相关信息
  const info = await redis.info('persistence');
  console.log('\n持久化信息（部分）：');
  info.split('\n').forEach(line => {
    if (line.includes('aof') || line.includes('rdb')) {
      console.log('  ', line.trim());
    }
  });

  await redis.del('aof:counter');
  await redis.quit();
}

aofDemo();
```

自动重写配置：

```bash
# redis.conf
# 当 AOF 文件比上次重写后增长了 100% 时，自动触发重写
auto-aof-rewrite-percentage 100

# AOF 文件至少达到 64MB 才触发重写（避免小文件频繁重写）
auto-aof-rewrite-min-size 64mb
```

## 6.3 混合持久化（Redis 4.0+）

Redis 4.0 引入了混合持久化——结合了 RDB 和 AOF 的优点。

工作原理：

1. AOF 重写时，**先以 RDB 格式写入当前数据快照**
2. **再以 AOF 格式追加重写期间的新命令**

```
混合持久化文件结构：
[RDB 快照数据][AOF 增量命令]
^^^^^^^^^^^^^^^^^^^^^^^^^^^^
恢复时：先加载 RDB 部分（快），再回放 AOF 部分（补上最新数据）
```

优点：

- 恢复速度接近 RDB（大部分数据以 RDB 格式存储）
- 数据安全性接近 AOF（增量数据实时记录）
- 文件体积比纯 AOF 小得多

```bash
# redis.conf（Redis 5.0+ 默认开启）
aof-use-rdb-preamble yes
```

## 6.4 持久化策略选择指南

| 场景 | 推荐策略 | 配置 |
|------|----------|------|
| 纯缓存（丢了无所谓） | 都不开 | `save ""` + `appendonly no` |
| 允许丢失几分钟数据 | 仅 RDB | `save 300 10` + `appendonly no` |
| 允许丢失1秒数据 | 仅 AOF | `save ""` + `appendonly yes` + `appendfsync everysec` |
| 要求最小数据丢失 | AOF always | `save ""` + `appendonly yes` + `appendfsync always` |
| 兼顾性能和安全（推荐） | 混合持久化 | RDB + AOF + `aof-use-rdb-preamble yes` |

> [!WARNING] 注意
> Redis 官方推荐同时开启 RDB 和 AOF。RDB 用于灾难恢复（定期备份到远程存储），AOF 用于日常持久化。两者互为补充。

## 6.5 Node.js 中监控持久化事件

```js
const Redis = require('ioredis');
const redis = new Redis();

async function monitorPersistence() {
  // ========== 监控持久化相关事件 ==========

  // 使用 MONITOR 命令监听所有命令（调试用，生产别开！）
  // const monitor = await redis.monitor();
  // monitor.on('monitor', (time, args, rawReply) => {
  //   if (args[0] === 'BGSAVE' || args[0] === 'BGREWRITEAOF') {
  //     console.log(`[持久化事件] ${args[0]} at ${new Date(time * 1000)}`);
  //   }
  // });

  // ========== 获取持久化状态信息 ==========
  const info = await redis.info('persistence');

  const parseInfo = (infoStr) => {
    const result = {};
    infoStr.split('\n').forEach(line => {
      const trimmed = line.trim();
      if (trimmed && !trimmed.startsWith('#')) {
        const [key, value] = trimmed.split(':');
        if (key && value) result[key] = value;
      }
    });
    return result;
  };

  const persistInfo = parseInfo(info);

  console.log('=== Redis 持久化状态 ===');
  console.log(`RDB 最后保存状态：${persistInfo.rdb_last_bgsave_status}`);
  console.log(`RDB 最后保存时间：${new Date(parseInt(persistInfo.rdb_last_save_time) * 1000).toISOString()}`);
  console.log(`RDB 当前是否正在保存：${persistInfo.rdb_bgsave_in_progress === '1' ? '是' : '否'}`);
  console.log(`AOF 是否开启：${persistInfo.aof_enabled === '1' ? '是' : '否'}`);

  if (persistInfo.aof_enabled === '1') {
    console.log(`AOF 文件大小：${persistInfo.aof_current_size} bytes`);
    console.log(`AOF 最后重写状态：${persistInfo.aof_last_bgrewrite_status}`);
    console.log(`AOF 重写是否进行中：${persistInfo.aof_rewrite_in_progress === '1' ? '是' : '否'}`);
  }

  // ========== 监控服务器事件（Redis 7.0+） ==========
  // 使用 Redis 的 Keyspace Notifications 来监控特定事件
  // 需要先开启通知
  await redis.config('set', 'notify-keyspace-events', 'KEA');

  // 创建订阅连接
  const subscriber = new Redis();

  // 订阅所有 Key 的事件
  subscriber.subscribe('__keyevent@0__:*');

  subscriber.on('message', (channel, message) => {
    console.log(`[Keyspace通知] ${channel}: ${message}`);
  });

  // 触发一些操作来产生事件
  console.log('\n--- 触发操作 ---');
  await redis.set('notify:test', 'hello');
  await redis.expire('notify:test', 2);
  await redis.set('notify:test2', 'world');
  await redis.del('notify:test2');

  // 等待事件到达
  await new Promise(resolve => setTimeout(resolve, 3000));

  // 清理
  await subscriber.unsubscribe();
  await subscriber.quit();
  await redis.del('notify:test');
  await redis.config('set', 'notify-keyspace-events', '');
  await redis.quit();
}

monitorPersistence();
```

## 6.6 持久化最佳实践

### 备份策略

```bash
# 1. 定期复制 RDB 文件到远程存储
# crontab: 每小时备份一次 RDB 文件
# 0 * * * * cp /var/lib/redis/dump.rdb /backup/redis/dump-$(date +\%Y\%m\%d\%H).rdb

# 2. 使用 S3/rsync 同步到远程
# aws s3 cp /var/lib/redis/dump.rdb s3://my-backup-bucket/redis/dump-$(date +%Y%m%d).rdb

# 3. 保留策略：保留最近7天的每日备份 + 最近4周的每周备份
```

### 数据恢复

```js
// 恢复数据不需要代码操作，只需要：
// 1. 停止 Redis
// 2. 将备份的 RDB 文件复制到 Redis 数据目录
//    cp /backup/redis/dump-20231015.rdb /var/lib/redis/dump.rdb
// 3. 启动 Redis
// 4. 数据自动加载

// 如果使用 AOF：
// 1. 停止 Redis
// 2. 将 AOF 文件复制到 Redis 数据目录
//    cp /backup/redis/appendonly.aof /var/lib/redis/appendonly.aof
// 3. 启动 Redis（Redis 会优先加载 AOF）
// 4. 可以使用 redis-cli --rdb 或 redis-check-aof 检查文件完整性
```

### Docker 环境下的持久化

```bash
# 确保挂载了数据卷
docker run -d \
  --name redis-persistent \
  -p 6379:6379 \
  -v redis-data:/data \
  redis:7-alpine \
  redis-server \
  --appendonly yes \
  --appendfsync everysec \
  --save 900 1 \
  --save 300 10 \
  --save 60 10000

# 手动触发 BGSAVE
docker exec redis-persistent redis-cli BGSAVE

# 查看 RDB 文件
docker exec redis-persistent ls -la /data/

# 备份 RDB 文件到宿主机
docker cp redis-persistent:/data/dump.rdb ./backup/dump.rdb
```

## 6.7 RDB vs AOF 终极对比

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 存储内容 | 数据快照 | 写命令日志 |
| 文件大小 | 小（二进制压缩） | 大（文本命令） |
| 恢复速度 | 快（直接加载） | 慢（逐条回放） |
| 数据安全 | 可能丢失最后一次快照后的数据 | 最多丢失 1 秒数据（everysec） |
| 写入性能 | 影响小（子进程） | always 模式影响大 |
| 适用场景 | 备份、灾难恢复 | 日常持久化 |
| 类比 | Git commit | 操作日志 / WAL |

## 6.8 小结

> **RDB 是存档点，AOF 是自动录像，混合持久化是两者兼得**

- **RDB**：定时快照，文件小、恢复快，但可能丢数据。像 Git commit。
- **AOF**：记录每条写命令，实时性好但文件大。像操作日志。
- **混合持久化**：AOF 重写时用 RDB 格式 + AOF 增量，两全其美。
- `BGSAVE` 比 `SAVE` 安全（不阻塞主进程），生产环境永远用 `BGSAVE`
- `appendfsync everysec` 是性价比最高的 AOF 策略
- 定期备份 RDB 文件到远程存储，这是你的"最后保险"

2. **对比题**：分别用 RDB-only 和 AOF-only 模式写入 10000 条数据，对比 `/data/dump.rdb` 和 `/data/appendonly.aof` 的文件大小。
