# 第14章：排错手册与安全复盘

> [!TIP] Part 3: CA 与 TLS 实战篇（实战篇）
> 全书收官章。前十三章的知识在这一章汇成两样可以带走的资产：一本报错字典（出了问题查它）与一份加固清单（没事的时候照它）。读完它，四个里程碑的最后一格画上勾。

排错能力是密码学工具学习的毕业考——语法可以查手册，判断力只能靠体系。本章先给方法（四层定位法），再给弹药（报错字典），然后重走五个真实破案现场；后半程是「不出事时的纪律」（加固清单）与「出事时的剧本」（应急预案与季度演练），最后用全书复盘收尾。

## 14.1 排错方法论：四层定位法

TLS 报错的混乱感，来自「网络、协议、证书、密钥」四层问题共用一套报错词汇。破案第一步永远是**分层定位**，自上而下排查，每层一个探针动作：

```text
第1层  连通层    端口通不通、SNI 带没带
        探针: s_client 报错前有没有走到握手
第2层  协议层    两端协议/套件有没有交集
        探针: s_client -tls1_2 / -tls1_3 强制探测
第3层  证书层    链全不全、时间对不对、SAN 配不配
        探针: Verify 码 + depth + x509 -text
第4层  密钥层    私钥口令、配对关系、格式
        探针: 公钥指纹比对 + grep BEGIN
```

两条铁律放在最前面。**铁律一：先跑 `openssl version`**——不同版本行为差异可以吃掉半小时（第1章的教训，此处成为军规）。**铁律二：任何「时好时坏」先怀疑链与 SNI**——桌面浏览器会自动补链、会按域名挑证书，curl/Java/手机不会，于是同一台服务器出现「这台机器好好的那台不行」的灵异现象，真相往往是不同客户端的补链能力不同（第11章）。

动手之前，信息收集是排错的一部分。五件事先记全，能省掉一半来回：

| 要收集 | 为什么 |
| ---- | ---- |
| 报错原文（一字不差） | 关键字是字典的钥匙，转述会丢掉 depth 与错误码 |
| 发生时间点（精确到分） | 对日志、对证书有效期、对部署记录全靠它 |
| 完整命令与版本 | `openssl version` 加原样命令——参数差异本身就是常见病因 |
| 影响面（谁行谁不行） | 「浏览器行手机不行」这类差异就是线索（铁律二的另一半） |
| 能否复现 | 可复现的故障是朋友，不可复现的才是敌人 |

五个问题排查无效、需要向外部求助（社区、厂商、更有经验的同事）时，求助帖的质量决定回答的质量：把上面五件事加上**最小复现命令**与**相关配置节选**一次性给全——第4章说过日志的读者面很广，求助时同理：信息给得越完整，别人越不用猜。

## 14.2 报错字典

全书出现过的报错，按排查频率与出现场景收拢成一张字典。用法：先搜报错关键字，再看「层」列对回 14.1 的定位法，最后按处置动作执行。

| 报错关键字 | 层 | 病因 | 处置 |
| ---- | ---- | ---- | ---- |
| `unable to get local issuer certificate` | 证书 | 客户端缺根证书，或服务器缺中间证书 | 客户端装 root.crt；服务器补 fullchain（第11章） |
| `self-signed certificate`（链中含自签） | 证书 | 自签/内部证书未被信任 | `--cacert` 单点信任，或导入信任库（第9、11章） |
| `certificate has expired` | 证书 | 到期未换 | 轮换证书；部署到期监控（第12章） |
| `certificate is not yet valid` | 证书 | 证书未生效或**本机时间不对** | 先查系统时间与 NTP，再查证书 |
| `subject name mismatch`（域名不匹配） | 证书 | SAN 不含目标域名，或没带 SNI 拿错证书 | 重签补 SAN；`s_client` 补 `-servername` |
| `key values mismatch` | 密钥 | 证书与私钥不配对 | 公钥指纹比对法换对文件（第6章） |
| `no start line` / `Expecting: ...` | 格式 | 编码（DER/PEM）或结构不对 | `grep BEGIN` 验货；补 `-inform DER`（第6章） |
| `Could not read private key`（无细节） | 格式 | 私钥加密但没给口令 | 补 `-passin` |
| `tlsv1 alert protocol version` | 协议 | 两端协议版本交集为空 | 对齐 `ssl_protocols`；升级过老客户端 |
| `sslv3 alert handshake failure` | 协议 | 套件无交集、缺 SNI、或服务器要求客户端证书 | 补 `-servername`；mTLS 场景补 `-cert -key` |
| `peer did not return a certificate` | 协议 | mTLS 下客户端未出示证书 | 客户端持证再连（第13章） |
| `AEAD ciphers not supported` | 工具 | `enc` 不支持 GCM（能力边界） | CBC + HMAC 组合（第3章） |
| 某算法报 `unsupported`（3.x） | 工具 | 算法被关进 legacy provider | 原则上不救活；确需老算法时显式 `-provider legacy` |
| `bad decrypt` | 对称 | 口令错，或 `-pbkdf2`/`-iter` 参数与加密时不一致 | 查加密时的参数记录，一字不差地复现 |
| `mac verify failure` | 密钥 | **p12 容器**的口令不对（MAC 校验先失败） | 确认口令与导出时一致（第6章） |
| `bad decrypt` + `maybe wrong password` | 密钥 | **加密私钥 PEM**（PKCS#8）口令不对（第5章实测栈） | 确认口令与加密时一致（第5章） |
| HMAC 重算对不上 | 对称 | HMAC 密钥与算摘要时不一致，或数据被改 | **先当事故查**，再核对密钥文件与环境变量（第2章） |
| `wrong final block length` | 对称 | 密文被截断、换行破坏或编码转换出错 | 检查传输链路是否动过文件（第3、4章） |
| `Verification failure`（签名） | 签名 | 文件被改、公钥拿错、哈希参数不一致 | **先当事故查**，再查参数（第7章） |
| `self-signed certificate in certificate chain` | 证书 | 链里混进了自签证书（p12 打包多带根、服务器把根也发了） | 清理链文件；确认信任的根是预期那张（第11章） |
| `error N at M depth lookup: ...` | 证书 | verify 的标准报错格式 | depth M 就是断点：0 叶子、1 中间、2 根（第11章） |
| `keystore password was incorrect` | 工具 | p12 用了 3.x 新加密，老 Java/Windows 打不开（或口令真错了） | 先确认口令；再补 `-legacy` 重打包（第6章） |
| `unable to load key file` | 格式 | 文件不存在、无权限或格式不符 | `ls -l` 看权限，`grep BEGIN` 看头行（第6章） |
| 浏览器红牌 `ERR_CERT_*` | 证书 | 浏览器的说法不同，病根同一批 | 用 s_client 拿 OpenSSL 侧报错，回本表对号（第9章） |

字典覆盖不了的长尾问题，标准动作是拿探针收窄：`s_client` 全量输出从头读——五段结构（第12章）里总有一段与现实预期不符，不符的那段就是案发现场。

查字典也有标准姿势，走一遍示范：假设日志里出现 `certificate verify failed`——

1. 搜关键字，命中证书层一串条目；
2. 看「层」列 → 证书层，回 14.1 调第 3 层探针；
3. `echo | openssl s_client -connect host:443 -servername host 2>/dev/null | grep -E "Verify|depth"`；
4. 拿到 Verify 码与 depth，回字典（和下面的返回码表）定处置。

四步走完，大多数现场已经从「一团乱麻」收敛成「一个待办动作」。Verify 返回码是 OpenSSL 侧的「行话」，最高频的十个单独列一张：

| Verify 码 | 含义 |
| ---- | ---- |
| 0 | `ok` |
| 2 | unable to get issuer certificate（缺中间或缺根） |
| 7 | certificate signature failure（签名验不过——链被调包过） |
| 9 | certificate not yet valid（未生效/本机时间不对） |
| 10 | certificate has expired（到期） |
| 18 | self signed certificate（自签未被信任） |
| 20 | unable to get local issuer certificate（客户端找不到签发者） |
| 21 | unable to verify the first certificate（链不完整，到不了信任锚） |
| 23 | certificate revoked（已撤销） |
| 26 | unsupported certificate purpose（EKU 用途不符） |

最后一步永远是「修复后复跑探针」——而且按第13章的纪律，负向用例（该拒绝的场景）也要过一遍，才算真修好。

## 14.3 五个破案现场

方法与字典是抽象的，现场是具体的。重走云笔记的五个真实案例，每个都用上「定位法 + 探针 + 字典」的组合拳。

**现场一：凌晨 40 分钟（危机三正传）。** 症状：全站浏览器红牌 `ERR_CERT_DATE_INVALID`，应用日志干净。破案：值班工程师若先跑 `s_client`，第⑤段 `Verify return code: 10 (certificate has expired)` 一分钟定罪——而现实中绕了 20 分钟应用层。复盘动作：到期监控（12.4）+ 60 天自动轮换（10.5），事故不再可能。**教训：分层定位法能救命，前提是它长在肌肉里而不是文档里。**

**现场二：浏览器正常，手机报错。** 症状：办公室里桌面浏览器访问 api 一切正常，同事的手机与 CI 里的 Java 构建全部报 `unable to get local issuer certificate`。破案：`-showcerts` 数链张数——只发了 1 张（裸叶子），而公网 CA 是三级链，缺中间证书；Windows 系的 Chrome/Edge 靠 AIA 自动补链掩盖了问题（Firefox 不拉 AIA，手机与 Java 更没这份好脾气）。处置：组装 fullchain（第11章）、nginx 换用、体检清单新增「链张数」项。**教训：浏览器的好脾气不是健康标准，探针才是。**

**现场三：mTLS 集体掉线。** 症状：某次给 notify 重签客户端证书后，它调 auth 全部被拒，报 `sslv3 alert handshake failure`。破案：用 s_client 持新证书模拟 notify 连接，服务端拒绝；对比旧证书的扩展发现——重签时 extfile 漏了 `extendedKeyUsage = clientAuth`，nginx 的 `ssl_verify_client` 直接不认。处置：Client CA 的签发脚本固化为模板（serverAuth 与 clientAuth 分属两个 extfile），防止手滑。**教训：模板化是给「手滑」上的锁，签发脚本宁可笨一点，不要灵活到能漏参数。**

**现场四：周一早上的集体红牌。** 症状：周一上班全组浏览器红牌 `certificate is not yet valid`，可证书明明上周才签的。破案：字典第四行的加粗提示——本机时间不对。`date` 一看，周末机房断电重启后 NTP 没同步成功，系统时间停在三天前。处置：修时间源，监控里追加「系统时间漂移」告警。**教训：证书层的报错未必是证书的病——系统时间是最常见的「别人的病」。**

**现场五：30 张证书的续期雪崩。** 症状：季度末批量轮换，auth 换完一切正常，notify 换完客户端开始报域名不匹配。破案：`x509 -noout -ext subjectAltName` 对比新旧证书——批量脚本里 SAN 变量在循环间被上一次的值污染（shell 变量未清空）。处置：修 bug 之外，把第12章体检脚本接进轮换流程——新证书上线前自动体检，异常即中止。**教训：批量操作没有体检闸门，等于把单点故障放大成批量故障。**

> [!WARNING] 排错的两条禁忌
> 一忌「改到通过为止」：安全报错（验签失败、证书校验失败）的正确第一反应是当事故查，把报错改「消失」不等于把问题修「正确」（第7章的同款警告，在运维现场同样成立）。二忌「绕过代替修复」：`-k`、`InsecureSkipVerify`、注释掉 verify 是排错界的 `rm -rf`——上生产前请把每一处绕过都找回来。

## 14.4 安全加固清单

没事的时候照着做的清单。分四组，每条都对应全书某一章的知识点，用「查什么」写成可执行动作：

| 分组 | 加固项 | 检查动作 |
| ---- | ---- | ---- |
| 协议与套件 | 只启用 TLS 1.2 / 1.3 | `s_client -tls1` 必须被拒 |
| 协议与套件 | 套件用 AEAD 族（AES-GCM / ChaCha20），禁 RC4、3DES、CBC 老套件 | `s_client -cipher` 逐个探测或用在线评测工具 |
| 证书与轮换 | 有效期不超过 90 天，到期告警线 21 天 | `cert-expiry.sh` 挂 cron 覆盖全部域名 |
| 证书与轮换 | SAN 与域名一一对应，不签通配符图省事 | `x509 -noout -ext subjectAltName` 抽查 |
| 证书与轮换 | 生产 CA 加中间层，根私钥离线 | 目录权限 + 签发日志审计 |
| 密钥与随机 | 私钥 600、按用途分离（服务器/客户端/签名各一套 CA） | `ls -l` 巡检 + 台账核对 |
| 密钥与随机 | 全部密钥出自 CSPRNG，不共用、不进 Git | `git log` 抽查 + 密钥台账 |
| 数据与流程 | 备份 encrypt-then-MAC、还原演练每季度 | 演练记录 |
| 数据与流程 | 发布物签名 + CI 强制验签 | 拦截一次篡改演练 |
| 工具链 | OpenSSL 3.x；升级评估例行化 | `openssl version` 巡检 |

清单不求一次全绿——按「协议与套件 → 证书与轮换 → 密钥与随机 → 数据与流程」的顺序逐组落地，每组落地都在消灭一类事故。

十项之外，还有五条**一票否决项**——只要出现一条，无论其他项多绿，整体评级即不合格：

- 生产代码或脚本里存在 `InsecureSkipVerify: true` / `curl -k` / `verify=False`
- 私钥出现在 Git 历史、聊天记录或网盘里（哪怕事后已删除——Git 会永远记得）
- 所有服务共用同一把证书或同一把密钥
- 加密口令与 HMAC 密钥是同一个值（密钥分离原则归零）
- 到期监控不存在，或告警从未接进有人看的地方

## 14.5 泄露应急预案：最坏情况的剧本

加固清单是「不出事时的纪律」，这一节是「出事时的剧本」。私钥泄露（服务器被入侵、误提交 Git、p12 连着口令外流）的分级行动单：

**服务器证书私钥泄露（影响单个服务）：**

```bash
# 1. 止血：立即下线该服务的 TLS（摘除监听或拒绝流量）
# 2. 换钥重签：新私钥 + 新 CSR（第10章流水线）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out new-key.pem
openssl req -new -key new-key.pem \
  -subj "/C=CN/O=CloudNote/CN=auth.cloudnote.internal" \
  -addext "subjectAltName=DNS:auth.cloudnote.internal" -out auth.csr
# 3. CA 签发、部署新三件套、六项体检、恢复上线（第13章）
# 4. 旧证书登记撤销或等过期，台账记一笔（第10章）
```

**根 CA 私钥泄露（灾难级）：** 没有撤销可救（10.5 的 WARNING）——直接启动换根剧本：签发新根、双根过渡并行分发、全员重新导入信任（11.5 流程反向再来一遍）、排查泄露窗口期内被签出的冒牌证书。这份剧本平时永远用不上，但它必须**提前写好放在那里**：事故当头现编剧本，一定会漏步骤。

**签名私钥泄露（发布体系，第7章）：** 换发布密钥对，新指纹**重新公示**（官网 + Wiki 双渠道），发布说明写明切换时间点；攻击者若已用旧钥签发过东西，按签名时间与泄露窗口的交集排查已分发产物。

三条剧本的共同骨架一句话：**先止血（下线/换钥）、再查伤（排查窗口期）、后补墙（堵住泄露路径）**。顺序不能反——先补墙不止血，攻击者还在门里。

## 14.6 演练：让防线保持「练过」

清单和剧本放久了会失效——不是内容过期，是**手感过期**。云笔记把四项演练钉进季度日历：

| 演练 | 动作 | 对应防线 | 合格标准 |
| ---- | ---- | ---- | ---- |
| 备份还原演练 | 随机挑一份三个月前的加密备份完整还原 | 第3-4章流水线 | 数据完整、HMAC 通过、耗时记录在案 |
| 发布包篡改演练 | 改一个字节再验签，确认 CI 真的拦截 | 第7章签名门禁 | 验签失败且流水线中止 |
| 证书轮换演练 | 手动走一遍完整轮换（不等告警） | 第10、12章 | 新证书体检六项全绿 |
| 假根冒充演练 | 用假根证书冒充内部 CA，确认全部客户端拒绝 | 第11章负向验收 | 无任何客户端放行 |

演练的意义第7章点破过：**防线不演练，等于没防线**——你永远不会知道「验签失败即中止」那行 `exit 1` 是不是真的会 exit。每次演练留一份记录（日期、结果、踩到的坑），这份记录本身就是团队的安全台账；下季度演练先翻它，坑不能踩第二遍。

## 14.7 全书复盘：把心智模型带走

回到 ch00 那条主线，此刻它应该是你的肌肉记忆而不是笔记：

```text
哈希管完整性   —— dgst：文件变没变（第2章）
对称加密管保密 —— enc：数据看不看得懂（第3-4章）
非对称管信任   —— genpkey / 签名：身份是谁（第5、7章）
证书管身份背书 —— req / x509 / verify：谁为身份担保（第8-11章）
TLS 把四层合一 —— s_client / nginx：链路上的活体实践（第12-13章）
```

四个里程碑的最终验收：M1（加密加校验双保险）第4章末过线；M2（密钥、CSR、自签三连）第9章末过线；M3（自建 CA 签发并部署上线）第13章过线；M4（用 s_client 独立破案）——用 14.3 的五个现场自测：不看答案能复述破案路径，即为通过。

三个危机的完整档案，从报警到封口，值得留底：

| 危机 | 症状 | 缺的防线 | 解法与章节 | 现状 |
| ---- | ---- | ---- | ---- | ---- |
| 危机一（第8周）备份静默损坏 | 数据悄悄烂掉没人知 | 无校验 | sha256 + HMAC + encrypt-then-MAC（第2、3章） | 还原演练季度化 |
| 危机二（第14周）发布包被替换 | 差一步全员中招 | 无签名 | Ed25519 签名 + CI 验签门禁（第7章） | 篡改演练季度化 |
| 危机三（第30周）证书到期全站瘫 | 40 分钟排查绕远路 | 无监控、无内部 CA | 到期监控 + 自建 CA + 60/21 节奏（第10-12章） | 轮换自动化 |

## 本章小结

- 排错先分层：连通 → 协议 → 证书 → 密钥，每层一个探针动作；「先 version 再动手」是军规
- 报错字典二十余查 + Verify 码表：拿到报错先搜关键字、回定位法、按处置走——多数问题是三个老熟人（缺根、缺中间、缺 SAN）换马甲出现
- 「时好时坏」先怀疑链与 SNI：浏览器会自动补链，curl/Java/手机不会——好脾气不是健康标准
- 安全报错当事故查，不当配置错修；绕过（-k、跳过验证）用完必回收，生产存在即一票否决
- 泄露应急三步曲：先止血、再查伤、后补墙——服务器证书换钥重签，根私钥泄露直接启动换根剧本
- 演练是防线的年检：还原、篡改、轮换、假根四项季度钉死，演练记录就是安全台账
- 加固清单按四组落地：协议套件、证书轮换、密钥随机、数据流程——每组落地消灭一类事故
- 主线回扣：哈希管完整性、加密管保密、证书管身份，TLS 是四层的合体——四个里程碑全过即毕业
