## 8.1 附加规则——全局生效的规则注入

「附加规则」（有的客户端叫「自定义规则」「全局扩展规则」）是一段**独立于当前配置文件、对所有配置生效**的规则列表：不管你加载哪份订阅、哪份模板，这段规则都会被注入到最终规则的**最前面**。

执行顺序与覆盖关系是本节的核心：

- 最终规则 = **附加规则在前 → 配置文件自带规则在后**，自上而下匹配、命中即停（7.6 的规则引擎语义不变）；
- 附加规则**不删除**订阅自带规则，只是排在它们前面「抢先命中」；
- 因此附加规则适合放「无论什么配置都必须成立」的条目——比如全书主线：内网永远直连。

把 7.6 的分流规则挪进附加规则是常见用法：

```yaml
# 附加规则（GUI 里逐条添加，最终合成如下顺序）
- IP-CIDR,10.66.66.0/24,phone-wg,no-resolve
- IP-CIDR,192.168.1.0/24,phone-wg,no-resolve
- DOMAIN-SUFFIX,home.lan,phone-wg
- IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
- IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
```

后两条 DIRECT 是附加规则的典型用法：**防误伤**——就算换了一份把你内网网段也「代理走」的订阅配置，附加规则也先把私有网段拦下来直连。这解决了「先猜再读」第一问的前半句：附加规则先执行。注意节点名 `phone-wg` 必须在当前配置里真实存在，否则引用它的附加规则会让整份配置加载失败——这也是 8.8 排障表的第一行。

## 8.2 订阅规则覆写——改写订阅自带的规则

「订阅规则覆写」作用于另一层：**只对「订阅」这一种配置来源生效**，在订阅内容加载后、附加规则注入前，对订阅自带的规则做改写。

两种来源、两种改写工具的分工：

| 设置项 | 作用对象 | 改写方式 | 典型用途 |
| ---- | ---- | ---- | ---- |
| 附加规则 | 所有配置文件 | 前置追加 | 内网直连等全局铁律 |
| 订阅规则覆写 | 仅订阅配置 | 增/删/改订阅自带规则 | 删掉订阅里不符合需求的规则 |
| 自定义配置模板 | 本地/自建配置 | 整份模板替换 | 7.5 的 wireguard 节点注入 |

覆写的典型场景：某份订阅自带 `GEOIP,CN,DIRECT` 但没有你想要的某条分流，用覆写**追加或替换**这一条，而不必维护一份完整的本地配置。回答「先猜再读」第一问的后半句：订阅自带规则**不会被丢掉**，覆写是在其基础上做增删改；想「只保留我自己的规则」需要用覆写把原规则清空（部分客户端支持「清空规则」选项），而不是靠附加规则去「压」它。

三层改写手段的执行顺序固定为：**订阅原文 → 订阅规则覆写 → 附加规则注入 → 最终规则**。执行顺序可以画成这样：

```text
订阅原文
   │
   ▼
订阅规则覆写（只改订阅）
   │
   ▼
附加规则注入（所有配置）
   │
   ▼
最终规则（自上而下匹配）
```

排障时按这个顺序检查每一层的产物，GUI 里通常能看到「生效后的规则预览」。

## 8.3 脚本与简化代理组——用 JS 动态改配置

「脚本」设置项允许一段 JavaScript 在配置加载时运行，对最终配置做**程序化改写**——规则、代理组、节点列表都能动。这是比覆写更进一步的手段：覆写是「增删改已知条目」，脚本是「按数据动态生成条目」。

最小可读示例（把内网网段规则批量生成，而不是手写五行）：

```javascript
// main 函数接收解析后的配置对象，返回改写后的对象
function main(config) {
  const 内网网段 = ["10.66.66.0/24", "192.168.1.0/24"];
  const 注入 = 内网网段.map(
    (cidr) => `IP-CIDR,${cidr},phone-wg,no-resolve`
  );
  config.rules = [...注入, ...config.rules];
  return config;
}
```

「简化代理组」（部分客户端叫「策略组简化」「代理组精简」）则是反方向的工具：把配置里冗长的代理组声明**收拢成几个手选组**——比如只留「手动选择」「自动测速」两个组，其余节点自动归入，界面立刻清爽。它不改流量行为，只改 UI 呈现与组结构。

何时用哪个的判断标准：

- 条目固定、就几条 → 直接写规则或附加规则（8.1）；
- 条目随订阅变化、要按模式批量处理 → 覆写（8.2）；
- 条目需要**计算**（遍历、过滤、拼接）→ 脚本（本节）。

本书主线（一个 wireguard 出站 + 四条规则）用不到脚本——把它当「知道有这能力、必要时再查文档」的工具即可。脚本改坏了配置的后果与写错 YAML 相同：整份配置加载失败，客户端回退或报错，删掉脚本即恢复。

## 8.4 策略组与链式代理——出口的两种进阶形态

「自定义配置模板」在 7.5 里只加了一个节点，这里补全它的两个进阶形态。**策略组（proxy-groups）**把多个出口收拢成一个「可切换的出口」：

```yaml
proxy-groups:
  - name: "内网出口"
    type: select          # 手动选择；fallback=故障转移，url-test=自动测速
    proxies:
      - phone-wg          # 自建 VPN（第七章）
      - DIRECT            # 直连兜底
```

规则里写 `IP-CIDR,10.66.66.0/24,内网出口` 后，连内网走哪个出口就在 GUI 里手选——`phone-wg` 挂了可临时切 DIRECT，不用改规则。`type` 字段决定组怎么选出口，常用的四种：

| type | 选出口的方式 | 适合 |
| ---- | ---- | ---- |
| select | 手动点选，选中即固定 | 内网出口这类「必须可控」的场景 |
| url-test | 定期测速，自动用最快的 | 多节点比速度 |
| fallback | 按顺序探活，用第一个活的 | 主备切换 |
| load-balance | 轮流分发连接 | 多出口摊带宽（会话可能换出口，SSH 不友好） |

**链式代理（dialer-proxy）**把两个出站串起来：流量先过第一跳、再从第一跳里发起第二跳。mihomo 的写法是在出站上加 `dialer-proxy` 字段，指向另一个出站名：

```yaml
proxies:
  - name: "phone-wg"
    type: wireguard
    server: 203.0.113.10
    port: 51820
    ip: 10.66.66.5              # 与 7.5 的 add 输出保持一致
    private-key: "pH0n3..."
    public-key: "k5S+1x..."
    # dialer-proxy: "第一跳"    ← 指向另一个出站名即可串联
```

含义：`phone-wg` 的 UDP 51820 包**先交给「第一跳」出站发送**，从第一跳的出口再连 VPN 服务器。适用场景是「VPN 服务器的 UDP 被墙/被限速，需要借道可达」——本书主线服务器直连可达，用不上串联；知道 `dialer-proxy` 一个字段就是链式代理的全部开关即可。串两跳的代价也要心里有数：延迟叠加、带宽取两跳较小值、任何一跳挂则整条链挂。

## 8.5 内建订阅转换——SubConverter 的功能说明

「订阅转换」（内建 SubConverter 服务）解决的是**格式适配**问题：订阅源返回的配置格式（base64 节点列表、SIP008、 sing-box JSON 等）与 mihomo 需要的 YAML 不一致时，转换服务把它翻成 mihomo 能加载的 YAML，并可顺带注入规则模板、重命名节点。

客户端里的相关设置通常三项：

| 设置项 | 含义 | 本书建议 |
| ---- | ---- | ---- |
| 内建转换开关 | 订阅加载前是否过一遍 SubConverter | 订阅格式本就是 mihomo YAML 时**关闭**——少一层转换少一层出错面 |
| 转换模板 | 转换时套用的规则模板（如 ACL4SSR） | 与 8.1 附加规则二选一，别两层都堆规则 |
| 自定义转换后端 | 换成自部署的 SubConverter | 在意订阅内容经过第三方服务时才需要；内建服务已是本地完成格式转换 |

必须重申本书的定位边界：**本教程不涉及任何订阅源的获取与选择**——订阅转换是纯格式处理功能，讲它是因为设置页里有这个开关，你需要知道它做了什么。自建 VPN 主线（第七章的 wireguard 节点写在本地模板里）完全不经过订阅转换，这一节对你而言是「读懂即可」的背景知识。

## 8.6 解锁检测——它是干什么用的

「解锁检测」是客户端的一个**探测功能**：按预设目标（Netflix、Disney+、ChatGPT 等）发起测试请求，按各出口逐一探测「该服务的某地区内容是否可访问」，在节点列表旁标注可用性。它是**读操作**——只发探测请求、只显示结果，不改任何配置。

与本书主线的关系一句话说清：自建 VPN 的目标是**远程接入内网**（SSH、数据库、NAS），探测目标列表里的流媒体服务与这个目标无关——「先猜再读」第三问的答案是：显示「Netflix 未解锁」既不是客户端坏了也不是 VPN 坏了，而是你的自建隧道本来就不以此为目——探测结果与隧道连通性是两个正交的指标。判断隧道好坏用 7.7 的三连验证（wg show 握手、规则命中、ping 通），不要看解锁检测的图标。

一个实用建议：如果客户端支持自定义检测目标，把它改成你的内网服务（比如对 `10.66.66.1:22` 做连通探测），解锁检测就变成了「内网可达性仪表盘」——这才是与自建 VPN 主线对齐的用法。

## 8.7 外部资源——GeoIP、GeoSite、MMDB、ASN 是什么

规则引擎写的 `GEOIP,CN`、`GEOSITE,apple-cn` 这类规则，背后要查**数据文件**——这就是「外部资源」设置项管理的内容：

| 资源类型 | 文件格式 | 回答的问题 | 规则示例 |
| ---- | ---- | ---- | ---- |
| GeoIP | .mmdb（MaxMind 格式） | 这个 IP 属于哪个国家/地区？ | `GEOIP,CN,DIRECT` |
| GeoSite | .dat / .yaml | 这个域名属于哪个网站分类？ | `GEOSITE,apple-cn,DIRECT` |
| ASN | .dat / .mmdb | 这个 IP 属于哪个自治系统（运营商/公司）？ | `GEOIP-ASN,AS13335,PROXY` |
| MMDB | 同 GeoIP | GeoIP 的载体格式本身 | Country/City 两种库 |

回答「先猜再读」第二问：`GEOIP,CN` 查的是本地的 MMDB 文件（IP 段 → 国家码的数据库），`GEOSITE,xxx` 查的是 GeoSite 文件（域名 → 分类名的列表）——**不是内置知识，是本地数据文件在支撑**。这些文件由社区维护、定期更新（IP 段和域名分类都会漂移），「外部资源」设置项管理的就是它们的**来源与更新**：检查更新按钮、更新周期、镜像地址。

对本书主线的意义在两个「不需要」：分流内网用的是 `IP-CIDR`（精确网段，不需要 GeoIP）；规则里没有 `GEOIP`/`GEOSITE` 时这些文件根本不会被加载。只有当你的规则开始用 GEOIP 类规则（比如「国内 IP 直连」），外部资源才从背景板变成必需品——那时需要确认文件已下载、版本较新，否则 GEOIP 规则会静默不命中或整份配置加载报错（视客户端版本而定）。

用到时的维护动作就三步，记住顺序即可：

- 检查：设置项里看每个文件的版本日期与体积（异常小的文件多半下载失败）；
- 更新：手动触发一次检查更新，或确认自动更新周期（社区数据一般每月都在变）；
- 验证：更新后随便挑一条 GEOIP 规则，到连接页确认命中行为没变。

文件损坏或更新中断的典型症状是「GEOIP 规则全部失效」或「加载时报 geo 文件解析错误」——处置办法都是删掉缓存文件重新下载，别手工编辑这些二进制/大文本文件。

## 8.8 排障与全书结束语

高级设置改出问题时，按「配置加载 → 规则命中 → 出口连通」三段定位：

| 症状 | 大概率原因 | 处置 |
| ---- | ---- | ---- |
| 配置加载失败 / 节点消失 | YAML 语法错误；附加规则引用了不存在的节点名 | 检查 8.1 的 `phone-wg` 是否在当前配置里 |
| 规则不命中 | 覆写与附加规则顺序误判；GEOIP 数据文件缺失或过期 | 按 8.2 的四段顺序核对；检查 8.7 资源更新 |
| 内网时通时断 | 复制旧 conf 导致两台客户端同地址（7.7）；策略组切到了 DIRECT | 花名册核对 + 8.4 的组内出口检查 |
| 配置「看起来对」但不生效 | 脚本（8.3）在加载时改坏了结构 | 临时禁用脚本逐段排除 |
| 订阅加载异常 | 8.5 的转换层问题 | 关闭内建转换直连加载验证 |

到这里，设置页每个开关都有了出处。全书的旅程也在此合拢：第一、二章建立「密钥即身份、隧道即加密转发」的原理地基；第三至五章把一台云服务器变成 VPN 网关，并用三个脚本把发放与注销工程化；第六章把单机隧道扩展成站点互联，交代了 OpenVPN 的选型坐标；第七、八章把你已有的 mihomo 客户端变成同一台服务器的另一种接入形态，并把设置页每个开关讲成了「配置的哪一层」。三篇合起来，是一条从原理到脚本、从服务器到客户端的完整闭环。

> [!TIP]
> 留给读者的最后一个练习：把第六章的站点到站点与第七章的 mihomo 接入组合起来——手机经 mihomo 连上云服务器后，再访问家里 NAS 的 `192.168.1.x`。能跑通这条两段式链路，并说清每一跳由哪个组件负责（mihomo 规则、wg AllowedIPs、NAS 回程），本书的目标就真正达成了。

## 本章小结

- 附加规则全局前置，订阅覆写只改订阅自带规则；顺序固定为订阅原文 → 覆写 → 附加注入；
- 覆写不删除订阅规则，只是增删改；想「只要自己的规则」需显式清空；
- 脚本是程序化改写（条目要计算才用），简化代理组只收拢 UI 不改行为；
- 策略组把多出口收拢成可切换出口，`dialer-proxy` 一个字段实现链式代理；
- 订阅转换是格式适配层，格式本就兼容时关闭它减少出错面；本书不涉及订阅源获取；
- 解锁检测是只读探测，与自建 VPN 的连通性正交；可自定义探测目标改造成内网仪表盘；
- GEOIP/GEOSITE/ASN 规则背后是本地数据文件，「外部资源」管理其来源与更新；IP-CIDR 分流不需要它们；
- 排障按「配置加载 → 规则命中 → 出口连通」三段走，脚本与数据文件是高级设置特有的两个故障源。

**全书结束语**：从一条 UDP 隧道到一张可编程的接入网络，你现在已经拥有把任何网络变成「自己的内网」的全部工具——原理懂了、服务器建了、脚本写了、客户端接了。愿你联网的每一台设备，都有一条自己说了算的回家路。
