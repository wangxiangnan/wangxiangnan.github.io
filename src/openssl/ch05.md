# 第5章：非对称密钥：genpkey 与算法选型

> [!TIP] Part 2: 非对称与证书篇（进阶篇）
> Part 2 开篇。前四章把「数据保得住」解决了，本章开始解决「身份信得过」——先造出非对称世界的第一对钥匙。如果你读过《Git 与 SSH 完全教程》第5章，公钥与私钥的直觉你已经有了，本章补上 OpenSSL 侧的完整操作。

对称加密留了一个死结。第3章的备份流水线里，加密口令只在你自己手里，所以没问题；可一旦要和对面的人保密通信——比如浏览器要连 api.cloudnote.example——你就得把对称钥匙先交给对方，而「怎么把钥匙安全地送到对面」本身就需要加密。鸡生蛋蛋生鸡，**对称密钥的分发问题无法用对称加密解决**。

解法你已经见过：把一把钥匙拆成两把。《Git 与 SSH 完全教程》第5章的类比原样搬来——**公钥是可以随便复印的挂锁，私钥是唯一能开锁的钥匙**，由公钥反推私钥在计算上不可行。挂锁公开发放（加密用），钥匙贴身收藏（解密用）；反过来，私钥签名像笔迹，公钥验签像笔迹鉴定（认证用）。本章的任务：在 OpenSSL 里把这对钥匙亲手造出来、保护好、验明白。

## 5.1 两把钥匙的两种用法

非对称体系里，「公钥私钥」这对结构有两种相反的用法，方向千万别搅混：

```text
用法一：加密（保住内容）
  对方的公钥加密  ──────────────►  对方的私钥解密
  （谁都能锁）                    （只有他有钥匙）

用法二：签名（证明身份）
  你的私钥签名    ──────────────►  大家的公钥验签
  （只有你能签）                  （谁都能验）
```

两种用法一张表对照，方向感钉死：

| | 用法一：加密 | 用法二：签名 |
| ---- | ---- | ---- |
| 回答的问题 | 内容会不会被偷看 | 内容是不是他发的 |
| 谁的钥匙加密/签名 | 接收方的**公钥** | 发送方的**私钥** |
| 谁的钥匙解密/验签 | 接收方的**私钥** | 发送方的**公钥** |
| 典型场景 | 护送对称密钥、加密投递 | 发布包签名、证书、JWT |

两栏的钥匙方向完全相反——这就是初学者最容易搅混的地方，也是本章开篇口诀「公钥出门，私钥不出门」要压住的方向感。判断任何非对称操作，先问一句「这步用的是谁的哪把钥匙」，答案清楚了，操作就清楚了。

两个方向的纪律合起来就是一句口诀：**公钥出门，私钥不出门**。加密方向用在密钥交换（TLS 握手的老式做法）、文件投递；签名方向用在第7章的发布包签名、第8章的证书。TLS 现代握手（1.3）里密钥交换改用了另一族算法（临时密钥协商），但「公钥管身份、对称管数据」的分工骨架从未变过。

「公钥管身份、对称管数据」还有一个工程理由值得展开：**非对称运算又慢又娇气，干不了重活**。两个硬约束：

- **慢三个数量级**：RSA 加密一条 200 字节消息的耗时，够 AES 加密上百 MB——让非对称算法直接加密大文件，性能立刻破产。
- **有数据上限**：RSA 直接加密的数据不能超过钥匙长度减去填充开销（2048 位钥匙实际只能装约 245 字节），EC 系列压根不提供加密功能。

所以现实世界的「用对方公钥加密文件」从来不是一步到位，而是**混合加密**（Hybrid Encryption）：`openssl rand` 造一把一次性对称密钥，AES 加密大文件；再用对方的 RSA 公钥加密这把一次性密钥，两个文件一起送过去。对方用自己的私钥解出一次性密钥，再解文件——非对称只干了它擅长的「护送钥匙」这 245 字节的活，重活全交给对称算法。TLS 握手、加密邮件（PGP）、端到端聊天，底层全是这套「对称扛货、非对称交钥匙」的分工。OpenSSL 命令行没有一键混合加密的封装（`pkeyutl -encrypt` 能演示 RSA 小数据加密，但工程实践都走工具链封装），理解分工比记命令重要。

## 5.2 genpkey 实战：一次学会三种算法

造钥匙的统一入口是 `genpkey`——第1章说过，3.x 时代一套命令通吃全算法家族。三种主流算法各造一把：

```bash
# RSA：老牌通用，HTTPS 证书的常青树
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out rsa-key.pem

# EC（椭圆曲线）：钥匙短、生成快，现代 TLS 服务器证书的主流
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec-key.pem

# Ed25519：新一代签名算法，最快也最短
openssl genpkey -algorithm ED25519 -out ed-key.pem
```

三条命令的体感差异值得亲手试：RSA 要搜索大素数，敲下去明显卡一两秒；EC 和 Ed25519 眨眼即出。想要精确数字可以用 `time` 量一下，顺便体会「为什么大厂批量签发证书都爱 EC」：

```bash
time openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out /tmp/r.pem
time openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out /tmp/e.pem
time openssl genpkey -algorithm ED25519 -out /tmp/ed.pem
```

在我这台机器上的典型结果：RSA 约 0.1~0.5 秒（看运气，素数搜索有随机性）、EC 约 20 毫秒、Ed25519 约 5 毫秒。单次生成无所谓，但想象一个每天轮换几千把密钥的证书服务，差的就是「分钟级」与「毫秒级」的距离。

产出文件的大小也值得 `ls -l` 看一眼——文件体积就是算法气质的直观呈现：

```text
-rw------- 1 wang wang 1728 rsa-key.pem    ← RSA 2048：笨重
-rw------- 1 wang wang  246 ec-key.pem     ← EC P-256：精悍
-rw------- 1 wang wang  122 ed-key.pem     ← Ed25519：极简
```

注意这比 5.3 表格里「私钥长度」的数字大——因为 PEM 文件除钥匙本体还包含封装头与 base64 排版，这个「文件 vs 本体」的差价第6章正式算账。（上面是 3.5.x 实测值；RSA 因素数与编码长度有随机波动，你的数字差个十几字节很正常。）

产出文件都是 PEM 格式（第6章细讲），裸私钥长这样：

```text
-----BEGIN PRIVATE KEY-----
MC4CAQAwBQYDK2VwBCIEIJri7M2v9F1eX5jA8kQ3hP6uW2sL9bN4cD7eG1fH0aI=
-----END PRIVATE KEY-----
```

导出公钥是同一个命令家族的 `pkey`：

```bash
openssl pkey -in ed-key.pem -pubout -out ed-pub.pem
```

公钥比私钥短一大截（Ed25519 裸公钥只有 32 字节，RSA 2048 公钥约 450 字符），它就是后面要「随便发」的那把挂锁。

一个值得停下来想十秒的事实：**公钥是从私钥文件里算出来的，不是独立保管的两份秘密**。私钥文件里其实完整包含着公钥信息，`-pubout` 只是把它提取出来；你永远不可能「丢了公钥但留着私钥」——丢了公钥只是忘了抄，随时能再导一份。反过来才危险：私钥文件损坏且无备份时，这对钥匙连同它的身份一起消失。这解释了上一节为什么私钥的保管纪律比公钥严一个数量级：全世界只需要保管好一件东西——私钥。

也正因为「公钥随私钥自带」，工程上有个反直觉的好习惯：**公钥文件不需要备份**。服务器迁移、机器重装时，只要加密私钥还在，`pkey -pubout` 十秒还原公钥；真正需要异地容灾的只有私钥本体（加密形态）。云笔记的备份脚本里，`api-pub.pem` 和 `release-pub.pem` 都不在备份清单上——省下的心思留给真正要紧的东西。

> [!NOTE] 命令年代对照
> 网上教程常见的 `openssl genrsa`、`openssl rsa -pubout` 是 1.x 时代写法，功能等价但已进入淘汰倒计时。见老写法就按第1章的对照表翻译：`genrsa` → `genpkey -algorithm RSA`，`rsa -pubout` → `pkey -pubout`。本书全部使用新写法。

## 5.3 算法选型：一张表定案

三种算法怎么选？把强度、长度、速度、兼容性放在一张表里比：

| | RSA 2048 | EC P-256 | Ed25519 |
| ---- | ---- | ---- | ---- |
| 安全强度（约） | 112 比特 | 128 比特 | 128 比特 |
| 私钥长度（PEM 整文件） | 约 1700 字符 | 约 250 字符 | 约 120 字符 |
| 生成速度 | 慢（搜索素数，秒级） | 快 | 最快 |
| 签名速度 | 慢 | 快 | 最快 |
| 登场年代 | 1977（算法家族） | 1985（理论）/ 2000 年代标准化 | 2015 |
| TLS 证书兼容性 | 全时代通吃 | 现代客户端全覆盖 | 2017 年后的客户端 |

这条决策树刻意把三种算法画进了同一个终点——无论选谁，私钥的保护纪律一模一样。算法可以选型，纪律没有例外。

三个补充判断依据：

- **RSA 的王牌是兼容性**。老设备、老中间件、部分企业网关只认 RSA，所以公网 TLS 场景它仍是稳妥的保底选项。
- **RSA 想加强度只能堆长度**（2048 → 3072 → 4096），签名和握手随长度**超线性**变慢（模运算成本涨得比钥匙更长）；EC/Ed25519 的强度来自曲线结构，长度几乎不动。这就是「RSA 4096 不如 P-256 时髦」的原因——更强了，但哪儿都更笨重。
- **Ed25519 的短板只剩历史**。2017 年后的浏览器、OpenSSH、云平台全部支持，新项目没有理由不选它；只有当你必须伺候 2015 年前的老古董时才退回 RSA。

选型还有一个容易忽略的维度：**同一台服务器的证书钥匙和签名钥匙不必同款，但同一用途内要一致**。比如 TLS 证书选了 P-256，将来轮换时也换 P-256——算法混用的管理成本（两套监控、两套兼容性测试）远大于性能差异。云笔记把「TLS 一律 P-256、签名一律 Ed25519」写进了技术决策记录，每次新人接手都不用重新吵一遍选型。

本书的云笔记决策：**API 服务器的 TLS 证书用 EC P-256，发布包签名用 Ed25519**——正好覆盖两大场景，第7、9、13章沿用这对组合。

## 5.4 保护好私钥：加密与权限

私钥一旦泄露，加密、签名、身份全套崩塌，所以造出来第一件事是上锁。两道锁：

**第一道：口令加密私钥本身。** `genpkey` 加一个对称加密参数，产出的私钥文件就自带保险箱：

```bash
# 先给口令文件本身安排住处和来源（第4章的同款纪律：rand 生成、600 权限）
mkdir -p $HOME/.cloudnote-secrets && chmod 700 $HOME/.cloudnote-secrets
openssl rand -base64 16 > $HOME/.cloudnote-secrets/KEY_PASS.txt
chmod 600 $HOME/.cloudnote-secrets/KEY_PASS.txt

openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 \
  -aes-256-cbc -pass file:$HOME/.cloudnote-secrets/KEY_PASS.txt \
  -out api-key.pem
```

区别一眼可辨：加密私钥的头行是 `-----BEGIN ENCRYPTED PRIVATE KEY-----`，裸私钥是 `-----BEGIN PRIVATE KEY-----`。以后用这把私钥的每条命令都得提供口令（`-passin`），烦，但这正是意义所在——**偷走文件的人拿到的只是密文**。取舍参考《Git 与 SSH 完全教程》第14章：交互频繁的场景配 ssh-agent 类工具自动化解锁，服务器上无人值守的服务则常用裸私钥加严防死守的权限。

**第二道：文件权限。** 和 SSH 私钥同一个军规：

```bash
chmod 600 api-key.pem && chmod 700 ~/.cloudnote-secrets
```

| 存放位置 | 权限 | 谁该能读 |
| ---- | ---- | ---- |
| 私钥文件 | 600 | 只有属主 |
| 私钥所在目录 | 700 | 只有属主 |
| 公钥文件 | 644 | 随便读 |

顺带钉死一句话：**私钥不进 Git、不上传对象存储、不发聊天工具**——你在第4章给密钥立的纪律，对私钥一字不改地适用，且后果更重（私钥泄露等于交出身份，必须立即作废更换）。

「作废更换」具体怎么操作？非对称密钥和第4章的对称钥匙有个本质区别：**私钥丢了可以重造，但重造出来的是全新身份**——新钥匙的公钥与旧的不成对，所有登记过旧公钥的地方都要更新。把处置预案写清楚：

| 情形 | 处置 | 代价 |
| ---- | ---- | ---- |
| 私钥文件误删，无备份 | 重新生成，公钥重新登记 | 半小时内，但签名历史「断代」 |
| 怀疑泄露但未证实 | 立即生成新钥匙对，旧公钥全部下架 | 同上，宁枉勿纵 |
| 确认泄露 | 同上 + 排查泄露期间的伪造痕迹 | 可能要审计历史签名与证书 |
| 私钥口令忘了 | 等同于丢失，走第一条 | 无解，没人能帮你找回 |

所以私钥也需要备份——但备份的方式是把**加密后的私钥文件**放进第3章的加密备份流水线，而不是明文抄在第二台机器上。第4章的密钥台账里，从今天起给非对称密钥也各加一行。

## 5.5 公钥指纹：给公钥验明正身

公钥随便发没有保密问题，但有**真伪问题**：你拿到的公钥真的是王哥的吗？万一中间被人调包了呢？这就是 SSH 世界里指纹告警防的同一件事（《Git 与 SSH 完全教程》第6章）。OpenSSL 侧的解法同构：给公钥算一枚指纹，通过**另一条渠道**（电话、官网 HTTPS 页面、面对面）核对：

```bash
openssl pkey -pubin -in ed-pub.pem -outform DER | openssl dgst -sha256
```

```text
(stdin)= 8a3f2c1e9d7b5a4f6e2c0d8b4a6f2e0c8d4b6a2f0e4c8d2b6a4f2e0c8d4b6a2f
```

先把公钥转成 DER 二进制（避免编码细节干扰哈希），再算 SHA-256，得到 64 个十六进制字符——这枚指纹就是公钥的「人脸」。以后任何人给你公钥，你算一遍指纹比对即可；第8章会看到，证书体系把这个「人工核对」的活儿交给了 CA，但核对指纹的思路一以贯之。

「两个人指纹撞车怎么办」的疑虑可以用第2章的生日界打消：SHA-256 指纹要凑出一对碰撞约需 2^128 次运算——全球算力开满跑上亿年也撞不出一次。指纹核对的真实风险从来不在数学，在**渠道**：如果你核对指纹用的也是同一条可能被窃听的渠道（比如都在同一个聊天群里发），等于用自己的矛戳自己的盾。所以「另一条渠道」四个字是重点：Wiki 上公示指纹、视频里口头念前 16 位、名片背面印指纹，都是把核对成本压到「低头看一眼」的实用主义设计。

顺带记一个指纹的「瘦身版」：有些工具展示的是指纹的**前 16 字节**（32 个 hex 字符）甚至再冒号分隔（`8A:3F:2C:1E:...`），那是为了人眼友好而截断的展示格式。核对时务必确认双方算的是同一口径——全文 64 位还是截断 32 位——口径不一致的比对结果毫无意义。证书世界同样存在 MD5 指纹与 SHA-256 指纹两种口径（第8章会同时看到它们），永远选长的。

## 5.6 实验：给云笔记造一对钥匙

按 5.3 的选型结论动手，产出两把钥匙供后续章节使用。这批钥匙会在第7章（签名）、第9章（证书请求）、第10章（CA）、第13章（HTTPS 上线）反复登场，所以每一步都按生产纪律走：

```bash
# 1. TLS 服务器钥匙（EC P-256，加密保存）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 \
  -aes-256-cbc -pass file:$HOME/.cloudnote-secrets/KEY_PASS.txt \
  -out api-key.pem

# 2. 发布签名钥匙（Ed25519，直接进密钥目录）
openssl genpkey -algorithm ED25519 -out $HOME/.cloudnote-secrets/release-key.pem

# 3. 导出公钥（公钥留在工作目录，私钥不出密钥目录）
openssl pkey -in api-key.pem -passin file:$HOME/.cloudnote-secrets/KEY_PASS.txt -pubout -out api-pub.pem
openssl pkey -in $HOME/.cloudnote-secrets/release-key.pem -pubout -out release-pub.pem

# 4. 验收：权限与指纹
chmod 600 api-key.pem $HOME/.cloudnote-secrets/release-key.pem
openssl pkey -pubin -in release-pub.pem -outform DER | openssl dgst -sha256
```

验收标准三条：两把私钥权限 600；用错误口令读 `api-key.pem` 必须报错（证明加密生效）；公钥指纹算得出来并抄进了团队 Wiki——这枚指纹第7章要当公示栏用。

错误口令演练值得单独跑一遍，认识一下那行报错长什么样：

```bash
echo "wrong-pass" > /tmp/wp.txt
openssl pkey -in api-key.pem -passin file:/tmp/wp.txt -noout
```

```text
Could not find private key of key from api-key.pem
...:Provider routines:ossl_cipher_unpadblock:bad decrypt:...
...:PKCS12 routines:PKCS12_pbe_crypt_ex:pkcs12 cipherfinal error:...maybe wrong password
```

最后一行的 `maybe wrong password` 是重点：加密私钥文件自带完整性检查，口令不对时 OpenSSL 不是「解出一堆乱码」而是直接拒绝——`bad decrypt` 报错栈出自 PKCS#8 封装的善意。顺手把 `/tmp/wp.txt` 删掉，别让假口令文件过夜。这个报错也提前给你一颗定心丸：第14章排错手册里，「钥匙口令忘了」和「钥匙文件损坏」的报错长得不一样，一眼可分。

> [!TIP] genpkey 与 ssh-keygen 是同行
> 《Git 与 SSH 完全教程》里用 `ssh-keygen -t ed25519` 造 SSH 钥匙，本章用 `openssl genpkey -algorithm ED25519`——两把是**同一种算法**（Ed25519）的两种封装格式，OpenSSH 用自己的私有格式，OpenSSL 用 PEM。所以「同一把钥匙既登 SSH 又做文件签名」需要格式转换工具牵线，日常更省心的做法是按用途各造各的——钥匙便宜，用途混居才是管理灾难。

## 本章小结

- 对称密钥的分发死结，用非对称解：**公钥是随便复印的挂锁，私钥是唯一钥匙**
- 两种用法方向相反：对方公钥加密、你私钥解密（保密）；你私钥签名、大家公钥验签（认证）——口诀「公钥出门，私钥不出门」
- 非对称干不了重活（慢三个数量级、RSA 有 245 字节上限），现实世界靠混合加密分工：**对称扛货，非对称交钥匙**
- `genpkey` 一套命令通吃三种算法：RSA（兼容王）、EC P-256（TLS 证书主流）、Ed25519（签名首选最快最短）
- 选型决策：TLS 证书 P-256、新项目签名 Ed25519、对接老系统 RSA 2048 起步；同用途内算法保持一致
- 私钥两道锁：`-aes-256-cbc -pass` 口令加密（头行变 ENCRYPTED）+ 权限 600；泄露后果是身份作废
- 私钥可重造但重造即换身份——备份加密私钥、登记台账、泄露后「宁枉勿纵」立即更换
- 公钥指纹（DER 化后 SHA-256）是防调包的核对手段——「另一条渠道核对指纹」这个思路将贯穿证书体系

**下一章预告**：钥匙造好了，可网上抄来的命令十有六七会栽在「unable to load key」上——PEM、DER、PKCS#1、PKCS#8、p12，格式家族的迷宫下一章带你走通。走通之后你会发现：本章那些「约 1700 字符」「约 68 字符」的数字，其实都是同一把钥匙穿着不同马甲的样子。
