# 第14章 事务与并发控制

**生活类比：** 你在网上购物，点击"支付"按钮后，后台要同时做两件事：你的账户扣款 + 商家账户入账。如果扣款成功但入账失败了，你的钱就"消失"了。事务就是保证这两步要么一起成功、要么一起回退的机制——就像情侣约定"要死一起死，要活一起活"。

## 14.1 ACID特性详解

事务有四大特性，简称ACID，它们是数据库可靠性的基石：

- **Atomicity（原子性）**：事务中的操作要么全部完成，要么全部不完成。就像原子一样不可再分。
- **Consistency（一致性）**：事务前后，数据库从一个一致状态转变到另一个一致状态。
- **Isolation（隔离性）**：并发事务之间互不干扰（理想状态，实际上需要权衡）。
- **Durability（持久性）**：事务一旦提交，其结果永久保存，即使断电也不会丢失。

## 14.2 事务基本语法

```sql
-- 开始事务
START TRANSACTION;

-- 执行操作
UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE user_id = 2;

-- 确认无误，提交
COMMIT;
```

```sql
-- 如果出了问题，回滚
START TRANSACTION;

UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
-- 发现余额不足！
ROLLBACK;  -- 撤销所有操作，数据恢复原样
```

```sql
-- 使用保存点(SAVEPOINT)：部分回滚
START TRANSACTION;

INSERT INTO orders (user_id, amount) VALUES (1, 500);
SAVEPOINT sp_after_order;

UPDATE inventory SET stock = stock - 1 WHERE product_id = 100;
-- 库存不足，回滚到保存点
ROLLBACK TO SAVEPOINT sp_after_order;

-- 订单还在，但库存更新被撤销了
-- 换一种方式处理库存...
UPDATE inventory SET stock = stock - 1 WHERE product_id = 200;

COMMIT;
```

> **Tip:** InnoDB引擎默认开启了自动提交（autocommit=1），每条SQL语句都是一个独立事务。如果你需要手动控制事务，记得先 `START TRANSACTION` 或者设置 `SET autocommit = 0`。

## 14.3 隔离级别与并发问题

当多个事务同时操作数据时，可能出现三种"灵异现象"：

**脏读(Dirty Read)**：读到了其他事务未提交的数据。

- 事务A修改了数据但还没提交，事务B读到了这个"半成品"数据

**不可重复读(Non-Repeatable Read)**：同一事务内两次读取同一行数据，结果不同。

- 事务A第一次读余额是1000，事务B修改了余额并提交，事务A再读变成了500

**幻读(Phantom Read)**：同一事务内两次范围查询，返回的行数不同。

- 事务A查"工资>10000的员工"有5个，事务B新插入了一条并提交，事务A再查变成6个

MySQL提供四种隔离级别来解决这些问题：

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别（当前会话）
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;  -- MySQL默认
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 最高 |
| READ COMMITTED | 解决 | 可能 | 可能 | 较高 |
| REPEATABLE READ | 解决 | 解决 | 可能* | 一般 |
| SERIALIZABLE | 解决 | 解决 | 解决 | 最低 |

> **Tip:** *MySQL的REPEATABLE READ通过MVCC和间隙锁，在很大程度上也解决了幻读问题。这是MySQL相比其他数据库的一个优势。默认使用REPEATABLE READ是经过深思熟虑的选择。

## 14.4 MVCC（多版本并发控制）原理

MVCC是MySQL实现高并发读写的核心机制。简单说，它通过保存数据的"历史版本"来实现读写不冲突。

核心组件：

- **隐藏列**：每行数据有 trx_id（最后修改的事务ID）和 roll_pointer（回滚指针）
- **Undo Log**：保存数据的历史版本，形成版本链
- **ReadView**：事务在某个时刻的"快照"，决定能看到哪些版本

```sql
-- MVCC 工作流程演示
-- 假设当前隔离级别为 REPEATABLE READ

-- 事务A
START TRANSACTION;
SELECT balance FROM accounts WHERE user_id = 1;  -- 结果: 1000（创建ReadView）

-- 此时事务B修改了余额并提交
-- UPDATE accounts SET balance = 500 WHERE user_id = 1; COMMIT;

-- 事务A再次读取
SELECT balance FROM accounts WHERE user_id = 1;  -- 结果仍然是: 1000
-- 因为ReadView没有变，事务A看到的还是"快照"版本
```

MVCC的精妙之处在于：读操作不需要加锁，通过版本链找到"当前事务能看到"的版本。这就实现了"读写不阻塞"，大大提高了并发性能。

## 14.5 锁机制

当MVCC搞不定的时候（比如写操作），就需要锁出场了。

**共享锁(S Lock / 读锁)**：允许事务读取一行。多个事务可以同时持有共享锁。

```sql
-- 显式加共享锁
SELECT * FROM accounts WHERE user_id = 1 LOCK IN SHARE MODE;
-- MySQL 8.0 推荐写法
SELECT * FROM accounts WHERE user_id = 1 FOR SHARE;
```

**排他锁(X Lock / 写锁)**：允许事务更新或删除一行。排他锁与任何其他锁都不兼容。

```sql
-- 显式加排他锁
SELECT * FROM accounts WHERE user_id = 1 FOR UPDATE;
-- 其他事务的 SELECT FOR UPDATE 和 INSERT/UPDATE/DELETE 会被阻塞
```

## 14.6 锁的粒度

**表锁**：锁定整张表。开销小，但并发度低。

```sql
-- 手动加表锁
LOCK TABLES employees READ;
-- 此时所有事务都能读，但都不能写

LOCK TABLES employees WRITE;
-- 此时只有当前事务能读写，其他事务既不能读也不能写

-- 释放表锁
UNLOCK TABLES;
```

**行锁**：只锁定涉及的行。InnoDB默认使用行锁，并发度高。

```sql
-- InnoDB 在 WHERE 条件使用索引时，自动使用行锁
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
-- 只锁住 user_id = 1 这一行

-- 如果 WHERE 条件没有用到索引，会退化为表锁！
UPDATE accounts SET balance = balance - 100 WHERE user_name = '张三';
-- 如果 user_name 没有索引，整张表都被锁住
```

**间隙锁(Gap Lock)**：锁定索引记录之间的"间隙"，防止其他事务在间隙中插入新行——这就是InnoDB在REPEATABLE READ下防止幻读的武器。

```sql
-- 假设索引中有 id=5 和 id=10 两条记录
-- 间隙锁会锁住 (5, 10) 这个区间

START TRANSACTION;
SELECT * FROM employees WHERE id BETWEEN 5 AND 10 FOR UPDATE;
-- 锁住了 id=5、id=10 以及 (5,10) 之间的间隙

-- 其他事务尝试插入 id=7 的记录会被阻塞
INSERT INTO employees (id, name) VALUES (7, '王五');  -- 阻塞！

COMMIT;
```

**临键锁(Next-Key Lock)**：行锁 + 间隙锁的组合，锁定记录本身及其前面的间隙。这是InnoDB在REPEATABLE READ下默认的锁算法。

> **Warning:** 间隙锁虽然解决了幻读问题，但也增加了死锁的概率。如果你的业务允许幻读，可以考虑把隔离级别降到READ COMMITTED，这时InnoDB不会使用间隙锁。

## 14.7 死锁检测与处理

死锁就是两个事务互相等待对方释放锁，谁也无法继续——就像两个人在窄路上迎面而行，谁都不肯让路。

```sql
-- 死锁场景示例
-- 事务A：
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;  -- 锁住 user_id=1
-- 等待锁住 user_id=2...

-- 事务B（同时执行）：
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 2;  -- 锁住 user_id=2
-- 等待锁住 user_id=1...
-- 死锁！
```

InnoDB有死锁检测机制（默认开启），检测到死锁时会自动回滚持有最少行锁的那个事务：

```sql
-- 查看死锁检测是否开启
SHOW VARIABLES LIKE 'innodb_deadlock_detect';

-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS;

-- 设置锁等待超时时间（默认50秒）
SET innodb_lock_wait_timeout = 10;
```

## 14.8 事务最佳实践

1. **事务要短**：长事务持有锁的时间长，影响并发，还可能导致Undo Log膨胀
2. **合理设置隔离级别**：大多数场景REPEATABLE READ就够了
3. **按固定顺序访问表和行**：减少死锁概率
4. **善用索引**：避免行锁退化为表锁
5. **应用层做好重试机制**：死锁回滚后自动重试

```sql
-- 一个良好的事务示例
START TRANSACTION;

-- 先查余额（加行锁）
SELECT balance FROM accounts WHERE user_id = 1 FOR UPDATE;

-- 检查余额充足后执行转账
UPDATE accounts SET balance = balance - 1000 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE user_id = 2;

-- 记录日志
INSERT INTO transfer_log (from_user, to_user, amount, created_at)
VALUES (1, 2, 1000, NOW());

COMMIT;
```

## 小结

事务是数据库可靠性的核心保障。ACID特性确保了数据的一致性，隔离级别在一致性和性能之间做权衡，MVCC实现了读写不冲突，而锁机制则保护了写操作的安全。理解这些概念不仅能帮你写出正确的SQL，还能让你在排查性能问题时有的放矢。
