## 7.1 开篇

同一 LLM，不同 Prompt，产出天差地别。Prompt = Agent 的**需求文档（PRD，Product Requirements Document）**。

## 7.2 三层框架

```
Layer 1: System Message — Agent是谁、能做什么
Layer 2: Few-shot — 例子教怎么回答
Layer 3: CoT — 引导思考方式
```

## 7.3 System Prompt — Agent 的"人设配置文件"

System Prompt 就像是一个函数的 `docstring + type hints + decorators` — 它定义了 Agent 的身份、能力边界和行为规范。

### 反面教材：模糊的 System Prompt

```python
BAD = "你是有帮助的AI助手。"
# 问题：
# 1. "有帮助"太模糊 — 什么叫有帮助？回答长还是短？技术还是通俗？
# 2. "AI助手"无边界 — 可以回答任何问题，包括它不擅长的
# 3. 无行为规范 — 可能编造信息、用"作为AI..."开头、回答过长或过短
# 类比：def func(x): pass  # 没有docstring、没有type hints、不知道做什么
```

### 正面教材：精确的 System Prompt

```python
GOOD = """你是 DocMind，Python后端和DevOps文档助手。

## 角色定位
- 身份：经验丰富的技术 Team Lead，擅长用通俗语言解释复杂概念
- 目标用户：1-5年经验的后端开发者
- 专业领域：Python / FastAPI / Docker / Kubernetes / PostgreSQL / Redis

## 能力边界
可以做：
- 解释技术概念（附代码示例）
- 排查常见错误（给出排查步骤）
- 比较技术方案（表格对比）
- 提供最佳实践建议
不可以做：
- 前端开发问题 → 推荐 MDN 或 React 官方文档
- 非技术领域 → 礼貌拒绝并引导回技术领域
- 未经验证的库/API → 标注 [UNCERTAIN]

## 输出规范
- 格式：Markdown，使用 **粗体** 标注核心概念
- 长度：简单问题 <100字，概念解释 100-300字，排查指南 300-500字
- 结构：先 TL;DR 总结，再详细展开
- 代码：必须有注释，使用 Python 3.11+ 语法
- 不确定时：标注 [UNCERTAIN]，不要编造

## 禁止行为
- 不要编造不存在的库、API、命令
- 不要用"作为AI..."开头
- 不要给出无法验证的性能数字
- 不要推荐已废弃的工具"""
```

### System Prompt 设计原则对照表

| 原则 | 类比 | 示例 |
| ------ | ------ | ------ |
| 精确角色 | 函数 docstring | "你是DocMind，Python后端文档助手" vs "你是AI助手" |
| 能力边界 | 类型注解 | "可以做X，不可以做Y" vs "尽量帮忙" |
| 行为规范 | API 文档 | "简单<100字，复杂<500字" vs "回答要合适" |
| 可测试 | assert | "不确定标注[UNCERTAIN]" vs "要诚实" |
| 结构化 | JSON Schema | 用标题/列表分隔，不是一坨文本 |

### 进阶技巧：动态 System Prompt

```python
def build_system_prompt(user_level: str, context: str) -> str:
    """根据用户水平和上下文动态生成 System Prompt"""
    base = """你是 DocMind，智能技术文档助手。
## 核心原则
- 用编程隐喻解释概念
- 代码示例必须有注释
- 不确定时标注 [UNCERTAIN]
"""
    
    # 根据用户水平调整深度
    level_config = {
        "junior": """
## 用户水平：初级（0-1年）
- 解释要通俗，避免过多术语
- 每个概念先给"一句话总结"
- 代码示例要简单，避免高级特性
- 多用类比：Redis ≈ Python dict（但持久化）
""",
        "mid": """
## 用户水平：中级（1-3年）
- 可以用术语，但要解释关键概念
- 代码示例可以用装饰器、async等中级特性
- 关注"为什么"而不仅是"怎么做"
""",
        "senior": """
## 用户水平：高级（3年+）
- 直接用术语，无需解释基础概念
- 代码示例可以用高级特性（metaclass、descriptor等）
- 关注性能、架构、权衡取舍
- 可以讨论设计哲学和trade-off
"""
    }
    
    # 根据上下文调整重点
    context_config = {
        "debug": "## 当前模式：问题排查\n- 给出系统化排查步骤\n- 优先检查常见原因",
        "learn": "## 当前模式：概念学习\n- 先给直觉理解，再深入细节\n- 附代码示例帮助理解",
        "compare": "## 当前模式：方案对比\n- 用表格对比\n- 给出推荐方案和理由"
    }
    
    return base + level_config.get(user_level, level_config["mid"]) + \
           context_config.get(context, context_config["learn"])

# 使用
junior_debug = build_system_prompt("junior", "debug")
senior_compare = build_system_prompt("senior", "compare")
print("=== Junior Debug Mode ===")
print(junior_debug[:200] + "...")
print("\n=== Senior Compare Mode ===")
print(senior_compare[:200] + "...")
```

**注意**：System Prompt 太长（>2000 tokens）会导致——每次请求都多花钱（按 token 计费）；占用 Context Window，留给对话历史的空间变少；LLM 可能"忘记"后面的指令（Lost in the Middle 问题，见 2.7）。对策：精简措辞删除冗余，只保留核心规则、细节用 Few-shot 教，定期 review 删掉不再需要的规则。

## 7.4 Few-shot — 用例子"教"Agent

Few-shot 就像是给函数写单元测试 — 通过几个精选示例，让 LLM 理解你想要的输入→输出映射。

### 为什么 Few-shot 有效？

```python
# Zero-shot（无示例）— LLM 猜测你想要什么
prompt_zero = "分类这个技术问题：FastAPI JWT?"
# 可能输出："这是一个关于身份验证的问题" ← 太泛

# Few-shot（有示例）— LLM 精确模仿你的格式
prompt_few = """分类技术问题，输出格式：分类:X/Y 难度:初级/中级/高级 标签:A,B,C

示例1
输入: FastAPI JWT?
输出: 分类:Web/认证 难度:中级 标签:FastAPI,JWT,Security

示例2
输入: Docker DNS?
输出: 分类:DevOps/容器 难度:中级 标签:Docker,DNS,网络

示例3
输入: Redis RDB vs AOF?
输出: 分类:DB/缓存 难度:初级 标签:Redis,持久化,配置

请处理:
输入: K8s HPA?
输出:"""
# 输出："分类:DevOps/编排 难度:高级 标签:Kubernetes,HPA,自动扩缩" ← 精确！
```

完整实现、动态示例选择与 token 成本对照放在 §8.3——那里把 Few-shot 当作一种推理策略，与 Zero-shot 做横向比较；本节只保留“为什么有效”和书写规范。

### Few-shot 最佳实践

```python
# 正确做法
good_practices = {
    "质量>数量": "3个精选示例 > 10个随意示例",
    "覆盖边界": "包含正常/异常/边界情况的示例",
    "格式一致": "所有示例输入输出格式完全一致",
    "多样性": "示例覆盖不同类别，避免偏见",
    "简洁": "示例输入不要太长，避免占用过多 token"
}

# 常见错误
bad_practices = {
    "太少": "只有1个示例 → LLM可能过拟合这个特例",
    "太偏": "全是简单示例 → 复杂问题处理不好",
    "格式乱": "示例1用JSON，示例2用YAML → LLM困惑",
    "太长": "每个示例100行 → token爆炸",
    "无边界": "没有展示『不应该做什么』的示例 → LLM可能越界"
}

# 示例：展示"不应该做什么"
negative_examples = [
    {"in": "今天天气怎么样?", "out": "[OUT_OF_SCOPE] 我只回答技术问题"},
    {"in": "帮我写个Python脚本", "out": "[OUT_OF_SCOPE] 我只分类问题，不生成代码"},
]
```

**注意 Few-shot 的 token 成本**：每个示例约 50-200 tokens（输入+输出），5 个示例 ≈ 250-1000 tokens，且每次请求都会带上。优化策略：示例尽量简洁（输入<20字，输出<30字）；动态选择，只带最相关的 2-3 个；缓存常用示例，避免重复构建。

## 7.5 Chain-of-Thought (CoT) — 让 Agent "写注释"思考

CoT 就像是让程序员在写代码前先写伪代码/注释 — 强制分步思考，避免跳步出错。

### 为什么 CoT 有效？

```python
# 无 CoT — LLM 直接给答案（像不看题直接猜答案）
question = "一个FastAPI服务有3个endpoint，每个endpoint平均处理2个数据库查询，" \
           "每个查询50ms，网络延迟10ms，求总延迟"

# 直接问（可能出错）
direct = f"{question} 总延迟是多少？"
# LLM 可能输出："约 300ms" ← 跳步了，可能算错

# 用 CoT（强制分步）
cot = f"""{question}

让我们一步一步计算：
1. 首先，计算单个 endpoint 的延迟
2. 然后，考虑并发情况
3. 最后，给出总延迟"""
# LLM 输出：
# "1. 单endpoint: 2查询×50ms + 10ms网络 = 110ms
#  2. 3个endpoint并发: max(110ms, 110ms, 110ms) = 110ms
#  3. 如果是串行: 3×110ms = 330ms
#  总延迟: 并发110ms，串行330ms" ← 更准确！
```

三种写法的完整实现与效果对比在 §8.4；Self-Consistency 与 ToT 分别在 §8.5、§8.6。本节只需要记住：CoT 的本质是把思考过程显式写进 Prompt，具体选型交给第8章。

### CoT 变体对比

| 变体 | 适用场景 | Token 成本 | 准确性 |
| ------ | ---------- | ----------- | -------- |
| Zero-shot CoT | 快速原型、简单问题 | 低 | 中 |
| Few-shot CoT | 复杂问题、需要特定格式 | 高 | 高 |
| 手动步骤 CoT | 你知道该怎么分析 | 中 | 高（引导强） |
| Auto-CoT | 自动化场景 | 中 | 中高 |

**CoT 的 trade-off**：换来准确性提升（尤其是数学、逻辑、多步推理），代价是 token 消耗增加（思考过程也要钱）和延迟增加（输出更长）。何时用：多步推理（数学、逻辑）必须用；简单查询（概念解释）不需要；工具调用（Agent）用 ReAct（CoT + Action）。

## 7.6 ReAct — 推理 + 行动的完美结合

ReAct = **Re**asoning + **Act**ing，是 Agent 的核心思维模式。它把 CoT（思考）和 Tool Use（行动）结合成一个循环：

```
Thought: 分析问题，决定下一步
Action: 选择工具并执行
Observation: 观察工具返回结果
Thought: 根据结果继续分析
Action: ...
... (循环直到解决)
Final Answer: 给出最终答案
```

### ReAct 为什么重要？

```python
# 纯 CoT（只思考，不能行动）
# 问题："我的 Docker 容器端口 8080 被谁占用了？"
# 思考："端口被占用可能是 nginx、Apache、或其他服务..."
# ← 光想没用，需要真正去检查！

# 纯 Tool Use（只行动，不思考）
# 执行 lsof -i :8080 → 返回 "nginx 12345"
# ← 拿到结果但不知道意味着什么，给不出建议

# ReAct（思考 + 行动）
# Thought: 端口被占用，需要检查谁在用
# Action: lsof -i :8080
# Observation: nginx 12345 root 6u IPv4 ...
# Thought: nginx 占用了 8080，给用户两个选择
# Final Answer: "端口 8080 被 nginx(PID 12345)占用。方案：a)停止nginx b)用其他端口"
```

### ReAct Prompt 模板

```python
REACT_SYSTEM = """你是一个技术问题排查助手。使用以下格式回答问题：

Thought: 分析问题，说明你在想什么、为什么这么做
Action: 要使用的工具（必须是可用工具之一）
Action Input: 工具的输入参数
Observation: 工具返回的结果
... (Thought/Action/Observation 可以重复多次)
Thought: 我现在知道最终答案了
Final Answer: 对原始问题的最终回答

可用工具：
- check_port(port): 检查端口占用
- run_command(cmd): 执行 shell 命令
- search_docs(query): 搜索技术文档

重要规则：
1. 每次只能调用一个工具
2. 必须等 Observation 后才能继续
3. 不要编造 Observation
4. 如果不确定，可以继续调查"""

# 模拟一个 ReAct 对话
react_example = """
用户: 我的 FastAPI 服务启动失败，报 "Address already in use"

Thought: 这个错误说明端口被占用了。需要先知道是哪个端口，然后检查占用情况。
        FastAPI 默认用 8000 端口。
Action: check_port
Action Input: 8000
Observation: COMMAND   PID  USER   FD   TYPE
             python   12345 dev    3u  IPv4  TCP *:8000 (LISTEN)

Thought: 端口 8000 被另一个 Python 进程（PID 12345）占用。
        可能是之前没关掉的 FastAPI 实例。给用户两个选择。
Final Answer: 端口 8000 被另一个 Python 进程（PID 12345）占用。
解决方案：
1. 杀掉旧进程：kill 12345
2. 或用其他端口：uvicorn main:app --port 8001
"""
```

完整的 ReAct 循环（解析 Thought/Action、执行工具、回填 Observation、失败恢复）是第16章的主题；这里只保留 Prompt 模板，因为“怎么把 ReAct 格式写给模型看”本身就是提示工程。

## 7.7 Prompt 反模式和系统化调试

写 Prompt 和写代码一样，有常见的反模式（Anti-patterns）和系统化的调试方法。

### 反模式 1：指令冲突

```python
# 反例：冲突的指令 — LLM 不知道听哪个
conflicting = """回答要简洁，一两句话搞定。
但同时要详细解释每个概念，给出代码示例，分析优缺点。"""
# 结果：LLM 纠结，输出不稳定

# 正例：分场景定义
```

### 系统化调试方法

```python
class PromptDebugger:
    """Prompt 调试器 — 像调试代码一样调试 Prompt"""
    
    def __init__(self, base_prompt: str):
        self.base_prompt = base_prompt
        self.history = []  # 记录每次修改
    
    def bisect_debug(self, test_cases: list[dict]) -> dict:
        """二分法：找出哪部分 Prompt 导致问题
        
        类比：git bisect — 快速定位引入 bug 的 commit
        """
        # 1. 把 Prompt 分成若干段
        sections = self.base_prompt.split("\n\n")
        
        # 2. 逐段测试，找出问题段
        results = {}
        for i, section in enumerate(sections):
            test_prompt = "\n\n".join(sections[:i+1])
            result = self._test_prompt(test_prompt, test_cases)
            results[f"section_{i}"] = result
        
        # 3. 定位到问题段后，细化修复
        return results
    
    def ab_test(self, variant_a: str, variant_b: str, 
                test_cases: list[dict]) -> dict:
        """A/B 测试：对比两个 Prompt 版本
        
        类比：AB测试 — 数据说话，不靠直觉
        """
        result_a = self._test_prompt(variant_a, test_cases)
        result_b = self._test_prompt(variant_b, test_cases)
        
        return {
            "variant_a": result_a,
            "variant_b": result_b,
            "winner": "A" if result_a["score"] > result_b["score"] else "B"
        }
    
    def edge_case_test(self, prompt: str) -> dict:
        """边界测试：测试极端情况
        
        类比：单元测试的边界用例
        """
        edge_cases = [
            {"input": "", "desc": "空输入"},
            {"input": "a" * 5000, "desc": "超长输入"},
            {"input": "！！！？？？", "desc": "纯符号"},
            {"input": "SELECT * FROM users; DROP TABLE users;", "desc": "注入攻击"},
            {"input": "今天天气怎么样?", "desc": "超领域问题"},
            {"input": "我是初学者" + "请解释Python" * 100, "desc": "重复内容"},
        ]
        
        results = {}
        for case in edge_cases:
            try:
                result = self._test_prompt(prompt, [case])
                results[case["desc"]] = "PASS" if result["score"] > 0.5 else "FAIL"
            except Exception as e:
                results[case["desc"]] = f"ERROR: {e}"
        
        return results
    
    def _test_prompt(self, prompt: str, test_cases: list[dict]) -> dict:
        """执行测试并评分

        每个用例格式：{"input": 用户输入, "expected": "期望关键词1|期望关键词2"}
        评分规则：命中期望关键词的比例；未给 expected 时，模型能正常返回即记满分。
        （生产环境建议换成 LLM 打分，见第26章评估与测试）
        """
        scores = []
        for case in test_cases:
            response = client.chat.completions.create(
                model="deepseek-chat",
                messages=[
                    {"role": "system", "content": prompt},
                    {"role": "user", "content": case["input"]}
                ],
                temperature=0
            ).choices[0].message.content

            keywords = [kw for kw in case.get("expected", "").split("|") if kw]
            if keywords:
                hits = sum(1 for kw in keywords if kw in response)
                scores.append(hits / len(keywords))
            else:
                # 未给期望关键词：模型正常返回、未崩溃即通过
                scores.append(1.0 if response.strip() else 0.0)
        return {"score": sum(scores) / len(scores) if scores else 0}

# 使用示例
debugger = PromptDebugger(base_prompt="你是 DocMind，技术文档助手。只回答技术问题。")

# 测试集：expected 里用 | 分隔期望命中的关键词
test_cases = [
    {"input": "什么是装饰器？", "expected": "装饰器|函数"},
    {"input": "今天天气怎么样？", "expected": "OUT_OF_SCOPE"},
]

# 1. 二分法定位问题段
bisect_results = debugger.bisect_debug(test_cases=test_cases)
print(bisect_results)

# 2. A/B 测试对比两个版本

    variant_a="你是DocMind。回答技术问题，简洁准确。",
    variant_b="你是DocMind，技术文档助手。回答需给出步骤和代码示例。",
    test_cases=test_cases
)
print(ab_results)

# 3. 边界测试

print(edge_results)
# 输出：{"空输入": "PASS", "超长输入": "FAIL", ...}
```

### Prompt 调试 Checklist

```python
debug_checklist = """
=== Prompt 调试 Checklist ===

□ 1. 指令是否清晰？
     - 角色定义明确？
     - 能力边界清楚？
     - 输出格式指定？

□ 2. 是否有冲突？
     - 没有矛盾的指令？
     - 长度要求合理？

□ 3. Few-shot 是否足够？
     - 至少2-3个示例？
     - 覆盖边界情况？
     - 格式一致？

□ 4. 是否测试边界？
     - 空输入？
     - 超长输入？
     - 超领域问题？

□ 5. 是否有版本控制？
     - 每次修改有记录？
     - 可以回滚？
     - 有基准测试？

□ 6. Token 成本是否合理？
     - System Prompt < 1000 tokens?
     - Few-shot 示例精简？
     - 没有冗余内容？
"""
print(debug_checklist)
```

**调试 Prompt 的黄金法则**：一次改一个变量，不要同时改多处；用数据说话，准备测试集不靠感觉；记录每次修改，像 git commit 一样；测试边界情况（空、长、乱、攻击）；定期 review——Prompt 也需要重构。

## 7.8 实战：DocMind System Prompt

```python
import os
from openai import OpenAI
from dotenv import load_dotenv
load_dotenv()

SP = """你是 DocMind，智能技术文档助手。
## 角色: 像经验丰富的技术Lead，目标用户1-5年后端
## 能力: 概念解释(+代码) | 问题排查(错误→步骤) | 方案比较(表格) | 代码示例(含注解)
## 规范: Markdown; **粗体**标概念; 含TL;DR; 快<100字/概念100-300字/排查300-500字
## 行为: 超领域→推荐; 歧义→确认; 危险操作→警告; 不用"作为AI..."开头"""

class DocMindV1:
    def __init__(self, m="deepseek-chat"):
        self.c = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com"); self.m = m
    def chat(self, q, h=None):
        msgs = [{"role":"system","content":SP}] + (h or []) + [{"role":"user","content":q}]
        return self.c.chat.completions.create(model=self.m, messages=msgs,
            temperature=0.3, max_tokens=1500).choices[0].message.content
    def explain(self, c): return self.chat(f"解释「{c}」，面向Python开发者，附代码。")
    def troubleshoot(self, e, ctx=""):
        return self.chat(f"错误:\n```\n{e}\n```" + (f"\n上下文:{ctx}" if ctx else ""))
    def compare(self, opts, scenario):
        return self.chat(f"场景:{scenario}\n方案:\n" +
                        "\n".join(f"- {o}" for o in opts) + "\n表格对比并推荐。")

dm = DocMindV1()
print(dm.explain("Python装饰器"))
print(dm.troubleshoot("psycopg2.OperationalError: connection slots reserved",
                      "FastAPI+SQLAlchemy+PG,200并发"))
print(dm.compare(["Celery+Redis","Dramatiq+RabbitMQ","RQ"], "FastAPI异步任务"))
```

## 本章小结

- Prompt 是给 Agent 写的需求文档：同一 LLM，不同 Prompt，产出天差地别。
- 三层框架从外到内：System Message 定人设，Few-shot 教格式，CoT 引导思考。
- System Prompt 像函数签名：角色、能力边界、输出规范、禁止行为缺一不可，总量控制在 2000 tokens 以内。
- Few-shot 质量 > 数量：3 个精选、格式一致、覆盖边界的示例，胜过 10 个随意的。
- CoT 强制分步思考，多步推理必备；简单查询不用，省 token 也省延迟。
- ReAct 把思考接上行动：Thought → Action → Observation 循环；本章只负责写对 Prompt 模板，完整循环见第16章。
- 四大反模式：指令冲突、否定过多、无结构、假设模型懂你的上下文——怀疑 Prompt 有问题时先对照这张清单。
- 调 Prompt 像调试代码：一次改一个变量、用测试集说话、记录每次修改、测边界情况。
