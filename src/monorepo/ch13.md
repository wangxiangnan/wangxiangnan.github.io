# Ch13：版本管理与发布

## 本章目标

- 理解 monorepo 中两种版本管理策略的优劣
- 掌握 Changesets 3 的安装、配置和使用
- 学会创建 changeset 并理解版本类型选择
- 实现自动 Changelog 生成
- 掌握完整的版本发布流程
- 在 CI 中通过 `changesets/action@v2` 实现自动化发布

## 13.1 Monorepo 版本管理策略

在 monorepo 中管理版本比单包项目复杂得多，因为有多个包需要协调版本。业界主要有两种策略：

### 策略一：固定版本（Lockstep / Fixed Version）

所有包共享同一个版本号。每次发布时，所有包同时升级版本。

```txt
packages/shared:   v2.3.0
packages/ui:       v2.3.0
packages/database: v2.3.0
apps/web:          v2.3.0
apps/api:          v2.3.0
```

**优点**：

- 简单，版本对应关系清晰
- 不需要担心跨包版本兼容性问题

**缺点**：

- 一个包的微小改动会导致所有包升级版本
- 对于发布到 npm 的公共包来说，频繁的不必要版本升级会困扰用户

**代表项目**：Angular、Babel

### 策略二：独立版本（Independent Version）

每个包维护自己的版本号，按需升级。

```txt
packages/shared:   v1.2.0
packages/ui:       v2.0.1
packages/database: v0.5.3
apps/web:          v3.1.0
apps/api:          v1.0.0
```

**优点**：

- 每个包的版本号有意义，反映其自身的变更
- 用户可以只升级需要的包

**缺点**：

- 需要处理包之间的版本依赖关系
- 管理更复杂

**代表项目**：Vue、Vite

### 我们的选择

对于 **内部应用**（`apps/web`、`apps/api`），它们不发布到 npm，版本管理不是重点，用 Git tag 或 Docker image tag 追踪即可。

对于 **共享包**（`packages/shared`、`packages/ui`、`packages/database`），如果要发布到 npm，建议使用**独立版本**，让版本号反映各自的变更。

**Changesets** 同时支持独立版本和固定版本，也是当前 monorepo 版本管理的事实标准。

## 13.2 Changesets 3 的安装与配置

按 Ch04 的 catalog 约定，先把 Changesets 加进 `pnpm-workspace.yaml`：

```yaml
catalogs:
  release:
    "@changesets/cli": ^3.0.3
    "@changesets/changelog-github": ^1.0.1
```

在根 `package.json` 的 `devDependencies` 中引用：

```json
{
  "devDependencies": {
    "@changesets/changelog-github": "catalog:release",
    "@changesets/cli": "catalog:release"
  }
}
```

安装并初始化：

```bash
pnpm install
pnpm changeset init
```

`changeset init` 会在根目录生成 `.changeset/` 目录和 `config.json`。修改为：

**.changeset/config.json**：

```json
{
  "$schema": "https://unpkg.com/@changesets/config@4.0.1/schema.json",
  "changelog": [
    "@changesets/changelog-github",
    { "repo": "your-github-username/taskflow" }
  ],
  "commit": false,
  "fixed": [],
  "linked": [],
  "access": "public",
  "baseBranch": "main",
  "updateInternalDependencies": "patch",
  "ignore": [
    "@taskflow/web",
    "@taskflow/api",
    "@taskflow/e2e",
    "@taskflow/ui",
    "@taskflow/database"
  ]
}
```

让我们逐项理解这些配置：

### `$schema`

指向与 `@changesets/cli@3` 配套的 `@changesets/config@4` schema。Changesets 升级大版本时 schema 也会变，建议和 `pnpm-lock.yaml` 一起更新；不要手写一个过期的 schema 地址，否则编辑器校验的字段可能和 CLI 实际支持的不一致。

### `changelog`

```json
"changelog": [
  "@changesets/changelog-github",
  { "repo": "your-github-username/taskflow" }
]
```

使用 GitHub 风格的 changelog 生成器，它会在 changelog 中包含 PR 链接、commit 链接和贡献者信息。`repo` 必须是 `owner/repo` 形式。如果不使用 GitHub，可以用 `@changesets/changelog-git`（只写 commit hash）或 `false`（不生成 changelog）。

> `@changesets/changelog-github` 是独立包，需要像上面那样显式安装。只装 `@changesets/cli` 时，CLI 内置的是 `@changesets/changelog-git`。

### `commit`

```json
"commit": false
```

设为 `false` 表示 `changeset version` 不会自动创建 git commit。推荐这样做：版本号、CHANGELOG 和删除的 changeset 文件都会被留在工作区，方便你在提交前检查。设为 `true` 时，每次 `changeset version` 都会自动提交。

### `fixed` 和 `linked`

```json
"fixed": [],
"linked": []
```

- **`fixed`**：数组中的包共享同一个版本号。例如 `[["@taskflow/shared", "@taskflow/ui"]]` 表示这两个包永远同版本发布。
- **`linked`**：数组中的包一起发布，但各自保留版本号；升级时保持它们之间的相对版本差，而不是强行对齐到同一个号。

对于大多数项目，保持为空（独立版本）就好。

### `access`

```json
"access": "public"
```

- **`restricted`**（默认）：发布为私有包，只有付费 npm 组织可用
- **`public`**：发布为公开包

`@taskflow/*` 是 scoped 包，npm 默认按私有处理。本教程的 `@taskflow/shared` 要公开发布，所以这里设为 `public`；同时它自己的 `publishConfig.access` 也有同样设置（见 13.10），两者保持一致。

> `apps/*` 和 `ui`、`database` 都是 `"private": true`，Changesets 默认不会为私有包升版本或发布。`ignore` 里的声明是显式的"双保险"：即使将来有人误删了 `private` 字段，也不会把它们发布出去。

### `baseBranch`

```json
"baseBranch": "main"
```

Changesets 判断"哪些 change 还没被消费"时使用的基线分支，通常是 `main` 或 `master`。

### `updateInternalDependencies`

```json
"updateInternalDependencies": "patch"
```

当上游包升级时，依赖它的包至少升级 `patch`。例如你同时发布 `@taskflow/ui` 和 `@taskflow/shared`，且 `ui` 依赖 `shared`：`shared` 从 `0.1.0` 升到 `0.2.0` 时，`ui` 里记录的依赖范围和自身版本都会被更新。另一个可选值是 `minor`，含义是内部依赖变更至少触发 minor。

在本教程中，`shared` 没有可发布的下游包（web / api 都在 `ignore` 里），所以这个设置当前不会产生实际版本变更，主要是为将来发布多个包做准备。

### `ignore`

```json
"ignore": [
  "@taskflow/web",
  "@taskflow/api",
  "@taskflow/e2e",
  "@taskflow/ui",
  "@taskflow/database"
]
```

应用、E2E 和内部包不发布到 npm，不需要版本管理。它们通过 Git tag 或 Docker image tag 来追踪版本。**本教程只有 `@taskflow/shared` 走发布流程**（Ch03 没有给它加 `private`）；`ui` 直接暴露源码、没有构建产物，`database` 依赖数据库环境，两者都保持 private 并列入 `ignore`。如果你要发布自己的库，把目标包移出 `ignore`，并完成 13.7 的公开包配置。

## 13.3 创建 Changeset：记录变更

每次你做了一个**需要发布**的改动，都应该创建一个 changeset。

```bash
# 创建一个新的 changeset
pnpm changeset
```

CLI 会交互式地询问（不同版本的措辞略有差异）：

```txt
🦋  Which packages would you like to include?
│  ◯ changed packages
│    ◯ @taskflow/shared
│  ◯ all packages

🦋  Which packages should have a major bump?
│  ◯ all packages
│    ◯ @taskflow/shared

🦋  Which packages should have a minor bump?
│  ◯ all packages
│    ◯ @taskflow/shared

🦋  Please enter a summary for this change.
│  › feat: 为 User 类型新增可选的 bio 字段

🦋  Is this your desired changeset? (Y/n) › Y
```

候选列表来自"可发布且未被 `ignore` 的包"。本教程只有 `@taskflow/shared` 符合条件；被 `ignore` 或标记为 private 的包不会出现在这里。

这会在 `.changeset/` 目录下生成一个 markdown 文件（文件名是随机生成的）：

**.changeset/brave-lions-dance.md**：

```markdown
---
"@taskflow/shared": minor
---

feat: 为 User 类型新增可选的 bio 字段

`User` 新增 `bio?: string`，用于个人简介。该字段可选，
现有调用方无需修改。
```

**只有列在文件顶部的包才会被升版本**。`shared` 升级后，依赖它的包会按 `updateInternalDependencies` 自动获得 patch 升级，不需要手写进 changeset。

> **为什么不让工具自动判断版本类型？** 因为只有开发者知道改动的语义：修 bug 是 `patch`，新增向后兼容的功能是 `minor`，删除 API 或改变行为是 `major`。自动化工具可以猜，但猜错一次就会让用户装到不兼容的版本。

如果某个改动确实不需要发布（例如只改了 CI 配置、README 或测试），用 `pnpm changeset add --empty` 生成一个空 changeset，明确表示"这次变更已评估，不需要发版"。

### 版本类型说明

| 类型 | 语义 | 版本变化示例 | 何时使用 |
| ------ | ------ | ------------- | --------- |
| `patch` | 补丁 | 0.1.0 → 0.1.1 | Bug 修复、文档修正、内部重构 |
| `minor` | 次版本 | 0.1.0 → 0.2.0 | 新增功能（向后兼容） |
| `major` | 主版本 | 0.1.0 → 1.0.0 | 破坏性变更（删除 API、改变行为） |

> `0.x` 阶段的包同样遵守这套语义。Changesets 不会因为版本号是 `0.x` 就特殊处理 `major`，所以小版本迭代期间要格外谨慎地判断改动是否破坏兼容性。

### 在 CI 中检查 changeset

为了防止开发者忘记创建 changeset，可以在 CI 中添加检查：

```yaml
# .github/workflows/changeset-check.yml
name: Changeset Check

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    # 版本发布 PR 里 changeset 已被消费，跳过检查
    if: github.head_ref != 'changeset-release/main'
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: pnpm/setup@v3
      - name: Check for changesets
        run: pnpm changeset status --since=origin/main
```

`fetch-depth: 0` 是必需的：`--since=origin/main` 需要完整历史才能取到基线分支。`pnpm/setup@v3` 会安装 pnpm、Node 并在检测到 `package.json` 时自动执行 `pnpm install`。

`changeset status` 在"有包被修改、但没有对应 changeset"时会以非零状态退出，正好可以当作检查用。`changeset-release/main` 是 `changesets/action` 创建版本 PR 时使用的分支名，必须跳过，否则版本 PR 一定会失败。

> **为什么这个检查很重要？** 忘记创建 changeset 是最常见的发布事故原因之一。没有 changeset，`changeset version` 不会升级任何版本，你的改动会被"静默遗漏"在下一次发布之外。

## 13.4 自动生成 Changelog

当你运行 `changeset version` 时，Changesets 会：

1. 消费所有 `.changeset/*.md` 文件
2. 根据声明的版本类型升级各包的版本号
3. 更新包之间的内部依赖版本
4. 在每个包的根目录生成或更新 `CHANGELOG.md`

**生成的 CHANGELOG.md 示例**：

```markdown
# @taskflow/shared

## 0.2.0

### Minor Changes

- [#42](https://github.com/your-github-username/taskflow/pull/42) [`abc1234`](https://github.com/your-github-username/taskflow/commit/abc1234) Thanks [@your-github-username](https://github.com/your-github-username)! - feat: 为 User 类型新增可选的 bio 字段

### Patch Changes

- Updated dependencies [[`def5678`](https://github.com/your-github-username/taskflow/commit/def5678)]:
  - @taskflow/tsconfig@0.2.0
```

标题层级是 `## 版本号` + `### Minor Changes`，这是 Changesets 的固定格式，不要手改，否则下一次生成会与历史记录不一致。

**在 `package.json` 中配置 repository 字段**，changelog 里的 PR / commit 链接才能正确指向仓库：

```json
{
  "name": "@taskflow/shared",
  "repository": {
    "type": "git",
    "url": "https://github.com/your-username/taskflow",
    "directory": "packages/shared"
  }
}
```

`directory` 字段让 GitHub 上的 "View source" 链接直接跳到 monorepo 子目录，发布公共包时建议填写。

## 13.5 版本发布流程

完整的发布流程如下：

### 步骤一：日常开发中创建 changesets

```bash
# 每次做完一个需要发布的功能/修复后
pnpm changeset
# 按照提示选择包和版本类型，输入变更描述
```

这些 changeset 文件会和代码一起提交到 Git。

### 步骤二：准备发布时，执行版本升级

```bash
# 在 main 分支上执行
git checkout main
git pull origin main

# 消费所有 changesets，升级版本号
pnpm changeset version
```

这个命令会：

- 删除 `.changeset/` 中已被消费的 changeset 文件
- 更新各包的 `package.json` 中的 `version` 字段
- 更新依赖该包的其他包的依赖版本
- 生成/更新 `CHANGELOG.md`

### 步骤三：检查并提交版本变更

```bash
# 查看变更
git diff

# 确认无误后提交
git add -A
git commit -m "chore: version packages"
```

### 步骤四：发布到 npm

```bash
# 构建所有包并发布
turbo run build
pnpm changeset publish
```

`changeset publish` 会：

- 对比 registry 上的版本，只发布版本号更高的包
- 调用 `npm publish`，因此各包的 `prepublishOnly` 生命周期脚本会执行
- 为每个发布的包创建 **annotated git tag**（如 `@taskflow/shared@0.2.0`）

### 步骤五：推送变更和 tags

```bash
git push origin main
git push origin --follow-tags
```

Changesets 使用 `git tag -m` 创建 annotated tag，所以 `--follow-tags` 能把它们一起推上去；如果用默认的 lightweight tag，`--follow-tags` 不会推送，必须显式 `git push --tags`。

> **本地手动发布适合第一次尝试。** 团队协作时应使用 13.8 的自动化流程：由 CI 创建版本 PR，合并后自动发布，避免"谁的机器上有 npm token 谁就能发版"。

## 13.6 完整的发布脚本

把散落的命令收进根 `package.json`：

```json
{
  "scripts": {
    "changeset": "changeset",
    "version-packages": "changeset version",
    "release": "turbo run build && changeset publish",
    "release:check": "turbo run build lint test typecheck",
    "release:push": "git push --follow-tags"
  }
}
```

几个命名上的坑：

- **不要叫 `version`**：`pnpm version` 是 pnpm 内置命令（等价于 `npm version`，会改版本号并创建 commit/tag），不会执行同名脚本。叫 `version-packages` 才能用 `pnpm version-packages` 明确调用。
- **不要叫 `publish`**：`pnpm publish` 同样是内置命令，会把**当前包**发布出去；在根目录执行会尝试发布根 `package.json`（它是 `private: true`，直接报错）。
- **`release` 先构建再发布**：Turborepo 会按依赖顺序构建，并复用缓存。`changeset publish` 本身不负责构建。
- **`release:check` 与发布解耦**：CI 里先跑检查，通过后才允许发布；本地也可以单独执行。

> **为什么用 `release:check` 而不是 `prepublish`？** `prepublish` 是 npm 的**安装生命周期**脚本：npm 7+ 在本机执行 `npm install` 时也会运行它。把它定义成"构建 + lint + test"会让每次安装依赖都跑一遍完整检查。发布前的构建应该放在 `release` 脚本或各包的 `prepublishOnly` 里，而不是根目录的 `prepublish`。

## 13.7 私有包 vs 公开包的发布配置

### 私有包（Private Packages）

如果包不发布到 npm，在 `package.json` 中设置：

```json
{
  "name": "@taskflow/e2e",
  "private": true
}
```

`private: true` 会完全阻止发布（`npm publish` 直接报错），Changesets 也会跳过它——即使忘了写进 `ignore`。

### 公开包（Public Packages）

scoped 包默认按私有处理，要公开发布必须在包级别显式声明：

```json
{
  "name": "@taskflow/shared",
  "publishConfig": {
    "access": "public"
  }
}
```

注意是 **`publishConfig.access`**，不是顶层的 `"access"`。顶层没有这个字段，写了也不会生效。

`.changeset/config.json` 里的 `access` 是**默认值**，包里的 `publishConfig` 优先级更高。两者都写 `public` 是最不容易出错的做法。

> **`@taskflow/shared` 从 Ch03 起就没有 `private`，但它也还没有 `publishConfig.access`。** scoped 包默认按 restricted 处理，第一次发布前必须补上 `publishConfig`，否则会要求付费 npm 组织。`ui` 和 `database` 保持 `private: true`，不要为了"统一"把它们改成公开包。

### 发布到私有 Registry

如果团队使用私有 npm registry（如 Verdaccio、Artifactory），在根目录 `.npmrc` 中配置 scope 和认证：

```ini
# 根目录 .npmrc
@taskflow:registry=https://your-registry.com/
//your-registry.com/:_authToken=${NODE_AUTH_TOKEN}
```

- 第一行只把 `@taskflow/*` 指向私有 registry，其余包仍走公共 npm。
- 第二行用环境变量占位，**不要把 token 写进文件**。CI 中通过 `NODE_AUTH_TOKEN` 注入，本地可以放在 shell 环境或未提交的 `.env` 中。
- `setup-node` 生成的 `.npmrc` 也使用 `${NODE_AUTH_TOKEN}` 变量名，保持一致可以减少排错成本。

> **2026 年的 npm 发布认证**：npm 已推荐使用 **Trusted Publishing（OIDC）**，无需长期 token；传统 Granular Access Token 最长 90 天且需要绕过 2FA，已不推荐。若 registry 不支持 OIDC，再退回 `NODE_AUTH_TOKEN` 方案。下面的 CI 示例使用 token，是因为它兼容性最好；启用 OIDC 后可以删掉该环境变量并给 job 加 `id-token: write` 权限。

## 13.8 在 CI 中自动化发布（GitHub Actions）

以下工作流使用 `changesets/action@v2`（与 Changesets 3 配套）：

**.github/workflows/release.yml**：

```yaml
name: Release

on:
  push:
    branches:
      - main

concurrency: ${{ github.workflow }}-${{ github.ref }}

permissions: {}

jobs:
  release:
    name: Release
    runs-on: ubuntu-latest
    permissions:
      contents: write        # 创建 commit / tag / release
      pull-requests: write   # 创建版本 PR

    steps:
      - name: Checkout
        uses: actions/checkout@v7
        with:
          fetch-depth: 0

      - name: Setup pnpm and Node.js
        uses: pnpm/setup@v3

      - name: Configure npm auth
        uses: actions/setup-node@v7
        with:
          node-version: 24
          registry-url: 'https://registry.npmjs.org/'
          package-manager-cache: false

      - name: Build, lint, test, typecheck
        run: pnpm release:check

      - name: Create Release Pull Request or Publish
        id: changesets
        uses: changesets/action@v2
        with:
          # 有未消费的 changeset 时，创建/更新版本 PR
          # 版本 PR 合并后，执行 publish 脚本发布
          version-script: pnpm version-packages
          publish-script: pnpm release
          commit-message: 'chore: version packages'
          pr-title: 'chore: version packages'
          create-github-releases: true
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

**这个工作流的工作原理**：

1. **main 分支有新的 push 时触发**
2. **检查**：构建、lint、测试、类型检查全部通过才继续
3. **`changesets/action@v2`**：
   - 如果存在未消费的 changesets，创建一个 "Version Packages" 的 PR（包含版本号、CHANGELOG 和删除 changeset 的改动）
   - 这个 PR 被 review 并合并后，工作流再次触发；此时没有待消费的 changeset，action 改为执行 `publish-script`，发布到 npm
4. **`create-github-releases: true`** 会为每个发布的包创建 GitHub Release 并打 tag

> **为什么通过 PR 来发布？** 这给了团队一个 review 的机会——合并前可以检查版本号是否正确、CHANGELOG 是否合理。这比在 push 时直接发布安全得多。

### v1 到 v2 的输入变化

`changesets/action@v2` 的输入名改成了 kebab-case，从旧教程迁移时最容易在这里踩坑：

| v1（Changesets 2） | v2（Changesets 3） |
| ------------------- | ------------------- |
| `publish` | `publish-script` |
| `version` | `version-script` |
| `commit` | `commit-message` |
| `title` | `pr-title` |
| `createGithubReleases` | `create-github-releases` |
| 输出 `publishedPackages` | 输出 `published-packages` |

另外，v2 要求把自定义 token 通过 `github-token` **输入**传入；设置 `GITHUB_TOKEN` 环境变量不会配置该 action（默认会使用 GitHub 自动提供的 token，所以上面的示例不需要传）。

### 两个必须检查的仓库设置

1. **Settings → Actions → General → Workflow permissions**：允许 GitHub Actions 创建和审批 PR，否则版本 PR 无法自动创建。
2. **Secrets**：在仓库或组织级别添加 `NPM_TOKEN`。`actions/setup-node` 会把 registry 认证写成 `${NODE_AUTH_TOKEN}`，所以工作流里注入的是 `NODE_AUTH_TOKEN`，值来自 `secrets.NPM_TOKEN`。

> 使用 npm Trusted Publishing 时，不需要 `NPM_TOKEN`；给 job 增加 `id-token: write` 权限并去掉 auth 步骤即可。生产环境优先考虑这种方式，token 只作为兼容方案。

## 13.9 发布前的检查与预发布

### Turborepo 如何编排检查

`release:check` 实际执行的是：

```bash
turbo run build lint test typecheck
```

执行顺序由 Ch10 的 `turbo.json` 决定，不需要在发布脚本里手写：

- `build` 依赖 `^build`，先构建上游包
- `test`、`typecheck` 依赖 `^build`，确保拿到最新的 `dist/*.d.ts`
- `lint` 不依赖构建，可以立即并行执行

Ch10 的配置已经覆盖了这些任务，发布章节不需要再新增 turbo 任务。如果只想检查受影响的包，可以用：

```bash
turbo run build lint test typecheck --affected
```

### 快照发布（Snapshot）

需要让用户提前试用某个提交时，用 Changesets 3 的 snapshot 模式，而不是随便打一个 `1.0.1`：

```bash
# 生成 0.0.0-canary-<时间戳> 形式的版本号
pnpm changeset version --snapshot canary

# 用 canary dist-tag 发布，不影响 latest
pnpm changeset publish --tag canary --no-git-tag
```

关键点：

- **不要提交** snapshot 产生的版本改动。它只用于发布，不代表仓库应有的版本状态；建议在临时分支上执行。
- **必须带 `--tag`**。否则 snapshot 会被发布到 `latest`，用户 `pnpm add` 时默认装到的就是临时版本。
- `--no-git-tag` 跳过 Git tag，避免污染正式 tag 列表。

如果团队要维护一条长期的 `alpha` / `beta` 预发布线，则使用 pre 模式：

```bash
pnpm changeset pre enter beta
pnpm changeset version        # 版本变为 0.2.0-beta.0
pnpm changeset publish        # 自动发布到 beta dist-tag
# 预发布结束后
pnpm changeset pre exit
pnpm changeset version        # 生成正式版本
```

`pre enter` 会在 `.changeset/pre.json` 记录状态，这个文件需要提交。pre 模式是全仓库生效的，不能只对部分包开启。

> **Snapshot 和 pre 模式怎么选？** 一次性的"帮忙验证这个 commit"用 snapshot；需要连续多个版本迭代、对外承诺语义化预发布线时用 pre 模式。不要把 snapshot 当成正式版本，也不要在 pre 模式里混入 snapshot。

## 13.10 包的发布配置清单

在发布一个包之前，确保 `package.json` 至少包含以下内容。以 `@taskflow/shared` 为例——它从 Ch03 起就没有 `private`，所以不需要额外删除；如果某个包仍是 private，先去掉该字段：

```json
{
  "name": "@taskflow/shared",
  "version": "0.2.0",
  "description": "TaskFlow 的共享类型、工具函数、常量和 Schema",
  "type": "module",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./types": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/types/index.js"
    },
    "./utils": {
      "types": "./dist/utils/index.d.ts",
      "import": "./dist/utils/index.js"
    },
    "./constants": {
      "types": "./dist/constants/index.d.ts",
      "import": "./dist/constants/index.js"
    },
    "./schemas": {
      "types": "./dist/schemas/index.d.ts",
      "import": "./dist/schemas/index.js"
    }
  },
  "files": ["dist"],
  "sideEffects": false,
  "dependencies": {
    "zod": "^4.6.7"
  },
  "engines": {
    "node": ">=24"
  },
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "https://github.com/your-username/taskflow",
    "directory": "packages/shared"
  },
  "keywords": ["taskflow", "shared", "utilities"],
  "publishConfig": {
    "access": "public"
  },
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "prepublishOnly": "pnpm build"
  }
}
```

关键字段说明：

| 字段 | 作用 | 说明 |
| ------ | ------ | ---- |
| `type` | 模块格式 | `module` 表示 ESM，与 Ch05 的构建输出一致 |
| `types` | 类型入口 | 兼容不读取 `exports` 的旧工具 |
| `exports` | 条件导出 | 每个子路径里的 `types` 必须放在 `import` 之前 |
| `files` | 发布白名单 | `["dist"]` 确保只发布构建产物 |
| `sideEffects` | 标记副作用 | `false` 帮助打包器 tree-shaking |
| `engines` | Node 版本范围 | 与根目录约束保持一致 |
| `repository` | 源码地址 | changelog 链接和 npm 页面需要 |
| `publishConfig` | 发布时配置 | scoped 公开包必须设置 `access: public` |
| `prepublishOnly` | 发布前钩子 | 兜底构建，防止发布空包或旧产物 |

> **`exports` 里的 `development` 条件不能带进 npm 包。** Ch05 为了让 Vite 直接读取 `src/` 的 TS 源码，在 `exports` 中加了 `"development": "./src/index.ts"`。这个条件只适合 workspace 内部消费；npm 包只发布 `dist/`，消费者在开发模式下解析到不存在的 `src/` 会直接报错。发布前要么删掉 `development` 条件，要么把 `src` 一起发布（不推荐）。上表的写法就是"已决定发布"后的最终形态。

另外两点：

- **`main` / `module` 不是必需的**。有 `exports` 时，现代 Node 和打包器会优先读它；`module` 甚至不是 Node 标准字段，只是打包器约定。本包只输出 ESM，不需要为了兼容 CJS 伪造一个 `main`。
- **`prepublishOnly` 是兜底，不是主构建入口**。`release` 脚本已经用 Turbo 构建过，正常情况下这里是缓存命中；但有人手动 `npm publish` 时，它能防止把未构建的目录发出去。

## 本章小结

1. **版本策略**：独立版本适合大多数 monorepo，Changesets 同时支持独立与固定版本
2. **Changesets 工作流**：`changeset`（记录变更）→ `changeset version`（升级版本号、生成 CHANGELOG）→ `changeset publish`（发布到 npm、打 annotated tag）
3. **Changelog**：`@changesets/changelog-github` 自动生成 PR / commit / 贡献者链接
4. **CI 自动化**：`changesets/action@v2` + 版本 PR，合并后自动发布；注意 v2 的 kebab-case 输入名
5. **发布前检查**：用 `release:check` 编排 build → lint → test → typecheck，避免使用会污染安装流程的 `prepublish`
6. **发布配置**：`exports`（去掉 `development` 条件）、`files`、`publishConfig.access`、`prepublishOnly` 缺一不可
7. **预发布**：一次性验证用 snapshot，长期预发布线用 `pre enter` / `pre exit`
