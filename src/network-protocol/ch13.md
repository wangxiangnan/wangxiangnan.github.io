# 第13章：HTTP 基础——Web 的基石

Part III：应用层——HTTP、DNS 与 Web 协议

## HTTP 的设计哲学：简单就是力量

1989 年，Tim Berners-Lee 在 CERN 工作期间提出了一个想法：让科学家们能方便地通过超链接共享文档。为了实现这件事，他需要一套规则——浏览器怎么向服务器要一个文件，服务器又该怎么把文件给浏览器。这就是 HTTP（HyperText Transfer Protocol，超文本传输协议）的起源。

HTTP 的设计哲学可以总结为三个关键词：

**无状态（Stateless）**：服务器不记得你是谁。每次请求都是一个全新的交互，就像你去一家餐厅吃饭，服务员每次都假装第一次见你，你必须每次都重新报上自己的会员号码。这听起来很蠢？但这是一个极其精明的工程决策——服务器不需要为每个客户端维护任何状态信息，这让服务器能同时服务成千上万个客户端而不会内存爆炸。

**请求-响应模型（Request-Response）**：客户端发请求，服务器回响应，一来一回，干净利落。没有异步回调，没有服务端主动推送（后来才有 WebSocket 来弥补这一点）。这种模型让 HTTP 极其容易理解和调试。

**文本可读（Human-Readable）**：HTTP/1.x 的报文是纯文本格式，你甚至可以用 Telnet 手动跟一个 Web 服务器对话。这意味着开发者不需要专门的解码工具就能看懂 HTTP 报文——抓个包就能分析，调试起来非常愉快。

## HTTP/1.1 报文格式

让我们看一个真实的 HTTP 请求报文：

```http
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0.0.0
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Connection: keep-alive
```

这个报文的结构是：

1. **请求行（Request Line）**：`GET /index.html HTTP/1.1` —— 方法 + 路径 + 协议版本，三部分用空格分隔
2. **头部（Headers）**：每行一个键值对，格式是 `Name: Value`，以 `\r\n` 结尾
3. **空行**：一个 `\r\n` 标志着头部的结束
4. **消息体（Body）**：GET 请求通常没有消息体；POST 请求的消息体在空行之后

再看一个响应报文：

```http
HTTP/1.1 200 OK
Date: Mon, 15 Jan 2024 08:30:00 GMT
Server: Apache/2.4.52 (Ubuntu)
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Connection: keep-alive

<!DOCTYPE html>
<html>
<head><title>Example</title></head>
<body><h1>Hello World</h1></body>
</html>
```

响应报文的结构：

1. **状态行（Status Line）**：`HTTP/1.1 200 OK` —— 协议版本 + 状态码 + 原因短语
2. **头部**：与请求头部格式相同
3. **空行**
4. **消息体**：实际的内容（HTML、JSON、图片二进制等）

注意一个关键细节：HTTP/1.1 使用 `\r\n`（CRLF）作为行分隔符，不是单纯的 `\n`。虽然很多服务器容错处理了 `\n`，但协议规范写的是 CRLF。

## 核心方法语义：每个动词都有它的脾气

HTTP 定义了一组方法（也叫"动词"），用来表达客户端想对资源执行什么操作：

**GET**：获取资源。两个重要特性——**安全**（Safe，不会修改服务器状态）和**幂等**（Idempotent，请求一次和请求一万次结果一样）。这就是为什么你刷新页面不会有什么副作用（理论上）。GET 请求的参数通常放在 URL 的查询字符串中：`/search?q=hello&page=2`。

**POST**：提交数据，通常用于创建资源或触发某个处理。它既不安全也不幂等——你在购物车里加了两次商品，购物车里真的会有两件。POST 的数据放在请求体中，没有长度限制（但服务器可能会限制）。

**PUT**：整体替换资源。如果 `/users/42` 存在，PUT 会用你提交的数据完全覆盖它；如果不存在，语义上可以创建它。PUT 是幂等的——用同样的数据 PUT 十次，结果和 PUT 一次一样。

**PATCH**：局部更新资源。与 PUT 不同，PATCH 只发送需要修改的字段。比如你只想改用户的邮箱，不需要把整个用户对象都发过去。

**DELETE**：删除资源。幂等——删除一个已经删除的资源也不会报错（返回 200 或 404 都是合理的）。

**HEAD**：和 GET 一模一样，但服务器只返回头部，不返回消息体。用于检查资源是否存在、获取资源大小等场景，省去下载整个内容的开销。

**OPTIONS**：询问服务器支持哪些方法。CORS 预检请求（Preflight）就是用的 OPTIONS——浏览器在发复杂请求之前先问一声："我能用 PUT 访问你吗？"

```http
OPTIONS /api/users HTTP/1.1
Host: api.example.com
Origin: https://frontend.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization
```

## 状态码体系：服务器的表情

HTTP 状态码是一个三位数字，第一位决定了类别：

**1xx - 信息性（Informational）**：请求正在处理中，还没完成。最常见的是 `101 Switching Protocols`——WebSocket 握手时服务器会返回这个状态码，表示"好的，我们切换到 WebSocket 协议"。

**2xx - 成功（Success）**：请求成功处理了。

- `200 OK`：最常见的成功响应
- `201 Created`：资源创建成功（POST 之后常见）
- `204 No Content`：请求成功但没有消息体（DELETE 之后常见）
- `206 Partial Content`：部分内容，配合 Range 请求实现断点续传

**3xx - 重定向（Redirection）**：资源在别的地方。

- `301 Moved Permanently`：永久重定向。浏览器会缓存这个重定向，下次直接访问新地址
- `302 Found`：临时重定向。搜索引擎不会更新索引
- `304 Not Modified`：资源没有变化，客户端可以使用缓存的版本（协商缓存的核心）
- `307 Temporary Redirect`：严格保持原方法的临时重定向（302 在某些浏览器中会把 POST 变成 GET，307 不会）

**4xx - 客户端错误（Client Error）**：请求有问题。

- `400 Bad Request`：请求格式有误
- `401 Unauthorized`：需要认证（更准确的意思应该是 "Unauthenticated"）
- `403 Forbidden`：认证了但你没权限
- `404 Not Found`：资源不存在
- `405 Method Not Allowed`：方法不被允许（比如对一个只读接口发了 POST）
- `429 Too Many Requests`：请求太频繁，被限流了

**5xx - 服务器错误（Server Error）**：服务器出了问题。

- `500 Internal Server Error`：服务器内部错误，万能兜底码
- `502 Bad Gateway`：网关或代理服务器从上游收到了无效响应（Nginx 代理后端挂了）
- `503 Service Unavailable`：服务暂不可用（过载或维护中）
- `504 Gateway Timeout`：网关等待上游超时

## 无状态的代价与收益

为什么 HTTP 选择了无状态？想象一下，如果服务器需要记住每个客户端的状态——登录了没、购物车有什么、上次访问了什么页面——那服务器就需要为每个活跃用户维护一个会话对象。1991 年，内存极其昂贵，Web 的用户群还很有限，这个选择是务实的。但到了今天的电商网站，我们显然需要"有状态"的用户体验。

**Cookie 就是 HTTP 无状态之上的"补丁"**。它的工作原理很简单：服务器在响应中塞一个 `Set-Cookie` 头部，浏览器把它存下来，之后每次请求都自动带上：

```http
HTTP/1.1 200 OK
Set-Cookie: session_id=abc123xyz; Path=/; HttpOnly
```

浏览器后续请求：

```http
GET /dashboard HTTP/1.1
Host: www.example.com
Cookie: session_id=abc123xyz
```

服务器拿到 `session_id`，去自己的数据库或内存缓存里查找对应的用户信息——这就是所谓的 **Session**。服务器依然是无状态的（HTTP 本身不变），但它利用 Cookie 作为"身份证明"，自己在后端维护了状态。

## 持久连接（Connection: keep-alive）

HTTP/1.0 的设计有一个严重问题：每个请求都要建立一个新的 TCP 连接。这意味着一个包含 10 张图片和 5 个 CSS 文件的网页，浏览器需要建立 16 次 TCP 连接（1 个 HTML + 10 个图片 + 5 个 CSS）。每次连接都要经历三次握手，在高延迟的网络下，光握手的时间就能让你感受到明显的卡顿。

HTTP/1.1 引入了 **持久连接（Persistent Connection）**作为默认行为：一个 TCP 连接上可以发送多个 HTTP 请求和响应。客户端通过 `Connection: keep-alive` 头部明确表示要维持连接（实际上在 HTTP/1.1 中这是默认的，只有想关闭连接时才需要发 `Connection: close`）。

但持久连接有个限制：请求必须**按顺序**发送和接收，这就是 **管线化（Pipelining）**的问题——如果第一个请求很慢，后面的请求都被堵住了，这就是**队头阻塞（Head-of-Line Blocking）**。这个问题直到 HTTP/2 才被真正解决。

## 编程实践：用 Python 手写一个最简 HTTP 服务器

我们来写一个能真正解析 HTTP 请求并返回响应的服务器。不用任何框架，从零开始：

```python
import socket

def parse_request(data: str) -> dict:
    """解析 HTTP 请求报文"""
    lines = data.split('\r\n')
    
    # 解析请求行
    request_line = lines[0]
    parts = request_line.split(' ')
    method, path, version = parts[0], parts[1], parts[2]
    
    # 解析头部
    headers = {}
    i = 1
    while i < len(lines) and lines[i]:
        if ':' in lines[i]:
            key, value = lines[i].split(':', 1)
            headers[key.strip().lower()] = value.strip()
        i += 1
    
    # 消息体（头部之后的内容）
    body = '\r\n'.join(lines[i+1:]) if i + 1 < len(lines) else ''
    
    return {
        'method': method,
        'path': path,
        'version': version,
        'headers': headers,
        'body': body
    }

def build_response(status_code: int, status_text: str, headers: dict, body: str = '') -> bytes:
    """构建 HTTP 响应报文"""
    response_line = f"HTTP/1.1 {status_code} {status_text}\r\n"
    header_lines = ''.join(f"{k}: {v}\r\n" for k, v in headers.items())
    response = response_line + header_lines + '\r\n' + body
    return response.encode('utf-8')

def handle_client(conn: socket.socket, addr):
    """处理一个客户端连接"""
    try:
        data = conn.recv(4096).decode('utf-8', errors='replace')
        request = parse_request(data)
        
        print(f"[{addr}] {request['method']} {request['path']}")
        print(f"  Headers: {request['headers']}")
        
        # 简单的路由
        if request['path'] == '/':
            body = '<html><body><h1>Hello from Python HTTP Server!</h1></body></html>'
            response = build_response(200, 'OK', {
                'Content-Type': 'text/html; charset=UTF-8',
                'Content-Length': str(len(body.encode('utf-8'))),
                'Connection': 'close'
            }, body)
        elif request['path'] == '/api/status':
            import json
            data = json.dumps({'status': 'running', 'method': request['method']})
            response = build_response(200, 'OK', {
                'Content-Type': 'application/json',
                'Content-Length': str(len(data)),
                'Connection': 'close'
            }, data)
        else:
            body = 'Not Found'
            response = build_response(404, 'Not Found', {
                'Content-Type': 'text/plain',
                'Content-Length': str(len(body)),
                'Connection': 'close'
            }, body)
        
        conn.sendall(response)
    finally:
        conn.close()

def main():
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind(('127.0.0.1', 8080))
    server.listen(5)
    print("HTTP Server listening on http://127.0.0.1:8080")
    
    try:
        while True:
            conn, addr = server.accept()
            handle_client(conn, addr)
    except KeyboardInterrupt:
        print("\nServer shutting down...")
    finally:
        server.close()

if __name__ == '__main__':
    main()
```

运行这个服务器后，用浏览器访问 `http://127.0.0.1:8080/` 就能看到页面，访问 `http://127.0.0.1:8080/api/status` 会返回 JSON。访问其他路径会得到 404。这个服务器是同步阻塞的——一次只能处理一个请求——但它的核心价值是让你看到 HTTP 报文的真实结构。

## 抓包实践：捕获完整的 HTTP 请求/响应

在 Wireshark 中过滤 `http` 协议，访问一个简单页面，你会看到类似这样的报文流：

**请求报文（逐行分析）**：

```
GET /index.html HTTP/1.1              ← 请求行：方法、路径、版本
Host: www.example.com                  ← HTTP/1.1 强制要求的头部
User-Agent: Mozilla/5.0 ...            ← 客户端标识
Accept: text/html,...                  ← 可接受的内容类型
Accept-Encoding: gzip, deflate, br     ← 支持的压缩算法
Accept-Language: zh-CN,zh;q=0.9        ← 语言偏好，q 是权重
Connection: keep-alive                 ← 请求保持连接
```

**响应报文（逐行分析）**：

```
HTTP/1.1 200 OK                        ← 状态行：版本、状态码、原因
Date: Mon, 15 Jan 2024 08:30:00 GMT   ← 服务器时间
Server: nginx/1.24.0                   ← 服务器软件
Content-Type: text/html; charset=UTF-8 ← 内容类型
Content-Length: 1256                   ← 消息体长度
Last-Modified: Fri, 12 Jan 2024 ...    ← 资源最后修改时间（协商缓存用）
ETag: "5f3c2d-4e8"                     ← 资源指纹（协商缓存用）
Cache-Control: max-age=3600            ← 缓存指令
Connection: keep-alive                 ← 保持连接
```

在 Wireshark 中展开 `Hypertext Transfer Protocol` 树，每个字段都可以点击查看详情。特别注意 `Content-Length` 和实际消息体长度是否一致——如果不一致，客户端就不知道消息体在哪里结束。
