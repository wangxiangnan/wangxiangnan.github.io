## 7.1 error 接口：Go 的错误哲学

### error 接口长什么样？

Go 语言对"错误"的定义极其简洁——只有一个方法：

```go
// error 是 Go 内置的接口，定义在 builtin 包中
type error interface {
    Error() string // 只要求实现一个方法：返回错误的文本描述
}
```

没错，任何类型只要实现了 `Error() string` 方法，它就是一个 error。这体现了 Go 的核心设计哲学：**错误是值（errors are values）**。错误不是需要特殊语法来处理的例外情况，它就是一个普通的值，可以赋值、传递、判断、包装。

打个比方：在 Go 的世界里，错误就像快递包裹里的一张便条——它安静地躺在返回值里，等着你打开包裹时看一眼。如果有便条（错误不为 nil），你就处理它；如果没有（nil），一切正常。

### 创建错误的两种方式

```go
package main

import (
    "errors"
    "fmt"
)

func main() {
    // 方式一：errors.New —— 创建一个简单的文本错误
    err1 := errors.New("文件不存在")
    fmt.Println(err1) // 输出：文件不存在

    // 方式二：fmt.Errorf —— 创建带格式化信息的错误
    filename := "config.yaml"
    err2 := fmt.Errorf("无法打开文件 %s", filename)
    fmt.Println(err2) // 输出：无法打开文件 config.yaml
}
```

`errors.New` 适合错误信息固定的场景；`fmt.Errorf` 适合需要把运行时变量嵌入错误信息的场景。

### 自定义错误类型

当简单的文本错误不够用时，你可以定义自己的错误类型。自定义错误类型的好处是：调用者可以根据类型做不同的处理，而不仅仅靠字符串匹配。

```go
package main

import "fmt"

// PathError 是一个自定义的错误类型
// 它携带了更多上下文信息：操作名称和文件路径
type PathError struct {
    Op   string // 操作名称，如 "open"、"read"
    Path string // 文件路径
    Err  error  // 底层错误（可以嵌套）
}

// 实现 error 接口——只需要实现 Error() string 方法
func (e *PathError) Error() string {
    return fmt.Sprintf("%s %s: %v", e.Op, e.Path, e.Err)
}

// Unwrap 方法让错误可以被 errors.Is / errors.As 穿透（详见下文）
func (e *PathError) Unwrap() error {
    return e.Err
}

func openFile(path string) error {
    // 模拟一个文件打开失败的错误
    return &PathError{
        Op:   "open",
        Path: path,
        Err:  errors.New("permission denied"),
    }
}

func main() {
    err := openFile("/etc/shadow")
    if err != nil {
        fmt.Println(err) // 输出：open /etc/shadow: permission denied
    }
}
```

### 错误包装与 errors.Is / errors.As（Go 1.13+）

在真实项目中，错误往往像洋葱一样一层层嵌套。底层函数产生一个原始错误，上层函数逐层添加上下文信息。Go 1.13 引入了 `%w` 格式化动词和 `errors.Is` / `errors.As` 两个工具函数，让错误包装变得优雅：

```go
package main

import (
    "errors"
    "fmt"
)

// 定义一个哨兵错误（sentinel error），后面会详细讲
var ErrNotFound = errors.New("not found")

func queryDB(id int) error {
    // 模拟数据库查询失败，返回原始错误
    return ErrNotFound
}

func getUser(id int) error {
    // 用 %w 包装错误，保留原始错误链的同时添加上下文
    err := queryDB(id)
    if err != nil {
        return fmt.Errorf("getUser(id=%d): %w", id, err)
    }
    return nil
}

func main() {
    err := getUser(42)

    // errors.Is 可以沿着错误链向上追溯，判断是否包含某个特定错误
    if errors.Is(err, ErrNotFound) {
        fmt.Println("用户不存在") // 会被执行
    }

    // errors.As 可以沿链查找特定类型的错误
    // 用法类似类型断言，但能穿透包装层
    var customErr *PathError // 假设 PathError 已定义
    if errors.As(err, &customErr) {
        fmt.Printf("路径错误：%s %s\n", customErr.Op, customErr.Path)
    }
}
```

关键点：`%w` 是"包装"，`%v` 是"格式化"。用 `%w` 包装的错误可以被 `errors.Is` / `errors.As` 穿透；用 `%v` 则不行，错误链在那里断开了。

### 深入理解：为什么 Go 选择"错误是值"而不是异常机制？

Java、Python 等语言使用 `try/catch` 异常机制，错误会沿着调用栈"抛出"，直到被捕获。这有两个问题：

1. **控制流不可见**：你不知道哪个函数会抛出异常、在哪里被捕获，调用栈变成了一个隐式的"弹射通道"。
2. **容易被忽视**：不捕获异常？程序照样编译通过，只是运行时可能崩溃。

Go 的设计哲学是**显式优于隐式**。函数签名中明确声明了可能返回 error，调用者必须在代码中处理它——哪怕只是写一个 `_` 明确忽略。这让错误处理变成了代码审查中可见的、可追踪的行为。

> 类比：异常机制像大楼的火警系统——一旦触发，整栋楼都在响，你不知道火在哪里。Go 的错误返回值像每个房间门口的温度计——你走到哪里都能看到当前的状态，一切尽在掌握。

## 7.2 错误处理最佳实践

### 三种常见的错误处理模式

**模式一：直接返回**——底层函数，不需要添加额外信息。

```go
func readConfig() ([]byte, error) {
    data, err := os.ReadFile("config.yaml")
    if err != nil {
        return nil, err // 直接返回，让上层决定怎么处理
    }
    return data, nil
}
```

**模式二：包装后返回**——中间层函数，需要添加上下文。

```go
func loadConfig() (*Config, error) {
    data, err := readConfig()
    if err != nil {
        // 用 %w 包装，保留错误链，同时告知调用者"在哪一步出的错"
        return nil, fmt.Errorf("loadConfig: %w", err)
    }
    var cfg Config
    if err := json.Unmarshal(data, &cfg); err != nil {
        return nil, fmt.Errorf("loadConfig: 解析配置失败: %w", err)
    }
    return &cfg, nil
}
```

**模式三：重试**——面对暂时性故障（网络抖动、锁竞争），可以尝试多次。

```go
func fetchWithRetry(url string, maxRetries int) ([]byte, error) {
    var err error
    for i := 0; i < maxRetries; i++ {
        resp, e := http.Get(url)
        if e == nil {
            defer resp.Body.Close()
            return io.ReadAll(resp.Body)
        }
        err = e // 记录最后一次错误
        time.Sleep(time.Duration(i+1) * time.Second) // 退避策略
    }
    return nil, fmt.Errorf("重试 %d 次后仍失败: %w", maxRetries, err)
}
```

### 哨兵错误 vs 错误类型

- **哨兵错误（Sentinel Errors）**：用包级别的 `var` 定义固定的错误值，如 `io.EOF`、`sql.ErrNoRows`。适合简单的、可枚举的错误。
- **错误类型（Error Types）**：定义实现了 `error` 接口的 struct，如 `net.Error`。适合需要携带丰富上下文的场景。

选择原则：**能用哨兵错误就不用错误类型，能用错误类型就不用字符串匹配。**

### 什么时候可以忽略错误？

用 `_` 忽略错误是合法的，但要确保你清楚自己在做什么：

```go
// 常见场景：fmt.Fprint 系列函数返回的写入字节数
// 写入 stdout 几乎不会失败，忽略是安全的
fmt.Fprintln(os.Stdout, "hello")

// 但写入文件或网络时，绝对不能忽略！
_, _ = conn.Write(data) // 危险！网络写入可能失败
```

### 设计原则："处理或传播，但永远不吞没"

这是 Go 错误处理的黄金法则。每一个 error 返回值，你只有三个选择：

1. **处理它**：在当前函数中解决问题（重试、降级、给用户友好提示）。
2. **传播它**：返回给调用者，让上层处理（可以包装后返回）。
3. **显式忽略**：用 `_` 明确表示"我考虑过了，这里不需要处理"。

最忌讳的做法是 `if err != nil {}` 写个空块——既没处理也没传播，这就是"吞没"错误，是 bug 的温床。

## 7.3 Panic 与 Recover：Go 的"最后手段"

### 什么时候会 panic？

Panic 分两种来源：

- **运行时 panic**：数组越界、nil 指针解引用、类型断言失败等。Go 运行时会自动触发。
- **显式 panic**：开发者主动调用 `panic()`。

Panic 一旦发生，正常的控制流被中断，函数开始"恐慌退出"——先执行所有 defer，然后逐层向调用栈上方传播，最终程序崩溃。

### Recover：在 defer 中"接住" panic

`recover()` 是唯一能阻止 panic 扩散的手段，但它**必须在 defer 函数中调用**才有效：

```go
package main

import "fmt"

// safeDivide 演示如何用 recover 从 panic 中恢复
func safeDivide(a, b int) (result int, err error) {
    // defer + recover 组合：在函数退出前检查是否发生了 panic
    defer func() {
        if r := recover(); r != nil {
            // r 是 panic 传入的值，类型是 interface{}
            err = fmt.Errorf("发生 panic: %v", r)
        }
    }()

    // 这里如果 b == 0，Go 运行时会 panic("runtime error: integer divide by zero")
    result = a / b
    return result, nil
}

func main() {
    val, err := safeDivide(10, 0)
    if err != nil {
        fmt.Println("捕获到错误:", err)
        // 输出：捕获到错误: 发生 panic: runtime error: integer divide by zero
    } else {
        fmt.Println("结果:", val)
    }
}
```

### Panic/Recover 的正确使用场景

Panic 不是用来替代 error 的，它只适用于**不可恢复的程序错误**：

- 程序初始化阶段，某个必需的配置缺失（"不应该发生的事发生了"）。
- 标准库中的一些内部实现（如 `encoding/json` 在递归过深时会 panic）。
- 框架层面统一兜底（如 Web 框架用 recover 防止一个请求的 panic 拖垮整个服务）。

### 为什么不应该用 panic 替代 error？

1. **调用者无法从函数签名看出可能 panic**——error 在返回值中明确声明，panic 是隐藏的控制流。
2. **panic 不可组合**——一旦 panic，所有正常的返回值逻辑都被跳过。
3. **测试困难**——panic 会中断测试流程，而 error 可以被断言和检查。

> 类比：error 是汽车的刹车灯——提前告诉你"前面有情况"；panic 是安全气囊——只在最极端的情况下弹出来，而且弹一次代价很大。

## 7.4 Go Modules：现代化的依赖管理

### 什么是 Go Module？

Go Module 是 Go 1.11 引入、1.16 起成为默认的依赖管理方案。它让你不再需要把所有代码放在 `GOPATH` 下，可以在任意目录创建项目，并且精确管理依赖版本。

### 初始化一个模块

```bash
# 在项目根目录执行，模块名通常使用仓库路径
go mod init github.com/yourname/myproject
```

执行后会生成 `go.mod` 文件，它记录了模块名、Go 版本和依赖列表。

### go mod tidy：自动整理依赖

```bash
# 扫描代码中的 import，自动添加缺失的依赖、移除未使用的依赖
go mod tidy
```

这个命令应该成为你的日常习惯——每次修改 import 后都跑一次。

### go.sum 文件

`go.sum` 记录了每个依赖的哈希校验值，确保你的依赖没有被篡改。**它必须提交到版本控制中**，否则团队成员可能拉到不同版本的代码。

### 语义化版本（Semantic Versioning）

Go Modules 遵循 `vMAJOR.MINOR.PATCH` 规范：
- **MAJOR**：不兼容的 API 变更（v1 -> v2）
- **MINOR**：向下兼容的新功能
- **PATCH**：向下兼容的 bug 修复

### 中国开发者必知：GOPROXY

由于网络原因，直接从 GitHub 拉取 Go 依赖可能很慢。设置国内代理是必须的：

```bash
# 推荐使用七牛云的 Go 代理
go env -w GOPROXY=https://goproxy.cn,direct

# 如果某些私有仓库不走代理
go env -w GONOPROXY=github.com/yourcompany/*
```

### 深入理解：从 GOPATH 到 Go Modules 的演进

Go 早期版本使用 `GOPATH` 模式——所有项目必须放在 `$GOPATH/src` 下，一个包只能有一个版本。这导致了臭名昭著的"钻石依赖"问题。Go Modules 通过引入 `go.mod` 文件实现了"最小版本选择"（Minimum Version Selection），在保持简单的同时解决了版本冲突。这个演进过程体现了 Go 社区"在实战中发现问题，用务实的方案解决问题"的工程哲学。

## 7.5 测试：Go 内置的测试框架

Go 不需要 JUnit、pytest 这样的第三方框架——标准库的 `testing` 包就足够了。

### 基础测试

测试文件以 `_test.go` 结尾，测试函数以 `Test` 开头：

```go
// math_test.go
package math_test

import (
    "math"
    "testing"
)

// 测试函数签名固定：func TestXxx(t *testing.T)
func TestSqrt(t *testing.T) {
    // 准备输入和期望输出
    got := math.Sqrt(4.0)
    want := 2.0

    // 用 t.Errorf 报告失败（不会中断测试）
    if got != want {
        t.Errorf("Sqrt(4.0) = %f, 期望 %f", got, want)
    }
}
```

运行测试：

```bash
go test ./...           # 运行所有测试
go test -v ./...        # 详细输出
go test -run TestSqrt   # 只运行特定测试
```

### 表驱动测试：Go 社区的黄金模式

当同一个函数有多组测试用例时，表驱动测试能让代码极其简洁：

```go
func TestAbs(t *testing.T) {
    // 用结构体切片定义测试表
    tests := []struct {
        name string  // 测试用例名称，便于定位失败项
        input    float64
        expected float64
    }{
        {"正数", 3.0, 3.0},
        {"负数", -5.0, 5.0},
        {"零", 0.0, 0.0},
        {"极小值", -0.001, 0.001},
    }

    for _, tt := range tests {
        // 用 t.Run 创建子测试，每个子测试独立运行、独立报告
        t.Run(tt.name, func(t *testing.T) {
            got := math.Abs(tt.input)
            if got != tt.expected {
                t.Errorf("Abs(%f) = %f, 期望 %f", tt.input, got, tt.expected)
            }
        })
    }
}
```

表驱动测试的好处：添加新用例只需在表中加一行，不需要写新的函数。

### 基准测试（Benchmark）

```go
// 基准测试函数以 Benchmark 开头，参数是 *testing.B
func BenchmarkFibonacci(b *testing.B) {
    // b.N 由测试框架自动设定，会逐步增大直到结果稳定
    for i := 0; i < b.N; i++ {
        fibonacci(20)
    }
}
```

运行：`go test -bench=BenchmarkFibonacci -benchmem`（`-benchmem` 显示内存分配）。

### 示例测试（Example）

```go
// Example 函数既是测试也是文档，会出现在 godoc 中
func ExampleSqrt() {
    fmt.Println(math.Sqrt(9))
    // Output: 3
}
```

`// Output:` 注释后面的内容是期望输出，不匹配则测试失败。

### 深入理解：Go 的测试哲学

Go 社区有一句名言：**"不追求覆盖率数字，追求测试的有效性。"** 100% 的覆盖率并不意味着代码没有 bug。真正有价值的测试应该覆盖**边界条件、错误路径和业务逻辑的关键决策点**。与其为了让覆盖率从 80% 升到 90% 去测试 getter/setter，不如花时间写清楚那几个复杂函数的边界用例。

## 7.6 标准库精选

Go 的标准库是"自带电池"哲学的体现——安装 Go 就拥有了大量高质量的工具包。以下是日常开发中最常用的几个：

| 包 | 用途 | 关键类型/函数 |
|---|---|---|
| `fmt` | 格式化输入输出 | `Printf`、`Sprintf`、`Errorf`、`Scan` |
| `os` | 操作系统交互 | `Open`、`ReadFile`、`Getenv`、`Exit` |
| `io` | 流式 IO 抽象 | `Reader`、`Writer`、`Copy`、`ReadAll` |
| `strings` | 字符串操作 | `Contains`、`Split`、`Join`、`Replace` |
| `strconv` | 字符串与基本类型互转 | `Atoi`、`Itoa`、`ParseFloat` |
| `bytes` | 字节切片操作 | `Buffer`、`Contains`、`Equal` |
| `encoding/json` | JSON 编解码 | `Marshal`、`Unmarshal`、`NewEncoder` |
| `net/http` | HTTP 客户端与服务端 | `Get`、`Post`、`ListenAndServe`、`Handler` |
| `log` | 日志记录 | `Println`、`Fatalf`、`SetFlags` |
| `context` | 上下文控制 | `WithTimeout`、`WithCancel`、`WithValue` |

`context` 包尤其重要——它是 Go 并发编程的"安全阀"。通过 context，你可以给一个操作设置超时时间、随时取消正在进行的任务、在调用链中传递请求级别的数据（如请求 ID、用户身份）。在涉及网络请求、数据库查询的并发场景中，context 几乎是必备的。

## 7.7 Go 工具链

Go 不仅是语言，更是一整套开发工具链。

### 代码质量三件套

```bash
go fmt ./...   # 自动格式化代码（统一缩进、空格、import 顺序）
go vet ./...   # 静态分析，检查常见错误（如 Printf 参数不匹配）
```

`go fmt` 消除了"缩进风格之争"——整个 Go 社区只有一种代码风格，由工具统一执行。

### 编译时注入版本信息

```bash
# 通过 -ldflags 在编译时将版本号注入到代码中
go build -ldflags "-X main.Version=1.2.3 -X main.BuildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" -o myapp
```

对应的 Go 代码：

```go
var (
    Version   string // 编译时由 -ldflags 注入
    BuildTime string
)

func main() {
    fmt.Printf("版本: %s, 构建时间: %s\n", Version, BuildTime)
}
```

### 交叉编译

Go 可以极其方便地为不同平台编译——只需设置两个环境变量：

```bash
# 编译 Linux 可执行文件（在 Windows 上执行）
GOOS=linux GOARCH=amd64 go build -o myapp-linux

# 编译 macOS ARM64（Apple Silicon）
GOOS=darwin GOARCH=arm64 go build -o myapp-mac

# 编译 Windows
GOOS=windows GOARCH=amd64 go build -o myapp.exe
```

Go 的编译器自带所有目标平台的代码生成器，不需要安装任何交叉编译工具链——这也是 Go 在 DevOps 和容器化时代大放异彩的原因之一。

### go generate：代码生成

`go generate` 扫描源码中的 `//go:generate` 注释，执行指定的代码生成工具。常用于自动生成 mock、序列化代码、协议定义等：

```go
//go:generate stringer -type=Color
type Color int

const (
    Red   Color = iota
    Green
    Blue
)
```

运行 `go generate ./...` 后，工具会自动生成 `Color` 类型的 `String()` 方法。

## 7.8 本章小结

本章我们走过了 Go 工程实践的几个关键领域：

1. **错误处理**：Go 用"错误是值"的哲学取代了异常机制，让错误处理变得显式、可追踪。核心原则是"处理或传播，但永远不吞没"。
2. **Panic/Recover**：这是"最后手段"，仅在不可恢复的极端情况下使用，绝不应替代正常的 error 返回值。
3. **Go Modules**：现代化的依赖管理方案，告别了 GOPATH 时代的版本混乱。`go mod tidy` 应该是你日常开发的一部分。
4. **测试**：`testing` 标准库 + 表驱动测试模式足以应对绝大多数场景。追求测试的有效性，而非覆盖率数字。
5. **标准库与工具链**：Go 自带丰富的标准库和完善的工具链，从格式化到交叉编译一应俱全。

**从"写代码"到"写工程"的思维转变**：写代码关注的是"功能如何实现"；写工程关注的是"功能如何可靠地运行、如何被测试、如何被部署、如何被他人维护"。Go 语言的设计哲学——简洁的语法、显式的错误处理、内置的测试支持、统一的工具链——无一不是在帮助开发者建立工程化的思维。

下一章，我们将进入实战项目，把这些工程实践真正用起来。
