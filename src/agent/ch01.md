## 1.1 开篇引入：一个真实场景的降维打击

假设你正在搭建一个"技术支持问答系统"。用户问：

> "我的 Docker 容器启动后，端口映射不生效，报 `bind: address already in use` 错误，怎么排查？"

### 1.1.1 传统 if-else 客服机器人

```python
# traditional_bot.py
def handle_question(question: str) -> str:
    """传统客服机器人：关键词匹配 + 规则分支"""
    q = question.lower()
    if "docker" in q:
        if "端口" in q or "port" in q:
            if "映射" in q:
                return "请参考 Docker 端口映射文档：https://docs.docker.com/"
            elif "暴露" in q:
                return "请使用 -p 参数：docker run -p 8080:80 nginx"
        elif "容器" in q:
            if "启动" in q:
                return "容器启动失败：1.镜像不存在 2.入口命令错误 3.资源不足"
        else:
            return "Docker 文档：https://docs.docker.com/"
    elif "kubernetes" in q:
        if "pod" in q:
            return "kubectl describe pod <name>"
        else:
            return "K8s 文档：https://kubernetes.io/docs/"
    # ... 省略 5000 行 if-else ...
    else:
        return "抱歉，我不理解您的问题。"

# 测试
answer = handle_question("Docker 端口映射不生效，报 bind: address already in use")
print(answer)
# 输出：请参考 Docker 端口映射文档
# —— 完全忽略了 "address already in use" 这个关键错误信息！
```

问题：1)关键词匹配粗糙 2)无法理解错误信息 3)无法执行排查 4)维护噩梦

> 你是不是想起了公司里某个 5000 行的规则引擎？那种"改一个规则就搞坏三个"的酸爽。

### 1.1.2 AI Agent 的处理方式

```python
# agent_demo.py
"""
Agent 处理思路：
1. 理解：端口映射失败，错误是 address already in use
2. 推理：宿主机端口被占用
3. 计划：检查端口占用 → 找到进程 → 给方案
4. 行动：调用 lsof/netstat 工具
5. 回答："端口 8080 被 nginx(PID 12345) 占用。
         方案：a) sudo kill 12345  b) docker run -p 9090:80"
"""

from langchain_openai import ChatOpenAI
from langchain.agents import tool, AgentExecutor, create_react_agent
from langchain import hub

@tool
def check_port_usage(port: int) -> str:
    """检查端口占用"""
    import subprocess
    result = subprocess.run(["lsof", "-i", f":{port}"],
                           capture_output=True, text=True, timeout=10)
    return result.stdout if result.stdout else f"端口 {port} 未占用"

@tool
def check_process_info(pid: int) -> str:
    """获取进程信息"""
    import subprocess
    result = subprocess.run(["ps", "-p", str(pid), "-o", "pid,cmd"],
                           capture_output=True, text=True, timeout=10)
    return result.stdout

llm = ChatOpenAI(model="gpt-4", temperature=0)
agent = create_react_agent(llm, [check_port_usage, check_process_info],
                          hub.pull("hwchase17/react"))
executor = AgentExecutor(agent=agent,
                        tools=[check_port_usage, check_process_info], verbose=True)
response = executor.invoke({
    "input": "Docker 端口映射失败，bind: address already in use"
})
print(response["output"])
```

**对比**：

| 维度 | if-else 机器人 | AI Agent |
| ------ | --------------- | ---------- |
| 理解 | 关键词匹配 | 语义理解 |
| 推理 | 无 | 根据错误推理根因 |
| 行动 | 返回文本 | 执行命令、调工具 |
| 适应 | 新场景加规则 | 同架构处理各种问题 |
| 维护 | 规则越多越难 | 核心稳定，扩展靠工具 |

> 传统机器人是写死的 `switch-case`，Agent 是**运行时动态生成逻辑**的智能调度器。

### 1.1.3 一个更直观的例子：邮件处理

让我们看另一个场景 — 处理用户发来的技术支持邮件：

```python
# 传统方式：需要为每种邮件类型写一个处理器
class TraditionalEmailHandler:
    def process(self, email: dict) -> dict:
        subject = email.get("subject", "").lower()
        body = email.get("body", "").lower()
        
        # Bug 报告
        if "bug" in subject or "error" in subject or "crash" in subject:
            priority = self._extract_priority(body)
            component = self._classify_component(body)
            return {
                "type": "bug_report",
                "action": "create_jira_ticket",
                "priority": priority,
                "component": component,
                "template": "bug_response_v3.txt",
            }
        
        # 功能请求
        elif "feature" in subject or "request" in subject or "wish" in subject:
            return {
                "type": "feature_request",
                "action": "add_to_backlog",
                "template": "feature_ack_v2.txt",
            }
        
        # 账单问题
        elif "billing" in subject or "invoice" in subject or "charge" in subject:
            return {
                "type": "billing_issue",
                "action": "forward_to_finance",
                "template": "billing_response_v1.txt",
            }
        
        # ... 你懂的，这里还会有几十个 elif ...
        # 而且每种类型里面的子分类又是另一棵 if-else 树
        
        else:
            return {
                "type": "unknown",
                "action": "forward_to_human",
                "template": "generic_response.txt",
            }

# 问题：
# 1. 如果一封邮件同时包含 "bug" 和 "feature request" 呢？
# 2. 如果用户用 "我觉得这里可以改进" 而不是 "feature request" 呢？
# 3. 如果用户写了一封很长很复杂的邮件，涉及多个问题呢？
# 4. 每次新加一种邮件类型，就要改这个函数（违反开闭原则）

# Agent 方式：一个统一的 Agent 处理所有类型
class AgentEmailHandler:
    def process(self, email: dict) -> dict:
        # Agent 使用 LLM 理解邮件内容，然后决定行动
        # 不需要预定义所有类型 — LLM 能理解任何自然语言
        response = self.agent.invoke({
            "input": f"处理以下邮件:\n主题: {email['subject']}\n内容: {email['body']}",
            "tools": [
                create_jira_ticket,      # 创建工单
                add_to_backlog,          # 添加到产品待办
                forward_to_finance,      # 转发给财务
                search_knowledge_base,   # 搜索知识库
                send_email_reply,        # 发送回复
            ]
        })
        return response
        # Agent 能处理传统方式覆盖不到的情况：
        # - 一封邮件多个问题 → Agent 会分步处理
        # - 非标准措辞 → LLM 理解语义
        # - 需要跨系统操作 → Agent 协调多个工具
```

这个邮件处理的例子更清楚地展示了 Agent 的优势：**一套架构，处理所有情况**。传统方式每增加一种情况就要加一堆代码，Agent 只需要增加一个工具。

## 1.2 Agent 的精确定义：PRAM 模型

**AI Agent = LLM 推理引擎 + 感知 + 推理 + 行动 + 记忆**

```
┌────────────────────────────────────────┐
│              AI Agent                  │
│  Perception → Reasoning → Action      │
│        └─────────┬──────────┘          │
│            ┌──────────┐                │
│            │  Memory  │                │
│            └──────────┘                │
└────────────────────────────────────────┘
```

- **P（感知）**：像 Request Handler，接收各种输入
- **R（推理）**：像 Business Logic，用 LLM 分析规划
- **A（行动）**：像调下游 API，通过工具与外部交互
- **M（记忆）**：短期=Redis（对话），长期=DB（知识）

> ⚠️ 没有工具使用和自主规划的程序，不管调了什么 LLM API，都不是 Agent，只是 Wrapper。

## 1.4 Agent ≈ 动态路由的微服务

| 微服务 | Agent | 说明 |
| -------- | ------- | ------ |
| Gateway | Perception | 入口预处理 |
| Router | LLM Reasoning | 动态决策 |
| Service | Tool | 能力单元 |
| Redis | Short-term Memory | 临时数据 |
| Database | Long-term Memory | 持久存储 |
| Saga | Planning | 多步编排 |

最大区别：**路由逻辑是 LLM 实时推理的，不是写死的**。

## 1.5 Agent vs 普通 LLM 调用

| 能力 | 普通 LLM | Agent |
| ------ | --------- | ------- |
| 回答 | 训练数据 | 实时信息 |
| 查数据 | 不能 | 通过工具 |
| 多步推理 | 单轮 | 可分多步 |
| 执行代码 | 不能 | 工具 |
| 记忆 | 每次独立 | 记忆系统 |
| 纠错 | 错了就错 | 检查重试 |

## 1.6 Agent vs RAG vs Fine-tuning

- **Fine-tuning**：送培训班（模型学特定风格）— 成本高，更新难
- **RAG**：给资料库（检索回答）— 知识可更新，可追溯
- **Agent**：给工具和权限（自主决策）— 灵活，但延迟高

```
选择：
├── 特定风格？ → Fine-tuning
├── 知识库问答？ → RAG
├── 多步+工具？ → Agent
└── 都要？ → Agent + RAG（最常见组合）
```
