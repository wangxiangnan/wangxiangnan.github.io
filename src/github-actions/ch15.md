# 第15章：部署到云平台

## 15.1 引言：部署的"最后一公里"

测试通过了，镜像构建好了，万事俱备，只差把代码送到它该去的地方。部署就像快递的"最后一公里"——前面的分拣、打包都做好了，最后得送到收件人手里。不同的云平台就像不同的"收件地址"，需要不同的"投递方式"。

本章我们将从最简单的静态站点部署开始，逐步深入到容器部署、SSH 部署、云厂商 OIDC 认证，最后聊聊蓝绿部署和金丝雀发布的思路。

## 15.2 GitHub Pages 静态站点部署

GitHub Pages 是最简单的部署方式，适合文档站点、博客、前端静态应用。你甚至不需要服务器——GitHub 帮你托管。

```yaml
name: Deploy to GitHub Pages

on:
  push:
    branches: [main]
  # 允许手动触发
  workflow_dispatch:

# 设置 GITHUB_TOKEN 的权限，允许部署到 Pages
permissions:
  contents: read
  pages: write
  id-token: write

# 同一时间只允许一个部署，避免冲突
concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 以 Next.js 项目为例
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install and Build
        run: |
          npm ci
          npm run build
        # Next.js 的 export 会生成静态文件到 out/ 目录

      # 上传构建产物
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: out

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

别忘了在仓库的 Settings → Pages 中将 Source 设置为 "GitHub Actions"。

## 15.3 Vercel / Netlify 前端部署

Vercel 和 Netlify 是前端部署的"两大天王"，它们提供了极其丝滑的部署体验。最简单的方式是安装它们的 GitHub App，自动在每次 PR 时创建预览部署（Preview Deployment），合并到 main 后自动部署到生产。

如果你想用 Actions 手动控制，以 Vercel 为例：

```yaml
name: Deploy to Vercel

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install Vercel CLI
        run: npm install -g vercel

      # 拉取 Vercel 项目的环境配置
      - name: Pull Vercel environment
        run: vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN }}

      # 构建项目
      - name: Build project
        run: vercel build --prod --token=${{ secrets.VERCEL_TOKEN }}

      # 部署（--prod 表示生产环境）
      - name: Deploy to Vercel
        id: deploy
        run: |
          url=$(vercel deploy --prebuilt --prod --token=${{ secrets.VERCEL_TOKEN }})
          echo "url=$url" >> $GITHUB_OUTPUT

      # 在 PR 评论中显示部署 URL
      - name: Comment PR with deploy URL
        if: github.event_name == 'pull_request'
        uses: marocchino/sticky-pull-request-comment@v2
        with:
          message: "🚀 Deployed to: ${{ steps.deploy.outputs.url }}"
```

## 15.4 Docker 镜像部署到各大平台

如果你的应用是 Docker 化的，理论上可以部署到任何支持容器的平台。常见的容器镜像仓库包括：

- **GitHub Container Registry (GHCR)**：和 GitHub 深度集成，使用 `GITHUB_TOKEN` 即可认证。
- **Docker Hub**：最经典的镜像仓库，需要 `DOCKER_USERNAME` 和 `DOCKER_PASSWORD`。
- **AWS ECR / GCP Artifact Registry / Azure ACR**：各大云厂商的托管容器仓库。

推送镜像的核心步骤几乎一样：登录仓库 → 构建镜像 → 打标签 → 推送。第13章和第14章的 Docker 构建步骤已经展示了推送 GHCR 的完整流程。

## 15.5 SSH 部署到自有服务器

当你有一台自己的 Linux 服务器时，SSH 部署是最直接的方式。`appleboy/ssh-action` 是这个领域最流行的 Action：

```yaml
name: Deploy via SSH

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Deploy to server via SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          # 使用 SSH 密钥认证（比密码安全得多）
          key: ${{ secrets.SERVER_SSH_KEY }}
          port: 22
          # 在远程服务器上执行的脚本
          script: |
            # 进入项目目录
            cd /var/www/my-app

            # 拉取最新的 Docker 镜像
            docker pull ghcr.io/my-org/my-app:latest

            # 停止旧容器，启动新容器
            docker stop my-app || true
            docker rm my-app || true
            docker run -d \
              --name my-app \
              --restart unless-stopped \
              -p 8080:3000 \
              --env-file .env \
              ghcr.io/my-org/my-app:latest

            # 清理旧镜像，释放磁盘空间
            docker image prune -f

            echo "Deployment completed at $(date)"
```

**安全提示**：永远不要在 Workflow 文件中硬编码服务器地址或密码。使用 GitHub Secrets 存储敏感信息，使用 SSH 密钥而非密码认证。

## 15.6 AWS / GCP / Azure 部署：OIDC 认证方式

传统的云部署需要在 GitHub Secrets 中存储长期的 Access Key——这就像一个永不过期的钥匙，一旦泄露后果严重。OIDC（OpenID Connect）是更安全的替代方案：GitHub 充当"身份认证中心"，临时颁发一个短生命周期的凭证给云厂商。

以 AWS 为例：

```yaml
name: Deploy to AWS

on:
  push:
    branches: [main]

permissions:
  id-token: write   # OIDC 必需
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 使用 OIDC 获取临时 AWS 凭证（无需存储 Access Key！）
      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: us-east-1

      # 登录 ECR
      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      # 构建、标记、推送镜像到 ECR
      - name: Build and push to ECR
        env:
          ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          ECR_REPOSITORY: my-app
        run: |
          docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }} .
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }}

      # 更新 ECS 服务（使用新镜像）
      - name: Deploy to ECS
        run: |
          aws ecs update-service \
            --cluster my-cluster \
            --service my-service \
            --force-new-deployment
```

OIDC 的核心优势是"零长期凭证"——就像酒店房的电子门卡，退房后自动失效，比传统钥匙安全得多。

## 15.7 部署策略：蓝绿部署与金丝雀发布

直接替换运行中的服务叫"就地部署"（In-place deployment），就像在飞行中换引擎——风险很高。更好的策略有：

**蓝绿部署（Blue-Green Deployment）**：

想象你有两个一模一样的舞台（蓝色和绿色）。蓝色舞台正在演出（生产环境），绿色舞台在幕后布置新场景（新版本）。布置完成后，灯光一切——观众甚至感觉不到切换。如果新版本出了问题，灯光切回蓝色舞台即可。

```
[用户请求] → [负载均衡器] → [🔵 Blue: v1.0 (当前)]
                            → [🟢 Green: v2.0 (新版)]
切换后：
[用户请求] → [负载均衡器] → [🟢 Green: v2.0 (当前)] ✅
                            → [🔵 Blue: v1.0 (待命)]
```

**金丝雀发布（Canary Release）**：

这个名字来源于矿工用金丝雀检测矿井中有毒气体的做法——先让一小部分用户试用新版本，如果没有问题再逐步扩大范围。

```
初始：    [100% 用户] → [v1.0]
金丝雀：  [90% 用户] → [v1.0]
          [10% 用户] → [v2.0] ← 金丝雀
观察没问题后：
全量：    [100% 用户] → [v2.0]
```

在 GitHub Actions 中实现这些策略，通常需要结合 Kubernetes 或云厂商的部署能力（如 AWS CodeDeploy、GCP Cloud Deploy）。基本思路是：Actions 负责构建和推送镜像，然后通过 API 调用触发平台的部署策略。

## 15.8 小结

部署方式的选择取决于你的技术栈和团队规模：静态站点用 GitHub Pages 最省事；前端应用用 Vercel/Netlify 最丝滑；容器化应用用 Docker + SSH/云厂商最灵活；大型团队则需要 Kubernetes + 蓝绿/金丝雀策略来保证部署安全。无论哪种方式，OIDC 认证都是比长期密钥更安全的选择。
