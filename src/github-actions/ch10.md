# 第10章：缓存依赖——让你的 Workflow 快起来

## 引言：时间就是金钱，CI 分钟就是账单

你知道 GitHub Actions 最让人肉疼的是什么吗？不是写 YAML——虽然那也挺折磨人的——是**每次运行都要重新 `npm install`**。

一个中等规模的 Node.js 项目，`npm ci` 可能要花 1-3 分钟。如果你的 Workflow 有 4 个并行的 Job（lint、test、build、e2e），每个都要装一遍依赖，光安装就花掉 4-12 分钟。一年下来，你光等依赖安装的时间够看完两季美剧了。

**缓存（Cache）** 就是来解决这个问题的。它的原理很简单：第一次安装依赖后，把 `node_modules` 塞进"冰箱"；下次运行时，直接从"冰箱"里拿出来，跳过安装步骤。

## actions/cache 的详细用法

```yaml
# 最基础的缓存配置
steps:
  - uses: actions/checkout@v4

  - name: 🗄️ 缓存 node_modules
    uses: actions/cache@v4
    with:
      path: ~/.npm                    # 要缓存的目录
      key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
      # key 的组成：
      # runner.os    → "Linux"（区分操作系统，避免把 Linux 的缓存给 Windows 用）
      # "npm"        → 固定前缀，区分不同类型的缓存
      # hashFiles    → 对 package-lock.json 取哈希，锁文件变了缓存就失效
      restore-keys: |
        ${{ runner.os }}-npm-
        # 回退键：精确匹配失败时，用前缀匹配找一个"最接近"的缓存
        # 就像一个"兜底方案"——虽然不是完全匹配，但至少能恢复大部分依赖

  - name: 安装依赖
    run: npm ci
    # npm ci 会检查 node_modules 是否已经存在
    # 如果缓存命中，node_modules 已经有内容，npm ci 会增量安装缺失的包
```

## Cache Key 策略——精确匹配与回退机制

Cache key 的设计是一门艺术。太精确了（每次都不同），缓存永远命中不了；太模糊了（永远一样），依赖更新了却还在用旧缓存。

```yaml
# 理解 restore-keys 的回退机制

# 假设你的 cache key 是：
key: Linux-npm-abc123def456
# restore-keys 是：
restore-keys: |
  Linux-npm-
  Linux-

# GitHub Actions 的匹配逻辑：
# 1. 先精确匹配 key："Linux-npm-abc123def456" → 找不到
# 2. 用第一个 restore-key 前缀匹配："Linux-npm-" → 找到 "Linux-npm-old789"
# 3. 如果还找不到，用第二个 restore-key："Linux-" → 找到 "Linux-pip-something"
# 4. 都找不到 → cache miss，从零开始

# 这就是为什么 restore-keys 要按"从精确到模糊"排列
```

**进阶：多路径、多 key 的缓存策略**

```yaml
# 更精细的缓存策略：分别缓存 npm 全局缓存和 node_modules
- name: 缓存 npm 全局缓存
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-cache-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-cache-

# 如果你想缓存 node_modules 本身（注意：这有风险，见下文）
- name: 缓存 node_modules
  uses: actions/cache@v4
  with:
    path: node_modules
    key: ${{ runner.os }}-node-modules-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-modules-
```

> **⚠️ 重要决策：缓存 `~/.npm` 还是 `node_modules`？**
>
> 缓存 `~/.npm`（npm 的下载缓存目录）更安全——`npm ci` 仍然会执行，只是不用从网络下载已有的包。
>
> 缓存 `node_modules` 更激进——直接跳过安装。但 `node_modules` 可能包含平台相关的二进制文件（比如 `esbuild`、`sharp`），换一台 runner 可能就不兼容了。
>
> **建议**：优先缓存 `~/.npm`，安全又有效。

## 常见语言的缓存路径

```yaml
# Node.js / JavaScript
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    # 如果用 yarn：
    # path: ~/.cache/yarn
    # key: ${{ runner.os }}-yarn-${{ hashFiles('**/yarn.lock') }}
    # 如果用 pnpm：
    # path: ~/.pnpm-store
    # key: ${{ runner.os }}-pnpm-${{ hashFiles('**/pnpm-lock.yaml') }}

# Python (pip)
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}

# Java (Maven)
- uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}

# Go
- uses: actions/cache@v4
  with:
    path: |
      ~/.cache/go-build
      ~/go/pkg/mod
    key: ${{ runner.os }}-go-${{ hashFiles('**/go.sum') }}

# Ruby (Bundler)
- uses: actions/cache@v4
  with:
    path: vendor/bundle
    key: ${{ runner.os }}-gems-${{ hashFiles('**/Gemfile.lock') }}
```

## 缓存大小限制和淘汰策略

GitHub Actions 的缓存有这些限制，你心里得有数：

- **单个仓库缓存上限**：10 GB（所有分支的缓存加在一起）
- **单个缓存条目上限**：10 GB（但一般不该这么大）
- **自动淘汰**：7 天未被访问的缓存会被自动删除（LRU 策略）
- **分支隔离**：默认分支（通常是 `main`）的缓存对所有分支可见；feature 分支的缓存只对自己和子分支可见

```yaml
# 缓存命中/未命中的判断：
# 一个 step 可以有条件地执行
- name: 安装依赖（仅在缓存未命中时）
  if: steps.npm-cache.outputs.cache-hit != 'true'
  run: npm ci

# 这里的 steps.npm-cache 引用的是前面 cache step 的 id
# 完整的写法：
- name: 缓存 npm
  id: npm-cache                          # 给这个 step 一个 id
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}

- name: 安装依赖
  if: steps.npm-cache.outputs.cache-hit != 'true'
  run: npm ci
  # 缓存命中时跳过安装，节省 1-3 分钟
```

## 实际案例：Node.js 项目缓存优化

让我们用数据说话。以下是一个真实 Node.js 项目的优化前后对比：

```yaml
# ❌ 优化前：每次都从头安装
name: CI (Slow)
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci          # 每次 90-180 秒
      - run: npm test         # 60 秒
      # 总耗时：~150-240 秒

# ✅ 优化后：利用缓存
name: CI (Fast)
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'        # 内置缓存！一行搞定（见下文）

      - name: 缓存 npm 依赖
        uses: actions/cache@v4
        id: npm-cache
        with:
          path: |
            ~/.npm
            node_modules       # 同时缓存 node_modules
          key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
          restore-keys: |
            ${{ runner.os }}-node-

      - name: 安装依赖
        if: steps.npm-cache.outputs.cache-hit != 'true'
        run: npm ci

      - run: npm test
      # 缓存命中时总耗时：~70 秒（节省 50%+）🎉
```

## 与 setup-node 内置缓存的区别

你可能注意到了，`actions/setup-node` 自身就有一个 `cache` 参数：

```yaml
# 最简洁的写法——一行启用缓存
- uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'npm'    # 自动缓存 ~/.npm，自动用 package-lock.json 的哈希作 key

# 这相当于：
# - uses: actions/cache@v4
#   with:
#     path: ~/.npm
#     key: <自动计算的key>
```

**内置缓存 vs 手动 `actions/cache`：**

| 维度 | `setup-node` 内置缓存 | 手动 `actions/cache` |
|------|----------------------|---------------------|
| 简洁性 | 一行搞定 | 需要写 5-6 行 |
| 灵活性 | 只能缓存 `~/.npm` | 可以缓存任意路径 |
| 自定义 key | 不支持 | 完全自定义 |
| restore-keys | 不支持 | 支持回退策略 |
| 适用场景 | 简单项目 | 需要精细控制的项目 |

**我的建议**：个人项目和简单 CI 用内置缓存，团队协作的大型项目用 `actions/cache` 手动控制。

## 小结

缓存是 CI/CD 优化中**投入产出比最高**的手段。花 5 分钟配置缓存，可能帮你每次节省 1-3 分钟，一年下来就是几十个小时。

核心要诀：

1. **Key 要精确**：用 lock 文件的哈希值，保证依赖变化时缓存失效
2. **回退要合理**：`restore-keys` 让你即使 lock 文件变了也能利用大部分旧缓存
3. **路径要对**：缓存的是"下载缓存"而不是"安装结果"，更安全
4. **注意上限**：10GB 的总限制，别把构建产物也塞进缓存

## 练习题

1. **基础题**：为你的 Node.js 项目配置 npm 缓存，对比缓存命中和未命中时的 Workflow 运行时间。
2. **进阶题**：设计一个缓存策略，同时缓存 `~/.npm` 和 Cypress 的二进制文件（`~/.cache/Cypress`），确保 Cypress E2E 测试也能加速。
3. **排错题**：你的缓存总是 miss（未命中），可能的原因有哪些？列出至少 3 个排查方向。
