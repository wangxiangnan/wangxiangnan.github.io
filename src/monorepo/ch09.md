# Ch09: 代码规范统一

## 本章目标

> 在 monorepo 中建立一套"不可违反"的代码规范体系：ESLint 10 保证代码质量，Prettier 3 保证格式一致，Husky 9 + lint-staged 17 在提交前自动修复，commitlint 21 规范提交信息。所有配置集中管理在 `packages/eslint-config` 中，各项目只保留极薄的入口文件。

## 9.1 ESLint 10 Flat Config 架构

ESLint 10 已经完全移除了 `.eslintrc` 体系，**flat config 是唯一的配置格式**。配置不再是被 ESLint 隐式解析的 JSON，而是普通的 JavaScript 模块——一个由配置对象组成的数组。这带来两个直接好处：

1. **可组合**：共享配置就是一个 npm 包，通过 `import` 拿到数组，再 `...` 展开。
2. **可推理**：配置的合并顺序就是数组顺序，没有 `extends`、`overrides`、`cascade` 的隐式规则。

在 monorepo 中，我们在 `packages/eslint-config` 中定义三层配置：

| 导出路径 | 适用对象 | 内容 |
| --- | --- | --- |
| `@taskflow/eslint-config/base` | 纯 TypeScript 包（shared） | JS + TS 推荐规则、通用质量规则 |
| `@taskflow/eslint-config/node` | Node.js 后端（api、database） | base + Node 全局变量 |
| `@taskflow/eslint-config/vue` | Vue 前端（web、ui） | base + Vue 推荐规则 + SFC 的 TS 解析 |

### 更新共享配置包

Ch03 已经创建了一个最小可用的 `packages/eslint-config`。现在把它补全为正式版本，编辑 `packages/eslint-config/package.json`：

```json
{
  "name": "@taskflow/eslint-config",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "exports": {
    "./base": "./base.js",
    "./vue": "./vue.js",
    "./node": "./node.js"
  },
  "dependencies": {
    "@eslint/js": "^10.0.1",
    "eslint-config-prettier": "^10.1.8",
    "eslint-plugin-vue": "^10.12.0",
    "globals": "^17.13.0",
    "typescript-eslint": "^8.72.1"
  },
  "peerDependencies": {
    "eslint": "^10.0.0"
  },
  "devDependencies": {
    "eslint": "^10.13.0"
  }
}
```

> **为什么 `eslint` 是 peerDependency？** 配置包只提供规则，真正执行 lint 的是各项目安装的 ESLint。声明为 peer 可以保证整个 workspace 使用同一个 ESLint 实例，避免插件与 ESLint 内核版本错配。

安装根目录的 ESLint：

```bash
pnpm add -Dw eslint@^10.13.0
```

> **TypeScript 7 的 peer 提示**：`typescript-eslint` 8.72 的 `peerDependencies` 仍写作 `typescript >=4.8.4 <6.1.0`，而本教程使用 TypeScript 7（原生编译器）。Ch02 的 `pnpm-workspace.yaml` 里已经用 `peerDependencyRules` 放行了这条规则，否则 `strictPeerDependencies` 会让安装直接失败。我们只使用非类型感知规则，不受版本提示影响。

### base.js — 通用规则（所有项目共享）

创建 `packages/eslint-config/base.js`：

```javascript
import js from '@eslint/js';
import tseslint from 'typescript-eslint';
import prettier from 'eslint-config-prettier/flat';
import globals from 'globals';

/**
 * 基础规则块 — 不包含 Prettier 兼容层
 *
 * 单独导出 rules 块是为了让 vue.js / node.js 能在末尾追加
 * eslint-config-prettier。prettier 必须排在所有格式化规则之后，
 * 否则它关闭的规则会被后面的配置重新打开。
 */
export const baseRules = tseslint.config(
  // 1. ESLint 官方推荐规则
  js.configs.recommended,

  // 2. TypeScript ESLint 推荐规则（非类型感知）
  ...tseslint.configs.recommended,

  // 3. 自定义质量规则
  {
    languageOptions: {
      ecmaVersion: 'latest',
      sourceType: 'module',
      globals: {
        ...globals.es2022,
      },
    },
    linterOptions: {
      // 残留的 eslint-disable 注释直接报错，避免"永久关闭"变成技术债
      reportUnusedDisableDirectives: 'error',
    },
    rules: {
      // 禁止 var，强制 let/const
      'no-var': 'error',

      // 能用 const 就不要用 let
      'prefer-const': 'error',

      // 未使用变量报错；以 _ 开头的参数/变量视为有意忽略
      '@typescript-eslint/no-unused-vars': ['error', {
        argsIgnorePattern: '^_',
        varsIgnorePattern: '^_',
      }],

      // 渐进式迁移：any 先警告，shared 包会覆盖为 error
      '@typescript-eslint/no-explicit-any': 'warn',

      // 纯类型导入必须使用 import type，方便打包器剔除
      '@typescript-eslint/consistent-type-imports': ['error', {
        prefer: 'type-imports',
        fixStyle: 'inline-type-imports',
      }],

      // 空 catch 必须写明原因，不能静默吞掉错误
      'no-empty': ['error', { allowEmptyCatch: false }],

      // 允许 warn/error 级别的日志
      'no-console': ['warn', { allow: ['warn', 'error'] }],

      // 强制严格相等
      eqeqeq: ['error', 'always'],
    },
  },

  // 4. 全局忽略（只含 ignores 的对象会被当作全局忽略）
  {
    ignores: [
      '**/node_modules/**',
      '**/dist/**',
      '**/.turbo/**',
      '**/coverage/**',
      '**/src/generated/**',
    ],
  },
);

// 单独使用 base 的包（如 shared）直接拿到完整配置
const baseConfig = [...baseRules, prettier];

export default baseConfig;
```

**关于 `eslint-config-prettier/flat`：**

Prettier 和 ESLint 都能改代码格式。`eslint-config-prettier` 的作用是关闭所有与 Prettier 冲突的 ESLint 格式化规则（缩进、引号、换行等），让两者各司其职：

- **ESLint 管质量**：未使用变量、错误的相等比较、危险的 `any`。
- **Prettier 管格式**：缩进、引号、换行、尾逗号。

注意导入路径是 `eslint-config-prettier/flat`，这是 ESLint 9+ flat config 专用的出口。旧的 `eslint-config-prettier` 默认出口仍是 eslintrc 时代的形状。

### vue.js — Vue 前端专用规则

创建 `packages/eslint-config/vue.js`：

```javascript
import pluginVue from 'eslint-plugin-vue';
import tseslint from 'typescript-eslint';
import prettier from 'eslint-config-prettier/flat';
import globals from 'globals';
import { baseRules } from './base.js';

/**
 * Vue 项目配置
 * 顺序很重要：base → Vue 推荐 → Vue 覆盖 → prettier
 */
const vueConfig = tseslint.config(
  ...baseRules,

  // Vue 官方推荐规则（flat 版本）
  ...pluginVue.configs['flat/recommended'],

  {
    files: ['**/*.vue'],
    languageOptions: {
      parserOptions: {
        // 让 vue-eslint-parser 把 <script lang="ts"> 交给 TS 解析器
        parser: tseslint.parser,
        extraFileExtensions: ['.vue'],
        sourceType: 'module',
      },
      globals: {
        ...globals.es2022,
        ...globals.browser,
      },
    },
    rules: {
      // 组件文件名不强制多单词（views 目录下已按页面命名）
      'vue/multi-word-component-names': 'off',

      // 只允许 <script setup>（Vue 3 推荐写法）
      'vue/component-api-style': ['error', ['script-setup']],

      // defineProps / defineEmits / defineSlots / defineModel 的书写顺序
      'vue/define-macros-order': ['error', {
        order: ['defineProps', 'defineEmits', 'defineSlots', 'defineModel'],
      }],

      // 模板属性顺序：结构指令 → 唯一属性 → 绑定 → 事件
      'vue/attributes-order': ['error', {
        order: [
          'DEFINITION',
          'LIST_RENDERING',
          'CONDITIONALS',
          'RENDER_MODIFIERS',
          'GLOBAL',
          'UNIQUE',
          'SLOT',
          'TWO_WAY_BINDING',
          'OTHER_DIRECTIVES',
          'OTHER_ATTR',
          'EVENTS',
          'CONTENT',
        ],
      }],

      // TS 已经在编译期检查未定义标识符；Vue 模板的编译产物会误报
      'no-undef': 'off',
      'no-unused-vars': 'off',

      // TS 的可选 prop 不需要运行时默认值
      'vue/require-default-prop': 'off',

      // v-html 有 XSS 风险，保留警告提醒评审
      'vue/no-v-html': 'warn',
    },
  },

  // 必须最后：关闭与 Prettier 冲突的 Vue / JS 格式化规则
  prettier,
);

export default vueConfig;
```

### node.js — Node.js 后端专用规则

创建 `packages/eslint-config/node.js`：

```javascript
import prettier from 'eslint-config-prettier/flat';
import globals from 'globals';
import { baseRules } from './base.js';

/**
 * Node.js 项目配置
 * 在 base 基础上补充 Node 全局变量，并放开后端日志限制
 */
const nodeConfig = [
  ...baseRules,

  {
    languageOptions: {
      globals: {
        ...globals.es2022,
        ...globals.node,
      },
    },
    rules: {
      // 后端需要结构化日志，console 由日志库接管前先放开
      'no-console': 'off',
    },
  },

  prettier,
];

export default nodeConfig;
```

> **为什么删掉了 `no-unhandled-rejections` 和 `no-sync`？**
> 这两条规则并不存在于 ESLint 核心或 `typescript-eslint` 中，它们来自 `eslint-plugin-n`。写在配置里不会生效，只会给读者造成"已经检查过了"的错觉。本项目的异步错误由 Express 5 自动转发 + 全局错误处理中间件兜底（Ch08）。如果确实需要 Node 专项规则，应安装 `eslint-plugin-n`，然后展开 `n.configs['flat/recommended']`。

### 给各包添加 lint 脚本

Ch03 之所以没有放 lint 脚本，是因为那时还没有 `eslint.config.js`。现在给 `apps/web`、`apps/api`、`packages/shared`、`packages/ui`、`packages/database` 的 `package.json` 都加上：

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix"
  },
  "devDependencies": {
    "@taskflow/eslint-config": "workspace:*",
    "eslint": "^10.13.0"
  }
}
```

三点说明：

1. **`eslint` 必须出现在每个消费者自己的 `devDependencies` 里**。pnpm 的 `autoInstallPeers: false` 不会替你补 peer 依赖，`@taskflow/eslint-config` 的 `eslint` peer 需要由使用方满足。
2. **`lint` 只检查、不修改**，适合 CI；`lint:fix` 才会写文件，适合本地和 lint-staged。把两者分开后，CI 不会出现"检查通过但工作区被改动"的怪现象。
3. `eslint .` 会从当前目录向上寻找最近的 `eslint.config.js`，所以每个包只检查自己的文件。

根目录脚本同步更新（在 Ch02 的基础上补充）：

```json
{
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "lint:fix": "turbo run lint:fix",
    "typecheck": "turbo run typecheck",
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

只检查单个包时，用 pnpm 的过滤器：

```bash
pnpm --filter @taskflow/web lint
pnpm --filter @taskflow/api lint:fix
```

## 9.3 Prettier 配置共享

Ch03 已经在根目录创建了 `.prettierrc`。这里把它补全，并解释每个选项的取舍：

```json
{
  "semi": true,
  "singleQuote": true,
  "trailingComma": "all",
  "printWidth": 100,
  "tabWidth": 2,
  "bracketSpacing": true,
  "arrowParens": "always",
  "endOfLine": "lf",
  "htmlWhitespaceSensitivity": "ignore",
  "vueIndentScriptAndStyle": false
}
```

- `singleQuote: true`：与教程中所有代码示例保持一致，也符合 Vue / TS 社区的主流习惯。
- `trailingComma: "all"`：多行参数、数组、对象都加尾逗号，diff 更干净，也是 Prettier 3 的默认值。
- `printWidth: 100`：80 对现代宽屏偏窄，100 在可读性和行数之间更平衡。
- `endOfLine: "lf"`：跨平台统一为 LF，避免 Windows 的 CRLF 制造整文件 diff。
- `htmlWhitespaceSensitivity: "ignore"`：Vue 模板的空白交给 CSS 控制，避免格式化改变渲染结果。

创建 `.prettierignore`：

```
node_modules
dist
.turbo
coverage
pnpm-lock.yaml
*.prisma
packages/database/src/generated
```

> **为什么忽略 `packages/database/src/generated`？** Prisma 7 生成的客户端是构建产物，每次 `prisma generate` 都会重写。格式化它既没有意义，还会在 CI 中制造"检查后文件又被改回去"的假 diff。

**为什么 Prettier 配置放在根目录而不是 packages 中？**

Prettier 会从被格式化文件所在目录开始向上查找最近的配置文件。放在根目录，意味着仓库里的每一个文件（包括 `apps/web`、`packages/shared`、根目录的 `turbo.json`）都共享同一套规则。如果放进 `packages/prettier-config`，那么根目录自己的 `.md`、`.json` 就没有配置覆盖，反而需要额外指定。

安装 Prettier（Ch02 已安装，这一步确认版本）：

```bash
pnpm add -Dw prettier@^3.9.10
```

格式化命令已经加到根目录脚本：

```bash
pnpm format         # 写入格式化结果
pnpm format:check   # 只检查，CI 使用
```

## 9.4 Husky + lint-staged：提交前自动检查

前面两节解决的是"规则是什么"，这一节解决"如何保证规则被执行"。Husky 负责在 Git 生命周期中插入钩子，lint-staged 负责只处理本次暂存的文件。

安装依赖：

```bash
pnpm add -Dw husky@^9.1.7 lint-staged@^17.6.0
```

初始化 Husky：

```bash
pnpm exec husky init
```

> 这里用 `pnpm exec` 而不是 `npx`。在 pnpm workspace 中，`npx` 可能解析到全局或其他版本的 husky；`pnpm exec` 保证执行的是根目录 `devDependencies` 里那个版本。

`husky init` 会做三件事：

1. 创建 `.husky/` 目录；
2. 写入一个示例 `pre-commit` 钩子；
3. 在根 `package.json` 中添加 `"prepare": "husky"`。

Husky 9 不再需要在钩子里 `source .husky/_/husky.sh`，也把 Git 的 `core.hooksPath` 指向 `.husky/_`（注意不是 `.husky`）。这是排查钩子不执行时的关键信息。

编辑 `.husky/pre-commit`：

```sh
#!/usr/bin/env sh
pnpm exec lint-staged
```

**为什么用 lint-staged 而不是直接运行 `turbo lint`？**

`turbo lint` 会检查整个仓库。在一个有几千个文件的项目里，哪怕只改了一行，也要等所有包跑完。`lint-staged` 只把你 `git add` 过的文件交给 ESLint 和 Prettier，通常 1-2 秒结束。两者并不冲突：本地提交走 lint-staged，CI 走全量 `turbo lint`。

在根 `package.json` 中配置 lint-staged：

```json
{
  "lint-staged": {
    "apps/**/*.{ts,tsx,vue,js}": [
      "eslint --fix",
      "prettier --write"
    ],
    "packages/{shared,ui,database}/**/*.{ts,tsx,vue,js}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{json,jsonc,yaml,yml,md,css,scss,html}": [
      "prettier --write"
    ]
  }
}
```

**为什么不直接写 `*.{ts,vue}`？**

根目录没有 `eslint.config.js`。如果一条全局的 `*.ts` 规则把根目录的 `commitlint.config.mjs` 或 `packages/eslint-config/base.js` 交给 ESLint，ESLint 10 会因为找不到配置文件而直接失败。按目录限定范围后：

- `apps/**` 和三个代码包：各自有 `eslint.config.js`，正常检查。
- 根目录的配置文件：只走 Prettier，不跑 ESLint。
- `packages/eslint-config` 本身：只走 Prettier，避免"检查配置的配置"的循环。

**工作流程：**

```
开发者输入 git commit
       │
       ▼
Husky 拦截 .husky/pre-commit
       │
       ▼
lint-staged 读取暂存文件列表
       │
       ├── apps/**、packages/{shared,ui,database}/** 的 TS/Vue/JS
       │      → eslint --fix → prettier --write
       │
       ├── 根目录的 json / md / yaml / css
       │      → prettier --write
       │
       ▼
自动把修复后的文件重新加入暂存区
       │
       ├── 仍有无法自动修复的错误 → 提交失败，终端打印文件名和规则
       └── 全部通过 → 提交成功
```

**为什么 `prepare` 脚本很重要？**

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

`prepare` 会在每次 `pnpm install` 之后自动执行。新人 clone 仓库、跑一次 `pnpm install`，Git 钩子就装好了，不需要额外看文档。CI 和 Docker 构建里没有 `.git`，钩子装不上，用 `HUSKY=0` 让 husky 安静跳过（Ch14 的 Dockerfile 会设置这个变量）；不要用 `--ignore-scripts`，那会把 esbuild 等依赖的构建脚本一起关掉。

> **Windows 提示**：Husky 的钩子由 Git for Windows 自带的 `sh` 执行，请在 Git Bash 或 PowerShell 中提交。如果钩子文件没有可执行权限，在 Git Bash 中运行 `chmod +x .husky/pre-commit .husky/commit-msg`，或执行 `git update-index --chmod=+x .husky/pre-commit`。

## 9.5 commitlint：规范 Commit Message

lint-staged 保证代码质量，commitlint 保证提交信息质量。安装：

```bash
pnpm add -Dw @commitlint/cli@^21.2.4 @commitlint/config-conventional@^21.2.4
```

根目录的 `package.json` 没有 `"type": "module"`（Ch02 中的根包只放脚本和工具），因此配置文件必须用 `.mjs` 后缀，否则 `export default` 会报语法错误。

创建 `commitlint.config.mjs`：

```javascript
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    // type 必须是以下值之一
    'type-enum': [2, 'always', [
      'feat',     // 新功能
      'fix',      // 修复 Bug
      'docs',     // 文档变更
      'style',    // 代码格式（不影响代码含义）
      'refactor', // 重构（既不是新功能也不是修复）
      'perf',     // 性能优化
      'test',     // 测试相关
      'build',    // 构建系统或外部依赖变更
      'ci',       // CI 配置变更
      'chore',    // 其他不修改源代码的变更
      'revert',   // 回滚提交
    ]],

    // scope 可选：feat(shared) 和 feat 都合法
    'scope-empty': [0],

    // subject 不能为空
    'subject-empty': [2, 'never'],

    // subject 不能以句号结尾
    'subject-full-stop': [2, 'never', '.'],

    // subject 不用句首大写、标题格式或全大写
    'subject-case': [2, 'never', ['sentence-case', 'start-case', 'pascal-case', 'upper-case']],

    // 标题行不超过 100 个字符（config-conventional 的默认值）
    'header-max-length': [2, 'always', 100],
  },
};
```

创建 `.husky/commit-msg` 钩子：

```sh
#!/usr/bin/env sh
pnpm exec commitlint --edit "$1"
```

`$1` 是 Git 传给钩子的临时文件路径，里面是本次提交信息。`--edit` 让 commitlint 读取并校验这个文件。

**Conventional Commits 格式：**

```
<type>(<scope>): <subject>

<body>

<footer>
```

示例：

```bash
# ✅ 正确
feat(shared): add Zod validation schemas for user DTOs
fix(api): handle undefined user in getUser controller
docs(readme): update installation instructions
refactor(web): extract api client into separate module

# ❌ 错误 — 会被拒绝
added new feature          # 缺少 type
fix: something.            # subject 以句号结尾
Update code                # type 不在枚举中，且 subject 是大写开头
```

**为什么 commit message 规范值得强制？**

1. **自动生成 CHANGELOG**：Changesets、semantic-release 等工具根据 `feat` / `fix` 自动归类变更。
2. **语义化版本**：`feat` 触发 minor，`fix` 触发 patch，`BREAKING CHANGE` 触发 major。
3. **可读的历史**：`git log --oneline` 一眼能看出每次提交的性质。
4. **减少无效信息**：团队里不会再出现 "update"、"fix bug"、"wip" 这类无法回溯的提交。

> 早期的教程常用 `standard-version` 生成 CHANGELOG，但该项目已停止维护。本教程的发布流程使用 Changesets（Ch13），它与 pnpm workspace 的配合更自然。

## 9.6 EditorConfig 和 VS Code 工作区设置

### EditorConfig

EditorConfig 解决的是"打开文件的第一秒"：不同编辑器（VS Code、WebStorm、Vim）在缩进、换行、字符集上的默认值不同。它比 Prettier 更底层，Prettier 尚未运行时也能生效。

创建根目录 `.editorconfig`：

```ini
root = true

end_of_line = lf
indent_style = space
indent_size = 2
insert_final_newline = true
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false

[Makefile]
indent_style = tab
```

`root = true` 阻止编辑器继续向上查找父目录的配置，确保仓库内的规则是最终规则。

## 9.7 Turborepo 中的 lint 任务配置

编辑根目录 `turbo.json`，把 lint 相关的任务补全（Ch10 会继续扩展其他任务）：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "globalDependencies": ["packages/eslint-config/**", "packages/tsconfig/**"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "lint": {
      "inputs": ["src/**", "tests/**", "eslint.config.js", "package.json"]
    },
    "lint:fix": {
      "cache": false
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json", "package.json"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "clean": {
      "cache": false
    }
  }
}
```

三个关键决策：

**1. `lint` 不需要 `dependsOn: ["^build"]`**

本教程使用的是 `tseslint.configs.recommended`，它是**非类型感知**规则集：只做语法和局部语义检查，不需要读取依赖包的 `.d.ts`。因此 lint 可以在依赖构建之前运行，和 Ch02 的初版配置一致，也能最大化并行度。

只有当你启用 `tseslint.configs.recommendedTypeChecked`（需要 `parserOptions.projectService`）时，才必须加上：

```json
"lint": {
  "dependsOn": ["^build"],
  "inputs": ["src/**", "tests/**", "eslint.config.js", "tsconfig.json", "package.json"]
}
```

因为类型感知规则要解析 `@taskflow/shared` 的类型，而 shared 的 `dist/*.d.ts` 还没生成时解析会失败。

**2. `lint:fix` 不缓存**

`lint:fix` 会修改源文件，属于副作用任务。缓存一个"会改文件"的任务没有意义，Turborepo 也可能回放缓存而跳过实际修复。

**3. `globalDependencies`**

`packages/eslint-config` 和 `packages/tsconfig` 不属于任何应用的依赖构建图，但它们的改动会影响所有包的 lint / typecheck 结果。把它们放进 `globalDependencies`，任何配置变更都会让全局 hash 失效，避免"改了规则但缓存仍然命中"的问题。代价是配置变更会让所有任务重新执行——对配置包来说这是正确的取舍。

## 9.9 常见配置问题和解决方案

### 问题 1：ESLint 报 "Parsing error: Cannot find module '@taskflow/shared'"

**原因：** 这不是普通 lint 的问题，而是启用了类型感知规则（`recommendedTypeChecked`）后，TypeScript 无法解析 shared 包的入口。shared 的 `exports` 中 `types` 指向 `dist/index.d.ts`，而 `dist` 还没有构建。

**解决：**

```bash
pnpm --filter @taskflow/shared build
```

并把 `turbo.json` 的 lint 任务改成 `dependsOn: ["^build"]`。如果你只用 `recommended`（本教程的默认配置），不会遇到这个问题。

### 问题 2：Husky 钩子不执行

**排查步骤：**

```bash
# Husky 9 的 hooksPath 是 .husky/_，不是 .husky
git config core.hooksPath

# 确认钩子文件存在且有执行权限
ls -la .husky/

# 重新安装钩子
pnpm exec husky init
```

如果 `core.hooksPath` 为空或指向别处，说明 `prepare` 没有执行。手动运行 `pnpm exec husky` 即可。另外，部分 Git GUI 客户端默认不执行钩子，请改用命令行提交。

### 问题 3：Prettier 和 ESLint 规则冲突

**症状：** 保存时 Prettier 把引号改成单引号，ESLint 又要求双引号，文件在保存后反复跳动。

**解决：** 确保 `eslint-config-prettier/flat` 在配置数组的**最后**。本教程的 `vue.js`、`node.js`、`base.js` 都遵循这个顺序。不要安装 `eslint-plugin-prettier`——它把 Prettier 当成 ESLint 规则运行，速度慢、报错位置差，官方也不推荐。

### 问题 4：VS Code 中 ESLint 不工作

**排查：**

1. 确认扩展是 `dbaeumer.vscode-eslint` 3.x 以上版本（支持 ESLint 10）。
2. 用 VS Code **打开仓库根目录**，而不是单独打开 `apps/web`。打开子目录时，pnpm workspace 的依赖解析会不完整。
3. 在输出面板选择 "ESLint"，查看它加载的是哪个 `eslint.config.js`。
4. 执行命令面板中的 `ESLint: Restart ESLint Server`。
5. 检查 `.vscode/settings.json` 中是否有残留的 `eslint.useFlatConfig`。ESLint 10 只支持 flat config，这个开关已经没有必要。

### 问题 5：lint-staged 提示 "File ignored because of a matching ignore pattern"

**原因：** 暂存了被 `ignores` 排除的文件（例如 `packages/database/src/generated` 下的产物），ESLint 对显式传入的忽略文件会给出警告。

**解决：** 不要提交生成产物；如果确实需要在脚本中传入整目录，使用 `eslint --no-warn-ignored`。

### 问题 6：lint-staged 在大项目中太慢

**优化一：启用 ESLint 缓存**

```json
{
  "lint-staged": {
    "apps/**/*.{ts,tsx,vue}": [
      "eslint --fix --cache",
      "prettier --write"
    ]
  }
}
```

并把 `.eslintcache` 加入 `.gitignore`。缓存按文件内容计算，未改动的文件会跳过。

**优化二：减少每个文件的处理步骤**

每个 glob 只保留必要的命令。ESLint 负责质量与可自动修复的问题，Prettier 负责格式，两者各跑一次即可。不要在一个 glob 里再叠加 `tsc`、`vitest`——类型检查和测试应该交给 `turbo typecheck` 和 CI，而不是每次提交都跑。

### 问题 7：commitlint 拒绝合法提交

**常见原因：**

- 使用了 `-m "update"` 这类缺少 type 的信息。
- subject 以句号结尾，或使用了 `Update code` 这种大写开头。
- 在 Windows 的 PowerShell 中，`!` 等字符被 shell 解释，导致实际提交信息与预期不同。必要时用 `git commit` 打开编辑器编写。

用 `git commit --no-verify` 可以跳过钩子，但只应在紧急热修复时使用，并在事后补一次规范提交。

## 本章小结

- ESLint 10 只支持 flat config，配置就是普通 JS 模块，共享配置通过 workspace 包分发
- `eslint-config-prettier/flat` 必须排在配置数组末尾，ESLint 管质量、Prettier 管格式
- 每个包声明自己的 `eslint` devDependency，满足 peer 并保证二进制可用
- Husky 9 + lint-staged 17 构成提交门禁，只处理暂存文件；`prepare` 让新成员零配置接入
- commitlint + Conventional Commits 为 Changesets 和语义化版本打基础
- lint 任务不需要 `^build`（非类型感知）；启用类型感知规则后才需要
