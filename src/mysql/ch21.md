# 第21章 分库分表

你家的衣柜能装多少衣服？100件？200件？如果塞进去10000件，找一件衣服可能要翻半个小时。数据库的表也是一样——当单表数据量突破千万甚至上亿行时，查询速度会像你在塞满的衣柜里找袜子一样，越来越慢。分库分表，就是给数据建一个"智能衣柜系统"。

## 21.1 为什么需要分库分表

在考虑分库分表之前，先确认你是否真的需要它。很多时候，优化索引、优化查询、升级硬件就能解决问题。这就好比你的房间乱了，第一反应不应该是"换个更大的房子"，而是先收拾收拾。

让我们来算一笔账：假设你的电商系统每天产生 10 万条订单，一年就是 3650 万条。三年下来就是超过 1 亿条记录。一条订单记录大约 500 字节，1 亿条就是 50GB。MySQL 单表在 1000 万行以内通常性能很好，超过 2000 万行就需要关注了，到了 5000 万以上，即使有索引，很多操作的延迟也会变得不可接受。这时候，分库分表就从"可选"变成了"必须"。

**什么时候该考虑分库分表：**

- 单表数据量超过 1000 万行（经验值）
- 单个数据库的 QPS 超过瓶颈（通常 5000-10000 QPS）
- 磁盘空间不足，单台服务器放不下所有数据
- 已经做过索引优化、读写分离等优化，仍然无法满足需求

> **Warning：** 分库分表是"最后的武器"。它引入的复杂度是巨大的——分布式事务、跨库JOIN、全局排序等问题都会冒出来。能不分就不分！

## 21.2 垂直拆分

垂直拆分是按业务维度将不同的表拆分到不同的数据库中。就像把一个大衣柜分成"上衣区"、"裤子区"、"鞋区"。垂直拆分通常是分库分表的第一步，也是最简单的一步——它不需要修改任何 SQL 查询逻辑，只需要把不同业务的数据库连接指向不同的地址即可。

垂直拆分的一个重要原则是"高内聚、低耦合"：经常一起被查询的表应该放在同一个数据库中，而很少有关联的表应该拆分到不同的数据库中。比如用户表和用户地址表总是在同一个查询中出现，就应该放在同一个库；而日志表和订单表几乎没有关联，就应该分开。

另一个常见的垂直拆分模式是"冷热分离"。比如电商系统中，最近三个月的订单是"热数据"，访问频率很高；而历史订单是"冷数据"，偶尔才会被查询。你可以把热数据放在一个高性能的数据库中，冷数据放在一个低成本的大容量数据库中。这种模式在很多互联网公司的实践中都非常常见。

```sql
-- 拆分前：一个数据库包含所有业务表
-- ecommerce_db
--   ├── users（用户表）
--   ├── products（商品表）
--   ├── orders（订单表）
--   ├── order_items（订单明细）
--   ├── reviews（评论表）
--   ├── logs（日志表）

-- 拆分后：按业务拆分为多个数据库
-- user_db:        users, user_addresses, user_profiles
-- product_db:     products, categories, inventory
-- order_db:       orders, order_items, payments
-- review_db:      reviews, ratings
-- log_db:         operation_logs, access_logs
```

**垂直拆分的优缺点：**

优点：

- 业务解耦，独立部署和维护
- 降低单库负载
- 可以针对不同业务库使用不同配置的服务器

缺点：

- 跨库 JOIN 变复杂
- 分布式事务问题

## 21.3 水平分表

水平分表是把同一张表的数据按某个规则拆分到多张结构相同的表中。就像把一个大抽屉的袜子按颜色分到不同的小盒子里。分表的关键在于路由规则的设计——如何根据查询条件快速定位到正确的分表，而不需要扫描所有分表。

在实际项目中，分表数量的选择也很有讲究。常见的做法是分 2 的幂次方（4、8、16、32、64），这样做有两个好处：第一，取模运算可以简化为位运算，性能更好；第二，未来扩容时可以用一致性 Hash 或"翻倍扩容法"，数据迁移量最小。另外，分表数量也不是越多越好——太多的分表会增加运维复杂度，每个分表都需要独立的索引、独立的缓冲，DDL 变更也需要在所有分表上执行。

**Range（范围分片）：**

```sql
-- 按时间范围分表
-- orders_202301: 2023年1月的订单
-- orders_202302: 2023年2月的订单
-- orders_202303: 2023年3月的订单

CREATE TABLE orders_202401 LIKE orders;
CREATE TABLE orders_202402 LIKE orders;

-- 按ID范围分表
-- users_0: id 1-10000000
-- users_1: id 10000001-20000000

-- 查询路由逻辑
-- SELECT * FROM orders WHERE create_time = '2024-01-15'
-- 路由到 orders_202401
```

**Hash（哈希分片）：**

```sql
-- 按 user_id 取模分 4 张表
-- orders_0: user_id % 4 == 0
-- orders_1: user_id % 4 == 1
-- orders_2: user_id % 4 == 2
-- orders_3: user_id % 4 == 3

-- 路由逻辑
-- 已知 user_id = 12345
-- 12345 % 4 = 1
-- 查询路由到 orders_1
```

**一致性Hash：**

解决扩容问题。普通 Hash 分片在增加节点时，大部分数据都需要重新分布。一致性 Hash 只需要迁移少量数据。

```
假设从 4 个分片扩展到 5 个分片：
普通 Hash: 约 80% 的数据需要迁移
一致性 Hash: 约 20% 的数据需要迁移
```

## 21.4 水平分库

水平分库是把同一张表的数据分散到多个数据库实例中。当单台服务器的资源不够用时，就需要分库来横向扩展。

```sql
-- 4库 x 4表 = 16个分片
-- db_0.orders_0, db_0.orders_1, db_0.orders_2, db_0.orders_3
-- db_1.orders_0, db_1.orders_1, db_1.orders_2, db_1.orders_3
-- db_2.orders_0, db_2.orders_1, db_2.orders_2, db_2.orders_3
-- db_3.orders_0, db_3.orders_1, db_3.orders_2, db_3.orders_3

-- 路由逻辑（先定位库，再定位表）
-- db_index = user_id % 4       (定位到哪个库)
-- table_index = user_id / 4 % 4 (定位到哪个表)
```

## 21.5 分片键的选择

分片键（Sharding Key）是分库分表方案中最关键的决策。选错了分片键，后面全是坑。

**选择原则：**

1. **高频查询字段**：大部分查询都应该带上这个字段
2. **数据分布均匀**：避免数据倾斜（某些分片数据量远大于其他分片）
3. **尽量避免修改**：分片键的值一旦确定，最好不要变更

```sql
-- 好的分片键示例：
-- 电商订单表 → user_id（用户ID）
--   原因：大部分查询都是"某个用户的订单"
--   user_id 分布均匀，不会被修改

-- 坏的分片键示例：
-- 电商订单表 → status（订单状态）
--   原因：状态值只有几个（已支付、已发货...），严重数据倾斜
--   大部分订单最终都会变成"已完成"
```

> **Tip：** 如果业务上既需要按 user_id 查询，又需要按 order_id 查询，可以考虑建立"二级索引表"来解决。

## 21.6 分布式ID方案

分库分表后，MySQL 的 AUTO_INCREMENT 就不能用了（每个分片各自自增会冲突）。我们需要一个全局唯一的 ID 生成方案。这个看似简单的问题，实际上是分布式系统设计中的一个经典难题。一个好的分布式 ID 方案需要同时满足：全局唯一、单调递增、高性能、高可用、信息安全（不能轻易推测出其他 ID）。

不同的方案各有优劣：UUID 生成简单但无序且太长，作为主键会导致严重的页分裂问题，写入性能可能下降 3-5 倍；数据库号段模式实现简单、ID 连续，但依赖数据库本身的可用性；雪花算法不依赖任何外部组件，生成速度极快（单机每秒可生成数百万个 ID），ID 整体有序且长度可控，但需要处理时钟回拨问题——如果服务器的系统时间被向后调整，可能产生重复 ID。在生产环境中，雪花算法是最常用的方案，因为它在性能和可用性之间取得了很好的平衡。

**UUID：**

```javascript
const { v4: uuidv4 } = require('uuid');

// 简单但有问题：
// 1. 字符串类型，占空间大（36字节）
// 2. 无序，作为主键会导致页分裂，写入性能差
const id = uuidv4(); // 'a1b2c3d4-e5f6-7890-abcd-ef1234567890'
```

**雪花算法（Snowflake）：**

```javascript
// 雪花算法 ID 结构（64位）：
// 1位符号位 + 41位时间戳 + 10位机器ID + 12位序列号
// 有序、全局唯一、高性能

class Snowflake {
  constructor(workerId, datacenterId) {
    this.workerId = workerId;
    this.datacenterId = datacenterId;
    this.sequence = 0;
    this.lastTimestamp = -1;
    // 起始时间戳：2024-01-01
    this.epoch = 1704067200000n;
  }

  nextId() {
    let timestamp = BigInt(Date.now());

    if (timestamp === this.lastTimestamp) {
      this.sequence = (this.sequence + 1) & 0xFFF;
      if (this.sequence === 0) {
        // 等待下一毫秒
        while (timestamp <= this.lastTimestamp) {
          timestamp = BigInt(Date.now());
        }
      }
    } else {
      this.sequence = 0;
    }

    this.lastTimestamp = timestamp;

    return ((timestamp - this.epoch) << 22n)
      | (BigInt(this.datacenterId) << 17n)
      | (BigInt(this.workerId) << 12n)
      | BigInt(this.sequence);
  }
}

const generator = new Snowflake(1, 1);
console.log(generator.nextId().toString()); // 例如：178234567890123456
```

**号段模式：**

```javascript
// 号段模式：每次从数据库批量获取一批ID，缓存在内存中
// 适合高并发场景，减少数据库访问

class SegmentIdGenerator {
  constructor(dbPool, bizTag, step = 1000) {
    this.dbPool = dbPool;
    this.bizTag = bizTag;
    this.step = step;
    this.currentId = 0;
    this.maxId = 0;
  }

  async getNextId() {
    if (this.currentId >= this.maxId) {
      await this.fetchNextSegment();
    }
    return ++this.currentId;
  }

  async fetchNextSegment() {
    // 原子更新，获取下一个号段
    const [result] = await this.dbPool.execute(
      `UPDATE id_generator 
       SET max_id = max_id + step, updated_at = NOW() 
       WHERE biz_tag = ?`,
      [this.bizTag]
    );

    const [rows] = await this.dbPool.execute(
      'SELECT max_id, step FROM id_generator WHERE biz_tag = ?',
      [this.bizTag]
    );

    this.maxId = rows[0].max_id;
    this.currentId = this.maxId - rows[0].step;
  }
}
```

## 21.7 跨分片查询的处理

分库分表后最头疼的问题之一就是跨分片查询。

```sql
-- 问题：查询所有用户的订单总额
-- 需要查询 orders_0, orders_1, orders_2, orders_3 然后汇总

-- 解决方案1：在应用层聚合
-- 分别查询每个分片，然后在代码中合并结果

-- 解决方案2：使用汇总表
CREATE TABLE orders_summary (
  user_id BIGINT PRIMARY KEY,
  total_amount DECIMAL(12,2),
  order_count INT,
  updated_at TIMESTAMP
);

-- 通过定时任务或消息队列异步更新汇总表
```

**常见跨分片场景及解决方案：**

```sql
-- 全局排序：先各分片排序，再在应用层归并排序
-- 全局分页：各分片取 offset+limit 条，在应用层排序后取 offset 到 offset+limit
-- 全局聚合：各分片分别聚合，在应用层做最终聚合
-- 跨分片JOIN：
--   方案1：冗余数据（反范式）
--   方案2：将关联数据拉到应用层JOIN
--   方案3：使用宽表/汇总表
```

## 21.8 分布式事务

分库分表后，一个原本简单的业务操作可能需要同时修改多个数据库中的数据。比如"下单"这个操作，需要同时在订单库创建订单、在库存库扣减库存、在用户库更新积分。如果其中任何一步失败了，其他步骤也需要回滚——这就是分布式事务问题。

**两阶段提交（2PC）：**

两阶段提交是经典的分布式事务协议，分为"准备阶段"和"提交阶段"。在准备阶段，所有参与者告诉协调者"我准备好了"；在提交阶段，协调者统一发出"提交"或"回滚"的指令。它的缺点是同步阻塞、性能差、协调者是单点故障。

**TCC（Try-Confirm-Cancel）模式：**

TCC 是一种应用层的补偿机制，不需要数据库层面的支持。每个操作都实现三个接口：Try（预留资源）、Confirm（确认提交）、Cancel（取消回滚）。

```javascript
// TCC 示例：下单扣库存
class InventoryService {
  // Try：冻结库存（不真正扣减）
  async tryReserve(productId, quantity) {
    const [result] = await pool.execute(
      `UPDATE inventory 
       SET frozen_qty = frozen_qty + ?, available_qty = available_qty - ?
       WHERE product_id = ? AND available_qty >= ?`,
      [quantity, quantity, productId, quantity]
    );
    return result.affectedRows > 0;
  }

  // Confirm：确认扣减（把冻结的变成已扣减的）
  async confirmReserve(productId, quantity) {
    await pool.execute(
      `UPDATE inventory 
       SET frozen_qty = frozen_qty - ?, sold_qty = sold_qty + ?
       WHERE product_id = ?`,
      [quantity, quantity, productId]
    );
  }

  // Cancel：取消预留（把冻结的还给可用库存）
  async cancelReserve(productId, quantity) {
    await pool.execute(
      `UPDATE inventory 
       SET frozen_qty = frozen_qty - ?, available_qty = available_qty + ?
       WHERE product_id = ?`,
      [quantity, quantity, productId]
    );
  }
}
```

**基于消息队列的最终一致性：**

这是实际生产中最常用的方案。不追求强一致性，而是通过异步消息保证"最终一致"。核心思路是：先完成主操作并发送一条消息，下游服务消费消息完成后续操作。如果消费失败，会重试直到成功。

```javascript
// 基于本地消息表的最终一致性方案
async function createOrderWithInventory(orderData) {
  const conn = await orderPool.getConnection();
  try {
    await conn.beginTransaction();

    // 1. 创建订单
    await conn.execute(
      'INSERT INTO orders (order_id, user_id, amount) VALUES (?, ?, ?)',
      [orderData.orderId, orderData.userId, orderData.amount]
    );

    // 2. 写入本地消息表（和订单在同一个事务中）
    await conn.execute(
      `INSERT INTO message_table (message_id, message_body, status) 
       VALUES (?, ?, 'PENDING')`,
      [generateMessageId(), JSON.stringify({
        type: 'ORDER_CREATED',
        orderId: orderData.orderId,
        productId: orderData.productId,
        quantity: orderData.quantity,
      })]
    );

    await conn.commit();

    // 3. 异步投递消息到 MQ（如果失败，定时任务会扫描消息表补发）
    await publishToMQ('ORDER_CREATED', orderData);

  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}
```

> **Warning：** 分布式事务是分布式系统中最难处理的问题之一。在分库分表方案设计阶段，就应该尽量避免跨库事务。如果实在避免不了，优先考虑最终一致性方案，而不是强一致性方案。

## 21.9 数据迁移与扩容

分库分表上线后，最让人头疼的事情之一就是扩容。当现有的分片数不够用时，你需要把数据重新分布到更多的分片上。这个过程需要非常谨慎，稍有不慎就会导致数据丢失或服务中断。

**双写迁移方案：**

这是最常用的在线迁移方案，分为四个阶段：

第一阶段：在旧库正常读写的基础上，同时向新库写入数据（双写）。此时以旧库为准。

第二阶段：将旧库的历史数据通过后台任务批量迁移到新库。由于第一阶段已经开启双写，新数据不会丢失。

第三阶段：数据迁移完成后，切换到从新库读取（双读），对比新旧库的读取结果是否一致。

第四阶段：确认新库数据完全正确后，关闭对旧库的写入，完成切换。

```javascript
// 双写迁移示例
class DualWriteOrderService {
  constructor(oldPool, newPool, migrationComplete) {
    this.oldPool = oldPool;
    this.newPool = newPool;
    this.migrationComplete = migrationComplete;
  }

  async createOrder(orderData) {
    // 始终写入旧库
    const result = await this.oldPool.execute(
      'INSERT INTO orders (...) VALUES (...)',
      [/* params */]
    );

    // 同时写入新库（异步，失败不阻塞主流程）
    this.newPool.execute(
      'INSERT INTO orders (...) VALUES (...)',
      [/* params */]
    ).catch(err => {
      console.error('Dual write to new DB failed:', err);
      // 记录失败日志，后续补偿
    });

    return result;
  }

  async getOrder(orderId) {
    if (this.migrationComplete) {
      // 迁移完成后从新库读取
      return this.newPool.execute('SELECT * FROM orders WHERE id = ?', [orderId]);
    } else {
      // 迁移期间从旧库读取
      return this.oldPool.execute('SELECT * FROM orders WHERE id = ?', [orderId]);
    }
  }
}
```

## 21.10 常用中间件

**Apache ShardingSphere：**

```javascript
// ShardingSphere-JDBC 是目前最流行的分库分表中间件
// 它作为 JDBC 驱动层，对应用透明

// 分片规则配置示例（YAML格式）
/*
dataSources:
  ds_0:
    url: jdbc:mysql://192.168.1.100:3306/order_db_0
    username: root
    password: pass
  ds_1:
    url: jdbc:mysql://192.168.1.101:3306/order_db_1
    username: root
    password: pass

rules:
  - !SHARDING
    tables:
      orders:
        actualDataNodes: ds_${0..1}.orders_${0..3}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: db_mod
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: table_mod
*/
```

**MyCat：**

```sql
-- MyCat 是一个数据库中间件代理，部署在应用和数据库之间
-- 应用连接 MyCat，MyCat 负责路由到正确的分片

-- schema.xml 配置示例
/*
<schema name="mydb" checkSQLschema="false" sqlMaxLimit="100">
  <table name="orders" dataNode="dn1,dn2,dn3,dn4" 
         rule="mod-long" />
</schema>

<dataNode name="dn1" dataHost="host1" database="order_db" />
<dataNode name="dn2" dataHost="host2" database="order_db" />
*/
```

> **Tip：** 对于 Node.js 项目，ShardingSphere 是 Java 生态的，不太方便直接用。Node.js 项目通常需要在应用层自己实现分片路由逻辑，或者使用 MyCat 这类代理层中间件。
