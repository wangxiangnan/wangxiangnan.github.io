## 7.1 定位澄清——mihomo 是什么、不是什么

先把第一章 1.6 那张 VPN 与代理对照表落到具体工具上。mihomo（Clash Meta 内核，CordC、Clash Verge 等 GUI 的底层）是一个**代理内核**：它监听本地代理端口、按规则把流量分发给各种出站协议。它常见于代理分流场景，但本书只用它的一个能力——**把 WireGuard 当作一种出站协议**，让它成为第三章那台服务器的一个客户端。

两种客户端形态的正面对比：

| 维度 | 官方客户端（第四章） | mihomo 客户端（本章） |
| ---- | ---- | ---- |
| 实现位置 | 系统级虚拟网卡（内核或驱动） | 用户态代理内核 + 规则引擎 |
| 流量接管 | 整张网络，协议无关 | 代理入口内的流量（7.2 的 TUN 可扩展到全局） |
| 分流方式 | AllowedIPs（网络层路由） | 规则引擎（域名、IP 段、端口可编程） |
| 配置形态 | 一张 conf 文件 | YAML 配置（GUI 里通常经「自定义配置模板/覆写」注入） |
| 适合 | 纯 VPN 需求，越简单越好 | 已在用 mihomo 系客户端、想统一管理分流 |

结论先行：**只是要连自己服务器的用户，官方客户端更省心**（一个 App 一个开关）；mihomo 形态的价值在于「一个客户端同时管代理与自建隧道」——规则引擎把两种流量统一调度。本书对 mihomo 的生态话题（订阅源、节点市场等）不做展开，第八章只讲客户端设置项的功能与配置管理本身。

CordC 本身的技术栈也交代一句：Flutter 界面 + 内置 mihomo 内核（内核组件独立于界面存在），所以本章的操作步骤在其他 mihomo 系客户端（Clash Verge、FlClash 等）里都能找到对应入口，只是菜单位置略有差异。

## 7.2 常规与网络设置——TUN 是关键开关

打开 CordC 的设置页，「常规」与「网络」两组里，真正影响本章任务的是**网络组**的 TUN 模式（各客户端命名略有差异：TUN 模式、虚拟网卡、增强模式）：

| 入口 | 接管范围 | SSH/数据库客户端能用吗 |
| ---- | ---- | ---- |
| 系统代理（默认） | 只接管「会读系统代理设置」的流量——浏览器、大部分 GUI 应用 | **不能**——SSH、psql 这类命令行工具不读系统代理 |
| TUN 模式 | 内核创建虚拟网卡，接管全部 IP 流量（1.6 说的 VPN 级接管） | 能——所有应用流量都进 mihomo |

这就是「先猜再读」第一问的答案：**没开 TUN 的 mihomo 不是 VPN 客户端**——它只是浏览器的代理。wireguard 出站配得再正确，SSH 的流量根本进不了 mihomo。开了 TUN，全部流量先进 mihomo 的规则引擎，再由规则决定去哪——这时 mihomo 才真正等价于第四章的官方客户端。

TUN 的代价也要知道：需要管理员/root 权限（建虚拟网卡），开启后**所有流量**都要过 mihomo 一道，内核调试复杂度上升。建议的用法：日常关 TUN 用系统代理，需要访问内网时临时开 TUN——或者干脆接受 7.6 的另一种解法（只让内网流量进隧道，其余交给系统）。

权限相关的小坑集中列一下，第一次开 TUN 的人几乎都会遇到：

| 症状 | 原因 | 处置 |
| ---- | ---- | ---- |
| 开关打开后弹权限请求，拒绝后失效 | TUN 建虚拟网卡需要管理员授权 | 重新开启并同意授权；Windows 上核对 UAC 弹窗 |
| TUN 开了但浏览器直连正常、SSH 无响应 | 部分客户端默认「绕过中国大陆 IP」之类分流先行 | 到 7.6 的规则里显式声明内网网段的去向 |
| 手机上 TUN 开关是灰的 | VPN 权限未授予（Android「VPN」弹窗、iOS「VPN 与设备管理」） | 系统设置里允许该 App 创建 VPN 配置 |
| 开 TUN 后其他 App 全部断网 | 规则引擎兜底策略不是 DIRECT，全部流量进了不存在的出口 | 检查兜底规则（7.6 的 `MATCH`）指向 |

「常规」组里其余项（开机自启、语言、主题等）与隧道无关，按喜好设置即可；「连接」项本章 7.4 单独讲。

### 7.2.1 踩坑实录——「认证能过、传输卡死」：TUN 大 MTU 撞上 WSL2 mirrored

一个真实案例，症状极具迷惑性：TUN 开得好好的，`ssh` 认证握手正常（服务端的欢迎语、报错都能收回来），`git push` 却永远卡在传输阶段——几 KB 的 ref 列表发出去就石沉大海，不报错、不超时，只能 Ctrl+C。换个仓库（github）推，一样卡；curl 下载几 MB 的文件，照样秒过。三条线索合起来把嫌疑全推给了「服务端故障」，真正的根因却在客户端：**mihomo 内核的 TUN 网卡默认 MTU 高达 9000**（一帧顶数帧的性能取向），而 WSL2 的 mirrored 网络模式把 Windows 网卡镜像进 Linux——镜像链路驮不动 9000 字节的大帧，PMTUD（路径 MTU 探测）又没能把「缩小分段」的信号送回来，于是链路两端的 TCP 按失真的 MTU 协商出约 8960 字节的分段上限（MTU 减去 IP 与 TCP 头），大包一遍遍重发、一遍遍被丢，连接就挂死在那里。

| 现象 | 解释 |
| ---- | ---- |
| SSH 认证、一行报错能通 | 几十字节的小包挤得过镜像链路 |
| `git push`/`fetch` 传大块数据挂死 | ref 列表、packfile 按大段组装，全被丢弃 |
| 换任何 git 服务器都一样 | 病在隧道链路，与目标站点无关 |
| `curl` 大文件正常 | 它走系统代理端口（用户态转发），根本不经 TUN |

**图 7-2｜大 MTU 在 WSL2 镜像链路里的黑洞**（红色框为唯一卡点，上下蓝框分别是发包方与接管方；修复就是让卡点只驮小帧）：

诊断只要两条命令：WSL 里 `ip link show eth4` 看镜像网卡的现场 MTU（本案例实测 9000）；Windows 侧 `netsh interface ipv4 show subinterfaces` 核对 TUN 虚拟网卡（本例设备名为 CordC）。修复分两步——先在 WSL 里临时降下来验证，立即生效、不用重启任何东西：

```bash
sudo ip link set eth4 mtu 1400
```

推送恢复后，再用管理员权限的 PowerShell 固化到 Windows 网卡源头（`store=persistent` 重启不丢，WSL 的镜像值自动跟随，客户端更新配置也带不走它）：

```powershell
netsh interface ipv4 set subinterface "CordC" mtu=1400 store=persistent
```

两个防走弯路的提醒。其一，多数机场客户端的设置界面根本不给 MTU 输入框，直接往它的配置文件里手加 `mtu` 字段，也会在下次保存时被应用的数据模型丢掉——网卡层的 netsh 才是不依赖客户端配置的正道。其二，别把这条 MTU 和 7.5 模板里照搬的 `mtu = 1420` 混为一谈：那是 WireGuard 出站隧道内部的 MTU（3.2 教过的字段），这里是 TUN 虚拟网卡的 MTU——两层网卡各管一段，参数互不相干。6.2 的「小包通、大包断」与本案同病不同灶：那边是多跳隧道把有效 MTU 压低了，这边是虚拟化链路驮不动虚高的默认值。3.2 说过 MTU 是活的参数——服务端配的 1420 只保证隧道那一段，客户端 TUN 网卡与镜像链路这一段，得靠本节的命令自己兜底。

## 7.3 DNS 设置——内网域名的解析路径

「DNS」分组是第二个要动的开关。mihomo 内置 DNS 处理器，TUN 模式开启后系统 DNS 会被交给它。要让第六章 6.4 的内网域名（`nas-tunnel.home.lan`）能解析，把内部 DNS 服务器指过去：

- 在 DNS 设置的 nameserver 列表里**加入 `10.66.66.1`**（6.4 部署的 dnsmasq）；
- 保持公网 DNS（如 `1.1.1.1`）也在列表——mihomo 会按域名与规则决定用哪个服务器。

没有 6.4 的 dnsmasq 就跳过本节：只用公网 DNS，用 IP 直连内网服务即可。一个常见误区要提前拆掉：**fake-ip 模式**（mihomo 的默认 DNS 行为之一，给域名返回假的 198.18.x.x 地址以便规则匹配）可能与内网域名的解析预期冲突——如果你发现浏览器访问 `nas-tunnel.home.lan` 异常而 SSH 用 IP 直连正常，把内网域名加进 fake-ip 的排除列表，让它拿到 dnsmasq 返回的真实内网 IP：

```yaml
dns:
  fake-ip-filter:
    - "+.home.lan"     # +. 前缀表示匹配自身及所有子域名
```

排除后 `home.lan` 系列域名返回真实地址（10.66.66.1 或 192.168.1.x），后续连接就能被 `IP-CIDR` 规则正确接住。DNS 模块的完整字段不在本章展开，记住「nameserver 加 10.66.66.1 + 出问题查 fake-ip」两件事就够本章使用。

## 7.4 连接页——每条流量的判决书

「连接」分组打开的是 mihomo 最有用的调试视图：当前所有活跃连接，每条显示**目标地址、命中的规则、出口链路**。它就是 4.7 排障表的 GUI 版——不用敲 tcpdump 就能回答「这个连接到底走了哪条路」。

使用姿势：开着连接页，然后在终端里 SSH 一次 `10.66.66.1`，连接页里立即出现这条连接，读它的三列：

- 目标 `10.66.66.1:22`——确认是预期的目的地；
- 命中规则——7.6 配好之前它会是 `MATCH`（兜底规则）或 `DIRECT`，配好之后应该变成你写的 `IP-CIDR,10.66.66.0/24`；
- 出口链——配好之后显示 wireguard 节点名。

把这个观察过程做成一张「配置前后」的对照表，排障时照着核对：

| 观察项 | 配置规则前 | 配置规则后（期待） |
| ---- | ---- | ---- |
| SSH 10.66.66.1 的命中规则 | `MATCH,DIRECT` 或没有记录 | `IP-CIDR,10.66.66.0/24` |
| 同一条连接的出口链 | DIRECT（或连接根本不出现） | `phone-wg` |
| 连接页上行/下行计数 | 内网 SSH 建立后应有持续小流量 | 同左，且经 `phone-wg` |
| 浏览器访问公网网站 | 直连或系统代理，与隧道无关 | 仍直连（`MATCH,DIRECT` 兜底） |

连接页与 4.7 的抓包互为补充：GUI 看的是 mihomo **内部**的判决（规则层），tcpdump 看的是**网络**上的实际包（链路层）。排障时先用前者定位规则问题，再用后者定位链路问题——顺序别反。

## 7.5 自定义配置模板——把 WireGuard 节点写进去

进入本章核心。mihomo 的节点定义在 YAML 里，GUI 客户端通常提供「自定义配置模板/覆写」入口（CordC 设置里对应「自定义配置模板」项：自定义 DNS、规则、策略组，可添加自定义节点）。先在服务器上发放一台新设备——这里有个衔接第五章的好机会：手机已经用官方 App 占了 `10.66.66.3`，换成 mihomo 接入就用 5.4 的轮换（revoke 再同名 re-add）。注意地址分配规则：脚本按「最大值 + 1」发放，若你已按第六章加入 NAS（`.4`），phone 会拿到 `.5`；若还没加 NAS，则会重新拿到 `.3`——**以脚本打印的地址为准**，下面的 `ip:` 跟着改：

```text
$ wg-client-revoke.sh phone
设备 phone 已注销：Peer 摘除、内核同步、材料归档至 /etc/wireguard/clients/archive/
$ wg-client-add.sh phone
设备 phone 已发放：10.66.66.5
```

然后从新生成的 `/etc/wireguard/clients/phone.private` 与 `server_public.key` 取出两把钥匙，在客户端的配置模板里添加节点：

```yaml
proxies:
  - name: "phone-wg"
    type: wireguard
    server: 203.0.113.10        # 对应 wg0.conf 的 Endpoint
    port: 51820
    ip: 10.66.66.5              # 以 add 脚本输出为准（未加 NAS 时为 .3）；字段名是 ip
    private-key: "pH0n3..."     # phone.private 的内容（轮换后重新生成）
    public-key: "k5S+1x..."     # server_public.key 的内容（对端公钥）
    mtu: 1420
    udp: true
    persistent-keepalive: 25
```

把这份 YAML 与第四章 4.1 的 conf 并排读，字段一一对应：

| mihomo 字段 | wg0.conf 对应 | 说明 |
| ---- | ---- | ---- |
| server / port | Endpoint = 203.0.113.10:51820 | 拆成了两个字段 |
| ip | Address = 10.66.66.5/24 | **字段名是 `ip`**，不是 address——最常抄错的字段 |
| private-key | PrivateKey | 本机私钥 |
| public-key | [Peer] PublicKey | 对端（服务器）公钥，方向与 conf 相同 |
| mtu | MTU | 1420 照搬 |
| persistent-keepalive | PersistentKeepalive = 25 | 同义换名 |
| （无对应） | AllowedIPs | 见下方版本说明 |

> [!NOTE]
> 版本差异提醒：`allowed-ips` 字段需要较新的 mihomo 版本（v1.18.1 起），添加 `allowed-ips: ["10.66.66.0/24"]` 可限定该出站内部接受的目的网段；旧版本没有这个字段，**省略即可**——mihomo 会把命中规则的流量交给 wireguard 出站，行为等同。同样，新版还支持 `peers` 数组形式（多 Peer 站点互联），单服务器场景用上表的扁平写法最通用。字段名以你客户端实际内核版本为准，报错时先怀疑版本差异。

保存模板并重载配置后，「连接」或「代理」页里应出现 `phone-wg` 节点。手机端的 CordC 用同一份模板即可复用（导出/同步配置，或照抄一遍）——这正是 7.1 说的「一份配置多端复用」，比官方 App 的逐台导入更工程化。

私钥安全的提醒与 4.4 一脉相承：`private-key` 写进 GUI 配置，就等于落进了客户端的配置存储——设备丢失时，这份私钥就是一台合法的 VPN 身份（2.3 的 Noise_IK 只认密钥不认设备）。所以手机端用 mihomo 接入后，4.4 的纪律同样生效：设备丢失或淘汰，立即用 5.4 的 revoke 注销再重发，别指望「应该没人拿到」。

## 7.6 规则分流——只让内网走隧道

节点就位，现在告诉 mihomo**哪些流量交给它**。在配置模板的 rules 段添加（规则自上而下匹配，命中即停）：

```yaml
rules:
  - IP-CIDR,10.66.66.0/24,phone-wg,no-resolve
  - IP-CIDR,192.168.1.0/24,phone-wg,no-resolve
  - DOMAIN-SUFFIX,home.lan,phone-wg
  - MATCH,DIRECT
```

这四行的语义：目的地址在 VPN 网段或家里内网的流量走 `phone-wg` 出站（`no-resolve` 表示纯按 IP 匹配、不做域名解析）；`home.lan` 后缀的域名（6.4 的内网命名）同样交给隧道；其余一切流量 `DIRECT` 直连——**不经 mihomo 的任何代理，行为与没装它一样**。

规则的短路求值可以画成这样：

```text
SSH 10.66.66.1:22
   │  规则自上而下匹配
   ├─ IP-CIDR,10.66.66.0/24 ──▶ phone-wg
   ├─ IP-CIDR,192.168.1.0/24 ─▶ phone-wg
   ├─ DOMAIN-SUFFIX,home.lan ─▶ phone-wg
   └─ MATCH ─────────────────▶ DIRECT
```

这就是「先猜再读」第二问的答案：没写规则时，`MATCH` 兜底把 SSH 流量判给 DIRECT——流量根本不会进 wireguard 出站。mihomo 的分流不在网络层路由（那是 AllowedIPs 的事），而在**规则引擎**：先有规则把流量「判给」wireguard 出站，出站才有机会加密它。

四行规则里两个易被忽略的细节值得展开。其一，`no-resolve` 的作用是「这条 IP-CIDR 规则只按目的 IP 匹配，不要为了匹配而先把域名解析成 IP」——没有它，带域名的连接会先触发一次 DNS 解析，可能造成 DNS 泄漏（解析请求走了直连）或多余延迟；对内网场景尤其重要，因为内网域名要在隧道内解析（6.4 的 dnsmasq），不该在隧道外提前解析。其二，规则顺序就是优先级：`DOMAIN-SUFFIX,home.lan` 放在 IP 规则后面没有问题（域名规则在连接建立时先按域名匹配），但如果把 `MATCH` 兜底放到中间，后面的规则就永远不生效——规则列表是**短路求值**，从上到下第一条命中的说了算。两种工具、两个决策点，对照着记：

| 决策问题 | 官方客户端 | mihomo |
| ---- | ---- | ---- |
| 这个包走不走隧道？ | AllowedIPs（内核路由表） | rules 规则引擎（IP-CIDR 等） |
| 走隧道后交给谁？ | 虚拟网卡 → 加密 | wireguard 出站 → 加密 |
| 不走的流量呢？ | 物理网卡原路 | DIRECT 直连 |

写完规则重载配置，终端里再 SSH 一次 `10.66.66.1`——连接页里这条连接的命中规则应变为 `IP-CIDR,10.66.66.0/24`，出口链显示 `phone-wg`。如果系统代理没开 TUN，SSH 流量则根本不出现在连接页里——回到 7.2 把 TUN 打开，这就是两个开关的联动关系。

## 7.7 验证与轮换——闭环三连

接入完成的验证，服务器与客户端各看一眼：

| 检查点 | 位置 | 期待结果 |
| ---- | ---- | ---- |
| 新 Peer 握手 | 服务器 `wg show` | peer（phone 公钥）`latest handshake` 数秒前 |
| 规则命中 | 客户端连接页 | 内网连接命中 `IP-CIDR`、出口 `phone-wg` |
| 端到端连通 | 手机终端 `ping 10.66.66.1` | 通（TUN 开启时） |

「先猜再读」第三问的答案在此收尾：如果你把官方 App 的旧 conf 直接复制给 mihomo（两边都写 `10.66.66.3`），服务端就会出现两条指向 `10.66.66.3/32` 的 Peer——后登记的那条会接管该地址，先登记的收不到返回流量；两台客户端仍能各自握手，于是互相顶替、时通时断，正是 4.7 排障表的「地址重叠」行。所以本章开头用 5.4 的轮换先注销再发放，让服务端只保留一个身份；脚本按 max+1 分配新地址（已加 NAS 时为 `.5`），不要手工复制旧 conf——**一台设备在服务端永远只有一个有效身份**，这是多客户端形态共存的纪律。

到这里，本书的接入形态拼图完整了：第四章的官方客户端是「网络层接管」，本章的 mihomo 是「规则引擎调度」，两者接的是同一台服务器、同一本花名册。把本章特有的故障单独收一张排障表，与 4.7 互相引用：

| 症状 | 大概率原因 | 处置 |
| ---- | ---- | ---- |
| 连接页里 SSH 根本不出现 | TUN 未开，SSH 流量没进 mihomo | 回 7.2 开 TUN 并授权 |
| 命中规则是 MATCH/DIRECT | 规则没写、顺序不对或没重载配置 | 核对 7.6 规则顺序，保存后重载 |
| 命中规则正确但连不通 | wireguard 出站字段抄错（`ip` 误写 address 等） | 对照 7.5 字段表逐项核对 |
| 配置加载失败 | 附加规则引用了不存在的节点名（第八章 8.8 详述） | 节点名与模板保持一致 |
| 内网域名解析失败 | fake-ip 拦了 home.lan，或 nameserver 没指 dnsmasq | 按 7.3 加 fake-ip-filter 排除项 |
| 时通时断 | 复制旧 conf 导致同地址并存，互踢 | 走 5.4 的 revoke + re-add，一个身份一个客户端 |

下一章把 mihomo 客户端的设置项扫完——你在设置页里看到的每个开关，从此都有出处。

## 本章小结

- mihomo 是代理内核，本书只用它的 wireguard 出站能力；纯 VPN 需求官方客户端更省心；
- TUN 是 mihomo 等价于 VPN 客户端的前提：系统代理只接管浏览器类应用，SSH 进不了 mihomo；
- 内网域名解析靠 DNS 设置里加 `10.66.66.1`；浏览器访问内网异常时查 fake-ip 模式；
- 连接页是规则层的排障入口：目标、命中规则、出口链三列自查，网络层的包再看 tcpdump；
- wireguard 节点 YAML 与 wg0.conf 字段一一对应，最易抄错的字段是 `ip`（不是 address）；
- 旧内核版本没有 `allowed-ips` 字段，省略即可；报错先怀疑版本差异；
- 分流靠规则引擎而非路由：`IP-CIDR` 命中网段交给出站，`MATCH,DIRECT` 兜底直连——没写规则 SSH 就不会进隧道；
- 一台设备在服务端只能有一个身份：换客户端形态先 revoke 再 re-add，别手工复制旧 conf；否则两个客户端会争同一地址、互踢。
