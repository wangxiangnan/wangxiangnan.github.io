# 第1章：Docker是什么？—— 为什么全世界都在容器化

## 引言：程序员的终极噩梦

每个程序员都经历过这样的场景：

> "这代码在我电脑上明明能跑啊！怎么到你那儿就炸了？"

你写了三天三夜的 Node.js 服务，本地跑得好好的，一部署到服务器——`npm install` 报错、Python 版本不对、系统库缺失……那一刻，你开始怀疑人生。

Docker 就是来解决这个"千古难题"的。它把你的应用连同它所需的一切（运行环境、系统工具、依赖库、配置文件）打包成一个标准化的"集装箱"，丢到任何机器上都能一模一样地运行。

如果说传统部署是"把零件散着运过去，到现场再组装调试"，那 Docker 就是"在工厂里装好，到现场插电即用"。

## 1.1 容器 vs 虚拟机：合租公寓 vs 独栋别墅

要理解容器，我们先看看它的"老大哥"——虚拟机（VM）。

**虚拟机 = 独栋别墅**

虚拟机就像在你家后院盖了一栋完整的别墅：有自己的地基（虚拟硬件）、水电系统（Guest OS）、装修（应用和依赖）。虽然功能完整，但盖一栋别墅需要大量资源（几个 GB 的磁盘、几个 GB 的内存），启动还要好几分钟。

**容器 = 合租公寓**

容器则像合租公寓：大家共用地基和水电（共享宿主机的操作系统内核），但每个房间（容器）是独立的，有自己的门锁和空间。启动几秒钟搞定，资源占用只有 MB 级别。

用代码来类比就更直观了：

```javascript
// 虚拟机的方式 —— 每个应用都搞一套完整环境
const vm = {
  hardware: '虚拟的 CPU、内存、磁盘',    // 虚拟硬件层
  guestOS: '完整的 Linux/Windows',        // 完整的客户操作系统
  runtime: 'Node.js 18.x',               // 运行时
  app: '你的 Express 应用',               // 应用代码
  size: '~5GB',                           // 体积巨大
  bootTime: '~2分钟'                      // 启动慢
};

// 容器的"合租"方式 —— 共享内核，轻量隔离
const container = {
  hostKernel: '共享宿主机的 Linux 内核',   // 不需要虚拟硬件和 Guest OS
  runtime: 'Node.js 18.x',               // 运行时
  app: '你的 Express 应用',               // 应用代码
  size: '~200MB',                         // 体积小巧
  bootTime: '~1秒'                        // 秒启动
};
```

对比总结表：

| 特性 | 虚拟机 | 容器 |
|------|--------|------|
| 隔离级别 | 硬件级（完全隔离） | 进程级（共享内核） |
| 启动速度 | 分钟级 | 秒级 |
| 资源占用 | GB 级 | MB 级 |
| 镜像大小 | 几个 GB | 几十到几百 MB |
| 运行密度 | 一台机器跑几个 VM | 一台机器跑几十个容器 |
| 安全性 | 更强（完全隔离） | 较弱（共享内核） |
| 适用场景 | 需要不同 OS、强隔离 | 微服务、CI/CD、快速部署 |

## 1.2 Docker 的架构

Docker 采用客户端-服务端（Client-Server）架构，就像你用手机 App（客户端）跟服务器（服务端）通信一样：

```bash
┌──────────────────────────────────────────────────┐
│                 Docker 架构                       │
│                                                   │
│  ┌─────────┐    REST API    ┌──────────────────┐ │
│  │ Docker  │ ──────────────→│  Docker Engine   │ │
│  │ Client  │                │  (dockerd 守护进程)│ │
│  │ (CLI)   │ ←──────────────│                  │ │
│  └─────────┘                └───────┬──────────┘ │
│                                     │            │
│                    ┌────────────────┼──────────┐ │
│                    │                │          │ │
│              ┌─────▼─────┐  ┌──────▼────┐     │ │
│              │ Container │  │ Container │ ...  │ │
│              │  (运行中)  │  │  (运行中)  │     │ │
│              └─────┬─────┘  └──────┬────┘     │ │
│                    │                │          │ │
│              ┌─────▼─────┐  ┌──────▼────┐     │ │
│              │  Image    │  │  Image    │     │ │
│              │ (只读模板) │  │ (只读模板) │     │ │
│              └───────────┘  └───────────┘     │ │
│                                                   │
│  ┌──────────────────────────────────────────┐    │
│  │          Registry（镜像仓库）              │    │
│  │  Docker Hub / 阿里云 / 私有仓库           │    │
│  └──────────────────────────────────────────┘    │
└──────────────────────────────────────────────────┘
```

四个核心概念：

**1. 镜像（Image）—— 应用的"类"**

镜像就像一个面向对象编程中的"类"（Class）。它定义了应用运行所需的一切：操作系统层、运行时、依赖、应用代码。镜像是只读的，你不能直接修改一个镜像。

```python
# 镜像就像 Python 中的类
class NodeApp:          # ← 这就是"镜像"
    os_layer = "Alpine Linux"
    runtime = "Node.js 18"
    dependencies = "express, mongoose, ..."
    code = "app.js, routes/, ..."
    
    def run(self):
        # 启动应用
        pass

# 容器就是类的实例
container1 = NodeApp()  # ← 这就是"容器"（实例1）
container2 = NodeApp()  # ← 另一个容器（实例2）
```

**2. 容器（Container）—— 镜像的"实例"**

容器是镜像运行起来的实例，就像 Class 创建出来的 Object。一个镜像可以运行出多个容器。容器有自己的可写层，但删除容器后这些修改就消失了（除非你用数据卷持久化）。

**3. 仓库（Registry）—— 镜像的"应用商店"**

Docker Hub 就是 Docker 世界的"App Store"。你可以从上面拉取（pull）别人做好的镜像，也可以推送（push）自己的镜像上去。除了 Docker Hub，还有阿里云容器镜像服务、GitHub Container Registry、自建私有仓库等。

**4. Docker Engine —— 幕后的"管家"**

Docker Engine（`dockerd` 守护进程）是真正干活的。它负责管理镜像、运行容器、构建镜像、处理网络和数据卷。你用 `docker` 命令行工具（Client）发号施令，Engine 在后台默默执行。

## 1.3 Docker 解决的核心问题

回到开头那个经典问题——"在我电脑上能跑啊！"

这个问题的根源是**环境不一致**。你的电脑有 Node.js 18，服务器装的是 Node.js 14；你用的是 macOS，服务器是 Ubuntu；你本地装了某个全局 npm 包，服务器上没装……

Docker 的解决方案：**把环境一起打包**。

```bash
# 不用 Docker 的部署方式（痛苦模式）
# 1. 在服务器上安装 Node.js（可能版本不对）
# 2. clone 代码
# 3. npm install（可能某个包编译失败）
# 4. 安装系统依赖（不同 Linux 发行版命令还不一样）
# 5. 配置环境变量
# 6. 祈祷它能跑起来

# 用 Docker 的部署方式（快乐模式）
docker pull myapp:latest    # 拉取打包好的镜像
docker run -d -p 3000:3000 myapp:latest  # 跑起来，完事
```

Docker 还解决了这些痛点：

- **环境一致性**：开发、测试、生产环境完全一致
- **快速扩缩容**：启动一个容器只要几秒，不是几分钟
- **版本管理**：镜像有标签（tag），可以随时回滚
- **资源隔离**：不同应用之间互不影响
- **CI/CD 友好**：构建一次，到处运行

## 1.4 Docker 的历史和生态简介

Docker 的故事始于 2013 年：

| 年份 | 事件 |
|------|------|
| 2013 | Solomon Hykes 在 PyCon 上演示 Docker，轰动全场 |
| 2013 | Docker 开源，迅速走红 GitHub |
| 2014 | Docker 1.0 发布，标志生产就绪 |
| 2016 | Docker 引入 Swarm Mode 内置集群编排 |
| 2017 | Docker 分为 CE（社区版）和 EE（企业版） |
| 2017 | Moby 项目诞生，Docker 的上游开源项目 |
| 2019 | Docker 企业版卖给 Mirantis |
| 2020 | Docker Desktop 对大企业开始收费 |
| 2022+ | Docker 继续迭代，BuildKit 成为默认构建引擎 |

**Docker 生态圈**：

- **Docker Compose**：用 YAML 文件定义和运行多容器应用
- **Docker Swarm**：Docker 原生的集群管理工具
- **Docker Machine**：在远程主机上安装 Docker（已被 cloud-init 等替代）
- **Kubernetes**：Google 开源的容器编排平台，已成为行业标准
- **containerd / runc**：Docker 底层的容器运行时，现在已独立发展

## 1.5 什么时候该用 Docker，什么时候不用

**该用 Docker 的场景**：

- 微服务架构（每个服务一个容器，独立部署）
- CI/CD 流水线（构建、测试、部署全流程容器化）
- 开发环境标准化（新人入职，`docker-compose up` 一键启动全部服务）
- 多环境部署（开发/测试/生产用同一镜像，只是配置不同）
- 需要快速扩缩容的 Web 应用
- 运行第三方服务（不想在本机装一堆数据库）

**不太适合 Docker 的场景**：

- 对性能要求极高的应用（如实时高频交易系统）——容器有一点额外开销
- 需要图形界面的桌面应用（虽然有 X11 转发方案，但很折腾）
- 单体巨石应用且团队完全没有容器经验——先从小范围试点开始
- 只需要运行一个简单静态网站——用 Nginx 直接部署更省事

> **Tip:** 如果你的团队还在犹豫要不要上 Docker，最好的切入点是"开发环境标准化"。让新同事能在 10 分钟内把整个项目跑起来，这一个好处就够说服老板了。

> **Warning:** 不要试图把所有东西都塞进一个容器里。Docker 的设计哲学是"一个容器一个进程"。如果你发现自己在容器里跑 supervisor 来管理 Nginx + Node.js + Redis，那说明你需要的是 Docker Compose，不是一个"超级容器"。

## 本章小结

- Docker 通过容器化技术解决了"在我电脑上能跑"的环境一致性问题
- 容器 vs 虚拟机 = 合租公寓 vs 独栋别墅：共享内核 vs 独立系统
- Docker 的四大核心：镜像（类/模板）、容器（实例）、仓库（应用商店）、Engine（管家）
- Docker 适合微服务、CI/CD、环境标准化等场景
