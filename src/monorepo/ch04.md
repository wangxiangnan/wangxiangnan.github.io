# Ch04: 依赖管理深入

## 本章目标

- 深入理解 `workspace:` 协议的各种用法和适用场

## 4.1 workspace 协议详解

在 Ch03 中，你已经看到了 `workspace:*` 的用法。pnpm 提供了多种 workspace 协议变体，每种有不同的语义。

### workspace:\*（最常用）

```json
{
  "dependencies": {
    "@taskflow/shared": "workspace:*"
  }
}
```

含义：**始终使用 workspace 中的本地版本**，无论它的版本号是什么。

这是最常用的写法，适用于你控制的内部包。当 `@taskflow/shared` 的版本从 `0.0.0` 升到 `1.0.0`，你不需要修改任何引用方。

### workspace:^ 和 workspace:~

```json
{
  "dependencies": {
    "@taskflow/shared": "workspace:^0.0.0"
  }
}
```

含义：使用 workspace 中的本地版本，但**当发布到 npm 时**，版本号会被替换为 `^0.0.0`。

这在你打算将包发布到 npm 时非常有用。在开发和发布两种场景下，版本约束行为不同：

| 场景 | `workspace:*` | `workspace:^0.0.0` |
| ------ | --------------- | ------------------- |
| 本地开发 | 使用本地版本 | 使用本地版本（需版本兼容） |
| 发布到 npm | 保留 `workspace:*`（会导致安装失败） | 替换为 `^0.0.0` |

> **什么时候用 `workspace:*`，什么时候用 `workspace:^`？** 如果你的包只用于内部、不会发布到 npm，用 `workspace:*` 最省事。如果你计划发布某些包（比如开源 `@taskflow/shared`），用 `workspace:^` 更安全。

### pnpm 发布时的版本替换

当你执行 `pnpm publish` 时，pnpm 会自动将 `workspace:` 协议替换为真实版本号：

```json
// 开发时的 package.json
{
  "dependencies": {
    "@taskflow/shared": "workspace:^0.0.0"
  }
}

// 发布后的 package.json（npm registry 上看到的）
{
  "dependencies": {
    "@taskflow/shared": "^0.0.0"
  }
}
```

如果你用的是 `workspace:*`，发布时会替换为确切的版本号：

```json
// workspace:* → "0.0.0"（精确版本）
```

### 强制使用 workspace 版本

如果你希望某个依赖**只能**从 workspace 解析，不允许从 registry 安装，可以在 `.npmrc` 中设置：

```ini
link-workspace-packages=true
```

这确保了即使你的版本范围与 registry 上的版本匹配，pnpm 也会优先使用 workspace 版本。

## 4.2 Hoisting 策略：pnpm vs npm/yarn

这是理解 pnpm 核心价值的关键章节。

### npm/yarn 的扁平化（Hoisting）

当你用 npm 安装依赖时，它会把所有依赖（包括传递依赖）**提升到根目录的 `node_modules/`** 中：

```
node_modules/
├── express/          # 你的直接依赖
├── accepts/          # express 的依赖（被提升）
├── mime-types/       # accepts 的依赖（被提升）
├── lodash/           # 某个包的依赖（被提升）
└── ... 几百个包全部平铺
```

这意味着：**即使你没有在 `package.json` 中声明 `lodash`，你的代码也能 `import lodash`**——因为 `lodash` 被提升到了你可以访问的 `node_modules/` 中。

这就是 **Phantom Dependency（幽灵依赖）** 问题。

### pnpm 的严格隔离

pnpm 采用了完全不同的策略。每个包的 `node_modules/` 只包含**它自己声明的依赖**，通过符号链接指向一个 `.pnpm` 目录中的真实内容：

```
node_modules/
├── .pnpm/                      # 真实包存放处（硬链接到全局 store）
│   ├── express@4.21.0/
│   │   └── node_modules/
│   │       ├── express/        # 真实文件
│   │       ├── accepts/        # express 的依赖
│   │       └── ...
│   └── ...
├── express -> .pnpm/express@4.21.0/node_modules/express   # 符号链接
└── @taskflow -> (workspace 包的符号链接)
```

在这个结构下：

- 你的代码只能 `import` 你在 `package.json` 中声明的依赖
- 传递依赖被隔离在 `.pnpm/` 中，你的代码无法直接访问
- 如果 `express` 内部依赖 `accepts`，`accepts` 只在 `express` 的 `node_modules/` 中可见

> **为什么这很重要？** 在 monorepo 中，严格的依赖隔离可以防止以下问题：
>
> 1. **隐式依赖**：包 A 没有声明依赖 `lodash`，但因为另一个包 B 依赖了 `lodash`（被 hoist 到根 `node_modules/`），包 A 的代码能跑。但当包 A 被单独使用或发布时，会因为缺少 `lodash` 而崩溃。
> 2. **版本冲突**：包 A 需要 `lodash@4`，包 B 需要 `lodash@3`。在 npm 的 hoisting 下，只有一个版本能被提升到根目录，另一个被嵌套——但你的代码可能意外引用了错误的版本。
> 3. **不可重复的构建**：hoisting 的结果取决于安装顺序和完整的依赖树。换一个环境重新安装，可能得到不同的目录结构。

### 对比总结

| 特性 | npm/yarn（hoisting） | pnpm（strict） |
| ------ | --------------------- | ---------------- |
| node_modules 结构 | 扁平化，所有包平铺 | 隔离，只有直接依赖可见 |
| 未声明的依赖 | 可以访问（phantom） | 无法访问（报错） |
| 磁盘使用 | 每个项目一份完整拷贝 | 全局 store + 硬链接 |
| 安装速度 | 基准 | 2-3x 更快 |
| 正确性保证 | 弱（隐式依赖） | 强（显式声明） |

### 如果某些包依赖 hoisting 怎么办？

有些老包（特别是某些 Webpack 插件、Babel 预设）假设依赖被 hoist 到根 `node_modules/`。在这种情况下，你可以在 `.npmrc` 中使用：

```ini
# 将所有依赖提升到根 node_modules（模拟 npm 行为）
shamefully-hoist=true

# 或者只提升特定的包
public-hoist-pattern[]=*eslint*
public-hoist-pattern[]=*typescript*
```

> **建议：** 尽量保持 `shamefully-hoist=false`（pnpm 默认值）。如果某个包需要 hoisting，优先修复那个包的依赖声明，而不是全局开启 hoisting。

## 4.3 Phantom Dependencies 问题详解

让我们通过一个具体的例子来深入理解这个问题。

### 场景复现

假设 `apps/api` 的 `package.json` 如下：

```json
{
  "name": "@taskflow/api",
  "dependencies": {
    "express": "^4.21.0"
  }
}
```

你在 `apps/api/src/index.ts` 中写了：

```typescript
import express from "express";
import cookieParser from "cookie-parser"; // ← 问题在这里
```

`cookie-parser` 并不是 `@taskflow/api` 的依赖。但假设 `express` 的某个传递依赖恰好也安装了 `cookie-parser`。

**在 npm/yarn 中**：由于 hoisting，`cookie-parser` 可能被提升到了根 `node_modules/`，你的代码**碰巧能运行**。但这是错的——你没有声明这个依赖。

**在 pnpm（strict 模式）中**：`import cookieParser from "cookie-parser"` 会直接报错：

```
Error: Cannot find module 'cookie-parser'
```

**这正是你想要的行为。** 它在开发阶段就暴露了问题，而不是等到发布后才发现。

### 修复方法

把缺失的依赖加到 `package.json` 中：

```json
{
  "name": "@taskflow/api",
  "dependencies": {
    "express": "^4.21.0",
    "cookie-parser": "^1.4.7"    // ← 显式声明
  }
}
```

然后重新安装：

```bash
pnpm install
```

### 如何检测已有的 Phantom Dependencies

如果你的项目是从 npm/yarn 迁移过来的，可能已经存在大量隐式依赖。可以用以下方法检测：

```bash
# pnpm 的严格模式本身就会在运行时报错
# 你也可以用 eslint 插件来静态检查
pnpm add -D eslint-plugin-import
```

在 ESLint 配置中启用 `import/no-extraneous-dependencies` 规则：

```js
{
  rules: {
    "import/no-extraneous-dependencies": "error"
  }
}
```

这会在 lint 阶段就标记出所有使用了但未在 `package.json` 中声明的依赖。

## 4.4 根目录依赖 vs 包级依赖

在 monorepo 中，一个常见的困惑是：**这个依赖应该放在根目录还是各个包里？**

### 规则一：开发工具放根目录

所有包共用的开发工具应该放在根目录的 `devDependencies` 中：

```json
// 根目录 package.json
{
  "devDependencies": {
    "prettier": "^3.4.2",        // 全局代码格式化
    "turbo": "^2.3.3",           // 构建编排
    "typescript": "^5.7.0"       // 也可以放根目录（如果所有包用同一版本）
  }
}
```

**为什么？** 因为这些工具在项目中只有一份配置、一个版本。你不需要每个包都安装一份 Prettier。

### 规则二：构建工具看情况

如果所有包使用相同版本的 TypeScript，可以放根目录。如果某些包需要不同版本，放在各自的 `devDependencies` 中：

```json
// packages/shared/package.json
{
  "devDependencies": {
    "typescript": "^5.7.0"
  }
}
```

> **实践中**：绝大多数情况下 TypeScript 版本应该统一，所以推荐放在根目录。但在本教程中，为了展示 pnpm workspace 的工作方式，我们把它也放在了各包的 `devDependencies` 中。

### 规则三：运行时依赖放包里

应用和共享包的运行时依赖**必须**放在各自的 `dependencies` 中：

```json
// apps/api/package.json
{
  "dependencies": {
    "express": "^4.21.0",        // API 的运行时依赖
    "cors": "^2.8.5"
  }
}

// packages/shared/package.json
{
  "dependencies": {
    "zod": "^3.24.0"             // shared 包的运行时依赖
  }
}
```

**为什么？** 因为当这个包被发布到 npm 并被外部安装时，`dependencies` 中的包会被自动安装，而根目录的依赖不会。

### 规则四：peerDependencies 的使用

当一个包期望使用方提供某个依赖时，用 `peerDependencies`：

```json
// packages/eslint-config/package.json
{
  "peerDependencies": {
    "eslint": "^9.0.0"
  }
}
```

这告诉使用方："我的配置需要 ESLint 9，请你自己安装它。" 这避免了同一个包被安装多份的问题。

### 总结表

| 依赖类型 | 位置 | 示例 |
| --------- | ------ | ------ |
| 全局开发工具 | 根目录 `devDependencies` | prettier, turbo |
| 通用构建工具 | 根目录或包级 `devDependencies` | typescript |
| 包级开发工具 | 包级 `devDependencies` | eslint（如果各包版本不同） |
| 运行时依赖 | 包级 `dependencies` | express, vue, zod |
| 内部包引用 | 包级 `dependencies` + `workspace:*` | @taskflow/shared |
| 期望使用方提供的 | 包级 `peerDependencies` | eslint（对配置包来说） |

## 4.5 依赖版本锁定策略：pnpm Catalog

pnpm 9 引入了一个强大的新功能：**Catalog（目录）**，用于在 monorepo 中统一管理依赖版本。

### 问题：版本分散

在 monorepo 中，多个包可能依赖同一个外部包：

```json
// packages/shared/package.json
{ "dependencies": { "zod": "^3.24.0" } }

// apps/api/package.json
{ "dependencies": { "zod": "^3.24.0" } }

// apps/web/package.json
{ "dependencies": { "zod": "^3.23.0" } }  // ← 版本不一致！
```

这种不一致会导致难以排查的 bug——`shared` 中用 zod 定义的 schema 在 `web` 中可能因为版本差异而行为不同。

### 传统解决方案

在 pnpm 9 之前，通常的做法是在根目录 `package.json` 中用一个注释字段来记录推荐版本：

```json
{
  "// dependencies comment": {
    "zod": "^3.24.0",
    "typescript": "^5.7.0"
  }
}
```

这显然不优雅——它只是一个"文档"，没有强制力。

### pnpm Catalog 解决方案

在 `pnpm-workspace.yaml` 中定义 catalog：

```yaml
packages:
  - "apps/*"
  - "packages/*"

catalog:
  zod: ^3.24.0
  typescript: ^5.7.0
  eslint: ^9.16.0
  "@types/node": ^22.10.0

catalogs:
  vue:
    vue: ^3.5.13
    "vue-router": ^4.5.0
    "vue-tsc": ^2.2.0
    "@vitejs/plugin-vue": ^5.2.0
  express:
    express: ^4.21.0
    cors: ^2.8.5
    "@types/express": ^5.0.0
    "@types/cors": ^2.8.17
```

然后在各包的 `package.json` 中用 `catalog:` 协议引用：

```json
// packages/shared/package.json
{
  "dependencies": {
    "zod": "catalog:"
  },
  "devDependencies": {
    "typescript": "catalog:"
  }
}

// apps/web/package.json
{
  "dependencies": {
    "vue": "catalog:vue",
    "vue-router": "catalog:vue"
  },
  "devDependencies": {
    "typescript": "catalog:",
    "@vitejs/plugin-vue": "catalog:vue",
    "vue-tsc": "catalog:vue"
  }
}

// apps/api/package.json
{
  "dependencies": {
    "express": "catalog:express",
    "cors": "catalog:express"
  },
  "devDependencies": {
    "typescript": "catalog:",
    "@types/express": "catalog:express",
    "@types/cors": "catalog:express"
  }
}
```

**Catalog 的工作方式：**

- `"catalog:"` 引用默认 catalog（`catalog:` 字段中定义的）
- `"catalog:vue"` 引用名为 `vue` 的 catalog（`catalogs.vue` 中定义的）
- pnpm 会在 `pnpm install` 时将 `catalog:` 解析为实际版本号
- 如果版本不在 catalog 中定义，pnpm 会报错

> **为什么要分多个 catalog？** 因为不同技术栈的依赖通常独立演进。Vue 生态的依赖（vue、vue-router、vue-tsc）放在一起，Express 生态的放在一起，通用工具（typescript、zod）放在默认 catalog。这样当你需要升级 Vue 版本时，只需修改一处。

### 实际效果

修改 `pnpm-workspace.yaml` 中的 `zod: ^3.24.0` 为 `zod: ^3.25.0`，然后执行 `pnpm install`，所有引用 `zod: "catalog:"` 的包会同时更新到 `^3.25.0`。

```bash
# 更新 catalog 后重新安装
pnpm install

# 验证所有包的 zod 版本一致
pnpm why zod
```

## 4.6 实际代码示例：workspace 引用的完整流程

让我们通过一个完整的例子来串联本章所有概念。

### 场景：在 shared 中添加一个新的工具函数，并在 api 和 web 中使用

**第一步：在 shared 中添加新功能**

编辑 `packages/shared/src/utils/index.ts`，添加一个 slug 生成函数：

```typescript
// packages/shared/src/utils/index.ts

// ... 已有代码 ...

/**
 * 将字符串转换为 URL-safe 的 slug
 */
export function slugify(text: string): string {
  return text
    .toLowerCase()
    .trim()
    .replace(/[^\w\s-]/g, "")
    .replace(/[\s_-]+/g, "-")
    .replace(/^-+|-+$/g, "");
}
```

**第二步：构建 shared 包**

```bash
pnpm --filter @taskflow/shared build
```

这会将 TypeScript 编译为 JavaScript 并生成 `.d.ts` 声明文件到 `packages/shared/dist/` 目录。

> **为什么需要 build？** 因为其他包引用的是 `dist/` 中的编译产物，不是 `src/` 中的 TypeScript 源码。这在 `package.json` 的 `exports` 字段中已经配置好了。

**第三步：在 api 中使用**

编辑 `apps/api/src/index.ts`：

```typescript
import cors from "cors";
import express from "express";

import {
  TaskStatus,
  getStatusLabel,
  slugify,                    // ← 新导入
} from "@taskflow/shared";

const app = express();
const PORT = process.env.PORT || 3001;

app.use(cors());
app.use(express.json());

// 健康检查接口
app.get("/api/health", (_req, res) => {
  res.json({
    status: "ok",
    timestamp: new Date().toISOString(),
  });
});

// 任务状态列表接口
app.get("/api/task-statuses", (_req, res) => {
  const statuses = Object.values(TaskStatus).map((status) => ({
    value: status,
    label: getStatusLabel(status),
  }));
  res.json(statuses);
});

// 新增：slug 生成接口
app.post("/api/slug", (req, res) => {
  const { text } = req.body as { text: string };
  if (!text) {
    res.status(400).json({ error: "text is required" });
    return;
  }
  res.json({ slug: slugify(text) });
});

app.listen(PORT, () => {
  console.log(`[API] Server running on http://localhost:${PORT}`);
});

export default app;
```

**第四步：验证引用关系**

查看 api 包对 shared 的依赖解析：

```bash
pnpm --filter @taskflow/api ls --depth 0
```

输出：

```
@taskflow/api@0.0.0
├── @taskflow/eslint-config@0.0.0 -> workspace package
├── @taskflow/shared@0.0.0 -> workspace package
├── @taskflow/tsconfig@0.0.0 -> workspace package
├── cors@2.8.5
├── express@4.21.0
└── ...
```

注意 `-> workspace package` 标记——这说明 pnpm 正确地将 `@taskflow/shared` 解析为本地 workspace 包，而非从 registry 下载。

**第五步：验证实时同步**

这就是 workspace 引用的魔力：**当你在 shared 中修改代码并重新 build 后，api 和 web 立即就能使用新的代码，不需要任何版本号更新或重新安装。**

```bash
# 1. 修改 shared
# (代码已在第一步中修改)

# 2. 重新构建 shared
pnpm --filter @taskflow/shared build

# 3. 启动 api 开发服务器
pnpm --filter @taskflow/api dev

# 4. 测试新接口
curl -X POST http://localhost:3001/api/slug \
  -H "Content-Type: application/json" \
  -d '{"text": "Hello Monorepo World"}'
# 输出: {"slug":"hello-monorepo-world"}
```

**第六步：使用 Turborepo 自动化构建顺序**

手动按顺序 build 很麻烦。让 Turborepo 来做：

```bash
turbo run build
```

Turborepo 会分析依赖图：

1. 先构建 `@taskflow/shared`（它没有内部依赖）
2. 然后并行构建 `@taskflow/api` 和 `@taskflow/web`（它们都依赖 shared，但彼此无关）

输出类似：

```
• Tasks:    3 successful, 3 total
• Cached:   0 cached, 3 total
• Time:     2.3s
```

第二次运行（没有修改任何文件）：

```bash
turbo run build
```

```
• Tasks:    3 successful, 3 total
• Cached:   3 cached, 3 total    ← 全部命中缓存！
• Time:     150ms >>> Full Turbo
```

**这就是 Turborepo 的核心价值**：基于文件内容哈希的缓存，让重复构建几乎瞬间完成。

## 4.7 依赖管理常见陷阱

### 陷阱一：忘记 build shared 就开始开发

如果你修改了 `packages/shared/src/` 中的代码但没有执行 build，`apps/web` 和 `apps/api` 引用的仍然是旧的编译产物。

**解决方案**：使用 `tsc --build --watch` 让 shared 包自动重新编译：

```bash
# 在 shared 目录下
pnpm --filter @taskflow/shared dev
```

或者使用 Turborepo 的 `dev` 任务来同时启动所有包的开发模式。

### 陷阱二：循环依赖

```
@taskflow/shared → @taskflow/utils → @taskflow/shared  ← 循环！
```

pnpm 会在安装时检测并报错。**永远不要让包之间形成循环依赖**。如果出现这种情况，说明你的包划分有问题，需要重新设计。

### 陷阱三：忘记添加 `"private": true`

如果根目录或某个不应发布的包忘记加 `"private": true`，有人可能不小心执行 `pnpm publish`，将内部代码发布到 npm。

### 陷阱四：Catalog 中版本范围不兼容

如果你在 catalog 中定义了 `typescript: ^5.7.0`，但某个包需要 `typescript: ^4.0.0`，不要把它放入 catalog——直接在包的 `devDependencies` 中指定确切版本。Catalog 只适合**所有包使用相同版本范围**的依赖。

## 4.9 依赖解析流程图

为了帮助理解 pnpm workspace 的依赖解析过程，以下是当你执行 `pnpm install` 时发生的事情：

```
pnpm install
    │
    ├── 1. 读取 pnpm-workspace.yaml
    │   识别所有 workspace 包的位置
    │
    ├── 2. 读取所有包的 package.json
    │   收集所有依赖声明
    │
    ├── 3. 解析 workspace: 协议
    │   @taskflow/shared → packages/shared/（本地路径）
    │   @taskflow/tsconfig → packages/tsconfig/（本地路径）
    │
    ├── 4. 解析 catalog: 协议
    │   zod: "catalog:" → ^3.24.0
    │   typescript: "catalog:" → ^5.7.0
    │   vue: "catalog:vue" → ^3.5.13
    │
    ├── 5. 从 registry 下载外部依赖
    │   存入全局 store（~/.pnpm-store/）
    │
    ├── 6. 创建硬链接和符号链接
    │   全局 store ──硬链接──► .pnpm/ 目录
    │   .pnpm/ ──符号链接──► 各包的 node_modules/
    │
    └── 7. 生成 pnpm-lock.yaml
        锁定所有依赖的精确版本
```

## 本章小结

- **`workspace:*`** 是 monorepo 内部引用的标准方式，表示"使用本地版本，不限版本范围"
- **`workspace:^`** 适用于需要发布到 npm 的包，发布时会自动替换为真实版本范围
- **pnpm 的严格隔离**防止了 phantom dependency 问题——未声明的依赖不会被意外访问
- **根目录依赖**用于全局共享的开发工具，**包级依赖**用于各包特有的运行时需求
- **Catalog 功能**（pnpm 9+）通过 `pnpm-workspace.yaml` 统一管理依赖版本，一处修改、全局生效
- 修改共享包后必须重新 build，或者使用 `--watch` 模式自动编译
