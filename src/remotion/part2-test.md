# Part 2 自测

本卷覆盖 Part 2 的两章：音画同步（时间戳如何驱动画面）、三个出口（Studio、render、Player 怎么共用一份组件）。玩法：闭卷——合上书从第 1 题做到最后，全部做完再逐题打开 `<details>` 对答案；每题答案带一句推导与回指小节，答错的按回指重读该章「本章小结」的要点，隔 1 天重做错题。

## 题目

**T1**：贯穿示例的音频是 8.81 秒，尾帧留 0.6 秒，总帧数是多少？用哪个公式算出来的？

<details>
<summary>答案</summary>

**283 帧**，公式是 `ceil((8.81 + 0.6) × 30) = ceil(282.3) = 283`（fps = 30）。

推导：总帧数由「音频时长 + 尾帧」决定，尾帧是 `getDurationInFrames` 里的一个常量（`TAIL`）——改它等于改总帧数，这是「帧数推算只允许一份实现」的含义。回指：3.3、3.4。
</details>

**T2**：句二起点 5.175 秒比句一终点 5.225 秒**早**了 50 毫秒。这段重叠会让场景时长算出负数吗？正确的处理是什么？

<details>
<summary>答案</summary>

不会算出负数，但必须显式处理：场景划分有一条铁律——**每个场景的起点不得早于前一个场景的起点**（单调钳制），重叠的 50 毫秒按「先到先得」归前一个场景。句二的原始起帧 155 因此被修正为 157。

推导：脏数据不会自己消失，钳制规则必须写在场景划分里；不钳制时误差会沿场景链累积成负时长。回指：3.4。
</details>

**T3**：转场是「额外占用时间」还是「与相邻场景重叠」？加了两段 15 帧转场之后，三个场景的 duration 之和是 283 还是 313？总帧数又是多少？

<details>
<summary>答案</summary>

转场是**重叠**：前一个场景淡出的那 15 帧，恰好是后一个场景淡入的 15 帧。三个场景的 duration 之和是 172 + 121 + 20 = **313**（每个 duration 里已经预加了 15 帧转场），总帧数 = 313 − 2×15 = **283**。

推导：正因如此，`duration = 下一场景名义起点 − 本场景名义起点 + TRANSITION_FRAMES` 这个公式才能让场景的实际显示起点落在名义起点上（157、263）。回指：3.5。
</details>

**T4**：字幕为什么不能放进场景里，而要挂在根组件上？

<details>
<summary>答案</summary>

因为转场进行时旧场景淡出、新场景淡入，字幕必须**纹丝不动**地高亮到正确的词——放进场景就会随场景一起被转场吃掉。而 `useCurrentFrame()` 在 Sequence 内部返回的是**局部帧号**，挂在根级才拿得到全局的 `t`。

推导：场景内的帧号从 0 重新计数，同一句话在场景内的局部时间与全局时间不一致，高亮就会错位。回指：3.6。
</details>

**T5**：转场的 duration 能不能超过相邻场景的 duration？23 帧的转场撞上 20 帧的结尾卡有哪两条处置路线？

<details>
<summary>答案</summary>

不能——TransitionSeries 规定「转场不得长于相邻任一场景」，超了直接报错。两条处置：①**给结尾卡腾地方**：尾帧从 0.6 秒改 0.7 秒，`ceil((8.81+0.7)×30) = 286`，结尾卡 = 286 − 263 = 23 帧，正好容纳；②**缩短弹簧**：调大 damping 让弹簧更快停住，实测帧数随之变短。

推导：结尾卡只有 20 帧是总帧数算出来的结果，要给它腾地方就得改总帧数——改 `TAIL` 常量一处，所有引用它的地方自动跟着变。回指：3.5、8.2。
</details>

**T6**：三个出口分别是什么命令、产出什么？它们共用什么？

<details>
<summary>答案</summary>

Studio（`npx remotion studio`）不产出文件、只做开发期预览；render（`npx remotion render`）产出 `out/video.mp4`；Player 是挂在自家 React 网页里的播放器、不产出文件、在网页内播放。三者共用**同一份组件与同一份 props**，所以画面永远一致。

推导：Studio 读 `public/` 与 `--props`，render 读 bundle 与 `--props`，Player 读网页自己 fetch 的 props——数据源可以不同，结构必须相同。回指：4.1、4.2、4.4。
</details>

**T7**：为什么 Player 里不能包一层 `<Composition>`？`staticFile("audio.mp3")` 在 Player 环境里解析成什么地址？

<details>
<summary>答案</summary>

因为 Composition 是「渲染管线」的规格声明，Player 已经自己承担了这个角色（`durationInFrames`、`fps`、`compositionWidth` 直接写在 Player 的 props 上），再包一层等于声明两次规格，Remotion 直接报错。Player 环境没有 Studio 的静态服务，要手动把 `remotion_staticBase` 指向站点根，于是 `staticFile("audio.mp3")` 解析为 `/audio.mp3`。

推导：规格只能声明一次——渲染侧由 Composition 声明，播放侧由 Player 的 props 声明。回指：4.4。
</details>

**T8**：出片时长和音频对不上时，先查什么？渲染报错最多的一类是「props 字段全是 undefined」，根因是什么？

<details>
<summary>答案</summary>

先查 `calculateMetadata` 有没有生效、`--props` 的路径与字段名对不对。props 字段全是 undefined 的根因是：**props 文件的结构与 `defaultProps` 不一致**，两边字段要逐字对齐。

推导：`defaultProps` 只是 Studio 打开时的兜底，渲染用的是 `--props` 注入的那份；两份结构不同字段就取不到。回指：4.2。
</details>

**T9**：同一份 `public/` 目录，三个出口各自怎么用它？为什么流水线里必须有「同步资产到 public/」这一步？

<details>
<summary>答案</summary>

Studio 与网页直接读 `public/` 里的音频、字体；渲染走的是 `out/` 里的数据（`--props` 注入的时间戳）。所以渲染读 `out/`、Studio 与网页读 `public/`，中间必须有一步把前者拷给后者，否则「网页上的片和成片不一样」。

推导：三个出口同源是「画面一致」的前提，而同源靠的是数据只写一份、其余入口都从它派生。回指：4.3、4.5。
</details>

**T10**：改完文案后要出片，正确顺序是什么？直接跑 `npm run video` 会拿到什么？

<details>
<summary>答案</summary>

顺序是：先 `npm run tts`（重新合成音频与时间戳），再 `npm run video`（画面跟着新数据重算）。直接跑 `video` 而跳过 `tts`，成片用的还是旧音频与旧时间戳——这是流水线最常见的误操作。

推导：`npm run video` 的三步里第一步才是合成；数据没换，画面自然还是旧的。回指：4.5。
</details>

**T11**：Studio 预览里看到的画面和成片不一样，最可能是什么原因？

<details>
<summary>答案</summary>

多半是**启动 Studio 时没带 `--props`**——Studio 用的是 `defaultProps` 兜底那一份数据，而渲染用的是 `--props` 注入的真数据，你验的根本不是要交付的那一版。

推导：同一份组件 + 同一份 props 才有一致性；props 这一环一断，三个出口就各说各话。回指：4.1。
</details>

**T12**：Studio 调试的标准节奏是什么？「三查」查哪三样？

<details>
<summary>答案</summary>

节奏是**逐帧检查替代反复观看**：先算出理论踩点帧（157、263），在时间轴上精确拖到这两帧，逐帧检查旧场景淡出与新场景淡入是否在同一帧开始，再整段播放看节奏。三查是：查规格（总帧数与画布是否仍与数据一致、calculateMetadata 有没有被绕过）、查转场（重叠期是否吻合）、查字幕（该帧高亮到的词是否与时间戳一致）。

推导：帧级问题只有帧级检查能发现，肉眼看整段视频会漏掉一两帧的错位。回指：4.1。
</details>

**T13**：贯穿示例里词级时间戳与句级时间戳各驱动什么？为什么两样都要？

<details>
<summary>答案</summary>

词级时间戳（21 个词）驱动**字幕逐词高亮**——`t >= w.start && t < w.end` 判定「这个词正在被读出」；句级时间戳（2 个句子）驱动**场景划分**——句一的终点就是标题卡的终点、句二的终点就是结尾卡的起点。两样都要：只有句级就没法逐词高亮，只有词级就没有场景边界。

推导：颗粒度不同，各管一层；词级时间戳精度到 100 纳秒 tick，句级只是它按句子切出的粗边界。回指：3.2、3.6。
</details>

**T14**：出片后用 `ffmpeg -i` 验收，贯穿示例的验收基准是什么？读出 9.45 秒而计算值是 9.41 秒，怎么解释？

<details>
<summary>答案</summary>

验收基准是「9.45 秒、1280×720、30fps、h264 + aac」。9.41 秒是 `8.81 + 0.6` 的秒数，283 帧 ÷ 30 ≈ 9.43 秒，mp4 封装再取整后读出 9.45 秒——三个数说的是同一件事：总帧数 283。真正要警惕的是「读出的时长与 `ceil((8.81+0.6)×30)` 算出的帧数对不上」，那才是 calculateMetadata 没生效。

推导：秒数是换算结果、帧数才是事实，验收要对着帧数核（帧数 × fps ≈ 读出时长，误差在一帧内即可）。回指：4.2、3.3。
</details>
