## 21.1 RPC 的概念：像调用本地函数一样调用远程服务

微服务架构里，订单服务要查用户信息，但用户服务在另一台机器上——不能直接调用内存里的函数。**RPC（Remote Procedure Call，远程过程调用）**的目标是让远程调用看起来像本地调用一样自然：

```python
# 理想中的 RPC——看起来就像本地函数
user = user_service.get_user(user_id=12345)
# 但这次调用跨越了网络，到达了另一台机器
```

实现这个「魔法」需要三件事：**序列化**（把参数变成字节）、**传输**（通过网络发送字节）、**反序列化**（在另一端还原参数）。客户端的「桩代码」（stub）把这三步藏起来——你写的是函数调用，底下跑的是完整的一次网络会话。本章的主角 gRPC = Protobuf（编码）+ HTTP/2（传输）+ 代码生成（桩）。

## 21.2 REST vs gRPC：JSON 文本 vs Protobuf 二进制

传统微服务通信常用 REST + JSON。JSON 可读性好，但有三个硬伤：

1. **体积大**：`{"name": "Alice", "age": 30, "email": "alice@example.com"}` 占 55 字节，键名反复重复。
2. **类型模糊**：`30` 是整数还是浮点？`"true"` 是字符串还是布尔？运行时才能确定。
3. **没有强类型契约**：API 变更时，客户端可能在运行时才发现字段缺失。

gRPC 用 **Protocol Buffers（Protobuf）**替代 JSON、用 **HTTP/2** 替代 HTTP/1.1——两刀都砍在根子上。效率对比留到 21.3 编码细节之后。

## 21.3 Protobuf：字段编号与 Wire Type

Protobuf 的核心思想：**用数字而不是字符串来标识字段**。先看 `.proto` 文件：

```protobuf
syntax = "proto3";

message User {
  string name = 1;           // 字段编号 1
  int32 age = 2;             // 字段编号 2
  string email = 3;          // 字段编号 3
  repeated string tags = 4;  // 数组类型
}

message GetUserRequest {
  int32 user_id = 1;
}

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
```

每个字段后面的 `= 1`、`= 2` 不是默认值，是**字段编号**。「先猜再读」第一问的答案：序列化时只有「编号 + 值」上线，字段名完全不出现在数据里——接收端靠双方共享的同一份 `.proto` 文件（编译期生成到代码里）把编号翻译回字段名。契约先行，这是 Protobuf 与 JSON 最大的哲学差异。

**Wire Type（线类型）**告诉解码器怎么读值：

| Wire Type | 含义 | 适用类型 |
| --------- | ---- | -------- |
| 0 | Varint | int32, int64, bool, enum |
| 1 | 64-bit | double, fixed64 |
| 2 | Length-delimited | string, bytes, message, repeated |
| 5 | 32-bit | float, fixed32 |

编码过程（以 `age = 30` 为例）：

- 标签字节 = `(字段编号 << 3) | Wire Type` = `(2 << 3) | 0` = `0x10`
- 值 30 的 Varint 编码 = `0x1E`（Varint 每字节的最高位表示「后面还有」，小数字只用 1 字节）
- 结果：`0x10 0x1E`，共 2 字节

同样的数据 JSON 要 `"age": 30` 共 8 字节。整个 User 对象：Protobuf 约 30 字节，JSON 55 字节——字段越多差距越大。

> [!TIP] 字段编号是契约，改它就是事故
> 编号一旦发布就不能更换或复用——旧客户端还按老编号解码，改了编号等于把字段搬到了别人家。要删字段用 `reserved` 标记占住编号。JSON 键名随手改是习惯，Protobuf 的编号是法律。

## 21.4 为什么 Protobuf 又小又快

四个机制叠出来的优势：

1. **字段名不传输**：`name`、`email` 这些字符串只存在于 `.proto` 里，线上只有编号。
2. **Varint 自适应**：小数字 1 字节、大数字多字节——90% 的现实字段都是小数字。
3. **无结构字符**：没有 `{`、`"`、`,`、空格这些纯语法开销。
4. **编译期类型检查**：代码生成器在编译时就绑定类型，运行时零解析成本。

实测参照：10 字段的消息 JSON 约 300 字节、Protobuf 约 80 字节（3.5 倍压缩），序列化/反序列化快 5-10 倍。代价同样明确：可读性没了——抓包里它是「乱码」，必须拿着 `.proto` 才能解码（21.8 亲眼验证）。

## 21.5 跑在 HTTP/2 上：四种调用模式

gRPC 选 HTTP/2 当传输层不是偶然：19.3 的多路复用让多条请求共用一条连接且互不阻塞，19.4 的 HPACK 省掉重复头部，流的天然双向能力正好承载流式调用。

「先猜再读」第二问的答案：与 WebSocket 的区别在于——WebSocket 是**独立协议**，自定义帧格式、一次升级后与 HTTP 无关；gRPC 的双向流**复用 HTTP/2 的流语义**，帧格式、流量控制、头部压缩全部继承，天然过 TLS 与标准基础设施。WebSocket 适合浏览器场景的自定义实时协议，gRPC 适合服务间有契约的结构化调用。

四种模式按数据流向分：

```
1. Unary（一元）：
   Client → Request → Server → Response
   例：GetUser(request) → user

2. Server Streaming（服务端流）：
   Client → Request → Server → Response1, Response2, ...
   例：WatchStock(symbol) → 持续推送价格

3. Client Streaming（客户端流）：
   Client → Request1, Request2, ... → Server → Response
   例：UploadChunks(data...) → 最终返回结果

4. Bidirectional Streaming（双向流）：
   Client ⇄ Server（双向独立）
   例：Chat——两边同时发
```

```protobuf
service ChatService {
  rpc SendMessage (Message) returns (Ack);                          // 一元
  rpc SubscribeChannel (ChannelRequest) returns (stream Message);   // 服务端流
  rpc UploadFile (stream FileChunk) returns (UploadResult);         // 客户端流
  rpc Chat (stream Message) returns (stream Message);               // 双向流
}
```

`stream` 关键字出现在参数还是返回值的位置，决定了流的方向——每种模式在 HTTP/2 里都是「一条流上的若干 HEADERS + DATA 帧」，区别只是帧谁发、发几条。

## 21.6 微服务定位：内部 gRPC、外部 REST

gRPC 最适合**服务间通信**：延迟敏感、带宽有限、需要强类型契约。但面向外部 API 时 REST 仍是更好的选择——浏览器原生支持 JSON、调试工具成熟、语义通用。「先猜再读」第三问的答案：浏览器无法直接发起 gRPC 调用，因为它控制不了原始的 HTTP/2 帧（ trails/自定义头部等细节超出 Fetch API 的能力范围）。

工程上的经典分层：**内部用 gRPC，外部用 REST**，中间加 API Gateway 做协议转换。非要浏览器直连 gRPC 时用 **gRPC-Web**：浏览器发 gRPC-Web 请求，代理（如 Envoy）转换为标准 gRPC——保留 Protobuf 效率与强类型，代价是多一跳代理与功能子集（双向流受限）。

网关的角色与第23章的负载均衡/反向代理一脉相承——那里讲的是流量分发，这里是协议翻译。

## 21.7 编程实践：Python gRPC 跑通一个服务

契约文件 `greet.proto`：

```protobuf
syntax = "proto3";

package greet;

message GreetRequest {
  string name = 1;
}

message GreetResponse {
  string message = 1;
}

service Greeter {
  rpc SayHello (GreetRequest) returns (GreetResponse);
}
```

生成代码与安装依赖：

```bash
pip install grpcio grpcio-tools
python -m grpc_tools.protoc -I. --python_out=. --grpc_python_out=. greet.proto
```

服务端：

```python
# server.py
import grpc
from concurrent import futures
import greet_pb2
import greet_pb2_grpc

class GreeterServicer(greet_pb2_grpc.GreeterServicer):
    def SayHello(self, request, context):
        # request 已是强类型对象：request.name 是 str
        return greet_pb2.GreetResponse(
            message=f"Hello, {request.name}! Welcome to gRPC."
        )

server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
greet_pb2_grpc.add_GreeterServicer_to_server(GreeterServicer(), server)
server.add_insecure_port('[::]:50051')
server.start()
print("gRPC server running on port 50051...")
server.wait_for_termination()
```

客户端：

```python
# client.py
import grpc
import greet_pb2
import greet_pb2_grpc

channel = grpc.insecure_channel('localhost:50051')
stub = greet_pb2_grpc.GreeterStub(channel)

response = stub.SayHello(greet_pb2.GreetRequest(name="Alice"))
print(f"Server says: {response.message}")
```

注意「像本地函数一样」的落点：`stub.SayHello(request)` 的写法与 21.1 的理想 RPC 一模一样——桩代码把序列化、网络、反序列化全部藏起来了。`insecure_channel` 只适合本机实验，生产走 TLS（`grpc.secure_channel` + 凭证，加密体系仍是第15章那一套）。

## 21.8 抓包实践：对比 gRPC 与 REST 报文

```bash
# 抓取 gRPC 流量（默认端口 50051）
tshark -i lo -f "tcp port 50051" -V -c 10

# 对比响应大小（REST 侧）
curl -s -o /dev/null -w "REST JSON size: %{size_download} bytes\n" \
  http://localhost:8080/api/greet?name=Alice
```

在 Wireshark 里，gRPC 的 DATA 帧载荷是一串「乱码」——那是二进制 Protobuf，正是 21.3 编码的字节流。对照 21.4 的数字，同样的信息 gRPC 载荷通常只有 REST JSON 的三分之一。想看懂内容，在 Wireshark 的 Preferences 里配置 proto 文件路径，解析器就能按契约解码出字段——「可读性换效率」的取舍在此具象化。

## 本章小结

- RPC 的魔法 = 桩代码遮住的三步：序列化、传输、反序列化——你写函数调用，底下跑网络会话。
- JSON 的三大硬伤：体积大（键名重复）、类型模糊、无强类型契约——gRPC 用 Protobuf + HTTP/2 双刀直取。
- Protobuf 的哲学是契约先行：线上只有字段编号与值，字段名留在双方共享的 `.proto` 里。
- 标签字节 = `(编号 << 3) | Wire Type`；Varint 让小数字只占 1 字节——`age=30` 全程 2 字节。
- 字段编号是法律：发布后不能改不能复用，删除要用 `reserved` 占位——这是兼容性的根基。
- 四种调用模式按数据流向分，本质都是 HTTP/2 流上的 HEADERS + DATA 帧组合；`stream` 写在哪边，流就往哪边。
- gRPC 与 WebSocket 的分野：复用 HTTP/2 流语义 vs 独立协议自定义帧——前者服务间契约调用，后者浏览器实时通道。
- 定位口诀：内部 gRPC、外部 REST、网关翻译；浏览器直连走 gRPC-Web，代价是多一跳代理。
