# 第13章：完整实战——Node.js 项目从测试到部署

## 13.1 引言：为什么要从 Node.js 开始？

如果把 CI/CD 比作一条流水线工厂，那 Node.js 项目就是最常见的"标准件"。Express.js 生态成熟、npm 包管理方便、部署目标明确，非常适合用来完整走一遍 CI/CD 流程。本章我们将以一个 Express.js REST API 项目为例，从 lint 检查开始，一路走到生产环境部署，构建一条完整的自动化流水线。

你可能会问："直接手动部署不行吗？"——当然行，就像你每天可以手动洗碗一样。但当项目规模变大、多人协作时，手动部署就变成了"灾难的温床"。忘记跑测试、搞错环境变量、部署了错误的分支……这些坑，CI/CD 帮你一次性填平。

## 13.2 项目结构假设

我们假设项目结构如下——一个典型的 Express.js REST API：

```
my-api/
├── .github/
│   └── workflows/
│       └── ci-cd.yml          # 我们的 Workflow 文件
├── src/
│   ├── app.js                 # Express 应用入口
│   ├── routes/
│   │   ├── users.js           # 用户路由
│   │   └── products.js        # 商品路由
│   ├── middleware/
│   │   └── auth.js            # 认证中间件
│   └── utils/
│       └── db.js              # 数据库连接工具
├── tests/
│   ├── unit/
│   │   └── users.test.js      # 单元测试
│   └── integration/
│       └── api.test.js        # 集成测试
├── Dockerfile                 # Docker 构建文件
├── package.json
├── .eslintrc.js               # ESLint 配置
└── .env.example               # 环境变量示例
```

这个结构不复杂：`src/` 放业务代码，`tests/` 放测试文件，`Dockerfile` 用来构建容器镜像。就像一间整理得很好的厨房——每样东西都有固定的位置，找起来毫不费力。

## 13.3 CI 流水线设计：四道关卡

一条好的 CI/CD 流水线，就像一座城堡的四道防线——每一道都在检查不同的"入侵者"：

1. **Lint（代码规范检查）**——第一道岗哨，检查代码的"仪容仪表"。变量命名是否规范？缩进是否正确？有没有未使用的变量？
2. **Test（自动化测试）**——第二道防线，验证代码的"内在逻辑"。单元测试确保函数行为正确，集成测试确保 API 端到端工作正常。
3. **Build（构建）**——第三道关卡，将代码"打包"成可部署的产物。对 Node.js 来说通常是 Docker 镜像。
4. **Deploy（部署）**——最后一道门，将通过所有检查的代码送到真正的运行环境中。

这四道关卡是顺序执行的：如果 lint 失败了，就没必要跑测试；如果测试失败了，就没必要构建；如果构建失败了，就没必要部署。这种"早失败"（fail-fast）策略，能帮你节省大量的时间和计算资源。

## 13.4 多环境支持：staging 和 production

在现实世界中，你至少需要两个环境——就像排练和正式演出：

- **Staging（预发布环境）**：和生产环境几乎一模一样，用来做"彩排"。新功能先部署到这里，让团队成员确认没问题。
- **Production（生产环境）**：真正的"正式演出"，面向最终用户。

为什么不能直接部署到生产？想象一下，如果一个未经验证的新功能直接上线，可能导致用户数据丢失、服务中断。Staging 环境就是你的"安全网"。

## 13.5 Environment 保护和审批机制

GitHub 的 Environment 功能，就像给生产环境加了一道"门禁系统"：

- **Required reviewers**：部署到生产环境前，需要指定的人审批通过。
- **Wait timer**：审批通过后，可以设置等待时间（比如等 30 分钟再部署，给你最后一次反悔的机会）。
- **Deployment branches**：限制只有特定分支（如 `main`）才能部署到某个环境。

配置方法：进入仓库的 Settings → Environments → New environment，然后设置相应的保护规则。

## 13.6 完整的 Workflow YAML 文件

这是本章的重头戏。让我们逐行解析一个完整的 CI/CD Workflow：

```yaml
# .github/workflows/ci-cd.yml
# 给这个 Workflow 取个响亮的名字
name: Node.js CI/CD Pipeline

# 触发条件：push 到 main/develop，或者对 main 发起 PR
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

# 定义全局环境变量（所有 job 都能访问）
env:
  NODE_VERSION: '20'
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ========== 第一关：代码规范检查 ==========
  lint:
    name: 🔍 Lint Check
    runs-on: ubuntu-latest
    steps:
      # 步骤1：把代码拉到 runner 上
      - name: Checkout code
        uses: actions/checkout@v4

      # 步骤2：安装 Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          # 利用 npm 缓存加速安装
          cache: 'npm'

      # 步骤3：安装依赖（ci 比 install 更适合 CI 环境）
      # npm ci 严格按照 package-lock.json 安装，保证一致性
      - name: Install dependencies
        run: npm ci

      # 步骤4：运行 ESLint
      - name: Run ESLint
        run: npx eslint src/ --ext .js --max-warnings 0
        # --max-warnings 0 表示任何警告都算失败，保持代码"洁癖"

  # ========== 第二关：自动化测试 ==========
  test:
    name: 🧪 Test Suite
    runs-on: ubuntu-latest
    # 依赖 lint 通过后才运行
    needs: lint
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      # 运行测试并生成覆盖率报告
      - name: Run tests with coverage
        run: npx jest --coverage --ci --reporters=default
        env:
          # 测试用的环境变量
          DATABASE_URL: postgresql://test:test@localhost:5432/test_db
          JWT_SECRET: test-secret-key-for-ci

      # 把覆盖率报告上传，方便在 PR 中查看
      - name: Upload coverage report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 7

  # ========== 第三关：构建 Docker 镜像 ==========
  build:
    name: 🏗️ Build Docker Image
    runs-on: ubuntu-latest
    needs: test
    # 只在 push 到 main 或 develop 时构建（PR 不需要）
    if: github.event_name == 'push'
    permissions:
      contents: read
      packages: write
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      # 配置 Docker Buildx（支持多平台构建和缓存）
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      # 登录 GitHub Container Registry
      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # 提取元数据（标签、标签名）
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=
            type=ref,event=branch
            type=raw,value=latest,enable={{is_default_branch}}

      # 构建并推送镜像
      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          # 利用 GitHub Actions 缓存加速构建
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ========== 第四关：部署到 Staging ==========
  deploy-staging:
    name: 🚀 Deploy to Staging
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/develop'
    environment:
      name: staging
      url: https://staging.my-api.example.com
    steps:
      - name: Deploy to staging server
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAGING_HOST }}
          username: ${{ secrets.STAGING_USER }}
          key: ${{ secrets.STAGING_SSH_KEY }}
          script: |
            cd /opt/my-api
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:develop
            docker compose -f docker-compose.staging.yml up -d
            echo "Staging deployment complete!"

  # ========== 第五关：部署到 Production（需审批）==========
  deploy-production:
    name: 🎯 Deploy to Production
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    environment:
      name: production
      url: https://api.example.com
    steps:
      - name: Deploy to production server
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PRODUCTION_HOST }}
          username: ${{ secrets.PRODUCTION_USER }}
          key: ${{ secrets.PRODUCTION_SSH_KEY }}
          script: |
            cd /opt/my-api
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
            # 蓝绿部署：先启动新容器，再切换流量
            docker compose -f docker-compose.prod.yml up -d --no-deps api
            # 等待健康检查通过
            sleep 10
            curl -f http://localhost:3000/health || exit 1
            echo "Production deployment successful! 🎉"
```

## 13.7 逐行解析几个关键点

**`npm ci` vs `npm install`**：在 CI 环境中永远用 `npm ci`。它会删除 `node_modules` 然后严格按照 `package-lock.json` 安装，确保每次构建的依赖完全一致。`npm install` 可能会"自作聪明"地更新一些包，导致不可预测的结果。

**`needs: lint`**：这个关键字建立了 Job 之间的依赖关系，形成了一条"流水线"。没有它，所有 Job 会并行运行，浪费了 lint 失败时本可以节省的资源。

**`if: github.event_name == 'push'`**：条件控制。PR 只需要跑 lint 和 test（让审查者看到代码质量），不需要构建镜像和部署。

**`environment` 关键字**：它连接了 GitHub 仓库中配置的 Environment 设置。当 Job 关联了某个 Environment 后，就能使用该 Environment 的 Secrets，同时受到保护规则的约束。

## 13.8 运行效果展示和问题排查

当一切配置好后，你在 GitHub 仓库的 Actions 标签页会看到这样的运行记录：

```
✅ Node.js CI/CD Pipeline · a3f2b1c · 2 minutes ago
  ✅ 🔍 Lint Check        (15s)
  ✅ 🧪 Test Suite         (1m 30s)
  ✅ 🏗️ Build Docker Image (2m)
  ✅ 🚀 Deploy to Staging  (45s)
  ⏸️ 🎯 Deploy to Production (Waiting for review)
```

当 Production 部署在等待审批时，你可以在 PR 的评论区看到"Deploy to Production"等待审核的提示。审核者点击 "Review deployments" 按钮后，部署才会继续。

**常见排查思路**：

- 如果 `npm ci` 失败：检查 `package-lock.json` 是否已提交到仓库。
- 如果测试超时：检查是否需要数据库连接，考虑使用 GitHub Services。
- 如果 Docker 构建失败：本地用 `docker build` 先验证一下。
- 如果部署失败：用 `ssh-action` 连接目标服务器后手动检查日志。

## 13.9 小结

本章我们完成了一个完整的 Node.js CI/CD 流水线：从代码规范检查、自动化测试，到 Docker 镜像构建，最后分环境部署。这条流水线就像一条"自动化传送带"，把代码从开发者的键盘一路送到生产服务器，中间不需要任何人工干预（除了生产环境的审批）。
