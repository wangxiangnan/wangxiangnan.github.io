# Ch12：测试策略

## 本章目标

- 用 Vitest 5 在 monorepo 中共享测试配置
- 覆盖三个层次：shared 单元测试、ui 组件测试、api 集成测试
- 用 Playwright 编写跨应用的端到端测试
- 在一个进程里汇总所有包的覆盖率
- 让 Turborepo 只运行受影响的测试

## 12.1 monorepo 测试的四个问题

单包项目的测试配置通常很简单：装一个 Vitest，写一个 `vitest.config.ts`，结束。到了 monorepo，问题会变成四个：

1. **依赖链影响**：修改 `packages/shared/src/utils/index.ts`，`apps/api` 的集成测试可能立刻失败，因为两边共享同一套类型和工具函数。
2. **配置重复**：五个包各写一份 `vitest.config.ts`，大部分选项完全一样，升级时容易漏改。
3. **运行效率**：CI 每次跑全部测试，哪怕这次只改了一个 README。
4. **覆盖率分散**：每个包生成自己的 `coverage/`，无法回答"整个仓库的覆盖率是多少"。

本章按"共享配置 → 分层测试 → 覆盖率 → 增量运行"的顺序解决这四个问题。

## 12.2 Vitest 5：共享配置与项目

### 安装依赖

先在 `pnpm-workspace.yaml` 的 `catalogs` 下增加一个 `test` 分组：

```yaml
catalogs:
  test:
    vitest: ^5.0.5
    "@vitest/coverage-v8": ^5.0.5
    "@vue/test-utils": ^2.5.1
    jsdom: ^30.1.3
    supertest: ^7.3.1
    "@types/supertest": ^7.2.1
    "@playwright/test": ^1.64.1
```

> 这里只展示新增的分组，实际文件里应把它合并到已有的 `catalogs` 下，而不是再写一个同名的 `catalogs` 键。

在根 `package.json` 中追加测试依赖：

```json
{
  "devDependencies": {
    "@vitest/coverage-v8": "catalog:test",
    "vitest": "catalog:test"
  }
}
```

执行 `pnpm install`。根目录安装 Vitest 是为了运行"一次跑完所有 project"的覆盖率命令；每个包仍然需要自己的 `vitest` 依赖，因为 pnpm 不会把根依赖提升到子包。

### 共享配置放在根目录

创建 `vitest.shared.ts`：

```typescript
import { defineConfig, mergeConfig } from 'vitest/config';

export const baseConfig = defineConfig({
  test: {
    globals: true,
    include: [
      'src/**/*.{test,spec}.{ts,tsx}',
      'tests/**/*.{test,spec}.{ts,tsx}',
    ],
    testTimeout: 10_000,
    restoreMocks: true,
    clearMocks: true,
  },
});

export const nodeConfig = mergeConfig(
  baseConfig,
  defineConfig({
    test: {
      environment: 'node',
      // 集成测试可能涉及真实的 HTTP、数据库或文件系统，给更宽的超时
      testTimeout: 30_000,
    },
  }),
);

export default baseConfig;
```

**为什么把共享配置放在根目录，而不是做一个 `@taskflow/vitest-config` 包？**

两种做法都可行，但配置包有一个容易忽略的坑：如果包入口导出 `.ts` 文件，Vitest 加载配置时会把 `node_modules` 里的依赖外部化，Node 直接遇到 `.ts` 就会报 `ERR_UNKNOWN_FILE_EXTENSION`；要解决就得给配置包加构建步骤，或者把配置写成纯 JS。根目录的 `vitest.shared.ts` 会被 Vite 直接打包进配置文件，既保留类型检查，又不需要额外构建。Vitest 官方文档中的 "shared config" 示例也是这种结构。

`baseConfig` 中的几个选项值得解释：

- `include`：测试文件既可以在 `src/` 下与源码同目录，也可以放在包级 `tests/` 下。
- `restoreMocks` / `clearMocks`：每个测试结束后自动还原 mock 的实现和调用记录，避免测试之间互相污染。
- `testTimeout`：默认 5 秒对单元测试足够，组件测试偶尔会慢一点，统一放宽到 10 秒。

### 每个包一个 project 配置

`packages/shared/vitest.config.ts`：

```typescript
import { defineProject, mergeConfig } from 'vitest/config';
import { baseConfig } from '../../vitest.shared.js';

export default mergeConfig(
  baseConfig,
  defineProject({
    test: {
      name: 'shared',
    },
  }),
);
```

`packages/ui/vitest.config.ts`：

```typescript
import { defineProject, mergeConfig } from 'vitest/config';
import vue from '@vitejs/plugin-vue';
import { baseConfig } from '../../vitest.shared.js';

export default mergeConfig(
  baseConfig,
  defineProject({
    plugins: [vue()],
    test: {
      name: 'ui',
      environment: 'jsdom',
    },
  }),
);
```

`apps/api/vitest.config.ts`：

```typescript
import { defineProject, mergeConfig } from 'vitest/config';
import { nodeConfig } from '../../vitest.shared.js';

export default mergeConfig(
  nodeConfig,
  defineProject({
    test: {
      name: 'api',
      env: {
        NODE_ENV: 'test',
        DATABASE_URL: 'postgresql://postgres:postgres@localhost:5432/taskflow_test?schema=public',
        JWT_SECRET: 'test-jwt-secret-at-least-32-characters',
        JWT_REFRESH_SECRET: 'test-refresh-secret-at-least-32-characters',
        CORS_ORIGINS: 'http://localhost:5173',
      },
    },
  }),
);
```

这里有三个关键点：

1. **用 `defineProject` 而不是 `defineConfig`**。project 配置不支持 `coverage`、`reporters` 等进程级选项，`defineProject` 会在类型层面提前拦住这些错误。
2. **`name` 必须唯一**。Vitest 用它在输出和 `--project` 过滤中标识每个项目。
3. **API 的环境变量在配置里注入**。`apps/api/src/config/env.ts` 在导入时就用 Zod 校验环境变量；如果测试机没有 `.env`，测试会在导入 `app` 的阶段直接失败。`test.env` 会在测试模块加载前写入 `process.env`，`dotenv` 又不会覆盖已有值，因此测试不依赖本机的 `.env`。

`packages/ui` 的 `package.json` 追加测试脚本和依赖：

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  },
  "devDependencies": {
    "@vitejs/plugin-vue": "catalog:vue",
    "@vue/test-utils": "catalog:test",
    "jsdom": "catalog:test",
    "vitest": "catalog:test"
  }
}
```

`apps/api` 追加：

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  },
  "devDependencies": {
    "@types/supertest": "catalog:test",
    "supertest": "catalog:test",
    "vitest": "catalog:test"
  }
}
```

`packages/shared` 只需要追加 `"vitest": "catalog:test"`。修改完三个包的 `package.json` 后，回到根目录执行一次 `pnpm install`。

### 根配置把 project 串起来

创建根目录 `vitest.config.ts`：

```typescript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    projects: ['packages/shared', 'packages/ui', 'apps/api'],
  },
});
```

`projects` 可以直接写目录，Vitest 会自动寻找目录下的 `vitest.config.ts`。这样本地运行 `pnpm exec vitest` 时，三个 project 会在同一个进程里执行，IDE 扩展也能正确发现测试。

但注意：**Turbo 和根 `vitest.config.ts` 是两条路径**。

- `pnpm test` 走 `turbo run test`：每个包独立执行、独立缓存，适合日常开发和 CI 增量运行。
- `pnpm exec vitest` 走根配置：一次加载所有 project，适合本地全量跑、调试和生成统一覆盖率。

不要把 Turbo 的 `test` 任务改成在根目录跑 `vitest`，否则会失去"每个包独立缓存"的能力。

## 12.3 单元测试：packages/shared

`packages/shared` 里的工具函数是纯函数，最适合做单元测试。测试文件与源码同目录，命名为 `index.test.ts`：

```typescript
import { afterEach, describe, expect, it, vi } from 'vitest';
import {
  createHealthResponse,
  errorResponse,
  formatDate,
  formatDateShort,
  isValidEmail,
  isValidPassword,
  isValidUsername,
  NotFoundError,
  successResponse,
  timeAgo,
  validateCreateUserDto,
} from './index.js';

afterEach(() => {
  vi.useRealTimers();
});

describe('isValidEmail', () => {
  it.each<[string, boolean]>([
    ['user@example.com', true],
    ['test.user@domain.co', true],
    ['', false],
    ['not-an-email', false],
    ['@domain.com', false],
    ['user@', false],
  ])('isValidEmail(%s) 返回 %s', (email, expected) => {
    expect(isValidEmail(email)).toBe(expected);
  });
});

describe('isValidUsername', () => {
  it.each<[string, boolean]>([
    ['charlie', true],
    ['user_01', true],
    ['ab', false],
    ['user name', false],
    ['user@name', false],
  ])('isValidUsername(%s) 返回 %s', (username, expected) => {
    expect(isValidUsername(username)).toBe(expected);
  });
});

describe('isValidPassword', () => {
  it('接受包含大小写字母和数字的 8 位以上密码', () => {
    expect(isValidPassword('Charlie123')).toBe(true);
  });

  it('拒绝过短的密码', () => {
    expect(isValidPassword('Ab1')).toBe(false);
  });

  it('拒绝缺少大写字母的密码', () => {
    expect(isValidPassword('charlie123')).toBe(false);
  });

  it('拒绝缺少数字的密码', () => {
    expect(isValidPassword('CharlieABC')).toBe(false);
  });
});

describe('validateCreateUserDto', () => {
  it('合法输入返回空数组', () => {
    expect(
      validateCreateUserDto({
        username: 'charlie',
        email: 'charlie@example.com',
        password: 'Charlie123',
      }),
    ).toEqual([]);
  });

  it('一次性返回所有字段的错误', () => {
    const errors = validateCreateUserDto({
      username: 'a',
      email: 'bad',
      password: '123',
    });
    expect(errors).toHaveLength(3);
  });
});

describe('日期格式化', () => {
  it('formatDate 返回 ISO 8601 字符串', () => {
    expect(formatDate('2024-01-15T08:30:00.000Z')).toBe('2024-01-15T08:30:00.000Z');
  });

  it('formatDate 对非法日期抛出错误', () => {
    expect(() => formatDate('not-a-date')).toThrow(/Invalid date/);
  });

  it('formatDateShort 使用本地时区输出 YYYY-MM-DD', () => {
    expect(formatDateShort(new Date(2024, 0, 15))).toBe('2024-01-15');
  });

  it('timeAgo 根据时间差选择单位', () => {
    vi.useFakeTimers();
    vi.setSystemTime(new Date('2026-01-01T12:00:00.000Z'));

    expect(timeAgo('2026-01-01T11:59:30.000Z')).toBe('30 秒前');
    expect(timeAgo('2026-01-01T10:00:00.000Z')).toBe('2 小时前');
    expect(timeAgo('2025-12-29T12:00:00.000Z')).toBe('3 天前');
    expect(timeAgo('2026-01-01T12:00:01.000Z')).toBe('刚刚');
  });
});

describe('API 响应与错误', () => {
  it('createHealthResponse 返回统一结构', () => {
    const health = createHealthResponse();
    expect(health.status).toBe('ok');
    expect(health.version).toBe('0.1.0');
    expect(health.timestamp).toMatch(/^\d{4}-\d{2}-\d{2}T/);
  });

  it('successResponse 构造成功响应', () => {
    expect(successResponse({ id: '1' })).toEqual({
      success: true,
      data: { id: '1' },
    });
  });

  it('successResponse 可以附加分页信息', () => {
    const meta = { page: 1, pageSize: 20, total: 1, totalPages: 1 };
    expect(successResponse([], meta)).toEqual({
      success: true,
      data: [],
      meta,
    });
  });

  it('errorResponse 构造失败响应', () => {
    expect(errorResponse({ code: 'NOT_FOUND', message: '资源不存在' })).toEqual({
      success: false,
      error: { code: 'NOT_FOUND', message: '资源不存在' },
    });
  });

  it('NotFoundError 携带状态码、错误码和可读消息', () => {
    const error = new NotFoundError('用户', '42');
    expect(error.statusCode).toBe(404);
    expect(error.code).toBe('NOT_FOUND');
    expect(error.message).toBe('用户（ID: 42）不存在');
    expect(error.toApiError()).toMatchObject({
      code: 'NOT_FOUND',
      message: '用户（ID: 42）不存在',
    });
  });
});
```

测试文件放在 `src/` 下会带来一个副作用：`tsc` 构建时会把 `*.test.ts` 也编译进 `dist/`。修改 `packages/shared/tsconfig.json`，把测试文件排除出构建：

```json
{
  "extends": "@taskflow/tsconfig/base.json",
  "compilerOptions": {
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"],
  "exclude": ["dist", "node_modules", "src/**/*.test.ts", "src/**/*.spec.ts"]
}
```

> 测试文件同目录的好处是修改源码时一眼就能看到对应测试；代价是构建配置必须显式排除测试。`packages/ui` 没有 `tsc` 构建步骤，不受这个问题影响。

给 `packages/shared/package.json` 加上测试脚本：

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest"
  }
}
```

运行：

```bash
pnpm --filter @taskflow/shared test
```

## 12.4 组件测试：BaseButton

组件测试介于单元测试和 E2E 之间：它不启动浏览器，但需要 DOM。Vitest 用 `jsdom` 模拟 `document`、`window` 和事件系统，`@vue/test-utils` 负责挂载组件、触发事件和读取 emit。

先给 `packages/ui/src/components/BaseButton.vue` 加一层保护。Ch07 的版本依赖原生 `disabled` 阻止点击，但测试工具调用 `trigger('click')` 时是直接派发事件，可能绕过浏览器的禁用行为：

```vue
<script setup lang="ts">
interface Props {
  variant?: 'primary' | 'secondary' | 'danger';
  size?: 'sm' | 'md' | 'lg';
  disabled?: boolean;
  loading?: boolean;
  type?: 'button' | 'submit' | 'reset';
}

const props = withDefaults(defineProps<Props>(), {
  variant: 'primary',
  size: 'md',
  disabled: false,
  loading: false,
  type: 'button',
});

const emit = defineEmits<{
  click: [event: MouseEvent];
}>();

function handleClick(event: MouseEvent) {
  // loading 时按钮同时处于 disabled 状态，这里再守一层，避免程序化触发事件
  if (props.disabled || props.loading) return;
  emit('click', event);
}
</script>
```

模板只需把 `@click="$emit('click', $event)"` 改成 `@click="handleClick"`，其余不变。

创建 `packages/ui/src/components/BaseButton.test.ts`：

```typescript
import { describe, expect, it } from 'vitest';
import { mount } from '@vue/test-utils';
import BaseButton from './BaseButton.vue';

describe('BaseButton', () => {
  it('渲染默认样式和插槽内容', () => {
    const wrapper = mount(BaseButton, {
      slots: { default: '保存' },
    });

    expect(wrapper.text()).toContain('保存');
    expect(wrapper.classes()).toEqual(
      expect.arrayContaining([
        'base-button',
        'base-button--primary',
        'base-button--md',
      ]),
    );
    expect(wrapper.attributes('type')).toBe('button');
  });

  it('根据 variant 和 size 生成对应的类名', () => {
    const wrapper = mount(BaseButton, {
      props: { variant: 'danger', size: 'lg' },
      slots: { default: '删除' },
    });

    expect(wrapper.classes()).toContain('base-button--danger');
    expect(wrapper.classes()).toContain('base-button--lg');
  });

  it('点击时触发 click 并携带 MouseEvent', async () => {
    const wrapper = mount(BaseButton, {
      slots: { default: '保存' },
    });

    await wrapper.trigger('click');

    const events = wrapper.emitted('click');
    expect(events).toHaveLength(1);
    expect(events?.[0]?.[0]).toBeInstanceOf(MouseEvent);
  });

  it('disabled 时不触发 click', async () => {
    const wrapper = mount(BaseButton, {
      props: { disabled: true },
      slots: { default: '保存' },
    });

    expect(wrapper.attributes('disabled')).toBeDefined();
    await wrapper.trigger('click');
    expect(wrapper.emitted('click')).toBeUndefined();
  });

  it('loading 时显示 spinner、禁用按钮且不触发 click', async () => {
    const wrapper = mount(BaseButton, {
      props: { loading: true },
      slots: { default: '提交中' },
    });

    expect(wrapper.find('.base-button__spinner').exists()).toBe(true);
    expect(wrapper.classes()).toContain('base-button--loading');
    expect(wrapper.attributes('disabled')).toBeDefined();

    await wrapper.trigger('click');
    expect(wrapper.emitted('click')).toBeUndefined();
  });

  it('支持 type="submit" 以触发表单提交', () => {
    const wrapper = mount(BaseButton, {
      props: { type: 'submit' },
      slots: { default: '登录' },
    });

    expect(wrapper.attributes('type')).toBe('submit');
  });
});
```

运行：

```bash
pnpm --filter @taskflow/ui test
```

这些测试覆盖了组件的三种关键状态：默认渲染、禁用、加载中。**不要用 E2E 测这些分支**——启动浏览器只为了点一个按钮，成本高且不稳定；组件测试能在毫秒级完成同样的验证。

## 12.5 API 集成测试：supertest + 真实 app

Ch08 已经把 HTTP 应用拆成 `app.ts` 和 `index.ts`：`app.ts` 组装中间件和路由，`index.ts` 只负责监听端口。测试直接导入 `app`，`supertest` 会在内存里发起请求，不占用 3000 端口，也不需要先启动服务。

创建 `apps/api/tests/api.test.ts`。集成测试放在包级 `tests/` 下，避免被 `tsc` 构建进 `dist/`：

```typescript
import { describe, expect, it } from 'vitest';
import request from 'supertest';
import type { ApiResponse, User } from '@taskflow/shared/types';
import { app } from '../src/app.js';

describe('GET /api/users', () => {
  it('返回用户列表和分页元信息', async () => {
    const res = await request(app).get('/api/users');

    expect(res.status).toBe(200);
    const body = res.body as ApiResponse<User[]>;
    expect(body.success).toBe(true);
    expect(body.data).toHaveLength(1);
    expect(body.data?.[0]?.username).toBe('admin');
    expect(body.meta).toMatchObject({
      page: 1,
      pageSize: 20,
      total: 1,
      totalPages: 1,
    });
  });

  it('分页参数非法时返回 400', async () => {
    const res = await request(app).get('/api/users?page=0');

    expect(res.status).toBe(400);
    const body = res.body as ApiResponse<never>;
    expect(body.success).toBe(false);
    expect(body.error?.code).toBe('VALIDATION_ERROR');
  });
});

describe('GET /api/users/:id', () => {
  it('返回指定用户', async () => {
    const res = await request(app).get('/api/users/1');

    expect(res.status).toBe(200);
    const body = res.body as ApiResponse<User>;
    expect(body.data).toMatchObject({
      id: '1',
      username: 'admin',
      email: 'admin@example.com',
      role: 'admin',
    });
  });

  it('用户不存在时返回 404 和结构化错误', async () => {
    const res = await request(app).get('/api/users/999');

    expect(res.status).toBe(404);
    const body = res.body as ApiResponse<never>;
    expect(body.success).toBe(false);
    expect(body.error?.code).toBe('NOT_FOUND');
    expect(body.error?.message).toContain('999');
  });
});

describe('POST /api/users', () => {
  it('创建用户且响应中不包含密码', async () => {
    const res = await request(app).post('/api/users').send({
      username: 'charlie',
      email: 'charlie@example.com',
      password: 'Charlie123',
    });

    expect(res.status).toBe(201);
    const body = res.body as ApiResponse<User>;
    expect(body.data).toMatchObject({
      username: 'charlie',
      email: 'charlie@example.com',
      role: 'viewer',
    });
    expect(body.data).not.toHaveProperty('password');
  });

  it('缺少必填字段时返回 400 和字段级错误', async () => {
    const res = await request(app).post('/api/users').send({
      username: 'charlie',
      password: 'Charlie123',
    });

    expect(res.status).toBe(400);
    const body = res.body as ApiResponse<never>;
    expect(body.error?.code).toBe('VALIDATION_ERROR');
    expect(Array.isArray(body.error?.details)).toBe(true);
  });
});
```

**为什么这比"再写一个模拟 app"更好？** 旧版本教程在测试文件里重新定义了一套 `/api/users` 路由，看起来能跑，但它验证的是测试里的副本，不是生产代码。真实项目中的回归往往出在中间件顺序、Zod Schema、错误处理这些"胶水"上；只有导入真实的 `app`，这些路径才会被覆盖。

测试里没有连接数据库：Ch08 的控制器目前使用内存中的 `mockUser`。等替换为 Prisma 后，集成测试应使用独立的测试数据库，并在每个测试后回滚事务；这类测试涉及外部状态，不应开启 Turbo 缓存。

运行：

```bash
pnpm --filter @taskflow/api test
```

## 12.6 端到端测试：Playwright

E2E 验证的是"用户打开浏览器，从首页走到目标页面"的完整链路。它不属于任何一个业务包，因此单独放在 `apps/e2e`。

创建 `apps/e2e/package.json`：

```json
{
  "name": "@taskflow/e2e",
  "private": true,
  "version": "0.1.0",
  "type": "module",
  "scripts": {
    "test:e2e": "playwright test",
    "test:e2e:ui": "playwright test --ui",
    "test:e2e:headed": "playwright test --headed"
  },
  "devDependencies": {
    "@playwright/test": "catalog:test"
  }
}
```

脚本故意命名为 `test:e2e` 而不是 `test`。根目录的 `pnpm test` 执行 `turbo run test`，如果 e2e 包也有 `test` 脚本，每次单元测试都会顺带启动浏览器和两个开发服务器——这通常不是你想要的行为。

创建 `apps/e2e/playwright.config.ts`：

```typescript
import { defineConfig, devices } from '@playwright/test';

const isCI = Boolean(process.env.CI);

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: isCI,
  retries: isCI ? 2 : 0,
  workers: isCI ? 1 : undefined,
  reporter: isCI ? 'html' : 'list',

  use: {
    baseURL: 'http://localhost:5173',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },

  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
  ],

  webServer: [
    {
      command: 'pnpm --filter @taskflow/api dev',
      url: 'http://localhost:3000/api/health',
      reuseExistingServer: !isCI,
      timeout: 60_000,
      env: {
        NODE_ENV: 'test',
        PORT: '3000',
        DATABASE_URL: 'postgresql://postgres:postgres@localhost:5432/taskflow?schema=public',
        JWT_SECRET: 'e2e-jwt-secret-at-least-32-characters',
        JWT_REFRESH_SECRET: 'e2e-refresh-secret-at-least-32-characters',
        CORS_ORIGINS: 'http://localhost:5173',
      },
    },
    {
      command: 'pnpm --filter @taskflow/web dev',
      url: 'http://localhost:5173',
      reuseExistingServer: !isCI,
      timeout: 60_000,
      env: {
        VITE_APP_TITLE: 'TaskFlow',
        VITE_API_ORIGIN: '',
      },
    },
  ],
});
```

数组里的两个 `webServer` 会被**同时**启动，Playwright 分别轮询各自的 `url`，两个地址都可用后才开始跑测试，结束后统一关闭。`url` 比 `port` 更可靠：它不只看端口是否打开，还要求 `/api/health` 真正返回响应。`reuseExistingServer: !isCI` 让本地开发时复用你已经开着的服务，CI 中则强制从干净状态启动。

创建 `apps/e2e/tests/auth.spec.ts`：

```typescript
import { expect, test } from '@playwright/test';

test.describe('TaskFlow Web', () => {
  test('首页公开可访问并显示标题', async ({ page }) => {
    await page.goto('/');

    await expect(page).toHaveTitle('首页 - TaskFlow');
    await expect(
      page.getByRole('heading', { name: '欢迎使用 TaskFlow' }),
    ).toBeVisible();
  });

  test('未登录访问用户列表会跳转到登录页', async ({ page }) => {
    await page.goto('/users');

    await expect(page).toHaveURL(/\/login\?redirect=(%2F|\/)users/);
    await expect(page.getByRole('heading', { name: '登录' })).toBeVisible();
  });

  test('登录表单会校验空字段', async ({ page }) => {
    await page.goto('/login');
    await page.getByRole('button', { name: '登录' }).click();

    await expect(page.getByText('请输入邮箱')).toBeVisible();
    await expect(page.getByText('请输入密码')).toBeVisible();
  });

  test('使用演示账号登录后回到用户列表', async ({ page }) => {
    await page.goto('/login?redirect=/users');

    await page.getByPlaceholder('your@email.com').fill('admin@example.com');
    await page.getByPlaceholder('输入密码').fill('Admin123');
    await page.getByRole('button', { name: '登录' }).click();

    await expect(page).toHaveURL('http://localhost:5173/users');
    await expect(
      page.getByRole('heading', { name: '用户列表' }),
    ).toBeVisible();
  });

  test('未知路由显示 404', async ({ page }) => {
    await page.goto('/missing-page');

    await expect(page.getByRole('heading', { name: '404' })).toBeVisible();
  });
});
```

这些用例对应 Ch07 的真实行为：

- 首页和 404 在路由中标记了 `requiresAuth: false`，未登录也能访问。
- `/users` 默认受保护，守卫会带上 `redirect` 查询参数跳到登录页。
- 登录成功后，`safeRedirect` 只接受站内路径，因此回到 `/users`。
- 演示账号是 Ch08 中模拟认证的 `admin@example.com` / `Admin123`。

安装浏览器并运行：

```bash
pnpm --filter @taskflow/e2e exec playwright install chromium
pnpm --filter @taskflow/e2e test:e2e
```

> Linux CI 上把第一条命令换成 `playwright install --with-deps chromium`，让 Playwright 一并安装浏览器依赖的系统库。Windows 和 macOS 不需要 `--with-deps`。

> E2E 依赖真实的 API 和 Web。API 的 `env.ts` 要求 `DATABASE_URL`、`JWT_SECRET` 等变量，配置里的 `webServer.env` 已经注入；如果后续控制器改为真实数据库查询，需要为 E2E 准备独立的测试库，不能让测试写生产数据。

## 12.7 覆盖率：一次运行，统一汇总

覆盖率是**进程级**配置：project 配置里写 `coverage` 不会生效，必须在根配置中定义。也不要用 `turbo run test -- --coverage` 来汇总覆盖率——那会在每个包各起一个 Vitest 进程，得到多份互不相干的报告。更新根目录 `vitest.config.ts`：

```typescript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    projects: ['packages/shared', 'packages/ui', 'apps/api'],
    coverage: {
      provider: 'v8',
      reporter: ['text', 'json-summary', 'html'],
      reportsDirectory: './coverage',
      include: [
        'packages/shared/src/**/*.ts',
        'packages/ui/src/**/*.{ts,vue}',
        'apps/api/src/**/*.ts',
      ],
      exclude: [
        '**/*.test.ts',
        '**/*.spec.ts',
        '**/*.d.ts',
        'packages/shared/src/types/**',
        'apps/api/src/index.ts',
      ],
    },
  },
});
```

在根 `package.json` 增加：

```json
{
  "scripts": {
    "test": "turbo run test",
    "test:coverage": "vitest run --coverage",
    "test:e2e": "turbo run test:e2e"
  }
}
```

运行：

```bash
pnpm test:coverage
```

Vitest 会在一个进程里加载三个 project，把它们的覆盖率合并成一份 `coverage/` 报告。这取代了旧方案中"每个包生成 coverage 再用脚本复制合并"的做法——那个脚本还要处理 ESM 下的 `__dirname`、`require` 和 scope 名称，既脆弱又容易漏包。

`include` 和 `exclude` 的取舍：

- `packages/shared/src/types/**` 只有类型声明，运行时没有可执行代码，纳入统计只会拉低分母。
- `apps/api/src/index.ts` 是启动入口，测试不会监听端口，排除它是合理的。
- 不要排除所有 `index.ts`：`packages/shared/src/utils/index.ts` 里是真正的工具函数，排除后会漏掉核心逻辑。

覆盖率稳定后，可以在 `coverage` 下增加阈值，让 CI 在覆盖率下降时失败：

```typescript
thresholds: {
  lines: 80,
  functions: 80,
  branches: 70,
  statements: 80,
},
```

不要在项目初期就设一个很高的阈值——先让测试跑起来、看清基线，再逐步提高。

把覆盖率产物加入 `.gitignore`：

```txt
coverage/
playwright-report/
test-results/
.vitest/
```

## 12.8 用 Turborepo 只运行受影响的测试

更新 `turbo.json` 中的测试任务。下面是需要修改的部分，Ch10 里的 `build`、`dev`、`lint` 等任务保持不变：

```json
{
  "globalDependencies": [
    "packages/tsconfig/**",
    "packages/eslint-config/**",
    "vitest.shared.ts"
  ],
  "tasks": {
    "test": {
      "dependsOn": ["^build"],
      "inputs": [
        "src/**",
        "tests/**",
        "vitest.config.ts",
        "package.json"
      ]
    },
    "test:e2e": {
      "cache": false
    }
  }
}
```

几个配置的含义：

- `dependsOn: ["^build"]`：测试本身可以直接跑 TS 源码，但如果测试导入了 `@taskflow/database` 这类入口指向 `dist/` 的包，就必须先构建上游。Ch10 已经解释过 `^build` 和 `build` 的区别。
- `inputs`：只有源码、测试、Vitest 配置和 `package.json` 变化时，测试缓存才失效。改 `README.md` 不会重跑测试。
- `globalDependencies` 中加入 `vitest.shared.ts`：根目录的共享配置不属于任何包，`--affected` 默认不会因为它的变化而选中包。放进全局依赖后，它变化时所有任务都会重新计算哈希，`--affected` 也会选中所有包。代价是构建和 lint 的缓存也会失效——测试配置很少改动，这个代价可以接受。
- `test:e2e` 不缓存：E2E 依赖真实浏览器、端口和外部服务，结果不稳定，缓存收益低。

只运行受影响的测试：

```bash
# 与 main 分支比较，运行变更包及其下游包的测试
pnpm turbo run test --filter="...[origin/main]"

# 运行 shared 及其所有下游包的测试
pnpm turbo run test --filter=@taskflow/shared...

# 使用 Turborepo 的默认基线（通常是 main）自动判断
pnpm turbo run test --affected
```

假设只修改了 `packages/shared/src/utils/index.ts`。依赖图是 `apps/api → packages/shared`、`apps/web → packages/shared`，而 `apps/web` 没有测试脚本，因此实际范围是：

```txt
• Packages in scope: @taskflow/api, @taskflow/shared
@taskflow/shared:test: cache miss, executing
@taskflow/api:test: cache miss, executing
```

`packages/ui` 不依赖 `shared`，它的测试不会被选中。这正是依赖图的价值：范围由真实的包依赖决定，而不是靠人工维护一份"改了 A 要跑 B"的清单。

`--affected` 需要完整的 Git 历史。CI 中 `actions/checkout` 默认只取一个提交，必须设置 `fetch-depth: 0`，否则 Turborepo 无法计算 diff。

## 12.9 在 CI 中运行测试

把测试接入 GitHub Actions：

```yaml
name: test

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0

      - uses: pnpm/setup@v3
        with:
          cache: true
          require-lockfile: true

      - run: pnpm --filter @taskflow/e2e exec playwright install --with-deps chromium

      - if: github.event_name == 'pull_request'
        run: pnpm turbo run test --affected
        env:
          TURBO_TEAM: ${{ vars.TURBO_TEAM }}
          TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}

      - if: github.event_name == 'push'
        run: pnpm test:coverage

      - run: pnpm turbo run test:e2e
```

几个细节：

- `fetch-depth: 0` 是 `--affected` 的前提，不是可选项。
- 远程缓存凭据沿用 Ch11 的 `TURBO_TEAM` 和 `TURBO_TOKEN`；测试任务命中缓存时，日志会直接回放，连 Vitest 都不会启动。
- PR 阶段用 `--affected` 只跑受影响的包；push 到 `main` 时基线就是 `main` 自身，diff 为空，因此改为全量运行，并顺便生成覆盖率报告。
- E2E 单独运行，因为它需要浏览器和两个 `webServer`，不适合塞进每个包的单元测试任务。
- 覆盖率报告可以上传到 Codecov、Coveralls 或对象存储，本章不展开。

## 本章小结

1. **共享配置**：根目录 `vitest.shared.ts` 保存公共选项，各包用 `defineProject` 合并自己的环境；根 `vitest.config.ts` 用 `projects` 把三个测试层串起来。
2. **三个层次**：
   - 单元测试（shared）：纯函数、错误类、响应构造器，速度最快。
   - 组件测试（ui）：`@vue/test-utils` + jsdom，验证渲染、事件和禁用状态。
   - 集成测试（api）：supertest 直接请求真实的 Express `app`，覆盖中间件、Zod 验证和错误处理。
3. **E2E**：Playwright 作为独立 app，`webServer` 自动启动 API 和 Web，测试真实的登录与路由守卫。
4. **覆盖率**：在根配置的 `coverage` 中统一收集，一次 `vitest --coverage` 合并所有 project，不再需要复制脚本。
5. **增量运行**：`turbo run test --affected` / `--filter="...[origin/main]"` 只跑受影响的包；`inputs` 和 `globalDependencies` 保证缓存既快又正确。
