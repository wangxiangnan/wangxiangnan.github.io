# 第5章：npm 与包管理——你的依赖帝国

## 引言：站在巨人的肩膀上（然后被巨人压死）

npm（Node Package Manager）是世界上最大的软件注册表——超过 200 万个包，每周数十亿次下载。它让你可以用一行命令就引入全世界最优秀的开源代码。

但正如蜘蛛侠的叔叔说的："能力越大，责任越大。" npm 的强大也带来了经典的 `node_modules` 黑洞问题：

```
宇宙中最重的东西：
1. 太阳          1.989 × 10^30 kg
2. 黑洞          取决于质量
3. node_modules  无法测量
```

这一章，我们来全面掌握 Node.js 的包管理生态。

## 5.1 包管理器三国演义：npm vs yarn vs pnpm

### npm：元老，默认的选择

npm 是 Node.js 自带的包管理器，不需要额外安装。

```bash
# 初始化项目
npm init -y

# 安装依赖
npm install express                 # 生产依赖
npm install -D typescript           # 开发依赖（-D = --save-dev）
npm install -g nodemon              # 全局安装

# 安装特定版本
npm install lodash@4.17.21
npm install react@^18.0.0

# 删除依赖
npm uninstall express
npm rm express                      # 简写

# 更新依赖
npm update                          # 更新所有
npm update express                  # 更新特定包
npm outdated                        # 查看过时的包

# 运行脚本
npm run dev
npm start                           # start/test/stop 可省略 run
npm test

# 查看包信息
npm info express
npm view express versions           # 查看所有版本
```

**npm 的安装策略**：扁平化安装（flat node_modules）

```
node_modules/
├── express/           ← 直接放在顶层
├── body-parser/       ← express 的依赖也提升到顶层
├── debug/             ← body-parser 的依赖也提升
└── ...
```

### yarn：曾经的救星

Facebook 在 2016 年发布 yarn，解决了当时 npm 的速度和确定性问题。

```bash
# 安装 yarn
npm install -g yarn
# 或者用 corepack（Node.js 16+）
corepack enable
corepack prepare yarn@stable --activate

# 基本命令
yarn init -y
yarn add express                    # 安装依赖
yarn add -D typescript              # 开发依赖
yarn global add nodemon             # 全局安装
yarn remove express                 # 删除
yarn upgrade                        # 更新

# yarn 独有功能
yarn why lodash                     # 为什么安装了这个包
yarn workspaces info                # workspace 信息
```

**Yarn Classic (v1)** vs **Yarn Berry (v2+)**：

- Yarn Classic：和 npm 类似的 node_modules 结构
- Yarn Berry：引入 PnP（Plug'n'Play），完全不需要 node_modules！

### pnpm：新时代的王者

pnpm（Performant npm）用独特的方式解决了 npm/yarn 的核心问题。

```bash
# 安装 pnpm
npm install -g pnpm
# 或者用 corepack
corepack enable
corepack prepare pnpm@latest --activate

# 基本命令（和 npm 几乎一样）
pnpm init
pnpm add express
pnpm add -D typescript
pnpm remove express
pnpm update
pnpm run dev

# pnpm 独有
pnpm store status                   # 查看全局存储状态
pnpm store prune                    # 清理未引用的包
```

**pnpm 的杀手锏：基于内容寻址的全局存储 + 符号链接**

```
全局存储（~/.pnpm-store/）：
  所有版本的所有包只存储一份！

项目 node_modules 结构：
node_modules/
├── .pnpm/                          ← 真实的包文件（通过硬链接指向全局存储）
│   ├── express@4.18.2/
│   │   └── node_modules/
│   │       ├── express/            ← 硬链接到全局存储
│   │       ├── body-parser/        ← express 的依赖在这里
│   │       └── ...
│   └── lodash@4.17.21/
│       └── node_modules/
│           └── lodash/
├── express -> .pnpm/express@4.18.2/node_modules/express  ← 符号链接
└── lodash -> .pnpm/lodash@4.17.21/node_modules/lodash
```

### 三者对比

| 特性 | npm | yarn (classic) | pnpm |
| ------ | ----- | --------------- | ------ |
| 速度 | 中等 | 快 | 最快 |
| 磁盘空间 | 大（每项目一份） | 大 | 小（全局存储+硬链接） |
| 幽灵依赖 | ⚠️ 有 | ⚠️ 有 | ✅ 无 |
| Lock 文件 | package-lock.json | yarn.lock | pnpm-lock.yaml |
| Monorepo | workspaces | workspaces | workspaces（最佳） |
| node_modules 结构 | 扁平 | 扁平 | 嵌套+符号链接 |
| 内置于 Node.js | ✅ | ❌ | ❌ |

### 什么是幽灵依赖（Phantom Dependencies）？

```javascript
// 假设你只安装了 express
// npm install express

// express 依赖了 body-parser
// npm 的扁平结构把 body-parser 也提升到了 node_modules 顶层

// ❌ 于是你可以直接 import 没有声明在 package.json 中的包！
import bodyParser from 'body-parser'; // 居然能用！

// 但这是不可靠的！
// 1. 如果 express 未来不再依赖 body-parser，你的代码就崩了
// 2. body-parser 的版本完全由 express 决定，不受你控制
// 3. pnpm 的严格模式下这会直接报错（这是好事）
```

pnpm 通过其独特的 node_modules 结构，天然地杜绝了幽灵依赖——你只能 import 自己 `package.json` 中声明的依赖。

## 5.2 package.json vs package-lock.json

### package.json：声明"我想要什么"

```json
{
  "dependencies": {
    "express": "^4.18.0"    // 我想要 4.18.x 以上的 express
  }
}
```

### package-lock.json：记录"我实际得到了什么"

```json
{
  "packages": {
    "node_modules/express": {
      "version": "4.18.2",           // 实际安装的精确版本
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-...",     // 完整性校验
      "dependencies": {
        "body-parser": "1.20.1",     // 子依赖的精确版本
        "cookie": "0.5.0",
        // ...
      }
    }
  }
}
```

**为什么需要 lock 文件？**

```
场景：你的 package.json 写 "express": "^4.18.0"

你安装时：   express@4.18.2（当时的最新4.x）
半年后同事安装：express@4.19.1（新发布了）

→ 两个人的 node_modules 不一样！
→ "在我电脑上明明能跑啊"问题重现

有了 lock 文件：两个人安装的都是精确的 4.18.2
→ 确保环境一致
```

**Lock 文件的规则**：

- ✅ 必须提交到 Git（应用项目）
- ❌ 不提交到 Git（如果是发布为 npm 包的库——库的 lock 文件不会被消费者使用）
- 🔄 用 `npm ci` 而不是 `npm install` 在 CI/CD 中安装（严格按照 lock 文件安装）

```bash
# npm install：可能更新 lock 文件
# npm ci：严格按照 lock 文件安装，更快更可靠
npm ci  # CI/CD 环境推荐
```

## 5.3 语义化版本（SemVer）详解

### 版本号格式

```
主版本.次版本.修订号
 MAJOR . MINOR . PATCH
   1   .   2   .   3

含义：
MAJOR：不兼容的 API 变更（Breaking Changes）
MINOR：向下兼容的新功能（New Features）
PATCH：向下兼容的 Bug 修复（Bug Fixes）

预发布版本：1.0.0-alpha.1, 1.0.0-beta.2, 1.0.0-rc.1
构建元数据：1.0.0+20240101
```

### ^ 和 ~ 的区别

```
"express": "^4.18.2"
           ↑ 锁定主版本
           允许：4.18.2, 4.18.3, 4.19.0, 4.99.99
           不允许：5.0.0

"express": "~4.18.2"
           ↑ 锁定主版本+次版本
           允许：4.18.2, 4.18.3, 4.18.99
           不允许：4.19.0

"express": "4.18.2"
           ↑ 精确版本，不允许任何更新

"express": "*"
           ↑ 任何版本（危险！别用！）

"express": ">=4.18.0 <5.0.0"
           ↑ 范围写法（和 ^ 等价）
```

### 实际建议

```json
{
  "dependencies": {
    // 大多数情况用 ^（npm 默认）
    "express": "^4.18.2",

    // 对于 0.x 版本的包要小心！
    // ^0.2.3 只允许 0.2.x（因为 0.x 被认为是不稳定的）
    "some-new-lib": "^0.2.3",

    // 确实需要精确版本时（比如有已知bug的特定版本间）
    "problematic-lib": "2.1.3"
  }
}
```

## 5.4 npm scripts 的强大

### 基本用法

```json
{
  "scripts": {
    "dev": "node --watch --env-file=.env src/index.mjs",
    "build": "tsc && cp package.json dist/",
    "start": "node dist/index.mjs",
    "test": "node --test 'src/**/*.test.mjs'",
    "lint": "eslint src/",
    "format": "prettier --write 'src/**/*.{js,ts,mjs}'",
    "typecheck": "tsc --noEmit",
    "clean": "rm -rf dist node_modules",
    "prepare": "husky install"
  }
}
```

### 生命周期钩子：pre 和 post

```json
{
  "scripts": {
    "prebuild": "npm run clean && npm run typecheck",
    "build": "tsc",
    "postbuild": "echo '构建完成！'",

    "pretest": "npm run lint",
    "test": "node --test",
    "posttest": "echo '测试通过！'",

    "preinstall": "node scripts/check-env.mjs",
    "prepare": "husky install"
  }
}
```

执行 `npm run build` 时，实际执行顺序：`prebuild` → `build` → `postbuild`

### 并行与串行执行

```json
{
  "scripts": {
    // 串行执行（&&）：前一个成功才执行下一个
    "build": "npm run typecheck && npm run compile && npm run copy-assets",

    // 并行执行：使用 npm-run-all 或 concurrently
    "dev": "concurrently \"npm run dev:server\" \"npm run dev:client\"",

    // 或者用 npm-run-all
    "dev:all": "run-p dev:server dev:client dev:worker",
    "build:all": "run-s clean typecheck compile",

    // Node.js 原生方式（使用 & 但只在 Unix 生效）
    "dev:unix": "node server.mjs & node worker.mjs"
  }
}
```

### 传递参数

```bash
# 通过 -- 传递额外参数
npm run test -- --grep "auth"
# 等同于执行：node --test --grep "auth"

npm run dev -- --port 8080
```

### 环境变量

```javascript
// npm scripts 中可用的环境变量
// npm_package_* 可以访问 package.json 的字段
console.log(process.env.npm_package_name);     // 包名
console.log(process.env.npm_package_version);  // 版本号

// npm_lifecycle_event 是当前执行的脚本名
console.log(process.env.npm_lifecycle_event);  // "build" / "test" / ...
```

## 5.5 发布自己的 npm 包

### 完整流程

```bash
# 1. 创建项目
mkdir my-awesome-util && cd my-awesome-util
npm init

# 2. 编写代码（略）

# 3. 注册 npm 账号（如果还没有）
npm adduser

# 4. 登录
npm login

# 5. 检查包名是否可用
npm search my-awesome-util
# 或直接看 https://www.npmjs.com/package/my-awesome-util

# 6. 发布前检查
npm pack --dry-run  # 查看会发布哪些文件
npm publish --dry-run  # 模拟发布

# 7. 正式发布
npm publish
# 作用域包需要加 --access public
npm publish --access public

# 8. 版本更新
npm version patch  # 1.0.0 → 1.0.1
npm version minor  # 1.0.0 → 1.1.0
npm version major  # 1.0.0 → 2.0.0
npm publish

# 9. 废弃一个版本（不是删除）
npm deprecate my-awesome-util@1.0.0 "有严重bug，请升级到1.0.1"

# 10. 撤销发布（72小时内可以）
npm unpublish my-awesome-util@1.0.0
```

### 发布前的 package.json 配置

```json
{
  "name": "@yourname/my-util",
  "version": "1.0.0",
  "description": "一个很有用的工具库",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ],
  "keywords": ["utility", "helper", "tool"],
  "author": "Your Name",
  "license": "MIT",
  "repository": {
    "type": "git",
    "url": "https://github.com/you/my-util.git"
  },
  "engines": {
    "node": ">=18.0.0"
  },
  "scripts": {
    "build": "tsup src/index.ts --format cjs,esm --dts",
    "prepublishOnly": "npm run build"
  }
}
```

## 5.6 npx 的妙用

npx 是 npm 5.2+ 自带的命令执行工具，有两大用途：

### 用途1：执行本地安装的包

```bash
# 不用 npx 时，要写完整路径
./node_modules/.bin/eslint src/

# 有了 npx，直接用
npx eslint src/
```

### 用途2：临时使用包（不安装到项目）

```bash
# 创建项目脚手架
npx create-react-app my-app
npx create-vite my-app
npx create-next-app my-app

# 临时使用工具
npx http-server .              # 快速起一个静态文件服务器
npx json-server db.json        # 快速 Mock API
npx kill-port 3000             # 杀死占用端口的进程
npx npm-check-updates -u       # 检查并更新所有依赖
npx tsc --init                 # 生成 tsconfig.json
npx license MIT                # 生成 LICENSE 文件

# 指定版本
npx node@18 script.mjs         # 用指定版本的 Node.js 运行

# 执行 GitHub gist
npx https://gist.github.com/yourname/xxxxx
```

## 5.7 Monorepo 与 Workspace

### 什么是 Monorepo？

将多个相关项目放在一个代码仓库中管理：

```
my-monorepo/
├── package.json              ← 根目录配置
├── packages/
│   ├── core/                 ← 核心库
│   │   ├── package.json
│   │   └── src/
│   ├── cli/                  ← CLI 工具
│   │   ├── package.json
│   │   └── src/
│   ├── server/               ← 服务端应用
│   │   ├── package.json
│   │   └── src/
│   └── shared/               ← 共享工具
│       ├── package.json
│       └── src/
└── pnpm-workspace.yaml       ← pnpm workspace 配置
```

### npm Workspaces

```json
// 根目录 package.json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": [
    "packages/*"
  ]
}
```

```bash
# 在特定 workspace 中运行命令
npm run build -w packages/core
npm run test --workspace=packages/server

# 在所有 workspace 中运行
npm run build --workspaces
npm run test -ws

# 给特定 workspace 添加依赖
npm install lodash -w packages/core
```

### pnpm Workspace（推荐）

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

```bash
# pnpm workspace 命令
pnpm add lodash --filter @myorg/core
pnpm run build --filter @myorg/server
pnpm run test --filter "./packages/**"
pnpm -r run build  # 递归执行所有包的 build

# 内部包引用
# packages/server/package.json
{
  "dependencies": {
    "@myorg/core": "workspace:*",    # 使用 workspace 协议
    "@myorg/shared": "workspace:^"
  }
}
```

## 5.8 安全审计

### npm audit

```bash
# 检查已知漏洞
npm audit

# 输出示例：
# ┌─────────────────┬────────────────────────────────────────┐
# │ High            │ Prototype Pollution in lodash           │
# ├─────────────────┼────────────────────────────────────────┤
# │ Package         │ lodash                                 │
# │ Patched in      │ >=4.17.21                              │
# │ Dependency of   │ my-old-lib                             │
# │ Path            │ my-old-lib > lodash                    │
# └─────────────────┴────────────────────────────────────────┘

# 自动修复（安全的更新）
npm audit fix

# 强制修复（可能有 breaking changes）
npm audit fix --force

# 只检查生产依赖
npm audit --omit=dev

# JSON 格式输出（CI/CD 中有用）
npm audit --json
```

### 依赖安全最佳实践

```json
// .npmrc
// 限制安装时执行的脚本（防止恶意包）
ignore-scripts=true

// 安装后手动运行需要的 lifecycle scripts
// npm rebuild
```

```bash
# 使用 socket.dev 或 snyk 做更深入的审计
npx socket optimize
npx snyk test

# 锁定依赖的确切来源
npm config set registry https://registry.npmjs.org/
```

## 5.9 .npmrc 配置与私有 Registry

### .npmrc 文件位置（优先级从高到低）

```
1. 项目级：/path/to/project/.npmrc
2. 用户级：~/.npmrc
3. 全局级：$PREFIX/etc/npmrc
4. npm 内置：/path/to/npm/npmrc
```

### 常用配置

```ini
# .npmrc

# 设置 registry（私有源）
registry=https://registry.npmmirror.com/

# 作用域包使用私有 registry
@mycompany:registry=https://npm.mycompany.com/

# 认证
//npm.mycompany.com/:_authToken=${NPM_TOKEN}

# 安装行为
save-exact=true          # 安装时使用精确版本（不加 ^）
engine-strict=true       # 强制检查 engines 字段
auto-install-peers=true  # 自动安装 peerDependencies

# 国内镜像加速
registry=https://registry.npmmirror.com/
# 也可以针对特定包设置
disturl=https://npmmirror.com/mirrors/node/
electron_mirror=https://npmmirror.com/mirrors/electron/
sass_binary_site=https://npmmirror.com/mirrors/node-sass/
```

### 私有 Registry 方案

```bash
# 方案1：GitHub Packages
@myorg:registry=https://npm.pkg.github.com/

# 方案2：GitLab Packages
@myorg:registry=https://gitlab.com/api/v4/packages/npm/

# 方案3：自建（Verdaccio）
# docker run -d --name verdaccio -p 4873:4873 verdaccio/verdaccio
registry=http://localhost:4873/

# 方案4：云服务（AWS CodeArtifact, Azure Artifacts, 阿里云等）
```

## 5.10 常见坑点

### 坑1：node_modules 地狱

```bash
# 清理重装（解决诡异问题的万能药）
rm -rf node_modules package-lock.json
npm install
# 或者
npx npkill  # 交互式删除 node_modules（可以批量清理多个项目）
```

### 坑2：版本冲突

```bash
# 查看为什么安装了某个包
npm explain lodash
npm ls lodash

# pnpm
pnpm why lodash
```

### 坑3：忘记区分 dependencies 和 devDependencies

```bash
# ❌ 把只在开发时用的包装到 dependencies
npm install jest           # 测试框架不该在生产环境

# ✅ 正确做法
npm install -D jest        # 开发依赖
npm install -D typescript
npm install -D eslint
npm install -D @types/node

# 生产环境安装时跳过 devDependencies
npm install --omit=dev
# 或设置环境变量
NODE_ENV=production npm install
```

### 坑4：lock 文件冲突

```bash
# 合并 lock 文件冲突时，不要手动解决！
# 接受任一方的版本，然后重新安装

git checkout --theirs package-lock.json  # 或 --ours
npm install
# npm 会重新生成正确的 lock 文件
```

## 5.11 本章小结

| 知识点 | 核心要点 |
| -------- | --------- |
| npm/yarn/pnpm | pnpm 最省空间最严格，npm 最通用，yarn PnP 最前卫 |
| lock 文件 | 保证环境一致性，必须提交到 Git |
| SemVer | ^锁主版本，~锁主+次，无符号精确匹配 |
| npm scripts | pre/post 钩子，串行&&，并行用工具 |
| 发布包 | exports map + files 白名单 + prepublishOnly |
| monorepo | workspace 协议管理内部依赖 |
| 安全 | npm audit + lock 文件 + .npmrc 配置 |

**一句话总结**：包管理器是你的后勤部队——选对工具（推荐 pnpm），管好版本（lock 文件），看好大门（安全审计）。
