## 10.1 本章目标

- 理解 Turborepo 的三个核心概念：Task、Dependency Graph、Cache

- 理解 `dependsOn` 的三种模式及其适用场景

## 10.2 为什么需要 Turborepo？

假设你要手动完成一次完整构建，可能会写出这样的脚本：

```bash
# 先构建被依赖的包
cd packages/shared && pnpm build
cd ../database && pnpm build

# 再构建应用
cd ../../apps/api && pnpm build
cd ../web && pnpm build
```

这个脚本有三个问题：

1. **顺序靠人维护**：依赖关系一变，脚本就失效。`database` 和 `shared` 之间没有依赖，却被强行串行。
2. **没有增量**：只改了一行代码，所有包都要重新编译。
3. **没有缓存**：同一份输入在本地和 CI 各构建一次，产物无法复用。

Turborepo 是一个**任务编排引擎**：它读取每个 `package.json` 的依赖关系，构建任务图，按拓扑顺序并行执行任务，并用内容哈希缓存结果。

需要说明的是，Turborepo 不负责打包，也不替代 Vite / tsc / Vitest。它只回答三个问题：**先跑谁、能不能并行、这次能不能跳过**。

## 10.3 安装与根脚本

Ch02 已经把 `turbo` 放进了根目录的 `devDependencies`。这里确认并锁定版本：

```bash
pnpm add -Dw turbo@^2.11.0
```

> **为什么是 `-Dw`？** `turbo` 只在开发和 CI 中使用，不应出现在任何生产依赖里。`-w` 表示安装到 workspace 根目录，这样根脚本可以直接调用它。

确认根 `package.json` 的 scripts（Ch09 已补齐 lint 和 format）：

```json
{
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "lint:fix": "turbo run lint:fix",
    "typecheck": "turbo run typecheck",
    "test": "turbo run test",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "prepare": "husky"
  }
}
```

`.gitignore` 中应包含：

```txt
# Turborepo
.turbo
```

Turborepo 会在根目录和每个包的 `.turbo/` 下存放本地缓存与运行日志。它们是本地产物，不提交。Ch11 会解释这些目录的具体结构。

## 10.4 turbo.json 核心配置

在根目录创建（或更新）`turbo.json`：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "globalDependencies": ["packages/tsconfig/**", "packages/eslint-config/**"],
  "globalEnv": ["CI", "NODE_ENV"],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs": [
        "src/**",
        "prisma/**",
        "prisma.config.ts",
        ".env*",
        "tsconfig.json",
        "package.json"
      ],
      "outputs": ["dist/**"],
      "env": ["VITE_APP_TITLE", "VITE_API_ORIGIN"]
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    },
    "lint": {
      "inputs": ["src/**", "tests/**", "eslint.config.js", "package.json"]
    },
    "lint:fix": {
      "cache": false
    },
    "typecheck": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tsconfig.json", "package.json"]
    },
    "test": {
      "dependsOn": ["^build"],
      "inputs": ["src/**", "tests/**", "vitest.config.*", "package.json"]
    },
    "clean": {
      "cache": false
    }
  }
}
```

逐块解释：

### `$schema`

```json
"$schema": "https://turborepo.dev/schema.json"
```

让 IDE 校验字段并补全。Turborepo 2.x 的官方 schema 地址是 `turborepo.dev`，`turbo.build/schema.json` 仍会重定向，但新项目应直接使用前者。

### `tasks`

`tasks` 的每个 key 对应各包 `package.json` 里的脚本名。运行 `turbo run build` 时，Turborepo 会：

1. 找出所有定义了 `build` 脚本的包；
2. 根据包依赖关系构建任务图；
3. 按 `dependsOn` 排序，尽可能并行；
4. 对每个任务计算 hash，命中缓存则跳过。

没有定义某个脚本的包会被直接跳过，不会报错。`packages/ui` 就没有 `build` 脚本（它以源码形式被消费），因此不会出现在 `turbo run build` 的执行列表里。

## 10.5 深入理解 `dependsOn`：三种模式

### 模式一：`"^build"` — 先构建上游依赖

```json
"build": {
  "dependsOn": ["^build"]
}
```

`^` 表示**上游包**。构建 `apps/web` 之前，先构建它依赖的所有包。依赖链如下：

```
apps/web → packages/ui
apps/web → packages/shared
apps/api → packages/database
apps/api → packages/shared
```

执行顺序：

```bash
$ turbo run build

• Packages in scope: @taskflow/api, @taskflow/database, @taskflow/shared, @taskflow/web
• Running build in 4 packages
• Remote caching disabled

@taskflow/shared:build: cache miss
@taskflow/database:build: cache miss
  # shared 和 database 没有依赖关系，并行执行

@taskflow/api:build: cache miss, depends on database, shared
@taskflow/web:build: cache miss, depends on shared
  # api 和 web 并行执行

Tasks:    4 successful, 4 total
Cached:   0 cached, 4 total
Time:     9.2s
```

`packages/ui` 没有 `build` 脚本，但它是 `apps/web` 的依赖。Vite 在构建 web 时会直接编译 ui 的 Vue 源码，因此不需要单独构建。

### 模式二：`"build"`（不带 `^`）— 只依赖自身

```json
"test": {
  "dependsOn": ["build"]
}
```

含义：运行当前包的 `test` 之前，先运行**同一个包**的 `build`。上游包是否构建过，不关心。

本教程的 `test` 用的是 `"^build"` 而不是 `"build"`：Vitest 可以直接执行 TS 源码，测试本身不需要当前包先构建；但测试可能 import `@taskflow/database`，而 database 的入口指向 `dist/`，所以需要先构建上游。

**选择规则：**

- 任务读取当前包的构建产物（例如 Node 直接运行 `dist/index.js`）→ `"build"`。
- 任务只需要上游包的产物，自己可以直接跑源码（Vitest、ESLint）→ `"^build"` 或 `[]`。

### 模式三：`[]` — 无依赖

```json
"lint": {
  "dependsOn": []
}
```

lint 可以立即并行执行，不需要等任何构建。前提是使用**非类型感知**规则（`tseslint.configs.recommended`），本教程正是如此。

如果启用 `recommendedTypeChecked`，ESLint 需要读取依赖包的 `.d.ts`，就必须改成：

```json
"lint": {
  "dependsOn": ["^build"],
  "inputs": ["src/**", "eslint.config.js", "tsconfig.json", "package.json"]
}
```

> **`dependsOn: []` 与省略 `dependsOn` 的区别**：两者都表示"没有依赖"。显式写空数组是为了让读者一眼看出这是有意为之，而不是漏配。

一个必须记住的限制：**persistent 任务不能作为 `dependsOn` 的目标**。`dev` 是长期运行的进程，永远不"完成"，所以 `test` 不能写 `dependsOn: ["dev"]`。Turborepo 会直接报错。

## 10.6 `inputs` 和 `outputs`

### `inputs`：哪些文件影响任务结果

```json
"build": {
  "inputs": ["src/**", "prisma/**", "prisma.config.ts", "tsconfig.json", "package.json"]
}
```

Turborepo 默认会把包内的所有文件纳入 hash。显式声明 `inputs` 后，只监控这些文件——改 `README.md` 不会让构建缓存失效。

`prisma/**` 和 `prisma.config.ts` 只对 `packages/database` 有意义，对其他包是无害的空匹配。database 的 `build` 会执行 `prisma generate`，Schema 变化必须触发重建。

**为什么 `package.json` 也要算输入？** 依赖版本变化会改变构建结果。锁文件在根目录，由 Turborepo 自动纳入全局 hash；包自己的 `package.json` 仍需显式声明。

**为什么 `.env*` 也在输入里？** Vite 在构建时读取 `apps/web/.env`，`VITE_*` 变量会被静态替换进产物。仅靠 `env` 只能捕获进程环境变量，捕获不到 `.env` 文件内容的变化，所以两者都要声明。

### `outputs`：任务产出什么

```json
"build": {
  "outputs": ["dist/**"]
}
```

缓存命中时，Turborepo 会直接把缓存的 `dist/` 恢复到工作区。**忘记配置 `outputs` 的后果**：任务仍然会被缓存，但只缓存日志，不会恢复文件；下游任务拿到空目录后构建失败，而且错误信息通常很隐晦。

`packages/ui` 没有 `dist`，因此没有 `outputs`；如果将来给 ui 加上构建步骤，要同步补上 `"outputs": ["dist/**"]`。

## 10.7 `cache` 和 `persistent`

```json
"dev": {
  "dependsOn": ["^build"],
  "cache": false,
  "persistent": true
}
```

- **`cache: false`**：`vite`、`tsx watch` 这类开发服务器每次启动都是新进程，缓存输出没有意义。
- **`persistent: true`**：告诉 Turborepo 这个任务不会自行退出。Turborepo 不会等它结束，也不会把它的输出当成其他任务的前置条件。

**关于 `persistent` 的常见误解：**

- 它不是"禁止并行"。多个 persistent 任务（web dev、api dev）会同时运行。
- 它不能出现在别人的 `dependsOn` 里。`persistent` 任务永远不会完成，等它等于死锁。
- 它必须搭配 `cache: false`。缓存一个永不结束的任务没有意义。

`dev` 为什么还要 `dependsOn: ["^build"]`？因为 `@taskflow/database` 的入口指向编译后的 `dist/`，API 启动时需要它存在。`shared` 通过 `development` 条件解析 TS 源码，`ui` 的 `exports` 直接指向源码，两者在开发时都不需要构建；所以这一步通常只会在第一次启动时构建 database，之后全部命中缓存。

## 10.8 `globalDependencies` 与环境变量

### `globalDependencies`

```json
"globalDependencies": ["packages/tsconfig/**", "packages/eslint-config/**"]
```

这些路径下的任何变化都会让**所有任务**的缓存失效。

为什么是这两个目录？

- `packages/tsconfig` 被所有包 `extends`，编译选项变了，所有产物都可能变。
- `packages/eslint-config` 被所有包引用，规则变了，lint 结果就会变。

这两个包不在应用的构建依赖图里，Turborepo 不会自动感知它们的变化，必须通过 `globalDependencies` 显式纳入全局 hash。

代价是：改一行 ESLint 规则，所有任务的缓存都会失效。对配置包来说这是正确的取舍——配置的影响范围本来就是全局的。

### `globalEnv` 与任务级 `env`

```json
"globalEnv": ["CI", "NODE_ENV"],
"tasks": {
  "build": {
    "env": ["VITE_APP_TITLE", "VITE_API_ORIGIN"]
  }
}
```

环境变量的值参与 hash 计算。设想你在 `NODE_ENV=development` 下构建过一次，随后切换到 `production`；如果 `NODE_ENV` 没有声明，Turborepo 会认为输入没变，直接把开发模式的缓存产物还给你。

- `globalEnv`：影响所有任务，适合 `CI`、`NODE_ENV`。
- 任务级 `env`：影响该任务在**所有包**中的 hash。`VITE_*` 只有 web 构建会读取，但写在 `build.env` 里会让每个包的 build 都把它算进 hash；对本项目来说，这点额外失效可以接受。
- `env` 支持通配符，例如 `"VITE_*"` 可以一次覆盖所有 Vite 变量。

> **`env` 不只是 hash 输入，它还是 strict 模式下的"白名单"。** 默认 `envMode: "strict"` 会把任务环境过滤到 `env`、`globalEnv`、`passThroughEnv` 声明的变量；漏声明的变量在任务里会直接读不到。变量值仍来自 shell、CI 或 `.env`，Turborepo 不会凭空生成。不要把密钥放进 `env` 来"传递"——strict 模式下它确实能被任务读到，但密钥会进入缓存键，轮换密钥就等于让所有缓存失效；构建期不需要的密钥应当留在运行时注入。

## 10.9 实际运行：执行顺序与缓存

### 场景一：首次 `turbo run build`

```bash
$ pnpm build

turbo 2.11.0

• Packages in scope: @taskflow/api, @taskflow/database, @taskflow/shared, @taskflow/web
• Running build in 4 packages
• Remote caching disabled

@taskflow/shared:build: cache miss, executing
@taskflow/database:build: cache miss, executing

@taskflow/api:build: cache miss, depends on database, shared
@taskflow/web:build: cache miss, depends on shared

Tasks:    4 successful, 4 total
Cached:   0 cached, 4 total
Time:     9.2s
```

### 场景二：再次运行（全部命中）

```bash
$ pnpm build

turbo 2.11.0
• Running build in 4 packages

@taskflow/shared:build: cache hit, replaying logs
@taskflow/database:build: cache hit, replaying logs
@taskflow/api:build: cache hit, replaying logs
@taskflow/web:build: cache hit, replaying logs

Tasks:    4 successful, 4 total
Cached:   4 cached, 4 total
Time:     180ms
```

第二次运行甚至没有真正执行构建，只是回放了日志并恢复 `dist/`。

### 场景三：只改 `packages/shared` 的一个文件

```bash
@taskflow/shared:build: cache miss      # 源码变了
@taskflow/database:build: cache hit     # 不依赖 shared
@taskflow/api:build: cache miss         # 依赖 shared（和 database）
@taskflow/web:build: cache miss         # 依赖 shared
```

受影响的任务重新执行，无关任务继续命中缓存。这就是"增量构建"。

### 场景四：用 `--filter` 只构建 web 及其依赖

```bash
$ turbo run build --filter=@taskflow/web

• Packages in scope: @taskflow/shared, @taskflow/ui, @taskflow/web
• Running build in 2 packages

@taskflow/shared:build: cache hit
@taskflow/web:build: cache miss
```

`@taskflow/ui` 在 scope 里，但没有 `build` 脚本，所以实际执行的只有 shared 和 web。

### 场景五：只运行受影响的任务

```bash
# 与 main 分支比较，只运行受影响的包
turbo run build --filter=...[main]
```

`...[main]` 表示"自 main 分支以来发生变化的包及其下游"。CI 中常用这个模式把全量构建压缩成增量构建。

## 10.10 与 npm scripts 的对比

| 能力 | 手写 npm scripts | Turborepo |
| ------ | ----------------- | ----------- |
| 执行顺序 | 手动维护 | 根据依赖图自动拓扑排序 |
| 并行度 | 通常串行 | 无依赖任务自动并行 |
| 缓存 | 无 | 内容哈希 + 产物恢复 |
| 过滤执行 | 手动 `cd` / `--filter` | `--filter` 支持包名、目录、git 变更 |
| 远程缓存 | 需要自建 | 原生支持（Ch11） |
| 任务图 | 无 | `--graph` |

Turborepo 不是万能的：如果仓库只有一个包，直接用 npm scripts 更简单；跨语言、跨工具链的复杂编排，可能需要 Bazel / Nx。对于 TypeScript 全栈 monorepo，Turborepo 的复杂度与收益比最合适。

## 10.11 为各个包补全构建脚本

Turborepo 只调用各包已有的脚本。下面是与前几章实现一致的最终版本。

**packages/shared/package.json**（Ch05 的实现，`tsc` 输出 ESM，不产出 CJS）：

```json
{
  "name": "@taskflow/shared",
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "dev": "tsc -p tsconfig.json --watch",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc --noEmit"
  }
}
```

**packages/ui/package.json**（源码即产物，没有 build）：

```json
{
  "name": "@taskflow/ui",
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "vue-tsc --noEmit"
  }
}
```

**packages/database/package.json**（Prisma 7：先 generate 再编译）：

```json
{
  "name": "@taskflow/database",
  "scripts": {
    "build": "prisma generate && tsc -p tsconfig.json",
    "db:generate": "prisma generate",
    "db:migrate": "prisma migrate dev",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc --noEmit"
  }
}
```

**apps/web/package.json**：

```json
{
  "name": "@taskflow/web",
  "scripts": {
    "build": "vue-tsc --noEmit && vite build",
    "dev": "vite",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "vue-tsc --noEmit"
  }
}
```

**apps/api/package.json**：

```json
{
  "name": "@taskflow/api",
  "scripts": {
    "build": "tsc -p tsconfig.json",
    "dev": "tsx watch --conditions=development src/index.ts",
    "start": "node dist/index.js",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc --noEmit"
  }
}
```

几点说明：

- **不要用 `tsup --format cjs`**。`apps` 和 `packages` 都是 ESM（各自声明 `"type": "module"`），shared 的导出、api 的入口也全是 ESM，额外产出 CJS 只会引入"双重包"问题。Node 24 对 ESM 的支持已经完整。
- **`build` 的 `outputs` 只声明真正产出 `dist/` 的包**。shared、database、api、web 都有 `dist/`；ui 没有。
- **`test` 脚本会在 Ch12 添加**。现在 `turbo run test` 会提示没有包定义该任务，这是正常的。
- 所有 `lint` / `lint:fix` 脚本都与 Ch09 的配置对应；`eslint .` 会使用各自目录下的 `eslint.config.js`。

## 10.12 用 `--graph` 可视化任务依赖

```bash
# 输出 DOT 到标准输出
turbo run build --graph

# 写入文件；扩展名决定格式，生成 SVG 需要本机安装 Graphviz
turbo run build --graph=build-graph.svg
```

DOT 内容可以粘贴到 [Graphviz Online](https://dreampuf.github.io/GraphvizOnline/) 查看。依赖图在排查"为什么某个包没有重新构建"时特别有用：如果 `api` 不在图里，说明它的 `build` 脚本没有被 Turborepo 识别；如果 `database → api` 的边缺失，说明 `package.json` 里的依赖没有声明。

## 本章小结

- Turborepo 只负责编排：先跑谁、能否并行、能否跳过
- `dependsOn` 的 `^` 表示上游包；`"build"` 表示当前包；`[]` 表示无依赖
- `inputs` / `outputs` 决定缓存是否准确；漏配 `outputs` 会导致缓存命中但产物缺失
- `persistent: true` 的任务必须 `cache: false`，且不能作为其他任务的依赖
- 配置包（tsconfig、eslint-config）通过 `globalDependencies` 参与全局缓存失效
- 构建脚本必须与项目的模块格式一致：本项目全链路 ESM，不需要 tsup 产出 CJS
