# 第18章：其他应用层协议——SMTP、FTP、SSH

## SMTP：邮件发送协议

SMTP（Simple Mail Transfer Protocol，简单邮件传输协议）是 1982 年在 RFC 821 中定义的。它的设计简单到令人惊讶——本质上就是一个基于文本的命令-响应协议，你用 Telnet 就能手动发一封邮件。

**SMTP 会话流程**：

```
Client → Server: [TCP 连接建立，端口 25 或 587]
Server → Client: 220 mail.example.com ESMTP ready
Client → Server: HELO client.example.com           ← 打招呼（ESMTP 用 EHLO）
Server → Client: 250 mail.example.com Hello
Client → Server: MAIL FROM:<alice@example.com>      ← 发件人
Server → Client: 250 OK
Client → Server: RCPT TO:<bob@receiver.com>         ← 收件人
Server → Client: 250 OK
Client → Server: DATA                                ← 开始传输邮件内容
Server → Client: 354 Start mail input; end with <CRLF>.<CRLF>
Client → Server: From: Alice <alice@example.com>
                 To: Bob <bob@receiver.com>
                 Subject: Hello!
                 Date: Mon, 15 Jan 2024 10:30:00 +0800
                 Content-Type: text/plain; charset=UTF-8

                 Hi Bob, how are you?
                 .                                    ← 单独一行的 . 表示结束
Server → Client: 250 OK, message accepted
Client → Server: QUIT
Server → Client: 221 Bye
```

注意几个特点：

- 所有命令都是纯文本，以 CRLF 结尾
- 响应码是三位数字：2xx 表示成功，3xx 表示需要更多信息，4xx 表示临时错误，5xx 表示永久错误
- 邮件内容以单独一行的 `.` 结束（如果邮件内容中有以 `.` 开头的行，SMTP 会在前面再加一个 `.`，这叫"点填充"）

**MIME：让邮件支持附件和非 ASCII 字符**

SMTP 最初只支持 7 位 ASCII 文本。MIME（Multipurpose Internet Mail Extensions）通过在邮件头部声明编码方式，让邮件可以携带附件和非 ASCII 字符：

```
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="----=_Part_123"

------=_Part_123
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: base64

5L2g5aW977yM5L2g5piv5Lit5paH5rGf6IO977yB
------=_Part_123
Content-Type: image/png; name="photo.png"
Content-Disposition: attachment; filename="photo.png"
Content-Transfer-Encoding: base64

iVBORw0KGgoAAAANSUhEUgAA...（图片的 Base64 编码）
------=_Part_123--
```

`multipart/mixed` 表示邮件包含多个部分，`boundary` 定义了分隔符。每个部分有自己的 `Content-Type` 和编码方式。`Content-Transfer-Encoding: base64` 把二进制数据转成 ASCII 字符，以便通过只支持 7 位 ASCII 的 SMTP 传输。

**POP3 vs IMAP：收邮件的两种哲学**

SMTP 只负责发邮件。收邮件有两个协议可选：

**POP3（Post Office Protocol version 3）**：把邮件下载到本地，然后（通常）从服务器删除。像把信箱里的信拿回家，信箱就空了。优点是不占服务器空间，缺点是多设备同步困难。

**IMAP（Internet Message Access Protocol）**：邮件保留在服务器上，客户端只是"查看"。像在线查看信箱，信还在里面。多设备都能看到同样的邮件状态（已读/未读/文件夹），但需要服务器提供足够的存储空间。

现代邮件客户端（Gmail、Outlook）几乎都使用 IMAP。

## FTP：文件传输——两个连接的协议

FTP（File Transfer Protocol）是一种用于文件传输的协议，定义于 1971 年（比 HTTP 还早了 20 年）。它的一个独特之处是使用**两个连接**：

- **控制连接（Control Connection）**：TCP 端口 21，用于发送命令和接收响应。整个会话期间保持连接。
- **数据连接（Data Connection）**：用于实际的文件传输和目录列表。每次传输文件都需要建立一个新的数据连接。

**主动模式 vs 被动模式**

**主动模式（Active Mode）**：客户端告诉服务器自己的 IP 和端口，服务器主动连接过来。

```
Client → Server: PORT 192,168,1,100,4,1        ← 告诉服务器：连我的 192.168.1.100:1025
Server → Client: 200 PORT command successful
Client → Server: LIST                            ← 请求目录列表
Server → Client: 150 Opening data connection
[服务器从端口 20 主动连接到客户端的 1025 端口]
[传输目录列表]
Server → Client: 226 Transfer complete
```

问题是：如果客户端在防火墙后面（NAT），服务器根本连不上客户端的私有 IP。

**被动模式（Passive Mode）**：客户端发 `PASV` 命令，服务器返回一个地址和端口，客户端去连接服务器。

```
Client → Server: PASV
Server → Client: 227 Entering Passive Mode (203,0,113,50,195,80)
                 ← 告诉客户端：连我的 203.0.113.50:50000
Client → Server: LIST
[客户端主动连接到服务器的 50000 端口]
[传输目录列表]
Server → Client: 226 Transfer complete
```

被动模式下，数据连接由客户端发起，不需要客户端有公网 IP。这就是为什么被动模式在现代网络中更常用——大部分客户端都在 NAT 后面。

FTP 的安全问题：所有命令（包括密码）都是明文传输的。安全的替代方案是 **FTPS**（FTP over TLS）和 **SFTP**（SSH File Transfer Protocol，注意它和 FTP 是完全不同的协议，只是功能类似）。

## SSH：安全远程登录

SSH（Secure Shell）是 1995 年由 Tatu Ylonen 开发的，目的是替代 Telnet、rlogin 等明文远程登录协议。SSH 提供了：

- 加密的远程命令行会话
- 安全的文件传输（SFTP、SCP）
- 端口转发和隧道

**SSH 握手过程**：

1. **协议版本交换**：双方交换 SSH 版本字符串

```
Client → Server: SSH-2.0-OpenSSH_9.0
Server → Client: SSH-2.0-OpenSSH_8.9
```

1. **密钥交换（Key Exchange）**：使用 Diffie-Hellman 或 ECDH 协商会话密钥。同时交换服务器的 Host Key（公钥），客户端验证这个 Host Key 是否在 `~/.ssh/known_hosts` 文件中。

2. **用户认证**：
   - **密码认证**：直接输入用户名密码（加密传输）
   - **公钥认证**：客户端用自己的私钥签名一个挑战值，服务器用客户端的公钥验证。这是推荐的认证方式——不受暴力破解影响。

3. **会话建立**：认证完成后，客户端可以打开多个 Channel（通道），每个通道是一个独立的逻辑连接（如一个终端会话、一个 SFTP 会话、一个端口转发）。

**SSH 隧道与端口转发**

SSH 的一大强大功能是端口转发——通过加密的 SSH 连接传输其他协议的流量。

**Local Forwarding（本地转发）**：把本地端口映射到远程服务器能访问的目标。

```bash
# 把本地的 3307 端口转发到远程服务器上 MySQL 的 3306 端口
ssh -L 3307:localhost:3306 user@remote-server
```

之后你用 `mysql -h 127.0.0.1 -P 3307` 连接，流量会通过 SSH 加密隧道到达远程服务器的 MySQL。这在远程数据库没有开放公网访问时非常有用。

**Remote Forwarding（远程转发）**：把远程服务器的端口映射到本地。

```bash
# 把远程服务器的 8080 端口转发到本地的 80 端口
ssh -R 8080:localhost:80 user@remote-server
```

之后别人访问 `remote-server:8080`，流量会通过 SSH 隧道转发到你本地的 Web 服务器。适合临时让外网访问你本地的开发服务器。

**Dynamic Forwarding（动态转发 / SOCKS 代理）**：创建一个 SOCKS 代理，所有流量都通过 SSH 隧道。

```bash
# 在本地 1080 端口启动 SOCKS 代理
ssh -D 1080 user@remote-server
```

配置浏览器的 SOCKS 代理为 `localhost:1080`，所有浏览器流量都会通过 SSH 隧道到达远程服务器再出去——相当于自建了一个加密的"VPN"。

## 编程实践：用 Python smtplib 发送邮件

```python
import smtplib
from email.mime.text import MIMEText
from email.mime.multipart import MIMEMultipart
from email.mime.base import MIMEBase
from email import encoders

def send_simple_email():
    """发送一封简单的邮件（使用 Gmail SMTP）"""
    # 构建邮件
    msg = MIMEMultipart()
    msg['From'] = 'your-email@gmail.com'
    msg['To'] = 'recipient@example.com'
    msg['Subject'] = 'Test Email from Python'
    
    # 正文
    body = "This is a test email sent from Python's smtplib.\n\nHello World!"
    msg.attach(MIMEText(body, 'plain', 'utf-8'))
    
    # 添加附件
    attachment_content = b"Hello, this is a test attachment."
    part = MIMEBase('application', 'octet-stream')
    part.set_payload(attachment_content)
    encoders.encode_base64(part)
    part.add_header(
        'Content-Disposition',
        'attachment; filename="test.txt"'
    )
    msg.attach(part)
    
    # 发送邮件（使用 Gmail 的 SMTP 服务器）
    try:
        # 使用 STARTTLS 加密连接
        server = smtplib.SMTP('smtp.gmail.com', 587)
        server.ehlo()
        server.starttls()  # 升级到 TLS 加密
        server.ehlo()
        
        server.login('your-email@gmail.com', 'your-app-password')
        server.send_message(msg)
        server.quit()
        print("Email sent successfully!")
        
    except smtplib.SMTPAuthenticationError:
        print("Authentication failed. Check your email and app password.")
    except smtplib.SMTPException as e:
        print(f"SMTP error: {e}")

def show_smtp_session():
    """开启调试模式，观察完整的 SMTP 会话"""
    server = smtplib.SMTP('smtp.gmail.com', 587)
    server.set_debuglevel(1)  # 打印所有 SMTP 命令和响应
    server.ehlo()
    server.starttls()
    server.ehlo()
    # 省略登录和发送...
    server.quit()

# show_smtp_session()  # 取消注释以查看 SMTP 会话
```

注意：Gmail 需要使用"应用专用密码"而非账户密码。在 Google 账户设置中生成一个 16 位的应用专用密码。

## 编程实践：用 paramiko 实现 SSH 自动化

```python
import paramiko
import sys

def ssh_command(hostname: str, username: str, command: str, key_file: str = None):
    """通过 SSH 执行远程命令"""
    client = paramiko.SSHClient()
    
    # 自动添加未知的 Host Key（生产环境不推荐）
    client.set_missing_host_key_policy(paramiko.AutoAddPolicy())
    
    # 连接参数
    connect_kwargs = {
        'hostname': hostname,
        'username': username,
        'port': 22,
        'timeout': 10,
    }
    
    if key_file:
        connect_kwargs['key_filename'] = key_file
    else:
        connect_kwargs['password'] = input(f"Password for {username}@{hostname}: ")
    
    try:
        client.connect(**connect_kwargs)
        print(f"Connected to {hostname}")
        
        # 执行命令
        stdin, stdout, stderr = client.exec_command(command)
        
        # 读取输出
        exit_code = stdout.channel.recv_exit_status()
        output = stdout.read().decode('utf-8')
        error = stderr.read().decode('utf-8')
        
        if output:
            print(f"STDOUT:\n{output}")
        if error:
            print(f"STDERR:\n{error}")
        print(f"Exit code: {exit_code}")
        
        return exit_code, output, error
        
    except paramiko.AuthenticationException:
        print("Authentication failed!")
        return -1, '', ''
    except paramiko.SSHException as e:
        print(f"SSH error: {e}")
        return -1, '', ''
    finally:
        client.close()

def ssh_sftp_upload(hostname: str, username: str, local_path: str, remote_path: str, key_file: str = None):
    """通过 SFTP 上传文件"""
    client = paramiko.SSHClient()
    client.set_missing_host_key_policy(paramiko.AutoAddPolicy())
    
    connect_kwargs = {
        'hostname': hostname,
        'username': username,
    }
    if key_file:
        connect_kwargs['key_filename'] = key_file
    
    try:
        client.connect(**connect_kwargs)
        sftp = client.open_sftp()
        
        print(f"Uploading {local_path} -> {remote_path}")
        sftp.put(local_path, remote_path)
        print("Upload complete!")
        
        sftp.close()
    finally:
        client.close()

if __name__ == '__main__':
    # 示例：远程执行命令
    # ssh_command('192.168.1.100', 'admin', 'uname -a', key_file='~/.ssh/id_rsa')
    
    # 示例：上传文件
    # ssh_sftp_upload('192.168.1.100', 'admin', 'local.txt', '/tmp/remote.txt')
    pass
```

安装依赖：`pip install paramiko`

## 抓包实践：对比明文 SMTP 和 TLS 加密 SMTP 的报文差异

在 Wireshark 中分别捕获两种 SMTP 会话：

**明文 SMTP（端口 25）**：

```
Client → Server: EHLO client.example.com
Server → Client: 250-mail.example.com Hello
                 250-SIZE 52428800
                 250-STARTTLS
                 250 OK
Client → Server: MAIL FROM:<alice@example.com>
Server → Client: 250 OK
Client → Server: RCPT TO:<bob@receiver.com>
Server → Client: 250 OK
Client → Server: DATA
Server → Client: 354 Start mail input
Client → Server: Subject: Secret Meeting
                 To: bob@receiver.com

                 Let's meet at 3pm. Don't tell anyone.
                 .
Server → Client: 250 OK
```

所有内容都是明文的！邮件主题、内容、收件人全部可见。

**TLS 加密 SMTP（端口 465 或 STARTTLS on 587）**：

```
Client → Server: [TLS ClientHello]
Server → Client: [TLS ServerHello, Certificate]
Client → Server: [TLS Finished]
Server → Client: [TLS Finished]
Client → Server: [Application Data]    ← 加密的 SMTP 命令
Server → Client: [Application Data]    ← 加密的 SMTP 响应
```

在 Wireshark 中，你只能看到 `Application Data`——完全无法分辨这是 SMTP 还是其他协议。这就是加密的力量。

如果使用 STARTTLS（端口 587），你会先看到明文 SMTP 握手，然后 `STARTTLS` 命令之后切换到加密：

```
Client → Server: EHLO client.example.com
Server → Client: 250-STARTTLS ...
Client → Server: STARTTLS              ← 从这里开始切换到 TLS
Server → Client: 220 Ready to start TLS
Client → Server: [TLS ClientHello]     ← TLS 握手开始
...
```

这种对比清晰地展示了加密前后数据可见性的差异——也是为什么在生产环境中，邮件传输应该始终使用 TLS。
