# 第6章：环境变量与 Secrets 管理——"密码藏好了吗？"

## 引言

2023 年，安全研究机构发现超过 **1000 万个密钥**被意外泄露在 GitHub 公开仓库中。这些泄露的 API Key、数据库密码和 Token 每年给企业造成的损失以**数亿美元**计。

在 CI/CD 流水线中，你几乎不可避免地需要用到敏感信息：数据库连接串、部署密钥、第三方 API Key……如何安全地管理这些信息，是每个 DevOps 工程师的必修课。本章，我们将系统学习 GitHub Actions 中的环境变量体系和 Secrets 管理机制。

---

## 6.1 env 的三种作用域

GitHub Actions 中的 `env` 就像 JavaScript 中的作用域链（scope chain）——离"使用点"越近的定义，优先级越高。

```yaml
name: Env Scope Demo

# ① Workflow 级——全局变量，所有 job 和 step 都能用
env:
  APP_NAME: 'my-awesome-app'
  NODE_ENV: 'production'

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest

    # ② Job 级——只在当前 job 内有效
    env:
      BUILD_MODE: 'release'

    steps:
      - name: 全局变量可用
        run: echo "App: $APP_NAME, Mode: $BUILD_MODE"

      # ③ Step 级——只在这个 step 内有效
      - name: Step 级变量
        env:
          TEMP_DIR: '/tmp/build-cache'
        run: echo "临时目录: $TEMP_DIR"

      - name: 上一个 step 的 TEMP_DIR 这里不可用
        run: echo "TEMP_DIR 为空: '$TEMP_DIR'"  # 输出空字符串
```

**作用域覆盖规则**（就像 JavaScript 的变量遮蔽）：

- Step 级 > Job 级 > Workflow 级
- 同名变量，内层覆盖外层

### 动态设置环境变量（跨 step 传递数据）

有时候你需要在一个 step 中计算某个值，然后在后续 step 中使用。GitHub 提供了 `$GITHUB_ENV` 文件来实现这一点：

```yaml
steps:
  - name: 计算版本号
    run: |
      # 从 package.json 读取版本号并设置到环境中
      VERSION=$(node -p "require('./package.json').version")
      echo "VERSION=$VERSION" >> $GITHUB_ENV

  - name: 使用版本号
    run: echo "当前版本: $VERSION"  # 输出从上一个 step 设置的值

  - name: 动态设置多行变量
    run: |
      {
        echo 'DEPLOY_NOTE<<EOF'
        echo "版本: $VERSION"
        echo "时间: $(date)"
        echo "部署者: ${{ github.actor }}"
        echo 'EOF'
      } >> $GITHUB_ENV

  - name: 使用多行变量
    run: echo "$DEPLOY_NOTE"
```

注意 `$GITHUB_ENV` 和 `env:` 块的区别：`env:` 是**静态定义**，`$GITHUB_ENV` 是**运行时动态写入**。后者写入的变量对**后续所有 step** 都可见，就像在 JavaScript 中给 `globalThis` 挂属性一样——一旦写入，全局生效。

## 6.2 默认环境变量

GitHub Actions 预置了一大堆环境变量，就像 Node.js 的 `process.env` 一样开箱即用。以下是最常用的几个：

```yaml
steps:
  - name: 查看默认环境变量
    run: |
      echo "仓库: $GITHUB_REPOSITORY"        # owner/repo-name
      echo "提交SHA: $GITHUB_SHA"             # 触发 workflow 的 commit hash
      echo "分支/Tag: $GITHUB_REF"            # refs/heads/main 或 refs/tags/v1.0
      echo "分支名: $GITHUB_REF_NAME"         # main 或 v1.0（不含 refs/ 前缀）
      echo "触发事件: $GITHUB_EVENT_NAME"     # push, pull_request 等
      echo "运行者: $GITHUB_ACTOR"            # 触发 workflow 的用户名
      echo "工作目录: $GITHUB_WORKSPACE"      # checkout 代码的目录
      echo "运行ID: $GITHUB_RUN_ID"           # 本次运行的唯一ID
      echo "运行编号: $GITHUB_RUN_NUMBER"     # 本 workflow 的第几次运行
```

**实用场景**：

```yaml
steps:
  - name: 生成带 commit hash 的构建产物
    run: |
      # 利用 GITHUB_SHA 给构建产物打标签
      BUILD_TAG="${GITHUB_SHA:0:7}"  # 取 SHA 前7位
      npm run build
      tar -czf "app-${BUILD_TAG}.tar.gz" dist/

  - name: 在 PR 评论中附加运行链接
    if: github.event_name == 'pull_request'
    run: |
      echo "本次 CI 运行链接:"
      echo "${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}"
```

## 6.3 Secrets 管理：敏感信息的安全屋

如果说 `env` 是一个透明的公告栏（谁都能看），那 `secrets` 就是一个上锁的保险箱——**只有运行时才解密，日志中自动脱敏**。

### 三种 Secrets 类型

1. **Repository Secrets**：仓库级，最常用，在该仓库的所有 workflow 中可用。
2. **Organization Secrets**：组织级，可以在组织的多个仓库间共享。
3. **Environment Secrets**：环境级（如 `production`、`staging`），与 Environment Protection Rules 配合使用，提供额外的安全层。

### 设置 Secrets

在仓库的 **Settings → Secrets and variables → Actions** 中添加。也可以通过 GitHub CLI 设置：

```bash
# 设置 Repository Secret
gh secret set DATABASE_URL --body "postgresql://user:pass@host:5432/db"

# 设置 Environment Secret（先创建环境）
gh api repos/OWNER/REPO/environments/production
gh secret set AWS_KEY --env production --body "AKIA..."
```

### 在 workflow 中使用

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    # 使用 Environment 来限定 secrets 的作用域
    environment: production

    steps:
      - name: 使用 Secrets
        env:
          # secrets 只能通过 env 传递给命令行，不能直接在 YAML 中展开
          DB_URL: ${{ secrets.DATABASE_URL }}
          API_KEY: ${{ secrets.API_KEY }}
        run: |
          # 在脚本中通过环境变量引用
          node scripts/deploy.js
          # deploy.js 中: process.env.DB_URL, process.env.API_KEY
```

**关键原则**：Secrets 永远不要在 YAML 中直接内联使用（如 `run: echo ${{ secrets.API_KEY }}`），而应该通过 `env` 映射到环境变量后再使用。原因很简单——YAML 中的表达式可能被意外记录到各种日志中。

## 6.4 最佳实践：永远不要把 Secret 打印到日志

这是一条铁律，值得用大写加粗体写在你团队的 Wiki 首页上。

GitHub Actions 有一个内置的**日志脱敏机制**：任何通过 `${{ secrets.XXX }}` 引用的值，如果被打印到日志中，会自动替换为 `***`。但这个机制不是万能的——如果你不小心用其他方式泄露了 secret，GitHub 帮不了你。

```yaml
# ❌ 危险：可能泄露 secret 的操作
steps:
  - name: 千万别这么干
    run: |
      echo "数据库密码是: $DB_PASSWORD"          # 如果 DB_PASSWORD 来自 env，不会被脱敏！
      set -x                                    # debug 模式会打印所有命令和参数
      curl -H "Authorization: Bearer $API_KEY"  # -v 模式可能泄露 header
      cat .env                                  # 如果 .env 文件包含 secret

# ✅ 安全做法
steps:
  - name: 安全使用 secrets
    env:
      DB_URL: ${{ secrets.DATABASE_URL }}
    run: |
      # 通过环境变量传递，不要 echo
      node -e "require('./scripts/db-migrate').run()"

      # 如果需要确认 secret 是否设置，只检查存在性
      if [ -z "$DB_URL" ]; then
        echo "ERROR: DB_URL is not set"
        exit 1
      fi
      echo "DB_URL is set: yes"  # 只确认存在，不打印值
```

### 自动检测 secret 泄露

如果你不小心把 secret 打印了，GitHub 的 **Push Protection** 和 **Secret Scanning** 功能会帮你检测。但这只是最后一道防线——最好的做法是**从源头避免泄露**。

## 6.5 OIDC 与 Token 权限管理

传统的"把云厂商的长期密钥存在 GitHub Secrets 里"的做法正在被淘汰——因为这些长期密钥一旦泄露，后果不堪设想。现代最佳实践是使用 **OIDC（OpenID Connect）** 来获取**临时凭证**。

```yaml
jobs:
  deploy-to-aws:
    runs-on: ubuntu-latest
    permissions:
      id-token: write      # 允许请求 OIDC token
      contents: read        # 允许 checkout 代码

    steps:
      - uses: actions/checkout@v4

      - name: 使用 OIDC 获取 AWS 临时凭证
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: us-east-1
          # 不需要 access-key-id 和 secret-access-key！
          # OIDC 会自动生成临时凭证

      - name: 使用 AWS CLI（使用临时凭证）
        run: aws s3 cp dist/ s3://my-bucket/ --recursive
```

**工作原理**：GitHub Actions 扮演一个"可信中间人"的角色——它生成一个 JWT Token，声明"我是仓库 X 的 workflow Y 的第 Z 次运行"。AWS（或其他云厂商）验证这个 Token 的签名，确认来源可信后，颁发临时凭证。这些凭证在 workflow 结束后自动失效，就像酒店房卡——退房后自动作废。

### permissions 精细控制

GitHub 的 `GITHUB_TOKEN` 默认权限比较宽松，但在安全敏感的项目中，你应该遵循**最小权限原则**：

```yaml
# 在 workflow 级别设置默认权限
permissions:
  contents: read          # 只读代码
  pull-requests: write    # 可以评论 PR

jobs:
  test:
    runs-on: ubuntu-latest
    # 不需要额外权限，继承 workflow 级别

  deploy:
    runs-on: ubuntu-latest
    # 这个 job 需要额外权限
    permissions:
      contents: read
      id-token: write     # OIDC
      packages: write     # 推送到 GitHub Packages
```

## 6.6 实际案例：Node.js 项目中的安全实践

```yaml
name: Secure Deploy

on:
  push:
    branches: [main]

env:
  NODE_ENV: production
  APP_PORT: 3000

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - run: npm ci --production=false

      - name: 构建应用
        env:
          # 构建时需要的非敏感配置
          NEXT_PUBLIC_API_URL: 'https://api.example.com'
        run: npm run build

      - name: 运行数据库迁移
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          # 只打印迁移状态，不打印连接串
        run: npm run db:migrate -- --silent

      - name: 部署到云平台（使用 OIDC）
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          STRIPE_SECRET_KEY: ${{ secrets.STRIPE_KEY }}
          SENDGRID_API_KEY: ${{ secrets.SENDGRID_KEY }}
        run: |
          # 所有 secret 通过环境变量注入
          # 部署脚本内部使用，不 echo 任何敏感信息
          node scripts/deploy.js --env production
```

## 小结

| 概念 | 作用域 | 是否敏感 | 持久性 |
|------|--------|---------|--------|
| `env:` 块 | 静态、声明时确定 | 否 | workflow 生命周期 |
| `$GITHUB_ENV` | 动态、后续 step | 否 | workflow 生命周期 |
| 默认环境变量 | 全局自动注入 | 否 | 单个 step |
| `secrets.XXX` | 通过 env 传递 | 是（自动脱敏） | 单个 step |
| OIDC Token | 临时凭证 | 是 | job 生命周期 |

记住三条铁律：

1. **永远不要在日志中打印 secret**——即使 GitHub 有脱敏机制。
2. **尽可能使用 OIDC**代替长期密钥。
3. **最小权限原则**——每个 job 只给它需要的权限。

## 练习题

1. **基础题**：创建一个 workflow，在 workflow 级设置 `NODE_ENV=production`，在某个 step 中动态读取 `package.json` 的 `version` 字段并写入 `$GITHUB_ENV`，在后续 step 中同时使用这两个变量。
2. **安全审计题**：给定以下 workflow 片段，找出所有可能导致 secret 泄露的问题并修复：

   ```yaml
   steps:
     - run: echo "Connecting to ${{ secrets.DATABASE_URL }}"
     - run: |
         set -x
         curl -H "Authorization: ${{ secrets.API_TOKEN }}" https://api.example.com
     - run: cat .env >> deploy.log
   ```

3. **设计题**：设计一套 Secrets 管理方案，满足以下需求：staging 和 production 环境使用不同的数据库连接串；组织内多个仓库共享同一个监控 API Key；新入职的开发者不能查看 production secrets。
