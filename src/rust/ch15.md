# 第15章：模块系统与Crate

Part IV：高级特性

恭喜你来到了 Rust 进阶篇！在前14章里，你已经掌握了所有权、借用、泛型、Trait、生命周期和闭包这些核心概念。现在，我们要进入"高手区"了——模块系统、智能指针、并发、面向对象的设计哲学，以及模式匹配的全部威力。

如果说前14章是学会"开车"，那接下来5章就是学会"修路"——你将能设计大型项目结构、管理复杂的所有权关系、写出安全的多线程代码，并用优雅的模式匹配处理各种数据结构。

## 场景引入

想象一下：你用 Python 写了一个小脚本，起初只有200行，全塞在 `main.py` 里。后来功能越加越多，变成了5000行，找函数像在迷宫里找厕所。于是你开始拆文件——`utils.py`、`models.py`、`api.py`，然后用 `import` 把它们串起来。

Rust 面临同样的问题，只不过它的解法更严格、更系统。Rust 的模块系统（Module System）就像一座精心设计的图书馆——每本书（模块）都有明确的分类编号，不是你想放哪就放哪的。

## 15.1 Crate 与 Package

在 Rust 的世界里，有三个核心概念需要区分：

| 概念 | 英文 | 含义 | 类比 |
| ------ | ------ | ------ | ------ |
| Package | 包 | 包含 `Cargo.toml` 的项目目录 | npm 的一个 package / Python 的一个 distribution |
| Crate | 箱 | 编译单元，分为二进制 crate 和库 crate | npm 包编译后产出的一个模块 |
| Module | 模块 | crate 内部的代码组织单元 | Python 的一个 `.py` 文件 |

一个 Package 可以包含多个 Crate（但最多一个库 crate），一个 Crate 可以包含多个 Module。

这里有一个关键区分：**二进制 Crate（Binary Crate）**和**库 Crate（Library Crate）**。二进制 Crate 编译后产出一个可执行文件（有 `main` 函数），库 Crate 编译后产出一个供其他项目使用的库（没有 `main` 函数）。一个 Package 可以有多个二进制 Crate（放在 `src/bin/` 目录下），但最多一个库 Crate。

```rust
// 用 Cargo 创建不同类型的 package

// 1. 二进制项目（可执行程序）
// cargo new my_app
// 生成 src/main.rs —— 这是一个二进制 crate 的根

// 2. 库项目（供别人使用的库）
// cargo new --lib my_lib
// 生成 src/lib.rs —— 这是一个库 crate 的根

// 3. 一个 Package 中包含多个二进制 crate
// 项目目录结构：
// my_project/
// ├── Cargo.toml
// └── src/
//     ├── lib.rs          ← 库 crate（最多一个）
//     ├── main.rs          ← 默认二进制 crate
//     └── bin/
//         ├── server.rs    ← 额外的二进制 crate: my_project-server
//         └── client.rs    ← 额外的二进制 crate: my_project-client
```

这和 Python 的 `setup.py`/`pyproject.toml` 不同——Python 的一个 package 可以同时提供库和命令行工具，而 Rust 通过 `src/bin/` 目录实现了更清晰的分离。每个 `bin/` 下的文件都会编译成独立的可执行文件。

## 15.2 模块树：mod、pub、use

模块是 Rust 中组织代码的基本单元。使用 `mod` 关键字声明模块：

```rust
// src/lib.rs

// 声明模块——告诉编译器"去加载对应的代码"
mod front_of_house {
    mod hosting {
        fn add_to_waitlist() {
            println!("已加入等候名单");
        }

        fn seat_at_table() {
            println!("已安排入座");
        }
    }

    mod serving {
        fn take_order() {
            println!("接受点单");
        }

        fn serve_order() {
            println!("上菜");
        }
    }
}
```

这段代码在编译器眼中形成了一棵**模块树（Module Tree）**：

```
crate (lib.rs 根模块)
 └── front_of_house
      ├── hosting
      │    ├── add_to_waitlist
      │    └── seat_at_table
      └── serving
           ├── take_order
           └── serve_order
```

就像文件系统的目录树一样，模块树清晰地展示了代码的层次结构。

**关于隐私的一个重要规则**：注意上面的代码中，所有模块和函数都没有 `pub` 标记。在 Rust 中，模块系统遵循一条核心规则——**子模块可以访问父模块的所有内容，但父模块无法访问子模块的私有内容**。这就像在公司里：实习生可以看到公司的公开文档，但 CEO 不能随便翻看实习生的私人笔记本。如果你想在模块外部使用某个函数或子模块，必须给它加上 `pub` 关键字。

这个设计选择是有深意的——Rust 的哲学是"默认最小权限"。你不说公开，就不公开。这比 Python 的"约定俗成"（用 `_` 前缀表示私有）要严格得多，也比 Java 的 `package-private` 默认行为更安全。

## 15.3 路径引用：绝对路径与相对路径

要调用模块中的函数，你需要指定路径，就像访问文件需要路径一样：

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {
            println!("已加入等候名单");
        }
    }
}

// 绝对路径：从 crate 根开始，以 crate:: 开头
// （类似文件系统的绝对路径 /home/user/project/...）
pub fn eat_at_restaurant_absolute() {
    crate::front_of_house::hosting::add_to_waitlist();
}

// 相对路径：从当前模块开始
// （类似文件系统的相对路径 ./front_of_house/...）
pub fn eat_at_restaurant_relative() {
    front_of_house::hosting::add_to_waitlist();
}
```

**注意 `pub` 关键字**——默认情况下，模块和函数都是**私有的**（和 Python 的 `_` 前缀约定不同，Rust 是"默认全私"）。你必须显式地用 `pub` 标记为公开，就像给房间装上门牌号和钥匙。

## 15.4 super 与 self

`super` 指向父模块，`self` 指向当前模块。就像文件系统中的 `..` 和 `.`：

```rust
mod outer {
    pub fn say_hello() {
        println!("Hello from outer!");
    }

    pub mod inner {
        pub fn greet() {
            // super 指向父模块 outer
            super::say_hello();

            // self 指向当前模块 inner（通常可以省略）
            self::say_hi();
        }

        pub fn say_hi() {
            println!("Hi from inner!");
        }
    }
}

fn main() {
    outer::inner::greet();
    // 输出: Hello from outer!
    //       Hi from inner!
}
```

## 15.5 use 关键字：路径别名

每次都写完整路径太啰嗦了，`use` 关键字可以"导入"路径，就像 Python 的 `from xxx import yyy`：

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {
            println!("已加入等候名单");
        }
    }
}

// 导入后可以直接用短名称调用
use crate::front_of_house::hosting;

pub fn eat_at_restaurant() {
    hosting::add_to_waitlist(); // 简洁！
}

// 也可以导入到具体函数（但 Rust 社区更推荐导入到模块级别）
use crate::front_of_house::hosting::add_to_waitlist;

pub fn eat_at_restaurant_v2() {
    add_to_waitlist(); // 更简洁，但可能引起命名冲突
}
```

**Rust 社区惯例**：导入结构体/枚举时直接导入到具体名称，导入模块时导入到父模块。这和 Python 的 `from module import Class` 习惯不太一样：

```rust
use std::collections::HashMap;  // 结构体：导入到具体名称 ✓
use std::io;                     // 模块：导入到模块级别 ✓

fn main() {
    let mut map = HashMap::new();
    let result = io::Result::Ok(());
}
```

## 15.6 可见性控制进阶

Rust 提供了精细的可见性控制，远比 Java 的 `public/protected/private` 灵活：

```rust
mod my_module {
    // 仅当前 crate 内可见（Java 里没有直接对应物）
    pub(crate) fn internal_api() {
        println!("这个函数只在本 crate 内可用");
    }

    // 仅父模块可见
    pub(super) fn parent_only() {
        println!("只有爸爸能看到我");
    }

    // 在指定路径可见
    pub(in crate::my_module) fn restricted() {
        println!("只有 my_module 内部能看到我");
    }

    pub mod sub {
        pub fn demo() {
            // 在子模块中可以调用 super 的 pub(super) 方法
            super::parent_only();
            super::internal_api();
        }
    }
}

fn main() {
    my_module::internal_api(); // OK：在同一个 crate 中
    // my_module::parent_only(); // 编译错误：对当前模块不可见
    my_module::sub::demo();
}
```

**结构体的字段可见性**有个容易踩的坑——结构体本身 `pub` 不代表字段也 `pub`，每个字段要单独标记：

```rust
pub struct User {
    pub name: String,      // 公开字段
    pub email: String,     // 公开字段
    password_hash: String, // 私有字段——外部无法直接访问
}

impl User {
    pub fn new(name: String, email: String, password: String) -> Self {
        User {
            name,
            email,
            password_hash: hash_password(&password),
        }
    }

    // 私有方法
    fn hash_password(password: &str) -> String {
        format!("hashed_{}", password) // 简化示例
    }

    // 公开的验证方法
    pub fn verify_password(&self, password: &str) -> bool {
        self.password_hash == Self::hash_password(password)
    }
}
```

## 15.7 文件系统中的模块组织

当模块变大时，你可以把模块拆分到独立文件中。Rust 有两种文件组织方式：

**方式一（内联模块 + 文件）**：在 `lib.rs` 中用 `mod xxx;` 声明模块，编译器会去找对应的文件。
**方式二（mod.rs 传统方式）**：创建一个目录，在里面放 `mod.rs` 文件。这种方式在 Rust 2018 之后不再推荐，但在老项目中仍然常见。

推荐方式一，因为它更清晰：看到文件名就知道它是一个模块，不需要在目录里找 `mod.rs`。

```
// 推荐的项目结构（Rust 2018+）：
// my_project/
// ├── Cargo.toml
// └── src/
//     ├── lib.rs                  ← crate 根（声明所有顶层模块）
//     ├── models.rs               ← models 模块
//     ├── models/
//     │   ├── user.rs             ← models::user 子模块
//     │   └── post.rs             ← models::post 子模块
//     ├── services.rs             ← services 模块
//     └── services/
//         ├── auth.rs             ← services::auth 子模块
//         └── notification.rs     ← services::notification 子模块

// 不推荐的老式结构：
// src/
// ├── lib.rs
// ├── models/
// │   ├── mod.rs    ← 这个 mod.rs 就是 models 模块
// │   ├── user.rs
// │   └── post.rs
// └── services/
//     ├── mod.rs
//     ├── auth.rs
//     └── notification.rs
```

```rust
// src/lib.rs
mod front_of_house; // 编译器会去找 src/front_of_house.rs

pub use crate::front_of_house::hosting; // 重导出

// src/front_of_house.rs
pub mod hosting; // 编译器会去找 src/front_of_house/hosting.rs

// src/front_of_house/hosting.rs
pub fn add_to_waitlist() {
    println!("已加入等候名单");
}
```

## 15.8 Cargo.toml 与依赖管理

Cargo.toml 是 Rust 项目的"身份证"和"购物清单"，类似 `package.json`（Node.js）或 `requirements.txt`（Python）：

```toml
# Cargo.toml
[package]
name = "my_restaurant"
version = "0.1.0"
edition = "2021"

[dependencies]
# 从 crates.io 引入外部 crate
serde = "1.0"                    # 序列化/反序列化
serde_json = "1.0"               # JSON 支持
rand = "0.8"                     # 随机数
reqwest = { version = "0.11", features = ["json"] }  # HTTP 客户端

# 使用 Git 仓库作为依赖
# my_lib = { git = "https://github.com/user/my_lib", branch = "main" }

# 使用本地路径作为依赖
# my_local_lib = { path = "../my_local_lib" }

[dev-dependencies]
# 仅测试时使用的依赖
assert_cmd = "2.0"
```

## 15.9 使用外部 Crate

```rust
// 引入外部 crate 的内容
use std::collections::HashMap;
use rand::Rng;

fn main() {
    // 使用标准库
    let mut scores = HashMap::new();
    scores.insert("Alice", 100);
    scores.insert("Bob", 85);

    // 使用 rand crate
    let mut rng = rand::thread_rng();
    let dice_roll: u8 = rng.gen_range(1..=6);

    println!("分数: {:?}", scores);
    println!("骰子: {}", dice_roll);
}
```

**`use` 冲突处理**——当两个 crate 导出了同名类型时：

```rust
use std::fmt;
use std::io;

// 方案一：用 as 起别名（类似 Python 的 import numpy as np）
use std::io::Result as IoResult;

fn run() -> fmt::Result {
    Ok(())
}

fn read_input() -> IoResult<String> {
    Ok(String::from("hello"))
}
```

## 15.10 工作空间（Workspace）

当你的项目由多个相关的 crate 组成时（比如一个框架拆成多个子库），使用工作空间来统一管理：

```toml
# 根目录/Cargo.toml
[workspace]
members = [
    "core",
    "web",
    "cli",
]

# 共享依赖版本——避免各子 crate 版本不一致
[workspace.dependencies]
serde = "1.0"
tokio = { version = "1", features = ["full"] }
```

```toml
# core/Cargo.toml
[package]
name = "my_framework_core"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { workspace = true }  # 使用工作空间统一版本
```

工作空间的好处：

- `cargo build` 一次编译所有子 crate
- 共享 `Cargo.lock`，版本一致
- 子 crate 之间可以互相依赖
- `cargo test` 一次运行所有测试

## 15.11 实战：组织一个多模块项目

让我们用一个完整的例子来把本章的知识串起来。假设我们要构建一个"迷你博客后端"：

```rust
// src/lib.rs —— 库 crate 根文件

// 声明模块
pub mod models;     // 数据模型
pub mod api;        // API 接口
mod database;       // 数据库层（内部实现，不对外暴露）

// 使用 pub use 重导出常用类型，让用户不用关心内部模块结构
pub use models::{Post, User};
pub use api::handle_request;

// src/models.rs
pub struct User {
    pub id: u64,
    pub name: String,
    pub email: String,
}

pub struct Post {
    pub id: u64,
    pub title: String,
    pub content: String,
    pub author_id: u64,
}

impl Post {
    pub fn new(title: String, content: String, author_id: u64) -> Self {
        Post { id: 0, title, content, author_id }
    }

    pub fn summary(&self) -> String {
        format!("{} (by author #{})", self.title, self.author_id)
    }
}

// src/database.rs（私有模块，外部不可见）
use super::models::{Post, User};

// pub(crate)：只在 crate 内部可见
pub(crate) fn save_post(post: &Post) -> bool {
    println!("[DB] 保存文章: {}", post.title);
    true
}

pub(crate) fn find_user(id: u64) -> Option<User> {
    println!("[DB] 查询用户 #{}", id);
    Some(User { id, name: "Alice".into(), email: "alice@example.com".into() })
}

// src/api.rs
use crate::models::Post;
use crate::database; // 可以访问私有模块，因为我们在同一个 crate 内

pub fn handle_request(title: String, content: String) -> String {
    let post = Post::new(title, content, 1);
    database::save_post(&post); // 调用内部数据库层
    format!("文章已创建: {}", post.summary())
}

// src/main.rs —— 二进制 crate
use my_blog::{handle_request, Post, User};
// 注意：我们用 use my_blog::... 而不是 use my_blog::api::...
// 这是因为 lib.rs 做了 pub use 重导出！

fn main() {
    let result = handle_request(
        "Rust 模块系统真棒".to_string(),
        "学完这一章你就懂了...".to_string(),
    );
    println!("{}", result);

    // my_blog::database::save_post(...) // 编译错误！database 是私有模块
}
```

这个结构体现了 Rust 模块系统的设计哲学：**对外暴露简洁的 API，内部实现自由灵活**。`database` 模块对用户完全隐藏，你可以随时替换数据库实现而不影响外部用户。这和 Python 包中的 `__init__.py` 里 `from .database import ...` 的重导出思路如出一辙。

## 常见陷阱

1. **忘记 `pub`**：模块和函数默认私有，新手最常犯的错误。如果你写了 `use` 却报"找不到"，先检查路径上每一环是否都是 `pub`。记住：路径中的每一个模块、每一个函数都需要是 `pub` 的，缺一不可。比如 `a::b::c()` 需要 `a` 是 pub 的，`b` 是 pub 的，`c` 也必须是 pub 的。

2. **`use` 与模块可见性的混淆**：`use` 导入的内容默认是私有的。如果你想在当前模块中"转手"导出，用 `pub use`（重导出，re-export）。这在构建库 crate 时特别重要——你可以在内部使用复杂的模块层次，但对外只暴露扁平的 API。

3. **枚举变体自动公开**：`use MyEnum::*;` 可以导入所有变体，但 `pub use` 枚举时变体也会一起公开，这和结构体不同。枚举的变体没有独立的可见性控制——枚举公开，变体就全部公开；枚举私有，变体就全部私有。

4. **`use` 的作用域**：`use` 导入只在当前模块中有效，不会自动传递到子模块。如果子模块也需要用，需要在子模块中再次 `use`。这和 Python 的 `import` 不同——Python 中导入的模块在当前文件的所有函数中都可用。

## 小结

| 概念 | 关键字 | 作用 |
| ------ | -------- | ------ |
| 声明模块 | `mod` | 在 crate 内创建模块 |
| 公开可见 | `pub` | 让外部能访问 |
| 导入路径 | `use` | 缩短调用路径 |
| 重导出 | `pub use` | 导入并再导出 |
| 父模块 | `super` | 相对路径指向父级 |
| 外部依赖 | `Cargo.toml` | 管理第三方 crate |
