# 第4章：随机数与口令：一切密钥的源头

> [!TIP] Part 1: 工具箱入门篇（地基篇）
> Part 1 收尾章。前三章的每一份安全承诺，最终都压在「钥匙够不够随机」上。本章钻进随机数的源头，顺手把 base64 这类「看起来像加密」的编码一次分清。

上一章的流水线里有两把钥匙：`BACKUP_PASS` 与 `BACKUP_HMAC_KEY`。王哥看完脚本后说：「口令我来定，我设了 `Cloudnote@2026`，够复杂吧——大小写、数字、特殊符号全齐。」这句话就是本章的引子。**「看起来复杂」和「随机」是两回事**：人类出于记忆本能挑的字符组合，在攻击者的字典里全是高频词条；一台 8 卡 GPU 一天能穷举的口令空间，比你想象的要小得多。而一切密钥的出生证明，都该由随机数签发。

## 4.1 随机性为什么是命门

先建立一个数量级直觉。安全强度用「熵」衡量，单位是比特——熵为 N 比特的钥匙，暴力穷举平均要试 2^N 次。把常见口令和密钥放在同一把尺子上：

| 来源 | 熵 | 暴力穷举代价 |
| ---- | ---- | ---- |
| 6 位短信验证码 | 约 20 比特 | 百万种组合，秒级扫完（所以验证码要配限速与有效期） |
| 8 位人类口令（大小写数字符号） | 约 40 比特 | 单卡 GPU 小时级 |
| 12 位人类口令 | 约 60 比特 | GPU 集群数月，逐渐够呛 |
| 20 位 `openssl rand` 密码 | 约 120 比特 | 全地球算力联合也遥遥无期 |
| 32 字节随机密钥 | **256 比特** | 宇宙热寂也数不完 |

关于人类口令那两行还有个解释：8 位可打印字符理论上有约 52 比特空间，但人不是均匀随机的——大写多半在开头、符号多半是感叹号、数字多半是生日，攻击者的字典正是按这些偏好排序的，实际熵被砍到 40 比特上下。**「人挑的」本身就是熵的漏斗**，这不是歧视人类，是认知科学的测量结论。

从 60 比特到 256 比特不是「强一点」，是跨过了不可逾越的鸿沟——**密码学的安全从不靠玄学，靠指数**。

随机性出过的事故里，最著名的一桩发生在 2008 年的 Debian 系：维护者为了消除一个代码检查工具的警告，删掉了 OpenSSL 随机数生成器里一行「看起来没用」的代码——那行正是熵的来源。此后两年间，Debian 及其衍生系统上生成的**所有** SSH 密钥、SSL 证书，随机数实际只剩进程号一个来源，钥匙空间从 2^N 塌缩到 3 万余种。脚本数小时就能穷举全部可能的密钥，全球数千台服务器的「锁」同时变成纸糊的。事故修复名单至今还挂在档案里。教训一句话：**随机数生成器是一个系统里最不该被「优化」的地方**。

这场事故还有个更扎心的细节：漏洞存续的两年里，没有任何一次入侵被归因于它——不是因为没人利用，而是因为利用者不说。直到有开发者发现「新装的系统每次生成密钥后，`ssh-keygen` 的指纹池小得可疑」才顺藤摸到根。**随机的失效是静默的**：文件格式正常、命令全部成功、指纹看起来像模像样——你唯一的防御是「熵来自被严格保护的代码路径」这个制度本身，而不是任何一次肉眼检查。

## 4.2 rand 实战

`openssl rand` 是全书第二短的命令，两个参数走天下。它只做一件事：向操作系统要 N 字节的密码学安全随机数，再按你指定的编码穿好衣服。熵在源头已经定死，编码只决定「穿什么衣服出门」：

```bash
openssl rand -hex 32      # 32 字节，输出 64 个十六进制字符
openssl rand -base64 32   # 32 字节，输出 44 个 base64 字符（含 = 填充）
openssl rand 16           # 不加编码参数：直接输出 16 字节二进制（别 cat 到终端）
```

三条命令输出的**熵完全相同**——都是 32（或 16）字节的原始随机性，hex 与 base64 只是同一批字节的两种衣服。这点必须刻进脑子，因为「base64 那串更长所以更安全」是初学者出现率 100% 的错觉：衣服不改变身体。选哪种编码的唯一标准是给谁看——给人比对选 hex，进协议传输选 base64。

| 参数 | 输出形态 | 一字节的化身 | 适合 |
| ---- | ---- | ---- | ---- |
| `-hex` | `3f9a1c7e...` | 2 个字符 | 人眼比对、指纹、hex 钥匙（如 `-K` 参数） |
| `-base64` | `kR9xV2mQ...=` | 约 1.33 个字符 | 密码、令牌——字符利用率高 |
| 无 | 二进制 | 1 个字节 | 管道喂给其他程序 |

先补一堂心算课，把「字节怎么变成字符」这笔账算清：hex 每字节展开 2 字符，16×2=32；base64 每 3 字节打包成 4 字符，32÷3×4≈42.7，取整到 4 的倍数并补 `=` 填充后是 44。base64 的 `=` 是「3 字节一组凑不齐」时的占位符，见到一两个 `=` 不是出错，是长度的诚实记录。这套换算的价值在第6章：PEM 格式就是 base64 穿的马甲，届时你看到证书文件每行 64 字符的来历，就是这一条。

**要多少字节才够？** 一张定案表，比背理论省事：

| 用途 | 最少字节数 | 生成命令 |
| ---- | ---- | ---- |
| 会话令牌、CSRF token | 16（128 比特） | `openssl rand -base64 16` |
| API 密钥、加密密钥 | 32（256 比特） | `openssl rand -base64 32` |
| HMAC 密钥 | 32 | `openssl rand -hex 32` |
| 盐（PBKDF2 用） | 16 | `openssl rand -hex 16` |
| 人类要背的密码 | `rand -base64 24`（32 字符） | 配合密码管理器 |

原则一句话：**对称密钥 128 比特起步、256 比特无忧**；宁可多给，绝不手抖少给。

**`$RANDOM` 到底差在哪？** 亲手量一次，比读十遍文章记得牢。bash 内置的 `$RANDOM` 取值范围是 0 到 32767——总共 15 比特的熵，连一个 8 位数字口令都凑不满：

```bash
# 「随机」生成一个 8 位数字口令的两种方式
echo $((RANDOM % 100000000))    # 看着像 8 位，实际只会打出 0~32767——取模无法凭空扩大取值域
openssl rand -hex 4             # rand 拼的：32 比特熵起步
```

更要命的是可预测性：`$RANDOM` 是 bash 用固定算法（线性同余）生成的伪随机数，**只要看到它的几个连续输出，后续全部可推算**——这不是概率劣势，是结构性破绽。图形验证码、短信验证码、重置令牌这类「攻击者会主动 guess」的场景，只要有一处用了语言内置的 `random` 模块或 `$RANDOM`，整个体系的强度就被最弱一环钉死在地板上。本书涉及安全的输出，只认 `openssl rand`（或应用代码里的 CSPRNG API）。

> [!WARNING] 随机数的三不要
> 不要用 `date +%s`、`$RANDOM`、时间戳当密钥——可预测等于没有加密。不要把 `rand` 的输出重复用：一把钥匙一个用途，泄露不连坐。不要在日志里打印钥匙：日志的读者面远比你想的广。

## 4.3 熵从哪来

`openssl rand` 的字节不是算术变出来的，它底层调用操作系统的密码学安全随机数生成器（CSPRNG，Cryptographically Secure PRNG）。Linux 上这条链路是：

```text
硬件事件（键盘中断 磁盘时序 网卡抖动……）
        │  收集
        ▼
内核熵池（持续搅拌）
        │  getrandom(2) 系统调用
        ▼
CSPRNG ──► /dev/urandom ──► openssl rand ──► 你的密钥
```

CSPRNG 的特点是：内部状态足够大、输出不可预测、哪怕部分状态泄露也不回溯历史输出。所以你在用户态该做的事其实只有一件——**别自作聪明换掉它**。自己用哈希拼时间戳「造」随机数、自己维护一个「随机」种子文件，都是把 Debian 事故亲手复刻一遍。

顺带一提，这张图里还有一个工程细节：CSPRNG 是**持续搅拌**的——即使两个进程在同一毫秒各要一把 32 字节钥匙，内核也会保证两者毫无关联。所以「多把钥匙分多次生成」和「一次生成后切分」安全性等价，选哪个纯看管理方便——云笔记选的是前者，每把钥匙独立生成、独立命名、独立进台账。

顺带澄清一个流传甚广的误区：老教程常说「生成密钥要用 `/dev/random`，`/dev/urandom` 不安全」。这在现代 Linux 上是**反的**——`/dev/random` 在熵池估计不足时会阻塞进程（历史上真的冻住过生产环境），而 `/dev/urandom` 走 CSPRNG，开机后安全性一致。`openssl rand` 已经替你选好了正确答案，你只需要不折腾。

这段历史值得一小段展开，因为它解释了「为什么老教程会那么说」。Linux 2.6 时代，内核用估算值判断熵池「够不够」：`/dev/random` 在估计不足时阻塞等待，`/dev/urandom` 则不阻塞直接出数。当年的顾虑是「熵不够时输出可预测」——但密码学界后来证明：CSPRNG 一旦在初始化时拿到过足量熵，之后的输出就不可预测，**持续阻塞毫无安全收益，只有可用性损失**。于是 2020 年，Linux 5.6 直接把 `/dev/random` 的阻塞池整个删掉，`getrandom(2)`（`openssl rand` 实际调用的接口）只在系统**首次**引导、熵池尚未初始化时阻塞——此后一律不阻塞。这条线彻底清爽了：容器里、云主机上、重启后的服务器上，`openssl rand` 既快又安全，「要不要用 /dev/random」从争议变成考古题。

真正需要你留意的边界只剩一处：极早期的嵌入式设备或刚开机几秒的系统上，`getrandom(2)` 可能还没就绪——表现为 `openssl rand` 卡住不返回。这不是坏了，是内核在等第一次开机熵，等几秒即可；企业级解决方案是硬件随机数芯片，那是另一个世界的话题。

## 4.4 passwd 与口令哈希

`rand` 之外，`openssl passwd` 是本章第二件工具，干的是另一件事：把口令做成**可存储的哈希**。你服务器的 `/etc/shadow` 里那串 `$6$...` 就是这类格式：

```bash
openssl passwd -6 'S3cret!Pass'
```

```text
$6$saltsalt$abcdefghijklmnopqrstuvw...
```

三种格式对号入座：

| 参数 | 格式 | 现状 |
| ---- | ---- | ---- |
| `-6` | SHA-512 crypt（`$6$`） | **本书选择**，通用性最好 |
| `-5` | SHA-256 crypt（`$5$`） | 可用，少见 |
| `-apr1` | Apache 变体 MD5（`$apr1$`） | htpasswd 场景遗留，能用但不新用 |
| `-1` | MD5 crypt（`$1$`） | 淘汰，仅考古 |

它和第2章的 `dgst` 都是哈希，但立场不同：`dgst` 算文件指纹，快是美德；`passwd -6` 算口令哈希，**慢是美德**（内建多轮迭代，专门拖慢离线爆破）。每次验证口令都重新算一遍，用户感知不到，攻击者爆破时每一条都要付满成本。

验证环节值得看一眼盐的行为——同一口令每次输出都不同（盐随机），但指定盐后结果恒定：

```bash
openssl passwd -6 -salt 'fixedsalt' 'S3cret!Pass'
openssl passwd -6 -salt 'fixedsalt' 'S3cret!Pass'   # 两次输出完全一致
```

这就是 `/etc/shadow` 的工作原理：登录验证时，系统从存储的哈希串里读出 `$6$` 后面那段盐，用同样方式重算一遍比对。**盐不需要保密，它只负责让同一口令在不同账号下哈希不同**——否则攻击者可以对整库共用一张预计算表。第10章给服务端账号设密码、第13章 htpasswd 场景，这条命令会再次出场。

为什么网站存口令要存哈希？因为数据库总会泄——**泄出去的必须是哈希**，攻击者拿到的只是一堆指纹，得先过 PBKDF2/SHA-512 crypt 的成本墙。反例是那些明文存口令、撞库后一夜裸奔的公司——你的口令有没有被明文存过，从「同一个口令在多家网站复用」的那一刻起就由不得你。所以本章实验的最后一步，就是把云笔记团队的口令习惯也升级掉。

## 4.5 编码三兄弟：hex、base64 与「这不是加密」

hex 和 base64 在本书反复出场，这里一次性钉死它们的身份：**编码不是加密**。

| | 编码（hex / base64） | 加密（AES） |
| ---- | ---- | ---- |
| 有没有钥匙 | 没有 | 有 |
| 谁能还原 | **任何人**，算法公开 | 没有钥匙的人不可行 |
| 目的 | 让二进制能在文本协议里安全旅行 | 让数据读不懂 |

判断法一句话：**没有钥匙就能还原的，都是编码**。base64 解码一秒钟，hex 更是直接可读——它们只是给二进制数据换了一身「文本协议能穿的衣服」。最常见的误解现场：把数据 base64 一下就当加密了（某著名令牌 JWT 的前两段就是明文 base64，谁都能解开看，它靠第三段的签名防篡改，从不防偷看）。

JWT 值得当场解剖一次，因为它把本章两个知识点装在一个身体里。一个典型的 JWT 长这样（三个 base64 段用 `.` 连接）：

```text
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ3YW5nIiwiZXhwIjoxODAwMDAwMDAwfQ.4d8a2c6e...
```

第一段解出来是 `{"alg":"HS256"}`——声明签名算法；第二段解出来是 `{"sub":"wang","exp":1800000000}`——用户与过期时间，**全是明文**；第三段才是 HMAC-SHA256 的签名，密钥正是服务器用本章的 `rand` 生成、台账里登记的那把。所以 JWT 的安全边界一句话：**内容不保密（别往里放敏感数据），但不可伪造（改了任何一段，第三段对不上）**。你以后在代码里签发 JWT 时，「密钥从哪来」的答案就是本章。

选择上，hex 两字符承载一字节、胜在人眼可比对（所以证书指纹用 hex）；base64 约 1.33 字符承载一字节、胜在紧凑（所以 PEM 证书、JWT 用它）。转换命令顺手记：

```bash
openssl base64 -in data.bin -out data.b64        # 编码
openssl base64 -d -in data.b64 -out data.bin     # 解码
```

一个会绊到人的细节：`openssl base64` 编码大文件时默认**每 64 字符折一行**（沿用 PEM 的排版传统），解码时也按行处理。如果你要把 base64 结果塞进 JSON 或 URL（这些场景不允许换行），加 `-A` 关成单行输出。反过来，解码别人给的单行长 base64 时若报错「invalid base64」，多半是对方按行编码了、你的阅读器截断了——`tr -d '\n'` 去掉换行再喂进去即可。编码器之间的换行习惯差异，是 base64 互操作问题的头号来源，第6章拆 PEM 时还会正式遇到它。

## 4.6 实验：给云笔记造钥匙

Part 1 的收官实验：生成三把真随机的钥匙，接上上一章的流水线，并立下保管纪律。做完后用三个问题自测，答不上就回到对应小节：

1. `BACKUP_PASS` 为什么不用自己编？（4.1：人挑的必是低熵的）
2. HMAC 密钥为什么和加密口令分两把？（第3章：密钥分离，泄露不连坐）
3. 台账为什么记「用途」而不记密钥本体？（台账会同步出去，密钥永不）

```bash
# 1. 生成三把钥匙（一次生成，分装三处）
openssl rand -base64 24 > /tmp/BACKUP_PASS.txt        # 备份加密口令，192 比特
openssl rand -hex 32   > /tmp/BACKUP_HMAC_KEY.txt     # 备份 HMAC 密钥，256 比特
openssl rand -base64 32 > /tmp/API_TOKEN.txt          # 对象存储 API 令牌，256 比特

# 2. 搬进专用密钥目录并锁死权限
mkdir -p ~/.cloudnote-secrets && chmod 700 ~/.cloudnote-secrets
mv /tmp/BACKUP_PASS.txt /tmp/BACKUP_HMAC_KEY.txt /tmp/API_TOKEN.txt ~/.cloudnote-secrets/
chmod 600 ~/.cloudnote-secrets/*

# 3. 流水线里通过环境变量引用（backup.sh 改两行）
export BACKUP_PASS=$(cat ~/.cloudnote-secrets/BACKUP_PASS.txt)
export BACKUP_HMAC_KEY=$(cat ~/.cloudnote-secrets/BACKUP_HMAC_KEY.txt)

# 4. 验收：三把钥匙长度、权限、互不相同
wc -c ~/.cloudnote-secrets/*           # 行数与字节数符合预期
ls -l ~/.cloudnote-secrets/            # 应全部 -rw------- (600)
diff <(openssl rand -hex 32) <(openssl rand -hex 32) >/dev/null \
  && echo "异常：两次 rand 输出相同" || echo "随机源工作正常"
```

为什么先写 /tmp 再 mv？生成与入库分两步走，是密钥操作的通用安全顺序：生成阶段用临时路径，验收长度与内容无误后，再以正确的权限落进正式目录。如果一步到位写进 `~/.cloudnote-secrets/`，中途断连或脚本失败可能留下一个权限未收紧、内容不完整的「半把钥匙」——半把钥匙比没有钥匙更危险，因为它看起来能用。

第四步最后一行是个俏皮但有效的冒烟测试：连跑两次 `rand` 还能输出相同，那 CSPRNG 一定是坏了——正常情况必然走到 `||` 分支。验收完把环境变量的 export 两行写进 `~/.bashrc` 或专用 env 文件（权限 600），别让钥匙每次开工都靠手敲。

三把钥匙各司其职：加密口令 192 比特（人不用记，密码管理器管）、HMAC 密钥 256 比特（与加密口令分离，符合密钥分离原则）、API 令牌 256 比特。保管纪律三条，和《Git 与 SSH 完全教程》第12章的 `.gitignore` 纪律一脉相承：

| 纪律 | 怎么做 | 为什么 |
| ---- | ---- | ---- |
| 不进 Git | 密钥目录绝不放在仓库路径下，`.gitignore` 兜底 | Git 的历史会永远记住你犯过的错 |
| 权限最小化 | 目录 700、文件 600 | 同机其他用户的眼睛也是威胁 |
| 定期轮换 | 密钥带日期命名，半年一换；怀疑泄露立刻换 | 轮换是「假设会泄露」前提下的必然动作 |

钥匙一多，「哪把钥匙管哪件事、什么时候生成、谁能换」就成了必须记账的事。云笔记团队最后立的是一份密钥台账——放在密码管理器里，任何一把钥匙的出生、用途、轮换日期都有据可查。台账与本机的钥匙文件是「账」与「货」的关系：账可以同步、可以打印、可以人手一份，货只存在于 `~/.cloudnote-secrets/` 里：

```text
# ~/.cloudnote-secrets/LEDGER.md（脱敏后入台账，密钥本体永不入台账）
| 钥匙 | 生成日期 | 用途 | 存放位置 | 轮换策略 | 责任人 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| BACKUP_PASS      | 2026-11-06 | 备份包加密   | ~/.cloudnote-secrets/ | 半年 | wang |
| BACKUP_HMAC_KEY  | 2026-11-06 | 备份密文校验 | ~/.cloudnote-secrets/ | 半年 | wang |
| API_TOKEN        | 2026-11-06 | 对象存储写入 | ~/.cloudnote-secrets/ | 季度 | 阿雪 |
| （预留行）        | —          | 新服务接入时先登记再生成 | — | — | — |
```

别嫌这张表土——第14章安全复盘中你会发现，几乎每一起密钥事故的根因调查，第一步都是「这把钥匙是谁在什么时候、给什么用的」。台账此刻多写一行，事故当晚少猜一小时。预留行是给未来的：新服务要密钥时，**先登记用途与责任人，再动手生成**——顺序反了，密钥就会像口香糖一样粘在代码里。

> [!TIP] 与密码管理器配合
> `rand -base64 24` 的输出直接粘进 1Password / Bitwarden 当密码用，就是「机器生成、人类托管」的标准姿势——人的脑子负责记住管理器的口令，管理器负责记住一切随机产物。反过来，「要记的密码自己编，记不住的再让机器生成」是灾难顺序：人会不自觉地往「能记住」的方向妥协。

至此 Part 1 完工。回到 ch00 的里程碑表自查：**M1（给任意文件做加密加校验双保险并完整还原）应该已经过线**——打包、加密、指纹、还原四个动作你已经各做过一遍。过线标准再强调一遍：不是「看过」，是「合上书写完 backup.sh 与 restore.sh 且还原结果 sha256 一致」。

顺手做一次轮换演练，把纪律变成肌肉记忆：`mv` 把 `BACKUP_HMAC_KEY.txt` 改名成 `BACKUP_HMAC_KEY.2026-11-06.retired.txt`，重新 `rand` 一把新的顶上，然后用旧密钥去验上周的 `.hmac` 文件——你会看到 `TAMPERED`（其实是密钥换了）。这个「换钥匙后旧清单立即失效」的体验提前演示了一个工程事实：**轮换必须与清单、备份的再生成联动**，只换钥匙不换清单，等于给所有历史数据判了死刑。完整轮换 SOP 在第14章复盘时收拢成清单。

## 本章小结

- 安全强度 = 熵的指数：人类口令约 40-60 比特，`rand` 随机 256 比特——「看起来复杂」和「随机」是两回事，衣服不改变身体
- `$RANDOM` 与语言内置 random 是 15 比特级别的伪随机，看到几个输出即可推算后续——安全场景一律 `openssl rand`
- 2008 年 Debian 事故：一行「没用」的熵代码被删，全球钥匙空间塌缩到 3 万种——**随机数生成器是最不该被优化的地方**
- `openssl rand -hex/-base64 N`：对称密钥 256 比特起步；会话令牌 128 比特起步
- 熵由内核 CSPRNG 提供，现代观点下 `/dev/urandom` 与 `getrandom(2)` 是正确选择——别自己造随机数
- `openssl passwd -6` 生成 `$6$` 口令哈希：存哈希不存口令，慢是美德；盐不保密，防的是预计算表
- **编码不是加密**：没有钥匙就能还原的都是编码；JWT 前两段明文可读，靠第三段签名防伪造
- 密钥纪律：不进 Git、权限 600、台账记账、定期轮换（轮换要与清单联动）——M1 里程碑应该已经过线
