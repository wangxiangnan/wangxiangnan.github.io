# 第10章：高级调试技巧

> "The most effective debugging tool is still careful thought, coupled with judiciously placed print statements." —— Brian Kernighan (1979)

Kernighan 说这话的时候是 1979 年。四十多年后的今天，我们有了更强大的工具——但"仔细思考"依然是调试的核心。这一章要给你的，是让 VSCode 成为你思考的放大器：复合调试让你同时观察系统的多个层面，浏览器调试让你打通前后端，远程调试让你排查生产环境的问题。

上一章是基础功，这一章是组合拳。

## 10.1 复合调试配置：同时调试前后端

在全栈开发中，你经常需要同时调试前端和后端。手动分别启动两个调试会话太原始了——`compounds` 配置让你一键启动所有调试：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Launch Backend",
            "type": "node",
            "request": "launch",
            "program": "${workspaceFolder}/server/src/index.ts",
            "runtimeArgs": ["--require", "ts-node/register"],
            "env": { "PORT": "4000" },
            "console": "integratedTerminal",
            "serverReadyAction": {
                "pattern": "Server running on (https?://\\S+)",
                "uriFormat": "%s",
                "action": "debugWithChrome"
            }
        },
        {
            "name": "Launch Frontend",
            "type": "chrome",
            "request": "launch",
            "url": "http://localhost:3000",
            "webRoot": "${workspaceFolder}/client/src",
            "sourceMaps": true
        }
    ],
    "compounds": [
        {
            "name": "Full Stack Debug",
            "configurations": ["Launch Backend", "Launch Frontend"],
            "presentation": {
                "hidden": false,
                "group": "fullstack",
                "order": 1
            },
            "stopAll": true
        }
    ]
}
```

关键点：

- `compounds` 数组定义复合配置
- `configurations` 列出要同时启动的调试配置名
- `stopAll: true` 表示停止任何一个时，停止所有（设为 `false` 则独立控制）
- `serverReadyAction` 是神来之笔：它监听后端输出的 `Server running on http://localhost:4000`，然后自动打开 Chrome 并附加调试器——无需手动打开浏览器

## 10.2 浏览器调试：前端开发必备

## Chrome / Edge 调试配置

```json
{
    "name": "Debug Chrome",
    "type": "chrome",
    "request": "launch",
    "url": "http://localhost:3000",
    "webRoot": "${workspaceFolder}/src",
    "sourceMaps": true,
    "sourceMapPathOverrides": {
        "webpack:///src/*": "${webRoot}/*",
        "webpack:///./*": "${webRoot}/*",
        "webpack:///*": "*"
    },
    "userDataDir": "${workspaceFolder}/.vscode/chrome-debug-profile",
    "runtimeArgs": [
        "--disable-web-security",
        "--auto-open-devtools-for-tabs"
    ]
}
```

## 关键配置解析

- `webRoot`：告诉调试器你的源码在哪里，以便 Source Map 能正确映射
- `sourceMapPathOverrides`：解决打包工具（Webpack/Vite）路径映射问题
- `userDataDir`：使用独立的 Chrome 配置文件（避免与你的个人浏览器冲突）
- `runtimeArgs`：传递给 Chrome 的启动参数

## Attach 模式（调试已打开的浏览器）

```json
{
    "name": "Attach to Chrome",
    "type": "chrome",
    "request": "attach",
    "port": 9222,
    "webRoot": "${workspaceFolder}/src",
    "sourceMaps": true
}
```

需要先用远程调试端口启动 Chrome：

```bash
# macOS
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome --remote-debugging-port=9222

# Windows
"C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222

# Linux
google-chrome --remote-debugging-port=9222
```

## 10.3 Node.js 调试进阶

## Attach 模式与远程调试

当你的 Node.js 服务运行在 Docker 容器或远程服务器中时，Attach 模式是你的唯一选择：

```json
{
    "name": "Attach to Remote Node.js",
    "type": "node",
    "request": "attach",
    "port": 9229,
    "address": "localhost",
    "localRoot": "${workspaceFolder}/src",
    "remoteRoot": "/app/src",
    "protocol": "inspector",
    "sourceMaps": true,
    "restart": true,
    "skipFiles": ["<node_internals>/**"]
}
```

服务器端需要用 `--inspect=0.0.0.0:9229` 启动（注意 `0.0.0.0` 允许外部连接，生产环境慎用）：

```bash
node --inspect=0.0.0.0:9229 dist/index.js
```

如果使用 Docker，确保端口映射：

```yaml
# docker-compose.yml
services:
  app:
    ports:
      - "9229:9229"   # 调试端口
      - "3000:3000"   # 应用端口
    command: node --inspect=0.0.0.0:9229 dist/index.js
```

## nodemon 热重载调试

开发中最常用的模式之一——代码改动自动重启，同时保持调试器连接：

```json
{
    "name": "Debug with Nodemon",
    "type": "node",
    "request": "launch",
    "runtimeExecutable": "nodemon",
    "runtimeArgs": [
        "--inspect",
        "--ext", "ts,json",
        "--exec", "ts-node",
        "src/index.ts"
    ],
    "restart": true,
    "console": "integratedTerminal",
    "skipFiles": ["<node_internals>/**"]
}
```

`"restart": true` 是关键——当 Node.js 进程重启时，调试器会自动重新连接，无需手动操作。

## 10.4 Python 调试

## 基础 Python 调试

```json
{
    "name": "Python: Current File",
    "type": "python",
    "request": "launch",
    "program": "${file}",
    "console": "integratedTerminal",
    "justMyCode": true,
    "env": {
        "PYTHONPATH": "${workspaceFolder}"
    }
}
```

## 虚拟环境调试

```json
{
    "name": "Python: Virtual Environment",
    "type": "python",
    "request": "launch",
    "program": "${file}",
    "console": "integratedTerminal",
    "python": "${workspaceFolder}/venv/bin/python",
    "justMyCode": false,
    "env": {
        "FLASK_APP": "app.py",
        "FLASK_DEBUG": "1"
    }
}
```

`justMyCode: false` 允许你 step into 第三方库的代码——在排查依赖库 bug 时很有用。

## Django 专用配置

```json
{
    "name": "Django: Development Server",
    "type": "python",
    "request": "launch",
    "program": "${workspaceFolder}/manage.py",
    "args": ["runserver", "--noreload"],
    "console": "integratedTerminal",
    "django": true,
    "env": {
        "DJANGO_SETTINGS_MODULE": "myproject.settings.dev"
    },
    "justMyCode": true
}
```

`"django": true` 启用 Django 模板断点——你可以在 `.html` 模板文件中设置断点！

## Flask 专用配置

```json
{
    "name": "Flask: Development",
    "type": "python",
    "request": "launch",
    "module": "flask",
    "args": ["run", "--no-debugger", "--no-reload"],
    "env": {
        "FLASK_APP": "src/app.py",
        "FLASK_ENV": "development"
    },
    "jinja": true,
    "justMyCode": true
}
```

`"jinja": true` 启用 Jinja2 模板断点。

## 10.5 数据断点和异常断点

## 数据断点（Data Breakpoint）

当某个变量的值发生变化时暂停——这在追踪"这个值什么时候被改的"问题时是终极武器。

在变量面板中，右键点击一个变量 → **Break on Value Change**。VSCode 会在该变量的值被修改时自动暂停，你可以从调用堆栈中追踪到修改来源。

> ⚠️ 注意：数据断点的可用性取决于调试器。Python（debugpy）和 C++（通过 GDB/LLDB）通常支持，Node.js 的支持较有限。

## 异常断点（Exception Breakpoint）

在断点面板底部，点击"异常断点"图标（像一个闪电），可以配置：

- **Uncaught Exceptions**：未捕获的异常时暂停（默认开启）
- **All Exceptions**：所有异常时暂停（包括被 `try/catch` 捕获的）
- **自定义异常过滤**：某些调试器允许按异常类型过滤

```json
// 也可以在 launch.json 中配置
{
    "name": "Debug with All Exceptions",
    "type": "node",
    "request": "launch",
    "program": "${workspaceFolder}/src/index.js",
    "stopOnEntry": false
}
```

在调试过程中，你可以随时在断点面板中切换异常断点的开关状态——这在排查"为什么这里有异常被吞掉了"时非常有用。

## 10.6 调试控制台进阶技巧

## 控制台变量格式化

在调试控制台中，你可以通过特定方式控制输出格式：

```javascript
// 以表格形式显示数组/对象
console.table(users)

// 以可折叠的树形显示
console.dir(config, { depth: null })

// 计时
console.time('db-query')
// ... 执行操作 ...
console.timeEnd('db-query')  // db-query: 42ms

// 条件日志
console.assert(user.age >= 18, 'User must be 18+')

// 分组
console.group('Request Processing')
console.log('Step 1: Validate')
console.log('Step 2: Transform')
console.log('Step 3: Save')
console.groupEnd()
```

## 在断点处执行调试命令

VSCode 的条件断点不仅可以用于条件暂停，还可以用于条件执行：

```javascript
// 条件断点中输入以下表达式
// 每次循环记录状态但不暂停
(debuggerCommand('log', `Loop iteration ${i}: value=${arr[i]}`), false)
```

## 10.7 实战：前后端同时调试的 Compound 配置

让我们为一个 React + Express 全栈项目配置完整的复合调试方案。

项目结构：

```
fullstack-app/
├── .vscode/
│   └── launch.json
├── client/          # React 前端 (Vite)
│   ├── src/
│   └── vite.config.ts
├── server/          # Express 后端
│   ├── src/
│   └── tsconfig.json
├── docker-compose.yml
└── package.json
```

## 完整 launch.json

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "Server: Debug",
            "type": "node",
            "request": "launch",
            "runtimeExecutable": "nodemon",
            "runtimeArgs": [
                "--inspect",
                "--ext", "ts",
                "--exec", "ts-node",
                "server/src/index.ts"
            ],
            "cwd": "${workspaceFolder}",
            "restart": true,
            "console": "integratedTerminal",
            "env": {
                "NODE_ENV": "development",
                "DATABASE_URL": "postgresql://localhost:5432/myapp"
            },
            "skipFiles": ["<node_internals>/**"],
            "serverReadyAction": {
                "pattern": "Server ready on port (\\d+)",
                "action": "startDebugging",
                "name": "Client: Debug Chrome"
            }
        },
        {
            "name": "Client: Debug Chrome",
            "type": "chrome",
            "request": "launch",
            "url": "http://localhost:5173",
            "webRoot": "${workspaceFolder}/client/src",
            "sourceMaps": true,
            "sourceMapPathOverrides": {
                "webpack:///src/*": "${webRoot}/*",
                "meteor://💻app/*": "${webRoot}/*"
            }
        },
        {
            "name": "Server: Attach",
            "type": "node",
            "request": "attach",
            "port": 9229,
            "restart": true,
            "skipFiles": ["<node_internals>/**"]
        },
        {
            "name": "Server: Jest Test",
            "type": "node",
            "request": "launch",
            "program": "${workspaceFolder}/node_modules/.bin/jest",
            "args": [
                "server/",
                "--runInBand",
                "--config", "server/jest.config.ts"
            ],
            "console": "integratedTerminal"
        }
    ],
    "compounds": [
        {
            "name": "Full Stack: Server + Client",
            "configurations": ["Server: Debug", "Client: Debug Chrome"],
            "stopAll": true,
            "presentation": {
                "hidden": false,
                "group": "fullstack",
                "order": 1

        },
        {
            "name": "Server + Tests",
            "configurations": ["Server: Debug", "Server: Jest Test"],
            "stopAll": false
        }
    ]
}
```

## 调试工作流

1. 选择 **Full Stack: Server + Client** 配置
2. 按 `F5` 启动
3. 后端服务器启动，监听 API 请求
4. Chrome 自动打开前端页面
5. 在前端 React 组件中设置断点（比如按钮点击处理函数）
6. 在后端 Express 路由中设置断点（比如 API 处理函数）
7. 在浏览器中操作，观察前端断点触发
8. 跟踪请求发送，观察后端断点触发
9. 在调试控制台中检查请求/响应数据
10. 修改代码，nodemon 自动重启后端，调试器自动重连

## 10.8 进阶：Source Maps 调试

Source Maps 是连接编译后代码与源码的桥梁。没有它，调试 TypeScript、React JSX、Sass 或任何需要编译的语言就是一场噩梦。

## Source Map 原理

```
TypeScript (源码)    →   tsc    →   JavaScript (编译后)    →   Source Map
src/index.ts                       dist/index.js              dist/index.js.map
```

Source Map 文件记录了编译后代码的每个位置与源码位置的映射关系。当调试器在 `dist/index.js` 的第 42 行暂停时，它查询 Source Map，发现这对应 `src/index.ts` 的第 35 行，于是你在编辑器中看到的是源码。

## 常见问题与解决

**断点"灰点"（未验证）**：

```json
// 确保 tsconfig.json 中开启了 sourceMap
{
    "compilerOptions": {
        "sourceMap": true,
        "inlineSourceMap": false,
        "inlineSources": true  // 将源码嵌入 Source Map
    }
}
```

**路径映射问题（Webpack/Vite）**：

```json
// launch.json 中修正路径映射
{
    "sourceMapPathOverrides": {
        "webpack:///./src/*": "${webRoot}/*",
        "webpack:///src/*": "${webRoot}/*",
        "webpack:///*": "*",
        "webpack:///./~/*": "${webRoot}/node_modules/*"
    }
}
```

## 调试 Minified 代码

当你在生产环境中遇到 bug，只有压缩后的代码时：

1. 如果有 Source Map（`app.min.js.map`），确保它和压缩文件在同一目录
2. 在 VSCode 中配置 `sourceMapPathOverrides` 指向你的源码目录
3. 如果没有 Source Map，使用 Chrome DevTools 的 **Pretty Print** 功能（`{}` 按钮）先格式化代码，然后在格式化后的代码上设置断点

```json
{
    "name": "Debug Production Build",
    "type": "chrome",
    "request": "launch",
    "url": "http://localhost:8080",
    "webRoot": "${workspaceFolder}/src",
    "sourceMaps": true,
    "resolveSourceMapLocations": [
        "${workspaceFolder}/**",
        "!**/node_modules/**"
    ]
}
```

📋 **本章小结**

- **compounds** 配置让你一键启动多个调试会话，适合全栈开发
- **serverReadyAction** 实现后端就绪后自动启动前端调试
- **浏览器调试** 支持 launch 和 attach 两种模式
- **Node.js Attach** 模式适用于 Docker、远程服务器、nodemon 等场景
- **Python 调试** 针对 Django/Flask 有专门的配置选项（模板断点等）
- **数据断点** 追踪变量变化，**异常断点** 捕获异常抛出
- **Source Maps** 是调试编译语言的必需配置，路径映射问题是最常见的调试障碍
