## 6.1 分流路由设计——一张 conf 管多条路

AllowedIPs 从来不止能写一个网段：**逗号分隔即可并存**，内核按最长前缀匹配（Longest Prefix Match）选路——目的地址落在多个网段里时，掩码最长的赢：

```ini
AllowedIPs = 10.66.66.0/24, 192.168.1.0/24
```

这行写进客户端 conf 后，路由决策变成三分支：10.66.66.x 走隧道（VPN 网段）、192.168.1.x 也走隧道（家里内网，6.2 之后生效）、其余走物理网卡。多 Peer 场景同理——如果你日后建了两条隧道（公司一条、家里一条），把 10.66.66.0/24 给公司、192.168.1.0/24 给家里，互不覆盖。

最长前缀匹配也带来一条必须记住的限制：**AllowedIPs 只能「加路」，不能「减路」**。比如 VPN 网段里有台测试机 10.66.66.9 你不想让它走隧道，在同一个 Peer 里再写一条 `10.66.66.9/32` 没有用——更精确的前缀仍指向同一个 Peer，包照样进隧道。要把某个地址排除出去，只能给它安排另一条更具体的路由（另一个 Peer/另一张网卡 + 策略路由），或者用 `Table = off` 关掉 wg-quick 的自动路由后自己画。这也是 WireGuard 不做「排除语法」的代价。反过来，`/24` 下再细分 `/25`、`/26` 给不同 Peer 属于高级玩法，本书的星型拓扑用不到；规则只有一条：**AllowedIPs 是你亲手画的地图，画了才通，没画就不通**。

| 场景 | 客户端 AllowedIPs | 效果 |
| ---- | ---- | ---- |
| 只访问 VPN 网段 | `10.66.66.0/24` | 第四章的默认分流 |
| VPN 网段 + 家里内网 | `10.66.66.0/24, 192.168.1.0/24` | 本章 6.2 的主线配置 |
| 全隧道 | `0.0.0.0/0` | 4.2 的全防护模式 |

一个全隧道模式的进阶需求值得预告：想「全隧道但排除某些网段」（比如公司 SSO 走本地网），wg-quick 没有「排除语法」，需要在 `PostUp` 里手工补路由或用 `Table = off` 关闭自动路由后自己画——复杂度陡增，本书不展开；多数人真正需要的是上面第二行的「多网段分流」，它简单且够用。

多网段分流还有一个与移动端相关的实用细节：iOS/Android 官方 App 对多网段 AllowedIPs 支持良好，逗号分隔照常导入；个别第三方客户端只认第一条——遇到「桌面通了手机不通」，先查这个兼容性坑。第七、八章的 mihomo 客户端在分流上有自己的一套规则体系，到时另讲。

## 6.2 站点到站点——把家里内网缝进隧道

目标：在外用笔记本访问家里内网的任何设备（打印机 192.168.1.30、传感器 192.168.1.40……），不只是 4.1 里那台装了客户端的 NAS。拓扑只有三跳：

```text
  笔记本(外)          云服务器(公网)           NAS(家, 192.168.1.20)
 10.66.66.2 ───────▶ 10.66.66.1 ──────────▶ 10.66.66.4 ──本地──▶ 192.168.1.30
  AllowedIPs:         查路由: 192.168.1/24    转发+伪装          打印机等
  含 192.168.1/24     → 属 NAS 那个 Peer     出家里网卡
```

「先猜再读」第二问在这里兑现：**家里不需要任何入站配置**。NAS 作为客户端**主动外连**服务器（Endpoint 是服务器的公网地址），隧道方向从家里发起——NAT 只挡「从外往里连」，挡不住「从里往外连」再顺原路返回。这与 2.6 保活的原理同源：谁先发起，谁的 NAT 映射就先建立，回程复用这条映射。

三台机器各改一处，缺一不可（这就是「先猜再读」第一问的两台配合机器：服务器与 NAS）：

**第一步，NAS 装 WireGuard 并写配置**（`192.168.1.20` 上的 `/etc/wireguard/wg0.conf`）：

```ini
[Interface]
Address = 10.66.66.4/24
PrivateKey = nAsPr1...(nas.private 的内容，第五章已发放)
# 收到隧道包后转发进家里内网，并伪装源地址
PostUp = sysctl -w net.ipv4.ip_forward=1; iptables -A FORWARD -i wg0 -j ACCEPT; iptables -A FORWARD -o wg0 -m state --state ESTABLISHED,RELATED -j ACCEPT; iptables -t nat -A POSTROUTING -d 192.168.1.0/24 -j MASQUERADE
PostDown = sysctl -w net.ipv4.ip_forward=0; iptables -D FORWARD -i wg0 -j ACCEPT; iptables -D FORWARD -o wg0 -m state --state ESTABLISHED,RELATED -j ACCEPT; iptables -t nat -D POSTROUTING -d 192.168.1.0/24 -j MASQUERADE

[Peer]
PublicKey = k5S+1x...(服务器公钥)
Endpoint = 203.0.113.10:51820
# 注意：只有 VPN 网段走隧道——家里内网是本地网络，绝不能进隧道
AllowedIPs = 10.66.66.0/24
PersistentKeepalive = 25
```

回程的 `-o wg0 ... ESTABLISHED,RELATED` 与 3.4 同款，NAS 上跑 Docker/ufw 时尤其不能省。

注意那个反直觉的点：NAS 的 AllowedIPs **不含** `192.168.1.0/24`——它就住在那个网段里，把本地网段送进隧道等于绕地球一圈回自己（环路）。第四章 4.1 的核对表在这里失效的场景，值得专门记住。

**第二步，服务器的 NAS Peer 段声明「它身后挂着家里内网」**（编辑 wg0.conf 后 syncconf，或直接用第五章脚本发完再改）：

```ini
[Peer]
# nas
PublicKey = uT9bVc...=
AllowedIPs = 10.66.66.4/32, 192.168.1.0/24
```

这一行是 2.5 cryptokey 路由的高光时刻：AllowedIPs 在服务端本来是白名单（允许 NAS 用这些源地址），加上 `192.168.1.0/24` 后**同时也是路由声明**——「去 192.168.1.x 的包，封装给 NAS 那条隧道」。路由表和准入表又一次合二为一。

**第三步，笔记本的多网段分流**：把 6.1 的 `10.66.66.0/24, 192.168.1.0/24` 写进客户端 conf，重新导入。

验证：笔记本 `ping 192.168.1.30`，通；在服务器 `tcpdump -ni wg0` 能看到笔记本 → 192.168.1.30 的明文包；NAS 上 `tcpdump -ni wg0` 同样可见。链路三跳，包在每条边上的样子都能亲眼看到——这比背配置有效得多。

一个站点互联特有的 MTU 提示：跨三跳的隧道叠加会进一步压低有效 MTU，若遇到「小包通、大包断」（ping 通、传文件卡），把 NAS 与客户端的 `MTU` 从 1420 再降到 1380 量级通常立愈——3.2 的 MTU 字段在多跳拓扑里是活的参数，不是常数。

方案升级路线：若家里的主路由器本身能跑 WireGuard（如 OpenWrt 固件），可把「NAS 网关」升级为「路由器网关」，整屋设备无需经 NAS 中转——原理与本节完全一致，只是 Peer 换成路由器、转发规则内置。本书选 NAS 方案是因为它零路由器依赖、任何能装 Linux 的盒子都能干。

## 6.3 无客户端设备——回程路由的两种解法

打印机、摄像头、智能家居这类嵌入式设备装不了 WireGuard，但 6.2 的拓扑已经让它们**天然可达**——靠的正是 NAS 的伪装（MASQUERADE）：隧道里来的包被改写源地址后送进家里内网，打印机看到的来源是 `192.168.1.20`（NAS），应答也回给 NAS，再由 NAS 沿隧道送回笔记本。设备全程不知道 VPN 的存在。

伪装方案零配置但有代价：**家里设备无法主动发起**到隧道设备的连接（`10.66.66.x` 在它眼里不可路由）。若需要双向（比如隧道内的手机 AirPlay 到电视），给家里设备补一条静态路由。判断用哪种方案只需要一个问题：**这台设备需不需要「知道」隧道里有人？** 不需要（打印机、传感器只被动服务）就伪装；需要（投屏、双向同步）就静态路由。两种方案对照：

| 方案 | 做法 | 单向/双向 | 何时选 |
| ---- | ---- | ---- | ---- |
| 伪装（6.2 默认） | NAS 出口 MASQUERADE | 单向：隧道 → 内网 | 默认选择，零侵入 |
| 静态路由 | 家里设备或其网关加 `10.66.66.0/24 via 192.168.1.20` | 双向 | 需要内网主动连隧道时 |

静态路由加在哪一层取决于你家网络：单网段小网络直接在设备上配网关不现实，通常加在主路由器上（管理界面找「静态路由」）；没条件改路由器就维持伪装方案，接受单向。

顺带补一个 2.6 留下的悬念：**两端 NAT 后**的直连问题（比如两台家用 NAS 互通）不属于本书拓扑——WireGuard 自身不做打洞，标准解法就是本章这个模式：找一台公网可达的机器做中转（我们的服务器），两端都以客户端身份连它。这也是 Tailscale 等托管方案的本质工作——把「找一台公网中转」产品化。

注意中转的代价：两端之间的流量要**经过服务器两跳**（A → 服务器 → B），带宽与延迟都翻倍。日常远程接入（客户端 ↔ 服务器）不受影响——流量本来就只有一跳；受影响的只是「客户端互访」这种少数场景，为自己的拓扑选择付出对应的带宽成本，是天经地义的工程取舍。

## 6.4 内网 DNS——dnsmasq 十行配置

网段打通后，下一个体验跃升是命名：`ping nas` 而不是 `ping 10.66.66.4`。服务器上装 dnsmasq（轻量 DNS + DHCP 服务），只监听隧道接口：

```text
$ sudo apt install -y dnsmasq
$ cat > /etc/dnsmasq.d/vpn.conf <<'EOF'
listen-address=10.66.66.1
bind-interfaces
# 内网域名：隧道内地址与家里内网地址各一个
address=/nas-tunnel.home.lan/10.66.66.4
address=/nas-home.home.lan/192.168.1.20
# 其余域名转发给公网 DNS
server=1.1.1.1
EOF
$ systemctl restart dnsmasq
$ sudo ufw allow in on wg0 to any port 53 proto udp    # 若启用 ufw
```

客户端把 `DNS = 1.1.1.1` 改成 `DNS = 10.66.66.1` 重新导入，验证：

```text
$ nslookup nas-tunnel.home.lan 10.66.66.1
Address: 10.66.66.4
```

两个设计点：`bind-interfaces` 限定 dnsmasq 只在 `10.66.66.1` 收查询，**不给公网接口开 53 端口**——开放解析器（Open Resolver）会被滥用为 DDoS 反射源，是 DNS 服务最经典的错误；`nas-tunnel` 与 `nas-home` 两个域名分开，因为从隧道访问家里 NAS 应该走 `10.66.66.4`（加密直达），从家里内网访问走 `192.168.1.20`（本地直达），一个域名返回哪个地址取决于问的人在哪边——命名清晰比统一省事重要。

还要注意 DNS 与分流的联动（4.5 的规则在多网段下依然成立）：`DNS = 10.66.66.1` 的查询包目的地是 VPN 网段，分流模式下自然进隧道；而其余域名的解析结果（公网网站 IP）若不在 AllowedIPs 里，访问流量照样走物理网卡——**内网域名进隧道、公网域名走原路**，这正是分流模式最理想的形态：只有你需要保护的东西在隧道里。

## 6.5 OpenVPN 对照——同一场景的另一种实现

悬了两章的对照表来交。先说清 OpenVPN 何时仍然值得用：目标设备只有 TCP 通道可用（WireGuard 是纯 UDP，2.3）；老旧路由器/系统没有 WireGuard 支持；团队已有成熟的证书签发流程。其他场景一律选 WireGuard。

最小可用的服务端配置长这样（对照意味大于实操——没有证书链它跑不起来，而证书链正是它「繁琐」的来源）：

```text
# /etc/openvpn/server/server.conf（节选）
port 1194
proto udp
dev tun
ca ca.crt          # CA 证书 —— WireGuard 没有的东西
cert server.crt    # 服务器证书
key server.key     # 服务器私钥
dh dh.pem          # DH 参数
server 10.8.0.0 255.255.255.0
# 若服务器背后另有内网（例如家里 192.168.1.0/24），再 push 对应路由：
# push "route 192.168.1.0 255.255.255.0"
client-to-client
```

注意 10.66.66.0/24 是本书 WireGuard 的隧道网段；OpenVPN 场景下它自己的隧道是 10.8.0.0/24，不要再把 WireGuard 的网段 push 给 OpenVPN 客户端。

同一场景（远程接入网关）下两种实现的真差异：

| 维度 | WireGuard（本书主线） | OpenVPN |
| ---- | ---- | ---- |
| 身份 | 32 字节密钥对 | CA 签发的证书链 |
| 配置文件 | 一张 conf，五个字段 | conf + 证书 + DH + 推送路由 |
| 传输层 | 仅 UDP | UDP/TCP 均可（TCP 穿透是它独有优势） |
| 客户端分发 | conf 或二维码 | 多文件证书包或内嵌 ovpn |
| 性能 | 内核态，接近裸网卡 | 用户态，数倍差距（2.1） |
| 协议设计 | 固定套件不协商 | TLS 协商，灵活但面大 |

协议层的完整对比（IPsec、隧道模式细节、各协议 RFC 背景）在站内[《网络协议完全教程》第二十二章](/network-protocol/ch22)，那里已经给过一张 WireGuard vs OpenVPN 的协议对比表——本章补充的是**运维视角**：你每天要维护的文件数量、要理解的概念数量、出错时的排查路径。三个维度 WireGuard 全面占优，这就是本书主线选它的完整理由。

如果确实要上手 OpenVPN，给一条最省事的路径提示：`easy-rsa` 工具包负责生成上表里的证书链（ca、cert、key、dh 四件），`apt install openvpn easy-rsa` 后按官方 quick start 逐步执行即可；客户端侧把证书与 conf 打包成 `.ovpn` 分发。你会立刻体会到 4.4 二维码分发在 WireGuard 里是多么奢侈的简洁——那是删掉整个证书体系的回报。

## 6.6 安全加固清单

最后用一张表收束本书的安全实践——按优先级排列，前三项实施成本低、收益大：

| 加固项 | 做法 | 对应原理 |
| ---- | ---- | ---- |
| 服务只监听内网 | SSH、数据库绑定 10.66.66.1 或 127.0.0.1，公网接口不监听 | 1.1 的风险账在此兑现 |
| 密钥最小持有 | 私钥只在设备本体；conf 走扫码或 SSH 直传 | 4.4 泄露面清单 |
| 配置权限审计 | `wg0.conf` 与 clients/ 全部 600/700（3.1 已设，定期复查） | PrivateKey 明文在文件里 |
| 换非标端口 | 51820 改自选高位端口 | 减少扫描噪音（协议本身静默，2.3，此项锦上添花） |
| 注销要彻底 | 设备退役/丢失立即 revoke（5.4），不删文件了事 | 白名单摘除即内核静默丢弃 |
| 定期轮换 | 可疑即 revoke + re-add（5.4），花名册留审计痕迹 | 2.4 前向保密管会话，静态密钥要人管 |
| 关闭 SaveConfig | conf 不写 `SaveConfig = true` | 运行时改动不回写，文件是唯一事实源（5.5 同理） |
| 监控握手 | 定时 `wg show` 记录 latest handshake，陌生 peer 告警 | 发现未授权接入的唯一窗口 |

其中「服务只监听内网」是整套体系的收益总账：第一章 1.1 算过的风险账，到这里才真正结清——数据库不再暴露公网、SSH 不再被全网扫描，公网上只剩一个静默的 UDP 端口。加固清单之外的「不做」也要交代：不需要 fail2ban（WireGuard 没有可爆破的登录表单，非法包直接静默丢弃）、不需要证书过期监控（没有证书）——WireGuard 的安全模型本身就把传统 VPN 的一大半运维负担消灭在了设计里。

清单不必一次做完：前三项在搭建当天顺手完成，中间三项纳入日常操作习惯（注销与轮换本来就该走脚本），后两项属于「知道即可、出问题再查」——安全实践跟代码一样，最怕的不是少，而是做了一遍没人维护。

## 本章小结

- AllowedIPs 逗号分隔多网段并存，内核按最长前缀匹配选路——分流从单网段扩展成多网段只需一行；
- 站点互联三步缺一不可：NAS 开转发与伪装、服务器 Peer 声明 `192.168.1.0/24`、客户端多网段分流；
- NAS 的 AllowedIPs 绝不能含家里本地网段——本地网络进隧道即环路，这是本章最重要的反直觉点；
- 家里零入站配置：NAS 主动外连服务器，NAT 挡不住由内向外的隧道——保活原理的又一次应用；
- 无客户端设备靠 MASQUERADE 单向可达，双向需求补静态路由 `10.66.66.0/24 via 192.168.1.20`；
- 两端 NAT 后的互通标准解法就是本章拓扑：公网中转 + 两端客户端化——Tailscale 的本质工作；
- dnsmasq 只绑隧道地址，公网不开 53——开放解析器是 DNS 服务的头号错误；
- OpenVPN 的位置：TCP 穿透与老设备兼容，其余场景 WireGuard 全面占优；协议层深挖见 ch22；
- 加固总账：服务只监听内网让 1.1 的风险清零，公网只剩一个静默的 UDP 端口。
