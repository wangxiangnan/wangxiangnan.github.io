# 第14章：Docker与CI/CD —— 自动化构建与部署

---

> 在前两部分中，我们学会了如何把应用"装进集装箱"（Dockerize），以及如何用 Docker Compose 让多个集装箱愉快地住在一起。现在，是时候让这条生产线真正自动化起来了——从代码提交到生产部署，全程无人值守。准备好了吗？我们要开启"工业模式"了。

## 引言：代码的自动流水线

想象一下你开了一家蛋糕店。最初，每个蛋糕你都是亲手做的——搅拌面糊、烤制、裱花、包装，全程手工。后来生意好了，你搞了一条流水线：自动搅拌→自动烘烤→自动裱花→自动包装。你只需要往入口扔原料，出口就出来一个完美蛋糕。

CI/CD（持续集成/持续部署）就是软件开发的"自动流水线"。你只需要 `git push`，剩下的事情——代码检查、构建镜像、运行测试、推送到仓库、部署上线——全部自动完成。

如果说 Docker 是标准化的"集装箱"，那 CI/CD 就是自动化搬运集装箱的"港口起重机"。没有 CI/CD，你每次发版都得手动 `docker build`、`docker push`、`ssh` 到服务器 `docker pull`……这不是 2024 年该有的工作方式。

> [!TIP] 提示
> CI 和 CD 的区别：CI（Continuous Integration）关注的是"代码合并后自动验证"，CD（Continuous Deployment/Delivery）关注的是"验证通过后自动上线"。两者组合起来，就是"从代码到生产"的完整自动化管道。

## 14.1 Docker 在 CI/CD 中的角色

在 CI/CD 流水线中，Docker 扮演着多重角色：

```bash
开发者 git push
    │
    ▼
┌─────────────────────────────────────────────────┐
│              CI/CD 流水线                         │
│                                                   │
│  ① Lint（代码检查）                               │
│      ↓                                            │
│  ② Build（构建 Docker 镜像）  ← Docker 是产物     │
│      ↓                                            │
│  ③ Test（在容器中运行测试）  ← Docker 是运行环境   │
│      ↓                                            │
│  ④ Push（推送镜像到 Registry）← Docker 是交付物   │
│      ↓                                            │
│  ⑤ Deploy（拉取镜像部署上线） ← Docker 是部署单元  │
└─────────────────────────────────────────────────┘
    │
    ▼
  生产环境运行
```

Docker 在每一步都提供了**一致性保证**：你在 CI 里构建的镜像，和最终在生产环境运行的镜像，是同一个东西。"在我机器上能跑"这个问题，从此不复存在。

## 14.2 GitHub Actions + Docker 完整流程

GitHub Actions 是目前最流行的 CI/CD 平台之一，和 GitHub 仓库天然集成，用起来非常方便。

### 14.2.1 编写 Docker CI Workflow

让我们为一个 Node.js 项目编写完整的 CI workflow：

```yaml
# .github/workflows/docker-ci.yml
# GitHub Actions 的工作流配置文件

name: Docker CI/CD Pipeline
# 工作流名称，会显示在 GitHub 的 Actions 页面上

on:
  push:
    branches: [main, develop]
    # 当 main 或 develop 分支有 push 时触发
  pull_request:
    branches: [main]
    # 当有 PR 指向 main 分支时也触发
    # 这样可以在合并前自动验证代码

env:
  REGISTRY: ghcr.io
  # 使用 GitHub Container Registry
  IMAGE_NAME: ${{ github.repository }}
  # 镜像名自动跟仓库名一致，比如 myorg/myapp

jobs:
  # ============ Job 1: 代码质量检查 ============
  lint:
    name: 🔍 代码检查
    runs-on: ubuntu-latest
    # 在 GitHub 提供的 Ubuntu 虚拟机上运行

    steps:
      - name: 检出代码
        uses: actions/checkout@v4
        # checkout action：把仓库代码拉到虚拟机里

      - name: 安装 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          # 自动缓存 npm 依赖，加速后续构建

      - name: 安装依赖并检查代码
        run: |
          npm ci
          # ci 比 install 更适合 CI 环境：
          # 它会严格按照 package-lock.json 安装，保证一致性
          npm run lint
          # 运行 ESLint 检查代码质量

  # ============ Job 2: 构建和测试 Docker 镜像 ============
  build-and-test:
    name: 🐳 构建与测试
    runs-on: ubuntu-latest
    needs: lint
    # 等 lint 通过后才开始构建，节省资源

    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 构建 Docker 镜像
        run: |
          docker build -t myapp:test .
          # 用 :test 标签构建，和生产镜像区分开

      - name: 在容器中运行测试
        run: |
          docker run --rm myapp:test npm test
          # --rm：容器退出后自动删除，不留垃圾
          # 在容器内运行测试，确保测试环境和生产环境一致

      - name: 保存镜像供后续 Job 使用
        if: github.ref == 'refs/heads/main'
        # 只有 main 分支才保存镜像，PR 不需要
        run: |
          docker save myapp:test | gzip > /tmp/myapp.tar.gz
          # 把镜像导出为文件，后续 Job 可以直接加载

      - name: 上传镜像文件
        if: github.ref == 'refs/heads/main'
        uses: actions/upload-artifact@v4
        with:
          name: docker-image
          path: /tmp/myapp.tar.gz
          retention-days: 1
          # 只保留1天，因为下次构建会有新镜像

  # ============ Job 3: 推送镜像到 Registry ============
  push:
    name: 📦 推送镜像
    runs-on: ubuntu-latest
    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    # 只有 main 分支的 push 才会推送镜像

    permissions:
      contents: read
      packages: write
      # 需要写入 packages 的权限才能推送到 GHCR

    steps:
      - name: 登录到 GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
          # GITHUB_TOKEN 是 GitHub 自动提供的，不需要手动配置

      - name: 提取元数据（标签和标签）
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=
            # 用 commit SHA 作为标签，比如 a1b2c3d
            type=raw,value=latest
            # 同时打上 latest 标签
            type=raw,value={{date 'YYYYMMDD'}}-{{sha}}
            # 日期+SHA 的组合格式，方便追溯

      - name: 构建并推送镜像
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          # 使用 GitHub Actions 的缓存
          cache-to: type=gha,mode=max
          # mode=max：缓存所有构建层，不仅仅是最终层
```

> [!TIP] 提示
> `docker/build-push-action` 是一个"瑞士军刀"级别的 Action，它内部使用了 BuildKit（还记得我们在第5章讲过的 Docker 新一代构建引擎吗？），自带多平台构建、缓存、SBOM 生成等高级功能。比手动写 `docker build` + `docker push` 强太多了。

### 14.2.2 多架构构建

现在 Apple Silicon（arm64）越来越普及，你的镜像可能需要在 amd64 和 arm64 上都能跑。手动构建两次太麻烦了，用 `build-push-action` 一次搞定：

```yaml
      # 在 push job 的 steps 中添加：

      - name: 配置 QEMU
        uses: docker/setup-qemu-action@v3
        # QEMU 是一个处理器模拟器
        # 它让 x86 的 GitHub Runner 也能构建 arm64 镜像
        # 就像给一个只会说中文的人配了一个同声翻译，他也能和外国朋友聊天了

      - name: 配置 Docker Buildx
        uses: docker/setup-buildx-action@v3
        # Buildx 是 Docker 的扩展构建工具
        # 支持多平台构建、高级缓存等功能

      - name: 构建并推送多架构镜像
        uses: docker/build-push-action@v5
        with:
          push: true
          platforms: linux/amd64,linux/arm64
          # 同时构建两个平台的镜像
          # 推送到 Registry 时会创建一个 manifest list
          # 用户 docker pull 时会自动拉取匹配自己平台的镜像
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

> **Warning:** 多架构构建比单架构慢很多（因为要用 QEMU 模拟不同 CPU），在免费的 GitHub Runner 上构建 arm64 镜像可能需要较长时间。如果你的项目对构建速度有要求，可以考虑使用自托管 Runner（Self-hosted Runner），或者使用 ARM 原生的 Runner。

### 14.2.3 缓存策略详解

Docker 构建缓存是加速 CI 的关键。GitHub Actions 提供了几种缓存方式：

```yaml
# 方式1：GitHub Actions Cache（推荐）
# 利用 GitHub 的缓存存储构建层
- uses: docker/build-push-action@v5
  with:
    cache-from: type=gha
    cache-to: type=gha,mode=max
    # 优点：零配置，自动管理
    # 缺点：缓存大小有限制（每个仓库10GB）

# 方式2：Registry Cache
# 把构建缓存推送到镜像仓库中
- uses: docker/build-push-action@v5
  with:
    cache-from: type=registry,ref=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:buildcache
    cache-to: type=registry,ref=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:buildcache,mode=max
    # 优点：缓存容量大，可以跨 Job 共享
    # 缺点：需要额外的存储空间

# 方式3：本地缓存（适合自托管 Runner）
- uses: docker/build-push-action@v5
  with:
    cache-from: type=local,src=/tmp/.buildx-cache
    cache-to: type=local,dest=/tmp/.buildx-cache-new,mode=max
# 需要手动管理缓存目录的轮转
```

> [!TIP] 提示
> 缓存就像你冰箱里的剩菜——能加速下次的"做饭"过程，但放太久会变质的。`mode=max` 表示缓存所有中间层，而不仅仅是最终层。对于多阶段构建（multi-stage build），这特别有用，因为连编译阶段的中间产物也会被缓存。

## 14.3 GitLab CI + Docker 完整流程

GitLab CI 是另一个流行的选择，尤其适合自建 GitLab 的团队。它的配置方式和 GitHub Actions 略有不同。

### 14.3.1 Docker-in-Docker vs Kaniko

在 GitLab CI 里构建 Docker 镜像，有两种主要方式：

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Docker-in-Docker (DinD) | 在容器里运行 Docker daemon | 功能完整 | 需要特权模式，安全风险 |
| Kaniko | 无 daemon 的镜像构建工具 | 不需要特权模式 | 某些高级特性不支持 |

```yaml
# .gitlab-ci.yml
# GitLab CI 配置文件

# ====== 全局配置 ======
variables:
  DOCKER_TLS_CERTDIR: "/certs"
  # DinD 模式需要 TLS 证书目录
  IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  # 镜像标签：registry地址/项目名:commit短SHA
  IMAGE_LATEST: $CI_REGISTRY_IMAGE:latest

stages:
  - lint
  - build
  - test
  - deploy

# ====== Stage 1: 代码检查 ======
lint:
  stage: lint
  image: node:20-alpine
  # 直接在 Node.js 容器中运行，不需要 Docker
  script:
    - npm ci
    - npm run lint
  rules:
    - if: $CI_MERGE_REQUEST_ID
    # 每个 MR 都检查
    - if: $CI_COMMIT_BRANCH == "main"

# ====== Stage 2: 构建 Docker 镜像（使用 DinD）======
build:
  stage: build
  image: docker:24
  # 使用 Docker CLI 镜像
  services:
    - docker:24-dind
    # DinD 服务：在容器旁边跑一个 Docker daemon
    # 就像在集装箱里又放了一个小型集装箱工厂
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    # 登录到 GitLab Container Registry
    # 这些变量是 GitLab 自动提供的
  script:
    - docker build -t $IMAGE_TAG -t $IMAGE_LATEST .
    - docker push $IMAGE_TAG
    - docker push $IMAGE_LATEST
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# ====== Stage 2 替代方案: 使用 Kaniko（更安全）======
build-kaniko:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:v1.9.1-debug
    entrypoint: [""]
    # Kaniko 不需要 Docker daemon
    # 它在用户空间直接构建镜像，更安全
  script:
    - /kaniko/executor
      --context "${CI_PROJECT_DIR}"
      --dockerfile "${CI_PROJECT_DIR}/Dockerfile"
      --destination "${IMAGE_TAG}"
      --destination "${IMAGE_LATEST}"
      --cache=true
      # 开启缓存加速
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual
      # 这个 Job 设为手动触发，和 DinD 版本二选一

# ====== Stage 3: 测试 ======
test:
  stage: test
  image: docker:24
  services:
    - docker:24-dind
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - docker pull $IMAGE_TAG
    - docker run --rm $IMAGE_TAG npm test
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# ====== Stage 4: 部署 ======
deploy:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add --no-cache openssh-client
    # 安装 SSH 客户端用于远程部署
  script:
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | ssh-add -
    - ssh -o StrictHostKeyChecking=no $DEPLOY_USER@$DEPLOY_HOST
      "docker pull $IMAGE_TAG &&
       docker stop myapp || true &&
       docker rm myapp || true &&
       docker run -d --name myapp -p 3000:3000 $IMAGE_TAG"
    # 简单的 SSH 部署：拉取新镜像，停掉旧容器，启动新容器
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  environment:
    name: production
    url: https://myapp.example.com
```

> **Warning:** Docker-in-Docker 需要 `privileged` 模式运行，这意味着容器拥有接近宿主机的权限。在共享 GitLab Runner 上要特别注意安全风险。如果你的 GitLab 管理员不允许特权模式，请使用 Kaniko 方案。

## 14.4 Jenkins + Docker Pipeline

Jenkins 是 CI/CD 领域的"老前辈"——虽然年纪大了，但依然是很多企业的首选。通过 Docker Pipeline Plugin，Jenkins 可以优雅地和 Docker 配合。

```groovy
// Jenkinsfile
// Jenkins Pipeline 配置文件（声明式语法）

pipeline {
    agent any
    // 在任意可用的 Jenkins agent 上运行

    environment {
        REGISTRY = 'registry.example.com'
        IMAGE_NAME = 'myapp'
        IMAGE_TAG = "${env.BUILD_NUMBER}"
        // 用 Jenkins 构建号作为镜像标签
        // 比如 myapp:42, myapp:43... 简单好追溯

        // 从 Jenkins 凭据管理中获取 Registry 登录信息
        REGISTRY_CREDENTIALS = credentials('docker-registry-credentials')
    }

    stages {
        stage('代码检查') {
            agent {
                docker {
                    image 'node:20-alpine'
                    // Jenkins 会自动拉取这个镜像
                    // 并在容器中运行此 stage 的所有步骤
                    args '-v /tmp:/tmp'
                    // 可以挂载卷到容器中
                }
            }
            steps {
                sh 'npm ci'
                sh 'npm run lint'
            }
        }

        stage('构建镜像') {
            steps {
                script {
                    // 使用 Docker Pipeline Plugin 的 build 方法
                    dockerImage = docker.build(
                        "${REGISTRY}/${IMAGE_NAME}:${IMAGE_TAG}",
                        "--build-arg NODE_ENV=production ."
                        // 通过 build-arg 传入构建参数
                    )
                }
            }
        }

        stage('测试') {
            steps {
                script {
                    // inside() 方法会在容器内部运行命令
                    dockerImage.inside {
                        sh 'npm test'
                        // 在构建好的镜像容器内运行测试
                        // 这确保了测试环境和生产环境一致
                    }
                }
            }
        }

        stage('推送镜像') {
            when {
                branch 'main'
                // 只有 main 分支才推送
            }
            steps {
                script {
                    docker.withRegistry(
                        "https://${REGISTRY}",
                        'docker-registry-credentials'
                        // 使用 Jenkins 凭据管理中的认证信息
                    ) {
                        dockerImage.push()
                        // 推送带 build number 标签的镜像
                        dockerImage.push('latest')
                        // 同时推送 latest 标签
                    }
                }
            }
        }

        stage('部署') {
            when {
                branch 'main'
            }
            steps {
                sshagent(['deploy-server-key']) {
                    sh """
                        ssh deploy@production-server '
                            docker pull ${REGISTRY}/${IMAGE_NAME}:${IMAGE_TAG} &&
                            docker-compose -f /opt/myapp/docker-compose.yml up -d
                            # 使用 docker-compose 在生产服务器上更新服务
                        '
                    """
                }
            }
        }
    }

    post {
        // Pipeline 结束后的清理工作
        always {
            // 不管成功失败都会执行
            sh 'docker image prune -f'
            // 清理悬空镜像，释放磁盘空间
        }
        success {
            echo '🎉 部署成功！去喝杯咖啡庆祝一下吧！'
        }
        failure {
            echo '💥 部署失败了……赶紧看看哪里出了问题。'
            // 这里可以加上 Slack/钉钉通知
        }
    }
}
```

> [!TIP] 提示
> Jenkins 的 Docker Pipeline Plugin 有一个很酷的功能：`docker.image().inside {}` 会自动处理容器生命周期，运行完命令后自动清理容器。就像 `using` 语句会自动释放资源一样，你不需要手动 `docker stop` 和 `docker rm`。

## 14.5 CI/CD 最佳实践

### 14.5.1 镜像标签策略

镜像标签就像是 Git commit 的 SHA——它应该能告诉你"这个镜像是什么时候、由谁、因为什么原因构建的"。

```bash
# ❌ 不推荐的标签策略
myapp:latest          # latest 在生产环境中是危险的！
                      # 因为你永远不知道 "latest" 到底是哪个版本
                      # 就像你永远不知道 "最新的代码" 是指哪次 commit

# ✅ 推荐的标签策略
myapp:a1b2c3d         # Git commit SHA —— 可追溯
myapp:1.2.3           # 语义化版本号 —— 人类友好
myapp:20240115-a1b2c3d  # 日期+SHA —— 时间和来源都有
myapp:main-a1b2c3d    # 分支+SHA —— 知道来自哪个分支

# 最佳实践：同时打多个标签
# docker build -t myapp:a1b2c3d -t myapp:1.2.3 -t myapp:latest .
```

### 14.5.2 安全扫描

在 CI 流水线中加入安全扫描，就像在蛋糕流水线上加一个"质检环节"——确保出去的产品没有问题：

```yaml
# 在 GitHub Actions 中使用 Trivy 进行安全扫描
- name: 扫描镜像漏洞
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
    format: 'sarif'
    output: 'trivy-results.sarif'
    severity: 'CRITICAL,HIGH'
    # 只关注高危和严重漏洞，减少噪音

- name: 上传扫描结果到 GitHub Security
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: 'trivy-results.sarif'
  # 扫描结果会出现在仓库的 Security 标签页中
```

### 14.5.3 部署策略

```bash
策略1：蓝绿部署（Blue-Green Deployment）
┌──────────────┐     ┌──────────────┐
│  蓝色环境     │     │  绿色环境     │
│  (当前生产)   │     │  (新版本)     │
│  v1.2.3      │     │  v1.2.4      │
│  ◄── 流量 ── │     │              │
└──────────────┘     └──────────────┘

部署步骤：
1. 在绿色环境部署新版本 v1.2.4
2. 在绿色环境运行冒烟测试
3. 切换流量到绿色环境
4. 如果出问题，立即切回蓝色环境

优点：零停机、可快速回滚
缺点：需要双倍资源


策略2：金丝雀部署（Canary Deployment）
┌────────────────────────────────┐
│  生产环境                       │
│                                │
│  ┌────────┐ ┌────────┐        │
│  │v1.2.3  │ │v1.2.3  │ 90%   │
│  │实例1   │ │实例2   │ ◄──流量│
│  └────────┘ └────────┘        │
│                                │
│  ┌────────┐                    │
│  │v1.2.4  │ 10%               │
│  │金丝雀  │ ◄──流量            │
│  └────────┘                    │
└────────────────────────────────┘

部署步骤：
1. 启动少量新版本实例（金丝雀）
2. 导入少量流量（比如10%）
3. 观察指标（错误率、延迟等）
4. 正常则逐步增加流量比例
5. 全部切换后删除旧版本

优点：风险最小、逐步验证
缺点：需要流量管理和监控
```

> [!TIP] 提示
> 选择部署策略就像选择发布策略——小团队小项目用简单的"滚动更新"就好，不用追求蓝绿或金丝雀。但如果你的服务用户量大、不能容忍停机，蓝绿部署是最低成本的"保险"。

## 14.6 实战：为 Node.js 项目配置完整的 GitHub Actions CI/CD

让我们把所有知识串起来，为一个实际的 Node.js 项目配置完整的 CI/CD。

首先，确保你的项目结构是这样的：

```bash
my-nodejs-app/
├── .github/
│   └── workflows/
│       └── ci-cd.yml
├── src/
│   ├── app.js
│   └── server.js
├── tests/
│   └── app.test.js
├── Dockerfile
├── .dockerignore
├── docker-compose.yml
├── package.json
└── package-lock.json
```

项目的 Dockerfile（多阶段构建，复习一下第5章的内容）：

```dockerfile
# Dockerfile

# ====== 阶段1：构建 ======
FROM node:20-alpine AS builder
WORKDIR /app

# 利用缓存层：先拷贝依赖描述文件
COPY package.json package-lock.json ./
RUN npm ci --only=production
# --only=production：只安装生产依赖
# 构建阶段不需要 devDependencies

# 拷贝源代码
COPY src/ ./src/

# ====== 阶段2：生产镜像 ======
FROM node:20-alpine AS production

# 安全最佳实践：不用 root 用户运行
RUN addgroup -g 1001 -S appgroup && \
    adduser -S appuser -u 1001 -G appgroup

WORKDIR /app

# 只从 builder 阶段拷贝必要文件
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/src ./src
COPY package.json ./

# 切换到非 root 用户
USER appuser

EXPOSE 3000

# 使用 node 而非 npm 启动，减少一层进程
CMD ["node", "src/server.js"]
```

完整的 CI/CD Workflow：

```yaml
# .github/workflows/ci-cd.yml

name: Node.js App CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ---- Job 1: Lint + Unit Test ----
  quality-check:
    name: 代码质量检查
    runs-on: ubuntu-latest

    services:
      # 如果测试需要数据库，可以在这里启动
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        # 等待数据库就绪后再运行测试

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - run: npm ci

      - name: ESLint 检查
        run: npm run lint

      - name: 单元测试
        run: npm test
        env:
          DATABASE_URL: postgresql://test:test@localhost:5432/testdb
          NODE_ENV: test

      - name: 上传测试覆盖率报告
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: coverage-report
          path: coverage/

  # ---- Job 2: Build Docker Image ----
  build:
    name: 构建 Docker 镜像
    runs-on: ubuntu-latest
    needs: quality-check

    permissions:
      contents: read
      packages: write

    outputs:
      image-tag: ${{ steps.meta.outputs.version }}
      image-digest: ${{ steps.build.outputs.digest }}

    steps:
      - uses: actions/checkout@v4

      - name: 配置 Buildx
        uses: docker/setup-buildx-action@v3

      - name: 登录 GHCR
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: 提取元数据
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=ref,event=pr
            type=sha,prefix=,format=short
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - name: 构建并推送
        id: build
        uses: docker/build-push-action@v5
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          # PR 时只构建不推送，用于验证 Dockerfile 是否正确

      - name: 安全扫描
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ steps.meta.outputs.version }}
          format: 'table'
          exit-code: '1'
          # 发现高危漏洞时让 CI 失败
          severity: 'CRITICAL'

  # ---- Job 3: Deploy ----
  deploy:
    name: 部署到生产环境
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    environment:
      name: production
      url: https://myapp.example.com
      # GitHub Environment：可以配置审批、保护规则等

    steps:
      - name: 部署到服务器
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: ${{ secrets.DEPLOY_USER }}
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            # 拉取新镜像
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ needs.build.outputs.image-tag }}

            # 使用 docker-compose 滚动更新
            cd /opt/myapp
            docker-compose pull
            docker-compose up -d --remove-orphans

            # 清理旧镜像
            docker image prune -f

            # 健康检查
            sleep 5
            curl -f http://localhost:3000/health || exit 1
```

::: v-pre
> [!TIP] 提示
> 这个 workflow 中使用了一个很实用的技巧——PR 时只构建不推送（`push: ${{ github.event_name != 'pull_request' }}`）。这样可以在 PR 阶段验证 Dockerfile 是否能正确构建，而不会污染 Registry。就像你在合并代码前会先跑一遍测试一样。
:::

## 本章小结

| 概念 | 说明 |
|------|------|
| CI/CD | 代码从提交到部署的自动化流水线 |
| GitHub Actions | GitHub 原生 CI/CD，配置简单，生态丰富 |
| GitLab CI | GitLab 原生 CI/CD，支持 DinD 和 Kaniko |
| Jenkins | 老牌 CI/CD，通过 Docker Pipeline Plugin 集成 |
| 镜像标签策略 | 使用 SHA/版本号/日期，避免在生产环境使用 `latest` |
| 安全扫描 | 在 CI 中用 Trivy 等工具自动检测漏洞 |
| 部署策略 | 蓝绿部署（双环境切换）、金丝雀部署（逐步放量） |

## 练习

1. **入门**：为你的一个项目配置 GitHub Actions CI workflow，实现 push 到 main 分支时自动构建并推送 Docker 镜像。
2. **进阶**：在上面的基础上添加安全扫描（Trivy），当检测到 CRITICAL 漏洞时阻止部署。
3. **挑战**：实现蓝绿部署策略——维护两个环境（blue/green），部署时先部署到非活跃环境，验证通过后切换 Nginx 反向代理。
