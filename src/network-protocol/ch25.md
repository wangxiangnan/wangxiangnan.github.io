## 25.1 Socket 编程基础：一切通信的起点

所有网络通信的起点都是 **Socket**——操作系统提供的网络通信抽象。你调用的每个 API，背后都是 8 章讲过的连接一生：

```python
"""TCP Echo：最基础的网络编程模式"""
import socket
import threading

def handle_client(conn):
    try:
        while True:
            data = conn.recv(1024)        # 阻塞等待数据
            if not data:                  # 空字节 = 对端发来 FIN（8.5 挥手完成）
                break
            conn.sendall(b"Echo: " + data)
    finally:
        conn.close()

server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)  # 对抗 8.6 的 TIME_WAIT
server.bind(('0.0.0.0', 9999))
server.listen(5)
print("[TCP Server] 监听端口 9999...")
while True:
    conn, addr = server.accept()          # 阻塞等待新连接
    print(f"[TCP Server] 新连接: {addr}")
    threading.Thread(target=handle_client, args=(conn,)).start()
```

三处细节都对应前文：`SO_REUSEADDR` 是为了让服务器重启时不必等 8.6 的 TIME_WAIT 消耗端口；`recv` 返回空字节意味着对端完成挥手；「一连接一线程」的模型简单直观，但 1000 个连接就要 1000 个线程——内存与调度开销爆炸，这就是下一个问题的起点。

## 25.2 I/O 模型：从阻塞到事件驱动

「先猜再读」第一问的答案是 **I/O 多路复用**。三级模型一路演进：

**阻塞 I/O**：`recv()` 等到天荒地老，一个连接占一个线程。简单但低效——25.1 就是这个模型。

**非阻塞 I/O**：`recv()` 没数据时立即返回而非挂起。但你需要不断轮询检查，CPU 烧在自己手里。

**I/O 多路复用**：一个线程同时监控一批 Socket，谁有事处理谁：

```
select() → poll() → epoll()（Linux）/ kqueue()（BSD/macOS）

select: 「这 1024 个 fd 谁有数据？」→ 每次全量遍历 → O(n)
epoll:  「有事件的 fd 名单给你」→ 注册兴趣列表，事件驱动回调 → O(1)
```

epoll 维护一个「兴趣列表」，注册的 Socket 有事件时直接返回就绪名单，无需遍历。C10K（单机一万连接）问题的答案是它，23.7 里 Nginx 轻松扛数万并发连接的底座也是它——现代高性能服务器几乎全是事件驱动架构。

## 25.3 asyncio：事件循环与协程

Python 的 `asyncio` 把 I/O 多路复用封装成 async/await 语法——17 章埋下的线在此兑现：

```python
"""asyncio 并发 Echo：一个线程处理数千连接"""
import asyncio

async def handle_echo(reader, writer):
    addr = writer.get_extra_info('peername')
    print(f"[Server] 新连接: {addr}")
    try:
        while True:
            data = await reader.read(1024)   # 挂起而非阻塞，让出事件循环
            if not data:
                break
            writer.write(f"Echo: {data.decode()}".encode())
            await writer.drain()             # 写缓冲过高时暂停——流控的应用层倒影
    finally:
        writer.close()
        await writer.wait_closed()
        print(f"[Server] 断开: {addr}")

async def main():
    server = await asyncio.start_server(handle_echo, '0.0.0.0', 9999)
    async with server:
        await server.serve_forever()

asyncio.run(main())
```

核心是**事件循环**：某个 `await` 的 I/O 未完成时，协程挂起、循环切去执行其他协程——单线程就处理大量并发连接，还免去了线程锁。`drain()` 值得单独记住：它在写缓冲区过高时暂停发送，正是 11.2 滑动窗口机制在应用层的倒影——TCP 的流控借你的手实现了背压。

## 25.4 协议设计方法论：帧、状态机与错误

自研协议要解决的**第一件事不是格式，是帧边界**——「先猜再读」第二问的答案：TCP 是字节流不是消息流（8.7），`recv(1024)` 返回的字节数跟「一条消息」毫无对应关系，可能半条、可能两条半。17.3 的 WebSocket 用长度字段重建帧边界，你的协议同样需要。

**需求先行**：写代码前先回答——传什么数据？延迟/吞吐/可靠性的要求？通信模式（请求响应/推送/双向）？连接是长是短？并发多大？答案决定你抄谁的作业：要可靠学 TCP，要推送学 MQTT，要极简学 CoAP。

**消息格式**三方案：

```
方案一 定长:     [类型 1B][载荷 固定N字节]          解析快，短消息也要占满 N 字节
方案二 长度前缀: [长度 4B][类型 1B][载荷 N字节]      最常用，帧边界清晰——SICP 选它
方案三 TLV:      [类型 1B][长度 2B][值 N字节] × N    灵活可扩展——21.3 的 Protobuf 就是这个思想
```

**状态机**：每个连接都有生命周期，用有限状态机管理——8.4 的 TCP 连接一生就是范本：

```
DISCONNECTED → CONNECTING → AUTHENTICATED → CHATTING → DISCONNECTED
任意状态 + error/timeout → 清理并回 DISCONNECTED
```

**错误处理三条军规**：每个阻塞操作都要有超时（永不无限等待）；重连用指数退避加随机抖动（9.4 的 RTO 退避思想，抖动防惊群）；后端不可用时降级返回缓存，而非直接报错。

**版本协商**：协议会演进，握手期就谈版本：

```
Client → Server: HELLO supported_versions=[1, 2, 3]
Server → Client: HELLO_OK selected_version=2
```

15.2 的 ALPN、24.8 的 MQTT Protocol Level 都是这个思想的现役案例——从第一版就留好字段，别等 v2 用户上不了线才想起。

## 25.5 编程实践：SICP——设计你自己的即时通讯协议

把方法论落到代码。**SICP（Simple Instant Chat Protocol）**：

```
SICP v1 协议规范
================

帧格式: [长度 4B big-endian][类型 1B][载荷 N 字节]

消息类型:
  0x01 CONNECT      客户端登录（载荷: 用户名）
  0x02 CONNECT_ACK  登录确认（载荷: 欢迎消息）
  0x03 MESSAGE      聊天消息（载荷: JSON {"from","text"}）
  0x04 BROADCAST    广播（载荷: 同 MESSAGE，服务器代发）
  0x05 USER_LIST    在线列表（载荷: JSON 数组）
  0x06 DISCONNECT   主动下线（载荷: 空）
  0xFF ERROR        错误（载荷: 错误消息）

状态机: DISCONNECTED → CONNECTING → AUTHENTICATED → CHATTING → DISCONNECTED
```

> [!TIP] 头定边界，载荷选编码，两层解耦
> SICP 载荷用 JSON 是为了可读性；换成 Protobuf（21.3）只是替换编码器，帧格式不动。自研协议时把「定边界」和「编码」分成两层，将来换编码不用动状态机。

`!I` 的 big-endian 是网络字节序——与 8.3 报头字段的约定一致。服务端：

```python
"""
SICP Server
运行: python sicp_server.py
"""
import asyncio
import json
import struct
import time

CONNECT, CONNECT_ACK, MESSAGE = 0x01, 0x02, 0x03
BROADCAST, USER_LIST, DISCONNECT, ERROR = 0x04, 0x05, 0x06, 0xFF

def encode_message(msg_type: int, payload: bytes) -> bytes:
    """[长度4B][类型1B][载荷]"""
    body = struct.pack('!B', msg_type) + payload
    return struct.pack('!I', len(body)) + body

async def decode_message(reader):
    """按长度前缀读一整条消息——帧边界的应用层重建"""
    length = struct.unpack('!I', await reader.readexactly(4))[0]
    body = await reader.readexactly(length)
    return body[0], body[1:]

class SICPServer:
    def __init__(self):
        self.clients = {}  # username -> StreamWriter

    def remove_client(self, name: str):
        if self.clients.pop(name, None):
            print(f"[Server] {name} 下线，在线: {list(self.clients)}")

    async def broadcast(self, sender: str, text: str):
        payload = json.dumps(
            {"from": sender, "text": text, "time": time.time()}).encode()
        msg = encode_message(BROADCAST, payload)
        for name, writer in list(self.clients.items()):
            if name == sender:
                continue
            try:
                writer.write(msg)
                await writer.drain()
            except Exception:
                self.remove_client(name)   # 广播失败视为死连接，顺手清理

    async def handle_client(self, reader, writer):
        username = None
        try:
            msg_type, payload = await asyncio.wait_for(
                decode_message(reader), timeout=10.0)  # 10 秒不发 CONNECT 就踢
            if msg_type != CONNECT:
                raise ValueError("expected CONNECT")
            username = payload.decode()
            if username in self.clients:
                writer.write(encode_message(ERROR, b"username taken"))
                await writer.drain()
                return
            self.clients[username] = writer
            ack = f"Welcome, {username}! online={len(self.clients)}".encode()
            writer.write(encode_message(CONNECT_ACK, ack))
            users = json.dumps(list(self.clients)).encode()
            writer.write(encode_message(USER_LIST, users))
            await writer.drain()
            await self.broadcast("SYSTEM", f"{username} joined")

            while True:
                msg_type, payload = await decode_message(reader)
                if msg_type == MESSAGE:
                    text = json.loads(payload.decode())["text"]
                    print(f"[Chat] {username}: {text}")
                    await self.broadcast(username, text)
                elif msg_type == DISCONNECT:
                    break
        except (asyncio.IncompleteReadError, ConnectionResetError,
                asyncio.TimeoutError, ValueError):
            pass   # 拔网线/超时/坏消息：全部走异常路径进 finally
        finally:
            if username:
                self.remove_client(username)
                await self.broadcast("SYSTEM", f"{username} left")
            writer.close()

    async def start(self):
        server = await asyncio.start_server(self.handle_client, '0.0.0.0', 8888)
        print("[SICP Server] 启动在端口 8888")
        async with server:
            await server.serve_forever()

asyncio.run(SICPServer().start())
```

「先猜再读」第三问的答案藏在 `finally` 块里：拔网线的用户发不出 DISCONNECT，但服务器读到 EOF 时抛 `IncompleteReadError`，走异常路径进 `finally` 清理并广播下线——这是 24.4 遗嘱消息的服务器自制版：MQTT 把「判死」交给 Broker，你把它写进了 `finally`。

客户端：

```python
"""
SICP Client
运行: python sicp_client.py Alice
"""
import asyncio
import json
import struct
import sys

def encode_message(msg_type: int, payload: bytes) -> bytes:
    body = struct.pack('!B', msg_type) + payload
    return struct.pack('!I', len(body)) + body

async def decode_message(reader):
    length = struct.unpack('!I', await reader.readexactly(4))[0]
    body = await reader.readexactly(length)
    return body[0], body[1:]

async def main():
    username = sys.argv[1]
    reader, writer = await asyncio.open_connection('127.0.0.1', 8888)
    writer.write(encode_message(0x01, username.encode()))    # CONNECT
    await writer.drain()

    async def receive_loop():
        try:
            while True:
                msg_type, payload = await decode_message(reader)
                if msg_type in (0x02, 0x05):
                    print(f"[Server] {payload.decode()}")
                elif msg_type == 0x04:
                    data = json.loads(payload.decode())
                    print(f"\n[{data['from']}]: {data['text']}")
                elif msg_type == 0xFF:
                    print(f"\n[错误] {payload.decode()}")
        except (asyncio.IncompleteReadError, ConnectionResetError):
            print("\n[连接已断开]")

    task = asyncio.create_task(receive_loop())
    loop = asyncio.get_running_loop()
    try:
        while True:
            text = await loop.run_in_executor(None, input, f"[{username}] > ")
            if text.strip() == '/quit':
                writer.write(encode_message(0x06, b''))      # DISCONNECT
                await writer.drain()
                break
            if text.strip():
                payload = json.dumps({"from": username, "text": text}).encode()
                writer.write(encode_message(0x03, payload))  # MESSAGE
                await writer.drain()
    except (EOFError, KeyboardInterrupt):
        pass
    finally:
        task.cancel()
        writer.close()

if __name__ == '__main__':
    if len(sys.argv) < 2:
        print("Usage: python sicp_client.py <username>")
        sys.exit(1)
    asyncio.run(main())
```

## 25.6 抓包实践：亲眼验证你写的协议

```bash
# 终端 1 启动服务器，终端 2/3 分别以 Alice、Bob 登录
python sicp_server.py
python sicp_client.py Alice
python sicp_client.py Bob
```

```bash
# 抓包验证帧格式（Bob 的 CONNECT 报文应该长这样）
tshark -i lo -f "tcp port 8888" -V

# TCP 流中的二进制数据：
# 0000: 00 00 00 0b    ← 长度前缀：消息体 11 字节
# 0004: 01             ← 类型：CONNECT
# 0005: 42 6f 62       ← 载荷："Bob"
```

四项验证清单，对应 25.4 的方法论：

1. **帧格式**：长度前缀、类型、载荷逐字节与规范对上——你的协议第一次「在线上有了实体」。
2. **广播**：Alice 发一条消息，多个客户端的 TCP 流里出现同一个 BROADCAST 帧。
3. **断线双路径**：`/quit` 能抓到 DISCONNECT 帧；直接 kill 客户端则没有——但服务器照样广播 SYSTEM left（finally 的功劳）。
4. **粘包**：写个小循环连续发 10 条消息，观察服务器仍逐条解析——长度前缀在 8.7 的字节流里重建了帧边界。

## 本章小结

- Socket 三板斧（accept/recv/sendall）背后是 8 章的连接一生：空字节即 FIN，SO_REUSEADDR 对抗 TIME_WAIT。
- I/O 模型三级跳：阻塞（一连接一线程）→ 非阻塞（轮询烧 CPU）→ 多路复用（epoll 事件回调 O(1)）——Nginx 的性能底座。
- asyncio 把事件循环封装成 async/await：await 挂起时让出循环，单线程伺候千连接；drain() 是 TCP 流控的应用层倒影。
- 自研协议第一坑是帧边界：TCP 是字节流，长度前缀在应用层重建帧——8.7 粘包与 17.3 长度字段是同一件事。
- 协议设计三件套：消息格式（定长/长度前缀/TLV）、状态机（TCP 连接一生是范本）、错误处理（超时、指数退避重连、降级）。
- 版本协商从第一版就要有：ALPN 与 MQTT Protocol Level 都是现役案例。
- 拔网线的清理靠异常路径的 finally——24.4 遗嘱消息的服务器自制版。

## 结语：从读协议到写协议

二十六章走完，从网线上的电压到 QUIC 的白板重画，你看到的是同一件事在每一层重演：**用明确的约定对抗不可靠的世界**。

协议设计的三条原则，全书每章都是它们的注脚：

1. **简单**：SMTP 靠文本命令跑了 40 多年（18.1）；WireGuard 用 4000 行代码进了内核（22.3）；MQTT 固定头只有 2 字节（24.2）。每个多余特性都是攻击面与 bug 的温床——少即是安全，少即是可靠。
2. **明确**：好的协议规范能让两个互不认识的团队写出完全兼容的实现。未定义行为是协议安全的最大敌人——TCP 状态机把每种输入的去向都写死（8.4），就是「明确」的范本。
3. **可扩展**：预留版本号、保留位、TLV 结构。HTTP 从 1.0 一路演进到 3（13→20 章）、Protobuf 用 reserved 占住编号（21.3）——演进不需要推倒重来。

最后一条铁律，也是本书想留给你的唯一一句咒语：

**永远不要假设网络是可靠的。**

每一个 `send()` 都可能失败，每一个 `recv()` 都可能超时，每一条连接都可能突然断开。从 TCP 的重传到 MQTT 的遗嘱，再到你 SICP 里的 `finally` 块——所有协议设计的终点，都是这一句话。

去写你自己的协议吧。现在你已经有了全部零件。
