# Ch02: 环境准备与项目初始化

## 本章目标

- 安装并配置 Node.js 版本管理工具
- 安装 pnpm 12
- 创建 monorepo 根目录并初始化 `pnpm-workspace.yaml`
- 配置根目录 `package.json`、`.gitignore`、`.npmrc` 等基础文件
- 完成一个完整的、可验证的初始化流程

> **全书版本基线（2026-10）**：Node.js 24 LTS、pnpm 12、Turborepo 2.11、TypeScript 7、ESLint 10、Vitest 5、Express 5、Zod 4、Prisma 7、Changesets 3。后续章节统一以这张表为准，不再各章单独指定。

## 2.1 Node.js 版本管理

在 monorepo 中，**所有包共享同一个 Node.js 版本**，因此统一版本至关重要。我们使用 `.nvmrc` 文件来锁定版本，确保团队所有成员和 CI 环境使用相同的 Node.js。

### 为什么是 Node.js 24

Node.js 的发布线在 2026 年的状态是：

| 版本 | 状态 | 维护截止 |
| ------ | ------ | ------ |
| Node.js 20 | 已 EOL | 2026-04 |
| Node.js 22 | Maintenance LTS | 2027-04 |
| Node.js 24 | **Active LTS** | 2028-04 |
| Node.js 26 | Current | 尚未进入 LTS |

教程选择 **Node.js 24 LTS**：它是当前活跃的 LTS，生态兼容性最好，同时满足 pnpm 12 的运行时要求（Node.js 22+）。Node.js 20 已经停止维护，不应再作为新项目的基线。

### 安装 nvm（Node Version Manager）

如果你还没安装 nvm，按平台选择安装方式：

**macOS / Linux：**

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
```

安装完成后重启终端，验证安装：

```bash
nvm --version
# 输出类似：0.40.1
```

**Windows：**

Windows 用户推荐使用 [nvm-windows](https://github.com/coreybutler/nvm-windows/releases)，下载安装包后按提示安装。

或者使用更现代的 [fnm](https://github.com/Schniz/fnm)（跨平台，Rust 编写，速度更快）：

```powershell
# Windows (通过 winget)
winget install Schniz.fnm

# 在 PowerShell 配置中添加（用于自动切换版本）
fnm env --use-on-cd | Out-String | Invoke-Expression
```

### 创建 .nvmrc

在项目根目录创建 `.nvmrc` 文件：

```bash
mkdir taskflow && cd taskflow

# 写入 Node.js 24 LTS 的主版本号
echo "24" > .nvmrc
```

使用主版本号而不是精确补丁号，可以让团队成员自动获得该 LTS 线的最新安全更新；如果你所在团队要求完全一致，也可以写精确版本（例如 `24.9.0`），但需要定期升级。

使用 `.nvmrc` 后，团队成员只需执行：

```bash
# 进入项目目录后
nvm use
# 输出：Now using node v24.x.x
```

如果你用的是 fnm，它甚至会在你 `cd` 进入目录时自动切换版本。

## 2.2 安装 pnpm 12

### 为什么选 pnpm

在 Ch01 中已经解释了选择 pnpm 的理由，这里补充一个直观的数据对比：

| 操作 | npm | yarn | pnpm |
| ------ | ----- | ------ | ------ |
| 安装全新依赖 | 基准 | 约 1.2x 更快 | 约 2-3x 更快 |
| 增量安装 | 基准 | 约 1.5x 更快 | 约 3-5x 更快 |
| 磁盘占用（10 个项目共用 react） | 10 份 | 10 份 | 1 份（硬链接） |

在 monorepo 场景下，速度和磁盘的优势会被进一步放大。

### 安装方式

推荐用 Corepack 或 npm 全局安装：

```bash
# 方式一：Corepack（Node 24 自带）
corepack enable
corepack prepare pnpm@12 --activate

# 方式二：npm 全局安装
npm install -g pnpm@12

# 验证安装
pnpm --version
# 输出类似：12.0.0
```

> **pnpm 12 的安装包是原生的**，不再依赖 npm CLI 作为兜底。如果你从 pnpm 11 升级，直接覆盖安装即可，`pnpm-lock.yaml` 可以继续使用。

## 2.3 初始化 Monorepo 根目录

现在我们开始正式创建项目。以下是一个完整的、可跟做的命令序列。

### 第一步：创建根目录并初始化 package.json

```bash
# 创建项目目录
mkdir taskflow && cd taskflow

# 初始化 package.json
pnpm init
```

这会在当前目录生成一个基础的 `package.json`。我们需要修改它。

### 第二步：编写根目录 package.json

打开 `package.json`，替换为以下内容：

```json
{
  "name": "taskflow",
  "version": "0.0.0",
  "private": true,
  "packageManager": "pnpm@12.0.0",
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": "^12.0.0",
      "onFail": "error"
    }
  },
  "engines": {
    "node": ">=24"
  },
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck",
    "clean": "turbo run clean",
    "format": "prettier --write \"**/*.{ts,tsx,vue,js,json,md}\""
  },
  "devDependencies": {
    "prettier": "^3.9.10",
    "turbo": "^2.11.0"
  }
}
```

逐个字段解释：

- **`"name": "taskflow"`**：项目名称。在 monorepo 中，根目录的 name 通常是项目品牌名。
- **`"private": true`**：**极其重要**。防止根目录的包被意外发布到 npm。Monorepo 的根目录永远不应该被发布。
- **`"packageManager": "pnpm@12.0.0"`**：精确锁定包管理器版本，Corepack 会据此选择 pnpm。请把补丁号替换成你本机 `pnpm --version` 的输出，团队统一即可。
- **`"devEngines.packageManager"`**：更严格的运行时约束，`onFail: "error"` 表示版本不匹配时直接失败。它与 `packageManager` 并不冲突：前者约束“允许的版本范围”，后者提供“精确的可执行版本”。
- **`"engines"`**：声明最低 Node.js 版本要求。pnpm 会在安装时检查。
- **`scripts`**：根目录的脚本通过 `turbo run` 来编排各子包的脚本执行。Ch10 会详细讲 `turbo.json` 的配置。
- **`devDependencies`**：放在根目录的 devDependencies 中的是整个项目共用的开发工具（Prettier、Turborepo）。

> **为什么 `turbo` 放在 devDependencies 而不是 dependencies？** 因为 Turborepo 只在开发和 CI 时使用，不会被打包到生产产物中。所有构建工具都应放在 devDependencies。

### 第三步：创建 pnpm-workspace.yaml

这是 pnpm workspace 的核心配置文件。**从 pnpm 11 开始，除了认证、registry、TLS、代理和本地地址之外，所有 pnpm 设置都必须写在这里**（或全局 `config.yaml`），写进 `.npmrc` 会被静默忽略。

在项目根目录创建 `pnpm-workspace.yaml`：

```yaml
packages:
  - "apps/*"
  - "packages/*"

# 供应链安全：pnpm 11+ 默认开启，这里显式写出便于团队理解
minimumReleaseAge: 1440        # 新发布的包需等待 1440 分钟（1 天）才允许安装
blockExoticSubdeps: true       # 阻止子依赖使用 git/file 等奇异源
strictDepBuilds: true          # 未在 allowBuilds 中声明的构建脚本直接报错
verifyDepsBeforeRun: install   # 运行脚本前校验 node_modules 与 lockfile 一致

# 允许执行 postinstall 的包（pnpm 11 起用 allowBuilds 取代 onlyBuiltDependencies）
allowBuilds:
  esbuild: true

# 依赖解析策略
autoInstallPeers: false
strictPeerDependencies: true

# TypeScript 7 是原生编译器，typescript-eslint 8.x 的 peer 范围尚未跟进
peerDependencyRules:
  allowedVersions:
    "typescript-eslint>typescript": "7"
    "@typescript-eslint/parser>typescript": "7"
    "@typescript-eslint/typescript-estree>typescript": "7"
```

这个配置的含义是：

- `packages`：`apps/` 和 `packages/` 下的每个子目录都是一个独立的包。
- `minimumReleaseAge`：供应链攻击的常见手法是抢注/劫持后立刻发版，延迟安装可以给社区留出发现时间。
- `blockExoticSubdeps`：防止子依赖偷偷引入 git 仓库或本地路径。
- `strictDepBuilds` + `allowBuilds`：只有显式允许的包才能执行安装脚本。`esbuild` 需要 postinstall 下载平台二进制，所以必须放行。
- `autoInstallPeers: false` + `strictPeerDependencies: true`：peer 依赖必须显式声明，版本不匹配直接报错，避免“能装上但运行时报错”。
- `peerDependencyRules`：typescript-eslint 8.72 的 peer 仍写作 `typescript >=4.8.4 <6.1.0`，而 TypeScript 7 与其 API 兼容但不在声明范围内。不显式放行的话，`strictPeerDependencies` 会让 `pnpm install` 直接失败。这是生态滞后于编译器的过渡配置，等 typescript-eslint 更新 peer 范围后即可删除。

> **为什么不用 `"**/package.json"` 这种通配符？** 因为显式列出 `apps/*` 和 `packages/*` 更清晰，也避免了意外把 `node_modules` 或其他目录识别为包。pnpm 要求精确、显式的配置。

**关于 packages 配置的更多选项：**

```yaml
# 如果需要排除某些目录
packages:
  - "apps/*"
  - "packages/*"
  - "!packages/deprecated-*"   # 排除 deprecated 开头的包

# 如果有不在 apps/packages 下的包
packages:
  - "apps/*"
  - "packages/*"
  - "tools/cli"                # 单独指定一个路径
```

### 第四步：创建目录结构

```bash
# 创建 apps 和 packages 目录
mkdir -p apps/web apps/api
mkdir -p packages/shared packages/eslint-config packages/tsconfig
```

暂时先创建空目录，后续章节会填充内容。

### 第五步：创建 .gitignore

在项目根目录创建 `.gitignore`：

```txt
# 依赖目录
node_modules/

# 构建产物
dist/
build/
.next/
.output/
.turbo/

# 日志
*.log
npm-debug.log*
pnpm-debug.log*

# 环境变量
.env
.env.local
.env.*.local

# 编辑器
.vscode/*
!.vscode/settings.json
!.vscode/extensions.json
.idea/

# 操作系统
.DS_Store
Thumbs.db

# 测试覆盖率
coverage/

# 临时文件
*.tmp
.cache/
```

> **为什么 `node_modules/` 要忽略？** 在 monorepo 中，pnpm 会在根目录和每个包下创建 `node_modules`。这些目录包含的是从全局 store 链接过来的文件，不应该提交到 Git。任何人 `git clone` 后只需执行 `pnpm install` 就能恢复。

### 第六步：创建 .npmrc

`.npmrc` 现在只负责“去哪里下载、用什么身份下载”：

```ini
registry=https://registry.npmjs.org/

# 私有 registry 示例（按需取消注释）
# @taskflow:registry=https://npm.pkg.github.com/
# //npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

逐行解释：

- **`registry`**：默认公共源。
- **scope 级 registry**：让 `@taskflow/*` 走私有源，其余包仍然走公共源。
- **`_authToken`**：认证信息属于 `.npmrc` 允许的内容；务必用环境变量插值，不要把 token 写死并提交。

> **pnpm 11+ 的重要变化**：`.npmrc` 只读取认证、registry、TLS、代理和本地地址这几类配置。`shamefully-hoist`、`node-linker`、`auto-install-peers`、`network-concurrency` 等设置如果还留在 `.npmrc`，**pnpm 不会报错，而是直接忽略**。看到“配置没生效”时，先检查它是不是放错了文件。
>
> 另外，pnpm 11 移除了 `manage-package-manager-versions` 开关；包管理器版本不匹配时的行为由 `pmOnFail` 控制。旧教程里在 `.npmrc` 写这个开关的做法已经失效。

### 第七步：安装根目录依赖

```bash
pnpm install
```

执行后你会看到 pnpm 在根目录创建了 `node_modules/` 和一个 `pnpm-lock.yaml` 文件。

> **`pnpm-lock.yaml` 必须提交到 Git。** 它确保所有开发者和 CI 环境安装完全相同版本的依赖。

### 第八步：初始化 Git 仓库

```bash
git init
git add .
git commit -m "chore: init monorepo with pnpm workspace"
```

此时你的目录结构应该是：

```txt
├── .gitignore
├── .npmrc
├── .nvmrc
├── apps/
│   ├── api/
│   └── web/

│   ├── shared/
│   └── tsconfig/

```

## 2.4 Turborepo 配置初探

虽然 Turborepo 的详细配置会在 Part 3 中深入讲解，但我们在这里先创建一个基础配置，确保 `turbo run` 命令可以正常工作。

在项目根目录创建 `turbo.json`：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {},
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "clean": {
      "cache": false
    }
  }
}
```

简单解释：

- **`build`**：`dependsOn: ["^build"]` 表示构建一个包之前，先构建它的所有依赖。`outputs: ["dist/**"]` 告诉 Turborepo 构建产物在 `dist/` 目录，用于缓存判断。
- **`dev`**：`cache: false` 表示开发服务器不缓存。`persistent: true` 表示这是一个长时间运行的进程（如 dev server），Turborepo 不会等待它完成。
- **`lint`**：lint 只读源码，不依赖上游构建，因此不需要 `dependsOn`。
- **`typecheck`**：依赖上游包的 build 完成，因为 TypeScript 需要读取上游生成的 `.d.ts` 声明文件。
- **`clean`**：清理操作不需要缓存。

验证 Turborepo 是否正常工作：

```bash
pnpm turbo build
```

输出应该类似：

```
• Packages in scope: 0
• Running build in 0 packages
• Remote caching disabled
  Tasks:    0 successful, 0 total
  Cached:   0 cached, 0 total
  Time:     0ms
```

这是正确的——此时 `apps/` 和 `packages/` 还是空目录，没有任何子包定义 `build` 脚本。

## 2.5 常见问题排查

**Q1: `pnpm install` 报错 "Cannot find module" 或版本不满足**

检查你的 Node.js 版本是否符合 `engines` 要求：

```bash
node --version  # 应该是 v24.x
pnpm --version  # 应该是 12.x
```

**Q2: `pnpm-workspace.yaml` 不被识别**

确保 YAML 格式正确（注意缩进用空格而非 tab）。可以用以下命令验证：

```bash
pnpm ls -r
```

如果报 YAML 解析错误，检查文件编码是否为 UTF-8。

**Q3: 安装后出现 peer dependency 警告**

由于我们在 `pnpm-workspace.yaml` 中设置了 `strictPeerDependencies: true`，某些包的 peer dependency 未安装时会报错。解决方案有两种：

- 安装缺失的 peer dependency
- 临时把 `strictPeerDependencies` 改为 `false`（不推荐长期保留）

**Q4: 明明改了 `.npmrc`，配置却不生效**

pnpm 11+ 不再从 `.npmrc` 读取非认证类设置。把对应配置迁移到 `pnpm-workspace.yaml`，例如：

```yaml
# 旧写法（.npmrc，已失效）
# shamefully-hoist=false
# auto-install-peers=false

# 新写法（pnpm-workspace.yaml）
shamefullyHoist: false
autoInstallPeers: false
```

**Q5: 构建脚本被阻止执行**

pnpm 11+ 默认阻止未声明的依赖执行安装脚本。看到 `Ignored build scripts` 提示时，把该包加入 `allowBuilds`：

```yaml
allowBuilds:
  esbuild: true
```

## 本章小结

- 使用 `.nvmrc` 锁定 Node.js 24 LTS，用 `packageManager` + `devEngines.packageManager` 锁定 pnpm 12——两道“锁”确保团队环境一致
- `pnpm-workspace.yaml` 是 workspace 的入口，同时承载 pnpm 11+ 的全部行为配置
- `.npmrc` 只放 registry 和认证信息；其他设置写进 `.npmrc` 会被静默忽略
- 根目录 `package.json` 的 `"private": true` 和 `"packageManager"` 字段不可遗漏
- pnpm 11+ 默认开启供应链安全策略：延迟安装新包、阻止奇异子依赖、拦截未声明的构建脚本
- `turbo.json` 定义了任务编排规则，`dependsOn: ["^build"]` 是最常见的模式
