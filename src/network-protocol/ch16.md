# 第16章：DNS——互联网的通讯录

## DNS 的设计动机

计算机之间通信靠 IP 地址，但人类记不住 `142.250.80.46` 这种数字串，更记不住 `2607:f8b0:4004:800::200e` 这种 IPv6 地址。我们需要一种方式，把人类友好的名字（`google.com`）映射到机器需要的地址（`142.250.80.46`）。

这个需求在 ARPANET 时代是通过一个文本文件 `HOSTS.TXT` 解决的——所有主机名和 IP 的映射关系都存在这个文件里，每个网络节点定期下载最新的副本。但当网络扩展到成千上万台主机时，这个中心化文件就成了瓶颈——每次更新都要同步到所有节点，名字冲突也成了家常便饭。

1983 年，Paul Mockapetris 设计了 DNS（Domain Name System），用**分布式数据库**替代了中心化的 HOSTS 文件。这是互联网基础设施中最伟大的设计之一——一个全球性的、去中心化的、层次化的命名系统，每天处理数万亿次查询。

## 域名空间结构

DNS 的域名空间是一棵倒置的树：

```
                        . (根域)
                       /|\
                     /  |  \
                  com  org  net  cn  edu ...  (顶级域 TLD)
                  /     |     \
              google  wiki  cloudflare  ...  (二级域 SLD)
               / \
           www  mail  api  ...  (子域名)
```

- **根域（Root）**：用 `.` 表示，通常省略。完整的域名应该写成 `www.example.com.`，最后的 `.` 就是根域。
- **顶级域（TLD, Top-Level Domain）**：`.com`、`.org`、`.net`、`.cn`、`.edu` 等。分为通用顶级域（gTLD）和国家代码顶级域（ccTLD）。近年来新增了上千个 gTLD，如 `.app`、`.dev`、`.xyz`。
- **二级域（SLD, Second-Level Domain）**：`example.com` 中的 `example`。这是你注册域名时买的部分。
- **子域名（Subdomain）**：`www.example.com`、`mail.example.com`。域名的拥有者可以自由创建子域名。

## DNS 查询过程

当你在浏览器输入 `www.example.com` 时，DNS 查询是这样进行的：

**1. 本地缓存检查**：浏览器先查自己的 DNS 缓存（Chrome 可以通过 `chrome://net-internals/#dns` 查看），然后查操作系统的缓存（Windows: `ipconfig /displaydns`，Linux: `systemd-resolve --statistics`）。

**2. 本地 DNS 解析器（Stub Resolver）**：如果缓存没有，请求发送到操作系统配置的 DNS 服务器（通常是你的 ISP 提供的递归解析器，或者你手动配置的 `8.8.8.8`、`1.1.1.1`）。

**3. 递归查询（Recursive Query）**：客户端对递归解析器说："帮我查 `www.example.com`，查不到就报错，别让我自己去找。"递归解析器承担全部查询工作。

**4. 迭代查询（Iterative Query）**：递归解析器自己去找答案的过程：

```
解析器 → 根服务器："www.example.com 在哪？"
根服务器 → 解析器："我不管 .com 的事，去找 .com 的服务器：192.5.6.30, 192.26.9.30, ..."

解析器 → .com TLD 服务器："www.example.com 在哪？"
TLD 服务器 → 解析器："example.com 的权威服务器是 ns1.example.com (93.184.216.34)"

解析器 → 权威服务器 ns1.example.com："www.example.com 的 IP 是什么？"
权威服务器 → 解析器："www.example.com → 93.184.216.34, TTL=3600"

解析器 → 客户端："www.example.com = 93.184.216.34"
```

递归解析器把结果缓存起来（缓存时间由 TTL 决定），下次有人再问 `www.example.com` 就不需要重新查了。

## DNS 报文格式

DNS 查询和响应使用统一的报文格式：

```
DNS Header (12 bytes):
  Transaction ID: 0xa3f2    ← 请求和响应的匹配标识
  Flags: 0x0100             ← 标准查询，期望递归
  Questions: 1
  Answer RRs: 0             ← 响应时包含答案数量
  Authority RRs: 0
  Additional RRs: 0

Question Section:
  Name: www.example.com     ← 查询的域名（实际编码为 \x03www\x07example\x03com\x00）
  Type: A (1)               ← 查询类型
  Class: IN (1)             ← 互联网类（几乎总是 IN）

Response Answer Section (响应时):
  Name: www.example.com
  Type: A (1)
  Class: IN (1)
  TTL: 3600                  ← 缓存时间（秒）
  Data Length: 4
  Address: 93.184.216.34    ← 解析结果
```

注意域名的编码方式——不是简单的字符串，而是**长度前缀编码**：每个标签前面加一个字节表示长度，最后以 `\x00` 结尾。`www.example.com` 编码为 `\x03www\x07example\x03com\x00`。

DNS 头部中的 **Flags** 字段包含多个标志位：

- **QR（1 bit）**：0=查询，1=响应
- **Opcode（4 bits）**：0=标准查询，1=反向查询，2=服务器状态查询
- **AA（1 bit）**：Authoritative Answer，权威回答
- **TC（1 bit）**：Truncated，报文被截断（UDP 超过 512 字节）
- **RD（1 bit）**：Recursion Desired，期望递归查询
- **RA（1 bit）**：Recursion Available，服务器支持递归
- **RCODE（4 bits）**：响应码，0=成功，3=域名不存在（NXDOMAIN）

## 记录类型

DNS 不只能映射 IP 地址，它支持多种记录类型：

- **A（Address）**：域名 → IPv4 地址。`www.example.com → 93.184.216.34`
- **AAAA（Quad-A）**：域名 → IPv6 地址。`www.example.com → 2606:2800:220:1:248:1893:25c8:1946`
- **CNAME（Canonical Name）**：域名 → 另一个域名（别名）。`www.example.com → example.com`。然后继续解析 `example.com` 的 A 记录。
- **MX（Mail Exchange）**：指定邮件服务器。`example.com → 10 mail.example.com`（10 是优先级，越小优先级越高）
- **TXT（Text）**：存储任意文本。常用于 SPF 邮件防伪造（`v=spf1 include:_spf.google.com ~all`）和域名所有权验证。
- **NS（Name Server）**：指定域名的权威 DNS 服务器。`example.com → ns1.example.com`
- **SOA（Start of Authority）**：域的权威信息，包括主 DNS 服务器、管理员邮箱、序列号、刷新间隔等。每个域只有一条 SOA 记录。
- **SRV（Service）**：指定特定服务的服务器地址。`_sip._tcp.example.com → 10 60 5060 sipserver.example.com`（优先级、权重、端口、目标）

## DNS 缓存

**TTL（Time To Live）**是 DNS 记录的"保质期"。TTL=3600 表示这条记录可以被缓存 3600 秒（1 小时）。过期后，下次查询必须重新向权威服务器请求。

TTL 的设计是一种工程权衡：

- **TTL 太长**（如 86400 秒 = 1 天）：减少查询次数，降低延迟，但记录变更生效很慢。如果你换了服务器 IP，用户可能一整天都访问旧 IP。
- **TTL 太短**（如 60 秒）：记录变更快速生效，但查询量暴增，延迟增大。

实际工程中常见的做法是：平时设置较长 TTL（如 3600），在需要迁移时提前把 TTL 缩短（如 300），迁移完成后再改回来。

DNS 缓存存在于多个层次：

1. **浏览器缓存**：浏览器自己缓存 DNS 结果
2. **操作系统缓存**：Windows DNS Client 服务、systemd-resolved
3. **递归解析器缓存**：ISP 的 DNS 服务器、8.8.8.8、1.1.1.1
4. **CDN 边缘节点**：CDN 自己也有 DNS 缓存

## DNS 安全威胁

**DNS 劫持**：攻击者篡改 DNS 查询结果，把用户导向假网站。2014 年，一些 ISP 把不存在的域名（NXDOMAIN）劫持到自己的广告页面。

**DNS 缓存投毒（Cache Poisoning）**：攻击者向递归解析器注入虚假的 DNS 记录。如果成功，所有使用该解析器的用户都会被误导。2008 年，Dan Kaminsky 发现了一个严重的 DNS 缓存投毒漏洞——DNS 的 Transaction ID 只有 16 位（65536 种可能），攻击者可以通过大量伪造响应来猜中。修复方法是随机化源端口（增加熵源）。

**DNSSEC（DNS Security Extensions）**通过在 DNS 记录中添加数字签名来解决这些问题。权威服务器用私钥签名 DNS 记录，解析器用公钥验证签名。如果签名不匹配，解析器就知道记录被篡改了。DNSSEC 的部署进展缓慢——它增加了查询延迟和报文大小，配置也很复杂。

## DoH 与 DoT：加密 DNS 的争议

传统 DNS 使用 UDP 端口 53，查询内容是明文的——你的 ISP、咖啡店 Wi-Fi 的管理员、甚至路过的任何人都能看到你在查什么域名。

**DoH（DNS over HTTPS）**：把 DNS 查询封装在 HTTPS 请求中，走 TCP 443 端口。对中间人来说，它看起来就像一个普通的 HTTPS 请求。Chrome 和 Firefox 已默认启用 DoH。

**DoT（DNS over TLS）**：在 DNS 查询外面包一层 TLS，走专用的 TCP 853 端口。比 DoH 更轻量（没有 HTTP 开销），但流量特征明显——网管一看 853 端口就知道这是 DNS。

争议在于：DoH 绕过了网络管理员的 DNS 管控。企业 IT 管理员可能依赖 DNS 过滤来阻止恶意网站，DoH 让这些策略失效了。隐私倡导者则认为用户有权加密自己的 DNS 查询。这是一个典型的隐私与管控的博弈。

## 编程实践：用 Python dnspython 库做 DNS 查询

```python
import dns.resolver
import dns.message
import dns.query
import struct

def demo_dns_query():
    """演示各种 DNS 记录类型的查询"""
    domain = "example.com"
    
    # 查询 A 记录（IPv4 地址）
    print(f"=== A Records for {domain} ===")
    answers = dns.resolver.resolve(domain, 'A')
    for rdata in answers:
        print(f"  {rdata.address}  (TTL: {answers.rrset.ttl})")
    
    # 查询 AAAA 记录（IPv6 地址）
    print(f"\n=== AAAA Records for {domain} ===")
    try:
        answers = dns.resolver.resolve(domain, 'AAAA')
        for rdata in answers:
            print(f"  {rdata.address}  (TTL: {answers.rrset.ttl})")
    except dns.resolver.NoAnswer:
        print("  No AAAA records found")
    
    # 查询 MX 记录（邮件服务器）
    print(f"\n=== MX Records for {domain} ===")
    try:
        answers = dns.resolver.resolve(domain, 'MX')
        for rdata in answers:
            print(f"  Priority: {rdata.preference}, Server: {rdata.exchange}")
    except dns.resolver.NoAnswer:
        print("  No MX records found")
    
    # 查询 TXT 记录
    print(f"\n=== TXT Records for {domain} ===")
    try:
        answers = dns.resolver.resolve(domain, 'TXT')
        for rdata in answers:
            print(f"  {rdata.to_text()}")
    except dns.resolver.NoAnswer:
        print("  No TXT records found")
    
    # 查询 NS 记录（权威 DNS 服务器）
    print(f"\n=== NS Records for {domain} ===")
    answers = dns.resolver.resolve(domain, 'NS')
    for rdata in answers:
        print(f"  {rdata.target}")
    
    # 手动构建 DNS 查询报文并发送到指定服务器
    print(f"\n=== Manual DNS Query to 8.8.8.8 ===")
    q = dns.message.make_query(domain, 'A')
    response = dns.query.udp(q, '8.8.8.8', timeout=5)
    print(f"  Response code: {response.rcode()}")
    print(f"  Flags: QR={response.flags & dns.flags.QR}, AA={response.flags & dns.flags.AA}")
    for answer in response.answer:
        for item in answer.items:
            print(f"  Answer: {item}  (TTL: {answer.ttl})")

def parse_dns_response_raw(data: bytes):
    """手动解析 DNS 响应报文（教学目的）"""
    # 解析 Header（12 字节）
    tx_id, flags, qdcount, ancount, nscount, arcount = struct.unpack('!HHHHHH', data[:12])
    print(f"Transaction ID: 0x{tx_id:04x}")
    print(f"Flags: 0x{flags:04x}")
    print(f"Questions: {qdcount}, Answers: {ancount}")
    print(f"Authority: {nscount}, Additional: {arcount}")
    
    # 解析 Question Section
    offset = 12
    for _ in range(qdcount):
        labels = []
        while data[offset] != 0:
            length = data[offset]
            offset += 1
            labels.append(data[offset:offset+length].decode())
            offset += length
        offset += 1  # 跳过结尾的 0x00
        qtype, qclass = struct.unpack('!HH', data[offset:offset+4])
        offset += 4
        print(f"Question: {'.'.join(labels)} Type:{qtype} Class:{qclass}")

demo_dns_query()
```

## 抓包实践：捕获 DNS 查询和响应

在 Wireshark 中过滤 `dns`，在浏览器中访问一个网站。你会看到大量 DNS 查询：

```
DNS Query:
  Transaction ID: 0xa3f2
  Flags: 0x0100 (Standard query, Recursion desired)
  Questions: 1, Answer RRs: 0
  Queries:
    www.example.com: type A, class IN

DNS Response:
  Transaction ID: 0xa3f2
  Flags: 0x8180 (Response, Recursion desired, Recursion available)
  Questions: 1, Answer RRs: 2
  Queries:
    www.example.com: type A, class IN
  Answers:
    www.example.com: type CNAME, cname example.com   (TTL: 300)
    example.com: type A, addr 93.184.216.34           (TTL: 3600)
```

注意这里有一个 CNAME 链：`www.example.com` 先解析为 `example.com`，然后 `example.com` 解析为 IP 地址。递归解析器把两步的结果一起返回给客户端，减少一次查询。

在 Wireshark 中展开 `Domain Name System` 树，可以看到每个字段的精确值。特别注意 `Time` 列——DNS 查询的延迟通常在 10-100ms 之间，但如果触发了完整的迭代查询（根 → TLD → 权威），可能需要 200-500ms。这就是为什么 DNS 缓存如此重要。
