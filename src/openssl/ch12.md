# 第12章：s_client：TLS 现场勘察

> [!TIP] Part 3: CA 与 TLS 实战篇（实战篇）
> 排错的第一工具章。证书体系的知识都到位了，本章把它们装进一支「现场勘察探针」——握手、证书、协议、到期，一条命令看清一个 TLS 端点的全部底细。

第三十周凌晨，api 证书到期，全站报错 40 分钟。复盘会上有个共识比事故本身更刺痛：**没有任何人在第一时间知道「是证书的事」**——大家先查了应用日志、数据库、负载均衡，绕了 20 分钟才有人想起看证书。如果团队人手一支 s_client 探针，第一分钟就能把「证书层」排除或定罪。本章就是把这个习惯装进你手里：`s_client` 是 OpenSSL 自带的 TLS 客户端，也是排查一切 HTTPS 问题的第一站。

## 12.1 基本盘：一次最简勘察

先跑起来再说：

```bash
openssl s_client -connect example.com:443 -servername example.com
```

`-connect` 指定目标（主机:端口），`-servername` 指定 SNI（Server Name Indication，服务器名称指示）——告诉服务器「我要连的是哪个域名」。**日常勘察两者要成对带上**：现代服务器一台机背后挂几十个域名，没有 SNI 它不知道该递哪张证书，可能回你一张默认证书甚至直接拒绝。单证书小站不带 `-servername` 也能连上，但那样测到的未必是用户看到的配置。勘察 CDN 后面的站点时报「域名不匹配」，先检查是不是忘了 `-servername`。

连接建立后终端会滚出一大段报告，最后停在一个交互提示符上——s_client 变成了一个可以手动发请求的 TLS 客户端（输入 HTTP 请求也能得到回应）。日常勘察用完即走，`echo | ` 管道喂一个回车让它自动收工：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | head -40
```

手动模式值得体验一次——在交互提示符下输入一个 HTTP 请求：

```text
GET / HTTP/1.1
Host: example.com
（随后连按两次回车，Host 头后必须有空行）
```

服务器回以正常响应。这个模式的价值不在日常使用（curl 更顺手），而在**隔离变量**：TLS 通了、HTTP 也通了，问题就不在这条链路上——排错时把链路一节一节点亮，是定位问题最朴素也最可靠的办法。

## 12.2 读懂输出五大段

s_client 的输出信息密度很高，但结构固定，五段划分后一目了然：

```text
① 验证时构建的链（客户端视角的递归过程）
depth=2 C=US, O=Internet Security Research Group, CN=ISRG Root X1
depth=1 C=US, O=Let's Encrypt, CN=R10
depth=0 CN=example.com

② 服务器发来的证书链（s=持有者 i=盖章者）
Certificate chain
 0 s:CN=example.com
   i:C=US, O=Let's Encrypt, CN=R10

③ 服务器证书原文（PEM）
Server certificate
-----BEGIN CERTIFICATE-----
...

④ 协商结果
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384

⑤ 校验结论
Verification: OK
Verify return code: 0 (ok)
```

| 段 | 回答的问题 | 排错时的用法 |
| ---- | ---- | ---- |
| ① depth 链 | 客户端信不信得过 | 报错看 depth 定层（第11章） |
| ② 证书链 | 服务器发了什么 | 数一数几张证书，缺中间一眼可见 |
| ③ PEM 原文 | 证书内容本体 | 可直接管道给 `x509` 继续拆 |
| ④ 协议与套件 | 用什么算法在加密 | 协议太老、套件太弱在此现形 |
| ⑤ 结论 | 最终裁决 | `0 (ok)` 是满分；非零码见 12.5 |

第①段与第②段值得对比着看：②是服务器发来的「存货」，①是客户端验证时实际走出的「路径」——两者可能不同（客户端可能用信任库里的另一张交叉签名证书搭桥）。日常排错先看⑤，出问题再看①定层、②对货。

## 12.3 高频勘察任务清单

s_client 的真正威力在于与管道组合。五个最高频的任务，命令全部一行：

| 任务 | 命令 | 看什么 |
| ---- | ---- | ---- |
| 查到期时间 | `... \| openssl x509 -noout -enddate` | `notAfter=...` |
| 查域名覆盖 | `... \| openssl x509 -noout -ext subjectAltName` | SAN 列表 |
| 查证书指纹 | `... \| openssl x509 -noout -fingerprint -sha256` | 与官网/浏览器比对 |
| 探协议版本 | `s_client ... -tls1_2` | `New, TLSv1.2` 或拒绝 |
| 探 HTTP/2 | `s_client ... -alpn h2` | `ALPN protocol: h2` |

协议探测的读法值得一提。用 `-tls1_2` 强制用 TLS 1.2 握手：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com -tls1_2 2>/dev/null | grep "New,"
```

```text
New, TLSv1.2, Cipher is ECDHE-RSA-AES256-GCM-SHA384
```

协商成功说明服务器**还接受**老协议（对内网老客户端是兼容，对公网站点是待加固项，第14章的加固清单会回收）。反过来用 `-tls1`（古董协议）探测，正常站点应该握手失败——**「该拒绝的拒绝了」同样是重要情报**。

顺带一提服务器接受的**套件**：`-cipher` 参数可以指定套件去试探（TLS 1.2 场景）：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com \
  -tls1_2 -cipher AES256-GCM-SHA384 2>/dev/null | grep -E "New,|error"
```

被服务器拒绝时握手直接失败——像 `-tls1` 一样，「拒绝弱套件」也是健康信号。TLS 1.3 的套件协商走另一套参数（`-ciphersuites`），日常体检看 ④ 段给出的最终套件即可。

嫌输出太长的话，1.1.1+ 提供了 `-brief` 精简模式，只要结论不要细节：

```text
$ echo | openssl s_client -brief -connect example.com:443 -servername example.com 2>/dev/null
CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Ciphersuite: TLS_AES_256_GCM_SHA384
Peer certificate: CN = example.com
Hash used: SHA256
Signature type: ECDSA
Verification: OK
Verify return code: 0 (ok)
```

协议、套件、证书结论各一行，日常巡检的体感极佳。（老 1.0.x 时代那种 `Connection: TLSv1.3, cipher ...` 单行汇总格式早已不存在，网上老教程的截图别照抄。）

STARTTLS 场景单列一笔：邮件协议（SMTP 25/587、IMAP 143）先明文通信、再原地升级 TLS——`s_client` 用 `-starttls smtp` / `-starttls imap` 先替你完成升级动作再进 TLS。少了这个参数，对着 25 端口直接握手只会收获一条莫名其妙的报错。

## 12.4 到期监控：危机三的流程化封口

把 12.3 的「查到期」升级成无人值守的监控脚本 `cert-expiry.sh`——这是凌晨 40 分钟事故的流程化封口：

```bash
#!/bin/bash
# 用法: ./cert-expiry.sh <域名>   距到期不足 21 天时告警
set -euo pipefail
HOST=$1

END=$(echo | openssl s_client -connect "$HOST:443" -servername "$HOST" 2>/dev/null \
      | openssl x509 -noout -enddate | cut -d= -f2)
DAYS=$(( ( $(date -d "$END" +%s) - $(date +%s) ) / 86400 ))

echo "$HOST: 距到期还有 $DAYS 天"
# 告警分支用 if 而不是 `[ ] && exit 1`：set -e 下后者条件为假时也会非零退出，cron 会天天报失败
if [ "$DAYS" -lt 21 ]; then
  echo "ALERT: $HOST 证书即将到期，立即轮换"
  exit 1
fi
```

挂进 cron 每天跑一遍，覆盖 api 与内网三个服务；告警接入团队 IM 的 webhook。**21 天的告警线不是拍脑袋**：给「发现问题 → 定位 → 轮换 → 验证」留出从容的工作日，而不是逼着凌晨的值班工程师现场救火。

> [!TIP] 监控的目标是「让到期不再成为事件」
> 云笔记的轮换周期 60 天（第10章），监控告警线 21 天——两层防线叠加后，「证书到期」从突发事故变成日常工单。运维的成熟度不体现在救火速度，体现在火源被流程浇灭。

单域脚本之上，批量版覆盖全部域名——域名清单一行一个存进 `domains.txt`：

```bash
#!/bin/bash
# check-all-certs.sh: 遍历清单逐一体检
while read -r HOST; do
  [ -z "$HOST" ] && continue
  ./cert-expiry.sh "$HOST" || true    # 单域告警不中断其余域的检查
done < domains.txt
```

cron 里跑批量版，所有证书的「距到期天数」每天汇成一张表。第10章立的 60/21 双数字从此由机器盯着，人只负责收到告警后的轮换动作——危机三的复盘结论「没有任何人在第一时间知道」，从流程上不复存在。

## 12.5 进阶勘察：四件重武器

**武器一：`-showcerts` 看全链。** 默认输出只给叶子的 PEM；加 `-showcerts` 一次给全（叶子 + 中间），配合 11.3 数一数服务器发了几张证书：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com -showcerts 2>/dev/null \
  | grep -c "BEGIN CERTIFICATE"     # 数证书张数：2 = 叶子+中间，1 = 疑似缺中间
```

**武器二：`-CAfile` 模拟客户端验证。** s_client 默认用系统信任库校验证书；用 `-CAfile` 换成自建的根证书，等于把 s_client 变成「内网专用客户端」，提前在服务端验清客户端将看到的裁决：

```bash
echo | openssl s_client -connect auth.cloudnote.internal:443 \
  -servername auth.cloudnote.internal \
  -CAfile /etc/cloudnote-ca/root.crt 2>/dev/null | grep "Verify"
```

```text
Verification: OK
Verify return code: 0 (ok)
```

**武器三：`-status` 看 OCSP 装订（stapling）。** 第11章讲过 OCSP stapling——服务器把取好的 OCSP 应答随握手「装订」递给你，`-status` 可以看服务器装没装：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com -status 2>/dev/null \
  | grep -A2 "OCSP"
```

没有输出属正常现象——行业正在从 OCSP 转向短有效期与 CRL（Let's Encrypt 已于 2025 年停用 OCSP），钉没钉不再是健康与否的判据。

**武器四：`-msg` 看握手报文本身。** 排查「握手死在哪一步」时，加 `-msg` 把每条握手消息逐个点亮：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com -msg 2>/dev/null \
  | grep -E "^>>> TLS|^<<< TLS" | head -6
```

```text
>>> TLS 1.3, HandshakeType ClientHello
<<< TLS 1.3, HandshakeType ServerHello
<<< TLS 1.3, HandshakeType EncryptedExtensions
```

`>>>` 是我们发出去的，`<<<` 是收到的——停在 ClientHello 之后没有回音，多半是防火墙或 SNI 配置问题；走完全程才断，问题在证书层。把《网络协议完全教程》第15章的握手时序图和这里对照着读，协议知识当场落地。

## 12.6 实验：给 api 做全身体检

综合演练：对 api.cloudnote.example（实验环境用自签 + `--cacert` 模拟，或对任一公网站点）完成六项体检，每项记录结论：

```bash
HOST=api.cloudnote.example
CAFILE=/etc/cloudnote-ca/root.crt   # 公网站点则省略此参数

# 1. 总裁决
echo | openssl s_client -connect $HOST:443 -servername $HOST -CAfile $CAFILE 2>/dev/null | grep "Verify"
# 2. 到期天数
./cert-expiry.sh $HOST
# 3. SAN 覆盖
echo | openssl s_client -connect $HOST:443 -servername $HOST 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName
# 4. 协议下限
echo | openssl s_client -connect $HOST:443 -servername $HOST -tls1_2 2>/dev/null | grep "New,"
# 5. 链张数
echo | openssl s_client -connect $HOST:443 -servername $HOST -showcerts 2>/dev/null \
  | grep -c "BEGIN CERTIFICATE"
# 6. 指纹留档
echo | openssl s_client -connect $HOST:443 -servername $HOST 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256
```

六项全绿的标准：裁决 OK、到期大于 21 天、SAN 含目标域名、最低接受 TLS 1.2、链张数符合拓扑、指纹与历史记录一致。这六项以后就是你的「接手任何一个 HTTPS 服务」标准动作——先体检，再动刀。

## 本章小结

- `s_client -connect -servername` 是 TLS 界的听诊器：SNI 必须带，缺了它服务器可能递错证书
- 输出五段各有其职：depth 链定层、证书链对货、PEM 拆细、协商看协议、Verify 码下裁决
- 管道是灵魂：`| openssl x509 -noout -enddate` 一行查到期，`-tls1_2` 探协议下限，`-showcerts` 数链张数
- 到期监控脚本 + cron + 21 天告警线：把「证书到期」从凌晨事故变成日常工单
- `-CAfile` 让 s_client 变身内网客户端，提前看清客户端将得到的裁决
- STARTTLS 服务用 `-starttls smtp/imap` 先升级再握手；`-msg` 把握手逐条点亮，断在哪一步一目了然
- 接手任何 HTTPS 服务的六个标准体检动作先做完，再谈改配置——第14章的排错手册全程用这套探针
