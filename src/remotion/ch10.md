# 第十章：规模化渲染——Node API、批量出片与云端渲染

> [!TIP] Part 4: 规模化与工程篇（图形、规模与工程）
> CLI 的 `remotion render` 是为「人敲命令」设计的；当「换一份 props 出一条片」要重复 N 次，就要把这条命令拆成可编程的函数。本章讲 `@remotion/bundler` 与 `renderMedia` 的 Node API、`renderStill` 抽帧、一张数据集批量出片，以及 Lambda 云端渲染的适用边界。先修：4.5（npm scripts 流水线）、9.5（gl 参数）。

## 为什么要学规模化渲染？

ch00 的生态位承诺是「换一份 props 就能批量出片」。CLI 一次只能跑一条命令，批量意味着 shell 循环、日志混乱、错误难收拾；Node API 让「渲染一条视频」降级为程序里的一个 `await`——从此排进任何业务逻辑。

## 10.1 三步走：bundle、selectComposition、renderMedia

CLI 那条命令在 Node 里拆成三步，贯穿示例的 `[3/3]` 渲染步完整化如下：

```ts
// scripts/render-node.mjs
import { readFile } from "node:fs/promises";
import { bundle } from "@remotion/bundler";
import { renderMedia, selectComposition } from "@remotion/renderer";

const serveUrl = await bundle({
  entryPoint: "./remotion/index.ts",
  onProgress: (p) => process.stdout.write(`打包 ${Math.round(p * 100)}%\r`),
});

const inputProps = JSON.parse(await readFile("out/timestamps.json", "utf-8"));
const composition = await selectComposition({
  serveUrl,
  id: "WinterVideo",
  inputProps,
});

await renderMedia({
  composition,
  serveUrl,
  codec: "h264",
  outputLocation: "out/video.mp4",
  inputProps,
});
```

三步各自回答一个问题：

- **`bundle()`**：源码 → Webpack 静态产物。回答「先猜再读」第一问：serveUrl 是一个**本地目录路径**，`renderMedia` 内部会起一个临时静态服务器让无头浏览器访问；它也可以推到远端，当普通 URL 用；
- **`selectComposition()`**：按真实 props 跑一遍 `calculateMetadata`，返回带 `durationInFrames` 的规格对象——1.2 的「规格跟着数据走」在这里被显式触发，所以 inputProps 必须传；
- **`renderMedia()`**：按规格渲染 + 编码。回答第三问：默认并发是 **CPU 线程数的一半、上限 8**，与 1.5 说的一致。

`renderMedia` 的参数一张表收全（对比 4.2 的 CLI 参数，几乎一一对应）：

| 参数 | 作用 | 备注 |
| ---- | ---- | ---- |
| `codec` | 输出编码 | 默认 `h264` |
| `outputLocation` | 输出文件路径 | 省略则不落盘，返回内存 Buffer |
| `inputProps` | 注入数据 | 必须与 selectComposition 传的完全一致 |
| `concurrency` | 并行截图标签页数 | 默认 CPU 半数、上限 8 |
| `chromiumOptions.gl` | 渲染器后端 | 9.5 的 three 场景传 `"angle"` |
| `frameRange` | 只渲染部分帧 | 排查单帧 `[157, 157]` |
| `timeoutInMilliseconds` | delayRender 超时 | 默认 30000（5.5 的 30 秒） |
| `onProgress` | 进度回调 | 见 10.3 |

配置文件里的 `Config.setChromiumOpenGlRenderer("angle")` **不作用于 Node API**——9.5 留的接口在此兑现：three 场景要显式传 `chromiumOptions: { gl: "angle" }`。

## 10.2 批量出片——一张数据集 N 条视频

回答「先猜再读」第二问：**bundle 只打一次**——Webpack 产物与 props 无关，同一份代码服务所有数据，100 条视频也只打包 1 次。规格与渲染才在循环内逐条跑：

```ts
// scripts/batch-render.mjs —— 三城天气批量出片
import { bundle } from "@remotion/bundler";
import { renderMedia, renderStill, selectComposition } from "@remotion/renderer";

const cities = [
  { city: "北京", script: "今天是2026年的冬天，来到北京已经接近15年。……" },
  { city: "上海", script: "……" },
  { city: "广州", script: "……" },
];

const serveUrl = await bundle({ entryPoint: "./remotion/index.ts" });   // 循环外，只一次

const failed: string[] = [];
for (const item of cities) {
  try {
    const inputProps = await tts(item.script);      // 出音频 + 词级时间戳
    const composition = await selectComposition({ serveUrl, id: "WinterVideo", inputProps });
    await renderMedia({
      composition, serveUrl, codec: "h264",
      outputLocation: `out/${item.city}.mp4`,
      inputProps,
    });
    await renderStill({                              // 抽一帧当封面
      composition, serveUrl,
      frame: 157,
      output: `out/${item.city}-cover.png`,
      inputProps,
    });
  } catch (err) {
    failed.push(item.city);
  }
}
console.log(failed.length ? `失败：${failed.join(", ")}` : "全部完成");
```

三个工程要点：

- **bundle 在循环外，selectComposition 在循环内**：不同 props 算出不同总帧数（8.81 秒 → 283 帧只是北京这一条），规格必须逐条重算——3.4 的「单一来源」在批量场景下的形态；
- **`renderStill()` 是抽帧旁支**：`frame` 指定帧号出一张图（`imageFormat` 默认 png），负数帧号从尾部倒数（`-1` 即最后一帧），封面、预览图、视频网站缩略图都靠它；
- **失败收集而非中断**：批量脚本的基本素养——一条失败不该毁掉整批，最后统一汇报。

并行度的常识：`renderMedia` 内部已经在并行截图（concurrency 个标签页），**多条视频之间再并行只会争抢同一颗 CPU**——一般串行循环即可；真要横向扩，靠的是 10.4 的云端而不是单机塞满。

## 10.3 进度观测——onProgress 与最慢帧

批量渲染动辄几分钟，观测接口值得一行配置：

```ts
await renderMedia({
  // ...
  onProgress: ({ renderedFrames, encodedFrames, stitchStage }) => {
    console.log(`截图 ${renderedFrames} 帧 / 编码 ${encodedFrames} 帧 / 阶段 ${stitchStage}`);
  },
  logLevel: "error",
});
```

- `renderedFrames` 与 `encodedFrames` 是两条独立推进的进度——4.0 起渲染与编码并行（parallel encoding），截图和写视频同时发生；
- 返回值里的 **`slowestFrames`** 列出最慢的 10 帧：优化渲染时长时先看它——慢帧通常指向某帧的重资源元素（大图、复杂滤镜、OffthreadVideo 的 seek）；
- `logLevel: "error"` 对应 4.2 CLI 参数表里的 `--log=error`，流水线里防刷屏。

## 10.4 @remotion/lambda——什么时候上云端

本地渲染的扩展性天花板是一台机器。Lambda 把「一台机器的并行」换成「一段时间的海量并行」：

工作模型四步：

```text
bundle 部署到 S3（成为可访问的网站）
    ▼
首次部署一个 Lambda 函数（内置 Chromium 层）
    ▼
渲染请求把视频切成小片，成百个 Lambda 并行渲染
    ▼
初始函数合体所有分片，mp4 上传 S3
```

适用判断一张表：

| 维度 | 本地 renderMedia | Lambda |
| ---- | ---- | ---- |
| 视频时长 | 无硬限制 | 单函数 15 分钟超时；磁盘上限折算约 32 分钟 1080p（2048MB 配置） |
| 并发 | 一台 CPU 的半数 | 每区域默认 1000 个并行函数，可申请提升 |
| 成本 | 占用机器时间 | 渲染期间按量计费，多分钟视频通常几美分 |
| 运维 | 零依赖 | 要 AWS 账号、凭证、region、bucket |

门槛与流程（Node API 三个函数，CLI 有对应子命令）：`deploySite()` 部署站点到 S3、`ensureLambdaFunction()` 部署渲染函数、`renderMediaOnLambda()` 发起渲染并返回 S3 地址。细节参数随版本演进较快，动手前以官方 Lambda 文档为准。

两条成本之外的注意：

- **License**：需要商业授权的团队使用云端渲染，须用 Remotion for Automators 授权覆盖（4.6 的 License 表在此延伸）；4.0.409 起 `renderMedia` / `renderStill` / Lambda 都支持 `licenseKey` 参数——符合免费条款的传 `"free-license"`，需授权的团队传密钥上报用量；
- **判断口诀**：一次性或低频 → 本地；量大且急（几百条、要分钟级出）→ Lambda；介于之间 → 先把本地 concurrency 调满、renderStill 抽帧复用 bundle，再考虑上云。

## 本章小结

- CLI 的 `remotion render` = `bundle()` → `selectComposition()` → `renderMedia()` 三步的语法糖
- bundle 产物与 props 无关，**批量出片只打一次包**；selectComposition 每条数据都要重算规格
- `renderStill(frame, output)` 抽帧出图做封面，`frame: -1` 即最后一帧
- `onProgress` 区分 rendered / encoded 两路进度；返回值 `slowestFrames` 是性能优化的第一线索
- Node API 不读配置文件，three 场景要显式传 `chromiumOptions: { gl: "angle" }`
- Lambda：15 分钟单函数超时、S3 存站点与产物、渲染期计费；商业团队云端渲染需 Automators 授权
- 口诀：一次性 → 本地；量大且急 → Lambda；先调满本地并发再谈上云
