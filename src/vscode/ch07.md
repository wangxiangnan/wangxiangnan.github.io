# 第7章：任务系统与自动化

> "Any task you do more than twice should be automated." —— 某个凌晨三点还在手动跑构建脚本的程序员

如果你是一名开发者，日常大概率是这样的：保存代码、运行构建、检查 lint、跑一遍测试，再看一眼输出有没有异常。这一套流程就像游戏里的"刷日常任务"——每天重复，但每天都得做。好消息是，VSCode 的任务系统（Task System）就是为此而生的：它能把你的"日常"变成一条可复用的流水线，按一次快捷键，剩下的交给它。

如果把 VSCode 比作一个操作系统，任务系统大概相当于 `cron + Makefile + shell script` 的合体。但它和编辑器、终端、问题面板是打通的——这是外部脚本给不了的。

> 注意：任务系统只在打开文件夹或工作区时可用。单独编辑一个文件时，VSCode 不会提供任务。

## 7.1 tasks.json：第一条任务

任务系统的核心配置文件是 `.vscode/tasks.json`。生成方式有两种：

- 命令面板（`Ctrl+Shift+P` / `⌘+Shift+P`）→ **Tasks: Configure Task** → **Create tasks.json file from template** → **Others**
- 直接在项目里新建 `.vscode/tasks.json`

先生成一条最简单的任务：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "echo",
            "type": "shell",
            "command": "echo Hello, Task System!",
            "problemMatcher": []
        }
    ]
}
```

这就像编程世界的 "Hello, World!"——它什么都没干，但证明任务系统已经活过来了。运行方式：

- 命令面板 → **Tasks: Run Task** → 选择 `echo`
- 菜单 **Terminal → Run Task...**
- 在任务列表右侧点齿轮，可以直接跳到 `tasks.json` 中对应的任务

这里有个新手最容易踩的坑：`Ctrl+Shift+B`（`⌘+Shift+B`）不是"运行任意任务"，而是 **Run Build Task**——只运行 `group.kind` 为 `build` 的默认任务。上面这条 `echo` 没有分组，所以按 `Ctrl+Shift+B` 不会执行它；项目里一个 build 任务都没有时，VSCode 会引导你先配置。

> 省事技巧：npm、Gulp、Grunt、Jake 的脚本会被自动发现，**Tasks: Run Task** 里会直接出现 `npm: build` 这样的条目，不写 `tasks.json` 也能跑。`npm.autoDetect` 控制 npm 脚本的自动发现开关。想给它挂问题匹配器或改终端行为时，再用齿轮把它"钉"进 `tasks.json`。

`version` 固定写 `"2.0.0"`。每个 task 对象可以包含以下关键属性：

| 字段 | 类型 | 说明 |
| ------ | ------ | ------ |
| `label` | string | 任务的唯一标识名，也是你在任务列表中看到的名字 |
| `type` | string | `shell`、`process`，或扩展提供的类型（如 `npm`） |
| `command` | string | 要执行的命令；纯组合任务可以省略 |
| `args` | string[] | 命令参数，避免手工处理引号 |
| `options` | object | 运行选项：`cwd`、`env`、`shell` |
| `problemMatcher` | string / object / array | 解析输出中的错误；`[]` 表示明确不解析 |
| `group` | string / object | 任务分组：`build`、`test`，或 `{ "kind": "build", "isDefault": true }` |
| `dependsOn` | string / string[] | 依赖的其他任务 |
| `dependsOrder` | string | `parallel`（默认）或 `sequence` |
| `presentation` | object | 终端面板显示控制 |
| `runOptions` | object | 何时运行，如 `runOn: "folderOpen"` |
| `hide` | boolean | 从 **Run Task** 列表隐藏，适合组合任务里的内部步骤 |

## 7.2 任务类型：shell、process 与 npm

VSCode 自带两种基础任务类型。**shell 类型** 是最常用的，它会把命令交给系统 shell 解释。这意味着你可以使用管道 `|`、重定向 `>`、`&&`、环境变量展开等所有 shell 特性：

```json
{
    "label": "build-and-notify",
    "type": "shell",
    "command": "npm run build && echo Build Success || echo Build Failed",
    "problemMatcher": ["$tsc"]
}
```

命令由哪个 shell 解释取决于系统：Windows 上通常是 PowerShell，Unix 上是 bash。想固定某个 shell，用 `options.shell` 指定（见 7.8）。

**process 类型** 直接执行一个可执行文件，不经过 shell。它更安全（不受 shell 注入影响），但也更受限：

```json
{
    "label": "run-node",
    "type": "process",
    "command": "node",
    "args": ["--inspect", "dist/server.js"],
    "problemMatcher": []
}
```

| 对比项 | shell | process |
| ------ | ------ | ------ |
| 是否经过 shell | 是 | 否 |
| 管道、重定向、`&&`、通配符展开 | 支持 | 不支持 |
| 参数控制 | 命令字符串 | `command` + `args`，边界更清晰 |
| 安全边界 | 需注意注入与转义 | 不经过 shell，参数按原样传递 |
| Windows 上的 `.cmd` 命令 | 可用 | 不能直接执行 |

选择原则很简单：**命令里有 `|`、`&&`、`>` 或环境变量展开，用 shell；只是执行一个程序加参数，用 process。** Windows 上尤其注意：`npm` 实际是 `npm.cmd`，用 process 直接执行 `npm` 会找不到可执行文件，这类命令请用 shell，或写成 `npm.cmd`。

参数里有空格时，优先把命令和参数分开写（`command` + `args`），VSCode 会自动处理引号；把整条命令塞进 `command` 则要自己保证转义正确。

### 跨平台命令

`rm -rf dist` 在 Windows 上会直接报错。两种做法：用跨平台工具（如 `rimraf`），或者用 `windows` / `linux` / `osx` 覆盖字段：

```json
{
    "label": "clean",
    "type": "shell",
    "command": "python3 scripts/clean.py",
    "windows": {
        "command": "py scripts/clean.py"
    },
    "problemMatcher": []
}
```

这些覆盖既可以写在单个任务里，也可以写在 `tasks.json` 顶层对所有任务生效。

### 更省事的 npm 类型

Node 项目还可以直接用 `type: "npm"` 跑 `package.json` 里的脚本，不必手写 `npm run`：

```json
{
    "label": "build",
    "type": "npm",
    "script": "build",
    "group": { "kind": "build", "isDefault": true },
    "problemMatcher": ["$tsc"]
}
```

npm 脚本默认会被自动发现，在 **Tasks: Run Task** 里显示为 `npm: build`。声明成 `type: npm` 的好处是可以给它挂 `group`、`problemMatcher`、`presentation`，而不用自己拼 shell 命令。

## 7.3 problemMatcher：错误跳转与后台任务信号

`problemMatcher` 有两个职责：

1. 解析任务输出，把错误/警告报进"问题"面板，并在编辑器中标记文件、行号、列号，支持点击跳转。
2. 通过 `background` 块告诉 VSCode：一个后台任务什么时候算"启动完成"，让依赖它的任务能正确等待。

任务本身只会输出文本，VSCode 并不知道 `src/app.ts:3:5: error: ...` 这种内容意味着什么。匹配器就是一张"翻译表"：用正则表达式提取文件、行号、列号、严重级别和消息。

### 内置匹配器

常见工具不需要手写，直接引用内置的即可：

```json
"problemMatcher": ["$tsc", "$eslint-stylish"]
```

| 匹配器 | 适用工具 | 路径假设 |
| ------ | ------ | ------ |
| `$tsc` | TypeScript 编译器 | 相对工作区 |
| `$tsc-watch` | `tsc --watch` | 相对工作区 |
| `$eslint-compact` / `$eslint-stylish` | ESLint | 相对工作区 |
| `$jshint` / `$jshint-stylish` | JSHint | 绝对路径 |
| `$go` | Go 编译器 | 相对工作区 |
| `$msCompile` | C# / VB 编译器 | 绝对路径 |
| `$lessc` / `$node-sass` | Less / Sass | 绝对路径 |

注意：`$gcc`、`$python` 不在内置列表里，它们分别由 C/C++、Python 扩展提供；装好扩展后同样可以直接引用。

如果任务输出不需要解析，写 `"problemMatcher": []`。空数组表示明确不解析，能避免第一次运行时被询问"选择哪个问题匹配器"。

### 自定义 pattern

工具没有内置匹配器时，自己写一个。下面匹配 `文件:行:列: 级别: 消息` 这种常见格式：

```json
"problemMatcher": {
    "owner": "mytool",
    "source": "my-linter",
    "fileLocation": ["relative", "${workspaceFolder}"],
    "pattern": {
        "regexp": "^([A-Za-z]:[^:]+|[^:]+):(\\d+):(\\d+):\\s+(error|warning):\\s+(.+)$",
        "file": 1,
        "line": 2,
        "column": 3,
        "severity": 4,
        "message": 5
    }
}
```

| 字段 | 说明 |
| ------ | ------ |
| `owner` | 问题归属方。相同 `owner` 的问题会在任务重新运行时整体替换，避免旧错误残留 |
| `source` | 在"问题"面板中显示的来源标签 |
| `fileLocation` | 文件路径类型：`autoDetect`（默认）、`relative`、`absolute`，或 `["relative", "${workspaceFolder}"]` |
| `pattern.regexp` | 解析一行输出的正则表达式 |
| `pattern.file` / `line` / `column` / `message` / `severity` / `code` | 捕获组编号，从 1 开始 |
| `severity`（匹配器级） | 默认严重级别；pattern 里指定了 `severity` 组时以组为准 |
| `loop` | 只用于多行 `pattern` 数组的最后一项，表示这组 pattern 会连续重复 |

两个容易踩的坑：

- **Windows 盘符**：`C:\project\a.ts:3:5` 里的 `C:` 会被当成字段分隔符。文件捕获组要能同时兼容盘符和相对路径（本例用 `([A-Za-z]:[^:]+|[^:]+)`），或者让工具输出相对路径。
- **多行输出**：ESLint stylish 这类工具会把一个问题拆成多行，此时 `pattern` 要写成数组，按数组顺序匹配；`loop: true` 只写在数组最后一项，单行 pattern 不需要写。

### 全局定义，多处复用

匹配器可以定义在 `tasks.json` 顶层，供多个任务引用；放在用户级 `tasks.json` 里还能跨项目共享：

```json
{
    "version": "2.0.0",
    "problemMatchers": {
        "myLinter": {
            "owner": "mytool",
            "fileLocation": ["relative", "${workspaceFolder}"],
            "pattern": {
                "regexp": "^(.+):(\\d+):(\\d+):\\s+(warning|error):\\s+(.+)$",
                "file": 1,
                "line": 2,
                "column": 3,
                "severity": 4,
                "message": 5
            }
        }
    },
    "tasks": [
        {
            "label": "lint",
            "type": "shell",
            "command": "my-linter src/",
            "problemMatcher": "$myLinter"
        }
    ]
}
```

也可以用 `"base": "$tsc"` 继承内置匹配器，只覆盖需要的字段。

### background：不是报错，是任务生命周期信号

对长驻任务（如 dev server、watch）来说，任务永远不会"结束"，VSCode 无法判断它什么时候启动完成。这时给任务加上 `isBackground: true`，并用 `background` 块声明"何时算开始、何时算完成"：

```json
{
    "label": "dev-server",
    "type": "shell",
    "command": "npm run dev",
    "isBackground": true,
    "problemMatcher": {
        "owner": "vite",
        "pattern": { "regexp": "." },
        "background": {
            "activeOnStart": true,
            "beginsPattern": "VITE v",
            "endsPattern": "Local:\\s+http"
        }
    }
}
```

| 字段 | 作用 |
| ------ | ------ |
| `activeOnStart: true` | 任务一开始就进入监控状态 |
| `beginsPattern` | 输出中出现该正则时，标记"新一轮编译/启动开始了" |
| `endsPattern` | 输出中出现该正则时，标记"编译/启动结束"（无论成败） |

实际效果：

1. **依赖等待**：其他任务若通过 `dependsOn` 指向它，会等 `endsPattern` 出现后才执行，而不是后台任务一开就跑。
2. **状态正确**：任务的"运行中"状态能正确反映启动/编译进度。

`pattern` 里的 `.` 只是占位符：`background` 必须配一个合法 pattern，但 `.` 没有捕获组，所以不会往问题面板塞任何条目。

还有两个容易忽略的点：

- `endsPattern` 只表示"这一轮结束"，匹配到 `ERROR` 也算结束，依赖任务会继续执行。失败判断要靠 problemMatcher 报错，或让后续任务自己检查。
- 在 `dependsOrder: "sequence"` 里，后台/监视任务必须有能判断"完成"的 `background` 匹配器，否则顺序会被卡住。

## 7.4 任务依赖和执行顺序：构建你的流水线

真实项目中的任务从来不是孤立的。构建之前要清理旧产物，测试之前要先构建，部署之前要通过所有检查。`dependsOn` 就是为此而生的：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "clean",
            "type": "shell",
            "command": "npx rimraf dist",
            "problemMatcher": []
        },
        {
            "label": "build",
            "type": "shell",
            "command": "npx tsc -p tsconfig.json",
            "dependsOn": "clean",
            "group": {
                "kind": "build",
                "isDefault": true
            },
            "problemMatcher": ["$tsc"]
        },
        {
            "label": "lint",
            "type": "shell",
            "command": "npx eslint .",
            "group": "test",
            "problemMatcher": ["$eslint-stylish"]
        },
        {
            "label": "test",
            "type": "shell",
            "command": "npx jest",
            "dependsOn": "build",
            "group": "test",
            "problemMatcher": []
        },
        {
            "label": "ci-pipeline",
            "dependsOn": ["lint", "test"],
            "dependsOrder": "sequence",
            "problemMatcher": []
        }
    ]
}
```

注意几个关键点：

- `dependsOn` 可以是单个字符串，也可以是数组。
- 数组形式默认为**并行执行**；需要顺序执行时，加上 `"dependsOrder": "sequence"`。
- `group` 设为 `"build"` 后，`Ctrl+Shift+B`（`⌘+Shift+B`）会运行该组的默认任务；设为 `"test"` 则通过 **Tasks: Run Test Task** 触发。
- `isDefault: true` 表示这是该组的默认任务。
- 纯组合任务可以只写 `label` + `dependsOn`，不需要 `type` 和 `command`；不想让辅助任务出现在 **Run Task** 列表里，加 `"hide": true`。

**最危险的一点是并行默认值**：如果把 `clean` 和 `build` 并列写进某个任务的 `dependsOn`，`clean` 可能在 `build` 跑到一半时删掉 `dist`。正确做法是让 `build` 依赖 `clean`，而不是让它们做兄弟。凡是共享状态（同一目录、同一端口、同一产物）的步骤，都应该串成链或显式使用 `sequence`。

任务跑得多了，还可以直接绑快捷键。在 `keybindings.json` 里加：

```json
{
    "key": "ctrl+alt+b",
    "command": "workbench.action.tasks.runTask",
    "args": "ci-pipeline"
}
```

## 7.5 自动运行任务：解放双手的终极形态

`runOptions` 可以让任务在特定时机自动触发，最典型的是打开文件夹时安装依赖：

```json
{
    "label": "install-deps",
    "type": "shell",
    "command": "npm install",
    "runOptions": {
        "runOn": "folderOpen"
    },
    "presentation": { "reveal": "silent" },
    "problemMatcher": []
}
```

`runOn` 只有两个值：

- `"folderOpen"`：打开文件夹时自动运行。
- `"default"`：只能手动触发（默认值）。

自动任务有两个前置条件：

1. 工作区必须处于**受信状态**（Workspace Trust）。不在受信工作区时，无论设置是什么，自动任务都不会运行。
2. `task.allowAutomaticTasks` 必须为 `"on"`（用户设置或工作区设置都可以）。从 VSCode 1.109 起，这个设置的默认值是 `"off"`，所以需要显式打开：

```json
{
    "task.allowAutomaticTasks": "on"
}
```

也可以在工作区里执行 **Tasks: Manage Automatic Tasks**，按工作区允许或禁止。

> ⚠️ 自动任务会在打开文件夹的瞬间执行代码。`npm install` 还会运行依赖包的 `install` / `postinstall` 脚本，只在你信任的项目里开启。

最后提醒：VSCode 没有 `runOn: "onSave"`。格式化请用 `editor.formatOnSave` 或 `editor.codeActionsOnSave`；需要在保存后跑任意命令，就用 watch 任务（`nodemon`、`tsx watch`、`tsc --watch`、`chokidar` 等）在后台监听，而不是给任务系统加一个不存在的生命周期钩子。

## 7.6 实战：Node.js 项目完整任务链

让我们为一个真实的 Express + TypeScript 项目搭建完整的任务链。项目结构如下：

```
my-express-app/
├── .vscode/
│   └── tasks.json
├── src/
│   ├── index.ts
│   └── routes/
├── tests/
├── package.json
└── tsconfig.json
```

完整 `tasks.json`：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "install-deps",
            "type": "shell",
            "command": "npm install",
            "runOptions": { "runOn": "folderOpen" },
            "presentation": { "reveal": "silent" },
            "problemMatcher": []
        },
        {
            "label": "clean",
            "type": "shell",
            "command": "npx rimraf dist",
            "problemMatcher": []
        },
        {
            "label": "compile",
            "type": "shell",
            "command": "npx tsc -p tsconfig.json",
            "dependsOn": "clean",
            "group": { "kind": "build", "isDefault": true },
            "problemMatcher": ["$tsc"],
            "presentation": {
                "reveal": "always",
                "panel": "shared"
            }
        },
        {
            "label": "lint",
            "type": "shell",
            "command": "npx eslint .",
            "group": "test",
            "problemMatcher": ["$eslint-stylish"],
            "presentation": {
                "reveal": "silent",
                "panel": "shared",
                "group": "checks"
            }
        },
        {
            "label": "unit-test",
            "type": "shell",
            "command": "npx jest",
            "args": ["--coverage", "--passWithNoTests"],
            "dependsOn": "compile",
            "group": "test",
            "problemMatcher": [],
            "presentation": {
                "reveal": "silent",
                "panel": "shared",
                "group": "checks"
            }
        },
        {
            "label": "dev-server",
            "type": "shell",
            "command": "npx tsx watch src/index.ts",
            "isBackground": true,
            "presentation": {
                "reveal": "always",
                "panel": "dedicated"
            },
            "problemMatcher": []
        },
        {
            "label": "build-all",
            "dependsOn": ["lint", "unit-test"],
            "dependsOrder": "sequence",
            "problemMatcher": []
        }
    ]
}
```

使用方式：

- `Ctrl+Shift+B`（`⌘+Shift+B`）：执行默认构建任务 `compile`（先 `clean`，再编译）。
- 命令面板 → **Tasks: Run Test Task**：在 `lint` 和 `unit-test` 中选择。
- 命令面板 → **Tasks: Run Task** → `dev-server`：启动开发服务器。
- 打开文件夹时自动执行 `npm install`（前提是自动任务已开启）。

几个设计细节：

- `unit-test` 已经 `dependsOn: "compile"`，所以 `build-all` 里不必再列一遍 `compile`，组合依赖即可。
- `lint` 用 `npx eslint .`。ESLint 9 默认的 flat config 不再支持 `--ext`，匹配范围写在 `eslint.config.js` 里；仍在使用 eslintrc 的老项目可以继续用 `--ext`。
- `dev-server` 用 `tsx watch`；老项目里常见的 `ts-node-dev` 作用相同。
- `dev-server` 的 `problemMatcher` 是空数组，所以其他任务不会等它就绪。需要等待时，按 7.3 给它配 `background` 匹配器。

## 7.7 presentation 面板控制：多终端管理

`presentation` 控制任务输出在终端面板中的行为，这是多任务并行时的关键：

| 字段 | 常用值 | 说明 |
| ------ | ------ | ------ |
| `reveal` | `always`（默认）/ `silent` / `never` | `silent`：只在任务启动失败、退出码非 0 或匹配到问题时才显示 |
| `revealProblems` | `never`（默认）/ `onProblem` / `always` | 是否自动切到"问题"面板 |
| `panel` | `shared`（默认）/ `dedicated` / `new` | `shared` 复用终端；`dedicated` 每个任务固定一个终端；`new` 每次新建 |
| `group` | 字符串（默认不分组） | 同一 `group` 的任务用终端**分屏**并列展示 |
| `focus` | `false`（默认） | 是否自动抢占输入焦点 |
| `echo` | `true`（默认） | 是否回显实际执行的命令 |
| `showReuseMessage` | `true`（默认） | 是否显示"终端将被任务复用"的提示 |
| `clear` | `false`（默认） | 每次运行前是否清屏 |
| `close` | `false`（默认） | 任务结束后是否关闭终端 |
| `preserveTerminalName` | `false`（默认） | 任务结束后是否保留终端名 |

建议的组织方式：

- **编译、lint、测试**：用 `panel: "shared"`；同一类检查给相同的 `group`，输出会分屏并列。成功时不想被打扰就配 `reveal: "silent"`。
- **开发服务器、watch**：用 `panel: "dedicated"` 或 `"new"`，避免被其他任务复用或清屏。
- **一次性初始化**：用 `shared` + `silent`，成功时不弹终端，失败时自动露出。

> 如果更习惯在"问题"面板里逐个处理，给检查任务配 `"revealProblems": "onProblem"`，出错时自动切过去。

`clear: true` 会清掉同一终端里的历史输出。长驻服务的共享终端上不要开，否则每次运行别的任务都可能把服务器日志清掉。

## 7.8 任务变量与 options

`tasks.json` 支持变量替换，常用变量如下：

| 变量 | 含义 |
| ------ | ------ |
| `${workspaceFolder}` | 当前工作区根目录 |
| `${workspaceFolderBasename}` | 工作区文件夹名 |
| `${file}` | 当前打开文件的绝对路径 |
| `${relativeFile}` | 当前文件相对工作区的路径 |
| `${relativeFileDirname}` | 当前文件相对工作区的目录 |
| `${fileBasenameNoExtension}` | 当前文件名（不含扩展名） |
| `${fileDirname}` | 当前文件所在目录 |
| `${lineNumber}` / `${selectedText}` | 当前行号 / 当前选中的文本 |
| `${env:NAME}` | 系统环境变量 `NAME` |
| `${config:setting.id}` | 读取 VSCode 设置项 |
| `${input:id}` | 引用 `inputs` 中定义的交互输入 |
| `${command:commandID}` | 执行命令并取其字符串返回值 |
| `${defaultBuildTask}` | 默认构建任务的名称 |

`${file}` 这类变量在任务启动时解析；用 **Tasks: Rerun Last Task** 重跑时默认会重新求值。写脚本时优先用 `${relativeFile}` 这类相对变量，换机器时更稳。

`options` 控制命令在哪里、以什么环境执行：

```json
{
    "label": "build:web",
    "type": "shell",
    "command": "npm run build",
    "options": {
        "cwd": "${workspaceFolder}/packages/web",
        "env": {
            "NODE_ENV": "production"
        }
    },
    "problemMatcher": []
}
```

- `cwd` 默认是工作区根目录。
- `env` 会合并到父进程环境上，只对任务进程生效；`options.env` 里设置的变量**不会**在 `command` / `args` 字符串里被展开。
- 想强制某个 shell，用 `options.shell`：

```json
"options": {
    "shell": {
        "executable": "bash",
        "args": ["-c"]
    }
}
```

`options` 也可以写在 `tasks.json` 顶层，作为所有任务的默认值；`windows` / `linux` / `osx` 覆盖同样适用于 `options`。

## 7.9 交互式输入：让任务接收参数

任务可以定义用户输入，让任务在运行时动态获取参数，就像函数接收参数一样：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "deploy",
            "type": "shell",
            "command": "npm run deploy -- --env=${input:environment} --region=${input:region}",
            "problemMatcher": []
        }
    ],
    "inputs": [
        {
            "id": "environment",
            "type": "pickString",
            "description": "Select deployment environment",
            "options": ["staging", "production", "preview"],
            "default": "staging"
        },
        {
            "id": "region",
            "type": "pickString",
            "description": "Select target region",
            "options": ["us-east-1", "eu-west-1", "ap-southeast-1"],
            "default": "us-east-1"
        }
    ]
}
```

输入类型有三种：

| 类型 | 形式 | 常用字段 |
| ------ | ------ | ------ |
| `pickString` | 下拉选择 | `options`、`default` |
| `promptString` | 文本输入框 | `default`、`password` |
| `command` | 执行命令并取其字符串返回值 | `command`、`args` |

几个细节：

- `inputs` 定义在 `tasks.json` 顶层，用 `${input:id}` 引用，**不支持嵌套**。
- `pickString` 的 `options` 既可以是字符串，也可以是 `{ "label": "...", "value": "..." }` 对象。
- `promptString` 支持 `"password": true`，输入内容不会显示。
- `command` 类型执行的是 VSCode 命令（必须返回字符串），不是 shell 命令；要执行 shell 命令，通常配合 Shell Command 之类的扩展。

## 7.10 进阶：自定义任务提供者扩展

如果想更深度地集成，VSCode 提供了 Task Provider API，允许扩展动态提供任务——不需要 `tasks.json`，由扩展代码生成任务列表：

```typescript
import * as vscode from 'vscode';

class MyBuildToolProvider implements vscode.TaskProvider {
    static readonly type = 'mybuildtool';

    provideTasks(token: vscode.CancellationToken): vscode.Task[] {
        // 扫描项目，动态生成任务列表
        const tasks: vscode.Task[] = [];
        const workspaceFolders = vscode.workspace.workspaceFolders;
        if (!workspaceFolders) return tasks;

        for (const folder of workspaceFolders) {
            if (token.isCancellationRequested) break;

            const buildTask = new vscode.Task(
                { type: MyBuildToolProvider.type, task: 'build' },
                folder,
                'build',
                MyBuildToolProvider.type,
                new vscode.ShellExecution('mybuild --compile')
            );
            buildTask.group = vscode.TaskGroup.Build;
            tasks.push(buildTask);
        }
        return tasks;
    }

    resolveTask(task: vscode.Task, _token: vscode.CancellationToken): vscode.Task | undefined {
        // tasks.json 中引用的任务也要能还原出执行方式
        const definition = task.definition;
        return new vscode.Task(
            definition,
            task.scope ?? vscode.TaskScope.Workspace,
            definition.task as string,
            MyBuildToolProvider.type,
            new vscode.ShellExecution(`mybuild --${definition.task}`)
        );
    }
}

vscode.tasks.registerTaskProvider(MyBuildToolProvider.type, new MyBuildToolProvider());
```

扩展还需要在 `package.json` 中声明任务类型：

```json
{
    "contributes": {
        "taskDefinitions": [
            {
                "type": "mybuildtool",
                "required": ["task"],
                "properties": {
                    "task": {
                        "type": "string",
                        "description": "要运行的目标"
                    }
                }
            }
        ]
    }
}
```

`taskDefinitions` 声明任务类型和可配置字段；`registerTaskProvider` 在扩展激活时注册。用户仍然可以在 `tasks.json` 里按 `type` 引用并覆盖这些任务。npm、Gulp、CMake Tools、Gradle 等扩展能给任务列表"变出"任务，靠的就是这套机制。

`resolveTask` 要使用同一个 definition 对象；如果只实现 `provideTasks` 而用户又在 `tasks.json` 里引用了任务，VSCode 会提示该任务无法创建。

📋 **本章小结**

- **tasks.json 2.0.0** 是 VSCode 自动化的核心，支持 `shell`、`process` 和扩展提供的任务类型（如 `npm`）
- `Ctrl+Shift+B` 只运行 **build 组的默认任务**；其他任务用 **Tasks: Run Task**，或绑定 `workbench.action.tasks.runTask` 快捷键
- **problemMatcher** 把构建输出变成可点击的问题；`[]` 表示不解析，`background` 块负责标记后台任务的启动/就绪
- **dependsOn + dependsOrder** 构建依赖链，默认并行、`sequence` 串行；共享状态的步骤务必串成链
- **runOptions.runOn** 只支持 `default` 和 `folderOpen`；自动任务需要受信工作区，且 `task.allowAutomaticTasks` 自 1.109 起默认是 `off`
- **presentation** 控制终端复用、分屏、清屏和失败时是否显示，长驻服务应使用独立终端
- **变量 + options + inputs** 让任务可移植、可配置、可交互
- **Task Provider API** 允许扩展动态注入任务，是深度集成的终极手段
