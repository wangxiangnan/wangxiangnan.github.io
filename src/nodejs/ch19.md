# 第19章：RESTful API设计与最佳实践

## 引言：API是开发者的UI

如果说普通用户看到的是网页界面，那开发者看到的就是API。一个设计糟糕的API就像一个布局混乱的网页——虽然功能都在，但用起来让人抓狂。

REST（Representational State Transfer）不是一个规范或标准，它是Roy Fielding在2000年博士论文中提出的一种**架构风格**。它不规定你"必须"怎么做，而是给出了一组约束和原则。遵循这些原则设计出的API，会更直觉、更一致、更容易使用和维护。

本章我们将从理论到实践，设计一套"让人用着舒服"的API。

## 19.1 REST架构风格6大约束

```
1. 客户端-服务器分离（Client-Server）
   → 前后端独立演进，互不依赖

2. 无状态（Stateless）
   → 每个请求包含所有必需信息，服务器不保存客户端状态

3. 可缓存（Cacheable）
   → 响应明确标识是否可缓存，提高性能

4. 统一接口（Uniform Interface）
   → 资源标识、资源操作、自描述消息、超媒体驱动

5. 分层系统（Layered System）
   → 客户端不知道是直连服务器还是经过中间层

6. 按需代码（Code on Demand）- 可选
   → 服务器可以传送可执行代码给客户端（如JS）
```

## 19.2 URL设计规范

### 19.2.1 资源命名

```
✅ 好的URL设计：
GET    /api/v1/users              获取用户列表
GET    /api/v1/users/123          获取单个用户
POST   /api/v1/users              创建用户
PUT    /api/v1/users/123          完整更新用户
PATCH  /api/v1/users/123          部分更新用户
DELETE /api/v1/users/123          删除用户

GET    /api/v1/users/123/posts    获取某用户的文章列表
GET    /api/v1/users/123/posts/456 获取某用户的某篇文章

❌ 糟糕的URL设计：
GET    /api/getUsers              动词！资源应该是名词
GET    /api/user/list             不统一
POST   /api/createUser            动词冗余（POST本身就是"创建"的意思）
GET    /api/users/get-by-id/123   啰嗦
DELETE /api/users/123/delete      delete冗余（DELETE方法已经表达了意图）

命名规则：
- 使用名词，不用动词（HTTP方法已经表达了动作）
- 使用复数形式（/users 不是 /user）
- 使用kebab-case（/order-items 不是 /orderItems）
- 层级关系用URL路径表达（/users/123/posts）
- 避免超过3层嵌套（/a/1/b/2/c/3 太深了）
```

### 19.2.2 版本控制

```typescript
// 方式1：URL路径版本（最常见、最直观）
// /api/v1/users
// /api/v2/users
import express from 'express';

const app = express();
const v1Router = express.Router();
const v2Router = express.Router();

v1Router.get('/users', (req, res) => {
  res.json({ version: 1, users: [{ name: 'Alice' }] });
});

v2Router.get('/users', (req, res) => {
  // v2返回不同的数据结构
  res.json({ version: 2, data: { users: [{ fullName: 'Alice Smith' }] } });
});

app.use('/api/v1', v1Router);
app.use('/api/v2', v2Router);

// 方式2：Header版本
// Accept: application/vnd.myapp.v2+json
app.get('/api/users', (req, res) => {
  const accept = req.headers.accept || '';
  const version = accept.match(/vnd\.myapp\.v(\d+)/)?.[1] || '1';

  if (version === '2') {
    res.json({ data: { users: [] } });
  } else {
    res.json({ users: [] });
  }
});

// 方式3：查询参数版本（不太推荐）
// /api/users?version=2
```

## 19.3 HTTP方法语义

```typescript
import express from 'express';
const app = express();
app.use(express.json());

// GET - 获取资源（幂等、安全、可缓存）
// "安全"意味着不会修改服务器状态
app.get('/api/articles', async (req, res) => {
  const { page = 1, limit = 10, category, sort } = req.query;
  // 查询列表，支持过滤、排序、分页
  res.json({ data: [], pagination: { page, limit, total: 0 } });
});

app.get('/api/articles/:id', async (req, res) => {
  // 获取单个资源
  res.json({ data: { id: req.params.id, title: '...' } });
});

// POST - 创建资源（非幂等）
// 每次调用都可能创建新资源
app.post('/api/articles', async (req, res) => {
  const article = await createArticle(req.body);
  // 201 Created + Location header指向新资源
  res.status(201)
    .location(`/api/articles/${article.id}`)
    .json({ data: article });
});

// PUT - 完整替换资源（幂等）
// 客户端发送完整的资源表示
// 调用100次结果和1次一样
app.put('/api/articles/:id', async (req, res) => {
  // 注意：PUT是完整替换，未提供的字段应该被清空/设默认值
  const article = await replaceArticle(req.params.id, req.body);
  res.json({ data: article });
});

// PATCH - 部分更新资源（可能非幂等）
// 只发送需要修改的字段
app.patch('/api/articles/:id', async (req, res) => {
  // 只更新提供的字段，其他保持不变
  const article = await updateArticle(req.params.id, req.body);
  res.json({ data: article });
});

// DELETE - 删除资源（幂等）
// 删除一次和删除多次效果一样（资源不存在了）
app.delete('/api/articles/:id', async (req, res) => {
  await deleteArticle(req.params.id);
  res.status(204).end(); // 204 No Content
});

// 非CRUD操作怎么设计？
// 把操作当作资源或使用自定义动作

// 方式1：操作作为子资源
app.post('/api/articles/:id/publish', async (req, res) => {
  // "发布"是对文章的一个操作
  await publishArticle(req.params.id);
  res.json({ data: { published: true } });
});

// 方式2：状态更新（用PATCH）
app.patch('/api/articles/:id', async (req, res) => {
  // { "status": "published" }
  res.json({});
});

// 模拟函数
async function createArticle(data: any) { return { id: '1', ...data }; }
async function replaceArticle(id: string, data: any) { return { id, ...data }; }
async function updateArticle(id: string, data: any) { return { id, ...data }; }
async function deleteArticle(id: string) {}
async function publishArticle(id: string) {}

app.listen(3000);
```

## 19.4 状态码使用指南

```typescript
// 2xx 成功
// 200 OK - 通用成功
// 201 Created - 资源创建成功（POST）
// 204 No Content - 成功但无响应体（DELETE）
// 206 Partial Content - 分片响应（大文件下载）

// 3xx 重定向
// 301 Moved Permanently - 永久重定向
// 302 Found - 临时重定向
// 304 Not Modified - 资源未变化（缓存有效）

// 4xx 客户端错误
// 400 Bad Request - 请求格式错误/参数无效
// 401 Unauthorized - 未认证（需要登录）
// 403 Forbidden - 已认证但无权限
// 404 Not Found - 资源不存在
// 405 Method Not Allowed - 方法不支持
// 409 Conflict - 冲突（如重复创建）
// 422 Unprocessable Entity - 语义错误（格式对但业务不允许）
// 429 Too Many Requests - 请求频率超限

// 5xx 服务器错误
// 500 Internal Server Error - 未知服务器错误
// 502 Bad Gateway - 网关错误
// 503 Service Unavailable - 服务不可用
// 504 Gateway Timeout - 网关超时

// 实践中的常见错误：
// ❌ 所有错误都返回200，靠body中的code区分
// ❌ 401和403分不清
// ❌ 把422当400用

// 区分401和403：
// 401：你是谁？我不认识你。请先登录。（NOT authenticated）
// 403：我认识你，但你没权限。别想了。（NOT authorized）
```

### 19.5.1 zod/joi/ajv对比

```typescript
// ============ Zod（推荐：类型安全、TypeScript原生） ============
import { z } from 'zod';

const createUserSchema = z.object({
  email: z.string().email('无效的邮箱格式'),
  username: z.string().min(3).max(30).regex(/^[a-zA-Z0-9_]+$/),
  password: z.string().min(8).max(128),
  age: z.number().int().min(0).max(150).optional(),
  tags: z.array(z.string()).max(5).default([]),
});

// 自动推断TypeScript类型！
type CreateUserInput = z.infer<typeof createUserSchema>;
// {
//   email: string;
//   username: string;
//   password: string;
//   age?: number;
//   tags: string[];
// }

// 使用
function validateWithZod(data: unknown) {
  const result = createUserSchema.safeParse(data);
  if (!result.success) {
    console.log(result.error.flatten());
    // { fieldErrors: { email: ['无效的邮箱格式'], ... } }
  } else {
    console.log(result.data); // 类型安全的数据
  }
}

// ============ Joi（成熟稳定，Express生态常见） ============
import Joi from 'joi';

const joiSchema = Joi.object({
  email: Joi.string().email().required(),
  username: Joi.string().alphanum().min(3).max(30).required(),
  password: Joi.string().min(8).required(),
  age: Joi.number().integer().min(0).max(150),
});

// ============ AJV（最快，JSON Schema标准，Fastify内置） ============
import Ajv from 'ajv';
import addFormats from 'ajv-formats';

const ajv = new Ajv({ allErrors: true });
addFormats(ajv);

const ajvSchema = {
  type: 'object',
  required: ['email', 'username', 'password'],
  properties: {
    email: { type: 'string', format: 'email' },
    username: { type: 'string', minLength: 3, maxLength: 30 },
    password: { type: 'string', minLength: 8 },
    age: { type: 'integer', minimum: 0, maximum: 150 },
  },
  additionalProperties: false,
};

const validate = ajv.compile(ajvSchema);

// 性能对比（验证1000个对象）：
// AJV:  ~1ms  (最快，编译Schema后的验证几乎无开销)
// Zod:  ~5ms  (较快，纯JavaScript验证)
// Joi:  ~15ms (较慢，功能最丰富)

// 推荐：
// - TypeScript项目 → Zod（类型推断无与伦比）
// - Fastify项目 → AJV（内置集成，JSON Schema复用）
// - Express项目 → Zod 或 Joi（看团队习惯）
```

### 19.6.1 统一响应结构

```typescript
// 成功响应
interface SuccessResponse<T> {
  success: true;
  data: T;
  meta?: {
    pagination?: PaginationMeta;
    [key: string]: unknown;
  };
}

// 错误响应
interface ErrorResponse {
  success: false;
  error: {
    code: string;        // 机器可读的错误代码
    message: string;     // 人类可读的错误消息
    details?: unknown;   // 详细错误信息（如验证错误的字段列表）
  };
}

interface PaginationMeta {
  page: number;
  limit: number;
  total: number;
  totalPages: number;
  hasNext: boolean;
  hasPrev: boolean;
}

// 实例
// GET /api/users?page=2&limit=10
const listResponse: SuccessResponse<User[]> = {
  success: true,
  data: [
    { id: '1', name: 'Alice', email: 'alice@example.com' },
    { id: '2', name: 'Bob', email: 'bob@example.com' },
  ],
  meta: {
    pagination: {
      page: 2,
      limit: 10,
      total: 45,
      totalPages: 5,
      hasNext: true,
      hasPrev: true,
    },
  },
};

// 错误响应实例

  success: false,
```

### 19.6.2 分页设计

```typescript
import express from 'express';

const app = express();

// 偏移分页（Offset Pagination）
// 简单直观，但大偏移量时性能差
app.get('/api/posts', async (req, res) => {
  const page = Math.max(1, parseInt(req.query.page as string) || 1);
  const limit = Math.min(100, Math.max(1, parseInt(req.query.limit as string) || 20));
  const offset = (page - 1) * limit;

  // SELECT * FROM posts ORDER BY created_at DESC LIMIT $limit OFFSET $offset
  // SELECT COUNT(*) FROM posts
  const posts = []; // 模拟查询结果
  const total = 100; // 模拟总数

  res.json({
    success: true,
    data: posts,
    meta: {
      pagination: {
        page,
        limit,
        total,
        totalPages: Math.ceil(total / limit),
        hasNext: page * limit < total,
        hasPrev: page > 1,
      },
    },
  });
});

// 游标分页（Cursor Pagination）
// 性能稳定，适合无限滚动，但不能跳页
app.get('/api/feed', async (req, res) => {
  const limit = Math.min(50, parseInt(req.query.limit as string) || 20);
  const cursor = req.query.cursor as string; // 上一页最后一条的ID或时间戳

  // 如果有cursor：WHERE created_at < $cursor ORDER BY created_at DESC LIMIT $limit+1
  // 如果没cursor：ORDER BY created_at DESC LIMIT $limit+1

  const items: any[] = []; // 模拟查询（多查一条来判断是否有下一页）
  const hasMore = items.length > limit;
  const data = hasMore ? items.slice(0, limit) : items;
  const nextCursor = hasMore ? data[data.length - 1]?.id : null;

  res.json({
    success: true,
    data,
    meta: {
      cursor: {
        next: nextCursor, // 前端下次请求带上这个
        hasMore,
      },
    },
  });
});

app.listen(3000);
```

## 19.8 速率限制(Rate Limiting)

```typescript
import express from 'express';

// 简单的内存速率限制器
class RateLimiter {
  private windows = new Map<string, { count: number; resetAt: number }>();
  private maxRequests: number;
  private windowMs: number;

  constructor(maxRequests: number = 100, windowMs: number = 60_000) {
    this.maxRequests = maxRequests;
    this.windowMs = windowMs;

    // 定期清理过期记录
    setInterval(() => this.cleanup(), windowMs);
  }

  isAllowed(key: string): { allowed: boolean; remaining: number; resetAt: number } {
    const now = Date.now();
    const record = this.windows.get(key);

    if (!record || now > record.resetAt) {
      this.windows.set(key, { count: 1, resetAt: now + this.windowMs });
      return { allowed: true, remaining: this.maxRequests - 1, resetAt: now + this.windowMs };
    }

    if (record.count >= this.maxRequests) {
      return { allowed: false, remaining: 0, resetAt: record.resetAt };
    }

    record.count++;
    return { allowed: true, remaining: this.maxRequests - record.count, resetAt: record.resetAt };
  }

  private cleanup(): void {
    const now = Date.now();
    for (const [key, record] of this.windows) {
      if (now > record.resetAt) {
        this.windows.delete(key);
      }
    }
  }
}

const app = express();

// 全局速率限制：每分钟100次
const globalLimiter = new RateLimiter(100, 60_000);

// API速率限制：每分钟20次
const apiLimiter = new RateLimiter(20, 60_000);

// 中间件
function rateLimit(limiter: RateLimiter) {
  return (req: express.Request, res: express.Response, next: express.NextFunction) => {
    const key = req.ip || 'unknown';
    const result = limiter.isAllowed(key);

    // 设置标准的速率限制头
    res.set({
      'X-RateLimit-Limit': String(100),
      'X-RateLimit-Remaining': String(result.remaining),
      'X-RateLimit-Reset': String(Math.ceil(result.resetAt / 1000)),
    });

    if (!result.allowed) {
      res.set('Retry-After', String(Math.ceil((result.resetAt - Date.now()) / 1000)));
      return res.status(429).json({
        success: false,
        error: {
          code: 'RATE_LIMITED',
          message: 'Too many requests, please try again later',
          retryAfter: Math.ceil((result.resetAt - Date.now()) / 1000),
        },
      });
    }

    next();
  };
}

app.use(rateLimit(globalLimiter));
app.use('/api', rateLimit(apiLimiter));

// 登录路由：更严格的限制（防暴力破解）
const loginLimiter = new RateLimiter(5, 15 * 60_000); // 15分钟5次
app.post('/auth/login', rateLimit(loginLimiter), (req, res) => {
  res.json({ message: 'Login endpoint' });
});

app.listen(3000);
```

## 19.9 API版本管理策略

```typescript
// 策略1：URL版本（最常用）
// /api/v1/users → /api/v2/users
// 优点：简单清晰
// 缺点：URL变化大

// 策略2：请求头版本
// Accept: application/vnd.myapp.v2+json
// 优点：URL干净
// 缺点：不直观，调试麻烦

// 策略3：查询参数版本
// /api/users?api_version=2
// 优点：简单
// 缺点：不够RESTful

// 实际建议：
// 1. 新项目用URL版本（/api/v1/...）
// 2. 尽量保持向后兼容，减少破坏性变更
// 3. 旧版本维护至少6-12个月后再下线
// 4. 提供迁移指南和变更日志

// 向后兼容的变更（不需要新版本）：
// - 新增可选字段
// - 新增新的端点
// - 新增新的查询参数

// 破坏性变更（需要新版本）：
// - 删除字段
// - 修改字段类型
// - 修改字段含义
// - 修改URL结构
// - 修改认证方式
```

## 19.10 GraphQL vs REST

```typescript
// 什么时候选GraphQL？

// REST的痛点：
// 1. Over-fetching: 只需要name和email，但GET /users返回了20个字段
// 2. Under-fetching: 一个页面需要调3个API才能拿到所有数据
// 3. 版本管理：每次修改可能要发布新版本

// GraphQL的优势：
// ✅ 精确获取需要的数据（客户端定义响应结构）
// ✅ 一次请求获取多个资源
// ✅ 强类型Schema + 自动文档
// ✅ 无需版本控制（Schema可以演进）

// GraphQL的劣势：
// ❌ 学习曲线陡
// ❌ 缓存复杂（HTTP缓存失效）
// ❌ 文件上传复杂
// ❌ N+1查询问题
// ❌ 安全性（恶意深层嵌套查询）

// 选择建议：
// - 简单CRUD、对外公开API → REST
// - 复杂前端、多端适配、频繁变更 → GraphQL
// - 微服务间通信 → gRPC
// - 实时数据 → WebSocket / SSE

// 也可以混合使用：
```

## 19.12 常见坑点

1. **URL中用动词**：`/getUsers` → 应该是 `GET /users`
2. **不一致的命名**：有的用 `camelCase`，有的用 `snake_case`，选一个坚持用。
3. **不恰当的状态码**：所有错误都返回200，靠code字段区分。
4. **没有分页**：列表接口不加分页，数据量大时性能炸裂。
5. **过度嵌套**：`/api/v1/companies/1/departments/2/employees/3/tasks/4` → 超过3层考虑扁平化。
6. **敏感信息泄露**：响应中包含password、internalId等不应该暴露的字段。
7. **没有速率限制**：被爬虫或攻击者打穿。
8. **缺少CORS配置**：前端调不通API一脸懵。

## 19.13 本章小结

| 原则 | 实践 |
| ------ | ------ |
| URL设计 | 名词复数、kebab-case、不超过3层嵌套 |
| HTTP方法 | GET读、POST创建、PUT替换、PATCH更新、DELETE删除 |
| 状态码 | 2xx成功、4xx客户端错误、5xx服务器错误 |
| 响应格式 | 统一结构：{ success, data, error, meta } |
| 验证 | Zod(TypeScript) / AJV(性能) / Joi(功能) |
| 分页 | 偏移分页(简单) / 游标分页(性能) |
| 文档 | OpenAPI/Swagger自动生成 |
| 安全 | 速率限制 + 认证鉴权 + 输入验证 |
| 版本 | URL版本(/api/v1/) + 向后兼容优先 |

**框架选择指南**：

- 需要快速开发 + 丰富生态 → **Express**
- 追求代码优雅 + 异步友好 → **Koa**
- 需要极致性能 + TypeScript → **Fastify**
- 企业级全功能 → **NestJS**（基于Express/Fastify）

**认证方案选择**：

- 传统Web应用 → Session + Cookie
- SPA / 移动端 → JWT (Access + Refresh Token)
- 第三方登录 → OAuth 2.0
- 混合方案 → JWT + Redis黑名单（兼顾无状态和可撤销）
