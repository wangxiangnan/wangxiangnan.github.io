## 19.1 为什么 HTTP/1.1 需要一场大修

想象一家只有一条传菜通道的餐厅：第一道菜没送完，后面的菜全堵在厨房里。这就是 13.6 的**队头阻塞（Head-of-Line Blocking）**——一条 TCP 字节流上，前一个响应没传完，后面的只能干等。

HTTP/1.1 时代的绕行方案是浏览器对同一域名开 6-8 条 TCP 连接（12.4 的五元组保证了它们互不冲突）。但每条连接都要三次握手、TLS 握手、独立维护拥塞窗口（第10章）——连接越多开销越大，还挤占了 12.7 提到的动态端口。

第二个顽疾是**头部冗余**：每次请求都重复携带 Cookie、User-Agent、Accept 等头部，同一会话里这些值几乎不变。加载 100 个资源 × 每次几百字节头部 ≈ 浪费几十 KB——在第10章调好的带宽里，这是纯损耗。

两个顽疾指向同一个根源：HTTP/1.1 的「文本 + 按序」模型。HTTP/2（脱胎于 Google 的 SPDY）对它做了深度重构。

## 19.2 二进制分帧：从文本到帧

HTTP/1.1 是纯文本协议，解析要逐行读、处理各种边界情况（13.7 手写服务器时你体会过了）。HTTP/2 把所有通信拆成小的**二进制帧**，每帧固定 9 字节头：

```
+-----------------------------------------------+
|                 Length (24)                     |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |               |
+-+-------------+---------------+               |
|R|              Stream ID (31)                 |
+-+---------------------------------------------+
|                 Frame Payload                  |
+-----------------------------------------------+
```

- **Length**：载荷长度（最大 2^24-1）。
- **Type**：帧类型——DATA（0x0）、HEADERS（0x1）、SETTINGS（0x4）、PING（0x6）、WINDOW_UPDATE（0x8）等。
- **Flags**：类型专属标志（如 END_STREAM 表示响应结束）。
- **Stream ID**：这个帧属于哪条流——19.3 的主角。

二进制让解析变成确定性的位运算：不再猜边界、不再容错空格。连接建立后双方先互发一个固定的「连接序言」（`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` + SETTINGS 帧），确认双方都说 HTTP/2——和 17.3 的 WebSocket 升级握手是同一种「协议协商」套路，只是换了个方向。

## 19.3 多路复用：一条连接跑所有流

HTTP/2 最核心的改进。同一个 TCP 连接上同时跑多条**流（Stream）**，每条流对应一个请求-响应对；帧通过 Stream ID 区分归属，接收方可以乱序收帧，再按 ID 重组。

```
一个 TCP 连接（Connection）
├── Stream 1（请求 /index.html）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
├── Stream 3（请求 /style.css）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
├── Stream 5（请求 /app.js）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
└── Stream 0（控制流：SETTINGS、PING 等）
```

「先猜再读」第三问的答案就在编号规则里：客户端发起的流用**奇数** ID（1、3、5……），服务端发起的用**偶数** ID——双向各自编号、永不冲突。偶数流干什么用？19.6 的 Server Push 会给出答案。Stream 0 是控制流，承载连接级帧。

HTTP/2 有自己的流级流量控制（WINDOW_UPDATE 帧调每条流的窗口），思想与 11.2 的 rwnd 相同，只是把「一个连接一个窗口」细化成「每条流一个窗口」。

**「先猜再读」第二问的答案：协议本身允许明文的 h2c，但浏览器只支持 TLS 之上的 h2。原因有二：明文网络中中间设备常按 HTTP/1.1 语义瞎处理流量；更重要的是，协商 HTTP/2 的 **ALPN** 扩展就藏在 TLS 握手里（15.2 的 ClientHello 扩展大家族的一员）——TLS 不在，协商通道就不在。这也是「浏览器里的 HTTP/2 几乎总是 HTTPS」的机制根源。

> [!TIP] curl 一眼验证 HTTP/2
> `curl -I --http2 https://www.example.com` 输出的状态行如果是 `HTTP/2 200`，说明协商成功；加 `-v` 能在 TLS 握手日志里看到 `ALPN: server accepted h2`——15.2 学的扩展字段在这里找到了现实工作。

## 19.4 头部压缩 HPACK

HPACK 用三招消除头部冗余：

1. **静态表**：内置 61 个最常用的头（`:method: GET`、`:status: 200`、`content-type: text/html` 等），直接用索引号引用。
2. **动态表**：连接期间双方共同维护的字典，出现过一次的头就存进去，之后只发索引——第一次发完整 `user-agent: Mozilla/...`（几百字节），第二次只发 1 个索引字节。
3. **Huffman 编码**：对必须发送的字符串做变长编码，高频字符用短码。

三招叠加，头部体积通常砍到原来的十分之一以下。但压缩与加密同用时有个经典陷阱：攻击者若能诱导你把「秘密」塞进压缩字典，就能通过观察密文长度逐字节猜出内容（CRIME 攻击的思路，当年针对 TLS 压缩）。HPACK 的对策是每个连接独立的字典 + 严格规范——第22章讲威胁模型时会再遇到「侧信道」这个概念：泄露信息的不是内容，是长度与时间。

## 19.5 流优先级与依赖树

资源有轻重：HTML 和 CSS 比 Logo 图片要紧。HTTP/2 允许客户端用 PRIORITY 帧声明依赖树与权重——「Stream 5 依赖 Stream 1，权重 16」，服务器据此调度带宽，先发关键资源、推迟次要资源。

理想很丰满，实践打折扣：优先级调度逻辑复杂，各服务器实现质量参差，客户端的声明又常常与真实需求脱节——这是 HTTP/2 最著名的一个「遗憾」，HTTP/3 对优先级机制做了简化重构（第20章一笔带过）。

## 19.6 Server Push：好心办坏事

服务器知道客户端请求 `/index.html` 后大概率还要 `/style.css`，可以不等客户端开口就推过去：发一个 **PUSH_PROMISE** 帧（「我要推这个资源了」），然后直接发送对应内容。

「先猜再读」第三问的另一半答案：服务器主动发起的流用偶数 ID——这就是偶数流的用途。

```python
# Server Push 概念示意（Stream 1 上同时发生）：
# 1. PUSH_PROMISE: "我要推 /style.css 了"
# 2. HEADERS + DATA: /index.html 的响应
# 3. HEADERS + DATA: /style.css 的响应（Stream 2，服务器发起）
```

但实践中效果不佳：服务器并不真正知道客户端缓存里有什么（14.1 的缓存状态对服务器不可见），经常推回一堆已缓存的资源——白费带宽还挤占连接。Chrome 在 2020 年移除了对它的支持，17.5 说「Server Push 已成历史」的判定在此落定。

## 19.7 成绩单：解决了什么，没解决什么

**解决了：**

- 应用层队头阻塞——多路复用让响应不再排队。
- 头部冗余——HPACK 砍掉九成重复。
- 连接开销——一条连接跑所有请求，握手、TLS、拥塞窗口都只付一次。

**没解决——「先猜再读」第一问的答案：TCP 层的队头阻塞。** 所有流共享同一条 TCP 连接，而 TCP 是一条按序字节流（8.1）：丢一个包，9.1 的累积确认机制会让整个连接停住等重传——**所有流一起堵**，哪怕丢的只是 Stream 3 的一帧。12.4 那条「要并行就多开连接」的逃生通道，HTTP/2 把它堵上了。

这是 HTTP/2 的阿喀厥斯之踵。病根在 TCP，药方只能开在传输层——下一章的 QUIC 换掉 TCP，才是治本。

## 19.8 编程实践：对比 HTTP/1.1 与 HTTP/2 的性能

```python
"""
对比 HTTP/1.1 和 HTTP/2 的并发请求性能
需要安装: pip install httpx[http2]
"""
import httpx
import asyncio
import time

URLS = [f"https://httpbin.org/delay/1" for _ in range(10)]

async def benchmark(http2: bool):
    async with httpx.AsyncClient(http2=http2) as client:
        start = time.perf_counter()
        tasks = [client.get(url) for url in URLS]
        responses = await asyncio.gather(*tasks)
        elapsed = time.perf_counter() - start
        version = "HTTP/2" if http2 else "HTTP/1.1"
        print(f"{version}: {len(responses)} 请求, 耗时 {elapsed:.2f}s")
        return elapsed

async def main():
    t1 = await benchmark(http2=False)
    t2 = await benchmark(http2=True)
    print(f"\nHTTP/2 比 HTTP/1.1 快了 {t1/t2:.1f} 倍")

asyncio.run(main())
```

预期结果：HTTP/1.1 约 10 秒（同一连接串行排队，队头阻塞显形），HTTP/2 约 1-2 秒（十请求复用一条连接交错并行）。注意对照 19.7 的结论——这个差距来自**应用层**的解放；若网络丢包，HTTP/2 的优势会明显缩水，那就是 TCP 层队头阻塞在拖后腿。

## 19.9 抓包实践：观察多路复用

Wireshark 过滤 `http2`（若走 TLS，先用 15.9 的 SSLKEYLOGFILE 解密），观察：

1. 连接建立后客户端发 SETTINGS 帧（Stream 0），宣告参数（如 `MAX_CONCURRENT_STREAMS=100`），服务器 SETTINGS+ACK。
2. 客户端在 Stream 1、3、5 上几乎同时发出 HEADERS 帧。
3. 响应帧交错到达——可能先收到 Stream 3 的 DATA，再收到 Stream 1 的 DATA：多路复用的直观证据。
4. 展开任意帧看 `Stream Identifier`，确认每个帧的归属；找一找 HPACK 解码后的 `:method: GET` 索引引用。

`tshark` 命令行版：

```bash
tshark -r capture.pcap -Y "http2" -T fields \
  -e frame.number -e http2.type -e http2.stream.id
```

## 本章小结

- HTTP/1.1 的两大顽疾：一条字节流的队头阻塞、每次请求重复的头部冗余——都源于「文本 + 按序」模型。
- 二进制分帧让解析变成确定性位运算：9 字节帧头 + Length/Type/Flags/Stream ID。
- 多路复用是核心解药：一条连接多条流，帧交错传输、按 Stream ID 重组，应用层队头阻塞终结。
- ALPN 把「用不用 h2」的协商藏进 TLS 握手——浏览器里的 HTTP/2 几乎必然是 HTTPS。
- HPACK 三板斧：静态表引用常见头、动态表记住会话内重复、Huffman 压缩剩余字符串。
- 流级 WINDOW_UPDATE 把 11.2 的 rwnd 思想细化到每条流。
- Server Push 死于信息不对称：服务器不知道客户端缓存里有什么，2020 年后浏览器陆续移除。
- HTTP/2 治好了应用层，却让 TCP 队头阻塞更疼——一条连接一处丢包，全部流陪堵；药方在传输层，见下一章。
