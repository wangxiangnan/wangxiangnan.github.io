# 第15章：哨兵模式——自动故障转移

## 引言：不眠的守夜人

你有没有这样的经历：凌晨三点，手机突然疯狂震动——生产环境的 Redis Master 挂了！你揉着眼睛爬起来，手动把 Replica 提升为 Master，再修改所有应用的连接配置……整个过程像是在黑暗中摸黑换轮胎。

如果有一个"不眠的守夜人"，7x24 小时盯着你的 Redis 集群，一旦发现 Master 挂了，就自动完成故障转移——选一个新的 Master，更新所有客户端的配置，整个过程你甚至不需要醒来。

这个"守夜人"就是 Redis Sentinel（哨兵）。

> **编程隐喻时间**：Sentinel 就像 Kubernetes 的 Controller——它持续监控（Watch）Redis 节点的状态，当检测到故障（Desired State != Actual State）时，自动执行修复动作（Reconciliation），让整个系统回到期望状态。

## 15.1 为什么需要哨兵？

主从复制虽然解决了数据冗余和读扩展的问题，但有一个致命缺陷：**Master 挂了怎么办？**

手动故障转移的痛苦：

1. 你收到告警 -> 手动确认 Master 确实挂了
2. 手动选择一个 Replica 提升为新 Master
3. 修改其他 Replica 的配置，指向新 Master
4. 修改所有应用的连接配置
5. 重启所有应用

这整个过程可能需要几十分钟，而且如果操作失误（比如选了一个数据最旧的 Replica），还会导致数据丢失。

**Sentinel 的作用就是把这个过程完全自动化。**

## 15.2 Sentinel 的工作原理

Sentinel 是一个特殊的 Redis 实例，它不存储业务数据，只负责**监控、通知和自动故障转移**。

### 15.2.1 监控机制

Sentinel 每隔一段时间（默认 10 秒）会向被监控的 Redis 实例发送命令：

```
Sentinel                          Master
   |  ---- INFO 命令（每10秒）---->  |
   |  <---- Master 状态信息 -------  |
   |                                  |
   |  ---- PING 命令（每1秒）------>  |
   |  <---- PONG --------------------  |
```

同时，Sentinel 之间也会互相 PING，确保彼此在线。

### 15.2.2 主观下线（SDOWN）和客观下线（ODOWN）

这是 Sentinel 的核心概念，理解这两个概念就理解了 Sentinel 的灵魂：

**主观下线（Subjectively Down, SDOWN）**：

- 单个 Sentinel 认为某个节点不可达
- 就像你觉得"这家餐厅不好吃"——这是你的**主观判断**
- Sentinel 在 `down-after-milliseconds` 内没有收到有效回复，就标记为 SDOWN

**客观下线（Objectively Down, ODOWN）**：

- 多个 Sentinel 都认为某个节点不可达，达成共识
- 就像大众点评上 90% 的人都说"这家餐厅不好吃"——这是**客观事实**
- 当 `quorum` 个 Sentinel 都标记为 SDOWN 时，状态变为 ODOWN

```
Sentinel-1: "Master 好像挂了！"（SDOWN）
Sentinel-2: "我也觉得！"        （SDOWN）
Sentinel-3: "确认，挂了！"       （SDOWN）
                |
           投票达成共识
                |
        Master = ODOWN（客观下线）
```

### 15.2.3 Leader 选举和故障转移流程

一旦 Master 被标记为 ODOWN，Sentinel 集群需要选出一个 **Leader Sentinel** 来执行故障转移：

```
Step 1: Sentinel 之间通过 Raft 算法选举 Leader
         |
Step 2: Leader 从所有 Replica 中选择一个作为新 Master
         选择标准：
         - Replica 优先级（replica-priority）
         - 复制偏移量（offset 最大的优先）
         - Run ID 字典序
         |
Step 3: Leader 向选中的 Replica 发送 SLAVEOF NO ONE
         |
Step 4: Leader 让其他 Replica 指向新 Master
         发送 SLAVEOF new_master_ip new_master_port
         |
Step 5: 通知客户端 Master 已切换
         |
Step 6: 如果旧 Master 恢复，将其变为新 Master 的 Replica
```

## 15.3 Sentinel 配置详解

### 15.3.1 sentinel.conf

```bash
# sentinel.conf -- Sentinel 配置文件

# Sentinel 监听端口（默认 26379）
port 26379

# 监控的主节点配置
# sentinel monitor <主节点名称> <IP> <端口> <quorum>
# quorum = 判定 ODOWN 所需的最少 Sentinel 数量
sentinel monitor mymaster 192.168.1.100 6379 2

# 如果 Master 有密码
sentinel auth-pass mymaster your_master_password

# 主观下线的判定时间（毫秒）
# 在这个时间内没有收到有效回复，就认为节点 SDOWN
sentinel down-after-milliseconds mymaster 5000

# 故障转移的超时时间（毫秒）
# 如果故障转移在这个时间内没完成，就重新开始
sentinel failover-timeout mymaster 60000

# 故障转移时，同时对新 Master 进行同步的 Replica 数量
# 值越小对集群影响越小，但恢复时间越长
sentinel parallel-syncs mymaster 1

# Sentinel 的日志文件
logfile "/var/log/redis/sentinel.log"

# Sentinel 的工作目录
dir "/var/lib/redis"
```

### 15.3.2 关键配置项解析

| 配置项 | 默认值 | 说明 | 建议 |
|--------|--------|------|------|
| `down-after-milliseconds` | 30000ms | 判定 SDOWN 的超时时间 | 网络好：3000-5000ms；网络差：10000ms |
| `failover-timeout` | 180000ms | 故障转移超时时间 | 至少是 down-after 的 10 倍 |
| `parallel-syncs` | 1 | 同时同步的 Replica 数 | 小型集群设为 1，大型集群可调为 2-3 |
| `quorum` | - | ODOWN 投票阈值 | 建议设为 Sentinel 数量的一半 + 1 |

## 15.4 启动和部署 Sentinel 集群

### 15.4.1 部署架构

```
            Sentinel-1 (26379)
           /                  \
Sentinel-2 (26379) --- Sentinel-3 (26379)
          |                      |
       Master (6379)          Replica-1 (6380)
          |
       Replica-2 (6381)
```

### 15.4.2 启动命令

```bash
# 启动三个 Sentinel 节点
redis-sentinel /etc/redis/sentinel-1.conf
redis-sentinel /etc/redis/sentinel-2.conf
redis-sentinel /etc/redis/sentinel-3.conf

# 或者使用 redis-server 加 --sentinel 参数
redis-server /etc/redis/sentinel-1.conf --sentinel
```

### 15.4.3 Sentinel 集群部署清单

- 至少 **3 个 Sentinel 节点**（奇数个，方便投票）
- Sentinel 节点应该分布在不同的物理服务器上
- Sentinel 节点应该和 Redis 节点在同一个局域网内（减少网络延迟的干扰）
- quorum 设置为 `Sentinel数量 / 2 + 1`（比如 3 个 Sentinel，quorum = 2）

## 15.5 Node.js 连接 Sentinel

### 15.5.1 ioredis 的 Sentinel 配置

```js
const Redis = require('ioredis');

// 通过 Sentinel 自动发现 Master
const redis = new Redis({
  sentinels: [
    { host: '192.168.1.10', port: 26379 },
    { host: '192.168.1.11', port: 26379 },
    { host: '192.168.1.12', port: 26379 },
  ],
  name: 'mymaster',           // Sentinel 监控的主节点名称
  password: 'your_password',  // Redis 密码（非 Sentinel 密码）
  sentinelPassword: 'sentinel_password',  // Sentinel 密码（如果有）

  // 连接选项
  connectTimeout: 5000,       // 连接超时
  commandTimeout: 3000,       // 命令超时
  maxRetriesPerRequest: 3,    // 每个命令最大重试次数
  
  // 重连策略
  retryStrategy(times) {
    const delay = Math.min(times * 200, 5000);
    console.log(`[Sentinel] 第 ${times} 次重连，延迟 ${delay}ms`);
    return delay;
  },

  // 重连错误处理
  reconnectOnError(err) {
    const targetError = 'READONLY';
    if (err.message.includes(targetError)) {
      console.log('[Sentinel] 检测到 READONLY 错误，正在重连...');
      return true;
    }
    return false;
  },
});

redis.on('connect', () => {
  console.log('[Sentinel] 已连接到 Master（由 Sentinel 自动发现）');
});

redis.on('error', (err) => {
  console.error('[Sentinel] 连接错误:', err.message);
});

// 正常使用，完全不需要关心当前谁是 Master
(async () => {
  await redis.set('hello', 'sentinel');
  const val = await redis.get('hello');
  console.log('读取结果:', val);  // sentinel
  
  redis.disconnect();
})();
```

### 15.5.2 故障转移事件监听

```js
const Redis = require('ioredis');

const redis = new Redis({
  sentinels: [
    { host: '192.168.1.10', port: 26379 },
    { host: '192.168.1.11', port: 26379 },
    { host: '192.168.1.12', port: 26379 },
  ],
  name: 'mymaster',
});

// 监听各种 Sentinel 事件
redis.on('+sentinel', (type, name, address) => {
  console.log(`[事件] 新的 Sentinel 加入: ${address}`);
});

redis.on('+slave', (type, name, address) => {
  console.log(`[事件] 新的 Replica 加入: ${address}`);
});

redis.on('+sdown', (type, name, address) => {
  console.log(`[事件] 节点主观下线: ${type} ${address}`);
});

redis.on('-sdown', (type, name, address) => {
  console.log(`[事件] 节点恢复在线: ${type} ${address}`);
});

redis.on('+odown', (type, name, address) => {
  console.log(`[事件] 节点客观下线: ${type} ${address}`);
});

redis.on('-odown', (type, name, address) => {
  console.log(`[事件] 节点恢复（客观）: ${type} ${address}`);
});

redis.on('+switch-master', (name, previousAddress, newAddress) => {
  console.log(`[事件] Master 切换!`);
  console.log(`  旧 Master: ${previousAddress}`);
  console.log(`  新 Master: ${newAddress}`);
  // ioredis 会自动切换到新 Master，无需手动操作
});

redis.on('+failover-state-reconf-slave', (type, name, address) => {
  console.log(`[事件] 故障转移中: 正在重新配置 Replica ${address}`);
});

redis.on('failover-end', () => {
  console.log(`[事件] 故障转移完成`);
});

// 保持连接，监听事件
console.log('正在监听 Sentinel 事件...');
```

### 15.5.3 Sentinel 模式下的读写分离

```js
const Redis = require('ioredis');

// 连接 Master（写操作）
const master = new Redis({
  sentinels: [
    { host: '192.168.1.10', port: 26379 },
    { host: '192.168.1.11', port: 26379 },
    { host: '192.168.1.12', port: 26379 },
  ],
  name: 'mymaster',
  role: 'master',       // 明确指定连接 Master
});

// 连接 Replica（读操作）
const replica = new Redis({
  sentinels: [
    { host: '192.168.1.10', port: 26379 },
    { host: '192.168.1.11', port: 26379 },
    { host: '192.168.1.12', port: 26379 },
  ],
  name: 'mymaster',
  role: 'slave',        // 明确指定连接 Replica
  preferredSlaves: [
    { ip: '192.168.1.101', port: 6380, prio: 1 },
    { ip: '192.168.1.102', port: 6380, prio: 2 },
  ],
});

class SentinelService {
  constructor(master, replica) {
    this.master = master;
    this.replica = replica;
  }

  async set(key, value, options = {}) {
    if (options.ex) {
      return this.master.set(key, value, 'EX', options.ex);
    }
    return this.master.set(key, value);
  }

  async get(key) {
    return this.replica.get(key);
  }

  async getStrong(key) {
    return this.master.get(key);
  }

  async writeAndRead(key, value) {
    await this.master.set(key, value);
    const numReplicas = await this.master.wait(1, 3000);
    console.log(`数据已同步到 ${numReplicas} 个 Replica`);
    return this.master.get(key);
  }
}

const service = new SentinelService(master, replica);

(async () => {
  await service.set('user:1', JSON.stringify({ name: '张三' }));
  const user = await service.get('user:1');
  console.log(user);
  
  service.master.disconnect();
  service.replica.disconnect();
})();
```

## 15.6 Sentinel 的最佳实践

### 15.6.1 脑裂问题

脑裂（Split-Brain）是 Sentinel 最棘手的问题：

```
网络分区发生：

[Sentinel-1] [Sentinel-2]    |    [Sentinel-3]
[Master]                      |    [Replica-1]
                              |
                      网络分区（防火墙/交换机故障）

Sentinel-1 和 Sentinel-2 认为 Master 正常
Sentinel-3 认为 Master 挂了，选举 Replica-1 为新 Master

结果：两个 Master 同时接受写操作 -> 数据冲突！
```

**解决方案**：在 Master 上配置最小 Replica 要求

```bash
# redis-master.conf
# 当可用 Replica 少于 1 个时，Master 拒绝写操作
min-replicas-to-write 1

# Replica 的最大复制延迟（秒），超过这个值不算"可用"
min-replicas-max-lag 10
```

这样，当网络分区发生时，少数派分区的 Master 因为没有足够的 Replica 而自动停止接受写操作，避免了脑裂。

> [!TIP] 提示
> ：`min-replicas-to-write` 的值不要设太大。如果你有 2 个 Replica，设为 1 就足够了。设为 2 的话，任何一个 Replica 出问题都会导致 Master 拒绝写入。

### 15.6.2 监控和告警

```js
const Redis = require('ioredis');

// 直接连接 Sentinel 获取监控信息
const sentinel = new Redis({ host: '192.168.1.10', port: 26379 });

async function getSentinelStatus() {
  const masters = await sentinel.call('sentinel', 'masters');
  console.log('=== 被监控的 Master ===');
  console.log(masters);

  const masterInfo = await sentinel.call('sentinel', 'master', 'mymaster');
  console.log('\n=== Master 详细信息 ===');
  console.log(masterInfo);

  const replicas = await sentinel.call('sentinel', 'slaves', 'mymaster');
  console.log('\n=== Replica 列表 ===');
  console.log(replicas);

  const sentinels = await sentinel.call('sentinel', 'sentinels', 'mymaster');
  console.log('\n=== Sentinel 列表 ===');
  console.log(sentinels);

  sentinel.disconnect();
}

getSentinelStatus();
```

### 15.6.3 Sentinel 部署 Checklist

- [ ] Sentinel 节点数量为奇数（推荐 3 或 5）

- [ ] `down-after-milliseconds` 根据网络质量调整
- [ ] Master 配置了 `min-replicas-to-write`

## 小结

Sentinel 是 Redis 的"自动运维管家"，它解决了主从复制最大的痛点——Master 故障时的自动故障转移。

核心机制：

- **SDOWN**：单个 Sentinel 的主观判断，"我觉得你挂了"
- **ODOWN**：多个 Sentinel 的共识判断，"我们都觉得你挂了"
- **Leader 选举**：选出一个 Sentinel 来执行故障转移
- **自动切换**：选出新 Master，更新所有 Replica 和客户端

就像 Kubernetes 的 Controller 一样，Sentinel 持续监控系统的状态，当实际状态偏离期望状态时，自动执行修复操作。

## 练习题

1. **基础题**：搭建一个 3 Sentinel + 1 Master + 2 Replica 的环境，手动停止 Master，观察故障转移过程。
2. **进阶题**：编写一个 Node.js 脚本，在故障转移期间持续执行读写操作，记录每次操作的延迟和成功率。
3. **挑战题**：模拟网络分区（使用 iptables 或 tc），验证脑裂问题的发生和 `min-replicas-to-write` 的防护效果。
