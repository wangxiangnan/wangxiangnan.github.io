# 第16章：智能指针

## 场景引入

在 Python 或 Java 中，你几乎不用操心内存——垃圾回收器（GC）帮你打理一切。在 C++ 中，你需要 `new`/`delete` 手动管理，或者用 `unique_ptr`、`shared_ptr` 这些智能指针来半自动化。

Rust 没有 GC，也没有手动 `delete`，那它靠什么？答案是：**所有权系统 + 智能指针**。智能指针是拥有额外元数据和能力的数据结构，它不仅存储数据的地址，还负责数据的分配和释放。你可以把它理解为"自带管家的引用"——它帮你记住该什么时候打扫房间。

你可能会问：Rust 不是已经有引用（`&T` 和 `&mut T`）了吗？引用和智能指针有什么区别？关键区别在于：**普通引用只是借用，不拥有数据；智能指针拥有数据，并在离开作用域时自动清理。** 类比来说，引用就像"借朋友的相机拍照"——用完还回去；智能指针就像"你自己买的相机"——你负责保管，搬家时带走，不要了扔掉。

本章我们将学习四种核心智能指针：`Box<T>`（独占堆内存）、`Rc<T>`（共享所有权）、`RefCell<T>`（内部可变性）、以及 `Arc<T>`（线程安全的共享所有权）。

## 16.1 Box\<T\>：堆上分配

`Box<T>` 是最简单的智能指针，它把数据放在**堆（heap）**上，而栈上只保留一个指向堆的指针。在 C++ 中，这类似 `std::unique_ptr`——独占所有权，不可复制，只能移动。在 Java 中，几乎所有对象都在堆上，你不需要显式选择。但在 Rust 中，数据默认在栈上（和 C/C++ 一样），你需要用 `Box` 显式地把它放到堆上。

**栈 vs 堆，为什么要关心？** 栈上的数据大小必须在编译时确定，而且栈空间有限（通常几 MB）。堆上的数据大小可以动态变化，空间也更大。当你处理大数据或大小不确定的数据时，就需要 `Box`。

**什么时候用 `Box<T>`？**

- 编译时大小不确定的类型（如递归类型）
- 数据量大且你希望移动时只复制指针（而非整个数据）
- 你只关心某个值是否实现了某个 trait（trait 对象）

```rust
fn main() {
    // 在堆上分配一个 i32
    let boxed_value = Box::new(42);
    println!("堆上的值: {}", boxed_value); // 自动解引用

    // 移动 Box 时，堆上的数据跟着走——不会复制整个数据
    let moved_box = boxed_value;
    println!("移动后: {}", moved_box);
    // println!("{}", boxed_value); // 编译错误：所有权已转移
}
```

**递归类型的经典问题与 Box 的解法**：

```rust
// 这段代码无法编译！因为编译器无法确定 Cons 的大小
// enum List {
//     Cons(i32, List),  // List 包含 List，无限嵌套，大小不确定
//     Nil,
// }

// 使用 Box 打破无限递归——Box 在栈上只有指针大小（8字节），指向堆上的数据
enum List {
    Cons(i32, Box<List>),
    Nil,
}

use List::{Cons, Nil};

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));

    // 遍历链表
    fn print_list(list: &List) {
        match list {
            Cons(val, next) => {
                print!("{} -> ", val);
                print_list(next);
            }
            Nil => println!("Nil"),
        }
    }

    print_list(&list);
    // 输出: 1 -> 2 -> 3 -> Nil
}
```

## 16.2 Deref Trait 与解引用强制转换

`Deref` trait 让你自定义 `*` 运算符的行为。更重要的是，Rust 有**解引用强制转换（Deref Coercion）**——自动把 `&Box<T>` 转换成 `&T`。

这个特性看起来不起眼，但它极大提升了代码的"人体工学"。想象一下，如果没有 Deref 强制转换，每次使用 `Box<String>` 时你都得手动写 `&*my_box` 来获取字符串引用——代码会变得非常丑陋。Deref 强制转换让你在使用智能指针时感觉就像在使用普通引用一样自然。

**Deref 强制转换链**的工作原理：编译器在编译时会反复调用 `deref()` 方法，直到找到匹配的类型。比如 `&Box<String>` 可以经过两步转换变成 `&str`：

1. `&Box<String>` → 调用 `Box::deref()` → `&String`
2. `&String` → 调用 `String::deref()` → `&str`

这就是为什么你可以把 `&Box<String>` 传给一个接受 `&str` 参数的函数，编译器会自动帮你完成转换。

```rust
use std::ops::Deref;

// 自己实现一个智能指针
struct MyBox<T>(T);

impl<T> MyBox<T> {
    fn new(x: T) -> MyBox<T> {
        MyBox(x)
    }
}

// 实现 Deref trait
impl<T> Deref for MyBox<T> {
    type Target = T; // 关联类型：解引用后的目标类型

    fn deref(&self) -> &Self::Target {
        &self.0 // 返回内部数据的引用
    }
}

fn greet(name: &str) {
    println!("Hello, {}!", name);
}

fn main() {
    let boxed_name = MyBox::new(String::from("Rust"));

    // Deref 强制转换链：
    // &MyBox<String> -> &String -> &str
    greet(&boxed_name); // 自动完成了两步转换！

    // 手动解引用
    let value = *boxed_name; // 等价于 *(boxed_name.deref())
    println!("值: {}", value);
}
```

**Deref 强制转换链的威力**：Rust 编译器会自动进行多步转换，比如 `&Box<String>` → `&String` → `&str`。这让你写代码时不用反复手动解引用，用起来和 Python 的"鸭子类型"一样自然。

## 16.3 Drop Trait 与资源清理

`Drop` trait 定义了值离开作用域时的行为——就像 Java 的 `finalize()` 方法，但更可靠（因为 Rust 保证一定会调用）。这个概念来自 C++ 的 **RAII（Resource Acquisition Is Initialization）**模式——资源的生命周期与对象的生命周期绑定。

RAII 是 Rust 资源管理的基石。文件句柄、网络连接、数据库连接、互斥锁……所有需要在某个时刻"清理"的资源，都通过 `Drop` trait 来自动管理。你不需要写 `try-finally`，不需要记着关闭资源——当变量离开作用域时，`drop()` 自动被调用。

和 Java 的 `finalize()` 不同，Rust 的 `drop()` 是**确定性的**——它总是在变量离开作用域的那一刻被调用，而不是等到 GC 运行时的某个不确定时刻。这意味着你可以依赖 `drop()` 来及时释放资源。

```rust
struct CustomSmartPointer {
    data: String,
}

impl Drop for CustomSmartPointer {
    fn drop(&mut self) {
        println!("正在清理: {}", self.data);
        // 这里可以释放文件句柄、网络连接、数据库连接等
    }
}

fn main() {
    let a = CustomSmartPointer { data: String::from("第一个") };
    let b = CustomSmartPointer { data: String::from("第二个") };

    println!("程序即将结束");
    // drop 按照创建的反序调用：先 b 后 a
    // 输出顺序：
    // 程序即将结束
    // 正在清理: 第二个
    // 正在清理: 第一个
}
```

**提前释放**：有时候你想在值离开作用域前就释放它（比如提前关闭文件）：

```rust
fn main() {
    let c = CustomSmartPointer { data: String::from("提前释放") };
    // c.drop(); // 编译错误！不允许显式调用 drop 方法
    drop(c);    // 正确做法：使用 std::mem::drop 函数
    println!("c 已经被释放了");
}
```

## 16.4 Rc\<T\>：引用计数（单线程共享所有权）

大多数情况下，所有权是明确的——一个值只有一个主人。但有时候，一个数据需要被多个地方"共享"。比如在图结构中，一个节点可能被多条边引用；又比如 GUI 编程中，一个按钮可能同时被工具栏和菜单栏引用。

`Rc<T>`（Reference Counted，引用计数）就是为这种场景设计的，类似 Python 的对象引用计数机制。在 Python 中，当你写 `a = [1,2,3]; b = a` 时，`a` 和 `b` 共享同一个列表对象，Python 用引用计数来追踪有多少个变量指向它——当计数归零时自动回收。`Rc<T>` 做了同样的事情，但是显式的、可控的。

**与 `Box<T>` 的关键区别**：`Box<T>` 是独占所有权（一份数据只有一个主人），`Rc<T>` 是共享所有权（一份数据可以有多个主人）。`Box` 像你的私人笔记本，`Rc` 像图书馆的书——多个人可以"借阅"，但没人能修改它。

```rust
use std::rc::Rc;

fn main() {
    // 创建一个 Rc，初始引用计数为 1
    let shared_data = Rc::new(String::from("共享数据"));
    println!("引用计数: {}", Rc::strong_count(&shared_data)); // 1

    {
        // Rc::clone 只复制指针（浅拷贝），不复制数据
        let clone1 = Rc::clone(&shared_data);
        println!("引用计数: {}", Rc::strong_count(&shared_data)); // 2

        {
            let clone2 = Rc::clone(&shared_data);
            println!("引用计数: {}", Rc::strong_count(&shared_data)); // 3
            println!("clone2 读到: {}", clone2);
        }
        // clone2 离开作用域，引用计数 -1
        println!("引用计数: {}", Rc::strong_count(&shared_data)); // 2
    }
    // clone1 离开作用域，引用计数 -1
    println!("引用计数: {}", Rc::strong_count(&shared_data)); // 1

    // shared_data 离开作用域，引用计数归零，数据被释放
}
```

**重要限制**：`Rc<T>` 只能提供**不可变引用**。如果你想通过 `Rc` 修改数据，编译器会毫不留情地拒绝你。想修改？请翻到下一节 `RefCell<T>`。

## 16.5 RefCell\<T\> 与内部可变性

`RefCell<T>` 实现了一种叫**内部可变性（Interior Mutability）**的模式——它允许你在持有不可变引用时修改数据。听起来违反 Rust 的核心规则？没错，它确实"绕过了"编译期检查，但代价是把检查推迟到了**运行时**。

类比：编译期借用检查就像"上班打卡"——迟到就报警。而 `RefCell` 是"弹性工作制"——不查打卡，但你自己得保证不冲突，否则运行时 panic。

**为什么需要这种"不安全"的东西？** 因为有些场景下，从外部看数据是不可变的（比如一个配置管理器只暴露 `&self` 方法），但内部确实需要修改状态（比如缓存命中次数）。在 Java/Python 中这很自然——你随时可以修改对象内部状态。但在 Rust 中，你需要 `RefCell` 来明确表达"我知道我在做什么"。

`RefCell` 的运行时规则很简单：

- 你可以在任意时刻拥有**多个不可变借用**（`borrow()`）
- 或者在任意时刻拥有**一个可变借用**（`borrow_mut()`）
- 两者不能同时存在，违反就会 panic（整个程序崩溃）

```rust
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(vec![1, 2, 3]);

    // 不可变借用（可以多次）
    let borrowed = data.borrow();
    println!("读取: {:?}", borrowed);
    drop(borrowed); // 必须释放，否则后续可变借用会 panic

    // 可变借用（同时只能有一次）
    let mut borrowed_mut = data.borrow_mut();
    borrowed_mut.push(4);
    println!("修改后: {:?}", borrowed_mut);
    drop(borrowed_mut);

    // 再次不可变借用
    println!("最终: {:?}", data.borrow());

    // 运行时违规：同时有不可变借用和可变借用
    let _r1 = data.borrow();
    // let _r2 = data.borrow_mut(); // 运行时 panic！违反了借用规则
}
```

## 16.6 Rc\<T\> + RefCell\<T\> 的组合拳

`Rc<T>` 给你共享所有权（但只读），`RefCell<T>` 给你内部可变性（但单所有者）。组合起来，你就得到了**多所有者 + 可变**的数据结构——这是 Rust 中最强大的组合之一。

为什么需要这个组合？因为在真实项目中，经常有这样的需求：多个组件需要共享同一份数据，而且还要能修改它。比如 GUI 中的共享配置、游戏中的共享状态、文档系统中的共享节点。在 Java 中这很自然——对象默认就是共享且可变的。但在 Rust 中，你需要显式地组合 `Rc` 和 `RefCell` 来表达这个意图，这种"显式优于隐式"的设计让你清楚地知道哪些数据是共享可变的——这恰恰是最容易出 bug 的地方。

**一个重要的心智模型**：`Rc<RefCell<T>>` 等价于 Java/Python 中的普通对象引用——多个变量指向同一个可变对象。区别在于，Rust 会在运行时检查借用规则，而 Java/Python 则完全不检查。

```rust
use std::rc::Rc;
use std::cell::RefCell;

#[derive(Debug)]
struct Node {
    value: i32,
    children: RefCell<Vec<Rc<Node>>>, // 可变的孩子列表
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    let root = Rc::new(Node {
        value: 10,
        children: RefCell::new(vec![Rc::clone(&branch)]),
    });

    // 动态添加子节点
    root.children.borrow_mut().push(Rc::new(Node {
        value: 7,
        children: RefCell::new(vec![]),
    }));

    println!("根节点值: {}", root.value);
    println!("孩子数量: {}", root.children.borrow().len()); // 2
    println!("第一个孩子值: {}", root.children.borrow()[0].value); // 5
}
```

## 16.7 循环引用与 Weak\<T\>

`Rc<T>` 有一个致命弱点——**循环引用会导致内存泄漏**。就像两个 Python 对象互相引用，如果没有 GC 的循环检测，它们的引用计数永远不会归零，数据永远不会被释放。

举个具体的例子：假设节点 A 引用节点 B，节点 B 也引用节点 A。A 的引用计数至少为1（因为 B 持有它），B 的引用计数也至少为1（因为 A 持有它）。即使外部的所有引用都消失了，A 和 B 仍然互相"牵着"，永远不会被释放。这就是内存泄漏。

`Weak<T>` 是解决方案——它不增加强引用计数，因此不会阻止数据被释放。访问 `Weak` 指向的数据时，需要先调用 `upgrade()` 方法，它返回 `Option<Rc<T>>`——如果数据还在就返回 `Some`，如果已经被释放就返回 `None`。这个设计非常优雅：它既允许你持有"弱引用"来打破循环，又通过 `Option` 让你显式处理"数据可能已不存在"的情况。

**经验法则**：在树形结构中，父节点用 `Rc`（强引用）持有子节点，子节点用 `Weak`（弱引用）指向父节点。因为父节点的生命周期应该包含子节点——父节点消失时，子节点也应该消失。

```rust
use std::rc::{Rc, Weak};
use std::cell::RefCell;

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,    // 弱引用指向父节点（不增加引用计数）
    children: RefCell<Vec<Rc<Node>>>, // 强引用指向子节点
}

fn main() {
    let leaf = Rc::new(Node {
        value: 3,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![]),
    });

    let branch = Rc::new(Node {
        value: 5,
        parent: RefCell::new(Weak::new()),
        children: RefCell::new(vec![Rc::clone(&leaf)]),
    });

    // 建立 leaf -> branch 的父节点引用（弱引用）
    *leaf.parent.borrow_mut() = Rc::downgrade(&branch);

    // 访问父节点需要先 upgrade()——如果数据已被释放，返回 None
    if let Some(parent) = leaf.parent.borrow().upgrade() {
        println!("leaf 的父节点值: {}", parent.value); // 5
    }

    println!("leaf 强引用计数: {}", Rc::strong_count(&leaf));   // 2
    println!("leaf 弱引用计数: {}", Rc::weak_count(&leaf));     // 0
    println!("branch 强引用计数: {}", Rc::strong_count(&branch)); // 1
    println!("branch 弱引用计数: {}", Rc::weak_count(&branch)); // 1（leaf 持有弱引用）
}
```

## 16.8 Arc\<T\> 简介

`Rc<T>` 不是线程安全的——如果多个线程同时修改引用计数，可能产生数据竞争。`Arc<T>`（Atomic Reference Counted）使用原子操作来保证线程安全，代价是轻微的性能开销。

你可以这样记：**Rc = Reference Counted**（单线程），**Arc = Atomic Reference Counted**（多线程）。就像 `Cell` 和 `AtomicCell` 的区别一样，带 "Atomic" 前缀的就是线程安全版本。

什么时候用 `Rc`，什么时候用 `Arc`？简单规则：**如果你的数据只在单线程中使用，用 `Rc`（更快）；如果需要跨线程共享，用 `Arc`。** 编译器也会帮你检查——如果你在多线程中误用了 `Rc`，它会直接拒绝编译。

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let shared = Arc::new(vec![1, 2, 3, 4, 5]);
    let mut handles = vec![];

    for i in 0..3 {
        let data = Arc::clone(&shared);
        let handle = thread::spawn(move || {
            let sum: i32 = data.iter().sum();
            println!("线程 {} 计算的和: {}", i, sum);
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }
}
```

## 常见陷阱

1. **`Rc<T>` 不能跨线程**：在多线程中使用 `Rc<T>` 会直接编译失败。跨线程请用 `Arc<T>`。编译器会给你一个清晰的错误信息："`Rc<T>` cannot be sent between threads safely"，然后建议你使用 `Arc<T>`。

2. **`RefCell<T>` 的运行时 panic**：同时有多个 `borrow()` 和 `borrow_mut()` 会在运行时 panic。建议在小范围内持有借用并尽快 `drop`。一个实用的技巧是：把 `borrow()` 的结果放在一个小作用域 `{}` 中，确保它在使用完后立即被释放。

3. **循环引用**：使用 `Rc<T>` 构建图/树时，一定要用 `Weak<T>` 来打破循环，否则内存永远不会释放。记住：强引用形成环 = 内存泄漏。设计数据结构时问自己："如果所有强引用都断了，数据能被释放吗？"

4. **Box 的不必要使用**：新手往往过度使用 `Box<T>`。在大多数情况下，Rust 的栈分配已经足够高效。只有当你确实需要堆分配（递归类型、大数据移动优化、trait 对象）时才使用 `Box`。不要像 Java 那样"什么都放在堆上"。

## 小结

| 智能指针 | 用途 | 线程安全 | 可变性 |
| ---------- | ------ | ---------- | -------- |
| `Box<T>` | 堆分配、递归类型 | 是（单所有者） | 可变（通过 `&mut`） |
| `Rc<T>` | 共享所有权（单线程） | 否 | 不可变 |
| `RefCell<T>` | 内部可变性 | 是（单线程） | 运行时检查 |
| `Arc<T>` | 共享所有权（多线程） | 是 | 不可变 |
| `Weak<T>` | 打破循环引用 | — | 不可变 |
