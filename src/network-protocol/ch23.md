## 23.1 CDN 的工作原理：把内容搬到用户身边

CDN（Content Delivery Network）的核心思想很简单：**把内容搬到离用户最近的地方**。没有 CDN 时，北京用户访问 `cdn.example.com/video.mp4` 要跨洋 200ms+；有 CDN，请求被导向北京边缘节点，10ms 级。

工作流程：

1. 用户请求 `cdn.example.com/image.jpg`。
2. DNS 解析返回最近的边缘节点 IP（如北京 `1.2.3.4`）——怎么返回的，23.2 揭晓。
3. 边缘节点查缓存：命中直接返回；未命中则**回源**（向源服务器请求）。
4. 回源内容缓存到边缘，再返回给用户——下次就是命中。

CDN 的缓存学问是 14.1/14.2 的放大版：**TTL** 决定边缘缓存时长；**Cache-Control** 指令全盘遵守；**缓存键（Cache Key）**通常是「URL + 部分请求头」的组合——14.3 的 `Vary` 在这里变得生死攸关：`Vary: Accept-Encoding` 少配一个，gzip 响应就可能发给不支持压缩的客户端并被错误缓存；**缓存预热**则把热门内容提前推到边缘，绕开首波回源。

## 23.2 DNS 调度：把你引到最近的节点

CDN 借用 DNS 的解析过程做地理调度——16.3 的迭代查询在这里被「征用」：

```
用户（北京） → 本地 DNS → CDN 的权威 DNS
                                ↓
                     根据请求来源 IP 判断地理位置
                                ↓
                     返回北京边缘节点 IP: 1.2.3.4

用户（上海） → 本地 DNS → CDN 的权威 DNS
                                ↓
                     返回上海边缘节点 IP: 5.6.7.8
```

「先猜再读」第一问的答案：是 CDN 的权威 DNS——16.3 里「TLD 指路」的角色，在这里按来源 IP 精确指路。

但有个先天缺陷：它看到的是 **DNS 服务器**的位置，不是用户的真实位置。北京用户如果用 Google DNS（8.8.8.8，Anycast 出口在美国），CDN 可能把 TA 导向美国节点。补救方案是 **EDNS Client Subnet**：DNS 请求携带用户子网信息，让权威 DNS 看到真实的「你在哪」。16.5 的 TTL 权衡在此同样适用：调度结果的 TTL 太长，用户搬家后仍被导向旧节点。

## 23.3 Anycast：一个 IP，多地开花

Anycast 是 IP 层的「魔法」：**多个地理位置的服务器宣告同一个 IP**，BGP 路由自动把流量导向「最近」的那个：

```
北京服务器宣告: 203.0.113.1/32
上海服务器宣告: 203.0.113.1/32
广州服务器宣告: 203.0.113.1/32

北京用户请求 203.0.113.1 → 路由到北京节点
上海用户请求 203.0.113.1 → 路由到上海节点
```

「先猜再读」第二问的答案：故障转移是自动的——一个节点挂了，它宣告的路由从 BGP 表中消失，流量自动切到其余节点，用户甚至无感。

Anycast 三大优势：无需 DNS 调度（IP 层自动就近）；天然抗 DDoS（22.1 的洪水被摊到全球节点）；故障自愈。Cloudflare、Google DNS（8.8.8.8）都重度使用。

> [!TIP] 用 ping 亲眼观察 Anycast
> `ping 8.8.8.8` 的延迟基本是你到「最近的 Google 节点」的延迟——这个地址在全球数百个位置同时存在。换一个非 Anycast 的固定 IP 对比延迟，就能直观感受「就近」的威力；若你在 5.4 做过 MTU 实验时发现 8.8.8.8 特别快，现在知道为什么了。

## 23.4 BGP：自治系统间的路由语言

互联网的骨架不是某一家公司的网络，而是数万个**自治系统（AS）**互联而成——中国电信 AS4134、Google AS15169……每个 AS 独立管理内部路由（OSPF 等内部协议的事，不展开），AS 之间靠 **BGP（Border Gateway Protocol）**交换路由。

BGP 的核心概念：

- **AS Path**：到达目标网络要经过的 AS 序列，如 `AS100 → AS200 → AS300`。
- **路由策略**：每个 AS 自主决定接受、拒绝、修改、优选哪些路由。
- **Peering 关系**：Transit（付费转接）与 Peering（免费互换）两种互联模式。

BGP 是**路径矢量协议**，路由决策受商业关系支配——「技术上最优」的路径未必被采用，因为绕道要付更多转接费。这决定了 BGP 的心智模型：它不只是技术协议，还是数万家公司之间持续谈判的产物。

## 23.5 BGP 劫持与防御

BGP 的设计基于**信任**：某个 AS 宣告「我能到达某前缀」，其他 AS 默认相信。于是有了 **BGP 劫持**——2018 年，某 AS 错误宣告了 Google 的 `216.58.192.0/19` 前缀，大量 Google 流量被引向错误网络。

防御手段：

- **RPKI**：用密码学证明「某 AS 有权宣告某前缀」——类比 16.6 的 DNSSEC 之于 DNS，同一招「给宣告加签名」。
- **BGPsec**：对路由更新逐跳签名，防伪造。

与 22 章的威胁模型对齐：BGP 劫持是「冒充」威胁在路由层的版本——不冒充服务器，冒充「通往服务器的路」。

## 23.6 负载均衡：L4、L7 与一致性哈希

流量大到单机扛不住，就需要负载均衡器分发：

**L4（传输层）**：只看 IP 和端口（12.4 的五元组），按源 IP 哈希或轮询分配连接。不解析内容，性能极高——每秒百万级连接没问题；但看不懂 URL，做不了智能分发。

**L7（应用层）**：理解 HTTP，可按 URL 路径、Cookie、Header 分发，支持 A/B 测试、灰度发布；代价是解析开销。

```
用户请求 → L4 负载均衡器（快速分发到集群）
         → L7 负载均衡器（智能路由到具体服务）
         → 应用服务器
```

L4 在前扛量、L7 在后做策略，是大规模架构的标准分工。

**一致性哈希**是横向扩容的经典算法：把服务器和键都映射到一个环上，每台服务器负责环上的一段。增删一台服务器时只有相邻段的 `1/N` 数据需要迁移——对比普通哈希「全量重排」天壤之别。CDN 的节点选择、分布式缓存分片都靠它。

## 23.7 反向代理：网关的真身

「先猜再读」第三问的答案：13.4 说的 502 Bad Gateway 里那个「网关」，就是**反向代理**。先分清两个方向：

- **正向代理**：客户端知道代理存在，通过它访问目标（企业出口、SSH 的 -D，见 18.4）。
- **反向代理**：客户端不知道代理存在，以为在直连目标服务器——Nginx 是典型。

Nginx 的工作流：

```
用户 → Nginx（反向代理）→ App Server 1
                        → App Server 2
                        → App Server 3

Nginx 做的四件事：
1. 接收用户请求（终结 TLS——证书装在它这里）
2. 按 URL 路径决定转发到哪个后端
3. 转发请求、接收响应
4. 给响应加缓存、压缩、安全头部后返回
```

502 与 504 的区别由此清晰：502 = Nginx 从上游收到了**无效响应**（后端崩了或答非所问）；504 = Nginx 等**上游超时**（后端活着但太慢）。都是网关替后端「背锅」——错误码的第一位是 5，因为报错的是网关自己。18 章的 SMTP「网关」、21 章的 API Gateway，与这里的是同一族角色。

## 23.8 编程实践：Python 实现简易反向代理

```python
"""
简易反向代理：按请求路径分发到不同后端
运行: python reverse_proxy.py
测试: curl http://localhost:8080/api/users
"""
import asyncio
from aiohttp import web, ClientSession

BACKENDS = {
    "/api/users": "http://localhost:3001",
    "/api/orders": "http://localhost:3002",
    "/static": "http://localhost:3003",
}

async def proxy_handler(request: web.Request) -> web.Response:
    """将请求转发到对应的后端服务"""
    path = request.path

    backend_url = None
    for prefix, url in BACKENDS.items():
        if path.startswith(prefix):
            backend_url = url
            break

    if not backend_url:
        return web.Response(status=404, text="No backend found for this path")

    target_url = f"{backend_url}{path}"
    headers = {k: v for k, v in request.headers.items()
               if k.lower() not in ('host', 'content-length')}

    async with ClientSession() as session:
        try:
            async with session.request(
                method=request.method,
                url=target_url,
                headers=headers,
                data=await request.read(),
                allow_redirects=False,
            ) as resp:
                body = await resp.read()
                response = web.Response(
                    status=resp.status,
                    body=body,
                    headers={k: v for k, v in resp.headers.items()
                             if k.lower() not in ('transfer-encoding',)},
                )
                # 代理标识头部——排障时用于确认「谁处理了请求」
                response.headers['X-Proxy'] = 'MiniProxy/1.0'
                response.headers['X-Backend'] = backend_url
                return response
        except Exception as e:
            # 后端无响应/异常——这正是 502 Bad Gateway 的诞生地
            return web.Response(status=502, text=f"Backend error: {e}")

app = web.Application()
app.router.add_route('*', '/{path_info:.*}', proxy_handler)

if __name__ == '__main__':
    print("Reverse proxy running on http://localhost:8080")
    web.run_app(app, host='0.0.0.0', port=8080)
```

亲手触发的 502 比背定义管用：把某个后端进程杀掉再请求对应路径，你亲手制造了一次 `502 Bad Gateway`。试试再加一条规则：把 `/static` 的响应缓存 60 秒（内存字典即可），就得到了一个带缓存的迷你 CDN 节点——23.1 的流程闭环。

## 23.9 抓包实践：追踪 CDN 路径

```bash
# 观察 CDN 响应头部
curl -sI https://www.cloudflare.com/cdn-cgi/trace
curl -sI https://cdnjs.cloudflare.com/ajax/libs/jquery/3.6.0/jquery.min.js
```

典型的 CDN 响应头：

```
cf-cache-status: HIT           ← 缓存命中
cf-ray: 7a3b2c1d-FRA          ← 处理请求的边缘节点标识
server: cloudflare             ← CDN 提供商
x-cache: Hit from cloudfront   ← AWS CloudFront 的缓存状态
via: 1.1 varnish               ← 经过的代理/CDN 节点链
age: 342                       ← 缓存副本已存在 342 秒
```

`cf-ray` 的 `-FRA` 表示请求被法兰克福节点处理，`-LAX` 表示洛杉矶——你的请求实际被哪个节点服务，响应头会「招供」。多试几个地区的网络（手机热点 vs 家里宽带），观察 `cf-ray` 与 `age` 的变化，配合 23.2 的 DNS 调度知识，整个「引路-缓存-回源」链条就亲眼可见了。

## 本章小结

- CDN 的本质是缓存的地理前置：边缘命中省一整个 RTT，未命中回源——14 章的缓存机制全球放大。
- DNS 调度寄生在 16.3 的解析过程上；它看到的是 DNS 服务器位置，EDNS Client Subnet 补上真实用户位置。
- Anycast 一个 IP 全球开花：BGP 自动就近选路、故障自愈、天然摊薄 DDoS。
- BGP 是商业协议：路由决策受 Peering 关系与转接费支配，不是纯技术最短路径。
- BGP 劫持是路由层的「冒充」，RPKI 之于 BGP 如 DNSSEC 之于 DNS——「给宣告加签名」一招通用。
- 负载均衡两层分工：L4 看五元组扛量，L7 看语义做策略；一致性哈希让扩容只迁 1/N。
- 反向代理是 502/504 的真身：终结 TLS、按路径分发、加缓存与安全头——502 是上游答错，504 是上游太慢。
- `cf-ray`/`age`/`via` 这些响应头是 CDN 路径的「招供」——排障第一步先看它们。
