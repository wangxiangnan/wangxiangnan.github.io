### 注意事项/补充知识

#### 使用Git Bash时

1. MSYS_NO_PATHCONV=1：在 Git Bash 下运行 Docker 挂载或含有路径命令时，这个前缀是“护身符”，专门防止 Git Bash 把 /app 这种路径错误地转换成 Windows 格式。
2. "$PWD"（大写且带引号）：正确获取当前 Windows 目录，并防止路径中的空格导致报错。
3. -w /app：将容器的工作目录切换到挂载点，这样 go run 就能直接找到 main.go。

#### 微服务是什么？和docker的关系

##### 微服务是“架构思想”（软件该怎么设计），Docker是“实现工具”（软件该怎么打包和运行）。它们不是同类事物，而是“设计蓝图”与“施工机械”的关系

为了让你彻底理清，我从三个维度拆解：

###### 1. 微服务是什么？（一种“分而治之”的组织形式）

想象一家大型综合医院（单体应用）：所有科室（挂号、药房、住院、化验）都在同一栋楼里，共用同一个挂号系统和同一个数据库。一旦药房系统崩溃，整栋楼可能都得停摆。

微服务就是把这栋楼拆成几十个独立的小诊所：

挂号诊所、药房诊所、化验诊所……各自独立运行。

每个诊所都有自己的独立数据库和编程语言（药房用Java，化验用Python都行）。

它们之间通过规定的网络接口（API/HTTP）互相喊话：“帮我查个血常规”。

核心优势：药房诊所关门装修（升级），挂号诊所依然正常运行，互不影响。

###### 2. Docker 和微服务是什么关系？（“集装箱”与“标准化装卸”）

微服务虽然好，但拆分后带来了巨大的运维噩梦：
以前只运维1个应用，现在要运维100个小应用。每个小应用依赖的底层环境（操作系统版本、JDK版本、库文件）可能都不一样。

Docker 就是解决这个“环境不一致”问题的“标准化集装箱”：

打包一致性：Docker把每个微服务（连同它的代码、运行环境、依赖库）一起打包成一个镜像（Image）。无论这个镜像跑到哪台服务器上，里面的环境都一模一样。

隔离性：每个Docker容器就像一个个独立的小房间，100个微服务跑在同一个物理机上，不会因为端口冲突或依赖库版本不同而“打架”。

###### 3. 它们到底是不是绑定的？（破除误解）

虽然它们经常一起出现，但记住这句话：

微服务 ≠ Docker。在没有Docker的年代，微服务也可以用一堆物理机或虚拟机（VM）来部署，但那样极其笨重（启动慢、占用空间大）。

Docker ≠ 微服务。你也可以用Docker把一个超大的“单体应用”装进去运行，这叫“容器化单体”，但它不是微服务架构。

真正的黄金搭档在于：

微服务的痛点Docker 如何解决
环境不一致（开发跑得通，上线就崩）镜像把环境固化为不可变的文件，一次构建，到处运行。
服务扩缩容慢（流量突增，来不及开新虚拟机）Docker容器秒级启动，配合K8s瞬间拉起10个新副本。
服务器资源利用率低容器比虚拟机轻量得多，一台物理机能跑几十个微服务容器。

###### 4. 一个“物流公司”的终极比喻

微服务 = 你决定把一家“大杂货铺”拆分成“果蔬部”、“日化部”、“食品部”分别独立经营（架构拆分）。

Docker = 你给这三个部门分别配了标准化的标准集装箱。果蔬的冷藏要求、日化的防潮要求，全封在各自的集装箱里，贴上标签（镜像）。

Kubernetes（K8s）（顺带一提）= 码头上的自动化调度塔台，负责指挥这成千上万个集装箱，该装船的装船，该卸货的卸货，坏了自动换新的。
