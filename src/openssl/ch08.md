# 第8章：证书解剖：读懂数字身份证

> [!TIP] Part 2: 非对称与证书篇（进阶篇）
> 上一章的签名体系还吊在一枚手工公示的指纹上，规模一大必然失灵。本章拆开「证书」这个黑盒——浏览器小锁背后那张数字身份证，每个字段都值得亲手读一遍。

第7章结尾留了个问题：指纹公示靠得住，但靠的是「每个用户都愿意来核对」这个不现实的前提。云笔记的答案和全世界的答案一致：**找一个大家都信的第三方，替你盖章**。第三方叫证书颁发机构（CA，Certificate Authority），盖出来的产物叫证书（Certificate）——它把公钥和持有者身份钉在一起，并用 CA 的私钥签名背书。从此用户不需要核对你，只需要信任 CA。本章不急着当 CA（第10章的事），先把证书这张「身份证」上的每一个字段读明白。

王哥对「CA」的第一反应很典型：「不就是一家公司吗，它凭什么可信？」这个问题分两层答：技术上，CA 的可信来自「它的公钥被操作系统/浏览器出厂预装」——这不是 CA 自封的，而是要过 WebTrust 之类审计、被各大浏览器厂商逐家评审后才进预装名单，进错了名单的（比如曾出事故的 WoSign）会被集体除名；运营上，CA 是被严格监管的持牌行业，签发行为全程留痕、接受多方监督。**信任锚从来不是免费的，它是审计、监管与除名机制共同维持的均衡**——这个理解会一路支撑到第10章：我们自己当 CA 时，「审计」就退化成团队内部的核对纪律。而「章」本身的技术构造——CA 拿什么签、签在哪些字节上——就是本章以下内容。

## 8.1 证书是什么：塑封的公钥

四路输入（公钥、身份、有效期、CA 签名）汇成一张卡，浏览器只看卡不看过程——这就是「信任可以被打包」的含义。下一节把卡面拆开逐字段读。

「塑封卡」类比里藏着一个漂亮的递归：CA 之所以可信，是因为操作系统和浏览器**出厂预装**了一批 CA 的证书（信任锚）。你在[《网络协议完全教程》第15章](/network-protocol/ch15)看到过 TLS 握手的协议流程，本章补上其中「证书」那一格的内部构造。证书遵循的国际标准叫 X.509，你见到的一切 HTTPS 证书都是这个格式。

X.509 的版本号也顺手交代：如今流通的都是 **v3**（8.2 输出第一行 `Version: 3`），因为只有 v3 引入了扩展字段；v1/v2 是上世纪九十年代的古董，见到 v1 证书的现代客户端反而会警惕。标准文档是 RFC 5280——本书不要求啃规范，但「遇到字段争议查 RFC 5280」这个坐标值得记下。

> [!TIP] 三处日常可见的证书现场
> 证书不是实验室标本，你每天路过它们三趟：浏览器地址栏小锁 → 证书详情（GUI 版的 `x509 -text`）；macOS 钥匙串访问 / Windows 证书管理器（系统信任库，第11章的主角）；`git clone https://...` 时 Git 背后悄悄验的那张证书。本章读完，这三处的每一行你都能读出含义——顺便试试在你自己的浏览器里找到 example.com 的指纹，和实验结果比对。

## 8.2 读一张真证书

读证书的命令是 `x509`，主力参数 `-text`——把证书全文翻译成人话。手里的 `api.crt` 从哪来不用着急：第9章造自签版、第10章由内部 CA 签发正式版，本章先用「已有的一张」练眼力。云笔记 API 服务器的一张证书（内部 CA 签发），拆开来长这样：

```bash
openssl x509 -in api.crt -noout -text
```

```text
Certificate:
    Data:
        Version: 3 (0x2)
        Serial Number:
            2a:7c:9e:01:33:bb:44:aa
        Signature Algorithm: ecdsa-with-SHA256
        Issuer: C=CN, O=CloudNote, CN=CloudNote Internal CA
        Validity
            Not Before: Nov  6 08:00:00 2026 GMT
            Not After : Feb  4 08:00:00 2027 GMT
        Subject: C=CN, O=CloudNote, CN=api.cloudnote.example
        Subject Public Key Info:
            Public Key Algorithm: id-ecPublicKey
                Public-Key: (256 bit)
                pub:
                    04:b2:8d:...
                ASN1 OID: prime256v1
                NIST CURVE: P-256
        X509v3 extensions:
            X509v3 Subject Alternative Name:
                DNS:api.cloudnote.example
            X509v3 Basic Constraints: critical
                CA:FALSE
            X509v3 Key Usage: critical
                Digital Signature
            X509v3 Extended Key Usage:
                TLS Web Server Authentication
            X509v3 Subject Key Identifier:
                A1:B2:C3:...
    Signature Algorithm: ecdsa-with-SHA256
         30:45:02:21:...
```

第一次读这么长的输出，建议按「三遍法」：第一遍只看 Issuer / Subject / Validity 三行，回答「谁的证、谁发的、到多久」；第二遍看 extensions 里的四条关键扩展；第三遍才轮到算法与指纹细节。输出里两处 `Signature Algorithm` 与末尾十六进制的含义见 8.3 的拆解，SAN 只有一条是因为这张证只服务一个域名。

样例里的 `ASN1 OID: prime256v1` 与 `NIST CURVE: P-256` 是同一根曲线的两种叫法（OID 是标准编号，NIST 名是俗称），第5章选型时写的 P-256 在证书里就落成这行——术语在 8.2 的样例、5.3 的选型表、第9章的签发命令三处来回出现，此刻正是把它们焊在一起的时候。

眼花缭乱是正常的——这张身份证上其实只有六组信息。一个字段速查表先立起来，8.3 逐组细讲：

| 字段组 | 内容 | 回答的问题 |
| ---- | ---- | ---- |
| Serial Number | 序列号 | CA 发的第几号证（撤销时按号作废） |
| Signature Algorithm | 签名算法 | CA 用什么算法盖的章 |
| Issuer | 签发者 | **谁**盖的章 |
| Validity | 有效期 | 章盖在什么时间段 |
| Subject | 持有者 | **给谁**发的证 |
| Subject Public Key Info | 公钥本体 | 塑封卡里的钥匙 |
| X509v3 extensions | 扩展 | 这把钥匙**能干什么、不能干什么** |

同一个字段表配上生活类比，第二遍读就有了抓手：

| 字段 | 塑封卡类比 | 读到什么算正常 |
| ---- | ---- | ---- |
| Issuer | 发卡银行 | 一个明确的机构名，且 Subject 与 Issuer 不同（除根证书） |
| Validity | 卡面有效期 | Not Before 已过、Not After 未到 |
| Subject | 持卡人姓名 | 应包含你要访问的域名 |
| Signature Algorithm | 银行的钢印工艺 | sha256WithRSA 或 ecdsa-with-SHA256 级别，不见 md5/sha1 |
| Serial | 卡号 | 全 CA 范围内唯一，被撤销时按号公告 |

两组信息里各藏一个「身份证件号」级别的细节：**Serial Number 在同一 CA 下必须唯一**——它是撤销公告（CRL，Certificate Revocation List，证书吊销列表）的检索键，「第 4102 号证书作废」全靠号找人，重号会误伤无辜证书。你第10章自建 CA 时 OpenSSL 会用序列号文件自动维护唯一性，理解它的存在即可。

`-noout` 的意思是「别把 PEM 原文打出来了，我要看译文」。日常还有几个更快的快捷参数，各取一个字段就走：

```bash
openssl x509 -in api.crt -noout -subject -issuer -dates
```

```text
subject=C=CN, O=CloudNote, CN=api.cloudnote.example
issuer=C=CN, O=CloudNote, CN=CloudNote Internal CA
notBefore=Nov  6 08:00:00 2026 GMT
notAfter=Feb  4 08:00:00 2027 GMT
```

四行输出就是一张证书的「四要素快查」：发给谁、谁发的、何时生效、何时到期。第12章的到期监控脚本抓的正是第四行；日常核对「这张证书是不是发给我服务的」，看第一、二行就够。这些快捷参数全部可以连用，比如 `-noout -subject -fingerprint -sha256` 一次取「身份 + 指纹」——用熟之后，绝大多数证书疑问在四要素层面就能终结。

## 8.3 核心字段逐个拆

**Issuer 与 Subject：一张卡上的两个名字。** Issuer 是盖章的 CA，Subject 是持卡的域名。两者的关系是理解证书体系的钥匙：普通服务器证书的 Issuer 是 CA、Subject 是你自己；而 CA 自己的证书（第10章要造的根证书）Issuer 和 Subject 是同一个名字——自己给自己盖章，这种「自签」正是信任链的起点。眼熟吗？第9章的自签名证书就是「自己给自己盖章」的最小版本，只不过没人替它背书。

Subject 的完整写法是一串缩写对（DN，Distinguished Name）：`C=CN, O=CloudNote, CN=api.cloudnote.example`——国家、组织、通用名。公网 CA 会核实 O（组织）真实性，所以企业证书卡面上有公司名；内网自建 CA 时这些字段自己填，唯一的硬规则是 **CN 应填域名**（老客户端兼容用）而 SAN 必须精确（现代客户端唯一依据）。字段顺序、大小写在 X.509 里都有定义，但工具链普遍宽容——抄全本章的样例写法即可，别自创格式。

**Validity：90 天的设定从哪来。** 云笔记内部证书定 90 天，公网上 Let's Encrypt 也是 90 天——这不是巧合，而是同一个工程判断：**有效期越短，泄露后的危害窗口越短**，代价是必须自动化续期。早年证书一年一换、忘续费导致全站瘫痪的事故（危机三里云笔记也中过一次招），正是行业把周期从 5 年一路压到 90 天的原因。趋势仍未停：公网证书体系已在推进更短的周期。

读 Validity 还有一个时区陷阱要提前拆：`Not After : Feb 4 08:00:00 2027 GMT` 里的 **GMT 是世界时**，与你的本地时间差着时区——「看起来 8 号过期，其实 9 号凌晨才过」这类误会都出自这里。OpenSSL 输出一律 GMT（UTC），`date -u` 可以随时对照；写监控脚本时也统一用 UTC 比较，别让本地时区混进判断。

**Subject Public Key Info：卡里的钥匙。** 算法与公钥本体（EC P-256 的钥匙只有 65 字节本体，RSA 2048 的要 256 字节）。注意证书里**只有公钥没有私钥**——私钥永远只在你手里，这是「塑封卡」与「裸钥匙」的关系：卡可以复印一万份，钥匙不行。

**Signature Algorithm 出现了两次，不是复制粘贴错误。** 证书开头那行声明「这张卡用什么工艺盖的章」，末尾那行下面跟着的十六进制串才是**章本身**（CA 签名的二进制真身）。两处算法必须一致——不一致本身就是伪造痕迹。验证签名真伪的操作就是第11章的 `verify`：用 CA 的公钥对末尾那串签名做验算，再比对摘要是否覆盖了整张卡面（第7章的签名原理原样适用，被签的「文件」就是证书的全部字段）。

至此「塑封卡」的每一格都被拆开看过：卡号（Serial）、钢印（Signature）、双名（Issuer/Subject）、有效期（Validity）、钥匙仓（SPKI）、权限页（扩展）。下一节专看权限页里最容易出事故的四条。

## 8.4 扩展字段：这把钥匙能干什么

X.509 v3 的扩展（extensions）是证书的「权限说明」，四个最关键的扩展决定了证书的生死边界：

| 扩展 | 值的含义 | 防的是什么 |
| ---- | ---- | ---- |
| Basic Constraints | `CA:TRUE` 才能签发别的证书；服务器证书 `CA:FALSE` | 拿服务器证书冒充 CA 签发假证书 |
| Key Usage | `Digital Signature`、`Key Encipherment` 等 | 拿签名钥匙干加密的活（跨岗使用） |
| Extended Key Usage | `TLS Web Server Authentication`（服务端）/ `TLS Web Client Authentication`（客户端） | 拿服务端证书去当客户端证书 |
| Subject Alternative Name | 证书**实际认可的全部域名** | 域名不匹配的冒用 |
| CRL Distribution Points | 撤销列表的下载地址 | 客户端无从查证证书是否已被吊销 |
| Authority Information Access | OCSP（Online Certificate Status Protocol，在线证书状态协议）查询地址与签发者证书获取地址 | 同上，在线版的撤销查询入口 |

SAN（Subject Alternative Name，主体备用名）要单独强调：**现代客户端验证域名只看 SAN，不看 Subject 里的 CN**。CN（Common Name）是历史遗留字段，出于兼容还在，但浏览器早已不认——这是无数老教程害人的地方：教程里教你在 CN 写域名，证书却配了别的 SAN，浏览器照样红牌。你要签发多域名或通配符证书，靠的就是 SAN 里列多个条目：

```text
X509v3 Subject Alternative Name:
    DNS:api.cloudnote.example
    DNS:*.cloudnote.example
    IP:203.0.113.10
```

多域名证书（一张卡印多个名字）的正当用途：同一台服务器同时服务 API 与管理后台。但它也是**审查重点**——一张证书的 SAN 列表越长，单点泄露的爆炸半径越大，云笔记的纪律是一张证书服务一个职责域，宁可多签几张。

通配符 `*.cloudnote.example` 还有一层要留意：星号**只匹配一层**子域，`a.b.cloudnote.example` 不在覆盖范围；且通配符签发的私钥能「顶替」所有子域，越少的机器该持有它。内部 CA 时代你可以自己拍板，接公网 CA 时通配符签发还要求更严的域名验证——行业用发放门槛补偿它的风险。

Basic Constraints 里 `critical` 字样也别放过：标记为 critical 的扩展，客户端**必须**理解并执行，不理解就拒绝证书——这是防伪等级最高的几条规则。

一张规范的服务器证书，四条扩展的「上岗配置」应该长这样——第10章自建 CA 签发时照此核对：

| 扩展 | 服务器证书的标准值 | 是否 critical |
| ---- | ---- | ---- |
| Basic Constraints | `CA:FALSE` | 是 |
| Key Usage | `Digital Signature`（EC 证书到这就够）或再加 `Key Encipherment`（RSA） | 是 |
| Extended Key Usage | `TLS Web Server Authentication`（服务端场景） | 否（但客户端会查） |
| Subject Alternative Name | 精确列出服务的域名，不多不少 | 否（但域名匹配全看它） |

配置错误在这张表上的典型表现：EKU 忘了带 `TLS Web Server Authentication`，浏览器报「证书用途不匹配」；SAN 列了 `*.cloudnote.example` 却没列裸域 `cloudnote.example`，主页访问红牌——通配符只匹配一层子域，这是另一个高频坑，第9章签发时会一并处理。

证书末尾那组看起来重复的 `Subject Key Identifier` 与（多级证书里才有的）`Authority Key Identifier` 也值得认识：前者是这张证书**自己的公钥指纹**（SKID），后者是**签发者公钥的指纹**（AKID）。多级证书链里，下一级证书的 AKID 必须等于上一级的 SKID——链就是靠这一对指纹「咬合」起来的，第11章验证证书链时它们是最快的诊断线索。单看 API 证书时，SKID 就像卡片背面的持卡人编号，AKID 像发卡行的机构编号。另外两条撤销相关扩展（CRL Distribution Points、AIA）在公网证书里常见、8.4 的表格已列出——它们是「去哪里查这张证有没有被吊销」的路标，第11章讲撤销时再登门。

## 8.5 证书不保护什么

读完证书正面，还要读它的反面——证书体系的三条责任边界：

**边界一：过期不自动失效，失效不自动发现。** 证书过期后浏览器拒绝连接，但「还差 3 天到期」不会有人来通知你——到期监控是使用者自己的事（第12章会用 s_client 写一条现成的监控命令）。云笔记的配套纪律先预告：证书有效 90 天、第 60 天轮换、剩余 21 天时监控告警——三层缓冲确保「忘了续」有两次补救机会。

**边界二：私钥泄露，证书不会自动作废。** 塑封卡被人连钥匙一起偷走，卡面上什么都看不出来。体系设计了「撤销」机制（CRL 吊销列表与 OCSP 在线查询，第11章细讲），但撤销机制的实效性在业内一直尴尬——**根本解法是短有效期 + 密钥轮换**，把「撤销」变成「等它自己过期」。你或许见过「某大厂紧急吊销证书」的新闻——那种紧急处置依赖撤销机制的全链路配合（CA 发布、客户端查询、运维强推），现实里常有一环掉链子；而 90 天周期下「不吊销、等过期」最多忍 90 天，两条路线的可靠性差距一目了然。

**边界三：CA 被攻破，殃及全部被签者。** 2011 年荷兰 CA 公司 DigiNotar 被入侵，攻击者签出了数百张假证书，其中包括 `*.google.com`——伊朗用户的 Gmail 流量被中间人截持。事件曝光后该 CA 签发的证书被各大浏览器集体除名，公司两个月内破产。这个案例两面都有教育意义：信任链的根被污染时，浏览器「集体换锁」的机制最终起了作用；但也说明**信任锚的选择从来不是纯技术问题**。

DigiNotar 的假证书能在几天内被发现，靠的是**证书透明度**（Certificate Transparency，CT）体系：所有公共 CA 签发的证书都要登记进几个公开可审计的日志库，域名持有者可以监控「有没有人给我的域名签证书」。Google Chrome 强制要求公网证书携带 CT 证明才显示小锁。自建 CA 的证书不进公共日志（内网域名也没必要），但 CT 的思路——**签发行为必须公开可查**——值得借鉴进内部流程：第10章会给内部 CA 建一个签发台账，本质就是迷你版 CT。

> [!NOTE] 证书验证到底验什么
> 浏览器校验一张服务器证书，实际验的是一串清单：域名匹配 SAN、在有效期内、签名链能追溯到一个预装信任锚、未被撤销、扩展约束没有被违反。这一串里有四项都挂在「链」上——证书链正是下一章之后的主线。
>
> 把这张清单和 8.4 的上岗配置表对照，你会发现浏览器其实是在替你执行一张「字段级检查表」。理解了这一点，「为什么配错一个扩展就红牌」就不再是玄学——每一条拒绝消息都对应表上的一行。

## 8.6 实验：亲手拆一张线上证书

不用等自建 CA，现在就能拆一张公网证书练手。从 example.com 拉一张（工具是第12章的 `s_client`，先抄后学）：

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 > example.pem

openssl x509 -in example.pem -noout -text
```

这组管道值得停下来拆一遍，因为它是最常用的「远程取证书」套路：`s_client` 完整模拟一次 TLS 握手，把服务器递来的证书连同握手过程全部打印；`2>/dev/null` 把握手过程的技术日志扔掉；`openssl x509` 不带参数时从标准输入读进第一张证书、默认以 PEM 文本输出——于是「活的服务器上的证书」被摘下来落成了本地文件。`echo |` 在开头喂一行输入，是防止某些服务器在等待客户端输入时挂住的小技巧。第12章会把 `s_client` 的每一行输出正式讲透，本章只借它这一个管道。管道的每一环都可以独立替换：换成 `-showcerts` 取全链（第11章）、换成 `x509 -noout -dates` 只看日期（第12章的监控脚本）——一条管道三种用法，全在组合。

带着四个问题去读输出，读完对照答案：

1. **Issuer 是谁？**——你会看到某家商业 CA 的名字，它就是为这张证书背书的第三方。
2. **有效期还剩多少天？**——`Not After` 减去今天，感受一下 90 天轮换的节奏。
3. **SAN 里列了几个域名？**——多数证书不止一个，找找有没有 `www.` 开头的孪生兄弟。
4. **Basic Constraints 是 CA:TRUE 还是 FALSE？**——服务器证书必须是 FALSE。

第五个隐藏问题：**Signature Algorithm 出现的两次一致吗？Key Usage 里有没有不该出现的项目？**——公网证书偶尔也会见到配置 sloppy 的样本，对照 8.4 的上岗配置表逐条审，练习「用标准审样本」的眼光。

顺手把指纹也取出来，和浏览器地址栏「连接安全 → 证书」里展示的 SHA-256 指纹比对——**两边一致**，你就亲眼验证了「浏览器和你用同一套工具看同一张身份证」：

```bash
openssl x509 -in example.pem -noout -fingerprint -sha256
```

进阶一步，用第6章埋过伏笔的 `asn1parse` 看证书的底层骨架：

```bash
openssl asn1parse -in example.pem | head -12
```

输出的嵌套结构里能找到 `-text` 视图的每一个字段——Version 是第一个 INTEGER，Validity 是两个 UTCTIME，SAN 是一串 context 标记的 DNS 条目。「译文」与「原文骨架」对照过一遍，证书格式在你眼里就再也不是黑盒。日常排错用 `-text`，怀疑文件损坏或字段异常时才请出 `asn1parse`。

实验收尾时把这张证书钉进云笔记的对照库：`example.pem` 存进 `~/cloudnote/dev/certs-samples/`，文件名标注抓取日期。以后遇到「这张公网证书和我内部证书长得不一样」的疑问，翻出样本对照即可——**建立自己的证书标本库**是排错经验最便宜的积累方式，第14章的排错手册会反复用到它。

进阶的读者还可以做一步「拆二进制」：`openssl x509 -in example.pem -outform DER -out example.der`，然后 `ls -l` 对比 PEM 与 DER 的体积——DER 约是 PEM 的 3/4（base64 有 33% 膨胀 + 头尾行）。公网证书约 1.2KB 起、内部证书更小，但浏览器每天要验的证书字节数累计惊人，这也是 TLS 1.3 顺手优化证书压缩的原因。体积账在第6章算过 PEM 的，这里算证书的，同一笔账。

| 验收项 | 命令 | 期望结果 |
| ---- | ---- | ---- |
| 证书可拉取 | s_client 管道 + `x509` | example.pem 生成 |
| 四问全部有答案 | `x509 -noout -text` | 四个问题逐一找到对应行 |
| 指纹与浏览器一致 | `-fingerprint -sha256` | 与证书详情页相同 |
| 扩展审核过关 | 对照 8.4 上岗配置表 | 四条扩展配置符合标准值 |
| 标本入库 | `ls ~/cloudnote/dev/certs-samples/` | 有日期标注的样本文件 |

## 本章小结

- 证书 = 塑封的公钥：公钥 + 身份 + 有效期 + 扩展约束，由 CA 私钥签名背书；信任锚的权威来自审计与除名机制，不是自封的
- 六组字段回答六个问题：序列号（第几号证，撤销的检索键）、算法（怎么盖章，出现两次）、Issuer（谁盖章）、Validity（何时有效）、Subject（发给谁）、公钥（钥匙本体）；SKID/AKID 是链咬合的指纹对
- 扩展是权限说明：Basic Constraints 分 CA 与非 CA、Key Usage 定岗位、EKU 定场景、**SAN 才是现代域名验证的唯一依据**；通配符只匹配一层子域
- 90 天有效期是行业共识：危害窗口短，代价是必须自动化续期；公网证书还要过证书透明度（CT）登记
- 证书不保护：到期没人通知、私钥泄露不自动作废、CA 被黑殃及池鱼——短周期与轮换是根本解法
- `x509 -text` 逐字段读、`-subject -issuer -dates -fingerprint` 快捷取字段；`s_client | x509` 拉真证书对照浏览器，`asn1parse` 看底层骨架

**下一章预告**：字段都认识了，该动手造第一张证书了——从密钥到 CSR 再到自签证书，一条命令的主线你会走通；浏览器对自签证书的红牌警告，也会在这一章给出正解。你会发现 8.2 那张「证书样本」里的每个字段，从这一章起都开始由你亲手填写。
