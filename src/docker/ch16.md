# 第16章：Docker Swarm —— 轻量级容器编排

## 引言：从个人开发者到团队管理

在前面的章节里，你就像是一个独立开发者——一个 Docker Host 上跑着你的所有容器。一切尽在掌控之中。

但是，当你的应用越来越受欢迎，一台服务器扛不住了，你需要把容器分布到多台服务器上运行。这时候问题就来了：

- 哪个容器应该跑在哪台服务器上？
- 某个容器挂了怎么办？谁来重启它？
- 流量怎么分配到不同的服务器上？
- 怎么做滚动升级而不影响用户？

这些问题，就像你从一个人写代码变成了管理一个开发团队——你需要"分配任务"（调度）、"监督进度"（健康检查）、"处理离职"（故障恢复）、"新人培训"（扩容）。

**容器编排**（Container Orchestration）就是自动化管理容器的"项目经理"。它帮你处理容器的部署、扩缩容、网络、负载均衡和故障恢复。

## 16.1 Swarm vs Kubernetes vs Nomad

市面上有三大容器编排工具，各有千秋：

```bash
┌────────────┬──────────────────┬──────────────────┬──────────────────┐
│  特性       │ Docker Swarm     │ Kubernetes       │ HashiCorp Nomad  │
├────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 学习曲线    │ 低 ⭐             │ 高 ⭐⭐⭐⭐⭐      │ 中 ⭐⭐⭐          │
│ 安装复杂度  │ 几乎不需要        │ 需要 kubeadm 等   │ 单二进制文件      │
│ 内置于Docker│ ✅ 是             │ ❌ 否             │ ❌ 否             │
│ 适用规模    │ 小-中型（<100节点）│ 中-超大型         │ 中-大型          │
│ YAML配置    │ docker-compose   │ k8s manifests    │ HCL/JSON         │
│ 自动扩缩容  │ 手动              │ HPA/VPA 自动      │ 需配合外部工具    │
│ 生态丰富度  │ 一般              │ 极其丰富          │ 一般              │
│ 上手时间    │ 半天              │ 2-4 周            │ 1 周             │
└────────────┴──────────────────┴──────────────────┴──────────────────┘
```

简单来说：

- **Swarm**：适合中小规模，学习成本低，"开箱即用"——就像 `git` 一样，基本命令半小时就能上手。
- **Kubernetes**：行业标准，功能极其强大，但学习曲线陡峭——就像 Vim，学会了效率极高，但入门需要耐心。
- **Nomad**：HashiCorp 家的产品，和 Consul/Vault/Terraform 配合很好——适合已经在用 HashiCorp 全家桶的团队。

> [!TIP] 提示
> 不要被 Kubernetes 的光芒闪到眼就觉得 Swarm 不行。很多公司的实际场景是：几十台服务器、几十个微服务——这种情况下 Swarm 完全够用，而且运维成本低得多。选工具不是选最酷的，而是选最合适的。就像你不会为了写一个 Hello World 就用 Spring Boot 一样。

## 16.2 Swarm 集群搭建

Swarm 是 Docker Engine 内置的编排功能，不需要安装任何额外软件。你的 Docker 已经自带了这个能力，只是还没有"激活"。

### 16.2.1 核心概念

```bash
Swarm 集群架构

┌─────────────────────────────────────────────────┐
│                  Swarm 集群                       │
│                                                   │
│  ┌──────────────┐    ┌──────────────┐            │
│  │ Manager 节点  │    │ Manager 节点  │            │
│  │ (Leader)      │    │ (Replica)    │            │
│  │               │    │              │            │
│  │ • 集群管理    │    │ • 备用管理    │            │
│  │ • 任务调度    │    │ • 参与选举    │            │
│  │ • 状态维护    │    │              │            │
│  └──────────────┘    └──────────────┘            │
│                                                   │
│  ┌──────────────┐    ┌──────────────┐            │
│  │ Worker 节点   │    │ Worker 节点   │            │
│  │               │    │              │            │
│  │ • 运行容器    │    │ • 运行容器    │            │
│  │ • 执行任务    │    │ • 执行任务    │            │
│  └──────────────┘    └──────────────┘            │
│                                                   │
└─────────────────────────────────────────────────┘

Manager 节点：
  - 负责集群的"大脑"工作：调度、状态管理、API 服务
  - 至少需要1个，生产环境建议3个或5个（奇数个，用于选举）
  - 也可以同时作为 Worker 运行容器

Worker 节点：
  - 负责"搬砖"：实际运行容器
  - 不直接参与集群管理决策
  - 通过 Manager 节点的 API 接收任务
```

### 16.2.2 初始化 Swarm 集群

```bash
# ===== 在 Manager 节点上执行 =====

# 初始化 Swarm
docker swarm init --advertise-addr 192.168.1.100
# --advertise-addr：告诉其他节点用这个 IP 来联系 Manager
# 就像你在公司通讯录里填的办公电话号码

# 输出会类似于：
# Swarm initialized: current node (abc123) is now a manager.
#
# To add a worker to this swarm, run the following command:
#   docker swarm join --token SWMTKN-1-xxxxx 192.168.1.100:2377
#
# To add a manager to this swarm, run 'docker swarm join-token manager'

# 保存好输出的 join token！Worker 节点需要用它来加入集群
# 这个 token 就像公司的"入职密码"，新员工（新节点）需要它才能加入
```

```bash
# ===== 在 Worker 节点上执行 =====

# 加入 Swarm 集群
docker swarm join --token SWMTKN-1-xxxxx 192.168.1.100:2377
# 使用 Manager 节点 init 时输出的命令即可

# 加入成功后，Manager 节点上可以看到新节点
# （在 Manager 节点上执行）
docker node ls
# ID          HOSTNAME    STATUS   AVAILABILITY   MANAGER STATUS
# abc123 *    manager1    Ready    Active         Leader
# def456      worker1     Ready    Active
# ghi789      worker2     Ready    Active
```

```bash
# 如果你忘记了 join token，可以重新获取

# 获取 Worker join token
docker swarm join-token worker
# 输出加入集群的完整命令

# 获取 Manager join token
docker swarm join-token manager
# Manager 节点需要不同的 token，因为权限更高
```

```bash
# 节点离开集群
# 在要离开的节点上执行
docker swarm leave
# Worker 节点可以直接离开

# Manager 节点需要先降级为 Worker
docker node demote manager-node-name
# 或者强制离开（不推荐，可能导致集群仲裁丢失）
docker swarm leave --force
```

> **Warning:** Manager 节点的数量必须是奇数（1、3、5、7），因为 Swarm 使用 Raft 共识算法，需要多数节点（quorum）才能做决策。如果你有 3 个 Manager，最多允许 1 个挂掉；5 个 Manager 允许 2 个挂掉。千万别搞偶数个 Manager——4 个 Manager 的容错能力和 3 个一样，还多了开销。

## 16.3 Service 管理

Service 是 Swarm 中的一等公民——它定义了你想要运行的容器的"蓝图"，Swarm 负责确保实际运行的容器数量始终符合你的期望。

```bash
# ====== 创建 Service ======

docker service create \
  --name web \
  --replicas 3 \
  --publish 80:80 \
  nginx:alpine
  # 创建一个名为 "web" 的服务
  # --replicas 3：始终运行 3 个实例
  # Swarm 会自动在 Worker 节点间分配这 3 个实例
  # 就像项目经理把 3 个相同的任务分配给不同的员工

# 查看服务状态
docker service ls
# ID     NAME   MODE       REPLICAS   IMAGE         PORTS
# abc    web    replicated 3/3        nginx:alpine  *:80->80/tcp

# 查看服务的详细任务分布
docker service ps web
# ID    NAME     IMAGE         NODE      STATUS
# 1     web.1    nginx:alpine  worker1   Running
# 2     web.2    nginx:alpine  worker2   Running
# 3     web.3    nginx:alpine  worker1   Running
# 可以看到 3 个副本分布在 2 个 Worker 节点上
```

```bash
# ====== 扩缩容 ======

# 扩容到 5 个副本
docker service scale web=5
# Swarm 会自动在可用节点上启动新的实例
# 就像项目忙不过来时，项目经理紧急招了2个新人

# 也可以同时扩缩多个服务
docker service scale web=5 api=3 db=2

# 缩容到 2 个副本
docker service scale web=2
# Swarm 会优雅地停止多余的实例
# 不是直接 kill，而是先发 SIGTERM 等待优雅退出
```

```bash
# ====== 滚动升级 ======

# 更新镜像版本
docker service update --image nginx:1.25-alpine web
# Swarm 会逐个更新实例，每次只更新一个
# 更新完一个、确认健康后，再更新下一个
# 就像给团队培训新版本工具，一次培训一个人，保证其他人继续干活

# 控制滚动升级的行为
docker service update \
  --image nginx:1.25-alpine \
  --update-parallelism 2 \
  # 每次同时更新 2 个实例
  --update-delay 10s \
  # 每批之间等 10 秒
  --update-failure-action rollback \
  # 更新失败时自动回滚
  --update-monitor 30s \
  # 更新后观察 30 秒判断是否健康
  web
```

```bash
# ====== 回滚 ======

# 如果新版本有问题，一键回滚
docker service rollback web
# 回滚到上一个版本
# Swarm 会执行和升级相同的滚动更新过程，只是方向反了

# 查看服务的更新历史
docker service update --help | grep rollback
# --rollback-parallelism   每次回滚的实例数
# --rollback-delay         每批之间的等待时间
# --rollback-failure-action 回滚失败时的操作
```

```bash
# ====== 删除 Service ======

docker service rm web
# 停止并删除服务的所有实例
```

> [!TIP] 提示
> `docker service update` 是一个"万能命令"——你几乎可以更新服务的任何属性：镜像版本、环境变量、挂载卷、资源限制、网络等。每次 update 都会触发滚动升级过程，确保零停机。

## 16.4 Stack 部署

手动一个个创建 Service 太累了，特别是当你的应用有 5-10 个服务时。Stack 允许你用 Compose 文件一次性部署整个应用——没错，就是我们之前学过的 `docker-compose.yml`！

```yaml
# docker-stack.yml
# Swarm Stack 部署文件
# 注意：和单机版 docker-compose.yml 有一些区别

version: '3.8'

services:
  # ====== Web 前端 ======
  web:
    image: myregistry.com/myapp-web:latest
    ports:
      - "80:3000"
    environment:
      - NODE_ENV=production
      - API_URL=http://api:8080
    deploy:
      replicas: 3
      # Stack 的 deploy 部分替代了 docker-compose 的 scale
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 3
        window: 120s
        # 120秒内失败超过3次就不再重试
        # 避免无限重启的"死循环"
      update_config:
        parallelism: 1
        delay: 10s
        failure_action: rollback
        monitor: 30s
      rollback_config:
        parallelism: 1
        delay: 5s
      resources:
        limits:
          cpus: '0.5'
          memory: 512M
        reservations:
          cpus: '0.25'
          memory: 256M
          # limits = 上限（硬限制，超过会被限制/杀死）
          # reservations = 保底（调度时确保有这么多资源）
    networks:
      - frontend
      - backend

  # ====== API 服务 ======
  api:
    image: myregistry.com/myapp-api:latest
    environment:
      - NODE_ENV=production
      - DB_HOST=postgres
      - REDIS_HOST=redis
    deploy:
      replicas: 2
      update_config:
        parallelism: 1
        delay: 15s
    secrets:
      - db_password
      - jwt_secret
      # Secrets 是 Swarm 的加密数据管理功能
      # 后面会详细讲解
    networks:
      - backend

  # ====== 数据库 ======
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: myapp
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
      # 从 Secret 文件中读取密码，而不是明文写在这里
    volumes:
      - db-data:/var/lib/postgresql/data
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.labels.storage == ssd
          # 数据库只运行在有 SSD 的节点上
          # 这是通过节点标签来实现的调度约束
    networks:
      - backend

  # ====== 缓存 ======
  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    deploy:
      replicas: 1
    networks:
      - backend

# ====== 卷 ======
volumes:
  db-data:
    driver: local
    # 注意：在 Swarm 中，local driver 的卷是节点本地的
    # 如果容器漂移到其他节点，数据不会跟着走！
    # 解决方案：使用共享存储驱动（如 NFS、Portworx）

# ====== 网络 ======
networks:
  frontend:
    driver: overlay
    # overlay 网络：跨节点的虚拟网络
    # 不同节点上的容器可以通过服务名互相通信
    # 就像给分布在不同城市的同事配了一个内部 VPN
  backend:
    driver: overlay
    internal: true
    # internal: true 表示这个网络不能从外部访问
    # 数据库和 Redis 不需要对外暴露

# ====== Secrets ======
secrets:
  db_password:
    external: true
    # 使用外部创建的 Secret（推荐）
  jwt_secret:
    external: true
```

```bash
# 创建 Secrets（部署 Stack 之前）
echo "MyDBP@ssw0rd" | docker secret create db_password -
echo "JWT-S3cr3t-K3y-2024" | docker secret create jwt_secret -
# - 表示从 stdin 读取

# 给节点打标签
docker node update --label-add storage=ssd worker1
# 标记 worker1 节点有 SSD 存储

# 部署 Stack
docker stack deploy -c docker-stack.yml myapp
# myapp 是 Stack 名称
# 所有服务和网络都会自动加上这个前缀
# 比如：myapp_web, myapp_api, myapp_postgres

# 查看 Stack 状态
docker stack ls
# NAME    SERVICES
# myapp   4

# 查看 Stack 中的服务
docker stack services myapp
# ID     NAME          REPLICAS   IMAGE
# ...    myapp_web     3/3        myregistry.com/myapp-web:latest
# ...    myapp_api     2/2        myregistry.com/myapp-api:latest
# ...    myapp_postgres 1/1       postgres:16-alpine
# ...    myapp_redis   1/1        redis:7-alpine

# 更新 Stack（修改 YAML 后重新部署）
docker stack deploy -c docker-stack.yml myapp
# Swarm 会对比差异，只更新变化的部分
# 就像 React 的 Virtual DOM diff 一样智能

# 删除 Stack
docker stack rm myapp
# 删除 Stack 下的所有服务、网络
# 但不会删除卷（数据安全）
```

> **Warning:** Swarm Stack 的 `docker-compose.yml` 和单机版有一些重要区别：`build` 指令不支持（必须提前构建好镜像）、`depends_on` 不支持（Swarm 没有启动顺序的概念）、`volumes` 的 bind mount 不支持（只能用 named volumes）。如果你的 Compose 文件用了这些特性，需要修改后才能用于 Stack。

## 16.5 Swarm 网络

Swarm 有三种网络模式，理解它们对排障至关重要：

```bash
┌─────────────────────────────────────────────────┐
│              Swarm 网络模型                       │
│                                                   │
│  ┌─────────────────────────────────────────┐     │
│  │           Overlay 网络                   │     │
│  │                                          │     │
│  │  ┌──────────┐         ┌──────────┐      │     │
│  │  │ Node A   │         │ Node B   │      │     │
│  │  │ ┌──────┐ │  VXLAN  │ ┌──────┐ │      │     │
│  │  │ │容器1 │◄├─────────┤►│容器3 │ │      │     │
│  │  │ └──────┘ │  隧道    │ └──────┘ │      │     │
│  │  │ ┌──────┐ │         │          │      │     │
│  │  │ │容器2 │ │         │          │      │     │
│  │  │ └──────┘ │         │          │      │     │
│  │  └──────────┘         └──────────┘      │     │
│  └─────────────────────────────────────────┘     │
│                                                   │
│  ┌─────────────────────────────────────────┐     │
│  │           Ingress 网络（默认）           │     │
│  │                                          │     │
│  │  外部流量 → 任意节点:80 → Routing Mesh   │     │
│  │                    ↓                     │     │
│  │              负载均衡到                   │     │
│  │           实际运行容器的节点              │     │
│  └─────────────────────────────────────────┘     │
│                                                   │
└─────────────────────────────────────────────────┘
```

```bash
# 创建 overlay 网络
docker network create \
  --driver overlay \
  --subnet 10.0.0.0/16 \
  --attachable \
  my-overlay-net
  # --attachable：允许独立的容器（非 service）也能加入这个网络
  # 方便调试时使用

# 查看网络详情
docker network inspect my-overlay-net
```

### Routing Mesh（路由网格）

Routing Mesh 是 Swarm 最酷的功能之一：当你在一个 Service 上 publish 了端口，**集群中所有节点**都会监听这个端口，即使该节点上没有运行这个 Service 的容器。

```bash
# 创建一个只有2个副本的服务（集群有3个Worker节点）
docker service create \
  --name api \
  --replicas 2 \
  --publish 8080:3000 \
  myapi:latest

# 假设副本运行在 worker1 和 worker2 上
# 但由于 Routing Mesh，你可以访问：
#   http://worker1:8080  ✅ （直接命中）
#   http://worker2:8080  ✅ （直接命中）
#   http://worker3:8080  ✅ （worker3 上没有容器，但请求会被转发到有容器的节点）
#   http://manager1:8080 ✅ （Manager 节点也可以！）

# 你可以把 DNS 轮询指向所有节点的 IP
# 或者在前面放一个外部负载均衡器（如 Nginx、HAProxy）
```

> [!TIP] 提示
> Routing Mesh 的工作方式就像公司前台——不管你去哪个办公室的前台问问题，前台都会帮你找到对应的人来回答。用户不需要知道"服务实际跑在哪个节点上"，访问任意节点就行。这意味着你不需要配置复杂的外部负载均衡器（虽然生产环境中还是推荐用）。

## 16.6 Swarm Secrets 管理

Secrets 是 Swarm 内置的敏感数据管理功能。比起把密码写在环境变量或配置文件里，Secrets 更加安全：

```bash
# ====== 创建 Secret ======

# 方式1：从文件创建
echo "super-secret-password" > password.txt
docker secret create db_password password.txt
rm password.txt
# 创建后立即删除源文件

# 方式2：从 stdin 创建（更安全，不留文件痕迹）
echo "super-secret-password" | docker secret create db_password -

# 方式3：使用 printf（避免末尾换行符）
printf "super-secret-password" | docker secret create db_password -

# 查看 Secrets 列表
docker secret ls
# ID            NAME          CREATED         UPDATED
# abc123        db_password   10 seconds ago  10 seconds ago
# 注意：列表中看不到 Secret 的实际内容，只能看到名字

# ====== 使用 Secret ======

# 在 Service 中使用
docker service create \
  --name myapp \
  --secret db_password \
  --secret source=jwt_secret,target=jwt_key \
  # source：Secret 名称
  # target：容器内的文件名（默认为 source 名称）
  myimage:latest

# Secret 在容器内以文件形式存在：
# /run/secrets/db_password
# /run/secrets/jwt_key
# 文件权限为 0444（只读），所有者为 root

# 在代码中读取 Secret：
# Node.js:
# const dbPassword = fs.readFileSync('/run/secrets/db_password', 'utf8').trim();
# Python:
# with open('/run/secrets/db_password') as f:
#     db_password = f.read().strip()

# ====== 更新 Secret ======
# Secret 是不可变的（immutable），不能直接更新
# 需要创建新的 Secret，然后更新 Service

printf "new-super-secret" | docker secret create db_password_v2 -

docker service update \
  --secret-rm db_password \
  --secret-add source=db_password_v2,target=db_password \
  myapp

# 删除旧的 Secret
docker secret rm db_password
```

> **Warning:** Swarm Secrets 虽然比环境变量安全（数据加密存储、传输时通过 TLS），但它不如专业的密钥管理工具（如 HashiCorp Vault）。如果你的安全要求很高（比如需要审计日志、动态密钥、密钥轮换），建议集成 Vault 而不是只用 Swarm Secrets。

## 16.7 实战：将一个 Compose 应用部署到 Swarm 集群

让我们把一个典型的 Web 应用从单机 Compose 迁移到 Swarm 集群。

**原始 docker-compose.yml（单机版）：**

```yaml
# docker-compose.yml（单机版）
version: '3.8'

services:
  web:
    build: ./frontend
    # ⚠️ Swarm Stack 不支持 build，需要提前构建好镜像
    ports:
      - "80:3000"
    depends_on:
      - api
      # ⚠️ Swarm Stack 不支持 depends_on

  api:
    build: ./backend
    ports:
      - "8080:8080"
    environment:
      DB_PASSWORD: my-secret-password
      # ⚠️ 不应该在 YAML 中明文写密码
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    volumes:
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
      # ⚠️ Swarm Stack 不支持 bind mount
      - db-data:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: my-secret-password

volumes:
  db-data:
```

**改造后的 Stack 文件（Swarm 版）：**

```yaml
# docker-stack.yml（Swarm 版）
version: '3.8'

services:
  web:
    image: registry.example.com/myapp-web:v1.0.0
    # ✅ 使用预构建的镜像
    ports:
      - "80:3000"
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
      resources:
        limits:
          memory: 256M
    networks:
      - frontend

  api:
    image: registry.example.com/myapp-api:v1.0.0
    environment:
      DB_HOST: db
      DB_PORT: "5432"
    deploy:
      replicas: 2
      update_config:
        parallelism: 1
        delay: 15s
        failure_action: rollback
      resources:
        limits:
          memory: 512M
    secrets:
      - db_password
    networks:
      - frontend
      - backend

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
      # ✅ 通过 Secret 文件读取密码
    volumes:
      - db-data:/var/lib/postgresql/data
    deploy:
      replicas: 1
      placement:
        constraints:
          - node.role == manager
          # 数据库固定在 Manager 节点
          # 因为 local volume 是节点本地的
    networks:
      - backend

volumes:
  db-data:

networks:
  frontend:
    driver: overlay
  backend:
    driver: overlay
    internal: true

secrets:
  db_password:
    external: true
```

```bash
# ====== 部署步骤 ======

# 1. 构建并推送镜像（在开发机上）
docker build -t registry.example.com/myapp-web:v1.0.0 ./frontend
docker build -t registry.example.com/myapp-api:v1.0.0 ./backend
docker push registry.example.com/myapp-web:v1.0.0
docker push registry.example.com/myapp-api:v1.0.0

# 2. 创建 Secret（在 Manager 节点上）
printf "MyS3cur3P@ss" | docker secret create db_password -

# 3. 部署 Stack
docker stack deploy -c docker-stack.yml myapp

# 4. 等待所有服务就绪
watch docker stack services myapp
# watch 命令会每2秒刷新输出
# 等所有 REPLICAS 显示为 N/N 就说明部署完成了

# 5. 验证部署
curl http://manager-node/health
# 通过 Routing Mesh，访问任意节点都可以
```

## 16.8 Swarm 的日常运维

```bash
# ====== 节点维护 ======

# 将节点设为"排水"模式（排走所有容器）
docker node update --availability drain worker2
# worker2 上的容器会被迁移到其他可用节点
# 新的任务不会被调度到这个节点
# 适合：系统升级、硬件维护

# 维护完成后恢复
docker node update --availability active worker2
# 注意：已经迁走的容器不会自动回来
# Swarm 会保持当前的分布，除非触发新的调度

# 将节点设为暂停（不接受新任务，但现有任务不迁移）
docker node update --availability pause worker2

# ====== 查看集群状态 ======

# 查看所有节点
docker node ls

# 查看节点详细信息
docker node inspect worker1 --pretty

# 查看所有服务
docker service ls

# 查看服务的任务分布
docker service ps myapp_api

# 查看服务日志（汇总所有副本的日志）
docker service logs myapp_api --tail 50 -f
# -f：follow 模式，实时查看
# --tail 50：只看最后 50 行

# ====== 故障排查 ======

# 查看某个任务为什么起不来
docker service ps myapp_api --no-trunc
# --no-trunc：不截断输出，看到完整的错误信息

# 查看 Swarm 事件
docker events --filter type=service
```

## 本章小结

| 概念 | 说明 |
|------|------|
| Swarm | Docker 内置的容器编排工具，开箱即用 |
| Manager 节点 | 集群管理节点，负责调度和状态管理（建议奇数个） |
| Worker 节点 | 运行容器的工作节点 |
| Service | 定义容器的蓝图，支持副本、滚动升级、回滚 |
| Stack | 使用 Compose 文件一次性部署多个服务 |
| Overlay 网络 | 跨节点的虚拟网络，让不同节点的容器互通 |
| Routing Mesh | 访问任意节点的端口都能被路由到正确的容器 |
| Secrets | 安全地管理敏感数据（密码、密钥等） |

## 练习

1. **入门**：在本地用 Docker Machine 或虚拟机创建 3 个节点（1 Manager + 2 Worker），搭建一个 Swarm 集群。
2. **进阶**：将一个多服务应用（Web + API + DB）编写为 Stack 文件，部署到集群中，验证服务和网络连通性。
3. **挑战**：模拟 Worker 节点故障（直接关闭虚拟机），观察 Swarm 如何自动将服务迁移到其他节点，记录故障恢复过程。
