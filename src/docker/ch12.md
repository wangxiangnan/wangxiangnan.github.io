# 第12章：Docker 性能优化 —— 让你的容器飞起来

## 引言：性能优化的"冰山模型"

Docker 性能优化就像一座冰山。水面之上，大家关注的是"镜像构建太慢了"、"容器启动太慢了"。但水面之下，隐藏着层缓存策略、构建并行化、存储驱动选择等大量优化空间。

很多开发者遇到性能问题时，第一反应是"加机器"——这就像你家网速慢就换一个更大的套餐，但也许只是你的路由器位置不对。本章将带你系统性地理解 Docker 的性能优化策略。

---

## 12.1 镜像瘦身策略

### 基础镜像大小对比

| 镜像 | 大小 | 适用场景 |
|------|------|---------|
| `ubuntu` | ~77MB | 需要完整系统工具 |
| `debian:slim` | ~52MB | 需要 apt 但追求小巧 |
| `alpine` | ~7MB | 通用选择，推荐 |
| `distroless/nodejs18` | ~20MB | 只含 Node.js 运行时 |
| `distroless/python3` | ~20MB | 只含 Python 运行时 |
| `scratch` | 0MB | Go/Rust 编译型语言 |

### Alpine 镜像

```dockerfile
# Node.js 应用使用 Alpine
FROM node:18-alpine    # ~120MB（对比 node:18 的 ~950MB）

# Python 应用使用 Alpine
FROM python:3.11-alpine  # ~50MB（对比 python:3.11 的 ~900MB）
```

> **Warning:** Alpine 使用 musl libc 而非 glibc，某些依赖 C 扩展的 Python 包（如 numpy、Pillow）在 Alpine 上可能有问题。此时考虑使用 `slim` 版本。

### Distroless 镜像

```dockerfile
# Node.js 使用 distroless
FROM node:18-alpine AS builder
WORKDIR /app
COPY . .
RUN npm ci --only=production

FROM gcr.io/distroless/nodejs18
WORKDIR /app
COPY --from=builder /app .
CMD ["server.js"]
# 注意：distroless 没有 shell！docker exec -it container sh 会失败
```

### Scratch 镜像（编译型语言）

```dockerfile
# Go 应用使用 scratch
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server .

FROM scratch
COPY --from=builder /app/server /server
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
EXPOSE 8080
ENTRYPOINT ["/server"]
# 最终镜像大小：~10MB（对比 golang 镜像的 ~800MB）
```

## 12.2 Layer 缓存优化（指令排序的艺术）

Docker 构建时，每条指令生成一个层。一旦某层的输入变化，该层及之后的所有层都会缓存失效。

```dockerfile
# ===== 错误示范：缓存利用率极低 =====
FROM node:18-alpine
WORKDIR /app

# 先复制所有文件（包括源码）
COPY . .

# 然后安装依赖
RUN npm ci --only=production
# 问题：每次修改源码，COPY . . 导致缓存失效
# npm ci 必须重新执行！每次构建都重新安装所有依赖！


# ===== 正确做法：充分利用缓存 =====
FROM node:18-alpine
WORKDIR /app

# 第一步：只复制依赖描述文件（很少变化）
COPY package.json package-lock.json ./

# 第二步：安装依赖（只要依赖不变，这一层会被缓存）
RUN npm ci --only=production

# 第三步：复制源代码（经常变化，放在后面）
COPY . .

CMD ["node", "server.js"]
# 效果：只要 package.json 没变，npm ci 就命中缓存
# 构建时间从 2 分钟降到 5 秒！
```

Python 项目同理：

```dockerfile
FROM python:3.11-slim
WORKDIR /app

# 只复制依赖文件
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 再复制应用代码
COPY . .
CMD ["gunicorn", "app:app"]
```

**Dockerfile 指令排序原则**：

```
1. FROM              ← 基础镜像（几乎不变）
2. 系统包安装         ← apt-get install（偶尔变化）
3. 依赖文件复制       ← COPY package.json（很少变化）
4. 依赖安装           ← npm ci / pip install（很少变化）
5. 配置文件复制       ← COPY config/（偶尔变化）
6. 源代码复制         ← COPY . .（经常变化）
7. 编译/构建          ← RUN npm run build（经常变化）
```

> [!TIP] 提示
> 如果你有一个"经常变化但被后续层依赖"的操作，考虑把它拆分成两个 `COPY` 指令。

## 12.3 .dockerignore 的正确使用

`.dockerignore` 之于 Docker 构建，就像 `.gitignore` 之于 Git。

```bash
# .dockerignore —— Node.js 项目的典型配置

# 依赖目录（会在容器内重新安装）
node_modules
npm-debug.log*

# 版本控制
.git
.gitignore

# IDE 配置
.vscode
.idea

# 环境变量文件（安全！）
.env
.env.local

# Docker 相关文件
Dockerfile*
docker-compose*.yml
.dockerignore

# 文档
README.md
docs/

# 测试文件
__tests__/
*.test.js
coverage/

# 构建产物
dist/
build/

# 操作系统文件
.DS_Store
```

没有 `.dockerignore` 的后果：

```bash
# 假设 node_modules 有 500MB
# 没有 .dockerignore：
docker build -t my-app .
# Sending build context to Docker daemon  512.3MB  ← 光传输就要很久！

# 有 .dockerignore：
docker build -t my-app .
# Sending build context to Docker daemon  2.4MB  ← 几秒钟搞定
```

> [!TIP] 提示
> `.dockerignore` 不仅减少构建上下文大小，还能防止敏感文件（`.env`、私钥）被意外打包进镜像。

## 12.4 多阶段构建的性能收益

```dockerfile
# ===== 完整的多阶段构建 =====

# 阶段1：安装所有依赖并构建
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                          # 安装所有依赖（包括 devDependencies）
COPY . .
RUN npm run build                   # TypeScript 编译、Webpack 打包
RUN npm prune --production          # 删除开发依赖

# 阶段2：只包含运行时文件
FROM node:18-alpine AS production
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./

USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

# builder 镜像：~800MB
# production 镜像：~150MB
```

```dockerfile
# Python 项目的多阶段构建
FROM python:3.11 AS builder
WORKDIR /app
COPY requirements.txt .
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY --from=builder /app .

RUN useradd -r appuser && chown -R appuser:appuser /app
USER appuser
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

## 12.5 BuildKit 并行构建

BuildKit 是 Docker 的下一代构建引擎，支持并行构建、缓存挂载等高级特性。

```bash
# 启用 BuildKit
export DOCKER_BUILDKIT=1

# 或使用 docker buildx
docker buildx build -t my-app .
```

BuildKit 会自动并行执行无依赖的阶段：

```dockerfile
# BuildKit 并行构建示例
FROM node:18-alpine AS frontend-builder
WORKDIR /frontend
COPY frontend/ .
RUN npm ci && npm run build

FROM python:3.11-slim AS backend-builder
WORKDIR /backend
COPY backend/ .
RUN pip install -r requirements.txt

# 这两个独立阶段会被 BuildKit 并行执行！
FROM alpine:latest AS final
COPY --from=frontend-builder /frontend/dist /app/frontend
COPY --from=backend-builder /backend /app/backend
```

```dockerfile
# BuildKit 缓存挂载（即使重建也不会重新下载）
# syntax=docker/dockerfile:1

FROM node:18-alpine
WORKDIR /app

RUN --mount=type=cache,target=/root/.npm \
    npm ci --only=production

COPY . .
CMD ["node", "server.js"]
```

## 12.6 容器资源限制与调度

```yaml
services:
  api:
    image: my-api:latest
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: '0.5'
        reservations:
          memory: 256M
          cpus: '0.25'

  db:
    image: postgres:15-alpine
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: '2.0'
```

```bash
# 运行时动态调整资源
docker update --memory=1g --cpus=1.0 my-container

# 查看实时资源使用
docker stats --no-stream
```

> [!TIP] 提示
> 内存限制的经验法则：观察应用在正常负载下的内存使用，设置为峰值的 1.5-2 倍。使用 `docker stats` 持续监控几天后再做决定。

## 12.7 Docker 存储驱动选择

| 存储驱动 | 性能 | 推荐场景 |
|---------|------|---------|
| **overlay2** | 优秀 | 推荐默认选择 |
| devicemapper | 一般 | 避免使用 |

```bash
# 查看当前存储驱动
docker info | grep "Storage Driver"
# 输出：Storage Driver: overlay2
```

> [!TIP] 提示
> 在 Linux 生产服务器上，确保使用 `overlay2`（现代 Docker 默认值）。如果你还在用 `devicemapper`，强烈建议迁移。

## 12.8 DNS 缓存优化

```bash
# 自定义 DNS 服务器
docker run -d \
  --dns 8.8.8.8 \
  --dns 8.8.4.4 \
  my-app
```

```yaml
# docker-compose.yml
services:
  api:
    image: my-api:latest
    dns:
      - 8.8.8.8
      - 8.8.4.4
```

> [!TIP] 提示
> 对于 Docker 内部的服务发现（容器名解析），Docker 的嵌入式 DNS（`127.0.0.11`）已经做了缓存，不需要额外优化。

## 12.9 镜像层共享与复用

```bash
# 查看磁盘使用情况
docker system df
# TYPE            TOTAL    ACTIVE   SIZE      RECLAIMABLE
# Images          15       5        3.2GB     1.8GB (56%)
# Containers      8        5        256MB     128MB (50%)
# Local Volumes   10       3        5.1GB     2.3GB (45%)
# Build Cache     20       0        800MB     800MB (100%)

# 清理未使用的资源
docker system prune                 # 清理停止的容器、悬空镜像
docker system prune -a              # + 未使用的镜像
docker system prune -a --volumes    # + 未使用的卷（慎用！）
docker builder prune                # 清理构建缓存
```

**层共享策略**：多个服务使用相同的自定义基础镜像，推送/拉取时只传输差异部分。

## 本章小结

- 选择合适的基础镜像是镜像瘦身的第一步（Alpine > slim > 完整镜像）
- Dockerfile 指令排序直接影响构建缓存命中率
- `.dockerignore` 减少构建上下文、保护敏感文件
- 多阶段构建同时优化镜像体积和构建性能
- BuildKit 的并行构建和缓存挂载是性能利器
- 使用 `overlay2` 存储驱动确保最佳 I/O 性能
- 定期清理未使用的镜像、容器和构建缓存

## 练习

1. **基础练习**：选择一个现有的 Dockerfile，按缓存优化原则重新排序指令，对比优化前后的构建时间。
2. **进阶练习**：将一个 Node.js 应用的镜像改为多阶段构建，对比优化前后的镜像大小。
3. **挑战练习**：使用 BuildKit 的缓存挂载特性优化 `npm ci`，确保依赖缓存跨构建持久化。
