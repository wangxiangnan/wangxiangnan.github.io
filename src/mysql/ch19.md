# 第19章 备份与恢复

如果把数据库比作你的"数字记忆"，那备份就是给这份记忆买的一份保险。想象一下，某天凌晨三点，一次误操作把用户表清空了——那种感觉，大概就像辛苦写了一周的论文，电脑突然蓝屏，而你没有保存。备份不是"要不要做"的问题，而是"怎么做才靠谱"的问题。

## 19.1 备份策略概览

在聊具体工具之前，我们先搞清楚三种主流备份策略：

**全量备份(Full Backup)**：把整个数据库完整拷贝一份。简单粗暴，但占空间、耗时间。就像每次出门前把整个家拍一张全景照片。

**增量备份(Incremental Backup)**：只备份自上次备份以来发生变化的数据。省空间、省时间，但恢复时需要"全量 + 所有增量"，链条长了容易出问题。

**差异备份(Differential Backup)**：备份自上次全量备份以来的所有变化。是增量和全量的折中方案。

| 策略 | 备份大小 | 恢复速度 | 复杂度 |
|------|---------|---------|--------|
| 全量 | 大 | 快 | 低 |
| 增量 | 小 | 慢 | 高 |
| 差异 | 中 | 中 | 中 |

> **Tip：** 生产环境中推荐"全量备份 + 增量备份"组合策略，比如每周日全量备份，每天增量备份。

**两个关键指标：RPO 和 RTO**

在设计备份策略时，你必须搞清楚两个核心指标：

- **RPO（Recovery Point Objective）**：你最多能容忍丢失多长时间的数据？如果你每小时备份一次，RPO 就是 1 小时。这意味着最坏情况下，你会丢失最近 1 小时的数据。
- **RTO（Recovery Time Objective）**：从故障发生到服务恢复，最多能容忍多长时间？如果你的数据库有 500GB，用 mysqldump 恢复可能需要几个小时，这就是你的 RTO。

不同的业务对 RPO 和 RTO 的要求天差地别。一个内部日志系统可能容忍丢失一天的数据（RPO=24h），而一个支付系统可能要求零数据丢失（RPO=0）。同样，一个面向用户的核心系统可能要求 5 分钟内恢复（RTO=5min），而一个报表系统可以容忍几小时的中断。

**备份存储的考量：**

备份文件放在哪里，也是一个需要认真考虑的问题。最基本的原则是"3-2-1 规则"：至少保留 3 份备份，使用 2 种不同的存储介质，其中 1 份放在异地。很多公司把备份放在和数据库同一台服务器上——如果服务器硬盘坏了，备份也跟着一起没了，这就尴尬了。

## 19.2 逻辑备份 vs 物理备份

在深入具体工具之前，我们需要理解逻辑备份和物理备份的本质区别：

**逻辑备份**是将数据导出为 SQL 语句（CREATE TABLE、INSERT 等）。恢复时，MySQL 需要重新执行这些 SQL 语句来重建数据。就好比你要搬新家，把每件家具拆成零件打包，到了新家再一件件组装回去——费时费力，但好处是灵活，你甚至可以在组装过程中做一些调整。

**物理备份**是直接拷贝数据库的底层数据文件（.ibd、.frm 等）。恢复时直接替换文件，速度极快。就像搬新家时直接把整个房间原封不动地搬过去——速度快，但灵活性差，目标环境必须兼容。

| 对比维度 | 逻辑备份 | 物理备份 |
|---------|---------|---------|
| 备份速度 | 慢（需要读取并转换数据） | 快（直接拷贝文件） |
| 恢复速度 | 慢（需要执行SQL） | 快（直接替换文件） |
| 跨版本兼容 | 好 | 差 |
| 跨平台 | 好 | 差 |
| 备份粒度 | 灵活（可选库、表） | 粗粒度（通常整个实例） |
| 适用数据量 | 中小（<50GB） | 大型（>50GB） |

## 19.3 mysqldump：逻辑备份的瑞士军刀

`mysqldump` 是 MySQL 自带的逻辑备份工具，它把数据导出为 SQL 语句。你可以把它理解为"把数据库翻译成一本菜谱，需要的时候照着重新做一遍"。

**基本语法：**

```sql
-- 备份单个数据库
mysqldump -u root -p database_name > backup.sql

-- 备份多个数据库
mysqldump -u root -p --databases db1 db2 db3 > backup.sql

-- 备份所有数据库
mysqldump -u root -p --all-databases > all_backup.sql

-- 备份单张表
mysqldump -u root -p database_name table_name > table_backup.sql
```

**常用生产级选项：**

```sql
mysqldump -u root -p \
  --single-transaction \
  --routines \
  --triggers \
  --events \
  --set-gtid-purged=OFF \
  --quick \
  --lock-tables=FALSE \
  mydb > mydb_backup.sql
```

各选项的含义：

- `--single-transaction`：对 InnoDB 表使用一致性快照，不锁表（重要！）
- `--routines`：导出存储过程和函数
- `--triggers`：导出触发器
- `--events`：导出事件调度器
- `--set-gtid-purged=OFF`：不在备份文件中包含 GTID 信息
- `--quick`：逐行读取，防止大表撑爆内存

> **Warning：** 如果你不加 `--single-transaction`，mysqldump 默认会锁表。在生产环境中，这意味着你的应用在备份期间无法写入数据！

**带压缩的备份：**

```sql
mysqldump -u root -p --single-transaction mydb | gzip > mydb_backup.sql.gz
```

## 19.4 mysqlpump：并行逻辑备份

`mysqlpump` 是 MySQL 5.7 引入的并行备份工具，可以理解为 mysqldump 的"多线程升级版"。

```sql
-- 基本用法（默认4个线程）
mysqlpump -u root -p --default-parallelism=4 mydb > mydb_pump.sql

-- 指定排除某些表
mysqlpump -u root -p \
  --exclude-databases=mysql,sys \
  --exclude-tables=log_table \
  --all-databases > full_pump.sql
```

> **Tip：** mysqlpump 的并行是按数据库级别的，如果你有10个数据库，它可以同时备份。但如果只有一个大数据库，并行效果有限。

## 19.5 mysqlbinlog：二进制日志备份

二进制日志（Binlog）记录了所有数据变更操作，是实现时间点恢复（Point-in-Time Recovery）的关键。

```sql
-- 查看可用的binlog文件
mysql> SHOW BINARY LOGS;

-- 查看binlog事件
mysql> SHOW BINLOG EVENTS IN 'binlog.000001' LIMIT 10;

-- 导出binlog为可读文本
mysqlbinlog --read-from-remote-server \
  --host=localhost --user=root --password \
  binlog.000001 > binlog_dump.txt
```

## 19.6 Percona XtraBackup：物理备份利器

对于大型数据库，逻辑备份（mysqldump）太慢了。Percona XtraBackup 是一个开源的物理备份工具，它直接拷贝数据文件，速度快得多，而且支持热备份（不锁表）。

```sql
-- 全量备份
xtrabackup --backup --target-dir=/data/backups/full \
  --user=root --password=yourpass

-- 准备备份（apply redo log）
xtrabackup --prepare --target-dir=/data/backups/full

-- 恢复
xtrabackup --copy-back --target-dir=/data/backups/full
```

**增量备份示例：**

```sql
-- 基于全量备份做增量
xtrabackup --backup --target-dir=/data/backups/inc1 \
  --incremental-basedir=/data/backups/full \
  --user=root --password=yourpass

-- 准备增量恢复
xtrabackup --prepare --apply-log-only \
  --target-dir=/data/backups/full \
  --incremental-dir=/data/backups/inc1
```

> **Tip：** 数据量超过 50GB 的生产环境，强烈建议使用 XtraBackup 而非 mysqldump。

## 19.7 恢复操作

**从 mysqldump 恢复：**

```sql
-- 恢复单个数据库
mysql -u root -p mydb < mydb_backup.sql

-- 从压缩文件恢复
gunzip < mydb_backup.sql.gz | mysql -u root -p mydb

-- 恢复所有数据库
mysql -u root -p < all_backup.sql
```

**时间点恢复（PITR）：**

假设你在上午10:00做了全量备份，下午3:00有人误删了一张表。你需要恢复到下午2:59的状态：

```sql
-- 第1步：恢复全量备份
mysql -u root -p mydb < full_backup.sql

-- 第2步：找到误操作的时间点
mysqlbinlog --start-datetime="2024-01-15 14:50:00" \
  --stop-datetime="2024-01-15 15:05:00" \
  binlog.000005 | grep -B5 "DROP TABLE"

-- 第3步：应用binlog到误操作之前
mysqlbinlog --start-datetime="2024-01-15 10:00:00" \
  --stop-datetime="2024-01-15 14:58:30" \
  binlog.000005 | mysql -u root -p mydb
```

> **Warning：** 时间点恢复的前提是你的 binlog_format 设置为 ROW 或 MIXED。如果是 STATEMENT 模式，某些操作可能无法精确重放。

## 19.8 自动化备份脚本

生产环境中，手动备份是不靠谱的。下面是一个实用的自动化备份脚本：

```javascript
// auto_backup.js - MySQL 自动备份脚本
const { execSync } = require('child_process');
const path = require('path');
const fs = require('fs');

const config = {
  host: 'localhost',
  user: 'root',
  password: 'your_secure_password',
  databases: ['mydb', 'production_db'],
  backupDir: '/data/mysql_backups',
  retentionDays: 30, // 保留30天的备份
};

function createBackup() {
  const timestamp = new Date().toISOString().replace(/[:.]/g, '-');

  config.databases.forEach(db => {
    const filename = `${db}_${timestamp}.sql.gz`;
    const filepath = path.join(config.backupDir, filename);

    const cmd = [
      `mysqldump -h ${config.host}`,
      `-u ${config.user}`,
      `-p${config.password}`,
      '--single-transaction',
      '--routines --triggers --events',
      `--set-gtid-purged=OFF`,
      `${db} | gzip > ${filepath}`
    ].join(' ');

    try {
      execSync(cmd, { stdio: 'pipe' });
      console.log(`Backup success: ${filename}`);
    } catch (err) {
      console.error(`Backup failed for ${db}:`, err.message);
    }
  });
}

function cleanupOldBackups() {
  const files = fs.readdirSync(config.backupDir);
  const cutoff = Date.now() - config.retentionDays * 86400000;

  files.forEach(file => {
    const filepath = path.join(config.backupDir, file);
    const stat = fs.statSync(filepath);
    if (stat.mtimeMs < cutoff && file.endsWith('.sql.gz')) {
      fs.unlinkSync(filepath);
      console.log(`Cleaned up old backup: ${file}`);
    }
  });
}

createBackup();
cleanupOldBackups();
```

用 crontab 设置每天凌晨3点自动执行：

```sql
-- crontab -e
0 3 * * * /usr/bin/node /opt/scripts/auto_backup.js >> /var/log/mysql_backup.log 2>&1
```

## 19.9 备份验证

备份最大的坑不是"没备份"，而是"备份了但从没验证过能不能恢复"。这就像带了救生圈上船，但从来没试过它能不能充气。真实案例：某知名公司每天自动备份，坚持了两年。某天数据库真的崩了，运维信心满满地拿出备份文件准备恢复，结果发现备份脚本三个月前就悄悄失败了，后面生成的全是空文件。这个教训的代价是三天停机，直接经济损失数百万。

**自动化验证流程：**

一个靠谱的备份验证流程应该包括以下步骤：首先，在独立的测试服务器上自动恢复备份文件；其次，验证恢复后的数据库结构是否完整（表数量、索引、存储过程是否齐全）；然后，抽样检查关键表的数据行数是否与源库一致；最后，运行一组预定义的验证查询，确认数据内容正确。这个过程应该每周自动执行一次，结果发送到运维团队的邮箱或即时通讯群组。

备份文件的完整性校验也很重要。你可以对每个备份文件计算 MD5 或 SHA256 哈希值，并保存到一个校验文件中。恢复之前先验证哈希值是否匹配，防止备份文件在传输或存储过程中被损坏。对于压缩的备份文件，还可以尝试用 `gzip -t` 命令检测压缩文件是否完好。

```sql
-- 验证备份的完整性（在测试服务器上）
mysql -u root -p test_restore < mydb_backup.sql

-- 检查表数量是否匹配
mysql -u root -p -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='test_restore';"

-- 抽样验证数据
mysql -u root -p test_restore -e "SELECT COUNT(*) FROM users;"
```

> **Warning：** 定期做恢复演练！建议每月至少做一次完整的恢复测试。很多公司的"备份策略"在真正需要恢复时才发现根本用不了。

## 小结

本章我们学习了：

- 三种备份策略的适用场景
- mysqldump、mysqlpump、XtraBackup 三大备份工具
- 基于 binlog 的时间点恢复
- 自动化备份脚本的编写
- 备份验证的重要性

记住：**没有经过恢复验证的备份 = 没有备份**。
