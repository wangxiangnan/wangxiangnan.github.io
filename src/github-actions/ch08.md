# 第8章：构建矩阵——一次搞定多版本测试

## 引言

想象你经营一家餐厅，每道新菜在上菜单之前都需要让**不同口味的试吃员**品尝——有人爱吃辣、有人不吃甜、有人对花生过敏。如果让试吃员排队一个个来，等全部吃完你才知道这道菜行不行，效率低得让人绝望。

**构建矩阵（Matrix Strategy）** 就是你 CI/CD 流水线里的"并行试吃团"。它让你同时在**多种操作系统、多种运行时版本、多种配置**下运行同一个 job，一次性覆盖所有需要测试的场景。

---

## 8.1 Matrix Strategy 基本语法

最简单的矩阵就像 JavaScript 的 `Array.prototype.map()`——对一个数组中的每个元素执行同一个操作：

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [16, 18, 20]  # 三个 Node.js 版本

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}  # 引用当前矩阵值

      - run: npm ci
      - run: npm test
```

这个配置会自动生成 **3 个并行的 job**：

- `test (16)` — 使用 Node.js 16
- `test (18)` — 使用 Node.js 18
- `test (20)` — 使用 Node.js 20

它们在 GitHub Actions 的界面上会显示为一个折叠组，展开后可以看到每个组合的运行状态。

**编程隐喻**：`matrix` 就像 `Promise.all()` 的并行执行器——你给它一组参数，它同时启动多个 job，全部完成后才返回结果（除非设置了 `fail-fast`，后文会讲）。

## 8.2 多维度矩阵：笛卡尔积的威力

当你定义多个维度时，GitHub 会自动计算**笛卡尔积**，生成所有可能的组合：

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]  # 3 个 OS
        node-version: [16, 18, 20]                          # 3 个 Node 版本
        # 3 × 3 = 9 个并行 job

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test
```

9 个 job 同时跑起来，就像你同时打开了 9 个终端窗口，每个窗口在不同的操作系统上用不同的 Node 版本跑测试。

### 三维度矩阵（OS × Node × 数据库）

```yaml
jobs:
  integration-test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        node-version: [18, 20]
        database: [postgres, mysql]
        # 2 × 2 × 2 = 8 个组合

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: test
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5
        # 注意：只有 matrix.database == 'postgres' 时才真正用到
      mysql:
        image: mysql:8
        env:
          MYSQL_ROOT_PASSWORD: test
        ports: ['3306:3306']

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - name: 运行集成测试
        env:
          DB_TYPE: ${{ matrix.database }}
        run: npm run test:integration
```

**注意**：services 是无条件启动的，不管 matrix 的当前组合是否需要它。如果你只想为特定数据库启动对应的 service，需要使用 `include`（下节讲解）。

## 8.3 include 和 exclude：精细控制组合

笛卡尔积虽然强大，但有时候你不需要"全部组合"。比如：

- Windows 上不需要测试 Node 16（已经 EOL）
- macOS 上只需要测试最新的 Node 版本
- 某些组合需要特殊的配置参数

### exclude：剔除不需要的组合

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [16, 18, 20]
    exclude:
      # Windows 上不测 Node 16
      - os: windows-latest
        node-version: 16
      # macOS 上只测 Node 20
      - os: macos-latest
        node-version: 16
      - os: macos-latest
        node-version: 18
    # 最终组合: 9 - 3 = 6 个
```

### include：添加特殊组合或额外参数

`include` 有两个用法：

**用法1：添加笛卡尔积之外的额外组合**

```yaml
strategy:
  matrix:
    os: [ubuntu-latest]
    node-version: [18, 20]
    include:
      # 额外添加一个实验性组合
      - os: ubuntu-latest
        node-version: 22  # Node 22 不在上面的列表中
        experimental: true
```

**用法2：为特定组合添加额外参数**

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node-version: [18, 20]
    include:
      # 为 ubuntu + node20 组合添加额外配置
      - os: ubuntu-latest
        node-version: 20
        coverage: true           # 只有这个组合跑覆盖率
        lint: true               # 只有这个组合跑 lint

steps:
  - run: npm ci
  - run: npm test -- --coverage=${{ matrix.coverage || false }}
  - if: matrix.lint
    run: npm run lint
```

**编程隐喻**：`exclude` 就像 `Array.prototype.filter()`——从笛卡尔积中剔除不符合条件的组合。`include` 就像 `Array.prototype.concat()`——往结果集中追加特殊的组合。两者配合使用，你可以构建出任意形状的组合矩阵。

## 8.4 fail-fast 策略：快速止损还是坚持到底？

默认情况下，如果矩阵中的**任何一个 job 失败**，GitHub 会**立即取消所有其他正在运行的 job**。这叫 `fail-fast` 策略。

```yaml
strategy:
  fail-fast: true   # 默认值：一个失败，全部取消
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20]
```

**为什么默认是 fail-fast**？因为如果 Node 18 上的测试失败了，Node 20 大概率也会失败——与其浪费 3 分钟的 CI 时间等结果，不如立即止损，让开发者赶紧去修。

**什么时候关闭 fail-fast**？当你需要**所有组合的完整结果**时：

```yaml
strategy:
  fail-fast: false  # 所有组合都跑完，即使有失败
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [16, 18, 20]
```

典型场景：

- **兼容性报告**：你想知道你的库在每个 Node 版本上的兼容性情况，即使某个版本失败了也要看其他版本的结果。
- **发布前检查**：在发布 npm 包之前，你需要完整的跨平台测试报告来决定支持的最低 Node 版本。
- **Flaky Test 排查**：有时候某个平台的测试不稳定，关闭 fail-fast 可以避免一个平台的偶发失败影响其他平台的结果。

### continue-on-error：允许特定组合失败

有时候某些组合是"预期中的失败"（比如实验性的 Node 版本），你不希望它们的失败阻塞整个 workflow：

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest]
        node-version: [18, 20, 22]
        include:
          - node-version: 22
            experimental: true
    # 当 experimental 为 true 时，失败不算 workflow 失败
    continue-on-error: ${{ matrix.experimental == true }}

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test
```

**生活类比**：`fail-fast` 就像烹饪比赛中的"一票否决"——任何评委给了不及格就淘汰。`continue-on-error` 就像"加分项"——这个选手的甜点环节可能翻车了，但不影响前菜和主菜的评分。

## 8.5 实际案例：全平台 × 多版本 CI 流水线

以下是一个开源 npm 库的完整 CI 配置，需要在多个平台和 Node 版本上验证兼容性：

```yaml
name: Cross-Platform CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  # ─── 第一阶段：快速检查（不纳入矩阵，因为只需要跑一次） ───
  quick-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck

  # ─── 第二阶段：矩阵测试 ───
  test:
    needs: quick-check  # lint 和 typecheck 通过后才跑矩阵测试
    runs-on: ${{ matrix.os }}

    strategy:
      fail-fast: false
      matrix:
        os:
          - ubuntu-latest
          - macos-latest
          - windows-latest
        node-version:
          - '18'
          - '20'
          - '22'
        include:
          # 只在 ubuntu + node 20 上生成覆盖率
          - os: ubuntu-latest
            node-version: '20'
            coverage: true
        exclude:
          # macOS runner 很贵，只测最新 Node 版本
          - os: macos-latest
            node-version: '18'
          - os: macos-latest
            node-version: '22'

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'

      # Windows 上换行符可能导致测试差异，需要处理
      - name: 配置 Git 换行符（Windows）
        if: runner.os == 'Windows'
        run: git config --global core.autocrlf false

      - run: npm ci

      # 根据矩阵值决定是否跑覆盖率
      - name: 运行测试（带覆盖率）
        if: matrix.coverage
        run: npm test -- --coverage --coverageReporters=text --coverageReporters=lcov

      - name: 运行测试（不带覆盖率）
        if: '!matrix.coverage'
        run: npm test

      # 只有覆盖率 job 才上传报告
      - name: 上传覆盖率
        if: matrix.coverage
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/

  # ─── 第三阶段：汇总结果 ───
  test-summary:
    needs: test
    runs-on: ubuntu-latest
    if: always()  # 无论 test 是否全部成功都执行
    steps:
      - name: 检查矩阵测试结果
        run: |
          if [ "${{ needs.test.result }}" == "success" ]; then
            echo "✅ 所有矩阵测试通过！"
          elif [ "${{ needs.test.result }}" == "failure" ]; then
            echo "❌ 部分矩阵测试失败"
            exit 1
          else
            echo "⚠️ 矩阵测试被跳过或取消"
          fi
```

**最终测试矩阵**（排除后）：

| # | OS | Node | 覆盖率 |
|---|-----|------|--------|
| 1 | Ubuntu | 18 | 否 |
| 2 | Ubuntu | 20 | **是** |
| 3 | Ubuntu | 22 | 否 |
| 4 | macOS | 20 | 否 |
| 5 | Windows | 18 | 否 |
| 6 | Windows | 20 | 否 |
| 7 | Windows | 22 | 否 |

共 7 个并行 job（从原始的 3×3=9 中排除了 2 个 macOS 组合），外加 1 个 quick-check job。

## 8.6 矩阵与并行执行的关系

GitHub Actions 中的矩阵 job **默认并行执行**，但有一些限制需要了解：

1. **并发限制**：免费版账号最多 20 个并发 job，Pro 账号 40 个，Enterprise 账号 500 个。如果你的矩阵生成了超过限制的 job 数量，多余的会排队等待。

2. **Runner 可用性**：`ubuntu-latest` 的 runner 资源最充足，`macos-latest` 和 `windows-latest` 可能需要排队（尤其是 macOS）。

3. **成本考虑**：macOS runner 的计费是 Ubuntu 的 **10 倍**，Windows 是 Ubuntu 的 **2 倍**。在设计矩阵时，要平衡覆盖范围和 CI 成本。

```yaml
# 经济实惠的矩阵设计
strategy:
  matrix:
    include:
      # Ubuntu 全覆盖（最便宜）
      - os: ubuntu-latest
        node: '18'
      - os: ubuntu-latest
        node: '20'
      - os: ubuntu-latest
        node: '22'
      # macOS 只测一个版本（最贵）
      - os: macos-latest
        node: '20'
      # Windows 测试两个版本
      - os: windows-latest
        node: '18'
      - os: windows-latest
        node: '20'
    # 总共 6 个 job，而不是笛卡尔积的 9 个
```

## 小结

| 概念 | 作用 | 类比 |
|------|------|------|
| 单维度 matrix | 在一个变量上遍历 | `Array.map()` |
| 多维度 matrix | 笛卡尔积组合 | 嵌套 `for` 循环 |
| `exclude` | 剔除不需要的组合 | `Array.filter()` |
| `include` | 添加额外组合或参数 | `Array.concat()` |
| `fail-fast` | 一个失败全部取消 | 短路求值 `&&` |
| `continue-on-error` | 允许特定组合失败 | `try-catch` |

矩阵设计的三条原则：

1. **够用就好**——不是所有组合都有价值，用 `exclude` 剔除低收益组合。
2. **成本意识**——macOS runner 是吞金兽，精简使用。
3. **分层策略**——快速检查（lint/typecheck）放前面，矩阵测试放后面，避免在低质量代码上浪费矩阵资源。
