# 第9章：TCP 的可靠性机制——序号、确认与重传

TCP 在不可靠的 IP 网络上提供可靠传输，靠的是三大武器：**序号**、**确认**和**重传**。本章深入剖析这些机制的细节和交互。

## 累积确认（Acknowledgment）：确认号的含义

TCP 的确认机制是 **累积的（Cumulative）**。确认号 N 的含义是："我已经正确收到了序号 N 之前的所有字节"——注意，是"所有"，不是"某些"。

举个例子：

```
发送方依次发送：
  段1: seq=0, len=1000  (字节 0~999)
  段2: seq=1000, len=1000 (字节 1000~1999)
  段3: seq=2000, len=1000 (字节 2000~2999)

接收方收到了段1和段3，段2丢失了。
接收方回复：ACK=1000
```

虽然段 3（字节 2000~2999）已经到了，但接收方的 ACK 仍然是 1000——因为段 2（字节 1000~1999）还没到。接收方会把段 3 的数据 **缓存** 起来，等段 2 到达后再一起交付给应用程序。

这就是累积确认的特点：**只确认连续已收到的数据**。这有一个副作用——即使段 3、段 4 都到了，只要段 2 没到，发送方就不知道后面的段已经安全到达。这个问题后面会由 SACK 来解决。

## 滑动窗口：发送方不需要傻等每一个 ACK

最朴素的可靠传输方式是 **停止等待（Stop-and-Wait）**：发送一个段，等 ACK，再发下一个。简单但效率极低——如果 RTT 是 100ms，每秒只能发送 10 个段。如果每个段 1460 字节（标准 MSS），吞吐量只有 14.6KB/s，对于一条 100Mbps 的链路来说，利用率不到 0.12%。

**滑动窗口（Sliding Window）** 解决了这个问题：发送方可以连续发送多个段，而不需要等待每一个 ACK。

```
发送窗口（Send Window）示意：

已确认    已发送未确认          未发送
  |<----->|<----------->|<---------------->|
  0      1000          4000              8000
          ^              ^
        Left           Right

窗口大小 = Right - Left = 3000 字节
```

发送窗口定义了发送方可以发送但尚未被确认的数据范围。当收到 ACK 时，窗口左边界右移（"滑动"），从而允许发送更多数据。

窗口大小由两个因素决定：

- **接收窗口（rwnd）**：接收方在 TCP 报头中声明的窗口大小，反映接收方的处理能力。
- **拥塞窗口（cwnd）**：由拥塞控制算法决定，反映网络的承载能力。

实际发送窗口 = min(rwnd, cwnd)。这是 TCP 设计的精妙之处：**同时受制于接收方的能力和网络的容量**。

## 超时重传（RTO）：怎么估算该等多久？

当发送方发出一个段后，如果在一定时间内没有收到确认，就需要重传。这个时间叫做 **RTO（Retransmission Timeout）**。

RTO 不能太短——如果比 RTT 还短，会触发不必要的重传，浪费带宽并加重网络负担。也不能太长——如果数据包真的丢了，等太久才重传会严重影响性能。

问题的核心在于：**RTT 是动态变化的**。网络拥塞时 RTT 增大，空闲时 RTT 减小。所以 RTO 需要自适应地跟踪 RTT 的变化。

TCP 使用 **SRTT（Smoothed Round-Trip Time）** 算法来估算 RTT，这个算法本质上是一个 **指数加权移动平均（EWMA）**：

```
SRTT = (1 - α) × SRTT + α × RTT_sample

其中 α = 1/8 = 0.125（RFC 6298 推荐值）
```

但光有平均值不够，还需要知道 RTT 的波动程度（方差）。如果 RTT 很稳定，RTO 可以设得紧一些；如果 RTT 波动大，RTO 就需要设得松一些。所以 TCP 还维护一个 **RTTVAR（RTT Variation）**：

```
RTTVAR = (1 - β) × RTTVAR + β × |SRTT - RTT_sample|

其中 β = 1/4 = 0.25
```

最终的 RTO 计算公式：

```
RTO = SRTT + max(G, 4 × RTTVAR)

其中 G 是时钟粒度（通常为 1ms 或更粗的系统定时器精度）
```

RFC 6298 还规定了 RTO 的下限：**RTO 不得小于 1 秒**（实际实现中，Linux 默认最小 RTO 为 200ms）。首次测量 RTT 时，使用以下公式：

```
SRTT = RTT_sample
RTTVAR = RTT_sample / 2
RTO = SRTT + max(G, 4 × RTTVAR)
```

当重传发生时，RTO 会 **指数退避（Exponential Backoff）**：每次重传失败，RTO 翻倍。第一次重传在 1 秒后，第二次在 2 秒后，第三次在 4 秒后……这样可以避免在网络严重拥塞时雪崩式地发送重传。

## 快速重传（Fast Retransmit）：收到 3 个重复 ACK 就重传

超时重传的问题在于：**等待超时太慢了**。如果 RTO 是 1 秒，而一个包在 50ms 时就丢了，发送方还要傻等 950ms 才开始重传。

好在 TCP 有一个更早的信号：**重复 ACK（Duplicate ACK）**。

当接收方收到一个乱序的段时，它会发送一个 ACK，确认号仍然指向"缺口"的位置。比如：

```
发送方发送：段1(seq=0), 段2(seq=1000), 段3(seq=2000), 段4(seq=3000)
段2丢失了。

接收方收到段1 → 回复 ACK=1000
接收方收到段3 → 回复 ACK=1000（重复！因为字节1000~1999还没到）
接收方收到段4 → 回复 ACK=1000（又重复！）
```

当发送方收到 **3 个重复的 ACK=1000** 时，这不是巧合——它强烈暗示段 2 已经丢失了（而不是简单的乱序）。TCP 此时会 **立即重传段 2**，而不需要等待超时。这就是 **快速重传（Fast Retransmit）**。

为什么是 3 个而不是 1 个或 2 个？因为少量的重复 ACK 可能只是乱序导致的（比如段 2 走了一条较慢的路径，稍后就到了）。3 个重复 ACK 是一个经验值，在"误判"和"快速响应"之间取得了较好的平衡。

## 快速恢复（Fast Recovery）：避免不必要的慢启动

在早期的 TCP Tahoe 实现中，快速重传后会把拥塞窗口（cwnd）重置为 1 个 MSS，然后重新进入慢启动。这过于保守了——3 个重复 ACK 说明网络虽然有些拥塞，但还没有严重到需要"从头开始"的地步（毕竟还有一些包成功到达了接收方）。

**快速恢复（Fast Recovery）** 是 TCP Reno 引入的改进：

1. 收到 3 个重复 ACK 时：`ssthresh = cwnd / 2`（保存当前窗口的一半作为阈值）
2. 进入快速恢复：`cwnd = ssthresh + 3`（加 3 是因为有 3 个段已经离开网络被接收方缓存了）
3. 每收到一个重复 ACK：`cwnd += 1`（允许发送更多数据，因为接收方在缓冲数据）
4. 收到对新数据的 ACK 时：退出快速恢复，`cwnd = ssthresh`，进入拥塞避免阶段

快速恢复的核心洞察是：**重复 ACK 意味着数据仍然在网络中流动（只是有些乱序），不应该像超时那样把发送速率降到极低。**

## SACK（Selective Acknowledgment）：精确告知哪些段收到了

累积确认有一个严重的缺陷：**只告诉发送方"连续已收到"的位置，不告诉发送方后面还有哪些段已经到达。**

考虑以下场景：

```
发送方发送了段1~段10，其中段2丢失了。
接收方收到了段1, 段3, 段4, 段5, 段6, 段7, 段8, 段9, 段10。

累积ACK只能回复：ACK=段2的起始序号
发送方只知道段2丢了，但不知道段3~段10都安全到达了。

如果此时发生超时，发送方会重传段2~段10——但实际上只需要重传段2！
```

**SACK（Selective Acknowledgment）** 解决了这个问题。它在 TCP 选项字段中增加了 **SACK 块（SACK Block）**，每个块描述一段"已收到的不连续数据"的范围：

```
TCP 选项中的 SACK 信息：
  SACK Block 1: left=2000, right=3000   （收到了字节 2000~2999）
  SACK Block 2: left=3000, right=5000   （收到了字节 3000~4999）
```

有了 SACK，发送方可以精确地知道哪些段需要重传，哪些段已经安全到达。这大大减少了不必要的重传，特别是在 **窗口较大且丢包率较高** 的网络环境中（如无线网络、跨国链路）。

SACK 在三次握手时通过 SYN 报文中的选项协商启用：`SACK permitted`。现代操作系统（Linux、Windows、macOS）默认都启用了 SACK。

## 编程实践：用 Python 模拟一个简单的可靠传输协议（在 UDP 上实现 ACK+重传）

为了深入理解 TCP 的可靠性机制，我们在 UDP 之上实现一个简化版的可靠传输协议。

**协议设计：**

- 每个数据包 = 4 字节序号 + 数据载荷
- ACK 包 = 4 字节确认序号
- 发送方维护超时重传（固定超时 500ms，简化版）
- 接收方发送累积确认

**发送方（可靠 UDP 客户端）：**

```python
import socket
import struct
import threading
import time

REMOTE_HOST = '127.0.0.1'
REMOTE_PORT = 7000
TIMEOUT = 0.5       # 重传超时（秒）
MAX_RETRIES = 10    # 最大重传次数

class ReliableSender:
    def __init__(self):
        self.sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        self.sock.settimeout(0.1)
        self.addr = (REMOTE_HOST, REMOTE_PORT)
        self.expected_ack = 0  # 期望收到的下一个 ACK
        self.lock = threading.Lock()
        self.acked = threading.Event()

    def send_reliably(self, data: bytes):
        """可靠地发送一段数据"""
        seq = self.expected_ack
        packet = struct.pack('!I', seq) + data
        retries = 0

        while retries < MAX_RETRIES:
            self.sock.sendto(packet, self.addr)
            print(f"  发送 seq={seq}, {len(data)} 字节 (第{retries+1}次)")

            # 等待 ACK
            deadline = time.time() + TIMEOUT
            while time.time() < deadline:
                try:
                    resp, _ = self.sock.recvfrom(1024)
                    ack = struct.unpack('!I', resp[:4])[0]
                    if ack == seq + len(data):
                        print(f"  收到 ACK={ack}，传输完成")
                        self.expected_ack = ack
                        return True
                except socket.timeout:
                    continue

            retries += 1
            print(f"  超时！重传 seq={seq}...")

        print(f"  达到最大重传次数，传输失败！")
        return False

    def send_stream(self, messages: list):
        """按顺序发送多段数据"""
        for msg in messages:
            success = self.send_reliably(msg.encode('utf-8'))
            if not success:
                print("传输中断！")
                return
            time.sleep(0.1)

if __name__ == '__main__':
    sender = ReliableSender()
    messages = [
        "Hello, Reliable UDP!",
        "这是第二条消息",
        "Packet #3 - testing retransmission",
        "Final message"
    ]
    sender.send_stream(messages)
```

**接收方（可靠 UDP 服务器）：**

```python
import socket
import struct
import random

LOCAL_HOST = '127.0.0.1'
LOCAL_PORT = 7000

def main():
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.bind((LOCAL_HOST, LOCAL_PORT))
    print(f"可靠 UDP 服务器监听 {LOCAL_HOST}:{LOCAL_PORT}")

    next_expected = 0

    while True:
        data, addr = sock.recvfrom(1024)
        seq = struct.unpack('!I', data[:4])[0]
        payload = data[4:]

        # 模拟丢包：20% 的概率不发送 ACK
        drop_ack = random.random() < 0.2

        if seq == next_expected:
            print(f"收到 seq={seq}, {len(payload)} 字节: "
                  f"{payload.decode('utf-8', errors='replace')}")
            next_expected = seq + len(payload)

            if drop_ack:
                print(f"  [模拟丢包] 不发送 ACK，等待重传")
                continue

            # 发送累积 ACK
            ack = struct.pack('!I', next_expected)
            sock.sendto(ack, addr)
            print(f"  发送 ACK={next_expected}")
        else:
            # 乱序包，仍然发 ACK（重复 ACK）
            ack = struct.pack('!I', next_expected)
            sock.sendto(ack, addr)
            print(f"  收到乱序包 seq={seq}，期望 {next_expected}，发送重复 ACK")

if __name__ == '__main__':
    main()
```

运行这个程序，你会看到类似输出：

```
发送 seq=0, 20 字节 (第1次)
收到 ACK=20，传输完成

发送 seq=20, 18 字节 (第1次)
超时！重传 seq=20...          ← 服务器故意丢了 ACK
发送 seq=20, 18 字节 (第2次)
收到 ACK=38，传输完成

发送 seq=38, 36 字节 (第1次)
收到 ACK=74，传输完成
```

这个简单实现展示了 TCP 可靠性的核心思想：序号用于标识数据、确认号用于告知已收到的数据、超时用于检测丢失、重传用于恢复丢失。TCP 只是把这些机制做得更加精细和高效。

## 抓包实践：制造丢包场景，观察 TCP 重传行为

在 Linux 上，我们可以用 `tc`（Traffic Control）工具模拟网络丢包：

```bash
# 对本地回环接口施加 10% 的丢包率
sudo tc qdisc add dev lo root netem loss 10%

# 验证设置
tc qdisc show dev lo
```

然后在另一个终端启动一个大文件传输（或使用 `iperf3`）：

```bash
# 终端1：启动 iperf3 服务器
iperf3 -s

# 终端2：运行 10 秒的 TCP 测试
iperf3 -c 127.0.0.1 -t 10
```

同时在 Wireshark 或 tcpdump 中抓包：

```bash
sudo tcpdump -i lo port 5201 -nn -S -w retransmit.pcap
```

在 Wireshark 中打开 `retransmit.pcap`，使用过滤器 `tcp.analysis.retransmission` 可以高亮所有重传报文。你会观察到：

```
No.  Time        Source          Destination   Info
1    0.000000    127.0.0.1       127.0.0.1     TCP 52345 > 5201 [SYN] Seq=0
2    0.000012    127.0.0.1       127.0.0.1     TCP 5201 > 52345 [SYN,ACK] Seq=0 Ack=1
3    0.000015    127.0.0.1       127.0.0.1     TCP 52345 > 5201 [ACK] Seq=1 Ack=1

# 正常数据传输...
45   0.012345    127.0.0.1       127.0.0.1     TCP [TCP segment] Seq=58401 Len=1448
46   0.012350    127.0.0.1       127.0.0.1     TCP [TCP segment] Seq=59849 Len=1448
47   0.012355    127.0.0.1       127.0.0.1     TCP [TCP segment] Seq=61297 Len=1448

# 丢包后的重传（注意序号与之前的某个包相同）
52   0.212400    127.0.0.1       127.0.0.1     TCP [TCP Retransmission] Seq=59849 Len=1448
     ↑ 距原始发送约 200ms（本地回环的 RTO 较小）

# 重复 ACK（接收方检测到丢包）
48   0.012400    127.0.0.1       127.0.0.1     TCP [TCP Dup ACK] Ack=59849
49   0.012410    127.0.0.1       127.0.0.1     TCP [TCP Dup ACK] Ack=59849
50   0.012420    127.0.0.1       127.0.0.1     TCP [TCP Dup ACK] Ack=59849
51   0.012430    127.0.0.1       127.0.0.1     TCP [TCP Fast Retransmission] Seq=59849
     ↑ 三个重复 ACK 触发快速重传（在 RTO 之前！）
```

**关键观察：**

- 重传报文的 **序号与原始报文完全相同**，但时间戳不同。
- 快速重传（Fast Retransmission）比超时重传更快——它在收到 3 个重复 ACK 后立刻触发，不需要等 RTO。
- Wireshark 会用红色标记重传报文、用黄色标记重复 ACK，使分析一目了然。
