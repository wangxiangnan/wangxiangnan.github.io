# 第11章：证书链与 verify：信任如何传递

> [!TIP] Part 3: CA 与 TLS 实战篇（实战篇）
> 上一章签发的证书部署后，阿雪的终端还是报错——信任没有自动到达客户端。本章拆开证书链：信任如何沿着「根 → 中间 → 叶子」逐级传递，nginx 为什么要配 fullchain，以及 verify 命令背後的递归逻辑。

auth 服务部署当天，阿雪在测试机上调接口，收获报错一条：

```text
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

她拿着问题来问：证书明明是合法的内部 CA 签的，verify 也过了，怎么 curl 不认？答案是本章的主题——**信任不是证书自带的属性，而是一条要亲手铺到位的链**。证书有效只代表「章是真的」；客户端还得知道「这个章的章，我信不信」。把这条递归铺明白，这类报错就永远有了方向。

## 11.1 信任的递归：链是什么

第10章建的是两级体系：根 CA 直接签发服务器证书。现实世界的公网体系普遍是三级：根 CA 签发中间 CA（Intermediate CA），中间 CA 再签发服务器证书。信任沿着签名逐级传递：

```text
根证书 Root CA（信任锚）        ← 自己给自己盖章
  CA:TRUE, pathlen:1           私钥离线深藏
   │ 签发
   ▼
中间证书 Intermediate（代办点）  ← 由根签发
  CA:TRUE, pathlen:0           私钥在线服务
   │ 签发
   ▼
叶子证书 Leaf（终端用户所见）    ← 由中间签发
  CA:FALSE                     私钥在服务器
```

验证一张叶子证书，客户端的问题是递归的：「叶子的章是中间 CA——中间 CA 我信吗？它的章是根 CA——根 CA 在我的预装信任库里吗？在，整条链成立。」任何一环断掉，报错就是阿雪见到的那条。

那为什么要加一层中间 CA？三个理由，全部来自血泪教训：

| 理由 | 展开 |
| ---- | ---- |
| 根私钥离线 | 根私钥越少使用越安全。中间 CA 在线干日常签发的脏活累活，根私钥锁进离线保险柜，一年用不了几次 |
| 事故隔离 | 某个中间 CA 出事（私钥泄露、滥发证书），撤销这一支即可，根毫发无伤——DigiNotar 事件里浏览器吊销的就是它的签发能力 |
| 灵活分级 | 不同业务线、不同安全等级可用不同中间 CA，各管一摊 |

云笔记内部 CA 两级（根直签服务器证书）是教学从简；当内部证书规模上百、或有分区签发需求时，照 10.2 的配方再造一张 `CA:TRUE, pathlen:0` 的中间证书即可——根的 `pathlen:0` 要改成 `pathlen:1`（允许下面挂一层）。

## 11.2 verify 实战：递归校验的现场

`verify` 命令就是把上一节的递归跑给你看。先看三级链的完整验证（用一个公网站点做素材，拉取它的链）：

```bash
# 拉一张真实站点证书与其链（s_client 第12章正式介绍，先抄）
echo | openssl s_client -connect example.com:443 -showcerts 2>/dev/null \
  | openssl x509 > leaf.pem

# 最简验证：-CAfile 给信任锚（系统默认信任库）
openssl verify leaf.pem
```

```text
leaf.pem: OK
```

`-CAfile` 不写时 verify 使用系统信任库（Linux 在 `/etc/ssl/certs/`），所以公网证书验证直接 OK。三级链的显式验证这样写：

```bash
openssl verify -CAfile root.crt -untrusted intermediate.pem leaf.pem
```

参数分工精确定义：**`-CAfile` 给信任锚（根），`-untrusted` 给待补的中间证书**。命名反直觉但精确——中间证书本身不是信任来源，只是帮你把「叶子 → 根」这条桥搭上。如果只给叶子不给中间：

```text
leaf.pem: error 20 at 1 depth lookup: unable to get local issuer certificate
```

报错里的 `at 1 depth` 是链上的层号：depth 0 是叶子，depth 1 是它的签发者——这行字直接告诉你断在哪一层。**读 verify 的报错先看 depth，排查就有了靶子**。

verify 还能把「它搭好的链」展示给你看——`-show_chain`：

```bash
openssl verify -show_chain -CAfile root.crt issued/auth.crt
```

```text
issued/auth.crt: OK
Chain:
depth=0: C = CN, O = CloudNote, CN = auth.cloudnote.internal (untrusted)
depth=1: C = CN, O = CloudNote, CN = CloudNote Internal Root CA
```

depth 0 是被验的叶子，depth 1 起是 verify 沿途收集的签发者。再进阶一个参数：`-purpose sslserver` 会连证书的**用途**一起验（EKU 必须含 serverAuth）——第8章讲的「扩展约束没有被违反」这一条，就是它在执行：

```bash
openssl verify -CAfile root.crt -purpose sslserver issued/auth.crt
```

## 11.3 fullchain：服务器要替客户端补链

递归校验有个常被误解的前提：客户端手里的链，是**服务器在握手时发过来的**。根证书客户端自己有（信任库），但中间证书客户端未必有——于是规矩形成：**服务器必须发送「叶子 + 全部中间证书」，根证书不发**（发了也没用，客户端只认自己信任库里那份）。

这个「叶子 + 中间」的合集就是 fullchain（全链文件）。组装与部署：

```bash
# 组装：叶子在前，中间在后（顺序错误部分客户端会拒绝）
cat leaf.pem intermediate.pem > fullchain.pem

# nginx 侧（第13章完整展开）
# ssl_certificate     /etc/cloudnote/auth/fullchain.pem;
# ssl_certificate_key /etc/cloudnote/auth/tls.key;
```

云笔记的两级内部 CA 场景，服务器只发叶子证书（没有中间层），根证书走的是**客户端信任库**——所以阿雪的修复就是把 `root.crt` 装进她的信任库（11.5 的实验）。而对接公网 CA 签发的证书时，fullchain 缺中间是历史悠久的经典事故，典型症状极具迷惑性：**桌面浏览器一切正常（浏览器会通过证书里的 AIA 字段自动下载缺失的中间证书），而 curl、Java 服务、部分手机却报错**（它们不做这个自动补链）。「浏览器好好的为什么手机不行」，十有八九是链没发全。

服务器发链的三种姿势，对照一眼：

| 服务器发送内容 | 结果 |
| ---- | ---- |
| 只发叶子 | 浏览器靠 AIA 救回（未必成功），curl/Java/手机报 `unable to get local issuer` |
| 叶子 + 中间（fullchain） | **正确姿势**，所有客户端通吃 |
| 叶子 + 中间 + 根 | 多数客户端无碍（忽略多余部分），但白白泄露内网结构，也不合规 |

fullchain 内部的顺序也有讲究：**叶子在最前，中间按「离叶子近的在前」排列**。顺序错了，一部分严格实现的客户端直接拒收，报错却指向别处——排查时用 `grep -c "BEGIN CERTIFICATE"` 数一数 fullchain 里装了几张证书（第6章的手法），再逐张看 Subject 确认顺序。

## 11.4 撤销查询：CRL 与 OCSP

第10章埋的撤销机制，这里补全生态。证书被撤销后，世界如何知道？两大机制：

| 机制 | 全称 | 工作方式 | 姿态 |
| ---- | ---- | ---- | ---- |
| CRL | 证书撤销列表 | CA 定期发布一张「作废序列号清单」，客户端下载比对 | 拉模式，清单可能很大 |
| OCSP | 在线证书状态协议 | 客户端对单张证书实时问 CA：「这张还有效吗？」 | 问模式，实时但要等回应 |

OpenSSL 里两者都有对应操作：CRL 用 `openssl ca -gencrl` 生成、`openssl verify -crl_check -CRLfile crl.pem` 校验；OCSP 用 `openssl ocsp` 子命令查询，或看服务器有没有把 OCSP 应答「钉」在握手里（OCSP stapling，`s_client -status` 可见，第12章实验）。但工程上必须诚实告诉你行业的真实状态：**撤销检查普遍是「软失败」的**——OCSP 服务器联系不上时，多数客户端选择放行而不是拦截，因为「因为查不了证书而断网」比「放过一张可疑证书」的代价更直观。这套尴尬正是第10章「短有效期 + 自动轮换」哲学的终极论据：把安全押在「过期即失效」上，比押在撤销查询上可靠得多。

CRL 这条路值得亲手走一遍最小闭环——假设 auth 服务要下线，撤销它：

```bash
# 1. CA 侧登记撤销（openssl ca 路线）
openssl ca -config openssl.cnf -revoke issued/auth.crt

# 2. 生成新的 CRL 并分发给客户端
openssl ca -config openssl.cnf -gencrl -out crl.pem

# 3. 客户端带 CRL 验证——被撤销的证书现出原形
openssl verify -crl_check -CRLfile crl.pem -CAfile root.crt issued/auth.crt
```

```text
error 23 at 0 depth lookup: certificate revoked
```

`error 23` 与第8章那张字段速查表对上了：撤销是按**序列号**定位的——CRL 里躺着一串被作废的序列号，验到匹配即拒绝。轻量路线（`x509 -req` 签发）没有数据库、造不出 CRL，这正是工程上迟早要升级 `openssl ca` 的原因。

OCSP 的现场则长这样（如今更像一份「格式标本」——公共 CA 的 OCSP 服务正在陆续关闭，Let's Encrypt 已于 2025 年停用，第12章还会回到这个趋势）：

```bash
openssl ocsp -issuer chain.pem -cert leaf.pem \
  -url http://ocsp.example-ca.example -resp_text -noverify 2>/dev/null | head -5
```

```text
leaf.pem: good
    This Update: Nov  6 02:00:00 2026 GMT
    Next Update: Nov 13 02:00:00 2026 GMT
```

`good` / `revoked` / `unknown` 三种答案，附一段有效期——OCSP 应答本身也是 CA 签名的数据，验签思想无处不在。

## 11.5 信任锚管理：把根证书装进客户端

回到阿雪的报错。修复 = 把云笔记根证书装进她的信任库。各平台的操作一张表收全：

| 平台 | 信任库位置 | 安装命令 |
| ---- | ---- | ---- |
| Debian/Ubuntu | `/usr/local/share/ca-certificates/` | `sudo cp root.crt /usr/local/share/ca-certificates/cloudnote-ca.crt && sudo update-ca-certificates` |
| RHEL/CentOS | `/etc/pki/ca-trust/source/anchors/` | `sudo cp root.crt /etc/pki/ca-trust/source/anchors/ && sudo update-ca-trust` |
| macOS | 系统钥匙串 | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain root.crt` |
| Windows | 系统证书存储 | 管理员运行 `certutil -addstore -f ROOT root.crt` |
| Java 服务 | JDK cacerts | `keytool -importcert -alias cloudnote-ca -file root.crt -keystore cacerts` |

装完后阿雪的原命令直接通过：

```text
$ curl https://auth.cloudnote.internal/healthz
{"status":"ok"}
```

注意这次连 `--cacert` 都不用写——信任进了系统级信任库，所有遵循系统库的工具（curl、浏览器、多数语言运行时）全部受益。对比第9章的两种信任方式：`--cacert` 是**单点信任**（只这一条命令信你），信任库导入是**批量信任**（整台机器信你）——内部 CA 的价值就在于把「逐台逐命令信任」升级成「一次导入，处处信任」。

一个常被追问的细节：**浏览器不一定用系统信任库**。Linux 上的 Chrome/Chromium 用系统库，Firefox 却自带独立的 NSS 证书库（Windows/macOS 上主流浏览器基本都随系统库）。所以偶有「curl 通了 Firefox 还红牌」的现场——给 Firefox 单独导入：

```bash
# Firefox/Linux：往 NSS 库导入（certutil 来自 libnss3-tools 包）
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n cloudnote-ca -i root.crt
```

排查「工具 A 信任、工具 B 不信任」时，第一问永远是：**它读的是哪个信任库**。

> [!WARNING] 导入根证书 = 让渡信任
> 把一张根证书装进信任库，等于宣告「这张证书签出的一切我都信」。只导入你**完全理解其私钥保管方式**的根证书——公司发的、自己建的可以；来路不明的根证书一旦导入，等于给该私钥的持有者颁发了全设备通行证（浏览器会对导入根证书弹红字警告，不是小题大做）。

## 11.6 实验：把内网信任铺到位

目标：让 203.0.113.10 上的 auth 服务被全团队成员无感信任，并补全 verify 的手感。

```bash
# 1. 在服务器上确认服务侧三件套齐备（第10章 10.6 已放置）
ls -l /etc/cloudnote/auth/

# 2. 把根证书分发给团队成员（scp / 内部 Wiki 附件均可）
scp wang@203.0.113.10:/etc/cloudnote-ca/root.crt .

# 3. 客户端导入信任库（Ubuntu 示例）
sudo cp root.crt /usr/local/share/ca-certificates/cloudnote-root.crt
sudo update-ca-certificates

# 4. 验收一：verify 用系统信任库直接过
openssl verify auth.cloudnote.internal.crt
# 期望: auth.cloudnote.internal.crt: OK

# 5. 验收二：curl 不带任何参数直连
curl https://auth.cloudnote.internal/healthz
```

验收三（可选进阶）：故意把服务器只配叶子、而公网场景缺中间——用 `s_client -showcerts` 对比一个配置正确的公网站点与一个故意缺链的本地 s_server，亲眼看到「Chain depth」的差别。

验收四（负向演练，同样重要）：把一张**别的**自签证书冒充根装进临时信任文件，verify 必须失败：

```bash
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout fake-key.pem -out fake-root.crt -days 1 -subj "/CN=Fake CA"
openssl verify -CAfile fake-root.crt issued/auth.crt
# 期望: error 20 at 1 depth lookup: unable to get local issuer certificate
```

假根验不出真链——**换任何一个字节的信任锚，递归都会在签名处断掉**。这个演练让你对「信任锚不可调包」有了手感，它是 11.5 WARNING 的实验版。

## 本章小结

- 信任是递归的：验叶子 → 查中间 → 查根 → 信任库兜底，任何一环断掉即报错；**报错里的 depth 告诉你断在哪层**
- 中间 CA 的三重意义：根私钥离线、事故隔离、分级管理——生产级 CA 几乎都是三级链
- verify 参数分工：`-CAfile` 给信任锚，`-untrusted` 给搭桥的中间证书
- 服务器必须发送「叶子 + 中间」（fullchain），根证书不发；缺中间的典型症状是**浏览器正常、curl/Java/手机报错**
- 撤销机制（CRL/OCSP）普遍软失败：短有效期 + 自动轮换是更可靠的失效保障
- 信任锚安装即信任让渡：内部 CA 根证书导入信任库后全机受益，但只导入你理解其私钥保管的根

**下一章预告**：信任铺好了，服务跑起来了——然后呢？下一章拿起排错的第一工具 `s_client`：握手怎么看、证书到期怎么盯、协议版本怎么探，危机三里那次凌晨全站报错的复盘，就靠它完成。
