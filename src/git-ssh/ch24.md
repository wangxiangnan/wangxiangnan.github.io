# 第24章：安全复盘与综合排错

> [!TIP] Part 4: 协同交响篇（交汇篇）
> 末章不引入新命令，只做三件事：把 24 章的知识串成一次完整旅行，演练密钥泄露的应急处置，再用一场连环故障检验你的排错功力。这是全书的大合奏。

第23章收尾时，`git push` 已经能自动上线——从工作区的一行修改到用户的浏览器，中间每一环你都亲手搭过。但搭过和真正理解是两回事：你能不能不看笔记，讲清这条链路上每一站发生了什么？出事时能不能顺着链路找到断点？本章就是这场毕业考试。它没有新知识，只有新连接——把已经认识的每一站，串成一条说得出口的完整旅程。

## 24.1 一条命令的旅行

先给整条链路画一张全景图。从你敲下 `git push` 的那一刻起，数据要经过九站：

```mermaid
flowchart LR
  W["工作区改动\n第3章"] --> C["git add + commit\n第3章"]
  C --> R["本地 refs 前移\n第9章"]
  R --> S["拉起 ssh 子进程\n第19章"]
  S --> E["加密通道\n第4-6章"]
  E --> U["服务端 receive-pack\n第19章"]
  U --> P["pre-receive 门禁\n第22章"]
  P --> D["post-receive 部署\n第23章"]
  D --> V["curl 验证上线\n第23章"]
```

fetch 是同一张图的镜像放映：方向反过来、upload-pack 与 receive-pack 对调，九站同样缺一不可。

九站逐个点名，每一站都能说出「发生了什么」和「哪一章讲过」：

| 站点 | 发生的事 | 出处 |
|------|---------|------|
| 1 工作区改动 | 文件修改，尚未被 Git 看见 | 第3章 |
| 2 add + commit | 修改成为带唯一哈希的快照对象 | 第3、7章 |
| 3 refs 前移 | main 指针文件内容换成新哈希 | 第9章 |
| 4 ssh 子进程 | git 拉起 ssh，把传输外包出去 | 第19章 |
| 5 加密通道 | 密钥认证、指纹核实、会话加密 | 第4-6章 |
| 6 receive-pack | 服务端收对象，反向协商只收缺的 | 第19章 |
| 7 pre-receive | 门禁脚本逐笔检查，非零整批拒绝 | 第22章 |
| 8 post-receive | checkout 到发布目录，重启服务 | 第23章 |
| 9 上线验证 | curl 看到新版本，链路闭环 | 第23章 |

用一段话把图走完：你在 `~/cloudnote` 改了文件，`git add` 进暂存区、`git commit` 成一个快照对象，main 的 refs 文件前移一个哈希；push 时 git 自己不懂网络，拉起 ssh 子进程，ssh 用密钥对完成双向认证——客户端核对服务器指纹，服务器验你的私钥——然后建起加密通道；对面的 git-receive-pack 收下对象，pre-receive 钩子逐一检查，退出码为零才放行更新 refs；随后 post-receive 钩子把 main 铺进发布目录、重启服务；最后一条 curl，看到新版本号。九站里会主动说「不」的有三处：指纹不符（第 5 站）、pre-receive 返回非零（第 7 站）、服务端拒绝非快进更新（第 6 站）——记住这三个「不」，再遇到任何推送失败，你都有了下锚的地方。

九站里，前三站是你能完全控制的本地世界，中间两站是 SSH 管的通道世界，后四站是 Git 管的服务端世界。**对照第0章那句「Git 管内容、SSH 管通道」，这张图就是它的完整展开**。里程碑 M3（口头复述 pull 全过程）与 M4（自建 push 即部署服务）到此都有了着落。建议合上教程对着这张图口头讲一遍，讲不顺的地方就是要回炉的章节——这正是 M3 的自测方式。

## 24.2 密钥泄露应急

旅行走通了，现在演练最坏情况。两种典型场景：

- **场景一：私钥误提交进 git**。最常见的姿势是 `git add .` 一把梭——调试时把包含 id_ed25519 的备份压缩包放进了仓库目录，而 .gitignore（第12章）里没有这条规则。GitHub 会自动扫描常见密钥格式并在推送时拦截（push protection），但拦截只认已知格式，自命名文件照样漏网。
- **场景二：电脑丢失**。磁盘没加密、私钥没设 passphrase（第14章），拿到机器就等于拿到钥匙。处理原则与场景一相同：**视同私钥已泄露**。顺带两条预防：全盘加密（LUKS 或 BitLocker）与给私钥设 passphrase，能把「丢电脑」从灾难降级为麻烦。

无论哪种，处置清单如下。总原则是先断门、再补锁、后查案——顺序不能乱，吊销永远第一位：

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 立即吊销：GitHub 上删除该公钥；逐台服务器清查 authorized_keys 删除对应行 | 关上所有已知大门 |
| 2 | 生成新钥对，重新登记（第5、20章的流程） | 恢复工作能力 |
| 3 | 核查泄露时间窗内的登录日志（第18章的方法） | 确认是否已被利用 |
| 4 | 检查 ssh-agent 缓存与其他机器上有没有该钥的副本 | 堵住衍生副本 |
| 5 | 若私钥进了 git 仓库：照常执行以上步骤，删除提交不是解药 | 见下文 |

第 1 步的「逐台清查」有把钥别名的，清查可以脚本化——authorized_keys 每行末尾的注释段（登记时写的 wang-laptop）这时成了搜索索引：

```bash
ssh wang@203.0.113.10 "grep -n wang-laptop ~/.ssh/authorized_keys"
  # 输出行号即待删行，确认后编辑删除
```

清查范围要覆盖所有登记过这把钥的地方——云服务器、跳板机、家里的旧笔记本，一台都别漏。第 3 步按第18章的方法翻 /var/log/auth.log 或 journalctl，重点看泄露时间窗内有没有「非你 IP」的 Accepted 记录——有没有人真的进来过，决定后面是「虚惊一场」还是「升级为入侵事件」。

第 5 步值得单独展开，因为它对应一个害人不浅的侥幸心理：「我把文件从仓库里删掉不就行了」。不行。第8章讲得很清楚：revert 只是追加反向提交，reset 只是移动指针——**已提交的对象会永远留在历史里**，任何人 clone 之后都能从历史里把你的私钥原样翻出来。git filter-repo 这类工具确实能重写历史清洗敏感文件，但那需要强推、需要所有协作者重置本地、需要平台清缓存——做完这一切，正确的心智依然必须是：**这把钥已经泄露，必须换**。更换密钥是唯一正解，历史清理只是补救。

清单里反复出现的「泄露时间窗」要抠准定义：从私钥第一次可能被未授权者看到的时刻算起——场景一是那次提交的时间戳，场景二是电脑最后一次离手的时刻。后续的日志核查、影响评估都以这个窗口为边界，宁可算宽一天，不可算窄一小时。

> [!WARNING] 换钥不是麻烦，是止损
> 一次换钥的成本是十分钟；被撬开的代价按泄露范围算：部署密钥（第23章）影响一个仓库，个人主钥影响你所有服务器与账号。预防靠 .gitignore（第12章）把私钥挡在仓库外，不靠平台兜底。

## 24.3 前向保密的安慰

换钥处理完，一个后怕的问题自然浮上来：私钥泄露之前，攻击者有没有可能已经录走了我的加密流量，等拿到私钥再回头解密？

答案是否定的，而且这要归功于第5章讲过的一个细节：**会话密钥是每次连接临时协商出来的**。现代 SSH 的密钥交换（curve25519 等算法族）属于临时密钥协商——双方用各自的一次性随机数现场算出会话密钥，用完即弃，长期私钥只参与身份认证，从不参与数据加密。打个比方：长期私钥是证明你身份的证件，而每个会话的保险柜钥匙都是当场浇铸、当场熔掉的——证件将来被偷，也开不了早已熔毁的锁。这个性质有个正式名字：**前向保密（Forward Secrecy）**——私钥将来泄露，过去的加密流量依然解不开。用抓包工具录一段 ssh 会话，你只能看到密文与随机数——这不是碰巧，是设计使然。

这个保护你不用配置，现代 OpenSSH 的默认算法组全部具备，但可以亲眼验证：第19章教过的 `-v` 大法再看一眼，输出里有这样一行：

```text
debug1: kex: algorithm: curve25519-sha256
  # kex 即 key exchange，curve25519 族属于临时密钥交换，自带前向保密
```

如果你的输出是另一串算法名，查一查它是否还在现代默认列表里——常年不更新的旧系统，最容易在这里掉队。

> [!NOTE] 前向保密的边界
> 它只保护过去的流量，不保护现在的你：agent 里还活着的私钥（第14章）、已经沦陷的当前会话、终端里待输的密码，都在射程之外。「现在」靠的还是老三样——钥不离身、权限最小、勤看日志。

顺带回应一个常见误解：换一台服务器不会影响其他会话——每个连接的会话密钥独立协商，互不继承，一扇门坏了不必换整栋楼的锁。安全没有银弹，前向保密只是把「过去」这一段锁死了，这就是它的全部承诺，也足够珍贵。

## 24.4 指纹告警决策树

通道世界还有一个老朋友要复盘：连接时突然弹出的红色警告，第6章的主角。它的原文值得再读一遍，因为每个字都是线索：

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
...
Host key verification failed.
```

它有两种截然相反的解释——服务器重装了，或者你正在被中间人劫持。处理它靠的不是胆量，是一棵决策树；树上没有一条路写着「无视警告」，这一项不在菜单里：

```text
        ssh 警告：主机指纹变了
                │
        能否当面或电话核实来源？
          ┌─────────┴─────────┐
        能核实               不能核实
          │                    │
     服务器重装过吗？        按攻击处理：
       ┌─────┴─────┐      换网络再操作
     重装过      没重装      核查服务器状态
        │        停手追查     清查 authorized_keys
   指纹与告知一致？           检查登录日志
     ┌────┴────┐             必要时换钥改密
   一致       不一致
  更新记录    停手追查
```

左边这条是正路，也是日常最常走的：机房同事告知「今晨重装了 203.0.113.10」，你登录服务器（或让管理员）核对真实指纹，一致后更新本地记录：

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
  # 在服务器上查看真实指纹，与告警弹窗里的新指纹比对

ssh-keygen -R 203.0.113.10
  # 从 known_hosts 移除旧记录（旧内容自动备份为 known_hosts.old）

ssh wang@203.0.113.10
  # 重连，核对弹窗指纹一致后再输 yes 写入新记录
```

右边这条没有商量余地：**来源无法核实时，按攻击处理**，而不是图省事删一行 known_hosts 继续连。换一个网络环境再试（公共 Wi-Fi 是劫持高发区）、核查服务器是否真的变动、清查 authorized_keys 有没有陌生公钥、翻登录日志——四步做完若无异常，再回头处理 known_hosts 不迟。删记录是最后一步，不是第一步。另外 `ssh-keygen -R` 会把旧记录备份进 known_hosts.old，更新错了随时能回退——工具的设计者早替你留了后悔药。

自动化时代这条纪律还要加码：如果你的部署脚本（第23章）里藏着「遇告警自动删 known_hosts 重连」的逻辑，中间人攻击就形同虚设——**自动化的便利会放大每一个被埋进去的坏习惯**，指纹核实这种事，永远留给人做。顺手把自己的部署脚本翻出来检查一遍，是今天最值得做的五分钟。

四种常见成因先对号入座：

| 告警场景 | 指纹变化原因 | 处置 |
|---------|-------------|------|
| 服务器重装系统 | 主机钥重新生成 | 核实后更新记录 |
| 迁移到新机器 | 新机器新钥 | 核实新机指纹后更新 |
| IP 被复用 | 别人的机器顶了这个 IP | 高度警惕，核实归属 |
| 无故告警 | 可能是中间人劫持 | 按攻击处理 |

## 24.5 综合故障演练

毕业考来了。周六下午，你照常 `ssh wang@203.0.113.10` 想看一眼部署日志，却连不上了。已知线索只有三条传闻：运维动过服务器、你上周清理过旧钥、有人改过服务器权限。用第18章的分层排查法，一层一层走。

第零层：先确认没犯低级错——地址没敲错、本地网络正常（随便开个网页试试）。这一层最不起眼，但按统计救回来的人最多：低级错误不排除，高级排查全白费。

第一层：网络与端口。报错原文先看清楚：

```text
ssh: connect to host 203.0.113.10 port 22: Connection refused
```

Connection refused 是「机器在、门没了」——不是超时（那是网络不通），是端口明确拒绝。ping 得通说明主机活着，那问题在 sshd 的监听端口。给运维打个电话：**sshd 端口改成了 2222，通知漏发了**。服务器上一条命令即可实锤：

```bash
ss -tlnp | grep ssh
  # LISTEN 0.0.0.0:2222 —— 门确实挪到了 2222
```

验证并顺手把它写进 config（第13章），下次就不用记了：

```bash
ssh -p 2222 wang@203.0.113.10
  # 能进认证阶段了，但报 Permission denied (publickey)
```

第二层：客户端密钥。新报错说明通道已通、卡在认证。上 `-v` 看它掏了什么钥匙（第19章的外包机制让 ssh 的内心活动全程可见）：

```text
debug1: identity file /c/Users/you/.ssh/id_ed25519-old type -1
debug1: Trying private key: /c/Users/you/.ssh/id_ed25519-old
debug1: No more authentication methods to try.
```

`type -1` 的意思是「文件不存在」——config 里的 IdentityFile 还指着上周清理掉的旧钥，加上 IdentitiesOnly yes 限定了只掏这一把，于是 ssh 两手空空。IdentitiesOnly yes 是第13章多账户场景的常见配置，它的副作用此刻显形：指定的钥不在，就绝不用别的。修正 config 里的路径指向新钥，再连：还是 Permission denied。

第三层：服务端授权。客户端已经没什么可查的了——钥在掏、指纹对、端口对，那就只剩服务端说不。这台是你自己的机器，上去看日志（第18章教过，真相在这里）：

```bash
sudo tail -5 /var/log/auth.log
```

日志里的两行说明了全部：

```text
Authentication refused: bad ownership or modes for file
/home/wang/.ssh/authorized_keys
```

第三起事故现身：有人批量改权限时把 authorized_keys 改成了 666——组和其他人可写，sshd 的 StrictModes（第17章）直接拒绝使用它。顺带纠正一个流传很广的说法：**644 其实是合法的**，sshd 只拒绝「组/其他人可写」或属主不对；真正触发拒绝的是 666 这类值，或者 .ssh 目录被改成 777。修复：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

改完不用重启 sshd——authorized_keys 的权限在每次认证时现查，保存即生效。再连，通过——用第20章的方法 `ssh -T` 式验证不必了，直接登上服务器，`tail` 那份让你跑了一下午的部署日志，收工。从 Connection refused 到收工，三个故障一层一个，没有一步靠猜——这就是分层法的含金量。

三个故障、三层世界——网络层（端口挪了）、客户端密钥层（config 指向死钥）、服务端授权层（权限太松）——一表收官：

| 故障 | 症状 | 真相 | 修复 |
|------|------|------|------|
| sshd 端口改 2222 | Connection refused | 门挪了位置 | config 更新 Port |
| config 指向已删旧钥 | Permission denied (publickey) | 客户端无钥可掏 | 修正 IdentityFile 路径 |
| authorized_keys 666 | 服务端日志 bad ownership or modes | StrictModes 拒绝松权限 | chmod 600 与 700 |

复盘这场演练的方法论比答案更值钱：**报错分层对号——refused 查网络，denied 查钥匙，权限报错查服务端**——第18章的分层排查法在真实连环故障里原样复用。你现在已经能处理 SSH 世界的绝大多数日常故障了。这场演练的每个故障单独拆开都不难，难的是三件事叠在一起时还守得住分层纪律——这正是它被放在末章的原因。

排错时还有个朴实的好习惯：拿一个文件记下每步的假设与证据——「假设端口没变，证据：refused」。三层走完，把记录从头读一遍，真相往往自己浮出来。分层法不是天赋，是记录纪律。

## 本章小结

- 一条 push 要走九站：工作区、提交、refs、ssh 子进程、加密通道、receive-pack、pre-receive、post-receive、上线验证，每站都能对应到具体章节
- 私钥误提交与电脑丢失同罪：视同已泄露，按吊销、换钥、查日志、查副本、清洗历史五步处置
- 从新提交里删文件救不了泄露：已提交对象永在历史里；换钥是唯一正解，历史清理只是补救
- 前向保密保证私钥未来泄露也解不开过去流量，但只保护过去——agent、当前会话、弱口令都在射程之外
- 指纹告警先核实来源：重装则核对指纹后 ssh-keygen -R 更新记录；无法核实按攻击处理，删 known_hosts 永远是最后一步
- 连环故障按分层拆：refused 查网络端口，denied 查客户端钥，权限报错查服务端日志
- authorized_keys 644 合法，666 才触发 StrictModes 拒绝——流言要靠原理纠正

**结束语**：全书 24 章到此收束。回头核对第0章的四个里程碑：

- M1 本地历史管理：不查文档完成建分支、合并、撤销一次误操作
- M2 免密远程登录：10 分钟内给一台新服务器配好免密
- M3 看透 pull：口头完整复述它从回车到合并的全过程
- M4 自建 Git 服务：从零搭出 push 即部署的私有链路

四条都能打勾的话，你已经跨过了大多数人多年没迈过去的门槛。

两张心智模型各留一句带走的话。Git 管内容：**提交过的几乎不可能丢，怕的从来不是丢，是没提交**。SSH 管通道：**私钥绝不出门，指纹核实了再信任**。所有命令都会过时，这两句话不会；哪天你忘了某条命令的写法，回各章速查，哪天你怀疑这一切是否值得，回这两句。

想继续深挖，站内有三条现成的路：[网络协议完全教程](/network-protocol/ch00)带你把 TLS 与协议分层讲透——那是 SSH 之外的另一套通道体系，理解一个再回看另一个会豁然开朗；[GitHub Actions 完全教程](/github-actions/ch01)能把第23章的部署流水线升级成带测试门禁的完整 CI/CD，从[第13章的 Node.js 实战](/github-actions/ch13)上手最快；[Linux 命令行完全教程](/linux-command/ch00)接手第17章之后的服务器日常管理。

写作至此，第0章副标题里那句「本书解决两个根本问题——改了什么、怎么安全送达」，应该已经有你的答案了：前一个问题，Git 用提交与历史回答；后一个问题，SSH 用密钥与通道回答，而两者在 Part 4 汇成一台上线的机器。

最后，把全书最重要的话放在末尾——它是第1章的第一习惯，也是今后每一次你犹豫要不要 commit 时的答案：**小步提交，频繁提交**。
