# 第9章：视图、触发器与 CTE——SQL 的高级魔法

## 9.1 开场白：从 CRUD 农民到 SQL 巫师

到这里为止，我们只学了 SQL 的"农民三件套"：CREATE、SELECT、INSERT/UPDATE/DELETE。够用吗？够用。够爽吗？不够。

真正让 SQL 从"数据操作"升级为"数据抽象"的，是这三样：

- **视图（View）**：把复杂查询封装成"虚拟表"。
- **触发器（Trigger）**：数据变化时自动执行的钩子。
- **CTE（Common Table Expression）**：临时命名的查询结果，让你写出人类可读的复杂 SQL。

这一章你会从 CRUD 农民进阶为 SQL 巫师。

## 9.2 视图（View）——SQL 的抽象层

视图 = 保存起来的 SELECT 语句 + 一个名字。

```sql
CREATE VIEW active_user AS
SELECT id, name, email
FROM user
WHERE deleted_at IS NULL AND status = 'active';
```

然后你可以像查表一样查视图：

```sql
SELECT * FROM active_user WHERE email LIKE '%@qq.com';
```

**视图不存储数据**！它每次被查询时才执行底层 SELECT。所以视图**不能加索引**（除非是物化视图，SQLite 不原生支持）。

**视图的用途**：

1. **屏蔽复杂度**：把 5 个 JOIN 封装起来，业务代码只查视图。
2. **权限控制**：用户只看视图，看不到底层表（SQLite 权限模型很弱，这一条主要在其他数据库有用）。
3. **兼容旧接口**：表结构改了，用视图保持旧的查询接口。
4. **命名 & 复用**：常用查询有个名字，团队沟通方便。

## 9.3 可更新视图与 INSTEAD OF 触发器

默认情况下 SQLite 的视图**只读**！你不能 `INSERT INTO active_user`——会报错。

想让视图可写？必须写 `INSTEAD OF` 触发器：

```sql
CREATE TRIGGER active_user_insert
INSTEAD OF INSERT ON active_user
BEGIN
  INSERT INTO user(id, name, email, status, deleted_at)
  VALUES (NEW.id, NEW.name, NEW.email, 'active', NULL);
END;

CREATE TRIGGER active_user_delete
INSTEAD OF DELETE ON active_user
BEGIN
  UPDATE user SET deleted_at = datetime('now') WHERE id = OLD.id;
END;

CREATE TRIGGER active_user_update
INSTEAD OF UPDATE ON active_user
BEGIN
  UPDATE user
  SET name = NEW.name, email = NEW.email
  WHERE id = OLD.id;
END;
```

现在 `INSERT/UPDATE/DELETE active_user` 就会被"重定向"到底层 user 表，并且 DELETE 变成了软删除。这就是**可更新视图**的实现方式。

## 9.4 触发器（Trigger）——数据变化的钩子

触发器 = 事件 + 时机 + 动作。

**三要素**：

- **时机**：BEFORE / AFTER / INSTEAD OF
- **事件**：INSERT / UPDATE [OF column] / DELETE
- **粒度**：FOR EACH ROW（SQLite 只支持这一种）

**语法模板**：

```sql
CREATE TRIGGER trigger_name
[BEFORE | AFTER | INSTEAD OF] [INSERT | UPDATE [OF col1, col2] | DELETE]
ON table_name
[FOR EACH ROW]
[WHEN condition]
BEGIN
  -- SQL 语句们
END;
```

**OLD 和 NEW 引用**：

- `INSERT`：只有 `NEW`（新插入的行）
- `DELETE`：只有 `OLD`（被删的行）
- `UPDATE`：两个都有（`OLD` 是旧值，`NEW` 是新值）

`INSTEAD OF` 只能用于视图，不能用于表。

## 9.5 实战案例 1：审计日志

需求：`user` 表的每次修改都要记录到 `audit_log`。

```sql
CREATE TABLE audit_log(
  id INTEGER PRIMARY KEY,
  table_name TEXT NOT NULL,
  row_id INTEGER NOT NULL,
  action TEXT NOT NULL,             -- 'INSERT', 'UPDATE', 'DELETE'
  old_data TEXT,                     -- JSON
  new_data TEXT,                     -- JSON
  changed_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TRIGGER user_audit_insert
AFTER INSERT ON user
BEGIN
  INSERT INTO audit_log(table_name, row_id, action, new_data)
  VALUES ('user', NEW.id, 'INSERT',
    json_object('name', NEW.name, 'email', NEW.email));
END;

CREATE TRIGGER user_audit_update
AFTER UPDATE ON user
BEGIN
  INSERT INTO audit_log(table_name, row_id, action, old_data, new_data)
  VALUES ('user', NEW.id, 'UPDATE',
    json_object('name', OLD.name, 'email', OLD.email),
    json_object('name', NEW.name, 'email', NEW.email));
END;

CREATE TRIGGER user_audit_delete
AFTER DELETE ON user
BEGIN
  INSERT INTO audit_log(table_name, row_id, action, old_data)
  VALUES ('user', OLD.id, 'DELETE',
    json_object('name', OLD.name, 'email', OLD.email));
END;
```

从此，业务代码不用关心审计——数据一变就自动记录。**这就是触发器最经典的用法**。

## 9.6 实战案例 2：自动 updated_at

需求：每次 UPDATE 都自动更新 `updated_at` 字段。

```sql
CREATE TABLE post(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  content TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TRIGGER post_update_time
AFTER UPDATE ON post
FOR EACH ROW
WHEN NEW.updated_at = OLD.updated_at    -- 防止无限循环
BEGIN
  UPDATE post SET updated_at = datetime('now') WHERE id = NEW.id;
END;
```

**关键点**：`WHEN NEW.updated_at = OLD.updated_at` 防止触发器自己更新 `updated_at` 时再次触发自己（无限递归）。SQLite 默认不允许 trigger 递归（有 `PRAGMA recursive_triggers` 开关），但保险起见加个 WHEN。

## 9.7 实战案例 3：手动实现级联删除

假设你不想用 FK 的 CASCADE（可能为了兼容旧数据），可以用触发器：

```sql
CREATE TRIGGER user_delete_cleanup
AFTER DELETE ON user
BEGIN
  DELETE FROM post WHERE user_id = OLD.id;
  DELETE FROM comment WHERE user_id = OLD.id;
  DELETE FROM session WHERE user_id = OLD.id;
END;
```

比 FK 更灵活（可以只清理特定条件），但需要自己维护。

## 9.8 实战案例 4：约束型触发器（BEFORE）

用触发器实现复杂约束：

```sql
CREATE TRIGGER check_balance_before_transfer
BEFORE UPDATE OF balance ON account
FOR EACH ROW
WHEN NEW.balance < 0
BEGIN
  SELECT RAISE(ABORT, '余额不能为负');
END;
```

`RAISE(ABORT, ...)` 会取消整个事务并抛错。也可以用 `RAISE(ROLLBACK, ...)`、`RAISE(FAIL, ...)`、`RAISE(IGNORE)`。

## 9.9 触发器的滥用与调试难题

触发器很爽，但也容易变成**噩梦**：

**问题 1：隐蔽的副作用**

业务代码 `UPDATE user SET name = 'x'`，结果背地里触发了 5 个 trigger，写了 10 张表——新来的同事完全不知道，debug 时崩溃。

**问题 2：性能陷阱**

每个 trigger 都是同步执行的。如果 trigger 里有复杂查询，会拖慢主操作。批量更新 100 万行时，触发器执行 100 万次，性能雪崩。

**问题 3：递归死循环**

trigger A 更新表 X → 表 X 的 trigger B → trigger B 更新表 Y → 表 Y 的 trigger C → trigger C 更新表 X → ……

`PRAGMA recursive_triggers = 0`（默认关）避免这种情况，但也可能让你的级联触发失效。

**问题 4：难以调试**

`INSERT` 报错，你以为是主 SQL 的问题，其实是 trigger 里的 CHECK 触发的。SQLite 的错误信息不会明确告诉你是哪个 trigger 报错。

**规避建议**：

1. **触发器越简单越好**，只做一件事。
2. **写好文档**：每个触发器旁边注释说明它做什么、为什么。
3. **避免跨表触发链**：A→B→C 尽量拉直成应用层控制。
4. **业务逻辑放应用层**：触发器主要用于"元数据"逻辑（审计、时间戳、计数器）。
5. **超过 3 个触发器 = 警惕**。

## 9.10 CTE（Common Table Expression）——WITH 子句

CTE 是 SQL 里的"临时命名子查询"。语法：

```sql
WITH cte_name AS (
  SELECT ...
)
SELECT * FROM cte_name WHERE ...;
```

**对比子查询**：

```sql
-- 子查询版
SELECT *
FROM (
  SELECT user_id, COUNT(*) AS post_count
  FROM post
  GROUP BY user_id
) t
WHERE t.post_count > 10;

-- CTE 版
WITH user_stats AS (
  SELECT user_id, COUNT(*) AS post_count
  FROM post
  GROUP BY user_id
)
SELECT * FROM user_stats WHERE post_count > 10;
```

**优点**：可读性大幅提升，尤其是多层嵌套时。

**多个 CTE 串联**：

```sql
WITH
active_user AS (
  SELECT * FROM user WHERE status = 'active'
),
user_stats AS (
  SELECT u.id, u.name, COUNT(p.id) AS post_count
  FROM active_user u
  LEFT JOIN post p ON p.user_id = u.id
  GROUP BY u.id
)
SELECT * FROM user_stats WHERE post_count > 5;
```

从上到下依次定义，后面的 CTE 可以引用前面的。**读起来像自然语言**。

## 9.11 CTE vs 子查询：性能

绝大多数 SQLite 版本里，CTE 和子查询**性能几乎一样**——SQLite 会把非递归 CTE 内联成子查询。所以选谁看可读性。

例外：SQLite 3.35+ 引入 `MATERIALIZED` 提示：

```sql
WITH cte AS MATERIALIZED (
  SELECT ...
)
SELECT ...;
```

强制物化 CTE（跑一次结果缓存在临时表）。适合 CTE 被多次引用且计算复杂的情况。反过来用 `NOT MATERIALIZED` 强制内联。

## 9.12 递归 CTE——树形结构的杀器

递归 CTE 让 SQL 能处理"无限深度"的层级数据（评论回复、组织架构、树、图）。语法：

```sql
WITH RECURSIVE cte AS (
  -- 锚点（base case）
  SELECT ... FROM ...
  UNION ALL
  -- 递归（recursive case）
  SELECT ... FROM ... JOIN cte ON ...
)
SELECT * FROM cte;
```

**经典例子**：生成 1~10：

```sql
WITH RECURSIVE nums(x) AS (
  SELECT 1
  UNION ALL
  SELECT x + 1 FROM nums WHERE x < 10
)
SELECT * FROM nums;
-- 1, 2, 3, ..., 10
```

**评论树**：

```sql
CREATE TABLE comment(id INTEGER PRIMARY KEY, parent_id INTEGER, content TEXT);

WITH RECURSIVE tree AS (
  SELECT id, parent_id, content, 0 AS depth
  FROM comment WHERE parent_id IS NULL       -- 根节点
  UNION ALL
  SELECT c.id, c.parent_id, c.content, t.depth + 1
  FROM comment c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree ORDER BY depth;
```

递归 CTE 是 Part 3 的重头戏，这里先埋个坑。

## 9.13 生成列（Generated Columns）——3.31+

生成列是"从其他列计算出来的列"，你不能直接 INSERT/UPDATE 它。

```sql
CREATE TABLE order_item(
  id INTEGER PRIMARY KEY,
  price REAL NOT NULL,
  quantity INTEGER NOT NULL,
  discount REAL DEFAULT 0,
  -- VIRTUAL：不存储，查询时计算（默认）
  subtotal REAL GENERATED ALWAYS AS (price * quantity * (1 - discount)) VIRTUAL,
  -- STORED：存储在磁盘上（更快查询，占空间）
  total REAL GENERATED ALWAYS AS (price * quantity * (1 - discount) * 1.1) STORED
);
```

**VIRTUAL vs STORED**：

| 特性       | VIRTUAL           | STORED              |
| ---------- | ----------------- | ------------------- |
| 磁盘占用   | 无                | 有                  |
| 查询速度   | 每次计算          | 直接读              |
| 更新触发   | 无                | 依赖列改时重算      |
| 索引       | 可（表达式索引）  | 可（普通索引）      |

**用途**：

- 派生数据（总价、全名、年龄）
- 提取 JSON 字段：`json_extract(data, '$.email') STORED`
- 索引优化：给 STORED 列建索引

```sql
CREATE TABLE user(
  id INTEGER PRIMARY KEY,
  first_name TEXT,
  last_name TEXT,
  full_name TEXT GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED
);
CREATE INDEX idx_full_name ON user(full_name);
```

## 9.14 Flutter 实战：用视图简化 Dart 模型映射

场景：你有 3 张表 `user`、`post`、`comment`，UI 要显示"每个用户的最新一篇帖子 + 评论数"。

**没有视图**：Dart 里写 JOIN 查询、手动映射到复杂的 DTO。

**用视图**：

```sql
CREATE VIEW user_summary AS
SELECT
  u.id,
  u.name,
  u.email,
  p.title AS latest_post_title,
  p.created_at AS latest_post_time,
  (SELECT COUNT(*) FROM comment c WHERE c.post_id = p.id) AS comment_count
FROM user u
LEFT JOIN post p ON p.id = (
  SELECT id FROM post WHERE user_id = u.id ORDER BY created_at DESC LIMIT 1
);
```

Dart 里就像查普通表：

```dart
class UserSummary {
  final int id;
  final String name;
  final String email;
  final String? latestPostTitle;
  final DateTime? latestPostTime;
  final int commentCount;

  UserSummary.fromMap(Map<String, dynamic> m)
    : id = m['id'] as int,
      name = m['name'] as String,
      email = m['email'] as String,
      latestPostTitle = m['latest_post_title'] as String?,
      latestPostTime = m['latest_post_time'] == null
        ? null : DateTime.parse(m['latest_post_time'] as String),
      commentCount = m['comment_count'] as int;
}

final rows = await db.query('user_summary');
final list = rows.map(UserSummary.fromMap).toList();
```

**drift 里的做法**：

drift 支持视图，用 `.drift` 文件：

```sql
-- schema.drift
CREATE VIEW user_summary AS
SELECT u.id, u.name, u.email, ...
FROM users u LEFT JOIN posts p ...;
```

或者用 Dart 类：

```dart
abstract class UserSummary extends View {
  UsersTable get users;
  PostsTable get posts;

  Expression<int> get id => users.id;
  Expression<String> get name => users.name;
  // ...

  @override
  Query as() => select([id, name, /*...*/])
    .from(users)
    .join([leftOuterJoin(posts, posts.userId.equalsExp(users.id))]);
}
```

然后 `db.select(userSummary).get()` 就能查——**类型全安全**。

## 9.15 常见坑点合集

**坑 1：视图里的 ORDER BY 无效**

```sql
CREATE VIEW v AS SELECT * FROM t ORDER BY id;   -- 内部 ORDER BY 可能被优化器忽略
SELECT * FROM v LIMIT 10;                        -- 顺序不保证
```

想要有序结果，在查询视图时加 `ORDER BY`。

**坑 2：触发器里的错误 → 主 SQL 报错**

```sql
INSERT INTO user VALUES (1, 'x');
-- 报错：Error: RAISE(ABORT, '...')
```

如果你在 Dart 里 `try-catch`，异常信息可能不够清晰。加日志、加详细的 RAISE 消息（比如 `RAISE(ABORT, 'trigger check_balance: negative balance')`）能救命。

**坑 3：触发器执行顺序不确定**

同一个事件有多个触发器时，SQLite 不保证执行顺序（不像 SQL Server 可以指定 first/last）。**不要写有顺序依赖的多个触发器**。

**坑 4：递归触发器**

```sql
CREATE TRIGGER t1 AFTER UPDATE ON tab BEGIN
  UPDATE tab SET updated_at = datetime('now') WHERE id = NEW.id;
END;
```

如果没有 WHEN 条件保护，t1 更新 tab 又会触发 t1，无限递归。默认 `recursive_triggers = 0` 会防止，但也可能导致你以为触发了但没触发。

**坑 5：生成列的 STORED 需要重建表**

3.31 之前的表不支持生成列，加生成列到已有 STORED 列需要 `ALTER TABLE ... ADD COLUMN`，但 STORED 列**不能通过 ALTER 添加**（3.45 依然），必须重建表。

**坑 6：CTE 里的名字冲突**

```sql
WITH t AS (SELECT * FROM user)
SELECT * FROM t JOIN t ON ...;   -- 需要别名区分
```

CTE 名不能和现有表名冲突（会遮盖表）。

**坑 7：INSTEAD OF 触发器只能用于视图**

```sql
CREATE TRIGGER x INSTEAD OF INSERT ON some_table BEGIN ... END;
-- Error: cannot create INSTEAD OF trigger on table
```

想在表上"改变"操作，用 BEFORE + RAISE(IGNORE)。

## 9.16 本章小结

- 视图 = 保存的 SELECT，不存数据，每次查询时执行。
- 想让视图可写？写 INSTEAD OF 触发器。
- 触发器三要素：时机（BEFORE/AFTER/INSTEAD OF）+ 事件（I/U/D）+ 动作。
- OLD/NEW 引用行数据；WHEN 子句加条件过滤。
- 常见用途：审计日志、自动 updated_at、级联清理、约束型触发。
- **触发器是双刃剑**：隐蔽副作用 + 性能陷阱 + 调试困难，慎用。
- CTE（WITH 子句）让复杂 SQL 变得像自然语言。
- 递归 CTE 处理树形结构，是 Part 3 的重头戏。
- 生成列（STORED/VIRTUAL）让派生字段自动计算。
- Flutter 里用视图简化复杂查询到 Dart 模型的映射；drift 支持视图定义。
- **金句**：视图是 SQL 的抽象；触发器是数据的钩子；CTE 是复杂逻辑的救星。三者用好，你就是队里的 SQL 巫师。
