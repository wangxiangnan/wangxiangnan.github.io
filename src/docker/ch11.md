# 第11章：Docker 安全最佳实践 —— 给你的容器穿上"防弹衣"

## 引言：容器安全的"瑞士奶酪模型"

安全领域有一个著名的"瑞士奶酪模型"：每一层安全措施就像一片瑞士奶酪，单独一片有很多洞（漏洞），但多层叠在一起，洞就被堵住了。Docker 安全也是一样——没有银弹，但多个最佳实践叠加起来，就能让你的容器固若金汤。

很多开发者觉得"我的应用又不值钱，谁攻击我啊"。这就像觉得"我家没什么值钱的东西，不用锁门"——但你忘了，攻击者可能不是冲着你的数据来的，而是想借用你的计算资源挖矿、作为跳板攻击内网其他服务、或者在你的镜像里植入后门。

---

## 11.1 Docker 安全的常见误区

**误区 1："容器就是虚拟机，天然隔离"**
错！容器共享宿主机的内核。一个内核漏洞就可能让容器"逃逸"到宿主机。容器更像是"合租公寓"——有各自的房间，但共享水电管道。

**误区 2："用官方镜像就安全了"**
官方镜像也有漏洞。`node:18` 镜像包含完整的操作系统包，其中可能有已知的 CVE。你需要定期更新镜像并扫描漏洞。

**误区 3："我的应用在容器里，不需要额外安全措施"**
如果你以 root 身份运行、暴露不必要的端口、挂载敏感宿主机目录，攻击面依然很大。

---

## 11.2 以非 root 用户运行容器

默认情况下，Docker 容器内的进程以 **root（UID 0）** 身份运行。这大大增加了容器逃逸的风险。

```dockerfile
# ===== 错误示范：以 root 运行 =====
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm ci --only=production
CMD ["node", "server.js"]
# 此时容器内进程是 root！

# ===== 正确做法：创建专用用户 =====
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .

# 修改文件归属（node 镜像自带 node 用户）
RUN chown -R node:node /app

# 切换到非 root 用户
USER node

CMD ["node", "server.js"]
```

```bash
# 也可以在运行时指定用户
docker run --user 1000:1000 my-app

# 验证当前用户
docker exec my-container whoami
# 输出：node（而不是 root）
```

对于 Python 应用：

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# 创建非 root 用户
RUN groupadd -r appgroup && useradd -r -g appgroup -d /app appuser \
    && chown -R appuser:appgroup /app

USER appuser
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

> [!TIP] 提示
> 很多官方镜像（如 `node`、`nginx`、`postgres`）已经预创建了非 root 用户。善用它们，不必每次都手动创建。

## 11.3 只读文件系统（--read-only）

将容器的根文件系统设为只读，可以防止攻击者在容器内写入恶意文件。

```yaml
# docker-compose.yml
services:
  api:
    image: my-api:latest
    read_only: true             # 只读文件系统
    tmpfs:
      - /tmp                    # 临时文件目录需要可写
      - /app/logs               # 日志目录需要可写
    volumes:
      - upload-data:/app/uploads  # 需要写入的业务数据
```

> **Warning:** 使用 `read_only` 时，应用的所有写入操作都必须指向 `tmpfs` 或 `volume` 挂载的目录。否则应用会因为权限错误而崩溃。

## 11.4 资源限制（--memory、--cpus、--pids-limit）

不限制容器资源，一个 bug 就能把整个宿主机拖垮（OOM）。

```yaml
# docker-compose.yml
services:
  api:
    image: my-api:latest
    deploy:
      resources:
        limits:                 # 上限（硬限制）
          memory: 512M
          cpus: '0.5'
          pids: 100
        reservations:           # 保留（软限制）
          memory: 256M
          cpus: '0.25'

  db:
    image: postgres:15-alpine
    deploy:
      resources:
        limits:
          memory: 1G
          cpus: '1.0'

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru
    deploy:
      resources:
        limits:
          memory: 256M
          cpus: '0.25'
```

```bash
# 监控容器资源使用
docker stats
# CONTAINER ID  NAME   CPU %   MEM USAGE / LIMIT   MEM %
# a1b2c3d4e5f6  api    2.50%   128MiB / 512MiB     25.0%
```

> [!TIP] 提示
> `--pids-limit` 是防止 fork 炸弹的关键措施。建议设置为应用实际需要的进程数的 2-3 倍（Node.js 一般 50-100，Java 应用可能需要 200+）。

## 11.5 Capabilities 管理

Linux Capabilities 把 root 权限拆分为多个细粒度的权限。

```yaml
# docker-compose.yml
services:
  api:
    image: my-api:latest
    cap_drop:
      - ALL                    # 删除所有 capabilities
    cap_add:
      - NET_BIND_SERVICE       # 只添加绑定端口 < 1024 的权限
      - CHOWN                  # 修改文件归属

  db:
    image: postgres:15-alpine
    cap_drop:
      - ALL
    cap_add:
      - CHOWN
      - SETUID
      - SETGID
      - DAC_OVERRIDE
```

| Capability | 用途 | 何时需要 |
|-----------|------|---------|
| `NET_BIND_SERVICE` | 绑定 < 1024 端口 | Nginx 监听 80/443 |
| `CHOWN` | 修改文件归属 | 数据库初始化 |
| `SETUID/SETGID` | 切换用户身份 | 需要从 root 降权的服务 |
| `SYS_ADMIN` | 近乎 root 的超级权限 | **几乎永远不要给容器！** |

> **Warning:** `SYS_ADMIN` 是最危险的 capability，它几乎等同于 root 权限。永远不要给普通应用容器添加 `SYS_ADMIN`。

## 11.6 Seccomp 与 AppArmor 简介

**Seccomp** 限制容器能调用的系统调用。Docker 自带默认配置，禁止约 44 个危险系统调用。

**AppArmor/SELinux** 是 Linux 的强制访问控制系统。Docker 会自动为容器生成 AppArmor 配置。

```bash
# 查看容器的 AppArmor 配置
docker inspect --format='{{.AppArmorProfile}}' my-container
```

> [!TIP] 提示
> 对于大多数场景，Docker 默认的 Seccomp 和 AppArmor 配置已经足够安全。只有有专门安全团队时才需要自定义。

## 11.7 Docker Content Trust（镜像签名）

Docker Content Trust 通过数字签名确保你拉取的镜像没有被篡改。

```bash
# 启用 Docker Content Trust
export DOCKER_CONTENT_TRUST=1

# 之后 docker pull 会验证签名
docker pull nginx:latest

# 为自定义镜像签名
export DOCKER_CONTENT_TRUST=1
docker push myrepo/myapp:1.0
```

> **Warning:** 不是所有镜像都启用了 Content Trust。很多第三方镜像没有签名，启用 DCT 后会导致无法拉取。建议只在 CI/CD 中对自己构建的镜像启用。

## 11.8 镜像安全扫描

### Docker Scout（Docker 官方）

```bash
# 扫描镜像漏洞
docker scout cves my-app:latest

# 查看安全建议
docker scout recommendations my-app:latest

# 比较两个镜像的安全差异
docker scout compare my-app:v1 my-app:v2
```

### Trivy（开源方案）

```bash
# 安装 Trivy
brew install trivy    # macOS

# 扫描镜像
trivy image my-app:latest

# 只扫描高危和严重漏洞
trivy image --severity HIGH,CRITICAL my-app:latest

# 生成 JSON 报告（CI/CD 中使用）
trivy image --format json --output report.json my-app:latest
```

```yaml
# GitHub Actions 集成 Trivy
name: Security Scan
on: [push]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t my-app:${{ github.sha }} .
      - name: Run Trivy
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: my-app:${{ github.sha }}
          severity: 'HIGH,CRITICAL'
          exit-code: '1'           # 发现高危漏洞时构建失败
```

> [!TIP] 提示
> 将镜像扫描集成到 CI/CD 流水线中。设置"门禁"策略：存在 CRITICAL 级别漏洞时阻止部署，HIGH 级别时发出警告。

## 11.9 Secrets 管理对比

| 方案 | 安全性 | 适用场景 |
|------|--------|---------|
| 环境变量 | 低 | 开发环境 |
| `.env` 文件 | 中 | 开发/单机部署 |
| Docker Secrets | 高 | Swarm 集群 |
| Compose Secrets | 中 | 单机部署 |
| HashiCorp Vault | 很高 | 企业级 |

```bash
# 环境变量的安全风险
docker inspect my-container | grep -i password
# 如果密码写在 environment 中，这里会直接暴露！
```

## 11.10 安全 Checklist

**镜像安全**

- [ ] 使用最小基础镜像（Alpine、distroless、scratch）
- [ ] 固定镜像版本（`node:18.17.0-alpine` 而非 `node:latest`）
- [ ] 定期扫描镜像漏洞（Docker Scout / Trivy）
- [ ] 不在镜像中包含敏感信息
- [ ] 使用 `.dockerignore` 排除不必要的文件

**运行时安全**

- [ ] 以非 root 用户运行
- [ ] 设置只读文件系统
- [ ] 限制资源使用（内存、CPU、PID）
- [ ] 最小化 capabilities
- [ ] 不暴露不必要的端口
- [ ] 不挂载 `/var/run/docker.sock`

**数据安全**

- [ ] 使用 Secrets 管理敏感配置
- [ ] `.env` 和 `secrets/` 加入 `.gitignore`
- [ ] 数据库使用强密码
- [ ] 启用 TLS/SSL 加密通信

> **Warning:** 永远不要将 `/var/run/docker.sock` 挂载到容器中！这等同于给容器完整的 Docker 控制权。

## 本章小结

- 以非 root 用户运行是最基本也最重要的安全措施
- 资源限制防止单个容器耗尽宿主机资源
- Capabilities 管理遵循最小权限原则：先 drop ALL，再 add 必要的
- 镜像安全扫描应该集成到 CI/CD 流水线中
- Secrets 管理比环境变量更安全，适用于生产环境
- 安全是一个持续的过程，使用 Checklist 确保不遗漏

## 练习

1. **基础练习**：为一个 Node.js 应用的 Dockerfile 添加非 root 用户、只读文件系统，并使用 `--cap-drop ALL` 运行。
2. **进阶练习**：使用 Trivy 扫描 `node:18` 和 `node:18-alpine`，对比高危漏洞数量。
3. **挑战练习**：根据安全 Checklist 审查一个现有的 `docker-compose.yml`，列出所有安全隐患并给出修复方案。
