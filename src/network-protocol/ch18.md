## 18.1 SMTP：邮件发送协议

SMTP（Simple Mail Transfer Protocol）1982 年定义于 RFC 821，设计简单到令人惊讶——纯文本的命令-响应协议，理论上用 Telnet 就能手动发一封邮件。

一次完整的 SMTP 会话：

```
Client → Server: [TCP 连接建立，端口 25 或 587]
Server → Client: 220 mail.example.com ESMTP ready
Client → Server: HELO client.example.com           ← 打招呼（ESMTP 用 EHLO）
Server → Client: 250 mail.example.com Hello
Client → Server: MAIL FROM:<alice@example.com>      ← 发件人
Server → Client: 250 OK
Client → Server: RCPT TO:<bob@receiver.com>         ← 收件人
Server → Client: 250 OK
Client → Server: DATA                                ← 开始传输内容
Server → Client: 354 Start mail input; end with <CRLF>.<CRLF>
Client → Server: From: Alice <alice@example.com>
                 Subject: Hello!
                 （空行）
                 Hi Bob, how are you?
                 .                                    ← 单独一行的 . 表示结束
Server → Client: 250 OK, message accepted
Client → Server: QUIT
Server → Client: 221 Bye
```

三个特点值得记：

- 所有命令纯文本、CRLF 结尾——与 13.2 的 HTTP 同一家族。
- 三位数字响应码：2xx 成功、3xx 要更多信息、4xx 临时错误、5xx 永久错误——这套「表情体系」HTTP 也继承了。
- 邮件内容以单独一行 `.` 结束；内容里若有 `.` 开头的行，协议规定前面再加一个 `.`（点填充）。

## 18.2 MIME 与收信协议：POP3 vs IMAP

SMTP 最初只支持 7 位 ASCII 文本，附件和中文字符都进不来。**MIME**（Multipurpose Internet Mail Extensions）通过头部声明编码方式解决了这个问题：

```
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="----=_Part_123"

------=_Part_123
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: base64

5L2g5aW977yM5L2g5piv5Lit5paH5rGf6IO977yB
------=_Part_123
Content-Type: image/png; name="photo.png"
Content-Disposition: attachment
Content-Transfer-Encoding: base64

iVBORw0KGgoAAAANSUhEUgAA...（图片的 Base64）
------=_Part_123--
```

`multipart/mixed` 表示多部分邮件，`boundary` 定义分隔符；`base64` 把二进制转成 ASCII 字符以通过只认 7 位文本的 SMTP——「用编码换通道」是老协议的典型补丁。

「先猜再读」第一问的答案：SMTP 只管送信到服务器，取信另有协议：

- **POP3**：把邮件下载到本地，然后（通常）从服务器删除——像把信箱里的信拿回家。不占服务器空间，但多设备同步困难。
- **IMAP**：邮件留在服务器，客户端只是查看——像在线看信箱。多设备看到同样的状态（已读/文件夹），代价是服务器存储压力大。

现代客户端（Gmail、Outlook）几乎都用 IMAP。对照第12章的端口表：25/587 发信、110/143/993 收信——一套邮件系统至少四个端口各司其职。

## 18.3 FTP：两个连接的协议

FTP（1971 年，比 HTTP 早 20 年）的独特设计：**控制与数据分离**——

- **控制连接**：TCP 21，发命令、收响应，整个会话保持。
- **数据连接**：每次传输文件或目录列表都新建一条。

「先猜再读」第二问的答案：分离让命令与数据互不阻塞（传大文件时仍能执行 `cd`、`ls`），但也埋下大坑——数据连接由谁发起？两种模式为此而生：

**主动模式**：客户端告诉服务器自己的地址，服务器反向连过来：

```
Client → Server: PORT 192,168,1,100,4,1   ← 连我的 192.168.1.100:1025
Server → Client: 200 PORT command successful
Client → Server: LIST
[服务器从端口 20 主动连接客户端的 1025]
Server → Client: 226 Transfer complete
```

坑就在这：客户端在 NAT/防火墙后面时（第4章的 NAT 知识），服务器根本连不进它的私有地址。

**被动模式**：反过来，客户端去连服务器开好的临时端口：

```
Client → Server: PASV
Server → Client: 227 Entering Passive Mode (203,0,113,50,195,80)
                  ← 连我的 203.0.113.50:50000
Client → Server: LIST
[客户端主动连接服务器的 50000]
Server → Client: 226 Transfer complete
```

数据连接由客户端发起，不需要客户端有公网 IP——这就是被动模式成为现代默认的原因：大部分客户端都在 NAT 后面。FTP 的明文问题与 SMTP 相同，安全替代是 **FTPS**（FTP over TLS）和 **SFTP**（SSH 的文件传输子系统——与 FTP 完全是两个协议，只是功能相似，见 18.4）。

## 18.4 SSH：安全远程登录

SSH（Secure Shell，1995）替代 Telnet/rlogin 等明文协议，提供加密的远程命令行、安全文件传输（SFTP/SCP）与端口隧道。

**握手四步**：

1. **版本交换**：双方互换 `SSH-2.0-OpenSSH_9.0` 这样的版本串。
2. **密钥交换**：Diffie-Hellman/ECDH 协商会话密钥（与 15.2 TLS 的 DH 魔法同源），同时拿到服务器 **Host Key**（公钥）。「先猜再读」第三问的答案：SSH 没有 CA——它的信任锚是 `~/.ssh/known_hosts` 文件与 TOFU 模型（Trust On First Use，第一次连接记录指纹，之后比对）。15.4 的 CA 是「可信第三方背书」，known_hosts 是「自己记住指纹」——两种信任模型，各有适用场景。
3. **用户认证**：密码认证（虽加密传输但可被暴力猜测）或公钥认证——客户端用私钥签名挑战值，服务器用公钥验证。推荐后者，且不受暴力破解影响。
4. **会话建立**：认证后可开多个 Channel（通道）——一个终端会话、一个 SFTP、一条端口转发，全部复用同一条加密连接。这个「连接内多路复用」的思想，第19章的 HTTP/2 会以更大规模重演。

**端口转发三式**：

```bash
# 本地转发：把本地 3307 映射到远程服务器可达的 MySQL 3306
ssh -L 3307:localhost:3306 user@remote-server
# 之后 mysql -h 127.0.0.1 -P 3307，流量经 SSH 隧道直达远程库

# 远程转发：把远程服务器的 8080 映射回本地 80
ssh -R 8080:localhost:80 user@remote-server
# 别人访问 remote-server:8080，流量穿隧道到你本地的开发服务器

# 动态转发：本地起 SOCKS 代理，浏览器流量全走 SSH 隧道
ssh -D 1080 user@remote-server
```

> [!TIP] -L / -R / -D 一句话记法
> 方向看「占用哪一端的端口」：-L 占本地（把远程服务拉到本地），-R 占远程（把本地服务推给远程），-D 在本地起 SOCKS 代理（动态决定去哪）。三式都只借一条 SSH 连接。

`-D` 的 SOCKS 代理相当于自建了一个加密转发通道——它与「VPN」的边界在第22章划清：本章管 SSH 协议机制，VPN/防火墙/零信任的安全体系归第22章。

## 18.5 编程实践：发邮件与 SSH 自动化

用 smtplib 发一封带附件的邮件（Gmail 需要在账户设置里生成 16 位「应用专用密码」，不能用登录密码）：

```python
import smtplib
from email.mime.text import MIMEText
from email.mime.multipart import MIMEMultipart
from email.mime.base import MIMEBase
from email import encoders

def send_simple_email():
    """发送一封带附件的邮件（STARTTLS 加密）"""
    msg = MIMEMultipart()
    msg['From'] = 'your-email@gmail.com'
    msg['To'] = 'recipient@example.com'
    msg['Subject'] = 'Test Email from Python'

    msg.attach(MIMEText("This is a test email.\n\nHello World!", 'plain', 'utf-8'))

    # 附件：二进制内容 Base64 编码——18.2 MIME 机制的具象化
    part = MIMEBase('application', 'octet-stream')
    part.set_payload(b"Hello, this is a test attachment.")
    encoders.encode_base64(part)
    part.add_header('Content-Disposition', 'attachment; filename="test.txt"')
    msg.attach(part)

    server = smtplib.SMTP('smtp.gmail.com', 587)
    server.ehlo()
    server.starttls()   # 明文通道升级为 TLS——机制见 18.6 抓包
    server.ehlo()
    server.login('your-email@gmail.com', 'your-app-password')
    server.send_message(msg)
    server.quit()
    print("Email sent successfully!")

# 想观察完整 SMTP 命令流：
# server = smtplib.SMTP('smtp.gmail.com', 587)
# server.set_debuglevel(1)   # 打印所有命令与响应
# server.ehlo(); server.starttls()
```

用 paramiko 实现 SSH 自动化（`pip install paramiko`）：

```python
import paramiko

def ssh_command(hostname: str, username: str, command: str, key_file: str = None):
    """通过 SSH 执行远程命令"""
    client = paramiko.SSHClient()
    # 自动添加未知 Host Key——生产环境应改用 known_hosts 校验
    client.set_missing_host_key_policy(paramiko.AutoAddPolicy())

    connect_kwargs = {'hostname': hostname, 'username': username,
                      'port': 22, 'timeout': 10}
    if key_file:
        connect_kwargs['key_filename'] = key_file
    else:
        connect_kwargs['password'] = input(f"Password for {username}@{hostname}: ")

    try:
        client.connect(**connect_kwargs)
        stdin, stdout, stderr = client.exec_command(command)
        exit_code = stdout.channel.recv_exit_status()
        print(f"STDOUT:\n{stdout.read().decode('utf-8')}")
        err = stderr.read().decode('utf-8')
        if err:
            print(f"STDERR:\n{err}")
        print(f"Exit code: {exit_code}")
        return exit_code
    except paramiko.AuthenticationException:
        print("Authentication failed!")
        return -1
    finally:
        client.close()

def ssh_sftp_upload(hostname, username, local_path, remote_path, key_file=None):
    """通过 SFTP 上传文件"""
    client = paramiko.SSHClient()
    client.set_missing_host_key_policy(paramiko.AutoAddPolicy())
    kwargs = {'hostname': hostname, 'username': username}
    if key_file:
        kwargs['key_filename'] = key_file
    client.connect(**kwargs)
    with client.open_sftp() as sftp:
        print(f"Uploading {local_path} -> {remote_path}")
        sftp.put(local_path, remote_path)
        print("Upload complete!")
    client.close()

# 示例（仅对授权主机执行）：
# ssh_command('192.168.1.100', 'admin', 'uname -a', key_file='~/.ssh/id_rsa')
# ssh_sftp_upload('192.168.1.100', 'admin', 'local.txt', '/tmp/remote.txt')
```

两个库分别复刻了本章的两个会话模型：smtplib 的 `starttls()` 对应 18.1 的命令流加 15 章的 TLS 升级；paramiko 的 `set_missing_host_key_policy` 则直接暴露了 18.4 的信任模型决策——AutoAddPolicy 等于放弃 TOFU 的防中间人价值，生产环境不要这么配。

## 18.6 抓包实践：明文 SMTP 与 TLS 加密的对比

Wireshark 分别捕获两种 SMTP 会话。**明文（端口 25）**：

```
Client → Server: EHLO client.example.com
Server → Client: 250-mail.example.com Hello
                 250-STARTTLS
                 250 OK
Client → Server: MAIL FROM:<alice@example.com>
Server → Client: 250 OK
Client → Server: DATA
Server → Client: 354 Start mail input
Client → Server: Subject: Secret Meeting
                 Let's meet at 3pm. Don't tell anyone.
                 .
Server → Client: 250 OK
```

所有内容明文可见——主题、正文、收件人一览无余。

**STARTTLS（端口 587）**：先明文握手，`STARTTLS` 命令后切换加密：

```
Client → Server: EHLO client.example.com
Server → Client: 250-STARTTLS ...
Client → Server: STARTTLS              ← 从这里开始切换
Server → Client: 220 Ready to start TLS
Client → Server: [TLS ClientHello]     ← 15.2 的握手登场
...
Client → Server: [Application Data]    ← 加密后的 SMTP 命令
```

切换点之后 Wireshark 里只剩 `Application Data`，无法分辨是 SMTP 还是别的协议——这正是 15 章加密的直接效果。对照两种抓包，你就明白为什么生产环境必须强制 TLS：加密不是可选项，是邮件内容的基本尊严。

## 本章小结

- SMTP 是文本命令式协议：HELO → MAIL → RCPT → DATA → QUIT，三位数字响应码与 HTTP 状态码一脉相承。
- MIME 用 boundary 分段、base64 编码，让 7 位 ASCII 的通道扛起了附件与多语言——「用编码换通道」。
- SMTP 只送信不收信：POP3 拿回家（单设备友好），IMAP 留在信箱（多设备同步）——现代默认是 IMAP。
- FTP 控制与数据分离，命令不阻塞传输；但数据连接谁发起成了难题，被动模式胜出因为客户端多在 NAT 后。
- SSH 的信任锚不是 CA 而是 known_hosts 的 TOFU——与 15.4 的第三方背书是两种信任模型。
- SSH 公钥认证优于密码认证：签名挑战值，天然免疫暴力破解。
- 端口转发三式：-L 拉远程到本地、-R 推本地到远程、-D 起 SOCKS——一条加密连接承载多种通道。
- 明文与 STARTTLS 的抓包对比是最直观的安全教育：加密之后，协议身份与内容全部隐身。
