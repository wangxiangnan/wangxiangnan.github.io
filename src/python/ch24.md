# 第 24 章 Git 协作与项目结构

你写了一个自认为完美的程序，存在 U 盘里交给老师。老师问："上次那个版本呢？还能找回吗？"你说："覆盖了……"——这是单人开发的困境。如果多个人一起写代码呢？你改了 A 文件，同事也改了 A 文件，合并时谁对谁错？这是团队协作的困境。

Git 就是为了解决这两个问题而生的：版本控制（保留历史、随时回退）和协作管理（多人并行开发、合并代码）。本章将带你掌握 Git 工作流的核心操作，并学习 Python 项目的标准目录结构——让你的项目不仅代码写得好，"长相"也专业。

## 24.1 Git 基础回顾

假设你已经了解 `git init`、`git add`、`git commit`、`git status` 这些基本操作（如果还不熟，先花 30 分钟过一遍 Git 入门教程），我们直接从团队协作开始。

### 分支：平行宇宙

分支（branch）是 Git 最强大的特性之一。每个分支就像代码库的一个平行宇宙——你可以在分支上自由修改，不影响主线。

```bash
# 查看所有分支
git branch

# 创建并切换到新分支
git checkout -b feature/user-login
# 或（Git 2.23+）
git switch -c feature/user-login

# 在新分支上开发、提交
git add .
git commit -m "feat: 实现用户登录功能"

# 切回主分支
git switch main

# 合并分支
git merge feature/user-login

# 删除已合并的分支
git branch -d feature/user-login
```

### 分支命名约定

好的分支命名让人一眼知道你在做什么：

```
feature/user-login        # 新功能
bugfix/null-pointer-fix   # Bug 修复
hotfix/security-patch     # 紧急修复（直接在 main 上出问题）
refactor/database-layer   # 重构
docs/update-readme        # 文档更新
```

## 24.2 Git 工作流

### GitHub Flow（最简洁，适合小团队）

```
main（始终保持可部署状态）
  └── feature/xxx（从 main 创建）
       └── 开发、提交
       └── 创建 Pull Request
       └── Code Review
       └── 合并到 main
       └── 部署
```

```bash
# 1. 从 main 创建功能分支
git switch main
git pull origin main
git switch -c feature/search-api

# 2. 开发并定期提交
git add src/search.py
git commit -m "feat: add search endpoint"

# 3. 推送到远程
git push -u origin feature/search-api

# 4. 在 GitHub 上创建 Pull Request
# 5. 等待 Code Review
# 6. Review 通过后合并
# 7. 删除远程分支（GitHub 上点按钮）
git branch -d feature/search-api
```

### Git Flow（更规范，适合发布周期长的项目）

```
main（生产环境代码）
  └── develop（开发主线）
       └── feature/xxx（功能分支）
       └── bugfix/xxx（bug 修复）
  └── release/x.x（发布分支，做最终测试）
  └── hotfix/xxx（紧急修复，从 main 创建）
```

小贴士：大部分现代项目（Web 应用、API 服务、库）用 GitHub Flow 就够了。Git Flow 更适合有版本发布周期的项目（如桌面软件、SDK）。

## 24.3 Pull Request 与 Code Review

Pull Request（PR，GitHub）或 Merge Request（MR，GitLab）不仅是一个合并请求，更是团队沟通的核心工具。

### 好的 PR 应该包含

```markdown
## 描述
简要说明这个 PR 做了什么、为什么这样做。

## 变更类型
- [x] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档

## 测试
- 新增单元测试 5 个
- 所有测试通过：pytest ✓
- 手动测试了 X、Y、Z 场景

## 截图/录屏
（如果是 UI 变更，附上截图）

## 备注
这个方案参考了 XXX 的思路，但做了 YYY 调整因为 ZZZ。
```

### Code Review 指南

**作为 Reviewer：**

- 先看整体设计，再看细节
- 关注逻辑正确性 > 边界情况 > 代码风格（风格交给工具）
- 给出建设性反馈，而不是"这不对"
- 区分"必须改"和"建议改"

**作为 PR 作者：**

- PR 要小（建议不超过 400 行改动）
- 自己先 Review 一遍再提
- 及时响应 Review 意见
- 合并前确保 CI 通过

## 24.6 src/ 布局 vs 扁平布局

### 扁平布局（flat layout）

```
my_project/
├── my_project/        # 包目录直接放在项目根下
│   ├── __init__.py
│   └── core.py
├── tests/
└── pyproject.toml
```

### src/ 布局

```
my_project/
├── src/
│   └── my_project/    # 包目录放在 src/ 下
│       ├── __init__.py
│       └── core.py
├── tests/
└── pyproject.toml
```

### 为什么要用 src/ 布局？

扁平布局有一个隐蔽的问题：在项目根目录运行 Python 时，`my_project/` 目录会直接出现在 `sys.path` 中。这意味着即使你没有安装这个包，`import my_project` 也能成功——但导入的可能不是你以为的那个版本。

src/ 布局强制你必须先安装包（`pip install -e .`），才能 `import` 它。这确保了测试环境和最终用户的使用方式一致。

```bash
# src/ 布局下，必须先安装再测试
pip install -e ".[dev]"  # 开发模式安装
pytest                    # 此时 import 的是安装后的包
```

小贴士：如果你开发的是要发布到 PyPI 的库，推荐 src/ 布局。如果只是内部工具或应用，扁平布局也完全可以。

## 24.8 实用的 Git 技巧

### 暂存工作区（stash）

```bash
# 正在开发功能 A，突然要修一个紧急 bug
git stash  # 暂存当前修改

# 修完 bug 后恢复
git stash pop

# 查看暂存列表
git stash list

# 恢复指定的暂存
git stash apply stash@{1}
```

### 交互式变基（rebase）

```bash
# 把你的分支的提交"整理"一下再合并
# 例如把 3 个小提交合并成 1 个
git switch feature/my-feature
git rebase -i HEAD~3  # 整理最近 3 个提交

# 在编辑器中：
# pick feat: 开始实现
# squash feat: 继续实现    ← 合并到上一个
# squash feat: 完成实现    ← 合并到上一个
```

小贴士：`rebase -i` 是整理提交历史的利器，但对已经推送到远程的提交要谨慎使用——如果别人已经基于你的提交开始工作，rebase 会造成混乱。

### 查看历史

```bash
# 简洁的提交历史
git log --oneline --graph --all

# 查看某个文件的修改历史
git log -p -- src/core.py

# 查看某一行是谁在什么时候改的
git blame src/core.py

# 搜索提交信息
git log --grep="fix login"
git log --author="Alice"
```

### 别名配置

```bash
# 常用别名
git config --global alias.st status
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.lg "log --oneline --graph --all"

# 使用
git st     # = git status
git lg     # = git log --oneline --graph --all
```

## 24.13 参考答案

**第 2 题：**

```bash
# 确保在 main 分支并且是最新
git switch main
git pull origin main

# 创建功能分支
git switch -c feature/add-search

# 第一次提交
echo "# Search Module" > src/search.py
git add src/search.py
git commit -m "feat: add search module skeleton"

# 第二次提交
# （编辑 src/search.py 添加代码）
git add src/search.py
git commit -m "feat: implement search function"

# 第三次提交
# （添加测试）
git add tests/test_search.py
git commit -m "test: add search tests"

# 合并回 main
git switch main
git merge feature/add-search

# 删除功能分支
git branch -d feature/add-search
```

**第 3 题：**

`git merge` 创建一个新的"合并提交"，保留完整的分支历史（两条线合为一条）。优点：历史完整、安全。缺点：提交历史可能比较乱。

`git rebase` 把你的提交"搬到"目标分支的最新提交之上，看起来像一条直线。优点：历史干净。缺点：改写了提交历史，如果提交已经推送到远程并被他人使用，会造成冲突。

使用场景：公共分支（main/develop）用 merge，个人功能分支在合并前用 rebase 整理提交。

**第 5 题：**

`.env` 文件包含敏感信息（API 密钥、数据库密码等），提交到 Git 会导致密钥泄露。团队协作时应该：1. 在 `.gitignore` 中排除 `.env`；2. 提供 `.env.example` 作为模板（只包含变量名和示例值）；3. 每个开发者自己创建 `.env` 文件填入真实值；4. 生产环境用环境变量或密钥管理服务注入。

**第 6 题：**

```
feat: add user authentication endpoint
fix: correct null pointer in order processing
docs: update API reference for v2 endpoints
refactor: extract validation logic into separate module
chore: update dependencies to latest versions
```

**第 7 题：**

扁平布局下，项目根目录在 `sys.path` 中，`import my_project` 会直接导入项目目录中的包——即使你没有安装它。这意味着测试可能通过了，但用户安装后行为可能不同（比如缺少 `__init__.py` 中的导出）。

src/ 布局下，`src/my_project/` 不在项目根目录，Python 找不到它。你必须先 `pip install -e .` 安装包，测试中的 `import` 才能成功。这确保了测试环境和用户环境一致。

## 24.14 常见错误与避坑

**1. 把秘密提交到 Git**

```bash
# 即使后来删除了，Git 历史中仍然存在！
# 如果不小心提交了 .env 或密钥文件：

# 立即从历史中清除
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env" \
  --prune-empty -- --all

# 或者用 git-filter-repo（更现代的工具）
pip install git-filter-repo
git filter-repo --path .env --invert-paths

# 重要：强制推送后通知团队成员重新克隆
# 并且立即轮换所有泄露的密钥！
```

**2. 在 main 分支上直接开发**

```bash
# 不要这样！
git switch main
# 直接写代码、提交...

# 应该创建功能分支
git switch -c feature/xxx
# 在分支上开发
```

直接在 main 上开发会导致：main 经常处于不稳定状态、无法并行开发多个功能、Code Review 变得困难。

**3. 巨大的提交**

一次性提交 50 个文件的修改，Review 的人看到就头疼。保持提交小而有意义——一个提交做一件事。

**4. 无意义的提交信息**

```
# 不好的提交信息
"fix"
"update"
"changes"
"asdf"

# 好的提交信息
"feat: add pagination to user list API"
"fix: handle empty response from payment gateway"
"refactor: extract email validation into utils module"
```

**5. 忘记 pull 就 push**

```bash
# 如果你和远程分支有分叉，直接 push 会失败
git push  # error: failed to push

# 先拉取远程变更
git pull --rebase  # 把你的提交变基到远程最新之上
git push
```

**6. 不写 README**

一个没有 README 的项目就像一个没有说明书的工具——别人不知道怎么用。哪怕只写三段话（这是什么、怎么安装、怎么用），也比空白好一万倍。
