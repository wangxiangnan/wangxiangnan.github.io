# 第6章：Git与版本控制深度集成

> `git add . && git commit -m "fix"` 是每个程序员都会的基本功。但日常开发里，真正耗时的往往不是敲命令，而是**看清改了什么、只提交该提交的部分、把冲突解对**。VSCode 的 Git 集成把这些步骤搬进了编辑器：暂存、提交、推送、Diff、冲突解决、历史追溯都有对应的界面。

这一章不是要取代命令行。更合理的用法是：**需要看清上下文时用 GUI，需要精确控制或批量操作时用命令行**。两者共用同一个仓库，随时可以切换。

## 6.1 源代码管理视图

源代码管理（Source Control，简称 SCM）视图是 Git 操作的主入口。快捷键：`Ctrl+Shift+G`（macOS `⌘+Shift+G`）。

### 视图结构

```
源代码管理
├── 仓库（Repositories）        ← 多仓库时切换当前仓库
├── 更改（Changes）             ← 未暂存的修改
│   ├── M  src/components/Button.tsx
│   ├── A  src/hooks/useAuth.ts
│   ├── D  src/old-utils.ts
│   └── U  src/config.local.ts
├── 暂存的更改（Staged Changes） ← 已暂存，准备提交
│   ├── M  src/App.tsx
│   └── M  package.json
├── 合并中的更改（Merge Changes） ← 冲突文件
│   └── C  src/config.ts
└── 提交消息输入框
    [输入提交消息...]
    [✓ 提交] [↻ 同步] [...]
```

较新版本的 VSCode 通过 **Repositories** 视图管理多个仓库，默认可以同时选中多个；仓库切换和选择模式的细节见 6.8。

### 文件状态字母

SCM 视图和资源管理器会用字母标记文件状态。字母比颜色更可靠，因为主题不同，颜色可能变化。

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| `M` | Modified | 已跟踪文件被修改 |
| `A` | Added | 新文件已加入暂存区 |
| `D` | Deleted | 文件被删除 |
| `R` | Renamed | 文件被重命名 |
| `U` | Untracked | 新文件，尚未被 Git 跟踪 |
| `C` | Conflict | 合并、变基或拣选时产生冲突 |

### 暂存与取消暂存

- 鼠标悬停在“更改”中的文件上，点击行末的 **+**：暂存该文件。
- 点击“更改”标题旁的 **+**：暂存全部更改。
- 在“暂存的更改”中点击 **−**：取消暂存。
- 右键文件：`Stage Changes`、`Unstage Changes`、`Discard Changes`。

`Discard Changes` 会直接丢弃工作区修改，无法用普通撤销找回。执行前先确认这个文件没有你想保留的内容。

只暂存一个文件里的**部分行**，见 6.2 的“部分暂存”。

### 提交消息与智能提交

在输入框写好提交消息后，按 `Ctrl+Enter`（macOS `⌘+Enter`）提交。默认只提交**已暂存**的内容；如果没有暂存任何文件，VSCode 会根据 Smart Commit 设置提示或自动暂存。

```jsonc
{
  // 没有暂存文件时，提交自动暂存更改
  "git.enableSmartCommit": true,

  // all: 暂存全部更改；tracked: 只暂存已跟踪文件
  "git.smartCommitChanges": "tracked",

  // 输入框为空时，用完整编辑器撰写提交消息
  "git.useEditorAsCommitInput": true,

  // 提交消息校验：布尔开关，不是 "warn"/"error"
  "git.inputValidation": true,
  "git.inputValidationLength": 72,
  "git.inputValidationSubjectLength": 50
}
```

`git.inputValidation` 是**布尔值**，打开后才会按长度阈值提示；长度阈值本身不负责开关。`git.smartCommitChanges: "tracked"` 适合“新文件想先检查再提交”的场景；如果你希望一次提交所有内容，用“更改”标题旁的 `...` → **Commit** → **Commit All**。

`git.useEditorAsCommitInput` 默认是 `true`：当输入框里没有消息时，提交会打开一个完整编辑器，方便写多行说明。喜欢在输入框里写短消息，可以把它设为 `false`。

## 6.2 差异编辑器与部分暂存

### 打开差异

- 在 SCM 视图点击任意更改文件。
- 命令面板执行 `Git: Open Changes`：查看当前文件的改动。
- 命令面板执行 `Git: Open All Changes`：把所有修改和未跟踪文件打开到多文件差异编辑器。

工作区差异的右侧是实际文件，可以直接编辑；提交与提交之间的历史差异通常是只读的。这样你可以一边看差异，一边修代码，不用来回切换标签页。

### 并排与内联

默认是并排（Side by Side）：左边是原始版本，右边是修改版本。点击差异编辑器右上角的 `...`，选择 **Inline View**，可以切换成单栏内联模式；再选 **Side by Side** 切回来。

```
并排模式
┌──────────────────────┬──────────────────────┐
│ 原始版本 (HEAD)       │ 修改版本 (Working)    │
│ function add(a, b) { │ function add(        │
│   return a + b;      │   a: number,         │
│ }                    │   b: number          │
│                      │ ): number {          │
│                      │   return a + b;      │
│                      │ }                    │
└──────────────────────┴──────────────────────┘
```

### 在差异之间跳转

| 快捷键 | 说明 |
| --- | --- |
| `Alt+F5` | 下一个变更 |
| `Shift+Alt+F5` | 上一个变更 |

macOS 对应 `Option+F5` / `Shift+Option+F5`。在并排差异中，行号槽（gutter）里的箭头可以**还原单个变更块**；在 SCM 工作区差异里，这相当于丢弃这一块修改，操作前看清楚。

### 部分暂存：只提交想提交的行

这是 VSCode Git 工作流里最实用的能力之一，但**不是 VSCode 独有**，很多 Git 客户端都支持。VSCode 的优势是直接把它和差异编辑器结合了起来。

1. 在 SCM 视图点击文件，打开差异。
2. 在右侧（工作区版本）选中要提交的行。
3. 点击选中区域旁 gutter 里的 **Stage** 按钮，或右键选择 **Stage Selected Ranges**。
4. 也可以命令面板执行 `Git: Stage Selected Ranges`。

对应的反向操作是 `Git: Unstage Selected Ranges` 和 `Git: Revert Selected Ranges`。这样可以把“修 bug”和“顺手重构”拆成两个提交，而不是被迫混在一起。

### 多文件差异

`Git: Open All Changes` 会打开一个多文件差异编辑器。顶部是文件列表，可以逐个查看；也可以用 `Ctrl+Tab` 在已打开的编辑器之间切换。文件多的时候，先在 SCM 视图里筛一遍，比在几十个标签页里翻更高效。

### 行内装饰

编辑器左侧的 gutter 会用颜色标记改动：绿色是新增，黄色是修改，红色三角是删除。相关设置：

```jsonc
{
  "git.decorations.enabled": true,
  "scm.diffDecorations": "all",
  "scm.diffDecorationsGutterWidth": 3,
  "scm.diffDecorationsGutterAction": "diff"
}
```

`scm.diffDecorations` 可设为 `all`、`overview`、`gutter`、`none`；`scm.diffDecorationsGutterAction` 设为 `diff` 时，点击 gutter 装饰会打开差异。

## 6.3 提交、同步与分支

### 提交的三种方式

| 方式 | 行为 | 适用场景 |
| --- | --- | --- |
| 提交按钮 / `Ctrl+Enter` | 提交已暂存内容；无暂存时按 Smart Commit 设置处理 | 日常提交 |
| `...` → Commit → Commit All | 提交全部更改 | 确认所有改动都属于同一个提交 |
| 命令面板 `Git: Commit Staged` | 只提交已暂存内容 | 想明确避开 Smart Commit 的自动暂存 |

提交后如果发现消息写错，可以执行 `Git: Undo Last Commit` 撤销最近一次提交并保留改动，再重新提交。这个操作只适合**还没有推送**的本地提交；已经推送的历史不要随便改写。

### 同步、拉取与推送

状态栏和 SCM 标题栏提供 `Sync`、`Pull`、`Push` 等按钮，命令面板里也有对应命令：

- `Git: Pull`：拉取远程更改。
- `Git: Pull (Rebase)`：拉取后把本地提交变基到远程分支上，历史更线性。
- `Git: Push`：推送本地提交。
- `Git: Sync`：先拉取再推送。
- `Git: Sync (Rebase)`：同步时使用变基。
- `Git: Publish Branch`：把本地新分支发布到远程。

```jsonc
{
  // 自动 fetch，不自动合并
  "git.autofetch": true,
  "git.autofetchPeriod": 180,
  "git.pruneOnFetch": true,

  // 同步前不再弹确认框
  "git.confirmSync": false,

  // 让 Sync 默认使用 rebase
  "git.rebaseWhenSync": true,

  // 提交成功后不自动推送
  "git.postCommitCommand": "none"
}
```

`git.autofetch` 还可以设为字符串 `"all"`，表示从所有远程抓取。`git.pruneOnFetch` 会清理远程已删除分支对应的远程跟踪引用，不会删你的本地分支。`git.confirmSync` 设为 `false` 会减少一次确认，但代价是少了一道“确认目标分支”的检查。

推送被拒绝通常是因为远程有你本地没有的提交。先 `Git: Pull (Rebase)` 处理冲突，再推送；不要用强推把别人的提交覆盖掉。确实需要强推时，先和协作者确认，并优先使用 `--force-with-lease`。

### 分支

点击状态栏左下角的分支名，可以：

- 切换分支。
- 创建新分支（Create new branch）。
- 从指定分支创建（Create Branch From）。
- 重命名或删除分支。

命令面板也提供 `Git: Create Branch...`、`Git: Delete Branch...` 等命令。新建功能分支前，先 `Git: Pull` 一下主分支，避免从过期的基线上开始。

### 创建 Pull Request

安装 **GitHub Pull Requests** 扩展后，推送分支时 VSCode 会提供创建 PR 的入口，也可以从 SCM 视图发起。PR 的标题、描述、审阅者可以在 VSCode 里填写；真正的评审和合并仍可能在浏览器里完成。别为了“全程不离开编辑器”而绕开团队已有的评审流程。

## 6.4 时间线与本地历史

### Timeline 视图

Timeline 显示**当前打开文件**的事件，包括 Git 提交和本地保存记录。位置在资源管理器侧边栏底部；也可以从命令面板执行 `Timeline: Toggle Visibility` 打开。

```
TIMELINE
├── 10 minutes ago · You
│   └── feat: add user authentication      a1b2c3d
├── 2 hours ago · You
│   └── fix: correct login redirect URL    e4f5g6h
├── Yesterday · Alice
│   └── refactor: extract auth service     i7j8k9l
└── Local History
    ├── Auto Save 5 min ago
    └── Auto Save 10 min ago
```

常用操作：

- 点击提交条目：查看该提交与当前文件的差异。
- 右键提交 → **Select for Compare**，再右键另一个提交 → **Compare with Selected**：比较两个历史版本。
- 右键提交 → **Copy Commit ID**：复制提交哈希，方便在终端里继续操作。
- 顶部筛选按钮可以分别开关 Git History 和 Local History。

需要看整个分支的历史，而不是单个文件，可以打开**源代码管理图（Source Control Graph）**视图；它把提交、分支和合并关系画成图。GitLens 的 Commit Graph 更完整，但属于 Pro 功能（见 6.7）。

### Local History：没提交也能找回

Local History 是 VSCode 自己保存的本地文件快照，和 Git 提交是两套机制。它在 Timeline 里以本地记录的形式出现，适合找回“改着改着删掉了，但还没提交”的代码。

- 右键 Local History 条目 → **Compare with Previous** / **Compare with File**：查看差异。
- 右键 → **Restore Contents**：把文件恢复到该快照。
- 命令面板执行 `Local History: Find Entry to Restore`：按文件查找要恢复的条目。

相关设置：

```jsonc
{
  "workbench.localHistory.enabled": true,

  // 每个文件最多保留 50 条记录
  "workbench.localHistory.maxFileEntries": 50,

  // 超过 256 KB 的文件不生成快照（单位：KB）
  "workbench.localHistory.maxFileSize": 256,

  // 10 秒内的连续保存合并为一条记录
  "workbench.localHistory.mergeWindow": 10,

  "workbench.localHistory.exclude": {
    "**/node_modules/**": true,
    "**/dist/**": true
  }
}
```

注意两点：Local History 只保存在本机，不会随 Git 推送，也不能替代提交；未命名文件、被排除的路径、超过大小限制的文件不会出现在历史里。

## 6.5 合并冲突与三方合并编辑器

### 冲突是怎么标的

合并、变基、拣选（cherry-pick）都可能产生冲突。冲突文件会进入“合并中的更改”，状态字母为 `C`。打开文件后，默认的冲突标记是两段：

```typescript
<<<<<<< HEAD
const API_URL = "https://api.production.com";
=======
const API_URL = "https://api.staging.com";
>>>>>>> feature/update-api
```

- `HEAD` 一侧是**当前分支**（Current）。
- `>>>>>>>` 一侧是**要合入的分支**（Incoming）。
- 如果团队配置了 `merge.conflictStyle=diff3`，中间还会多出 `|||||||` 开头的共同祖先版本；VSCode 也能识别。

在冲突块上方，VSCode 会显示内联操作：

- **Accept Current Change**
- **Accept Incoming Change**
- **Accept Both Changes**
- **Compare Changes**

简单冲突直接点按钮即可；复杂冲突建议打开合并编辑器。

### 三方合并编辑器

右键冲突文件 → **Resolve in Merge Editor**（文档里也叫 Open in Merge Editor）。如果希望所有冲突都自动用它打开，设置：

```jsonc
{
  "git.mergeEditor": true,
  "mergeEditor.diffAlgorithm": "advanced",
  "mergeEditor.showDeletionMarkers": true
}
```

`git.mergeEditor` 默认是 `false`，所以不设置时也能手动打开。合并编辑器的布局是：

```
┌──────────────────┬──────────────────┐
│ Incoming（左）    │ Current（右）     │
│ 要合入的版本      │ 当前分支版本      │
├──────────────────┴──────────────────┤
│ Result（下，可编辑）                 │
│                                      │
│ 选择、组合或手动编辑，直到冲突消失    │
└──────────────────────────────────────┘
```

注意左右顺序：**Incoming 在左，Current 在右，Result 在底部**。需要看共同祖先时，点右上角 `...` → **Show Base**。在结果区可以接受某一侧、组合双方，也可以直接手动改。所有冲突处理完后点击 **Complete Merge**，VSCode 会暂存该文件并关闭合并编辑器。

### 完成或中止

- 普通合并：所有冲突文件 Complete Merge 后，提交这次合并。
- 变基：冲突解决并暂存后，在终端执行 `git rebase --continue`。内置 Git 集成没有单独的“Continue Rebase”命令，这一步用命令行最直接。
- 拣选：解决冲突后执行 `git cherry-pick --continue`。

想放弃当前操作，可以执行 `Git: Abort Merge`、`Git: Abort Rebase` 或 `Git: Abort Cherry Pick`。中止会回到操作前的状态，但你在冲突解决过程中手动做的修改也会一并丢弃，执行前确认。

> 变基时的 Current/Incoming 含义和普通合并相反：Current 是你要变基到的上游分支，Incoming 是你正在重放的提交。别死记“Current 就是我的分支”，以编辑器里的分支提示和提交信息为准。

## 6.6 变基与历史整理

### 内置的普通变基

命令面板执行 `Git: Rebase Branch...`，选择目标分支，VSCode 会把当前分支变基到该分支上。这是**非交互式**变基，不会出现可拖拽的提交列表。执行前确保工作区干净（提交或 stash），否则 Git 会拒绝。

变基过程中如果冲突，按 6.5 解决，然后执行 `git rebase --continue`；想放弃就执行 `Git: Abort Rebase`。

`Git: Pull (Rebase)` 和 `Git: Sync (Rebase)` 也是变基，但它们发生在拉取/同步时，和“把当前分支变基到某个分支”不是同一件事。

### 交互式变基：内置方式

VSCode 没有内置的可视化交互式变基编辑器。最稳的方式仍是 `git rebase -i`，只是把编辑器换成 VSCode：

```bash
git config --global core.editor "code --wait"
git rebase -i HEAD~5
```

如果 Git 使用单独的 sequence editor 编辑待办列表，再设置：

```bash
git config --global sequence.editor "code --wait"
```

保存并关闭待办列表标签页后，Git 才会继续。待办列表里的操作：

| 操作 | 缩写 | 说明 |
| --- | --- | --- |
| `pick` | `p` | 保留该提交 |
| `reword` | `r` | 保留提交，修改提交消息 |
| `edit` | `e` | 暂停在该提交，允许修改内容 |
| `squash` | `s` | 合并到前一个提交，并编辑合并后的消息 |
| `fixup` | `f` | 合并到前一个提交，丢弃该提交的消息 |
| `drop` | `d` | 丢弃该提交 |

调整行的顺序就是调整提交顺序；删掉一行等同于 `drop`。`edit` 暂停后，修改完要 `git add` 再 `git rebase --continue`。中途想放弃，执行 `git rebase --abort`。

### GitLens 的交互式 Rebase 编辑器

安装 GitLens 后，可以从命令面板执行它的 Rebase 命令，或在 Commit Graph 里选择提交进行交互式整理。GitLens 提供可视化的 Interactive Rebase Editor，可以调整顺序、选择 squash/fixup/reword/drop；这个功能属于 **GitLens Pro**，免费版仍可用上面的 `git rebase -i` 方式。

### 变基的风险

变基会改写提交哈希。已经推送、且别人可能基于它工作的分支，不要随意变基；团队约定用 merge 就用 merge。强推前先沟通，并优先使用 `--force-with-lease`。

## 6.7 提交追溯与进阶操作

### 内置 Git Blame

VSCode 1.97 起内置了基础 Git Blame，不再必须安装扩展：

- 编辑器行内装饰显示光标所在行的最后修改信息。
- 状态栏显示当前行的作者和时间。
- 鼠标悬停可以查看更详细的信息。

默认状态是：**行内装饰关闭，状态栏开启**。用命令面板切换：

- `Git: Toggle Git Blame Editor Decoration`
- `Git: Toggle Git Blame Status Bar Item`

```jsonc
{
  "git.blame.editorDecoration.enabled": true,
  "git.blame.editorDecoration.template": "${subject}, ${authorName} (${authorDateAgo})",
  "git.blame.statusBarItem.enabled": true,
  "git.blame.statusBarItem.template": "${authorName} (${authorDateAgo})",
  "git.blame.ignoreWhitespace": false
}
```

模板支持 `${hash}`、`${hashShort}`、`${subject}`、`${authorName}`、`${authorEmail}`、`${authorDate}`、`${authorDateAgo}` 等变量。行内装饰默认关闭是有意的：它能提供信息，但也会占用编辑空间。

如果同时装了 GitLens，内置状态栏和 GitLens 的行内 blame 可能重复，保留一个即可。

### GitLens：更完整的历史视图

GitLens 仍然是最流行的 Git 扩展之一，免费版就包含当前行 blame、CodeLens 和悬停信息；Commit Graph、交互式 Rebase Editor 等属于 Pro。常用设置：

```jsonc
{
  "gitlens.currentLine.enabled": true,
  "gitlens.codeLens.enabled": true
}
```

GitLens 的设置项会随版本调整，遇到对不上的键名，直接在设置 UI 搜索 `gitlens` 更可靠。

### Stash

命令面板提供完整的 stash 操作：

| 命令 | 作用 |
| --- | --- |
| `Git: Stash` | 暂存当前修改（可输入说明） |
| `Git: Stash (Include Untracked)` | 连未跟踪文件一起暂存 |
| `Git: Stash Staged` | 只暂存已暂存的内容 |
| `Git: Apply Stash...` | 应用某个 stash，保留 stash 记录 |
| `Git: Pop Stash...` | 应用并删除该 stash |
| `Git: View Stash...` | 查看 stash 内容 |
| `Git: Drop Stash...` | 删除某个 stash |
| `Git: Drop All Stashes...` | 删除全部 stash |

`Apply` 和 `Pop` 的区别很关键：前者可以重复应用，后者应用后就从列表里消失。`Drop All Stashes` 是破坏性操作，先确认没有还想保留的进度。stash 不是备份，重要工作还是应该提交到分支。

### Cherry-pick

命令面板执行 `Git: Cherry Pick...`，从快速选择里挑一个提交，把它应用到当前分支。冲突时按 6.5 解决，然后：

```bash
git cherry-pick --continue
```

想放弃就执行 `Git: Abort Cherry Pick` 或 `git cherry-pick --abort`。GitLens 的 Commit Graph 也提供右键 Cherry Pick。

### Undo 与 Revert

这两个词很容易混：

- `Git: Undo Last Commit`：撤销**最近一次**本地提交，保留改动。适合刚提交完发现漏了文件，且还没推送。
- `git revert <commit>`：创建一个**反向提交**，抵消目标提交的改动。历史不会被改写，适合已经推送的提交。
- `Git: Revert Change` / `Git: Revert Selected Ranges`：只还原差异中的某个变更块，属于工作区操作，执行前确认。

任意提交的 revert 在 VSCode 内置 Git 里没有独立的全功能入口，直接用终端最清楚：

```bash
git revert <commit-hash>
```

## 6.8 多仓库、设置与完整工作流

### Repositories 视图

多仓库工作区里，较新版本的 VSCode 通过 **Repositories** 视图管理仓库。命令面板执行 `Source Control: Focus on Repositories View` 可以聚焦到它。

```jsonc
{
  // 即使只有一个仓库，也显示仓库行
  "scm.alwaysShowRepositories": true,

  // multiple（新版默认）：可同时选择多个仓库；single：一次只看一个
  "scm.repositories.selectionMode": "multiple"
}
```

`selectionMode` 为 `multiple`（新版默认）时可以同时选中多个仓库，SCM 视图会汇总它们的更改，适合前后端一起改的场景；设为 `single` 后，在 Repositories 视图里点哪个仓库，SCM 视图就只显示哪个仓库。旧版本可能没有这个设置，也可能默认是 `single`。

### 仓库探测

工作区里的仓库不会总能被自动发现。相关设置：

```jsonc
{
  // true | "subFolders" | "openEditors" | false
  "git.autoRepositoryDetection": true,

  // 额外扫描的路径
  "git.scanRepositories": ["./packages"],

  // 扫描子目录的最大深度
  "git.repositoryScanMaxDepth": 3,

  // 打开子目录时，如何处理父目录里的仓库
  "git.openRepositoryInParentFolders": "prompt"
}
```

`git.openRepositoryInParentFolders` 可取 `prompt`、`always`、`never`。如果你打开的是大型 monorepo 的子目录，VSCode 可能会提示使用父目录的仓库；选 `never` 可以避免这种自动向上查找，但也意味着你要自己把正确的仓库加进工作区。

### 实战：一个 Feature 分支的完整流程

假设要给项目加“用户头像上传”功能。

**1. 从最新的主分支开分支**

```text
点击状态栏分支名 → Create new branch...
输入：feature/avatar-upload
基于：main
```

如果本地 `main` 落后，先 `Git: Pull`，再开分支。

**2. 编码，随时看差异**

SCM 视图会实时列出修改。点击文件查看差异，利用 gutter 装饰确认哪些是新增、哪些是修改。

**3. 只暂存该提交的部分**

在差异编辑器里选中与头像上传相关的行，执行 `Git: Stage Selected Ranges`；把顺手改的日志、调试代码留在“更改”里，等会儿单独提交或丢弃。

**4. 提交**

```text
feat(user): add avatar upload component

- Add AvatarUpload component with drag & drop
- Implement image cropping with react-cropper
- Add file size and type validation
- Update UserSettings page to include avatar upload

Closes #142
```

按 `Ctrl+Enter` 提交。提交后检查“暂存的更改”是否清空，确认没有漏文件。

**5. 同步并解决冲突**

如果远程 `main` 有更新，执行 `Git: Pull (Rebase)`。遇到冲突时：

1. 打开冲突文件，简单冲突点 Accept Current/Incoming/Both。
2. 复杂冲突右键 **Resolve in Merge Editor**。
3. 在 Result 区处理完，点 **Complete Merge**。
4. 终端执行 `git rebase --continue`。

**6. 推送并创建 PR**

执行 `Git: Push`。首次推送新分支时用 `Git: Publish Branch`。安装了 GitHub Pull Requests 扩展后，可以从 VSCode 发起 PR；评审和合并按团队流程走。

**7. 合并后清理**

切回 `main`，`Git: Pull`，然后删除本地功能分支（`Git: Delete Branch...`）。远程分支是否删除，取决于团队的 PR 设置。

### 常见问题

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 提交只包含一部分文件 | 只暂存了部分文件；`smartCommitChanges` 设为 `tracked` | 查看“暂存的更改”；需要全部提交时用 Commit All |
| 看不到某个仓库 | 仓库在子目录/父目录，未被探测 | 打开 Repositories 视图；调整 `git.autoRepositoryDetection`、`git.scanRepositories`、`git.openRepositoryInParentFolders` |
| 行内 Blame 不显示 | 内置行内装饰默认关闭 | 执行 `Git: Toggle Git Blame Editor Decoration`，或设置 `git.blame.editorDecoration.enabled` |
| Local History 没有记录 | 功能被关闭、文件超过大小限制、路径被排除 | 检查 `workbench.localHistory.enabled`、`maxFileSize`、`exclude` |
| 合并编辑器没有自动打开 | `git.mergeEditor` 默认是 `false` | 右键冲突文件 → Resolve in Merge Editor，或把设置改为 `true` |
| 变基冲突解决后卡住 | 只完成了文件合并，没有继续变基 | 终端执行 `git rebase --continue` |
| 交互式变基打开了 Vim | `core.editor` / `sequence.editor` 没指向 VSCode | 设为 `code --wait`，保存并关闭标签页后才继续 |
| 推送被拒绝 | 远程有本地没有的提交 | 先 Pull (Rebase) 解决冲突，再推送；不要直接强推 |
| 多仓库只显示一个 | `scm.repositories.selectionMode` 被设为 `"single"`（旧版默认） | 在 Repositories 视图切换仓库，或把设置改为 `"multiple"` |
| Stash 应用后不见了 | 用了 Pop 而不是 Apply | 需要保留记录时用 Apply Stash；不要轻易 Drop All Stashes |

📋 **本章小结**

- **SCM 视图**是 Git 操作中心：暂存、取消暂存、提交、同步、分支切换都能在这里完成
- **部分暂存**通过差异编辑器选中行、gutter 的 Stage 按钮或 `Git: Stage Selected Ranges` 完成，不是 VSCode 独有
- **Diff 编辑器**支持并排和内联模式，工作区差异的右侧可直接编辑，`Alt+F5` / `Shift+Alt+F5` 在变更间跳转
- **提交**默认只包含已暂存内容；Smart Commit、Commit All、`git.useEditorAsCommitInput` 控制不同的提交习惯
- **Timeline** 同时展示 Git 提交和本地保存；Local History 用 `workbench.localHistory.*` 配置，能找回未提交的修改
- **三方合并编辑器**的布局是 Incoming 在左、Current 在右、Result 在下；完成后用 Complete Merge 暂存文件
- **内置变基**是非交互式的；交互式变基用 `git rebase -i` + `code --wait`，或使用 GitLens 的 Pro 编辑器
- **VSCode 1.97+ 已内置 Git Blame**（行内装饰默认关闭、状态栏默认开启）；GitLens 提供更丰富的 blame、CodeLens 和历史视图
- **Stash、Cherry-pick、Revert** 都有内置入口；全量 revert 和历史改写仍建议用命令行确认
- **多仓库**通过 Repositories 视图、`scm.repositories.selectionMode` 和仓库探测设置管理
- 一条 Feature 分支的完整流程可以在 VSCode 内完成，但冲突后的 `rebase --continue`、评审合并等步骤仍可能需要终端或浏览器
