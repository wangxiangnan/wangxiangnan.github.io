# 第6章：架构师的工具箱——ADR、文档与评审

> [!TIP] Part 1: 从零认识软件架构（基础概念篇）
> 在画第一张架构图之前，先把"内功"练好。这六章帮你建立软件架构的完整概念框架。最后一章讲"落地"：决策怎么记录、文档怎么写、评审怎么开、风险怎么提前排掉。

前面五章讲了概念、目标、视图、原则和风格。这一章解决一个更现实的问题：**这些认知如何沉淀下来、传递出去、被团队长期使用？**答案是四个工具：ADR 记决策，轻量文档传认知，评审守质量，走线骨架排风险。外加一份沟通指南——架构师的一半工作在对话里完成。

## 6.1 ADR：一页纸记住"为什么"

架构决策记录（Architecture Decision Record, ADR）由 Michael Nygard 在 2011 年提出，是工具箱里性价比最高的一件：**用一个短文档，记录一次重要的架构决策及其理由**。

为什么需要它？两年后新同事看着代码库问："我们为什么用 RocketMQ 不用 Kafka？"没有 ADR，答案是三选一：没人记得；拍脑袋编一个；把当年的架构师从退休生活里挖出来。有了 ADR，答案是翻开 ADR-007。再往后推演：三年后要重构消息队列时，ADR 里记录的备选方案能让你直接从上次思考的断点继续，而不是从零吵一遍。

ADR 的模板只要六个字段：

| 字段 | 回答的问题 | 典型篇幅 |
| ---- | ---------- | -------- |
| 标题 | 编号加一句话结论 | 1 行 |
| 状态 | 提议 / 已接受 / 已废弃 / 被 ADR-xxx 取代 | 1 行 |
| 背景 | 当时面对什么问题、什么约束 | 3-5 行 |
| 决策 | 我们决定做什么（动词开头，可执行） | 2-3 行 |
| 备选方案 | 考虑过哪些、为什么放弃 | 每个方案 2-3 行 |
| 后果 | 好处、代价、需要跟进的事 | 3-5 行 |

模板虽小，填对不容易，四个要点：

- **背景写"被迫"**：写下当时的约束（人力、时间、存量系统），没有约束的决策不叫决策，叫许愿
- **备选方案至少两个**：只有一个方案可选时，说明你调研得还不够，而不是问题太简单
- **后果里必须有负面项**：只写好处的 ADR 是广告，评审时会被打回
- **一行一个决定**：决策字段里出现"同时"和"另外"，说明这该拆成两个 ADR

来看一份云书店的完整 ADR——注意它的长度：一页纸以内，十五分钟能写完：

```markdown
**ADR-007：大促下单链路引入消息队列做异步削峰**

**状态**：已接受（2025-04-12 架构评审会通过，取代 ADR-003 的同步扣库存方案）

**背景**：
云书店日订单 5 万，大促 0 点抢购下单峰值 500 QPS，为日常峰值的 10 倍。
当前下单链路同步扣减 MySQL 库存，行锁竞争导致连接池耗尽，上次大促核心
交易瘫痪 47 分钟。团队 20 人，运维能力有限，要求 3 个月内完成改造，
且不推翻阶段 1 的模块化单体结构。

**决策**：
1. 引入 RocketMQ（自建，3 副本）作为消息队列。
2. 下单主链路只做两件事：校验并保存订单（状态"待处理"），发布 OrderCreated 事件。
3. 库存模块异步消费事件完成扣减；失败进重试队列，3 次失败转人工对账。
4. 下单接口 P99 目标：从 900 毫秒降到 300 毫秒以内。

**备选方案**：
- 方案 A：升级数据库规格并优化索引。峰值扛不住，行锁是天花板，放弃。
- 方案 B：Redis 预扣库存加异步落库。性能更好，但引入预热、回补、超时回收
  三类新问题，当前人力维护不起，保留为 ADR-008 的候选。

**后果**：
- 正面：下单不再被库存拖垮；库存、积分、通知三个模块解耦，可独立演进。
- 负面：库存从强一致变为毫秒级最终一致，超卖风险由"预占 15 分钟"兜底；
  新增每日对账任务，差异超 10 单告警。
- 跟进：RocketMQ 运维手册与告警规则 2 周内补齐（负责人：阿珍）。
```

ADR 胜过百页架构文档的秘诀在于**小**：百页文档写一次没人读、半年就过期；一页 ADR 十五分钟能写，决策变了再补一条"被 ADR-015 取代"即可。它记录的是**不可从代码里读出的信息**——代码能告诉你系统怎么连，只有 ADR 能告诉你为什么这样连、当时放弃了什么。

ADR 的日常使用节奏很简单：

- **编号递增，只增不改**：决策变更时写新 ADR，并在旧 ADR 的状态里标注"被 ADR-xxx 取代"，历史永远可追溯
- **谁提议谁执笔**：写 ADR 是练习清晰思考的过程，写不清楚说明还没想清楚
- **评审会上过 ADR，而不是过 PPT**：云书店的架构评审会，材料就是 C4 图加候选 ADR，会开得又快又实
- **季度回顾**：每季度翻一遍 ADR 列表，把"已接受"但现实已经偏离的挑出来重新决策——这是架构治理的主要抓手

把这四条养成习惯，ADR 就从"一篇文档"变成团队的肌肉记忆。

> [!NOTE] 实践建议
> ADR 存在代码仓库里（如 docs/adr/ 目录），和代码一起评审、一起版本化。一条经验法则：凡是评审会上吵了超过二十分钟的决策，都值得一条 ADR。

## 6.2 架构文档：多薄才有人读

先立一条总纲：**为读者写，而不是为自己写**。你写给未来自己查的，是记录；你写给团队照着做的，才是文档。有了 ADR 还需要别的文档吗？需要，但原则变了：**架构文档要像旅行指南，而不是产品说明书**。旅行指南告诉你"三天怎么玩最值"，说明书教你"拧螺丝要对角线顺序"。没人读说明书，但旅行指南人人翻。

写之前先想清楚给谁看——不同读者的需求差出一个物种：

| 读者 | 他们要什么 | 写什么 | 篇幅上限 |
| ---- | ---------- | ------ | -------- |
| 新入职工程师 | 多快能上手改代码 | 1 页系统地图 + 关键约束清单 | 2 页 |
| 产品与业务 | 系统能不能支撑我的需求 | 能力清单 + 已知限制 | 1 页 |
| 评审专家 | 方案的风险与权衡 | C4 图 + ADR + 风险清单 | 10 页 |
| 未来的自己 | 当时为什么这么定 | ADR 与演进时间线 | 持续追加 |

四条写作原则，来自无数"文档烂尾楼"的教训：

1. **写决策，不写现状**。现状代码自己会说话（第 3 章的 C4 图也从代码生成），文档只写代码里读不出来的"为什么"。
2. **一图胜千言，但要分级**。用 C4 视图组织：新人看 L1，开发看 L2/L3，别混。
3. **设腐朽警报**。文档里的截图、版本号、机器规格都会过期，给每页文档标注"最后验证日期"，季度评审时刷新。
4. **最薄可用**。先写 1 页，读者追问再扩到 10 页；上来就写 100 页的文档，作者自己都不会读完第二遍。

对应的四个写作反模式，对号入座：

- 把代码粘贴进文档当"详细设计"——代码自己会说话，文档要说代码不会说的
- 用截图贴架构图——图过期了没人知道，文本图（Mermaid）至少能 diff
- 文档里写"详见 XX 群讨论"——群记录半年就找不到，等于没写
- 为评审临时赶工 50 页——评审人只会读前 5 页，第 6 页起全是无效劳动

云书店的架构 wiki 目录，是"薄文档"的一个可抄的样板：

```text
docs/
├── overview.md          ← 1 页：L1 图 + 一句话定位 + 外部依赖清单
├── containers.md        ← 2 页：L2 图 + 部署拓扑 + 容量现状
├── constraints.md       ← 1 页：八条模块依赖规则 + 编码红线
├── adr/                 ← ADR-001 到 ADR-023，每条一页
├── runbooks/            ← 大促预案、故障处置手册（运维维护）
└── radar.md             ← 技术雷达，季度更新

全站加起来不到 40 页，但新人入职、方案评审、事故复盘都找得到入口。
对比某些项目 300 页无人问津的"架构圣经"：薄就是渗透率，渗透率就是价值。
```

## 6.3 架构评审：流程与常见失败模式

评审的输入是"候选 ADR + C4 图 + 风险清单"，输出是"结论 + 行动项 + 归档"。两样东西都轻，但缺一不可。它的目的不是证明方案正确，而是**尽早找到最大的风险**。一场健康的评审，最有价值的问题永远是这三个：这个方案在什么条件下会失败？有没有更简单的方案被跳过了？半年后最可能被推翻的决策是哪条？

云书店的标准流程五步：

1. **提前 3 天发材料**：目标、约束、方案、备选、风险清单。没有风险清单的评审基本是走过场——自己都不敢列风险，怎么指望别人帮你找？
2. **预审**：拉 1-2 位资深同事花 30 分钟对齐，别让评审会变成大家第一次看方案。
3. **评审会 60 分钟**：前 20 分钟过背景与约束，中间 30 分钟集中攻风险点，最后 10 分钟拍板。先审"怎么切怎么连"，再审"用什么"。
4. **结论只有三种**：通过 / 有条件通过（带行动项）/ 不通过。没有"再研究研究"这种第四种结论——那等于没有结论。
5. **跟进**：行动项写明负责人和截止日期，跟踪到关闭；变更了的决策回写 ADR。

评审角色也要提前定好，避免现场抢话筒：

- **主持人**：控时间、控议题，确保"先切分后选型"的顺序不被带偏
- **提案人**：讲清楚问题与方案，回答质疑但不辩解到失态
- **评审人**：至少两人，会前已读完材料并提交书面意见
- **记录员**：实时记录结论与行动项，散会前当场宣读确认

人手不够时可以一人多角，但主持人和提案人不要合并——又当裁判又当运动员，评审就名存实亡了。时间实在不够时的最简版评审：1 位评审人、1 小时、书面意见先行——比 6 个人开 2 小时会效率高得多。

评审翻车的姿势五花八门，常见的有六种：

| 失败模式 | 症状 | 解法 |
| -------- | ---- | ---- |
| PPT 架构 | 图很漂亮，代码完全是另一回事 | 评审带代码仓库，用走线骨架验证 |
| 一言堂 | 架构师说了算，其他人只点头 | 会前收书面意见，主持人控场 |
| 只审选型不审切分 | 吵了 40 分钟 MySQL 还是 PostgreSQL | 先审组件划分与依赖方向，再审选型 |
| 没有跟进 | 行动项散会即蒸发 | 行动项写负责人和截止日期，纳入周会 |
| 批斗会 | 提问变成对人的攻击 | 对事不对人：质疑决策，不质疑人 |
| 文档烂尾 | 评审后文档从此不再更新 | 评审通过即冻结版本，后续变更走 ADR |

对照打分：六个模式命中三个以上，说明评审流程需要先修再开——修复流程比修复某个具体方案更值钱。

最后一条文化建议：评审通过不是终点，而是"共同担保"的开始——所有评审人在 ADR 上署名，方案将来出问题一起复盘改进，而不是回头追责提案人。担保制让评审人真正认真，也让提案人不再孤军奋战。

## 6.4 原型验证与走线骨架：风险前置

**原型验证（Spike）**：用最便宜的代码回答最贵的疑问。规则很简单——给最大的架构风险点专门打一枪，时间盒 1 到 2 周，代码写完即弃（它只为回答问题而生）。云书店的真实例子：团队担心"百万册书的搜索要做到 P99 200 毫秒"有风险，于是花 3 天用 Elasticsearch 导入 10 万册书的数据原型，实测 P99 80 毫秒，方案放心立项。3 天的成本，买断了一个方向上所有的不确定。

选什么做原型验证？优先级排序：**先验证"会不会彻底失败"的，再验证"做得好不好"的**。第三方对接的认证方式、极端负载下的响应时间、冷门组件的稳定性，这些"可能一票否决整个方案"的点优先；纯性能调优类的疑问，通常放到走线骨架之后再压测也不迟。

Spike 和走线骨架是一对搭档：Spike 消灭单点的不确定，走线骨架消灭全局的集成风险——先 Spike 后骨架，是云书店新项目的标准开场。

**走线骨架（Walking Skeleton）**由 Alistair Cockburn 提出：先构建一个**打通全链路的最小系统**——功能最少，但所有架构上的关键环节全部贯通。对云书店，就是第一周只做这一条命脉：

```text
走线骨架：先把"一条命脉"全线打通，再长肉

 第一周只做这条链路（不含任何锦上添花的功能）：

  [Web 页面] ──下单──▶ [订单 API] ──预占──▶ [库存 API] ──发起──▶ [支付网关]
      ▲                                                            │
      └──────────────── 返回"下单成功" ◀──── 支付回调 ◀────────────┘

 链路全线贯通后，才逐个往骨架上"长肉"：
 优惠券、积分、书评、推荐、营销弹窗……全部走在已验证的轨道上
```

用时序视角再看一遍这条骨架链路：

```mermaid
graph LR
    W["Web 页面"] -->|"1 下单"| O["订单 API"]
    O -->|"2 预占库存"| I["库存 API"]
    I -->|"3 发起支付"| P["支付网关"]
    P -->|"4 支付回调"| O
    O -->|"5 返回成功"| W
```

走线骨架的价值在于**架构风险前置**：部署方式、跨模块调用、支付对接、回调处理——所有最容易出事的关键环节，在项目第一周就全部暴露和验证过了。等业务功能铺开时，工程师们不是在"探索未知"，而是在"往已验证的轨道上加车厢"。云书店把它定为铁律：任何新系统、新服务的第一个里程碑，都是走线骨架上线，而不是第一个完整功能。

配套一个反面教材：某团队把走线骨架理解成"先搭框架"——搭了一个月的通用脚手架、权限体系、日志平台，唯独没有一条真实业务链路通到底。第四周开始写订单功能时，才发现支付回调的签名校验方案和库存预占模型都有致命问题，骨架白搭。记住判据：**走线骨架的验收标准是"一个真实用户请求从入口走到出口"，而不是"框架代码就绪"**。骨架上可以什么功能都没有，但不能有任何一环是"以后再说"。

## 6.5 技术雷达：尝鲜也要有节奏

技术雷达（Technology Radar）源自 ThoughtWorks 的实践：把团队用到的所有技术放进四个同心圆环，一眼看清"什么该用、什么在试、什么该退"。它不是炫技清单，而是团队技术品味的公开声明：

| 环 | 含义 | 云书店当前（示例） |
| -- | ---- | ------------------ |
| 采用（Adopt） | 默认首选，绕开它才需要论证 | MySQL、Redis、Spring Boot、Kubernetes |
| 试验（Trial） | 已在非核心链路验证，扩大范围前慎用 | RocketMQ、OpenTelemetry |
| 评估（Assess） | 正在调研，不进生产 | 某新型向量数据库 |
| 暂缓（Hold） | 不建议新项目使用，存量逐步迁移 | 自研网关、某过气 ORM |

雷达的妙处在于把"该不该用新技术"从无数次重复讨论变成一次维护：新同事问"为什么不用 XX 框架"，答案是指向雷达——它在"评估"环，我们正在验证，验证通过会升入"试验"。对外统一口径，对内控制尝鲜节奏，顺便逼架构师每季度认真看看技术世界的变化。维护雷达只需要一个季度一次的例会，规则有三条：

- **移动要有依据**：一项技术升级环，必须附上试验报告——谁试的、试了什么场景、数据如何
- **一次最多移动两项**：防止"季度例会"变成集体追新的狂欢
- **Hold 不是死刑**：存量系统继续维护，只是新项目绕行；技术退场也讲究软着陆

雷达的格式不限，一张表格足矣，关键是每季度真的开这个会——连续错过两个季度，雷达就成了墙上的装饰画。

## 6.6 架构师的三种对话

第 1 章说过，架构师 35% 的时间在沟通。但跟产品经理、跟老板、跟开发说话，必须是三套完全不同的语言。对话能力的本质是翻译：把同一套架构认知，翻译成对方语言体系里的价值表达。三种对话的对象、语言、雷区各不相同，一张表先建立框架：

| 对话对象 | 他们关心什么 | 你应该说什么 | 你不该说什么 |
| -------- | ------------ | ------------ | ------------ |
| 产品经理 | 做不做、先做谁、什么时候好 | 把质量属性翻译成业务语言，给选项和代价 | 术语轰炸：熔断、限流、防腐层 |
| 老板 | 钱多少、风险多大、什么时候上线 | 风险、成本、里程碑，加一个明确建议 | 技术细节和实现路线 |
| 开发工程师 | 边界在哪、为什么这么定 | 明确的约束、接口、示例代码，解释 why | 模糊的"你看着办"，或越俎代庖 |

三段标准话术，感受一下差别：

**对产品**："秒杀有两种做法。A 方案两周上线，峰值超过 1 万单时会排队；B 方案六周，能稳扛 5 万单。如果秒杀是拉新手段，我建议先 A 后 B——用两周的数据再决定要不要投入六周。"（翻译成选项 + 代价 + 建议，把技术决策变成业务决策。）

**对老板**："大促方案已就绪：核心链路完成压测，配了降级预案。最坏情况是支付渠道方故障，自动切换预计影响 5 分钟以内。需要追加每月 3 万的备用通道预算，否则极端情况下损失可能上探到 50 万。"（风险量化，给选择题不给问答题。第 2 章那句"99.95% 等于全年最多停 4.4 小时"，就是这种翻译的最好例子。）

**对开发**："订单模块不许直接读库存表，只能调 InventoryGateway 接口。原因三个：表结构变更要可控、未来库存要独立部署、测试要能脱离数据库。示例代码在 docs/adr/007。如果这个约束挡住了你的需求，周四评审会上我们讨论调整约束本身，而不是绕过它。"（约束 + 理由 + 逃生通道。）

三个共同点：**说结论、给选项、解释为什么**。架构师的可信度就是在这一次次对话里攒出来的。最后附赠三句禁忌句式，说出来就把对话聊死了：

- 对产品说"这个做不了"——架构师不说做不了，说的是"能做到，代价是 X，你要吗"
- 对老板说"涉及技术细节你不用懂"——老板不懂细节但要担风险，你的职责是翻译风险
- 对开发说"就这么定了别问为什么"——没有 why 的约束会被绕过，有一次就够了

如果你只记得本章一件事，就记这句：**架构师的三种对话，本质都是把同一个事实翻译成对方的收益与风险**。翻译得准，方案就顺；翻译得差，再好的架构也会死于误解。

## 本章小结

- ADR 用一页纸记录决策与理由：背景、决策、备选方案、后果，十五分钟能写，两年后有人读
- ADR 记录的是代码里读不出的信息：为什么这样连、当时放弃了什么
- 架构文档要像旅行指南不像说明书：写决策不写现状、按读者分级、设腐朽警报、最薄可用
- 评审的目的是找最大风险，不是证明正确；结论只有三种：通过、有条件通过、不通过
- 评审六大失败模式：PPT 架构、一言堂、只审选型、没有跟进、批斗会、文档烂尾
- 原型验证用最便宜的代码回答最贵的疑问；走线骨架先打通全链路，再往已验证的轨道上长肉
- 技术雷达用四个环管理技术选型：采用、试验、评估、暂缓
- 三种对话三套语言：对产品给选项和代价，对老板给风险和建议，对开发给约束和理由
- 架构的可信度是攒出来的：说结论、给选项、解释为什么，一次都不能少
