# 第11章：流量控制与 TCP 进阶特性

## 流量控制 vs 拥塞控制：一个是保护接收方，一个是保护网络

这两个概念经常被混淆，但它们解决的问题完全不同：

| 对比维度 | 流量控制（Flow Control） | 拥塞控制（Congestion Control） |
| --------- | ---------------------- | -------------------------- |
| 保护对象 | 接收方 | 整个网络 |
| 触发信号 | 接收方缓冲区满了 | 网络丢包或延迟增加 |
| 控制机制 | 接收窗口（rwnd） | 拥塞窗口（cwnd） |
| 反馈来源 | 接收方（TCP 报头中的窗口字段） | 发送方自行检测（丢包、RTT） |
| 影响范围 | 仅当前连接 | 所有经过同一路径的连接 |

打个比方：流量控制像是餐厅服务员根据你吃饭的速度调节上菜速度——你吃太慢，菜就堆在桌上了。拥塞控制像是高速公路的匝道信号灯——车太多时就限制进入高速的车辆数。

## 接收窗口（rwnd）：接收方说"我还能收多少"

TCP 报头中的 **窗口大小（Window Size）** 字段就是 rwnd。接收方在每次发送 ACK 时，告知发送方"我当前还有多少缓冲区空间可以接收数据"。

```
接收方缓冲区状态：

已交付给应用  |  已收到未交付  |  空闲缓冲区
<----------->|<----------->|<------------------>
     0           2000          5000              65535

rwnd = 空闲缓冲区 = 65535 - 5000 = 60535 字节
```

接收方在 ACK 中设置 `Window Size = 60535`，发送方据此调整发送速率。当应用程序从缓冲区中读取数据后，空闲空间增加，rwnd 增大，发送方可以继续发送。

## 零窗口探测（Zero Window Probe）

当接收方的应用程序处理数据很慢时，缓冲区会被填满，接收方不得不发送 **零窗口（Zero Window）** 通知：`Window Size = 0`。

发送方收到零窗口通知后，暂停发送。但问题来了：当接收方腾出空间后，怎么通知发送方继续发送？如果这个"窗口更新"报文丢了，发送方就永远停在那里了。

**零窗口探测** 解决了这个问题：当发送方收到零窗口通知后，它会周期性地发送一个 **探测报文**（只包含 1 字节数据），强制接收方回复 ACK 并在 ACK 中声明当前的窗口大小。探测间隔从约 1 秒开始，逐渐增长到约 60 秒。

## Nagle 算法与 TCP_NODELAY：实时性 vs 效率的权衡

**Nagle 算法** 由 John Nagle 在 1984 年提出，旨在解决 **小包问题（Small Packet Problem）**。

问题是这样的：如果你每次按键都发送一个 TCP 报文，比如你在 SSH 中打字，每个字符会产生一个 40 字节（20 字节 IP 头 + 20 字节 TCP 头）的报文来承载 1 字节的数据。带宽利用率只有 1/41 ≈ 2.4%！

Nagle 算法的规则很简单：

> 如果还有已发送但未确认的数据，就不要发送新的小包（小于 MSS 的包）。把新数据缓冲起来，等到之前的 ACK 到达后，把所有缓冲的数据合并成一个大包一起发送。

这在低速链路上很有效。但在现代高速网络中，Nagle 算法会带来 **不必要的延迟**。想象一个实时游戏：你发了一个位置更新（20 字节），Nagle 算法会等到前一个包的 ACK 回来才发送——这增加了 1 个 RTT 的延迟。

解决方案是设置 **TCP_NODELAY** 选项，禁用 Nagle 算法：

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
```

几乎所有需要低延迟的应用（游戏、实时交易、交互式终端）都应该设置 TCP_NODELAY。而批量数据传输（文件传输、数据库同步）则应该保持 Nagle 算法启用以提高效率。

注意：Nagle 算法还与另一个机制有著名的交互问题——**延迟确认（Delayed ACK）**。TCP 接收方并不总是立即回复 ACK，而是等待约 200ms，看是否有数据可以"捎带"确认。如果发送方启用了 Nagle 算法，而接收方使用了延迟确认，就可能出现死锁：发送方等待 ACK 才能发送新数据，接收方等待新数据才发送 ACK。设置 TCP_NODELAY 可以避免这个问题。

## TCP Keep-Alive：检测死连接

TCP 连接是"逻辑连接"——它只存在于两端的内存中，不依赖任何物理链路。这意味着如果一方突然崩溃（比如电脑断电、进程被 kill），另一方可能永远不知道连接已经死了。

这就是 **僵尸连接（Half-Open Connection）** 问题。TCP Keep-Alive 机制通过定期发送探测报文来检测这种情况：

1. 连接空闲超过 **keepalive_time**（默认 7200 秒 = 2 小时）后，发送一个探测报文（ACK，不携带数据，序号 = 上次发送序号 - 1）。
2. 如果对方正常，会回复 ACK。
3. 如果对方已死，不会回复。发送方再发送 **keepalive_probes**（默认 9 次），每次间隔 **keepalive_intvl**（默认 75 秒）。
4. 如果所有探测都无响应，连接被判定为死亡，应用程序收到错误通知。

```python
sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
sock.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)

# Linux 特有的精细控制
if hasattr(socket, 'TCP_KEEPIDLE'):
    sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPIDLE, 60)    # 60秒后开始探测
    sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPINTVL, 10)   # 探测间隔10秒
    sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_KEEPCNT, 5)      # 最多探测5次
```

2 小时的默认值太长了。在实际生产环境中，大多数应用（如 Web 服务器、数据库连接池）会将 Keep-Alive 调为 60-120 秒，以便更快地检测和清理死连接。

## 最大段大小（MSS）与窗口缩放（Window Scaling）

**MSS（Maximum Segment Size）** 是 TCP 每个段中数据载荷的最大长度（不含 TCP 报头）。MSS = MTU - IP 头 - TCP 头 = 1500 - 20 - 20 = **1460 字节**（以太网标准 MTU 为 1500 字节）。

MSS 在三次握手时通过 SYN 报文的选项字段协商：双方各自声明自己能接受的最大 MSS，取较小值。如果一方不声明，默认 MSS = 536 字节（这是为了确保即使经过多层封装也不会超出 IP 的最小重组缓冲区大小 576 字节）。

**窗口缩放（Window Scaling）** 解决了 TCP 报头中 16 位窗口大小字段的上限问题。16 位最大只能表示 65535 字节 ≈ 64KB，但对于现代高速网络来说这远远不够。

例如，一条 1Gbps 的链路、RTT=50ms，根据 **带宽-延迟积（BDP）** 公式：

```
BDP = 带宽 × RTT = 1Gbps × 50ms = 1000Mbps × 0.05s = 50Mb = 6.25MB
```

要充分利用这条链路，发送窗口需要达到 6.25MB，远超 64KB。窗口缩放通过一个 **缩放因子（Scale Factor）** 来解决这个问题：

```
实际窗口 = TCP 报头中的窗口值 × 2^(缩放因子)

如果缩放因子 = 7：
实际窗口 = 65535 × 2^7 = 65535 × 128 ≈ 8MB
```

缩放因子在三次握手时通过 SYN 选项协商，最大值为 14（即最大窗口 = 65535 × 2^14 ≈ 1GB）。

## TCP Fast Open：减少握手延迟

TCP 三次握手需要一个 RTT 才能完成，然后才能发送数据。对于短连接（如 HTTP 请求），这意味着总延迟中有一个 RTT 纯粹花在了握手上。

**TCP Fast Open（TFO）** 允许客户端在 SYN 报文中直接携带数据（通常是 HTTP 请求），从而省去一个 RTT。

工作原理：

1. 第一次连接：正常的三次握手，但服务器在 SYN+ACK 中返回一个 **Fast Open Cookie**。
2. 后续连接：客户端在 SYN 报文中携带 Cookie 和数据。服务器验证 Cookie 后，如果有效，立即开始处理数据（在三次握手完成之前！）。

```python
# Linux 上启用 TCP Fast Open
# 服务器端
sock.setsockopt(socket.SOL_TCP, socket.TCP_FASTOPEN, 5)  # 队列长度

# 客户端
# Linux 4.11+ 支持 socket.TCP_FASTOPEN_CONNECT
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_FASTOPEN_CONNECT, 1)
```

TCP Fast Open 可以将 HTTP 请求的延迟降低约 1 个 RTT。对于 RTT=100ms 的连接，这意味着 100ms 的性能提升——这在 Web 性能优化中是显著的。

## 编程实践：调优 TCP 参数并测量效果

```python
import socket
import time
import threading

def start_echo_server(port, buffer_size=65536):
    """启动 Echo 服务器"""
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind(('127.0.0.1', port))
    server.listen(1)

    conn, addr = server.accept()
    conn.setsockopt(socket.SOL_SOCKET, socket.SO_RCVBUF, buffer_size)

    total = 0
    while True:
        data = conn.recv(65536)
        if not data:
            break
        total += len(data)
        conn.sendall(data)

    conn.close()
    server.close()
    return total

def benchmark_client(port, data_size, nodelay=False, sndbuf=65536):
    """客户端性能测试"""
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF, sndbuf)

    if nodelay:
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

    sock.connect(('127.0.0.1', port))

    # 打印实际的缓冲区大小
    actual_sndbuf = sock.getsockopt(socket.SOL_SOCKET, socket.SO_SNDBUF)
    print(f"  实际发送缓冲区: {actual_sndbuf} 字节")

    chunk = b'x' * 4096  # 4KB 块
    sent = 0
    start = time.perf_counter()

    while sent < data_size:
        to_send = min(len(chunk), data_size - sent)
        sock.sendall(chunk[:to_send])
        # 读取回复（echo）
        received = 0
        while received < to_send:
            data = sock.recv(65536)
            if not data:
                break
            received += len(data)
        sent += to_send

    elapsed = time.perf_counter() - start
    throughput = (data_size / 1024 / 1024) / elapsed  # MB/s
    sock.close()
    return elapsed, throughput

def run_benchmark():
    data_size = 50 * 1024 * 1024  # 50MB

    configs = [
        {"name": "默认配置", "nodelay": False, "sndbuf": 65536, "rcvbuf": 65536},
        {"name": "TCP_NODELAY=1", "nodelay": True, "sndbuf": 65536, "rcvbuf": 65536},
        {"name": "大缓冲区(1MB)", "nodelay": False, "sndbuf": 1048576, "rcvbuf": 1048576},
        {"name": "NODELAY+大缓冲区", "nodelay": True, "sndbuf": 1048576, "rcvbuf": 1048576},
    ]

    for i, cfg in enumerate(configs):
        port = 9100 + i
        # 启动服务器（在后台线程中）
        server_thread = threading.Thread(
            target=start_echo_server, args=(port, cfg["rcvbuf"]))
        server_thread.daemon = True
        server_thread.start()
        time.sleep(0.2)  # 等待服务器启动

        print(f"\n{'='*50}")
        print(f"测试配置: {cfg['name']}")
        print(f"  TCP_NODELAY={cfg['nodelay']}, "
              f"SO_SNDBUF={cfg['sndbuf']}, SO_RCVBUF={cfg['rcvbuf']}")

        elapsed, throughput = benchmark_client(
            port, data_size, nodelay=cfg["nodelay"], sndbuf=cfg["sndbuf"])

        print(f"  传输 {data_size/1024/1024:.0f}MB 耗时: {elapsed:.3f} 秒")
        print(f"  吞吐量: {throughput:.1f} MB/s")

if __name__ == '__main__':
    run_benchmark()
```

在本地回环接口上，由于 RTT 极低（< 0.1ms），不同配置的差异可能不大。但如果你在两台机器之间测试（RTT > 1ms），你会明显看到：

- **TCP_NODELAY** 在小包密集传输时显著提升延迟表现，但对大块数据传输影响不大。
- **大缓冲区** 在高 BDP 链路（高带宽、高延迟）上显著提升吞吐量，因为更大的窗口允许更多数据"在途"。
- 注意：Linux 会将你设置的 SO_SNDBUF 值翻倍（内核会额外分配空间用于簿记），所以 `getsockopt` 返回的值通常是你设置的 2 倍。

## 抓包实践：观察 Nagle 算法的效果和 TCP_NODELAY 的差异

编写两个简单的测试程序，一个启用 Nagle 算法，一个禁用：

```python
# test_nagle.py
import socket
import time

def test_with_nagle(nodelay: bool):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    if nodelay:
        sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)

    sock.connect(('127.0.0.1', 80))

    # 连续发送 5 个小包（每个 10 字节）
    for i in range(5):
        sock.send(f"PKT{i:02d}DATA".encode())
        time.sleep(0.01)  # 模拟应用层的间隔

    time.sleep(1)
    sock.close()

# 分别测试
test_with_nagle(False)  # Nagle 启用
test_with_nagle(True)   # Nagle 禁用（TCP_NODELAY）
```

在 tcpdump 中捕获：

```bash
sudo tcpdump -i lo port 80 -nn -S -tttt
```

**Nagle 启用时的抓包：**

```
10:00:00.001  127.0.0.1.54321 > 127.0.0.1.80: Flags [P.], seq 1:11, length 10 "PKT00DATA"
10:00:00.010  127.0.0.1.54321 > 127.0.0.1.80: Flags [P.], seq 11:21, length 10 "PKT01DATA"
10:00:00.012  127.0.0.1.54321 > 127.0.0.1.80: Flags [P.], seq 21:41, length 20 "PKT02DATAPKT03DATA"
10:00:00.022  127.0.0.1.54321 > 127.0.0.1.80: Flags [P.], seq 41:51, length 10 "PKT04DATA"
```

注意第 3 个报文：`PKT02DATA` 和 `PKT03DATA` 被 **合并** 成了一个 20 字节的报文。这就是 Nagle 算法的效果——它在等待 ACK 的过程中缓冲了后续的小包，然后一次性发送。

**TCP_NODELAY 启用时的抓包：**

```
10:00:01.001  127.0.0.1.54322 > 127.0.0.1.80: Flags [P.], seq 1:11, length 10 "PKT00DATA"
10:00:01.010  127.0.0.1.54322 > 127.0.0.1.80: Flags [P.], seq 11:21, length 10 "PKT01DATA"
10:00:01.020  127.0.0.1.54322 > 127.0.0.1.80: Flags [P.], seq 21:31, length 10 "PKT02DATA"
10:00:01.030  127.0.0.1.54322 > 127.0.0.1.80: Flags [P.], seq 31:41, length 10 "PKT03DATA"
10:00:01.040  127.0.0.1.54322 > 127.0.0.1.80: Flags [P.], seq 41:51, length 10 "PKT04DATA"
```

每个包都是独立的 10 字节，没有任何合并。每个 `send()` 调用立刻产生一个 TCP 报文。

在本地回环上差异不明显（RTT 太小），但在跨网络测试中，Nagle 的延迟缓冲效果会更加显著。
