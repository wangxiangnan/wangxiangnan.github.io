# 第8章：TCP 基础——建立连接与可靠传输

## TCP 的设计目标：在不可靠的网络上提供可靠传输

IP 层是一个"尽力而为"（best-effort）的服务：它不保证数据包能送达，不保证按顺序到达，不保证数据不被篡改。在这种不可靠的基础上，TCP 要提供 **完全可靠** 的字节流服务。

这就像邮政系统告诉你"我可能会丢信、可能把信送错、可能把信件顺序搞乱"，而 TCP 要在这种邮政系统之上构建一个"绝对不丢、绝对不错、绝对有序"的通信管道。

TCP 的核心设计目标可以概括为四点：

1. **可靠传输**：发送方发出的每一个字节，接收方都能正确收到。如果丢失，自动重传。
2. **有序交付**：接收方看到的数据顺序与发送方发送的顺序完全一致。
3. **完整性校验**：通过校验和检测数据损坏，丢弃损坏的数据并触发重传。
4. **流量控制与拥塞控制**：不让发送方淹没接收方，也不让发送方压垮网络。

为了实现这些目标，TCP 引入了一系列机制：连接管理、序号、确认、重传、滑动窗口、拥塞控制。这些机制将在接下来的几章中逐一展开。

## 三次握手：为什么是三次不是两次？为什么不是四次？

TCP 是面向连接的协议。在传输数据之前，双方必须先建立一个"连接"。这个连接的建立过程就是著名的 **三次握手（Three-Way Handshake）**。

```
客户端                         服务器
  |                              |
  |---- SYN (seq=x) ----------->|   第一次：客户端说"我想连接"
  |                              |
  |<--- SYN+ACK (seq=y,ack=x+1)-|   第二次：服务器说"好的，我也想连"
  |                              |
  |---- ACK (seq=x+1,ack=y+1)->|   第三次：客户端说"确认，连上了"
  |                              |
  |==== 连接已建立，开始传输 ====|
```

**SYN（Synchronize）** 和 **ACK（Acknowledge）** 是 TCP 报头中的两个标志位（Flag）。SYN=1 表示这是一个连接请求/响应，ACK=1 表示确认号字段有效。

现在回答一个经典面试题：**为什么是三次，不是两次？**

假设只有两次握手：

```
客户端                         服务器
  |---- SYN (seq=x) ----------->|
  |<--- SYN+ACK (seq=y,ack=x+1)-|
  |==== 服务器认为连接已建立 ====|
```

问题出在哪里？服务器在发送 SYN+ACK 后就认为连接已建立，开始为这个连接分配资源（缓冲区、定时器等）。但如果客户端的 SYN 是一个 **滞留的旧报文**（Delayed Duplicate）——比如客户端之前发起过一次连接，那个 SYN 在网络中迷路了，现在才到达服务器——服务器会以为这是一次新的连接请求，分配资源并等待数据。而客户端根本不知道这个连接的存在，不会发送任何数据。结果：服务器白白浪费资源。

三次握手解决了这个问题：客户端收到 SYN+ACK 后，会检查这个 SYN+ACK 是否对应自己当前正在发起的连接。如果是一个"意外"的 SYN+ACK（对应一个旧的、已经放弃的连接请求），客户端会回复 RST（Reset），服务器收到 RST 后释放资源。关键在于：**服务器在收到第三次握手的 ACK 之前，不会进入完全的连接建立状态。**

**那为什么不是四次？** 奥卡姆剃刀原则——三次已经足够在双方之间同步两个关键信息：客户端的初始序号（ISN）和服务器的初始序号（ISN）。三次报文交换刚好够双方各发一次 SYN 并各收一次 ACK。多一次纯属浪费。

## TCP 报头详解：序号、确认号、窗口大小、标志位

TCP 的报头比 UDP 复杂得多，最小长度为 **20 字节**（不含选项字段），最大可达 60 字节：

```
 0      7 8     15 16    23 24    31
+--------+--------+--------+--------+
|     源端口号     |    目的端口号    |
+--------+--------+--------+--------+
|             序号(Seq)             |
+--------+--------+--------+--------+
|           确认号(Ack)             |
+--------+--------+--------+--------+
|数据偏移| 保留 |U A P R S F|  窗口大小 |
| (4bit) |(4bit)|R C S S Y I| (16bit) |
|        |      |G K H T N N|         |
+--------+--------+--------+--------+
|         校验和      |   紧急指针    |
+--------+--------+--------+--------+
|              选项(可变长)          |
+--------+--------+--------+--------+
```

关键字段详解：

- **序号（Sequence Number，32 位）**：本报文段中第一个数据字节的序号。假设你发送了 1000 字节的数据，起始序号为 5000，那么这 1000 字节的序号范围是 5000~5999。连接建立时，序号从一个随机选择的 **ISN（Initial Sequence Number）** 开始。为什么随机？安全考虑——如果序号可预测，攻击者可以伪造数据包劫持连接（TCP 序列号预测攻击）。

- **确认号（Acknowledgment Number，32 位）**：期望收到的下一个字节的序号。如果确认号是 6000，表示"我已经完整收到了序号 5999 及之前的所有数据，我期望下一个收到的是序号 6000"。这就是 **累积确认** 的核心。

- **数据偏移（Data Offset，4 位）**：TCP 报头的长度，以 4 字节为单位。最小值为 5（即 20 字节），最大值为 15（即 60 字节）。之所以叫"数据偏移"，是因为它同时也指示了数据载荷从第几个字节开始。

- **标志位（Flags，6 位）**：
  - **URG**：紧急指针有效。本报文中有紧急数据，接收方应优先处理。
  - **ACK**：确认号字段有效。除了最初的 SYN 报文外，所有 TCP 报文都应该设置此位。
  - **PSH**：推送标志。告诉接收方"不要缓冲，立即把数据交给应用程序"。
  - **RST**：重置连接。表示发生了严重错误，需要立即终止连接。
  - **SYN**：同步序号，用于建立连接。
  - **FIN**：发送方已完成数据发送，请求关闭连接。

- **窗口大小（Window Size，16 位）**：接收方当前还能接收多少字节的数据（即接收窗口 rwnd）。这是 TCP 流量控制的核心机制。最大值为 65535 字节——对于高速网络来说太小了，所以后面引入了 **窗口缩放选项（Window Scaling）**。

- **校验和（Checksum，16 位）**：强制字段，覆盖 TCP 报头、数据以及 IP 伪首部。

- **紧急指针（Urgent Pointer，16 位）**：配合 URG 标志使用，指出本报文中紧急数据的末尾位置。实际应用中很少使用（Telnet 是少数使用它的协议之一）。

## 序号与确认号：滑动窗口的基石

序号和确认号是 TCP 可靠传输的基石。理解它们的关键在于认识到：**TCP 是面向字节的协议，不是面向报文的。**

这意味着什么？假设应用程序分三次调用 `send()`：

```python
sock.send(b"Hello")       # 5 字节
sock.send(b" World")      # 6 字节
sock.send(b"!")           # 1 字节
```

TCP 并不关心你调了几次 `send()`。在 TCP 看来，这就是一个连续的字节流：`H-e-l-l-o- -W-o-r-l-d-!`，共 12 字节。如果当前序号是 1000，那么：

- `H` 的序号是 1000
- `e` 的序号是 1001
- `!` 的序号是 1011

接收方可能一次性收到全部 12 字节，也可能分两次收到（比如先收到 8 字节，再收到 4 字节）。TCP 负责把这些数据重新组装成原始的字节流，交给应用程序。

确认号的累积性质意味着：如果接收方发送 ACK=1008，它表示序号 1000~1007 的 8 个字节都已正确收到。即使中间有乱序到达的报文（比如序号 1010 的报文先到，序号 1008 的后到），TCP 也会缓存乱序数据，但确认号只会推进到"连续已收到的最后一个字节的下一个"。

## 数据传输的完整过程：从 SYN 到 FIN

一次完整的 TCP 连接生命周期包含三个阶段：

**阶段一：连接建立（三次握手）**

```
Client (ISN=1000)              Server (ISN=5000)
      |                              |
      |--- SYN, seq=1000 ----------->|
      |                              |
      |<-- SYN+ACK, seq=5000,        |
      |          ack=1001 -----------|
      |                              |
      |--- ACK, seq=1001,           |
      |        ack=5001 ------------>|
```

握手完成后，双方的状态：

- 客户端：下一个要发送的字节序号是 1001，期望收到的下一个字节序号是 5001
- 服务器：下一个要发送的字节序号是 5001，期望收到的下一个字节序号是 1001

注意：SYN 报文本身"消耗"了一个序号（虽然没有携带应用数据），所以 SYN 之后的序号加 1。

**阶段二：数据传输**

```
Client                        Server
  |                               |
  |--- PSH+ACK, seq=1001,        |
  |    ack=5001, data="Hello" -->|   客户端发送 5 字节
  |                               |
  |<-- ACK, seq=5001,            |   服务器确认收到
  |    ack=1006 -----------------|
  |                               |
  |<-- PSH+ACK, seq=5001,        |
  |    ack=1006, data="World" ---|   服务器发送 5 字节
  |                               |
  |--- ACK, seq=1006,            |   客户端确认收到
  |    ack=5006 ---------------->|
```

每一方在发送数据时捎带（piggyback）对另一方数据的确认，这是 TCP 的高效之处——不需要单独的 ACK 报文。

**阶段三：连接关闭（四次挥手）**

## 四次挥手：为什么断开比建立多一次？TIME_WAIT 的意义

TCP 连接的关闭不是简单的"一方说再见，另一方说拜拜"。因为 TCP 是 **全双工** 的——数据可以同时双向流动，所以每个方向必须独立关闭。

```
Client                         Server
  |                              |
  |--- FIN, seq=1006,           |   第一次：客户端说"我发完了"
  |    ack=5006 --------------->|
  |                              |
  |<-- ACK, seq=5006,           |   第二次：服务器说"收到你的FIN"
  |    ack=1007 ---------------|
  |                              |
  |    (服务器可能还在发送剩余数据)   |
  |                              |
  |<-- FIN, seq=5200,           |   第三次：服务器说"我也发完了"
  |    ack=1007 ---------------|
  |                              |
  |--- ACK, seq=1007,           |   第四次：客户端说"收到你的FIN"
  |    ack=5201 -------------->|
  |                              |
  |    [TIME_WAIT: 2*MSL]       |   客户端进入 TIME_WAIT 状态
```

**为什么是四次而不是三次？** 因为关闭连接时，收到 FIN 的一方可能还有数据要发送。当客户端发送 FIN 时，服务器收到后先回复 ACK，但服务器可能还没发完自己的数据。等服务器把所有数据发完后，才发送自己的 FIN。这就把建立连接时可以合并的 SYN+ACK 拆分成了独立的 ACK 和 FIN，多了一次。

**TIME_WAIT 的意义：** 注意最后一步——发送最后一个 ACK 的一方（本例中是客户端）会进入 **TIME_WAIT** 状态，持续 **2×MSL（Maximum Segment Lifetime，通常为 2 分钟，即共 4 分钟）**。这不是浪费，而是出于两个重要原因：

1. **确保最后的 ACK 能到达对方**：如果这个 ACK 丢失了，服务器会重发 FIN。处于 TIME_WAIT 状态的客户端可以再次回复 ACK。如果没有 TIME_WAIT，客户端已经关闭了连接，收到重发的 FIN 后会回复 RST，服务器会认为连接异常终止。

2. **防止旧连接的报文干扰新连接**：如果一对 IP+端口立刻建立新连接，旧连接中滞留的报文可能会混入新连接。等待 2×MSL 可以确保旧连接的所有报文都在网络中消亡。

TIME_WAIT 是高并发服务器的一个常见痛点。如果一个 Web 服务器每秒关闭大量连接，TIME_WAIT 状态的连接会累积，占用端口资源。常见的调优方法包括减小 MSL 值、启用 `tcp_tw_reuse` 等。

## 编程实践：用 Python socket 写 TCP 服务器，处理粘包问题

TCP 是字节流协议，这意味着 **数据没有边界**。你分两次 `send()` 发送的数据，接收方可能在一次 `recv()` 中全部收到——这就是所谓的 **粘包问题**。

```python
import socket
import struct

HOST = '127.0.0.1'
PORT = 8888

def handle_client(conn, addr):
    """处理单个客户端连接"""
    print(f"新连接来自: {addr}")
    buffer = b""  # 接收缓冲区

    while True:
        data = conn.recv(4096)
        if not data:
            break  # 客户端关闭连接

        buffer += data

        # 使用长度前缀协议解包：每个消息 = 4字节长度(网络字节序) + 数据
        while len(buffer) >= 4:
            # 读取消息长度（前4字节）
            msg_len = struct.unpack('!I', buffer[:4])[0]

            # 检查是否收到了完整的消息
            if len(buffer) < 4 + msg_len:
                break  # 数据不完整，等待更多数据

            # 提取完整消息
            msg = buffer[4:4 + msg_len]
            buffer = buffer[4 + msg_len:]  # 移除已处理的数据

            print(f"收到完整消息 ({msg_len} 字节): {msg.decode('utf-8')}")

            # 回复
            reply = f"已收到: {msg.decode('utf-8')}".encode('utf-8')
            reply = struct.pack('!I', len(reply)) + reply
            conn.sendall(reply)

    conn.close()
    print(f"连接关闭: {addr}")

def main():
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    # 允许地址复用，避免 TIME_WAIT 导致的重启失败
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((HOST, PORT))
    server.listen(5)
    print(f"TCP 服务器监听 {HOST}:{PORT}")

    while True:
        conn, addr = server.accept()
        handle_client(conn, addr)

if __name__ == '__main__':
    main()
```

**粘包问题的本质**：TCP 把应用数据看作一条连续的字节河流，而应用层的消息是河流中的一段段水。如果你不在水段之间做标记，下游就不知道哪里是一段水的开始和结束。

**解决方案：长度前缀协议**。在每个消息前面加上一个固定长度的字段（这里是 4 字节的无符号整数），表示后面消息体的长度。接收方先读取 4 字节得到长度 N，再读取 N 字节得到一个完整消息。HTTP/2、gRPC、Redis 的 RESP 协议等都使用了类似的方法。

## 抓包实践：完整追踪一次 TCP 连接的建立、数据传输和关闭

用 `tcpdump` 或 Wireshark 追踪一次完整的 HTTP 请求：

```bash
# 捕获与某 Web 服务器的通信
sudo tcpdump -i any host 93.184.216.34 and port 80 -nn -S
```

然后用 `curl` 发起请求：

```bash
curl http://93.184.216.34/
```

抓包结果（已精简，重点标注）：

```

  Flags [F.], seq 2145891262, ack 3271845079, win 512
```

- 三次握手在不到 50ms 内完成（从 0.001 到 0.046 秒，其中 44ms 是网络往返延迟）。
- 客户端在发送 ACK 的 **同一个毫秒** 内就发送了 HTTP 请求——这就是 TCP 的"延迟确认+数据捎带"优化。
- 四次挥手中，服务器把 ACK 和 FIN 合并成了一个报文（Flags [F.]），所以实际只用了三次报文——因为服务器收到 FIN 时没有更多数据要发送。
