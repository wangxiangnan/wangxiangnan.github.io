# 第19章：HTTP/2——HTTP 的大修

Part IV：前沿与实战——现代协议与网络编程

## 为什么 HTTP/1.1 需要一场大修？

想象你去一家餐厅吃饭。HTTP/1.1 就像那种只有一条传菜通道的餐厅：第一道菜没送完，后面的菜全堵在厨房里。你明明点了五个菜，却只能一个接一个地等。这就是 **队头阻塞（Head-of-Line Blocking）**——前一个请求没响应完，后面的请求只能干等。

HTTP/1.1 时代为了绕过这个限制，浏览器通常对同一个域名开 6-8 个 TCP 连接（这就是你抓包时看到一堆并发连接的原因）。但这带来了新问题：每个 TCP 连接都要三次握手、TLS 握手、维护独立的拥塞窗口——连接越多，开销越大。

除了队头阻塞，HTTP/1.1 还有一个令人头疼的问题：**头部冗余**。每次请求都要带上 Cookie、User-Agent、Accept 等一堆头部，很多时候这些值在同一个会话中完全一样。一个典型的网页可能加载 100 个资源，每次都重复发送 500 字节的头部，白白浪费 50KB 的带宽。

## HTTP/2 的三大改进

HTTP/2（基于 Google 的 SPDY 实验协议）对 HTTP/1.1 做了一次深度重构，核心改进有三个：

**1. 二进制分帧（Binary Framing）**

HTTP/1.1 是纯文本协议，解析起来很麻烦——你得逐行读取、处理各种边界情况。HTTP/2 将所有通信拆分成小型的**二进制帧（Frame）**，每个帧有固定的 9 字节帧头：

```
+-----------------------------------------------+
|                 Length (24)                     |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |               |
+-+-------------+---------------+               |
|R|              Stream ID (31)                 |
+-+---------------------------------------------+
|                 Frame Payload                 |
+-----------------------------------------------+
```

其中 `R` 是保留位，`Stream ID` 标识这个帧属于哪个流。帧类型包括 DATA（0x0）、HEADERS（0x1）、SETTINGS（0x4）、PING（0x6）等。二进制格式让解析变得确定性的快，不再有文本解析的歧义。

**2. 多路复用（Multiplexing）**

这是 HTTP/2 最核心的改进。在同一个 TCP 连接上，可以同时传输多个**流（Stream）**，每个流对应一个请求-响应对。帧通过 Stream ID 区分归属，接收方可以乱序接收帧，然后按 Stream ID 重新组装。

打个比方：HTTP/1.1 是一条单行道，车只能一辆一辆走；HTTP/2 把这条路变成了多车道高速公路，每条车道（流）的车互不影响。

**3. 头部压缩（HPACK）**

HTTP/2 使用 HPACK 算法压缩头部。它维护一个**动态字典**，记录已经发送过的头部键值对。后续请求只需发送字典索引而非完整值。比如第一次发送 `:method: GET`，第二次只需发送索引号 `2`，一个字节搞定。

## 帧、流、连接的关系

```
一个 TCP 连接（Connection）
├── Stream 1（请求 /index.html）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
├── Stream 3（请求 /style.css）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
├── Stream 5（请求 /app.js）
│   ├── HEADERS 帧
│   └── DATA 帧 × N
└── Stream 0（控制流：SETTINGS、PING 等）
```

客户端发起的流用奇数 ID（1, 3, 5...），服务端发起的用偶数 ID（2, 4, 6...）。Stream 0 是控制流，用于传输连接级别的帧（如 SETTINGS、WINDOW_UPDATE）。

## 流的优先级与依赖

HTTP/2 允许客户端声明流的优先级。通过 PRIORITY 帧，客户端可以告诉服务器"Stream 5 依赖 Stream 1，权重为 16"。服务器据此分配带宽，优先发送关键资源（如 HTML 和 CSS），推迟次要资源（如图片）。

不过在实践中，很多服务器并未很好地实现优先级调度，这也是 HTTP/2 的一个遗憾。

## Server Push：服务器主动推送资源

当服务器知道客户端请求 `/index.html` 后大概率还会请求 `/style.css`，它可以主动推送 CSS 而不必等客户端解析 HTML 后再发起请求。服务器发送一个 PUSH_PROMISE 帧，告诉客户端"我要推送这个资源了"，然后直接发送对应的 HEADERS 和 DATA 帧。

```python
# Server Push 的概念示意
# 客户端请求 index.html
# 服务器响应:
#   1. PUSH_PROMISE: "我要推 /style.css 了" (Stream 1 上)
#   2. HEADERS + DATA: /index.html 的内容 (Stream 1 上)
#   3. HEADERS + DATA: /style.css 的内容 (Stream 2 上，服务器主动发起)
```

但 Server Push 在实践中效果不佳——服务器并不真正知道客户端缓存里有什么，经常推送客户端已经缓存的资源。Chrome 在 2020 年已经移除了对 Server Push 的支持。

## HTTP/2 解决了什么，没解决什么

**解决了：**

- 应用层的队头阻塞（多路复用）
- 头部冗余（HPACK 压缩）
- 连接开销（一个连接跑所有请求）

**没解决：**

- **TCP 层的队头阻塞**。HTTP/2 的多个流共享同一个 TCP 连接。如果 TCP 层丢了某个包，TCP 的可靠传输机制会阻塞整个连接——所有流都得等那个丢失的包重传完成。这就是 HTTP/2 的阿喀琉斯之踵，也是后来 QUIC 和 HTTP/3 要解决的核心问题。

## 编程实践：对比 HTTP/1.1 和 HTTP/2 性能

```python
"""
对比 HTTP/1.1 和 HTTP/2 的并发请求性能
需要安装: pip install httpx[http2]
"""
import httpx
import asyncio
import time

URLS = [f"https://httpbin.org/delay/1" for _ in range(10)]

async def benchmark(http2: bool):
    async with httpx.AsyncClient(http2=http2) as client:
        start = time.perf_counter()
        tasks = [client.get(url) for url in URLS]
        responses = await asyncio.gather(*tasks)
        elapsed = time.perf_counter() - start
        version = "HTTP/2" if http2 else "HTTP/1.1"
        print(f"{version}: {len(responses)} 请求, 耗时 {elapsed:.2f}s")
        return elapsed

async def main():
    t1 = await benchmark(http2=False)
    t2 = await benchmark(http2=True)
    print(f"\nHTTP/2 比 HTTP/1.1 快了 {t1/t2:.1f} 倍")

asyncio.run(main())
```

预期结果：HTTP/1.1 大约需要 10 秒（串行），HTTP/2 大约 1-2 秒（并行多路复用）。差距非常明显。

## 抓包实践：观察 HTTP/2 多路复用

在 Wireshark 中过滤 `http2`，你会看到：

1. 连接建立后，客户端发送 SETTINGS 帧（`Settings - ACK` 标志位为 0），告知服务器自己的参数（如 `MAX_CONCURRENT_STREAMS=100`）。
2. 服务器回复 SETTINGS + ACK。
3. 客户端在 Stream 1、3、5 上几乎同时发出 HEADERS 帧。
4. 服务器的响应帧交错到达——可能先收到 Stream 3 的 DATA，再收到 Stream 1 的 DATA。这就是多路复用的直观体现。
5. 观察帧头中的 `Stream Identifier` 字段，你能清楚看到每个帧属于哪个流。

使用 `tshark` 命令行也能快速分析：

```bash
tshark -r capture.pcap -Y "http2" -T fields -e frame.number -e http2.type -e http2.stream.id
```
