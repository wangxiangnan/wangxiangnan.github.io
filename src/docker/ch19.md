# 第19章：K8s部署实战

## 引言：从"能跑就行"到"企业级部署"

上一章我们学会了 K8s 的基础——能把应用"跑起来"了。但这就像你写了一个 `Hello World` 级别的 CRUD 应用——能跑，但离生产级别还差十万八千里。

本章我们要解决的问题是：

- 怎么做到**零停机更新**？（用户正用着呢，你不能把服务停了再部署）
- 怎么让外部用户访问集群内的服务？（ClusterIP 只在集群内生效）
- 怎么做**持久化存储**？（Pod 重启后数据不能丢了）
- 怎么处理**定时任务**？（`cron` 表达式在 K8s 里怎么用？）
- 怎么部署一个**完整的微服务架构**？

如果说上一章是"学会了开车"，这一章就是"上了高速公路"。

## 19.1 Deployment 深入

### 副本与滚动更新

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nodejs-app
spec:
  replicas: 3               # 始终保持 3 个 Pod 副本
  strategy:
    type: RollingUpdate      # 滚动更新策略（默认）
    rollingUpdate:
      maxSurge: 1            # 更新时最多多出 1 个 Pod（可以是数字或百分比）
      maxUnavailable: 0      # 更新时不允许有 Pod 不可用
      # 效果：先创建 1 个新 Pod（共 4 个），确认健康后再杀 1 个旧 Pod
      # 重复直到所有 Pod 都更新完成
  template:
    spec:
      containers:
      - name: app
        image: my-nodejs:v2.0   # 修改镜像版本触发滚动更新
```

**滚动更新的过程（`maxSurge: 1, maxUnavailable: 0`）：**

```bash
时间线：
T0: [v1, v1, v1]           # 3 个 v1 Pod
T1: [v1, v1, v1, v2]       # 创建 1 个 v2 Pod（maxSurge=1）
T2: [v1, v1, v2]           # v2 就绪后，删除 1 个 v1（maxUnavailable=0）
T3: [v1, v1, v2, v2]       # 再创建 1 个 v2
T4: [v1, v2, v2]           # 再删除 1 个 v1
T5: [v1, v2, v2, v2]       # 再创建 1 个 v2
T6: [v2, v2, v2]           # 删除最后 1 个 v1，更新完成！
```

> [!TIP] 提示
> `maxUnavailable: 0` 确保了**零停机更新**——在旧 Pod 被杀之前，新 Pod 必须已经就绪并通过健康检查。代价是更新速度会慢一些。如果你能容忍短暂的服务降级，可以设为 `maxUnavailable: 1` 来加速更新。

### 回滚

```bash
# 查看部署历史
kubectl rollout history deployment/nodejs-app

# 查看某个版本的详细信息
kubectl rollout history deployment/nodejs-app --revision=3

# 回滚到上一版本
kubectl rollout undo deployment/nodejs-app

# 回滚到指定版本
kubectl rollout undo deployment/nodejs-app --to-revision=2

# 暂停和恢复更新（批量修改时使用）
kubectl rollout pause deployment/nodejs-app
# ... 做多个修改 ...
kubectl rollout resume deployment/nodejs-app
```

> **Warning:** 滚动更新时，如果你的新版本有 bug 导致所有 Pod 都不就绪，Deployment 会"卡住"而不会自动回滚。你需要手动执行 `kubectl rollout undo`。建议在 CI/CD 中集成自动回滚逻辑。

## 19.2 Service 类型详解

Service 有四种类型，适用于不同场景：

```yaml
# 1. ClusterIP（默认）—— 集群内部访问
apiVersion: v1
kind: Service
metadata:
  name: internal-service
spec:
  type: ClusterIP           # 仅集群内可访问
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 3000
# 用途：微服务之间的内部通信

---
# 2. NodePort —— 通过节点端口暴露（开发/测试用）
apiVersion: v1
kind: Service
metadata:
  name: nodeport-service
spec:
  type: NodePort
  selector:
    app: myapp
  ports:
  - port: 80                # Service 端口（集群内访问）
    targetPort: 3000         # Pod 端口
    nodePort: 30080          # 节点端口（30000-32767 范围）
# 访问方式：http://<任意节点IP>:30080

---
# 3. LoadBalancer —— 云服务商负载均衡器（生产用）
apiVersion: v1
kind: Service
metadata:
  name: lb-service
spec:
  type: LoadBalancer         # 自动创建云服务商的负载均衡器
  selector:
    app: myapp
  ports:
  - port: 80
    targetPort: 3000
# 在 AWS 上会创建一个 ELB，在 GCP 上创建 Cloud LB
# 本地环境（Minikube）需要执行 minikube tunnel

---
# 4. ExternalName —— 映射外部服务
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: rds.amazonaws.com  # 映射到外部域名
# 用途：让集群内的 Pod 通过 external-db.default.svc.cluster.local
# 访问外部数据库，方便后续迁移
```

**选择指南：**

```bash
你的服务只需要集群内部访问？ → ClusterIP
你需要从外部访问，且在云上？ → LoadBalancer
你只是开发测试？ → NodePort
你需要连接外部服务？ → ExternalName
你有多个域名/路径需要路由？ → ClusterIP + Ingress（下一节）
```

## 19.3 Ingress 与 Ingress Controller

Service 的 LoadBalancer 类型有一个问题：**每暴露一个服务就需要一个负载均衡器**（在云上 = 钱）。Ingress 解决了这个问题——它像 Nginx 反向代理一样，用**一个入口**根据不同的域名/路径路由到不同的 Service。

```yaml
# 首先，你需要安装 Ingress Controller
# Minikube
minikube addons enable ingress

# 或者安装 Nginx Ingress Controller
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml

# 然后创建 Ingress 资源
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx      # 指定使用 Nginx Ingress Controller
  rules:
  - host: api.example.com      # 域名
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /admin
        pathType: Prefix
        backend:
          service:
            name: admin-service
            port:
              number: 80
  - host: www.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
  tls:                         # TLS 证书配置
  - hosts:
    - api.example.com
    - www.example.com
    secretName: tls-secret     # 需要提前创建包含证书的 Secret
```

**Ingress vs Service 的关系：**

```bash
用户请求
    │
    ▼
Ingress Controller（Nginx/Traefik）  ← 唯一的入口
    │
    ├── api.example.com     → api-service      → API Pods
    ├── www.example.com     → frontend-service → Frontend Pods
    └── api.example.com/admin → admin-service  → Admin Pods
```

> [!TIP] 提示
> 常见的 Ingress Controller 除了 Nginx Ingress，还有 **Traefik**（自带 Dashboard、自动服务发现、配置更简单）和 **Kong**（基于 Nginx，增加了 API 网关能力）。选择哪个取决于你的需求复杂度。

## 19.4 PersistentVolume & PersistentVolumeClaim —— 存储管理

Pod 是"无状态"的——Pod 重启后，里面的数据全没了。这对 Web 服务没问题，但数据库怎么办？

K8s 的存储模型使用了**供给-消费**的解耦设计：

- **PersistentVolume (PV)**：管理员提供的"存储资源"（供给方）
- **PersistentVolumeClaim (PVC)**：Pod 对存储的"申请"（消费方）

类比：PV 就像公司的共享网盘空间（100GB），PVC 就像你申请了其中 20GB 给你的项目用。

```yaml
# PersistentVolume：管理员创建的存储资源
apiVersion: v1
kind: PersistentVolume
metadata:
  name: mongo-pv
spec:
  capacity:
    storage: 10Gi            # 总容量 10GB
  accessModes:
  - ReadWriteOnce            # 只能被一个节点挂载读写
  persistentVolumeReclaimPolicy: Retain  # PVC 删除后保留数据
  storageClassName: standard  # 存储类名称
  hostPath:                   # 本地开发用 hostPath（生产用云存储）
    path: /data/mongo

---
# PersistentVolumeClaim：应用申请存储
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mongo-pvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi           # 申请 5GB
  storageClassName: standard

---
# 在 Pod/Deployment 中使用 PVC
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mongodb
spec:
  replicas: 1                # 数据库通常只跑 1 个副本
  selector:
    matchLabels:
      app: mongodb
  template:
    metadata:
      labels:
        app: mongodb
    spec:
      containers:
      - name: mongodb
        image: mongo:6.0
        ports:
        - containerPort: 27017
        volumeMounts:
        - name: mongo-storage
          mountPath: /data/db   # MongoDB 数据目录
      volumes:
      - name: mongo-storage
        persistentVolumeClaim:
          claimName: mongo-pvc  # 引用上面的 PVC
```

> **Warning:** `hostPath` 类型的 PV 只在开发环境使用（数据存在某个具体节点上，节点挂了数据就没了）。生产环境应该使用云服务商的存储（AWS EBS、GCP Persistent Disk）或分布式存储（Ceph、NFS），通过 `StorageClass` 自动供给。

## 19.5 StatefulSet vs Deployment

对于数据库这类**有状态应用**，Deployment 并不合适。因为 Deployment 创建的 Pod 是无差别的、可互换的。但数据库需要：

- 稳定的网络标识（每个实例有固定的名称和 DNS）
- 稳定的存储（Pod 重启后仍然挂载同一块存储）
- 有序的启停（先启主节点，再启从节点）

**StatefulSet** 就是为有状态应用设计的：

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongodb-replica
spec:
  serviceName: mongodb-headless  # 必须配合 Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: mongodb
  template:
    metadata:
      labels:
        app: mongodb
    spec:
      containers:
      - name: mongodb
        image: mongo:6.0
        ports:
        - containerPort: 27017
        volumeMounts:
        - name: data
          mountPath: /data/db
  # volumeClaimTemplates：为每个 Pod 自动创建独立的 PVC！
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 5Gi
---
# Headless Service（clusterIP: None）
# 为每个 Pod 创建独立的 DNS 记录
apiVersion: v1
kind: Service
metadata:
  name: mongodb-headless
spec:
  clusterIP: None             # Headless！不分配集群 IP
  selector:
    app: mongodb
  ports:
  - port: 27017
```

StatefulSet 创建的 Pod 有固定的命名规则：`mongodb-replica-0`、`mongodb-replica-1`、`mongodb-replica-2`。Pod `0` 先启动，`0` 就绪后才启动 `1`，以此类推。每个 Pod 挂载独立的 PVC（`data-mongodb-replica-0`、`data-mongodb-replica-1`），重启后还是原来的存储。

```bash
Deployment（无状态）：
Pod 名称随机，删除重建后名称变化
Pod-a3x8f → 重启 → Pod-k2m9p（换了名字，换了存储）

StatefulSet（有状态）：
Pod 名称固定，删除重建后名称不变
mongo-0 → 重启 → mongo-0（名字不变，存储不变）
```

## 19.6 Job & CronJob —— 批处理与定时任务

```yaml
# Job：运行一次就结束的任务（类似 docker run --rm）
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3            # 失败最多重试 3 次
  activeDeadlineSeconds: 600 # 超时时间 10 分钟
  template:
    spec:
      containers:
      - name: migrate
        image: my-app:v1.0
        command: ["node", "migrate.js"]  # 执行完就退出
      restartPolicy: Never   # 完成后不重启
---
# CronJob：定时执行的任务
apiVersion: batch/v1
kind: CronJob
metadata:
  name: cleanup-old-data
spec:
  schedule: "0 2 * * *"      # 每天凌晨 2 点执行（标准 cron 表达式）
  # ┌─── 分钟 (0-59)
  # │ ┌─── 小时 (0-23)
  # │ │ ┌─── 日 (1-31)
  # │ │ │ ┌─── 月 (1-12)
  # │ │ │ │ ┌─── 星期几 (0-7, 0和7都是周日)
  # │ │ │ │ │
  # * * * * *
  concurrencyPolicy: Forbid  # 禁止并发执行（上一次没跑完，这次跳过）
  successfulJobsHistoryLimit: 3  # 保留最近 3 次成功记录
  failedJobsHistoryLimit: 1      # 保留最近 1 次失败记录
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: cleanup
            image: my-app:v1.0
            command: ["node", "cleanup.js"]
          restartPolicy: OnFailure
```

## 19.7 Init Containers & Sidecar Containers

### Init Containers —— 在主容器启动前执行

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      # Init Containers：按顺序执行，全部成功后才启动主容器
      initContainers:
      - name: wait-for-db
        image: busybox
        # 等待数据库就绪才继续（常见场景！）
        command: ['sh', '-c', 'until nc -z mongo-service 27017; do echo waiting for db; sleep 2; done']
      - name: run-migrations
        image: my-app:v1.0
        command: ['node', 'migrate.js']
        # 运行数据库迁移脚本
      containers:
      - name: app
        image: my-app:v1.0
        ports:
        - containerPort: 3000
```

**Init Containers 的执行流程：**

```bash
wait-for-db（等待数据库就绪）
    │ 完成
    ▼
run-migrations（执行数据库迁移）
    │ 完成
    ▼
app（启动主应用）← 此时数据库已就绪，迁移已执行
```

### Sidecar Containers —— 与主容器并行的辅助容器

```yaml
spec:
  containers:
  # 主容器：你的应用
  - name: app
    image: my-app:v1.0
    volumeMounts:
    - name: log-volume
      mountPath: /app/logs

  # Sidecar 1：日志收集（把日志文件发到 Elasticsearch）
  - name: log-shipper
    image: fluentd:v1.16
    volumeMounts:
    - name: log-volume
      mountPath: /app/logs
      readOnly: true
    # fluentd 配置：读取日志文件 → 发送到 ES

  # Sidecar 2：Envoy 代理（服务网格常用）
  - name: envoy-proxy
    image: envoyproxy/envoy:v1.28
    ports:
    - containerPort: 8080

  volumes:
  - name: log-volume
    emptyDir: {}   # Pod 内共享的临时存储
```

**Sidecar 模式的精髓**：关注点分离。你的应用只负责业务逻辑，日志收集、流量代理、安全认证等横切关注点由 sidecar 处理。这就是"微服务中的微服务"。

## 19.8 ConfigMap 热更新

ConfigMap 可以以**环境变量**或**文件挂载**两种方式注入 Pod，热更新行为不同：

```yaml
# 方式1：环境变量（不支持热更新，需要重启 Pod）
env:
- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: LOG_LEVEL

# 方式2：文件挂载（支持热更新，但应用需要监听文件变化）
volumeMounts:
- name: config
  mountPath: /etc/config
volumes:
- name: config
  configMap:
    name: app-config
```

对于方式2，当你 `kubectl apply` 更新 ConfigMap 后，挂载的文件会自动更新（有一定延迟，通常 1-2 分钟）。但你的应用需要能够检测到文件变化并重新加载配置。

```javascript
// Node.js 示例：监听配置文件变化
const fs = require('fs');
const path = require('path');

let config = loadConfig();

fs.watchFile(path.join('/etc/config', 'config.json'), (curr, prev) => {
  console.log('Config file changed, reloading...');
  config = loadConfig();
});

function loadConfig() {
  const raw = fs.readFileSync('/etc/config/config.json', 'utf-8');
  return JSON.parse(raw);
}
```

> **Warning:** 环境变量方式的 ConfigMap **不支持**热更新。如果你用 `envFrom` 注入 ConfigMap，更新 ConfigMap 后需要重新部署 Deployment（比如修改一个注解触发滚动更新）才能生效。

## 19.9 实战：部署完整的 Node.js 微服务架构

让我们部署一个包含 API + MongoDB + Redis + Nginx Ingress 的完整架构。

### 架构概览

```bash
用户请求 → Ingress Controller → Ingress
                                      │
                        ┌─────────────┼─────────────┐
                        │             │             │
                        ▼             ▼             ▼
                   api-service   redis-service  mongo-service
                   (Deployment)  (Deployment)   (StatefulSet)
                   [3 replicas]  [1 replica]    [1 replica + PVC]
                        │             │
                        └─── Ingress 路由 ───┘
```

### 完整的 K8s 资源文件

```yaml
# ===== k8s/namespace.yaml =====
apiVersion: v1
kind: Namespace
metadata:
  name: microservices

---
# ===== k8s/configmap.yaml =====
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: microservices
data:
  MONGO_URI: "mongodb://mongo-service:27017/myapp"
  REDIS_HOST: "redis-service"
  REDIS_PORT: "6379"
  NODE_ENV: "production"
  LOG_LEVEL: "info"

---
# ===== k8s/secrets.yaml =====
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
  namespace: microservices
type: Opaque
data:
  # echo -n "my-jwt-secret-key" | base64
  JWT_SECRET: bXktand0LXNlY3JldC1rZXk=

---
# ===== k8s/mongodb.yaml =====
apiVersion: v1
kind: Service
metadata:
  name: mongo-service
  namespace: microservices
spec:
  selector:
    app: mongodb
  ports:
  - port: 27017
    targetPort: 27017
  clusterIP: None            # Headless Service（配合 StatefulSet）
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongodb
  namespace: microservices
spec:
  serviceName: mongo-service
  replicas: 1
  selector:
    matchLabels:
      app: mongodb
  template:
    metadata:
      labels:
        app: mongodb
    spec:
      containers:
      - name: mongodb
        image: mongo:6.0
        ports:
        - containerPort: 27017
        volumeMounts:
        - name: mongo-data
          mountPath: /data/db
        resources:
          requests:
            memory: "256Mi"
            cpu: "200m"
          limits:
            memory: "512Mi"
            cpu: "500m"
  volumeClaimTemplates:
  - metadata:
      name: mongo-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 5Gi

---
# ===== k8s/redis.yaml =====
apiVersion: v1
kind: Service
metadata:
  name: redis-service
  namespace: microservices
spec:
  selector:
    app: redis
  ports:
  - port: 6379
    targetPort: 6379
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: microservices
spec:
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
      - name: redis
        image: redis:7-alpine
        ports:
        - containerPort: 6379
        resources:
          requests:
            memory: "64Mi"
            cpu: "50m"
          limits:
            memory: "128Mi"
            cpu: "200m"

---
# ===== k8s/api-deployment.yaml =====
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: microservices
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: api
    spec:
      initContainers:
      - name: wait-for-deps
        image: busybox
        command: ['sh', '-c', '
          until nc -z mongo-service 27017 && nc -z redis-service 6379;
          do echo "Waiting for dependencies..."; sleep 3;
          done; echo "Dependencies ready!"']
      containers:
      - name: api
        image: my-nodejs-api:v1.0
        imagePullPolicy: IfNotPresent
        ports:
        - containerPort: 3000
        envFrom:
        - configMapRef:
            name: app-config
        env:
        - name: JWT_SECRET
          valueFrom:
            secretKeyRef:
              name: app-secrets
              key: JWT_SECRET
```

### 应用代码

```python
# app.py
from flask import Flask, jsonify, request
import psycopg2
import os
import time

app = Flask(__name__)

def get_db_connection():
    """获取数据库连接"""
    return psycopg2.connect(
        host=os.environ.get('DB_HOST', 'postgres-service'),
        port=os.environ.get('DB_PORT', '5432'),
        dbname=os.environ.get('DB_NAME', 'myapp'),
        user=os.environ.get('DB_USER', 'postgres'),
        password=os.environ.get('DB_PASSWORD', 'secret')
    )

@app.route('/health')
def health():
    """健康检查端点"""
    try:
        conn = get_db_connection()
        conn.close()
        return jsonify({"status": "ok", "db": "connected"})
    except Exception as e:
        return jsonify({"status": "error", "db": str(e)}), 503

@app.route('/api/items', methods=['GET'])
def get_items():
    """获取所有 items"""
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute('SELECT id, name, created_at FROM items ORDER BY created_at DESC')
    items = [{"id": r[0], "name": r[1], "created_at": str(r[2])} for r in cur.fetchall()]
    cur.close()
    conn.close()
    return jsonify(items)

@app.route('/api/items', methods=['POST'])
def create_item():
    """创建新 item"""
    data = request.get_json()
    conn = get_db_connection()
    cur = conn.cursor()
    cur.execute('INSERT INTO items (name) VALUES (%s) RETURNING id', (data['name'],))
    item_id = cur.fetchone()[0]
    conn.commit()
    cur.close()
    conn.close()
    return jsonify({"id": item_id, "name": data['name']}), 201

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

## 本章小结

- **Deployment** 支持滚动更新和回滚，`maxSurge` 和 `maxUnavailable` 控制更新策略
- **Service** 四种类型各有适用场景，生产环境通常用 LoadBalancer + Ingress
- **Ingress** 统一管理外部访问入口，支持域名/路径路由和 TLS 终止
- **PV/PVC** 解决有状态应用的持久化存储问题
- **StatefulSet** 为数据库等有状态应用提供稳定的网络标识和存储
- **Job/CronJob** 处理一次性任务和定时任务
- **Init Container** 处理启动前依赖（等数据库就绪、跑迁移脚本等）
- **Sidecar** 实现关注点分离（日志收集、代理等）

## 练习

1. **滚动更新**：部署一个 v1.0 的应用，修改代码为 v2.0，观察滚动更新过程。使用 `kubectl rollout undo` 回滚
2. **Ingress**：为你的应用配置 Ingress，实现根据路径 `/api` 和 `/admin` 路由到不同 Service
3. **StatefulSet**：部署一个带持久化存储的 PostgreSQL，删除 Pod 后验证数据仍然存在
4. **CronJob**：创建一个每 5 分钟执行一次的 CronJob，输出当前时间和 Pod 名称
5. **综合挑战**：部署完整的 Node.js 微服务架构（参考 19.9），实现从零停机的滚动更新
