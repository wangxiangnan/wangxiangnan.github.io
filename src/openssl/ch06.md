# 第6章：格式迷宫：PEM、DER 与 PKCS 家族

> [!TIP] Part 2: 非对称与证书篇（进阶篇）
> 进阶篇的第二道坎，也是新手报错率最高的一章。钥匙和证书在磁盘上有一整族格式，网上抄来的命令十有六七栽在「unable to load key」上——本章把迷宫走通，以后见格式报错如见熟人。

王哥拿同事阿雪发来的一个证书文件想配进 nginx，命令敲下去：

```text
nginx: [emerg] PEM_read_bio_X509_aux("/etc/nginx/api.crt") failed
```

文件明明存在、权限也对，怎么就读不了？十有八九不是权限问题，是**格式问题**：文件的内容结构和 nginx 期待的不一样。这一章把「内容结构」与「文件编码」两层皮讲清楚——分清这两层，格式报错就再也吓不到你。王哥的这起事故本章末尾会有完整复盘，先补地基。

## 6.1 两层皮：结构层与编码层

密钥与证书的格式体系，要按两个互相独立的维度拆：

| 维度 | 问的问题 | 成员 |
| ---- | ---- | ---- |
| **结构层** | 文件里装的是什么数据结构？ | X.509 证书、PKCS#8 私钥、PKCS#1 私钥、PKCS#12 打包、CSR 申请表——PKCS（Public-Key Cryptography Standards，公钥密码学标准）是一族编号标准的总称 |
| **编码层** | 这份结构用什么方式写进文件？ | PEM（base64 文本，带头尾行）、DER（Distinguished Encoding Rules，ASN.1 的纯二进制编码） |

```text
 结构层（装什么）                编码层（怎么写）
┌────────────────────┐        ┌──────────────────┐
│ X.509 证书          │        │ PEM：base64 文本  │
│ PKCS#8 私钥         │ ────►  │  -----BEGIN...   │
│ PKCS#1 老私钥       │        │ DER：纯二进制      │
│ PKCS#12 打包        │        └──────────────────┘
│ CSR 申请表          │
└────────────────────┘
```

两层皮自由组合：同一张 X.509 证书可以写成 PEM（Linux 世界默认），也可以写成 DER（Windows 世界常见）；同一个 PKCS#8 私钥既可以是裸的 PEM，也可以是加密的 PEM。混乱的根源正是这两层的组合爆炸——而头行（PEM）是唯一可靠的自我介绍。

结构层还有一个幕后总管值得认识：这些结构的底层数据格式由 **ASN.1**（Abstract Syntax Notation One，抽象语法标记）定义、DER 是它的一种严格编码。你不必学 ASN.1 语法——只需要知道两点：其一，证书、密钥、CSR 的「里面长什么样」（字段顺序、类型、长度）全由 ASN.1 模块一锤定音，所以全世界任何实现解析出来的结果一致；其二，OpenSSL 提供了一个 `asn1parse` 子命令可以把任何 DER/PEM 文件按 ASN.1 结构逐字段拆开：

```bash
openssl asn1parse -in api.crt | head -8
```

```text
0:d=0  hl=4 l= 691 cons: SEQUENCE
4:d=1  hl=2 l=  59 cons: SEQUENCE
6:d=2  hl=2 l=  32 prim: INTEGER       (证书序列号)
40:d=2  hl=2 l=  13 cons: SEQUENCE    (签名算法)
...
```

`d=` 是嵌套深度、`l=` 是字段长度，整张证书就是一棵 ASN.1 树。日常排错用不到它，但「报错信息里的 object identifier 看不懂」或「怀疑证书文件被截断」时，asn1parse 是终极显微镜——第8章解剖证书时我们会再用它一次。

## 6.2 PEM 解剖：会读头行就赢了一半

PEM（Privacy-Enhanced Mail，一个带着历史包袱的名字）格式朴素到透明：一行声明开头，base64 编码的正文，一行声明收尾。它的妙处是**一个文件可以装多个块**——比如证书链文件就是几张证书首尾相接。

读任何 PEM 文件先看头行，头行即身份：

| 头行 | 结构 | 身份 |
| ---- | ---- | ---- |
| `-----BEGIN CERTIFICATE-----` | X.509 | 证书（数字身份证） |
| `-----BEGIN CERTIFICATE REQUEST-----` | PKCS#10 | CSR（证书申请表） |
| `-----BEGIN PRIVATE KEY-----` | PKCS#8 | 现代格式私钥（可加密） |
| `-----BEGIN ENCRYPTED PRIVATE KEY-----` | PKCS#8 加密 | 上了锁的私钥（第5章 `-aes-256-cbc` 的产物） |
| `-----BEGIN RSA PRIVATE KEY-----` | PKCS#1 | 老式 RSA 私钥（1.x 时代产物） |
| `-----BEGIN EC PRIVATE KEY-----` | SEC1 | 老式 EC 私钥 |
| `-----BEGIN PUBLIC KEY-----` | SPKI | 裸公钥 |
| `-----BEGIN TRUSTED CERTIFICATE-----` | X.509 + 信任位 | 少见，信任库格式 |

一秒钟扫出头行的方法：

```bash
grep -c "BEGIN" bundle.pem        # 数一数装了几个块
grep "BEGIN" bundle.pem           # 逐个看身份
```

结构层的「代际差异」值得一提：PKCS#1 和 SEC1 是各算法自说自话的老格式，PKCS#8 是统一各家族的现代信封。你不需要手工造老格式，但需要会把老货升级成新格式——`pkey` 读进老格式、默认吐出 PKCS#8：

```bash
openssl pkey -in old-rsa.pem -out modern-rsa.pem
```

读头行验货：`RSA PRIVATE KEY` 变成了 `PRIVATE KEY`，升级完成。nginx、新版工具链对 PKCS#8 全都来者不拒，见到老格式就顺手转一把是消除「玄学报错」的好习惯。

一把钥匙升级前后**内容等价但字节不同**——如果你正拿老文件做指纹比对（6.5 的配对检查），记得用升级后的文件重新生成基准，别拿旧指纹来对。同理，第2章的校验清单若是给老格式文件登记过，升级后要重新登记。格式转换是「内容不变、字节必变」的操作，所有依赖字节指纹的流程都会感知它。

## 6.3 编码转换：PEM 与 DER 互换

编码层的转换是 `-inform` 与 `-outform` 两个参数的事，所有读取类命令通用：

```bash
# PEM 转 DER（发给只认二进制的系统，如部分 Windows 组件）
openssl x509 -in api.crt -outform DER -out api.der
openssl pkey -in api-key.pem -outform DER -out api-key.der

# DER 转 PEM（反向，注意多加 -inform）
openssl x509 -inform DER -in api.der -out api.crt
openssl pkey -inform DER -in api-key.der -out api-key.pem
```

记忆法：**`-inform` 说「进来的长这样」，`-outform` 说「出去的要这样」**，不写时默认都是 PEM。一个经验判断帮你快速分辨手里文件是哪种编码：用文本编辑器打开，能看到 `-----BEGIN` 的是 PEM；打开是乱码的是 DER。

遇到一整个目录的证书都要转格式时，套个循环一次干完：

```bash
mkdir -p der/
for f in *.crt; do
  openssl x509 -in "$f" -outform DER -out "der/${f%.crt}.der"
done
```

循环里的 `${f%.crt}` 是第3章 restore.sh 同款的后缀剥离。批量转换前建议先 `grep -L "BEGIN" *.crt` 圈出目录里的 DER 文件（`-L` 列出**不含**匹配的文件）——对 DER 文件跑上面的命令会报 `no start line`，先验货再转，一步不浪费。

## 6.4 打包与拆包：pkcs12

实际工程里经常要把「私钥 + 证书 + 中间证书链」**装进一个文件**流转——发给同事、导入 Windows/IIS、配置 Java 服务。干这活的格式是 PKCS#12（文件常叫 .p12 或 .pfx），它自带口令加密，是天然的「保险箱快递盒」：

```bash
# 导出口令同样是 rand 生成、台账登记（第4章纪律）
openssl rand -base64 16 > ~/.cloudnote-secrets/P12_PASS.txt
chmod 600 ~/.cloudnote-secrets/P12_PASS.txt

# 打包：私钥 + 服务器证书 + 证书链，全程用一个导出口令
export P12PASS=$(cat ~/.cloudnote-secrets/P12_PASS.txt)
openssl pkcs12 -export \
  -in api.crt -inkey api-key.pem -passin file:$HOME/.cloudnote-secrets/KEY_PASS.txt \
  -certfile chain.pem \
  -name "cloudnote-api" -passout env:P12PASS -out api-bundle.p12
```

| 参数 | 作用 |
| ---- | ---- |
| `-in` / `-inkey` | 证书与私钥（第13章会讲 `-in` 常用 fullchain） |
| `-certfile` | 额外附上的证书链 |
| `-name` | 包内条目的友好名称 |
| `-passout` | 导出口令——**这个口令要单独告知收件人**，它不是你的私钥口令 |

拆包是打包的镜像动作，`-nokeys` 与 `-nocerts` 分别只取证书或只取钥匙：

```bash
# 全拆（-nodes 表示输出的私钥不加口令——仅限你完全掌控的机器）
openssl pkcs12 -in api-bundle.p12 -passin env:P12PASS -nodes -out all-in-one.pem

# 只要证书 / 只要私钥
openssl pkcs12 -in api-bundle.p12 -passin env:P12PASS -nokeys  -clcerts -out api.crt
openssl pkcs12 -in api-bundle.p12 -passin env:P12PASS -nocerts -nodes -out api-key.pem
```

`-info` 是 p12 的「透视镜」，打印包内清单与加密参数——发出去之前看一眼，比到了对端再排错便宜十倍：

```text
$ openssl pkcs12 -info -in api-bundle.p12 -passin env:P12PASS -nokeys
MAC: sha256, Iteration 2048
PKCS7 Encrypted data: PBES2, PBKDF2, AES-256-CBC, Iteration 2048, PRF hmacWithSHA256
Certificate bag
Bag Attributes
    localKeyID: 54 69 6D ...
    friendlyName: cloudnote-api
subject=CN = api.cloudnote.example
issuer=CN = Cloudnote Internal CA
-----BEGIN CERTIFICATE-----
MIIBszCCAVmgAwIBAgIUXn3...
```

读这份输出的三个要点：首行 `MAC` 是整包的完整性校验（口令错误的报错就出自它）；第二行能看到包内加密用的算法族——`PBES2 + PBKDF2 + AES-256-CBC` 就是 3.x 的现代默认，老系统打不开时 `-legacy` 会把这行换成 `PBE-SHA1-3DES` 一类老古董；`friendlyName` 就是你 `-name` 起的名字，Windows 导入向导里显示的就是它。

> [!WARNING] 3.x 的 -legacy 之坑
> OpenSSL 3.x 生成的 .p12 默认用现代加密（AES-256 + PBKDF2），但**一些老 Java 版本、老 Windows 系统打不开**，报错往往是神秘的 `keystore password was incorrect`。给老系统发 p12 时加 `-legacy` 参数降级到老算法。反向的坑也存在：老工具生成的 RC2 加密 p12 在 3.x 里读取时可能要临时启用 legacy 提供者（第1章的伏笔在此回收）。

## 6.5 后缀与报错速查

后缀的世界约定俗成大于标准，一张表足够日常导航：

| 后缀 | 通常是什么 | 常见编码 |
| ---- | ---- | ---- |
| `.pem` | 什么都可能是 | 必是 PEM |
| `.crt` / `.cer` | 证书 | PEM 或 DER 都常见（**.cer 尤其二义**，用 6.2 的方法验货） |
| `.key` | 私钥 | 通常是 PEM |
| `.csr` | 证书申请表 | 通常是 PEM |
| `.der` | 证书或密钥 | 必是 DER |
| `.p12` / `.pfx` | 打包（私钥+证书+链） | PKCS#12 容器 |
| `.jks` | Java 专有密钥库 | 另一个世界，需 keytool 转换 |

**报错速查**是本章的真正干货，格式相关的四大高频报错与处置：

| 报错关键字 | 真实病因 | 处置 |
| ---- | ---- | ---- |
| `no start line` / `Expecting: ...` | 拿 DER 文件当 PEM 读，或头行不属于期待的结构 | 加 `-inform DER`；`grep BEGIN` 验货 |
| `Could not read private key`（无更多提示） | 私钥加密但没给口令 | 补 `-passin` |
| `key values mismatch` | 私钥与证书不配对（配错了文件） | 见下方指纹比对法 |
| `PEM_read_bio failed`（nginx 等） | 配置指向的文件格式不对 | 同第一条，先验货再改配置 |

「key values mismatch」的排查姿势值得单独记：比较证书与私钥导出的公钥指纹，一致才算配对：

```bash
openssl x509 -in api.crt -noout -pubkey | openssl dgst -sha256
openssl pkey -in api-key.pem -passin file:$HOME/.cloudnote-secrets/KEY_PASS.txt -pubout | openssl dgst -sha256
```

两行输出一致 → 配对，问题在别处；不一致 → 找错文件了。这个方法和第5章的公钥指纹一脉相承，又是「哈希当指纹」的一次上岗。

## 6.6 实验：给阿雪一个 p12 全家桶

场景：阿雪要在她的 Windows 测试机上配置与内网 API 的连接，需要私钥与证书。你打包发送，她验收拆包。

**打包方（你）：**

```bash
export P12PASS=$(openssl rand -base64 18)
# 口令随后通过 IM/电话单独告知阿雪，不与 p12 同渠道发送
openssl pkcs12 -export -in api.crt -inkey api-key.pem \
  -passin file:$HOME/.cloudnote-secrets/KEY_PASS.txt \
  -passout env:P12PASS -name "cloudnote-api" -out api-bundle.p12
# 打包完先自检一遍：能否列出包内条目
openssl pkcs12 -info -in api-bundle.p12 -nokeys -passin env:P12PASS
```

**验收方（阿雪）：**

```bash
openssl pkcs12 -in api-bundle.p12 -passin pass:'收到的口令' -nodes -clcerts -nokeys -out api.crt
openssl pkcs12 -in api-bundle.p12 -passin pass:'收到的口令' -nocerts -nodes -out api-key.pem
# 核对配对（6.5 的指纹法）
openssl x509 -in api.crt -noout -pubkey | openssl dgst -sha256
openssl pkey -in api-key.pem -pubout | openssl dgst -sha256
```

> [!NOTE] 口令的传递渠道纪律
> p12 文件与它的口令**永远走两条渠道**：文件走邮件或网盘，口令走即时通讯或口头——单渠道泄露不构成完整泄露。这和 SSH 私钥加 passphrase 的思路同源：多一道独立防线。另外留意打包命令里口令通过环境变量（`env:`）传入而不是写在命令行上（第3章的 `-pass pass:` 教训，这里同理）。

验收标准：`pkcs12 -info` 能列出包内证书与私钥条目；拆包后公钥指纹两侧一致。至此你具备了「证书物流」的全部能力——不过手里还只有自签的散装证书。它们怎么变成一张有身份的正式证书、证书链又是什么，正是后面三章的主线。

顺带收掉开头王哥那桩悬案：`PEM_read_bio_X509_aux failed` 的真凶，是阿雪发来的 `api.crt` 其实是 **DER 编码**（她从 Windows 机器上导出的），nginx 只认 PEM。解法两选一：转一次格式（`openssl x509 -inform DER -in api.crt -out api.pem`），或按第13章的规范改发 fullchain PEM。复盘完毕——你现在回头看她发来的文件，`grep BEGIN` 一秒钟就能确诊。

## 本章小结

- 格式体系分两层：**结构层**（X.509 / PKCS#8 / PKCS#1 / PKCS#12 / CSR）与**编码层**（PEM 文本 / DER 二进制），自由组合才有千姿百态；底层由 ASN.1 一锤定音，`asn1parse` 是终极显微镜
- PEM 的头行是唯一可靠的自我介绍：`grep BEGIN` 验货一秒定位问题
- 编码转换一个套路：`-inform` 管进口、`-outform` 管出口；老私钥（PKCS#1/SEC1）用 `pkey` 读一遍即升级为 PKCS#8
- p12 是「私钥+证书+证书链」的加密快递盒：`pkcs12 -export` 打包、`-nokeys/-nocerts` 拆包；3.x 默认新加密，老系统要 `-legacy`
- 四大报错速查：no start line（编码/结构不对）、读私钥失败（缺口令）、key values mismatch（配错对，用公钥指纹比对）、PEM_read_bio failed（nginx 指错文件）
- 后缀是习俗不是标准：`.cer` 可能是 PEM 也可能是 DER，永远验货

**下一章预告**：物流能力就位，开始干正事——给发布包盖防伪章。数字签名把「文件没变过」升级成「文件没变过，而且是我发的」，危机二里那次未遂的更新包篡改，本章给它画上句号。
