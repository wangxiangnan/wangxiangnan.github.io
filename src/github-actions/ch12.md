# 第12章：自定义 Action——用 JavaScript/Docker 写自己的 Action

## 引言：站在巨人的肩膀上，然后成为巨人

GitHub Marketplace 上有数万个现成的 Action 可用。大多数时候，`checkout`、`setup-node`、`cache` 这些官方和社区 Action 已经够用了。

但总有一天，你会发现：

> "我需要一个小众的部署工具，但没人写对应的 Action。"
> "我们有一套内部 API，我想在 CI 里调用它，但找不到合适的 Action。"
> "我想把 5 个 Step 封装成一个 Action，让团队用起来更简单。"

这时候，你就需要自己动手写 Action 了。别紧张——写一个 Action 没有想象中那么复杂。本质上，你就是在写一个**带约定接口的脚本**。

## 三种 Action 类型

GitHub Actions 支持三种类型的自定义 Action。选择哪种，取决于你的需求：

```
你需要写一个自定义 Action
│
├── 只是把几个现有步骤打包在一起？
│   └── ✅ Composite Action（组合型）
│       最简单，就是 YAML 里的 steps 封装
│
├── 需要用 JavaScript/TypeScript 编写复杂逻辑？
│   └── ✅ JavaScript Action
│       可以调用 npm 生态、操作 GitHub API、处理复杂数据
│
└── 需要运行一个特定语言的工具或需要特殊运行时？
    └── ✅ Docker Action
        自带完整运行环境，适合 Python、Go、Rust 等工具
```

**决策树精简版**：

| 类型 | 适用场景 | 运行速度 | 开发难度 | 灵活性 |
|------|---------|---------|---------|-------|
| Composite | 封装多个 YAML 步骤 | 最快（原生） | 最低 | 中 |
| JavaScript | 复杂逻辑、API 调用 | 快 | 中 | 高 |
| Docker | 需要特殊运行时 | 最慢（需构建镜像） | 高 | 最高 |

## Composite Action——最简单的复用

Composite Action 不需要写代码，只需要一个 `action.yml` 文件：

```yaml
# actions/setup-and-test/action.yml
# 这个 Action 把"安装 Node + 安装依赖 + 运行测试"打包成一个步骤

name: 'Setup and Test'
description: '一键完成 Node.js 项目的安装和测试'

inputs:
  node-version:
    description: 'Node.js 版本'
    required: false
    default: '20'
  test-command:
    description: '测试命令'
    required: false
    default: 'npm test'

outputs:
  coverage:
    description: '测试覆盖率'
    value: ${{ steps.test.outputs.coverage }}

runs:
  using: 'composite'                  # 声明这是 Composite Action
  steps:
    - name: 设置 Node.js
      uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}

    - name: 安装依赖
      shell: bash                      # Composite Action 的每个 step 必须指定 shell
      run: npm ci

    - name: 运行测试
      id: test
      shell: bash
      run: |
        ${{ inputs.test-command }}
        # 假设测试工具输出了覆盖率
        echo "coverage=87.5" >> $GITHUB_OUTPUT
```

使用时：

```yaml
steps:
  - uses: actions/checkout@v4
  - uses: ./actions/setup-and-test     # 像使用其他 Action 一样调用
    with:
      node-version: '18'
      test-command: 'npm run test:coverage'
```

## JavaScript Action 开发全流程

这是最常用的自定义 Action 类型。让我们从零开始，构建一个"自动生成 Changelog"的 Action。

**第一步：创建项目结构**

```
my-changelog-action/
├── action.yml            # Action 的"身份证"——定义输入输出和入口
├── index.js              # 主逻辑文件
├── dist/                 # 打包后的文件（使用 ncc 打包）
│   └── index.js
├── package.json
├── node_modules/
└── README.md
```

**第二步：定义 action.yml**

```yaml
# action.yml —— Action 的元数据定义文件
name: 'Auto Changelog Generator'
description: '根据 Git 提交记录自动生成 Changelog'
author: 'Your Name'

# 定义图标和颜色（在 Marketplace 上展示用）
branding:
  icon: 'file-text'
  color: 'blue'

inputs:
  token:
    description: 'GitHub Token，用于访问 API'
    required: true
    default: ${{ github.token }}       # 默认使用内置的 GITHUB_TOKEN
  from-tag:
    description: '起始标签（不指定则从上一个 tag 开始）'
    required: false
    default: ''
  to-tag:
    description: '结束标签（不指定则到 HEAD）'
    required: false
    default: 'HEAD'
  output-file:
    description: '输出文件路径'
    required: false
    default: 'CHANGELOG.md'
  format:
    description: '输出格式：markdown 或 json'
    required: false
    default: 'markdown'

outputs:
  changelog:
    description: '生成的 Changelog 内容'
  file-path:
    description: '输出文件的完整路径'
  commit-count:
    description: '包含的提交数量'

runs:
  using: 'node20'                      # 使用 Node.js 20 运行时
  main: 'dist/index.js'                # 入口文件（打包后的）
```

**第三步：编写 index.js**

```javascript
// index.js
// @actions/core 提供了与 Workflow 引擎交互的标准接口
// @actions/github 提供了 GitHub API 的封装（基于 Octokit）

const core = require('@actions/core');
const github = require('@actions/github');

async function run() {
  try {
    // 1. 读取输入参数（对应 action.yml 中定义的 inputs）
    const token = core.getInput('token', { required: true });
    const fromTag = core.getInput('from-tag');
    const toTag = core.getInput('to-tag') || 'HEAD';
    const outputFile = core.getInput('output-file') || 'CHANGELOG.md';
    const format = core.getInput('format') || 'markdown';

    // 打印调试信息（只有在启用 debug 模式时才可见）
    core.debug(`参数: fromTag=${fromTag}, toTag=${toTag}, format=${format}`);

    // 2. 使用 @actions/github 创建 Octokit 客户端
    const octokit = github.getOctokit(token);
    const { owner, repo } = github.context.repo;
    // github.context 包含当前运行的上下文信息：
    // - repo: { owner, repo }  当前仓库
    // - sha: 当前 commit SHA
    // - ref: 当前分支/tag 引用
    // - eventName: 触发事件名

    // 3. 获取两个 tag 之间的 commits
    core.info('正在获取提交记录...');    // info 级别的日志会在运行时显示
    core.startGroup('获取 Commits');    // 在日志中创建一个可折叠的分组

    let commits;
    if (fromTag) {
      // 比较两个 tag 之间的差异
      const comparison = await octokit.rest.repos.compareCommits({
        owner,
        repo,
        base: fromTag,
        head: toTag,
      });
      commits = comparison.data.commits;
    } else {
      // 获取最近的提交
      const response = await octokit.rest.repos.listCommits({
        owner,
        repo,
        per_page: 50,
      });
      commits = response.data;
    }

    core.endGroup();                    // 结束分组
    core.info(`找到 ${commits.length} 条提交记录`);

    // 4. 按类型分类提交（类似 conventional-changelog）
    const categories = {
      'Features': [],                   // feat: 新功能
      'Bug Fixes': [],                  // fix: 修复
      'Documentation': [],              // docs: 文档
      'Refactoring': [],                // refactor: 重构
      'Other': [],                      // 其他
    };

    for (const commit of commits) {
      const message = commit.commit.message;
      const sha = commit.sha.substring(0, 7);  // 短 SHA
      const entry = `- ${message} (${sha})`;

      if (message.startsWith('feat')) {
        categories['Features'].push(entry);
      } else if (message.startsWith('fix')) {
        categories['Bug Fixes'].push(entry);
      } else if (message.startsWith('docs')) {
        categories['Documentation'].push(entry);
      } else if (message.startsWith('refactor')) {
        categories['Refactoring'].push(entry);
      } else {
        categories['Other'].push(entry);
      }
    }

    // 5. 生成 Changelog 内容
    let changelog = `# Changelog\n\n`;
    const date = new Date().toISOString().split('T')[0];
    changelog += `## [${toTag}] - ${date}\n\n`;

    for (const [category, entries] of Object.entries(categories)) {
      if (entries.length > 0) {
        changelog += `## ${category}\n\n`;
        changelog += entries.join('\n') + '\n\n';
      }
    }

    // 6. 写入文件
    const fs = require('fs');
    fs.writeFileSync(outputFile, changelog);
    core.info(`Changelog 已写入 ${outputFile}`);

    // 7. 设置输出（对应 action.yml 中定义的 outputs）
    core.setOutput('changelog', changelog);
    core.setOutput('file-path', outputFile);
    core.setOutput('commit-count', commits.length.toString());

    // 8. 添加 Workflow Summary（运行结束后在 GitHub UI 上展示）
    await core.summary
      .addHeading('📝 Changelog 生成报告')
      .addTable([
        [
          { data: '类别', header: true },
          { data: '数量', header: true },
        ],
        ...Object.entries(categories)
          .filter(([, entries]) => entries.length > 0)
          .map(([cat, entries]) => [cat, entries.length.toString()]),
      ])
      .write();

  } catch (error) {
    // 标记 Action 为失败状态
    core.setFailed(`Action 执行失败: ${error.message}`);
    // core.setFailed 会：
    // 1. 打印错误信息到日志
    // 2. 将 exit code 设为 1
    // 3. 将 Workflow Step 标记为失败
  }
}

run();
```

**第四步：打包（使用 @vercel/ncc）**

```json
// package.json
{
  "name": "auto-changelog-action",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "build": "ncc build index.js --license licenses.txt",
    "test": "jest"
  },
  "dependencies": {
    "@actions/core": "^1.10.0",
    "@actions/github": "^6.0.0"
  },
  "devDependencies": {
    "@vercel/ncc": "^0.38.0",
    "jest": "^29.0.0"
  }
}
```

```bash
# 安装依赖
npm install

# 打包：ncc 会把 index.js 和所有依赖打包成一个文件
# 这样运行 Action 时就不需要在 runner 上 npm install 了
npm run build

# dist/index.js 就是最终的入口文件
# action.yml 中的 main 字段指向的就是它
```

> **为什么要打包？** 因为 GitHub Actions 运行 JavaScript Action 时，不会自动执行 `npm install`。打包后，所有的依赖都内联到 `dist/index.js` 中，实现"零安装"运行。

**第五步：发布和使用**

```yaml
# 在你的项目 Workflow 中使用
steps:
  - uses: actions/checkout@v4
    with:
      fetch-depth: 0    # 需要完整的 Git 历史来生成 Changelog

  - name: 生成 Changelog
    uses: your-username/auto-changelog-action@v1
    # 如果是私有仓库中的 Action：
    # uses: your-username/auto-changelog-action@v1
    # 需要确保 GITHUB_TOKEN 有访问权限
    with:
      from-tag: 'v1.0.0'
      to-tag: 'v1.1.0'
      output-file: 'CHANGELOG.md'
      format: 'markdown'

  - name: 提交 Changelog
    run: |
      git config user.name "github-actions[bot]"
      git config user.email "github-actions[bot]@users.noreply.github.com"
      git add CHANGELOG.md
      git commit -m "docs: update changelog for v1.1.0"
      git push
```

## @actions/core 核心 API 速查

```javascript
const core = require('@actions/core');

// ===== 输入/输出 =====
core.getInput('param-name');           // 获取输入参数（字符串）
core.getBooleanInput('flag');          // 获取布尔输入
core.getMultilineInput('list');        // 获取多行输入（返回数组）
core.setOutput('key', 'value');        // 设置输出参数

// ===== 日志 =====
core.info('普通信息');                   // 普通日志
core.warning('警告信息');                // ⚠️ 黄色警告
core.error('错误信息');                  // ❌ 红色错误
core.debug('调试信息');                  // 🔍 仅 debug 模式可见
core.notice('通知');                     // 显示在 Annotations 中
core.startGroup('分组名');              // 创建可折叠日志组
core.endGroup();                         // 结束日志组

// ===== 状态管理 =====
core.setFailed('出错了');               // 标记 Step 失败
core.saveState('key', 'value');         // 保存状态（Post Step 可读取）
core.getState('key');                   // 读取状态

// ===== 环境变量和路径 =====
core.exportVariable('NAME', 'value');   // 设置环境变量（后续 Step 可用）
core.addPath('/usr/local/bin');         // 添加到 PATH

// ===== 其他 =====
core.isDebug();                         // 是否启用了 debug 模式
core.toPosixPath('C:\\path\\to');       // 路径格式转换
```

## Docker Action 基础

当你的 Action 需要特定的运行环境（比如 Python、Go、或者一个特定的 CLI 工具），Docker Action 是你的选择：

```yaml
# action.yml
name: 'Python Linter Action'
description: '使用 Python 工具进行代码检查'

inputs:
  python-version:
    description: 'Python 版本'
    required: false
    default: '3.11'
  check-path:
    description: '要检查的路径'
    required: false
    default: '.'

runs:
  using: 'docker'                       # 声明这是 Docker Action
  image: 'Dockerfile'                   # 使用本地 Dockerfile
  # image: 'docker://python:3.11'      # 或者直接使用 Docker Hub 上的镜像
  args:                                 # 传给容器的参数
    - ${{ inputs.check-path }}
  env:
    PYTHON_VERSION: ${{ inputs.python-version }}
```

```dockerfile
# Dockerfile
FROM python:3.11-slim

# 安装你需要的工具
RUN pip install flake8 black mypy

# 复制入口脚本
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

ENTRYPOINT ["/entrypoint.sh"]
```

```bash
#!/bin/bash
# entrypoint.sh

CHECK_PATH=$1

echo "🔍 检查路径: $CHECK_PATH"

# 运行 flake8
flake8 "$CHECK_PATH" --max-line-length=120
FLAKE8_EXIT=$?

# 运行 black（仅检查，不修改）
black --check "$CHECK_PATH"
BLACK_EXIT=$?

# 运行 mypy
mypy "$CHECK_PATH"
MYPY_EXIT=$?

# 汇总结果
if [ $FLAKE8_EXIT -ne 0 ] || [ $BLACK_EXIT -ne 0 ] || [ $MYPY_EXIT -ne 0 ]; then
  echo "::error::代码检查未通过"
  exit 1
fi

echo "✅ 所有检查通过！"
```

> **Docker Action 的缺点**：每次运行都需要构建 Docker 镜像（除非你预构建好并推到 Docker Hub），这会显著增加运行时间。所以对于能用 JavaScript 或 Composite 实现的场景，不推荐用 Docker。

## 测试和版本管理策略

**测试你的 Action**：

```javascript

// Mock @actions/core

        }),
      },
    },
```

**版本管理策略**：

发布自定义 Action 时，推荐遵循语义化版本，并维护一个浮动的 Major 标签：

```bash
# 发布 v1.0.0
git tag v1.0.0
git push origin v1.0.0

# 同时创建/更新浮动的 v1 标签
# 这样用户可以用 @v1 来引用，自动获取最新的 v1.x.x
git tag -f v1
git push origin -f v1

# 当有破坏性变更时，发布 v2.0.0
git tag v2.0.0
git push origin v2.0.0
git tag -f v2
git push origin -f v2
# v1 标签保持不变，使用 @v1 的用户不受影响
```

用户引用的三种方式：

```yaml
# 方式1：引用 Major 版本（推荐——自动获取兼容更新）
uses: your-username/your-action@v1

# 方式2：引用精确版本（最安全——但需要手动更新）
uses: your-username/your-action@v1.2.3

# 方式3：引用分支（开发阶段用——生产环境别这么做）
uses: your-username/your-action@main
```

## 小结

自定义 Action 是 GitHub Actions 生态的精髓——它让你从"使用者"变成了"贡献者"。

选择哪种 Action 类型的决策框架：

1. **Composite Action**：你只是想把几个步骤打包，不涉及复杂逻辑。写个 `action.yml` 就完事。
2. **JavaScript Action**：你需要和 GitHub API 交互、处理复杂数据、做条件判断。用 `@actions/core` 和 `@actions/github` 写起来很顺手。
3. **Docker Action**：你的工具需要特定的运行环境（Python/Go/Rust CLI 等），JavaScript 搞不定。

无论选择哪种，都请遵循这些最佳实践：

- 写好 `action.yml` 中的 `description`，帮助别人（和你自己）在 Marketplace 上找到它
- 用 ncc 打包 JavaScript Action，确保零依赖运行
- 用浮动 Major 标签管理版本，让用户安全地获取更新
- 写测试！Action 也是代码，也需要测试

## 练习题

1. **基础题**：创建一个 Composite Action，封装"checkout + setup-node + npm ci + npm test"四个步骤，支持 `node-version` 输入参数。
2. **进阶题**：创建一个 JavaScript Action，读取 PR 的描述，检查是否包含 `## Testing` 章节，如果没有则自动添加一条评论提醒作者补充测试说明。
3. **挑战题**：创建一个 Docker Action，使用 `hadolint` 工具检查项目中的所有 Dockerfile 是否符合最佳实践，并将检查结果输出为 GitHub Annotations（直接在 PR 的 diff 视图中显示问题）。
