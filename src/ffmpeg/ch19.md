## 19.1 为什么需要流媒体

先搞清楚一个根本问题：**下载**和**流式传输**到底有什么区别？

**下载模式**：你必须把整个文件下载完，才能开始观看。就像你买了一整本书，必须等快递送到才能翻开第一页。

**流式传输**：数据像自来水一样"流"过来，边下载边播放。你打开水龙头就有水喝，不用等整个水库灌满。

更本质的区别在于：

| 特性 | 下载模式 | 流式传输 |
| ------ | ---------- | ---------- |
| 播放时机 | 下载完成后 | 几乎即时 |
| 存储需求 | 需要完整存储空间 | 只需缓存少量数据 |
| 带宽利用 | 一次性占满带宽 | 按需持续占用 |
| 交互性 | 无（单向传输） | 支持实时交互（弹幕、连麦） |
| 内容保护 | 文件易被复制 | 可以做加密和 DRM |

想象一个场景：你要做一场万人在线的直播。如果用下载模式，每个人都要等你录完才能看——那不叫直播，那叫"发布会录像"。流媒体协议的存在，就是为了让音视频数据能够实时、高效、可靠地传输到每一个终端。

## 19.2 流媒体协议全景图

在深入细节之前，先看看流媒体世界的"家族谱"：

```
流媒体协议
├── 基于 TCP/UDP 的传统协议
│   ├── RTMP（Adobe/Flash 时代）
│   ├── RTSP + RTP（监控/会议）
│   └── RTCP（控制通道）
├── 基于 HTTP 的现代协议
│   ├── HLS（Apple 主导，最主流）
│   ├── DASH（开放标准）
│   └── HDS（Adobe，已淘汰）
├── 新兴低延迟协议
│   ├── SRT（Haivision 开源）
│   ├── WebRTC（浏览器原生）
│   └── RIST（广播级）
└── 私有协议
    ├── QUIC-based（各大厂自研）
    └── 各类"魔改"协议
```

别被这个树状图吓到。实际工作中，你最常用到的就是 RTMP（推流用）、HLS（分发用）、SRT（低延迟传输用）。下面我们逐一击破。

## 19.3 RTMP：Flash 时代的遗产

**RTMP（Real-Time Messaging Protocol）** 是 Adobe 在 Flash 时代搞出来的协议。虽然 Flash 已经进了历史的垃圾堆，但 RTMP 至今仍是直播推流的事实标准——几乎所有直播平台都支持 RTMP 推流。

**工作流程：**

```
推流端                    RTMP服务器                   播放端
  │                          │                          │
  │─── TCP 三次握手 ────────→│                          │
  │─── RTMP 握手 ──────────→│                          │
  │←── 握手响应 ────────────│                          │
  │─── connect("live") ────→│                          │
  │─── publish("stream") ──→│                          │
  │─── 音视频数据流 ───────→│                          │
  │                          │←── play("stream") ──────│
  │                          │─── 音视频数据流 ──────→│
```

**握手过程**（对，RTMP 也要握手）：

1. **C0/S0**：交换版本号（1字节）
2. **C1/S1**：交换时间戳和随机数据（1536字节）
3. **C2/S2**：回显对方的 C1/S1 数据

握手完成后，客户端发送 `connect` 命令连接到应用（通常是 `live`），然后通过 `publish` 命令发布流，或通过 `play` 命令播放流。

**优点：**

- 延迟低（通常 1-3 秒）
- 几乎所有直播平台都支持
- FFmpeg 原生支持，用起来简单

**缺点：**

- 基于 TCP，网络差时延迟会飙升（TCP 队头阻塞）
- 浏览器已不支持（没有 Flash 播放器了）
- 加密支持有限（RTMPS 只是套了个 TLS）
- 不适合大规模分发（需要长连接）

**RTMP 的消息分块机制：**

RTMP 把数据分成"消息"（Message），每个消息再分成"块"（Chunk）。默认块大小是 128 字节，但可以通过 `chunk_size` 参数调整：

```
一个视频帧（假设 10KB）
├── Chunk 1: 128 bytes + Chunk Header
├── Chunk 2: 128 bytes + Chunk Header
├── Chunk 3: 128 bytes + Chunk Header
├── ...
└── Chunk N: 剩余 bytes + Chunk Header
```

为什么要分块？因为 RTMP 需要在一条 TCP 连接上同时传输音视频数据和控制消息。分块后可以交错传输，避免一个大视频帧阻塞住控制消息。

**RTMP 的变种协议：**

- **RTMP**：原始版本，明文传输，端口 1935
- **RTMPS**：RTMP over TLS/SSL，加密传输，端口 443
- **RTMPE**：Adobe 私有加密（已过时）
- **RTMPT**：RTMP over HTTP，穿透防火墙用（已过时）

```bash
# RTMPS 推流（加密传输）
ffmpeg -re -i input.mp4 -c copy -f flv rtmps://server:443/live/stream

# RTMP 推流带认证
ffmpeg -re -i input.mp4 -c copy -f flv "rtmp://server/live/stream?user=admin&pass=secret"
```

FFmpeg 中更完整的 RTMP 使用场景：

```bash
# 推流到 RTMP 服务器（不转码，直接复制流）
ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream

# 推流时转码为 720p
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 1500k -s 1280x720 \
  -c:a aac -b:a 96k \
  -f flv rtmp://server/live/stream_720p

# 从 RTMP 服务器拉流并保存
ffmpeg -i rtmp://server/live/stream -c copy output.mp4

# 从 RTMP 拉流并实时播放（输出到 SDL/屏幕）
ffplay rtmp://server/live/stream
```

## 19.4 HLS：当今最主流的协议

**HLS（HTTP Live Streaming）** 是 Apple 在 2009 年推出的流媒体协议。为什么它能成为主流？因为它聪明地利用了 HTTP 基础设施——CDN、缓存、防火墙穿透，全都开箱即用。

**核心工作原理：**

```
                    ┌─────────────────────┐
                    │   m3u8 索引文件      │
                    │  (播放列表)          │
                    └────────┬────────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
        ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
        │ segment0  │ │ segment1  │ │ segment2  │
        │   .ts     │ │   .ts     │ │   .ts     │
        │ (10秒)    │ │ (10秒)    │ │ (10秒)    │
        └───────────┘ └───────────┘ └───────────┘
```

HLS 把视频切成一个个小片段（`.ts` 文件），然后用一个索引文件（`.m3u8`）把这些片段串起来。播放器下载 m3u8，按照列表顺序下载 ts 片段并播放。

**m3u8 文件示例：**

```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:10
#EXT-X-MEDIA-SEQUENCE:0
#EXTINF:10.0,
segment000.ts
#EXTINF:10.0,
segment001.ts
#EXTINF:8.5,
segment002.ts
#EXT-X-ENDLIST
```

- `#EXT-X-TARGETDURATION`：每个片段的目标时长（秒）
- `#EXTINF`：实际片段时长
- `#EXT-X-MEDIA-SEQUENCE`：第一个片段的序号
- `#EXT-X-ENDLIST`：表示直播结束（点播必须有，直播中没有它表示还在持续）

**延迟特点：**

- 标准 HLS 延迟：10-30 秒（需要缓冲 3 个片段）
- Low-Latency HLS (LL-HLS)：2-5 秒（Apple 在 2020 年推出）

LL-HLS 通过引入**部分片段（Partial Segments）**和**阻塞式播放列表重载**来降低延迟。我们会在 22 章深入讲解。

**优点：**

- 基于 HTTP，天然适配 CDN
- 支持自适应码率（ABR）
- iOS/Android 原生支持
- 可以做 AES-128 加密
- 生态成熟，工具链完善

**缺点：**

- 延迟较高（标准模式）
- 切片产生大量小文件，对存储和文件系统有压力

FFmpeg 生成 HLS：

```bash
ffmpeg -i input.mp4 \
  -c:v libx264 -c:a aac \
  -hls_time 10 \
  -hls_list_size 0 \
  -hls_segment_filename "segment%03d.ts" \
  output.m3u8
```

## 19.5 DASH：开放标准版 HLS

**DASH（Dynamic Adaptive Streaming over HTTP）** 是 MPEG 组织制定的国际标准（ISO/IEC 23009-1）。可以把它理解为"非 Apple 版的 HLS"——理念相同，但格式不同。

DASH 使用 **MPD（Media Presentation Description）** 文件来描述媒体信息，类似 HLS 的 m3u8，但是 XML 格式：

```xml
<?xml version="1.0"?>
<MPD xmlns="urn:mpeg:dash:schema:mpd:2011" type="static"
     mediaPresentationDuration="PT5M">
  <Period>
    <AdaptationSet mimeType="video/mp4">
      <Representation id="1" bandwidth="500000" width="640" height="360">
        <BaseURL>video_360p.mp4</BaseURL>
        <SegmentBase indexRange="674-1149">
          <Initialization range="0-673"/>
        </SegmentBase>
      </Representation>
      <Representation id="2" bandwidth="1500000" width="1280" height="720">
        <BaseURL>video_720p.mp4</BaseURL>
      </Representation>
    </AdaptationSet>
    <AdaptationSet mimeType="audio/mp4">
      <Representation id="3" bandwidth="128000">
        <BaseURL>audio.mp4</BaseURL>
      </Representation>
    </AdaptationSet>
  </Period>
</MPD>
```

**HLS vs DASH 对比：**

| 特性 | HLS | DASH |
| ------ | ----- | ------ |
| 发起者 | Apple | MPEG（开放标准） |
| 索引文件 | m3u8 (文本) | MPD (XML) |
| 片段格式 | TS / fMP4 | fMP4 |
| iOS 原生支持 | 是 | 否（需第三方库） |
| Android 原生支持 | 部分 | 是（ExoPlayer） |
| DRM | FairPlay | Widevine/PlayReady |
| 编码无关 | 较新标准才支持 | 天然支持 |

FFmpeg 生成 DASH：

```bash
ffmpeg -i input.mp4 \
  -c:v libx264 -c:a aac \
  -f dash \
  -seg_duration 10 \
  -use_template 1 \
  -use_timeline 1 \
  output.mpd
```

## 19.6 SRT：低延迟的新星

**SRT（Secure Reliable Transport）** 是 Haivision 在 2017 年开源的传输协议。它的目标很明确：**在不可靠的网络上实现低延迟、高可靠的音视频传输**。

SRT 的杀手锏是它的**抗丢包机制**：

```
发送端                      网络                        接收端
  │                          │                          │
  │─── 包 1 ────────────────→│──→ 包 1 ───────────────→│ ✓
  │─── 包 2 ────────────────→│ ✗  包 2 丢了!           │
  │─── 包 3 ────────────────→│──→ 包 3 ───────────────→│ ✓
  │                          │                          │
  │←── NAK: 包 2 丢了 ──────│←─────────────────────────│
  │─── 重传包 2 ────────────→│──→ 包 2 ───────────────→│ ✓
  │                          │                          │
  │   接收端缓冲区重组: [包1, 包2, 包3] → 按序播放       │
```

核心机制：

- **ARQ（自动重传请求）**：丢了包？我重传给你
- **FEC（前向纠错）**：额外发送冗余数据，丢包后可以用算法恢复
- **拥塞控制**：根据网络状况动态调整发送速率
- **AES 加密**：支持 128/192/256 位加密

FFmpeg 中使用 SRT：

```bash
# SRT 推流（Listener 模式，等待对方连接）
ffmpeg -re -i input.mp4 -c copy -f mpegts \
  "srt://:9000?mode=listener&latency=200000"

# SRT 推流（Caller 模式，主动连接）
ffmpeg -re -i input.mp4 -c copy -f mpegts \
  "srt://remote-server:9000?mode=caller&latency=200000"

# SRT 拉流
ffmpeg -i "srt://server:9000?mode=caller" -c copy output.mp4
```

注意 `latency` 参数的单位是**微秒**，200000 微秒 = 200 毫秒。这个值需要根据网络状况调整——网络越差，需要的延迟缓冲越大。

## 19.7 RTSP：监控领域的常青树

**RTSP（Real-Time Streaming Protocol）** 是一个"老家伙"了。它主要用于 IP 摄像头和视频会议系统。你家小区的监控摄像头，十有八九用的是 RTSP。

RTSP 本身只负责"控制"（播放、暂停、停止），实际的数据传输靠 **RTP（Real-time Transport Protocol）** 来完成：

```
客户端                         RTSP 服务器
  │                               │
  │── DESCRIBE rtsp://cam/1 ────→│  "这个流有什么？"
  │←────── SDP 描述 ────────────│  "H.264 视频 + AAC 音频"
  │                               │
  │── SETUP (视频轨道) ─────────→│  "我要接收视频，用 RTP 端口 5000"
  │←────── 200 OK ──────────────│  "好的，我发到你的 5000 端口"
  │                               │
  │── PLAY ──────────────────────→│  "开始播放"
  │←────── 200 OK ──────────────│
  │                               │
  │←════ RTP 视频数据流 ════════│  (通过 UDP/TCP 传输)
  │                               │
  │── TEARDOWN ─────────────────→│  "停止播放"
```

RTSP 地址格式通常是这样的：

```
rtsp://admin:password@192.168.1.100:554/stream1
rtsp://192.168.1.100:554/h264/ch1/main/av_stream
```

FFmpeg 中使用 RTSP：

```bash
# 从 RTSP 摄像头拉流并录制
ffmpeg -i "rtsp://admin:pass@192.168.1.100:554/stream1" \
  -c copy camera_record.mp4

# RTSP 转 RTMP 推流（让监控画面在网页上播放）
ffmpeg -i "rtsp://camera/stream1" \
  -c:v libx264 -c:a aac \
  -f flv rtmp://server/live/camera1

# 强制使用 TCP 传输（解决 UDP 丢包问题）
ffmpeg -rtsp_transport tcp \
  -i "rtsp://camera/stream1" \
  -c copy output.mp4
```

> **提示**：RTSP 默认使用 UDP 传输 RTP 数据，网络不好时容易花屏。加上 `-rtsp_transport tcp` 可以强制使用 TCP，虽然延迟可能略高，但画面更稳定。

## 19.8 协议对比与选型指南

一张表总结所有协议：

| 协议 | 延迟 | 传输方式 | 浏览器兼容 | CDN 友好 | 主要场景 |
| ------ | ------ | ---------- | ------------ | ---------- | ---------- |
| RTMP | 1-3s | TCP | 不支持 | 不友好 | 推流（编码器→服务器） |
| HLS | 10-30s | HTTP | 大部分 | 非常友好 | 大规模直播/点播分发 |
| LL-HLS | 2-5s | HTTP | 大部分 | 友好 | 低延迟直播 |
| DASH | 10-30s | HTTP | 需JS库 | 非常友好 | Android/Web 分发 |
| SRT | <1s | UDP | 不支持 | 不友好 | 专业传输（电视台/远程制作） |
| RTSP | 1-2s | UDP/TCP | 不支持 | 不友好 | 监控摄像头/视频会议 |
| WebRTC | <0.5s | UDP | 原生支持 | 不友好 | 连麦/视频会议/互动直播 |

**选型建议：**

- **做直播平台**：RTMP 推流 + HLS 分发（经典组合）
- **做视频点播**：HLS 或 DASH（配合 CDN）
- **做监控系统**：RTSP 拉流 + 转码分发
- **做远程制作**：SRT（跨地域传输）
- **做互动直播**：WebRTC（连麦）+ RTMP（普通观众）

## 19.9 WebRTC：实时通信的未来

虽然 FFmpeg 对 WebRTC 的支持有限，但作为流媒体从业者，你不能不了解它。

**WebRTC（Web Real-Time Communication）** 是浏览器原生的实时通信协议。它的延迟可以做到 100 毫秒以内——这意味着两个人可以在网页上"面对面"对话，几乎感觉不到延迟。

```
传统直播架构（RTMP → 转码 → HLS）：延迟 5-30 秒
WebRTC 架构（P2P 或 SFU）：延迟 < 0.5 秒
```

**WebRTC 的核心组件：**

- **ICE（Interactive Connectivity Establishment）**：找到两个终端之间的最佳通信路径
- **STUN（Session Traversal Utilities for NAT）**：帮你发现自己在 NAT 后面的公网地址
- **TURN（Traversal Using Relays around NAT）**：当 P2P 不通时，用中继服务器转发
- **DTLS（Datagram Transport Layer Security）**：加密所有数据
- **SRTP（Secure Real-time Transport Protocol）**：加密音视频流

**WebRTC 在直播中的角色：**

典型的互动直播架构是"WebRTC 互动 + HLS 观看"：

```
主播（WebRTC推流）──→ SFU 服务器 ──→ 连麦观众（WebRTC）
                        │
                        └──→ 转码 ──→ HLS ──→ 普通观众（数十万）
```

- 连麦的主播和嘉宾用 WebRTC（超低延迟）
- 普通观众用 HLS（CDN 分发，成本更低）

主流开源 WebRTC 服务器：

- **Janus**：通用 WebRTC 网关
- **mediasoup**：Node.js 的 SFU 框架
- **Pion**：Go 语言的 WebRTC 库
- **SRS 5.0**：已支持 WebRTC 推流和播放

## 19.10 自适应码率（ABR）的概念

**ABR（Adaptive Bitrate）** 是流媒体最重要的技术之一。它的思想很简单：**根据用户的网速，自动切换视频质量**。

```
用户网速 10Mbps  ──→  播放 1080p（8Mbps）
用户网速 3Mbps   ──→  播放 720p（2Mbps）
用户网速 500Kbps ──→  播放 360p（400Kbps）
```

实现方式：

1. 编码器把同一个视频编码成多个码率版本
2. 服务器同时提供多个码率的切片
3. m3u8/MPD 文件描述所有可用的码率
4. 播放器根据网络状况自动选择

HLS 多码率的 Master Playlist：

```
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=400000,RESOLUTION=640x360
low/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1500000,RESOLUTION=1280x720
mid/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=4000000,RESOLUTION=1920x1080
high/index.m3u8
```

FFmpeg 生成多码率 HLS：

```bash
ffmpeg -i input.mp4 \
  -map 0:v -map 0:v -map 0:v -map 0:a \
  -c:v libx264 -c:a aac \
  -b:v:0 400k -s:v:0 640x360 \
  -b:v:1 1500k -s:v:1 1280x720 \
  -b:v:2 4000k -s:v:2 1920x1080 \
  -f hls \
  -hls_time 6 \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0,a:0 v:1,a:0 v:2,a:0" \
  "vs%v/index.m3u8"
```

这条命令会生成：

- `master.m3u8`：主播放列表
- `vs0/index.m3u8`：360p 的切片列表
- `vs1/index.m3u8`：720p 的切片列表
- `vs2/index.m3u8`：1080p 的切片列表

**码率阶梯推荐：**

不同内容类型需要不同的码率阶梯。静态内容（PPT、屏幕录制）可以用更低的码率，而动态内容（体育赛事、游戏直播）需要更高的码率：

| 分辨率 | 静态内容码率 | 普通内容码率 | 动态内容码率 |
| -------- | ------------- | ------------- | ------------- |
| 2160p (4K) | 8-12 Mbps | 15-20 Mbps | 25-35 Mbps |
| 1080p | 3-5 Mbps | 5-8 Mbps | 8-12 Mbps |
| 720p | 1.5-2.5 Mbps | 2.5-4 Mbps | 4-6 Mbps |
| 480p | 0.8-1.2 Mbps | 1.2-2 Mbps | 2-3 Mbps |
| 360p | 0.4-0.6 Mbps | 0.6-1 Mbps | 1-1.5 Mbps |
| 240p | 0.2-0.3 Mbps | 0.3-0.5 Mbps | 0.5-0.8 Mbps |

**ABR 的编码策略：**

编码多码率变体有两种方式：

1. **独立编码**：每个码率独立编码一次。简单但慢，且无法做帧级对齐
2. **阶梯式编码（Ladder Encoding）**：使用 `x264` 的 `--vbv-maxrate` 和 `--vbv-bufsize` 精细控制

```bash
# 独立编码（简单但慢）
for bitrate in 500k 1500k 4000k; do
    ffmpeg -i input.mp4 -c:v libx264 -b:v $bitrate \
        -c:a aac -b:a 128k "output_${bitrate}.mp4"
done

# 更聪明的方式：一次编码出多码率（利用 -map）
ffmpeg -i input.mp4 \
  -map 0:v -map 0:v -map 0:v \
  -c:v:0 libx264 -b:v:0 4000k -s:v:0 1920x1080 \
  -c:v:1 libx264 -b:v:1 1500k -s:v:1 1280x720 \
  -c:v:2 libx264 -b:v:2 500k -s:v:2 640x360 \
  -c:a aac -b:a 128k \
  -f hls \
  -master_pl_name master.m3u8 \
  -var_stream_map "v:0 v:1 v:2" \
  "vs%v/index.m3u8"
```

**客户端 ABR 算法简介：**

播放器是怎么决定用哪个码率的？常见的算法有：

- **吞吐量估算法**：测量下载速度，选择低于当前网速 80% 的码率（保守策略）
- **缓冲区占用法（BBA）**：根据缓冲区充盈程度调整码率
- **混合策略（MPC）**：结合吞吐量和缓冲区，使用模型预测最优码率
- **强化学习（Pensieve）**：用机器学习自动学习最优策略（MIT 出品）

这些算法对内容开发者来说是透明的，但了解它们有助于你理解为什么有时候用户的画质会"跳动"——那不是 bug，是 ABR 在正常工作。

## 19.11 实际部署中的协议组合

在真实的生产环境中，你不会只用一种协议。典型的直播架构是这样的：

```
主播端（RTMP推流）
       │
       ▼
   源站服务器
       │
       ├── 转码集群（多码率）
       │      │
       │      ├── 1080p → HLS → CDN → 观众（高端设备）
       │      ├── 720p → HLS → CDN → 观众（中端设备）
       │      ├── 480p → HLS → CDN → 观众（低端设备）
       │      └── 360p → HLS → CDN → 观众（弱网环境）
       │
       ├── 录制服务 → 回放系统
       │
       └── 截图服务 → 封面图/审核
```

**各层协议选择的考量：**

- **推流层**（主播→服务器）：RTMP 是标配。虽然它老了，但所有推流软件（OBS、XSplit）和硬件编码器都支持它。如果你需要更低的推流延迟，可以用 SRT 或 WebRTC
- **转码层**（服务器内部）：FFmpeg 做转码。这一层不涉及网络协议，纯粹是把一路流变成多路不同码率的流
- **分发层**（服务器→观众）：HLS 是绝对主流。它基于 HTTP，天然适配 CDN，能覆盖 99% 的终端设备
- **录制层**：直接用 FFmpeg 录制 RTMP 流到 MP4 文件。如果要做回放，再把 MP4 转成 HLS 点播

**一个真实案例：**

假设你要搭建一个在线教育直播平台，需要支持以下功能：

1. 老师用 OBS 推流上课
2. 学生通过网页观看直播
3. 课后自动生成回放视频
4. 支持手机端和电脑端
5. 网络差时自动降低画质

技术选型：

- 推流：RTMP（OBS 原生支持）
- 服务器：SRS（开箱即用，支持 RTMP+HLS+录制）
- 分发：HLS 多码率（3 档：1080p/720p/480p）
- 回放：录制 MP4 → 转码 → HLS 点播
- 播放器：hls.js（自动 ABR）
- CDN：阿里云/腾讯云 CDN（国内分发）

整套方案下来，你需要的核心技术就是：RTMP 推流 + SRS 服务器 + HLS 切片 + CDN 分发 + FFmpeg 后处理。这些技术，你在这本书里全都学了。

## 本章小结

- **流媒体的本质**是"边下载边播放"，区别于传统下载模式
- **RTMP** 虽然老旧，但仍是推流的事实标准
- **HLS** 是目前最主流的分发协议，基于 HTTP，CDN 友好
- **DASH** 是 HLS 的开放标准替代方案
- **SRT** 是专业领域的低延迟传输利器
- **RTSP** 在监控领域仍然不可替代
- **ABR 自适应码率**是提升用户体验的关键技术
