## 21.1 生产环境 K8s 集群搭建

### 云服务商托管方案（推荐）

在生产环境中，几乎没有人自建 K8s 集群（除非你有专职的运维团队）。主流方案是使用云服务商的托管 K8s 服务：

| 云服务商 | 服务名称 | 特点 |
|---------|---------|------|
| AWS | EKS（Elastic Kubernetes Service） | 生态最丰富，与 AWS 服务深度集成 |
| GCP | GKE（Google Kubernetes Engine） | K8s 的亲儿子（Google 开发），体验最好 |
| Azure | AKS（Azure Kubernetes Service） | 企业友好，Windows 节点支持好 |
| 阿里云 | ACK（容器服务 Kubernetes 版） | 国内首选，中文文档完善 |
| 腾讯云 | TKE（容器服务） | 国内备选 |

```bash
自建集群 vs 托管集群：

自建集群：
- 你需要自己管理 Master 节点（etcd 备份、证书轮换、版本升级）
- 你需要自己处理高可用（多个 Master、负载均衡）
- 适合：对数据主权有严格要求的企业、学习目的

托管集群：
- 云服务商帮你管理 Master 节点（你甚至看不到它）
- 自动高可用、自动升级、自动备份 etcd
- 你只需要关注 Worker 节点和上面的应用
- 适合：99% 的团队
```


### 镜像预热

新节点加入集群时，拉取大镜像会导致 Pod 启动缓慢。解决方案：

```yaml
# DaemonSet 方式：在每个节点上预拉取镜像
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: image-prepull
spec:
  selector:
    matchLabels:
      app: image-prepull
  template:
    metadata:
      labels:
        app: image-prepull
    spec:
      initContainers:
      - name: prepull
        image: my-app:v1.2.3   # 要预拉的镜像
        command: ["sh", "-c", "echo Image pulled && exit 0"]
      containers:
      - name: pause
        image: registry.k8s.io/pause:3.9
```

## 21.3 资源配置：Requests vs Limits

这是 K8s 中最容易配错、也最重要的配置之一。

```bash
Requests（请求量）= 你向集群"预定"的资源
  → Scheduler 用它来决定 Pod 放在哪个节点
  → 节点必须保证有这么多资源才会接受 Pod

Limits（上限）= 你最多能用多少资源
  → CPU 超过 limit：被节流（throttle），变慢但不崩溃
  → 内存超过 limit：被 OOM Kill（直接杀死！）
```

```yaml
resources:
  requests:                      # 保底资源
    cpu: "200m"                  # 0.2 个 CPU 核心
    memory: "256Mi"              # 256 MB 内存
  limits:                        # 资源上限
    cpu: "1000m"                 # 1 个 CPU 核心
    memory: "512Mi"              # 512 MB 内存
```

**配置建议：**

```
如何确定 requests？
  → 在负载测试下观察实际使用的 P50（中位数）
  → requests 设为 P50 的 1.2-1.5 倍

如何确定 limits？
  → 观察实际使用的 P99（99 分位）
  → limits 设为 P99 的 1.5-2 倍
  → 内存 limits 不要设太低，OOM Kill 很痛

CPU vs 内存的区别：
  → CPU 是可压缩资源：超过 limit 只是变慢（被节流）
  → 内存是不可压缩资源：超过 limit 直接被杀（OOM Kill）
  → 所以：CPU limits 可以设宽松，内存 limits 要谨慎
```

> [!WARNING] 注意
> 不设 requests/limits 的 Pod 就像一个不写类型定义的 TypeScript 项目——能跑，但迟早出事。没有 requests，Scheduler 不知道节点是否还有资源，可能导致节点过载。没有 limits，一个内存泄漏的 Pod 可以把整个节点拖垮。

## 21.4 健康检查：三种 Probe

K8s 提供了三种探针来监控 Pod 的健康状态：

```yaml
containers:
- name: app
  image: my-app:v1.0

  # 1. Liveness Probe（存活探针）
  # "你还活着吗？" → 失败就重启 Pod
  livenessProbe:
    httpGet:
      path: /healthz            # 存活检查端点
      port: 3000
    initialDelaySeconds: 15     # 容器启动后等 15 秒才开始探测
    periodSeconds: 20           # 每 20 秒探测一次
    timeoutSeconds: 5           # 超时 5 秒算失败
    failureThreshold: 3         # 连续 3 次失败才判定为不存活
    successThreshold: 1         # 1 次成功就算存活

  # 2. Readiness Probe（就绪探针）
  # "你准备好接收流量了吗？" → 失败就从 Service 端点中移除
  readinessProbe:
    httpGet:
      path: /ready              # 就绪检查端点
      port: 3000
    initialDelaySeconds: 5
    periodSeconds: 5
    failureThreshold: 3

  # 3. Startup Probe（启动探针）
  # "你启动完了吗？" → 启动期间禁用其他探针
  # 适用于启动很慢的应用（如 Java Spring Boot 应用）
  startupProbe:
    httpGet:
      path: /healthz
      port: 3000
    initialDelaySeconds: 10
    periodSeconds: 5
    failureThreshold: 30        # 最多等 30 × 5 = 150 秒启动
    # startupProbe 成功后，liveness 和 readiness 才开始生效
```

**三种探针的区别：**

```bash
Startup Probe：
  ┌── 应用启动中 ──┐
  │                │
  启动探针失败      启动探针成功
  （继续等）        ↓
              Liveness + Readiness 开始生效

Liveness Probe：
  ┌── 应用运行中 ──┐
  │                │
  存活探针失败      存活探针成功
  （重启 Pod！）    （继续运行）

Readiness Probe：
  ┌── 应用运行中 ──┐
  │                │
  就绪探针失败      就绪探针成功
  （停止发流量）    （恢复发流量）
  （不重启 Pod！）
```

**健康检查端点的设计原则：**

```javascript
// Node.js Express 示例

// /healthz - Liveness 探针用
// 只检查应用进程本身是否正常（不要检查数据库！）
app.get('/healthz', (req, res) => {
  // 进程能执行到这里 = 还活着
  res.status(200).json({ status: 'ok' });
});

// /ready - Readiness 探针用
// 检查应用是否准备好接收流量（包括依赖）
app.get('/ready', async (req, res) => {
  try {
    // 检查数据库连接
    await db.testConnection();
    // 检查 Redis 连接
    await redis.ping();
    // 检查关键资源
    if (!isConfigLoaded()) {
      return res.status(503).json({ status: 'not ready', reason: 'config not loaded' });
    }
    res.status(200).json({ status: 'ready' });
  } catch (err) {
    res.status(503).json({ status: 'not ready', reason: err.message });
  }
});
```

> [!WARNING] 注意
> **不要在 Liveness Probe 中检查数据库连接！** 如果数据库临时不可用，所有 Pod 的 Liveness 都会失败，导致所有 Pod 同时被重启——等数据库恢复后，所有 Pod 又同时启动、同时请求数据库，形成"惊群效应"，可能再次压垮数据库。Liveness 只检查进程本身，Readiness 检查依赖。

## 21.5 优雅停机

当 K8s 要停止一个 Pod 时（滚动更新、缩容、节点维护），默认流程：

```bash
1. K8s 发送 SIGTERM 信号给容器进程
2. 等待 terminationGracePeriodSeconds（默认 30 秒）
3. 如果还没退出，发送 SIGKILL 强制杀死
```

问题是：如果你的应用收到 SIGTERM 后直接退出，正在处理的请求就会丢失。我们需要**优雅停机**：

```yaml
spec:
  terminationGracePeriodSeconds: 60  # 给应用 60 秒处理停机
  containers:
  - name: app
    image: my-app:v1.0
    lifecycle:
      preStop:
        exec:
          # 在 SIGTERM 之前执行（给 Ingress/Service 时间更新端点列表）
          command: ["sh", "-c", "sleep 5"]
```

```javascript
// Node.js 优雅停机实现
const server = app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});

// 正在处理的请求计数
let activeConnections = 0;

// 跟踪活跃连接
server.on('connection', (socket) => {
  activeConnections++;
  socket.on('close', () => activeConnections--);
});

// 优雅停机处理
function gracefulShutdown(signal) {
  console.log(`Received ${signal}. Starting graceful shutdown...`);

  // 1. 停止接受新连接
  server.close(() => {
    console.log('No more new connections accepted');

    // 2. 等待现有请求完成
    if (activeConnections === 0) {
      console.log('All requests completed. Exiting.');
      process.exit(0);
    } else {
      console.log(`Waiting for ${activeConnections} active connections...`);
    }
  });

  // 3. 设置强制退出超时（比 terminationGracePeriodSeconds 短几秒）
  setTimeout(() => {
    console.error('Forced shutdown: some connections did not close in time');
    process.exit(1);
  }, 55000);  // 55 秒（gracefulPeriod 是 60 秒）
}

process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));
```

```python
# Python Flask + Gunicorn 优雅停机
import signal
import sys

def graceful_shutdown(signum, frame):
    """优雅停机处理"""
    print(f"Received signal {signum}, shutting down gracefully...")
    # Gunicorn 会自动处理 SIGTERM：
    # 1. 停止接受新请求
    # 2. 等待当前请求完成
    # 3. 退出 worker 进程
    sys.exit(0)

signal.signal(signal.SIGTERM, graceful_shutdown)
```

> [!TIP] 提示
> `preStop: sleep 5` 看起来多此一举，但实际上非常重要。K8s 发送 SIGTERM 和更新 Service 端点列表（告诉 kube-proxy 不再往这个 Pod 发流量）是**同时**进行的。如果不 sleep 等待，在端点列表更新完成前，可能还有新请求被路由到正在关闭的 Pod。

## 21.6 Pod Disruption Budget（PDB）

PDB 保护你的应用在"自愿性中断"（节点维护、集群升级）期间仍然有足够的副本可用：

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  # 两种方式（选一个）：
  minAvailable: 2               # 始终至少 2 个 Pod 可用
  # maxUnavailable: 1           # 最多 1 个 Pod 不可用

  selector:
    matchLabels:
      app: api                  # 保护的 Pod
```

```bash
场景：你有 5 个 API Pod，PDB 设置 minAvailable: 3

节点维护时：
- K8s 一次驱逐 1 个 Pod → 剩余 4 个 → 满足 PDB → 允许
- 再次驱逐 1 个 → 剩余 3 个 → 满足 PDB → 允许
- 再次驱逐 1 个 → 剩余 2 个 → 不满足 PDB → 阻止！等待恢复

如果没有 PDB：
- K8s 可能同时驱逐多个 Pod，导致服务完全不可用
```

### 应用暴露自定义指标

```javascript
// Node.js：使用 prom-client 暴露 Prometheus 指标
const client = require('prom-client');

// 收集默认指标（内存、CPU 等）
client.collectDefaultMetrics();

// 自定义指标
const httpRequestDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Duration of HTTP requests in seconds',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 2, 5]
});

const activeConnections = new client.Gauge({
  name: 'active_connections',
  help: 'Number of active connections'
});

const requestCounter = new client.Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests',
  labelNames: ['method', 'route', 'status_code']
});

// Express 中间件
app.use((req, res, next) => {
  activeConnections.inc();
  const end = httpRequestDuration.startTimer();

  res.on('finish', () => {
    activeConnections.dec();
    end({ method: req.method, route: req.path, status_code: res.statusCode });
    requestCounter.inc({ method: req.method, route: req.path, status_code: res.statusCode });
  });

  next();
});

// /metrics 端点（Prometheus 会拉取这个端点）
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
```

## 21.9 告警：Alertmanager 配置

监控不告警 = 出了问题你不知道 = 用户先于你发现问题。

```yaml
# PrometheusRule：定义告警规则
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-alerts
  labels:
    release: monitoring
spec:
  groups:
  - name: api-alerts
    rules:
    # 高错误率告警
    - alert: HighErrorRate
      expr: |
        sum(rate(http_requests_total{status_code=~"5.."}[5m]))
        /
        sum(rate(http_requests_total[5m]))
        > 0.05
      for: 5m                    # 持续 5 分钟才告警（避免瞬间抖动误报）
      labels:
        severity: critical
      annotations:
        summary: "API 错误率超过 5%"
        description: "当前错误率: {{ $value | humanizePercentage }}"

    # Pod 重启告警
    - alert: PodCrashLooping
      expr: increase(kube_pod_container_status_restarts_total[1h]) > 3
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.pod }} 在过去 1 小时重启超过 3 次"

    # 磁盘空间告警
    - alert: DiskSpaceLow
      expr: |
        (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) < 0.1
      for: 10m
      labels:
        severity: warning
      annotations:
        summary: "节点 {{ $labels.node }} 磁盘空间不足 10%"

    # HPA 达到上限告警
    - alert: HPAMaxedOut
      expr: kube_horizontalpodautoscaler_status_current_replicas == kube_horizontalpodautoscaler_spec_max_replicas
      for: 15m
      labels:
        severity: warning
      annotations:
        summary: "HPA {{ $labels.horizontalpodautoscaler }} 已达到最大副本数上限"
```

## 21.10 灾备：备份与恢复

### etcd 备份与恢复

```bash
# etcd 是 K8s 的"大脑"——所有集群状态都存在这里
# 如果 etcd 数据丢失，整个集群就没了

# 备份 etcd（在 Master 节点上执行）
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot-$(date +%Y%m%d).db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
```

## 21.11 CI/CD + K8s 完整部署流水线

```bash
完整流水线：

代码提交 → CI 构建/测试 → 镜像构建/推送 → 更新 K8s 配置 → 部署

具体步骤：
┌─────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ Git Push │──▶│  CI:     │──▶│ Build &  │──▶│ Update   │──▶│ Deploy   │
│          │   │  Lint    │   │ Push     │   │ K8s YAML │   │ to K8s   │
│          │   │  Test    │   │ Image    │   │ (GitOps) │   │          │
└─────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

```yaml
# GitHub Actions 示例
name: Deploy to K8s
on:
  push:
    branches: [main]

env:
  REGISTRY: registry.example.com
  IMAGE_NAME: my-app

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    # 1. 代码检查
    - name: Lint
      run: npm run lint

    # 2. 单元测试
    - name: Test
      run: npm test

    # 3. 构建 Docker 镜像
    - name: Build Image
      run: |
        docker build -t $REGISTRY/$IMAGE_NAME:${{ github.sha }} .
        docker tag $REGISTRY/$IMAGE_NAME:${{ github.sha }} $REGISTRY/$IMAGE_NAME:latest

    # 4. 推送到私有仓库
    - name: Push Image
      run: |
        echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login $REGISTRY -u ${{ secrets.REGISTRY_USER }} --password-stdin
        docker push $REGISTRY/$IMAGE_NAME:${{ github.sha }}
        docker push $REGISTRY/$IMAGE_NAME:latest

    # 5. 更新 K8s 配置仓库（GitOps 方式）
    - name: Update K8s Manifest
      run: |
        git clone https://${{ secrets.GIT_TOKEN }}@github.com/myorg/k8s-configs.git
        cd k8s-configs
        # 更新镜像标签
        sed -i "s|image: $REGISTRY/$IMAGE_NAME:.*|image: $REGISTRY/$IMAGE_NAME:${{ github.sha }}|" overlays/production/deployment.yaml
        git config user.name "CI Bot"
        git config user.email "ci@example.com"
        git add .
        git commit -m "Update image to ${{ github.sha }}"
        git push

    # 6. ArgoCD 会自动检测 Git 变更并同步到集群
    # 如果需要手动部署（非 GitOps）：
    # - name: Deploy to K8s
    #   run: |
    #     kubectl set image deployment/my-app \
    #       app=$REGISTRY/$IMAGE_NAME:${{ github.sha }} \
    #       -n production
```

## 21.12 12-Factor App 原则与容器化

[12-Factor App](https://12factor.net/) 是构建现代化应用的十二条原则。容器化天然契合其中的大部分：

| 原则 | 说明 | 容器化实现 |
|------|------|-----------|
| **I. 基准代码** | 一份代码，多份部署 | 同一个镜像用于 dev/staging/prod |
| **II. 依赖** | 显式声明依赖 | `package.json` / `requirements.txt` + Dockerfile |
| **III. 配置** | 配置存储于环境中 | 环境变量 + ConfigMap + Secret |
| **IV. 后端服务** | 把后端服务当附加资源 | 通过 URL 连接，可随时替换 |
| **V. 构建/发布/运行** | 严格分离 | CI 构建镜像 → 推送仓库 → K8s 运行 |
| **VI. 无状态** | 进程无状态 | 多个 Pod 副本，数据存外部 |
| **VII. 端口绑定** | 应用自带 HTTP 服务 | 容器暴露端口 |
| **VIII. 并发** | 通过进程模型扩展 | K8s 多副本 + HPA |
| **IX. 易处理** | 快速启动和优雅终止 | 健康检查 + 优雅停机 |
| **X. 开发/生产一致** | 保持环境一致 | 同一个镜像，不同配置 |
| **XI. 日志** | 日志作为事件流 | 输出到 stdout，日志系统收集 |
| **XII. 管理进程** | 一次性任务作为独立进程 | K8s Job / CronJob |

## 21.13 生产 Checklist

部署到生产之前，逐项检查：

### 安全 ✓

- [ ] 容器不以 root 用户运行（`USER` 指令）
- [ ] 使用最小基础镜像（Alpine / Distroless）
- [ ] 镜像不含敏感信息（`.dockerignore` 配置正确）
- [ ] Secret 使用外部密钥管理（非明文 Base64）
- [ ] Network Policies 限制了 Pod 间通信
- [ ] RBAC 遵循最小权限原则
- [ ] 镜像来自可信仓库，使用固定版本标签
- [ ] 启用了 Pod Security Standards（`restricted` 级别）

### 可靠性 ✓

- [ ] Deployment 设置了 `replicas >= 2`
- [ ] 配置了 Liveness / Readiness / Startup Probe
- [ ] Pod 配置了 `resources.requests` 和 `resources.limits`
- [ ] 实现了优雅停机（SIGTERM 处理 + preStop Hook）
- [ ] 配置了 Pod Disruption Budget
- [ ] 有状态服务使用了 StatefulSet + PVC
- [ ] 数据库有定期备份（Velero / etcd 快照）

### 可观测性 ✓

- [ ] 应用暴露了 `/metrics` 端点（Prometheus 格式）
- [ ] 配置了 ServiceMonitor
- [ ] 日志输出到 stdout（JSON 格式）
- [ ] 配置了关键告警规则（错误率、Pod 重启、磁盘空间）
- [ ] Grafana Dashboard 已创建
- [ ] 请求包含 `X-Request-ID` 用于分布式追踪

### 性能 ✓

- [ ] HPA 配置了合理的 min/max 副本数和目标指标
- [ ] 镜像使用了多阶段构建（减小体积）
- [ ] 配置了镜像预热（大镜像场景）
- [ ] 数据库连接池大小与 Pod 副本数匹配
- [ ] 设置了合理的超时时间

### 部署 ✓

- [ ] CI/CD 流水线包含 lint → test → build → push → deploy
- [ ] 使用不可变镜像标签（Git SHA 或语义化版本）
- [ ] 滚动更新策略配置了 `maxUnavailable: 0`
- [ ] 验证了回滚流程（手动执行一次）
- [ ] 生产变更有审批流程（PR Review / GitOps）
