# 第9章：Artifacts 与缓存——快递包裹与冰箱里的剩菜

## 引言：为什么你需要关心"文件传递"？

想象一个场景：你的 CI/CD 流水线有三道工序——第一道跑测试，第二道做构建，第三道发布上线。问题来了：**第二道工序怎么拿到第一道工序生成的文件？**

在单机时代，这不是问题——文件就在磁盘上躺着呢。但 GitHub Actions 的每个 Job 都运行在一台全新的虚拟机上，就像你每天换一台电脑上班，U盘（或者网盘）就成了你的生命线。

GitHub Actions 提供了两套机制来解决这个问题：**Artifacts** 和 **Cache**。它们看起来都是"在 Job 之间传文件"，但设计哲学完全不同。搞清楚它们的区别，是写好复杂 Workflow 的第一步。

## 核心概念：快递包裹 vs 冰箱里的剩菜

**Artifacts（制品/构件）** 就像快递包裹：

- 你把东西打包发出去（upload），别人拆包收进来（download）
- 包裹有保质期（保留期），过期自动销毁
- 包裹里的东西是**最终产物**——构建好的二进制文件、测试报告、截图
- 你可以在 GitHub 的 UI 上直接下载这些包裹
- 每次都是"全新打包，全新拆封"

**Cache（缓存）** 就像冰箱里的剩菜：

- 你把半成品塞进冰箱（save），下次做饭直接拿出来热热（restore）
- 剩菜是为了**省时间**——不用重新洗菜切菜（不用重新安装依赖）
- 你不能在 GitHub UI 上"下载"缓存，它只服务于 Workflow 运行
- 如果冰箱里的东西过期了或者找不到了，你就得重新做（cache miss）

一句话总结：**Artifacts 是给人用的最终产物，Cache 是给机器用的加速手段。**

## upload-artifact 和 download-artifact 的使用

让我们从一个真实的 Node.js 项目场景出发。你有一个 React 应用，需要在 `build` Job 中构建，然后在 `deploy` Job 中部署。

```yaml
# .github/workflows/build-and-deploy.yml
name: Build and Deploy

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 安装依赖
        run: npm ci

      - name: 构建项目
        run: npm run build
        # 执行完毕后，dist/ 目录下会生成静态文件

      - name: 📦 上传构建产物
        uses: actions/upload-artifact@v4
        with:
          name: build-output          # 给这个"快递包裹"取个名字
          path: dist/                  # 要打包的文件/目录路径
          retention-days: 7            # 保留 7 天（默认 90 天）
          if-no-files-found: error     # 如果找不到文件就报错（而不是静默跳过）
          # 其他选项：'warn'（警告但继续）和 'ignore'（静默跳过）

      - name: 📊 上传测试报告（同时保存）
        run: npm test -- --coverage
        # 假设测试报告输出到 coverage/ 目录

      - name: 📦 上传测试报告
        if: always()  # 即使测试失败也要上传报告——你总得看看"尸体"吧
        uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: |
            coverage/
            test-results/
          retention-days: 14           # 测试报告多留几天，方便事后排查
```

然后在另一个 Job 中下载这些产物：

```yaml
  deploy:
    needs: build                       # 声明依赖关系：deploy 等 build 跑完
    runs-on: ubuntu-latest
    steps:
      - name: 📥 下载构建产物
        uses: actions/download-artifact@v4
        with:
          name: build-output           # 指定要拆的"包裹名"
          path: ./deploy-files         # 解压到这个目录（不指定则放到当前目录）

      - name: 确认文件已就位
        run: ls -la ./deploy-files
        # 你会看到 dist/ 里的所有文件都在这儿了

      - name: 🚀 部署到服务器
        run: |
          echo "将 ./deploy-files 部署到生产环境..."
          # 实际的部署命令
```

## 跨 Job 传递文件

这是 Artifacts 最经典的用法。但有几个坑必须注意：

```yaml
# ⚠️ 常见陷阱：Artifact 不会保留目录结构（除非你指定）
# 假设你有两个目录要传递：
jobs:
  producer:
    runs-on: ubuntu-latest
    steps:
      - name: 生成多个产物
        run: |
          mkdir -p output/api output/web
          echo '{"status":"ok"}' > output/api/health.json
          echo '<html></html>' > output/web/index.html

      # ✅ 推荐：打包成一个 artifact，保留目录结构
      - uses: actions/upload-artifact@v4
        with:
          name: all-outputs
          path: output/                # 整个目录打包

  consumer:
    needs: producer
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: all-outputs
          path: ./received
      # 结果：./received/api/health.json 和 ./received/web/index.html
      # 目录结构完美保留 ✅
```

**批量下载所有 Artifacts**——当你在 Matrix 构建中收集所有变体的结果时特别有用：

```yaml
  collect-all:
    needs: [matrix-build]
    runs-on: ubuntu-latest
    steps:
      # 不指定 name，就会下载当前 Workflow Run 中的所有 Artifacts
      # 每个 Artifact 会放到以自己名字命名的子目录中
      - uses: actions/download-artifact@v4
        with:
          path: all-artifacts/
          merge-multiple: true   # v4 新增：合并到同一目录而不是按名字分子目录

      - run: ls -R all-artifacts/
```

## Artifacts 的保留期设置

Artifacts 会占用你 GitHub 账户的存储空间。对于免费账户，每个仓库有一定的免费额度。设置合理的保留期是个好习惯：

```yaml
# 在仓库设置中也可以配置默认保留期
# Settings > Actions > General > Artifact and log retention

# 在 Workflow 中按需覆盖
- uses: actions/upload-artifact@v4
  with:
    name: nightly-build
    path: release/
    retention-days: 30    # 夜间构建保留一个月

- uses: upload-artifact@v4
  with:
    name: debug-logs
    path: logs/
    retention-days: 1     # 调试日志留一天就够了，谁还会看一个月前的 debug log？
```

## 实际案例：完整的构建-测试-发布流水线

让我们把所有知识串起来，构建一个完整的场景：

```yaml
name: Full Pipeline with Artifacts

on:
  pull_request:
    branches: [main]

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci
      - run: npm run lint
      - run: npm test -- --ci --reporters=default --reporters=jest-junit

      # 即使测试挂了，也上传测试报告供事后分析
      - name: 保存测试报告
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: jest-report
          path: junit.xml
          retention-days: 7

  build:
    needs: lint-and-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci
      - run: npm run build

      - name: 上传构建产物
        uses: actions/upload-artifact@v4
        with:
          name: app-build
          path: |
            dist/
            package.json       # 部署时可能也需要 package.json
          retention-days: 3

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging         # 使用 Environment 保护规则
    steps:
      - name: 下载构建产物
        uses: actions/download-artifact@v4
        with:
          name: app-build
          path: ./dist

      - name: 部署到 Staging
        run: |
          echo "部署版本 ${{ github.sha }} 到 Staging 环境"
          # npx wrangler pages deploy ./dist --project-name=my-app
```

## 小结

| 特性 | Artifacts | Cache |
|------|-----------|-------|
| 目的 | 传递最终产物 | 加速 Workflow |
| 可见性 | 可在 UI 下载 | 仅 Workflow 内部使用 |
| 生命周期 | 有明确保留期 | 自动淘汰（7天未访问） |
| 典型内容 | 构建产物、测试报告 | 依赖包、编译缓存 |
| 速度 | 较慢（需要压缩上传） | 较快（增量更新） |

记住这个比喻：**Artifacts 是你精心包装送给用户的礼物，Cache 是你偷偷藏起来下次自己用的半成品食材。**

## 练习题

1. **基础题**：创建一个 Workflow，在 Job A 中生成一个包含当前时间的文本文件，上传为 Artifact，然后在 Job B 中下载并打印其内容。
2. **进阶题**：设计一个 Matrix 构建（Node.js 16/18/20），每个变体生成各自的测试报告 Artifact，最后一个汇总 Job 下载所有报告并合并成一份。
3. **思考题**：如果你需要在同一个 Job 的不同 Step 之间传递大文件（比如 2GB 的数据集），你应该用 Artifacts 还是别的方式？为什么？
