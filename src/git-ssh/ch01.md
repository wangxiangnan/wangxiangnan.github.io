# 第1章：为什么需要版本控制

> [!TIP] Part 1: 基础概念篇（地基篇）
> 本篇目标是建立两个地基模型：Git 的「三区」与 SSH 的「通道」。本章先回答最根本的问题——我们为什么需要版本控制。理解了「痛」，后面所有命令才有了存在的理由。

凌晨一点，你盯着屏幕上的资源管理器：`cloudnote_v1`、`cloudnote_v2`、`cloudnote_final`、`cloudnote_final_2`、`cloudnote_final_真的不改了`。这是你的笔记应用项目，写了一个月。为了保险，你每改几天就复制一份文件夹。

就在刚才，你手一抖，把写了两周的新版笔记同步功能拖进了回收站，还顺手清空了。最新的完整代码，只存在于三天前拷进 U 盘的那份 `cloudnote_final_2` 里——而那之后你又改了六十多处。

这不是编出来的段子，这是每个程序员都经历过（或即将经历）的现场。计算机科学早就为这类痛苦准备好了系统性的解法，本章就来回答三个问题：手工管理到底败在哪？版本控制（Version Control）承诺了什么？以及——为什么偏偏是 Git？

## 1.1 复制粘贴管理的三宗罪

回到开头那个资源管理器。文件夹复制大法看似稳妥，实际上藏着三宗罪。

**罪一：覆盖即永别。** 复制的本质是快照快照再快照，但空间有限时你会删旧版——删的那一刻，历史就永远消失了。Git 里有一个吓人但真实的说法：**在 Git 的世界里，提交过的东西几乎不可能真正丢失**；而在复制粘贴的世界里，丢失只需要一次手滑。

**罪二：差异全靠脑补。** `cloudnote_final_2` 和 `cloudnote_final` 之间差了什么？没有工具能告诉你，只有你的记忆，而记忆在凌晨一点最不可靠。

**罪三：协作必踩脚。** 你和同事同时改了 `index.html`：你先发了你的版本，同事又把他保存的版本覆盖上去——你的修改静默蒸发，甚至没人发现。

把需求和管理方式摆在一起，差距一目了然：

| 核心需求 | 文件夹复制 | 版本控制系统 |
|---------|-----------|-------------|
| 回到任意历史时刻 | 手工留底，删了就没了 | 每次提交都是永久存档 |
| 看两个版本差在哪 | 人眼逐文件对比 | `git diff` 一条命令 |
| 找出某行代码是谁改的 | 无解 | 追溯到具体提交与作者 |
| 多人同时修改 | 互相覆盖，先到先得 | 自动合并，冲突显式提示 |
| 异地备份 | 手动拷 U 盘 | 克隆即完整备份 |

把「复制粘贴大法」用在云笔记上，典型的一天是这样的：

- 上午 10:00：复制 `cloudnote_v3` 为 `cloudnote_v4`，改同步逻辑
- 下午 14:00：发现 v4 改坏了，想退回 v3——但 v3 和 v2 谁更新？文件夹时间戳被移动操作刷新过，不可信
- 下午 16:00：同事问「把你昨天那个能用的版本发我」——你翻了十分钟，不确定哪个是「昨天能用的」
- 晚上 22:00：心一横，直接在 v4 上继续改，祈祷别再坏
- 晚上 23:00：想起 U 盘里还有份「备份」——上次拷是什么时候来着？没人记得
- 深夜 00:30：把所有文件夹压成一个 zip 发到自己邮箱——仪式感拉满，历史为零

这不是懒，是**工具不支持**：文件夹系统只认识「路径和字节」，不认识「历史和意图」。版本控制补的正是这个缺口。

云笔记项目第 1 个月的体量：47 个文件、约 3MB、日均保存 30 次。就是这个不起眼的规模，手工管理已经开始崩坏——规模越大，崩坏越快。

> [!NOTE] 先记住这组数字
> 云笔记阶段 1：47 个文件、约 3MB、50 次提交、1 个开发者。全书所有例子都围绕这个真实感十足的小项目展开——到阶段 3，它会变成 3 人团队、12000 次提交、1.2GB（含图片素材）的正经产品。规模在长，方法论不变。

## 1.2 版本控制的四个核心承诺

版本控制系统的承诺可以浓缩为四条，每一条都精准命中一宗罪：

1. **存档不覆盖**：每次提交（commit）都是对整个项目的一次永久快照，历史链条只增不减。云笔记的每次提交都永久留底，删错的代码随时可回。
2. **差异一键可见**：任意两个时刻之间改了哪些文件、哪些行，一条 `git diff` 全部列清。三天前和今天的 `notes.html` 差在哪，一眼见分晓，不再靠记忆。
3. **时光可倒流**：回到昨天的状态、找回删掉的函数、对比三个月前的方案，都是常规操作。回收站从此吓不到你。
4. **并行不踩脚**：每个人在自己的分支（branch）上开发，最后合并（merge）——冲突会被显式标出，而不是静默覆盖。这为阶段 3 的 3 人协作埋下伏笔。

| 承诺 | 入门命令 | 深入章节 |
|------|---------|---------|
| 存档不覆盖 | `git add` / `git commit` | 第3章 |
| 差异一键可见 | `git diff` / `git log` | 第7章 |
| 时光可倒流 | `git restore` / `git reset` / `git revert` | 第8章 |
| 并行不踩脚 | `git branch` / `git switch` / `git merge` | 第9-10章 |

这张表同时是后续十章的路线图——每学一章，就点亮一格。

注意第四条：版本控制解决协作问题的思路不是「禁止同时修改」，而是**把冲突显式化**——让「两个人都改了同一行」这个时刻变得无法忽视，而不是悄悄让后保存的覆盖先保存的。这个思路贯穿全书。

顺带一提，四条承诺里最反直觉的是第一条——「只增不减」。很多新手担心仓库会像复制文件夹一样越堆越大，实际上 Git 只存差异化的对象并做压缩（1.6 节会用数据证明）。**历史不是负担，而是资产。**

先尝三口甜头，感受一下，不必深究语法（后面章节细讲）：

```bash
git log --oneline        # 承诺 1+2：历史一目了然
git diff HEAD~1          # 承诺 2：这次提交改了什么
git checkout a1b2c3d -- notes.html   # 承诺 3：从任意历史版本捞回一个文件
```

> [!NOTE] 为什么「几乎」不可能丢失
> Git 的历史保真有一个前提：代码至少提交过。没 commit 的修改、以及从未克隆过仓库的机器，不在保护范围内。所以本书反复强调的第一习惯是：**小步提交，频繁提交**。

## 1.3 三代版本控制工具

版本控制不是 Git 的发明。把工具史摊开看，你能看清 Git 的每一步设计为什么长这样：

```text
第一代：本地式          第二代：集中式         第三代：分布式
(RCS, 1982)          (SVN, 2000)          (Git, 2005)

┌────────┐           ┌────────┐           ┌────────┐  ┌────────┐
│你的机器  │           │ 中央服务器│ ◄──────► │你的机器  │  │同事机器  │
│完整历史  │           │ 唯一历史  │  网络往返  │完整历史  │  │完整历史  │
└────────┘           └────────┘           └───┬────┘  └───┬────┘
                                              │ 任意两点可同步
                                        (克隆 = 完整备份)
```

| 维度 | 本地式（RCS） | 集中式（SVN） | 分布式（Git） |
|------|--------------|--------------|--------------|
| 历史存放在哪 | 自己的机器 | 中央服务器（唯一权威） | 每个克隆都是完整副本 |
| 提交需要联网吗 | 不需要 | 必须联网 | 提交本地完成，推送才联网 |
| 服务器宕机后果 | 无影响 | 全员瘫痪，历史唯一副本告危 | 无影响，可从任意克隆恢复 |
| 分支成本 | 昂贵 | 昂贵（目录级拷贝） | 近乎零成本（第9章见分晓） |
| 典型代表 | RCS、CVS | SVN、CVS（后期） | Git、Mercurial |

集中式（Centralized）的致命伤是**单点故障**：服务器硬盘一旦损毁且没有备份，全公司的历史随之蒸发。分布式（Distributed）把「完整历史」复制到每个人手里——云笔记阶段 2 能实现双机同步，靠的正是这个特性：每一份克隆都是完整备份，任何一台机器挂了都不丢历史。

在时间轴上再看一眼：1982 年 Walter Tichy 发布本地式工具 RCS；1990 年前后 CVS 让版本控制走进团队；2000 年 CollabNet 推出 SVN 力图取代 CVS，集中式到达巅峰；2005 年 Git 诞生，分布式登台；2008 年 GitHub 上线把它推向大众；2018 年微软以 75 亿美元收购 GitHub——一个命令行工具长成了生态。四十年演进只回答了一个问题：**历史副本应该放在哪、放几份。**

顺带解释一个常见疑问：为什么集中式统治了十年之久？因为在「公司内网 + 中心机房」的年代，集中式的缺点几乎不存在——网络永远可达，服务器有专业备份。是远程办公与开源协作把「人人离线也能提交」变成刚需之后，分布式的优势才真正兑现。技术选型从来不是绝对优劣，而是场景匹配。

## 1.4 Git 的诞生：一场被迫的自救

Git 的诞生是个带火药味的故事。2002 年起，Linux 内核社区使用商业版本控制工具 BitKeeper 管理代码。2005 年，双方因授权争议谈崩，内核社区失去了免费使用权。

当时 Linux 内核的规模：贡献者上千人，每年数万次提交，对合并速度和非线性开发的要求没有任何现成开源工具能满足。于是 Linus Torvalds 自己动手，用大约两周时间写出了 Git 的雏形。他给自己定的设计目标，今天读来依然句句是刀：

1. **速度**：提交、分支、合并必须快到无感——分支在 Git 里近乎零成本。
2. **简单的设计**：数据模型干净，而不是功能堆砌。
3. **完全分布式**：没有「中央服务器」这个概念上的必需品。
4. **强力支持非线性开发**：同时并行上千个分支是日常，不是异常。

事实证明这不是一次性自救：今天 Linux 内核单月提交超过 10 万次，全部由 Git 管理；2008 年 GitHub 上线，又把「分布式 + 社交化协作」做成了平台，Git 由此成为事实上的行业标准。

把四个设计目标和 Git 的实现机制对上号，你会发现它们在后续章节里都会拆开细讲：

| 设计目标 | Git 的兑现方式 | 详见 |
|---------|---------------|------|
| 速度 | 分支只是一个指针文件，创建零拷贝 | 第9章 |
| 简单设计 | 全部历史存于一个内容寻址的对象库 | 第3、19章 |
| 完全分布式 | 克隆即全量备份，无需中央服务器 | 第21章 |
| 强非线性支持 | 分支与合并是第一等公民 | 第10章 |

值得一提的是，「两周写出雏形」的说法在社区流传甚广，Linus 本人的表述是 2005 年 4 月开始开发、数周内达到可用——细节虽有出入，但那份「等不到现成工具就自己写」的紧迫感是真实的。很多伟大的工具都诞生于这种时刻。顺带一提，Git 这个名字也是 Linus 式的自嘲：他开玩笑说自己「以己之名命名所有项目，先是 Linux，现在是 git」，后来才补上了「愚蠢自负的内容跟踪器」（the stupid content tracker）这个官方自我介绍。

> [!TIP] 学的是模型，不是命令
> 二十年间 Git 的命令表象变了很多，但底层数据模型几乎没动。所以本书会不断带你「往下多看一层」：分支是文件、提交是快照、pull 的本质是两个进程在对话。模型通了，命令只是查询手册。

## 1.5 五分钟上手：你的第一连击

空谈无益，现在就动手。目标：五分钟内创建仓库并完成第一次提交。以下命令逐行可复制执行，`#` 之后是解释性注释，不会被执行。

```bash
  # 1. 安装（Ubuntu/Debian；Windows 下载 Git for Windows 安装包）
  sudo apt install git
  git --version          # 确认安装，例如 git version 2.43.0

  # 2. 创建项目目录并初始化仓库
  mkdir ~/cloudnote && cd ~/cloudnote
  git init               # 输出: Initialized empty Git repository

  # 3. 创建第一个文件
  echo "# 云笔记" > README.md

  # 4. 提交三连击
  git add README.md          # 放入暂存区（第3章详解）
  git commit -m "云笔记的第一页"   # 存档为永久快照
  git log --oneline          # 查看历史
```

`git log --oneline` 会输出类似这样一行：

```text
a1b2c3d (HEAD -> main) 云笔记的第一页
```

开头那串 `a1b2c3d` 是这次提交的哈希值（Hash）——你可以把它理解为这次快照的「身份证号」。`HEAD` 指向你当前所在的分支位置，`main` 是默认分支名。这些概念第 9 章会彻底拆开，现在只需要知道：**你的项目从此有了第一页不可磨灭的历史**。

第一次 `git commit` 的完整输出也值得逐行看一眼：

```text
[main (root-commit) a1b2c3d] 云笔记的第一页
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

`root-commit` 表示这是仓库的第一个提交；`1 insertion(+)` 统计了行数变化；`100644` 是文件权限模式的标记。顺带留意：输出里的 `a1b2c3d` 与 `git log` 看到的一致——同一个身份证号。从这一刻起，这次快照连同作者、时间、说明，永久写入了 `.git/objects`。

> [!TIP] 关于默认分支名
> Git 2.28 起可用 `git config --global init.defaultBranch main` 指定新建仓库的默认分支名；旧版本默认叫 `master`。本书统一使用 `main`——两者只是名字不同，机制完全一致。为什么改名如此轻而易举？第9章讲完「分支是个指针」你自然会懂。

如果你在第 4 步被拦下，提示 `Please tell me who you are`——这正是下一章要解决的第一件事。

## 1.6 神秘的 .git 目录：仓库的大脑

在 `~/cloudnote` 里执行 `ls -la`，你会看到一个此前不存在的隐藏目录：

```text
~/cloudnote/
├── README.md      ← 你的文件（工作区）
└── .git/          ← 仓库的大脑（版本库本体）
    ├── HEAD           # 指针：当前在哪个分支（第9章）
    ├── config         # 本仓库专属配置（第2章）
    ├── objects/       # 所有历史数据的真正存身之处
    └── refs/          # 分支与标签的「书签」（第9章）
```

两个此刻就要建立的认知：

- **「版本库」（Repository）指的就是这个 `.git` 目录**，不是你的文件夹。你的 `README.md` 只是工作区里的一份普通文件。
- **不要手动修改 `.git` 里的任何东西**。可以看（`ls`、`cat`），不要动。全书唯一例外是第 9 章让你亲眼确认「分支是一个 41 字节的文件」。

做个实验感受分布式的价值：把整个 `~/cloudnote` 目录复制到另一个位置（甚至另一台机器），新位置的仓库带着完整历史照常工作。这就是 1.3 节说的「克隆即完整备份」——此时云笔记仓库约 3MB，成本几乎为零。

再做两个小观察：`du -sh .git` 看看仓库大脑的体积，此刻不足 100KB——第一次提交远比你想象的轻。之后每提交几次就看一眼，你会发现它的增长远小于文件本身的体积：Git 按对象存储并压缩重复内容（第19章会解释 packfile 机制）。**轻，是 Git 敢让你频繁提交的底气。**

好奇的话，再 `ls .git/objects` 看一眼：你会看到一堆以两个字符命名的目录（如 `a1/`、`9d/`）——这是 Git 给对象做的「抽屉」，完整哈希的前两位当目录名、余下 38 位当文件名。这种**内容寻址**（content-addressed）的命名方式意味着内容相同的文件只存一份，第3章会带你亲眼验证。

```text
.git/objects/
├── a1/          # 完整哈希前两位 = 抽屉号
│   └── b2c3d…   # 余下 38 位 = 对象文件名
├── info/        # 元数据（暂不用管）
└── pack/        # 打包文件（第19章详说）
```

> [!WARNING] 手滑预防针
> 从本章起，你的每一次「后悔」都有对应的 git 命令解决；但 `.git` 目录被手动破坏除外。保持敬畏：操作命令，不操作大脑。

## 1.7 Git ≠ GitHub：先分清工具与平台

最后澄清一个高频混淆。Git 和 GitHub 不是一回事，也从来不是必须绑定的关系：

| | Git | GitHub |
|---|-----|--------|
| 本质 | 命令行版本控制工具 | 托管 Git 仓库的商业平台 |
| 诞生 | 2005 年，Linus Torvalds | 2008 年，GitHub 公司（2018 年被微软收购） |
| 运行在哪 | 你的本地机器，离线可用 | 云端，在线使用 |
| 是否必需 | 是 | 否——GitLab、Gitea 或自家服务器（第21章）同样胜任 |

两个常见的自问自答：

- **Git 能离线工作吗？** 完全能。提交、分支、查看历史全在本地完成，联网只在「同步到远程」时才需要——这正是分布式与集中式最大的体感差异。
- **用 Git 必须注册 GitHub 账号吗？** 不需要。账号是「同步与协作」环节的需求，而且同步的对象不一定是 GitHub——GitLab、Gitea、甚至你自己的一台服务器（第21章）都行。

一个类比：**Git 是发动机，GitHub 是租车公司**。发动机装在自家车上（第21章的裸仓库）照样跑；租车公司额外提供了导航（Pull Request）、保险（权限管理）、路况（CI 状态），这就是第20章要讲的增值层。

理解了这个分层，也就理解了本书的结构：先用 12 章把「发动机」拆透，再用后半程讲怎么把它开上公路——无论是租的（GitHub）还是自己的（自建服务器）。如果这一章只带走一句话，就是：**学 Git 不等于注册 GitHub。**

## 本章小结

- 文件夹复制管理有三宗罪：覆盖即永别、差异靠脑补、协作必踩脚
- 版本控制的四个承诺：存档不覆盖、差异可见、时光倒流、并行不踩脚
- 集中式的思路是把冲突显式化，而不是禁止同时修改——这个思路贯穿全书
- 三代工具的演进主线是「历史副本放在哪」：本地 → 集中服务器 → 每人一份
- 集中式的致命伤是单点故障；分布式让每次克隆都成为完整备份
- Git 诞生于 2005 年 BitKeeper 断供后的自救，设计目标是速度、简单、分布式、强非线性支持
- `git init` 创建的不是文件夹而是仓库大脑 `.git`；「版本库」指的就是它
- Git 是本地工具，GitHub 是托管平台：前者必需，后者可替换（GitLab、Gitea、自建服务器皆可）
