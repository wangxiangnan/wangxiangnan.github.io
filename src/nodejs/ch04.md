# 第4章：异步编程（下）——事件循环深度解密

## 引言：单线程不等于弱鸡

"什么？Node.js 是单线程的？那怎么处理高并发？"

每次听到这个问题，我都想举一个例子：你家小区只有一个快递柜管理员（单线程），但他并不需要亲自去送每一件快递。他的工作是：接收包裹 → 放进对应格子 → 通知取件 → 处理下一个。真正运输快递的是一大堆快递员（I/O 线程、系统调用、libuv 线程池）。

**单线程 ≠ 只有一个线程在干活**。准确地说：

- **JavaScript 执行**是单线程的（你的代码在主线程上跑）
- **I/O 操作**是多线程/异步的（libuv 的线程池 + OS 异步接口）
- **整个 Node.js 进程**包含多个线程（V8 GC 线程、libuv 线程池、Worker 线程等）

## 4.1 事件循环的六个阶段

Node.js 的事件循环基于 libuv，分为六个阶段（phase），每一轮循环按顺序执行：

```
   ┌───────────────────────────┐
┌─>│        timers              │ ← setTimeout/setInterval 回调
│  └──────────┬────────────────┘
│  ┌──────────┴────────────────┐
│  │     pending callbacks      │ ← 系统操作回调（如 TCP 错误）
│  └──────────┬────────────────┘
│  ┌──────────┴────────────────┐
│  │       idle, prepare        │ ← 内部使用
│  └──────────┬────────────────┘
│  ┌──────────┴────────────────┐        ┌───────────────┐
│  │          poll              │<───────┤  incoming:    │
│  │  (轮询：执行I/O回调)       │        │  connections, │
│  └──────────┬────────────────┘        │  data, etc.   │
│  ┌──────────┴────────────────┐        └───────────────┘
│  │         check             │ ← setImmediate 回调
│  └──────────┬────────────────┘
│  ┌──────────┴────────────────┐
│  │      close callbacks       │ ← socket.on('close', ...)
│  └──────────┬────────────────┘
└─────────────┘
```

### 各阶段详解

#### 1. Timers 阶段

执行 `setTimeout` 和 `setInterval` 的回调。

```javascript
// 注意：timer 的延迟时间是"最少延迟"，不是"精确延迟"
setTimeout(() => {
  console.log('这个回调在 timers 阶段执行');
}, 100);
// 实际可能在 100ms、101ms、甚至 200ms 后执行
// 取决于其他回调的执行时间和事件循环的当前状态
```

**关键理解**：setTimeout 的回调不是"到时间就执行"，而是"到时间后，在下一次事件循环的 timers 阶段才执行"。

#### 2. Pending Callbacks 阶段

执行延迟到下一个循环迭代的 I/O 回调。主要处理一些系统操作的回调，如 TCP 连接收到 ECONNREFUSED 时的错误回调。

大多数情况下你不会直接和这个阶段打交道。

#### 3. Idle, Prepare 阶段

仅供 Node.js 内部使用。你的代码不会在这个阶段执行。就像后台保洁，你看不到但它确实在工作。

#### 4. Poll 阶段（最重要！）

这是事件循环最重要的阶段，它做两件事：

1. 计算应该阻塞和轮询 I/O 的时间
2. 处理 poll 队列中的事件（I/O 回调）

```javascript
import { readFile } from 'node:fs';

readFile('./big-file.txt', (err, data) => {
  // 这个回调在 poll 阶段执行
  console.log('文件读取完毕');
});
```

**Poll 阶段的行为逻辑**：

- 如果 poll 队列不为空：依次执行队列中的回调
- 如果 poll 队列为空：
  - 如果有 `setImmediate` 回调等待：离开 poll，进入 check 阶段
  - 如果没有 `setImmediate`：阻塞在这里等待新的 I/O 事件
  - 但如果有 timer 到期了：回到 timers 阶段

#### 5. Check 阶段

执行 `setImmediate` 的回调。`setImmediate` 可以理解为"在当前 poll 阶段完成后立即执行"。

```javascript
setImmediate(() => {
  console.log('这个回调在 check 阶段执行');
});
```

#### 6. Close Callbacks 阶段

执行关闭事件的回调，比如 `socket.on('close', ...)`。

```javascript
import { createServer } from 'node:net';

const server = createServer((socket) => {
  socket.on('close', () => {
    // 这个回调在 close callbacks 阶段执行
    console.log('连接关闭');
  });
});
```

## 4.2 微任务与宏任务

在每个阶段之间（以及每个阶段内的每个回调之后），Node.js 会清空微任务队列。

### 执行顺序规则

```
每个宏任务执行完后：
1. 清空所有 process.nextTick 回调
2. 清空所有 Promise 微任务（.then/.catch/.finally 回调）
3. 继续下一个宏任务或进入下一个阶段
```

```javascript
// 验证执行顺序
console.log('1. 同步代码');

process.nextTick(() => {
  console.log('3. nextTick');
});

Promise.resolve().then(() => {
  console.log('4. Promise 微任务');
});

setTimeout(() => {
  console.log('6. setTimeout (timers 阶段)');
}, 0);

setImmediate(() => {
  console.log('7. setImmediate (check 阶段)');
});

console.log('2. 同步代码（继续）');

// 输出顺序：
// 1. 同步代码
// 2. 同步代码（继续）
// 3. nextTick
// 4. Promise 微任务
// 5/6. setTimeout / setImmediate（顺序不确定，见下文解释）
```

## 4.3 nextTick vs setImmediate vs setTimeout(0)

这三个是面试中最常被问到的话题，让我们彻底搞清楚：

### process.nextTick

```javascript
process.nextTick(() => {
  console.log('nextTick 回调');
});
```

- **执行时机**：在当前操作完成后，事件循环继续之前
- **优先级**：最高！比 Promise 微任务还高
- **本质**：不属于事件循环的任何阶段，是一个"插队机制"
- **危险**：如果递归调用 nextTick，会"饿死"事件循环（I/O永远得不到处理）

```javascript
// ⚠️ 危险示例：递归 nextTick 会阻塞事件循环
function recursiveNextTick() {
  process.nextTick(recursiveNextTick);
  // I/O 回调永远不会被执行！
}
// 永远不要这样做！
```

### setImmediate

```javascript
setImmediate(() => {
  console.log('setImmediate 回调');
});
```

- **执行时机**：在当前 poll 阶段完成后的 check 阶段
- **优先级**：比 nextTick 低，但在 I/O 回调之后有确定性
- **本质**：事件循环 check 阶段的回调
- **推荐**：在 I/O 回调中想"尽快但不阻塞"地执行某些逻辑时使用

### setTimeout(fn, 0)

```javascript
setTimeout(() => {
  console.log('setTimeout 0 回调');
}, 0);
// 实际上最小延迟是 1ms（规范规定）
```

- **执行时机**：在下一轮事件循环的 timers 阶段
- **实际延迟**：至少 1ms（Node.js 内部会将 0 改为 1）

### 经典对比实验

```javascript
// 实验1：主模块中（顺序不确定）
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// 输出顺序不确定！取决于进程性能和系统调度
// 因为 setTimeout(fn, 0) 实际是 setTimeout(fn, 1)
// 如果事件循环启动时已经过了 1ms → timeout 先执行
// 如果还没过 1ms → immediate 先执行

// 实验2：在 I/O 回调中（顺序确定！）
import { readFile } from 'node:fs';

readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 永远是：immediate → timeout
// 因为 I/O 回调在 poll 阶段执行，poll 之后是 check（setImmediate）
// 然后才是下一轮的 timers（setTimeout）
```

### 一张图总结

```
┌──────────────────────────────────────────────────┐
│                  主线程执行栈                       │
│          （同步代码执行完毕后...）                   │
└──────────────────────┬───────────────────────────┘
                       │
           ┌───────────▼───────────┐
           │   process.nextTick    │  ← 最高优先级
           │   队列（全部清空）      │
           └───────────┬───────────┘
                       │
           ┌───────────▼───────────┐
           │   Promise 微任务       │  ← 次高优先级
           │   队列（全部清空）      │
           └───────────┬───────────┘
                       │
           ┌───────────▼───────────┐
           │   事件循环各阶段       │  ← timers → poll → check → ...
           │  （宏任务逐个执行）     │
           └───────────────────────┘
           ↑                      │
           └──── 每个宏任务后 ──────┘
                 再清空 nextTick 和 微任务
```

## 4.4 经典面试题解析

### 题目1：基础输出顺序

```javascript
console.log('start');

setTimeout(() => {
  console.log('timeout');
}, 0);

Promise.resolve().then(() => {
  console.log('promise');
});

process.nextTick(() => {
  console.log('nextTick');
});

console.log('end');
```

**答案**：

```
start
end
nextTick
promise
timeout
```

**解析**：

1. `start` 和 `end` 是同步代码，立即执行
2. 同步代码执行完后，清空微任务
3. nextTick 优先级高于 Promise，先执行 `nextTick`
4. 然后执行 `promise`
5. 最后在 timers 阶段执行 `timeout`

### 题目2：嵌套的微任务

```javascript
Promise.resolve().then(() => {
  console.log('promise1');
  process.nextTick(() => {
    console.log('nextTick in promise1');
  });
}).then(() => {
  console.log('promise2');
});

process.nextTick(() => {
  console.log('nextTick1');
  Promise.resolve().then(() => {
    console.log('promise in nextTick1');
  });
});

process.nextTick(() => {
  console.log('nextTick2');
});
```

**答案**：

```
nextTick1
nextTick2
promise in nextTick1
promise1
promise2
nextTick in promise1
```

**解析**：

1. 所有 nextTick 先清空：`nextTick1` → `nextTick2`
2. 清空 nextTick 过程中产生的 Promise 微任务：`promise in nextTick1`
3. 清空最初的 Promise 微任务：`promise1`
4. promise1 的 .then 产生 `promise2`（微任务），以及一个 nextTick
5. 先清空当前微任务：`promise2`
6. 然后清空 nextTick：`nextTick in promise1`

### 题目3：setTimeout 与 setImmediate 的竞争

```javascript
const fs = require('fs');

fs.readFile(__filename, () => {
  console.log('I/O callback');

  setTimeout(() => {
    console.log('timeout in I/O');
  }, 0);

  setImmediate(() => {
    console.log('immediate in I/O');
  });

  process.nextTick(() => {
    console.log('nextTick in I/O');
  });

  Promise.resolve().then(() => {
    console.log('promise in I/O');
  });
});
```

**答案**（确定的）：

```
I/O callback
nextTick in I/O
promise in I/O
immediate in I/O
timeout in I/O
```

**解析**：

1. I/O 回调在 poll 阶段执行
2. 回调执行完后，清空 nextTick 和 微任务：`nextTick in I/O` → `promise in I/O`
3. poll 阶段结束后进入 check 阶段：`immediate in I/O`
4. 下一轮事件循环的 timers 阶段：`timeout in I/O`

### 题目4：async/await 的展开

```javascript
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}

async function async2() {
  console.log('async2');
}

console.log('script start');

setTimeout(() => {
  console.log('setTimeout');
}, 0);

async1();

new Promise((resolve) => {
  console.log('promise1');
  resolve();
}).then(() => {
  console.log('promise2');
});

console.log('script end');
```

**答案**：

```
script start
async1 start
async2
promise1
script end
async1 end
promise2
setTimeout
```

**解析**：

1. 同步执行：`script start`
2. 调用 async1：`async1 start`
3. 遇到 await async2()，先执行 async2()：`async2`
4. await 之后的代码变成微任务（等 async2 的 Promise resolve 后执行）
5. 继续同步代码：创建 Promise 时执行 executor：`promise1`
6. .then 注册微任务
7. 同步代码：`script end`
8. 清空微任务：`async1 end`（await 后面的代码）→ `promise2`
9. 宏任务：`setTimeout`

### 题目5：综合题

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
  new Promise(resolve => {
    console.log('3');
    resolve();
  }).then(() => {
    console.log('4');
  });
});

new Promise(resolve => {
  console.log('5');
  resolve();
}).then(() => {
  console.log('6');
});

setTimeout(() => {
  console.log('7');
  new Promise(resolve => {
    console.log('8');
    resolve();
  }).then(() => {
    console.log('9');
  });
});

console.log('10');
```

**答案**：

```
1
5
10
6
2
3
4
7
8
9
```

**解析**：

1. 同步代码：`1` → `5`（Promise 构造函数是同步的！）→ `10`
2. 微任务：`6`
3. 第一个 setTimeout 宏任务：`2` → `3`（构造函数同步）→ 清空微任务 `4`
4. 第二个 setTimeout 宏任务：`7` → `8` → 清空微任务 `9`

### 题目6：nextTick 饿死 I/O

```javascript
import { readFile } from 'node:fs';

// 注册一个 I/O 操作
readFile('./package.json', () => {
  console.log('file read');  // 什么时候执行？
});

// 递归 nextTick
let count = 0;
function recursiveTick() {
  if (count++ < 5) {
    process.nextTick(recursiveTick);
    console.log(`nextTick ${count}`);
  }
}
recursiveTick();
```

**输出**：

```
nextTick 1
nextTick 2
nextTick 3
nextTick 4
nextTick 5
file read
```

即使文件读取很快完成，nextTick 递归也会优先执行完毕。如果把 5 改成 5000000，`file read` 会被严重延迟。这就是为什么官方推荐用 setImmediate 而不是 nextTick。

## 4.5 libuv 线程池：为什么文件操作不阻塞主线程

### 哪些操作使用线程池？

```
使用 libuv 线程池的操作：
├── 文件系统操作（fs.*）
├── DNS 查找（dns.lookup）
├── 某些加密操作（crypto.pbkdf2, crypto.randomBytes）
├── zlib 压缩/解压
└── 用户自定义的 Worker

不使用线程池（直接使用 OS 异步接口）：
├── TCP/UDP 网络操作
├── 管道操作
├── DNS resolve（dns.resolve，使用 c-ares 库）
└── 信号处理
```

### 线程池大小

```javascript
// 默认线程池大小：4
// 可以通过环境变量修改（最大 1024）
// 必须在程序启动时设置

// 方法1：命令行
// UV_THREADPOOL_SIZE=8 node server.mjs

// 方法2：在代码最开头设置（必须在任何异步操作之前）
process.env.UV_THREADPOOL_SIZE = '8';
```

### 实验：线程池对并发的影响

```javascript
// threadpool-demo.mjs
import { pbkdf2 } from 'node:crypto';

const NUM_TASKS = 8;
const start = Date.now();

for (let i = 0; i < NUM_TASKS; i++) {
  pbkdf2('password', 'salt', 100000, 64, 'sha512', (err, key) => {
    console.log(`任务 ${i + 1} 完成，耗时: ${Date.now() - start}ms`);
  });
}
```

**默认线程池大小 4 时的输出**（假设每个任务需要 ~50ms）：

```
任务 1 完成，耗时: 52ms   ← 前4个几乎同时完成
任务 2 完成，耗时: 53ms   ← （并行执行）
任务 3 完成，耗时: 54ms
任务 4 完成，耗时: 55ms
任务 5 完成，耗时: 103ms  ← 后4个等前面的完成
任务 6 完成，耗时: 104ms  ← 才能开始
任务 7 完成，耗时: 105ms
任务 8 完成，耗时: 106ms
```

设置 `UV_THREADPOOL_SIZE=8` 后，8个任务几乎同时完成。

## 4.6 实战：用代码验证事件循环各阶段

```javascript

// 这段代码可以帮你"看到"事件循环的各个阶段

import { readFile } from 'node:fs';

console.log('=== 脚本开始 ===');

// Timers 阶段
setTimeout(() => {
  console.log('[Timers] setTimeout 0');
}, 0);

setTimeout(() => {
  console.log('[Timers] setTimeout 100');
}, 100);

// Check 阶段
setImmediate(() => {
  console.log('[Check] setImmediate 1');

  // 在 check 阶段中嵌套
  setImmediate(() => {
    console.log('[Check] 嵌套 setImmediate（下一轮）');
  });

  setTimeout(() => {
    console.log('[Timers] setTimeout in setImmediate');
  }, 0);

  process.nextTick(() => {
    console.log('[Microtask] nextTick in setImmediate');
  });
});

// Poll 阶段（I/O）
readFile('./package.json', () => {
  console.log('[Poll] I/O 回调');

  setImmediate(() => {
    console.log('[Check] setImmediate in I/O');
  });

  setTimeout(() => {
    console.log('[Timers] setTimeout in I/O');
  }, 0);
});

// 微任务
process.nextTick(() => {
  console.log('[Microtask] nextTick 1');
});

Promise.resolve().then(() => {
  console.log('[Microtask] Promise 1');
});

process.nextTick(() => {
  console.log('[Microtask] nextTick 2');
  Promise.resolve().then(() => {
    console.log('[Microtask] Promise in nextTick');
  });
});

console.log('=== 脚本结束 ===');
```

**典型输出**：

```

=== 脚本结束 ===
```

## 4.7 常见坑点

### 坑1：过度使用 nextTick

```javascript
// ❌ 用 nextTick 做"延迟执行"——可能饿死 I/O
process.nextTick(() => {
  heavyComputation(); // 如果这里很耗时...
});

// ✅ 用 setImmediate 代替（给 I/O 留出空间）
setImmediate(() => {
  heavyComputation();
});
```

### 坑2：以为 setTimeout(0) 是"立即执行"

```javascript
// setTimeout(fn, 0) 不是"立即执行"！
// 它是"至少等 1ms，然后在下一次 timers 阶段执行"
console.log('before');
setTimeout(() => console.log('timeout'), 0);
console.log('after');
// 输出：before → after → timeout

// 如果你需要"当前同步代码执行完后尽快执行"，用：
process.nextTick(() => console.log('asap'));
// 或者
queueMicrotask(() => console.log('also asap'));
```

### 坑3：定时器精度问题

```javascript
// ❌ 期望精确的定时
function sleep(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

const start = Date.now();
await sleep(100);
console.log(`实际等待: ${Date.now() - start}ms`);
// 可能输出 101, 103, 甚至 115
// Node.js 的定时器不是高精度时钟！

// 如果需要高精度计时，用 performance.now()
import { performance } from 'node:perf_hooks';
const t0 = performance.now();
// ... 操作 ...
const t1 = performance.now();
console.log(`精确耗时: ${(t1 - t0).toFixed(3)}ms`);
```

### 坑4：CPU 密集任务阻塞事件循环

```javascript
// ❌ 这会阻塞整个服务器！
function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

import { createServer } from 'node:http';

const server = createServer((req, res) => {
  if (req.url === '/fib') {
    const result = fibonacci(45); // 这可能需要几秒钟
    // 在这几秒内，其他所有请求都无法处理！
    res.end(`Result: ${result}`);
  }
});

// ✅ 解决方案1：使用 Worker Threads
import { Worker, isMainThread, parentPort } from 'node:worker_threads';

if (isMainThread) {
  // 主线程：把CPU密集任务交给Worker
  const server = createServer((req, res) => {
    const worker = new Worker(new URL(import.meta.url));
    worker.postMessage(45);
    worker.on('message', (result) => {
      res.end(`Result: ${result}`);
    });
  });
} else {
  // Worker 线程：执行计算
  parentPort.on('message', (n) => {
    parentPort.postMessage(fibonacci(n));
  });
}

// ✅ 解决方案2：分割任务，让出事件循环
async function fibonacciAsync(n) {
  if (n <= 1) return n;
  // 每计算一些就让出控制权
  if (n % 10 === 0) {
    await new Promise(resolve => setImmediate(resolve));
  }
  return fibonacciAsync(n - 1) + fibonacciAsync(n - 2);
}
```

## 4.8 本章小结

| 知识点 | 核心要点 |
| -------- | --------- |
| 事件循环 | 6个阶段：timers → pending → idle → poll → check → close |
| 微任务 | nextTick > Promise，在每个宏任务之间清空 |
| nextTick | 最高优先级，但可能饿死 I/O |
| setImmediate | check 阶段执行，在 I/O 回调后最可靠 |
| setTimeout(0) | 至少 1ms 延迟，在 timers 阶段执行 |
| 线程池 | 默认 4 线程，处理 fs/dns/crypto 等操作 |
| CPU 密集 | 用 Worker Threads 或任务分割解决 |

**一句话总结**：事件循环是 Node.js 的心跳。理解它的阶段和优先级，你就能预测任何异步代码的执行顺序，写出不阻塞的高性能代码。
